The eval harness

7 metricsprint-friendly One harness for the whole course. The golden-set format, every metric with the source that establishes it, and the reporting rule. Print it and keep it beside the file that holds your numbers.

There is one harness and every module re-runs it. Module 1 builds it, module 2 moves the numbers, module 4 grows the set, modules 5 and 6 re-run it, and module 6's CI gate is a threshold on one of its scores. A course with two evaluation harnesses has none, because the reader will maintain neither. If a later page seems to want a second set, it wants a new row in this one.

1. The golden set, and what a row is

A golden set is a list of rows, and a row is a question plus the identifier of the passage that answers it. That is the entire data structure, and it lives in the repository as a small file rather than in a notebook.

Two rules decide whether it is worth having, and both are about how the questions are written.

  • Write them by hand, as a stranger would ask. Handing a passage to a model and asking for a question it answers measures whether your retriever can find a passage from words lifted out of it, which it always can. The score comes out high and means nothing. The gap between the asker's vocabulary and the author's is the thing you are actually measuring.
  • Thirty is the target and ten is enough to start. Thirty hand-written questions is about ninety minutes. It is not a statistically comfortable sample and does not need to be: a change too small to show up in thirty questions is a change too small to spend a week on.

The set only ever grows. Module 2 adds a poisoned chunk permanently, module 4 adds five unanswerable questions and three promoted production failures, and nothing is ever removed, because a set that shrinks when a question becomes inconvenient has stopped being evidence. Where it is developed: lesson 0160.

2. The seven metrics, and who says so

Adopt the vocabulary rather than the library. Metric names travel between tools and survive version bumps; a 0.x API does not.

MetricWhat it asksEstablished by
recall@k
retrieval		 The fraction of questions whose answering passage appears in the top k retrieved. The primary metric for this course, because the generator cannot use a passage that did not arrive, so a recall failure is an upper bound on everything downstream. 0160. Anthropic's contextual-retrieval write-up reports the same quantity inverted as a failure rate, "1 minus recall@20", which is the form to use when reporting an improvement.
nDCG@10
retrieval, ranked		 Discounts each hit by how far down the list it sits and normalises against the best possible ordering, so a perfect ranking scores 1. Use recall while you are fixing what arrives; add nDCG when you start changing the order. 0160, via BEIR, which reports it as the headline metric across all eighteen of its datasets. This course does not derive the formula.
Faithfulness
generation		 Whether the answer's claims are supported by the retrieved passages. The hallucination metric, and the one to add first. 0170, Ragas 0.4.x for the name.
Response relevancy
generation		 Whether the answer addresses the question rather than an adjacent one. 0170, Ragas 0.4.x.
Context precision
retrieval, in a generation framework		 Scores the retrieved set itself. Overlaps what recall@k already measures. 0170. Where it disagrees with the 0160 number, the 0160 number is the one with no model in it.
Context recall
retrieval, in a generation framework		 The same caution as context precision: a retrieval metric wearing a generation name. 0170.
Noise sensitivity
generation		 How much an irrelevant retrieved passage degrades the answer. The metric module 4's retrieval grader is built to move. 0170.
Five metrics on a dashboard is not five independent readings. Two of the five generation metrics score the retriever, so only faithfulness and response relevancy are genuinely new beside recall@k and nDCG@10. That is the honest shape and it is worth saying out loud before somebody reads a correlated pair as corroboration.

3. The judge is a component, so it has its own number

Four of the seven metrics are scored by a model, which makes the scorer part of the system under test.

The rule that governs every one of those scores: report the judge's agreement with your own hand-scoring beside every score it produces, and treat it as the confidence interval on that score. If your judge agrees with you on 17 of 20 answers, a quality move from 0.78 to 0.81 is not a result. If it agrees on 19 of 20, the same move might be. The difference is knowable and it costs one hour.

Module 6's CI gate inherits this directly: a threshold that distinguishes two scores closer together than the judge's own agreement is reporting the judge rather than the system. See lesson 0660.

The four named biases

BiasWhat it does to youThe cheap defence
PositionPresent the same two answers in the opposite order and the judge can prefer whichever came first.Swap the order and score twice; keep the result only when the two agree, and call a disagreement a tie.
VerbosityA preference for longer answers, so a prompt change that only made answers longer shows as a quality improvement.Score mean answer length as its own column, so you can see it rather than argue about it.
Self-enhancementA preference for text from the same model family, which is a live problem if you judge one vendor's answers with the same vendor's judge.Judge with a different model family than you generate with, where you can.
Limited reasoningThe judge is not better at the task than a model of its class.Fix the rubric before you see any outputs. A rubric written after reading the answers is a description of those answers.

All four are named in the MT-Bench paper's own abstract, which is the source to read because it examines the method rather than advertising it. The same paper reports GPT-4 judgments reaching over 80% agreement with human preferences on that benchmark, which the authors note is the level humans reach with each other. That is the ceiling and it is somebody else's measurement on their benchmark, so it is evidence the method can work and never a score to assume for your judge on your corpus.

4. The reporting rule

One rule, and it is what makes a number in this project evidence rather than folklore.

A number with no k, no named question set and no corpus version is not a number.

"Recall went up to 0.71" is unusable in four weeks. This is the same claim written so that somebody can reproduce or contradict it:

recall@10 = 0.71 on golden-v2, corpus handbook-v7, BM25 baseline 0.58

It identifies which of the possible systems it came from. That matters more than it sounds: lesson 0100 counts three corpus snapshots against two model ids against two eval-set versions against five prompt versions and gets sixty distinct systems, of which your dashboard is showing exactly one.

The four artefacts that must be versioned together, with how often each moves: corpus daily, prompt hourly, model id quarterly and not by you, eval set weekly and only upward.

Nothing on this sheet is a target. Every published figure quoted here - the over-80% judge agreement, BEIR's eighteen datasets, the contextual-retrieval failure rates - is somebody else's measurement on somebody else's corpus, and each is written that way on the page that develops it. Your own numbers come from your own corpus and are the only ones that can tell you whether a change worked.
