A WHERE clause spends the recall budget a second time

foundation 11 min Arithmetic and defaults quoted from pgvector at tag v0.8.6; the graph structure from the HNSW paper at v4. · pgvector v0.8.6

The one-minute version

  • Exact nearest-neighbour search is correct and does not scale. An approximate index buys latency with recall, deliberately, and you choose the exchange rate.
  • HNSW is a layered proximity graph. Its authors report logarithmic complexity scaling, and three knobs are yours: m, ef_construction and ef_search.
  • The defect nobody expects: filtering happens after the index scan. pgvector's own README works it out - a condition matching 10% of rows, at the default hnsw.ef_search of 40, leaves about four rows.
  • That reads to a user as "it does not know about our European documents", and to you as a retrieval bug with a one-line fix.
  • The fixes are hnsw.iterative_scan, a partial index, or partitioning, and each costs something different.

1. When exact search stops being an option

Exact nearest-neighbour search compares the query against every vector. It is trivially correct, and its cost is the whole index on every query. At a few thousand chunks that is fine and you should use it, because a correct baseline is worth more than a fast approximation you cannot check against.

It stops being fine somewhere in the hundreds of thousands, and where exactly depends on your dimension count, your hardware and your latency budget rather than on a rule. The important part is what you give up when you leave it: from that point on, your retrieval is approximate and its error rate is a parameter you set, and if you never set it deliberately you have taken a default somebody else chose.

2. What HNSW actually builds

Malkov and Yashunin's construction is a multi-layer set of proximity graphs over nested subsets of the data. The layer an element appears in is chosen randomly with an exponentially decaying probability, so the top layers are sparse and the bottom layer holds everything. A search starts at the top, follows edges greedily toward the query, drops a layer, and repeats. The paper's claim for this is logarithmic complexity scaling, and the separation of link lengths by scale is what buys it.

Three parameters are yours, and pgvector exposes them by those names:

m is how many links each node keeps. More links means a better-connected graph, higher recall and a larger index. ef_construction is how hard the builder works to find good links, so it costs build time and nothing at query time. hnsw.ef_search is the one that matters daily: how many candidates the search keeps in flight. It is the recall-for-latency dial, it is set per session, and its default in pgvector is 40.

3. The four-row result

Now the defect that costs a week the first time it happens, quoted from the documentation rather than paraphrased.

pgvector's README says it plainly: with approximate indexes, filtering is applied after the index is scanned. It then works the example: if a condition matches 10% of rows, with HNSW and the default hnsw.ef_search of 40, only 4 rows will match on average.

Read that against a query asking for ten results. You get four. Not four wrong ones, and not an error: four correct rows and six that silently do not exist. A user reports that the assistant does not seem to know about the European policy documents. You check, and the European policy documents are in the index. They were candidates for nothing, because they were not among the forty the graph walk happened to reach.

4. Three fixes, and what each costs

Iterative scans, added in pgvector 0.8.0, are the general answer: the index keeps scanning until enough rows are found or a cap is reached. SET hnsw.iterative_scan = strict_order preserves exact distance order; relaxed_order allows slight reordering and the README says it gives better recall. You pay in latency, variably, and the variance is the part to watch.

A partial index suits a filter over a few known values: build a separate HNSW index per value, and each query scans an index containing only matching rows, so the filter costs nothing at query time. You pay in index count and in the fact that a new value needs a new index.

Partitioning is the same idea when there are many distinct values, and you pay in schema complexity.

There is a fourth option worth naming because it is often correct: put the filter in the ranking rather than in the query. Retrieve without a filter, then drop non-matching rows and take the top ten of what remains. That works when the filter is loose and fails exactly where the problem was, which is when the filter is tight.

The four-row figure and the default ef_search of 40 are pgvector's own documentation at tag v0.8.6, describing pgvector's behaviour. Other vector stores apply filters at different points in the scan and some do it during traversal rather than after it, so the number does not transfer. What transfers is the question: ask your store where in the scan the filter is applied, and treat "after" as a recall budget you are spending twice.

Check yourself

Retrieval practice

Answer from memory before revealing.

A filtered query on pgvector asks for ten rows and returns four. What happened?
Filtering is applied after the index scan, so a 10% condition over the 40 candidates a default ef_search returns leaves about four. Too few matching rows is possible but is the case you would have noticed; the point is that thousands can match and you still get four. The m parameter changes graph connectivity and recall broadly, not this specific interaction. pgvector applies no distance cap of its own.
Your filter has three possible values and is used on every query. Which fix costs least at query time?
Three known values is exactly the shape a partial index suits: each query scans an index holding only matching rows, so the filter costs nothing during the scan. Raising ef_search scans more of the graph on every query, filter or not. Iterative scans work and add variable latency, which is why they are the general rather than the cheapest answer. Filtering after ranking still pays the same recall cost that caused the problem.

Practice about 35 minutes, with a database

Practice 1foundation

Reproduce the four-row result on your own data, then fix it and price the fix.

Index your corpus with HNSW. Add a metadata column - source directory, document type, whatever your corpus actually has - and confirm roughly what fraction of rows each value covers. Run a query with LIMIT 10 and a filter matching about a tenth of the table, and count the rows you get back.

Then SET hnsw.iterative_scan = strict_order, run the identical query, and record both the row count and the latency, before and after. Both numbers, not just the first.

Hint

Use EXPLAIN ANALYZE rather than a stopwatch, and run each query several times so you are reading a warm cache in both cases. The first execution after an index build measures the disk, not the fix.

If your table is small enough that the planner chooses a sequential scan, the trap will not reproduce, because there is no approximate index in the plan to filter after. Check the plan before concluding the documentation is wrong.

Show what the experiment should produce
  1. The row count before the fix should be near your selectivity times 40. A filter matching a tenth gives about four; a filter matching a twentieth gives about two. If you get ten, check the plan: a sequential scan has no candidate set to truncate, and you have not reproduced the condition.
  2. The latency after the fix is the number worth keeping. Iterative scanning keeps going until it has enough rows, so its cost depends on how rare the matching rows are. A filter matching one row in a hundred can cost many times the unfiltered query, and that is a p99 problem rather than a p50 one.
  3. Compare against exact search while your corpus is still small enough to allow it. Turn the index off, run the same query as a sequential scan, and you have ground truth for what the approximate index missed. That comparison is impossible later and is the only way to know your recall rather than assume it.
  4. Write the chosen ef_search into the charter with the reason. It is a parameter with a default that suits nobody in particular, and an unrecorded value is one somebody will change during an incident.
  5. Add one filtered question to your golden set. Lesson 0160 builds that set properly. A filtered question in it means this defect can never come back silently, which is the whole reason the set exists.

Sanity check. After enabling iterative scans you should get your full ten rows and a higher, more variable latency. If the row count is still four, the setting did not apply to the session you measured in; if the latency did not move at all, you are probably reading a cached plan rather than a fresh execution.

Your teacher. Ask your agent to write the query that, for one of your filter values, returns the rows the approximate index missed: the set difference between an exact sequential scan and the indexed query. Read a few of them. If any of them would have answered a question in your golden set, you have a number for what the index costs you rather than a feeling.
