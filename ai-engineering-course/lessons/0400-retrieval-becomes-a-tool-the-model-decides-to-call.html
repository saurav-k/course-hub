Module 04 · From basic to agentic RAG · Lesson 0400

Moving one decision into the model changes what you must watch

working 11 min Grounded in the two papers that established adaptive retrieval and the reason-and-act loop, read at v1 and v3. · Self-RAG

The one-minute version

  • Until now retrieval was a stage that always ran with a fixed k. Making it a tool hands the model one decision: whether to search, and with what query.
  • Self-RAG names the defect that motivates it: retrieving a fixed number of passages regardless of whether retrieval is necessary costs you on questions that needed none and starves the ones that needed two.
  • The tool description is not documentation. It is the thing the model plans against, and it is the only lever you keep over the query it writes.
  • Tools are not free before a single call is made: the tool-use system prompt has a published, per-model token cost, and your schemas sit on top of it.
  • The new number this lesson produces is searches per question, and your existing trace already nests to show it.

1. The defect that motivates it

Two modules of work went into making one retrieval good. The trouble is that it always happens, identically, whatever the question.

Self-RAG states the problem in its own abstract, and the wording is worth keeping: indiscriminately retrieving and incorporating a fixed number of passages, regardless of whether retrieval is necessary or the passages are relevant, diminishes the model's versatility and can lead to unhelpful responses. Both halves of that bite. A question your corpus cannot answer still gets ten passages of near-misses, which is worse than none because it looks like evidence. A question needing two lookups gets one.

Their fix is a model trained to retrieve on demand and to critique what came back using special tokens they call reflection tokens, generated inline so the behaviour is controllable at inference time. You are not going to train that model. What transfers is the shape: retrieval is a decision, and something has to make it. In a tool-using loop, the model makes it.

2. The loop this rides on

The loop itself belongs to module 3, which builds it. This page assumes it and changes only what the model can reach from inside it. If you have not read A tool call is the only verb an agent has, read it first: it is the page that explains that the model emits a name and a JSON object and executes nothing.

The published result under the loop is ReAct, which interleaves reasoning traces with task-specific actions rather than doing either alone. Its reported gains are on interactive benchmarks rather than on retrieval: 34% absolute improvement in success rate on ALFWorld and 10% absolute on WebShop, against imitation and reinforcement learning baselines. Those are the paper's numbers on the paper's tasks, and they are evidence that interleaving beats separating, not a prediction about your corpus.

3. The description is the lever you keep

You gave up the decision. What you keep is the tool definition, and the part of it that matters is the sentence a reader would skim past.

The model plans against the description. A tool described as "searches the knowledge base" invites the model to paste the user's question in verbatim, which is exactly the paraphrase failure lesson 0160 measured. A tool described as "searches internal policy documents by topic; queries work best as a noun phrase naming the policy area, not as a full question" changes the queries you get. That is prompt engineering, but it is prompt engineering aimed at the one string you can still control.

It is also not free. Anthropic publishes the token cost of the tool-use system prompt per model, before any schema of yours is added.

4. The number this produces

You have given the model a decision, so you now owe yourself a way to see it. Your trace from lesson 0150 already does this without change: an Execute tool span wraps each call and the Retrievals span nests inside it, so one question's trace shows how many searches it cost and what each returned.

Searches per question is the metric this lesson adds, and it is worth watching as a distribution rather than a mean. A mean of 1.4 hides the shape that matters: a long tail of questions where the model searched five times and still answered badly is a different problem from a body of questions where it searched none and should have.

Check yourself

Retrieval practice

Answer from memory before revealing.

What does Self-RAG's abstract name as the defect in always retrieving a fixed number of passages?
The paper's wording is that retrieving indiscriminately, regardless of whether retrieval is necessary or the passages are relevant, diminishes versatility. Ordering is lesson 0240's problem and is not what this paper raises. Index growth is an operational cost unrelated to the claim. Window size is a real constraint and also not the defect named here.
You mount one retrieval tool and the model never calls it on a given question. What do you pay?
The tool-use system prompt is added whenever tools are present, at a published per-model cost, and your schema sits on top of it, so every request pays whether or not a call happens. Paying nothing assumes the cost is per call, which is the intuition this section exists to correct. The schema and the system prompt are both added, not one or the other. No retrieval ran, so the store charges nothing.

Practice about 40 minutes, with a terminal

Practice 1working

Turn your retriever into a tool, and measure what the model does with the decision you just handed it.

Expose the retriever with a written description and a schema whose arguments constrain the query. Run your thirty-question golden set through the loop and record, per question, how many searches happened and what query text the model wrote for each.

Then rewrite the tool description once, deliberately, to steer the query shape, and re-run. Report recall at 10 and searches per question before and after, and the token cost per question for both.

Hint

The query text is already recorded if you followed lesson 0150: it is gen_ai.retrieval.query.text on the retrieval span, which is one of the two Opt-In attributes. If you did not turn it on then, turn it on now, because this exercise is unreadable without it.

Compare against the fixed pipeline rather than against nothing. You have a baseline from module 1 and it is the only thing that can tell you whether the loop helped.

Show what the comparison should tell you
  1. Read the queries the model wrote before you read any score. They are the most informative output of this exercise. A model that pastes the user's question in verbatim has been given a description that told it nothing, and the fix is one sentence rather than a different model.
  2. Expect the mean searches per question to sit near one, and ignore the mean. The interesting mass is the tail: the questions with three or more searches are the ones the fixed pipeline was silently failing, and the questions with zero are where the model decided it already knew, which is the case you must check by hand because it is where confident wrong answers come from.
  3. Recall may not move, and that is a real result. Adaptive retrieval helps most on questions needing more than one lookup. If your golden set has few of those, this module buys you little and you have learned something worth writing in the charter rather than a technique to keep.
  4. The cost will roughly double on multi-search questions. Record it now, because module 6's cost work is measured against exactly this number and lesson 0450 shows what happens when the loop is allowed to run long.
  5. Keep the description in the versioned prompt record from lesson 0250. It is a prompt in every sense that matters: it changes model behaviour, it has no test of its own, and somebody will edit it on a Tuesday.

Sanity check. Searches per question should never be zero for every question in a corpus-grounded system: if it is, the model is answering from parametric memory and your tool description or your system prompt is failing to make retrieval attractive. Equally, if it is above three for most questions, the description is too vague and the model is groping. Both extremes are description defects rather than model defects.

Your teacher. Give your agent the ten worst queries the model wrote and the passages that actually answer those questions, and ask it to write a tool description that would have produced better queries. Then run its description against your golden set. If it beats yours, you have learned what your description was failing to say; if it does not, you have a measured reason to keep yours.

Primary source to go deeper

The paper that framed retrieval as a decision the model makes rather than a stage that always runs: Self-RAG: Learning to Retrieve, Generate, and Critique through Self-Reflection, Asai et al., at v1. Read its abstract's description of what indiscriminate retrieval costs. The loop underneath is ReAct: Synergizing Reasoning and Acting in Language Models, Yao et al., at v3. For the tool-call mechanics this page assumes, Reading a tool-call trace in AI Software Developer is the hands-on treatment.
