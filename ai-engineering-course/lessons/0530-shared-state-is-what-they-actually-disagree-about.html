Module 05 · Multi-agent systems · Lesson 0530

Two agents share exactly what you made them share

working 8 min The failure modes named here are observed rather than imagined: they come from a study of over 1,600 annotated traces across seven frameworks, arXiv 2503.13657v3. · Why Do Multi-Agent LLM Systems Fail?

The one-minute version

  • There are three ways one agent's work reaches another: in the message list, in a shared state key, or through an external store neither of them owns.
  • They differ in cost, in who can see them, and in what a process restart does to each. Only the third survives everything.
  • Two of the failure modes catalogued across 1,600 traces are shared-state design errors rather than model errors: losing conversation history, and one agent withholding what another needed.
  • The question that decides the design is not "where can I put this" but "what happens to this when the process dies".
  • And the one nobody asks until it bites: two agents writing the same key at the same time.

1. Three mechanisms, in the order people reach for them

The message list is the default and the one lesson 0510 already priced. The worker's output comes back as a tool result and sits in the orchestrator's conversation, where every subsequent turn re-sends it. It is visible to the model, expensive per turn, and gone when the conversation ends.

A shared state key is the first deliberate choice. Google's ADK, read at 2.8.0, exposes this as output_key on an agent: the source states plainly that it names "the key in session state to store the output of the agent", and gives its purpose as to "connect agents to coordinate with each other". The value is written once and read by name, so it is not re-sent on every turn - and the model does not see it unless you put it in a prompt.

An external store is the third, and it is the one lesson 0340 already taught you: LangGraph at 1.2.x splits exactly here, with a checkpointer persisting "a thread's graph state as checkpoints" for short-term, thread-scoped memory, and a store persisting "application-defined data outside the graph state" for long-term, cross-thread memory.

A2A adds a fourth identifier worth knowing when the peer is not yours: a Task carries a context_id, which groups related tasks and messages into one collection. It is not a store - it is the key you would store things under, across a boundary you do not control.

2. The question that decides it

Ask what a restart does. Not a crash - an ordinary deploy, which happens far more often than a stall.

The message list dies with the request. Shared session state dies with the process unless you backed it with a database, and the trap here is that the in-memory version passes every test you will write. An external store survives, which is why it is the only place a value belongs if a second process, a retry or a human will ever need it.

The cost runs the other way, which is why this is a trade rather than an answer. Over a run of several handoffs the message list grows with everything anyone said, while a state key costs one write and one read, and an external store costs a round trip.

3. Two observed failures, and both are yours

Cemri et al. built a taxonomy of multi-agent failures from over 1,600 annotated traces across seven frameworks, developing it on 150 traces with expert annotators and reporting an inter-annotator agreement of 0.88. Fourteen modes, in three categories.

Two of the fourteen are shared-state design errors, and naming them that way is the point. One is the loss of conversation history: context is truncated unexpectedly and agents proceed without what they had. The other is information withholding, where an agent fails to pass on something another agent needed.

Neither is a model failing to reason. Losing history is a mechanism whose lifetime was shorter than the task; withholding is a route that was never built. Both are fixed in your code, and both look like "the model got confused" in a transcript, which is why the trace lesson comes next.

4. The write nobody sequenced

One more question, and it only appears once you have parallel workers. What happens when two of them write the same key?

If your shared state is a dictionary, the answer is that the last writer wins and nothing records that the first one existed. If two workers were each asked to enrich the supplier list and both write supplier_list, you keep one enrichment and lose the other, with no error and a plausible-looking result.

Three fixes, in increasing cost. Key by writer, so supplier_list.a and supplier_list.b both survive and the orchestrator merges them. Append rather than set, so the state holds a list and order is the only thing at risk. Or serialise the writes, which removes the parallelism you paid for and is usually the wrong answer to a problem the first two solve.

The fourteen failure modes and the agreement figure are Cemri et al.'s own results on their own annotated corpus, and this page paraphrases the two it uses rather than reproducing the taxonomy, which is published under a licence that does not permit redistribution here. The token curve in section 2 is this course's arithmetic over lesson 0310's stated assumptions. The framework behaviours are read at google-adk 2.8.0 and LangGraph 1.2.x, and they are evidence that the three-way split is real rather than the subject of the lesson.

Check yourself

Retrieval practice

Answer from memory before revealing.

A value must still be available after a deploy restarts the process mid-request. Which route guarantees it?
Only a store outside the process survives the process. The message list dies with the conversation and is the most expensive of the three per turn. An in-memory state key is the trap: it passes every test and vanishes on the deploy. A worker's own context is the shortest-lived of all, ending with its turn.
Two parallel workers both write the key supplier_list. What does a plain dictionary do?
Last write wins and the first value is gone with no record, which is why the result looks plausible and is half of what you paid for. Nothing raises: a dictionary has no notion of conflict. Merging and keeping both are the two fixes from section 4, and you have to build them - key by writer, or append to a list.

Practice about 40 minutes, with your capstone

Practice 1working

Break the sharing on purpose, then choose a lifetime deliberately.

Run two workers in parallel writing one key. If your capstone has only one worker, run the same one twice with different arguments. Observe what is in the state afterwards, and confirm that nothing anywhere reported a problem.

Then restart the process mid-request - kill it after the first worker writes and before the second reads - and retry. Record which of your three routes still had the value.

Then choose, and write it down. For each value that crosses between agents in your capstone, record its route and its lifetime in docs/decision-multi-agent.md: message list, state key, or store, and why. One line each.

Hint

You do not need real parallelism to see the conflict. Two sequential writes to the same key with no read in between demonstrate the same lost update, and are easier to trigger reliably.

The restart is the part people skip because it feels like infrastructure. It takes one kill and it is the only way to tell an in-memory store from a durable one, since both behave identically until then.

Show what a good state table looks like
  1. Most values belong in the message list, and that is fine. A worker's short answer that the orchestrator immediately uses does not need durability. The table exists so that the two or three values that do need it are visible rather than assumed.
  2. The expensive value is the one to move first. Whatever cost the most tokens to produce - a comparison over twenty documents, a full supplier list - is the one whose recomputation after a restart you will notice on the bill.
  3. Keying by writer is almost always the right first fix. It costs one string change, keeps both results, and turns a silent lost update into an explicit merge the orchestrator performs and you can read in the ledger from lesson 0520.
  4. Write the lifetime, not the technology. "Durable for the request" and "durable for the tenant" are decisions; "Postgres" is an implementation of one of them, and recording the technology instead is how the next person changes it without knowing what they broke.

Sanity check. If every value in your table is in the store, you have made every handoff pay a round trip for values that were never going to outlive the request. If every value is in the message list, your first restart mid-request will recompute the whole thing - which is exactly the run you just did.

Your teacher. Give your assistant the list of values that cross between your agents and ask it, for each one, what would happen if the value were missing when the next agent read it: recompute, wrong answer, or crash. The ones where the answer is "wrong answer" are the dangerous ones, because those are the runs that finish and look fine, and they are where the two observed failure modes in section 3 actually live.
