Module 04 · From basic to agentic RAG · Lesson 0440

A mounted server changes what reaches the window

working 12 min Schema, annotation defaults and trace propagation read in the Model Context Protocol at revision 2026-07-28; span attributes at convention commit fee465db, marked Development. · The protocol itself

The one-minute version

  • This page is the host side and nothing else. The protocol is taught next door and writing a server is taught beside it; both are linked and neither is repeated here.
  • Mounting a server makes its index another retrieval source the model may choose, so top-k is no longer the only thing deciding what reaches the window.
  • A host reads three things before trusting a tool: the input schema, the optional output schema, and the annotations. The annotation defaults are the trap: unset means destructive and open-world.
  • The specification says plainly that a client should never make tool-use decisions from annotations sent by an untrusted server, which turns module 2's untrusted-document problem into an architecture problem.
  • Trace context crosses the boundary through _meta, so one trace id can span your app, a server you do not run, and the model call that used its output.

1. What this page is, and is not

The Model Context Protocol is taught elsewhere in this hub and taught well, so it is not taught again here. MCP in one page covers the three roles, the server primitives, one exchange on the wire and the two transports, and it is written against revision 2026-07-28. Write your first MCP server walks through building one in two languages. Read the first before this page if the protocol is new to you.

What none of those pages takes is the framing this one needs: your retrieval system as a host that mounts servers other people run. That is where agentic RAG actually meets the protocol, and it is a different set of questions from writing a server.

2. What changes when the source is not yours

Two modules of retrieval work assumed one thing: you chose what was in the index. Every lever, from chunking to fusion to reranking, was a lever over your own corpus.

A mounted server breaks that assumption in a specific way. You do not choose its chunking, you do not see its scores, and its top_k is its own. What you get is a tool the model may call, whose results arrive as text in the same window as yours. So the question "why was this answer wrong" acquires a new branch that lesson 0120's taxonomy did not have: the passage came from a source whose retrieval you cannot inspect.

The practical consequence is a recording rule. Tag every retrieved passage with the source that produced it, and put the tag on the span, because from the answer alone a passage from your handbook and a passage from somebody's ticketing system are indistinguishable.

3. The three things a host reads, and the defaults that bite

Before your host lets the model call a tool, three parts of that tool's definition are worth reading, and all three are in the specification's schema at revision 2026-07-28.

The input schema is required and is JSON Schema 2020-12, with an object at the root. It is the same object lesson 0210 built with Pydantic, arriving over a wire instead of from your own code. The output schema is optional, and when a server declares one its results come back as structured content conforming to it, which is what lets you validate a third party's output at your boundary rather than trusting prose.

The third is tool annotations, and this is the part to internalise, because the defaults are the opposite of reassuring:

That last point is the specification's own, and it is worth quoting because it settles the design: clients should never make tool use decisions based on tool annotations received from untrusted servers.

Read that beside module 2's lesson 0280, "The document you retrieved is untrusted input". That page is about text arriving inside a prompt you wrote. This is the same problem one level up: the untrusted thing is now a capability, and it arrives with its own self-description that you are told not to believe. What is left is what you can verify yourself: who runs the server, what network it can reach, what credentials your client holds, and what your host will refuse regardless of what the annotations claim. Module 6's lesson 0650 owns the containment side of that.

4. The trace crosses the boundary

The good news arrives from the same revision. MCP documents OpenTelemetry context propagation through the _meta keys traceparent, tracestate and baggage.

So the trace id that lesson 0150 started on your own request travels into a server you do not run, and comes back. One trace can span your application, a third party's process and the model call that used its output, which is the furthest the observability thread of this course reaches.

Alongside it the conventions define mcp.method.name, mcp.protocol.version, mcp.request.id and mcp.session.id, plus client and server operation-duration metrics, so a slow answer can be attributed to the mounted server rather than guessed at.

Two version facts have to travel together here, and they currently disagree. The MCP semantic conventions are Status: Development, in a repository with no releases and no tags, and their own examples still show an initialize method and an mcp.session.id attribute. MCP revision 2026-07-28 removed both: the initialize handshake is gone and protocol-level sessions were removed with it. Instrument the shape rather than the spelling, and record the protocol revision you are speaking beside the convention commit you are instrumenting to, because a page that names only one of the two cannot be checked later.

Check yourself

Retrieval practice

Answer from memory before revealing.

A mounted server's tool sets no annotations at all. What has it declared to your host?
In the schema at revision 2026-07-28, destructiveHint and openWorldHint both default to true, so omitting them is a claim that the tool may destroy things and may reach anything. The reassuring reading is the intuitive one and is exactly backwards. There is no follow-up query for annotations; the defaults apply. Your own tools take the same defaults, which is a reason to set them explicitly rather than a reason to relax.
Why does the specification say not to make tool-use decisions from an untrusted server's annotations?
Annotations are self-description with nothing behind them, so a server that wants to be called can declare itself read-only and harmless. Being optional is true and is a separate problem, handled by the defaults. They are carried on every transport. They describe the tool, which is exactly why an untrusted server's version of that description is worthless.

Practice about 45 minutes, with a terminal

Practice 1working

Mount one server you did not write, and find out whether it helped.

Pick any MCP server that can answer questions in your domain and mount it beside your own retriever. Before running anything, read its tool definitions: record for each tool whether it declares an output schema, and what its four annotations say or leave unset.

Then run your golden set twice, once with it mounted and once without, and report recall at 10, the share of questions where the model chose the mounted tool, and the added latency. Tag every result with its source on the span so you can tell later which passages came from where.

Hint

Drive the server by hand before your host touches it, exactly as the sibling course's server lesson does in reverse. Call tools/list and read the raw JSON: the annotations and the output schema are right there, and reading them is faster than reading whatever documentation the server ships.

If the model never chooses the mounted tool, the problem is almost certainly its description rather than its results, which is lesson 0400's finding arriving again on somebody else's text that you cannot edit.

Show what the two runs tell you
  1. Most third-party tools you inspect will set no annotations. That is the normal state of the ecosystem and it means your host is being told the tool may be destructive and open-world. Since you cannot fix their declaration, the response is to bound what your host will let it do, which is the fourth row of the scorecard.
  2. Recall may fall. A second source adds candidates that compete for room in the window, and if its results are less relevant than yours, the answer gets worse while the system looks more capable. This is the measurement that stops a demo from becoming an architecture.
  3. Watch the latency tail rather than the mean. You have added a network dependency you do not operate to the request path, so its p99 is now inside yours, and module 6's lesson 0610 is about exactly that shape of dependency.
  4. The source tag is the row you will regret omitting. Without it, a wrong answer six weeks from now is unattributable between two indexes, and lesson 0430's triage has a bucket it cannot assign.
  5. Write the decision down with its number. "Mounted, recall 0.71 to 0.68, unmounted again" is a result worth keeping, and it stops the same server being proposed again next quarter.

Sanity check. If mounting changed nothing at all - same recall, same answers, the tool never chosen - check that the tool is actually reaching the model by looking for its definition in the request rather than assuming the mount succeeded. A server that is configured but not advertised is the quiet failure here, and it looks identical to a server that is simply not useful.

Your teacher. Give your agent the raw tools/list output from the server you mounted and ask it, for each tool, what the annotations claim and what your host would be permitting if it believed them. Then ask what it would allow that tool to do if it assumed the annotations were written by somebody who wanted to be called. The gap between those two answers is the bound you should be enforcing.
