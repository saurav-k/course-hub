Non-determinism decides which tier a test belongs in, not whether you write one

working 10 min Fixture mechanics read from the pytest documentation at version 9.1.1, and the third tier is the golden set lesson 0160 built rather than a second harness. · pytest monkeypatch

The one-minute version

  • “You cannot test it, the output changes every time” is a claim about one function call, and your system is not one function call.
  • Tier 1 is deterministic and covers everything around the model: parsing, routing, chunking, retrieval order, the packing of the prompt. It is most of your code.
  • Tier 2 is the contract: every call you make to something you do not own, replayed from a response you recorded once. It runs with the network refused.
  • Tier 3 is behavioural: the golden set from module 1, scored, against a threshold. It costs money and minutes, so it runs on a schedule rather than on every push.
  • The line-coverage number on this repository says nothing about whether the answers are right, and a reviewer who asks for it is asking the wrong question.

1. Non-determinism sorts your assertions, it does not excuse them

The sentence that stops most teams testing an AI system is that the output is different every time, so there is nothing to assert. It is true of exactly one thing: the text a model returns for a given prompt. Everything else in the repository is as deterministic as it ever was.

So the question is never whether an assertion is possible, but which tier it belongs in, and the tiers are separated by what each one needs in order to run. Tier 1 needs nothing. Tier 2 needs a file. Tier 3 needs a provider, a budget and several minutes. That ordering is also how often each should run, and the cheapest tier catches the most defects because it covers the most code.

LinkedIn's engineering team wrote up the failure that makes this concrete. Their model had to emit parameters for internal API calls and “~10% of the time the LLM would make mistakes and often output data that was invalid”, and the fix that took that to about 0.01% was a defensive parser rather than a better prompt. A parser is tier 1. The most expensive defect in their published account was caught, and could only have been caught, by the cheapest kind of test in this lesson - and that is their measurement of their own product, not a rate to expect on yours.

2. Tier 1: everything around the model

Write these exactly as you would write tests for any service, because that is what they are. The list is longer than people expect once they go looking.

A chunker is a pure function of a document and a size, so it takes a table of cases. Retrieval order is deterministic given an index and a query vector, so a ranking is an assertion about a list. The prompt your code packs is a string built from a template and some passages, so you can assert that a passage with no source id never reaches it. A router that picks a workspace or a tool is a classifier over a fixed set, so its refusal path is testable. And every parse of anything the model emitted is tier 1, which is where the LinkedIn defect lived.

None of it needs a model, a key or a network, and the whole tier should return in the seconds any unit suite takes.

3. Tier 2: record the call once, then never make it

Tier 2 asserts the shape of the exchange with everything you do not own: the provider, the vector store, any mounted tool server. You call the real thing once, by hand, save what came back, and every test after that replays the file.

What it catches survives tier 1 and never shows up in tier 3: a renamed field, a changed response shape, a tool schema and a handler that disagree about a key. None is a quality problem and all are outages.

The mechanism is ordinary. The pytest documentation names the case directly - a test that “invokes code which cannot be easily tested such as network access” - and its monkeypatch fixture substitutes the transport for the duration of one test, with the guarantee that “all modifications will be undone after the requesting test function or fixture has finished”.

One rule makes the tier honest: refuse the network for the whole suite rather than stubbing per test. An autouse fixture that raises on any real send turns a forgotten stub from a quiet slow test that costs money into a loud failure with a stack trace.

4. Tier 3: the golden set, with a threshold, on a schedule

Tier 3 is the only tier that touches the thing that changes, and it is the tier this course has been building since module 1. It runs the golden set from lesson 0160, scores it the way lesson 0170 established, and compares the score against a threshold rather than against a fixed string. There is no second harness: lesson 0660 already wired this one into a gate.

What is new in this lesson is the cadence, and the cadence is an arithmetic problem. Take a thirty-question golden set, one request each at about 9,000 input and 700 output tokens, on Claude Sonnet 5 at its published list price of $2 and $10 per million. That is $0.018 plus $0.007, so $0.025 a question and $0.75 a run, and the judge lesson 0170 introduced adds roughly $0.005 a question on top, for about $0.90 a run.

Tiers 1 and 2 return in seconds and belong on every push. Tier 3 belongs on a schedule, plus on demand for any change that touches a prompt, a chunker or a retrieval parameter, and that split is the whole hands-on act of this lesson.

5. What a reviewer looks for, and the number that means nothing here

A stranger reading your repository looks for three things, in this order: whether the suite runs at all from a clean clone, whether anything in it reaches the network, and whether any assertion is about the quality of an answer rather than about the plumbing. A suite that passes the first two and has nothing in tier 3 is a well-tested pipeline attached to an unmeasured product.

What they should not ask for is line coverage, and it is worth being able to say why in one sentence. Coverage measures which lines ran, and the defect you are afraid of is a system whose lines all ran and whose answer was wrong. A retrieval service can reach high coverage with no tier 3 tests at all, which makes the number an accurate measurement of something nobody is worried about. Report the three tiers and their cadences instead.

Tier 3 is the tier that can turn green because it stopped testing. A judge whose prompt drifted, a golden set whose corpus version moved, an eval that silently skipped twenty of its thirty questions - each produces a passing run. Assert the count as well as the score: a run that scored well on nine questions is a failure, not a pass, and it is the one failure mode this tier has that the other two do not.

Check yourself

Retrieval practice

Answer from memory before revealing.

Your chunker splits a document into passages of a fixed size. Which tier does a test of it belong in?
A chunker is deterministic given a document and a size, so it is an ordinary unit test with a table of cases. Tier 2 exists for calls to things you do not own, and you own the chunker. Chunk size does move the tier 3 score, but that makes it a parameter worth sweeping rather than the place its correctness is asserted. And that the best size is a judgement does not make the boundary behaviour untestable.
Why does the suite refuse the network for every test rather than stubbing the provider test by test?
A per-test stub that somebody forgets produces a test that passes, runs slowly and costs money, and nothing about the result says so. Refusing globally converts that into a stack trace. Recorded replies are still needed - the refusal is what protects them. Tier 3 deliberately does reach the provider and is marked to bypass the refusal. And monkeypatch is one documented way to substitute a transport rather than the only one.

Practice about 40 minutes, in your repository

Practice 1working

Write one test in each tier, then split the cadence. This is module 8's first increment to the capstone and it is what makes lesson 0810's clean clone worth anything.

Tier 1. Pick the least glamorous deterministic function you have - the chunker, the packer, the parser of a tool call - and write a table of cases including one empty input and one input that is one byte over a boundary.

Tier 2. Call your provider once by hand, save the whole reply to tests/recorded/, and write a test that replays it and asserts what your handler does with it. Then add the autouse fixture that refuses the network and watch which of your existing tests turn red.

Tier 3. Run the golden set from lesson 0160 once, record the score, and put a threshold slightly below it. Then make the pipeline run tiers 1 and 2 on every push and tier 3 nightly, and price the cadence you chose.

Hint

The tests that turn red when you refuse the network are the finding, not the chore. Each one was reaching a real service, which means each one was slower, flakier and more expensive than its author believed.

Set the tier 3 threshold from the run you just did rather than from an ambition. A threshold above your current score is a gate that is red on the day you install it, and a red gate gets disabled within a week.

Show what the three tests look like when they are done
  1. Tier 1 asserts a value. Twelve cases over the chunker, running in about 40 milliseconds, and two of them fail on the first run: the empty document returns one empty chunk rather than none, and a passage exactly at the boundary is duplicated across two chunks. Both are real defects and neither needed a model to find.
  2. Tier 2 asserts a shape. One recorded reply, one test, and it fails immediately because the handler reads arguments while the recorded payload carries input. That is the defect this tier exists for: it never appears in tier 1, because tier 1 tested your own invented stub, and it never appears in tier 3, because a broken tool call reads as a slightly worse score.
  3. Tier 3 asserts a threshold and a count. Recall at ten came out at 0.68 on the thirty questions, so the gate is set at 0.64 and the run also asserts that thirty questions were scored. Without the count, a set that silently loads twenty rows passes with a better number.
  4. The cadence is written down beside the gate. Tiers 1 and 2 on every push, about nine seconds. Tier 3 nightly, about six minutes and $0.90 a run, which is $27 a month at the arithmetic in section 4. Both numbers go in the README that lesson 0810 is about.

Sanity check. If tier 1 found no defects at all, the cases are too kind: add an empty input, a one-byte-over-the-boundary input and a duplicate. If tier 2 passed first time, check that the refusal fixture is actually installed - a contract test that passes against a live provider is a contract test that proved nothing about the recording.

Your teacher. If the tier boundaries still feel arbitrary, ask your agent to list every function in your repository and sort them into the three tiers, then to say which sort it was unsure about and why. The uncertain ones are usually places where your own code and a call you do not own are tangled in one function, and splitting that function is the real finding. If you cannot bring yourself to drop the coverage number, ask it to write the sentence you would say to a reviewer who asks for it.

Primary source to go deeper

The fixture that makes tier 2 possible, its nine helper methods and the guarantee that every modification is undone after the test: monkeypatch in the pytest documentation, read against version 9.1.1. Read the warning about patching the wrong name beside your own transport, because patching where a symbol was defined rather than where it is looked up is the way a refused network quietly permits a call.
