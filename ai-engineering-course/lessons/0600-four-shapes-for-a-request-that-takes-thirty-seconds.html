Nobody waits thirty seconds for a page that is still thinking

working 10 min Framed against FastAPI's own account of what it does with def and async def, read at 0.141.x, and the Message Batches API limits as Anthropic publishes them. · Concurrency and async / await

The one-minute version

  • Everything that makes an AI service different from an ordinary one falls out of a single fact: a model call is a slow, expensive, non-idempotent call to a machine you do not own.
  • There are four request shapes and no fifth: synchronous, streamed, queued with a handle, and offline batch. Every endpoint you have is one of them, whether or not you chose.
  • The question that picks the shape is not technical. It is does the caller wait, and does the answer have to be fresh.
  • Your demo is synchronous everywhere because that is the default, and the default is wrong for at least one endpoint you already have.
  • Anthropic prices the batch shape at 50% of standard, so the shape is not only an availability decision.

1. The request that does not fit the shape you have

Your service works. You call it, it thinks for a while, and it returns an answer you are pleased with. Then a second person calls it while you are still waiting, and a third one gives up after fifteen seconds and clicks the button again, and now there are two of the same expensive request in flight and one of them will be thrown away.

Nothing in that paragraph is about model quality, and none of it happens to a service that returns in eighty milliseconds. It happens because a model call has four properties an ordinary database read does not have, and every one of them breaks an assumption the default request shape is built on. It is slow, in seconds rather than milliseconds. It is incremental, because tokens arrive one at a time and the first one is available long before the last. It is expensive, so a request you throw away costs real money rather than a little CPU. And it is non-idempotent: the retry your client library performs for you does not return the earlier answer, it pays for a second one.

Those four properties are the whole of this module's premise, so it is worth being precise about which one hurts where. Slow decides whether the caller can hold a connection. Incremental decides whether they have to. Expensive decides what a duplicate costs. Non-idempotent decides whether a retry is safe, and it is the one people discover last.

2. The four shapes, and the question that picks one

Synchronous is what you already have. The caller opens a connection, you generate, you reply. It is correct whenever generation is genuinely short and the caller genuinely cannot proceed without the whole answer, and it is the wrong default for everything else because it makes the caller's patience your capacity limit.

Streamed holds the same connection and changes what the caller experiences, because the first token can be on their screen a second in while the last is twenty seconds away. Nothing about the total work changes. This is the one shape that improves a number you cannot improve any other way, and lesson 0620 is about that number.

Queued with a handle is the shape people skip. The caller posts the work, you return an identifier immediately, and the work happens without anybody holding a socket. It costs you a job store and a way to report progress, and it buys the only thing that actually survives a slow provider: your service stops being slow when the model is.

Offline batch is the shape where no caller exists. You accumulate work and submit it as a block. Anthropic's Message Batches API charges 50% of standard prices for exactly this, caps a batch at 100,000 requests or 256 MB, expires anything unfinished after 24 hours, and keeps results downloadable for 29 days. Those are the vendor's published limits, not a measurement, and they are the shape of the promise: cheaper, bounded, and no use at all to somebody waiting.

The question that picks the shape is two words long. Does the caller wait? If no, you are in the bottom two rows and the only remaining question is whether the answer has to be fresh. If yes, the second question is whether a partial answer is worth anything, and if it is, you stream.

3. What the caller actually holds open

The arithmetic is worth doing once, on assumptions you can replace with your own. Take a request that generates 600 output tokens, a model that produces about 25 tokens a second, and a time to first token of about 1.2 seconds. Generation is then 600 / 25 = 24 seconds, and the whole request is about 25.2 seconds.

Under the synchronous shape the caller holds a connection for all 25.2 of those seconds and sees nothing until the end. Streamed, the same 25.2 seconds of work produce something readable at 1.2 seconds. Queued, the caller's own request is a write to a job store and returns in well under a second; the 25.2 seconds still happen, on your side, where a timeout is yours to set. Those three numbers are this page's arithmetic over the three assumptions above, and every one of them moves if your model or your output length differs.

4. The one thing FastAPI will do behind your back

There is a specific way to build the queued shape and lose all of its benefit, and it is common enough to be worth naming. FastAPI documents that a path operation declared with plain def "is run in an external threadpool that is then awaited", while one declared async def is awaited directly on the event loop. That is the whole rule, and the consequence is that a blocking call - a synchronous provider SDK, a synchronous database driver - inside an async def handler blocks the loop and therefore every other request in the process, including the cheap poll that was supposed to be fast.

So the shape is not only about your route table. An endpoint that returns a job handle in one line still stalls the whole worker if that one line is a blocking write on the event loop. Declare the handler def and let the framework give it a thread, or use a client that genuinely awaits. Both are correct; mixing them is what is not.

This is a service-design concern rather than an AI one, and Backend Engineering, Concurrency is how a server waits is where the general mechanism lives.

The batch limits on this page - 50% of standard pricing, 100,000 requests or 256 MB, a 24-hour expiry and 29 days of result retention - are Anthropic's published product limits for its own API, read at the documentation linked below. They are not a measurement, they are not a benchmark, and they are not a claim about any other provider. Gemini's batch behaviour is documented separately and differs; check it rather than assuming this transfers.

Check yourself

Retrieval practice

Answer from memory before revealing.

A user reloads your page after fifteen seconds because nothing has appeared. Which property of a model call makes that reload expensive rather than merely untidy?
Non-idempotence is what turns the reload into a second paid generation rather than a second read of the same answer. Slowness is why they reloaded, which is the cause and not the cost. Incremental arrival is the property streaming exploits, and it would have prevented the reload rather than made it cheap. That the provider is external matters for outages, covered in 0610, and not for this.
Your nightly job re-summarises every document that changed. Which shape does the two-question test in section 2 select, and on which answer?
The first question is whether a caller is waiting, and for a nightly job nobody is, which reaches the batch leaf directly and at half the price on the published rates. Streaming is about a waiting reader, and there is none. Synchronous is what the job probably is today and it is the shape being replaced. Queued is the right answer only when a caller does come back for the result on a human timescale, which the second question is there to separate.

Practice about 45 minutes, in your own repository

Practice 1working

This is module 6's first increment to the capstone, and it is a sorting exercise before it is a coding one.

List every endpoint your application exposes that ends in a model call. Most readers find between three and six: an ask endpoint, an ingest or re-index endpoint, something that summarises, and at least one thing a scheduled job calls.

For each one, answer the two questions from section 2 in writing - does a caller wait, and is a partial answer worth anything - and write down the shape that falls out. Then compare that list with what your code does today. The gap is the exercise.

Then implement the two that differ most: convert your main ask endpoint to a streamed response, and convert one endpoint that no caller waits on into a queued job that returns an identifier.

Hint

The job store does not have to be a queue broker. A table with an id, a status, a result and a created timestamp is enough to prove the shape, and swapping it for a real broker later changes no caller.

If every endpoint you have comes out synchronous, you have probably answered "does a caller wait" for the HTTP client rather than for a person. A scheduled job is an HTTP client that is not waiting for anything.

Show what a finished sort looks like
  1. The ask endpoint is streamed, not synchronous. A caller waits and a partial answer is worth a great deal, because reading starts at the first token. This is the single change on this page that a user notices, and it changes no cost.
  2. Re-indexing is queued. A caller triggers it and then does something else, so it returns an id and a status. Making this synchronous is what causes the ten-minute request that a load balancer eventually kills, and the kill leaves the index half written.
  3. The nightly summary is batch. Nobody is waiting and freshness is measured in a day, so it takes the published half price. This is the one endpoint whose shape is a cost decision rather than an availability decision.
  4. One endpoint stays synchronous, and you should be able to name it. Usually something short and cheap - a classification, a routing decision - where the caller genuinely cannot continue and generation is under a second. If nothing on your list qualifies, that is a finding rather than a mistake.
  5. Write the four-row table into the repository. Endpoint, shape, and the sentence that justified it. Lesson 0610 sets timeouts per shape and lesson 0620 sets a latency budget per shape, and both start from this table.

Sanity check. If your streamed endpoint's total time went down, you measured wrong: streaming moves when value arrives and does not reduce the work. Time to first token should fall by roughly the generation time, and total time should be unchanged within noise. If total time rose slightly, that is the streaming overhead and it is expected.

Your teacher. If the four shapes still feel like three, ask your agent for a real endpoint in your own code and have it argue both sides of "does the caller wait" for that specific route, naming who the caller is in each argument. If the FastAPI rule in section 4 felt abstract, ask it to write the two-line handler that blocks the event loop and the corrected version beside it, and to say which one your current code resembles.
