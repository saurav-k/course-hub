Module 03 · Agents and agentic systems · Lesson 0300

Most of what you build is a workflow, and you should know which one

working 9 min The taxonomy on this page is Anthropic's operational definition of its own patterns, quoted from its engineering write-up rather than paraphrased. · Building effective agents

The one-minute version

  • A workflow orchestrates a model through code paths you wrote. An agent lets the model direct its own process. Those are two different products, not two settings.
  • There are five workflow shapes worth naming, and the pipeline you built in module 2 is already one of them.
  • The sixth shape is the agent, and its distinguishing property is not intelligence: it is that nobody knows how many model calls this request will take.
  • That is the whole bill. Every other cost in this module is a consequence of it.
  • Before you loop, score the feature against five questions. Most features fail, and the correct outcome is a workflow with a name.

1. Two words that are usually used as one

Anthropic's engineering write-up draws the line in two sentences, and they are worth quoting rather than summarising because almost every other use of these words is looser. Workflows are "systems where LLMs and tools are orchestrated through predefined code paths". Agents are "systems where LLMs dynamically direct their own processes and tool usage, maintaining control over how they accomplish tasks".

The distinction is about who owns the control flow, and nothing else. It is not about how many tools there are, how good the model is, or whether the word appears in your pitch. A service that calls one model four times in a fixed order is a workflow. A service that calls one model an unknown number of times, in an order the model picks, is an agent, even with a single tool.

Your module 2 pipeline is a workflow, and specifically it is the first shape below. That is not a criticism. It is the reason it is cheap, testable and traceable, and every one of those properties is something the sixth shape spends.

2. Five shapes, each an answer to a different question

Prompt chaining decomposes a task into fixed steps, each model call working on the previous output. Reach for it when the task genuinely has stages and you can name them: draft, then check the draft against the source, then format.

Routing classifies the input and sends it to a specialised followup. It is the shape that pays best in a question-answering service, because "summarise this policy" and "what changed between these two versions" want different prompts and often different retrieval settings.

Parallelization runs independent subtasks at once, either by sectioning one task into pieces or by voting on the same task several times. It buys latency, or it buys confidence, and it never buys both.

Orchestrator-workers has a central model break the task down, delegate to workers, and synthesise. The number of workers is decided per request, so this is the first shape whose cost you cannot read off the code.

Evaluator-optimizer has one call generate and another criticise, in a loop with a round limit. Lesson 0360 is about the one thing that decides whether this shape works at all, which is where the critic's evidence comes from.

3. The sixth shape, and the number nobody has

The sixth shape is the autonomous agent, and Anthropic's own condition for reaching for it is narrow: open-ended problems "where it's difficult or impossible to predict the required number of steps" and where you cannot hardcode a fixed path.

Do the arithmetic that follows from that. Take a three-step chain, a router that classifies then answers, a parallel fan of three sections plus an aggregation, an orchestrator that happens to pick three workers, and an evaluator-optimizer capped at two rounds. Those are 3, 2, 4, 5 and 4 model calls. Every one of those numbers is knowable before the request arrives, from the source file for the first three and from the plan for the fourth.

The agent has no such number. Not a large one: none. Whatever figure you put on the chart below for the sixth bar is a figure you invented, which is precisely why the next lesson is about putting one there on purpose.

4. Score it before you loop

Five questions decide it, and they are questions about the task rather than about the model. Answer them for a feature you are actually being asked for, not for the most interesting one you can imagine.

5. What to build it with, and when to stop

The same write-up ends with advice worth taking literally: frameworks help you start quickly, and you should "not hesitate to reduce abstraction layers and build with basic components as you move to production". This course takes that as a rule rather than a suggestion. Reference code here is the provider SDK, Pydantic, one vector store and, where a graph genuinely helps, LangGraph 1.2.x. Anything else you see named on these pages is evidence that a mechanism is real, pinned to a version in the sentence, and never the subject.

The practical reason is on the previous chart. Four of the six shapes are ten lines of Python around calls you are already making. A framework that hides those ten lines also hides the turn count, and the turn count is the thing this module is about.

This six-way split is Anthropic's operational definition of its own patterns, published in its own engineering write-up. It is a useful vocabulary and it is not a field-wide standard: other vendors name overlapping shapes differently, and no specification defines "agent". Use it because it makes a decision arguable, and say whose it is when you use it in a design review.

Check yourself

Retrieval practice

Answer from memory before revealing.

Your service classifies each question, then sends it to one of three prompts tuned for that class. Which shape is that?
Routing classifies the input and directs it to a specialised followup, which is exactly this. Prompt chaining would run all three prompts in sequence on one input rather than choosing between them. An orchestrator would decide how many workers to use per request, and here the fan-out is always one. It is not an agent because every edge in the diagram is written in your source file.
On the two definitions in section 1, what makes a system an agent rather than a workflow?
The definition turns on who owns the control flow: an agent dynamically directs its own process. Tool count is irrelevant - a one-tool loop is still an agent, and a four-tool fixed pipeline is still a workflow. Running several models at once is parallelization, which is a workflow shape. Retrieving before generating is the module 2 pipeline, and it is the most workflow-shaped thing in this course.

Practice about 25 minutes, with your capstone repository

Practice 1working

This is module 3's first increment to your capstone, and it produces a file rather than code.

Write docs/shape.md in your own repository. Three things go in it.

First, name which of the six shapes your current pipeline is, in one sentence, and count the model calls one request makes today. Read the count out of your trace rather than out of your memory of the code.

Second, take the one feature request you have actually received that the current shape cannot serve, and score it on the card above. Record the score, the band, and which row scored lowest.

Third, write the sentence from row five: the stop condition, in one sentence, whatever the score was. If you cannot write it, that is the finding, and you write that down instead.

Hint

The model-call count is not a design question. Your module 1 trace already has one span per model call, so the count is a query over one request rather than a reading of the code, and the two disagreeing is itself worth knowing.

If every feature you can think of scores in the top band, you have chosen the most interesting feature rather than the next one. Score the one in your issue tracker.

Show what a good shape record looks like
  1. The shape is almost always prompt chaining or routing. A retrieval pipeline with a query rewrite in front of it is a two-step chain; one with a classifier is routing. Naming it is what lets you say later what changed.
  2. The call count from the trace beats the call count from the code. A retry, a query expansion or a judge you added in module 1 are all model calls, and they are all in the trace. A count that comes out higher than you expected is the useful outcome of this exercise.
  3. The lowest-scoring row is the design. A feature that fails row three, the external signal, does not become an agent by adding a loop: it becomes an agent that cannot tell when to stop. A feature that fails row two, the open tool set, is routing wearing a costume.
  4. The stop-condition sentence is the deliverable. "Stop when the answer cites at least one retrieved passage, or after four tool calls, whichever comes first" is a sentence you can turn into code in the next lesson. "Stop when it has enough information" is not, and noticing that now is cheaper than noticing it in production.

Sanity check. If your feature scored in the top band on all five rows, re-read row four with a number in mind rather than an intuition. Most internal question-answering features are worth a handful of extra turns and not fifty, and a card that scores full marks on the first feature you tried is usually a card answered about a demo.

Your teacher. If the workflow-against-agent line still feels blurry, describe your pipeline to your assistant and ask it to name which of the six shapes it is and, specifically, which line of your code owns the control flow. Then ask it for the smallest change that would move it to the next shape along, and what that change costs in model calls per request. If it answers with a framework name rather than with a control-flow line, ask again.
