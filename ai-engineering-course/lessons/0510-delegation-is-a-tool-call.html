A handoff is an ordinary tool call with an agent behind it

working 8 min The convergence is the evidence: two unrelated runtimes generate the same tool name for a handoff, one of them pinned at 0.22.0 and one read on an unpinned branch, as noted below. · Handoffs

The one-minute version

  • Delegation adds no new primitive. The orchestrator calls a tool, and the tool happens to be another agent.
  • Two runtimes built independently generate the same name for it: transfer_to_<agent_name>. That is convergence rather than a convention somebody published.
  • Everything from lessons 0320 and 0330 therefore applies: the description is behaviour, the schema is a contract, and a failure has to be visible to the caller.
  • The design decision is what crosses the edge. The common default hands the receiving agent the entire prior conversation.
  • Three topologies, and one question separates them: who is allowed to decide what happens next.

1. Two runtimes, one tool name

The OpenAI Agents SDK, read at 0.22.0, states the mechanism in one sentence: "Handoffs are represented as tools to the LLM. So if there's a handoff to an agent named Refund Agent, the tool would be named transfer_to_refund_agent."

The langgraph-supervisor package builds the same thing from the other direction. Its create_handoff_tool defaults the tool name to transfer_to_<agent_name> and the description to Ask agent '<name>' for help, with the agent name normalised to snake case.

Two teams solving the same problem produced the same tool name. That is the useful kind of evidence: not a standard anybody agreed to, but the shape the problem has. And it settles what a handoff is - the model does not gain a new verb, it gains one more entry in the catalogue it already had in lesson 0320.

Everything from that lesson and the next therefore transfers without modification. The handoff tool's description decides when it fires, so it is behaviour rather than documentation. Its schema is a contract. And when the worker fails, lesson 0330 applies exactly: the failure belongs in the result where the orchestrator's model can read it, not as an exception that ends the run.

2. The decision nobody makes on purpose

Here is where a handoff stops being a tool call and becomes an architecture. When the worker runs, what does it see?

The OpenAI Agents SDK documents its default plainly: "the new agent takes over the conversation, and gets to see the entire previous conversation history", with input filters and a nest_handoff_history setting available to change that. The supervisor package makes the same choice, passing the message history to the agent it transfers to.

That default is generous and it is exactly the knob Cognition's first principle from lesson 0500 is about - share full traces rather than individual messages, because an agent that cannot see the earlier decisions will make conflicting ones. So the default is defensible.

It is also the largest line on your bill. Every token of that history is re-sent on every turn the worker takes, which is lesson 0310's quadratic arithmetic applied to a second agent that inherited a conversation it did not have.

3. Three shapes, one question

Runtimes offer a small set of arrangements and the marketing names differ, so hold the question rather than the names: who is allowed to decide what happens next?

In a supervisor, one agent owns every decision and workers only answer. It is the easiest to trace, because there is one place the path is chosen, and the easiest to bottleneck.

In a swarm, peers transfer directly to each other. Any agent may decide, so the path is emergent and a trace has no single owner - which is worth knowing before you debug one in lesson 0550.

In a sequential pipeline, nobody decides. The order is written in your code, which makes it a workflow rather than a multi-agent system, and lesson 0300's taxonomy already covered it. Frameworks ship this as an agent shape - Google's ADK at 2.8.0 exposes SequentialAgent, ParallelAgent and LoopAgent beside its model-driven one - and it remains the cheapest thing on this page by a wide margin.

One distinction to keep, because it decides your error handling. Routing chooses once and does not come back; the chosen agent owns the answer. Delegation expects a return, so the orchestrator must be able to read a worker's failure and try something else.

The OpenAI Agents SDK is quoted at 0.22.0, a pinned pre-1.0 release. langgraph-supervisor was read on its main branch rather than at a tag, so its default tool name and description are stated here as what that branch does and not as a pinned fact. Both are evidence for the convergence rather than the subject of this page: what generalises is that a handoff is an ordinary tool call and that something has to decide what history crosses with it.

Check yourself

Retrieval practice

Answer from memory before revealing.

Mechanically, what does the model emit when an orchestrator hands work to a specialist?
A handoff is represented to the model as a tool, named transfer_to_agent_name in two independent runtimes, so the model emits the same tool_use block it emits for retrieval. There is no new role in the message list. It is not framework-only: you can build it with the provider SDK alone, which is why the convergence is interesting. And no new endpoint is involved - your own process runs the second agent.
In the OpenAI Agents SDK at 0.22.0, what does the receiving agent see by default after a handoff?
The documentation states that the new agent gets to see the entire previous conversation history, and input filters exist to narrow it. Only the last turn and a summary are both things you can configure, and both are cheaper and riskier - they are the other two bars on the chart. Nothing until it asks would make the worker start blind, which no runtime does by default because it is the coherence failure Cognition warns about.

Practice about 45 minutes, with your capstone

Practice 1working

Only do this if lesson 0500's record said yes. If it said no, read it and move on - the refusal is the increment.

Add one specialist behind a handoff tool. One, not three: the comparison step, or whichever subtask your record named as independent and read-only. Give the handoff tool a description written to the standard of lesson 0320, and make a worker failure return as a result rather than raise.

Print the message list the worker actually receives. Not the list you meant to pass - the serialized one, the same way you captured the tools block in lesson 0320. Count its tokens.

Then run it three ways: full history, the last two turns, and a short summary you write. Record all three token counts and the module 1 golden-set score for each, in docs/decision-multi-agent.md beside the projection you already wrote.

Hint

Pick questions where the worker genuinely needs earlier context - a follow-up that says "and the other one" - or all three filters will score identically and you will conclude, wrongly, that history is free to drop.

If your runtime hides the handoff payload, remember that your own process is the one starting the worker. You can log the list at that call site without the framework's cooperation.

Show what a good handoff edge looks like
  1. The measured payload is bigger than the one you intended. Tool results from earlier turns, the orchestrator's own reasoning text and the full tool catalogue usually travel too. That gap between intent and bytes is the entire finding.
  2. The three filters do not score the same, and the middle one usually wins. Full history is expensive, a summary loses the follow-up questions, and a short window of recent turns is where most systems land - but only your golden set can say that for your questions.
  3. The worker's failure has to be a result. If the comparison worker cannot find a second supplier to compare, the orchestrator should read that sentence and ask differently. Lesson 0330's arithmetic applies with more force here, because an aborted run has now paid for two agents.
  4. One specialist is a finished exercise. The second and third add nothing to your understanding of the edge and triple the bill, and lesson 0520 is where a design with several workers actually needs its own machinery.

Sanity check. Your full-history payload should be roughly the size of the conversation so far, in the low thousands of tokens for a short thread. A number in the low hundreds means you passed only the last message and have been running the cheapest filter without choosing it - which is worth knowing, and is not the default this page describes.

Your teacher. Give your assistant the serialized message list your worker received and ask it to mark every message as needed or not needed for the worker's task, then to write the shortest summary that preserves the needed ones. Run that summary as your third filter. Where it drops something the worker turns out to need, you have found the coherence cost of a cheap edge, on your own questions rather than in an argument.

Primary source to go deeper
