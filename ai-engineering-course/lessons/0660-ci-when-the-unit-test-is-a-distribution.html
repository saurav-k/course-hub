A threshold tighter than your noise is a coin toss with a red cross on it

working 10 min Built on the golden set and the judge from module 1, whose agreement number is the confidence interval on every automated score here. · Workflow triggers

The one-minute version

  • A prompt is source code with no compiler and no type checker. Nothing catches a bad edit except a measurement, so the pipeline needs one.
  • Three tiers, three frequencies: deterministic tests on every push, tool contracts on every push, the golden set on a schedule and before a release.
  • A gate is a metric, a threshold and a sample size, and the third is the one people omit. Thirty questions carries about ±7 points of standard error on a score near 80%.
  • So a threshold set inside that band fails honest builds at random, and a team that has been red-for-no-reason twice stops reading the gate.
  • Module 1's judge agreement is the ceiling on all of it: no threshold can be tighter than the judge's agreement with your own hand-scoring.

1. Three tiers, and what each one can catch

The instinct on arriving here is to ask how to test a model. That is the wrong first question, because most of what breaks is not the model at all.

Tier 1 is deterministic and covers everything around the model. Chunk boundaries, the packing order from lesson 0630, the retrieval ranking for a fixed index, the parsing of a structured output, the four request shapes from lesson 0600. These are ordinary tests with ordinary assertions, they run in seconds, and they catch the majority of real regressions because the majority of real regressions are in your own code.

Tier 2 is the tool contract. Every tool your agent can call, exercised against a recorded request and a recorded response, with no model in the loop. This catches the change that quietly alters a tool's schema or its error shape, which is invisible to tier 1 and expensive to find in tier 3.

Tier 3 is the golden set, and it is the only tier that measures quality. The thirty questions from module 1, each with the passage that answers it, scored on the metrics module 1 established: recall@10 and nDCG@10 for retrieval, and Faithfulness, Context Precision, Context Recall, Response Relevancy and Noise Sensitivity for generation.

Tier 3 costs real money and real minutes, so it does not run on every push. It runs nightly, and before a release, and on any pull request that touches a prompt, a retrieval parameter or a model id - which is a path filter rather than a judgement.

2. A gate is three numbers, and everyone forgets the third

"Faithfulness must be at least 0.82" is not a gate. It is two thirds of one, and the missing third is the sample size, which decides whether 0.82 means anything.

Do the arithmetic. A score like Faithfulness is a proportion over the questions in the set. For a proportion near 0.8 on a set of 30, the standard error is the square root of 0.8 times 0.2 divided by 30, which is the square root of 0.00533, which is about 0.073. So an honest run of the identical system twice can differ by seven points in either direction without anything having changed.

That has a hard consequence. A threshold of 0.82 against a system whose true score is 0.85 fails a meaningful fraction of clean builds. Do that twice and your team learns that the eval gate is flaky, and a gate people re-run until it passes is worse than no gate, because it costs money and teaches contempt.

There are exactly three honest responses and you should pick one deliberately. Set the threshold outside the band, which means gating on a large regression rather than a small one. Enlarge the set, since the error falls with the square root of the count, so 120 questions roughly halves it. Or gate on the delta against the previous run rather than on an absolute value, which cancels some of the shared variance. Most teams should start with the first and work towards the second.

And above all of it sits module 1's rule: the judge's agreement with your own hand-scoring is the confidence interval on every automated number in this course. If your judge agrees with you 80% of the time, a gate that distinguishes 0.84 from 0.82 is reporting the judge's opinion rather than your system's behaviour. The statistics under this belong to Statistical Foundations for Machine Learning, and this page only insists that you write the sample size next to the threshold.

3. The tool is the least important decision here

Several runners will do this. promptfoo runs a declarative config in CI and fails the build on a failing assertion, with a cache path and TTL configurable through environment variables, so a run whose inputs have not changed is cheap. DeepEval, at python-v4.2.0, drives the same idea from pytest. A hundred lines of your own Python over the harness module 1 already built does it too, and for many readers that is the right answer because there is nothing to learn.

This course does not pin a version for promptfoo, because the documentation read for it publishes commands and cache variables and no version number, and a version this course cannot verify is one it will not print. Choose on whether the tool can express your metrics and whether it can be cached, and treat the choice as reversible.

What is not negotiable is that the gate reads the same golden set, computes the same metric names, and reports the sample size. A second evaluation harness built for CI is the failure this section exists to prevent: two harnesses produce two numbers, and nobody can say which is the system's.

4. What rolling back actually means here

One asymmetry to leave with, because it decides how much you need the gate.

A prompt regression is a git revert. The prompt is a file, the file is in the repository, and undoing it restores the previous behaviour exactly. That is the easy case and it is the case the gate is built for.

A model change is not. If your provider's model id moves, or you move it, the previous behaviour may not be available to return to, and the golden set is the only evidence you will have about what changed. That is a supply question rather than a pipeline one, and Staff AI, Model supply is a dependency owns it. What belongs here is only this: pin the model id in configuration and treat a change to it as a code change, so it goes through the same gate as a prompt edit rather than arriving through a vendor's default.

Finally, a caution about the shape of the curve you are gating. LinkedIn's team reported reaching "80% of the basic experience we were aiming to provide within the first month" and then spending "an additional four months attempting to surpass 95% completion", with each further point slower than the last. That is their measurement on their product, and the transferable part is the shape: the gate matters most in the long flat part, where changes are small, noise is comparable to the effect, and nobody can tell progress from drift by looking.

The standard error of 0.073 is this page's arithmetic on a stated assumption - a proportion near 0.8 over 30 items - and the ten-commit chart is an illustration of that arithmetic rather than a measurement of any system. Your own variance depends on your set, your metric and your judge, and it is worth measuring directly by running the identical system five times and looking at the spread. The LinkedIn figures are that team's measurement of their own product and are evidence about the shape of a quality curve, not a target for yours.

Check yourself

Retrieval practice

Answer from memory before revealing.

Your eval gate has failed three clean builds this month and passed on re-run each time. What is the most likely cause?
Passing on re-run with no change is the signature of a threshold inside the sampling band, because the same system genuinely produces a different score each run. The first two are worth ruling out and neither explains why a re-run reliably fixes it. An edited golden set would shift the score persistently rather than intermittently, and it would show up as a diff. The fix is a wider threshold or a bigger set, not a re-run button.
Which change should trigger the expensive tier, on the path-filter rule in section 3?
A model id is exactly the kind of change that can move every score while breaking no test, which is why section 4 says to pin it and treat it as code. The other three cannot change what the model answers: an API field and a rename are caught by tier 1 if they break anything, and a manifest edit is lesson 0610's territory. Running the golden set on all four would make the gate too slow to keep and is how path filters get deleted.

Practice about an hour, in your own repository

Practice 1working

Two measurements and one workflow, and the first measurement is the one that decides the workflow.

Measure your own noise first. Run your golden set five times with nothing changed and record the five scores. The spread you see is the floor on any threshold you can set, and it is usually wider than people expect.

Then write the gate with all three numbers in it: the metric, the threshold, and the sample size, with the threshold placed outside the spread you just measured. Put it in a workflow with a path filter so it runs on prompt, retrieval and model-id changes and not on everything.

Then break it on purpose. Make a prompt edit you believe is bad - remove the instruction to cite sources, or halve the retrieved passages - and confirm the gate goes red. Then revert and confirm it goes green.

Hint

If five runs give five identical scores, your evaluation is deterministic somewhere it should not be: check that you are not caching model responses across runs, and that temperature is what you think it is.

Cache the eval on a key built from your prompt files and your golden set, as the third assembler part does. Without it the nightly job is the line item somebody deletes in three months.

Show what a working gate looks like
  1. Five runs, and the spread is the deliverable. Write min, max and median into the repository beside the threshold. The next person to tighten the threshold needs to see this or they will tighten it into the noise.
  2. The threshold sits below the spread, not inside it. That feels too loose and it is the correct setting: this gate exists to catch a regression somebody would notice, not to detect a two-point drift that your judge cannot resolve anyway.
  3. The deliberate break should be unambiguous. If removing the citation instruction does not move Faithfulness at all, that is a finding about your metric rather than about your gate, and it is worth more than the exercise.
  4. The number is reported on green builds too. A gate whose output is only visible when it fails is a gate nobody trusts the day it fires. Print the score and the sample size into the job summary every run.
  5. The model id is pinned in configuration and covered by the path filter. This is the smallest change on this page and the one most likely to save you, because it is the only failure mode here that no test catches and no revert undoes.

Sanity check. Your measured spread over five runs should be in the same neighbourhood as the arithmetic in section 2 - for a thirty-item set on a score near 0.8, a spread of a few points to about fifteen across five runs is unremarkable. A spread of one point means something is cached; a spread of forty means the metric is not measuring what you think, and neither is a threshold problem.

Your teacher. If the sample-size argument still feels theoretical, ask your agent to compute the standard error for your own set size and score, then to say what the smallest regression you could reliably detect is. If your gate is red and you are not sure why, hand it the last five runs and ask whether the drop is outside the spread of the previous runs before you go looking for a cause.
