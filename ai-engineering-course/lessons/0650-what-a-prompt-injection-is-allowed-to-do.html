Module 06 · Deployment · Lesson 0650

Stop asking whether the text is malicious; decide what it is allowed to reach

working 10 min The six patterns and the guiding principle are read from arXiv:2506.08837v3 with the PDF open, section 3 and section 3.1. · Design Patterns for Securing LLM Agents

The one-minute version

  • Prompt injection is not a filtering problem. Fourteen researchers' published position is that a general-purpose agent probably cannot be made reliably safe at all with today's models.
  • So the design question changes from "is this text malicious" - unanswerable - to "what may this agent do now that it has read this text", which is answerable in code.
  • Six named patterns answer it, each by giving up a specific capability: Action-Selector, Plan-Then-Execute, LLM Map-Reduce, Dual LLM, Code-Then-Execute, Context-Minimization.
  • The price is measurable. CaMeL solved 77% of AgentDojo tasks with provable security against 84% undefended - a real cost, and a small one.
  • Your capstone is already one of the six, badly. Naming which one is most of the work.

1. The claim you are not allowed to soften

Fourteen researchers from ETH Zurich, Google, Microsoft, IBM, Invariant Labs and others published a set of design patterns for this problem, and the paper opens by saying what it does not believe in.

Detection and adversarial training, they write, "are likely to remain heuristic in nature - and thus inherently brittle", and then, plainly: "As long as both agents and their defenses rely on the current class of language models, we believe it is unlikely that general-purpose agents can provide meaningful and reliable safety guarantees."

That is a negative claim and it is the foundation of everything after it. The patterns below are not a menu of hardening tips you apply on top of a general-purpose agent to make it safe. They are six ways of building an agent that is deliberately not general-purpose, and the paper says so: these patterns "impose intentional constraints on agents, explicitly limiting their ability to perform arbitrary tasks."

The principle they all share is the sentence worth memorising: "once an LLM agent has ingested untrusted input, it must be constrained so that it is impossible for that input to trigger any consequential actions - that is, actions with negative side effects on the system or its environment."

Note the word impossible. Not unlikely, not filtered, not detected. The whole discipline is moving the guarantee out of the model and into the surrounding program, where an ordinary engineer can reason about it.

2. Six patterns, and what each one costs

Each pattern buys its guarantee with a specific piece of capability. Read the right-hand column as the price rather than as a caveat.

Action-Selector. The agent translates a request into one of a fixed list of pre-defined actions and no output flows back into it. The paper calls it "an LLM-modulated switch statement". Immune to injection through tool results, because there are none. Cost: it cannot use what it finds.

Plan-Then-Execute. The agent fixes the whole list of tool calls before any untrusted data arrives, then executes it. Tool output can no longer change which actions happen - the paper describes it as a form of control-flow integrity. Cost: injected text can still alter the arguments, and the paper says so explicitly; a compromised calendar entry cannot add an email send, but it can change what the email says.

LLM Map-Reduce. One isolated sub-agent per untrusted document, each returning something constrained - the paper's example is a boolean - and a reduce step that is either not an LLM or is protected by a constraint on the map outputs. Cost: complexity, and per-document calls.

Dual LLM. A privileged model that plans and holds tools but never sees untrusted text, and a quarantined model that reads untrusted text and holds no tools. Results pass by symbolic reference through an ordinary non-model orchestrator, so the privileged model manipulates a variable it cannot dereference. Cost: the privileged model is reasoning about content it cannot read.

Code-Then-Execute. The agent writes a program that calls tools and spawns unprivileged models, and the program is then run. Cost: you are now reviewing generated code, and the sandbox is load-bearing.

Context-Minimization. The user's own prompt is removed from the context after it has selected the action, so it cannot influence the answer. Cost: nothing downstream can refer back to how the question was phrased.

The paper works all six through ten case studies - among them a SQL agent, an email and calendar assistant, a customer service chatbot, a resume screener and a software engineering agent - which is the section to read when you are deciding which one your own application is.

3. The price of the guarantee, measured once

A pattern that costs half your product's usefulness is not a pattern anybody ships, so it matters that somebody measured the cost.

CaMeL is an implementation of the strictest end of this family: it extracts control and data flow from the trusted query so that untrusted data can never affect the program flow, and it attaches capabilities to values so that a policy is enforced when a tool is called. On the AgentDojo benchmark it solved 77% of tasks with provable security, against 84% for an undefended agent.

Seven percentage points is the price of the guarantee on that benchmark. That is a real cost and a much smaller one than most engineers expect when they first hear "the privileged model may not read the document", and it is the number to bring to the conversation where somebody argues that security here is impractical.

It is one benchmark, and the guarantee is provable with respect to the threat model the paper defines rather than in general. Do not let it become "CaMeL is secure"; it is "this construction provably resists this class of attack, at this measured cost in utility".

4. Which pattern your capstone already is

Almost every RAG application arrives at this lesson as an accidental worst case: a general-purpose loop, with retrieval feeding text straight back into a model that also holds every tool the application has. That is the shape the paper says cannot be made reliably safe.

For most readers of this course Plan-Then-Execute is the cheapest real improvement, because a retrieval-augmented answer is usually a fixed sequence anyway: retrieve, then answer. Committing to that sequence before any document is read costs almost nothing and removes the entire class of attack where a passage adds a tool call. Remember the limit the paper states: arguments can still be influenced, so a tool that sends something outward still needs its arguments constrained or confirmed.

Where your application does have a tool with consequences - it writes, it pays, it emails - the honest options are Dual LLM or an explicit human confirmation, and the confirmation is not a lesser choice. The paper keeps sandboxing and user confirmation as general best practices distinct from the six patterns, and says every agent should incorporate them "to the extent possible".

A pattern's guarantee holds against the threat model its paper defines, and a page that promised more than that would be doing the thing both papers were written against.

Check yourself

Retrieval practice

Answer from memory before revealing.

You adopt Plan-Then-Execute. A retrieved passage carries an injected instruction. What can it still do?
The paper states this limit directly: the plan of calls is fixed, but an injection can still manipulate the inputs to those calls, so it cannot add a send and can alter what is sent. The second and third options are exactly what the pattern does prevent, which is its whole value. The fourth is the overclaim the pattern invites, and believing it is how a team ships an email tool whose body an attacker writes.
Under the Dual LLM pattern, what does the privileged model do with a value the quarantined model extracted?
The privileged model manipulates a symbolic variable and cannot dereference it, because dereferencing would put untrusted text in front of the model that holds the tools, which is the one thing the pattern exists to prevent. An ordinary non-model orchestrator substitutes the real value at call time. The other three options all involve the privileged model reading the content, which collapses the pattern into a general-purpose agent with extra steps.

Practice about an hour, with your capstone

Practice 1working

Three steps, and the first one is the one people skip.

Draw your own turn as a taint map. List every block of text that reaches the model in one turn and mark each as written by you, by your user, or by somebody else. Retrieved passages are somebody else's, including the ones from your own wiki, because "somebody at this company could edit it" is the property that matters.

List every tool the turn can reach and mark the consequential ones - anything that writes, pays, sends, or discloses across a permission boundary. Then check the pairing: is there any path from a foreign block to a consequential tool? For nearly everyone the answer is yes.

Apply one pattern and prove it. Fix the plan before retrieval runs. Then write an injected passage into your own corpus - a real document with a real instruction in it - run the question that retrieves it, and confirm from the trace that no unplanned tool call happened.

Hint

Write the injection the way a real one arrives: inside a document that is otherwise entirely legitimate and genuinely useful for the question. An injection in a document nobody would retrieve tests nothing.

Remove it from your corpus afterwards, or keep it in a fixture the ingestion pipeline never sees. An injected document left in a real index is a live trap for the next person who runs an evaluation.

Show what a finished containment looks like
  1. The taint map is the deliverable, not the fix. Most readers discover the foreign share is larger than they thought, because a retrieved passage feels like your own data until you ask who may edit it. Keep the map: lesson 0730 in module 7 asks for it again.
  2. The path usually exists and is usually short. Retrieved passage to model to tool, one hop, because the tools were attached to the same model that reads the documents. Naming that single hop is the moment the lesson lands.
  3. Plan-Then-Execute is a small diff. Decide the tool sequence from the question alone, before retrieval, and execute it. For a plain RAG answer this changes almost no behaviour, which is why it is the right first pattern rather than the most impressive one.
  4. The proof is the trace, not the answer. A correct-looking answer proves nothing, because a well-written injection produces one. What proves containment is that the trace's tool calls match the plan exactly. Lesson 0670 makes that comparison an alert.
  5. Write down what is still reachable. Arguments can still be influenced, so name the tool whose arguments still come from retrieved content and say what constrains them - a schema, an allowlist, a human confirmation. An honest note beats a claim of safety.

Sanity check. After the fix, your injected passage should still be retrieved and should still appear in the context - if it stopped being retrieved, you accidentally tested your retriever rather than your containment. The right result is that the passage arrives, the model reads it, and the tool call it asks for does not happen.

Your teacher. If the six patterns still feel like one idea, ask your agent to take your own application and describe it under three of them, saying what each version can no longer do. If your taint map came out with no foreign blocks, ask it who is able to edit each source you retrieve from, and re-do the map with those answers.
