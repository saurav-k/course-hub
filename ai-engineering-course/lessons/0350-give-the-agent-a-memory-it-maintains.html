A memory the agent maintains is a file-write primitive you handed it

working 9 min Written against the Claude memory tool, tool type memory_20250818, whose documentation states both the six commands and where the path check has to live. · Memory tool

The one-minute version

  • The fourth store from the last lesson has a shipped shape: six file commands, a directory prefix, and no server.
  • It is client-side. The model asks for a file operation, your handler performs it against storage you own, and /memories is a prefix you map rather than a directory that exists.
  • That makes it the only store a person can open, diff and correct - and it makes it an arbitrary file write with a friendly name.
  • The vendor is explicit about where the check lives: your implementation "must validate every path in every command". Nothing upstream does it for you.
  • The second danger is quieter. A memory file is a place where somebody else's words can arrive wearing your agent's handwriting.

1. Six commands, and no server anywhere

The Claude memory tool is declared with a single entry - a type of memory_20250818 and a name of memory - and you write no input schema, because Anthropic publishes the schema and trains the model on it.

Six commands come with it: view shows a directory or a file, optionally a line range; create writes a file; str_replace edits one; insert adds text after a line; delete removes a file or directory; rename moves one.

The part that surprises people is where those run. The documentation says the tool "operates client-side: Claude requests file operations, and your application executes them", and that /memories is "a prefix that your handler maps onto real storage, such as a per-user directory or keys in a database". So there is no memory service. There is your handler, a switch on the command name, and whatever store you decide backs it - which means the four-store choice from the last lesson is still yours: a memory tool over a per-tenant database table is as legitimate as one over a directory.

2. The gate, and why omitting it is the default

The documentation carries a warning rather than a note, and it is worth reading as a specification of your work: a malicious path such as /memories/../../secrets.env "can reach files outside the /memories directory", and "your implementation must validate every path in every command".

Four safeguards are named there, and all four are cheap. Check that every path starts with the prefix. Resolve to a canonical form and confirm the result is still inside the memory root. Reject traversal sequences, including the backslash spellings. Watch for the URL-encoded forms such as %2e%2e%2f. In Python that is Path.resolve() followed by relative_to(), and it is four lines that must sit in one place that every command goes through.

The reason this is the default failure rather than an exotic one is the shape of the code. Six commands invite six handler functions, each taking a path, and a check written into five of them is a check that does not exist. Put the validation in the dispatcher, before the switch, and make the six functions take something that is already a resolved, in-bounds path.

Three more limits are worth building at the same time, because the documentation names all three and none of them arrives on its own: cap how large a file may grow, cap how much view returns and let the model page through the rest, and expire files nobody has read in a long time.

3. What the model is told to do with it

Enabling the tool changes the system prompt, and the API adds the instruction for you rather than expecting you to write it. Its shape is a protocol: look at the memory directory before doing anything else, record progress as you go, and - the line worth keeping - assume interruption, because the context window may be reset at any moment and anything not written down is lost.

That instruction is the reason this store behaves differently from the other three. The agent is not being given a cache. It is being told to treat its own context as unreliable and its memory directory as the durable record, which is a design stance rather than a feature, and it is the same stance behind module 4's checkpointed pause.

One neighbouring mechanism is worth naming so you do not build it twice. Compaction summarises the conversation server-side as it approaches the window limit; memory is a store you own and control. They solve different halves and the documentation recommends both for long-running agents: compaction keeps the active context small, and memory preserves what must survive being summarised.

4. Whose handwriting is that

Here is the failure that no path check catches. Your agent reads a supplier's document, decides one paragraph is worth remembering, and writes it into /memories/findings.md. Three sessions later that paragraph is read back at start-up, in your agent's own file, with no marker saying it came from outside.

Text that arrived as untrusted input has been laundered into a store the agent trusts. Module 2's lesson on the retrieved document as untrusted input is the same seam one stage earlier, and the memory file is where the seam becomes invisible - because a retrieved passage at least looks retrieved, and a memory file looks like something the system knows.

The fix is a habit rather than a mechanism: record provenance in the file. A memory line that carries where it came from can be judged later, by the model and by you. A memory line that does not is an assertion of unknown origin at the top of every future session.

The six commands, the client-side execution and the path-validation requirement are all Anthropic's own documentation of its own tool, quoted at tool type memory_20250818; a different provider's memory feature will differ, and the version belongs in the sentence whenever you quote one. What generalises is the shape: a memory an agent maintains is a write primitive, and the boundary check is the implementer's.

Check yourself

Retrieval practice

Answer from memory before revealing.

Under the memory tool, who actually performs the file operations the model asks for?
The tool is client-side: the model requests an operation and your application executes it against storage you control. The provider stores nothing, which is why the same tool can sit over a directory or a database table. A schema describes arguments and executes nothing. There is no managed service in this design at all, and believing there is one is how the path check gets skipped.
Which of these does the memory tool documentation put squarely on the implementer rather than the model?
The documentation states that your implementation must validate every path in every command, and names traversal sequences and their encoded forms. Training is the provider's, and relying on the model to refuse a bad path is relying on a defence that has no enforcement behind it. There is no tool schema for you to encrypt, since the provider publishes it. The type id is a published constant, not something you version.

Practice about 40 minutes, with a terminal

Practice 1working

Build the handler, then attack it.

Implement the six commands against the store you chose in the last lesson, keyed per tenant. Put the path validation in the dispatcher, before the command switch, so the six handlers receive a path that is already resolved and in bounds.

Then write the test that matters. Send each of these as a path and confirm every one is refused: /memories/../secrets.env, /memories/../../etc/passwd, a backslash spelling, and the URL-encoded form. Assert on the refusal, not on the absence of a crash.

Then run two sessions. In the first, let the agent record what it learned. Start a second with an empty context and confirm it reads the directory before it works. Record in docs/shape.md the tokens the second session spent before its first useful action.

Hint

Resolve first, compare second. Checking that a string starts with /memories before resolving it passes every one of the four attacks, because they all start with /memories.

If your store is a database rather than a directory, the check does not go away, it changes shape: the path becomes a key, and the equivalent bug is a key that escapes the tenant prefix. Write the same four tests against that.

Show what a good handler looks like
  1. One gate, not six. The dispatcher resolves the path to a canonical form, confirms it is inside the tenant's own root, and passes a validated object onward. A handler that still accepts a raw string is a handler somebody will call directly next year.
  2. Refusals are results, not exceptions. This is lesson 0330 applied: a rejected path is something the model can correct, so it comes back with the error flag set and a sentence saying the path must be under the memory root. A raise here ends a session over a typo.
  3. The start-up cost is real and worth knowing. A session that lists the directory and reads two files has spent several hundred tokens before it has done anything, every time. That is the price of the store, and it is what the pruning limits in section 2 keep bounded.
  4. Write provenance into the file, not into your notes. A remembered line that says where it came from - the user said it, a document said it, the agent inferred it - is a line a later session can weigh. Without that, section 4's laundering happens quietly and there is nothing in the file to catch it.

Sanity check. Your four traversal tests should all fail closed on the first run, before you write the fix. A suite where they pass immediately is a suite testing a store that has no traversal surface - a flat key-value map, say - and in that case write the tenant-prefix version instead, because the equivalent bug is still there.

Your teacher. Hand your assistant your dispatcher and ask it for five more path spellings that should be refused, then run them. Ask separately for the one it is least sure about. Then take a memory file your agent actually wrote and ask it to mark each line by origin - the user, a document, or the agent's own inference - and see how many lines it cannot classify. Those are the lines section 4 is about.
