Module 02 · Retrieval quality and context engineering · Lesson 0210

Let it reason in prose, then extract into the schema

working 9 min Grounded in the Pydantic and provider documentation, and in a measurement of what format restrictions cost reasoning, read at arXiv:2408.02442v3. · arXiv:2408.02442

The one-minute version

  • Lesson 0200 gave every chunk an identity. This lesson gives the answer one, so a citation points at a chunk you can open.
  • One object exists in three forms - a Python class, the JSON Schema it generates, and the payload on the wire - and the provider only ever sees the middle one.
  • Both vendors enforce it and they spell it differently. Teach yourself the shape they agree on: you hand over a schema and receive an object you can validate.
  • The schema is not free. It is sent on every request, on top of a published per-model floor, and each optional field is a permanent tax.
  • One measured finding should change your default: constraining the format costs reasoning. Reason in prose first and extract afterwards.

1. One object, three forms

A first pipeline returns a string, and the string is fine until something downstream has to read it. Then somebody writes a regular expression to find the citation, and a month later a model phrases the answer differently and the regular expression finds nothing and reports no error.

Declare the answer instead. A Pydantic model is a Python class, and calling model_json_schema() on it produces a JSON Schema - the documentation states the generated schemas are "compliant with the following specifications: JSON Schema Draft 2020-12 and OpenAPI Specification v3.1.0". That schema is what you send. What comes back is a payload, and validating it turns the same class into the gate.

So the class is written once and used three ways: to declare, to constrain, and to check. The one form the provider ever sees is the middle one, which is why a docstring you wrote for a colleague matters here: it becomes a description in the schema and it is read by the model.

answer.py · the declaration this course uses from here on
from pydantic import BaseModel, Field

class Cite(BaseModel):
    chunk_id: str = Field(description="The chunk_id from the ingest pipeline, lesson 0200.")
    quote: str = Field(description="The sentence in that chunk that supports the claim.")

class Answer(BaseModel):
    text: str = Field(description="The answer, in prose, for a reader.")
    citations: list[Cite] = Field(description="One entry per claim. Empty means unsupported.")

SCHEMA = Answer.model_json_schema()   # what the provider is actually sent

2. Two spellings of one shape

Both providers this course uses will hold the model to that schema, and the two mechanisms are not the same mechanism.

Claude takes it as a tool: a tool is a name, a description and an input_schema, and the documentation says to add strict: true to a custom tool definition "to ensure Claude's tool calls always match your schema exactly". Gemini takes it as a response schema, and its documentation is explicit that "Gemini's structured output mode supports a subset of the JSON Schema specification", with the warning that "Very large or deeply nested schemas may be rejected".

That difference is worth one design decision and no more. Keep the model definition in one file, keep the provider call behind one function, and let the schema be generated rather than typed twice. The shape both vendors agree on is the part that survives a provider swap.

3. What the contract costs, on every request

The schema is input tokens and it is sent every time. Claude's own documentation publishes the floor: supplying any tools at all adds a tool-use system prompt, and for Claude Opus 5 that is 286 tokens at a tool_choice of auto or none and 406 tokens at any or tool. Your own schema sits on top of that.

The rest is arithmetic you can do. A field costs its name, its type and its description, and a description written well enough to steer the model is a sentence rather than a word; call it about 25 tokens a field and substitute your own count once you have measured one. Sixteen fields is then roughly 400 tokens of schema on top of a 286-token floor, on every request, for the life of the endpoint.

4. Reasoning inside the schema is the expensive way

There is one finding here that should move your default, and it cuts against the tidy design. Tam and colleagues measured what happens when a model is made to answer inside a structured format rather than freely, and report "a significant decline in LLMs reasoning abilities under format restrictions", with stricter constraints producing greater degradation on reasoning tasks.

The design move that follows is cheap. Let the model answer in prose, then make a second, small call whose only job is to extract that prose into the object. The reasoning happens where it is unconstrained; the schema is applied to text that already exists. It costs one extra call and it is the pattern to reach for whenever the answer needs work rather than lookup.

That is one paper, and its abstract names "various common tasks" without listing them, so the size of the effect on your questions is unknown. Treat it as a reason to try the two-call shape on your own golden set and compare, not as a rule. This course does not have a second measurement to set beside it.

5. Validate once, at the edge

The last part is a habit rather than a mechanism. Validation belongs where the untrusted value arrives, and nowhere else. Parse the payload into Answer at the boundary, raise on failure, and let every function after that take an Answer and never a dictionary.

The payoff is that "the model returned something weird" stops being a category. It becomes a validation error with a field name in it, at a known line, countable across a run. Absence stops being implicit too: an answer with no supporting passage returns an empty citations list, which is a value your code can branch on, rather than a sentence that happens not to mention a source.

6. What this changed

Re-run the golden set. The retrieval numbers will not move, because nothing about retrieval changed, and that is the honest row to write down.

Two other numbers do move and both are worth recording. The first is the parse failure rate: the share of answers your code could not turn into an object, which was previously invisible because a regular expression that matches nothing looks the same as a question with no answer. The second is tokens per request, which went up by the size of your schema plus the published floor, and which you now know rather than guess.

The whiteboard framing of the same argument - what a grounded answer owes its sources, stated as a design property rather than as a class - is Citation grounding in AI System Design for Staff+ Interviews.

Check yourself

Retrieval practice

Answer from memory before revealing.

Which of these does a provider's schema guarantee actually give you?
A schema constrains the form of the reply and nothing else, so parsing is the whole of what it buys. Whether a citation supports its claim is faithfulness, which lesson 0170 measures with a judge. Whether the answer used only retrieved text is grounding, also measured rather than enforced. A confidence field is a number the model wrote, and it is constrained to be a float, not to be true.
Your answers get worse when you switch from prose replies to a strict schema. What does the measured finding in section 4 suggest first?
The paper's finding is about reasoning under format restriction, so the fix is to stop making the model reason inside the format: prose first, extraction second. Retrieving more passages changes what is available, not how it is expressed. Dropping strictness while still demanding one JSON reply keeps the constraint and loses the guarantee. Longer descriptions make the schema bigger, which is a cost with no reason to help.

Practice about 35 minutes, with a terminal

Practice 1working

Your capstone currently returns a string. Give it an object.

Declare the answer as a Pydantic model with a text field and a citations list, where each citation carries the chunk_id your lesson 0200 pipeline produces. Generate the JSON Schema and count its tokens with the same counter you use for requests.

Make a malformed reply an exception rather than a string that flows on. Validate at the boundary, log the failure with the question that produced it, and run the whole golden set.

Record two numbers beside the module 1 baseline: the parse failure rate over the golden set, and the tokens your schema adds to every request.

Then run the golden set once more with the two-call shape - prose answer first, extraction second - and compare faithfulness with the single-call version.

Hint

Count the schema in the same tokeniser your provider bills you with, not in characters. The published per-model floor is separate and adds on top; do not try to find it inside your own schema count.

For the two-call comparison, keep everything else identical - same retrieved passages, same question order - or you are comparing two changes at once.

Show what a good result looks like
  1. Count the floor and the schema separately. For Claude Opus 5 the tool-use system prompt is 286 tokens at tool_choice: auto, published per model, and your schema is whatever your counter says on Answer.model_json_schema(). Two numbers, added, is the per-request tax.
  2. The parse failure rate is the number that was previously invisible. Zero out of thirty is a good result and a suspicious one until you have deliberately fed the validator a bad payload and watched it raise.
  3. An empty citation list is a result, not a bug. A question the corpus cannot answer should produce an answer with no citations, and your code should be able to branch on that. If your model never returns an empty list, the field description is not saying that empty is allowed.
  4. Write the retrieval row down as unchanged. "recall@10 unchanged, parse failures 3 of 30 to 0 of 30, +321 tokens per request" is the honest shape of this lesson's row, and the last term is the price you agreed to.

Sanity check. The tokens your schema adds should be in the low hundreds for a two-field model. If your count is in the thousands, you are counting the retrieved passages along with the schema; if it is under twenty, you are counting the class source rather than the generated schema, which is several times larger because every description is repeated into it.

Your teacher. Ask your agent to print Answer.model_json_schema() and then to name, field by field, what a model could return that satisfies the schema and is still useless to you. Then ask it to write the two-call extraction shape from section 4 and to run both versions over five of your golden-set questions, showing the answers side by side rather than only the scores.
