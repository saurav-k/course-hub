Three things your system could not do before: refuse, pause, and learn

frontier 8 min The fourth capstone stop. Module 4's six increments, and the three new behaviours each one has to demonstrate rather than claim. · The eval harness

The one-minute version

  • Module 4 added three behaviours the system genuinely lacked: it can refuse, it can pause and resume, and it can learn from its own failures.
  • Each is demonstrable rather than assertable, and each has a test that fails loudly if the behaviour is missing.
  • The golden set grew without you writing the new rows: five unanswerable questions and three failures promoted from real traffic.
  • The retriever is now a surface other processes call, which means it is a second public thing for module 6 to deploy and secure.
  • The gate: kill it mid-approval and it resumes; ask it something the corpus cannot answer and it declines.

1. Refusing is a behaviour, so it needs its own rows

An agent that always answers is an agent that answers when it should not. Module 4 put a grader in front of the generation step so the system can decline, and a decline is only a feature if it is scored.

That is why the golden set gained five questions the corpus genuinely cannot answer, with the correct behaviour recorded as a refusal. Without them a refusal path is untested code that fires in production for the first time.

Two failure modes are worth watching for in your own numbers. A grader tuned too tight refuses answerable questions, which shows up as your ordinary recall rows getting worse while the refusal rows improve. A grader tuned too loose passes everything, which shows up as the five unanswerable questions being answered confidently. Both are visible only because both kinds of row are in one set.

2. Pausing is easy; resuming is the part that breaks

Putting a human approval in front of a side-effecting action is a few lines. Surviving a process death while waiting for that approval is a design decision about where the state lives, and it is the one this stop actually checks.

The test is blunt and takes two minutes: start a run, reach the approval, kill the process, restart it, and approve. If the run completes, the checkpoint is real. If it does not, the pause was in memory and the feature only worked because nothing had gone wrong yet.

One caveat module 4 is careful about and this stop repeats: a checkpointed runtime typically restarts the whole node rather than resuming at the line after the pause. That matters because any side effect before the pause happens twice, so the work either side of an approval has to be idempotent or has to sit after it.

3. The set grew without you writing it

Module 1 had you write thirty questions by hand, and said that was about ninety minutes of work. Module 4 is where the set starts growing faster than you can write it, from two sources that cost you nothing per row.

Unanswerable questions are cheap to invent and can only be written by somebody who knows the corpus, which is you. Promoted failures are free: a feedback endpoint whose records carry the trace id turns a complaint into a reproducible case, and three of those become permanent rows.

The trace id is the load-bearing part. A thumbs-down with no trace id is an opinion; a thumbs-down that names a trace is a row you can add to the set with the retrieved documents and their scores already attached.

4. You now have a second public surface

Exposing the retriever as something other processes call is the increment with the longest tail, because it changes what module 6 has to deploy.

Before, your system had one entry point that you controlled end to end. Now it has two, and the second one is called by clients whose behaviour you do not write. Everything module 6 says about request shapes, health checks, cost ceilings and containment applies to it, and the containment part is the one people forget: a tool surface that other agents call is a place untrusted instructions can arrive from a direction your own product never sends them.

Write that surface into the endpoint table now, while it is fresh. Lesson Ship it asks for that table finished, and a surface missing from it is a surface with no shape, no budget and no probe.

The thirty-nine rows in the chart are the counts modules 2 and 4 add to module 1's thirty, drawn to scale. They are the course's own increments and not a measurement of anything. Your own set will differ, and the only rule that matters is the one from module 1: it grows, nothing is removed, and every number in the course is measured on it.

Check yourself

Retrieval practice

Answer from memory before revealing.

Your approval pause works perfectly in testing. What single test tells you whether it is real?
Everything about an in-memory pause and a durable checkpoint looks identical until the process dies, so killing it mid-wait is the only test that distinguishes them. Double approval and cross-account approval are both worth testing and neither touches durability. Pause duration matters for timeouts rather than for whether the state survives, and a long pause on a healthy process still proves nothing.
Your five unanswerable questions are all being answered confidently. What does that indicate?
Questions chosen because the corpus cannot answer them should produce refusals; confident answers to all five means the grader is passing everything, which is the loose-tuning failure mode. The first two are worth ruling out by re-reading one question against the corpus, and they would not explain all five. The third inverts the point: a system that answers what it cannot know has worse behaviour, not better, and no recall number shows it.

Practice about 40 minutes, with a terminal

Capstonefrontier

Three demonstrations and one table edit. Each demonstration takes minutes and each one has failed for somebody who was sure it would not.

Demonstrate the refusal. Run your five unanswerable questions and confirm all five decline. Record how many of your ordinary rows regressed at the same time, because a grader tight enough to refuse can be tight enough to refuse too much.

Demonstrate the resume. Start a run, reach the approval, kill the process, restart, approve, and confirm it completes. Then check whether any side effect before the pause happened twice.

Demonstrate the promotion. Take one real failure, follow its trace id into a golden-set row, and confirm the row reproduces the failure before you fix anything.

Then add the second surface to the endpoint table from lesson 0600, with its shape and the sentence that justified it.

Hint

If killing the process loses the run, look at where the checkpoint is configured before you look at the code. An in-memory saver is usually the default and is usually what shipped.

If a side effect happened twice, the fix is ordering rather than cleverness: move the effect after the approval, or make it idempotent with a key the caller supplies.

Show what a finished stop looks like
  1. Five refusals and a recorded regression count. The second number is the one people skip. A grader that refuses all five and breaks four answerable questions is not obviously an improvement, and only both numbers together say so.
  2. The kill test passes, or you found a real defect. Either outcome is a good use of two minutes, and the second is more valuable.
  3. One promoted row that reproduces its original failure. If the row passes immediately, the trace id did not carry enough - usually the retrieved document ids and scores are missing, which is the module 1 span attribute this depends on.
  4. The endpoint table has one more row than it did. The retriever surface, its shape, and a note that its callers are not yours.
  5. The set is at least eight rows larger than you hand-wrote, and none of the additions came from a model generating questions from passages.

Sanity check. After adding five unanswerable questions your headline answer score should fall slightly, because the set now contains rows your system used to get credit for answering. If it rose, the refusals are being scored as correct answers, and the grading of the new rows is wrong rather than the system being better.

Your teacher. If the resume test passed on the first try, ask your agent where the checkpoint is actually persisted and what happens if that store is unavailable at restart. If your promoted row did not reproduce its failure, hand it the trace and ask which attribute the row would need in order to be reproducible.
