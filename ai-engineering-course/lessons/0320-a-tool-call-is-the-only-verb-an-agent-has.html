Module 03 · Agents and agentic systems · Lesson 0320

The model emits a name and a JSON object, and it executes nothing

working 9 min Written against the Claude tool-use documentation and the Model Context Protocol schema at revision 2026-07-28, which are two spellings of one shape. · Tool use with Claude

The one-minute version

  • A tool call is not the model doing something. It is the model asking, in JSON, and then waiting.
  • Your code runs the function and hands the result back. Every capability the agent appears to have is a function you wrote on your side of that line.
  • The model gets three things about each tool: a name, a description, and a schema. That is the whole contract, and it is prose plus types.
  • Turning tools on costs tokens before any tool is called: 286 tokens on Claude Opus 5, rising to 406 if you force a call. Those are Anthropic's published figures for its own models.
  • You can take the choice away with tool_choice, which is how you turn one turn of an agent back into a workflow.

1. Nothing executes on the model's side

Both major providers state this plainly and it is still the thing most often misread. Claude's tool-use documentation describes client tools as running in your application: Claude responds with stop_reason: "tool_use" and one or more tool_use blocks, "your code executes the operation and sends back a tool_result". Google's function-calling documentation says the same thing about Gemini in one sentence: the model does not execute the function itself, and you extract the name and the arguments and execute them in your application.

One qualification, because it is the exception that proves the boundary. Claude also offers server tools such as web search, which Anthropic runs on its own infrastructure and whose results arrive in the same response. Those are a hosted convenience, not a different mechanism, and every tool you define yourself is a client tool.

Read the consequence rather than the sentence. The agent's capabilities are a list of functions in your repository. Its permissions are your service account's. Its blast radius is whatever those functions can reach. There is no separate agent identity to reason about until you build one, and module 6 is where that becomes a security question.

2. Three things, and one of them is prose

What the model receives about a tool is small enough to hold in your head. Claude's documentation gives a tool a name, a description and an input_schema. The Model Context Protocol at revision 2026-07-28 spells the same three name, description and inputSchema, and adds two rules worth knowing: tool arguments are always JSON objects, so type: "object" is required at the root, and everything below that may be any JSON Schema 2020-12 keyword, which is the default when no $schema is given.

The description is the half that decides behaviour, and it is out of scope here because a sibling course owns it: The description is behaviour, not documentation is the page to read, and it is worth the click before you write your first one.

The half this page owns is the typed one, and specifically the return. The protocol's Tool also carries an optional outputSchema, and a result may then carry structuredContent alongside its human-readable content. That matters more than it sounds: a retrieval tool whose output is typed can have its passages stored, cited and scored by your own code, while one that returns a paragraph can only be re-read by the model.

3. Turning tools on costs tokens before any tool is used

When a request carries a tools parameter, the API adds a system prompt that enables tool use, and Anthropic publishes what it costs per model. On Claude Opus 5 it is 286 tokens with a tool_choice of auto or none, and 406 if you set any or name a tool. Claude Sonnet 5 is 354 and 474. Claude Haiku 4.5 is 496 and 588.

Those are Anthropic's own published figures for its own models, and they are not a target for anything: they are a fixed overhead you should know about, and the useful reading is the ordering. Forcing a tool call always costs more than allowing one, and the cheaper model is not the cheaper request here.

Add your own schemas on top, which the assembler above prices, and the tool block is the second-largest thing in a request after retrieved text.

4. Taking the choice back

tool_choice is the knob that decides whether this turn is agentic at all. With the default auto, the model decides each turn whether to call a tool or answer directly. Set any and it must call something. Name a tool and it must call that one. Set none and it cannot.

Gemini offers the same three modes under the names auto, any and none, which is the shape to teach and remember; the field names differ between the two APIs, so read whichever one you are writing against rather than trusting a snippet.

The practical use is narrower than it looks. Forcing a call is how you make one turn deterministic - a classification step in a routing workflow, for example, where letting the model answer directly is simply a bug. Claude also exposes disable_parallel_tool_use, which caps a turn at one call and is worth setting whenever your tools have side effects that must be ordered.

The token figures in section 3 are Anthropic's measurement of its own models, published in its own documentation, and they carry a model id because they change with it. Do not carry them into a cost model for another provider, and re-read the table when you change models. Gemini publishes no equivalent figure that this course could open, so no comparison is drawn here.

Check yourself

Retrieval practice

Answer from memory before revealing.

For a tool you define yourself, who executes the function when the model emits a tool call?
A tool you define is a client tool: the model returns a tool_use block and your process runs the operation and sends back a tool_result. The provider's servers execute only Anthropic's own server tools, such as web search, which you did not define. A schema validates arguments and runs nothing. The model has no execution surface at all, which is the whole point of the boundary.
On Claude Opus 5, what does switching tool_choice from auto to any do to the tool-use system prompt?
Anthropic publishes 286 tokens for auto or none and 406 for any or a named tool, a difference of 120. There is a change, so the first option is out. Forcing a call adds instruction rather than removing it, so it cannot halve anything. Your own tool schemas are sent in the tools parameter regardless of tool_choice, and this figure is the preamble on top of them.

Practice about 30 minutes, with a terminal

Practice 1working

This increment makes your existing retrieval function callable by a model, and it is deliberately not the module 4 version.

Bind one tool - your module 2 retrieval function, unchanged - with a name, a description and an input schema carrying query and top_k. Keep the provider behind one adapter so switching costs one edit.

Print the exact bytes your client sends. Not your dictionary: the serialized request. Count the tokens in the tools block and record the number.

Then change one word of the description - swap "matching passages" for "relevant information", or delete the second sentence - and send the same question again. Record whether the model still called the tool, and with what top_k.

Hint

Most SDKs will serialize the request for you without sending it, and if yours will not, an HTTP proxy or a logging transport gets you the same bytes. Reading your own dictionary is the version of this exercise that teaches nothing.

Pick a question where top_k genuinely matters - a comparison across several documents rather than a single lookup - or the argument the model chooses will not move whatever you do to the description.

Show what a good first binding looks like
  1. The serialized request is bigger than the dictionary you wrote. The schema is expanded, the descriptions on each property are sent, and the tool-use preamble from section 3 is added on top and does not appear in your bytes at all. Your recorded number is the part you control, and the published figure is the part you do not.
  2. The default in the schema is a real default and the model reads it. A top_k with a documented range and a default gets sensible arguments. One with a bare integer type gets whatever the model feels, which on a comparison question is often 3.
  3. One word of description changes the plan, and that is the lesson. "Relevant information" invites the model to answer from what it already knows and check afterwards. "Matching passages with their source ids" describes an artefact, and artefacts get fetched. This is why the sibling course spends a whole page on the sentence.
  4. Keep the adapter. One function that turns your internal tool record into the provider's shape is what makes the Gemini comparison a ten-minute exercise later instead of a rewrite, and it is where tool_choice will live when lesson 0330 gives you a reason to force a call.

Sanity check. Your tools block should come out in the low hundreds of tokens for one tool, not in the tens and not in the thousands. Tens means you sent a name and no schema, and the model is guessing at arguments. Thousands means you inlined an example payload into the description, which is a cost you pay on every turn of every request forever.

Your teacher. Give your assistant the serialized tools block you captured and ask it to read the schema back to you as a contract: what must be supplied, what may be omitted, what happens on a value outside the range, and what the tool promises to return. Then ask what it cannot tell from the schema alone. That gap is what the description is for, and it is also what lesson 0330 turns into an error the model can act on.
