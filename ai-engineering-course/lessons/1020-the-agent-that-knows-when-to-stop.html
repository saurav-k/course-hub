A loop with no ceiling is a bill with no upper bound

frontier 8 min The third capstone stop. Module 3's eight increments, assembled into one agent that stops on purpose and can be scored on how it got there. · The eval harness

The one-minute version

  • Module 3 replaced a fixed sequence with a loop. A loop is the first thing in this course that can run away, and everything here is about bounding it.
  • Three ceilings, and behind each a sentence the user sees when it fires. A ceiling with no degradation behind it is a crash with a nicer name.
  • Two boundaries became yours to guard: the tool boundary, where every capability is a function you wrote, and the memory path, which the vendor says your implementation must validate.
  • The harness grew a second and a third axis. A right answer reached by four redundant calls scores the same as a good one until you compare the path.
  • The gate: your agent stops for a reason you chose, and you can name the reason from the trace.

1. Three ceilings, and the sentence behind each

Every agent runtime executes the same short loop and every one of them stops naturally on the same condition: typed output with no tool calls. That exit is the one you do not control, because it depends on the model deciding it is finished.

So you add three you do control - a turn limit, a token limit and a deadline - and the choice between them is a product decision with an owner rather than a default to accept.

The turn limit deserves the most attention because its cost is not linear. Each turn re-sends the entire history, so doubling a ceiling from 8 turns to 16 multiplies prompt tokens by roughly four on lesson 0310's assumptions rather than by two. A ceiling raised "just to be safe" is a bill raised quadratically.

The part people leave out is the sentence. A ceiling with no user-visible degradation behind it is a crash with a nicer name. For each of your three, write what the caller sees when it fires - a partial answer with a note, a handle to resume from, an honest refusal - and write it before you pick the number.

2. Two boundaries that are now yours

The tool boundary. A tool call is the model emitting a name and a JSON object and then waiting. Nothing executes on its side. Every capability your agent appears to have is a function you wrote, which means every capability is also a permission you granted - and that is the sentence module 6's containment lesson picks up directly.

The memory path. The file-backed memory from 0350 is the only store a person can open, diff and correct, and it is an arbitrary file write with a friendly name. The vendor states plainly that your implementation "must validate every path in every command"; nothing upstream does it for you. Your capstone owes a test that attempts a traversal and fails.

The second danger there is quieter and worth carrying into module 6: a memory file is a place where somebody else's words can arrive wearing your agent's handwriting. A fact written during a poisoned session is read back later as the agent's own note.

3. The harness grew two more axes

Module 1's harness scores answers. An agent can reach a right answer through four redundant calls, and that score does not move - so module 3 added a second axis and revealed a third.

Trajectory compares the tool calls made against the ones you expected, under a named match rule, and three rules are enough: exact, in order, and any order. Naming which rule you used is part of the number, exactly as naming k is part of recall@k.

Reliability is the axis nobody looks at until it bites. Yao et al.'s pass^k asks whether all k trials of the same task succeeded, and their best agent scored 61.2% on a single trial and under 25% across eight runs of the same task. That is their measurement on their benchmark, and the transferable part is the shape: an agent that works once is not an agent that works.

All three go into the same golden set. This course does not get a second harness, and the eval harness sheet records what each module adds to the one it has.

The 286-token tool overhead and the pass^k figures are published measurements by Anthropic and by Yao et al. respectively, each on their own models and benchmarks, and each is written that way on the lesson that develops it. The token counts in the stepper and the three scores in the chart are illustrations of a shape rather than measurements of anything. Your own ceilings and your own three scores come from your own runs, which is what module 1's baseline exists to make comparable.

Retrieval practice

Answer from memory before revealing.

You raise the turn ceiling from 8 to 16 "to be safe". What roughly happens to prompt tokens on a long run?
Each turn re-sends the whole history, so the tokens accumulate quadratically in the number of turns rather than linearly, and doubling the ceiling costs about four times as much on lesson 0310's assumptions. The first option is the intuition being corrected. Output tokens do grow, but the prompt side is where the quadratic sits. The last option is a real effect at the margin and nowhere near large enough to reverse the sign.
Your agent answers correctly every time you try it, and your answer score is 1.0. What have you not measured?
An answer score is blind to how the answer was reached and to whether the same task succeeds on every trial, which is exactly why module 3 adds trajectory and reliability. Faithfulness and recall are module 1 metrics that a 1.0 answer score already speaks to. The first option is the failure this stop exists to prevent: "it worked when I tried it" is a single trial, and pass^k is the axis that asks about the other seven.

Practice about 40 minutes, in your own repository

Capstonefrontier

Module 3 left eight commits behind. This stop checks that four specific properties actually hold, because each one is easy to believe and cheap to disprove.

Write the three ceilings down with their sentences. Turn, token, deadline: the number, and what the caller sees when it fires. Then trigger each one deliberately and confirm the caller gets that sentence rather than a stack trace or a hang.

Run the traversal test. Ask the memory tool to write outside its prefix and confirm it is refused. If you do not have this test, write it now; it is four lines and it is the difference between a memory store and an arbitrary file write.

Add expected trajectories to at least five rows of your golden set, naming the match rule you used, and record the trajectory score beside the answer score.

Then run one task eight times and record how many times all eight succeeded. That number is your first reliability reading.

Hint

If a ceiling fires and the caller sees a 500, the ceiling exists and the degradation does not. Those are two separate pieces of work and the second is the one this stop is about.

Pick the match rule before you look at the runs. A rule chosen after seeing the trajectories is a description of those trajectories, which is the same trap lesson 0170 names for a judge rubric.

Show what a finished stop looks like
  1. Three ceilings, three sentences, all three triggered. Most readers find that one of the three has no sentence at all - usually the deadline - and that it currently surfaces as a timeout the caller cannot distinguish from an outage.
  2. The traversal test fails the traversal. If it passes, your handler is trusting a path the model supplied, and that is a file-write vulnerability rather than a memory feature.
  3. The trajectory score is lower than the answer score, and that is normal. An agent that answers correctly by a wandering route is the common case, and seeing the gap is the point of adding the axis.
  4. The reliability number is worse than you expect. Eight-for-eight is a hard bar, and a published agent scored 61.2% once and under 25% across eight. Record yours without adjusting the task until it looks better.
  5. All of it goes into the one golden set. Not a second file, not a notebook. Module 6's CI gate reads this set, and it can only gate on numbers that live in it.

Sanity check. Your trajectory score should be strictly below 1.0 on at least one row, and your eight-trial reliability should be below your single-trial score. If both came out perfect, the expected trajectories were probably written from the runs you observed rather than from what the task requires - rewrite two of them from the task description alone and measure again.

Your teacher. If the three ceilings feel interchangeable, ask your agent which of the three would fire first on your own longest recorded run, and what the caller currently sees when it does. If your trajectory scores came out near 1.0 everywhere, hand it three of your expected trajectories and ask whether each was derivable from the task alone or only from watching a run.
