Most memory bugs are one fact sitting in the wrong store

working 9 min The two-store split is quoted from LangGraph 1.2.x, which names both; the span vocabulary is from the OpenTelemetry GenAI conventions, marked Development throughout. · LangGraph persistence

The one-minute version

  • "Memory" is four stores, and they differ by how long a fact lives and who is allowed to write it.
  • The context window is one of them, and it is the one that charges you rent every turn. The other three charge once.
  • Every runtime ships the same split under different nouns: a thread-scoped checkpoint and a cross-thread store.
  • Putting twenty remembered facts in the system prompt costs about eight times as much over ten turns as fetching the two you need, on the arithmetic below.
  • Retrieving from memory is retrieval, so everything module 1 and module 2 taught you about recall applies here unchanged.

1. Four stores, and what each one is actually for

The context window holds this turn. Everything in it is re-sent on the next turn, so a fact you put here is a fact you pay for once per turn for the rest of the run. Module 2's lesson on the window as an attention budget is the other half of this: it costs money and it also costs attention.

Thread state holds this conversation. It survives between turns without being in the prompt, and it survives a process restart if you back it with a database. It does not survive the conversation ending, and it is invisible to a second conversation with the same person.

A cross-thread store holds this user, or this tenant, indefinitely. It is the first store where a fact learned on Tuesday can be used in December, and it is the first one where you have to decide what may be forgotten.

Files the agent writes hold the project, and they have a property none of the others do: a person can open them. That is worth more than it sounds when something goes wrong, and it is why the next lesson is about them specifically.

2. The same split, under two names

You do not have to take the four-way split on trust, because runtimes ship it. LangGraph at 1.2.x names two of them and defines each in one sentence: checkpointers "persist a thread's graph state as checkpoints" and are for "short-term, thread-scoped memory", while stores "persist application-defined data outside the graph state" and are for "long-term, cross-thread memory". The thread id is what selects the first.

That library is a fixture on this page and not its subject. What matters is that the distinction is forced on anybody who builds this: a conversation needs somewhere to keep its own state, and a user needs somewhere that outlives conversations, and those are different stores with different keys, different growth and different deletion rules. If your own implementation has only one of them, one of the two jobs is being done badly.

3. What keeping it in the prompt costs

Here is the arithmetic that decides the design, and it uses one assumption you should replace with your own. Say you have twenty remembered facts about a user or a tenant, each about 200 tokens, and a typical request needs two of them.

Keeping all twenty in the system prompt costs 4,000 tokens on every turn. Over a ten-turn run that is 40,000 tokens, and nineteen twentieths of them were never relevant. Fetching two on demand costs 400 tokens a turn, plus roughly 100 for the search call, so the same ten turns cost about 5,000. That is an 8× difference on the memory alone, before the retrieved passages your pipeline was already sending.

Anthropic's write-up on context engineering names the effect behind the other half of this, which is not about money: as the number of tokens in the window rises, "the model's ability to accurately recall information from that context decreases". So the expensive option is also the one that dilutes what you kept.

4. Fetching from memory is retrieval, with all of module 2 attached

The moment you fetch two facts out of twenty, you have a retrieval problem: recall, ranking, and a question about what happens when the right fact is not returned. That is the same problem module 2 spent nine lessons on, and the same measurements apply.

Park et al.'s generative-agents paper (arXiv 2304.03442v2) is the primary source worth reading here, and the useful part is the ablation rather than the simulation: they remove observation, planning and reflection in turn and report that each contributes to the behaviour. In other words the store was never the interesting part. The retrieval policy over the store is what carries the behaviour, which is exactly what module 2 would have predicted.

Packer et al.'s MemGPT paper (arXiv 2310.08560v2) supplies the other framing: memory tiers moved in and out of a limited window, borrowed from how an operating system provides the appearance of more memory than it has. Read it for the analogy and not for the implementation.

5. There is already a vocabulary for the spans

You do not have to invent names for what your memory layer does. The OpenTelemetry semantic conventions for generative AI register memory operations alongside the model ones: create_memory, search_memory, update_memory, upsert_memory and delete_memory, plus create_memory_store and delete_memory_store for the store's own lifecycle.

Two things travel with those names every time this course quotes them. They live in a repository that publishes no release and no tag at all, and every document in it is marked Status: Development, so attribute spellings can change. What you are committing to is the shape - one span per memory operation, on the same trace as the model call that needed it - and a rename costs you one file of constants. That is the same bargain module 1 made when it instrumented the retrieval span.

The chart in section 3 is this page's arithmetic over one stated assumption, not a measurement. The claim that recall falls as the window grows is Anthropic's, reported in its own context-engineering write-up on its own models, and it is evidence that the effect is real rather than a threshold for your system. If you want a number for your own corpus, module 1's harness is where it comes from.

Check yourself

Retrieval practice

Answer from memory before revealing.

A fact must still be available in a brand-new conversation next month. Which store is the one that guarantees it?
A cross-thread store is keyed to the user or tenant rather than to the conversation, so a new thread can read it. The context window ends with the turn. The thread checkpoint survives a restart but is keyed to the old thread id, which is exactly the trap: it looks durable and is unreachable. The system prompt is the context window with extra steps, and it charges rent on every turn.
You want one agreed span vocabulary for reads and writes against your memory store. What do the GenAI conventions offer?
The conventions register create, search, update, upsert and delete as distinct memory operation names, plus two for the store's own lifecycle, so a search and a write are told apart in the trace. They are not model-only. One generic span would lose the distinction that makes the trace worth having. Metrics exist too, and the operation names are span operations, which is what the question asked for.

Practice about 30 minutes, with a terminal

Practice 1working

Move one fact out of your prompt, and prove it survived.

Find a fact your capstone currently keeps in the system prompt that is really about one user, one tenant or one corpus rather than about the service. There is almost always one: a default document set, a preferred citation style, a team's own vocabulary.

Write it into a cross-thread store keyed by user or tenant, and fetch it at request time instead. Wrap the read and the write in spans, using the operation names from section 5.

Then restart the process and open a new conversation, and confirm the fact is still applied. Record in docs/shape.md the tokens your system prompt lost, and the number of memory spans one request now produces.

Hint

Do not build a memory service. A table with a tenant key, a name, a value and an updated timestamp is a cross-thread store, and it is the right size for this exercise.

If you cannot find a fact to move, look at the sentences in your system prompt that begin with "always" or "this team". Those are usually facts about one caller wearing a rule's clothes.

Show what a good first move looks like
  1. The fact you find is usually a default, not a preference. "Cite the 2019 policy set unless asked otherwise" reads like an instruction and is a fact about one tenant, which is why it was in the prompt: instructions go there and facts do not.
  2. The read has to be conditional or you have moved nothing. Fetching every stored fact on every request is the system prompt again, in a slower place. The read should be keyed on the request, and if you cannot key it yet, that is what module 4's retrieval-as-a-tool lesson solves.
  3. The spans are what make the next decision arguable. Once a request shows one search_memory span returning two rows, you can ask whether the right two came back, which is a recall question and one your module 1 harness already knows how to answer.
  4. The restart is the test that matters, and it is the one people skip. A store held in a process dictionary passes every unit test and loses everything on the first deploy. Restarting before you believe it takes ten seconds.

Sanity check. Your system prompt should have got measurably shorter and your request should now carry one or two memory spans. If the prompt is the same length, you copied the fact rather than moving it, and you are now paying for it twice.

Your teacher. Paste your current system prompt to your assistant and ask it to split every line into two lists: instructions about how the service should behave, and facts about a particular user, tenant or corpus. Then ask which of the four stores each fact belongs in, and why. The disagreements are the interesting part - especially any fact it puts in a file rather than a store, because that is the one somebody will eventually need to correct by hand.

Primary source to go deeper

The two-store split in the words of a runtime that implements both: Persistence, LangGraph 1.2.x. For memory as an architecture rather than a store, with the ablation that shows the retrieval policy is what carries the behaviour: Generative Agents, Park et al., v2. For the span names, read them with the Development banner in view: the OpenTelemetry GenAI semantic conventions.
