Choose where the loop stops, or your provider's timeout will choose for you

working 8 min The loop's shape is quoted from a runner that documents it, the OpenAI Agents SDK at 0.22.0, as evidence that the shape is real rather than as the subject. · Running agents

The one-minute version

  • Every agent runtime executes the same four-line loop, and every one of them stops on the same condition: typed output with no tool calls.
  • You get three ceilings on top of that: a turn limit, a token limit and a deadline. Choosing between them is a product decision and it has an owner.
  • The reason the turn limit matters more than it looks: each turn re-sends the entire history, so the cost of a run is quadratic in its turns, not linear.
  • Doubling the ceiling from 8 turns to 16 multiplies the prompt tokens by about four on the assumptions below, not by two.
  • A ceiling with no user-visible degradation behind it is a crash with a nicer name. Write the sentence, then the number.

1. The loop, and its one natural exit

Runtimes differ in almost everything and agree on this. The OpenAI Agents SDK at 0.22.0 documents its runner as a numbered loop, and the numbering is worth reading because it is the shape underneath every framework you will meet: call the model with the current input; if the output is final, return it; if it is a handoff, swap the agent and re-run; if it produces tool calls, run them, append the results, and re-run.

The interesting line is the definition of final, which that runtime states as text output of the desired type with no tool calls. That is the loop's only natural exit, and it is a property of the model's output rather than of your task being done. So the loop ends when the model stops asking for things. It does not end when the answer is good, and nothing in the loop is checking.

Everything else is a wall you build. The same runtime raises a MaxTurnsExceeded exception when the configured turn count is passed, which is the first of the three.

2. Why a turn ceiling is not a linear budget

Here is the part that surprises people who have only priced single-shot calls. The model is stateless, so every turn sends the whole conversation again: the system prompt, the tool schemas, the question, and every assistant message and tool result produced so far.

Work it with four assumptions and substitute your own afterwards. Say the system prompt and tool schemas come to 500 tokens, the question is 20, each assistant turn adds about 150 tokens, and each tool result adds about 400. Every completed turn therefore adds roughly 550 tokens to the history that the next turn must re-send.

Turn n sends 520 + 550(n − 1) prompt tokens, so a run of N turns sends 520N + 550 × N(N − 1)/2 in total. At N = 8 that is 19,560 prompt tokens. At N = 16 it is 74,320. Doubling the ceiling multiplied the bill by 3.8, and the naive estimate of 520 tokens a turn would have said 8,320.

3. Which of the three walls your product actually needs

A turn ceiling is the one to reach for first, because it is the only one that maps onto the thing going wrong. Loops fail by repeating, and a repeat costs a turn.

A token ceiling is what you need when tool results vary wildly in size. One retrieval that returns a hundred passages can blow a context window inside three turns while the turn counter reads three, and the model then fails on a length error rather than on your rule.

A deadline is what a user-facing request needs, because a person waiting has a limit that is not measured in tokens. It is also the only one of the three that survives a slow provider.

Set all three. They are cheap, and they fail in different directions.

4. What an unbounded loop looks like before it looks expensive

Two of the failure modes catalogued in the multi-agent failure study by Cemri et al. (arXiv 2503.13657v3) describe this precisely, and they were observed rather than imagined: the study's taxonomy names a mode for an agent that does not recognise the criteria for stopping, and another for unnecessarily repeating steps already completed. Those two are the same trace read twice.

You already have the instrument. Your module 1 trace has one span per model call, so an agent run is a span count, and a run whose span count sits at the ceiling is a run that did not finish - it was cut off. That distinction never appears in the answer, which is why the ceiling needs a message.

Write the degradation before the number. "I could not finish this within the budget for one question, and here is what I found so far, with the two passages I did retrieve" is a product. An exception that reaches a user as a 500 is not, and the two differ by about six lines of code.

Both lines on the chart in section 2 are this page's arithmetic over four stated assumptions, not a measurement of any system. Substitute your own system-prompt size and tool-result size before you quote a number from it to anyone. What is not an assumption is the shape: any loop that re-sends its history is quadratic in turns, and that follows from the mechanism rather than from the numbers.

Check yourself

Retrieval practice

Answer from memory before revealing.

In the runner loop quoted in section 1, what makes an output the final one?
The documented rule is text output of the desired type with no tool calls, so both halves matter: untyped text is not final and typed text alongside a tool call is not either. A model that stops emitting text has produced nothing to return. A successful tool result is exactly the case that sends the loop round again. A handoff also re-runs the loop, with a different agent, so it is the opposite of an exit.
On section 2's assumptions, raising the turn ceiling from 8 to 16 multiplies the run's prompt tokens by roughly what?
19,560 tokens becomes 74,320, which is about 3.8 times, because turn n carries every earlier turn with it. Doubling would be right only if each turn cost the same as the first. Caching changes the price of the re-sent tokens and not their count, and it is module 6's subject rather than a reason the count stays flat. Eight would be the extra turns counted at the first turn's price, which is the naive line on the chart.

Practice about 30 minutes, with a terminal

Practice 1working

Put the wall in, then walk into it on purpose.

Add all three ceilings to your capstone's agent path: a turn count, a token count for the whole run, and a deadline. Put them in one configuration object, not scattered through the call sites, and read them at the request boundary rather than inside the agent.

Then set the turn ceiling to two and send a question that genuinely needs three or four tool calls. Catch whatever your runtime raises, and return the partial answer with an honest sentence rather than an error.

Record two numbers in docs/shape.md: the prompt tokens your run actually spent at the ceiling you shipped, read from the trace, and the number the same run would spend at twice that ceiling. Compute the second one, do not measure it.

Hint

The deadline is the one that is easy to get wrong. A per-request deadline that is not also passed to the provider client leaves you cancelling a call the provider is still billing you for.

For the second number, you do not need the exact formula from section 2. Sum the prompt-token counts your trace already records, per turn, and extend the pattern by the same per-turn growth you measured.

Show what a good ceiling looks like
  1. One config object, read once, at the boundary. A turn limit buried in the agent constructor is a limit that a second call site silently does not have. Reading it where the request arrives is also what lets a future admin endpoint raise it for one tenant without a deploy.
  2. The degradation is the deliverable, not the exception. The test is whether a user who hits the ceiling gets something they can act on: what was found, what was not, and whether retrying is worth their time. If the honest answer is "nothing useful", say that, and say it in one sentence.
  3. The measured number will be lower than you expect and the projected one higher. Most requests finish in two or three turns. The ceiling is not the average, it is the promise, and the two get confused in exactly the meeting where the bill comes up.
  4. Write down which wall fired. A run that ended on the deadline and a run that ended on the turn count are different defects with different fixes, and by the time it reaches a dashboard they look identical unless you recorded which one it was.

Sanity check. Your projected cost at double the ceiling should be roughly three to four times the measured one, not two. If you got two, you extended the average per-turn cost rather than the growing one, and the growth is the whole point of the exercise.

Your teacher. Hand your assistant the per-turn prompt-token counts from one real run of your own agent and ask it to fit the growth, then to say what the run would cost at ceilings of 8, 16 and 32. Then ask the harder question: which of the three walls should fire first for your product, and what the user sees in each case. If it answers with three numbers and no sentences, ask it for the sentences.

Primary source to go deeper
