Module 04 · From basic to agentic RAG · Lesson 0410

A system that cannot refuse will always answer

working 11 min Grounded in the paper that put a lightweight evaluator between retrieval and generation, read at v3. · Corrective RAG

The one-minute version

  • The pipeline you have will answer every question, including the ones your corpus cannot answer. Fluently. That is the failure this lesson closes.
  • Corrective RAG puts a lightweight retrieval evaluator between the two halves, returning a confidence degree that triggers different retrieval actions.
  • The evaluator buys you a refusal path, and the design move is to make "I could not find this" a first-class answer with its own eval cases rather than an error.
  • The same principle governs tool errors: an error the model cannot see is an error it cannot correct, so a failed retrieval belongs in the result, not in an exception.
  • The evaluator is a second model call on the request path, so it has a bill and this page works it out.

1. The failure this closes

Your retrieval is good now. Recall at ten moved through module 2 and you can defend it. And on any question whose answer is simply not in the corpus, the pipeline still returns ten passages, and the model still writes a confident paragraph out of the nearest ones.

This is not a hallucination in the sense people mean. The model did what it was asked: it wrote an answer grounded in the passages it was given. The passages were wrong for the question, and nothing in the system was responsible for noticing.

Lesson 0170's metric for it is noise sensitivity, which asks how much an irrelevant retrieved passage degrades the answer. This lesson is what moves that number.

2. The published shape

Corrective RAG adds what its abstract calls a lightweight retrieval evaluator: it assesses the overall quality of the retrieved documents for a query and returns a confidence degree, on which different knowledge retrieval actions are triggered.

The paper describes three outcomes from that confidence, and this course does not name its three labels, because the abstract does not enumerate them and nobody here has read the paper's body. What the abstract does state is two of the mechanisms: large-scale web search is used as an extension when the internal retrieval is not good enough, and a decompose-then-recompose step selectively keeps the key information from retrieved documents and filters the rest.

The transferable design is smaller than the paper and easier to build: score the retrieved set before generating, and branch on the score. A cheap model, or even a cross-encoder you already have from lesson 0270, is enough to say whether these ten passages plausibly contain an answer to this question.

3. The refusal is the point

Of the three exits, the one that changes the product is the refusal, and it is the one teams leave out because it feels like admitting defeat.

It is the opposite. A system that says "I could not find this in the handbook" is more useful than one that guesses, because a user can act on it: they escalate, they search themselves, they tell you the document is missing. A confident wrong answer costs them the time to discover it is wrong, plus whatever they did in the meantime.

Make it a first-class answer with its own eval cases. Add unanswerable questions to the golden set from lesson 0160, with the expected behaviour being a refusal, and now refusing correctly is something you measure rather than hope for. Without those rows, every change you make will quietly push the system back toward answering everything, because that is what every other metric rewards.

4. A failed retrieval is a result, not an exception

The fault-tolerance half of this lesson is one rule with a wide reach. When the store times out, the reranker fails, or the grader itself errors, the temptation is to raise an exception and return a 500.

Inside a tool-using loop that is the wrong shape, and the reason is stated plainly in the Model Context Protocol specification at revision 2026-07-28: an error originating in the tool should be reported inside the result with an error flag set, not as a protocol-level error response, because otherwise the model cannot see that an error occurred and self-correct. A failed tool call is a result, not an exception is where that argument is made in full; this page is where it lands on retrieval.

So: a store timeout comes back to the model as "the search failed, no results", and the model can try a narrower query or refuse. A store timeout raised as an exception ends the request and tells the user nothing. Everything else about retries, timeouts and circuit breakers is general engineering that Resilience Patterns owns, and module 6's lesson 0610 owns what is different when the dependency is a model provider.

5. What the grader costs

The grader is a model call on the request path, so it adds latency to every question and money to every question, including the ones that did not need it.

The arithmetic is worth doing before you build it. A grader that reads ten passages is reading roughly the same input as the generator: call it 4,000 input tokens for the passages plus a short instruction, and perhaps 10 output tokens if you ask for a single score. Against a generation call of the same 4,000 input and 300 output, the grader is close to a doubling of input tokens and almost no extra output.

Three ways to make it affordable, in the order worth trying. Grade fewer passages than you generate from, because deciding whether an answer is present needs less evidence than writing one. Use a smaller model, since this is a classification task and not a writing task. Reuse the reranker you already run: a cross-encoder score below a threshold you calibrate on your golden set is a grader with no extra model call at all, and it is the version to build first.

Check yourself

Retrieval practice

Answer from memory before revealing.

Your store times out inside a tool-using loop. What should the model receive?
An error the model cannot see is an error it cannot correct, so the failure belongs in the result where the model can read it and try a narrower query or refuse. A protocol error ends the turn and the model never learns anything happened. An empty list with no explanation is indistinguishable from a corpus that has no answer, which sends the model down the wrong branch. Serving another question's passages is a correctness bug, not a fallback.
Why does the refusal path need its own rows in the golden set?
Recall, faithfulness and relevance all improve when the system answers, so without cases where refusing is the correct behaviour, every future change quietly pushes it back toward answering everything. Refusals are usually faster, not slower, and timing is not why. A judge is no more reliable on refusals than on anything else. Refusals are easy to grade automatically, which is precisely why adding the rows is cheap.

Practice about 45 minutes, with a terminal

Practice 1working

Give the system a way to refuse, and prove it uses it.

First, add five unanswerable questions to your golden set: questions in your domain whose answer is genuinely not in your corpus. Record the expected behaviour as a refusal. Run them now, before building anything, and record how many produce a confident answer. That number is what this lesson is fixing.

Then build the grader as a threshold on the reranker score you already compute, calibrated on your golden set, with three branches. Re-run the whole set, and report recall at 10 unchanged, refusals correct out of five, and false refusals on the answerable questions.

Hint

Calibrate the threshold on the answerable questions first: find the score below which your known-good passage almost never sits. That is your floor, and starting from the score distribution you already have costs nothing and beats guessing a number.

Watch the false refusals harder than the correct ones. A grader that refuses everything scores five out of five on the new rows and has destroyed the product.

Show what the two numbers together mean
  1. Before the grader, expect four or five of the five unanswerable questions to get a confident answer. That is the normal, healthy-looking state of a pipeline that has no refusal path, and seeing it on your own corpus is the point of running them first.
  2. Report correct refusals and false refusals as a pair, always. Either number alone is gameable in opposite directions: a threshold at the top refuses everything, a threshold at the bottom refuses nothing, and only the pair shows you the trade. This is the same discipline as recall and precision and it is the same mistake if you drop one.
  3. A false refusal on a question the system used to answer correctly is a regression, even though the answer is now honest. Treat it as one. If the threshold costs you more correct answers than it prevents wrong ones, it is set too high, and your golden set is what tells you.
  4. Grade fewer passages than you generate from. Start at three. If grading the top three gives the same verdict as grading ten on your golden set, you have the same quality at a third of the added input cost, and the calculator above shows what that is worth per day.
  5. Record the grade on the retrieval span. It is the input to lesson 0430's triage: a wrong answer that the grader rated highly is a different defect from one it rated poorly and answered anyway.

Sanity check. If your grader refuses zero of the five unanswerable questions, the threshold is below the noise floor of your scores and is doing nothing; if it refuses any of your original thirty, check those by hand before adjusting, because one or two of them may genuinely be unanswerable and you have found a defect in the golden set rather than in the grader.

Your teacher. Ask your agent to write five questions that sound exactly like your corpus but whose answers are not in it. Those are much harder than obviously out-of-domain questions and they are what your users will actually ask. Then ask it to look at the retrieval scores for those five beside five answerable ones, and to propose the threshold. Check its reasoning against your own distribution rather than taking the number.
