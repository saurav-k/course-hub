The word "cache" is doing four jobs in your architecture diagram

working 9 min Multipliers, breakpoint limits and the invalidation order are Anthropic's published documentation for its own API; the base price used in the arithmetic is this page's assumption. · Prompt caching

The one-minute version

  • Four different mechanisms are all called caching, at four layers, with four different owners. Naming them separately is most of the work.
  • The provider's prompt cache is the one with the best return and the one teams most often fail to use, because it needs the prompt ordered rather than configured.
  • The published multipliers make the arithmetic exact: a write costs 1.25x at the five-minute lifetime and 2x at the hour, a read costs 0.1x.
  • From those two numbers, the five-minute cache pays from the second request and the hour-long one from the third. Everything after that is nearly free.
  • Invalidation is not a timer, it is an ordering rule: tools, then system, then messages, and a change at any level invalidates that level and everything after it.

1. Four mechanisms, named apart

The exact-match response cache is ordinary. The same question arrives, byte for byte, and you return the stored answer without calling anything. It is a dictionary with a key you chose, it is completely under your control, and its hit rate on real traffic is usually disappointing because people do not repeat themselves exactly. It is still worth having, because when it hits it costs nothing at all.

The semantic cache relaxes "byte for byte" into "close enough", which is a much bigger promise and a much bigger risk. Lesson 0640 is entirely about that risk and it is the only lesson in this module about a technique you might decide not to ship.

The provider's prompt cache is different in kind: you never read from it and never write to it directly. You mark part of your prompt, and if a later request begins with the same marked prefix the provider charges you far less for it. You cannot inspect it, you cannot invalidate it on purpose, and the only lever you have is the order of your own prompt.

The serving engine's KV cache is the attention key-value state reused across steps and, with prefix caching, across requests. If you call a hosted API you cannot see it and it is not your concern; if you run the engine, it very much is, and LLM Inference Optimization, KV cache eviction and long context owns it.

2. The prompt cache, in exact arithmetic

This is the layer worth doing arithmetic on, because the numbers are published rather than estimated. Anthropic documents that cache write tokens cost 1.25 times the base input price at the five-minute lifetime and 2 times at the one-hour lifetime, and that cache read tokens cost 0.1 times the base input price.

So take a prefix that would otherwise cost 1 unit each time it is sent. Sending it N times uncached costs N. Sending it with a five-minute cache costs 1.25 for the first request and 0.1 for each of the others: 1.25 + 0.1(N-1). Setting those equal gives 1.15 = 0.9N, so N is about 1.28 - which means the cache is already cheaper at the second request. For the hour-long lifetime the write is 2 rather than 1.25, the break-even is about 2.11, and it pays from the third.

That is a startlingly low bar, and it is why failing to use this layer is the most common avoidable cost in an AI application. It is also why the interesting question is never "is it worth caching" but "why is my prefix not stable enough to cache".

3. The cache is bought with prompt order, not with configuration

Here is the part that catches people. A prompt cache matches a prefix. If anything early in your prompt changes per request, nothing after it can be cached, however stable that later material is.

Anthropic documents the hierarchy explicitly: prefixes are created in the order tools, then system, then messages, and a change at one level invalidates that level and every level after it. So a tool definition that varies per user invalidates the system prompt and the messages too, even though neither of them changed.

That turns prompt assembly into a sorting problem. Everything invariant goes first - tool definitions, the system prompt, the long policy document, the few-shot examples - and everything per-request goes last, which for a RAG application means the retrieved passages and the question. If your current code interpolates the user's name into the system prompt, that one substitution is costing you the entire cache.

The mechanism has published limits worth knowing before you design around it: at most four explicit cache breakpoints, a lookback window of 20 blocks, and a minimum cacheable prefix that varies by model from 512 to 4,096 tokens - so a short prompt marked for caching is simply not cached, and no error tells you.

4. Implicit, explicit, and what does not transfer

The two providers this course writes against expose the same idea with different defaults, and the difference is worth one paragraph so that a reader does not carry an assumption across.

Anthropic's is explicit: you mark a breakpoint with cache_control and you can see what happened, because the response reports cache_creation_input_tokens and cache_read_input_tokens separately from ordinary input tokens. That readback is the whole reason the hands-on exercise below is possible.

Google's Gemini offers implicit caching, documented as enabled by default for Gemini 2.5 and newer models, with a minimum of 2,048 tokens on 2.5 Flash and Pro and 4,096 on the 3.x models, and hits reported in usage.total_cached_tokens. The prefix discipline in section 3 applies just as much: an implicit cache still matches a prefix, so it still rewards the same sorting.

What does not transfer is the arithmetic. The 1.25x, 2x and 0.1x multipliers are Anthropic's published rates for Anthropic's API. This course does not state a Gemini discount figure, because the documentation read for it carries the minimums and the implicit-explicit split and does not carry a rate. Look it up for your provider rather than assuming the numbers above.

Every multiplier, limit and minimum on this page is Anthropic's published product documentation for its own API, read at the page linked below, and every one of them can change without changing this lesson's argument. The dollar figures in the calculator rest on an assumed base price of $3 per million input tokens, which is this figure's assumption and nobody's published rate. The tenfold gap between its two readings is the documented read multiplier and stands on its own.

Check yourself

Retrieval practice

Answer from memory before revealing.

Your system prompt interpolates the signed-in user's display name. What does that one substitution cost you?
Invalidation runs forward through the documented hierarchy, so a change in system invalidates system and messages while leaving tools intact. The first option is the intuition being corrected: the cost is not the size of the change, it is everything downstream of where it sits. Tools come before system and survive. And the cache matches a prefix rather than a block, so the damage never stops at the block that moved.
Using the published multipliers, at which request does a five-minute cached prefix become cheaper than sending it uncached?
A write costs 1.25 and each read 0.1, so N sends cost N uncached and 1.25 plus 0.1 times N minus one when cached. Those are equal at about 1.28 requests, so the second request is already cheaper. The fourth is the answer for the one-hour lifetime rounded up twice, and the two larger numbers are what people guess when they assume a cache needs a high hit count to pay, which is true of caches whose write cost is a whole extra request rather than a quarter of one.

Practice about 40 minutes, in your own repository

Practice 1working

This is a sorting exercise with a readback, and the readback is what makes it real rather than plausible.

Print your current prompt in assembly order and label every block with how often it changes: never, per user, per session, per request. Most readers find at least one block that changes more often than it needs to.

Re-sort it so that everything invariant precedes everything variable, and move any per-request interpolation out of the system prompt and into the messages.

Place one breakpoint at the end of the stable region, send the same conversation twice, and read cache_creation_input_tokens and cache_read_input_tokens back from both responses. The first request should report a write and the second a read of about the same size.

Hint

If the second request reports a write rather than a read, something in your prefix moved between the two. A timestamp, a request id, a randomised example order, or a set serialised in a different order each time are the four usual causes, and the last one is the hardest to spot.

If both requests report neither a write nor a read, your prefix is probably below the model's minimum. Check the per-model minimum before assuming the breakpoint is wrong.

Show what a finished restructure looks like
  1. The block table comes first and is the real deliverable. Four rows of "never, per user, per session, per request" over your own prompt. The sorting is obvious once the table exists and impossible to reason about before it does.
  2. Retrieved passages belong at the end, with the question. They change every request by construction, so anything placed after them is uncacheable and anything placed before them is fine. Readers who put retrieved context near the top for readability pay for that choice on every request.
  3. The readback is the proof and the numbers should be close. A write of roughly the prefix size on the first request, a read of roughly the same on the second. If the read is much smaller than the write, your breakpoint is earlier in the prompt than you intended.
  4. Record the hourly saving beside the latency budget from lesson 0620. Prefix tokens times requests an hour, times nine tenths of your base input rate. It is usually the largest single line item this module produces.
  5. Do not add the response cache yet. The prompt cache costs you a sort and no correctness risk. The next two layers up cost correctness risk, and lesson 0640 is about measuring it before you accept it.

Sanity check. Your reported cache read on the second request should be close to the size of the region before your breakpoint, and your ordinary input tokens on that request should be close to only the question and the retrieved passages. If ordinary input tokens are still nearly the whole prompt, the cache is not being hit at all and no amount of cost arithmetic will show it - fix the readback before trusting any saving.

Your teacher. If the four layers still blur, ask your agent to take your own architecture and say, for each of the four, whether you have it, who operates it, and what would prove it is working. If the ordering rule felt abstract, hand it your actual prompt assembly code and ask it to list every value that changes per request and where in the prefix each one currently sits.
