Module 02 · Retrieval quality and context engineering · Lesson 0200

You cannot fix a corpus you can only rebuild

working 10 min Grounded in the Docling technical report, read at arXiv:2408.09869v5, and in the pgvector README at tag v0.8.6. · arXiv:2408.09869

The one-minute version

  • Module 1 left you a baseline. Every lesson in module 2 changes one thing and re-runs the same golden set, and the first thing to change is the pipeline that made the corpus.
  • Ingestion has four stages - fetch, parse, split, embed - and parsing is where most corpora lose their answers, silently, before retrieval has run once.
  • A chunk needs an identity: a stable id, the source it came from, where in that source it sat, and a checksum. Without one it cannot be deleted, re-embedded or cited.
  • The checksum is what makes re-ingestion idempotent. Run the script twice and the row count must not move; that is the test, and it is one SQL query.
  • None of this moves recall on its own. It is what makes every later change in this module reversible and attributable.

1. The stage that loses the answer

Ask somebody where their retrieval pipeline goes wrong and they will name the embedding model or the top-k. Open the parsed text of ten documents from their corpus and you will usually find the answer somewhere else: a table read left to right into one long line of numbers with no column headings, a two-column page interleaved paragraph by paragraph, a figure caption glued onto the sentence above it.

This is not a formatting complaint. A table flattened into prose is an answer destroyed before retrieval ever runs, and no reranker recovers it, because the fact is no longer in the corpus in a form anything can match.

The fix is to treat parsing as what it is. Docling, the MIT-licensed converter whose technical report is arXiv:2408.09869v5, describes itself as "powered by state-of-the-art specialized AI models for layout analysis (DocLayNet) and table structure recognition (TableFormer)". Layout analysis and table structure recognition are models with published names, not regular expressions you were too lazy to write. Whatever converter you pick, the question to ask it is whether it has one, and the way to find out is to read ten parsed documents rather than the tool's own README.

2. A chunk is a record, not a string

Most first pipelines store a chunk as text plus a vector. That is enough to answer a question once and not enough to do anything afterwards.

Four questions arrive within a week of shipping, and each one needs a field the string does not have. This document was withdrawn - delete its chunks needs a source. We changed embedding model - re-embed only what changed needs a checksum. The answer cited something - where in the document is it needs an offset. Two chunks say opposite things - which is newer needs both.

So a chunk is a record with an identity, and the identity is derived rather than generated. A random UUID is a new identity on every run, which means every re-ingest is a full rebuild. Derive the id from the source uri and the chunk's offset in that source, and the same chunk keeps the same id forever, which is what lets you compare two runs at all.

3. Running it twice must change nothing

An ingestion script you are afraid to run is a corpus you cannot fix. The property that removes the fear is idempotency: ingesting the same document twice leaves the index exactly as it was after the first time.

The checksum is what decides. Hash the source document on fetch. If the hash matches what is already stored, skip it entirely - no parse, no split, no embedding call, no row written. If the hash differs, delete every chunk whose source_uri is that document and write the new ones. If the source is gone, delete its chunks. Three branches, and the last two are the reason a chunk needs a source in the first place.

Here is the arithmetic that makes the point, on assumptions you should replace with your own. Take a corpus of 500 documents producing 1,000 chunks, ingested three times, with one document edited between the second run and the third; that document holds four chunks. An append-only pipeline writes 1,000 rows each time and ends at 3,000, of which two thirds are duplicates competing with each other for the same top-k. A checksum-keyed pipeline ends at 1,000, having rewritten four rows. The gap is not a performance difference; it is the difference between a corpus and a pile.

One vendor-specific trap goes with this, and it is worth reading before you build. The pgvector README, at tag v0.8.6, states plainly that "with approximate indexes, filtering is applied after the index is scanned. If a condition matches 10% of rows, with HNSW and the default hnsw.ef_search of 40, only 4 rows will match on average." Filtering by corpus_version is exactly such a condition. Storing the field is right; filtering on it inside an approximate search is where you spend a recall budget you have not measured, and lesson 0140 is where that arithmetic was done.

4. What this changed, and what it did not

Re-run the golden set from module 1 now, before anything else in this module. On most corpora the number does not move, and that is the honest result to write down: identity and idempotency are not a retrieval improvement.

What they change is what the next six lessons are worth. A chunk-size sweep you cannot re-run is one measurement. A contextualisation pass you cannot roll back is a corpus you now have to rebuild from scratch. Every delta in this module is a comparison of two ingests, and a comparison needs both sides to be reproducible.

If the number did move, look at the duplicates. A corpus that had been ingested several times was answering from three copies of the same passage, and deduplicating it changed the top-k for every question at once. That is a real gain and it belongs in the table with the others.

The whiteboard framing of corpus freshness and re-ingestion, which is the version of this argument you would give in a design discussion rather than at a terminal, is Document freshness in AI System Design for Staff+ Interviews.

Check yourself

Retrieval practice

Answer from memory before revealing.

Your ingest gives every chunk a fresh UUID on each run. Which operation becomes impossible?
A fresh id every run means no row in the new ingest can be matched to a row in the old one, so "only what changed" has no meaning and every re-ingest is a full rebuild. Searching still works, because search does not care what a row is called. Counting rows and reading text back are both properties of a single run and are unaffected. The identity is not for the reader; it is for the diff between two runs.
A question about a figure in a report returns nothing, at any top-k. What do you look at first?
If the parse dropped or scrambled the figure, the fact is not in the corpus and no retrieval setting can return it, so reading the parsed text is the only check that can distinguish "not retrieved" from "not present". A bigger embedding model, a larger k and a different metric all assume the passage exists and rank badly, which is the second hypothesis rather than the first.

Practice about 40 minutes, with a terminal

Practice 1working

This is module 2's first increment to your capstone, and everything else in the module rests on it.

Rewrite your ingestion as four named stages - fetch, parse, split, embed - and make each chunk a record with a derived chunk_id, a source_uri, a char_offset, and the source document's sha256.

Then prove idempotency. Count the rows in your index. Run the whole ingest again over the unchanged corpus. Count again. The two numbers must be identical, and if they are not, the ingest is appending rather than replacing.

Then prove incremental update. Edit one document, re-run, and confirm that only that document's chunks changed and the total moved by exactly the difference in that document's chunk count.

Finally, re-run the module 1 golden set and record recall@10 next to the baseline, whatever it does.

Hint

Derive the id rather than generating one: sha1(source_uri + ":" + char_offset), truncated, is enough and needs no counter and no coordination.

The delete-then-write branch is easier to get right than an upsert, because a document that lost a paragraph has fewer chunks than it did and an upsert leaves the extra ones behind.

Show what a good result looks like
  1. The row count is the test, and it is one query. SELECT count(*) FROM chunks; before and after. Two identical numbers is the whole proof, and it takes ten seconds to re-run whenever you touch the pipeline.
  2. The second run should be fast, not merely harmless. If it takes as long as the first, the skip branch is not firing and you are paying for embeddings you already have. Time both runs and compare.
  3. The edited document is the sharper test. If it had 6 chunks and now has 5, the total must fall by exactly 1. A total that rises by 5 means the delete branch is missing; a total that does not move means the checksum was never recomputed.
  4. Write the golden-set number down even when it did not move. "Recall@10 unchanged at 0.61 after the ingest rewrite" is the row that makes the next six deltas mean something. A table in which every change helped is a table nobody measured.

Sanity check. If your second run wrote zero rows and your row count is unchanged, but the run took as long as the first, you are re-parsing and re-embedding before comparing the checksum. Move the hash comparison to immediately after fetch, where it can skip the expensive stages rather than merely discard their output.

Your teacher. Ask your agent to take ten documents from your own corpus, print the parsed text of each, and list every place where a table, a figure caption or a multi-column layout has been flattened. Then ask it, for each one, which question in your golden set that damage would make unanswerable. If it cannot name one, your corpus may genuinely be plain prose, which is worth knowing before you pay for a better parser.
