The runtime restarts the node, so your side effects run twice

working 11 min Mechanics and the resume caveat from the LangGraph interrupt documentation, at 1.2.x; the protocol equivalents at MCP revision 2026-07-28 and A2A 1.0. · LangGraph interrupts

The one-minute version

  • An input() call is not human-in-the-loop. A real approval takes hours or days, and nothing you own should be blocked for that long.
  • A pause is a persistence problem: write the state, return, and let a later process resume it from a key.
  • The caveat that costs everyone an afternoon: on resume the runtime restarts the whole node from the beginning, so anything before the pause runs again.
  • That makes idempotency a requirement of any node containing an interrupt, not a nicety, and it decides where you put the pause.
  • Three independent designs put the resumption state outside the paused process, which is why this is a mechanism rather than one framework's feature.

1. Why blocking is not an option

The obvious implementation is to stop and wait. In a notebook that works, and it is how most examples show it, because an example's approval arrives two seconds later from the person who wrote it.

A real approval is a person who is in a meeting, then at lunch, then gone until tomorrow. Blocking for that means a held process, a held connection and a held database transaction if you were unlucky, and it means a deploy kills the run. Module 6's lesson 0600 works through the request shapes for work that outlives a response, and a human approval is that problem with the duration multiplied by ten thousand.

So the pause has to be a write. The run stops, its state goes somewhere durable under a key, and the process is free. Later, anything holding that key can resume it.

2. The mechanism, in one implementation

LangGraph at 1.2.x is the worked example here, and this course uses it as a fixture rather than a subject: what matters is the shape, and you should be able to rebuild it on anything with durable storage.

interrupt() called inside a node stops the graph and hands a value back to the caller. The runtime saves the state through a checkpointer, identified by a thread_id. The documentation is explicit about what the checkpointer buys: it writes the exact graph state so you can resume later, even from an error state.

Resuming is a second invocation carrying Command(resume=...), and the value you pass becomes the return value of the original interrupt() call.

3. The caveat, quoted

Here is the sentence to read twice, from the documentation itself: when execution resumes, the runtime restarts the entire node from the beginning - it does not resume from the exact line where interrupt was called. Any code that ran before the interrupt will execute again.

Think about what is usually above an approval prompt. A retrieval, which is harmless to repeat. A model call, which is merely expensive to repeat. And, in the code people actually write, the thing being approved: the draft was generated, the ticket was created, the email was composed and saved. All of it runs a second time on resume.

Two rules fall straight out. Put nothing with a side effect above an interrupt in the same node: do the work in one node, pause in the next. And where you cannot avoid it, make the side effect idempotent with a key derived from the run rather than from the clock, exactly as an at-least-once queue consumer must.

4. Four patterns, and where the pause belongs

The documentation names four shapes and they are worth knowing by name because they need different state. Approve or reject routes to different nodes on the answer. Review and edit state hands the human a value and takes back a modified one. Interrupts inside tools put the pause in the tool itself, so approval is per tool call rather than per turn. Validating human input loops back until the answer is acceptable.

For a retrieval system the useful rule is narrower: pause before an action with a side effect, never before an answer. A reader waiting for a paragraph will not wait for a human, and a human asked to approve every answer will start approving without reading within a day, which is worse than no approval at all.

5. Three designs, one shape

It is worth knowing this is not a LangGraph idea, because that is what makes it safe to build on.

The Model Context Protocol replaced server-initiated requests at revision 2026-07-28 with Multi Round-Trip Requests: a server returns a result marked as needing input, with an opaque requestState, and the client retries the original request carrying its responses and that same state. The A2A protocol at version 1.0 carries TASK_STATE_INPUT_REQUIRED and TASK_STATE_AUTH_REQUIRED as interrupted task states, alongside its terminal ones.

Three independent designs, and all three put the resumption state outside the process that paused and hand the caller a key. When protocols and frameworks converge on a shape without copying each other, the shape is the thing to learn. The two protocols belong to module 5, which teaches them; this page borrows only the fact that they agree.

Check yourself

Retrieval practice

Answer from memory before revealing.

A node retrieves, drafts an email, sends it, then interrupts for approval. What happens on resume?
The runtime restarts the whole node from its first line, so everything above the interrupt runs again, and the send is above it. Continuing after the interrupt is what people assume and is exactly what the documentation says does not happen. Nothing detects the repeat, which is why the defect is silent. Re-evaluating only the interrupt would be the safe behaviour and is not the behaviour.
Where does a pause belong in a retrieval system?
Pausing before a side effect is where a human's judgement changes the outcome and where the cost of being wrong is real. Pausing before every answer makes a reader wait for a person, and an approver asked to read every answer stops reading within a day. Retrievals are read-only and approving them buys nothing. Collecting feedback after the answer is lesson 0430 and needs no pause at all.

Practice about 40 minutes, with a terminal

Practice 1working

Put an approval in front of one side-effecting action, then kill the process to prove the pause is real.

Pick the one action in your system that writes something: filing a ticket, sending a message, updating a record. If you have none, add a trivial one that appends a line to a file, because the exercise is about the mechanism.

Build it with the pause in its own node. Run until it pauses, kill the process, start a new one, and resume with the approval. Then deliberately build the bad version, with the write above the interrupt in the same node, and count the lines in your file after a resume.

Hint

Use a file-backed or database checkpointer rather than an in-memory one for this exercise. An in-memory checkpointer dies with the process and the kill step will look like a framework bug rather than the thing you were testing.

The thread_id is the whole interface. Print it when the run pauses, and resume from a completely separate script that knows nothing except that string.

Show what both versions demonstrate
  1. The good version writes one line and the bad version writes two. That is the entire lesson, reproduced in about forty minutes, and it is worth having seen on your own machine because it is invisible in review: the code reads correctly top to bottom and the defect only exists across a resume.
  2. Resuming from a separate process is the part that proves it. If you resume in the same script, an in-memory variable can carry the state and you have tested nothing. A different process holding only the thread id is the real interface.
  3. Note what it cost to resume. The retrieval and the draft happened twice, so the token bill for an approved request is roughly double an unapproved one. That belongs in the cost model module 6 builds, and it is a line people forget entirely.
  4. Now decide where your pause actually goes. In most retrieval systems the honest answer is that there is exactly one action worth approving, and every other pause is ceremony that trains the approver to click yes.
  5. Record the paused state in the trace. A run that is waiting on a human looks identical to a run that is stuck, unless the span says which, and module 6's lesson 0670 is about failures that are quiet.

Sanity check. After killing the process, your file should contain the state and your resume should succeed with no part of the original process alive. If resume only works while the first process is still running, you are using an in-memory checkpointer and have built the blocking version with extra steps.

Your teacher. Show your agent the node you wrote and ask it to list, in order, every statement that will execute a second time on resume, and which of them has an effect outside the process. Then ask where it would split the node. The disagreements are worth reading: the usual one is whether an expensive but harmless model call should also move, which is a cost decision rather than a correctness one.
