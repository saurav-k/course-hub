An error the model cannot see is an error the model cannot correct

working 8 min The rule and the annotation defaults are read from the Model Context Protocol schema at revision 2026-07-28, which states both in its own comments. · MCP schema

The one-minute version

  • Two kinds of failure look identical in your code and are opposite in the loop: one the model reads, one that unwinds the run.
  • The protocol is unusually direct about it. A tool's own error belongs inside the result, marked, so "the LLM would not be able to see that an error occurred and self-correct" is not what happens.
  • A protocol-level error is reserved for failures in finding the tool, not in running it.
  • Aborting a run throws away everything you already paid for. On the arithmetic below, returning the error instead is cheaper per delivered answer at every failure rate.
  • Before you let the model retry, read the four annotation hints. Two of them default to the dangerous answer.

1. The rule, and the one exception to it

The Model Context Protocol at revision 2026-07-28 states this in the schema itself rather than in a guide, which is why it is worth quoting. Errors that originate from the tool "SHOULD be reported inside the result object, with isError set to true, not as an MCP protocol-level error response. Otherwise, the LLM would not be able to see that an error occurred and self-correct."

The same comment gives the exception: "any errors in finding the tool, an error indicating that the server does not support tool calls, or any other exceptional conditions, should be reported as an MCP error response."

So the line is not about severity, and this is the part people get backwards. It is about whose mistake it is. A malformed argument, a query that matched nothing, a rate limit, a record that does not exist: all of those are things the model could do differently next turn, so they go where it can read them. A tool that is not mounted, or a transport that is down, is not something the model can fix by rewording, so it belongs to your error handling.

Claude's Messages API has the same shape under different names: a tool_result block carries an is_error flag, and the content beside it is what the model reads. Two spellings, one design.

2. What abandoning a run actually costs

Take the assumptions from lesson 0310 and put a failure in the middle. A six-turn run costs 11,370 prompt tokens. A run that dies at turn four has spent 5,380 and returns nothing at all. A run that reads the error and finishes one turn later than it would have costs 15,190 and returns an answer.

The comparison that matters is not per run, because the failed run produced nothing to compare. It is cost per delivered answer. With a tool-failure rate f, aborting gives ((1 − f) × 11,370 + f × 5,380) ÷ (1 − f), because you still pay for the failures and only the successes deliver. Recovering gives (1 − f) × 11,370 + f × 15,190, and everything delivers.

At a failure rate of 20% that is 12,715 tokens per answer against 12,134. Recovery is cheaper and it is also complete, which is the unusual case where the careful thing is also the cheap one.

3. Before you let it try again

Recovery means the model calls your function a second time, so the second call has to be safe. The protocol schema carries four hints that describe exactly this, and two of their documented defaults are the cautious-sounding answer rather than the safe-sounding one.

readOnlyHint defaults to false: unless you say otherwise, the tool is assumed to modify something. destructiveHint defaults to true, so a tool that is not read-only is assumed to be able to destroy. idempotentHint defaults to false, so repeating a call is assumed to have an additional effect. openWorldHint defaults to true, so the tool is assumed to reach an open world of external entities.

That is a well-chosen set of defaults and it has a consequence: an unannotated tool is one that nothing may safely retry. Your retrieval tool is read-only and idempotent and closed-world, and saying so is four lines that let every layer above it retry with confidence.

One line travels with those hints and the schema states it plainly: annotations are untrusted unless the server is, and a client "should never make tool use decisions based on ToolAnnotations received from untrusted servers". That matters the moment your agent mounts a server somebody else runs, which is where module 4 picks this up.

The same caution applies to what comes back. A tool result is text from outside your prompt, arriving inside it, and module 2's lesson on the retrieved document as untrusted input is the same seam seen one stage earlier. A tool that returns a document has all of that problem and a tool that returns an error string has a smaller version of it: keep your error messages your own words, never an unfiltered upstream body.

The chart in section 2 assumes the retry succeeds, and that assumption is doing real work. At the time this course was researched, no primary source could be found that measured how often a model recovers from a visible tool error, so this page argues the effect from the mechanism and the arithmetic rather than from a measurement. If you measure it on your own system, your number is better than this page's reasoning - and it is the kind of number worth writing down.

Check yourself

Retrieval practice

Answer from memory before revealing.

Your retrieval tool is called with a filter that matches no documents. Where does that failure belong?
An empty match is the tool working correctly on a query the model can reword, so it goes in the result where the model reads it. A protocol-level error is reserved for failures in finding the tool at all. An exception handler is the same thing said in your language, and it ends the run. Retrying silently repeats the same filter and hides from the model the one fact it needed.
A tool ships an annotations object with every hint unset. What do the schema's documented defaults then claim about it?
readOnlyHint defaults to false and destructiveHint to true, so an unset tool is assumed to be able to destroy, and openWorldHint defaults to true. The first option inverts both. The third inverts idempotentHint, which defaults to false. Something is very much claimed, which is the point: omission is a claim, and it is the cautious one.

Practice about 30 minutes, with a terminal

Practice 1working

Make your capstone's tool fail two ways and watch the loop behave differently.

Split your tool's error handling in two. Domain failures - an out-of-range argument, an empty result set, a filter that does not parse - return a result with the error flag set and one sentence the model can act on. Infrastructure failures - the index is unreachable, the credential expired - keep raising.

Then trigger each one. Ask a question that provokes an out-of-range top_k, and separately point the tool at a dead index. Capture both traces.

Record two numbers in docs/shape.md: the turns and prompt tokens the recovered run spent, and the turns and prompt tokens the aborted run spent before it died. Then annotate the tool with all four hints and say in one line why each value is what it is.

Hint

The error sentence is a prompt, so write it as one. "top_k must be between 1 and 20" gets a corrected call. "ValidationError: 1 validation error for SearchArgs" gets an apology and a second identical attempt.

If the model does not retry at all, check that your error result is attached to the tool call rather than appended as a fresh user message. A result the runtime cannot correlate is a result the model reads as unrelated.

Show what a good split looks like
  1. The split is by who can fix it, not by how bad it is. A 429 from your vector store is recoverable by waiting, which is your job, not the model's, so it raises. An empty result set is recoverable by asking differently, which is the model's job, so it returns.
  2. One sentence, in your own words, naming the constraint and the allowed range. Echoing an upstream exception message is how somebody else's text ends up inside your prompt, which is the seam module 2 spends a lesson on.
  3. The aborted run's token count is the number to put in front of people. It is money you spent and cannot show anybody, and it is usually larger than expected because the failure lands mid-run rather than at the start.
  4. Annotating is four lines and it changes what is allowed above you. A retrieval tool marked read-only, idempotent and closed-world can be retried by any layer without a conversation. The same tool unannotated is one that a careful caller must refuse to retry, and the schema's defaults say so.

Sanity check. Your recovered run should take exactly one or two more turns than the happy path, not five. A run that spends four extra turns is a run where the model never understood the constraint, and the fix is the sentence rather than the retry budget.

Your teacher. Paste your tool's error strings to your assistant and ask it, for each one, what it would do next if it received that as a tool result. The useful answers are the ones where it names a specific corrected call. Where it says it would apologise or ask the user, the sentence is not carrying the constraint, and rewriting it is cheaper than any change to the loop.
