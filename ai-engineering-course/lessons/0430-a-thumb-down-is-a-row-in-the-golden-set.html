Feedback with no trace id is a feeling you cannot act on

working 10 min Closes the thread opened at lesson 0150, using the span attributes recorded there and the metric vocabulary of lesson 0170. · The golden set

The one-minute version

  • A thumbs-down column that nobody can act on is worse than no column, because it looks like you are listening.
  • What makes a report actionable is the trace id. Without it nobody can reconstruct what the system actually did, and the report is one person's memory of a paragraph.
  • Every field you need is already on the span from lesson 0150. The feedback endpoint stores a pointer, not a copy.
  • Triage sorts each report into module 1's three buckets, and each bucket has a different fix in a different module.
  • A triaged failure becomes a golden-set row. That is how the set grows from thirty to two hundred without anybody sitting down to write two hundred questions.

1. The column nobody reads

Almost every system ships thumbs up and down eventually. Almost none of them uses the data, and the reason is mechanical rather than cultural.

A row saying 2026-08-14, thumbs down, "wrong answer about expenses" cannot be acted on. Which passages were retrieved? What did they score? Which prompt version wrote it? Was the answer wrong or merely unhelpful? Nobody knows, and nobody can find out, because the request is gone. So the rows accumulate, somebody skims them quarterly, and the conclusion is always "retrieval seems to be the problem", which was already true.

The fix is not more fields on the form. Users will not fill them in and should not be asked to. The fix is one hidden field: the trace id of the request they are complaining about.

2. The record that works

With a trace id, everything else is already recorded. Lesson 0150 put the query text and every returned document with its id and score on the retrieval span, and module 2's lesson 0250, "A prompt is a versioned artefact with a name", puts the prompt name and version on the inference span, so the feedback record stores a pointer and inherits the rest.

That is the design rule worth stating: store the pointer, not the copy. A feedback table that duplicates the passages goes stale, disagrees with the trace, and doubles your exposure to whatever was in them. A feedback table holding a trace id, a verdict and one optional sentence of user text is small, honest and joins cleanly.

3. Triage into three buckets

With the trace joined, triage is fast and mostly mechanical, and it sorts into the taxonomy lesson 0120 established.

Not retrieved. The answering passage is absent from the document list. Look at the scores and the query the model wrote. This is a recall defect and it belongs to modules 1, 2 and 4.

Retrieved and not used. The passage is in the list, often ranked low, and the answer ignored it. This is a ranking or packing defect and it belongs to module 2, and lesson 0410's grader is what catches the version of it where nothing relevant was retrieved at all.

Retrieved and contradicted. The right passage arrived and something else in the window won. This is the rarest and the most interesting, and it is usually a corpus problem: two documents disagree and nobody had noticed.

Doing this by hand for twenty reports takes an afternoon and tells you more about where to spend the next month than any dashboard. The proportions are the finding: a system whose reports are ninety percent "not retrieved" needs module 2 work, and one whose reports are mostly "retrieved and contradicted" needs a librarian rather than an engineer.

4. Promotion, and how the set grows

A triaged report becomes a golden-set row: the user's question, the passage that should have answered it, and a note saying why it was hard. That is the same three-field shape lesson 0160 defined, and the row costs about two minutes now that the passage has already been identified during triage.

This is how a thirty-question set becomes a two-hundred-question set without anybody scheduling a workshop, and it is a better set than a written one because every row is a failure that actually happened to somebody.

One caution, from the team that has published most about running this loop. Anthropic's account of building a research system says plainly that human evaluation catches what automation misses, and keeps a share of the budget on reading outputs by hand. Promotion is not a substitute for that. It is what happens after somebody read one.

Check yourself

Retrieval practice

Answer from memory before revealing.

Which single field makes a feedback report actionable?
The trace id joins the report to what the system actually did, and every other fact you need is already on that trace. A timestamp cannot identify one request among many in the same second. The user's own words describe the symptom rather than the cause and are often about a different problem than the one that fired. The model version is useful and is already on the inference span, so it comes free with the join.
Most of your triaged reports fall in the "retrieved and contradicted" bucket. What does that suggest?
That bucket means the right passage arrived and something else in the window won, which usually means two documents say different things and nobody had noticed. It is a corpus problem rather than a code problem. Recall is fine by definition in this bucket, since the passage was retrieved. Ranking would show as "retrieved and not used". Window length is worth checking and would not explain a pattern concentrated in this one bucket.

Practice about 50 minutes, half of it reading traces

Practice 1working

Wire the loop, then run it by hand on twenty real answers.

Add a feedback endpoint that stores a trace id, a verdict and an optional note, and nothing else. Confirm you can go from a stored record to the full retrieval span, with the query and all document scores, in one query.

Then generate twenty answers from questions that are not in your golden set, read each one against its trace, and triage it into one of the three buckets. Report the proportions, promote three of the failures into the golden set, and re-run the set.

Hint

Get the join working before you collect anything. A feedback endpoint that stores an id you cannot resolve is the failure mode this whole lesson is about, and it is easiest to catch on the first record rather than the thousandth.

Triage against the trace, not against the answer. If you find yourself deciding a bucket by reading the paragraph, you are guessing: open the document list and look at whether the passage is there and where it ranked.

Show what the proportions tell you
  1. Expect "not retrieved" to dominate, and expect that to be uncomfortable. After two modules of retrieval work it is tempting to assume the remaining failures are generation problems. On most corpora they are not, and the trace settles it in seconds rather than in an argument.
  2. A bucket you cannot assign is itself a finding. Usually it means the trace is missing something: no scores recorded, or the prompt version absent, so you cannot tell what the model saw. Fix the instrumentation before collecting more, because every uninstrumented report is one you will re-triage later.
  3. Promote the failures, not the near-misses. A row where the answer was slightly worse than you hoped teaches the set nothing. A row where the evidence never arrived is a hard case that will still be hard in six months, which is what a regression test is for.
  4. Re-running the set after promotion will lower your score, and that is correct. You have added three questions the system currently fails. A golden set whose score only ever rises is a set that has stopped being told about failures.
  5. Write the proportions into the charter beside the numbers from module 1. They are the answer to "what should we work on next" and they expire, so date-free as they must be, they still want re-measuring each time the corpus changes materially.

Sanity check. Every one of your twenty reports should be assignable to exactly one bucket using only the trace. If several feel like two buckets at once, you are probably looking at a contradicted case and calling it not-used; the test is whether the answering passage is in the list at all, which is a yes or no rather than a judgement.

Your teacher. Hand your agent one trace as JSON with the user's complaint and ask it to assign a bucket and quote the evidence in the span that decides it. Do the same twenty by hand first and compare, exactly as you compared with the judge in lesson 0170. Where you and it disagree, the bucket definitions need a sentence, and that sentence belongs in your triage guide rather than in an argument.
