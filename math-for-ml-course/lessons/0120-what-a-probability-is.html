Module 07 · Probability · Lesson 120

A probability means two different things, and the mathematics does not care

foundation 9 min The two readings, and why the axioms are neutral between them. · Deep Learning, ch 3.1

The one-minute version

  • "70 percent of requests are cached" and "I am 70 percent sure this request is abusive" are both probabilities and they are not the same kind of claim.
  • The first is a rate over repetitions. You can count it, because the repetitions happened.
  • The second is a degree of belief. This request happens once, so there is nothing to count.
  • Both obey the same three rules, which is why the next fourteen pages never ask you to pick a side.

1. Two sentences, both saying 70 percent

Here are two claims a serving team might make in the same meeting.

"This route serves a cached response 70 percent of the time." That is a statement about a long run. Requests arrive, some are cached, and if you count enough of them the fraction settles. You can check the claim by counting, and if the count comes back at 40 percent the claim was wrong.

"I am 70 percent sure this particular request is abusive." There is no long run here. This request exists once, it either is or is not abusive, and no amount of counting will produce a fraction. The number is a statement about how strongly you believe something, not about how often it happens.

Both are probabilities. The difference has a name, and knowing the name stops the two sliding into each other.

2. The frequentist reading, and what it needs

On the frequentist reading, a probability is the rate at which an event occurs over repetitions. The definition is almost aggressively practical: it tells you what to measure.

P(A) ≈ (number of times A happened) ÷ (number of trials) A: the event you care about, which is a set of outcomes rather than a single one. number of trials: how many repetitions you observed. The ≈ is doing real work: this is an estimate of the rate, not the rate itself, and the two are different until the number of trials is large.

The catch is in that last sentence. A rate estimated from ten trials is barely a rate at all. Watch it settle.

3. The Bayesian reading, and what it needs

On the Bayesian reading, a probability is a degree of belief. Goodfellow, Bengio and Courville put it exactly: probability represents "a degree of belief, with 1 indicating absolute certainty". Nothing is being counted. The number says how strongly a claim is held, and it moves when evidence arrives.

This is the reading that lets you say something about a one-off. There is no population of copies of this request, and there does not need to be.

4. The point of this page: the rules are the same

The reframing Whichever reading you hold, a probability obeys the same three rules, so every technique in this module works for both. You never have to choose a philosophy to do the arithmetic.

This is not a diplomatic compromise, it is a result. The Deep Learning book states it plainly: "the only way to satisfy those properties is to treat Bayesian probabilities as behaving exactly the same as frequentist probabilities", pointing back to work from 1926 showing that a short list of common-sense requirements forces it.

Hajek's course notes take the same position and say why: they "do not present or advocate any one comprehensive philosophy for the meaning and application of probability theory", and present the axioms instead. This course does the same. The next page is those axioms.

5. Where this bites in machine learning

A model outputs 0.7. What kind of number is that?

It is a number the network produced. Whether it is also a rate is an empirical question about the model, and the answer is frequently no. If you gather every example the model scored near 0.7 and about 70 percent of them turn out to be positive, the output behaves like a rate and the model is said to be well calibrated. If 40 percent of them do, the output is a score that happens to lie between 0 and 1. Both models can have identical accuracy.

A model that outputs 0.9 on the examples it gets wrong is not "90 percent right" about them. Reading a score as a rate is a claim that has to be checked, and checking it is what Module 09 does under the name calibration. Until then, treat a model output as a number with the right range and no promises.

6. Worked: the same number under both readings

The module's dataset is requests.csv, a log of 25,000 requests to an inference endpoint. We will use it on every page from here to the end of the module, so it is worth meeting once properly.

Of those 25,000 requests, 99 were abusive. Take that single number and read it both ways.

  1. Count the abusive requests. The flagged column is true on 99 rows out of 25,000.
  2. Divide. 99 ÷ 25,000 = 0.003960, which is about 1 request in 253.
  3. Read it forwards. As a rate, this is a complete and checkable statement about a finished two-day window. The repetitions happened, and you can count them again and get the same answer.
  4. Now point it at the next request. "The next request has a 0.396 percent chance of being abusive" is a different claim. Nothing has been counted, because the next request has not happened.
  5. Name what the second claim assumes. It assumes the next request is exchangeable with the 25,000: same traffic mix, same attackers, same defences. That is an assumption about the world, and it is doing all the work.

Sanity check. The answer must sit between 0 and 1, and it must be small, because a log in which four requests in a thousand are abusive is already a bad day. It is 0.00396.

What changes if you take only the first 200 rows. There are no flagged requests at all in the first 200, so the estimate is 0. The rate did not change; the sample was too small to contain a rare event. That is the same lesson the chart above teaches, and it is sharper for a rare class: the rarer the event, the more repetitions a rate needs before it means anything.

7. The same thing, at a scale you cannot do by hand

The hand calculation above used one division. The program does the same arithmetic 25,000 times, once for every prefix of the log, which is how the chart in section 2 was drawn. It computes the running estimate twice, once with a loop that mirrors the hand calculation and once vectorised, and asserts the two agree.

code/0120-what-a-probability-is.py · NumPy and Pandas only · download
def running_rate_from_the_definition(outcomes):
    """Count the successes, count the trials, divide. One row at a time."""
    estimates = np.empty(len(outcomes), dtype=float)
    successes = 0
    for trial, outcome in enumerate(outcomes, start=1):
        successes += int(outcome)
        estimates[trial - 1] = successes / trial
    return estimates


def running_rate_vectorised(outcomes):
    """The same estimate, computed for every prefix at once."""
    trials = np.arange(1, len(outcomes) + 1)
    return np.cumsum(outcomes) / trials


assert np.allclose(by_definition, vectorised[:200])

The assertion is the teaching. A reader who only sees np.cumsum has learned an API; a reader who sees both agree has learned that the API is the definition, run faster.

Check yourself

Retrieval practice

Answer from memory before revealing.

A model outputs 0.7 for one image. What would you have to collect to check whether that 0.7 behaves like a rate?
A rate is a claim about a population, so you need the population: the examples scored near 0.7, and what they turned out to be. The first option measures whether the model learned, which is a different question. The third describes the model rather than its outputs. The fourth gives you agreement between two models, and two models can agree and both be badly calibrated.
"There is a 60 percent chance the new checkpoint beats the current one next month." Which reading does that sentence require?
There is one next month and it will resolve once, so there is no long run to count and the number has to be a belief. The first two options are true statements about where the number might have come from - past releases are exactly how you would form the belief - but forming a belief from rates does not make the claim itself a rate. The fourth is wrong because "60 percent chance" is precisely a probability.

Practice about 10 minutes, with paper

Practice 1foundation

In the first twenty rows of requests.csv, sixteen requests come from a verified user.

Find the estimated P(verified_user) from those twenty rows. Then say, in one sentence, what would have to be true for that estimate to be a good guess at the rate over all 25,000 rows.

Hint

The first part is one division. The second part is not arithmetic at all: ask what the twenty rows would have to be a fair sample of, and whether the first twenty rows of a time-ordered log are that.

Show the worked solution
  1. Divide. 16 ÷ 20 = 0.80.
  2. Compare against the whole file. Over all 25,000 rows the rate is 0.7008, so the twenty-row estimate is a tenth too high.
  3. Say what it assumes. The twenty rows would have to be representative of the whole log. They are the first twenty rows of a time-ordered log, so they are a sample from one moment rather than from the whole window, and any change in traffic mix over the three hours breaks the assumption.

Sanity check. The answer lies between 0 and 1 and lands near 0.7, so it is the right sort of number. Notice also that a twenty-row estimate can only ever move in steps of 0.05, so even a perfectly representative sample could not have landed closer to 0.7008 than 0.70.

Your teacher. If the two readings still feel like the same thing, try this on the next number someone quotes you: ask "what would I count to check that?" If you can describe the counting, it is a rate. If the honest answer is "nothing, it only happens once", it is a belief - and it can still be a perfectly good number. Ask an agent to give you five probability claims from a postmortem and sort them into the two piles.
