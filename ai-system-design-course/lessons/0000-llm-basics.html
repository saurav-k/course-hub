Pillar 01 · Foundations · Chapter 1

LLM Basics

19 topics The vocabulary an interviewer assumes you already own before the design question starts.

The one-minute version

  • A model does not see text. It sees tokens, and every cost, latency, and limit in your design is denominated in them.
  • The context window is a budget, not a container. Filling it degrades accuracy and raises cost at the same time.
  • Structured outputs and tool calling are what turn a text generator into a system component you can put behind an API.
  • Every quality lever you have - prompting, routing, small models, fine-tuning - is a trade against latency and cost. Interviewers want the trade named, not the lever named.

1. The unit of everything: tokens and context

A classic design round starts by sizing requests per second and bytes on disk. An AI round starts by sizing tokens. If you cannot convert a product requirement into a token count, you cannot size the system, price it, or set a latency budget for it. Everything in this chapter hangs off that.

Tokens

A token is a sub-word unit produced by a tokenizer such as byte-pair encoding. It is not a word and not a character, which is why "how many tokens is this document" has no clean answer without running the tokenizer. Two consequences matter at the whiteboard. First, non-English text and code often tokenize less efficiently, so the same page costs more in some languages than others. Second, you cannot truncate safely by counting characters. Source: tiktoken, the reference BPE tokenizer.

Context window

The context window is the maximum number of tokens the model can attend to in one request, covering system prompt, conversation history, retrieved documents, tool definitions, tool results, and the answer being generated. The naive reading is that a bigger window solves retrieval. It does not. Liu et al. showed accuracy is highest when the relevant passage sits at the beginning or the end of the context and measurably worse when it sits in the middle. Treat the window as a budget you allocate deliberately, with the most important evidence placed at the edges. Source: "Lost in the Middle" (Liu et al., 2023).

Interview trap. "The model has a million-token window, so we can skip retrieval and just send everything." This is the single most common mistake at Senior level. Attention cost, time to first token, price per request, and mid-context accuracy loss all move against you. Retrieval is a precision mechanism, not a workaround for a small window.

Prompt design

Prompt design is interface design. In a production system the prompt is a versioned artifact with a schema, tests, and a rollback path, not a string a developer edits in production. The design-round answer is that prompts live in a prompt service with versioning and evaluation attached, which is covered in Chapter 3.

System prompts

The system prompt carries role, policy, and constraints, and is the highest-trust text in the request. That trust is exactly why it is a security boundary: everything else in the window, including retrieved documents and tool output, is attacker-influenceable input. Chapter 6 develops this. Source: Greshake et al. on indirect prompt injection.

2. Controlling the output

Temperature

Temperature rescales the probability distribution before sampling. Low temperature concentrates mass on the highest-probability tokens and makes output more repeatable; high temperature flattens the distribution and increases variety. Temperature zero is not literally deterministic in a distributed serving stack, because batching, hardware, and kernel non-determinism can still change results. Say "low variance", not "deterministic", and you will sound like someone who has operated one of these.

Top-p sampling

Top-p, or nucleus sampling, restricts sampling to the smallest set of tokens whose cumulative probability exceeds p. Holtzman et al. introduced it after showing that maximising likelihood produces bland, repetitive text, while unrestricted sampling wanders into the low-probability tail. Tuning both temperature and top-p aggressively at the same time is a common source of unreproducible behaviour. Source: "The Curious Case of Neural Text Degeneration" (Holtzman et al., 2019).

Your summariser returns different text for identical inputs, and product wants that stopped. Which change addresses the cause most directly?
Sampling parameters control output variance. A bigger window, a bigger model, or deeper retrieval all change the answer without addressing variability. Note the honest caveat: pinning both reduces variance sharply but does not guarantee byte-identical output in a batched serving stack.

Structured outputs

Structured output means the model is constrained during decoding so that the emitted tokens must conform to a supplied JSON Schema. This is a decoding-time guarantee, categorically different from instructing the model to "reply in JSON" and hoping. In a design round, say that schema conformance is enforced by constrained decoding and that you still validate at the boundary, because a schema-valid object can still be semantically wrong. Source: OpenAI Structured Outputs.

JSON mode

JSON mode is the weaker predecessor: it guarantees syntactically valid JSON but not conformance to your schema. Knowing the difference between "parses" and "conforms" is a quick signal of production experience.

3. Turning a model into a component

Function calling

Function calling lets you declare typed functions and have the model emit a structured request to invoke one. The model never executes anything. It returns intent; your code decides whether to honour it. That sentence is the whole security posture, and interviewers listen for it. Source: OpenAI Function Calling.

Tool calling

Tool calling generalises this into a loop: the model requests a tool, your runtime executes it, the result is appended to the conversation, and the model continues. Each turn consumes context and adds a round trip, so a five-tool chain has five times the latency variance of a single call. Source: Anthropic Tool Use.

Agents

An agent is a model running in a loop with tools, deciding its own next step. Anthropic's guidance is worth quoting in an interview: most production value comes from composable workflows, and agents should be reserved for problems where the number of steps genuinely cannot be predicted in advance. Loops mean unbounded cost, unbounded latency, and compounding error, so a step budget and a termination condition are part of the design, not an operational detail. Source: "Building Effective Agents" (Anthropic).

Memory

Memory is not a model feature. It is a retrieval and storage design you build: short-term conversation state, summarised history, and long-term facts in a store you can inspect, correct, and delete. Treating memory as a database with a retention policy and a deletion path is also what makes it survive a privacy review.

Guardrails

Guardrails are the checks around the model: input filtering, output validation, schema conformance, policy classification, and refusal handling. Two properties matter in design. They run as separate, cheap, independently monitored components, and they must fail in a defined direction. Chapter 6 covers what to do when a guardrail is unavailable.

4. Failure, latency, and choice

Hallucinations

A hallucination is fluent output unsupported by any source. The survey literature separates factuality failures, where output contradicts the world, from faithfulness failures, where output contradicts the supplied context. This distinction is worth real points: faithfulness is fixable with grounding and citation checks, while factuality needs retrieval or a knowledge boundary. Source: hallucination survey (Zhang et al., 2023).

Model latency

Model latency has two numbers, and quoting one marks you as a beginner. Time to first token is dominated by prefill and queueing, and it is what the user experiences as responsiveness. Inter-token latency times the output length gives total generation time. Streaming improves perceived latency without changing either. Chapter 4 turns these into budgets.

Model routing

Routing sends each request to the cheapest model that can serve it, using a classifier, heuristics, or a difficulty estimate, with escalation on low confidence. The design questions are who owns the routing policy, how you evaluate a routing change, and what happens when the cheap model is confidently wrong. Answer the third one and you have answered the round.

Small versus large models

Small models cost less, respond faster, fit on cheaper accelerators, and are easier to host yourself. Large models generalise better on unfamiliar tasks. The mature position is a portfolio: a small model for the narrow, high-volume path, a large model for the long tail, and an evaluation harness that tells you where the boundary actually sits rather than where you guessed it sits.

Fine-tuning versus prompting

Prompting changes behaviour per request with no training cost and instant rollback. Fine-tuning moves behaviour into the weights, shortens prompts, and can let a smaller model match a larger one on a narrow task, at the cost of a data pipeline, a training loop, versioning, and a much slower iteration cycle. Parameter-efficient methods such as LoRA cut the cost of that loop substantially but do not remove the operational burden. Default to prompting and retrieval; fine-tune when you have a stable task, a labelled dataset, and evidence that prompting has plateaued. Source: LoRA (Hu et al., 2021).

Open-source versus closed models

Closed models are consumed as an API: best-in-class quality, no infrastructure, but a hard dependency on a vendor's pricing, availability, deprecation schedule, and data policy. Open-weight models give control over hosting, data residency, and cost curve, and let you fine-tune freely, but you now own GPU capacity planning, serving, and upgrades. Senior candidates answer with the deciding factors rather than a preference: data-residency obligations, cost at your actual volume, latency floor, and how badly a forced model deprecation would hurt.

A support assistant answers correctly but occasionally cites a policy that does not appear in the retrieved documents. What is the precise name for this?
Output contradicting the supplied context is unfaithfulness, and it is measurable: check that each claim is supported by a retrieved span. Recall failure would mean the policy was never retrieved at all, which is a different fix. Naming the specific failure is what separates a Staff answer from a Senior one.

5. Interview drill

Questions that actually get asked on this material, and the trap inside each one.

  • "Estimate the monthly cost of this assistant." The trap is answering in requests. Convert to tokens: average input tokens including system prompt and retrieved context, average output tokens, requests per user per day, active users. State the assumptions aloud. Chapter 4 gives the arithmetic.
  • "We have a huge context window now. Do we still need RAG?" The trap is agreeing. Cost, time to first token, and mid-context accuracy loss all argue for retrieval, and the freshness and permissions arguments are independent of window size.
  • "How do you stop the model returning malformed JSON?" The trap is answering "prompt it better". Constrained decoding against a schema, then boundary validation, then a defined fallback.
  • "Your agent occasionally loops forever. What do you change?" The trap is tuning the prompt. Step budgets, a termination condition, per-request cost ceilings, and a fallback to a deterministic workflow.
  • "Should we fine-tune?" The trap is saying yes. Ask what the task is, whether it is stable, whether labelled data exists, and whether prompting has actually plateaued against a measured baseline.
Your teacher. The highest-leverage habit in this chapter is converting every requirement into tokens before you draw a single box. Try it on a system you already know: pick a product feature, estimate its input and output tokens, and multiply out. Ask me to check your arithmetic and challenge your assumptions - that is where interviewers push hardest.

Primary source to go deeper

Read Liu et al., "Lost in the Middle" (2023). It is short, empirical, and permanently changes how you think about stuffing a context window. Pair it with "Building Effective Agents" for the workflow-versus-agent judgement.
