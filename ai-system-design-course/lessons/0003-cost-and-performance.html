Pillar 04 · Economics · Chapter 4

Cost and Performance

18 topics Where AI system design stops resembling web system design.

The one-minute version

  • In a web system the marginal request is nearly free. In an AI system it is the dominant line item, and that changes which designs are correct.
  • Generation is memory-bandwidth bound and sequential, so batching raises throughput while doing nothing for a single request's latency.
  • Caching is the highest-leverage lever you own - prompt caching, semantic caching, and response caching attack three different costs.
  • Interviewers want cost per query and cost per user, with assumptions stated aloud. A design with no unit economics is not finished.

1. Sizing in tokens

Every number in this chapter derives from one calculation. Cost per query is input tokens times input price, plus output tokens times output price, where input tokens include the system prompt, tool definitions, conversation history, and every retrieved chunk. Output tokens are usually the smaller count and frequently the more expensive rate.

cost/query = (Tin × pin) + (Tout × pout) Read as: the tokens you send, priced at the input rate, plus the tokens the model generates, priced at the output rate. Tin is where retrieval and history quietly inflate your bill; Tout is where latency lives, because output is produced one token at a time.
Say your assumptions aloud. Public, citable cost figures for a named company's production system barely exist. Interviewers are not checking your prices. They are checking whether you know which quantities matter and whether you flag them as assumptions rather than asserting them as facts.

Token budgeting

Allocate the context window explicitly: so many tokens for instructions, so many for retrieved evidence, so many for history, and a reserve for the answer. Enforce the budget in code with a defined eviction order, because an unbudgeted window silently grows until it hits a limit in production.

Cost per query

The unit that makes an architecture arguable. It exposes that a rerank step, a query rewrite, and an agent loop each add real money, and it turns "should we add this step" into a decision instead of a preference.

Cost per user

Cost per query times queries per user per period. This is the number that determines whether the product has a viable business model, and quoting it unprompted reads as seniority. Watch the distribution rather than the mean: a small number of heavy users routinely dominate spend, which is why per-tenant token quotas exist.

2. Making prompts cheaper

Prompt compression

Shorten what you send: summarise history rather than replaying it, trim boilerplate instructions, and drop retrieved chunks that the reranker scored poorly. The cheapest token is the one you never send, and this is usually the first place to look when a bill surprises someone.

Prompt caching

Providers can cache the processed prefix of a prompt so that repeated system instructions, tool definitions, and stable documents are not reprocessed on every request, cutting both cost and time to first token on a hit. This makes prompt layout an optimisation target: stable content first, volatile content last, because a cache hit requires an identical prefix. Source: Anthropic prompt caching.

Semantic caching

Cache on meaning rather than exact string: embed the query, and serve a stored answer if a previous query is close enough. Powerful for support and FAQ workloads with heavy paraphrase. The danger is a false hit returning a confidently wrong answer, so it needs a conservative similarity threshold, scoping by tenant and permissions, and an invalidation story tied to document freshness.

Response caching

Exact-match caching on a normalised request. Boring, safe, and effective for hot paths. Cache key correctness is the whole game: it must include the model, the prompt version, retrieval results, and the user's permission scope, or you will serve one tenant's answer to another.

Batch requests

Group independent work into one submission and accept higher latency for a lower rate. Applies to embedding backfills, bulk classification, and evaluation runs. Source: OpenAI Batch API.

Costs jumped after you added retrieval, though traffic is unchanged. Which measurement isolates the cause fastest?
Retrieval inflates input tokens, so attribute them by section: instructions, history, retrieved chunks. That immediately shows whether top-k is too high, chunks are too large, or reranking is not trimming the tail. Request rate did not change, and utilisation and latency are symptoms rather than causes.

3. Making the model cheaper

Model quantization

Store and compute weights at lower precision to cut memory and raise throughput. GPTQ and AWQ are the standard post-training approaches, and AWQ's insight is that a small fraction of weights are salient and should be protected rather than quantised uniformly. There is a quality cliff, and where it sits is task-dependent, so the correct interview answer is that you quantise and then re-run your evaluation set rather than trusting a published benchmark. Sources: GPTQ, AWQ.

Distillation

Train a small student model on a large teacher's outputs, transferring behaviour on a narrow task at a fraction of the serving cost. Hinton et al. established the technique long before LLMs, and it is the mechanism behind most "small model that punches above its weight" claims. Source: "Distilling the Knowledge in a Neural Network" (Hinton et al., 2015).

Model selection

Pick per request, not per product. A classification step does not need your best model. Tie selection to a measured quality bar on your own evaluation set so the choice is defensible rather than aesthetic.

4. Serving mechanics and latency

Latency budgets

Allocate the end-to-end target across the hops: gateway, retrieval, rerank, prefill, and generation. Budget at the tail, not the mean - p95 and p99 are what users feel and what interviewers ask about. State which hop you would cut first when the budget is blown.

Cold starts

Loading tens of gigabytes of weights onto an accelerator is slow, which makes scale-to-zero unattractive for interactive paths and makes autoscaling lag real traffic. The usual answers are warm pools, pre-loaded replicas, and provisioned capacity for the interactive tier.

GPU utilization

High utilisation does not mean efficient work. Decoding is dominated by moving weights and KV cache through memory rather than by arithmetic, which is exactly the observation behind FlashAttention's IO-aware design. A fleet can look busy while producing few tokens, so measure tokens per second per accelerator alongside utilisation. Source: FlashAttention (Dao et al., 2022).

Throughput

Continuous batching, introduced as iteration-level scheduling in Orca, lets a new request join a running batch at the next decoding step instead of waiting for the current batch to finish, which raises throughput dramatically at high concurrency. PagedAttention then removed the memory fragmentation that limited how many sequences could share a device, by managing the KV cache in fixed-size blocks like virtual memory pages. Together these are why modern serving stacks outperform naive batching by a wide margin. Sources: Orca (OSDI 2022), vLLM PagedAttention.

Inference scaling

Scale on queue depth and token throughput rather than on CPU. Accelerators are scarce and slow to acquire, so the honest answer includes capacity as a procurement constraint, not merely an autoscaling policy.

5. Behaviour under overload

Backpressure

When demand exceeds capacity, push the signal upstream: bounded queues, admission control, and explicit rejection. Unbounded queues do not add capacity, they convert a fast failure into a slow one while consuming memory.

Load shedding

Drop work deliberately, by priority, so the system degrades instead of collapsing. Shed the cheap and the retryable first: background summarisation before interactive chat, free tier before paid. The Google SRE treatment transfers directly, and the AI-specific twist is that you can shed quality as well as requests - drop the reranker, shrink top-k, or route to a smaller model before you start rejecting users. Source: Google SRE Book, "Handling Overload".

Under peak load your accelerators report ninety percent utilisation, yet tokens per second has fallen. What best explains this?
Utilisation measures busy time, not useful work. When KV cache memory is fragmented or exhausted, concurrency drops and the device spends its time moving data rather than producing tokens. This is precisely the problem PagedAttention targets, and why tokens per second per accelerator is the metric that matters.

6. Interview drill

  • "What does this cost to run at a million users?" Tokens in, tokens out, queries per user, stated assumptions. Then name the two levers you would pull first: caching and prompt size.
  • "Cut latency by half." Separate time to first token from generation time. Streaming, prompt caching, and a smaller model attack different halves.
  • "Traffic triples tomorrow. What breaks?" Accelerator capacity, queue depth, and vendor rate limits. Then give the shedding order.
  • "Would you self-host?" Volume, latency floor, data residency, and whether you have the operational appetite. Below a certain volume, self-hosting is more expensive, not less.
  • "Where would you add a cache?" Three answers, not one: prompt prefix, semantic query, exact response - each with its invalidation and correctness risk.
Your teacher. Build the habit of quoting a cost per query with the assumptions attached, unprompted. It is the single fastest way to signal that you have operated one of these rather than only read about them. Ask me to throw a product at you and time how long it takes you to produce a defensible number.

Primary source to go deeper

Read the vLLM PagedAttention paper. It explains why serving efficiency is a memory-management problem, which is the insight most candidates are missing. Follow it with "Handling Overload" for the behaviour-under-stress half.
