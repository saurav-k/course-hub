AI System Architecture

19 topics The boxes you draw, and why each one earns its place.

The one-minute version

  • This is the chapter where your distributed-systems experience transfers almost intact. The topology is familiar; the constraints are not.
  • The model gateway is the single most valuable box on the board: it is where routing, fallback, rate limiting, cost accounting, and provider independence live.
  • AI requests are slow, expensive, and variable in duration, which pushes you toward streaming, queueing, and async far earlier than a CRUD system would.
  • Every serious design has a fallback path and a human path. Draw them, or an interviewer will ask why you did not.

1. The reference architecture

Start from a shape you can defend, then delete what the requirements do not justify. Sculley et al. made the durable point that the model is a small box in a large system, and that the surrounding infrastructure is where the debt accumulates. Source: "Hidden Technical Debt in Machine Learning Systems" (Sculley et al., 2015).

2. The entry path

API gateway

Authentication, quota enforcement, request validation, and rate limiting, exactly as in any system you have built. The AI-specific addition is that quota is meaningfully denominated in tokens rather than requests, because a single request can legitimately cost a hundred times another.

Request routing

Routing decides which pipeline serves the request: a cheap classification path, a full retrieval path, or a long-running agent path. Doing this early keeps the expensive machinery off simple requests.

Model gateway

A single internal interface in front of every model, hosted or vendor. It owns model selection and routing, retries and timeouts, provider failover, token accounting and cost attribution, prompt and response logging, and rate limiting per tenant. If you draw exactly one AI-specific box in an interview, draw this one - it is what makes provider changes, price changes, and deprecations survivable.

Prompt service

Prompts are versioned artifacts with tests and a rollback path, served by their own component rather than compiled into every caller. This is what lets you evaluate a prompt change the way you would evaluate a code change, and roll it back in seconds when the evaluation says no.

Inference service

Where generation happens: a vendor API, or your own serving stack on GPUs. Self-hosting buys control over cost curve, data residency, and latency floor, and costs you capacity planning, batching, and upgrades. Chapter 4 covers the serving mechanics.

3. Retrieval and features

Retrieval service

Retrieval is its own service with its own scaling profile, its own cache, and its own quality metrics, as developed in Chapter 2. Collapsing it into the application is what makes it impossible to measure later.

Ranking service

Reranking is a separate hop because its cost profile differs sharply from search: it is model inference over a candidate list, so it batches, caches, and fails differently. Separating it lets you degrade to unreranked results under load rather than failing the request.

Feature store

A feature store serves the same feature values to offline training and online inference, which is what prevents training-serving skew, and it is the piece that makes personalisation and ranking features tractable. Uber's Michelangelo write-up remains the clearest public description of why the abstraction exists. Source: Michelangelo (Uber Engineering).

Offline pipelines

Ingestion, chunking, embedding, index building, feature computation, and evaluation runs. This is a batch data platform with all the usual concerns: schedules, backfills, idempotency, and lineage. Interviewers notice when a candidate draws only the request path and leaves the index magically populated.

Online serving

The synchronous path, bounded by a latency budget. The rule of thumb worth stating: anything that cannot meet the budget belongs on the async path, not in a slower synchronous one.

4. Time, load, and shape of response

Async processing

Document ingestion, bulk summarisation, and long agent runs return a job identifier and notify on completion. Trying to keep these synchronous is the most common cause of a design collapsing under follow-up questions.

Queueing

Queues absorb burst, smooth expensive GPU work, and let you prioritise. They also introduce the questions an interviewer will reach for immediately: what is the maximum queue depth, what is the timeout, and what does the user see while waiting. Have answers ready.

Streaming responses

Streaming tokens as they are generated transforms perceived latency without changing total generation time, and it is why server-sent events are the default transport for chat interfaces. Note the operational costs: long-lived connections, harder retries once bytes have been sent, and output guardrails that must now run incrementally. Source: Server-sent events, WHATWG HTML specification.

Rate limiting

Limit tokens per minute alongside requests per minute, per tenant and per user, because request counts do not bound cost. Vendor limits are themselves a dependency: your gateway must handle being throttled upstream, which is a fallback concern.

Fan-out and fan-in

Fan out across documents, sub-questions, or candidate models, then merge. This buys parallelism and quality, and it multiplies cost while making the tail latency of the slowest branch your latency. Bound the fan-out and set a per-branch deadline.

A summarisation feature over long documents intermittently times out at the gateway under normal traffic levels. What is the structural fix?
Work whose duration scales with input length does not belong on a synchronous path. Raising timeouts converts a fast failure into a slow one and holds connections open; retries on expensive generation multiply cost against a system already struggling.

5. Inference modes and safety nets

Batch inference

Offline, high-throughput processing where latency does not matter: back-filling embeddings, classifying a corpus, precomputing summaries. Providers price this lower precisely because it lets them schedule around live traffic. Source: OpenAI Batch API.

Real-time inference

The interactive path, where time to first token dominates the experience. Keep it narrow: retrieve, rank, generate, stream.

Human-in-the-loop systems

For consequential actions, low confidence, or regulated decisions, a human approves or corrects. Design it as a first-class path with a queue, a reviewer interface, an SLA, and a feedback capture that flows back into evaluation. Treated as an afterthought it becomes an unstaffed backlog.

Fallback workflows

What happens when the model is down, throttled, too slow, or refuses. Options in descending order of quality: a different model, a smaller model, a cached response, raw search results without generation, or an honest error. The Google SRE framing of graceful degradation applies unchanged, and stating a specific degradation ladder is one of the strongest signals you can give. Source: Google SRE Book, "Handling Overload".

Which single component most reduces the blast radius when your primary model provider raises prices or deprecates a model?
All four are useful, but only the gateway makes the provider a swappable dependency. Without it, model identifiers, retry logic, and cost accounting are scattered across every caller, and a deprecation becomes a migration across the whole codebase.

6. Interview drill

  • "Design an AI assistant over our product documentation." The trap is drawing only the request path. Draw the offline pipeline too, and say how the index is built and refreshed.
  • "What happens when the provider has an outage?" Give the degradation ladder, not the word "fallback".
  • "How do you roll out a prompt change safely?" Prompt service, versioning, offline evaluation on a golden set, then a small online experiment, with rollback.
  • "Where does the human sit in this system?" Confidence threshold, review queue, SLA, and the loop back into evaluation data.
  • "Why not put the model call directly in the application?" Cost attribution, routing, failover, and logging all become per-caller problems. That is the gateway argument, and it is the same argument as any shared client library, only with money attached.
Your teacher. Practise drawing this architecture from memory in under three minutes, then deleting every box the stated requirements do not justify. Interviewers reward the deletion as much as the drawing - an unjustified box reads as pattern-matching rather than design. Ask me to give you a requirement set and critique what you kept.
