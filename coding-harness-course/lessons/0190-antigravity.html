The one-minute version

  • The defining move is consolidation: desktop app, CLI, IDE extensions, and SDK all drive one Go agent harness.
  • A surface embeds it by spawning a process, shaking hands over stdio, then trading protobuf events over localhost.
  • Sensitive actions are resources scored against deny, ask, allow lists - with sandboxing on, grants compile into the container policy.
  • The bet: agents communicate through artifacts - plan first, walkthrough with evidence after - and comments join a running loop.

The architectural fact everything else hangs on is consolidation, stated plainly in the CLI launch post: the CLI and desktop app "use the same Antigravity agent harness, share the same settings," built for "consolidation of a single agent harness across Google-built developer surfaces." The SDK shows what that means mechanically: a surface spawns a Go binary named localharness, writes a length-prefixed InputConfig protobuf to its stdin, reads back an OutputConfig carrying a localhost port plus an API key, connects to ws://localhost:{port}, and from then on trades protobuf events (local_connection.py:1295).

The loop

The loop runs inside the binary, so no source is readable - but two official documents expose its shape: the hooks reference names the interception points, and headless mode prints a real run's raw event stream. Your message becomes an InputEvent(UserInput), appearing in the stream as step_type: user_input. Before each model call, PreInvocation hooks may inject steps - a synthetic tool call, user message, or ephemeral system message. The reply returns as typed steps - text, thinking, or tool calls. Each tool call passes the permission engine and any PreToolUse hook, whose five decisions include force_ask and deny_unless_prior_grant. The canonical stop is a builtin finish tool, and the Stop hook receives terminationReason (model_stop, max_steps_exceeded, error) plus fullyIdle - and may answer "decision": "continue" to force another iteration. Every run ends with usage counts: input_tokens, thinking_tokens, cache_read_tokens.

Edits are search-and-replace shaped. Creation is whole-file: write_to_file carries full CodeContent. Modification targets "a single contiguous block of text": replace_file_content takes literal TargetContent and ReplacementContent, and multi_replace_file_content batches several blocks per file (hooks reference). What happens when an edit does not apply is not publicly documented; the parameters hint at recovery loops - TargetLintErrorIds references lint errors on earlier edits, and Instruction fields carry intent for retries - but no documented fallback cascade exists.

Context assembly

Prompt assembly splits between the closed harness and documented extension points. The harness holds default agent instructions; the SDK maps TemplatedSystemInstructions to sections appended after them and CustomSystemInstructions to a full replacement, and a custom agent's Markdown body is compiled into the system prompt (local_connection.py:761). Rules live in two tiers: global ~/.gemini/GEMINI.md and workspace .agents/rules/*.md, capped at 12,000 characters each, with four activation modes - Manual (@-mention), Always On, Model Decision (the model judges a description), and Glob (Rules docs). Skills use progressive disclosure: the window carries only names and descriptions first, and a SKILL.md is read on demand. Custom agents are themselves a context strategy - Google frames them explicitly as the fix for "context window bloat," since only their declared tools and skills enter. History is a step list persisted to transcript.jsonl; compaction is a first-class StepType.COMPACTION step whose positions compaction_indices records (conversation.py:235), though the threshold policy is not publicly documented. Session budgets cap max_model_calls, max_tool_calls, and net uncached tokens via BudgetConfig.

Trust posture

One permission engine spans all surfaces. Every sensitive operation is a resource written action(target), evaluated across three lists with strict precedence Deny > Ask > Allow (Permissions docs). Workspace files auto-allow; almost everything else defaults to Ask, web browsing included. Approval cards are editable - before clicking Allow you can widen a file or URL target yourself, say from one file to its parent directory, and the grant persists for the turn.

The distinctive move is what happens when sandboxing turns on (preview on macOS and Linux): your grants compile into the container policy (Sandbox docs). Paths allowed under read_file populate read-only mounts, write_file paths populate read-write mounts, and read_url domains become the outbound AllowedDomains list - under native OS containment (nsjail on Linux, sandbox-exec on macOS), off by default via enableTerminalSandbox: false. Escape hatches are explicit: the unsandboxed(prefix) grant, a per-run "run without sandbox restrictions" prompt option, and headless --dangerously-skip-permissions. Compare lesson 0140's subject, which sandboxes first and amends policy afterward; Antigravity keeps one rule set and derives both prompts and container from it.

Two conventions are adopted rather than invented - skills follow the cross-industry SKILL.md standard, and hooks echo Claude Code's event names - which matters for the lineage question below. One idea is genuinely uncommon: execution symmetry. A custom agent defined once can be something you chat with directly (mainAgent) and something a coordinator delegates to (subagent), with per-agent command policies separating safe autonomous shell work from gated high-risk commands.

Model behavior

The selector offers Gemini 3.7/3.6/3.5 Flash with reasoning-effort tiers, Gemini 3.1 Pro, Claude Sonnet 4.6 and Opus 4.6 (thinking), and GPT-OSS-120b; enterprise plans exclude the Anthropic and OpenAI entries, and choice is sticky within a turn (Models docs). Affinity shows up in encoding details. A hook payload's modelName reads gemini-3.6-flash-medium: effort is folded into the slug for Gemini models, while the Claude entries carry none. In the proto layer a ModelConfig carries a GeminiAPIEndpoint, VertexEndpoint, GemmaEndpoint, or CustomEndpoint - there is no Anthropic or OpenAI endpoint type, because third-party models arrive served through Google's managed backend rather than through your keys (localharness.proto, messages 135-166). Gemini-specific knobs are first-class types: five ThinkingLevels including extra_high, and a ServiceTier field.

This is affinity as stated product strategy - the 2.0 announcement lists as a goal to "integrate the Antigravity product agent harness with the Gemini training and evaluation stacks," co-developing layers no third-party harness can co-develop - and its everyday trace is cache_read_tokens in every usage envelope. Where lesson 0220's subject compiles per-family adapters from a catalog, Antigravity needs no adapter zoo: non-Gemini models arrive pre-adapted through Google's endpoint, with no documented special handling beyond availability.

The distinctive mechanism: artifacts as the review surface

Every other harness in the cast reviews work through one of two windows: the live tool-call stream (Claude Code, Gemini CLI) or the finished diff (Copilot's review flow). The launch post argues both fail the same test - one drowns you in calls, the other shows "only the final code change with no context on how the agent got there... Neither engenders user trust" - and answers with a third unit: the artifact, "tangible deliverables in formats that are easier for users to validate than raw tool calls, such as task lists, implementation plans, walkthroughs, screenshots, and browser recordings" (launch post). Two properties make this structural rather than cosmetic.

First, feedback lands mid-flight. Comments on a plan or screenshot - Google-doc-style - "will be automatically incorporated into the agent's execution without requiring you to stop the agent's process." The artifact becomes a coordination object between you and a running loop; whether that loop pauses at the plan gate is itself a setting, the Artifact Review Policy: Request Review halts for explicit approval, Always Proceed bypasses the pause (Artifact Review docs). Second, verification ships as part of the deliverable: for browser tasks the walkthrough must carry the evidence - screenshots and screen recordings of the agent's own work - because the stated emphasis is "to thoroughly think through verification of its work, not just the work itself."

Honest lineage note: the manager descends from Antigravity's own 1.0 Agent Manager, skills are an adopted standard, and hooks echo an existing event model. The artifact protocol - structured deliverables, mid-flight comments wired into a live loop, verification evidence in the deliverable - is the part this harness adds, and no other member of the cast does it.

The core is closed, and three mechanisms this page leans on sit behind that wall: the compaction threshold, the failed-edit recovery path, and checkpoint rollback semantics are each undocumented as of the fetch date. Every claim above traces to official documentation or the inspectable SDK at the pinned commit - where neither covers a mechanism, this page says so instead of guessing.

Check yourself

Retrieval practice

Answer from memory before revealing.

Why does the SDK spawn the harness as a subprocess and reconnect over a port, instead of importing it like a library?
Consolidation is the stated goal: a single Go harness, upgraded centrally, embedded by desktop app, CLI, IDE panels, and SDK through the same spawn-handshake-event protocol. Protobuf crosses process boundaries fine - that is what it is for; no elevation is involved anywhere in the handshake; and cgo-style bridging is a real technique the design simply did not need.
Terminal sandboxing is enabled. What does the engine do with an existing read_file(/var/log/app) grant?
The permissions doc is explicit: granted read paths dynamically populate the sandbox's read-only filesystem allowlist - the same rule set drives both prompting and containment. Re-prompting contradicts what a grant means; widening is something the user does manually in an approval card, never automatic; and dropping grants inverts the entire design, since grants are exactly what the policy is built from.

Practice about 15 minutes, reading code in the browser

Practice 1working

Open local_connection.py at the pinned commit and trace the embedding handshake: find the subprocess.Popen spawn, the stdin write of an InputConfig, the stdout read of an OutputConfig, and the WebSocket connect that follows.

Find: the three transport upgrades a session passes through, in order, and one concrete reason stdio alone could not carry the rest of the conversation.

Hint

Follow the bytes: what travels on the child's stdio is exactly one configuration exchange. Ask what changes about the traffic after the port appears - who can connect, how many readers, in which directions.

Show the worked solution
  1. Upgrade one - spawn. The surface launches the localharness binary as a child process; discovery order is an env var, then the wheel copy, then $PATH.
  2. Upgrade two - bootstrap over stdio. A length-prefixed InputConfig goes in; a length-prefixed OutputConfig comes back carrying a localhost port and API key.
  3. Upgrade three - events over the socket. Everything after initialization flows as protobuf events over ws://localhost:{port}, authenticated by that key.
  4. Why stdio cannot be the whole story. Stdio is a private pipe to one parent; the socket is an addressable endpoint any local observer - a second panel, a monitoring tool, the Remote Control daemon - can subscribe to, and it decouples the session's lifetime from the parent's file descriptors.

Sanity check. You should have found exactly one config exchange on stdio and everything else on the socket - if you see tool results flowing over stdio, you are reading the wrong connection class in the file.

Your teacher. If the consolidation architecture has not landed, ask for the counterfactual: what would Google have to publish per surface if each shipped its own harness fork? For the distinctive mechanism, ask it to compare reviewing a task in Antigravity against reviewing a long Claude Code run you stepped away from - what does each show you first?
