The protocol that turned plugins into config files

working 11 min Framed against the Model Context Protocol specification, with every harness claim read from its repository or official docs. · MCP specification

The one-minute version

  • Before MCP, giving an agent new tools meant writing against that harness's private plugin API - or forking it.
  • MCP moved the boundary to a wire protocol: any harness speaking it can drive any compliant server, thirteen of our fifteen cast members included.
  • Adoption has four depths, from thin config-file clients to Goose, which runs its own built-in tools through MCP transports.
  • Two members refuse it - one by era, one by design - and their reasons are the trade-off stated out loud.

1. The protocol in one lifecycle

MCP is JSON-RPC between two roles: a host - the harness you are running - and servers it launches or reaches over a transport. A server offers three primitives: tools (model-callable functions with JSON schemas), resources (readable data addressed by URI), and prompts (reusable templates). The wire speaks in three moves: a handshake, a discovery listing, then calls.

The transports under those messages are where implementations diverge first: stdio (the harness spawns the server as a subprocess and speaks over pipes), Streamable HTTP (network calls to a remote server, usually with OAuth), and legacy SSE, which newer clients are actively deleting. Codex removed SSE support outright from its config types (mcp_types.rs, stdio and HTTP variants only), and Goose rejects configured SSE servers with a migration message (extension_manager.rs:1474, "SSE is unsupported, migrate to streamable_http").

3. Four depths of adoption

The table flattens a real difference: saying yes to a protocol is not one decision but a ladder of them. At the bottom rung a harness parses config and proxies calls - Codex, Kimi CLI, and opencode are essentially thin clients. One rung up, the protocol grows product features: Claude Code adds scoped configuration and OAuth flows and defers tool schemas until needed; Cursor distributes servers through a team marketplace and wires hooks around them; Antigravity ships a curated store; Cline and Roo build dedicated hub subsystems with per-tool approval lists. The top rung belongs to Goose alone among the open-source cast: its own bundled capabilities - memory, computer control, even the developer tools - are compiled-in MCP servers spoken to over in-process duplex pipes (goose-mcp/lib.rs), and its platform extensions implement the same client trait directly in Rust (mcp_client.rs:86). For Goose, MCP is not an integration format; it is internal architecture - the Goose deep dive shows what that buys.

4. What stays different anyway

Convergence stops at the wire. Three things stay stubbornly per-harness.

Naming. The same server surfaces under different dialects: mcp__server__tool in Claude Code and Codex, server__tool in Cline and Goose, mcp_server_tool in Gemini CLI (mcp-tool.ts:37, prefix constant), while Roo keeps XML-style wrappers named use_mcp_tool. Nothing breaks - each adapter owns its namespace - but prompts, permission rules, and logs written against one dialect do not transfer.

Context cost. Every mounted server donates its schemas to the window before the first keystroke, which is why deferral exists: Claude Code loads names only and fetches full definitions through a search step when needed ("Tool search keeps MCP context usage low by deferring tool definitions", its docs); Kimi can hold a server back entirely until the first turn; Windsurf caps the combined budget at one hundred tools. Lesson 0010 calls this principle two - context is assembled by code - and deferral is that principle applied to the tool list.

Trust seams. Each harness draws its own gate across the same protocol: Roo has an alwaysAllowMcp category and per-tool overrides; Cline has one global MCP toggle plus per-server auto-approve lists; Kimi routes every MCP call through approval under the action name mcp:<tool>; Antigravity defaults unconfigured MCP tools to Ask; Claude Code writes rules like mcp__github__*; Goose consults the server's own read_only_hint annotation, then falls back to an LLM judge. And because servers are supply chain, two members check what they launch: Gemini gates workspace-configured servers behind folder trust, and Goose screens npx/uvx launches against OSV malware advisories - though it fails open when the network does.

The reframing Lesson 0010's principle seven says growth means adopting shared protocols rather than adding features. MCP is that principle's biggest win - and the refusers are its standing counterexample. Aider simply predates the protocol and never needed it. Pi refuses deliberately, telling readers to build integrations as extensions or reach for ordinary CLI tools - proof that the protocol is a choice with a price, not a law of nature.

Check yourself

Retrieval practice

Answer from memory before revealing.

Your team writes one small MCP server wrapping internal build tools. Which harnesses can drive it?
The protocol decouples by design: Python, TypeScript, and Go servers all work from any client. Servers are separate processes reached over pipes or HTTP, no TTY involved. The spec is open, and membership gates nothing.
A project mounts forty servers and startup token cost explodes. Which mechanism pays names now and schemas later?
Claude Code's tool search and Kimi's deferred loading both work this way. Caching lowers cost without shrinking the window, compaction targets old conversation rather than live tool definitions, and namespacing prevents collisions while saving almost nothing.

Practice about 25 minutes, with a terminal

Practice 1working

Pick any published stdio MCP server - the filesystem server from the MCP examples works well. Register it twice: once in Goose's config.yaml extensions map and once in a second harness's equivalent config (Gemini's settings, Codex's [mcp_servers], whatever you have installed). Start each harness and ask it to list the tools it can see from your server.

Find: the exact tool names each harness shows, written down side by side, plus which config scope each one required.

Hint

You are hunting the naming dialect from section 4: prefixes and separators differ per harness even though the server binary is byte-identical.

Show the worked solution
  1. Register in Goose. Add the server under extensions: in ~/.config/goose/config.yaml with type stdio, then ask goose to enumerate its tools.
  2. Register in the second harness. Add the same command and args to its config format, start it, and enumerate again.
  3. Compare. Goose shows unprefixed-or-namespaced names per its extension rules, Gemini prefixes mcp_, Claude Code uses mcp__server__tool - same server, three dialects.

Sanity check. If the names differ while the server did not, you proved the adapter layer owns naming; if they match, both configs resolved to the same harness by accident.

Your teacher. If the four depths have not landed, ask it to argue which rung Codex belongs on and why its SSE removal is evidence either way. If trust seams feel abstract, ask for the failure each seam catches: an always-allow toggle, a missing folder-trust prompt, a malicious npx package.
