The one-minute version

  • Only the chat and agent half of Copilot is open source. The ghost-text completion engine stays closed, shipped as a pinned npm dependency.
  • Prompts are TSX component trees: every piece of context declares a priority, and an overflow prunes the lowest-priority subtree.
  • The loop never dispatches tools itself. Tool calls from last round execute during the render of the next prompt, inside a component's render method.
  • Failed patches get one repair attempt by a cheap model before your expensive one ever hears about it.

The loop

Agent mode is a while (true) loop in toolCallingLoop.ts whose each iteration builds a prompt, streams a response, and decides whether to continue. The default agent-mode cap comes from the chat.agent.maxRequests setting at 200; other intents get far fewer. Hitting the cap shows a Continue? dialog - unless the request's permission level is autopilot, which silently raises the limit by half as much again, up to the same hard ceiling of 200.

Context assembly

Every iteration rebuilds the whole window by rendering AgentPrompt, and the tree reads top to bottom like the window itself (agentPrompt.tsx): a system message carrying identity and safety rules plus a per-model system prompt chosen by family; custom instructions headed by .github/copilot-instructions.md; a memoized global-context user message with environment and workspace info capped by a TokenLimit; then history, prior tool rounds, and finally the current question. Two budgets bind the whole thing: any single tool result may claim at most half the window (MAX_TOOL_RESPONSE_PCT = 0.5), and the message list keeps a ten percent safety margin under the model maximum.

Trust posture

There is no operating-system sandbox in this codebase - isolation belongs to VS Code core's terminal approvals and workspace trust. What the extension owns is a contract: any dangerous tool must attach confirmation messages to its prepared invocation, which the editor turns into a diff preview and a yes/no. Above that sit two escalation levels defined for requests, auto-approve and autopilot, the second adding the continue-until-complete behavior you saw in the loop diagram. Hooks give teams their own gate: a PreToolUse command can return allow, ask, or deny and rewrite the tool input before anything runs, configured as JSON commands over stdin and stdout. Content exclusion filters what reads and searches can see, in .gitignore style.

Set against lesson 0050's four postures, Copilot is an ask-first harness whose asking is delegated to each tool's own declaration - the opposite pole from Codex CLI enforcing a sandbox first and treating approval as remediation.

Model behavior

Every Copilot-served model flows through one endpoint whose wire protocol is picked from per-model metadata delivered by the server: OpenAI Chat Completions, the Responses API, or Anthropic Messages behind an experiment flag. The client hardcodes no default model - the server's metadata marks which model is default. What differs per family is everything around that choice:

FamilyWhat changes
Claudenative Messages protocol; adaptive thinking with clamped budgets and beta headers; signed thinking blocks replayed into history; explicit cache_control breakpoints, at most four
GPT-5.x and Codex modelsResponses protocol; reasoning effort levels; encrypted reasoning content requested and echoed back; cache control via copilot_cache_control parts keyed by conversation
GeminiChat Completions plus a dedicated system-prompt class; orphaned tool calls stripped from responses before they enter history
Everyone elseChat Completions plus a family-matched system prompt - nine OpenAI variants alone exist alongside anthropic and gemini prompt classes

Snapshot tests pin rendered prompts per family, so the per-model divergence is deliberate and versioned rather than accidental. Lesson 0100 generalizes the pattern across the cast.

The distinctive mechanism

In Claude Code, Codex, Cursor or Aider, dispatching a tool is loop code: response arrives, harness executes calls, appends results, sends again. This loop never executes a tool. It stores each round, and on the next iteration the prompt tree contains a ChatToolCalls element whose render() method invokes the pending tools through the tools service (toolCalling.tsx), wrapping each result in an element that lands back in the message list. Execution is a side effect of composing the next request.

Three consequences fall out. Permission hooks fire inside the same render pass, so a deny decision edits the very content being composed rather than intercepting a side channel. Subagents reuse the trick wholesale: spawn one and you get another loop whose own renders execute its own tools. And the cost is real - when tools misbehave, debugging means understanding a renderer, because there is no separate dispatch stage to breakpoint. Lesson 0010 collects the design forces behind such convergences; this harness demonstrates its sharpest version, that wherever the harness builds its context is where the harness actually acts.

Runner-up mechanisms worth teaching beside it: patch healing sends a failed apply_patch document plus the file's real contents to the cheap copilot-fast endpoint for one repair attempt before returning failure upward (applyPatchTool.tsx, healCommit) - the same self-healing instinct as Gemini CLI's edit cascade, bought with a small model instead of a matching cascade. And autopilot's stop gate requires a literal task_complete tool call plus a summary, turning "am I done?" from a judgment into a wire-level event.

Check yourself

Retrieval practice

Answer from memory before revealing.

In Copilot Chat agent mode, where do a model's tool calls actually execute?
ChatToolCalls.render() walks the stored rounds and invokes each pending tool while composing the next prompt - the loop body itself never dispatches. There is no post-stream worker pool, core owns terminals but not this dispatch, and approval is per-tool via confirmation messages, not batch-gated.
Your apply_patch call fails because the surrounding lines drifted from what the model expected. What does the harness try next?
healCommit hands the failed patch and current document text to the copilot-fast endpoint once before surfacing failure. There is no rewrite fallback, no forced-apply prompt, and the point of the healer is precisely that the main model should not spend a turn re-learning the file.

Practice about 10 minutes, with paper

Practice 1working

Recall the pruning rule from the prompt-tsx README: when a rendered tree exceeds its budget, the lowest-priority sibling is dropped first, and siblings tie-broken by their children. Copilot's non-cache-breakpoint tree declares these priorities: conversation history 700, prior tool rounds 899, current user message 900, and - in autopilot only - the task_complete reminder 80.

Find: the eviction order of those four elements under an overflowing window, and the reason the product still behaves sensibly in normal use despite the reminder being first out.

Hint

Sort by the declared numbers, lowest evicted first. Then ask: when does the reminder even exist in the tree, and how big can a single turn's overflow be relative to it?

Show the worked solution
  1. Sort ascending. Eviction order: task_complete reminder (80), then conversation history (700), then prior tool rounds (899), then your current message (900).
  2. Explain why it rarely bites. The reminder only exists in autopilot requests, and it is a few dozen tokens against a window measured in six figures - it is evicted only when nearly everything else is already gone.
  3. Name the design reading. Priority encodes importance, not recency: the harness decided your live question outranks even its own instructions, and old history outranks nothing at all.

Sanity check. If the order came out history-first, transcripts would lose memory before losing trivia, which is the opposite of observed behavior - the declared ladder matches what users see.

Your teacher. Ask it to contrast this page's renderer-dispatcher with lesson 120's reply-as-action parser: both moved work out of a dedicated dispatch phase, into rendering in one case and parsing in the other. Which failures does each design make harder to see, and which easier?
