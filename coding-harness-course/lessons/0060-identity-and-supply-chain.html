Module 03 · Trust · Lesson 06

Your agent has a body, and the operating system can see it

working 10 min Grounded in Apple's code-signing documentation and in pi-launcher read at commit 564fa16. · Gatekeeper and runtime protection

The one-minute version

  • Every tool call your agent makes executes inside a process carrying an identity the OS can verify - or an identity it cannot.
  • An ad-hoc signature seals the bytes but vouches for nobody: its cdhash changes on every build and nothing stable survives an update.
  • A designated requirement on Developer ID code names the signer rather than the bytes, so it stays constant across releases - which is what credential brokers match against.
  • One cast member, pi-launcher, designs this layer deliberately: a signed process identity plus a release pipeline that refuses to ship what fails a gate.

1. What macOS can actually see

Every executable on Apple Silicon must carry a valid signature or the kernel refuses to map it. The cheapest possible signature is the ad-hoc one, made with codesign --sign -: no certificate, no identity, just a cryptographic seal over the bytes. That seal does two things - it satisfies the kernel, and it makes tampering detectable. It deliberately does not do a third: it never answers who vouches for this code.

Two more terms carry the rest of the page. The cdhash is the hash of the signature's code directory, which covers the page hashes of the whole executable - a unique fingerprint of one exact build (TN3127). Rebuild with a single changed byte and the cdhash changes. The designated requirement (DR) exists to fix exactly that instability: it states what makes code an instance of this program, and Apple's tech note TN2206 says it should be satisfied by future updates too (TN2206). For Developer ID code the DR names the identifier, anchor apple generic, and the Team ID - the signer, not the bytes.

Gatekeeper is the policy face of all this: before first launch of downloaded software it verifies the code comes from an identified developer, was notarized by Apple, and has not been altered. Its command-line form, spctl, accepts Developer ID or Mac App Store signatures. An ad-hoc app fails both tests - not because the seal is broken, but because there is nobody behind it.

2. Who eats this property

The consumer that motivated pi-launcher is named in its README: Automic Vault, which approves credential access by walking the process ancestry and matching designated requirements along the way (README.md:35). When an agent asks for an API key, the vault inspects everything between the agent and your shell.

Note what would and would not fix this. Signing once is not enough - any later rebuild changes the cdhash again. The fix is a signature whose policy-facing part names something durable. That is the whole difference between the two halves of the figure above.

3. Wrapping without breaking the terminal

So put a signed program above the agent. The naive way is execve: the wrapper replaces its own image with the target's. That destroys the point in one syscall - the moment the launcher execs into Pi, the process tree shows Pi's ad-hoc Mach-O again. pi-launcher instead forks and stays alive as Pi's direct parent forever (fork at pi-launcher.c:175, execve at :199).

Staying alive as an extra family member creates the second problem: a wrapper that mishandles signals breaks job control in ways users feel instantly. The launcher's rule is never deliver a signal twice. Terminal-generated signals such as Ctrl-C go to the whole foreground process group, so the launcher ignores SIGINT and SIGQUIT itself rather than forwarding them; it forwards only signals aimed at its own PID - SIGHUP, SIGTERM, SIGUSR1, SIGUSR2 (kForwardedSignals, pi-launcher.c:54) - and if Pi dies by signal, the launcher raises that same signal on itself so $? matches a direct run exactly. The deep dive on this project, lesson 025, walks the full Ctrl-C path and the test suite that proves it.

4. Provenance is a pipeline, not a promise

Identity answers who signed this; provenance answers are these the bytes they published. pi-launcher's answer is mechanical. The upstream Pi release is pinned by tag, tarball URL, and SHA-256 in packaging/pi-release.json, and every build verifies the download twice: against the pinned hash and against the entry in upstream's own published SHA256SUMS (fetch-pi.sh:57-71). Two independent references must agree before anything proceeds.

The signing chain runs inside-out through nested code, with hardened runtime and secure timestamps, then notarization and stapling; the release workflow verifies the artifact three times and launches it three times, including a fresh re-download of the published zip checked byte-for-byte. When an upstream release fails any gate, the pipeline files a quarantine issue keyed by the exact tag and never retries that tag while the issue is open - a failed gate stops the world instead of shipping anyway. Lesson 025 draws the whole pipeline as a figure; the transferable shape fits in one sentence: pins, dual verification, and gates whose failure mode is quarantine, not a warning label.

5. What about the other fifteen

The uncomfortable result of surveying the cast is how few harnesses treat this layer as designed. Our sixteen reports record distribution and update facts unevenly - and that unevenness is itself the finding: for most of the cast, process identity is an accident of the install method. A stable identity is not authorization, and it is not a sandbox. Matching a designated requirement tells a policy tool which program is asking - whether to grant anything remains the tool's decision, untested until tested. And the wrapped agent still runs with your full user permissions: signing changes who is vouching, never what the code may touch.

Check yourself

Retrieval practice

Answer from memory before revealing.

A teammate downloads a coding-agent binary directly and macOS blocks it at first launch. It was signed ad-hoc. Why?
Gatekeeper and spctl accept Developer ID or App Store signatures; ad-hoc code has neither, so there is no developer to identify. The first option describes a real property - the cdhash does change - but that is not the rejection reason. The third invents a mechanism, and the fourth is false: ad-hoc signatures do not expire.
Why must pi-launcher fork and stay alive instead of exec-ing straight into the agent?
Exec preserves file descriptors, so the first option is false; Pi needs no resident parent, and dispositions need resetting rather than copying. The real reason is structural: the launcher's value is being a signed ancestor, and exec turns it into the very unsigned binary it was wrapping.

Practice about 15 minutes, with a terminal

Practice 1working

On a Mac, pick two programs you run daily - for example a GUI app in /Applications and an npm-installed CLI on your PATH. Run codesign -dr - <path> on each and read the designated requirement it prints, then codesign -dv --entitlements - <path> for the entitlements.

Find: for each binary, whether its DR names a Team ID (stable across updates) or nothing at all - and therefore whether a credential broker could say anything durable about it.

Hint

Apple-signed and Developer-ID apps typically print identifier "..." and anchor apple generic and certificate ... with a Team ID. A script that is really a Node or shell entry point often prints nothing useful at all - ask what process the OS actually sees when it runs.

Show the worked solution
  1. Run the inspection. codesign -dr - prints the designated requirement, or reports that the binary is not signed at all.
  2. Classify each result. A DR naming anchor apple generic plus a Team ID survives updates; a missing or ad-hoc result identifies one build only, and an unsigned script identifies nothing.
  3. Draw the consequence. Any tool gating access by process identity can match the first kind forever and the second kind never.

Sanity check. At least one of your two picks should show a Team-ID-backed DR and the other little or nothing - daily toolchains mix both worlds constantly, which is exactly why this layer usually goes unnoticed.

Your teacher. If the cdhash-versus-designated-requirement distinction has not landed, ask for the thought experiment: what would a credential broker have to store to recognize a program rebuilt nightly? Then ask it to walk your own PATH guessing which entries could pass.
