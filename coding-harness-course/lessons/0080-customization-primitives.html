Module 04 · Extending · Lesson 08

Four customization primitives decide who your agent can become

working 9 min Evidence read from each harness's own source or documentation; the Roo Code deep dive develops its mode system in full. · Agent Skills standard

The one-minute version

  • MCP adds tools. These four primitives change something bigger: what the agent knows, where work happens, what policy enforces, and who the agent is.
  • Each primitive takes one of three forms: a file convention you commit, a config schema you register, or a runtime API the model calls.
  • The cast disagrees wildly - one ships thirty hook events, several ship none, and the skill file that eight harnesses share is loaded four different ways.
  • The mode system, carried furthest by Roo Code, is what happens when you stop treating these as features and bind them into one authorable persona.

1. Four questions, four primitives

The confusion this page fixes is real: all four primitives arrive as markdown files or JSON somewhere under a dotfolder, so they look like one feature. They answer different questions. A skill answers "what should the model know when this task appears" - it changes context content. A subagent answers "where does work happen" - it changes process topology, giving a job its own context window so its debris never lands in yours. A hook answers "what enforces the rules" - it changes who holds policy, moving decisions from human review to deterministic code. A mode answers "who is the agent right now" - it changes identity: role, permissions, sometimes even the model behind it.

2. Skills: knowledge that loads only when needed

A skill is a folder whose SKILL.md carries frontmatter - a name and a description - plus instructions. The trick that makes it scale is progressive disclosure: at startup the harness reads only names and descriptions, a line or two each; the full body enters context only when a task matches. The Agent Skills standard describes this as three stages - discovery, activation, execution - and it is why you can install dozens of skills without paying for them until they fire.

The convergence is remarkable and the divergence is instructive. Eight members of our cast read some flavor of SKILL.md. Claude Code resolves personal, project, enterprise, and plugin scopes, merges the old .claude/commands/*.md convention into skills, and exposes both paths to the same invocation: the model calls the Skill tool, or you type /deploy. Roo Code adds mode targeting - a skill under .roo/skills-code/ activates only in Code mode - and lets project skills override global ones. Kimi CLI turns every standard skill into a slash command, and its flow skills go further: a Mermaid diagram inside the SKILL.md is parsed into an executable state machine. Then there is the dissenting design. GitHub Copilot Chat does not give the model a skill-loading tool at all - its prompt carries an <additional_skills_reminder> telling the model to ReadFile the SKILL.md itself. Same file format, same progressive disclosure, but loading is delegated to ordinary tool use rather than a dedicated primitive. And Aider ships no skills at all: its predecessor-era answer was the repo map, not packaged procedures.

3. Subagents: isolation as a primitive

A subagent is a nested loop: the main conversation asks a smaller agent to do a bounded job in its own context window and accept back only a summary. The point is arithmetic - a search that reads forty files would otherwise spend your window on debris. What varies is how much you can author. Claude Code makes subagents a file convention: a markdown file in .claude/agents/ with frontmatter choosing its tools, model, permission mode, even a persistent memory, and the model reaches for it through the Agent tool. Codex CLI splits the difference - role definitions live in TOML under agents/, but spawning goes through a model-callable family (spawn_agent, send_message, wait_agent). Roo Code binds subtasks to modes: the orchestrator calls new_task, the child runs in a different mode with its own model profile, and only the child's completion summary returns - we draw that loop in full in the Roo Code deep dive. And two members answer with absence. Cline has no subagent mechanism. Pi refuses one on purpose - its documentation lists sub-agents among the things it intentionally omits, offering instead the honest escape hatch that a shell command can always launch a second Pi. Absence here is architecture: nothing to configure, nothing to trust, and the window stays whole.

4. Hooks: policy you write down

A hook is your code standing where harness code would otherwise stand alone: before a tool executes, after it fails, when the session starts, when the model tries to stop. The shape is nearly universal - the harness sends event details as JSON, your handler replies with a decision or an exit code, and a blocking verdict feeds back to the model as information rather than an error. Claude Code's PreToolUse hook can return permissionDecision: deny; Codex CLI's Stop hook can block completion and continue the loop; Windsurf's pre_run_command blocks a shell call with exit code 2.

What the counts below show is a design space, not a maturity contest. Pi and Claude Code expose around thirty lifecycle points because they treat extensibility as the product. Codex, Goose, Windsurf, and Kimi cluster near twelve - enough to gate tools, prompts, and stops. Cline wires only seven events, but spends them lavishly: its checkpoint system is itself a beforeModel hook. At the other pole sit three deliberate zeros: Aider offers lint and test commands you configure, but no events; Roo Code ships no hook system at all - its safety story leans on approval gates and mode restrictions instead.

5. Modes: identity as configuration

A mode rebinds who the agent is, mid-project, without restarting anything. The minimal version changes the prompt. Aider's chat modes swap the coder class under you - type /chat-mode architect and a SwitchCoder exception tears the current object down and rebuilds it with shared history, switching between an ask persona and an edit persona. Cline's plan and act presets go further, keeping a separate provider per side and rebuilding the whole session on switch. But the version worth studying binds four dimensions at once. In Roo Code a mode is one authorable YAML object whose slug simultaneously selects the opening of the system prompt, the tool groups the model may call - restricted, if you wish, to files matching a regex - a directory of mode-scoped rules, and a sticky API profile remembering which model that persona prefers. Orchestrator mode carries zero tool groups: it can think and delegate through new_task, nothing else. That binding - prompt, permissions, rules, and model in one object you commit - is the fullest expression of persona on the market, and the Roo Code deep dive walks its mechanics file by file. Windsurf marks the opposite shore: its modes are fixed by the vendor and its documentation states plainly that no user-defined modes exist.

The reframing Ask of any harness not "does it have skills" but "which of these four did it make authorable, in what form, and what did that choice cost". Eight harnesses sharing one skill format while loading it four ways tells you the industry standardized the container and left the semantics open.

Check yourself

Retrieval practice

Answer from memory before revealing.

Your teammate says their agent "reads a markdown file into context only when the current task matches it". Which primitive is doing that work?
Conditional loading of instructions on task match is progressive disclosure - the skill contract. The first option describes policy enforcement, which decides rather than loads. The third isolates work but does not select content by relevance. The fourth swaps identity wholesale rather than adding task knowledge.
Roo Code's orchestrator mode ships zero tool groups yet still coordinates multi-step work. What makes that coherent?
Delegation tools - new_task and companions like attempt_completion - are always available regardless of group membership, so orchestrator can delegate without touching files. Hooks are absent in Roo Code entirely. Sticky profiles pick models, never permissions. MCP would add external tools, but orchestrator's design needs none of them.

Practice about 15 minutes, with your own machine

Practice 1working

Open the home directory and repository root of whichever coding harness you drive daily. Inventory its extension surface against the four primitives: find one artifact per primitive - a skill folder, a subagent definition, a hook registration, a mode file - and classify each finding as file convention, config schema, or runtime API.

Find: for each of the four primitives, either the artifact proving it exists or an explicit "absent", plus the form it takes.

Hint

Search for SKILL.md, then for directories named agents or modes under the harness dotfolder, then grep its docs or settings schema for event names containing Tool. Absence is a finding too - say what the harness offers instead.

Show the worked solution
  1. Skills. A Claude Code setup shows ~/.claude/skills/*/SKILL.md - file convention. A Copilot setup shows the same folders but no loader tool - still a convention, loaded differently.
  2. Subagents. .claude/agents/*.md or Codex's agents/*.toml are conventions; Roo Code exposes delegation through the new_task runtime tool instead. If you find neither, check whether the shell can nest the harness - Pi's documented pattern.
  3. Hooks. A hooks key in settings JSON or a hooks.json is a config schema. Zero results means the harness gates by approval prompts instead - record which posture you actually have.
  4. Modes. A .roomodes file or a modes pane in settings proves authorable identity; fixed plan/ask toggles do not count - those are permission switches, not personas.

Sanity check. Most harnesses land on two or three of four; a page with all four present and none absent usually means you classified the same artifact twice - a skill and its slash command are one finding, not two.

Your teacher. If the four primitives still blur, ask it to take one harness at a time and produce the four-row table from section 1 filled in with that harness's real identifiers - then argue about which row is weakest. For a deeper pass, ask it to explain why Roo Code could skip hooks entirely and still ship a safety story.

Primary source to go deeper

The Agent Skills specification - the one file format most of this cast converged on, including its three-stage progressive-disclosure contract: agentskills.io. Reading it after this page, notice how little it fixes: the loading mechanism, the scoping rules, and the invocation surface are all left to each harness.
