Goose is a workflow engine with an agent loop inside

Read these five files, in this order:
  1. crates/goose/src/agents/agent.rs - the reply loop, the 1000-turn cap, the inspector chain
  2. crates/goose/src/agents/extension_manager.rs - every capability as MCP, transport zoo included
  3. crates/goose/src/agents/prompt_manager.rs - assembly order, with crates/goose/src/prompts/system.md beside it
  4. crates/goose/src/agents/moim.rs - the MOIM turn-context channel, goose's quietest good idea
  5. crates/goose/src/agents/schedule_tool.rs - manage_schedule, the self-scheduling seam, with scheduler.rs alongside
Community: issues and discussions on the repository, plus engineering posts vendored under documentation/blog/. Block donated the project to the Agentic AI Foundation under the Linux Foundation.

The one-minute version

  • One backend process serves both front doors: the CLI runs it in-process; the desktop app spawns it and speaks ACP over localhost TLS.
  • The loop is standard until you look closer: persistence-first (the user message commits to SQLite before any model call) with a five-inspector trust chain above it.
  • Every capability, first-party or third-party, speaks MCP - even bundled built-ins ride an in-process transport.
  • The distinctive move: declarative recipes on a cron scheduler where registering the schedule is itself a tool the model calls.

There are two front doors into one process model. The CLI links the agent library directly; the desktop app is UI-only and at startup spawns a local backend (goose serve --tls --enable-scheduler, gooseServe.ts), polls GET /status for readiness, pins the cert fingerprint the child prints as GOOSED_CERT_FINGERPRINT=, and then speaks ACP - Agent Client Protocol JSON-RPC - over wss://127.0.0.1/acp?token=... (acp/transport/mod.rs). Because the server receives the shared data directory, CLI and desktop see one session store.

The loop

Entry is Agent::reply flowing to reply_impl in agent.rs, and its first act is the one worth remembering: persist the user message to SQLite before asking the model anything, then reload the conversation from disk. Each outer iteration drains steering messages the human queued mid-turn, enforces DEFAULT_MAX_TURNS of 1000 (overridable via GOOSE_MAX_TURNS), and streams from the provider. Tool requests are categorized frontend-versus-backend, then handed to an inspection chain producing approved, needs-approval, or denied; approved calls execute concurrently through the ExtensionManager, results append to SQLite, and the loop continues while the stream carries content.

A second loop ships behind GOOSE_STATE_MACHINE=1 (forced for bang-shell commands): the whole pipeline becomes ordered operations - entry hook, slash command, steer, max turns, compaction, approval, skill, recipe, tool execution, retry, stop hook, exit-on-error - with a final inference runner aggregating context and tools from all of them. Same behavior, factored as a state machine; the migration is ongoing in the open.

Context assembly

SystemPromptBuilder::build in prompt_manager.rs composes, in order: a deliberately small persona file (system.md, thirty-nine lines with no working-directory or date line); additional instructions from enabled extensions; then hints. Hint loading is a place where folklore beats facts: the defaults are exactly .goosehints and AGENTS.md - globals from the config directory, then project files walked from git root down to cwd (load_hints.rs). CLAUDE.md, .cursorrules, and GEMINI.md are not loaded unless you add them via the CONTEXT_FILE_NAMES setting. Two choices exist purely for cache hits: the extension catalog renders alphabetically, and the timestamp is truncated to the hour.

The unusual piece is MOIM ("top of mind", moim.rs): once per turn, goose appends an agent-only user message carrying minute-truncated time, working directory, remaining-token estimates once past half the budget, and extension-contributed state like the todo list. It is persisted once and never edited, so caches survive and visible history stays clean. Below 32k contexts it switches off entirely.

Compaction triggers proactively above 0.8 of the context limit (DEFAULT_COMPACTION_THRESHOLD) or reactively on overflow: one LLM call summarizes history into structured JSON - intent, files touched, pending tasks, next step - re-rendered as an agent-only summary message, originals kept in storage but hidden from the agent, latest real user message preserved verbatim. Before that bites, older tool request/response pairs are replaced by one-line summaries in batches of ten. Token counts estimate with tiktoken's o200k_base regardless of vendor; there are no embeddings anywhere - recall is SQL keyword search.

Trust posture

Four modes (goose_mode.rs): auto approves everything, approve asks every call, smart_approve waves reads through and asks about the rest, chat removes tools entirely. Decisions flow through five inspectors merged so any can deny or escalate but none can force-run: pattern security (disabled by default), egress telemetry (log-only, always allows), an opt-in LLM adversary reviewer (fails open), the permission inspector honoring your persisted lists in permission.yaml, and repetition detection. Smart approve consults the server's own read_only_hint, then falls back to an LLM judge that sees arguments as untrusted data. Persistent grants are per tool name and survive sessions; allow-once never persists.

There is no OS-level sandbox. An experimental macOS Seatbelt integration shipped in v1.25.0 and was removed; the project's own post for that release says the server "runs with the same permissions as your user account and is not sandboxed at the OS level" (blog post, in-repo). Shell commands spawn as ordinary children with full privileges; Docker confinement exists only as an option for stdio MCP servers, and the malware-advisory screen on npx/uvx launches fails open without network.

Extension surface

The tool-ecosystem page placed Goose at the top of the adoption ladder; here is the mechanism in one breath. Thirteen platform extensions implement the MCP client trait in-process (developer, skills, summon, scheduler, todo, analyze, and friends); bundled servers compile into the binary and speak over in-process duplex pipes; external servers connect by stdio, Streamable HTTP, or docker exec. Two consequences are unique. The model can manage its own tooling mid-session - extensionmanager__manage_extensions enables and disables servers live (ext_manager.rs). And skills follow the agentskills.io convention but with a twist: every discovered SKILL.md automatically becomes a slash command, alongside nine built-ins, with precedence builtin over recipe over skill. Hooks arrive through plugins - twelve lifecycle events, though only PreToolUse and Stop can block. Subagents spawn via delegate as fresh in-process agents on dedicated sessions, twenty-five turns by default, nesting prohibited.

Model behavior

The Provider trait has exactly one required method - stream - and the registry layers fifteen preferred providers, twenty built-ins, and forty-four declarative JSON-defined endpoints. Wire formats are a separate layer of formatter modules, so providers reuse dialects: Vertex routes Claude models through the Anthropic builder. Per-family divergence concentrates in three places:

The distinctive mechanism

Recipes plus the scheduler, closed into a loop the model itself controls. A recipe is a declarative YAML artifact: instructions that join the system prompt or a prompt that becomes the user message; typed parameters; embedded extension requirements; provider/model settings; a JSON schema for structured output; retry policies whose success checks are predicates re-run against the transcript; and sub-recipes with parameter passing. Rendering is template-sandboxed to the recipe's own directory, and validation rejects undeclared variables. The scheduler executes recipes on six-field cron expressions, creating headless scheduled sessions and persisting jobs with hardened byte-for-byte copies of the recipe they will run.

The third step is the one no sibling harness takes: manage_schedule is exposed to the model as an ordinary tool (schedule_tool.rs). A running session can register future invocations of any recipe - including one it just wrote to disk moments earlier - then, days later, read those sessions' outputs back through the same tool's list-and-inspect actions. Combined with delegate, one conversation can spawn parallel work now and book recurring work for later.

Honest framing: the core REPL, hint files, approval modes, and MCP plumbing follow the industry pattern goose helped popularize as one of the first MCP-native agents in January 2025. This page demonstrates principle seven - grow by adopting shared protocols - and principle nine, state as a designed artifact: SQLite is re-read before every reply, rollback truncates the conversation tail, forks copy sessions. Even the stop condition is policy, principle one: a thousand-turn ceiling, and chat mode removing tools altogether. The novelty is the workflow layer around the loop, not the loop.

Check yourself

Retrieval practice

Answer from memory before revealing.

What does Goose's manage_schedule tool actually hand the model?
The tool registers, lists, and inspects scheduled jobs - including recipes authored minutes earlier. Turn caps come from configuration, recipes are authored rather than extracted, and crash semantics belong to the session store, not the scheduler.
A fresh project contains CLAUDE.md and AGENTS.md. Which does Goose load by default?
The hardcoded defaults are exactly .goosehints and AGENTS.md. CLAUDE.md, .cursorrules, and GEMINI.md load only if you add them via CONTEXT_FILE_NAMES; there is no merge-with-precedence rule, and recipes have nothing to do with hint discovery.

Practice about 30 minutes, with a terminal

Practice 1working

Write a five-line recipe: a title, one instruction telling the agent to append today's date and one fact to a local log file, and nothing else. Validate it with goose recipe validate your-recipe.yaml, run it once with goose run --recipe your-recipe.yaml, then ask a live goose session to schedule that recipe to run every minute using its own manage_schedule tool.

Find: the new job in the scheduler's persisted file, the hardened copy of your recipe beside it, and the headless session rows appearing afterward in the session store.

Hint

You are watching one SQLite store serve interactive and scheduled sessions at once. Compare session types after the cron fires twice.

Show the worked solution
  1. Validate and run. The validator rejects undeclared variables, so a minimal file passes only when truly minimal; the manual run proves the instruction works interactively first.
  2. Schedule from inside the loop. Asking the live session - rather than clicking a dialog - exercises manage_schedule: the model calls the tool with your recipe path and a cron expression.
  3. Verify the artifacts. The job lands in schedule.json with a hardened copy of the recipe under scheduled_recipes/, and each firing creates a new session row of the scheduled type.

Sanity check. If the scheduled runs appear in the same store as your interactive session, you confirmed the one-store claim; if the recipe copy differs from your file, you edited it after booking - the snapshot protects against exactly that.

Your teacher. If the self-scheduling loop has not landed, ask for the threat model: what could a malicious recipe book, and which of the five inspectors would see it. If context assembly feels busy, ask why MOIM persists once per turn instead of updating in place.
