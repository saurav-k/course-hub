Identity

Roo Code began in late 2024 as Roo Cline, a fork of Cline, and rebranded once custom modes arrived - its own changelog credits the rename to outgrowing fifty thousand installations. It is a TypeScript monorepo whose extension host runs one agent core behind two shells: the VS Code webview UI, and a CLI that runs the same code headlessly through a fake VS Code API (@roo-code/vscode-shim). At the pinned commit it counted roughly twenty-four thousand GitHub stars and three million installs, and its self-description - a whole dev team in your editor - is more literal than most slogans: the product's central artifact is the ability to define teammates.

The loop

The loop lives almost entirely in Task.ts. An outer while (!this.abort) drives an inner iteration stack; each iteration expands mentions, appends fresh environment details, rebuilds the system prompt, and streams from the provider. Tool calls arrive through native function calling only - the XML-in-text-stream parser inherited from Cline was deleted outright, so a malformed call without an id is refused with an error telling the model that XML calls are no longer supported. The inherited trick survives: tools execute while later blocks are still streaming, and each result is pushed straight into the next user message. The turn ends only when the model calls attempt_completion, which blocks awaiting your verdict - approval idles the task, feedback text becomes the next tool result. A task never completes autonomously; the user or a request cap closes it, a fact the source states in a comment beside the loop itself.

Context assembly

Every request rebuilds the prompt from scratch: the active mode's role definition opens it, followed by tool-use guidance, capabilities, the list of available modes with their whenToUse hints, skills, rules, system facts, and finally the user's instruction block - global settings, then mode-specific instructions, then rules files in strict precedence (.roo/rules-{mode}/ directories before legacy .roorules, AGENTS.md honored when enabled). Notably absent: CLAUDE.md and .cursorrules are never loaded natively. A fresh <environment_details> block rides onto the last user message every turn - visible editors, running terminals, recently modified files, git status, current mode - replacing any stale copy first.

Budgeting is explicit arithmetic: usable window equals context window minus a ten percent buffer minus reserved output tokens. Crossing the condense threshold triggers one summarizer call whose output replaces prior history non-destructively - old messages stay tagged on disk so checkpoints can rewind past them - with a half sliding-window truncation as fallback and a forced seventy-five percent reduction if the window is exceeded outright.

Trust posture

Roo Code sits in the ask-first family with granular automation. Seven auto-approval categories - read-only, write, protected writes, MCP, mode switches, subtasks, commands - each toggle independently; command gating splits chained commands and matches allowlists by longest prefix. Two guardrails are worth stealing mentally: a spend limiter caps consecutive requests and cumulative cost even when everything is approved, and a protected-file controller requires separate consent before anything may write .roomodes, .roorules, AGENTS.md, or .roo/** - the configuration surface itself is defended, because a harness that edits its own permissions has lost them. There is no OS sandbox and no network policy; rollback instead comes from a shadow git repository per task that commits before every mutating tool. And the hook count from the previous page shows here as a zero: policy is approvals, categories, and mode restrictions, not user-written event handlers.

Extension surface

MCP speaks all three transports with project config overriding global; skills follow the Agent Skills standard from four locations with mode-scoped directories; slash commands are markdown files with frontmatter; subtasks run through new_task. What the cast shares here matters less than what binds it: every extension mechanism reads the current mode before deciding what exists - skill directories gain a mode suffix, MCP tools filter by group membership, and the tools themselves are withheld per mode rather than merely discouraged.

Model behavior

A factory switch covers about twenty-seven providers over two wire dialects, with typed catalogs carrying context windows, prices, and capability flags per model. Family handling differs where the families differ: Claude thinking budgets clamp against max tokens with temperature pinned while thinking, GPT-5 models drop temperature support and ride the Responses API, Gemini receives every tool definition plus an allowlist enforcing mode restrictions at the API level, Bedrock places token-aware cache points by strategy rather than markers. The default profile points at Anthropic's Sonnet via OpenRouter. None of that is unusual by cast standards - the distinctive part is who selects the model, which is the next section.

The distinctive mechanism

The mode system binds four dimensions into one authorable object. A single YAML entry in .roomodes sets the role definition that opens the system prompt, the tool groups - optionally restricted by file regex - the mode-specific rules directory, and a sticky API profile remembered per mode in secrets storage, restored automatically whenever you switch. Enforcement is real: validation checks every completed tool call against the mode's groups and regex, including paths parsed out of patch bodies, and rejects violations as error results the model must handle.

The arithmetic makes the design legible. Counting static built-ins - four read tools, three edit tools, two command tools, two MCP wrappers, plus seven always-available companions including delegation - the code mode carries eighteen tools, ask thirteen, and orchestrator exactly seven. Five built-in modes ship with the product, each a different answer to "who is working now", and any number of yours can sit beside them in version control.

The repository was archived read-only in May 2026 after the original team moved to a successor product, with community maintenance announced in the final changelog. Every mechanism described here is verifiable at the pinned commit forever, but the project will not evolve - treat this page as a snapshot of the fullest persona-binding design shipped to date, not a living roadmap.

Retrieval practice

Answer from memory before revealing.

An architect mode restricts its edit group to markdown files. Where does that restriction actually bite?
Validation runs on every completed tool call against the mode's groups and regex - paths inside patch bodies included - and returns an error result. The prompt informs but does not enforce. The UI hides nothing here, and while tool filtering does happen per group, the regex check happens at execution time on arguments.
You switch from code mode to docs-writer mode. What happens to the model selection?
Sticky profiles map every mode slug to an API config in secrets storage, restored on switch - that is the mechanism the docs call Sticky Models. Option one describes the opt-out lock setting, not the default. There is no fresh-default reset, and parent-child inheritance belongs to subtasks, not mode switching.
