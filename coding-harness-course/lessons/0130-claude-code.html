Claude Code: the loop that reviews itself

working 12 min Closed source - covered entirely from Anthropic's official documentation, fetched August 2026, plus its documented claude auto-mode defaults export run locally. · code.claude.com/docs

Explore it yourself

No repository exists to open. Claude Code is closed by Anthropic: proprietary license, one native binary bundling its own runtime. Its GitHub repo (anthropics/claude-code) hosts issues and the changelog only - no source tree, so no SHA or file list.

Five official pages, in reading order:

  1. How Claude Code works - loop, sessions, checkpoints
  2. Choose a permission mode - six modes, classifier policy
  3. Configure permissions - rule syntax, precedence, hooks
  4. Explore the context window - startup stack, compaction
  5. Tools reference - full tool table, exact Edit semantics

Where the community is: design arguments live in the repo's issues; the docs tree is indexable via llms.txt.

The one-minute version

  • Claude Code is one engine wearing every host - terminal, IDE extensions, desktop, web, and the Agent SDK all drive the same loop.
  • The loop stops when the model stops calling tools - no turn cap by default; maxTurns and maxBudgetUsd are opt-in.
  • Context is assembled before you speak: about 7,850 startup tokens, CLAUDE.md arriving as a user message, not system prompt.
  • Its trust posture is classify-first: a second model judges each action against a maintained policy instead of asking you.
  • Distinctive mechanism: the classifier-gated loop - default starting mode on Pro, Max, and Team since v2.1.228.

Identity, and one process behind every host

Anthropic's docs name their own product an agentic harness: "the tools, context management, and execution environment that turn a language model into a capable coding agent" (How Claude Code works). First public release was the research preview of February 2025; today it ships as one native executable carrying the terminal UI, the agent loop, the tool executors, the MCP client, the hook runner, the permission engine, and the transcript writer. Because the binary is closed, those boundaries are read from documented behavior rather than file names - a limit worth holding onto for the whole page.

The same engine serves every surface. The VS Code and JetBrains extensions, the desktop app, claude.ai, Slack, and CI pipelines all drive the identical loop; the Agent SDK literally spawns the Claude Code binary as a subprocess. Around that one process live three kinds of neighbors: each shell command runs as its own child process, stdio MCP servers are long-lived children, and subagents run inside the same process but in their own context windows (sub-agents docs).

The loop: gather, act, verify, review

The docs describe the cycle as three phases - gather context, take action, verify results - blended and repeated. The Agent SDK reference gives the precise turn vocabulary, and it runs the same loop: the session opens with a SystemMessage of subtype init, the model replies with text, one or more tool_use blocks, or both, the harness executes each requested tool, results return inside a UserMessage as tool_result content, and the round repeats until a response carries no tool calls (Agent SDK loop). Read-only tools may run concurrently; state-mutating ones run sequentially. When the turn ends, a ResultMessage carries the final text, cost, usage, session id, and a stop reason.

The stop condition is principle 1 from lesson 0010, and here it is deliberately loose: no turn cap exists by default. maxTurns counts tool-use turns only, and maxBudgetUsd covers subagent spend too - both opt-in. You stay in the loop as the interrupt path: Esc cancels the running tool, and a typed correction joins between actions.

Context: the bill before your keystroke

Lesson 0030 charted the startup stack from Claude Code's own published simulation: system prompt near 4,200 tokens, auto memory index, environment info, deferred MCP tool names, skill descriptions, and your global plus project CLAUDE.md. Two structural facts matter more than the totals. Memory files are not part of the system prompt - the docs state plainly that CLAUDE.md content is delivered as a user message after it. And precedence is concatenation, not override: managed policy loads first, then user settings, then ancestor directories root-down, then the project file (memory docs). Loading is lazy where it can be: subdirectory CLAUDE.md files and path-scoped .claude/rules/*.md load when Claude reads a matching file, and MCP tool schemas stay deferred until ToolSearch fetches one - only names occupy the window before that.

The governor - principle 3 - fires when the window fills: clear older tool outputs first, then summarize. Compaction is not just shrinking. The conversation collapses into a structured summary keeping roughly 12 percent of the summarized tokens, and then the harness deterministically rebuilds a working set: it re-reads up to five recently modified files plus the rules matching them, and re-injects the body of every skill invoked this session, capped at 5,000 tokens each (context-window docs). The skill listing does not come back.

Trust: classify-first, promoted to default

Lesson 0050 placed this harness at the classify-first posture; the mechanism pages behind that placement stack three layers. Permission modes set the baseline (permission modes):

ModeWhat runs without asking
default (Manual)reads only
acceptEditsreads, edits, common filesystem commands in scope
planread-only research until you approve a plan
autoeverything, after the classifier judges each action
dontAskpre-approved tools only, rest denied silently
bypassPermissionseverything except what even bypass cannot approve

Rules override per-tool on top of any mode, evaluated deny first, then ask, then allow - first match wins, and specificity never changes the order. Two details repay attention. A bare-name deny such as Bash removes the tool from the model's context entirely, so a forbidden capability costs zero tokens and zero prompts. And an approval you grant interactively becomes law: choosing "yes, and don't ask again" writes a rule into .claude/settings.local.json, resolved through worktrees so it applies across the repository (permissions docs). Deny rules block in every mode including bypass; beneath them, an optional OS sandbox bounds what an approved action can reach - Seatbelt on macOS, bubblewrap plus a network proxy elsewhere (sandboxing docs).

Extensions: conventions and schemas, not plugins

Every growable surface from lesson 0080 is present, and nearly all of them are file conventions or config schema rather than runtime API. Skills are SKILL.md files with YAML frontmatter, loaded progressively - one-line descriptions at startup, full bodies on invoke - following the open standard this project originated and donated. Subagents are markdown files under .claude/agents/ whose frontmatter selects tools, model, permission mode, even persistent memory. Hooks are a config key carrying around thirty lifecycle events, from PreToolUse through PreCompact to Stop, with handler types spanning shell commands, HTTP posts, MCP calls, LLM-judged prompts, and tool-using subagents; a blocking hook outranks an allow rule. MCP connects external tools over four transports, with project-scoped servers declared in .mcp.json and exposed as mcp__server__tool. Plugins bundle all of the above into one installable package, and custom slash commands are skills in disguise (skills, hooks, MCP docs).

Models: co-evolved with its own family

Native targets are the Claude families, addressed through aliases - sonnet, opus, haiku, fable, and opusplan, which plans with Opus and executes with Sonnet. Third-party providers are first-class: Amazon Bedrock, Google Cloud's Agent Platform, Microsoft Foundry, and any gateway speaking the Anthropic dialect via ANTHROPIC_BASE_URL, with aliases resolving per provider (model configuration). This is co-design as a lived practice: features are keyed to model generations, not to the harness uniformly. Auto mode requires recent families and degrades to Manual on older ones, with different floors per provider. The Write-before-Read constraint relaxed only on newer models. Task-tracking tools are withheld on some models unless opted in. Each model carries its own prompt cache, so switching models pays a full uncached re-read of the stable prefix. The system-prompt text itself, and any per-model prompt differences, are unpublished - the docs describe behavior, not wording.

The distinctive mechanism

Why this one exists The classifier-gated autonomous loop. Where Codex CLI enforces first and asks second - the OS sandbox fails closed, then your approval amends its policy - Claude Code judges first: in auto mode, a second Claude model call reviews each action before execution, against a maintained security policy you can print. Run claude auto-mode defaults and the harness hands you the whole thing as JSON: seventeen named allow exceptions, sixty-seven named soft-denies, one hard deny called Data Exfiltration, and twenty environment entries defining your trusted infrastructure. The rule names are the design readable aloud - Code from External, Production Deploy, Git Destructive, Blind Apply, Merge Without Review, Self-Modification, Tmux Self Drive, Instruction Poisoning. This is not a heuristic filter bolted onto a prompt; it sits inside the loop between response parse and dispatch, caches verdicts per host and port, reviews inter-agent messages too, integrates with plan mode and the sandbox proxy, and became the default starting mode on Pro, Max, and Team plans in v2.1.228. No other member of this cast ships an LLM reviewer with a published, evolving, exportable policy as a first-class permission mode.

The honest costs sit in the same documents. Trust still lives outside the worker model's discretion - principle 5 holds - but it moved into another model, one Anthropic also controls, so the posture is available to Anthropic in a way competitors cannot copy wholesale. A misjudgment is silent by nature: the invisible error is classify-first's named failure mode. And the escape hatches are explicit: explicit ask rules always force a prompt, administrators kill it with disableAutoMode, and the docs themselves say to pair it with a sandbox for defense in depth.

Everything on this page comes from official documentation and the policy export, not from source. The classifier's internal prompt, how verdicts are computed, and any per-model system-prompt differences are not publicly documented - where the docs describe behavior, this page says what they say, and no further.

Check yourself

Retrieval practice

Answer from memory before revealing.

In auto mode, the classifier approves a request to a new network host. Minutes later the same session repeats the identical request, and no new content has entered the conversation. What happens?
Verdicts cache per host and port: an allow is reused until new content enters the conversation, and a deny reached by evaluation lasts for the turn. Changing your permission mode or rules drops every cached verdict. The first option wastes the cache, the second confuses Manual-mode behavior with auto mode, and the third invents a one-sided cache the docs do not describe.
Managed settings deny Bash(git push *). A session runs in bypassPermissions inside a container, and Claude tries git push origin main. What does the gate do?
Deny-first precedence survives every mode including bypass - that is what makes managed deny rules an organizational guarantee. Bypass skips prompts and allow rules, not denies. Had the rule been a bare-name deny, the tool would have been removed from Claude's context entirely, and no approval path exists for that form.

Practice about 15 minutes, with a terminal

Practice 1working

Run claude auto-mode defaults and read the JSON it prints. Then, without looking back at this page: name the top-level keys, count the rules in each, and find which named rule would judge each of these three actions - piping a script from the internet into a shell, a force push, and Claude typing keystrokes into its own terminal pane.

Find: the key names, the three counts, and the three rule names - then classify the policy overall using the four postures from lesson 0050.

Hint

The export separates absolute blocks from rules with a consent path - the two list types map onto hard versus soft denial, and the third list holds named exceptions to the blocks.

Show the worked solution
  1. Name the keys. allow, soft_deny, hard_deny, and environment, the last defining trusted infrastructure the other three refer to.
  2. Count them. At the version current while this page was written: 17 allow exceptions, 67 soft denies, 1 hard deny, 20 environment entries. Your counts may differ - the policy evolves release by release, which is the point of maintaining it.
  3. Match the actions. Piping remote script into shell is judged by Code from External; a force push by Git Destructive; driving its own pane by Tmux Self Drive.
  4. Classify the posture. Classify-first, with ask rules and the OS sandbox layered beneath - and note that printing the policy is itself unusual: most classifiers expose no rule text at all.

Sanity check. Exact counts will drift with versions, but the four-key shape and the presence of named, sentence-length rules should not - if your export has unnamed one-line rules, you are likely looking at different tooling altogether.

Your teacher. If the trust section did not land, ask it to walk one concrete command - a production deploy attempt, say - through deny rules, hooks, the classifier, and the sandbox in order, naming which layer could stop it first. If the compaction chart felt abstract, ask it to redo the arithmetic with your own session's /context output.
