Module 04 · Extending · Lesson 90

Code mode turns a tool fan-out into one generated program

working 10 min Read from each harness's public source at the commits pinned in this page's links. · example: Codex's exec tool name

The one-minute version

  • Every tool call normally costs a full model round trip: the request goes out, the result comes back, the model thinks again before the next call.
  • Code mode collapses that fan-out: the model writes one TypeScript program whose statements call tools, and the harness executes the whole thing locally.
  • Three members of our cast built it independently. Codex CLI made it the default path for its newest models, Goose ships it opt-in and off, opencode keeps it behind an experimental flag.
  • The savings are real - fewer round trips, compact results, stable caching - but a failed program is one opaque failure, and debugging shifts from reading a transcript to reading generated code.

The round-trip tax

Watch a coding agent work through its transcript and count the turns. A task like "run the test suite in each of these twelve directories and retry the failures once" becomes a procession: call bash for directory one, wait, read the result, decide, call again for directory two. Each hop is one sampling request - the full history travels to the model and back just so something can decide whether to run the next command. The harness pays latency on every hop, the provider bills tokens for re-reading the history, and any prompt cache in front of the model must survive the growing tail.

A shell tool already offers an escape hatch - nothing stops the model from writing one big script that loops over all twelve directories. Code mode formalizes that escape hatch with structure: typed bindings back into the harness's real tools, not raw text scraping of shell output.

Three implementations of one idea

The cast contains three first-hand implementations, and they disagree about execution venue and default status. Codex CLI defines a freeform custom tool literally named exec (with a companion wait), whose argument is TypeScript source (code-mode-protocol/src/lib.rs, the constants naming both tools). The source runs in a dedicated out-of-process host crate family (code-mode-host), and the descriptions of ordinary tools get rewritten to show how each would be reached from inside a program (tools/src/code_mode.rs). Most striking is who gets it: six model entries in the bundled catalog ship "tool_mode": "code_mode_only", including the default gpt-5.6-sol, which hides every direct tool (models-manager/models.json). For those models there is no choice to make - generating a program is the only way to act.

Goose reaches the same design from the extensions side: four tools named execute_typescript, execute_bash, list_functions and get_function_details let a script enumerate the available extension calls and batch them, each callback dispatching into the same dispatch_tool_call path a normal tool call would take (code_execution.rs, handlers near lines 216 and 251, callback dispatch at line 383). It ships off by default. opencode's version lives in a separate packages/codemode interpreter package with its own standard library, mounted as a single execute tool only when the experimental flag is set (registry.ts, flag gate at line 118).

How a generated program reaches real tools

The execution shape is common to all three, drawn here Goose-style because its dispatch path is the most visible: the script never touches files or networks directly. Each tool call inside the program becomes a callback into the dispatcher the interactive loop already uses, so permissions, telemetry, and result formatting stay identical to a plain tool call.

What it saves and what it costs

The savings column is why OpenAI flagged its newest models this way. Round trips collapse, as the chart above showed. Intermediate values stay compact: a loop over forty files returns the three failures that matter, not forty full results re-read by the model. And the wire stays cache-friendly - one stable exec call replaces a long tail of growing history.

The cost column is equally structural. A program that throws on line fifty has really done the work of lines one through forty-nine - those tool calls executed - but what comes back is one failed result describing a program, not a clean checkpoint the model can continue from. Wrong-tool-call errors used to be small and local; wrong-program errors are large and opaque. Debugging moves from reading a transcript of decisions to reading generated code, and the host becomes part of the security surface, since it runs model-written TypeScript and must sandbox it exactly as seriously as a shell command.

The reframing Tool schemas have been the interface between model and harness. Code mode demotes them to a compilation target: the model no longer addresses tools one declaration at a time, it addresses an API surface, and lesson 0010's principle that the loop is a product of the model's limits explains why independent teams converged here at the moment models became good enough to write the glue.

Is it where the field is heading? The adoption spectrum says "probably, slowly": one cast member made it the only path for its newest models, one ships it off by default, one keeps it behind a flag, and the rest have not started. The mechanism pages ahead keep meeting the same pressure - lesson 160 shows a harness compressing the loop from the other side - but no other member currently lets the model author the orchestration itself.

Check yourself

Retrieval practice

Answer from memory before revealing.

You pick the newest default model in Codex CLI and ask it to refactor six files. What tool surface does it actually receive?
Six bundled catalog entries ship "tool_mode": "code_mode_only", including the default, which hides direct tools entirely - writing a program is the only way to act. This is not a settings gate you flip, MCP contributions do not change it, and exec replaces rather than joins the direct surface.
A generated program reads ten files successfully, then its final write call fails. What does the model see?
The program is one tool call from the loop's perspective, so its outcome arrives as one result - but the bindings genuinely dispatched, so the ten reads stand and nothing rewinds. Reruns are the model's decision, not an automatic prompt.

Practice about 10 minutes, with paper

Practice 1working

A task fans out over twelve directories: run each directory's tests, retry a failure once if it occurs, and suppose exactly two directories fail on the first attempt. Count sampling requests that carry tool traffic - the final text-only summary cancels out either way.

Find: the count for direct tool calling (one call per check, one per retry) and for code mode (one exec call), and the ratio between them.

Hint

Direct: twelve checks plus one extra call per failing directory. Code mode: everything - checks, branches, retries - happens between statements of one program.

Show the worked solution
  1. Count the direct path. 12 checks + 2 retries = 14 sampling requests carrying tool results.
  2. Count the code-mode path. All twelve checks, the two branch decisions, and both retries execute inside the host: 1 request.
  3. Take the ratio. 14 ÷ 1 = 14× fewer tool-carrying round trips.

Sanity check. With zero failures the counts become 12 and 1 - the saving tracks fan-out width, not luck, because branching and retrying moved in-process.

Your teacher. Ask it to take your last multi-step agent session and split each action into "must be decided by the model" versus "could be a line of generated code". Then ask which single error in that session would have been harder to debug as one failed program instead of fifteen visible steps.
