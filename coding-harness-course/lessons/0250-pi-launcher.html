The one-minute version

  • Pi ships ad-hoc signed, which runs fine but presents no stable identity: its cdhash changes on every build.
  • The launcher is a fork-and-stay parent: it execs Pi as a child and remains in the tree forever, wearing the one Developer ID signature.
  • It touches nothing else: terminal transparency by never touching the terminal and never delivering a signal twice.
  • A gated pipeline pins upstream by checksum, signs inside-out, notarizes, re-downloads its own artifact - and quarantines an upstream release that fails any gate.

The problem it solves is lesson 0060's in miniature: official Pi binaries are ad-hoc signed, so they satisfy the kernel and fool nobody at Gatekeeper, and their cdhash - the fingerprint of one exact build - differs after every rebuild. A credential broker that approves access by walking process ancestry finds nothing durable to match. Wrap Pi in a Developer-ID-signed app and every Pi process sits under a parent whose designated requirement names identifier, anchor apple generic, and Team ID - identical across releases.

Process architecture: fork and stay alive

A classic CLI wrapper calls execve and becomes its target. That single syscall would erase the whole point here: once replaced, the process tree shows Pi's unsigned Mach-O again. So the launcher forks and stays alive as Pi's direct parent permanently (pi-launcher.c:175 fork, :199 execve).

What the launcher may execute is a set of size one, enforced by code shape rather than convention: it resolves its own path with proc_pidpath, canonicalizes it with realpath - dissolving symlink games - strips the last component, and joins the compile-time constant ../Resources/pi/pi. There is exactly one execve call site, no PATH search, no argument parsing, no environment override; a missing target exits 127, an unrunnable one 126. Arguments pass byte-for-byte into the child's argv, untouched.

Terminal transparency

An extra process in the foreground job can wreck job control, so the design rule is never touch the terminal, never deliver a signal twice.

One race deserves notice: between fork and recording the child's PID, a forwarded signal could be lost, so those four signals are blocked around the fork and unblocked only after the PID is stored. And because ignored dispositions survive execve (POSIX exec), the child resets every catchable signal to default before loading Pi - otherwise the parent's SIG_IGN would leak into the agent.

Trust posture

The security boundary is the payload path, and it holds because there is nothing else to reach. Negative tests attack each escape hatch and fail to break in: a poisoned PATH changes nothing, environment variables named like targets are ignored, flag-shaped arguments pass through as Pi arguments, and a bare copy of the binary outside a bundle exits 127 rather than running anything. Entitlements are a posture too: the launcher ships with zero, asserted by its own verification gate, while bundled Pi carries exactly one - com.apple.security.cs.allow-jit (Apple's reference) - because it is a Bun-compiled JavaScriptCore runtime and the hardened runtime blocks JIT memory without it.

What this is not: not a sandbox - Pi still runs with your full user permissions; not authorization - a stable designated requirement gives a policy tool something to match, but whether that tool grants anything is unproven until tested; and not runtime re-verification - nothing re-checks a signature at each exec, so provenance is enforced by the release pipeline, not per launch. The guarantee also bottoms out in trusting upstream's own release channel.

The skeleton's other rows are absences by design, and the absence is the architecture: no loop lives here (the loop belongs to Pi - see lesson 024's deep dive), no context is assembled, there is no extension surface beyond replacing the bundle, and model behavior passes through untouched. Every row a harness page fills in, this page answers "delegated, unchanged".

The distinctive mechanism: a pipeline that refuses to ship

The strongest material is the machine that produces the artifact you install. Upstream Pi is pinned by version, URL, and SHA-256; every fetch verifies against both the pinned hash and upstream's published SHA256SUMS (fetch-pi.sh:57-71); signing runs inside-out through nested code with hardened runtime and secure timestamps; and the release workflow verifies and launches the artifact repeatedly - including a fresh re-download of the published zip checked byte-for-byte - before the Homebrew cask is allowed to move.

This fired in anger once: upstream Pi v0.84.2 was quarantined after a contract script hard-coded the previous launcher version and failed. The fix derived the version from published git tags instead, and the incident now lives on as a regression test citing the failing run - a gate that failed correctly, blast radius contained, root cause converted into a test.

How it proves all this

Claims about invisible inter-process behavior cannot be unit-tested, so four suites drive real processes instead. Functional tests swap a probe binary into the identical bundle layout - the launcher cannot tell the difference, which is the point - and assert byte-exact argv passing, exit codes across the full range, five different signal deaths reproduced, and the negative boundary attacks above. PTY tests build a fake interactive shell on a real pseudo-terminal with setsid and TIOCSCTTY, then prove ISATTY on all stdio, one SIGWINCH per resize, one SIGINT per Ctrl-C, and suspend-and-resume via keyboard and via Pi's own group-stop style. Automation tests exercise the updater and quarantine scripts against a fake GitHub API, including the reproduced v0.84.2 incident. Finally a smoke test runs the real bundled Pi through the real launcher, because signature structure is not launchability.

Check yourself

Retrieval practice

Answer from memory before revealing.

You press Ctrl-C while the agent runs under pi-launcher. Why does the launcher not forward SIGINT to Pi?
Group delivery is the mechanism: forwarding would double-deliver, so the launcher sets SIGINT to ignored and lets the line discipline do the work once. Nothing forbids forwarding terminal signals, Pi's handler choice does not change the launcher's arithmetic, and no conversion exists anywhere in the source.
An upstream Pi release passes discovery but fails one full-suite gate on macOS. What does the sync workflow do?
Quarantine is durable and human-owned: while the labelled issue stays open the tag is never attempted, though newer releases are judged fresh. Daily retries against a red gate, shipping untested, and silent skips are precisely the behaviors the design refuses.

Practice about 20 minutes, reading only

Practice 1working

Open scripts/verify-app.sh at the pinned commit and list every check the verification gate performs - structure, architectures, signing identity, hardened runtime, timestamps, entitlement counts, designated requirements, stapled tickets, spctl acceptance.

Find: for each check, the one-line claim it proves, then name a property a buyer might assume that no check in the file covers.

Hint

The checks prove facts about the artifact as distributed. Ask which claims concern the artifact's behavior after distribution - say, at every future launch - and look for their absence.

Show the worked solution
  1. Tabulate the checks. Each maps to one claim: arm64-only Mach-Os, Developer ID authority with the right Team ID, hardened-runtime flags, secure timestamps, exactly one entitlement on Pi and none on the launcher, correct designated requirements, valid stapled ticket, Gatekeeper acceptance.
  2. Hunt the uncovered assumption. Nothing re-verifies the signature at each launch - provenance is established at build and install time only.
  3. Price it. A user who later replaces or tampers with the payload inside the bundle is outside every gate in this file.

Sanity check. Your list should have roughly ten distinct claims and your uncovered column should include per-launch re-verification - the same limit the page's warning callout states.

Your teacher. If the fork-and-stay rationale has not landed, ask for the counterfactual: rewrite the launcher as a ten-line exec shim and name everything that breaks. For the pipeline, ask it to rank the gates by cost of removal - which one would you drop last?
