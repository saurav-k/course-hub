Cursor: the harness that trains its own models

working 12 min Closed source - covered entirely from Anysphere's official documentation, changelog, and engineering posts, all fetched August 2026. · cursor.com/docs

Explore it yourself

No repository exists to open. Cursor is a closed product by Anysphere: proprietary license, no public source tree, so there is no pinned commit SHA and no file list. The desktop editor is built on the VS Code codebase (the docs say so directly) and the terminal CLI ships as a standalone binary via an install script - neither is inspectable the way this course's open members are.

Read these five official pages instead, in this order:

  1. Agent overview - components, tools, checkpoints, queueing
  2. Rules - rule types, frontmatter, precedence
  3. Run Modes - Auto-review classifier, sandbox platforms, network defaults
  4. Hooks reference - the event catalog that doubles as the loop's skeleton
  5. Tab RL engineering post - the training loop behind the distinctive mechanism

Where the community is: the changelog ships several entries a month, the engineering blog carries the mechanism posts cited below, and users gather on forum.cursor.com.

The one-minute version

  • Cursor is one harness wearing four surfaces - editor, Agents Window, web/mobile, CLI - all driving the same loop, rules, skills, MCP servers, and hooks.
  • Its trust posture is classify-first: an allowlist runs instantly, sandbox-eligible commands run boxed in, and everything else is judged by a small model before you are bothered.
  • Its sandbox profiles are generated at runtime from your workspace settings and ignore files, not shipped as static policy.
  • The distinctive mechanism: Cursor trains its own models on its own harness telemetry, continuously - the loop closes through weights, which no other cast member can copy.

The loop

The loop's code is closed, but its instrumentation is public and precise: the hooks reference names every stage where user code can attach, and those event names are the authoritative turn skeleton. A prompt passes beforeSubmitPrompt; context is assembled from the eight categories below; one request carries per-model parameters (thinking, effort, context, plus a fast switch); the reply parses into text, thinking blocks, and tool calls. Each call then meets the gate - beforeShellExecution, beforeMCPExecution, or beforeReadFile hooks, plus the active Run Mode - which may allow, ask, deny, or rewrite the input before execution, possibly inside the sandbox. Results append through afterShellExecution, afterMCPExecution, and afterFileEdit, and the cycle repeats until the reply carries no tool calls. Two documented extensions make the stop conditional: a stop hook receives a loop_count and may return a followup_message that auto-continues the agent up to a configurable limit defaulting to five, and steering messages injected mid-task wait for the next tool-call boundary rather than interrupting an action.

Context assembly

Every chat shares one window, and Cursor's own settings tray divides it into eight named categories: system prompt, tools, rules, skills, MCP, subagents, summarized conversation, and conversation. Rules land at the start; they follow a documented precedence of Team, then Project, then User, with earlier sources winning conflicts. Project rules are .mdc files under .cursor/rules whose frontmatter decides inclusion: alwaysApply attaches unconditionally, globs attach when a matching file appears in context, and a description alone makes the model pull the rule in when relevant. Plain AGENTS.md works at the root and nested directories, deeper files winning - and the CLI additionally reads CLAUDE.md. Skills contribute their description lines up front and load bodies progressively, scoped by path globs.

Near the limit, older turns compress into a summary automatically or on demand via /summarize; per-model parameters such as claude-opus-5[context=300k] raise ceilings. This is principle 3 from lesson 0010 with the dial unpublished - Cursor shows a fullness ring, never a number.

Trust posture

Since version 3.6 the recommended default is Auto-review, the classify-first posture: allowlisted calls run immediately; commands that fit the sandbox's file and network limits run inside it; everything else goes to a classifier running Claude 4.5 Haiku or GPT-5.4 Mini, which may allow the call, tell the agent to try another approach, or escalate to you. Two config files steer the gate without asking each time: permissions.json holds allowlist patterns for MCP tools and terminal command prefixes plus free-text autoRun guidance, and team-admin dashboard settings override both. Cursor states plainly that none of this is a security boundary - the boundary work lives one layer down.

The sandbox is generated at runtime, not shipped: on macOS a Seatbelt profile compiled from workspace settings, admin settings, and .cursorignore; on Linux Landlock plus seccomp mapping the workspace into an overlay where ignored files become unreadable stubs; on Windows the Linux sandbox inside WSL2. Network is deny-by-default with a package-manager allowlist, RFC 1918 and cloud-metadata addresses are always blocked against SSRF, and protected paths like .git/config and .git/hooks are never writable even by configuration. Escape hatches exist and are honest about it: an insecure_none sandbox type, network Allow All, and a Run Everything mode.

Model behavior

One gateway fronts Anthropic, OpenAI, Google, xAI-partner, Moonshot, and Z.ai models alongside first-party ones, and the abstraction is deliberately uniform: every model takes the same parameter triple plus the fast switch, and Cursor states it tunes instructions and tools specifically for each frontier model rather than exposing provider differences to users. The differences still leak where money and behavior meet: cache-write billing exists for some families and not others, reasoning-effort variants appear as separate model ids, and long-context surcharges differ per row of the pricing table. The affinity, though, is structural. Composer, the first-party model, is tuned for tool use, file edits, and terminal operations inside Cursor; its Shell tool descriptions were rewritten by hand to explain sandbox constraints until agents recovered gracefully, measured on an internal benchmark; and on legacy plans subagents run on Composer regardless of any model configuration. A harness that owns its models can bind them to itself - the rest of the cast can only describe their tools better.

The distinctive mechanism

Every harness routes prompts to models. Cursor is the only member of the cast that closes the loop in both directions between the harness and the weights. Downward: Composer's reinforcement learning used targeted textual feedback that re-inserts the harness's real tool list at the offending step of a failed rollout - the model studies this harness's tool surface as training signal. Upward: Tab runs on hundreds of millions of human accept-or-reject decisions a day, feeding online RL whose reward is shaped around a 25 percent accept-probability threshold, with new checkpoints rolled out many times a day - a release cadence quarterly-trained competitors structurally cannot match.

An honest caveat belongs here, because each ingredient exists elsewhere. Kernel sandboxes are Codex CLI's home turf, LLM permission classifiers are Claude Code's, next-edit prediction descends from Copilot's lineage, with Supermaven acquired along the way. The novel thing is ownership: one vendor operating the harness, the telemetry, the training stack, and the weights as a single system on a daily cadence. That integration - not any single part - is what a competitor cannot fork.

Everything on this page rests on official documentation, not source. Function names do not exist publicly; the loop is reconstructed from the hook-event catalog; the byte-level ordering of the context window and the failed-edit retry path are not publicly documented and are marked as such wherever they matter. Treat undocumented corners as unknown, not as absent.

Practice about 15 minutes, with Cursor installed

Practice 1working

Recover the loop's skeleton behaviorally, the way this page had to. In one session: submit a task that needs one shell command and watch which approvals fire; add a beforeShellExecution hook that logs its input and exit; run a long task until the summary notice appears; then press rewind and confirm the checkpoint restores files that git status shows as untracked.

Find: for each of the four observations, the corresponding stage on the sequence diagram above, and one thing the observation told you that the docs did not.

Hint

The hook log gives you timestamps: gaps between entries are model time, bursts are tool time. For the checkpoint check, pick a fresh directory without git init - if restore still works, checkpoints live outside git, as documented.

Show the worked solution
  1. Approval observation maps to the gate stage. Which calls prompted and which ran silently tells you your effective allowlist, whether or not you ever opened permissions.json.
  2. The hook log maps to beforeShellExecution. Its payload confirms the documented input schema and - the doc-free bonus - shows the sandbox flag value attached to the call.
  3. The summary notice maps to summarized conversation. Comparing the ring before and after estimates the reclaim without any published threshold number.
  4. Rewind in a non-git directory maps to checkpoints stored separately from git. Restore working there proves the storage claim behaviorally.

Sanity check. Four observations should land on four different diagram stages; two landing on the same stage usually means one observation was really measuring the other.
