Community: GitHub issues and discussions on the repository, plus the author's "What I learned building a minimal coding agent". A signed macOS launcher (pi-launcher) is a separate project with its own deep dive.

The one-minute version

  • The engine ships as three libraries: pi-ai for providers, pi-agent-core for the loop, pi-coding-agent as their consumer.
  • The loop accepts any StreamFn, so it drives real providers or your test double identically.
  • Absence is architecture: no MCP, no subagents, no permission popups - each becomes an extension exercise.
  • The cost: shell executes unasked by default; containerization is your job.

One process does everything: main() dispatches to interactive TUI, print mode (-p), or RPC mode (JSONL over stdio), and optional server/client packages add socket transport. The publish boundaries are the real module lines - five npm packages, imported strictly downward: coding-agent → agent-core → ai.

The loop

The loop lives in one file of the library package and knows nothing about files, terminals, or permissions. It works on internal message types, converts once per request at the model boundary, and takes its behavior entirely from a config object.

Above the library sits the product's AgentSession, which subscribes to every loop event, persists each finished message, drives auto-compaction and retries, and only then emits agent_settled - a deliberately distinct event meaning no retry, compaction, or follow-up work remains. Extensions that want "the agent is truly done" listen for that, not for agent_end.

Context assembly

Pi's stated philosophy is minimal, fully visible context: the default system prompt is about one thousand tokens including tool definitions, and nothing enters the window behind your back. The assembly order, rebuilt fresh each turn by buildSystemPrompt:

Cross-model handoff is handled at the boundary by transformMessages: switch models mid-session and unsigned thinking blocks degrade to plain text, orphaned tool calls get synthetic error results, and OpenAI-style 450-character tool-call IDs are renormalized to Anthropic's charset so old history stays replayable.

Trust posture

The security documentation says it flatly: Pi runs with the permissions of the account that starts it and ships no sandbox. Every tool, including arbitrary shell, executes without prompting - the author calls this YOLO by default, arguing partial sandboxes are security theater once the model can write and run code. What exists instead:

  • Project trust - an input-loading guard, not a sandbox: before loading anything under a project's .pi/ directory, Pi asks; decisions persist in ~/.pi/agent/trust.json.
  • Read-only mode - --tools read,grep,find,ls shrinks the toolset; -ne disables extensions.
  • Containerize the whole thing - three documented patterns, including the Gondolin extension that routes every tool call into a local Linux micro-VM with the project mounted at /workspace.
  • Build your own gate - the extension event tool_call can return {block: true}, which is exactly how the docs suggest confirming risky commands.
Running Pi as shipped means shell commands execute with your full user permissions, unasked. That is a designed posture, not a gap - but it moves the entire safety burden onto the environment you run it in. The failure mode is silent by construction: nothing will ever stop to ask.

Extension surface

Extensions are TypeScript modules auto-discovered from .pi/extensions/ (trust-gated) and ~/.pi/agent/extensions/, hot-reloaded with /reload. The loader runs them through jiti with virtual modules, so an extension imports @earendil-works/pi-ai and gets the same instance the binary uses - even inside the compiled executable. The runtime API exposes roughly thirty lifecycle events (before_agent_start, turn_start, tool_call, before_provider_request...) plus registration points for tools, commands, shortcuts, flags, providers, and custom UI components.

Skills are SKILL.md directories whose index lands in the system prompt while bodies load on demand. Slash commands come from Markdown templates in .pi/prompts or registerCommand. Packages bundle any of the above for npm/git distribution via pi install. Two absences are deliberate: the usage docs state Pi "intentionally does not include built-in MCP, sub-agents, permission popups, plan mode, to-dos, or background bash" - the sanctioned alternative to MCP is ordinary CLI tools with READMEs the model reads progressively.

Model behavior

Dispatch is two-stage: Models.streamSimple resolves auth (API key, env var, or OAuth) and routes to a wire-API adapter. Ten adapters ship - Anthropic Messages, three OpenAI dialects, two Google dialects, Bedrock, Mistral, and Pi's own gateway protocol - covering around forty known providers from a generated catalog.

Per-family differences live inside the adapters behind one neutral vocabulary, a reasoning level mapped through each model's thinkingLevelMap: adaptive-thinking Claude models take an effort level, older ones a token budget carved out of max_tokens; OpenAI-compatible models get reasoning_effort clamped per provider; Google models get thinkingConfig. Prompt caching is marked where Anthropic rewards it, on tools and the last user message. Nothing in the code favors one family - the deepest single-family code is Claude-specific simply because Anthropic exposes the most surface to integrate.

The distinctive mechanism

Every other harness in this cast bakes its engine into its product, or exposes plugins that run inside someone else's loop. Pi publishes the engine itself as two libraries and ships the product as their consumer:

Evidence that this is structural, not cosmetic: the RPC mode, the server/client packages, and the author's own Slack integration all consume AgentSession programmatically rather than shelling out to the CLI; the example extensions include one registering a complete custom Anthropic-compatible provider through the public API; and an experimental packages/agent/src/harness/ skeleton shows durable-session machinery being generalized back down into the library layer. Even the extension loader enforces the architecture - virtual modules exist precisely so third-party code shares one set of package instances with the host.

The companion trait is absence as architecture: no MCP, no subagents, no permission popups, no plan mode. Each missing feature is an invitation to build it on the event hooks - which is why Pi's capability list lives in its extension ecosystem rather than in its changelog. The cost is symmetrical: the minimal thousand-token prompt trusts the model to do more with less scaffolding, and the empty trust layer hands you a loaded tool with no safety on it. Whether that reads as freedom or as unpaid work is exactly the trade-off the course's next pages ask you to price.

Retrieval practice

Answer from memory before revealing.

What makes Pi's loop a library rather than a hardcoded pipeline?
The AgentLoopConfig injection points are the mechanism - the loop never names a provider, a file system, or a UI. MCP is deliberately absent, nothing rewrites bytecode, and RPC is one consumer of the session layer, not the owner of the loop.
A response hits the output-token limit mid-way through streaming a batch of tool-call arguments. What does the loop do?
failToolCallsFromTruncatedMessage fails them all: streamed arguments may be silently cut, and executing half a JSON payload is worse than executing none. Partial-batch execution would run unverifiable inputs, and neither retry nor deferral exists at that point in the loop.

Practice about 20 minutes, with a terminal

Practice 1working

In a scratch directory, run npm i @earendil-works/pi-agent-core @earendil-works/pi-ai and write a twenty-line script that calls agentLoop with a fake StreamFn - an async function that yields one text delta reading "hello from a test double" and a done event, never touching the network.

Find: proof in your terminal that the loop emitted agent_start, message_update, and agent_end driven entirely by your fake - the engine ran with zero providers configured.

Hint

Your fake must satisfy the StreamFn contract from packages/ai/src/types.ts: yield protocol events, never throw. Start from start, emit one text_delta, then done with an empty usage record.

Show the worked solution
  1. Write the fake. An async generator yielding {type: "start"}, one {type: "text_delta", delta: "..."}, then {type: "done", ...} - six lines.
  2. Wire the loop. Call agentLoop([yourPrompt], {systemPrompt: "", messages: []}, {...config, tools: []}, undefined, fakeStreamFn) and iterate the returned EventStream, logging each event type.
  3. Observe. The console shows agent_start, turn_start, message_start/update/end, turn_end, agent_end - the full cycle with no API key anywhere.

Sanity check. If events flowed without a provider, you proved the decoupling claim; if you needed a key, you accidentally called the product CLI instead of the library.

Your teacher. If the three-library split has not landed, ask for the thought experiment: what would porting this loop to a different provider require, line-for-line? If the trust posture unsettled you, ask it to sketch the Gondolin containerization pattern as a sequence of boundaries.
