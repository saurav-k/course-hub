Identity

Cline Bot Inc. publishes the extension under publisher id saoudrizwan: Apache-2.0, TypeScript throughout, first released in July 2024 as "Claude Dev" and renamed that September, today around 67,000 stars and 320-plus contributors. Its own words: "Autonomous coding agent right in your IDE… with your permission every step of the way." One structural fact before you browse: the famous single-package extension is mid-way through a rewrite into a monorepo whose engine ships as SDK packages - @cline/agents holds the stateless loop, @cline/core session orchestration and persistence, @cline/llms the providers, @cline/shared the contracts and prompt builders (sdk/ARCHITECTURE.md). The VS Code extension hosts them in-process, and its React webview speaks protobuf-over-gRPC to the extension host rather than ordinary VS Code messaging.

The loop

The loop is one function: AgentRuntime.execute(). Each iteration calls generateAssistantMessageWithOverflowRecovery(), which opens the provider stream and assembles text, reasoning, and tool-call deltas into one assistant message. Stop condition one: a reply carrying zero tool calls ends the run with finishRun("completed") - there is no completion tool any more, plain text is completion. Otherwise executeToolCalls() walks each call through prepareToolExecution(): hooks first, then tool policy, and anything not pre-approved parks the entire loop inside requestToolApproval(), a Promise the UI resolves with a click or a denial reason that becomes the tool error text. Results append as tool messages and the wheel turns. Two extras: a terminal tool flagged completesRun (submit_and_exit, yolo preset) ends the run by succeeding, and if the provider rejects the request for sheer size, overflow recovery forces compaction once mid-run and retries.

Context assembly

buildClineSystemPrompt() renders a deliberately short template: platform, date, working directory, a rules slot, and - when planning - the plan-mode behavioral contract. Tool semantics moved out of the prompt into JSON-schema tool descriptions, so the modern system prompt is a fraction of classic Cline's XML-era monster. Rules load through file watchers rather than per-task injection: workspace AGENTS.md, .cline/rules, the deprecated .clinerules, global ~/.agents/AGENTS.md and ~/.cline/rules - and the extension still tracks .cursorrules and .windsurfrules for migrants (paths.ts). @file mentions inline before send; there is no embedding index, codebase search is live ripgrep through search_codebase. History is append-only and the canonical transcript is never destroyed: compaction is a projection computed at prepare-turn time, triggered at 90 percent of the model's max input tokens (default budget 128,000), summarizing older turns with the provider itself while keeping the recent tail verbatim.

Trust posture

The approval seam is one callback, requestToolApproval. The extension force-registers an ask-first policy on every user-facing tool, then evaluates your live auto-approve toggles at ask time - flipping the approval bar mid-task takes effect on the very next call. Categories map one-to-one onto toggles: reads, edits, safe commands, browser, and one global MCP switch. When a call does need asking, the coordinator opens a read-only diff preview and parks the loop until you decide; a denial reason travels back as the tool error text. Under that human layer, plan mode arms a mechanical one: a beforeTool hook rejects file-mutating shell constructs - rm, mv, sed -i, redirections, history-rewriting git - before policies or approval ever see them, because hooks fire ahead of the policy check. The yolo preset approves everything and adds submit_and_exit for unattended runs. And the honest limit: there is no OS-level sandbox around shell execution at all - isolation effort concentrates on plugin subprocesses, so Cline's posture is ask-first, not sandbox-first.

Model behavior

Providers sit behind a gateway registry built on the Vercel AI SDK, with the model catalog auto-generated from models.dev - roughly 181 provider ids. The session factory resolves a provider and a model id separately per mode, so plan and act can run different vendors entirely, and the default provider id is cline, the company's own gateway. Per-family behavior is explicit code, not folklore: a routing rule literally named codex-and-gpt-use-apply-patch enables apply_patch and disables editor for OpenAI-family models - swapping the edit dialect to match what those models were trained to emit. Chat-completions wire format cannot carry images inside tool results, so middleware splits media parts into a synthetic following user message instead of letting the converter stringify them into opaque base64 noise. Catalog capability flags carry reasoning-effort styles and prompt-cache support into request options per model.

The distinctive mechanism

Most harnesses bolt plan mode on as a prompt variant inside one conversation. Cline makes the two modes different programs. Flipping the toggle calls togglePlanActMode(), which aborts the running session - killing any in-flight turn - rebuilds the entire runtime under an exclusive lock, and starts a replacement session seeded with the prior transcript. The rebuild swaps more than tools: each mode carries its own provider, model id, and reasoning effort, so planning can literally run a different brain than acting.

How does the replacement session remember? Through prompt engineering made structural: every outbound user message ships wrapped as <user_input mode="plan|act">, switches add a <mode_notice> marker, and the system prompt teaches the model that the newest message's mode governs regardless of earlier allowances. In VS Code, plan sessions deliberately omit the switch_to_act_mode tool so the human stays the gate between thinking and doing, and automatic continuation fires only after a genuine plan_completion_result exists. This is lesson 0010's design force - control flow belongs to the harness, not to the model's judgment - pushed further than anywhere else in the cast: Cline would rather rebuild its whole runtime than trust a prompt suffix.

The reframing Modes are processes, not prompts. Where the wrapper believer sees a settings toggle, the engineer sees teardown-and-rebuild with continuity carried as tagged data - which is why a plan-mode conversation here structurally cannot contain an edit tool, instead of merely being asked not to use one.

Honest runners-up: checkpoints stored as private git refs - refs/cline/checkpoints/<sessionId>/<runCount> inside your own repository, created once per user turn by a beforeModel hook - keep snapshots invisible to git stash list yet garbage-collection safe; and per-mode provider pairing means "different model for planning" is a factory decision, not a hack.

Check yourself

Retrieval practice

Answer from memory before revealing.

You flip the toggle from plan to act mid-conversation. What does Cline actually do?
togglePlanActMode tears down the session and performs a full rebuild that reseeds the new session with the prior transcript. The first option is how most other harnesses implement plan mode - the thing Cline refuses to do. The third contradicts the whole point, which is continuity. The fourth confuses the approval bar, which is evaluated live per call, with the mode system.
Where do Cline's checkpoint snapshots actually live?
Checkpoints are commits under refs/cline/checkpoints/<sessionId>/<runCount>, real refs so git's garbage collector leaves them alone but private so they never clutter your branches or stash. The shadow clone was the older design this one replaced. Nothing is zipped, and staying out of stash list is exactly the design goal.

Practice 1working

Clone and pin: git clone https://github.com/cline/cline, then git checkout 491b30b8. Trace one mode switch end to end without running anything: find where the toggle enters the rebuild, what the act preset grants that plan denies, and where the continuity tag gets stamped onto your message.

Find: the function that serializes rebuilds, the two preset flags that differ between plan and act, and the exact function that wraps your text in the mode tag.

Hint

Start at togglePlanActMode in apps/vscode/src/sdk/sdk-mode-coordinator.ts and follow the rebuild scheduler; then compare presets.ts flag tables; the tag lives in sdk/packages/shared/src/prompt/format.ts.

Show the worked solution
  1. The serialization point. rebuildSessionForMode wraps the whole teardown-replace-continuation sequence in the rebuild scheduler's runExclusive, so a second toggle during a rebuild queues instead of interleaving.
  2. The preset delta. Plan sets enableEditor: false while act leaves it true - everything else matches, which is why the command-guard hook, not the toolset alone, carries plan-mode safety.
  3. The stamp. format.ts's wrapper emits <user_input mode="..."> around the raw input, applied in prepareTurnInput before the run starts.

Sanity check. If your trace shows the guard hook firing before the approval callback, you read the right layers - enforcement, policy, and consent are three different files here, and confusing them is the classic misread of this codebase.

Your teacher. If the rebuild story has not landed, ask it to walk what specifically dies and what specifically survives a plan-to-act toggle, listing each survivor by name. If the approval seam felt abstract, ask it to contrast Cline's parked-Promise gate with a sandbox-first harness, counting what the user sees in each when a shell command fires.
