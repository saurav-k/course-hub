The one-minute version

  • One Bun process serves every client - TUI, editor extensions, desktop, ACP hosts - through one generated HTTP and SSE SDK.
  • The loop is an explicit while (true) in SessionPrompt.runLoop: iterate while the reply ends in tool calls, compact instead of overflowing, and cap steps only where an agent declares a budget.
  • Behavior follows the model: the persona prompt, reasoning-effort menu, sampling constants, cache breakpoints, even which edit tools exist, are all derived per model family at request time.
  • The distinctive move is the model-behavior compiler: a hosted models.dev catalog treated as declarative truth, plus a doom-loop breaker that converts a third identical call into a human question.

The process shape surprises people who remember the old Go TUI: everything runs in one Bun process. A yargs CLI (src/index.ts) starts the UI, the UI boots the real HTTP server inside a Bun Worker (cli/cmd/tui.ts, cli/tui/worker.ts), and the TUI frontend talks to that server like any other client - over TCP, or through an in-memory bridge that shuttles fetch calls into the server under the fake origin http://opencode.internal. The router is an Effect HttpApi (server/server.ts) with typed route groups, and every consumer - TUI, VS Code extension, desktop app, opencode run, ACP hosts such as Zed - uses the same generated SDK over HTTP plus SSE events.

The loop

runLoop in session/prompt.ts is a plain while (true), and reading it top to bottom is reading the whole turn cycle. Each iteration reloads projected history, checks the stop condition, drains queued subtasks, guards the context budget, resolves the agent's toolset, rebuilds the system prompt, streams one model step, and consumes normalized events. Three details carry real engineering weight:

  • The stop condition is precise. The loop breaks only when the last assistant message finished with something other than tool-calls, has no pending non-provider-executed tool parts, and belongs to the latest user message - interrupted orphans cannot keep it alive.
  • Overflow becomes compaction, not a crash. When the finished message exceeds usable context, the loop enqueues auto-compaction instead of calling the model.
  • A doom-loop breaker watches dispatch. After three identical consecutive tool calls, SessionProcessor forces a doom_loop permission prompt - a human question as a circuit breaker.

Step budgets exist but are opt-in per agent: agent.steps ?? Infinity. On the final allowed step the loop appends a MAX_STEPS_PROMPT assistant prefill telling the model to wrap up - the leash announces itself. Title generation and session summaries ride along as forked side jobs on the hidden title agent, so they never pollute the main transcript.

Context assembly

The system context is rebuilt fresh every iteration, in a fixed order, and its second slot is already model-specific:

Instruction files follow a strict precedence: one global file (~/.config/opencode/AGENTS.md, falling back to ~/.claude/CLAUDE.md), then the first match of AGENTS.md, then CLAUDE.md, then the deprecated CONTEXT.md, scanning upward from the working directory. Two lazy mechanisms extend this without spending startup tokens: @file mentions in your prompt expand into eager reads, and when a Read touches a file deep in the tree, any unattached AGENTS.md between it and the root is injected once. Budgeting is arithmetic in session/overflow.ts - usable context equals the catalog's limit.context minus reserved output tokens - and compaction works in two layers: prune erases old tool outputs outside a protected recent window (2,000 to 15,000 tokens, active only past 20,000 total), then summarize runs a hidden compaction agent over the serialized transcript and restarts the loop with a synthetic continue message. Skill outputs are exempt from pruning - the model asked for them.

Trust posture

Permissions are ordered wildcard rules - {permission, pattern, action} with actions allow, ask, deny, matched last-rule-wins, defaulting to ask when nothing matches. The shipped agents lean permissive-but-guarded: everything allowed by default, with doom_loop set to ask, reads outside the worktree set to ask, and reads of *.env files requiring approval. Asking is asynchronous and event-driven: the pending request parks the tool call on a deferred while the client answers once, always, or reject; always appends a session-lifetime allow rule. A CLI flag approves everything not explicitly denied - the flag's hidden aliases are --yolo and --dangerously-skip-permissions.

There is no OS-level sandbox. Bash runs as a plain child process of the server, network egress is unfiltered, and the entire trust story is rule matching plus the external-directory read gate. On a compromised or confused model, nothing contains the blast radius except a wildcard pattern list - the exact opposite trade-off to Codex CLI's fail-closed Seatbelt sandbox, and one step short of Pi, which ships no gate at all.

Model behavior

Support is catalog-driven end to end. At startup the provider service fetches https://models.opencode.ai/api.json - a models.dev snapshot operated by the project - caches it with a five-minute TTL behind a cross-process file lock, and reads three things off each entry: context limits, costs, and an npm field naming the Vercel AI SDK package to load. About twenty provider packages ship bundled; anything else is npm-installed at runtime and dynamically imported, which is how the project claims seventy-five-plus providers with a small team. The default model falls through config, then recent use, then a hardcoded preference order led by gpt-5 and claude-sonnet-4.

All per-family differences concentrate in one middleware pipeline, ProviderTransform, applied to every request: different base persona files per family; reasoning-effort menus derived from model ID and release date - newer GPT-5.x builds unlock lower and higher effort tiers that older ones never see; hardcoded sampling constants per family (Claude gets temperature omitted entirely, Gemini 2.5 and 3 get 1.0 / 0.95 / 64); explicit Anthropic cache breakpoints on the last two system and last two conversation messages; and JSON-schema surgery per backend, because Gemini and Moonshot validators reject schemas OpenAI accepts.

The distinctive mechanism

The loop itself is conventional - a ReAct-style while (true) over AI SDK streamText, structurally close to peers in this cast. What sets opencode apart is what decides its behavior. Most harnesses special-case models with scattered conditionals; opencode treats one externally-hosted catalog as declarative truth and compiles it at runtime into every layer:

This is the answer to "why does the same model behave differently under different harnesses": under opencode, changing the model ID silently rewires the persona, the reasoning-effort menu, the sampling envelope, the cache layout, the wire-format fixes, and the tool surface - deterministically, from data. Two runner-up mechanisms deserve mention. The doom-loop circuit breaker turns repetition into a human decision, converting a failure mode other harnesses handle with silent retries into an ask. And the Context Epoch design documented in the repository's CONTEXT.md - admitting mid-conversation system-message changes only at safe provider-turn boundaries so cached prefixes stay valid within an epoch - is already visible in the database schema, though not yet the executing path. Treat it as a roadmap item, not a feature.

Two of the design principles lesson 0010 distills show up here in their purest form. First, the model adapter is where affinity lives: nothing about the loop changed across families, yet the effective agent differs sharply. Second, defaults are the product: the catalog's numbers - context limits, output reserves, cost weights - quietly decide what compacts, what fits, and what a session costs, before any user preference is consulted.

Check yourself

Retrieval practice

Answer from memory before revealing.

The model makes the exact same tool call three times in a row. What does opencode do on the third?
SessionProcessor counts identical consecutive calls and forces a doom_loop ask at three. Restarting and dropping calls do not exist as mechanisms, and compaction fires on token budgets rather than repetition - the breaker's whole point is that a stuck loop needs a person, not a smaller window.
You switch a session's default model from a Claude model to a GPT-5 model. What changes?
The catalog-driven swap removes edit/write and exposes apply_patch for GPT models, while the persona file, effort ladder, sampling constants, and cache placement all re-derive from the new record too. Pricing and limits indeed come from the same catalog, but they are far from the only change.

Practice 1working

Open models.dev's raw catalog at https://models.dev/api.json and pick any model you use. From its record alone - id string, release date, provider - predict four things opencode would derive: which persona prompt file it loads, which reasoning-effort tiers it exposes, whether it keeps edit/write or gets apply_patch, and where cache breakpoints go.

Find: each prediction checked against the pinned source - session/system.ts for the persona map, provider/transform.ts for the effort ladder and caching rules, and tool/registry.ts for the swap condition.

Hint

The persona files are chosen by matching substrings of the model ID; the effort ladder gates tiers on the release date field; the swap keys on model IDs starting gpt- excluding some open-weight and legacy variants.

Show the worked solution
  1. Read the record. Note the id, the provider, the release_date, and the npm field naming the AI SDK package.
  2. Predict from data. An ID containing claude maps to the Anthropic persona file; a gpt-5-prefixed ID predicts the patch-dialect tool swap and a release-date-gated effort menu.
  3. Verify in source. system.provider() picks the prompt file; variants() builds the effort tiers; the registry's provider check performs the swap; Anthropic-shaped IDs get explicit cache breakpoints.
  4. Score yourself. Four-for-four means you can now predict harness behavior from catalog data alone - the compiler's promise.

Sanity check. If any prediction required reading the loop in prompt.ts, it was not a catalog-derived behavior - the whole claim is that these decisions live downstream of the loop, in the transform pipeline.

Your teacher. If the compiler idea has not landed, ask it to enumerate what would break if the catalog served a wrong release_date for one model. If the trust posture felt thin, ask it to compare the blast radius of opencode's allow-by-default rules against Codex CLI's fail-closed sandbox for the same runaway command.
