Four ways to stand between a model and your machine

working 9 min Evidence from fifteen harnesses: source repositories at their report-pinned commits, official documentation for the closed ones. · Claude Code permissions docs

The one-minute version

  • A tool call is about to run. Something decides whether it does: that something is the trust gate, and every harness builds a different one.
  • There are only four postures: ask a human first, enforce with the OS and treat approval as recovery, let a second model adjudicate, or ship no gate at all.
  • Each posture buys real safety and pays a real failure mode: prompt fatigue, false denials, invisible classifier errors, or total exposure.
  • The deepest split is not ask versus don't-ask. It is where the yes lives after it is granted - per call, per session, per repository, or forever.

1. One command, two gates

The clearest way to see a posture is to run the same harmless-looking command - npm install - through two of them. Under an ask-first gate, the harness stops before anything happens and puts the decision in front of you. Under an enforce-first gate, the harness just tries: the command starts immediately inside an operating-system sandbox, and you hear about it only if the sandbox says no.

Aider is the purest ask-first design: its shell suggestions run only after explicit confirmation, and even the --yes-always flag deliberately answers "n" for shell commands (Aider-AI/aider, aider/io.py:834-837). Codex CLI is the purest enforce-first design: its default sandbox mode is read-only, every generated profile denies by default, and approval exists to recover from denials (openai/codex, codex-rs/protocol/src/protocol.rs:1006-1058, codex-rs/core/src/tools/orchestrator.rs). Same model class, same command, structurally different experiences - which is the wrapper belief eroding again.

2. The four postures

Ask first

Who lives here: Aider, Cline, Kimi CLI, Roo Code, opencode - and every harness's manual mode. The mechanism is an approval callback on each mutating tool. Cline's self-description is "with your permission every step of the way" (ClineBot/cline, apps/vscode/package.json); Kimi routes every mutating call through Approval.request (MoonshotAI/kimi-cli, src/kimi_cli/soul/approval.py:200); opencode matches each call against ordered allow|ask|deny rules and falls back to ask when nothing matches (anomalyco/opencode, packages/opencode/src/permission/index.ts:37-44).

The failure mode is prompt fatigue. A gate that asks about everything trains its user to stop reading, so every ask-first harness ships a rubber stamp: opencode hides --yolo behind --auto (cli/cmd/tui.ts:126-135), Kimi exposes -y, Roo offers per-category toggles ending in allowedCommands: ["*"] (RooCodeInc/Roo-Code, src/core/auto-approval/index.ts:17-183). Aider alone refuses to stamp its most dangerous category - the strongest guard in the product, and the admission that this posture cannot protect a user who has already decided to stop being asked.

Sandbox first

Who lives here: Codex CLI as a primary posture; Cursor, Gemini CLI, and Google Antigravity as a layered one. The mechanism is kernel-level containment around every child process, so "may this run" is answered by the operating system rather than by a dialog. Codex generates a fresh Seatbelt profile per invocation on macOS with a deny-default base, and wraps Linux commands in bubblewrap plus a seccomp filter (openai/codex, codex-rs/sandboxing/src/seatbelt.rs:844-1032, codex-rs/linux-sandbox/src/linux_run_main.rs:199-274). Antigravity's permission engine compiles your read_file/write_file/read_url grants directly into the sandbox's filesystem and network allowlists, and reserves an unsandboxed() action type for commands allowed to escape containment (Antigravity docs: Permissions).

The failure mode is the false denial: legitimate work trips the wall mid-task, and a naive implementation strands the agent there. The interesting designs therefore make recovery first-class: denial heuristics read exit codes and stderr for "operation not permitted", then one approval reruns the command unsandboxed (codex-rs/sandboxing/src/denial.rs:13-72). Cursor documents its own sandbox as "best-effort guardrails rather than a hard security boundary" - an honest limit worth quoting (Cursor docs: Agent Security).

Classify first

Who lives here: Claude Code's auto mode as the flagship; Windsurf's Auto level as a lighter variant; Codex's Guardian reviewer as a secondary layer. The mechanism replaces the human at the prompt with a second model call judging the action against a maintained security policy - Claude documents auto mode as auto-approving tool calls "with background safety checks" (Claude Code docs: Configure permissions). Windsurf's Auto level makes the primary model its own classifier: the run_command tool carries a SafeToAutoRun flag the model sets itself, and risky commands still prompt - premium models only (Windsurf docs: Terminal).

The failure mode is the invisible error. A tired human misjudges visibly; a classifier misjudges silently, and its verdicts are only as good as the written policy behind them. The posture also couples safety to model capability: Claude documents that auto mode requires recent model families, and Windsurf gates Auto behind premium models - the gate literally degrades when the models underneath are older.

Nothing at all

Who lives here: Pi, deliberately, with pi-launcher as its identity complement. Pi's security documentation states plainly that it runs with the permissions of the account that started it, includes no built-in sandbox, and argues the design point: a partial in-process sandbox "would be easy to misunderstand as a security boundary", so real isolation belongs to a container or VM outside the harness (pi-mono docs: Security). What Pi keeps is narrower: project trust, a guard on loading project-local configuration, not on what tools do afterward.

The failure mode is total exposure, acknowledged rather than mitigated: unattended work is expected to wrap the whole process in a container, moving the posture choice from the harness author to the operator. That is a coherent answer - and it makes Pi the control group for every other entry in this course.

3. Where the yes lives

The second question a posture must answer is quieter: once granted, how long does an approval last? Get this wrong and either you re-answer the same prompt all day, or a decision you meant for one command quietly becomes permanent policy.

The lifetime ladder matters because the rungs are silent. Claude Code evaluates rules deny-first, then ask, then allow: a broad deny blocks every matching call no matter what else was approved (Claude Code docs: Configure permissions). Codex's amendment appends an allow rule to a Starlark policy validated at load time (openai/codex, codex-rs/execpolicy/README.md). When you audit an agent's posture, enumerate what it has already memorized: session grants, saved rules, and amended policies are the residue of every yes you ever gave.

The reframing A permission system is not a wall with a guard; it is a decision about who is allowed to be surprised. Ask-first surprises you before every risk. Enforce-first lets the OS be surprised instead and surfaces only the failures. Classify-first delegates the surprise to another model. Nothing-at-all decides nobody should be surprised, and tells you to bring your own container.
Placements on this page are judgments from sources pinned at each report's commit, not permanent facts: Cursor's sandbox is documented as best-effort, Antigravity's terminal sandboxing is a preview, and Claude Code's auto mode requires recent model families. Any of these can move a point on the map above, in either direction, within one release.

Check yourself

Retrieval practice

Answer from memory before revealing.

Your agent runs everything inside generated OS sandbox profiles and speaks up only when a command dies with "operation not permitted". Which posture is this, and what happens next?
This is Codex CLI's signature flow: attempt under the generated profile, detect denial from exit code and output, then offer a single approval for an unsandboxed rerun. The first option describes Claude Code's auto mode, which judges before execution rather than after failure. The second reverses the order - ask-first prompts before anything runs. The fourth mistakes a designed recovery path for a misconfiguration.
Pi ships no sandbox on purpose. Which sentence is closest to its documented argument?
Pi's security doc argues a partial in-process sandbox would be easy to misunderstand as a security boundary while still depending on the host shell, filesystem, credentials, and extension code - so isolation belongs to a container or VM. The first and third options invent performance rationales the doc never makes. The fourth misattributes the job: Pi says the operator brings containment, not the model provider.

Practice about 20 minutes, with your daily agent

Practice 1working

Classify your own daily driver. Give it three probes inside an ordinary session, in a scratch repository you can afford to reset:

Find: (1) ask it to run df -h and note whether anything prompts; (2) ask it to append a line to a file outside the working directory, such as ~/posture-probe.txt, and note what happens; (3) check its documentation or settings for any sandbox flag, then write down which of the four postures it defaults to, with one piece of evidence per probe.

Hint

The second probe is the discriminator: whether the write prompts, gets blocked by something that is not a prompt, or simply succeeds tells you which axis you are on before you read any docs.

Show the worked solution
  1. Score the reads. A silent df -h proves nothing by itself - every posture allows reads, which is why the probe set includes a write.
  2. Score the outside-cwd write. A dialog means an ask-first or hybrid gate; a block without a dialog means an OS sandbox denied it; silence plus success means no gate at all for writes.
  3. Name the posture. Manual-mode Claude Code lands ask-first; Codex CLI under its default profile lands sandbox-first with the denial visible; Windsurf at Turbo lands classify-first with you opted out; Pi lands nothing-at-all and its own docs tell you so.
  4. Check where yeses accumulate. Look for saved rules or amended policy files - .claude/settings.local.json, Codex's execpolicy rules - because yesterday's approvals are part of today's posture.

Sanity check. An honest classification names one observed behavior per probe; if all three probes ran silently with no wall and no documentation of either, you have found a Pi - which is exactly one of the four answers, not a failure of the exercise.

Your teacher. If the four postures blur, ask it to re-derive the quadrant chart from memory, then to place two harnesses you use but this page did not name. If the grant-lifetime ladder felt abstract, have it trace one real "don't ask again" click from your own history to wherever the rule now lives.
