Codex CLI: the sandbox decides first, and you teach it the rest

working 12 min Read from source at a pinned commit during this course's research phase. · openai/codex

Explore it yourself

Repository: github.com/openai/codex · License: Apache-2.0 · Language: Rust (with a TypeScript SDK wrapper). Analysis pinned to commit 7c6eb0eef113ddc16ae5b207ac9add364b489798; paths below live under codex-rs/.

The five files to read first, in reading order:

  1. core/src/session/turn.rs - run_turn: the whole agent loop in one function.
  2. core/src/tools/orchestrator.rs - approval, sandbox selection, and the retry-on-denial flow.
  3. core/src/tools/handlers/apply_patch.lark - the edit grammar, as an actual grammar file.
  4. sandboxing/src/seatbelt.rs - how a macOS sandbox profile is generated per invocation.
  5. models-manager/models.json - the model catalog that drives prompts, budgets, and which tools exist.

Community: design arguments happen in the repository's issues; releases and their notes live on the releases page.

The one-minute version

  • Codex CLI is one native binary playing many CLIs: TUI, non-interactive exec, MCP server, IDE backend - all clients of one embedded app-server.
  • The loop captures a frozen StepContext per sampling request, executes parallel-safe tools concurrently, and lets you steer mid-turn.
  • Its trust posture is unique in this cast: enforce first - every command starts sandboxed - and approvals exist to recover, then persist as policy amendments.
  • Model behavior is data, not code: a bundled catalog carries per-model prompt templates, budgets, and even whether direct tools exist at all.

1. One binary, many CLIs

Install Codex and you get a single executable whose behavior depends on what you call it. codex-rs/arg0/src/lib.rs:60-174 inspects argv[0] and argv[1] and dispatches to entirely different programs from the same bytes: the interactive TUI, apply_patch, the Linux sandbox helper, and an escalation wrapper. The code names the trick itself - deploy one executable, expose many CLIs (openai/codex, arg0/src/lib.rs:195-199). Symlinks under $CODEX_HOME/tmp/arg0/ put those aliases on the child process PATH, so even sandboxed commands can re-invoke them.

The second surprise is that the TUI never links the agent core. Every surface is a JSON-RPC client of the app-server, and in the TUI process that server runs embedded over memory channels while speaking the same envelope as the network transports (app-server/src/in_process.rs:1-24). Inside the core, communication is two queues per session: Op requests in, EventMsg events out (protocol/src/protocol.rs:545-659).

2. The loop: capture once, sample, steer

run_turn (core/src/session/turn.rs:155) is the loop its own doc comment describes: each sampling request returns function calls, which execute and feed back, or an assistant message, which ends the turn. Three moves make it worth reading line by line:

Capture once. Before sampling, the session freezes a StepContext - model info, approval policy, MCP binding, and a fully built ToolRouter. The comment gives the reason: context, advertised tools, and executed tool calls must share one request view (turn.rs:335). Tools cannot appear mid-step.

Steer anytime. Input typed while the model works lands in a pending queue and drains into history between iterations - so redirection happens at a step boundary, never mid-tool-call.

Stop explicitly. After each pass the loop continues only if the model emitted tool calls, asked for follow-up, or you queued input (turn.rs:425). When it stops, Stop hooks get a veto: they may inject a continuation prompt and force another iteration, or end the turn.

3. Context: the catalog is the constitution

Nothing about Codex's prompt is hardcoded per model family. Every entry in the bundled catalog models-manager/models.json carries its own full instruction template, context window, reasoning ladder, truncation policy, and tool configuration; unknown models fall back to generic metadata with a warning. Per session the resolution order is config override, then resumed history, then the model's template (core/src/session/mod.rs:658-676).

Project memory arrives through an AGENTS.md walk refreshed every step: climb from the working directory to the project root, take one file per directory root-down - AGENTS.override.md beats AGENTS.md - concatenated deepest-last under a shared 32 KiB budget (core/src/agents_md.rs:267-281, config/src/config_toml.rs:73).

The distinctive context move is world-state diffing: environment, permissions, and memory-file sections render only their change against the previous snapshot, so an unchanged fact costs zero tokens and a changed one announces itself as a replacement (core/src/session/world_state.rs:32-299). When history outgrows the window, compaction has three engines - local summarization, provider-served remote compaction on OpenAI endpoints, or a fresh window when the token-budget feature is active - chosen at runtime by capability (core/src/session/turn.rs:1191-1271).

4. Trust: enforce first, ask second, learn forever

This is the posture lesson 0050 introduced, seen from inside. Four approval policies (UnlessTrusted, OnRequest, Granular, Never) sit on top of three containment levels (read-only default, workspace-write, full access), but the load-bearing wall is below all of them: on macOS every command runs under a freshly generated Seatbelt profile whose base policy denies by default; on Linux, bubblewrap builds the filesystem view and a two-stage seccomp filter drops capabilities and most sockets (sandboxing/src/seatbelt.rs:844-1032, linux-sandbox/src/linux_run_main.rs:199-274). Windows uses restricted tokens plus firewall filters.

The orchestrator's doc comment states the recovery doctrine outright - approval, select sandbox, attempt, retry escalated on denial (core/src/tools/orchestrator.rs:4-7). Denials are recognized heuristically from exit codes and stderr keywords, one approval reruns the command unsandboxed, and ApprovedForSession caches the verdict so a repeated command does not re-prompt. Two escalations are unusual enough to name. A patched zsh intercepts every execve through a wrapper binary, so individual subcommands of a compound command can escape the sandbox on approval while the shell stays confined (shell-escalation/README.md). And an approving user can choose ApprovedExecpolicyAmendment, which appends a Starlark prefix_rule to a policy file validated at load time - the approval becomes permanent, reviewable law (execpolicy/README.md).

A secondary layer, the Guardian reviewer, is an LLM session with strict JSON verdicts that fail closed; it can grant on-request approvals without showing you anything.

5. Edits: a grammar, a ladder, a trapdoor

All editing goes through one custom tool, apply_patch, whose argument is raw patch text parsed against an embedded Lark grammar - add, delete, update, and optional move, with search-and-replace chunks anchored by optional @@ context lines (core/src/tools/handlers/apply_patch.lark). Because it is a freeform tool, the model emits the document directly, not JSON.

There is a trapdoor: patches routed through the shell tool are intercepted. A tree-sitter Bash query recognizes exactly the apply_patch <<'EOF' pattern, extracts the heredoc, and applies it as if the model had called the tool - while a bare patch body passed as a command errors with ImplicitInvocation rather than applying silently (core/src/tools/handlers/apply_patch.rs:507-553). Shell output comes back truncated to a per-model policy, ten thousand tokens by default, with the original count reported.

6. Models: behavior shipped as data

The wire layer collapsed to one protocol: WireApi holds a single variant, Responses, and configuring Chat Completions is a hard error (model-provider-info/src/lib.rs:62-68). Requests carry store: false and replay encrypted reasoning items, keeping conversational state client-side. Affinity is structural: freeform tools, remote compaction, and the WebSocket transport are Responses-side features other providers may lack, so the same harness quietly offers fewer tools elsewhere.

The catalog goes further than prompts. Newest-family entries ship "tool_mode": "code_mode_only": direct tools are hidden entirely, replaced by one freeform exec tool whose argument is TypeScript that calls nested tools through an out-of-process host over gRPC (code-mode-protocol/src/lib.rs:50). The default model is simply the first picker-visible entry in the catalog - currently a member of that code-mode-only family.

7. The distinctive mechanism

Why this one exists Enforce-first trust that amends itself. Other harnesses gate execution socially - ask, or classify, or both. Codex gates physically, detects failure, and converts your single approval into three progressively durable things: a retry, a session grant, or a persisted Starlark rule. Combined with in-shell per-subcommand escalation, the result is a trust system with a learning curve measured in approvals, not configuration. Code mode - tools invoked from model-written TypeScript as the default path on newest models - is the runner-up worth watching.

8. The extension surface at a glance

The mechanism pages cover each of these in depth; what matters here is that all of them hang off config layers and the tool router rather than off any surface. Config itself stacks nine layers - packaged defaults through MDM, user, project .codex/, and session flags - with higher layers winning (config/src/config_layer_source.rs:6-58).

Retrieval practice

Answer from memory before revealing.

A command fails inside the Codex sandbox with an operation-not-permitted error. What does the orchestrator do next?
The documented flow is approval, sandbox selection, attempt, then retry with an escalated strategy on denial - one approval unlocks the unsandboxed rerun and caches for the session. The first option describes an abort, not a recovery. The second invents a command rewriter that does not exist. The fourth invents a model downgrade; model changes trigger compaction, not permission handling.
What makes an approved Codex command different from a "don't ask again" approval in most other harnesses?
The amendment choice writes a Starlark prefix_rule into load-time-validated policy - approval becomes law. Session grants do exist as an intermediate rung, but the distinctive destination is the persisted rule. No second model countersigns approvals; the Guardian reviewer grants instead of you, it does not verify you. Directory scoping is not the distinguishing property.
