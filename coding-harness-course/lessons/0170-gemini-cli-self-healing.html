The community: issue tracker, discussions, and Google's public roadmap board.

Identity

Google's terminal agent describes itself as "an open-source AI agent that brings the power of Gemini directly into your terminal." The repository appeared in April 2025, the npm package followed that June, and by August 2026 it carried roughly 106,700 stars and 14,500 forks - the fastest-growing artifact this course studies. One npm workspace, seven packages, but two matter: @google/gemini-cli-core, the headless engine, and @google/gemini-cli, an Ink/React terminal UI that owns loop closure in interactive mode. The split is real - core never imports cli; they talk through typed event streams (ServerGeminiStreamEvent) and a confirmation MessageBus.

The loop

One engine, two drivers. Headless (gemini -p "...") runs a plain while-loop over events; interactive mode hands the same job to a React hook whose completion callback re-submits tool results as a continuation. Inside the engine, processTurn compresses history when needed, refreshes model-specific tool declarations, and streams; every functionCalls[] entry becomes a ToolCallRequest event with a synthesized id. Two stop conditions deserve attention. The next-speaker check is an extra structured model call asking who talks next - the turn may not end just because no tools are pending. And loop detection watches every event, nudging once ("take a step back") before aborting on a second consecutive repeat.

Context assembly

The window fills in a fixed order. The system instruction is composed from named snippets - conditionally included per model and mode - and can be swapped wholesale via the GEMINI_SYSTEM_MD environment variable or dumped with GEMINI_WRITE_SYSTEM_MD. Then memory: GEMINI.md files load from four tiers - global, extension context, project files walked upward from cwd to git root, and a private .gemini/MEMORY.md index - with recursive @path imports up to depth five. The filename itself is configurable, so teams run AGENTS.md conventions by setting contextFileName. Precedence is written into the prompt: deeper files override shallower ones on style, never on safety mandates. When high-intent tools touch a subdirectory later in the session, JIT discovery appends that directory's GEMINI.md to the tool output - memory arriving exactly when it becomes relevant.

Trust posture

Four approval modes sit on top of a real policy engine, not a boolean: default asks for writes and shell, auto_edit approves edits, yolo approves everything, and plan mode restricts the toolset outright. Every call passes checkPolicy against TOML rule files from system, user, and workspace scopes; outcomes are ALLOW, DENY, or ASK_USER, and "always allow" writes narrowed persistent rules keyed by tool plus argument patterns rather than blanket grants. Sandboxing ships behind one factory with four implementations - macOS Seatbelt profiles, Linux bubblewrap, a Windows restricted-token sandbox, and container mode via docker, podman, or gVisor with network egress through a local proxy. Folder trust gates whether workspace-local commands, MCP servers, and skills load at all; untrusted tool output is wrapped in <untrusted_context> tags carrying a standing instruction to ignore directives inside.

Model behavior

This harness is Gemini-only by design - there is no Anthropic or OpenAI adapter, and auth flows through Google identities: OAuth personal login, API key, Vertex AI, Cloud Shell, or a gateway base-URL override for proxies. Affinity shows up as explicit per-family forks rather than folklore. getToolSet(modelId) returns a rewritten manifest for Gemini 3 versus a legacy set - Gemini 3's grep description advertises symbol matching the legacy one does not, and its replace makes the semantic instruction parameter required. supportsModernFeatures switches between two whole system-prompt dialects. Most tellingly, Gemini 3 validates thoughtSignature on replayed function calls, and the harness injects a synthetic signature rather than let the API reject unsigned calls - compatibility shims shaped exactly to one model family's wire dialect, the phenomenon the Models module names per-family affinity.

The distinctive mechanism

Lesson 0040 placed this harness alone in school three: when an edit fails to match, most harnesses bounce an error and burn a full agentic round-trip. Gemini CLI instead spends its own machinery first - a graded deterministic cascade, and then the step nobody else ships: a targeted micro-inference whose only job is to repair the harness's failed decode of the model's intent.

The economics are the point. A bounced edit costs a complete round-trip: the model reads the error, re-reads the file, and re-emits the whole edit. The repair call sends a narrow envelope - instruction, the failed pair, current content refreshed from disk if it changed underneath, the specific failure reason - and receives back a corrected pair that re-enters the deterministic cascade from the top. It can even conclude "no changes required," converting a would-be failure into a legitimate no-op result. Copilot Chat independently grew the same organ for patches and credits this codebase in its healing header - convergent evolution across competing vendors, which is about as strong a signal as this course gets.

The reframing Self-healing moves reliability from the model's discipline into the harness's machinery. Where the wrapper believer sees "the model fixed its mistake," the engineer sees a pipeline that refuses to hand its own decode failure back upstream.

Honest runners-up: shadow-git checkpointing (a hidden repo snapshots your tree before restorable calls, so /restore works even outside git projects) resembles peer rewind features but stands on its own work-tree implementation; and the next-speaker check - spending a model call to decide whether the turn may end - is a genuine second novelty this harness runs every single turn.

Check yourself

Retrieval practice

Answer from memory before revealing.

A turn's reply contains no tool calls. What else must happen before Gemini CLI ends the turn?
checkNextSpeaker is a second structured model call over the BaseLlmClient, and its verdict gates the stop. Cooldowns and queue draining are not part of the design. Loop detection fires only on repeated events - it nudges first and aborts on a repeat, it does not certify normal stops.
Why does the repair path refresh file content from disk before calling the fixer?
Repairing against stale bytes would produce another mismatch - the code detects content drift and reloads before the call. Token savings, sandbox rules, and telemetry resets are not what the refresh is for.

Practice about 30 minutes, with a terminal

Practice 1working

Clone the repository at the pinned commit: git clone https://github.com/google-gemini/gemini-cli, then git checkout 812f7a2b. Trace one edit end to end without running anything: find where replace enters the cascade, name the four deterministic strategies in order, and locate the exact object sent to the repair model.

Find: the function names and line regions for each strategy, the score gate on the fuzzy matcher, and the field list of the repair request.

Hint

Start at calculateReplacement in edit.ts; the strategies appear in the order the code tries them, and utils/llm-edit-fixer.ts holds the repair envelope.

Show the worked solution
  1. Deterministic stages. Exact literal, then flexible whitespace-insensitive line matching with indentation preservation, then token-based regex for formatting drift, then a Levenshtein sliding window gated by a complexity budget.
  2. The repair boundary. Only after all four fail does control pass to attemptSelfCorrection and llm-edit-fixer.
  3. The envelope. Instruction, the failed old/new strings, current file content refreshed if drifted, and the specific failure reason - answered by a corrected pair or a legitimate no-change verdict.

Sanity check. If you found five deterministic strategies, you counted the repair call itself - it is not deterministic, which is exactly the boundary this page draws.

Your teacher. If the loop diagram felt busy, ask for a re-walk with a concrete task like "rename this variable" and name what each participant holds at each arrow. If the distinctive mechanism has not landed, ask it to contrast what happens on a failed edit here versus in a school-one harness, counting the round-trips.
