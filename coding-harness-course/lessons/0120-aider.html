Five files to read first, in this order:

  1. aider/main.py - startup, config search, and the REPL that swaps coders on mode change
  2. aider/coders/base_coder.py - the loop every edit format shares
  3. aider/coders/editblock_coder.py - SEARCH/REPLACE parsing and its graded matching fallbacks
  4. aider/repomap.py - tree-sitter tags into a PageRank graph
  5. aider/models.py - the per-model settings matcher behind 357 catalog entries

Where the community is: GitHub issues and pull requests carry most design arguments; there is also a Discord linked from aider.chat, and the edit-formats and repo-map docs pages are the project's own explainers.

The one-minute version

  • Aider predates tool calling: the model's formatted reply text is the action, parsed after the fact into edits.
  • Retrieval is front-loaded into the prompt: a PageRank repo map over tree-sitter reference graphs ships every turn.
  • There are no permission modes and no sandbox - git commits are the safety net, taken automatically before and after edits.
  • Its per-model settings file encodes years of family-specific workarounds - the ancestor of today's model-adapter layer.

The lineage label matters more than the version numbers. Aider was built when models could not call functions reliably, so it never grew the tool layer the rest of this course studies - and it remains fully useful without one.

Context assembly

Every turn rebuilds the message list from scratch in an order fixed by ChatChunks.all_messages() (chat_chunks.py:16-26). Two choices stand out against the modern cast. Memory files load never: there is no AGENTS.md convention anywhere in the package - you maintain a conventions file and add it yourself. And the map rides as a fake exchange, a user message followed by a scripted "Ok, I won't try and edit those files without asking", which teaches the model the map is read-only context.

Trust posture

Aider's posture is consent plus git, with no sandbox anywhere. Files must be added to the chat before they can be edited; anything else triggers a question via confirm_ask. The sharpest guard is easy to miss: --yes-always, which auto-approves almost everything, deliberately answers no to suggested shell commands, because those prompts demand an explicit yes (io.py:834-837). Rollback is /undo, which refuses to reset any commit Aider did not make this session.

By default Aider skips pre-commit hooks - its commits pass --no-verify unless you pass --git-commit-verify (repo.py:277-279). Teams whose hooks are their security control should know the default is off.

Extension surface

There is none in the agent-era sense: no MCP client, no hooks, no subagents, no skill packs - none appear anywhere in the package. What Aider offers is configuration depth. A YAML file overrides any per-model setting including the edit format; a JSON file adds model pricing and context sizes; aliases rename models; --lint-cmd and --test-cmd wire in your own commands to run after edits; and watch mode turns AI! comments in any editor into prompts. New behaviors mean new code - the extension story is "fork us".

Model behavior

The adapter layer is a 357-entry YAML catalog plus substring heuristics that pick an edit format, a caching strategy, and sampling defaults per family (models.py:437-598). It is the oldest surviving artifact of harnesses bending around model quirks:

The distinctive mechanism

No other member of the cast computes a static ranked outline of the repository and ships it in every prompt. Aider's repo map replaces retrieval with ranking: extract every definition and reference with tree-sitter queries cached by mtime, build a directed multigraph linking files that share identifiers, run personalized PageRank, then binary-search how many ranked entries fit the token budget rendered as compact code outlines (repomap.py:365-706).

The interesting engineering is in the weights. An edge from a file already in the chat counts fifty times; identifiers the user typed get ten times; long snake-case or camel-case names - the distinctive ones - get ten times; underscore-private names and identifiers defined in more than five places get divided by ten (repomap.py:481-514). Those multipliers are written-down hypotheses about what a model needs to see, tuned over years of benchmarks.

The honest cost side: the map is stale between refreshes, blind to anything tree-sitter cannot parse, and charged to the window every turn. Agentic retrieval inverts all three - fresh, format-free, pay-per-use - at the price of latency and extra turns. Neither dominates; the deep dives ahead will keep meeting this trade in new clothes.

Check yourself

Retrieval practice

Answer from memory before revealing.

Aider's model suggests running your test suite. You launched aider with --yes-always. What happens?
Shell prompts are marked explicit-yes-required, and confirm_ask deliberately treats a blanket yes as a no for exactly those prompts. There is no sandbox mode to enable, and repetition changes nothing about the gate. This is the strongest guard in the product precisely because yes-always covers everything else.
Why does the repo map arrive as a user message paired with a scripted assistant reply?
The scripted reply says "Ok, I won't try and edit those files without asking" - it frames the map as read-only context, mirroring how added files are framed. No provider caps system messages that way, the map is rebuilt between turns rather than mid-turn, and the pairing exists to constrain, not to invite correction.

Practice about 15 minutes, with paper

Practice 1working

An edge in Aider's graph carries weight use_mul × √n, where n is the reference count and the multipliers stack multiplicatively (repomap.py:487-514). Compute the weight of this edge: the identifier is parse_config_file, the user mentioned it in chat; it is snake-case with 17 characters; it is defined in 2 files; it is referenced 4 times, all from a file already in the chat; it does not start with an underscore.

Find: the final edge weight, and which single factor contributed most.

Hint

List each multiplier separately first: mention, name length, definer count, privacy, chat-file origin. Then multiply them together and finally apply the square root of the reference count.

Show the worked solution
  1. Stack the multipliers. Mentioned ×10, snake-case and at least 8 chars ×10, 2 definers so no damper, no underscore so no damper, referencer in chat ×50: base 10 × 10 × 50 = 5,000.
  2. Apply the reference scaling. √4 = 2, so weight = 5,000 × 2 = 1,000.
  3. Name the biggest factor. The chat-file origin, worth ×50 alone - relevance to the current conversation outweighs everything else combined.

Sanity check. Drop the chat-file origin and the weight falls to 20 - a fifty-fold difference from one factor, which is why where you are standing dominates what the map shows.

Your teacher. Ask it to walk one real identifier from your own repository through the multiplier table and predict whether it makes the map. Then ask it to argue the other side: what would have to be true for a grep loop to beat the map on both cost and freshness.
