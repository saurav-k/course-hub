Publishing the work so a stranger can trust it

11 min publishing guide A repository shape that works for every proposal, a README skeleton with the claim on line one, demo rules learned the hard way by this course's own pages, and how to write about statistics so a non-statistician can repeat your argument in a meeting.

The one-minute version

  • One repository shape fits all eight proposals: runnable demo at the root, audit card beside it, raw third-party data left upstream with fetch instructions.
  • The README starts with the claim in one sentence, not with the story of how you came to have the idea.
  • Demo rules are absolute: opens by double-click from disk, no keys, no install, survives losing the network, legible in dark mode and print.
  • Write for the reader who must retell your argument without you present: decision first, one metaphor maximum, every number carries its interval or says why it needs none.

1. The repository shape

Works for every proposal on the menu:

project-name/
  index.html          ← the runnable demo (self-contained, zero dependencies)
  README.md           ← written for the reader below; starts with the claim
  src/                ← model + audit code, commented in reading order
  data/               ← generated seeds + tiny derived extracts you may ship;
                        raw third-party data stays upstream, with fetch instructions
  AUDIT.md            ← the week-6 audit card, exported
  LICENSE             ← code licence (MIT / Apache-2.0); content licence separate
                        if prose is substantial

Three decisions in that shape deserve their reasoning stated:

  • The demo lives at the root because it is the argument. Anyone landing in the repository should reach something running in one click, not after reading build instructions.
  • Raw third-party data stays upstream. Shipping scraped or licensed datasets inside your repository creates legal exposure and a provenance hole in one move - the failure catalogue names this data laundering. Ship instead: your fetch script, the date you fetched, a checksum of what you got, and derived extracts small enough to be clearly transformative.
  • AUDIT.md sits beside README.md, not buried in src/, because the audit is a first-class deliverable of this course - the part most portfolios lack. A reviewer who reads only two files gets the claim and the critique.

2. The README skeleton

In this order:

  1. The claim in one sentence. "A calibrated filter flags spam at a threshold chosen from what false positives cost" - not "This project began as an exploration of…". The history can come later, if at all.
  2. What is random here, and why that distribution. Two or three sentences naming the probabilistic core, the same answer you gave the four-question gate.
  3. How to run. For a proper capstone demo this is one line: open index.html. If it takes more than one line, the demo needs fixing before the README does.
  4. Results table with intervals. Every headline number side by side with its interval and its method. No bare points anywhere in the table.
  5. What would falsify this. The observation that would make you withdraw the claim, stated before anyone asks.
  6. Attribution and licences. Data source, licence terms, what you shipped versus what you left upstream, code licence.
  7. Limits. Sample size, population shift between your data and deployment reality, proxy labels - named plainly, each with its consequence.

Note what the skeleton does not contain: a methodology tour, an apology for simplicity, a related-work survey. Those can live in src/ comments or nowhere. The README serves a reader deciding whether to trust and reuse the work, and every section above earns ten seconds of that reader's attention.

3. Demo rules

This course's own pages model every rule; steal the constraints wholesale:

  • Opens from disk by double-click. No server process, no CORS gymnastics, no build step. If it needs npm start, it fails the stranger test.
  • Degrades gracefully without network. Data either ships inside the page or loads from a file beside it. A spinner waiting on an API is a broken demo wearing a costume.
  • States its provenance on screen. Where the numbers came from, when they were fetched, what was simulated. On the page, not only in the README - screenshots travel without repositories.
  • Dark-mode safe. Colours read from tokens at draw time if you draw to canvas; contrast checked in both themes. This course has been bitten enough times to encode the lesson in its builder spec.
  • Prints sensibly if it ends in an audit card. The audit is meant to travel into meetings; give it a print layout worth carrying.

Test them the way a stranger will: fresh browser profile, airplane mode on, second display disconnected, dark mode forced by the OS. Ten minutes of hostile testing finds everything reviewers find, before they find it.

4. Writing about the work for non-statisticians

Five rules, each earning its place:

  1. Lead with the decision the uncertainty changes, never with the estimator. "We flag fewer innocent people at the same recall" beats "FPR improved at constant TPR". The reader needs to know what changed for whom before they care how you measured it.
  2. One metaphor maximum per document. Metaphors are load-bearing exactly once; the second one mixes with the first and both collapse. Choose the single analogy your audience already owns and ride it the whole way.
  3. Every number either carries its interval or says why it needs none. Counts from the full dataset need none; estimates from samples always do. The discipline of asking which is which is itself half of honesty axis.
  4. Name the trade-off you chose instead of implying there was none. Every threshold choice gives something up; saying which loss you accepted is what separates a decision from a coincidence.
  5. End with the falsifier. The last analytical sentence of the document names the evidence that would change the conclusion. Documents that cannot end any other way read as marketing; documents that do read as science.

Then apply the meeting test: read your draft asking only whether your manager could repeat the argument at a meeting without you in the room. Not agree with it - repeat it: state the claim, name the evidence, quote the interval, concede the limit. That is the entire standard, and it is a higher bar than it sounds.

Check yourself

Your weather-audit demo calls the forecast API live on every page load, cached for speed. Which publishing rule does this break?
A live call means the artifact depends on network and time: airplane mode kills it, and worse, the numbers drift under the reader's feet - the reliability diagram someone screenshots tomorrow audits a different fortnight than yours did. Freeze the fetch behind a dated snapshot constant, ship it with the page, and let the README say where it came from and when.
Which README opening line follows the skeleton?
Line 1 leads with the claim and immediately prices it: interval, sample size, method pointer. Line 3 names techniques but states no result; lines 1 and 4 lead with biography and table of contents respectively - all three postpone the only thing the first sentence exists to deliver. Claim, then price, then proof.
Your teacher. Open your current project draft's README and delete everything before the claim. Whatever you just deleted probably belongs in a design journal, not in front of the number. Keep the deleted text somewhere private if it hurts; the README stays ruthless.
