Nine cheap answers voting beat one expensive one - until you count why

working 10 min Binomial counting prices the majority-vote policy exactly: nine nano samples at p = 0.75 agree correctly 95.1 percent of the time, for $0.00486.

The one-minute version

  • Any-correct needs an oracle saying which sample is right; majority vote needs nothing but the samples - it is the self-consistency policy you can actually ship.
  • P(exactly k right in n) = C(n,k) x pk(1-p)(n-k): count the orderings, price one ordering.
  • Sum k from the majority threshold up to n and you have the policy's quality. For n = 9, p = 0.75: five terms totalling 0.95107.
  • Compute C(n,k) with a short multiplicative loop - never factorials, which overflow past 171! and quietly hand back Infinity.

Two ways to keep a sample set

The planner's sampling rows answer "what do we do with n nano answers?" differently. The any-correct row assumes something inspects the samples and keeps the request if any landed right - realistic when answers verify themselves, as generated code does against a test suite, and otherwise an optimistic bound. Majority vote is the version needing no inspector at all: generate n independent answers and ship the most common one. Wang et al.'s self-consistency result is this policy: across reasoning benchmarks, plurality voting over sampled chains beats any single chain.

Majority needs odd n - ties are resolved by spending one more sample, not by flipping coins. Its quality question is precise: what is the probability that at least half of n independent Bernoulli(p) trials come out correct? Answering it means counting.

Count sequences, price one, multiply

A specific pattern - say samples 1, 3 and 7 right out of five, the rest wrong - has probability pk(1-p)(n-k) by Lesson 7's independence: each hit contributes a factor p, each miss a factor (1-p), and the pattern's own ordering fixes how they group. But the event "exactly k right" does not care which positions fired. It is the union of many disjoint patterns, all equally likely, so its probability is the pattern price times the pattern count:

P(exactly k right in n) = C(n,k) x pk x (1-p)(n-k) Read as: C(n,k), spoken "n choose k", counts how many distinct position-patterns hold k successes among n slots - n!/(k!(n-k)!), though the very next paragraph refuses to compute it that way. Multiply the count by the price of any single pattern and you hold the whole event.
P(majority correct) = ∑k = (n+1)/2 ... n C(n,k) x pk x (1-p)(n-k) Read as: add the exact-count probabilities for every winning tally - for odd n, everything from (n+1)/2 upward. These are disjoint complete outcomes, Lesson 4's legal addition. This one line is the entire majority-vote policy.

Worked at n = 9, p = 0.75, where the majority threshold is 5:

  1. Tally k = 5. C(9,5) = 126 patterns; each costs 0.755 x 0.254 = 0.000927; contribution 0.11680.
  2. Tally k = 6. C(9,6) = 84; 0.756 x 0.253 = 0.002780; contribution 0.23360.
  3. Tally k = 7. C(9,7) = 36; 0.757 x 0.252 = 0.008341; contribution 0.30034.
  4. Tallies k = 8 and 9. 0.22525 and 0.07508.
  5. Add the winners. 0.11680 + 0.23360 + 0.30034 + 0.22525 + 0.07508 = 0.95107.

Ninety-five point one percent from calls worth $0.00054 each - $0.00486 for the set, against $0.012 for one frontier call at 0.97. That comparison is the week's economic thesis in two numbers, and Lesson 9 automates it. First, the implementation habit the design brief insists on:

counting without factorials · runnable JavaScript
function choose(n, k) {          // C(n,k) the safe way
  var r = 1;
  for (var i = 0; i < k; i++) {
    r = r * (n - i) / (i + 1);
  }
  return r;
}

function pMajority(n, p) {       // n must be odd
  var s = 0, maj = (n + 1) / 2;
  for (var k = maj; k <= n; k++) {
    s += choose(n, k) * Math.pow(p, k) * Math.pow(1 - p, n - k);
  }
  return s;
}
Why not n!/(k!(n-k)!)Because 171! is where doubles die: beyond it the factorial returns Infinity, and C(200,100) - a number any laptop can hold - comes back as NaN through the formula yet computes fine through the loop, whose running value never leaves the range of the final answer. The symptom in a broken build is readouts showing NaN or Infinity for large n; the cause is almost always a factorial written honestly. The loop interleaves each multiplication with a division, so intermediate values stay near 1 and precision survives.

Check yourself

Nine independent samples, ps = 0.75. What is P(exactly 6 right)?
Count the orderings - C(9,6) = 84 ways to place six hits among nine slots - then price one ordering, 0.756 x 0.253, and multiply: about 0.2336. Omitting the count prices a single named pattern; inverting the coefficient asks for nine objects chosen from six, which is meaningless here; and 6/9 is a frequency summary, not a probability statement about the next batch.
Why does the build compute C(n,k) through the multiplicative loop rather than the textbook factorial formula?
Doubles give out at 171!, while C(200,100) fits comfortably in one - the loop's running value stays small because every step multiplies then divides, whereas the formula's intermediates are astronomically large before cancelling. Rounding differences are negligible either way; the loop actually performs a similar number of operations; and Math.pow exists natively, no imports involved.
Your teacher. Set the sliders to n = 3, p = 0.51 and watch majority vote score barely above a coin despite "three heads are better than one". Then push n to 15 at the same p: about 0.53, glacial. Voting amplifies an edge; it cannot create one. When your per-sample accuracy sits below one half, the honest policy is frontier-always, not more ballots - which is exactly what the planner will say tomorrow.
