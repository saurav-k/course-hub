Before any formula, one request is just two ways the world can land

foundation 8 min The sample space, an event, and the ten-line function that plays the role of the universe for the rest of the week.

The one-minute version

  • The sample space is the set of things that can happen. For one request to one model, it is exactly {correct, wrong} - two outcomes, no more.
  • An event is any subset of that set. "It was correct" is the subset {correct}.
  • You write the world as a function, bernoulli(p), which lands correct with probability p and wrong otherwise.
  • Run it ten thousand times and the frequency of correct answers settles down close to p - the number the whole week spends is now something you have watched happen.

The set of things that can happen

Strip one inference request down until nothing is left but its outcome. You send a prompt to a model; eventually either the answer is correct or it is wrong. That pair is the sample space, written S:

S = {correct, wrong} Read as: the sample space S holds every possible outcome of one request, and here there are exactly two. Nothing about price, latency or model identity belongs in S - those describe how the request runs, not what can happen.

An event is any subset of S. There are four: the empty set (nothing happens, which cannot occur when the request always lands somewhere), {correct}, {wrong}, and all of S. When you say "P(the answer is correct)" you are attaching a number to one of those subsets. If the foundations-course notation of sets and sample spaces has gone cold, its language-of-sets page and its sample-space page carry the careful treatment; here we only need the two-element version, and we need it running in a browser.

Why insist on the set at all? Because every quantity the planner produces later - the chance a cascade ships, the chance five samples contain one hit, the chance your quality bar is met - is built by combining events over spaces exactly like this one. A probability that is never attached to a subset of outcomes is a vibe. This week does not ship vibes.

Write the world as a function

Probability enters through one number: p, the chance the answer lands in {correct}. Nobody knows your task's true p - that honesty comes in Lesson 6 - so the build plays the role of the world with a function taking p as a parameter. Here is the whole thing:

the world · runnable JavaScript, no dependencies
function bernoulli(p) {
  return Math.random() < p ? 1 : 0;
}
bernoulli(p) returns 1 with probability p, and 0 otherwise Read as: Math.random() draws a number u uniformly between 0 and 1 (MDN, Math.random()). Every value in [0, p) covers a fraction p of that range, so the comparison u < p succeeds with probability exactly p. Returning 1 codes the outcome correct; returning 0 codes wrong.

A single yes-or-no draw with success probability p is called a Bernoulli trial, after the Swiss family of mathematicians who studied gambling odds professionally. The name is worth knowing because the week's entire cast - samples, checks, escalations - will be built by calling this one function with different arguments and counting.

What the picture proves, and what it only suggests

The dashed line is the input p. The wandering trace is a fact about the output side: the fraction of correct answers among the requests run so far. Early on it swings wildly - with ten requests, seven versus eight correct answers moves the frequency by a tenth. By a thousand requests it hugs the line. The gap readout under the chart puts a number on the hug at ten thousand: usually within a hundredth, occasionally a little outside, never far outside.

This is the empirical face of the week's first trade-off. Simulation is honest - it makes no assumptions beyond the world function you wrote - but it is also imprecise, and the imprecision shrinks slowly, like the square root of the number of trials. Derivation is the opposite: exact, instant, and only as good as its assumptions. The Spend Planner will carry both, side by side, for exactly this reason. An analytic column that disagrees wildly with its simulated neighbour is telling you the derivation's assumptions and the world disagree - and in Lesson 5 you will meet the classic case where that mismatch direction diagnoses the exact error.

Where randomness comes fromThe build seeds its random stream (default 42), so every reader of this page sees byte-identical traces and the prose can quote numbers without hedging. Real simulations seed differently each run. The mathematics does not care which, and neither should you - what matters is that the stream behaves like independent coin flips, which is a property the seeded generator was chosen for.

Check yourself

One request goes to the nano tier. What is the sample space?
The sample space lists what can happen, and a request either ends up correct or wrong. The tier name describes who answered, not what occurred; there is no third outcome hiding between correct and wrong; and the price is certain before the request is sent, so it is not an outcome at all. Confusing the actors or the costs with the outcomes is the standard first-week slip, and every later table in the planner inherits its columns from getting this right.
Five independent requests go to the nano tier, each correct with probability 0.8. Someone claims the chance that at least one is correct equals 5 x 0.8 = 4. What is the sharpest thing to say to them?
The immediate defect is that 4 is not a probability: no event can carry probability past 1. The deeper reason the addition fails is indeed overlap - the five "this request is correct" events occur together all the time, and naive addition counts those joint occurrences five times over - which is the fix Lesson 2 builds properly with the complement rule. But the answer the question asked for is the one visible from the axioms alone. Rounding has nothing to do with it, and the two-outcome restriction is invented.
Your teacher. Change one thing in bernoulli: make it return u <= p ? 1 : 0 instead. Nothing measurable changes - the boundary has measure zero - and noticing why is exactly the habit of separating continuous draws from discrete outcomes that Lesson 2's axioms formalise. Then set p to 95 and count how many of your own production features you would trust to a coin that biased.

Where this came from

Bernoulli trials and the stable-frequency observation go back to Jacob Bernoulli's Ars Conjectandi (1713); a modern textbook treatment with the same two-outcome framing is Sheldon Ross, A First Course in Probability, chapter 4. The uniform-draw construction used by Math.random() is documented on MDN. The formal set-language this page compresses lives in the foundations course's sample-space lesson.
