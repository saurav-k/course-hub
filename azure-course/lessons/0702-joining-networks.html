Peering joins two networks and only two, so every hub is a transit design

working 11 min Capability area networking-core, rows network-peering and transit-hub, with the recorded absence shared-vpc beside them. · Virtual network peering

The one-minute version

  • Peering is non-transitive. Two spokes peered to a hub cannot reach each other through it unless something in the hub is made to forward them.
  • Gateway transit is the exception worth knowing: a spoke can use the hub's VPN or ExpressRoute gateway rather than holding one of its own.
  • Peering costs nothing for bandwidth inside a region and bills per gigabyte across regions, which quietly shapes where chatty components are placed.
  • A Virtual WAN hub is the managed alternative: Basic is site-to-site only, Standard is any-to-any, and the secured-hub pattern embeds Azure Firewall with routing intent.
  • Azure has no shared-network construct. A hub subscription owns the network and workload subscriptions either peer into it or receive role assignments on its subnets.

The property that decides everything

How a packet actually crosses between two spokes

The reframing Gateway transit is the one place the platform does supply transit for you. A spoke peered with gateway transit enabled uses the hub's VPN or ExpressRoute gateway instead of deploying its own, which is what makes a central connectivity subscription affordable: one gateway serves the estate rather than one per workload network.

Two hub shapes

The per-hub connection and scale numbers move, and this course deliberately quotes none of them. Read them from the vendor's current limits table at the moment you design, and treat any figure written into an architecture document as needing a date beside it. The same applies to how many peerings one network will carry.

Retrieval practice

Answer from memory before revealing.

Two spokes are peered to the same hub and cannot reach each other. What is missing?
Peering is non-transitive, so spoke-to-spoke needs a forwarding device plus routes sending traffic to it. The second option is wrong twice - direct peering between spokes is possible and would not be "unsupported", it is simply not what a hub design uses. The third names a real feature that carries gateway traffic, not spoke-to-spoke traffic. The fourth confuses the managed hub types with self-built peering.
What is the difference between a Basic and a Standard Virtual WAN hub?
The two types differ in capability rather than in size - any-to-any, ExpressRoute and hub-to-hub arrive with Standard. The first and second treat a capability tier as a size or a scope. The fourth describes the secured-hub pattern, which is an option on top rather than the definition of the tier.
Four subscriptions must use one virtual network. What does Azure offer?
There is no sharing construct - the pattern is one owner plus access granted to others. The first two options describe constructs the corpus records as absent. The third invents an inheritance behaviour that management groups do not have for resources.

Practice about 20 minutes, with paper

Practice 1working

An estate has one connectivity subscription and twelve workload subscriptions, each with its own virtual network in the same region. Requirements: every workload must reach an on-premises estate; two of the twelve must talk directly to each other; a shared logging component in the connectivity subscription must be reachable from all twelve; and the platform team wants inspection of all traffic between workloads. A proposal peers all twelve to the hub and declares the requirements met.

Take it apart: say which requirements the peering alone satisfies, which it does not, and what else is needed for each of the rest.

Hint

Sort the four requirements into "between a spoke and the hub" and "between two spokes". Peering answers one of those categories on its own and neither part of the other.

Show the worked solution
  1. Sort the requirements. Reaching on-premises and reaching the shared logging component are both spoke-to-hub. Talking between two workloads and inspecting traffic between workloads are both spoke-to-spoke.
  2. Check the shared logging component. It lives in the connectivity subscription's network, and each spoke is peered to that network, so this one is genuinely satisfied by the peering as proposed.
  3. Check the on-premises requirement. Peering alone does not give a spoke the use of the hub's gateway - that is what gateway transit is for. With it enabled on each peering, one gateway in the connectivity subscription serves all twelve, which is the reason the subscription exists.
  4. Check the direct workload-to-workload requirement. Peering is non-transitive, so the two spokes cannot reach each other through the hub. This needs a forwarding device in the hub plus a user-defined route on each of the two spokes sending the other's prefix to it.
  5. Check the inspection requirement. Inspection of traffic between workloads is the same mechanism seen from the platform team's side: the device in the hub is where inspection happens, and the routes are what guarantee traffic reaches it rather than taking a shorter path.
  6. Notice what the last two share. Once inspection is required for all inter-workload traffic, direct spoke-to-spoke peering between the two chatty subscriptions would bypass it. So the answer to requirement two must be the hub path rather than a direct peering, even though a direct peering would be simpler.

Sanity check. Exactly one of the four requirements should have been met by the proposal as written. If you also counted the on-premises one, check whether gateway transit was actually enabled - being peered to a network that has a gateway is not the same as being allowed to use it.
