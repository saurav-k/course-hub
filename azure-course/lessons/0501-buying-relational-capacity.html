Relational capacity is bought as an abstraction, and the abstraction decides what you can share and pause

working 10 min Capability area databases, rows relational-managed and relational-serverless. · Azure SQL Database serverless tier

The one-minute version

  • Azure prices relational compute in capacity abstractions rather than in hardware: DTU and vCore for the SQL family, and instance classes for the community engines.
  • An elastic pool lets many databases draw from one budget, which is the answer whenever the peaks do not line up.
  • Hyperscale is an architecture rather than a bigger size: it grows a single database far beyond the ordinary ceiling and restores it quickly.
  • The serverless tier auto-scales between a minimum and maximum vCore setting and pauses to zero when idle - but only if nothing long-running is in the way.
  • Zone-redundant configuration spreads the engine's replicas across availability zones. It is a different mechanism from a read replica, and it answers a different failure.

The unit is an abstraction, not a machine

The reframing Azure does not sell you a database server with a stated core count and memory size. It sells a capacity abstraction baked into the service: DTU or vCore on Azure SQL Database, and request units on Cosmos DB two pages from here. The consequence is that capacity becomes a thing you can pool, scale and pause, because it was never tied to a machine in the first place.

Pausing to zero, and the condition that quietly forbids it

The community engines answer the same question differently. PostgreSQL Flexible Server and MySQL Flexible Server offer burstable instance classes rather than a true pause: the cost floor is lower but it is not zero, and there is no resume event to design around.

Redundancy is a separate knob from replication

Zone-redundant configuration and a read replica are not two grades of the same feature. Zone redundancy spreads the engine's own replicas across availability zones inside one region, so losing a zone is handled by the service. A read replica is a second, separately addressable database that serves reads, and across regions it promotes asynchronously. A design that lists only one of them has answered only one of two different failures - and the one it usually skips is the zone.

Both are configuration on a database you already have rather than a different product, which is why they are easy to leave until later and expensive to add under pressure. Lesson 0102 introduced the zone vocabulary, and module 14 takes the backup and failover mechanisms that sit above both.

Check yourself

Retrieval practice

Answer from memory before revealing.

Twelve small databases each peak at a different hour of the day. Which capacity shape fits, and why?
An elastic pool exists for exactly this load shape - many databases sharing one budget. Hyperscale answers a size question about one database, not a sharing question about many. Serverless is a plausible distractor and would work if each database were genuinely idle between peaks, but pooling is the documented answer for non-coincident peaks. Zone redundancy is a failure-domain mechanism and adds no capacity.
A plan claims a serverless database will cost nothing overnight. What must be checked before that claim is believed?
Auto-pause requires that no long-running feature is in the way, and replication is the documented example. The first option describes the auto-scaling floor, which is not the same as reaching zero. The second is true of serverless but does not decide whether pausing happens. The third mixes up two capacity shapes that answer different questions.
Which statement about zone-redundant configuration is correct?
Zone redundancy is about the placement of the engine's replicas across zones in a single region. The first option confuses two failure domains - a zone is not a region. The second describes a read replica, which is a separate database. The fourth invents a dependency between two independent settings.

Practice about 20 minutes, with paper

Practice 1working

A company runs an internal expenses tool on Azure SQL Database. It is used heavily between nine and eleven each morning and almost never otherwise, it replicates a small reference table to a reporting database continuously, and the finance team says a slow first page load in the morning would generate complaints. Someone proposes moving it to the serverless tier and, separately, adding a cross-region read replica so that "the database is covered".

Take the proposal apart: say what the serverless tier will and will not do here, what the read replica does and does not cover, and what you would configure instead.

Hint

Check the serverless proposal against the two states in the lifecycle diagram separately - auto-scaling and auto-pause are not the same promise. Then ask which failure domain the read replica covers, and which one nobody has mentioned yet.

Show the worked solution
  1. Test auto-scaling. A workload that is heavy for two hours and quiet for twenty-two is exactly what auto-scaling between a minimum and maximum vCore setting is for, so this half of the proposal is sound.
  2. Test auto-pause. Continuous replication of the reference table is a long-running feature, and auto-pause requires that none is in the way. The database will therefore never reach the paused state and the overnight saving in the proposal does not exist.
  3. Test the cold-start claim against the requirement. Even if the replication were removed to unblock pausing, the pause flushes the warm cache and the first user of the morning pays for refilling it - which is precisely the complaint the finance team named in advance.
  4. Ask what the read replica covers. A cross-region replica answers regional loss, at the price of asynchronous promotion. It does nothing about losing a single availability zone, and nothing has been said about zones at all.
  5. State the configuration you would choose. Serverless for the auto-scaling, with the expectation of a non-zero floor rather than a pause, and zone-redundant configuration so a lost zone is handled inside the region. Keep the cross-region replica only if regional loss is genuinely in scope, and record that its promotion is asynchronous.

Sanity check. Exactly one half of the serverless proposal should have survived, and your final design should name two redundancy mechanisms rather than one. If the word "zone" appears nowhere in your answer, the failure domain the proposal skipped is still skipped.
