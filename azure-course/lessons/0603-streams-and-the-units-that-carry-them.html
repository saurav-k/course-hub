Ingesting a stream and processing one are separate purchases

working 11 min Capability area analytics, rows stream-ingest and stream-analytics. · Azure Event Hubs

The one-minute version

  • Azure Event Hubs is the high-throughput ingestion side. It is bought in throughput units on Standard and processing units on Premium and Dedicated.
  • It exposes a Kafka protocol endpoint, so an existing Kafka application repoints at the bootstrap endpoint with minimal changes rather than being rewritten.
  • Capture archives the raw events to Blob Storage or Data Lake Storage automatically, which turns the stream into lake files without a pipeline.
  • Azure Stream Analytics is the processing side: a SQL subset with windowing, reference joins and anomaly-detection functions, running in the cloud or on IoT Edge.
  • Both sit in the superseded-but-supported position for greenfield work on the Fabric surface, where Real-Time Intelligence is where Microsoft points new designs.

The two halves, and what each one meters

The reframing The Kafka endpoint is not a migration tool, it is a protocol surface. An existing Kafka producer or consumer repoints at the Event Hubs bootstrap endpoint and keeps its client library, its serialisation and most of its configuration. That makes "move to Event Hubs" a connection-string change for the application tier and a real design decision only for the operations around it.

What a windowed query is doing

Around that core, the processing service adds reference joins, which bring a slow-changing lookup alongside the fast stream, and anomaly-detection functions, which are available in the query language rather than requiring a separate model. It also runs on IoT Edge as well as in the cloud, so the same query shape can be pushed out to where the devices are.

Event Hubs is one of three services whose names people swap. It is the high-volume stream ingester; Event Grid is a discrete-event push router; Service Bus is the enterprise broker with queues and topics. Module 12 works the distinction properly. The short discriminator is who pulls, and whether the message rate is a design constraint - if the rate is the reason the service exists, it is Event Hubs.

Retrieval practice

Answer from memory before revealing.

A stream must land in the lake as raw events, with no transformation. What is the least machinery that achieves it?
Capture is a property of the ingestion service and writes raw events to Blob or Data Lake Storage automatically. The first and third options both work and both add a service, a meter and a failure mode that Capture removes. The fourth confuses the on-premises reach mechanism from the previous lesson with an archival one.
What does the Kafka protocol endpoint change for an existing Kafka application?
A protocol surface means the client stays and the endpoint changes. The first option is the rewrite the endpoint exists to avoid. The second invents a re-encoding requirement. The third confuses the ingestion half with the processing half, which is the whole point of the split on this page.
Why does a query over a stream need a window at all?
Without a bound there is nothing to aggregate over and no moment at which to emit. The second and fourth options attach the window to features that sit beside it rather than depend on it. The third confuses the query construct with the purchasing unit on the other half of the design.

Practice about 20 minutes, with paper

Practice 1working

A logistics company already runs a Kafka topic on its own hardware, fed by vehicle telematics. It wants three things in Azure: a per-minute count of events by depot on a live dashboard, the raw events kept for two years for later investigation, and an alert when a vehicle's readings look abnormal. A proposal suggests one Stream Analytics job reading from Kafka directly, writing to a dashboard, to a storage account, and to an alerting webhook.

Take the proposal apart: say which half of the design is missing, which of the three outputs should not be produced by the processing job, and what changes for the existing Kafka producers.

Hint

Draw the two halves before judging the proposal, and ask for each of the three requirements which half it belongs to. One of the three does not belong to either half in the way the proposal assumes.

Show the worked solution
  1. Find the missing half. The proposal names a processing service and no ingestion service. Something has to receive the events at volume before anything can query them, and that is Event Hubs with its throughput or processing units.
  2. Sort the per-minute count. This is a windowed aggregate over the stream, which is exactly what the processing half exists for. It stays with Stream Analytics.
  3. Sort the two-year raw archive. This is not a processing requirement at all. Routing it through the query engine makes the archive depend on the job running, and adds a meter for work that does nothing to the data. Event Hubs Capture writes the raw events to storage on its own, so the archive belongs to the ingestion half.
  4. Sort the anomaly alert. Anomaly-detection functions are available in the query language, so this one does stay with the processing job and does not need a separate model or service.
  5. Work out what the producers do. They keep their Kafka client and repoint at the Event Hubs bootstrap endpoint. The change is a connection configuration rather than a rewrite, which is the reason this migration is affordable at all.
  6. State the corrected shape. Producers to Event Hubs over the Kafka endpoint, Capture writing raw events into the lake for the two-year requirement, and one Stream Analytics job producing the per-minute counts and the anomaly alerts.

Sanity check. After the correction, the archive should survive the processing job being stopped. If stopping the job would still interrupt the two-year record, the archive is still hanging off the wrong half of the design.
