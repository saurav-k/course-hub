A private endpoint is only private once DNS agrees

working 12 min Capability area networking-core row private-endpoint, with private-dns from dns-domains. · Azure Private Link

The one-minute version

  • A private endpoint is a network interface with a private address in your subnet, pointed at one subresource of a platform service - or at your own service behind a Standard load balancer.
  • It needs DNS to answer the service's own name with that private address, which is what the privatelink private DNS zones exist for. Without them the name still resolves publicly and nothing is private.
  • Traffic is single-direction: you reach the service, the service cannot call you.
  • Azure DNS Private Resolver replaces hand-built forwarder machines: an outbound endpoint with rule sets sends on-premises suffixes to on-premises resolvers, and an inbound endpoint lets on-premises resolve Azure private zones.
  • Traffic at the endpoint is invisible to flow logs. Capture it at the source interface instead, or the evidence is simply not there.

What actually happens when the name is resolved

The reframing Granularity is the subresource, not the service. A storage account serving blobs and files needs one endpoint per subresource, each with its own private DNS record, exactly as lesson 0400 said. A design that provisions one endpoint and calls the account private has made half of it private, and the half that is still public looks identical from the application.

The rest of the endpoint's own behaviour

The older mechanism, service endpoints, is still there and still appropriate where a private address of your own is not what you need. The architect's default on Azure is the pair - a private endpoint plus a private DNS zone - and a design choosing the older mechanism should be able to say why the private address is unnecessary.

Names that have to cross the boundary

Flow logs do not record traffic inbound at the private endpoint's interface. If you need evidence that a workload used the private path, capture it at the source interface, because there is nothing to read at the destination. A control that is audited by looking for endpoint traffic in flow logs will report an absence and be believed.

Retrieval practice

Answer from memory before revealing.

A private endpoint is created, but the private DNS zone is never linked to the network. What happens?
The name resolves publicly as it always did, so nothing breaks and the private path is unused. The first and fourth options both assume a visible failure, which is exactly what does not happen. The third invents an interception behaviour - the endpoint is an address, not a proxy for the public one.
Which statement about a private endpoint's traffic direction is correct?
Initiation is single-direction by design, which is a large part of the security argument for Private Link. The first two options treat approval or routing as what unlocks a reverse path. The third has the direction backwards.
An on-premises client cannot resolve a privatelink name over an established tunnel. What supplies the answer?
The inbound endpoint is the direction that lets on-premises resolvers reach Azure private zones. The second option is the opposite direction - it sends Azure queries out to on-premises. The third misplaces a resource that only exists inside a virtual network. The fourth would publish internal addresses publicly and defeat the purpose.

Practice about 20 minutes, with paper

Practice 1working

A compliance rule says no workload data may traverse the public internet. An estate has a storage account serving blobs and files, a database, and an on-premises batch job that reads from all three over an existing tunnel. The team creates one private endpoint per service, links the privatelink zones to the workload network, and reports the rule as satisfied. An auditor then asks for evidence and is shown flow logs with no traffic at the endpoints.

Assess it: name the two configuration defects, say what the auditor was actually looking at, and say what evidence you would produce instead.

Hint

Count the subresources before you count the services. Then ask which network the on-premises job's resolver consults, and whether that resolver has ever heard of a privatelink zone.

Show the worked solution
  1. Count the endpoints needed. The storage account serves two subresources, blobs and files, and granularity is per subresource. Three services therefore need at least four endpoints, and the team created three.
  2. Name the first defect. One of the storage subresources has no endpoint, so the workload reaching it resolves the public name publicly and uses the public path. Nothing fails, which is why nobody noticed.
  3. Follow the on-premises job. It resolves names using on-premises resolvers, which know nothing about the privatelink zones linked to the Azure network. So it resolves the public names and takes the public path for all three services.
  4. Name the second defect. The estate needs a Private Resolver inbound endpoint so that on-premises resolvers can resolve the Azure private zones. Linking a zone to a virtual network does nothing for a client outside that network.
  5. Read the auditor's evidence correctly. Flow logs do not record traffic inbound at a private endpoint interface, so an empty result there is expected whether the private path is used or not. It is not evidence of anything, and treating it as evidence of failure would be as wrong as treating it as evidence of success.
  6. Produce evidence that exists. Capture at the source interfaces, where flow records do exist, and show the connections going to private addresses. Pair that with the configuration itself - the endpoint per subresource, the zone links, and the resolver rule sets - since the control is a configuration claim as much as a traffic claim.

Sanity check. Your endpoint count should be at least four rather than three, and your evidence should come from the source side rather than the destination side. If your answer produced destination-side evidence, it is describing a stream that does not exist.
