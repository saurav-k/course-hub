Two mechanisms remove the secret, one inside Azure and one outside

working 12 min Capability area identity-workload, rows workload-identity, workload-identity-federation, cross-account-assumption and short-lived-credentials. · Managed identities

The one-minute version

  • A managed identity is an Entra service principal whose credential Microsoft holds and rotates. Code fetches a token from the local instance metadata service, and no secret exists anywhere for you to leak.
  • User-assigned is the recommended type: it is a resource in its own right, survives the workload, and is shared. System-assigned dies with its parent.
  • Outside Azure, workload identity federation trusts an external issuer. A federated credential carries issuer, subject and audience, and the match is case-sensitive end to end.
  • There is no assume-role primitive. Cross-tenant work is a multi-tenant application consented into the other tenant, or Azure Lighthouse delegation.
  • The lifetime to design around is not seventy-five minutes. Where continuous access evaluation applies, a token's life may extend to twenty-four to twenty-eight hours, traded for near-real-time revocation.

Three details decide whether this works, and all three fail quietly. The match on subject and audience is case-sensitive end to end, so a capitalisation difference between a repository name and the credential is a rejection with nothing obviously wrong. Only the first hundred signing keys from an issuer's key set are cached, so an unusual identity provider with a larger ring breaks intermittently. And Entra-issued tokens are not accepted as federated input in general - the one carve-out is the documented managed-identity path, where a workload on Azure compute holding a user-assigned managed identity exchanges it for an application registration's token.

Practice about 20 minutes, with paper

Practice 1working

A team runs a deployment pipeline in GitHub Actions, a batch job on a virtual machine in Azure, and a data job on a Kubernetes cluster hosted on another cloud. All three currently authenticate with a client secret stored in the pipeline's own secret store, and all three use the same application registration. The team also has a contract to manage a customer's subscription in the customer's own tenant, and does it today by holding a user account in that tenant.

Redesign it: remove every secret you can, say which mechanism each workload uses, and say what replaces the account in the customer's tenant.

Hint

Ask for each workload whether it runs inside Azure's boundary or outside it. That single question chooses the mechanism. Then treat the shared application registration as a separate problem from the secret.

Show the worked solution
  1. Sort the three workloads by boundary. The virtual machine is inside Azure. The GitHub Actions pipeline and the foreign Kubernetes cluster are outside it. That is the whole basis of the mechanism choice.
  2. Fix the virtual machine. Give it a user-assigned managed identity. Tokens come from the local metadata service and no secret exists, and because the identity is a resource of its own the role assignments survive a rebuild of the machine.
  3. Fix the pipeline. Configure a federated credential with the pipeline provider as the issuer, and a subject naming the specific repository and branch. Check the case of every value, because the match is case-sensitive and a mismatch presents as an unexplained refusal.
  4. Fix the foreign cluster. Same mechanism, different issuer: the cluster's own OpenID Connect issuer, with a subject bound to the service account the job runs as. Federation is not specific to one provider, which is why the same shape covers both external cases.
  5. Split the shared registration. One registration for three workloads means one compromise reaches all three, and it also means the subject values cannot be tight. Give each workload its own identity or registration, and remember that a managed identity used as a federated credential holder supports at most twenty of them.
  6. Replace the customer-tenant account. A user account in somebody else's tenant is a standing human credential with no clear audit story. Azure Lighthouse delegates the named subscriptions or resource groups into the managing tenant instead, with cross-tenant activity visible. Alternatively a multi-tenant application registration is consented in the customer's tenant and receives role assignments there.
  7. State what remains. No client secret anywhere, three distinct workload identities, and a delegation relationship rather than an account. What is left to review periodically is the set of delegations and the subject values on each federated credential.

Sanity check. Your redesign should use two different mechanisms rather than one, split by the Azure boundary. If federation covered all three workloads, the machine inside Azure is doing more work than it needs to - the metadata service is already there.
