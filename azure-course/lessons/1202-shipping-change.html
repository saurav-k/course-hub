The pipeline holds no secret, and the rollback is a gesture rather than a deployment

working 11 min Capability area iac-deployment, rows cicd-pipeline, artifact-registry and progressive-delivery. · Deployment slots

The one-minute version

  • Both first-party pipeline products reach Azure through workload identity federation, so neither stores a credential for the estate.
  • Azure Artifacts is the package feed, with upstream sources caching public registries; container images live in the registry from lesson 0302.
  • Three progressive-delivery rails exist natively: a slot swap, weighted revisions, and weight overrides at the global edge.
  • A swap switches routing rules between slots - it is not an address flip - and the instances swapped out are recycled, abandoning anything long-running they were holding.
  • Slots also route by percentage, so weighted release is not a reason to change hosting tier on its own.

A pipeline that holds nothing worth stealing

Around the deployment sits the ordinary machinery: self-hosted agents where a build must run inside your own network, and environments with approvals where a human has to see the preview from lesson 1201 before an apply. Packages come from Azure Artifacts, whose upstream sources aggregate and cache public registries behind one feed with its own permissions - which is what makes a build reproducible when a public package disappears.

Three rails, three rollback gestures

The reframing A swap is a switch of routing rules between two slots, not a change of address. The consequence is that both slots keep existing and the one that was in production becomes the staging slot, which is what makes swapping back instant. It also means anything that identified the deployment by address is unaffected, because no address moved.

What a swap does that surprises people

Guardrails ride this same pipeline. Lesson 0901's policy-as-code repository is deployed by the machinery on this page, with the same review and the same approval gates - and its audit-then-deny ramp is the policy equivalent of a weighted release. An organisation that builds a careful delivery system for applications and applies governance by hand in a portal has built the mechanism and then declined to use it where it matters most.

Check yourself

Retrieval practice

Answer from memory before revealing.

What actually happens during a slot swap?
A swap switches routing between two slots that both continue to exist, which is what makes swapping back instant. The first describes an address flip. The second describes a redeployment. The fourth deletes the thing you would roll back to.
A workload holds long-running operations. What must be planned before swapping?
The instances that leave production are recycled and abandon what they were holding. The second inverts warm-up, which happens before traffic. The third and fourth invent behaviours - sticky settings do not block a swap and capacity is not lost by it.
A team wants percentage-based canary releases and proposes moving from an application service to a container service for it. What should be pointed out?
Percentage routing is available on slots as well as on revisions, so weighting is not a reason to move. The first denies a documented capability. The third is wrong - revisions take weighted percentages. The fourth invents a product requirement.

Practice about 15 minutes, with paper

Practice 1working

A team ships a web application from a pipeline that authenticates using a client secret stored in the pipeline's secret store, deploys straight over production, and rolls back by redeploying the previous build - which takes about twenty minutes. The application processes uploads that can take several minutes each. They want faster rollback, no stored credential, and a way to expose a release to a small share of users first.

Redesign it: name the change for each requirement, and say what the upload behaviour forces them to add.

Hint

Take the three requirements in order and name a mechanism for each. Then read the upload detail against what happens to instances that leave production.

Show the worked solution
  1. Remove the stored credential. Configure workload identity federation for the pipeline, with a subject naming the repository and the branch or environment. Nothing is stored, and the pipeline's access is decided by role assignments as usual.
  2. Check the case. Matching is case-sensitive end to end, so verify every value in the federated credential against what the pipeline actually presents - a mismatch here fails with nothing obviously wrong.
  3. Make rollback cheap. Deploy to a staging slot, warm it up, and swap. Rollback becomes a swap back rather than a twenty-minute rebuild, because both slots still exist.
  4. Expose the release gradually. Slots route by percentage, so a small share of traffic can go to the new slot before the swap. No change of hosting model is required for this.
  5. Read the upload behaviour. The instances that leave production on a swap are recycled, and anything they were holding is abandoned. An upload taking several minutes is exactly that kind of work.
  6. Add what that forces. A drain step: stop accepting new uploads on the outgoing instances and let in-flight work complete before swapping, or make the work resumable so an abandoned attempt is retried rather than lost. Without one of the two, the faster rollback comes with a new failure mode.
  7. Check the sticky settings. Settings marked as belonging to the slot stay behind on a swap. Confirm which are marked before the first swap rather than discovering it when production picks up a staging connection string, or fails to.

Sanity check. Your redesign should make rollback a configuration change and should add exactly one behaviour that was not asked for. If the upload handling was not mentioned, the swap has quietly introduced a way to lose work.
