One set of files, three engines, and the difference is what you provision

working 10 min Capability area analytics, rows serverless-query-engine, data-warehouse and managed-spark. · Synapse serverless SQL pool

The one-minute version

  • Files in the lake are not owned by an engine. The same Parquet, CSV, JSON and Delta files can be read by three different engines without being moved.
  • A serverless SQL pool runs T-SQL over those files with no cluster to provision, and is billed per terabyte of data processed.
  • It can publish views that reporting tools query as if they were tables, which is how a lake becomes reachable from a tool that only understands SQL.
  • The provisioned warehouse is the other SQL answer: capacity you hold, and therefore a cost that does not follow the query.
  • Spark is the third engine, and it forks the same way the module does: Azure Databricks is a first-party Microsoft-operated service, and the Fabric Spark runtime is the bundled alternative.

Three engines over the same files

How a query with no cluster actually reaches a file

The reframing The serverless engine has a twin on the other surface. The Fabric SQL analytics endpoint is the same capability inside Fabric, so "T-SQL directly over lake files" is a capability of the platform rather than of one product. The provisioned engine, meanwhile, is the warehouse row from lesson 0600 - which means the serverless-against-provisioned choice and the Azure-against-Fabric choice are two separate decisions that are easy to collapse into one by accident.

Spark, and a naming trap worth defusing

A serverless engine has no idle cost and a provisioned one does, which makes serverless look unconditionally cheaper. It is not: the meter counts bytes processed, so a dashboard that refreshes constantly over wide files can cost more than held capacity would have. The comparison is between a per-query meter and a held rate, and it is decided by query volume and file layout rather than by which word sounds cheaper.

Practice about 15 minutes, with paper

Practice 1working

A finance team has one dashboard. It refreshes every five minutes during working hours, reads six columns out of a wide event table stored as one large uncompressed CSV file per day, and is currently served by a serverless SQL pool because "serverless has no idle cost". The bill has grown steadily and nobody has changed the dashboard.

Diagnose it: say what the meter is actually counting here, name the two changes that would reduce the bill without changing the engine, and say under what condition you would change the engine instead.

Hint

Write down what a query has to read to answer six columns out of a CSV file, then write down what it would have to read out of a columnar file. Then multiply by the refresh count rather than looking at one query.

Show the worked solution
  1. Name the meter. The serverless engine bills by data processed, so the cost of the dashboard is the bytes each refresh reads, multiplied by the number of refreshes. Nothing about the dashboard changing is required for the bill to grow - the files growing is enough.
  2. Work out what one refresh reads. The file is one large uncompressed CSV, so a query asking for six columns still has to read every column of every row it touches. There is nothing in that layout for the engine to skip on, so the bytes processed are the whole file.
  3. Apply the first change. Store the table as Parquet, which the engine reads natively. A columnar layout lets a reader take only the columns a query names, so the same query processes a fraction of the bytes and the meter falls with it.
  4. Apply the second change. Lay the files out so that a query for a recent window can skip the rest, rather than presenting one large undifferentiated file per day, so the dashboard stops paying to touch history it never displays.
  5. Label what is Azure and what is not. The two facts this course sources are that the engine reads these formats and that it bills by data processed. That a columnar layout lets a reader skip columns is a general property of file formats rather than an Azure claim, and it is flagged here so the reader can tell the two apart.
  6. Count the refreshes. Refreshing every five minutes through a working day is on the order of a hundred refreshes daily, so any per-query saving is multiplied a hundredfold - and so is any per-query waste.
  7. State the condition for changing the engine. If the refresh rate is high enough that the per-query meter, even on well-laid-out Parquet, exceeds a held capacity rate, the provisioned warehouse becomes the cheaper shape. That is a volume argument, and it should be made with the new file layout in place rather than against the old one.

Sanity check. Both of your no-engine-change fixes should be about what the query is allowed to skip, not about how fast the engine is. If either one is a tuning change to the query itself, look again - the meter here counts bytes, and the query already asks for only six columns.
