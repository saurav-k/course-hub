The state question splits the field before any syntax does

working 11 min Capability area iac-deployment, rows native-iac-template, terraform-provider, iac-in-code-sdk, config-management and kubernetes-config-management. · Bicep

The one-minute version

  • Bicep and ARM templates keep no state file. Resource Manager already knows what exists, so there is nothing to store, lock or leak.
  • Bicep transpiles to ARM JSON, which is why it supports every API version from the day it appears rather than waiting for anything to be released.
  • The Terraform provider is mature and widely used and keeps its own state file, commonly in a storage account with lease-based locking.
  • Azure ships no first-party development kit for infrastructure in a general-purpose language; the third-party ecosystems fill that space.
  • Two extensions of the same idea: machine configuration reaches inside a guest, and the service operator lets a Kubernetes control plane reconcile Azure resources.

Four options, and the fork that separates them

The reframing Bicep is not a wrapper you wait for. It compiles to the template language Resource Manager already accepts, so a resource type or property published today is expressible today. That is a structural property of transpilation rather than a promise about release cadence, and it is the single most useful thing to know when comparing it with anything that ships as a provider.

Why one path lags and the other does not

Two places the same idea is extended

Two things on this page are third-party rather than vendor-published, and this course labels them at the point of use rather than blending them in. The in-code ecosystems are third-party products; Azure publishes no first-party kit of that shape. And the service operator, although Microsoft-published, is open source installed into your own cluster rather than a managed service - so its support and upgrade model is yours, and each resource it exposes carries its own API version generated from the platform specifications.

Why does the native path need no state file?

Practice about 15 minutes, with paper

Practice 1working

An organisation has three years of ARM templates in JSON, a platform team fluent in Terraform, and a requirement to adopt new Azure services quickly - a recent one was blocked for weeks waiting for tooling support. It also needs to enforce a set of in-guest settings across virtual machines, including machines running in its own data centre. Somebody proposes rewriting everything by hand in the newer language.

Advise them: say what to do with the existing templates, how to decide between the two main paths, and how the in-guest requirement is met.

Hint

Take the three requirements separately. One is about migration cost, one is about the release path to a new API version, and one is not an infrastructure-language question at all.

Show the worked solution
  1. Deal with the existing templates. A hand rewrite is unnecessary: the newer language ships a decompiler that converts existing JSON. That turns a rewrite project into a conversion followed by review and tidying.
  2. Name what the blocked adoption was. Waiting weeks for tooling support is the provider release path. The transpiled path reaches a new API version the day it exists, and the bridging provider is the escape hatch on the other path.
  3. Weigh the team's fluency honestly. Terraform is mature and widely used, and a fluent team is a real asset. The decision is between that fluency plus a release-cycle dependency and a state file, or the native path with neither.
  4. State the state-file consequence. If they stay on Terraform, the state file is an object to place, lock and protect - commonly a storage account with lease-based locking - and it becomes part of the security and recovery design.
  5. Propose a shape rather than a winner. Given the specific complaint they raised, the native path removes the cause of it. A defensible middle is to convert the existing JSON and use the native path for anything that needs new API versions, while the team's existing Terraform estate continues where it is working.
  6. Answer the in-guest requirement. Not with either language. Machine configuration audits and enforces files, registry values, packages and scripts inside a guest, assigned through policy - and it reaches machines projected into Resource Manager from the data centre, which is what makes the on-premises half possible at all.

Sanity check. Your answer should reject the hand rewrite and should answer the third requirement with something that is not an infrastructure language. If the in-guest settings ended up in a template, they are describing a machine's resource properties rather than what is inside it.
