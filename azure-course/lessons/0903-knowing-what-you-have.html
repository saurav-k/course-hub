One query language answers what exists, and the labels that make it useful do not inherit

working 11 min Capability area governance-policy rows resource-graph-query and config-drift-assessment, with resource-tagging and quota-management. · Azure Resource Graph

The one-minute version

  • Azure Resource Graph queries resource properties across subscriptions and tenants in KQL. It is throttled but cheap, and it is the fastest inventory surface on the platform.
  • It is not a reporting sideshow: it backs portal search, network-manager dynamic groups and fleet placement, so estate queries and platform behaviour share one engine.
  • Change detection has two halves. Control-plane change history shows property diffs around an event, and in-guest change tracking needs the agent.
  • Tags do not inherit from a resource group to the resources inside it. Enforce them with a policy modify effect, or inherit them only for cost reporting.
  • Quotas are per region and per family, adjustable through a support request or the quota interface, and they are a capacity ceiling rather than a governance rule.

The inventory surface, and what else runs on it

It is also part of a larger pattern worth naming once: one query language reaches inventory, change history, platform logs and analytics alike. Lesson 0503 met the engine family behind it, and module 10 uses the same language against telemetry. Learning KQL is therefore a platform-wide investment rather than a per-service one.

Two kinds of change, two mechanisms

The reframing Tags do not inherit. A tag on a resource group is on the resource group, and the resources inside it carry nothing. Two mechanisms close the gap and they are not equivalent: the modify policy effect from lesson 0900 actually writes the tag onto the resource, while cost management inheritance applies the parent's tag in reporting views only. The first changes the estate and the second changes a report - and a design that wanted the first and configured the second will find the tag missing everywhere except the invoice view.

The rest of the tagging picture

Quotas are a ceiling, not a rule

Quotas are set per region and per family, and they are raised through a support request or the quota interface rather than by a policy. They are worth separating from governance because they fail differently: a policy denies a deployment for a reason you wrote, and a quota denies it because a number in a region was reached. A few of the platform's structural limits are worth carrying directionally - 800 resource-type instances per resource group with many exemptions, five diagnostic settings per resource, 200 policy assignments per scope, and 10,000 management groups per directory - because each one has ended a design that assumed otherwise. The vendor's limits article is the live authority for all of them.

Check yourself

Retrieval practice

Answer from memory before revealing.

A cost-centre tag is set on every resource group and the resources show no tag. Why?
There is no inheritance to propagate - a tag lives on the object it was applied to. The first option imagines a timing issue. The third invents a reserved-key behaviour. The fourth invents a setting that does not exist, though cost management does offer inheritance for reporting views.
Somebody asks which file changed on a virtual machine last Tuesday, and no agent was installed. What can you tell them?
Nothing inside a machine reaches the control plane on its own, so without the agent there is no record to retrieve. The first three all assume the control-plane mechanisms see inside a guest, which is precisely the boundary this page draws.
Which statement about Resource Graph is correct?
Several platform behaviours run on the graph, which is what makes it more than a reporting tool. The second and fourth understate it - it queries across subscriptions and tenants and is not a daily export. The third overstates it: operation history belongs to the control-plane record.

Practice about 15 minutes, with paper

Practice 1working

A finance team wants every Azure cost attributed to one of twelve cost centres. The platform team applies a cost-centre tag to every resource group, switches on cost management tag inheritance, and reports the work complete. Three months later, finance reports that about a tenth of the spend is unattributed and that a policy intended to target one cost centre's resources is missing some of them.

Diagnose it: explain both symptoms, say what should have been done instead, and name what remains unsolvable however the tagging is done.

Hint

The two symptoms have different causes. Ask what inheritance in a reporting view actually writes, and separately ask whether every resource type can hold a tag at all.

Show the worked solution
  1. Explain the policy symptom. Cost management inheritance applies the parent's tag in reporting views. It does not write the tag onto the resource, so anything that reads the resource - including a policy targeting on the tag - still sees no tag. The policy is not broken; the tag is not there.
  2. Explain the first part of the cost symptom. If any spend is being attributed at all, the inheritance view is doing its job for the resources whose resource group carries the tag. So the unattributed tenth is coming from somewhere the parent tag does not reach.
  3. Find the second cause. Some resource types do not support tags. Those resources cannot carry a cost centre by any means, so a share of the spend is unattributable by tag no matter how well the standard is applied.
  4. Say what should have been done. A policy assignment using the modify effect, writing the cost-centre tag onto resources at creation and remediating existing ones. That makes the tag real, which fixes the policy-targeting symptom and removes the dependence on a reporting-only view.
  5. Handle what remains. For untaggable types, attribution has to come from structure rather than metadata - which resource group or subscription the resource is in - so the standard needs a documented rule for that residue rather than pretending it does not exist.
  6. Add the check. A Resource Graph query listing resources without the tag, run regularly, turns "about a tenth" into a specific list that can be worked through.

Sanity check. Your diagnosis should have two distinct causes, and only one of them should be fixable by changing the tagging mechanism. If both symptoms came out with the same cause, the untaggable types have not been accounted for.
