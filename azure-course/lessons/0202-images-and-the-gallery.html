Azure versions and replicates the image, and expresses the launch template as something other than a resource

working 9 min Capability area compute-iaas, row vm-images, and the instance-template row Azure answers differently. · Azure Compute Gallery

The one-minute version

  • Azure Compute Gallery is the managed home for your own images. It gives them versions and replicates those versions to the regions you name.
  • It holds both generalised and specialised images, and it is the successor to unmanaged images and to the older "shared image gallery" branding.
  • The replication list is a real design decision: a scale-out deployment in a region reads the image version from that region, so an unreplicated region is a deployment that has further to reach.
  • Azure ships no standalone reusable instance-template resource. The scale-set model is the desired-state definition, and Bicep or ARM modules stamp out individual machines.
  • Because there is no template object, scheduled scaling lives in the autoscale profile rather than in the launch specification - a difference that changes where you go looking.

What the gallery actually holds

Two kinds of image live in a definition: generalised and specialised. Which of the two you publish changes how the version is consumed, and the Compute Gallery documentation is the authority for how each is prepared and when to reach for it - this page names the fork rather than restating the vendor's procedure for it.

The naming history here trips people who search for documentation. The gallery is the successor to unmanaged images and to the older shared image gallery branding, so a page, a script or a colleague's memory using either older name is describing the same product line at an earlier point. Treat "shared image gallery" as the old name of the thing you are configuring, not as a different feature you have not enabled.

The launch template that is not a resource

This is a genuine structural difference rather than a missing feature, and reading it as an absence produces a search that never terminates. There is nothing to create, so the question "where is our launch template" has to be re-asked as "which scale set carries this model" or "which module stamps this machine".

The other half: state that is enforced rather than baked

Check yourself

Retrieval practice

Answer from memory before revealing.

A team asks where to find the reusable launch template their new scale set should use. What is the right answer?
Azure has no standalone instance-template resource, and the scale-set model plays that role. The first option invents a gallery level that does not exist. The second and third describe places a newcomer looks precisely because they expect a template object to be somewhere.
Why does the replication list on an image version matter to a multi-region deployment?
Replication puts a copy of the version in each target region so a scale-out deployment there reads it locally. The first option invents a restriction on generalised images. The third invents an expiry. The fourth confuses replication with versioning, which are two separate things the gallery does.
A long-lived machine drifts from its baseline weeks after it was deployed from a gallery image. What addresses the drift?
Baking decides what a machine starts as, and Machine Configuration is what audits and enforces it afterwards. The first two options are real gallery operations that change future deployments and leave the running machine untouched. The fourth changes how the image is consumed, not whether a live machine has drifted.

Practice about 15 minutes, with paper

Practice 1working

An estate runs one application in three regions. Its hardened base image is published once, and deployments in all three regions have been slow and occasionally fail during a rollout. The team also cannot find where to configure a nightly scale-down, and a compliance auditor has asked how they prove a running machine still matches its baseline.

Answer all three: what to change about the image, where the schedule actually lives, and what produces the compliance evidence.

Hint

Each of the three has a different home. One is a property of the image version, one is a property of the autoscale profile, and one is a different service entirely.

Show the worked solution
  1. Fix the image. Add all three regions to the image version's replication list. A deployment reads the version from its own region, so the two unreplicated regions are reaching further than they need to on every rollout.
  2. Keep the versioning discipline. Because the gallery versions images, the rollback story is "deploy the previous version", which only works if the previous version is still replicated to the same regions. Replication is per version, so a rollback plan has to include it.
  3. Find the schedule. There is no launch template to hold it. Scheduled scaling lives in the Azure Monitor autoscale profile attached to the scale set, which is why searching the machine or image configuration for it finds nothing.
  4. Produce the evidence. Machine Configuration audits in-guest state against an assigned configuration and reports drift, and can enforce it. That report, not the image version, is what answers the auditor - the image only proves what the machine started as.

Sanity check. Your three answers should name three different places: an image version property, an autoscale profile, and a separate governance service. If two of them landed in the same place, one of the three questions has been folded into another.
