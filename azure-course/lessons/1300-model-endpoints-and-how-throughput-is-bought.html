A model endpoint is an ordinary Azure resource with an unusual meter

working 11 min Capability area ai-ml, row managed-model-api, with ai-safety-guardrails beside it. · Microsoft Foundry Models

The one-minute version

  • The hosted model service serves frontier and open models from one catalogue, so the choice of model is a configuration rather than a different product.
  • Throughput is bought two ways: provisioned units that reserve capacity and smooth latency, or tokens billed as they are consumed.
  • Everything else is the platform vocabulary you already have: role assignments decide who may call it, and a managed virtual network gives it private connectivity.
  • Content filtering is wired in as the default, with configurable severity thresholds per harm category rather than a single switch.
  • Prompt Shields covers direct and indirect prompt injection, which is a category of attack that has no equivalent anywhere else in this course.

What the endpoint is made of

The reframing The model is a configuration, not a product boundary. One catalogue serves several model families through one service, so changing models is a deployment change rather than a migration to a different service with different identity, networking and telemetry. That is what makes an evaluation across models practical, and it is the single biggest structural difference from wiring up a model provider directly.

Two guards, and only one of them is familiar

Severity thresholds are configurable per harm category rather than being a single sensitivity dial, which is what lets an application that legitimately handles difficult subject matter stay usable. There is an interactive studio for testing those thresholds against real content before they reach production - the same rehearse-before-enforce habit as lesson 0901's audit mode and lesson 1100's detection mode.

Everything else is a decision you have already made

Reserved throughput is a commitment in the sense of lesson 0904: capacity is held and paid for whether or not it is used, and the discount is only realised by the traffic that actually lands on it. A design that provisions units for a workload whose demand is spiky is buying predictability it does not need, and one that runs a steady high-volume workload on token billing is paying burst rates for a load that never bursts.

Practice about 15 minutes, with paper

Practice 1working

A company is deploying an internal assistant that summarises documents users upload. Requirements: several teams share one endpoint with per-team rate limits; no traffic to the endpoint may cross the public internet; the workloads calling it must hold no credential; usage must be attributable per team; and demand is expected to be low and spiky for six months while teams experiment. A proposal buys reserved throughput units, gives each team a key, and exposes the endpoint directly.

Take it apart: correct each of the three decisions, and name the attack this application is specifically exposed to.

Hint

Three of the requirements have been answered in earlier modules; work out which module each belongs to. Then read the last requirement against the purchasing fork, and read the application's actual behaviour against the guards.

Show the worked solution
  1. Correct the purchasing decision. Demand is low and spiky for six months, which is the case token billing exists for. Reserved units hold capacity that is paid for whether it is used or not, so the proposal commits to a steady load the workload does not have.
  2. Correct the credential decision. Keys for each team are exactly what lesson 0803 removes. The calling workloads take managed identities, and role assignments decide who may call the endpoint - which also makes usage attributable to a principal rather than to whoever holds a key.
  3. Correct the exposure decision. Put the endpoint behind the gateway from lesson 1204, which is where per-team rate limits belong, and use the managed virtual network so the traffic does not traverse the public internet.
  4. Meet the attribution requirement properly. With identities rather than keys, calls are attributable in the identity sign-in records, and the gateway can additionally throttle and report per caller. The key-based design attributes nothing once a key is shared.
  5. Name the specific exposure. The application summarises documents that users upload, so the model is routinely given content the company did not write. That is the indirect prompt injection case precisely, and it is what prompt shields exist for.
  6. Set the thresholds deliberately. Severity is configurable per harm category, and the interactive studio exists to test those settings against real content before production - the same rehearse-before-enforce habit as an audit-mode policy or a detection-mode firewall.
  7. Revisit the purchasing decision later. If usage settles into a steady high volume after the experimental period, the reserved units become the right answer. That is a review date, not a decision to make now.

Sanity check. Three of your corrections should reference earlier modules rather than anything specific to models. If the indirect injection risk did not appear, re-read what the application actually feeds the model.
