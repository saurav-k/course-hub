Module 04 · Storage · Lesson 0403

Three services answer three different shared-file questions, and getting data in is arithmetic before it is a product

working 11 min Capability area storage, rows file-storage, hybrid-storage-gateway and bulk-transfer-appliance. · Azure Files

The one-minute version

  • Azure Files is the managed SMB and NFS share. Azure NetApp Files is the enterprise engine beside it. Azure File Sync is neither - it keeps a Windows file server you already own in step with a share.
  • A file share needs an identity story, and there are three: Entra Kerberos, an on-premises Active Directory domain, or Entra Domain Services.
  • Premium shares provision performance the way a disk does; transactional shares pay per operation. That is the same per-peak against per-use trade as the previous page.
  • File Sync's cloud tiering leaves a stub on the local server while the cold blocks live in the share, which is what makes an ageing file server finite again.
  • Moving bulk data in is decided by a division: size over sustained rate. Do it before choosing between the network and a shipped appliance.

Three services, three questions

Who is allowed to open the file

Two further properties of Azure Files echo decisions made earlier in this module. Premium shares provision performance the way a disk does, while transactional shares are billed per operation - the same per-peak against per-use question the previous page asked about disks and pools. And a share carries soft delete, with vaulted copies available through Azure Backup, so the protection stack from lesson 0401 is not blob-only.

The reframing Cloud tiering is what makes File Sync more than replication. The local server keeps a stub where a cold file used to be, and the blocks live in the share until something opens them. The server therefore stops growing without anyone deleting anything - which is why File Sync is usually adopted as a capacity answer and only later appreciated as a resilience one.

Getting bulk data in: do the division first

The offline path is the Azure Data Box family, from a Disk at 8 terabytes to a Heavy at around 800 terabytes usable, with hardware encryption, chain of custody and a wipe after upload. Where the transfer is continuous rather than a one-time move, Azure Storage Mover runs agent-based migrations of NFS and SMB sources into Azure Files and Blob Storage as projects and jobs, with the service holding the plan and the state while an appliance in your environment does the copying.

The division above assumes a link that is fully yours for the whole period. Real links carry other traffic, real transfers stop and restart, and a 741-day figure is not a schedule anyone will keep to. Treat the arithmetic as a lower bound, and if the lower bound is already unacceptable the product question has answered itself.

Check yourself

Retrieval practice

Answer from memory before revealing.

A Windows file server is out of disk space and the team wants to keep using it. Which service fits?
File Sync tiers cold blocks to a share and leaves a stub, so the existing server keeps serving and stops growing. The first and fourth are places to put data rather than ways to keep a server. The third moves data once and does nothing about the server continuing to fill up.
Which limit of Entra Domain Services should be known before choosing it for a file share?
The one-way synchronisation from Entra ID means the managed domain is not an extension of an on-premises forest, and its schema is not yours to change. The first contradicts what the service provides. The second invents a colocation rule. The third describes the very thing the managed domain removes.
A team must move 800 terabytes and has a one-gigabit link. What does the arithmetic say?
6,400 terabits divided by one gigabit per second is about 74 days, and that is the optimistic figure. The second option is the ten-gigabit answer, the third is off by a factor of twenty-four, and the fourth substitutes a pricing question for the feasibility one that has to be answered first.

Practice about 20 minutes, with paper

Practice 1working

A company is closing a data centre. It holds 300 terabytes on Windows file servers used by staff every day, joined to an on-premises Active Directory forest that is staying. The site has a 500 megabit per second internet link shared with everything else. The cutover window is six weeks.

Plan the move: do the arithmetic, choose the transfer path, choose the destination and its identity option, and say what happens to the file servers during the six weeks.

Hint

Do the division before anything else, and be honest that the link is shared. Then notice that the forest is staying, which decides the identity option, and that staff need the files throughout - which rules out a plan that stops serving them.

Show the worked solution
  1. Do the division. 300 terabytes is 2,400 terabits. At 0.5 gigabits per second fully sustained that is 4,800,000 seconds, which is about 56 days - already longer than the six-week window, and that figure assumes the link carries nothing else.
  2. Choose the transfer path. The lower bound has already failed, so the offline path is the answer: a Data Box sized for 300 terabytes, with hardware encryption, chain of custody and a wipe after upload.
  3. Choose the destination. Azure Files, because the workload is staff opening files over SMB and that is what a managed share is for. NetApp Files would be the answer if the requirement had named enterprise NAS behaviour or cross-region replication, and neither was stated.
  4. Choose the identity option. The on-premises forest is staying, so join the share to that existing Active Directory domain rather than to Entra Domain Services - the managed domain synchronises one way from Entra and would not extend the forest the staff accounts already live in.
  5. Keep serving during the window. Put Azure File Sync on the existing servers. Staff keep using the servers they know while the share becomes authoritative, cloud tiering keeps the local servers from filling, and the eventual data-centre closure removes a cache rather than a source.

Sanity check. Your plan should have staff working uninterrupted for the whole six weeks. If the plan has a weekend where nobody can open a file, the sync step was replaced by a copy - which is the difference between a migration and an outage.
