Three questions choose a relational engine, and one of them is about the network

working 10 min Capability area databases, rows relational-managed and sql-managed-instance. · Azure SQL Database

The one-minute version

  • Azure's relational catalogue answers three questions: which engine dialect, how much of that engine's surface you need, and where the engine sits on the network.
  • Azure SQL Database is the database as a managed object. Azure SQL Managed Instance is a near-complete SQL Server engine deployed inside your own virtual network.
  • For the community engines the deployment model is the whole answer: Flexible Server is the current shape for both PostgreSQL and MySQL, and Single Server is the trap.
  • Read replicas exist on the community engines within and across regions, and a cross-region replica promotes asynchronously, so promotion is not free of data loss.
  • There is no globally consistent relational engine on Azure. Global distribution and one strongly consistent SQL image are not offered together.

The three questions, in the order that matters

The reframing Azure SQL Managed Instance is not a bigger Azure SQL Database. It is the lift-and-shift target for the cases where the platform database's feature gaps block a migration outright: it carries SQL Agent, cross-database queries and CLR, and it is deployed inside your own virtual network rather than reached at a Microsoft-hosted endpoint. Where many small instances would each be wasteful, instance pools share capacity between them, and the Link feature keeps an instance in sync with SQL Server 2022 running on premises.

Where the engine sits, drawn twice

The community engines, where the deployment model is the answer

Azure Database for PostgreSQL and Azure Database for MySQL run the community engines rather than a Microsoft dialect of them, so the interesting choices are operational. Flexible Server offers tunable maintenance windows, zone-redundant high availability, and read replicas both inside a region and across regions. PostgreSQL adds PgBouncer for connection pooling, in-place major-version upgrades, and customer-managed keys.

A cross-region read replica promotes asynchronously. That makes it a real answer for regional failure and a poor answer for a recovery point objective of zero, because whatever had not replicated at the moment of promotion is gone. A design that writes "read replica in the paired region" under a zero-data-loss requirement has not met the requirement, and nothing in the platform will say so.

The shape that is genuinely missing

Azure has no globally consistent relational engine: no product offers one strongly consistent SQL image spread across regions. Azure Cosmos DB is globally distributed, but it offers a tunable consistency spectrum over a NoSQL model rather than a single relational image, and the next lesson but one is where that trade is worked properly. A design that needs both global writes and relational consistency is choosing which half to give up, not shopping for a service.

Check yourself

Retrieval practice

Answer from memory before revealing.

A migration is blocked because the application relies on SQL Agent jobs and cross-database queries. Which shape is the documented answer?
Managed Instance exists for exactly this case - the near-complete engine surface that the platform database does not offer. Hyperscale changes how large a single database can grow, not which engine features exist. An elastic pool shares capacity between databases and does not enable queries across them. Converting to a different dialect solves a problem nobody had.
What does choosing Managed Instance commit you to beyond the engine itself?
Managed Instance is deployed into a virtual network, so the subnet and its routing belong to the decision. The second option describes how Azure SQL Database is reached privately, which is the other shape on this page. The third and fourth invent commitments the service does not make.
A design promises zero data loss on regional failure and proposes a cross-region read replica of a Flexible Server. What is wrong?
The cross-region replica promotes asynchronously, which bounds recovery time but not data loss. The first option is false - replicas exist within and across regions. The second is false, since promotion is the documented path. The third invents a maintenance requirement that is not the mechanism at issue.

Practice about 20 minutes, with paper

Practice 1working

A retail platform is moving off a self-hosted estate. It has three relational workloads: a catalogue on PostgreSQL that is read far more than it is written and must serve two continents; an orders database on SQL Server that uses SQL Agent for nightly jobs; and a small reporting database on SQL Server with no unusual engine features. The team wants one product for all three, no public endpoints anywhere, and no data loss if a region is lost.

Take the design apart: say which of the three questions each workload answers differently, how many products you end up with, and which requirement cannot be met as written.

Hint

Work the three questions in order for each workload, and stop as soon as two workloads answer one of them differently. Then check the two blanket requirements - private only, and no data loss - against what each chosen product actually offers.

Show the worked solution
  1. Answer the dialect question three times. The catalogue is PostgreSQL, the other two are SQL Server. That alone forbids one product for all three, because the dialect question has no shared answer.
  2. Answer the surface question for the two SQL Server workloads. Orders needs SQL Agent, which puts it on Managed Instance. Reporting needs nothing unusual, so it belongs on Azure SQL Database, where the elastic pool and serverless options in the next lesson become available to it. Two answers, two products.
  3. Answer the placement question. Managed Instance arrives in a subnet of your virtual network. Azure SQL Database and PostgreSQL Flexible Server are reached privately through a private endpoint targeting the relevant subresource, each with a private DNS zone record. So the private-only requirement is met, but by two different mechanisms and with endpoints to provision.
  4. Test the two-continent requirement. A read-heavy catalogue is exactly what cross-region read replicas are for, so the reads are served locally on the second continent while writes stay with the primary.
  5. Test the zero-data-loss requirement. This is the one that fails. The cross-region replica promotes asynchronously, and there is no globally consistent relational engine on Azure to fall back to. Either the recovery point objective moves off zero, or global distribution is given up and the workload stays regional with zone redundancy.

Sanity check. Your product count should be three, not one, and exactly one requirement should have failed. If everything passed, the zero-data-loss line was not tested against asynchronous promotion - which is the same mistake the design started with.
