Azure Functions declares what a function is wired to, so the plumbing is configuration rather than code

working 9 min Capability area serverless-app, row functions-faas. · Azure Functions

The one-minute version

  • A function has one trigger that starts it, and any number of bindings that hand it inputs and take its outputs. Both are declared, not written.
  • Triggers span HTTP, queues, timers and more than sixty event sources, which is why the timer trigger is one of the answers to Azure's missing standalone scheduler.
  • The hosting plan is the real design decision. It decides scale to zero, per-instance concurrency, private networking and whether instances are kept warm.
  • Durable Functions is the extension that adds stateful orchestration, so a long multi-step process does not have to become a chain of queues you maintain.
  • The trap is treating the plans as price tiers of one product. They differ in capability, and a virtual-network requirement rules some of them out before cost is discussed.

Trigger and binding, rather than event and handler

The hosting plan is the design decision

PlanWhat it gives
ConsumptionScale to zero: no instances and no charge when nothing is happening.
Flex ConsumptionPer-instance concurrency control, and virtual-network integration.
PremiumPre-warmed instances, and virtual-network integration.
DedicatedRuns on an App Service plan, alongside web applications on the same plan.
The reframing These are not four prices for one thing. Read the column as capabilities and most designs pick themselves: a function that must reach a private endpoint needs a plan with virtual-network integration, and a function whose first request must not wait needs pre-warmed instances. Cost is what you optimise after those two questions have been answered.

State, without a queue you maintain

Durable Functions sits beside Logic Apps in Azure's workflow story, and module 12 takes the pair apart properly. The reason it appears here is that the choice between "a function" and "a workflow" is usually made while writing the function, not later.

A timer-triggered function is one of the three places Azure's scheduling capability lives, along with Logic Apps recurrence and Automation schedules. There is no standalone scheduler service, so a design that says "we will add the cron service later" never finds one. Decide which of the three owns your schedules at the same time as you decide anything else about them.

Check yourself

Retrieval practice

Answer from memory before revealing.

A function must read from a database reachable only over a private endpoint. What does that settle first?
Virtual-network integration is a property of the hosting plan, so the requirement rules plans in or out before anything else is chosen. The first and second options attach the network capability to the runtime and the trigger, neither of which decides it. The third confuses a networking feature of the plan with regional availability.
What is the difference between a trigger and an output binding?
One trigger starts a function; bindings carry data in and out and are declared rather than written. The first option reverses the two. The third denies that both are declarative, which is the model's whole point. The fourth turns both into scheduling mechanisms.
A five-step business process needs to survive hours between steps. What does Durable Functions change about building it?
The orchestrator remembers where it is, so the bookkeeping stops being yours. The first overstates it into removing queues rather than removing the state table. The second names a hosting plan, which is a separate decision. The fourth confuses it with the other half of Azure's workflow story.

Practice about 15 minutes, with paper

Practice 1working

Four small workloads are proposed as functions: a public webhook receiver that must answer within a fraction of a second at any hour; a nightly reconciliation that reads a database over a private endpoint; a queue worker that is busy for two hours a day and idle otherwise; and a six-step refund process with human approval in the middle.

For each, name the hosting plan property that decides it, and say which one should not be a plain function at all.

Hint

Three of the four are settled by one property of the plan each: warm instances, network integration, or falling to zero. The fourth is settled by what has to be remembered between steps.

Show the worked solution
  1. The webhook receiver. "At any hour, within a fraction of a second" is a requirement about the first request after a quiet period, so the deciding property is pre-warmed instances, which the Premium plan provides. Consumption would meet the throughput and not the promise.
  2. The nightly reconciliation. A private endpoint is only reachable from a plan with virtual-network integration, which rules the plan list down to Flex Consumption, Premium or Dedicated before cost enters the conversation.
  3. The queue worker. Busy for two hours and idle for twenty-two is the case scale to zero exists for, so Consumption - unless it also needs a private path, at which point it joins the second workload's shortlist.
  4. The refund process. Human approval in the middle means the process waits for an unbounded time and must remember where it was. That is Durable Functions, an orchestrator with activities, rather than a plain function - or Logic Apps if the approval step is better expressed as a workflow.
  5. Say what is shared. Nothing forces these onto one plan, but functions sharing a plan share its properties, so grouping them is a decision about the strictest requirement in the group.

Sanity check. Each of the first three should be decided by a different plan property. If two of them landed on the same reason, re-read what the requirement actually promised - throughput, reachability and idleness are three different constraints.
