An untested recovery claim is an estimate wearing a number

working 10 min Capability area resilience-migration, rows resilience-assessment and well-architected-framework. · Azure Chaos Studio

The one-minute version

  • Chaos Studio injects faults deliberately - shutting a machine down, adding network latency, breaking name resolution - so a claim becomes an observation.
  • Faults come in two forms: agent-based, which needs an agent inside the machine, and service-direct, which the platform injects itself.
  • Experiment guards and role-scoped targeting are what keep an experiment from becoming an incident, and they are part of the design rather than a precaution.
  • The Business Continuity Center is the estate-wide view of protection posture and readiness across backup and recovery.
  • The Well-Architected Framework supplies the five-pillar review, with an assessment that produces a scored remediation list rather than a report.

Injecting a failure on purpose

The reframing Fault injection tests the response as much as the system. Breaking name resolution deliberately tells you whether the alert fired, whether it reached anybody, whether the runbook was correct and whether the dashboards showed the cause - all of which are module 10's material being exercised. A design that passes the technical half and fails the human half has learned the more useful thing.

Two views above the individual test

The continuity product is newer than most of what this course covers, and the research behind these pages notes that its feature set should be confirmed on the vendor's own page before it is cited in a design. That caution is the same discipline lesson 0103 established: state the lifecycle position rather than assuming today's shape is permanent.

An experiment is only as informative as the telemetry underneath it. If the failure being injected is one of the blind spots from lesson 1004 - resolution of a public name, traffic at a private endpoint, an outbound translation - then the experiment will produce a symptom with no record explaining it. Check that the stream exists before injecting the fault, or the result is a lesson about your telemetry rather than about your resilience.

Check yourself

Retrieval practice

Answer from memory before revealing.

What is the difference between an agent-based and a service-direct fault?
Where the fault is injected from is the distinction, and it decides how much preparation an experiment needs. The first invents a scope split. The third would make one family unsafe by design. The fourth invents an environment restriction.
What bounds which resources an experiment can affect?
Targeting is scoped by role assignments, so the existing access model does the bounding. The other three invent limits that would each be either too coarse or too easy to get wrong.
What does the framework assessment produce?
A scored remediation plan is the output, and being a backlog is what makes it usable. The second describes the continuity view. The third describes a test failover. The fourth describes the compliance dashboard from lesson 0901.

Practice about 15 minutes, with paper

Practice 1working

A team is asked to prove three resilience claims about a workload spread across availability zones: that losing one zone does not interrupt service; that a dependency becoming slow degrades the application rather than failing it; and that the on-call rota notices within five minutes. The workload's machines have the monitoring agent installed. Somebody proposes testing all three at once during a quiet weekend.

Plan the tests: choose a fault type for each claim, say what to check before running any of them, and say what is wrong with testing all three at once.

Hint

Two of the three claims are about the system and one is about the people. Then ask, for each fault, whether the telemetry that would show the result actually exists.

Show the worked solution
  1. The zone claim. Shutting machines down is a service-direct fault, so it needs nothing inside the guest. Target the machines in one zone, scoped by role so the experiment cannot reach the others, and observe whether service continues.
  2. The slow-dependency claim. Adding network latency is also service-direct. This one tests a behaviour the application must have been written for, so a failure here is a design finding rather than a configuration one.
  3. The five-minute claim. This is not a system property at all. It is tested by running one of the first two faults and measuring how long it takes for the alert to fire, reach somebody and be acknowledged - which is module 10's alerting and action groups being exercised.
  4. Check the telemetry first. Before injecting anything, confirm that the streams that would show each symptom exist and are being collected. If a fault produces a symptom in one of lesson 1004's blind spots, the experiment teaches you about your telemetry instead.
  5. Check the agent question. The machines have the monitoring agent, which is not the same thing as the fault agent. Only agent-based faults need that second one, and neither of the two chosen faults does - so nothing extra is needed here, but the distinction is worth verifying rather than assuming.
  6. Set the guards. Each experiment needs a condition that stops it, so a test that starts behaving unexpectedly ends itself rather than being ended by an incident commander.
  7. Reject the combined test. Running all three at once means a failure cannot be attributed to a cause: if the service degrades, was it the lost zone, the latency, or their interaction? Run them separately, with the response measurement attached to whichever one runs first, and combine faults only once each is understood alone.

Sanity check. Both of your faults should be service-direct, and one of your three claims should be measured rather than injected. If all three were framed as system tests, the human claim has not actually been tested.
