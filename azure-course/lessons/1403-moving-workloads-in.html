Module 14 · Resilience and migration · Lesson 1403

A migration is an assessment before it is a move

working 11 min Capability area resilience-migration, rows migration-service and online-transfer, with db-migration-service from databases. · Azure Migrate

The one-minute version

  • Azure Migrate is a hub: it discovers servers, databases and web applications, sizes the targets they would need, and drives the move.
  • Its dependency analysis is agentless and maps how the estate actually talks to itself, which is what decides what has to move together.
  • Three different services carry the payload: the hub for servers, the database migration service for data tiers, and Storage Mover for file shares.
  • Database migration runs online or offline, and the online mode is where change data capture lives - as lesson 0602 said, that capability has no product of its own.
  • Bulk seeding by appliance from lesson 0403 remains the answer when the data is too large to move over a network in the time available.

Discovery decides the plan

The reframing Sizing is a recommendation, not a decision. The hub proposes targets from what it observed running, which means it sizes for the estate as it is rather than as it should be - including years of over-provisioning. Take the recommendation as a starting point and then apply the capacity thinking from modules 02 and 05: an under-used machine moved at its observed size is an over-provisioned machine with a cloud bill attached.

Three payloads, three services

Two alternatives for the same file job are worth naming, because they are frequently the right answer: the command-line copy tool for a scripted move, and the pipelines from lesson 0602 where the copy is part of a wider data flow. The managed service earns its place when the move is large, repeated, or has to be reported on.

Cutting over a database without stopping it

A migration's target design is where this course's earlier absences arrive all at once. There is no globally consistent relational engine from lesson 0500, no permission boundary from lesson 0801, no network-sharing construct from lesson 0702, and no per-query log for public name resolution from lesson 1004. An estate arriving with requirements built on any of those has a design conversation ahead of it, and discovering that during a cutover weekend is the worst possible time.

Check yourself

Retrieval practice

Answer from memory before revealing.

What does dependency analysis contribute to a migration plan?
The dependency map is what turns a server list into applications and decides what moves together. The first is sizing, a separate output. The second describes online database migration. The fourth describes the file-move service's logs.
Why does an online database migration shorten the outage?
Continuous change capture keeps the target close to the source, so only the cutover is an outage. The second confuses availability with throughput. The third describes dual writes, which is a different pattern. The fourth invents a sizing behaviour.
How should a sizing recommendation from discovery be treated?
It reflects the estate as it is, including any over-provisioning, so it is where the sizing conversation starts. The first accepts existing waste. The second and third both convert an observation into a bound it does not support.

Practice about 20 minutes, with paper

Practice 1working

A company is moving a data centre. It holds forty virtualised servers, one large database that must not be down for more than a few minutes, and eighty terabytes of file shares. The team has a spreadsheet listing which servers belong to which application, plans to size the targets from the current specifications, and intends to copy the file shares over the existing internet connection during the migration weekend.

Plan it: name the service for each payload, say what to do about the spreadsheet and the sizing, and say what is wrong with the file plan.

Hint

Take the three payloads first, then question the two things the team believes it already knows, then do the arithmetic on the file copy against the time available.

Show the worked solution
  1. Place the servers. Azure Migrate, using agentless migration for the virtualised estate, with discovery first.
  2. Place the database. The database migration service in online mode, so the target is kept current and the outage is the cutover rather than the copy. A few minutes of downtime rules the offline mode out entirely at this size.
  3. Place the file shares. Storage Mover, organised as projects and jobs with per-job copy logs, with an appliance registered in the environment doing the copying. The logs are what will answer "did everything arrive" afterwards.
  4. Distrust the spreadsheet. Run agentless dependency analysis and compare it with the spreadsheet. The map is what decides the waves, and the difference between the two is the list of surprises this migration would otherwise have found at the weekend.
  5. Distrust the sizing. Sizing from current specifications carries every over-provisioned machine across unchanged. Take the discovery recommendation, which is based on observed usage, and then apply the capacity thinking from modules 02 and 05 rather than either number as given.
  6. Reject the file plan. Eighty terabytes over an ordinary internet connection in a weekend is not a schedule, it is an assumption. Lesson 0403's division applies: past a certain size, bulk data travels by appliance rather than by network, and the seed is done in advance with only the changes copied at the end.
  7. Sequence it. Discovery and dependency analysis, then waves planned from the map, then the bulk file seed shipped ahead of time, then the database replicating online during the preceding weeks, and only then a cutover weekend whose only long-running task is the final delta.

Sanity check. Your plan should question two things the team already believed and should move the largest payload off the migration weekend entirely. If eighty terabytes is still crossing the network on the Saturday, the transfer arithmetic has not been done.
