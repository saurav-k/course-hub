Module 04 · Storage · Lesson 0400

The storage account is where the decisions live, and some of them are made once at creation

working 11 min Capability area storage, row object-storage, with data-lake beside it. · Azure Blob Storage

The one-minute version

  • A storage account is the object that carries redundancy, the namespace shape, the keys and the network posture. Individual blobs carry far less than people expect.
  • The namespace is flat unless the hierarchical namespace is enabled, and that is a choice made when the account is created rather than later.
  • The hierarchical form is Data Lake Storage Gen2: the same storage with directory semantics and POSIX-style access control lists tied to Entra identities.
  • Access has four shapes, and only one of them is both short-lived and identity-backed: a user-delegation shared access signature, signed by Entra credentials.
  • Private access is granular in a way that surprises people. A private endpoint targets one subresource, so blob and file need separate endpoints.

What is decided where

The account type matters as a prerequisite too. Blob Storage features described in this module require General Purpose v2 accounts, and private endpoints for the blob subresource are General Purpose v2 only. An older account is not a smaller account; it is an account several features simply do not apply to.

Flat by default, hierarchical by decision

The reframing A blob container's namespace is flat. What looks like a folder is a prefix in the blob's name. Turning on the hierarchical namespace makes directories real, which is what Data Lake Storage Gen2 is: the same storage with directory semantics and POSIX-style access control lists that resolve against Entra identities. It is enabled per account at creation, so a lake workload discovered later is a new account and a copy, not a setting.

Four ways in, and only one of them ages well

Private access to storage is per subresource, not per account. A private endpoint targets the blob subresource, or the file subresource, and so on - so an account serving both needs two endpoints and two private DNS zone records. A design that provisions one endpoint and declares the account private has made half of it private and left the other half reachable exactly as before.

What the object store does not offer

Two shapes that exist elsewhere have honest answers here rather than products. There is no single-zone high-performance object class: premium block blob accounts are solid-state backed with single-digit millisecond first-byte latency and per-transaction pricing, but they remain regionally redundant, so they do not make the trade of giving up cross-zone redundancy to buy latency. And Azure Storage itself has no table-aware container type: Delta tables with managed maintenance live in OneLake and the Fabric lakehouse, while storage holds table files as ordinary objects.

Check yourself

Retrieval practice

Answer from memory before revealing.

A team discovers six months in that its analytics workload needs directory semantics and POSIX-style access control lists. What does that cost them?
The hierarchical namespace is enabled per storage account at creation, so it is not a switch you flip afterwards. The first option invents container-level granularity. The second and third describe real account settings that have nothing to do with the namespace shape.
Which access shape is both short-lived and traceable to a person or workload identity?
A user-delegation signature is signed with a key obtained from Entra, so it has a short expiry and an identity behind it. The first inherits the account key's long life and anonymity. The third rotates a credential without making it identity-backed. The fourth is a real mechanism for managing signature validity, but it does not by itself supply an identity.
An account serves both blobs and file shares. One private endpoint has been created for it. What is the state of the account?
A private endpoint targets one subresource, so a single endpoint covers blob or file and not both. The second and fourth options both assume account-level granularity. The third invents a pairing requirement, which would at least fail loudly - the real behaviour fails quietly, which is why it matters.

Practice about 20 minutes, with paper

Practice 1working

A design proposes one storage account for a whole product: application uploads, an analytics lake, and a file share for a legacy Windows component. The account is to be locally redundant, private, and accessed by a single account key stored in a secrets manager and shared by all three consumers.

Take the design apart: say which requirements conflict at the account level, how many accounts and private endpoints you would end up with, and what replaces the shared key.

Hint

List the four account-level decisions first, then check each of the three workloads against them. The conflicts appear wherever two workloads want different answers to the same account-level question.

Show the worked solution
  1. Test the namespace shape. The lake needs the hierarchical namespace with its directory semantics and access control lists; the upload store does not, and the shape is an account-level choice made at creation. That is the first hard split: at least two accounts.
  2. Test the redundancy. Locally redundant storage survives hardware failure inside one location. Whether that is acceptable differs by workload - application uploads are usually the least replaceable data in the list - and redundancy is again an account-level setting, so a workload needing more is a further split rather than a per-container option.
  3. Count the private endpoints. Endpoints target one subresource each. The blob subresource on each account needs one, and the file share needs one for the file subresource, so the count is per account and per subresource - never one for the product.
  4. Replace the shared key. A single account key shared by three consumers gives all three full power over everything and traces back to nobody. Replace it with Entra principals holding role assignments for the direct callers, and user-delegation shared access signatures where a signature genuinely has to be handed to something that cannot hold an identity.
  5. State the resulting shape. Two or three accounts split by namespace shape and redundancy need, one private endpoint per subresource in use on each, and no long-lived key in the design at all.

Sanity check. Your endpoint count should be larger than your account count, because at least one account serves two subresources. If they are equal, the file share's endpoint has been forgotten - which is the same mistake the design started with.
