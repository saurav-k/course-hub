An Azure virtual machine is an assembly, and the interesting parts are the resources bolted to it

working 10 min Capability area compute-iaas, rows vm-instances and gpu-compute. · Azure Virtual Machines

The one-minute version

  • The machine resource itself is thin. The network interface, the disks and the image are separate resources with their own lifetimes, and most of the design lives in them.
  • A size is a name from a catalogue, and the family letter carries the ratio: B for burstable, D for general, E for memory, F for compute, L for storage.
  • The network interface is the debugging unit. It owns the addresses, the security-group attachment and the accelerated-networking switch, and it is where the effective-rules view is rendered.
  • Graphics and accelerator work is the N-series, and it is usually consumed through a higher service rather than as a standalone machine.
  • You should not need a public address to sign in. Bastion brokers the session and Entra login authorises the operating-system sign-in itself.

The assembly

Reading a size name

Family letterWhat the ratio is tuned for
BBurstable: cheap baseline with credit-driven bursts
DGeneral purpose: the default balance
EMemory optimised
FCompute optimised
LStorage optimised
NGPU: NC for accelerated compute, ND for multi-GPU training, NV for visualisation

Alongside the family letter a size carries a generation, which is why the catalogue is full of names such as Dav5 and Ev5. The Virtual Machines documentation is the live authority for what every letter in a size name means, and it is worth reading rather than guessing, because the suffix letters encode processor vendor and feature options that change between generations.

A size existing in a region does not mean it can be placed anywhere in that region. Some sizes are zonal-only in newer regions, so a design that pins machines to zones can meet a size that is available in the region and not in the zone you wanted. Check the size against the zone, not only against the region, before committing a placement.

The interface is where the network truth lives

Every machine attaches through one or more network interfaces, and the interface is the object that carries the interesting switches. It owns the IP configurations, including any public address association. It is one of the two places a network security group can attach - the other being the subnet, and both can apply at once. It carries the accelerated-networking switch, which offloads the datapath through single-root input-output virtualisation, and the IP-forwarding flag that lets the machine act as a network appliance.

It is also the debugging unit. The effective security rules view renders per interface, which is why a "why can we not reach this machine" session starts at the interface rather than at the machine.

The reframing When both a subnet security group and an interface security group exist, both must allow the traffic. Inbound is evaluated subnet first then interface, and outbound is evaluated interface first then subnet. Microsoft's own advice is to pick one layer, and the reason is exactly this: two layers double the places an answer can hide.

Getting in without a public address

The third leg of the same idea is the machine's outbound identity. A managed identity lets code on the machine fetch tokens from the local instance metadata service with no secret stored anywhere. Module 08 works it through properly; the point here is that a well-built machine has no inbound public address, no local account and no outbound secret.

Check yourself

Retrieval practice

Answer from memory before revealing.

Traffic to a machine is being dropped. A security group is attached to the subnet and another to the machine's interface. What is true?
Both attachments can exist at once and inbound traffic is evaluated at the subnet then the interface, so both must allow it. The first two options each describe a replacement that does not happen, and picking either is what leads to hours spent reading the wrong rule set. The fourth invents a cancellation.
Which pairing of mechanism and question is correct?
Bastion answers how the session reaches a machine without a public address, and Entra login answers who may sign in to the operating system. The second and third options swap the two jobs, and the fourth attributes to both of them work that belongs to managed identity and to the network interface.
A design pins machines to availability zone 2 in a new region, using a size confirmed available in that region. What still has to be checked?
Some sizes are zonal-only in newer regions, so regional availability does not settle zonal availability. The first option names a real interface property that has nothing to do with placement. The second invents an identity quota. The third confuses zones with regions - image replication is a regional concern, covered in lesson 0202.

Practice about 15 minutes, with paper

Practice 1working

An operations team asks for "one Linux jump box with a public address, a local opsadmin account whose key is in a password manager, and a stored service-principal secret so scripts on it can call Azure".

Rewrite the request using the three mechanisms on this page, and say what each replacement removes.

Hint

There are three separate credentials or exposures in the request. Deal with them one at a time: the inbound path, the operating-system account, and the outbound secret.

Show the worked solution
  1. Remove the public address. Put Azure Bastion in front of the machine. The session reaches the machine over the private network, so the machine needs no public address at all, and the session is recorded in Bastion's own diagnostics.
  2. Remove the local account. Enable Entra login for virtual machines. Sign-in is then authorised by two roles - Virtual Machine Administrator Login and Virtual Machine User Login - and the Linux path uses a short-lived OpenSSH certificate rather than a stored key. Conditional Access, including multifactor authentication, now applies to the sign-in itself.
  3. Remove the outbound secret. Assign a managed identity to the machine. Code fetches tokens from the local instance metadata service, so there is no service-principal secret to store, rotate or leak.
  4. State what is left. One machine with no inbound public address, no local credential and no stored outbound secret - and three audit trails instead of none: Bastion session diagnostics, Entra sign-in logs, and the Activity Log for what the identity did.

Sanity check. Count the secrets in your rewritten design. If the answer is not zero, one of the three mechanisms has been left out - and if you added a key vault to hold the jump box's key, you replaced a stored secret with a better-stored secret rather than removing it.
