Module 11 · Security services · Lesson 1103

The security information system is a workspace, which makes every telemetry decision a security decision

working 11 min Capability area security-services, row threat-detection, with the recorded absence security-investigation-graph. · Microsoft Sentinel

The one-minute version

  • Microsoft Sentinel runs on a Log Analytics workspace. It is not a separate store, so the plans, retention and volume levers from lesson 1002 apply to it directly.
  • Its billing follows the workspace meters and adds its own, which is why the documented advice is to keep operational and security data in separate workspaces.
  • It adds behaviour analytics, watchlists and incident fusion - correlating separate signals into one incident rather than a stream of alerts.
  • There is no separate investigation-graph product: the graph and the entity pages live inside this service.
  • Response is automation rules and playbooks, and a playbook is a Logic App - so lesson 1200's integration vocabulary is the vocabulary of security response too.

One store, two products, two meters

The reframing There is no separate investigation-graph service. The graph that shows how an incident's entities relate, and the entity pages behind it, are features of this product rather than a product of their own. That matters when a design goes looking for a name to put in a diagram: the answer is the security information system, and the graph is what you get by using it.

From alerts to an incident

Its correlation extends beyond Azure: the wider security portal brings signals from other Microsoft security products together, and the workload-protection alerts from lesson 1102 land as security records in the workspace and correlate there. The estate connectors from that page mean other clouds appear in the same picture.

Every blind spot from lesson 1004 becomes a detection gap here. There is no per-query log for public name resolution, so a detection about resolved names needs a resolver on the path. Traffic at a private endpoint is not recorded there, so a detection about who reached a database needs source-side capture. And resource logs are documented as lossy, so a detection that must never miss an event should be fed from a durable path rather than from those logs alone.

Check yourself

Retrieval practice

Answer from memory before revealing.

Why does the documented advice suggest separate workspaces for operations and security?
Enabling the product applies its meters to the workspace's contents, so shared workspaces pay the security rate for operational data. The first is a real consideration but not the documented reason. The second is false. The fourth invents a contention effect.
What does incident fusion do?
Fusion turns related signals into a single incident, which is what makes a queue workable. The second describes deduplication. The third and fourth attach the word to billing and to querying, neither of which is what it means here.
A detection must alert on every occurrence of an event, with no misses. What should feed it?
The vendor documents that small losses may occur, so a no-miss requirement needs the durable path from lesson 1000. The first denies the documented behaviour. The second attributes completeness to enrichment. The third names a place where flow records are not collected at all.

Practice about 15 minutes, with paper

Practice 1working

A security team is standing up detection for the first time. They plan to enable the security product on the existing operational workspace, write rules against the streams already collected there, and respond manually. Their first three detection ideas are: a workload resolving an unexpected external name; an unapproved source connecting to a database reached through a private endpoint; and a role assignment being created at a management group.

Review the plan: say what is wrong with the workspace decision, assess each detection idea against the streams that exist, and say what to add for response.

Hint

Take the workspace decision first, because it is the expensive one. Then check each detection idea against lesson 1004's blind spots before checking it against a rule.

Show the worked solution
  1. Assess the workspace decision. Enabling the product on the operational workspace applies the security meters to all the operational telemetry in it. That is the documented reason to separate them, and the exception - a combined volume qualifying for a better commitment tier - is arithmetic they should do rather than assume.
  2. Assess the name-resolution detection. There is no per-query log for public zones, so no rule can be written against a stream that does not exist. Making this detection possible means putting a firewall proxy or the private resolver on the resolution path - an architecture change, as lesson 1004 established.
  3. Assess the private-endpoint detection. Traffic at the endpoint is not recorded there, so a rule looking for endpoint-side records finds nothing and reports nothing. Capture at the source interfaces instead, and write the rule against those records.
  4. Assess the role-assignment detection. This one works today. Control-plane operations are recorded by default, they include the caller, and they are exported into a workspace for free. It is the only one of the three that needs no new collection.
  5. Note the latency. That stream is documented at three to twenty minutes end to end, so the detection is a minutes-class one however often the rule is evaluated. Say so rather than promising near-real-time.
  6. Add the response mechanism. Automation rules trigger on incident creation or update, and playbooks are Logic Apps, so the response can be built from the integration primitives the organisation already has - notify, ticket, or act.
  7. Add the reference data. Two of the three ideas depend on knowing what is expected - which names, which sources. Watchlists are where that reference data lives, and without it the rules are either noisy or silent.

Sanity check. Exactly one of the three detections should be writable today, and one of the other two should need an architecture change rather than a configuration change. If all three looked writable, the blind spots from lesson 1004 have not been applied.
