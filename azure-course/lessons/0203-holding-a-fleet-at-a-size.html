A scale set is two products wearing one name, and the orchestration mode is the choice that decides which one you get

working 9 min Capability area compute-scaling, row autoscaling-group, with batch-compute beside it. · Virtual Machine Scale Sets

The one-minute version

  • A scale set holds a homogeneous group of load-balanced machines at a size, replacing members that fail.
  • It has two orchestration modes, and they are not two tiers of one thing. Uniform is the classic form; Flexible mixes sizes, spreads across availability zones and works with ordinary machine features.
  • Autoscale, including scheduled and predictive scaling, is documented against Uniform mode - so the mode choice reaches further than it first appears.
  • Replacement is driven by the Application Health extension: the fleet acts on what the application reports, not only on whether the machine is powered on.
  • When the work is a queue of jobs rather than a service to keep up, Azure Batch is the shape, and it can draw on Spot capacity with its own autoscale formulas.

The mode is the product choice

The model that members are stamped from lives inside the scale set, because Azure has no separate template resource - the previous page located it. Two consequences follow. Scheduled scaling is configured in the autoscale profile beside the set rather than in a launch specification. And changing what members look like is an edit to the set itself, which is why a scale set is often the smallest unit an infrastructure-as-code module manages.

Replacement is driven by what the application says

This is also what makes Spot capacity usable. Spot machines are available for scale sets and for Kubernetes node pools, and an eviction inside a fleet is a member disappearing - which the fleet already knows how to handle. The same eviction on a hand-placed single machine is an outage, so the discount belongs to the fleet, not to the individual machine.

When a fleet is the wrong shape

Check yourself

Retrieval practice

Answer from memory before revealing.

A fleet holds ten machines at a size. Three of them are running but returning errors, and the count never changes. What is most likely missing?
Health-based replacement acts on what the application reports, and with no health extension a powered-on member serving errors looks healthy to the set. The second option describes scaling rather than replacement. The third is false - replacement is not a Flexible-only behaviour. The fourth would break deployments in a region, not leave running members unhealthy.
A design needs one fleet containing two different machine sizes, deliberately spread across availability zones. Which mode fits?
Mixing sizes and spreading across availability zones is what Flexible mode is for. The first two options attach Flexible's properties to Uniform, and the second also puts sizing in the autoscale profile, which holds scaling rules rather than the member model. The fourth denies a capability the product has.
Why is Spot capacity a better fit for a scale set than for a single machine?
A fleet already handles members disappearing, so an eviction is an event it knows how to absorb. The first option invents a billing model. The third is wrong because Spot is also available as a standalone machine - it is just a worse idea there. The fourth contradicts the fact that Spot carries no service level agreement anywhere.

Practice about 20 minutes, with paper

Practice 1working

A media company runs two workloads. The first is a public API that must stay available and whose traffic has a strong, repeatable daily shape. The second is a nightly transcode of the day's uploads: thousands of independent tasks that finish when the queue empties.

Choose the compute shape for each, name the orchestration mode where one applies, say where the daily shape is configured, and place the Spot discount where it belongs.

Hint

Ask of each workload whether it ends. Then, for whichever one is a fleet, ask which mode the scaling behaviour you need is documented against.

Show the worked solution
  1. Classify the two workloads. The API is a service that must stay up under varying load, so it is a scale set. The transcode is a finite queue of independent tasks that ends, so it is Azure Batch with pools, jobs and tasks.
  2. Pick the mode for the fleet. The repeatable daily shape is exactly what scheduled and predictive scaling are for, and Azure Monitor autoscale with those profiles is documented against Uniform mode. Choose Uniform unless something else in the design needs mixed sizes or an explicit zone spread, in which case the trade has to be made deliberately.
  3. Locate the daily shape. In the Azure Monitor autoscale profile beside the scale set. There is no launch template to hold it, so a search of the machine or image configuration finds nothing.
  4. Place the discount. Spot belongs on the Batch pools: the work is interruptible, the pool tears down at the end anyway, and Batch pools can use Spot capacity with autoscale formulas. Keep the public API off Spot, because Spot carries no service level agreement and availability is the API's whole requirement.
  5. Add the health signal. Put the Application Health extension on the fleet so the API's own health, not merely its power state, drives replacement.

Sanity check. Exactly one of the two workloads should end up on Spot, and it should be the one that ends. If the API ended up on Spot to save money, the design has traded the single requirement it was given.
