An App Service swap switches routing rules, and everything the old instances were still doing is abandoned

working 10 min Capability area serverless-app, rows paas-web-runtime and static-site-hosting. · Deployment slots

The one-minute version

  • App Service runs code or a container as a managed web application, with TLS, virtual-network integration and built-in authentication that fronts Entra and social providers.
  • A deployment slot is a second copy of the application that receives a build, warms up, and is then swapped into production.
  • The swap switches routing rules between the slots. It is not an address flip, and rollback is simply swapping back.
  • The cost nobody reads: the instances that were serving production recycle in staging afterwards, and any long-running operation they were holding is abandoned.
  • Slots also carry a traffic percentage per slot, so canary weighting is native here too - it is not a reason on its own to move to a container platform.

The three objects

What a swap actually does

Two beliefs about swaps are common and wrong. It is not a virtual-address flip, so reasoning about it as a DNS or load-balancer change predicts the wrong failure modes. And canary weighting is not a reason to leave App Service: slots carry a traffic percentage natively, so "we need weighted rollout" does not by itself justify moving an application onto a container platform.

The Git-driven half

The reframing One managed runtime in this family is on its way out. Azure Spring Apps is retiring, and Microsoft names Container Apps and AKS as the replacements, so new Java Spring work belongs on one of those two rather than on the managed Spring runtime. Which statement about the slot swap mechanism is accurate?
The swap exchanges routing rules between two slots, which is why rollback is the same gesture in reverse. The second describes the address-flip model that people assume and that predicts the wrong failure modes. The third describes a file copy, and the fourth a rename, neither of which would leave a slot to roll back into.

Slots support a per-slot traffic percentage, so weighted rollout is native and is not a reason to move. The first overstates what a mesh is needed for. The third invents a tier requirement. The fourth confuses per-pull-request preview environments with production traffic weighting.

Practice about 20 minutes, with paper

Practice 1working

A retail application runs on App Service with a staging slot. Releases are done by swapping. Two problems appear. First, a nightly report generator that runs inside the same application occasionally produces truncated output on release days. Second, a connection string that should differ between staging and production keeps travelling with the code, so staging writes to the production database after every swap.

Diagnose both from the swap's documented behaviour, and give the fix for each.

Hint

One problem is about what happens to the old instances after the routing rules switch. The other is about which settings are considered part of the slot rather than part of the deployment.

Show the worked solution
  1. Diagnose the truncated report. After a swap the instances that had been serving production recycle in the staging slot, and any long-running operation they hold is abandoned. A report generator running in-process on those instances is exactly such an operation, so a release during a report truncates it.
  2. Fix it by moving the work. Take the report out of the request-serving application. A timer-triggered function or a Container Apps job runs it on its own lifecycle, so a web release cannot interrupt it. Keeping it in-process and releasing only outside the report window is a schedule, not a fix.
  3. Diagnose the connection string. A setting travels with the code across a swap unless it is marked sticky to its slot. An unmarked connection string therefore follows the build into production and back, which is why staging ends up pointing at production data.
  4. Fix it with sticky settings. Mark the connection string as a slot setting so it stays with the slot rather than moving with the deployment. Then verify by swapping twice and confirming each slot still holds its own value.
  5. Note what the swap is not. Neither problem is caused by an address change, because no address changes - both follow from routing rules switching between two live slots.

Sanity check. Your two fixes should live in different places: one moves work out of the application, the other changes a setting's stickiness. If both came out as "release at a quieter time", neither root cause has been addressed.
