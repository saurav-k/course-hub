Module 05 · Databases · Lesson 0502

Cosmos DB prices work rather than hardware, which is why the partition key decides everything else

working 11 min Capability area databases, rows nosql-keyvalue and nosql-document. · Azure Cosmos DB

The one-minute version

  • Cosmos DB meters every operation in request units. Reads, writes and queries all draw from the same meter, so a query's shape is a cost as well as a latency.
  • The partition-key choice is the core design decision, and it is made in the data model rather than in a tier or a size.
  • Consistency is a spectrum from eventual to strong, selectable per request, so one application can pay for strength only where it needs it.
  • Throughput comes in three shapes: provisioned, autoscale billed against the maximum you set, and a serverless form for spiky small workloads.
  • Cosmos DB carries several API surfaces. The Table API gives Azure Tables semantics, while native Azure Tables stay inside a storage account - two different products with one vocabulary.

One meter, and everything draws from it

The reframing In a relational design the schema decides correctness and the tier decides capacity. In Cosmos DB the partition key does both. It is the field that decides how documents are grouped, therefore which requests can be served from one place, therefore how evenly the meter is spent. Microsoft names it the core design decision of the service, and it is chosen in the data model rather than in any setting you can revise from a portal blade later.

Consistency is a dial, and it is per request

Cosmos DB being globally distributed does not make it a globally consistent relational engine, and Azure ships no such engine. What is on offer is a tunable consistency spectrum over a NoSQL model, not one strongly consistent SQL image spread across regions. A requirement that says "global writes, relational guarantees" is a requirement to choose one of the two, and lesson 0500 is where the relational half of that trade was set out.

Several front doors on one service

The MongoDB compatibility story carries one caution the vendor states plainly: driver compatibility is full, but feature parity is not automatic, so an existing estate should be checked against the published parity matrix before it is moved rather than after.

Check yourself

Retrieval practice

Answer from memory before revealing.

Why does the request unit make a performance problem and a cost problem the same problem?
One currency covers every operation, so a query that scans more is more expensive in exactly the unit that measures how much work it did. The second option describes provisioning without explaining the shared unit. The third confuses a latency guarantee with the absence of a performance dimension. The fourth is the opposite of the mechanism.
Which statement about consistency in Cosmos DB is correct?
The spectrum runs from eventual to strong and the level is selectable per request. The first two options place the choice at the wrong object, which would remove the per-request cost decision entirely. The fourth is the specific mistake the page warns about - global distribution is not global relational consistency.
A team says its data is "in Azure Tables". What has to be established before designing against that?
One vocabulary covers two products - the Cosmos DB Table API and native Azure Tables inside a storage account - so the product must be established first. The other three are real questions, but each one only becomes answerable once you know which of the two products is being discussed.

Practice about 20 minutes, with paper

Practice 1working

A telemetry service stores one document per device reading in Cosmos DB. Almost every read is "give me the last hour of readings for one device". The team has proposed the calendar date as the partition key, because it is short and always present, and has set autoscale with a high maximum so that "throughput is never the constraint". They also plan to read at the strong end of the consistency spectrum everywhere, on the grounds that correctness matters.

Take the design apart: say what the partition key does to the dominant read, what the autoscale setting actually commits them to, and where the consistency choice is buying nothing.

Hint

Ask which field the dominant read filters on, then ask whether the proposed key groups documents the same way. Then look again at what autoscale is billed against, rather than what it scales to.

Show the worked solution
  1. Name the dominant access pattern. Every read is scoped to one device and a time window, so the field the reads filter on first is the device, not the date.
  2. Check the proposed key against it. Partitioning by date groups every device's readings for a day together, so a single-device read cannot be answered from one group and instead spends request units scanning across devices. The key has been chosen for its shape rather than for the query, which is the classic form of this mistake.
  3. Check what the key does to writes. Every reading written on a given day carries the same key value, so the entire write load of the service concentrates on one group at a time and moves to a new one at midnight. The design has made the meter spend unevenly by construction.
  4. Read the autoscale setting honestly. Autoscale is billed against the maximum that is set, not only against what is used, so "a high maximum so throughput is never the constraint" is a standing cost commitment rather than a free safety margin. It also hides the partitioning defect, because the scan is paid for rather than failing.
  5. Test the consistency choice. The spectrum is selectable per request, so reading at the strong end everywhere charges more request units and adds latency on every read, including the many that are a device fetching its own recent history and would tolerate a weaker level. Strength should be reserved for the reads whose correctness genuinely depends on it.
  6. State the corrected shape. Partition on the device so that the dominant read is served from one group and the write load spreads across devices, set the autoscale maximum to a figure you are willing to be billed against, and choose the consistency level per request rather than once for the whole application.

Sanity check. Your partition key should be the field the dominant read filters on first, and it should also be the field that spreads writes most evenly. If those two tests disagree, you have found a genuine trade-off - if they agree, as they do here, the original choice was simply wrong on both counts.
