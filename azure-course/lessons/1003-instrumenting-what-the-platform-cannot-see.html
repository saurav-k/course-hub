Three ways to see inside, and each one lands somewhere different

working 12 min Capability area observability, rows telemetry-agent, distributed-tracing, managed-prometheus and dashboards. · Application Insights and OpenTelemetry

The one-minute version

  • The Azure Monitor Agent collects from a host - events, performance counters, syslog and text logs - and data collection rules decide what each machine sends.
  • One agent serves several rules at once, so what is collected changes centrally rather than machine by machine.
  • Inside a process, the Azure Monitor OpenTelemetry distro is the recommended instrumentation. It produces requests, dependencies, exceptions and traces, and correlates them into an application map.
  • There is no separate error-reporting product: exception grouping lives inside the application telemetry, in its failures view.
  • Managed Prometheus is a third store with its own language and its own limits - eighteen months of retention, and a single query spanning at most thirty-two days.

Three layers, three stores

The reframing A data collection rule is the object that makes agent-based collection manageable. The agent is installed once, and one agent can be attached to several rules at the same time, so "collect the security event log from every machine in this scope" is a rule change rather than a fleet operation. The rule is also where transformations happen, which is the trimming point lesson 1002 pointed at.

What an application map is made of

Three practical details sit around it. Live metrics stream without being charged, which makes them the right tool during a deployment. The application telemetry tables ride free at ninety days, as lesson 1002 said, and ingestion is billed through the workspace that hosts them. And the browser instrumentation remains a separate, non-OpenTelemetry path, so a page-view story and a server-side trace are not produced by the same library.

Packaged views, and what they do not cover

Two limits belong to the Prometheus store and surprise people who arrive from a self-run server. Retention is eighteen months, which is generous, but a single query may span at most thirty-two days, so a year-over-year comparison is several queries rather than one. Collection is either a managed add-on scraping a Kubernetes cluster or remote write from a server you run, and the store sits apart from platform metrics - so the metrics explorer and a Prometheus dashboard are looking at different data even when the names match.

Two narrower tools complete the picture. Availability tests run URL checks from Azure points of presence, with certificate-expiry checking and custom headers, and the current form is the standard test - the older multi-step and ping tests are retired. For .NET applications, a profiler and a snapshot debugger collect hot paths and exception-triggered dumps in production without a redeploy.

Check yourself

Retrieval practice

Answer from memory before revealing.

A team wants exception grouping and asks which Azure service provides it. What is the answer?
Error reporting is delivered inside the application telemetry rather than as its own product. The first invents a service. The second attributes it to the host agent, which does not see inside a process. The fourth names a real tool that collects dumps rather than providing the grouping.
What does a data collection rule change about operating an agent fleet?
Rules move the decision about what to collect off the machine, and one agent can be attached to several at once. The second removes the agent, which still does the collecting. The third inverts the benefit. The fourth confuses trimming with being free.
A dashboard needs a year-over-year comparison of a Prometheus series. What is the constraint?
Retention is eighteen months and the per-query span is capped at thirty-two days, so the data exists and one query cannot cover it. The first and third misstate the retention and the store. The fourth blames the language rather than the platform limit.

Practice about 15 minutes, with paper

Practice 1working

A checkout service is intermittently slow. It runs on Kubernetes, calls two internal services and one database, and the cluster already has the container bundle enabled and managed Prometheus scraping it. The team can see elevated pod processor use and a rise in cluster events, and cannot tell which call is slow. Somebody proposes enabling the host agent on the nodes to get more detail.

Diagnose the gap: say what each existing layer can and cannot answer, say why the proposal will not help, and name what to add.

Hint

For each of the three layers, ask what it observes: a host, a process, or a scrape endpoint. The question being asked is about a call between services, so ask which layer sees calls at all.

Show the worked solution
  1. Say what the container bundle sees. Container output, cluster events and inventory, plus performance data. It can show that a pod is busy and that events are firing, and it explicitly does not carry application traces.
  2. Say what Prometheus sees. Whatever is exposed at a scrape endpoint, as numeric series in a separate store queried in PromQL. Useful for rates and saturation, and blind to the path a single request took.
  3. Test the proposal. The host agent collects from a host - events, counters, syslog, text logs. It sees the machine, not the process's outbound calls, so it adds host detail to a question that is not about the host.
  4. Name the missing layer. The process. Instrumenting the service with the OpenTelemetry distro produces request and dependency records with a correlation identifier, which is what makes "which call is slow" answerable at all.
  5. Say what it produces. An application map correlated from those records, in which the slow dependency is a named edge rather than an inference from processor use.
  6. Warn about the gap. The map is only as complete as the instrumentation. If one of the two internal services does not propagate the correlation, it appears as a gap in the map rather than as an error, and the investigation stalls one hop short.
  7. Note the free tool for the next deployment. Live metrics stream without charge, so watching a fix land is cheap even when the rest of the telemetry is not.

Sanity check. Your answer should add exactly one layer, and it should be the one that observes calls rather than machines. If the host agent survived in your answer, ask what question it would answer that the container bundle does not already.
