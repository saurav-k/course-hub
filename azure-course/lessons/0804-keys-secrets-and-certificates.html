One vault, three kinds of object, three different lifecycle problems

working 12 min Capability area secrets-keys, rows key-management, secrets-store, certificate-manager, byok-hyok and hsm. · Azure Key Vault

The one-minute version

  • Every Azure service already encrypts at rest with a platform key. A customer-managed key does not add encryption - it moves the root of the envelope into a vault you control.
  • Soft delete and purge protection are on by default at creation, which makes a vault far harder to destroy and slightly harder to reuse a name.
  • Access comes two ways: role-based access control, which is recommended, and the legacy access-policy model that predates it.
  • Secrets are versioned and addressed by URI, which is what makes rotation possible without a redeploy, and the Secrets Store CSI driver mounts them into pods using a workload identity.
  • Azure has no managed private certificate authority. The vault issues certificates through integrated public authorities, and a private hierarchy runs on your own infrastructure.

Three objects, three problems

What a customer-managed key actually changes

The reframing Key Vault Premium and Managed HSM both run hardware validated to FIPS 140-3 Level 3. The difference is tenancy and operating model rather than certification: Managed HSM is a single-tenant pool with its own local role-based access control, a higher fixed hourly cost, and a security domain whose download and quorum handling is a prerequisite for recovering it. That security domain is a disaster-recovery obligation you accept on day one, not a feature you enable later.

The lifecycle that makes a vault hard to lose

Getting a secret into a workload without copying it

One boundary is worth respecting: the vault is for secrets, and Azure App Configuration complements it for the configuration that is not secret. Storing large non-secret configuration in a vault works and then makes every configuration read a secret read, with the access model and the cost that implies.

Certificates, and the authority that is not there

Azure has no managed private certificate authority. The vault issues certificates through integrated public authorities, and an internal hierarchy runs on your own Active Directory Certificate Services. Two more details bite: vault auto-renewal requires a certificate from the integrated authority, purchased through the vault, and anything else is a manual signing-request loop somebody has to remember. And the free managed certificates for web applications do not cover wildcards, while the global and regional edge products from lesson 0704 need their certificates in the vault or uploaded.

Retrieval practice

Answer from memory before revealing.

What does moving a service to a customer-managed key change?
Data is already encrypted with a platform key, so what changes is who holds the root. The first option is the most common misconception and would make the default unsafe, which it is not. The second and fourth invent mechanics the envelope pattern does not have.
A vault is deleted and a new one with the same name cannot be created. Why?
A soft-deleted vault still exists and still holds its name. The second option overstates purge protection, which prevents early destruction rather than reserving names forever. The third and fourth invent rules that are not the cause here.
An estate needs an internal certificate authority for service-to-service certificates. What does Azure offer?
There is no managed private authority; the vault integrates with public ones. The first two invent a service that does not exist, and the second additionally confuses key storage with certificate issuance. The third names a real feature aimed at public web certificates, not internal ones.

Practice about 20 minutes, with paper

Practice 1working

A regulated customer requires four things: encryption keys must be under the customer's control with a documented way to revoke them; the key material must sit in hardware validated to a recognised standard; internal service-to-service traffic must use certificates from the customer's own authority; and a public site must serve a wildcard certificate. An engineer proposes Key Vault with customer-managed keys everywhere, the free managed certificates for the public site, and Key Vault as the internal authority.

Assess it: say which requirements the proposal meets, which two it cannot, and what has to be verified rather than assumed.

Hint

Take the four requirements one at a time and ask which of the three object types each belongs to. The two failures are both certificate requirements, and the thing to verify is on the key side.

Show the worked solution
  1. Check the key control requirement. Customer-managed keys do put the root of the envelope in the customer's vault, and withdrawing access to that key is the revocation lever. So this one is met in principle.
  2. Check the hardware requirement. Both Key Vault Premium and Managed HSM run hardware validated to FIPS 140-3 Level 3, so the requirement is met either way. If the customer additionally wants single tenancy, Managed HSM is the answer - and the security domain becomes a recovery obligation from day one.
  3. Check the internal authority requirement. This fails. Azure has no managed private certificate authority, and the vault integrates with public authorities rather than acting as one. The internal hierarchy runs on the customer's own Active Directory Certificate Services.
  4. Check the wildcard requirement. This fails too. The free managed certificates for web applications do not cover wildcards, so the public site needs a certificate obtained elsewhere and placed in the vault, or uploaded to the edge product serving it.
  5. Name what must be verified. The revocation lever. Revocation semantics differ per service - some stop serving immediately and some continue briefly - so a documented kill switch has to be tested against each service in scope rather than inferred from the pattern.
  6. State the corrected proposal. Customer-managed keys with the hardware tier the customer's tenancy requirement chooses, a tested revocation procedure per service, the internal authority on the customer's own infrastructure with certificates loaded into the vault, and a purchased wildcard certificate for the public site.

Sanity check. Both of your failures should be certificate requirements and neither should be a key requirement. If you also failed the hardware requirement, re-read the tiers: the validated hardware is not exclusive to the single-tenant product.
