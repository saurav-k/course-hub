Four specialised stores, each answering a question a table and a document cannot

working 11 min Capability area databases, rows in-memory-cache, timeseries-database, graph-database and ledger. · Azure Data Explorer

The one-minute version

  • Azure Managed Redis is the current managed Redis service, running Redis Enterprise engines. The older Azure Cache for Redis has a published retirement schedule, so it is a migration source rather than a design choice.
  • Azure Data Explorer, also called Kusto, is the columnar engine for telemetry and time series. The same engine family sits under Log Analytics and Fabric Real-Time Intelligence, and KQL is the shared language.
  • Graph has three homes, and the current answer for new designs is Graph in Microsoft Fabric rather than the Cosmos DB Gremlin API.
  • Azure confidential ledger is an append-only store inside hardware enclaves that returns a cryptographic receipt for every write, so integrity holds against the operator too.
  • Tamper evidence also exists inside Azure SQL Database as ledger tables. Choosing between them is a question about who you are proving things to.

Four questions, four engines

The cache, and the name that is now a migration source

The reframing Azure Managed Redis is the go-forward managed Redis service, built on Redis Enterprise engines, with modules such as search, JSON and bloom filters available on the higher tiers. Azure Cache for Redis is the previous service and it carries a published retirement schedule for every one of its tiers. That makes the pair a naming trap rather than a choice: a new design picks the managed service, and an existing deployment is a migration with a clock on it. The vendor's own retirement material is the live authority for those dates, and this course links it rather than restating them.

The telemetry engine you will meet again

Azure Data Explorer, universally called Kusto, is a fast columnar analytics engine for telemetry and time-series data, queried in KQL. Its significance to an architect is larger than its product page suggests: the same engine family backs Log Analytics and Fabric Real-Time Intelligence, which is why one query language reaches logs, resource inventory and analytics alike. Time Series Insights, the earlier product in this space, has been retired, and Data Explorer together with Fabric Real-Time Intelligence is the replacement path.

Graph, which forks three ways

Fabric Graph is billed in Fabric capacity units rather than in the per-resource units the rest of this module uses, and its published billing model includes a minimum of 100 GB of storage charged at the OneLake cache rate. That floor is invisible on an architecture diagram and decisive on a small dataset, so check it against the size of the graph you actually have before choosing this home over the other two.

Proving that history was not edited

Tamper evidence also exists one module back, inside Azure SQL Database, as ledger tables that keep a tamper-evident history of a relational table. The two are not competitors so much as answers to different audiences: ledger tables prove history inside a database you already run and query, while the confidential ledger produces evidence intended to be checked by someone who does not trust the platform operator.

Check yourself

Retrieval practice

Answer from memory before revealing.

A new service needs a managed Redis cache. Which statement should drive the choice?
The older service has a published retirement schedule for every tier, so a new design starts on the current service. The first option treats a retiring product as a tier of the current one, which is exactly the naming trap. The third names a real difference but not the one that decides this. The fourth is simply false - both are managed services.
Why does Azure Data Explorer matter more to an architect than its own product page suggests?
One engine family under several products is why KQL reaches logs, inventory and analytics alike, and that is the fact worth carrying. The first and second options overstate the engine's role against stores that answer different questions. The third invents a routing requirement that the observability module contradicts.
What does the receipt returned by Azure confidential ledger actually provide?
Independent verification is the point - it is what makes the guarantee hold even against the operator. The second option describes a multi-party network, and this is a single-party ledger. The third confuses append-only with unreadable. The fourth describes a backup, which is a different concern entirely.

Practice about 20 minutes, with paper

Practice 1working

A regulator-facing product keeps an audit trail of approvals. Each approval names an approver, a case and a timestamp, and the regulator wants to be able to check any single approval on its own, without asking the operator to confirm anything. The product also wants to answer "which approvers are connected to which cases, two hops out" for a dataset of a few hundred megabytes, and it already runs its case data in Azure SQL Database. A proposal suggests Graph in Microsoft Fabric for the relationship question and Azure Cosmos DB for the audit trail.

Take the proposal apart: say which of the four questions each requirement is really asking, and where the proposed answer is wrong.

Hint

Sort each requirement into one of the four branches of the taxonomy figure before comparing products. Then, for the graph branch, look at the size of the dataset against the billing floor rather than at the capability.

Show the worked solution
  1. Classify the audit trail. The requirement is that a third party can check one approval without trusting the operator, which is the "how provable" branch. That is not something a document store provides, so proposing Cosmos DB answers the wrong question.
  2. Choose within the provable branch. Ledger tables would give tamper-evident history inside the relational database the product already runs, which is convenient but leaves the verification inside the platform. The stated audience is a regulator who wants to verify independently, so the confidential ledger and its receipts is the answer that matches the requirement as written.
  3. Classify the two-hop question. Relationships as first-class objects put this in the "how connected" branch, so a graph answer is right in kind.
  4. Choose within the graph branch. Three homes exist. The data already lives in Azure SQL Database, and node and edge tables ship inside that engine, so the relationship question can be answered without adding a product at all.
  5. Test the proposed graph home against its billing floor. Fabric Graph carries a published minimum of 100 GB of storage billed at the OneLake cache rate. A dataset of a few hundred megabytes would pay that floor for a fraction of its use, so the proposal is expensive for the size of the problem even though it is capable of solving it.
  6. State the corrected shape. Node and edge tables inside the existing Azure SQL Database for the relationship question, and Azure confidential ledger for the approvals, keeping the receipts alongside the records so the regulator can verify without the operator.

Sanity check. Both parts of the original proposal should have moved, and your corrected design should add exactly one new service rather than two. If you kept a document store for the audit trail, re-read the requirement - "without asking the operator to confirm anything" is the phrase that rules it out.
