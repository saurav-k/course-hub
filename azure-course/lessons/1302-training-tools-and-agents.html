Models you build, tools you call, and agents that need an identity

working 11 min Capability area ai-ml, rows model-training-platform, speech-vision-document-ai and agent-platform. · Azure Machine Learning

The one-minute version

  • Azure Machine Learning is the platform for models you build: training, tuning, a registry, and endpoints that serve real-time or batch inference on managed compute.
  • Its pipelines and curated environments are what make a training run reproducible, and its responsible-artificial-intelligence dashboards are part of the product rather than a separate tool.
  • The specialist services - speech, vision and document extraction - solve narrow problems well, and some of them run in containers on disconnected hosts.
  • The agent runtime is in preview: tools, threads and evaluation hooks, with traces flowing to the application telemetry from lesson 1003 through OpenTelemetry.
  • Agent identity is a real design question, and the directory's agent identity construct is itself in preview - so the honest answer today is a workload identity plus a named human sponsor.

The platform for a model you build

The reframing The specialist services are not models you reason about. Speech recognition and translation, image analysis and optical character recognition, and structured extraction from documents are narrow problems with well-defined outputs, and calling one is closer to calling a library than to designing around a model. Their branding has moved more than once - they were the cognitive services and now sit under the wider tools brand - so recognise them by what they do rather than by the name on the page.

Where a specialist service can run

Agents, and the question they raise

Both halves of the agent story are in preview: the runtime itself, which the corpus notes has already been renamed once, and the directory's purpose-built agent identity construct with its sponsorship and governance model. So the honest design today is the one lesson 0803 already supports - a user-assigned managed identity per agent, scoped by role assignments, with a named human owner recorded somewhere durable - while the purpose-built construct is watched rather than depended on.

Check yourself

Retrieval practice

Answer from memory before revealing.

What makes a training run reproducible on this platform?
Repeatable steps plus a pinned dependency set is what reproducibility means here. The first stores the output rather than making the run repeatable. The second is about serving. The fourth is an analysis surface rather than a reproducibility mechanism.
A site's data may not leave the building. Which option makes a specialist service usable?
Container deployment on a disconnected host is what keeps the data on site. The second, third and fourth all keep traffic private or local while the data still leaves the building, which is what the requirement forbids.
What is the honest position on agent identity today?
Both surfaces are in preview, so the durable answer is the workload identity from lesson 0803 with a named owner. The first overstates availability. The third describes the audit problem rather than a design. The fourth misplaces authorisation, which belongs to the system the tool acts on.

Practice about 15 minutes, with paper

Practice 1working

An insurer wants an agent that reads a claim document, extracts the structured fields, checks a policy database, and raises a ticket when a claim needs review. It also wants a fraud-scoring model trained on its own historical claims. A proposal builds document extraction with a general model endpoint and a long prompt, runs the fraud model from a notebook on a laptop, and has the agent act using the credentials of the operator who started it.

Take it apart: correct each of the three decisions, and say what the agent's identity should be today.

Hint

Ask of each of the three whether a narrow service already solves it, whether a platform already exists for it, and who is accountable for an action. The third question is the one with no fully settled answer.

Show the worked solution
  1. Correct the extraction decision. Structured extraction from documents is one of the specialist services. Using a general model endpoint with a long prompt for it costs more per document, gives a less predictable output shape, and puts a well-defined problem into a component that has to be evaluated rather than tested.
  2. Correct the training decision. A notebook on a laptop is not reproducible: the dependency set is whatever that machine has and the steps are whatever was executed. Move it to a pipeline with a curated environment, on managed compute, so a rerun is a rerun.
  3. Make the trained model deployable. Register the model as a versioned artefact and serve it from an endpoint - real-time if scoring happens during the agent's run, batch if scoring is done in bulk. Only then does module 12's release discipline apply to it at all.
  4. Correct the identity decision. Acting as the operator makes every action appear to be that person's, which destroys the audit trail and grants the agent whatever that person happens to hold. It is the exact problem lesson 0803 removed for other workloads.
  5. State the identity to use today. A user-assigned managed identity for the agent, with role assignments granting only what its tools genuinely need, and a named human owner recorded durably. The purpose-built directory construct is in preview and is watched rather than depended on.
  6. Add the observability. Agent traces reach the application telemetry through the ordinary instrumentation path, so the correlation and cost decisions from lessons 1002 and 1003 apply unchanged - including that traces are volume like any other telemetry.

Sanity check. Two of your three corrections should replace something bespoke with an existing platform feature, and the third should be an identity decision rather than a capability one. If the agent still acts as a person, the audit trail is still gone.
