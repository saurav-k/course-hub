A pod on AKS can hold an Azure identity without ever holding a secret

working 11 min Capability area containers, rows service-mesh, kubernetes-backup and kubernetes-fleet-management, with workload-identity-federation. · Workload identity federation

The one-minute version

  • An AKS cluster issues service-account-bound OIDC tokens, and a federated credential in Entra trusts that issuer - so a pod exchanges its own token for an Azure token with no secret anywhere.
  • The trust is described by three fields, issuer, subject and audience, and every one of them is matched case-sensitively.
  • Secrets that must still be read come through the Secrets Store CSI driver, which mounts Key Vault content and detects rotation.
  • The mesh path on AKS is the managed Istio add-on, whose revisions upgrade independently of the Kubernetes version. The older Open Service Mesh add-on is retired.
  • Backup and multi-cluster management are not Kubernetes-shaped products here: backup lives inside the central Azure Backup service, and many clusters are grouped by Fleet Manager.

How a pod gets an Azure token

Two documented details turn a working setup into a silent failure. The issuer, subject and audience match is case-sensitive end to end, so a subject that differs only in capitalisation fails with no useful signal. And only the first 100 signing keys from an identity provider's key set are cached, which matters when the provider is not the cluster. There is also a ceiling of 20 federated credentials on a managed identity used this way, so a design that mints one credential per branch or per namespace will meet it.

Where a secret genuinely has to be read - a third-party API key, a connection string - the Secrets Store CSI driver mounts Key Vault content into the pod and detects rotation, authenticating with a user-assigned managed identity or with workload identity. The point of the pair is that the pod's own identity is never a secret, and the secrets it does read arrive through a mount rather than an environment variable baked at deploy time.

The mesh, and what an add-on being managed buys

The mesh path on AKS is the Istio add-on, giving mutual TLS between workloads, traffic management and layer-seven observability. The Open Service Mesh add-on that preceded it is retired, so "the AKS service mesh" means Istio.

The reframing The managed part that matters is the upgrade story. Mesh upgrades run on revision channels decoupled from the Kubernetes version, so you are not choosing between a cluster upgrade and a mesh upgrade in the same maintenance window. On a self-run mesh those two clocks are yours to reconcile.

Practice about 20 minutes, with paper

Practice 1frontier

A platform team runs eight AKS clusters across three subscriptions in one tenant. Each cluster runs the same twelve services. Today, every service holds a client secret in a Kubernetes secret so it can reach a storage account and a database, upgrades are done cluster by cluster by hand, and there is no way to move a namespace to another cluster after an incident.

Replace all three practices with the Azure-shaped answer, and name the one limit that could bite the identity design at this scale.

Hint

Each of the three has a service that answers it. For the identity limit, count how many federated credentials the naive design would need on one identity.

Show the worked solution
  1. Remove the secrets. Turn on workload identity: each cluster issues service-account-bound OIDC tokens, and a federated credential on a user-assigned managed identity trusts that issuer with a matching subject and audience. The Kubernetes secrets holding client secrets then have nothing left to hold, and role assignments in Azure decide what each service may reach.
  2. Handle the secrets that remain. Anything that is genuinely a secret rather than an identity - a third-party API key - moves to Key Vault and is mounted through the Secrets Store CSI driver, which also detects rotation.
  3. Replace hand upgrades. Join the eight clusters to a Fleet Manager fleet. Members may be joined across subscriptions inside one tenant, which covers the three subscriptions, and update runs stage version and node-image upgrades across members in an order you choose.
  4. Answer the incident case. Azure Backup for AKS backs up cluster resources together with their persistent volumes, and a restore can be filtered by namespace and can target a different cluster - which is exactly "move this namespace somewhere else after an incident".
  5. Name the limit. A managed identity used this way supports at most twenty federated credentials. One credential per cluster per service - eight times twelve - is ninety-six, so the design must not mint a credential per pairing. Share one identity per service across clusters where the subject allows it, or split identities per service, so no single identity approaches the ceiling.

Sanity check. The final design should contain zero client secrets and no identity carrying more than twenty federated credentials. If your credential count per identity is in the dozens, the identity boundary was drawn per cluster when it should have been drawn per service.
