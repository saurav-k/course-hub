Everything you do to Azure goes through one door, and the door is Azure Resource Manager

foundation 9 min The control plane, before any service. Capability area iac-deployment, rows native-iac-template and resource-graph-query. · Resource Manager overview

The one-minute version

  • Azure has one management layer, Azure Resource Manager, and the portal is a client of it exactly like a script is. There is no second, richer path.
  • Manager runs a fixed sequence on every call: authenticate, authorise, test against policy, then forward to a resource provider such as Microsoft.Compute.
  • Because every tool rides the same API surface, tooling stays at parity. The one documented lag is portal-side, at about 180 days from a capability's release.
  • A resource group is a lifecycle container, not a location. Its own region holds only metadata, and deleting the group deletes everything in it.
  • The cost of one door is that every guardrail is a property of that door: role assignments, policy and locks are all evaluated there, so a data-plane action that never touches Manager is not covered by any of them.

One door, five clients

The Resource Manager overview states the consequence plainly: because all tools ride one API surface, they stay consistent with each other. The exception it documents is the portal, where new API functionality appears within about 180 days of initial release. So a capability announced with a REST or template example may be some months from having a form to fill in.

The endpoint itself is worth knowing by name. Microsoft recommends the global endpoint management.azure.com because it enables DNS-based traffic distribution, automatic failover and routing to the closest or healthiest region. Manager's own operations are distributed per region and fail over across availability zones, so the control plane is not a single building somewhere.

The reframing Azure's control plane is not "the portal, plus some automation". It is one API with several skins. Every guardrail you will meet in this course - role assignments, policy effects, resource locks, deny assignments - is a rule attached to that API, which is also why none of them can see a request that does not use it.

What a single call actually passes through

Subtraction exists in exactly one place. A deny assignment blocks an action regardless of what roles the principal holds, and customers cannot create one: Azure itself creates them, today mainly when a deployment stack is configured to protect what it made. Module 08 works the whole evaluation out in detail; here it is enough to know that the additive model has one platform-owned exception and that the exception outranks an Owner.

A resource group is a lifecycle container, not a place

Three structural rules follow from the same overview page and they shape real designs. Every resource belongs to exactly one group. Deleting the group deletes everything in it, which makes the group the natural unit for anything with a shared lifetime, such as one environment of one application. And a group holds up to 800 instances of a given resource type, with some types exempt, which is the ceiling that eventually splits a very large estate into more groups than its owners expected.

Tags look like they should inherit down this structure and they do not. A tag on a resource group is not inherited by the resources inside it, so a cost report grouped by a tag that only exists on groups reports almost nothing. The fixes are a policy modify effect that writes the tag onto each resource, or the inheritance view in Cost Management - and choosing neither is the common outcome, discovered a quarter later.

Reading the estate back

One door has a second benefit that is easy to miss: because every resource was created through Manager, every resource is described in one queryable model. Azure Resource Graph queries resource properties across many subscriptions at once in KQL, the same query language Azure Monitor uses for logs, and it carries change-history tables as well. It is the fastest inventory and drift surface on the platform, and it is what the portal's own search box runs on.

The same property is what makes infrastructure as code unusually clean here. Bicep transpiles to Resource Manager JSON and keeps no state file of its own, because Manager already holds the state. Module 12 takes that apart properly.

Check yourself

Retrieval practice

Answer from memory before revealing.

A principal holds Owner on a resource group and tries to delete a resource in it. The delete fails. Which explanation is consistent with how Resource Manager evaluates a call?
Deny assignments are the one subtractive element and they outrank an Owner. The first option is wrong because Owner does carry delete. The third inverts the model - assignments union, they never subtract. The fourth invents a second authorisation step: the provider is reached only after Manager has already decided.
What does the region you choose for a resource group actually decide?
The group's region holds metadata, and control-plane calls reroute to a backup region if it degrades. The first option is wrong because resources in a group may sit in different regions. The second describes a failover the group does not perform. The third is a plausible confusion: billing follows each resource, not its group.
Why does a new Azure capability sometimes have a CLI command before it has a portal blade?
All clients share one API surface, and the documented lag is portal-side at about 180 days. The second and third options both imagine two control planes, which is the misconception this page exists to remove. The fourth invents a publishing order that providers do not have.

Practice about 15 minutes, with paper

Practice 1foundation

A team runs one application in one Azure region. All of its resources sit in a single resource group, and that group's region was set to a second region "for resilience". Someone has also tagged the group costCentre=retail and is confused that the monthly cost export shows almost nothing under that tag.

Write down what the group's region genuinely buys them, what it does not, and the two ways the tag can be made to reach the resources.

Hint

Separate the two planes before you answer. Ask what still works if the group's region is unavailable, then ask what still works if the application's region is unavailable.

Show the worked solution
  1. Name what the group's region stores. Metadata only. If that region degrades, Resource Manager reroutes control-plane calls for the group to a backup region, so the team can still list, update and delete their resources.
  2. Name what it does not do. It moves nothing. Data-plane access is unaffected by group placement, and it is affected if the resource's own region dies. The application still lives entirely in its one region, so the arrangement buys management continuity and no workload resilience at all.
  3. Explain the empty cost report. Tags do not inherit from a group to the resources in it, so a tag written once on the group is present on exactly one object. The resources carry no costCentre at all.
  4. Give the two fixes. Assign an Azure Policy modify effect that writes the tag onto resources in scope and remediates the existing ones, or read cost through the inheritance view in Cost Management, which applies the group's tag at reporting time rather than on the resource.

Sanity check. Your answer should contain the sentence "the workload is still single-region". If placing the resource group elsewhere came out looking like a resilience measure, the two planes have been merged back together.

Your teacher. If the two planes are still blurred, ask an agent to take one resource you know and list, separately, every operation that goes through Resource Manager and every operation that does not. The second list - reading a blob, querying a database, connecting over SSH - is exactly the set that role assignments at management scope will not see.
