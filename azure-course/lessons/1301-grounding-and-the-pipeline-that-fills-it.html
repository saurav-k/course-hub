The retrieval product is an assembly, not a service with a name

working 11 min Capability area ai-ml, rows vector-store and managed-rag-pipeline. · Vector search

The one-minute version

  • Vectors live in two places: inside a search index, or inside the document store from lesson 0502 using its own vector index type.
  • The search index offers an approximate index and an exhaustive option, which is the recall-against-cost dial rather than two products.
  • Integrated vectorization is assembled from the search service's own parts - indexers, skillsets and vectorizers - rather than sold as a separate retrieval product.
  • The same pipeline embeds the query at search time, which is what lets an application send text rather than a vector.
  • Quantization and oversampling are the tuning dials, and they trade recall against cost rather than adding accuracy for free.

Two homes for a vector

The reframing The approximate and exhaustive options are a dial, not a tier. Exhaustive comparison gives the best recall a corpus can offer and costs more to run; the approximate index trades a small amount of recall for a large amount of speed. The right position depends on corpus size and on how much a missed passage costs, and it is a decision to revisit with measurements rather than to make once from a default.

The pipeline, drawn as the parts it is made of

Grounding flows in the model service consume the resulting index, so the pipeline and the endpoint from lesson 1300 meet at the index rather than through a bespoke integration. Everything on this page is therefore a search design, and the model is downstream of it.

The dials, and what they actually trade

The retrieval-augmented pattern has no product name on Azure. It is assembled from the search service's indexers, skillsets and vectorizers, exactly as change data capture was assembled inside other services in lesson 0602 and scheduling was in lesson 1204. A design searching the catalogue for a retrieval product will not find one, and the useful sentence is "integrated vectorization in the search service" rather than a category name.

Check yourself

Retrieval practice

Answer from memory before revealing.

An application sends a user's question as plain text and gets passages back. What made that possible?
Query-time embedding by the same pipeline is what removes the embedding client from the application. The first puts the step in the wrong service. The second would make vector search impossible. The third is the situation this feature exists to avoid.
What do quantization and oversampling trade against each other?
Compact storage gives up precision, and retrieving more candidates buys recall back at query cost. The other three name real trade-offs in a retrieval design that are not what these two dials control.
Which requirement points at the search index rather than the document store for vectors?
Hybrid retrieval belongs to the search index and is the property that most often decides the choice. The second argues for the document store. The third and fourth are true of either home and decide nothing between them.

Practice about 15 minutes, with paper

Practice 1working

A support team wants an assistant grounded in three sources: a policy library of documents in a lake, a product catalogue already held in the document store, and a set of ticket records. Users must be able to search by product code as well as by description, the corpus of policy documents is large, and the team has proposed writing a nightly job that reads every document, calls an embedding model, and writes vectors into a table.

Redesign it: place the vectors, say what replaces the nightly job, and name the requirement that decides the vector home.

Hint

Look at the product-code requirement first - it is a keyword match, not a similarity match. Then ask which of the three sources an indexer could pull from on its own.

Show the worked solution
  1. Find the deciding requirement. Searching by product code is exact keyword matching, and searching by description is similarity. Needing both in one query is hybrid retrieval, which belongs to the search index. That settles the vector home for anything users search this way.
  2. Place the policy library. Documents in a lake are a source an indexer can pull from, so they belong in the search index with the rest.
  3. Decide about the catalogue. The catalogue already lives in the document store, which has its own vector index type. Keeping vectors beside those documents avoids a copy - but it forfeits hybrid retrieval over them, and the product-code requirement is exactly hybrid. So the catalogue is indexed into the search service too, and the duplication is a deliberate cost.
  4. Replace the nightly job. Integrated vectorization does all of it: an indexer pulls the sources, a skillset chunks the content, a vectorizer embeds each chunk, and the chunk and its vector are written together. Nothing about that has to be written or operated by the team.
  5. Remove the application's embedding client too. The query is embedded by the same pipeline at search time, so the assistant sends the user's question as text. That is a second piece of code the redesign deletes.
  6. Set the index dials with the corpus in mind. The policy corpus is large, so the approximate index rather than exhaustive comparison, with quantization to hold the footprint and oversampling to buy recall back at query time - stated as a trade rather than presented as a free improvement.
  7. Connect it to the endpoint. Grounding flows in the model service consume the resulting index, so no bespoke integration sits between retrieval and the model.

Sanity check. Your redesign should delete two pieces of code the team was going to write, and should accept one deliberate duplication rather than pretending it away. If the product-code search ended up as a similarity match, the hybrid requirement has been missed.
