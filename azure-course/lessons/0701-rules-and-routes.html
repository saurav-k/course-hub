Three layers decide whether a packet moves, and one of them always goes first

working 12 min Capability area networking-core, rows stateful-packet-filter, route-table, network-manager and nat-gateway. · Network security groups

The one-minute version

  • Security admin rules in Virtual Network Manager evaluate before network security groups and can deny across them, which is the closest thing Azure has to a central network guardrail.
  • A network security group is a stateful filter with priorities from 100 to 4096, lowest number wins, and processing stops at the first match.
  • A group can attach at the subnet, at the interface, or both at once, and when both exist the evaluation order differs by direction and both must allow inbound traffic.
  • Routing is separate: a user-defined route overrides system routes by longest prefix match, with next hops including a virtual appliance, a gateway, the network, the internet, or None, which is a blackhole.
  • Outbound internet egress with predictable addresses is the NAT Gateway. It is outbound-initiated only, allocated per zone, and it emits metrics but no per-translation log.

The three layers, in order

Two attachment points, and an order that flips

The reframing Rule ordering inside a group has one law: priorities run from 100 to 4096, the lowest number wins, and processing stops at the first match. There is no accumulation and no second opinion. Default rules allow traffic within the network until something overrides them, so the interesting question about a group is rarely what it allows - it is which rule matched first and stopped everything after it from being consulted.

Grouping by role instead of by address

An application security group lets a rule name a role rather than an address range: interfaces are made members of the group, and rules reference the group. It is the nearest thing Azure has to an attribute-based network policy, and the corpus is explicit that it is only near - there is no attribute-based network intent layer on Azure, and rules still resolve to addresses and ports underneath. What the group buys is that the membership changes without the rule changing.

Routing, and the next hop called None

Leaving the network with an address you chose

Two telemetry absences shape how this page is debugged. A network security group emits no per-rule verdict log: the allow-or-deny outcome is carried by virtual network flow logs instead, which module 10 covers. And the NAT Gateway has no per-translation record at all. So an investigation that starts by looking for "which rule denied this" is looking for a stream that does not exist, and should start from the flow logs and the effective-rules view instead.

Check yourself

Retrieval practice

Answer from memory before revealing.

A security admin rule denies a port, and a subnet security group allows it. What happens?
Admin rules evaluate before groups and their decisions terminate evaluation, which is what makes them a guardrail. The first option invents a merge. The second applies a proximity rule that does not exist here. The fourth describes an audit behaviour rather than the enforcement one.
A group is attached to both the subnet and the interface. An inbound allow rule is added to the interface group only. What is the result?
Both layers must allow inbound traffic, so an allow at one layer alone changes nothing. The first option assumes the layers are alternatives. The third is close but wrong in the same way - an absent deny is not an allow. The fourth invents a direction split between the two attachment points.
Traffic to one prefix disappears with no denial recorded anywhere. What should be checked first?
A next hop of None discards traffic silently, which fits "gone with nothing denied". The first is a real failure but presents as connection problems rather than one missing prefix. The second would change which rules apply, not make denials invisible. The third has the priority rule backwards - 4096 is the weakest priority, not the strongest.

Practice about 20 minutes, with paper

Practice 1working

A platform team must guarantee that a management port is never reachable from the internet on any workload in the estate, whatever a workload team configures. It must also route all outbound internet traffic through an inspection appliance, and give a payments partner a fixed set of source addresses to allow-list. Application teams keep their own security groups on their own subnets and want to continue doing so.

Design the controls: name the layer each requirement belongs to, say why the first cannot be met with a security group, and say what the partner requirement collides with.

Hint

Work the three layers in the order the second figure draws them, and ask for each requirement which layer can still be overridden by somebody else. Then check the third requirement against the direction NAT Gateway works in.

Show the worked solution
  1. Test the guarantee against a security group. A group is owned by whoever owns the subnet or the interface, so a workload team can add a permissive rule at a lower priority number and it will match first. A guarantee cannot live in a layer the guaranteed-against party controls.
  2. Place the guarantee. It belongs in a security admin rule, because those evaluate before groups and a Deny terminates evaluation. The application teams keep their own groups, and the guarantee holds above them.
  3. Place the inspection requirement. Sending outbound traffic through an appliance is a routing decision, not a filtering one, so it is a user-defined route on each workload subnet with a next hop of virtual appliance. Longest prefix match is what makes the override take effect over the system route to the internet.
  4. Place the partner addresses. A stable set of outbound source addresses is what NAT Gateway provides, and it is outbound-initiated only, which suits a partner allow-list exactly - nothing reaches inward through it.
  5. Find the collision. The second and third requirements both claim the outbound path. If all internet-bound traffic is routed to the inspection appliance, it leaves the estate from the appliance rather than through the subnet's NAT Gateway, so the addresses the partner sees are the appliance's. The two requirements have to be reconciled on one egress design rather than configured independently.
  6. State what is monitored and how. Neither the groups nor the gateway produce per-rule or per-translation records, so the estate's evidence is virtual network flow logs for the allow-and-deny outcome and gateway metrics for port pressure.

Sanity check. Your three requirements should land on three different layers, and exactly one pair should conflict. If nothing conflicted, re-read requirements two and three - both of them decide what the last hop out of the estate is, and only one of them can.
