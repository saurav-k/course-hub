Container Apps hides the cluster without leaving Kubernetes, and the revision is the unit you ship

working 10 min Capability area containers, rows serverless-containers and container-registry. · Azure Container Apps

The one-minute version

  • Azure Container Apps runs containers with no cluster to operate. It is built on Kubernetes and KEDA underneath, which is why its scaling model is event-driven and it can scale to zero.
  • Its deployment unit is the revision, and traffic is split between revisions by weight - so blue-green and canary are settings rather than tooling.
  • An environment is the shared boundary that several container apps sit inside, and it is what integrates them with a virtual network.
  • Container Instances is the other shape: one container, no orchestrator, fastest cold start, and no scaling group at all. New designs should reach for Container Apps.
  • Azure ships no proprietary non-Kubernetes orchestrator. Container Apps is the nearest managed alternative and it is Kubernetes underneath, which is a different answer from not having one.

Three rungs, one image

The reframing Azure has no proprietary non-Kubernetes orchestrator. That is not a gap in capability: Container Apps answers the same design question, and it answers it by hiding Kubernetes rather than by replacing it. The practical consequence is that concepts you know from Kubernetes - probes, scaling on a queue depth, jobs - reappear here in a smaller vocabulary rather than being absent.

Shipping is a weight, not a deployment

An environment is the boundary the revisions live in: several container apps share one, and it is the object that carries the virtual-network integration. There is also a jobs mode for work that runs and finishes - batch or event-driven - rather than serving continuously, which is the same fleet-or-scheduler distinction the compute module drew.

Which statement about Azure and container orchestrators is accurate?
There is no proprietary non-Kubernetes orchestrator, and Container Apps answers the same need by running Kubernetes and KEDA underneath. The first invents a product. The second reads the absence as a capability gap, which is exactly backwards. The fourth promotes Container Instances, which has no orchestrator at all, into one.
A single container must run once a day, start as fast as possible, and needs no scaling. Which service fits best?
Container Instances is the per-container shape with the fastest cold start and no scaling group, which is exactly this workload. The second and third both work and both carry an operating surface the job does not need. The fourth confuses a build task with a runtime.

Practice about 15 minutes, with paper

Practice 1working

A three-service application currently runs on an AKS cluster that the team does not want to operate. Two services are HTTP APIs that are idle overnight; the third consumes a queue and must scale on its depth. Images are built on a laptop and pushed by hand, and the application must reach a database over a private network path.

Move it off the cluster: name the target for each service, say what the environment does for the private path, and replace the manual build.

Hint

Ask which properties of the workload the substrate has to supply: falling to zero, scaling on a queue, and being inside a virtual network. All three are properties of the same target here.

Show the worked solution
  1. Place the two APIs. Container Apps, because scale-to-zero is native and idle overnight is exactly the case it pays for. Each is a container app with its own revisions.
  2. Place the queue consumer. Also Container Apps. Its scaling is event-driven through KEDA underneath, so queue depth is a first-class scale signal rather than something you translate into a CPU metric.
  3. Handle the private path. Put all three container apps in one environment, which is the shared boundary that carries the virtual-network integration - so the private path is a property of the environment rather than of each app.
  4. Replace the manual build. Use ACR Tasks, which builds images in response to commits or on a schedule. The three apps then pull from the registry rather than from whatever was last pushed by hand.
  5. Say what you gave up. The cluster is gone and with it the node-pool controls from lesson 0300: no GPU pool, no Spot pool, no direct control over the machines. If any of the three services later needs one of those, it moves back onto AKS rather than being configured here.

Sanity check. All three services should land on the same target and in the same environment. If the queue consumer ended up somewhere else because "it is not a web app", check what its scaling actually needs - event-driven scaling is the reason Container Apps suits it.
