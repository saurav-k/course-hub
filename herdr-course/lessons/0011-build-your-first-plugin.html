Module 05 · Plugin development · Lesson 11

From empty folder to running plugin

working 11 min A complete two-file plugin, every line explained, with the commands to run it. · the docs' own first-plugin guide

The one-minute version

  • You will build hello-herdr: one action and one popup pane, in plain bash.
  • herdr plugin link registers your working folder in place - no copying.
  • herdr plugin action invoke runs it; stdout lands in the command log.
  • Edits need no reinstall - herdr re-reads the folder before every call.

1. Write the two files

Create a folder named hello-herdr containing exactly this:

hello-herdr/herdr-plugin.toml · the whole contract, ten fields
id = "example.hello"
name = "Hello Herdr"
version = "0.1.0"
min_herdr_version = "0.7.0"
description = "Smallest useful Herdr plugin."
platforms = ["linux", "macos"]

[[actions]]
id = "greet"
title = "Greet the focused workspace"
contexts = ["workspace"]
command = ["bash", "hello.sh"]

[[panes]]
id = "hello-pane"
title = "Hello pane"
placement = "popup"
width = "60%"
height = 12
command = ["bash", "hello.sh", "--interactive"]
hello-herdr/hello.sh · plain bash, no dependencies
#!/usr/bin/env bash
set -euo pipefail

herdr_bin="${HERDR_BIN_PATH:-herdr}"

if [[ "${1:-}" == "--interactive" ]]; then
  echo "Hello from ${HERDR_PLUGIN_ID:-unknown}"
  echo "(entrypoint ${HERDR_PLUGIN_ENTRYPOINT_ID:-?})"
  echo
  echo "== workspaces right now =="
  "$herdr_bin" workspace list || true
  printf '\npress enter to close...'
  read -r _
else
  echo "greet from ${HERDR_PLUGIN_ID} in ${HERDR_WORKSPACE_ID:-no-workspace}"
  echo "focused pane: ${HERDR_PANE_ID:-none}, cwd: ${PWD}"
fi

Windows users: add "windows" to platforms only if you also port the script - PowerShell works fine as a command target.

2. What each part does

Manifest lineWhy it is there
id = "example.hello"global name; dots allowed here, which is why entry ids below may not use them
min_herdr_version = "0.7.0"required since plugin v1 shipped; herdr refuses older binaries (gate)
platforms = [...]omitting it links with a warning; listing it gives clean refusals elsewhere
[[actions]] id = "greet"invocable as example.hello.greet or bare greet if unambiguous
contexts = ["workspace"]advertises that the action makes sense relative to a workspace
command = ["bash", "hello.sh"]plain argv - no shell wrapping unless you ask for one
[[panes]] placement = "popup"a floating session-modal terminal; width/height are legal only for popups (rule)
Script lineWhat herdr handed you
HERDR_BIN_PATH:-herdrpath to the running binary; calling through it beats hoping herdr is on PATH (injection)
--interactive branchpane processes run in a real terminal, so they can read input
HERDR_PLUGIN_ENTRYPOINT_IDwhich pane entry started this run - set for panes only (panes env)
HERDR_WORKSPACE_ID, HERDR_PANE_IDconvenience ids derived from the invocation context (context ids)
action branch outputcaptured into the command log - actions have no terminal of their own

3. One folder, two personalities

The same script serves both entrypoints, because herdr tells each run why it exists (action env, pane env):

4. Run it

cd hello-herdr
herdr plugin link "$PWD"
herdr plugin list
herdr plugin action invoke example.hello.greet
herdr plugin log list --plugin example.hello
herdr plugin pane open --plugin example.hello --entrypoint hello-pane

The invoke prints nothing itself - its output goes to the log, which the next command shows. The pane open floats a real terminal running the same script interactively. Close it by pressing enter at the prompt.

Action output is capped at 64 KiB per stream and the log keeps the last 200 records in memory only - restarting herdr clears it (caps). Print summaries, not dumps.

Check yourself

Retrieval practice

Answer from memory before revealing.

You just edited hello.sh. What must you do before the change takes effect?
The server refreshes its registry and re-reads manifests from disk before every plugin call (refresh), so the next invocation picks up edits. Relinking is harmless but redundant, restarting throws away the log, and version bumps matter only when publishing.
Where does an action's printed output go?
Actions run without a terminal; their stdout and stderr are captured into PluginCommandLogInfo records readable via herdr plugin log list (log record). Only pane processes own a terminal, and discarded output would make debugging impossible.
