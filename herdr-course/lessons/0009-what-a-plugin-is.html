Module 05 · Plugin development · Lesson 09

A plugin is just a folder of commands herdr knows how to start

foundation 7 min Herdr runs coding agents in terminal panes. A plugin teaches it new tricks without touching herdr itself. · plugin docs

The one-minute version

  • Herdr is a terminal manager: many panes, each often running an AI coding agent, watched by one always-on server.
  • A plugin is one folder: a herdr-plugin.toml manifest plus scripts or binaries in any language.
  • The manifest declares five entry kinds: actions, startup hooks, event hooks, panes, and link handlers.
  • There is no SDK and no sandbox - the whole herdr CLI is the plugin API.

1. The whole plugin, in one picture

You do not need the words "terminal multiplexer" or "coding agent" to follow this chapter. Think of herdr as one window holding many terminal panels. In some panels people type commands; in others an AI assistant works away on its own. A plugin is a way to add your own automation around all of that.

Nothing else is required. Bash, Node, Python, Lua, Rust binaries - the manifest launches plain argv commands, so anything your machine can run works (docs, plugins.mdx, lines 6-8). There is no separate SDK and no restricted command set: "the entire Herdr CLI is the plugin API" (same doc, lines 23-25).

The reframing A plugin does not get special powers. It gets exactly the powers you already have typing herdr ... in a pane - packaged so anyone can install them with one command.

2. Five things a plugin can add

All five are declared up front in the manifest. Herdr reads the list, starts the right program at the right moment, and records what happened (schema: plugins.rs).

  • Actions are named commands - invocable from the CLI, from a custom keybinding, or from another plugin (invoke handler).
  • Startup hooks run once after herdr restores its session, for setup work (startup runner).
  • Event hooks fire when herdr emits a lifecycle event such as worktree.created or pane.agent_status_changed (event allowlist).
  • Panes open real terminals inside herdr - as overlays, popups, splits, tabs, or zoomed (panes.rs).
  • Link handlers intercept ctrl-clicked terminal URLs matching a regex and route them to one of your actions instead of the browser (click matcher).

3. What a plugin cannot do

The boundaries are deliberate and versioned as "plugin v1" (docs, lines 31-52):

  • No runtime registration - entrypoints live in the manifest only.
  • No native UI beyond terminals - a popup has no pane id and joins no layout APIs.
  • No managed storage API - plugins own their own files in folders herdr sets aside.
  • No shell expansion - commands run as bare argv arrays.
  • No high-volume events - per-keystroke output events are excluded from hooks (enforced by test).
Plugins are not sandboxed. Build and runtime commands run as you, with your permissions, and can call the full CLI. Install only plugins whose source you have skimmed - herdr shows a preview before installing but does not review code (docs, lines 37-52).

4. The marketplace is an index, not an app store

There is no submission queue. The marketplace at herdr.dev/plugins is rebuilt automatically from public GitHub repositories tagged with the topic herdr-plugin: a worker rescans GitHub every 30 minutes, validates each manifest's required metadata, and publishes a JSON index the site renders (marketplace worker). Publishing a plugin means pushing a repository.

Retrieval practice

Answer from memory before revealing.

What must every plugin directory contain?
The manifest named herdr-plugin.toml is the one required file - it is the contract herdr parses (loader). Nothing about Node, signing, or Rust is required: plugins may be written in any language, including no compilation at all.
How does a running plugin ask herdr to do something?
There is no plugin-only API: the docs state the entire herdr CLI is the plugin API, and HERDR_BIN_PATH hands the plugin the binary path to call. Runtime registration is not part of v1, libraries are optional, and raw process signals carry no herdr protocol.
