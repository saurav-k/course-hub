Every run is spawn, environment, callback, log

working 9 min Which trigger starts what, the variables your process receives, and every route back into herdr. · the spawn chokepoint

The one-minute version

  • Five triggers start plugin commands: actions, startup hooks, event hooks, link clicks, and pane opens.
  • Every run gets a HERDR_PLUGIN_* environment; the full context also arrives as one JSON blob.
  • To act, the plugin calls back through HERDR_BIN_PATH or the socket - the same API you type.
  • Each run leaves one log record: status, exit code, capped stdout and stderr.

1. What herdr puts in your environment

The spawn function is one code path for actions, hooks and events (env injection). Pane opens add their own (pane env).

2. The context, decoded

HERDR_PLUGIN_CONTEXT_JSON answers "where am I, what is focused, what just happened". Its shape (schema):

  • workspace_id / label / cwd - which workspace, its display name and folder
  • tab_id / label, focused_pane_id / cwd - where the user is looking
  • focused_pane_agent / agent_status - which AI runs there and its state
  • selected_text - live terminal selection, when there is one
  • clicked_url, link_handler_id - for link-click invocations
  • invocation_source, correlation_id - why this ran: cli, keybinding, link_click, startup, api

Fields are filled when they are known. An event about a closed tab still carries its ids even after the object is gone (per-event mapping) - read defensively.

3. One run, end to end

Concurrency is capped at 32 simultaneous plugin commands; excess requests fail fast with plugin_command_limit_reached. Long-running hook processes eat the budget (limit). Hooks should restore state and exit, not supervise.

4. Every route back into herdr

  • Any CLI command via HERDR_BIN_PATH - workspace, pane, terminal title, layout export/apply. This is the recommended route because it hides unix-socket versus windows-pipe differences (docs).
  • Raw JSON requests to the socket at HERDR_SOCKET_PATH - eleven plugin.* methods plus everything else the API serves (socket docs).
  • Your own files under CONFIG_DIR and STATE_DIR - no storage API exists, so durable state is yours to own.
The habit Read individual env vars for ids; parse CONTEXT_JSON for everything else; call back through HERDR_BIN_PATH. Three habits cover nearly every plugin ever shipped.

Retrieval practice

Answer from memory before revealing.

When is HERDR_PLUGIN_ACTION_ID present in the environment?
It is set only on the action path; startup and event hooks get HERDR_PLUGIN_EVENT instead, and panes get HERDR_PLUGIN_ENTRYPOINT_ID (branching). That split is how one script can tell why it was started.
You want a hook that reacts to every keystroke an agent types. Possible?
The hookable event list deliberately excludes output_changed and other noisy kinds until semantics exist for them, enforced by test (exclusion test). events.subscribe exists for clients, but manifest hooks cannot name these events - unknown names are warnings and simply never fire.
