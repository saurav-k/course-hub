Run it where the work lives - reach it from anywhere

working 8 min Three ways to reach a session, two update channels, and how herdr.dev itself is built and served. · herdr.dev/docs/persistence-remote

The one-minute version

  • Three access paths: run locally, SSH in first, or herdr --remote as a thin client.
  • The thin client runs on your laptop, so local desktop features - like pasting an image - bridge to the remote session.
  • Updates come from two JSON manifests: latest.json for stable, preview.json for the opt-in channel.
  • Those manifests and the whole docs site are generated by CI from the same repository you install from.

1. Three ways in

SSH-first: ssh you@server then herdr. Everything runs remotely; any SSH client works, including phones (how-to-work, opened this session). Thin-client: herdr --remote workbox connects over SSH, starts or attaches the remote server, streams the UI locally - which is why image paste can bridge: your client copies the image to a remote temp file and pastes that path (persistence-remote.mdx:38-49). Remote hosts must be Linux or macOS; Windows cannot be a remote host yet (src/remote.rs:9-14). By default Herdr wraps the connection in its own generated SSH config adding keepalives plus a connection-reuse socket; your own settings win ([remote].manage_ssh_config).

2. Update channels

herdr update downloads the channel asset, verifies SHA-256, and atomically replaces the binary on Unix; on Windows it re-runs the installer script embedded inside the binary itself (src/update.rs:690). If an update would change the client-server wire protocol, Herdr asks before touching the running server; --handoff opts into live handoff instead (install docs: update).

The quiet trap: switching to preview gets you fixes weeks early - and preview can regress. The docs' own advice is stable unless you want that tradeoff, and Windows preview installs stay on preview until you explicitly switch back (install.mdx:138-140).

3. Where herdr.dev comes from

This is the deployment story beginners rarely see. Pushing a version tag makes CI build five release binaries, create the GitHub Release, then commit the updated latest.json and the tagged docs snapshot back into the repository and ping Cloudflare Pages to rebuild the site (.github/workflows/release.yml:369-452). The plugin marketplace is separate again: a Cloudflare Worker scans GitHub every thirty minutes for repositories tagged herdr-plugin, parses each herdr-plugin.toml, and publishes an index snapshot to R2, which the website renders at /plugins/ (workers/plugin-marketplace/src/index.ts:3-32; verified live while writing this page).

Check yourself

Retrieval practice

Answer from memory before revealing.

What makes herdr --remote able to paste a clipboard image into a remote pane?
Because the thin client executes on your machine, it can copy the image to a remote temp file and paste that path. SSH-first mode has no such client on your side, so nothing bridges; there is no upload service and no conversion step.
A Homebrew user wants next week's fixes today. What is the correct move?
Preview is a direct-install channel; brew owns that binary and its versions. Handoff concerns replacing a running server during update, not choosing a channel - and ripping out brew to chase fixes trades a working setup for regression risk.
