The manifest is the entire contract

working 8 min Every field in herdr-plugin.toml, how it is validated, and where installed plugins end up on disk. · manifest loader source

The one-minute version

  • Four fields are required on every plugin: id, name, version, and min_herdr_version.
  • Validation happens at load time, before anything runs - a bad manifest never reaches the runtime.
  • Installed plugins are tracked in one registry file; the server re-reads manifests before every plugin call.
  • Entrypoint ids are local and dot-free; herdr qualifies them as plugin.id.action.

1. The fields, all of them

The loader accepts a directory or a direct manifest path, appends herdr-plugin.toml if needed, and parses strict TOML (loader lines). Required means linking fails without them.

FieldTypeRequiredRule
idstringyes≤120 chars, ASCII letters/digits and : . _ - (id rule)
namestringyesnon-empty after trimming (check)
versionstringyesfree-form display version (check)
min_herdr_versionsemver stringyesthree-part semver; refused outright if newer than your herdr (gate)
descriptionstringnotrimmed; dropped when empty
platformsarraywarned if absentsubset of linux/macos/windows; empty array rejected (rule)
[[build]]table listnoargv commands run only during github install (runner)
[[startup]]table listnoone-shot commands after session restore (runner)
[[actions]]table listnoid + title + command; optional contexts and description; unique ids
[[events]]table listnoon (event name) + command; unknown names become warnings, not errors
[[panes]]table listnoid + title + command; placement overlay/popup/split/tab/zoomed; width/height popup-only (rule)
[[link_handlers]]table listnorust regex pattern + action that must exist in the same plugin (rule)

Every repeatable block also takes its own platforms, which overrides the top-level list (inheritance).

2. From folder to registry

Installing or linking registers the plugin in one JSON file under herdr's config directory, guarded by a lock and written atomically (registry writer). GitHub installs are cloned into a managed checkout named for the plugin id.

What lives therePath
the registry of installed plugins~/.config/herdr/plugins.json
managed checkouts of github installs~/.config/herdr/plugins/github/<slug>-<hash>
a plugin's user-editable config folder~/.config/herdr/plugins/config/<encoded-id>
a plugin's runtime state folder~/.local/state/herdr/plugins/<encoded-id>

Paths follow XDG on unix and AppData on windows (dir resolution, plugin paths).

Setting min_herdr_version higher than the herdr you run is a hard refusal with error plugin_requires_newer_herdr - not a warning. Declare the oldest version whose APIs you use, nothing newer.

3. Enabled, disabled, gone

A registry entry has a small life of its own. Linking and unlinking add and remove it; enable and disable flip a flag; and a broken manifest does not remove the entry - it comes back listed with warnings (reload rule).

Naming Entry ids may contain dots but action, pane and handler ids may not - so example.hello.greet is always "action greet in plugin example.hello", never something ambiguous (docs).

Check yourself

Retrieval practice

Answer from memory before revealing.

Which of these action ids does herdr reject?
Action ids allow letters, digits, colon, underscore and hyphen - but not dots, which are reserved as the separator in qualified ids like plugin.id.action (charset). The first three are all legal spellings.
A manifest declares platforms = [] - an empty array. What happens?
An empty array is an explicit error: omit the field entirely to mean "unknown" (rule). Omitting links fine with a warning, and neither spelling ever grants all platforms - undeclared platform support blocks invocation rather than allowing it.
