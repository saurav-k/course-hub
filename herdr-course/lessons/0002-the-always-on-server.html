Module 02 · How it works · Lesson 02

One binary plays two roles - a keeper and a viewer

working 7 min The background server, the attachable client, the sockets between them, and the real terminals underneath. · herdr.dev/docs/session-state

The one-minute version

  • Typing herdr starts a hidden server daemon (first time) or attaches as a thin client (every time after).
  • The server owns the real terminals - PTYs - where your shells and agents live; the client only sends keystrokes and paints frames.
  • Detaching kills the viewer and nothing else; the server keeps parsing output and saving snapshots even with zero clients.
  • The cost of this design: a stopped server means dead processes - restore rebuilds shape, not running programs.

1. The keeper and the viewer

Picture a night watchman for a floor of tiny offices. Every pane is an office with a worker - an agent - who does not go home just because you left the building. The watchman is the server daemon: he holds the keys to every office (the PTY master ends), walks the halls all night, and writes on his clipboard whether each worker is busy or stuck. Your terminal runs the client, which is just a window into the building. Both are the same binary: the first herdr spawns the daemon detached so it survives your shell, then every herdr after that becomes a viewer (src/server/autodetect.rs:290-306).

The split is load-bearing. The client encodes your input and paints the frames it receives; it holds nothing. The server owns every PTY, runs its render loop even when no client is attached - so background panes stay current and reattaching is seamless (src/server/headless.rs server loop; arch report section 2.3). The two processes speak a version-pinned binary protocol on one socket and newline-delimited JSON on the other; a client and server that disagree on protocol version refuse to pair (src/protocol/wire.rs:16).

2. What a detach actually does

Because the watchman never sleeps, a network drop or a closed lid is just a longer detach. The harder case is the server itself stopping - and here the honest answer is a table:

EventWhat survivesWhy
detach / network dropeverything - processes, layout, live screensthe server held the PTYs all along
server stoplayout, directories, labels, agent conversation refsa session.json snapshot on disk
machine restartsame snapshot; processes are gonerestore re-spawns shells in saved cwds
update with --handoffeven the live terminals change handsreal PTY file descriptors passed to the new server

The persistence half of this table is a mechanism, not magic: see the hotel metaphor below and docs/next/website/src/content/docs/session-state.mdx "What survives".

The one-way door: herdr server stop ends the server and its pane processes together. Restore can rebuild the rooms from the photo album, but the workers inside them are new shells - unless an integration re-dials the agent's saved conversation.

Persistence works like a hotel that photographs every room nightly. While you live in the hotel, nothing needs restoring - your stuff is simply still there. If it burns down, the photo album (session.json, saved with a five-second debounce after every change) shows the exact furniture arrangement, and housekeeping rebuilds each room (src/persist/snapshot.rs, arch report section 4.1). Guests who bookmarked their place in a conversation get the concierge treatment: the same phone call is re-dialed - claude --resume <id> - instead of starting a new one.

Retrieval practice

Answer from memory before revealing.

You detach and close the lid for three hours. What is true when you return?
The server renders even with zero clients, so reattach is seamless. Pausing describes suspend, discarding describes a dumb logger - the emulator keeps full state - and there is no hidden renderer, only the daemon's own loop.
One-shot commands like herdr status speak on which socket?
Commands and agents use the JSON API - the same surface plugins and scripts use. The binary socket carries framed pixels for TUI viewers, herdr.dev serves releases and docs, and the snapshot file is output, not transport.
