Four situations Herdr was built for

foundation 6 min Concrete scenarios, each grounded in one shipped feature - every feature cited to the docs or code behind it. · herdr.dev/docs/how-to-work

The one-minute version

  • Solo dev, many agents: one sidebar answers "which of my agents needs me" across all projects.
  • Team on one box: named sessions give each member isolated panes and sockets on shared compute.
  • Overnight jobs: detach keeps processes alive through a closed lid - a full restart is the weaker path.
  • Agent fleets: agents drive agents through agent prompt --wait --until blocked.

1. Solo: five agents, one glance

Give each project its own workspace; the sidebar rolls every agent's state up per workspace (concepts.mdx:8-16). When one blocks - waiting on an approval - its dot changes, a sound plays if you enabled it ([ui.sound], embedded mp3s at src/sound.rs:27-37), and a toast can appear. You answer the blocked one first without touring terminals.

2. Team: one shared machine

Put Herdr on the box with the GPUs and credentials. Each member attaches their own named session - independent panes, tabs, sockets and runtime state, sharing one config file (persistence-remote.mdx:17-36). Members on laptops use herdr --remote for a local-feeling client; someone's phone can SSH in and attach the same session mid-incident.

3. Overnight: close the lid, keep the job

Detach keeps the server owning the PTYs, so closing your laptop changes nothing for running agents. The docs' own survival table marks detach-and-reattach as the strongest tier - processes, layout and live screens all return (session-state, opened this session). A full server restart is the weaker tier: shape returns, processes do not - unless an integration resumes the agent conversation natively.

Do not confuse tiers: surviving a lid close is detach. Surviving the machine rebooting is restore - and restore brings back layout, not live processes, unless native agent resume had a session reference from an official integration.

4. Fleets: agents supervising agents

An orchestrator script can start a worker agent in a pane, hand it a task, and park until it genuinely needs input: herdr agent start <name> --kind claude --pane <id> confirms interactive readiness; herdr agent prompt <target> "<task>" --wait --until blocked submits and waits, refusing to submit into an already-blocked pane (src/cli/spec.rs:344-437; the bundled skill taught to agents lives at skills/herdr/SKILL.md, embedded via src/main.rs:483-484).

Retrieval practice

Answer from memory before revealing.

Two teammates want isolation on one shared box. What gives it?
Named sessions are separate runtime namespaces - own panes and sockets. Workspaces organise within one namespace, so option two still shares it; there is one global config file by design; channels are about update source, not runtime isolation.
What does prompt --wait --until blocked guarantee the orchestrator?
Blocked is precisely the needs-input state - success, completion and exit are different conditions the orchestrator never assumed. That is also why submitting into an already-blocked pane is rejected outright.
