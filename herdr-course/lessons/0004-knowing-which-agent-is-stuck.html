Module 02 · How it works · Lesson 04

Herdr reads the whiteboard outside every office door

working 8 min The signature feature: how a pane becomes working, blocked, or idle - the detection pipeline, the state machine, and why it makes Herdr a runtime rather than a multiplexer. · herdr.dev/docs/agents

The one-minute version

  • Every pane gets a check roughly every 300 ms: who is running, then what does the bottom of the screen say.
  • State rules live in per-agent TOML manifests - sticky notes describing what stuck looks like - hot-swappable without restart.
  • Blocked is deliberately strict: an unrecognized screen means idle, never a false alarm.
  • The payoff: a sidebar that answers "who needs me", and an API where one agent can wait until another is genuinely blocked.

1. The pipeline, every third of a second

Back to the watchman. He cannot see inside the offices - only the whiteboard mounted outside each door. So per pane, on a ~300 ms tick, Herdr asks the operating system which program holds the foreground (is it claude, codex, a shell?), then reads up to the last 24 rows of that pane's screen from its own embedded terminal emulator - pinned to the buffer bottom even when you scroll away (src/pane/terminal.rs:41, arch report section 5.2). OSC window titles and progress strings count as evidence too.

The rules are the sticky notes. Nobody modified Claude Code to announce its mood, so Herdr keeps a folder of notes per agent - "if the bottom of the screen says press enter to confirm, that one is waiting for YOU" - and checks each screen against the notes. When an agent ships a new UI, maintainers publish a corrected note, and it hot-swaps into your running server without restarting anything (src/detect/manifests/*.toml, arch report section 5.5). Rules can demand several strings together, exclude strings, or anchor to regions like "after the last prompt marker" so stale scrollback cannot vote.

2. The state machine

Two design choices deserve attention. First, blocked is strict: a known agent whose screen matches nothing falls back to idle, because a false "needs you" alarm is worse than a missed one. Second, done is not detected at all - it is computed as idle-plus-unseen, so it clears the moment you look at the pane (src/app/agent_view.rs:387-394). And when screen reading is not trustworthy enough, some agents offer something better: official integrations install hooks that report state changes directly, and for a few agents those reports simply overrule the screen - one source of truth, no flapping (arch report section 5.4).

Best of all, every classification is explainable. Run herdr agent explain <target> --json and Herdr shows the matched rule, its priority, the evidence region, and which manifest version decided - so when a state surprises you, you can ask why and get an answer (src/detect/manifest.rs, arch report section 5.5).

Do not trust a "blocked" you did not investigate - and do not distrust one without checking. herdr agent explain exists precisely so the sidebar's claim is never the last word; the matched rule and its evidence are.

Check yourself

Retrieval practice

Answer from memory before revealing.

Why is done missing from the detector's own states?
Done is computed from idle and your attention, so it clears when you look - no detector state could know whether you looked. Process exit publishes as idle, and plugins are unrelated to the state machine.
An agent release changes its UI and detection goes quiet. What fixes it?
Manifests are the sticky notes - replaceable while the shift continues, no restart. Downgrading the agent inverts the fix, restarting is never required for manifests, and unknown only describes unrecognized programs, not a life sentence.
