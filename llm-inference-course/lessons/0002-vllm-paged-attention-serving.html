vLLM and PagedAttention Serving

vLLM is the default answer to "how do I serve this model to many users at once." Its core trick, PagedAttention, treats the KV cache like virtual memory so almost no VRAM is wasted, which is what lets it batch aggressively and push throughput far past a naive loop.

The one-minute version

  • One command, vllm serve <model>, gives you an OpenAI-compatible server on port 8000.
  • PagedAttention stores the KV cache in fixed-size blocks like OS memory pages, so fragmentation is near zero and you can pack many more sequences into the same GPU.
  • Continuous batching adds and removes sequences every decode step, keeping the GPU full instead of waiting for the slowest request in a fixed batch.
  • Prefix caching (--enable-prefix-caching) reuses the KV of shared prompt prefixes so repeated system prompts are not recomputed.
  • You tune it with a handful of flags: --gpu-memory-utilization, --max-num-seqs, --max-model-len, --tensor-parallel-size.

1. Why this matters

A naive server keeps one contiguous KV region per request, sized for the longest output it might produce. Most requests finish early, so that reserved space sits empty: fragmentation wastes the exact resource that limits how many users you can serve. PagedAttention removes that waste, and the freed memory turns directly into more concurrent sequences and higher throughput on the same card.

2. PagedAttention: KV cache as paged memory

The insight is borrowed straight from operating systems. Instead of one long contiguous array per sequence, the KV cache is chopped into fixed-size blocks (a handful of tokens each). A per-sequence block table maps logical token positions to physical blocks, which can sit anywhere in the pool. A sequence grows by grabbing a new block; when it finishes, its blocks return to the pool for the next request.

Why paging unlocks throughput The scarcest resource in decode is KV-cache memory, not compute. Recover the wasted memory and you can raise the number of in-flight sequences, which is the single biggest lever on tokens per second. Paging is what makes aggressive batching safe.

3. Continuous batching: never wait for the slowest request

Static batching groups N requests, runs them together, and cannot start anyone new until the whole batch finishes - so one long generation stalls everyone. vLLM instead schedules at the iteration level: every decode step it can retire finished sequences and admit waiting ones, keeping the batch as full as memory allows.

4. Prefix caching: stop recomputing shared prompts

Many requests share an opening: the same long system prompt, the same few-shot examples. With --enable-prefix-caching, vLLM hashes prompt prefixes and reuses the already-computed KV blocks for any request that starts the same way. The shared part is prefilled once; only the unique tail does new work, which cuts TTFT and prefill cost for high-overlap workloads.

step 4 · watch throughput rise with a concurrency loop
import asyncio, time
from openai import AsyncOpenAI

client = AsyncOpenAI(base_url="http://localhost:8000/v1", api_key="none")
MODEL = "meta-llama/Meta-Llama-3-8B-Instruct"

async def one_call():
    r = await client.completions.create(model=MODEL, prompt="Explain KV cache.", max_tokens=128)
    return r.usage.completion_tokens

async def run(concurrency):
    t0 = time.perf_counter()
    tokens = await asyncio.gather(*[one_call() for _ in range(concurrency)])
    dt = time.perf_counter() - t0
    print(f"concurrency={concurrency:3d}  total_tok/s={sum(tokens)/dt:8.1f}")

for c in (1, 8, 32, 128):          # same GPU, more in-flight requests
    asyncio.run(run(c))

Expected shape: tokens per second climbs steeply from concurrency 1 to 32 as continuous batching fills the GPU, then flattens once you hit the KV-cache or compute ceiling. That flattening point is your practical --max-num-seqs.

6. The tuning flags that actually move the needle

FlagWhat it controlsTurn it up whenCost of turning it up
--gpu-memory-utilizationVRAM fraction for weights + KVYou want a larger KV pool and more sequencesToo high risks out-of-memory under load
--max-num-seqsMax concurrent sequences per batchYou have spare KV memory to fillMore KV pressure, possible preemption
--max-model-lenMax context length per requestPrompts or outputs are longEach sequence reserves more KV blocks

Check yourself

Retrieval practice

Answer from memory before revealing.

What problem does PagedAttention primarily solve?
Paged KV blocks cut fragmentation to near zero, and the recovered memory becomes more concurrent sequences.
How does continuous batching differ from static batching?
Iteration-level scheduling frees a finished sequence and admits a waiting one on the next step, so the GPU never idles.
When does --enable-prefix-caching help the most?
Shared prefixes are prefilled once and reused, so high-overlap workloads see lower TTFT and prefill cost.
What is the risk of setting --gpu-memory-utilization too high?
A higher fraction grows the KV pool but leaves less slack, so bursts of long sequences can OOM.
