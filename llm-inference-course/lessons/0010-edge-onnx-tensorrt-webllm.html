Edge Deployment: ONNX, TensorRT, WebLLM

Not every model belongs on a central GPU server. Sometimes you compile it into a hardware-specific engine, ship it to a CPU or phone, or run it inside the user's browser. This lesson maps three edge targets and their build workflows, and the lab exports a small model to ONNX and runs it locally.

The one-minute version

  • Edge means running the model off the central server: on an NVIDIA GPU appliance, on CPU/mobile, or in the browser.
  • TensorRT-LLM compiles a model into a fused, hardware-specific engine for NVIDIA GPUs, with in-flight batching served via Triton.
  • ONNX Runtime exports the model to a portable graph that runs cross-platform on CPU, mobile, and many accelerators.
  • WebLLM runs a quantized model entirely in the browser via WebGPU, so no server or network round-trip is involved.
  • Each trades portability against peak speed. The lab exports to ONNX with one command and runs inference with ONNX Runtime.

1. Why this matters

Central serving is not always the answer. You may need the lowest possible latency on a fixed NVIDIA box, or you may need to run offline on a laptop CPU or a phone, or you may want to keep data on the user's device and pay nothing per token. Each of those pushes you to a different target with a different build workflow. Knowing which one fits saves you from forcing a browser model onto a datacentre GPU, or vice versa.

The key insight Edge targets trade portability for peak performance. A TensorRT-LLM engine is the fastest option but only on the exact GPU it was compiled for. ONNX runs almost anywhere but slower. WebLLM runs with zero infrastructure but is bounded by the user's browser and hardware. There is no universal best, only a best-for-this-constraint.

2. TensorRT-LLM: compile an engine for the GPU

TensorRT-LLM takes a model and compiles it into an optimized engine targeting a specific NVIDIA GPU generation. During the build it fuses kernels (merging many small operations into fewer big ones), selects the fastest implementation for each layer, and bakes in the chosen precision. The result is a serialized engine that runs faster than a general runtime but is tied to that hardware and shape. In production it is served through Triton Inference Server, which adds in-flight batching (the continuous-batching idea from Lesson 04) so many requests share the engine efficiently.

The modern path uses the TensorRT-LLM Python LLM API or trtllm-serve, which build the engine from a Hugging Face name for you. The older convert_checkpoint.py then trtllm-build then run.py sequence still exists but is considered legacy. Either way, the deliverable is a compiled engine plus a Triton config.

3. ONNX Runtime: one portable graph, many devices

ONNX (Open Neural Network Exchange) is a standard file format for a model's compute graph. You export your PyTorch model to an .onnx graph once, then run it with ONNX Runtime, which has execution providers for CPU, CUDA, DirectML, CoreML, and mobile NPUs. The same file runs on a server, a laptop, or a phone; ONNX Runtime picks the best available backend. It is slower than a hand-tuned TensorRT engine but wins on reach and simplicity.

4. WebLLM: the model in the browser

WebLLM runs a quantized model entirely in the user's browser using WebGPU for hardware acceleration. There is no server call and no token cost; the weights download once and inference happens in the tab. It exposes an OpenAI-style chat.completions.create API, so app code looks familiar. The tradeoffs are real: model size is limited by browser memory, the first load downloads hundreds of megabytes, and speed depends on the user's GPU. But for privacy-sensitive or offline-capable apps it is unbeatable, since data never leaves the device.

5. Lab: export to ONNX and run it locally

Goal

Export a small model to ONNX, run it with ONNX Runtime, and note the TensorRT-LLM and WebLLM paths

You will export a small causal LM to ONNX with one command, load it with ORTModelForCausalLM, and generate text on CPU with no GPU required. Then you will see the TensorRT-LLM build flow and a WebLLM snippet so you can recognise all three when you meet them.

export a model to ONNX with optimum
$ pip install "optimum[onnxruntime]" transformers # export a small instruct model to an ONNX graph (CPU-friendly) $ optimum-cli export onnx \ --model HuggingFaceTB/SmolLM2-360M-Instruct \ --task text-generation \ onnx_smollm/ Validating ONNX model onnx_smollm/model.onnx ... All good, model saved at onnx_smollm/ # add --optimize O2 for graph fusions, or O4 for fp16 on GPU
run_onnx.py · inference with ONNX Runtime on CPU
from optimum.onnxruntime import ORTModelForCausalLM
from transformers import AutoTokenizer
import time

model_dir = "onnx_smollm"
tok = AutoTokenizer.from_pretrained(model_dir)
model = ORTModelForCausalLM.from_pretrained(model_dir)   # loads the .onnx graph

prompt = "Explain what an ONNX graph is, in one sentence."
inputs = tok(prompt, return_tensors="pt")

t0 = time.perf_counter()
out = model.generate(**inputs, max_new_tokens=64)
dt = time.perf_counter() - t0

text = tok.decode(out[0], skip_special_tokens=True)
n = out.shape[1] - inputs["input_ids"].shape[1]
print(text)
print(f"\n{n} tokens in {dt:.2f}s -> {n/dt:.1f} tok/s on CPU")

Now the two paths you will not run here but should recognise. The TensorRT-LLM build compiles an engine for an NVIDIA GPU:

TensorRT-LLM: build an engine (modern LLM API path)
$ pip install tensorrt-llm # modern path: the LLM API builds the engine from a HF name $ python -c "from tensorrt_llm import LLM; \ llm = LLM(model='meta-llama/Llama-3.1-8B-Instruct'); \ print(llm.generate('Hello').outputs[0].text)" # or serve it with in-flight batching: $ trtllm-serve meta-llama/Llama-3.1-8B-Instruct # legacy path (still works): convert_checkpoint.py -> trtllm-build -> run.py
WebLLM: run a quantized model in the browser (WebGPU)
// npm install @mlc-ai/web-llm  ; needs a WebGPU-capable browser
import * as webllm from "@mlc-ai/web-llm";

const engine = await webllm.CreateMLCEngine(
  "Llama-3.1-8B-Instruct-q4f16_1-MLC",          // quantized, browser-ready build
  { initProgressCallback: (p) => console.log(p.text) }   // weights download once
);

const reply = await engine.chat.completions.create({
  messages: [{ role: "user", content: "Say hi in one sentence." }],
});
console.log(reply.choices[0].message.content);   // runs fully on-device, no server

Retrieval practice

Answer from memory before revealing.

Why is a TensorRT-LLM engine the fastest but the least portable option?
The build fuses kernels and picks the fastest layers for a specific NVIDIA GPU, which is where the speed comes from and why the engine is hardware-specific.
What is the main advantage of exporting to ONNX Runtime?
ONNX Runtime trades peak speed for reach: a single exported graph runs across CPU, GPU, and mobile execution providers.
What makes WebLLM distinctive among these targets?
WebLLM runs a quantized model on-device in the browser using WebGPU, so there is no server, no network call, and no per-token cost.
What does Triton add on top of a TensorRT-LLM engine?
Triton hosts the engine and adds in-flight (continuous) batching, letting many concurrent requests share the compiled engine efficiently.
