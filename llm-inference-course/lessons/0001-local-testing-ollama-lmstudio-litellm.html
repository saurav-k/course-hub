Local Testing: Ollama, LM Studio, LiteLLM

Get a real model answering on your laptop in minutes, then hide every provider behind one OpenAI-compatible endpoint so your code never changes when you swap the backend. This is the workbench you will use for the rest of the course.

The one-minute version

  • Ollama is the fastest way to a running model: ollama run llama3 pulls the weights and serves an OpenAI-compatible API at http://localhost:11434/v1.
  • LM Studio is the same idea with a GUI: browse models, click load, click Start Server, and it exposes http://localhost:1234/v1.
  • LiteLLM is a thin proxy and SDK that puts one OpenAI-compatible face in front of Ollama, OpenAI, Anthropic, and 100+ others, so your app code stops caring who serves the tokens.
  • The pattern for the whole course: point the standard openai client at a base_url, keep the code fixed, and change only the URL behind it.

1. Why this matters

Every serving engine you meet later - vLLM, SGLang, TensorRT-LLM - speaks the same OpenAI HTTP dialect. If you write your client against that dialect once, you can point it at a toy model on your laptop today and a GPU fleet in production next month with zero code changes. The job of this lesson is to build that habit: one client, many swappable backends, unified by a gateway.

2. Ollama: the fastest path to a running model

Ollama bundles a model runner and a small HTTP server into one binary. You give it a model name, it downloads a quantized build, loads it, and starts serving. The run command drops you into a chat REPL, but the moment the daemon is up it is also answering HTTP on port 11434.

Crucially, Ollama exposes an OpenAI-compatible surface at /v1. That means the same openai Python client you would use against api.openai.com works unchanged - you only change the base_url and pass a throwaway API key.

3. LM Studio: the same thing with a GUI

LM Studio is a desktop app for people who would rather click than type. You search a model catalog, download a quantized GGUF build, and load it with a slider for how much to offload to the GPU. Its Local Server (or Developer) tab has a Start Server button that exposes an OpenAI-compatible API on http://localhost:1234/v1. Same contract as Ollama, different front door - handy on a workstation where you want to eyeball memory use and token speed as you go.

One contract, many doors Ollama and LM Studio both speak /v1/chat/completions. The only differences that reach your code are the port (11434 vs 1234) and the model string. That is exactly why a gateway in front of them pays off.

4. LiteLLM: one endpoint in front of everything

LiteLLM comes in two shapes. As an SDK, litellm.completion(...) calls any provider with one function and provider-prefixed model names like ollama/llama3 or gpt-4o-mini. As a proxy, litellm --model ollama/llama3 starts an OpenAI-compatible server on http://0.0.0.0:4000 that forwards to the backend you named. The proxy is the piece you deploy: it centralizes keys, retries, rate limits, and cost tracking so individual apps stay dumb.

5. Lab: run a model, then put a gateway in front of it

Goal

Start Ollama, call it with the openai client, then front it with LiteLLM and prove the code did not change

You will bring up a local model, hit it directly, then insert the LiteLLM proxy and confirm the exact same client code works by only swapping the URL. That swap-the-URL-not-the-code move is the entire point.

step 1 · install and start a model with Ollama
# macOS: brew install ollama | Linux: curl -fsSL https://ollama.com/install.sh | sh $ ollama serve # start the daemon (skip if the app is already running) $ ollama run llama3 # pulls weights on first run, then opens a chat REPL >>> Send a message (/bye to exit) $ curl http://localhost:11434/v1/models # confirm the OpenAI-compatible surface is up {"object":"list","data":[{"id":"llama3","object":"model",...}]}
step 2 · call Ollama directly with the standard openai client
from openai import OpenAI

# point the STANDARD OpenAI client straight at Ollama
client = OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")  # key is ignored

resp = client.chat.completions.create(
    model="llama3",
    messages=[{"role": "user", "content": "Say hello in one short sentence."}],
)
print(resp.choices[0].message.content)
step 3 · put LiteLLM in front, then repoint the SAME client
$ pip install "litellm[proxy]" $ litellm --model ollama/llama3 # OpenAI-compatible proxy on http://0.0.0.0:4000 LiteLLM: Proxy running on http://0.0.0.0:4000
from openai import OpenAI

# ONLY the base_url changed: 11434 -> 4000. The rest is byte-for-byte identical.
client = OpenAI(base_url="http://localhost:4000", api_key="sk-anything")

resp = client.chat.completions.create(
    model="ollama/llama3",   # provider-prefixed name the proxy routes on
    messages=[{"role": "user", "content": "Say hello in one short sentence."}],
)
print(resp.choices[0].message.content)

Success looks like this: identical client code returns a reply in both step 2 and step 3, and the LiteLLM terminal logs the request. You have just decoupled your app from the backend.

Retrieval practice

Answer from memory before revealing.

On which URL does Ollama expose its OpenAI-compatible API by default?
Ollama serves the OpenAI-compatible surface at port 11434 under the /v1 path.
What is the main reason to run LiteLLM as a proxy?
The proxy is a control point: one OpenAI-compatible URL, with keys and routing managed in one place.
When you move a client from Ollama to the LiteLLM proxy, what changes in your code?
That is the whole habit: the code is fixed, only the base_url (11434 to 4000) moves.
Why might your very first Ollama request feel slow after a pause?
Ollama unloads idle models after keep_alive, so the next call pays the load cost again.
