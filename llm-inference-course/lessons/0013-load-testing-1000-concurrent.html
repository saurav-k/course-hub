Load Testing 1000+ Concurrent Requests

Dashboards tell you how the service behaves today. Load testing tells you where it breaks tomorrow. This lab ramps concurrency until you find the knee, the point where adding load stops adding throughput and only adds latency. Official tool: vLLM benchmark suite (vllm bench serve).

The one-minute version

  • There are two load models. Closed-loop holds N clients that each wait for a reply before sending again. Open-loop fires at a fixed arrival rate no matter how slow the server is. They stress the system differently.
  • Realistic tests use realistic prompt and output length distributions, not one fixed prompt. Length drives prefill and decode cost.
  • You ramp concurrency and plot latency against throughput. Early on, throughput rises and latency barely moves. Past the knee, throughput flattens and latency explodes.
  • The number you ship is the concurrency just below the knee that still meets your p95 SLO. That is your capacity per replica.

1. Why this matters

Every serving stack has a saturation point. Below it, the GPU has spare batch capacity and each extra request is nearly free. Above it, the batch is full, new requests queue, and latency grows without bound while throughput stays pinned at its ceiling. If you do not find that point deliberately in a test, you will find it accidentally in production during your biggest traffic day.

2. Open-loop versus closed-loop

This distinction decides what your test actually measures. In a closed-loop model you keep a fixed number of virtual users; each one sends a request, waits for the full response, then sends the next. The offered load automatically backs off when the server slows, so you can never overload it past what it can serve. In an open-loop model you send at a fixed arrival rate (say 200 requests/second) regardless of how fast replies come back, so a slow server builds an unbounded backlog, exactly like real internet traffic.

Which to use Use closed-loop (fixed concurrency) to measure peak throughput and find the knee cleanly. Use open-loop (fixed request rate) to test whether you survive a real arrival spike and to size queues and timeouts. Report both; they answer different questions.

3. The latency-versus-throughput curve

Plot achieved throughput on the x-axis and p95 latency on the y-axis as you raise concurrency. The curve has three regions. In the linear region the batch has room, so throughput climbs and latency is nearly flat. At the knee, the batch is full; throughput reaches its max and further load only lengthens the queue. In the saturated region throughput is pinned while latency rises steeply toward timeouts.

4. Lab: ramp to 1000+ and find the knee

Goal

Drive a vLLM server past 1000 concurrent requests and record p50/p95/p99 TTFT and throughput per level

First use vLLM's own benchmark for a trusted baseline, then run a small asyncio generator that ramps concurrency and prints the curve. Both talk to the OpenAI-compatible endpoint from earlier lessons.

Sweep --max-concurrency across 32, 128, 512, 1024 and watch throughput plateau while P99 TTFT climbs. That plateau is the knee. For full control over the ramp and streaming TTFT, run your own generator:

rampload.py · asyncio load generator, ramps concurrency, records percentiles
import asyncio, time, statistics, aiohttp

URL   = "http://localhost:8000/v1/chat/completions"
MODEL = "meta-llama/Llama-3.1-8B-Instruct"
LEVELS = [1, 8, 32, 128, 512, 1024]      # concurrency ramp, closed-loop
REQS_PER_LEVEL = 2000

async def one_request(session, sem):
    """Fire one streaming request; return (ttft_s, total_s)."""
    async with sem:                       # cap in-flight = concurrency level
        body = {
            "model": MODEL,
            "messages": [{"role": "user", "content": "Summarise the water cycle."}],
            "max_tokens": 128,
            "stream": True,
        }
        t0 = time.perf_counter()
        ttft = None
        async with session.post(URL, json=body) as resp:
            async for line in resp.content:          # SSE stream
                if line.startswith(b"data:") and ttft is None:
                    ttft = time.perf_counter() - t0  # first token arrived
        return ttft, time.perf_counter() - t0

async def run_level(concurrency):
    sem = asyncio.Semaphore(concurrency)
    async with aiohttp.ClientSession() as s:
        t0 = time.perf_counter()
        results = await asyncio.gather(
            *(one_request(s, sem) for _ in range(REQS_PER_LEVEL)))
        wall = time.perf_counter() - t0
    ttfts = sorted(r[0] * 1000 for r in results if r[0])   # ms
    def pct(p): return ttfts[int(len(ttfts) * p) - 1]
    print(f"conc={concurrency:>4}  "
          f"p50={pct(.50):6.0f}  p95={pct(.95):6.0f}  p99={pct(.99):6.0f} ms  "
          f"thr={REQS_PER_LEVEL / wall:6.1f} req/s")

async def main():
    for c in LEVELS:                      # ramp: each level is one point on the curve
        await run_level(c)

asyncio.run(main())

5. Reading the numbers honestly

Two traps make load-test numbers lie. First, a single fixed prompt underestimates real cost; production prompts vary in length, and a mix of long and short changes batching. Always drive with a length distribution close to your traffic. Second, reporting only the mean hides the tail; p99 is where your angriest users live. Report p50, p95, and p99, and state the prompt and output length distribution you used, or the numbers are not reproducible.
