Quantization Tradeoffs: INT4, FP8, AWQ, GPTQ

Weights are the biggest thing in GPU memory and, during decode, the thing you re-read every token. Store them in fewer bits and you shrink memory and move fewer bytes per step. The catch is quality. This lesson maps the memory-quality-speed triangle and shows how to serve a quantized model in vLLM.

The one-minute version

  • Quantization stores weights (and optionally the KV cache or activations) in fewer bits: FP16 to INT8, INT4, or FP8.
  • Because decode is memory-bound, fewer bits per weight means fewer bytes to move per token, so you get both smaller VRAM and often higher throughput.
  • The tension is a triangle: memory vs quality vs speed. Push bits down far enough and quality starts to drop.
  • GPTQ and AWQ are smart 4-bit weight-only methods; FP8 (E4M3/E5M2) is a hardware-native 8-bit format on H100-class GPUs.
  • In vLLM it is one flag: --quantization awq|gptq|fp8. This lab compares VRAM, throughput, and a quick quality check against FP16.

1. Why this matters

A 13B model in FP16 needs about 26 GB just for weights, before any KV cache. That may not fit your GPU, and every decode step must stream all 26 GB from memory to produce one token. Halving the bits roughly halves both numbers. Quantization is the single highest-leverage move for fitting bigger models on smaller hardware and speeding up the memory-bound decode phase at the same time.

The key insight Decode is limited by memory bandwidth, not math. Fewer bits per weight directly cuts the bytes moved per token, so lower precision buys throughput as a side effect of buying memory. That is why quantization is a serving win, not just a fit-it-on-the-card trick.

2. What you can quantize: weights, KV cache, activations

Not all tensors are equal. Weight-only quantization shrinks the parameters and is the safest, most common choice. KV-cache quantization stores the growing per-token cache in fewer bits, which matters most for long contexts. Activation quantization also lowers the intermediate values, enabling faster integer math but hurting quality the most because activations have wild outliers.

3. The formats: INT8, INT4, FP8

Integer quantization maps a float range onto evenly spaced integer buckets using a scale (and sometimes a zero-point). INT8 is nearly lossless for weights; INT4 is aggressive and needs a smart method to stay accurate. FP8 keeps a floating layout in 8 bits, so it holds a much wider dynamic range than INT8, which is why modern hardware favours it.

wq = round(w / s)  ·  s ,   s = max(|w|) / (2b−1 − 1) w: the original weight. s: a scale that maps the float range onto b-bit integers. wq: the reconstructed weight after rounding to the nearest bucket. Fewer bits (smaller b) means coarser buckets and larger rounding error, which is exactly the quality cost you are trading for memory.

FP8 comes in two shapes. E4M3 (4 exponent, 3 mantissa bits) has more precision and a narrower range, good for weights and activations. E5M2 (5 exponent, 2 mantissa) has more range and less precision, useful for gradients and some caches. FP8 matmul runs natively on Hopper-class GPUs (H100) and later, so it is fast without custom kernels.

4. GPTQ vs AWQ: two ways to keep 4-bit accurate

Naive 4-bit rounding wrecks quality because the coarse buckets destroy important weights. Both GPTQ and AWQ are post-training quantization (PTQ) methods that use a small calibration dataset to round more cleverly, but they think about the problem differently.

GPTQ is Hessian-based: it looks at how sensitive the loss is to each weight (via second-order information) and adjusts the remaining weights to compensate for the error introduced by each one it rounds. It quantizes column by column, correcting as it goes. AWQ (activation-aware weight quantization) observes that a small fraction of weight channels are salient because they multiply large activations; it protects those channels by scaling them up before rounding so they survive at full effective precision, then scales back after.

5. Where quality actually drops

Quantized models rarely fail on easy prompts. Degradation shows up on the hard tail: multi-step reasoning, long-context recall, code with strict syntax, and rare tokens. INT8 weight-only is usually indistinguishable from FP16. INT4 with GPTQ or AWQ is close on most tasks but can lose a point or two on reasoning benchmarks. Push toward 3-bit or activation-quantize carelessly and the drop becomes obvious. Always measure on your prompts, not just a leaderboard number.

quality_probe.py · eyeball answers on prompts that stress reasoning
from openai import OpenAI

probes = [
    "If 3 painters paint 3 fences in 3 hours, how long for 100 painters and 100 fences?",
    "Write a Python function that returns the nth prime. Include a docstring.",
    "Summarise the plot of Hamlet in exactly two sentences.",
]

def ask(port, model):
    c = OpenAI(base_url=f"http://localhost:{port}/v1", api_key="none")
    for p in probes:
        r = c.chat.completions.create(model=model,
            messages=[{"role": "user", "content": p}], max_tokens=200)
        print(f"[{model}] {r.choices[0].message.content[:160]}\n")

ask(8000, "Qwen/Qwen2.5-7B-Instruct")       # FP16
ask(8001, "Qwen/Qwen2.5-7B-Instruct-AWQ")   # AWQ 4-bit

Retrieval practice

Answer from memory before revealing.

Why does weight quantization speed up the decode phase, not just save memory?
Decode re-reads the weights every token and is limited by memory bandwidth, so cutting bits per weight directly cuts bytes moved and speeds the step up.
What is the core idea behind AWQ's activation-aware quantization?
AWQ finds salient channels (those hit by big activations) and scales them to survive 4-bit rounding. The Hessian approach is GPTQ, a different method.
What distinguishes FP8 E4M3 from E5M2?
E4M3 has more mantissa bits (precision, narrower range); E5M2 has more exponent bits (range, less precision). Both are 8-bit and native on H100.
Where does quantization quality loss usually show up first?
Easy prompts survive quantization fine. Degradation appears on reasoning, long-context recall, and code, so measure on your own hard prompts.
