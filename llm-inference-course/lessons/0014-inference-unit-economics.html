How Inference Costs Break Unit Economics

A GPU has one price: dollars per hour. A product has a different unit: dollars per 1M tokens, per request, per user. This lab is the bridge between them, and the levers (utilisation, batch size, quantization, routing) that decide whether you make money or bleed it.

The one-minute version

  • Every cost number starts from one formula: cost_per_token = gpu_hourly / (tokens_per_s × 3600 × utilisation). Everything else is that dial turned.
  • Utilisation is the silent killer. A GPU billed 24/7 but busy 30% of the time costs three times as much per token as one kept busy 90%.
  • Batch size and continuous batching raise tokens/s; quantization raises tokens/s and lets a smaller GPU do the job; routing sends cheap requests to cheap models.
  • Margins die in three places: idle GPUs, long outputs (you pay per output token), and retries (you pay twice for one answer).

1. Why this matters

You can serve a model beautifully and still lose money on every request if you never translate GPU-hours into per-token cost. A rented H100 might cost a few dollars an hour whether it serves a million tokens or ten. The product charges per token or per seat. If the two numbers are not connected in a spreadsheet you control, you are pricing blind, and the first time you find out is when the cloud bill arrives.

2. The one formula, and its dials

Start from the GPU's hourly price and ask how many useful tokens it produces in that hour. A GPU running at throughput T tokens per second, busy a fraction u of the time, produces T × 3600 × u tokens per hour. Divide the hourly price by that, and you have cost per token.

cost_per_1M_tokens = gpu_hourly / (T × 3600 × u) × 106 gpu_hourly: rented GPU price per hour. T: sustained throughput in tokens/second at your batch size. u: utilisation, the fraction of paid time the GPU is actually serving. Both T and u are things you can move; the GPU price often is not.

Three dials change the answer. Utilisation (u) is how much of the time you paid for was spent serving; idle GPUs waste it linearly. Throughput (T) rises with larger effective batches (continuous batching) and with quantization, which moves more tokens per second and can fit the model on a cheaper card. Routing changes which GPU and model a request even lands on, so cheap requests never touch the expensive box.

3. Where the margin actually dies

Three leaks account for most blown budgets, and all three are invisible in the GPU price.

The retry trap A 2% failure rate with automatic retries is not a 2% cost bump. Failed requests often fail late, after most tokens are generated, so you pay nearly full price for the failure and full price again for the retry. Cap output length, set hard timeouts, and count retries as real tokens in your cost model.

4. Lab: build the cost calculator

Goal

Turn GPU $/hr, tokens/s, and utilisation into $ per 1M tokens, then sweep a sensitivity table

You will write the one-function calculator, print your base case as cost per 1M tokens and per request, then sweep utilisation against throughput so you can see which dial pays off most.

cost.py · the whole model is one formula plus a sweep
def cost_per_1m(gpu_hourly, tokens_per_s, utilisation):
    """$ per 1,000,000 tokens for one GPU at a given throughput and utilisation."""
    effective_tokens_per_hour = tokens_per_s * 3600 * utilisation
    return gpu_hourly / effective_tokens_per_hour * 1_000_000

def cost_per_request(gpu_hourly, tokens_per_s, utilisation, tokens_per_req):
    return cost_per_1m(gpu_hourly, tokens_per_s, utilisation) / 1_000_000 * tokens_per_req

GPU_HOURLY = 2.50            # rented A100/H100-class card, $/hr
BASE_T     = 4000            # sustained tokens/s at your batch size
BASE_U     = 0.50            # honestly measured utilisation

base = cost_per_1m(GPU_HOURLY, BASE_T, BASE_U)
print(f"base case: ${base:5.2f} per 1M tokens")
print(f"a 700-token answer costs "
      f"${cost_per_request(GPU_HOURLY, BASE_T, BASE_U, 700)*100:5.3f} cents")

print("\n$ per 1M tokens   util->   30%     50%     70%     90%")
for T in (2000, 4000, 6000):
    row = "  ".join(f"${cost_per_1m(GPU_HOURLY, T, u):5.2f}"
                    for u in (0.30, 0.50, 0.70, 0.90))
    print(f"  T = {T:>4} tok/s        {row}")

5. Which lever, in what order

LeverMovesTypical effectCost
Continuous batchingT and u up2-10x tokens/s vs static batchingConfig change (Lesson 04)
Quantization (INT4/FP8)T up, GPU cheaper1.5-3x tokens/s, fits smaller cardSmall quality hit (Lesson 07)
Right-size + autoscaleu upKills idle-GPU wasteOps work (Lessons 11-12)
RoutingAvoids the cost entirelyCheap prompts skip the big modelRouter logic (Lesson 08)
Output caps + timeoutsFewer wasted tokensStops long-output and retry leaksPolicy change (Lesson 09)
The order that pays Fix utilisation first: an idle GPU wastes money no optimisation can recover. Then raise throughput with batching and quantization. Then route and cap so you never generate a token you did not need. Utilisation and throughput are the denominator; guard the numerator (tokens generated) last.

In the cost formula, where does utilisation sit and why does it matter?
u multiplies effective tokens in the denominator; halving it roughly doubles cost per token.
Why is a 2% failure rate with retries worse than a flat 2% cost increase?
Late failures burn nearly full tokens; the retry then pays full price again for one answer.
Two GPUs cost the same per hour. Why can their cost per token differ 9x?
Same price, different denominator: throughput and utilisation set how many tokens the hour buys.
Which lever should you pull first to cut cost per token?
Idle GPUs waste money nothing else recovers; raise utilisation first, then throughput, then guard tokens.
