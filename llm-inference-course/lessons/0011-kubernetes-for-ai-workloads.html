Kubernetes for AI Workloads: HPA and Autoscaling

One vLLM pod is a demo. A fleet that grows and shrinks with traffic is a service. This lab wires a vLLM Deployment to a GPU node, exposes it with a Service, and scales it on queue depth instead of CPU. Official docs: vLLM on Kubernetes and KEDA Prometheus scaler.

The one-minute version

  • GPUs are scheduled as extended resources. Install the NVIDIA device plugin, then ask for nvidia.com/gpu: 1 in your pod. One pod owns a whole GPU by default.
  • A vLLM server is a normal Deployment plus a Service, with readiness and liveness probes on /health so traffic only arrives after the model has loaded.
  • The default HPA scales on CPU, which is useless for LLM serving (the CPU is idle while the GPU works). Scale on a custom metric: vllm:num_requests_waiting (queue depth), via Prometheus Adapter or KEDA.
  • The enemy is cold start: a new GPU pod needs minutes to pull the image, load weights, and capture CUDA graphs. Keep warm replicas, pre-pull images, and pre-provision GPU nodes.

1. Why this matters

Traffic to an LLM service is spiky. If you run a fixed number of GPU pods, you pay for the peak all day, or you get crushed when the peak arrives. Autoscaling is the fix, but the naive knob (CPU utilisation) does not move for an inference server, because the GPU carries the load and the CPU sits near idle. You have to scale on a signal the GPU actually produces: the request queue.

2. How a GPU gets scheduled

Kubernetes does not know what a GPU is out of the box. The NVIDIA device plugin, run as a DaemonSet on every GPU node, advertises each card as an allocatable resource named nvidia.com/gpu. Your pod then requests it under resources.limits, and the scheduler only places the pod on a node that has a free card. There is no fractional sharing by default: a pod that asks for one GPU gets the whole device.

# Install the NVIDIA device plugin (pin the version you tested) $ kubectl create -f https://raw.githubusercontent.com/NVIDIA/k8s-device-plugin/v0.17.1/deployments/static/nvidia-device-plugin.yml daemonset.apps/nvidia-device-plugin-daemonset created # Confirm the node now advertises GPUs $ kubectl get nodes -o=jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.status.allocatable.nvidia\.com/gpu}{"\n"}{end}' gpu-node-a100-1 1

3. Deployment, Service, and probes

A vLLM server is deployed like any other stateless HTTP app, with two differences: it asks for a GPU, and its probes must account for a slow start. vLLM exposes /health once the engine is ready. A readiness probe on that path keeps the pod out of the Service (no traffic) until the model is loaded. A liveness probe restarts the pod if the engine wedges. Because model load takes minutes, use a startup probe with a generous budget so the liveness probe does not kill the pod mid-load.

Goal

Deploy a vLLM server on a GPU, expose it, and autoscale on queue depth

You will apply three manifests: a Deployment that requests one GPU and runs vllm/vllm-openai, a Service that load-balances across the pods, and an autoscaler that watches vllm:num_requests_waiting. Everything below is real and currently valid; pin image tags in production.

vllm-deploy.yaml · Deployment + Service
apiVersion: apps/v1
kind: Deployment
metadata:
  name: vllm-llama
  labels: { app: vllm-llama }
spec:
  replicas: 1
  selector: { matchLabels: { app: vllm-llama } }
  template:
    metadata:
      labels: { app: vllm-llama }
    spec:
      containers:
        - name: vllm
          image: vllm/vllm-openai:v0.6.6            # pin, do not use :latest
          args:
            - "--model"
            - "meta-llama/Llama-3.1-8B-Instruct"
            - "--max-model-len"
            - "8192"
          ports:
            - { name: http, containerPort: 8000 }
          env:
            - name: HUGGING_FACE_HUB_TOKEN
              valueFrom: { secretKeyRef: { name: hf-token, key: token } }
          resources:
            limits:
              nvidia.com/gpu: 1                      # one whole GPU
          startupProbe:                              # protects the slow model load
            httpGet: { path: /health, port: 8000 }
            failureThreshold: 60                     # 60 x 10s = up to 10 min to load
            periodSeconds: 10
          readinessProbe:                            # keeps traffic off until ready
            httpGet: { path: /health, port: 8000 }
            periodSeconds: 5
          livenessProbe:                             # restart if the engine wedges
            httpGet: { path: /health, port: 8000 }
            periodSeconds: 10
---
apiVersion: v1
kind: Service
metadata:
  name: vllm-llama
spec:
  selector: { app: vllm-llama }
  ports:
    - { name: http, port: 80, targetPort: 8000 }

It is NOT Ready until weights load. $ kubectl get pods -w -l app=vllm-llama vllm-llama-6c... 0/1 ContainerCreating 0 40s vllm-llama-6c... 0/1 Running 0 95s # engine still loading vllm-llama-6c... 1/1 Running 0 214s # startupProbe passed, Ready
vllm-hpa.yaml · HPA on a custom metric (via Prometheus Adapter)
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: vllm-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: vllm-llama
  minReplicas: 1                                     # never scale to zero here
  maxReplicas: 8
  metrics:
    - type: Pods
      pods:
        metric:
          name: vllm_num_requests_waiting            # exposed by Prometheus Adapter
        target:
          type: AverageValue
          averageValue: "5"                          # target ~5 queued req per pod
  behavior:
    scaleUp:   { stabilizationWindowSeconds: 30 }    # react fast to spikes
    scaleDown: { stabilizationWindowSeconds: 300 }   # drain slowly, avoid thrash

The HPA cannot read vllm:num_requests_waiting directly. A Prometheus Adapter scrapes vLLM and republishes the gauge into the Kubernetes custom-metrics API (the colon becomes an underscore, so it appears as vllm_num_requests_waiting). If you would rather skip the adapter, KEDA queries Prometheus itself and generates the HPA for you:

vllm-scaledobject.yaml · KEDA alternative (no adapter needed)
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: vllm-scaler
spec:
  scaleTargetRef:
    name: vllm-llama
  minReplicaCount: 1
  maxReplicaCount: 8
  cooldownPeriod: 300
  triggers:
    - type: prometheus
      metadata:
        serverAddress: http://prometheus.monitoring.svc:9090
        query: sum(vllm:num_requests_waiting)        # total queue across pods
        threshold: "5"
$ kubectl apply -f vllm-hpa.yaml horizontalpodautoscaler.autoscaling/vllm-hpa created $ kubectl get hpa vllm-hpa NAME REFERENCE TARGETS MINPODS MAXPODS REPLICAS vllm-hpa Deployment/vllm-llama 1200m/5 (avg) 1 8 1 # Under load the queue fills, the target ratio crosses 1, and pods are added $ kubectl get hpa vllm-hpa vllm-hpa Deployment/vllm-llama 7/5 (avg) 1 8 4

4. The autoscaling control loop

The HPA is a control loop. Every 15 seconds it reads the current metric, compares it to the target, and computes a desired replica count as ceil(current / target × currentReplicas). KEDA sits in front of Prometheus and feeds that same loop. The whole request-to-scale path forms a cycle: requests hit the Service, pile into per-pod queues, the queue is scraped as a metric, the autoscaler reads it, and replicas change.

5. Cold start is the real bottleneck

The autoscaler can ask for a new pod in seconds, but that pod is not useful until it is Ready, and getting there is slow. A fresh GPU pod must pull a multi-gigabyte image, download or read model weights, load them onto the GPU, and capture CUDA graphs. On a large model this is minutes, not seconds, and if the GPU node itself has to be provisioned by the cluster autoscaler first, add several more.

Cold-start painStage it hitsMitigation
Multi-GB image pullPullingPre-pull to nodes (DaemonSet), bake into node image, use a registry mirror
Weight download from HubLoadingCache weights on a PVC or hostPath, or bake them into the image
Weights to GPU + CUDA graphsLoading, WarmingKeep warm replicas (minReplicas ≥ 1), over-provision headroom
No GPU node availablePendingPre-provisioned GPU node pool, pause pods, cluster autoscaler with buffer
The warm-pool rule Because a new pod is minutes away, autoscaling alone cannot save you from a sharp spike. Run enough warm replicas to absorb the spike while new pods boot, and set minReplicas above zero so you never pay the full cold-start tax on the first request after a lull.

Why is CPU utilisation a poor autoscaling signal for a vLLM pod?
Inference load lives on the GPU; the CPU stays low, so scale on queue depth instead.
What does the NVIDIA device plugin actually do?
The plugin makes GPUs schedulable; without it, a GPU request stays Pending forever.
Why keep the readiness probe separate from a startup probe on a GPU pod?
Startup probe covers the slow load window; readiness gates traffic; liveness restarts a wedged engine.
Why does autoscaling alone fail to protect against a sharp traffic spike?
Cold start dominates; keep warm replicas and pre-provision nodes to bridge the gap while pods boot.
