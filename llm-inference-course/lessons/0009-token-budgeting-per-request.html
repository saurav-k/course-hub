A Token Budgeting System per User Request

Tokens are the unit you pay for and the unit that fills the KV cache. Without a budget, one runaway prompt or one abusive user can blow your cost and starve everyone else. This lab builds middleware that counts, caps, trims, and accounts for tokens before a request ever reaches the model.

The one-minute version

  • Every request has an input and an output token count; both cost money and both consume KV-cache memory.
  • Count tokens up front with a tokenizer (tiktoken), cap the output with max_tokens, and trim the history when it will not fit.
  • Enforce per-user quotas with a token bucket: each user refills tokens over time and a request must draw from the balance.
  • A cost guard rejects or degrades a request before it overspends, rather than discovering the bill afterward.
  • This lab builds budgeting middleware that counts with tiktoken, enforces a bucket, trims history, and blocks an over-budget request gracefully.

1. Why this matters

Bills and outages both come from the same place: unbounded tokens. A user pastes a 50-page document, or a loop retries with ever-growing context, or one tenant hammers the endpoint. Each of those quietly multiplies your token spend and eats KV-cache slots that other requests need. Budgeting turns "hope for the best" into an explicit contract: this user gets this many tokens per minute, this request may generate at most this many, and anything over is refused or trimmed before it costs you.

The key insight You cannot enforce what you have not measured. Counting tokens before the call is what makes every other control possible: caps, quotas, trimming, and cost guards all depend on knowing the token count up front rather than learning it from the provider's response.

2. Count first: input and output tokens

A token is not a word or a character; it is a chunk the model's tokenizer produces. You count the input by running the same tokenizer the model uses. The output you cannot count in advance, so you bound it with max_tokens. Total budget for a request is the input tokens plus that output cap, and that sum is what must fit the model's context window and your cost limit.

tokens_request = tokens_input + max_tokens_output ≤ min(context_window, budget) tokens_input: measured now with the tokenizer. max_tokens_output: the cap you set on generation. Their sum must stay under both the model's context_window (a hard limit) and your per-request budget (a cost limit). If it does not, you trim the input or lower the output cap before calling.

3. Fit the budget: trim and summarise

When a conversation grows past the budget, you have to make room. The cheapest move is to drop the oldest turns while keeping the system prompt and the most recent messages, since recency usually matters most. A richer move is to summarise older turns into a short recap and prepend that, preserving context at a fraction of the tokens. Either way you decide the policy before the call, not after the provider rejects an oversized request.

4. Enforce quotas: the token bucket

Per-user fairness needs a rate limit measured in tokens, not requests, because requests vary wildly in size. The token bucket is the standard tool: each user has a bucket that refills at a steady rate up to a maximum capacity. A request must remove tokens equal to its budget from the bucket; if the bucket lacks enough, the request is rejected or delayed. Bursts are allowed up to the bucket size, but sustained usage is capped at the refill rate.

budget.py · token counting, bucket, trimming, and the guard
import time, tiktoken

ENC = tiktoken.get_encoding("o200k_base")   # GPT-4o family; use encoding_for_model to auto-pick

def count_tokens(messages) -> int:
    # ~4 tokens overhead per message for role/formatting; good enough for budgeting
    return sum(len(ENC.encode(m["content"])) + 4 for m in messages)

class TokenBucket:
    def __init__(self, capacity: int, refill_per_sec: float):
        self.capacity = capacity
        self.refill = refill_per_sec
        self.tokens = capacity
        self.ts = time.monotonic()
    def _refill(self):
        now = time.monotonic()
        self.tokens = min(self.capacity, self.tokens + (now - self.ts) * self.refill)
        self.ts = now
    def try_spend(self, n: int) -> bool:
        self._refill()
        if self.tokens >= n:
            self.tokens -= n
            return True
        return False                        # not enough balance -> reject

def trim_to_fit(messages, max_input_tokens):
    """Keep the system message + most recent turns until we fit the budget."""
    system = [m for m in messages if m["role"] == "system"]
    rest   = [m for m in messages if m["role"] != "system"]
    while count_tokens(system + rest) > max_input_tokens and len(rest) > 1:
        rest.pop(0)                         # drop the oldest non-system turn
    return system + rest

BUCKETS = {}   # user_id -> TokenBucket

def guarded_call(user_id, messages, max_tokens=256,
                 context_window=8192, per_user_capacity=20000, refill=200):
    bucket = BUCKETS.setdefault(user_id, TokenBucket(per_user_capacity, refill))
    messages = trim_to_fit(messages, context_window - max_tokens)
    budget = count_tokens(messages) + max_tokens

    if not bucket.try_spend(budget):
        return {"status": 429, "error": "token budget exceeded, slow down",
                "needed": budget, "available": int(bucket.tokens)}

    # within budget: forward the real call here (OpenAI client), then record usage
    # r = client.chat.completions.create(model=..., messages=messages, max_tokens=max_tokens)
    return {"status": 200, "input_tokens": budget - max_tokens,
            "output_cap": max_tokens, "spent": budget}

Why must you count input tokens before calling the model?
You cannot enforce what you have not measured. Counting up front is what makes caps, quotas, trimming, and cost guards possible before any spend.
What does a token bucket give each user?
The bucket refills at a steady rate up to a capacity, so users may burst up to the bucket size but their sustained rate is the refill rate.
Why cap output with max_tokens when you already count the input?
You cannot pre-count generation, so max_tokens bounds the one part of the request you cannot measure beforehand.
When history exceeds the budget, what does summarising trade for dropping?
Summarising keeps the gist of old turns for far fewer tokens, at the cost of an extra call to produce the recap. Dropping is instant but forgets detail.
