Inference 101: Prefill, Decode, and the Metrics That Matter

The mental model the whole course rests on. Before you touch vLLM, you need to know what actually happens when a model answers, and which numbers you are optimising.

The one-minute version

  • Serving an LLM has two phases: prefill (read the whole prompt at once, compute-bound) and decode (emit one token at a time, memory-bound).
  • The two phases have opposite bottlenecks, so almost every optimisation targets one of them specifically.
  • Latency splits into TTFT (time to first token) and TPOT (time per output token). Users feel both.
  • There is a permanent tug-of-war between latency (fast for one user) and throughput (many users at once). Batching trades one for the other.

1. What happens when a model answers

Send a prompt and the model does two very different jobs. First it reads your entire prompt in a single parallel pass and fills the KV cache: this is prefill. Then it generates the reply one token at a time, each new token attending to everything before it: this is decode. Understanding that these are separate phases with separate bottlenecks is the foundation of every trick in this course.

2. Why the two phases have opposite bottlenecks

In prefill, hundreds of prompt tokens are processed together, so the GPU does big matrix multiplies and its compute units stay saturated. It is compute-bound. In decode, each step processes just one new token but must read the entire model weights and the growing KV cache from memory. There is very little math per byte moved, so the GPU sits waiting on memory. It is memory-bandwidth-bound.

The roofline idea Every kernel is limited either by how fast the GPU can compute (FLOPs) or by how fast it can move data (bytes). Decode moves a lot of bytes (weights + KV cache) for very few FLOPs, so it lives under the memory roof. That single fact explains MQA, GQA, KV quantization, and continuous batching all at once.

3. The metrics you will optimise

TTFT
Time to First Token
prefill latency - the initial wait
TPOT
Time per Out Token
decode latency - the streaming speed
Throughput
tokens / sec
total across all users
Goodput
useful req / sec
requests that met their SLO

Total latency for a request is roughly TTFT + (output_tokens × TPOT). A chatbot lives or dies on low TTFT (the reply must start fast) and a smooth TPOT (tokens must stream faster than the user reads, about 5-10 per second minimum). A batch summarisation job cares only about total throughput.

request_latency ≈ TTFT + Nout · TPOT TTFT: the one-time prefill wait before streaming starts. Nout: how many tokens you generate. TPOT: the steady per-token gap during decode. Long outputs are dominated by the TPOT term, which is exactly the memory-bound phase.

4. The latency vs throughput tug-of-war

Here is the tension that shapes every serving decision. Running one request alone gives the lowest latency but wastes the GPU. Packing many requests into a batch keeps the GPU full and multiplies throughput, but each individual request waits a little longer. Batching converts spare compute into more served users at the cost of per-user speed.

5. Lab: measure it yourself

Goal

Send one request and separate TTFT from TPOT

You will hit any OpenAI-compatible endpoint (a local Ollama or vLLM server, set up in Lessons 01-02) with streaming on, and time the first token versus the rest. This is the measurement you will repeat all course long.

measure_latency.py · runnable with the openai client
import time
from openai import OpenAI

client = OpenAI(base_url="http://localhost:8000/v1", api_key="none")

t0 = time.perf_counter()
first_token_time = None
n_out = 0

stream = client.chat.completions.create(
    model="local-model",
    messages=[{"role": "user", "content": "Explain KV cache in two sentences."}],
    stream=True,                          # stream so we can time the first token
)
for chunk in stream:
    delta = chunk.choices[0].delta.content
    if not delta:
        continue
    now = time.perf_counter()
    if first_token_time is None:
        first_token_time = now            # the moment the first token arrives
    n_out += 1
last = time.perf_counter()

ttft = first_token_time - t0
tpot = (last - first_token_time) / max(n_out - 1, 1)
print(f"TTFT      : {ttft*1000:7.1f} ms")
print(f"TPOT      : {tpot*1000:7.1f} ms/token  ({1/tpot:5.1f} tok/s)")
print(f"total     : {(last - t0)*1000:7.1f} ms for {n_out} tokens")

Run it a few times. Watch how TTFT grows with a longer prompt (more prefill work) while TPOT stays roughly flat (decode is per-token). That difference is the whole point of this lesson.

Retrieval practice

Answer from memory before revealing.

Which phase is memory-bandwidth-bound rather than compute-bound?
Decode moves lots of bytes for little math per token, so it waits on memory, not compute.
What does TTFT measure?
TTFT is time to first token, dominated by prefill; TPOT is the per-token decode gap.
What does larger batching mainly trade away?
Bigger batches saturate the GPU for higher throughput but add queuing delay per request.
Roughly how is total request latency composed?
latency ≈ TTFT + N_out × TPOT; long outputs are dominated by the TPOT term.
