Module 03 · Routing and Budgeting · Lesson 08

Build a Model Router by Cost, Latency, Quality

Most requests do not need your best model. A router sends each prompt to the cheapest model that will still do the job, and escalates only when it must. Done well it cuts cost by half or more with almost no quality loss. This lab builds one in Python.

The one-minute version

  • A router picks a model per request instead of sending everything to the biggest one.
  • Two main shapes: a cascade (try a cheap model first, escalate on low confidence) and a predictive router (a classifier scores difficulty up front and dispatches once).
  • The knob you tune is a threshold that trades cost against quality: route more to the strong model for quality, more to the weak model for savings.
  • Always add fallbacks: on error or timeout, retry a different model so one provider hiccup does not fail the request.
  • RouteLLM is a ready-made framework for the predictive style; this lab builds a rules-plus-classifier router and measures blended cost, latency, and quality.

1. Why this matters

Sending every request to a frontier model is like taking a taxi to the mailbox. A large fraction of traffic is easy: greetings, formatting, short factual answers, simple rewrites. Those succeed on a model that costs a tenth as much and answers faster. The hard minority (multi-step reasoning, tricky code, nuanced judgement) genuinely needs the big model. A router separates the two so you pay frontier prices only when they buy you something.

The key insight Routing works because difficulty is skewed: a few prompts are hard and many are easy. If you can cheaply tell them apart, you capture most of the savings of the small model and most of the quality of the large one. The router's whole job is that one prediction.

2. Cascade vs predictive routing

There are two ways to decide. A cascade is reactive: run the cheap model, and if its answer looks weak (low confidence, a refusal, a failed check) escalate to the stronger model. You sometimes pay for two calls, but you never send an easy prompt to the big model. A predictive router is proactive: a small, fast classifier or embedding model scores the prompt's difficulty before any generation and dispatches to one model. One call, but the prediction can be wrong.

3. How the router decides

A practical router stacks three layers, cheapest first. Rules catch obvious cases instantly (very short prompts, known keywords, a required-model override). If no rule fires, a lightweight classifier or embedding router produces a difficulty score. That score is compared to a threshold to choose the model. Wrapping all of it, fallbacks catch errors and timeouts and retry elsewhere.

Cblended = fsmall · csmall + flarge · clarge fsmall, flarge: the fraction of requests routed to each model (they sum to 1). csmall, clarge: the per-request cost of each model. Lowering the threshold pushes more traffic to the small model, raising fsmall and dropping blended cost, until quality on the misrouted prompts starts to suffer.

4. Difficulty scoring, and RouteLLM

The scorer can be as simple as a logistic-regression classifier over prompt embeddings, trained on examples labelled easy or hard. It can also be an off-the-shelf framework. RouteLLM ships pretrained routers (a matrix-factorization router, a BERT classifier, and others) that predict the probability the strong model would beat the weak one on a given prompt. You calibrate a threshold so that, say, half the calls go to the strong model, then route by comparing each prompt's predicted win-rate to that threshold.

5. Lab: build and measure a router

Goal

Route easy vs hard prompts to small vs large models, then measure blended cost, latency, and quality

You will build a router with a rules layer, a tiny difficulty classifier, and fallbacks, run a mixed prompt set through it, and compute the blended metrics against an all-large baseline. You can point it at two OpenAI-compatible endpoints (local vLLM ports from earlier lessons) or two API models.

router.py · rules + classifier + fallback
import time
from openai import OpenAI

SMALL = ("http://localhost:8001/v1", "small-model", 0.10)   # url, name, $/1k req
LARGE = ("http://localhost:8000/v1", "large-model", 1.00)

HARD_KEYWORDS = ("prove", "step by step", "debug", "why does", "optimise")

def difficulty_score(prompt: str) -> float:
    """Stand-in for a trained classifier: a cheap heuristic on 0..1.
    Swap this for logistic regression over embeddings, or a RouteLLM router."""
    score = 0.0
    if len(prompt) > 240:                 score += 0.4   # long prompts skew hard
    if any(k in prompt.lower() for k in HARD_KEYWORDS): score += 0.4
    if any(c in prompt for c in "{}()[];"):             score += 0.2   # code-ish
    return min(score, 1.0)

def route(prompt: str, threshold: float = 0.5):
    # Layer 1: rules (instant, no model call)
    if len(prompt) < 40:
        return SMALL
    # Layer 2: difficulty classifier vs threshold
    return LARGE if difficulty_score(prompt) >= threshold else SMALL

def call(prompt: str, threshold: float = 0.5):
    url, model, cost = route(prompt, threshold)
    try:
        c = OpenAI(base_url=url, api_key="none")
        t0 = time.perf_counter()
        r = c.chat.completions.create(model=model,
            messages=[{"role": "user", "content": prompt}],
            max_tokens=256, timeout=20)
        return r.choices[0].message.content, model, cost, time.perf_counter() - t0
    except Exception:
        # Layer 3: fallback to the other model on error/timeout
        url, model, cost = LARGE if model == SMALL[1] else SMALL
        c = OpenAI(base_url=url, api_key="none")
        r = c.chat.completions.create(model=model,
            messages=[{"role": "user", "content": prompt}], max_tokens=256)
        return r.choices[0].message.content, model + "(fallback)", cost, 0.0
measure.py · blended cost, latency, and a quality spot-check
prompts = [
    "hi",                                            # rule -> small
    "Translate 'good morning' to French.",           # easy -> small
    "What time is it in Tokyo right now?",           # easy -> small
    "Prove that the square root of 2 is irrational, step by step.",  # hard -> large
    "Debug why this recursion never terminates: def f(n): return f(n)",  # hard -> large
]

total_cost = 0.0; lat = []; routed = {}
for p in prompts:
    ans, model, cost, dt = call(p, threshold=0.5)
    total_cost += cost; lat.append(dt)
    routed[model] = routed.get(model, 0) + 1
    print(f"[{model:16}] {p[:40]:40} -> {ans[:50]}")

n = len(prompts)
print(f"\nrouted: {routed}")
print(f"blended cost / req : {total_cost/n:.3f}")
print(f"vs all-large       : {LARGE[2]:.3f}")
print(f"savings            : {(1 - (total_cost/n)/LARGE[2])*100:.0f}%")
print(f"p50 latency        : {sorted(lat)[len(lat)//2]*1000:.0f} ms")

Answer from memory before revealing.

Why does routing save so much without much quality loss?
Traffic is mostly easy, so a cheap scorer that separates easy from hard captures most of the savings while the few hard prompts still reach the big model.
How does a cascade differ from a predictive router?
The cascade is reactive (run cheap, escalate on weak output); the predictive router is proactive (score difficulty, dispatch once).
In the blended-cost model, what does lowering the threshold do?
A lower threshold routes more prompts to the small model, cutting blended cost but risking a bad answer on any hard prompt that got misrouted.
Why does a production router always need a fallback layer?
Fallbacks catch errors and timeouts and retry a different model, so one provider hiccup degrades to a slower answer rather than a failed request.
