KV Cache Eviction for Long Contexts

The KV cache grows linearly with context length, so long conversations and documents eventually will not fit in VRAM. When you cannot keep everything, you must choose what to drop. This lesson covers the four main eviction strategies and has you build a sliding-window plus attention-sink cache and measure the memory it saves.

The one-minute version

  • KV cache size grows with every token, so at long context it becomes the memory bottleneck and eventually overflows.
  • Sliding window keeps only the last W tokens; cheap, but it forgets the start, which usually breaks generation.
  • Attention sinks (StreamingLLM) keep a few initial tokens plus the recent window, which stabilizes quality at tiny cost.
  • H2O (heavy hitters) keeps the tokens that actually receive the most attention, plus recent ones.
  • Quantized KV stores the same tokens in fewer bits (e.g. 8 or 4 bit) instead of dropping any.
  • Every method trades memory against quality and recall. There is no free keep-everything option.

1. Why this matters

The KV cache holds a key and value vector for every token in every layer. Double the context and you double the cache. On long chats, agent scratchpads, or big documents, the cache can dwarf the model weights and blow past the GPU budget. When that happens your options are to reject the request, page KV to slower memory, or evict tokens. Eviction is the lever this lesson is about.

2. What to keep, what to drop

Sliding window is the naive fix: keep the most recent W tokens and forget the rest. It fails surprisingly hard, because models dump a lot of attention onto the very first tokens regardless of content - the attention sink. Drop those and the attention distribution destabilizes and output degrades. StreamingLLM's fix is elegant: always keep a handful of initial sink tokens plus the recent window.

The attention-sink insight Models learn to park excess attention on the first few tokens as a kind of no-op. Those tokens carry little meaning but huge attention mass. Evict them and every later token's softmax is thrown off. Keep 4 of them and quality holds even as you slide the window over millions of tokens.

3. The four strategies compared

Sliding window and StreamingLLM decide what to keep by position. H2O decides by importance: it tracks accumulated attention and keeps the heavy hitters that other tokens actually look at, plus recent tokens. Quantized KV changes the question entirely: keep every token, but store each in 8 or 4 bits to shrink the footprint without eviction.

4. Lab: build a sliding-window + attention-sink cache

Goal

Implement a fixed-size evicting KV cache and measure memory saved vs context kept

No GPU needed. You will model the KV cache as a list of per-token entries, feed it a long stream, and cap it at "sink tokens plus recent window." Then you compare its fixed footprint against a full cache and see exactly how much memory you traded for how much dropped context.

streaming_kv.py · pure Python, run anywhere
class StreamingKVCache:
    """StreamingLLM-style cache: keep S sink tokens + last W tokens."""
    def __init__(self, n_sink=4, window=1024):
        self.n_sink, self.window = n_sink, window
        self.tokens = []          # each entry stands in for one token's KV
        self.dropped = 0

    def append(self, token_id):
        self.tokens.append(token_id)
        budget = self.n_sink + self.window
        if len(self.tokens) > budget:
            # protect the sink prefix, drop the OLDEST non-sink (middle) token
            del self.tokens[self.n_sink]
            self.dropped += 1

    def size(self):
        return len(self.tokens)

# feed a long context and compare against a full cache
N = 100_000
full = list(range(N))                       # full cache keeps every token
cache = StreamingKVCache(n_sink=4, window=1024)
for tok in range(N):
    cache.append(tok)

full_bytes   = len(full)        # 1 unit of KV per token (relative)
stream_bytes = cache.size()
print(f"context tokens seen : {N}")
print(f"full cache size     : {full_bytes} units")
print(f"streaming cache size: {stream_bytes} units (fixed)")
print(f"memory saved        : {100 * (1 - stream_bytes/full_bytes):.1f}%")
print(f"tokens dropped      : {cache.dropped}")
print(f"kept: sink={cache.tokens[:4]}  recent_tail={cache.tokens[-3:]}")
context tokens seen : 100000 full cache size : 100000 units streaming cache size: 1028 units (fixed) memory saved : 99.0% tokens dropped : 98972 kept: sink=[0, 1, 2, 3] recent_tail=[99997, 99998, 99999]

The cache flatlines at sink + window = 1028 units no matter how long the stream runs, while the full cache grows without bound. You saved ~99% of KV memory. The tradeoff is explicit: the dropped middle tokens are gone, so anything that depended on them is unrecoverable. That is the memory-vs-recall dial.

Why does a plain sliding-window cache degrade generation quality?
Models park heavy attention on the first tokens; evicting those sink tokens throws off every later softmax.
What is StreamingLLM's fix over a plain sliding window?
Retaining a handful of sink tokens plus the window preserves the attention distribution at tiny cost.
How does H2O decide which tokens to keep?
H2O tracks accumulated attention and retains the heavy hitters plus recent tokens.
How does quantized KV differ from the eviction methods?
Quantization shrinks the footprint by spending precision, so no token is evicted at all.
