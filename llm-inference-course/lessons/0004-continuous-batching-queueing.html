Continuous Batching and Request Queue Management

The single biggest throughput lever in LLM serving is not a faster kernel, it is a smarter schedule. Continuous batching adds and removes sequences every decode step so a finished request frees its slot immediately, instead of the whole batch waiting for the slowest one. This lesson shows why, and has you measure it.

The one-minute version

  • Static batching runs a fixed group together and cannot admit anyone new until the slowest request finishes. Short requests wait behind long ones.
  • Continuous (in-flight) batching schedules at the iteration level: every decode step it retires finished sequences and admits waiting ones.
  • This raises throughput and cuts tail latency at once, because slots are never wasted idling on stragglers.
  • Around it sits queue management: admission control, queue depth limits, fairness, and chunked prefill so big prompts do not stall ongoing decodes.

1. Why this matters

Output lengths vary wildly: one request emits 12 tokens, another 800. Under static batching they share a batch and the whole batch runs until the 800-token one is done, so the 12-token request is held hostage. That is wasted GPU and a brutal tail latency. Continuous batching lets the short one leave the instant it finishes and pulls a fresh request into the freed slot.

2. The two schedules over time

Picture four requests with different output lengths sharing two slots. Under static batching, a slot cannot take a new request until its whole batch is done. Under continuous batching, the slot refills the moment its current request finishes.

Why the tail drops too Tail latency is dominated by requests that wait a long time before running. When a finished sequence frees its slot immediately, queued requests start sooner, so the slowest few finish earlier. Continuous batching improves p99 latency and throughput together, which is rare.

3. The queue around the scheduler

Iteration-level scheduling needs guardrails. Admission control decides whether a new request can enter given current KV-cache use; admit too many and you preempt running sequences. Queue depth caps how many wait before you shed load or return 429. Fairness stops one heavy user from starving others. Chunked prefill splits a huge prompt into pieces interleaved with ongoing decode, so a 20k-token prompt does not freeze everyone else's streaming.

4. Lab: simulate both schedules and measure the gap

Goal

Model static vs continuous batching in plain Python and compare throughput and tail latency

No GPU needed. Each request costs one time unit per output token. Static batching runs fixed groups and waits for the slowest; continuous batching refills any free slot every step. You will see the same requests finish faster and with a lower tail under continuous batching.

batching_sim.py · pure Python, run anywhere
import random

random.seed(0)
N, SLOTS = 200, 8
# output lengths: mostly short, a few long -> the classic straggler mix
lengths = [random.choice([5, 8, 12] * 6 + [200, 400]) for _ in range(N)]

def static_batching(lengths, slots):
    t = 0
    finish = [0] * len(lengths)
    for i in range(0, len(lengths), slots):
        batch = lengths[i:i + slots]
        batch_time = max(batch)           # batch waits for the SLOWEST
        for j, _ in enumerate(batch):
            finish[i + j] = t + batch_time  # everyone leaves together
        t += batch_time
    return t, finish

def continuous_batching(lengths, slots):
    remaining = {i: L for i, L in enumerate(lengths)}
    waiting = list(range(len(lengths)))
    active, finish, t = {}, [0] * len(lengths), 0
    while waiting or active:
        while len(active) < slots and waiting:   # refill free slots every step
            i = waiting.pop(0)
            active[i] = remaining[i]
        t += 1
        for i in list(active):                    # one decode step for all active
            active[i] -= 1
            if active[i] == 0:
                finish[i] = t                     # frees its slot immediately
                del active[i]
    return t, finish

def report(name, makespan, finish):
    lat = sorted(finish)
    p50 = lat[len(lat) // 2]
    p99 = lat[int(len(lat) * 0.99)]
    print(f"{name:22s} makespan={makespan:5d}  tput={len(finish)/makespan:5.2f} req/u  "
          f"p50={p50:4d}  p99={p99:4d}")

report("static batching",     *static_batching(lengths, SLOTS))
report("continuous batching", *continuous_batching(lengths, SLOTS))
static batching makespan= 2016 tput= 0.10 req/u p50= 824 p99=2016 continuous batching makespan= 1090 tput= 0.18 req/u p50= 232 p99=1074

Same requests, same slot count. Continuous batching finishes the whole set in roughly half the wall clock and slashes both p50 and p99, because short requests stop waiting behind the 200 and 400 token stragglers. That gap is the throughput lever.

Retrieval practice

Answer from memory before revealing.

At what granularity does continuous batching make scheduling decisions?
It schedules at the iteration level, so a finished sequence frees its slot and a waiting one is admitted immediately.
Why does static batching hurt tail latency so badly?
The batch cannot refill until its slowest member finishes, so short requests wait behind long ones.
What does chunked prefill prevent?
Splitting a huge prompt into chunks interleaved with decode keeps ongoing streams from freezing.
What is the job of admission control in the scheduler?
Admission control gates entry on free KV so the engine does not over-admit and preempt running sequences.
