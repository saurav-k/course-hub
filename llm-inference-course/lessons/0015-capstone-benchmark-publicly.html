Module 06 · Economics and Craft · Lesson 15

Capstone: Build, Benchmark, and Share an Optimized Service

Everything so far, in one artifact. Pick a model, serve it optimized, instrument it, load test it, price it, and publish an honest benchmark that a stranger could reproduce. This is the finale, and the skill that outlasts any single model release.

The one-minute version

  • The capstone is a full loop: serve (vLLM + quantization + continuous batching, speculative where it helps) → instrument (Prometheus + Grafana) → load test (find the knee) → price ($ per 1M tokens) → publish.
  • An honest benchmark states its methodology: exact hardware, model, quantization, prompt and output length distribution, load model, and the full p50/p95/p99, not one cherry-picked latency.
  • Reproducibility is the whole point. If a reader cannot rerun your commands and land within a few percent, it is marketing, not measurement.
  • To keep learning, read the methods in inference papers (arXiv cs.LG, cs.DC) and engine blogs, not the headline from a model-release post.

1. Why this matters

The internet is full of LLM benchmarks that mean nothing: one prompt, one request, a suspiciously round tokens/second, no hardware named, no percentiles. They are unfalsifiable and therefore useless. The engineer who can publish a benchmark another person can reproduce, and who can read someone else's benchmark and spot the missing methodology, is the one whose numbers get trusted. That skill compounds long after today's model is obsolete.

2. The end-to-end optimized stack

Your capstone service is the whole course wired together: a client hits a router that enforces a per-request token budget, the router forwards to a vLLM server running a quantized model with continuous batching, and every layer emits metrics into Prometheus and Grafana. Nothing here is new; the capstone is proving you can assemble it and measure it.

3. Serve it optimized

Continuous batching is on by default in vLLM. Add quantization to raise throughput and fit a smaller card, and turn on speculative decoding only if your workload (low concurrency, predictable text) actually benefits, since it can hurt at high batch sizes.

# Quantized (FP8) vLLM server with a large batch ceiling $ vllm serve meta-llama/Llama-3.1-8B-Instruct \ --quantization fp8 \ --max-num-seqs 256 \ --gpu-memory-utilization 0.90 INFO ... Using FP8 KV cache INFO ... Started server on http://0.0.0.0:8000 # Speculative decoding syntax is version-sensitive; check your vLLM version. # Recent vLLM uses a --speculative-config JSON blob: $ vllm serve meta-llama/Llama-3.1-8B-Instruct \ --speculative-config '{"model": "meta-llama/Llama-3.2-1B-Instruct", "num_speculative_tokens": 5}'
Turn one dial at a time If you enable quantization, larger batches, and speculative decoding all at once, you cannot tell which helped. Benchmark a plain baseline first, then add one optimization, re-run the identical load test, and record the delta. That per-lever table is the most useful part of your report.

4. Lab: the capstone spec, report, and publish checklist

Goal

Produce a reproducible benchmark report for your optimized service

Follow the spec, fill the results table, and pass the publish checklist. The deliverable is a single page (or README) that a stranger could clone and rerun.

Capstone spec

  • Pick one model and one GPU class you can actually rent or borrow
  • Serve it with vLLM: quantization + continuous batching, speculative only if it helps
  • Instrument it: Prometheus scrape + a Grafana panel for TTFT, tokens/s, KV%, and $/1M
  • Load test it: ramp concurrency with vllm bench serve until you find the knee
  • Price it: compute $ per 1M tokens at your measured throughput and utilisation
  • Publish: the report template below, with commands, so it reproduces

Publish checklist (fail any = not reproducible)

  • Exact model revision, engine version, and GPU + instance type are named
  • Prompt and output length distributions are described, not just a mean
  • Load model (open vs closed-loop) and the exact command are shown
  • p50, p95, and p99 are all reported, never a lone mean
  • Warm-up runs are discarded and the run count is stated
  • Cost per 1M tokens shows its GPU price and utilisation inputs
  • A copy-paste block lets a reader rerun the whole thing

5. Reading research instead of hype

Model-release posts sell a headline; inference progress lives in the methods sections of papers and engine engineering blogs. When you read one, skip to how it was measured. A trustworthy result names its hardware, batch size, sequence lengths, and baseline, and reports a distribution. A dubious one shows a single latency with none of that context.

Retrieval practice

Answer from memory before revealing.

What single property makes a published benchmark trustworthy?
Reproducibility is the test; a number nobody else can reproduce is marketing, not measurement.
Why enable optimizations one at a time when benchmarking?
Turning one dial per run gives a per-lever delta table; all-at-once hides which change helped.
When reading an inference paper, what do you check first?
Methods decide whether the number means anything; no hardware or baseline means no trust.
Why report p50, p95, and p99 rather than a single mean latency?
A mean can look great while p99 is terrible; publish the distribution so the tail is visible.
