SGLang and RadixAttention

SGLang is a serving engine built around one idea: automatically reuse KV cache across requests that share a prefix, using a radix tree. When your workload is full of shared system prompts, few-shot examples, agents, or multi-turn chat, that reuse is a big win over recomputing the same prefix again and again.

The one-minute version

  • Launch it with python -m sglang.launch_server --model-path <model> --port 30000; it serves an OpenAI-compatible API on port 30000.
  • RadixAttention keeps every request's KV in a shared radix tree keyed by tokens, so any new request that starts with a cached prefix reuses that KV instead of recomputing it.
  • It is on by default; disable with --disable-radix-cache. Prefixes are evicted LRU when memory is tight.
  • SGLang shines when prefixes are heavily shared (agents, few-shot, multi-turn, batch eval). With little overlap, its edge over vLLM shrinks.
  • It also ships a structured-generation front end for constrained and multi-step programs.

1. Why this matters

Look at real traffic and you will see the same tokens over and over: a 1,000-token system prompt on every agent call, the same five few-shot examples on every classification, the whole conversation replayed each multi-turn step. A plain engine reprefills that shared prefix every time. RadixAttention prefills it once and lets every later request point at the cached KV, so repeated prefixes become nearly free.

2. RadixAttention: a radix tree of cached prefixes

A radix tree is a compact prefix tree: shared token sequences share a path from the root, and paths branch only where requests diverge. SGLang stores KV against tree nodes, so a new request walks the tree matching its tokens and reuses the KV for the longest prefix already present, computing new KV only past the branch point.

Reuse vs eviction The tree is bounded by GPU memory. When it fills, SGLang evicts least-recently-used branches. Hot shared prefixes stay resident and keep hitting; cold one-off prefixes fall out. That is why steady, high-overlap traffic benefits most.

3. When SGLang beats vLLM, and when it does not

Both engines do paged KV and continuous batching. The differentiator is automatic cross-request prefix reuse. If your traffic reuses long prefixes, SGLang can cut prefill dramatically. If every request is unique, there is little to reuse and the two engines land close together, so you should pick on model support, features, and your own benchmarks.

4. Lab: prove the prefix-cache benefit

Goal

Launch SGLang and watch TTFT collapse on repeated shared-prefix requests

You will serve a model, send a batch of requests that all start with the same long system prompt, and compare the first request's TTFT (cold, full prefill) against later ones (warm, prefix reused). The gap is RadixAttention working.

step 3 · measure cold vs warm TTFT on a shared prefix
import time
from openai import OpenAI

client = OpenAI(base_url="http://localhost:30000/v1", api_key="none")
MODEL = "meta-llama/Meta-Llama-3-8B-Instruct"

SYSTEM = "You are a support agent. " * 200      # a long, SHARED prefix (~1k tokens)
questions = ["Reset my password.", "Cancel my plan.", "Update my email.", "Add a seat."]

def ttft(system, question):
    t0 = time.perf_counter()
    stream = client.chat.completions.create(
        model=MODEL, stream=True,
        messages=[{"role": "system", "content": system},
                  {"role": "user",   "content": question}],
    )
    for chunk in stream:
        if chunk.choices[0].delta.content:
            return (time.perf_counter() - t0) * 1000   # ms to first token

for i, q in enumerate(questions):
    tag = "cold (full prefill)" if i == 0 else "warm (prefix reused)"
    print(f"req {i}  TTFT={ttft(SYSTEM, q):6.1f} ms   {tag}")
req 0 TTFT= 210.4 ms cold (full prefill) req 1 TTFT= 38.9 ms warm (prefix reused) req 2 TTFT= 37.2 ms warm (prefix reused) req 3 TTFT= 36.5 ms warm (prefix reused)

The first request pays the full shared-prefix prefill; every later request reuses that KV and its TTFT drops sharply. Rerun with --disable-radix-cache and every request looks like the cold one - that difference is the whole lesson.

What does RadixAttention reuse across separate requests?
Cached KV for shared prefixes lives in a radix tree; a matching request reuses it instead of recomputing.
Which workload benefits most from SGLang's prefix reuse?
Heavy prefix overlap (agents, few-shot, multi-turn) is exactly where reuse pays off most.
How is RadixAttention configured at launch in SGLang?
RadixAttention is enabled by default; you disable it with --disable-radix-cache for an A/B.
What happens to cached prefixes when the radix tree runs out of memory?
Eviction is LRU, so frequently used shared prefixes remain resident and keep hitting.
