Observability: Latency, Tokens, Errors, Costs

You already autoscale on a vLLM metric. This lab wires the whole picture: scrape vLLM's built-in /metrics with Prometheus, dashboard it in Grafana, and turn raw counters into the four golden signals plus tokens and dollars. Official docs: vLLM metrics and Prometheus getting started.

The one-minute version

  • vLLM (and SGLang) already expose a Prometheus /metrics endpoint. You do not instrument the model; you scrape what it emits.
  • The signals you want are histograms and counters: vllm:time_to_first_token_seconds, vllm:time_per_output_token_seconds, vllm:num_requests_waiting, vllm:kv_cache_usage_perc, vllm:generation_tokens_total.
  • Track the four golden signals (latency, traffic, errors, saturation), then add the two that pay the bills: tokens/s and $ per 1M tokens.
  • The pipeline is boring and reliable: exporter → Prometheus → Grafana → alerts. A recording rule converts tokens/s straight into a cost number.

1. Why this matters

You cannot optimise or defend a service you cannot see. When a customer says "it got slow," you need to answer in seconds: was it TTFT or TPOT, was the queue full, was the KV cache saturated, were we dropping requests, and what did that hour cost. vLLM hands you all of that for free through Prometheus-format metrics. The work is not instrumentation, it is plumbing the numbers into a place you can query and alert on.

2. The metrics pipeline

The stack has four moving parts. vLLM is the exporter: it publishes counters and histograms on /metrics. Prometheus scrapes that endpoint every few seconds and stores time series. Grafana queries Prometheus with PromQL and draws panels. An alerting path (Alertmanager or Grafana alerts) fires when a query crosses a threshold. Nothing here is LLM-specific except the metric names.

3. The signals that matter

Google's four golden signals map cleanly onto vLLM's metrics, and two extra rows capture the economics.

The four PromQL queries that answer "is it healthy?"
# p95 TTFT over 5 minutes (latency signal)
histogram_quantile(0.95,
  sum by (le) (rate(vllm:time_to_first_token_seconds_bucket[5m])))

# output tokens per second (throughput / traffic)
sum(rate(vllm:generation_tokens_total[1m]))

# KV cache utilisation, 0 to 1 (saturation)
avg(vllm:kv_cache_usage_perc)

# queue depth right now (saturation, the early warning)
sum(vllm:num_requests_waiting)
vllm_rules.yml · a recording rule turns tokens/s into dollars
groups:
  - name: vllm-cost
    rules:
      # $ per 1M output tokens, given a $2.50/hr GPU.
      # cost/1M = (gpu $/hr / 3600 s) / (tokens/s) * 1e6
      - record: vllm:cost_per_million_output_tokens
        expr: |
          (2.50 / 3600)
          / clamp_min(sum(rate(vllm:generation_tokens_total[5m])), 1)
          * 1e6

  - name: vllm-alerts
    rules:
      - alert: TTFT_p95_SLO_breach
        expr: |
          histogram_quantile(0.95,
            sum by (le) (rate(vllm:time_to_first_token_seconds_bucket[5m]))) > 1.5
        for: 5m
        labels: { severity: page }
        annotations: { summary: "p95 TTFT above 1.5s for 5m" }

5. From metric to alert

An alert is a query plus a threshold plus a for duration. Prometheus evaluates the rule on a schedule; when the expression stays true for the whole for window, the alert moves from Pending to Firing and Alertmanager routes it. The for window is what stops a single slow scrape from paging you at 3am.

$ per 1M tokens = (gpu_hourly / 3600) / tokens_per_second × 106 gpu_hourly: your GPU price per hour. Divide by 3600 for cost per second, divide by tokens/s for cost per token, scale to a million. This is the exact expression the recording rule above computes, so cost sits on the same dashboard as latency.

Check yourself

Retrieval practice

Answer from memory before revealing.

How does vLLM expose its serving metrics to Prometheus?
vLLM is a pull-based exporter; Prometheus scrapes /metrics. You wire the plumbing, not the model.
Why is TTFT stored as histogram buckets rather than a single latency number?
Histograms keep per-bucket counts, so histogram_quantile derives p50/p95/p99 at query time.
Which pair of metrics best represents the saturation golden signal?
Queue depth and KV cache fill are your capacity ceiling; both are pure saturation signals.
What is the point of the 'for' duration on an alerting rule?
The 'for' window is the Pending-to-Firing buffer; it filters out one-off noisy scrapes.
