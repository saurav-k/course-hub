Speculative Decoding and Draft Model Handoffs

Decode is memory-bound: the GPU spends most of a token step waiting on memory, not doing math. Speculative decoding fills that idle compute by guessing several tokens ahead with a cheap model and verifying them in a single target pass. Same output distribution, fewer expensive steps.

The one-minute version

  • A small draft model proposes K tokens cheaply; the big target model verifies all K in one forward pass instead of K passes.
  • An accept/reject rule keeps only the tokens the target would have produced anyway, so the output distribution is provably identical to plain decoding.
  • Speedup is driven by the acceptance rate: a draft that agrees with the target often wins big; a poor draft can be slower than baseline.
  • Self-speculation (Medusa, EAGLE) and n-gram / prompt-lookup drafting remove the separate draft model entirely.
  • In vLLM you turn it on with one flag: --speculative-config. This lab measures tokens/s and acceptance versus a baseline.

1. Why this matters

In the decode phase, each new token requires re-reading the entire model weights from GPU memory to compute exactly one token. The arithmetic is tiny relative to the bytes moved, so the compute units sit idle waiting on memory bandwidth. That idle compute is free real estate. Speculative decoding trades a little extra math (checking K guesses at once) for far fewer of those expensive memory-bound steps. When the guesses are good, you get the same text two to three times faster.

The key insight Verifying K tokens costs almost the same as generating 1, because the target pass is memory-bound: reading the weights dominates, and it reads them once whether it scores 1 position or K. So if the draft is right most of the time, you get several tokens for the price of one target pass.

2. Draft, verify, accept: the mechanism

The loop has three moves. The draft model autoregressively generates K candidate tokens. The target model then runs one forward pass over the prompt plus those K candidates, producing its own probability for each position in parallel. Finally the accept/reject step walks left to right: it keeps a candidate if a random draw is under the ratio of target to draft probability, and stops at the first rejection, resampling that one token from a corrected distribution.

That last property is what makes speculative decoding safe to turn on in production: it is not an approximation. The math guarantees the sampled output has the same distribution as standard decoding from the target model. You are only changing how fast you reach those tokens, never which tokens are statistically possible.

tokens_per_round ≈ (1 − αK+1) / (1 − α) α: acceptance rate, the probability the target accepts a given draft token. K: how many tokens the draft proposes per round. As α approaches 1 you commit close to K+1 tokens per single target pass; as α drops toward 0 you commit about 1 and gain nothing while paying the draft overhead.

3. Acceptance rate is the whole game

Every design choice reduces to one number: how often the target accepts the draft. A draft model that is a smaller sibling of the target (same family, same tokenizer, similar training data) agrees often, so acceptance is high. A mismatched or too-weak draft agrees rarely, and you spend real time drafting tokens that get thrown away. There is also a cost floor: the draft itself takes time, so a slow draft eats the savings even when acceptance is decent.

4. Four ways to produce the draft

You do not always need a second model. The draft can come from a separate small model, from extra prediction heads bolted onto the target, or from cheap string matching over the text you already have.

Self-speculation (Medusa and EAGLE) is attractive because there is no second model to load, schedule, or keep in sync. Medusa adds lightweight heads that each predict a token a few steps ahead; EAGLE drafts in the target's own feature space and tends to hit higher acceptance, with EAGLE-3 pushing it further. N-gram / prompt-lookup decoding is the cheapest of all: when the output is likely to repeat text from the prompt (summarisation, code edits, RAG with quotation), it just proposes the next span it already saw. No weights, no training, and often a solid win on repetitive workloads.

Goal

Compare tokens/s and acceptance rate: baseline vs speculative

install and launch a baseline vLLM server

Now stop it and relaunch with n-gram speculative decoding. The config is a single JSON blob. num_speculative_tokens is K; prompt_lookup_min/max bound the n-gram length matched against the running text.

launch with n-gram (prompt-lookup) speculative decoding
$ vllm serve meta-llama/Llama-3.1-8B-Instruct \ --port 8000 \ --speculative-config '{"method":"ngram", "num_speculative_tokens":4, "prompt_lookup_min":2, "prompt_lookup_max":5}' # For a draft model instead of n-gram: # --speculative-config '{"model":"meta-llama/Llama-3.2-1B-Instruct","num_speculative_tokens":5}' # For EAGLE self-speculation: # --speculative-config '{"method":"eagle","model":"yuhuili/EAGLE-LLaMA3.1-Instruct-8B","num_speculative_tokens":5}'

Hit both servers with the same summarisation-style prompt (lots of quotable text) and time the stream. Reuse the streaming timer from Lesson 00, or the minimal loop below.

bench.py · measure tokens/s against an OpenAI-compatible endpoint
import time
from openai import OpenAI

client = OpenAI(base_url="http://localhost:8000/v1", api_key="none")
prompt = "Summarise this passage, quoting key phrases verbatim:\n" + open("article.txt").read()

t0 = time.perf_counter(); n = 0
stream = client.chat.completions.create(
    model="meta-llama/Llama-3.1-8B-Instruct",
    messages=[{"role": "user", "content": prompt}],
    max_tokens=400, stream=True,
)
for chunk in stream:
    if chunk.choices[0].delta.content:
        n += 1
dt = time.perf_counter() - t0
print(f"{n} tokens in {dt:.2f}s -> {n/dt:6.1f} tok/s")

spec_sim.py · no-GPU accept/reject simulator (shows the accounting)
import random

def speculative_round(alpha, K):
    """Return tokens committed in one round given acceptance prob alpha
    and K drafted tokens. Mirrors the left-to-right accept/reject rule."""
    committed = 0
    for _ in range(K):
        if random.random() < alpha:   # target accepts this draft token
            committed += 1
        else:
            break                      # first rejection stops the round
    return committed + 1               # +1: target always resamples one token

def simulate(alpha, K, rounds=20000):
    total = sum(speculative_round(alpha, K) for _ in range(rounds))
    tokens_per_round = total / rounds
    # baseline commits exactly 1 token per target pass
    return tokens_per_round, tokens_per_round / 1.0

for alpha in (0.9, 0.7, 0.5, 0.3):
    tpr, speedup = simulate(alpha, K=4)
    print(f"alpha={alpha:>3}  tokens/target-pass={tpr:4.2f}  ~{speedup:4.2f}x vs baseline")

Retrieval practice

Answer from memory before revealing.

Why can the target verify K draft tokens for roughly the cost of one token?
The target pass is memory-bound: it reads the weights once whether it scores 1 or K positions, so verifying K is nearly free relative to generating 1.
What does the accept/reject rule guarantee about the committed output?
Rejection resamples from a corrected distribution, so the committed tokens are distributed exactly as the target alone would produce. It is exact, not approximate.
Which single quantity most determines the speedup you actually get?
Speedup rises with acceptance rate. A draft the target rarely accepts commits about one token per round and can even lose to baseline after draft overhead.
When is n-gram / prompt-lookup drafting an especially strong fit?
Prompt-lookup proposes spans it already saw in the running text, so repetitive workloads (summarisation, RAG quotation, code edits) hit high acceptance with zero extra weights.
