Module 02 · Advanced context engineering · Lesson 0250

One useful tool is about forty lines, and mounting it changes what the model plans

foundation 13 min Both servers below were built and driven with raw JSON-RPC while this page was written. · Build an MCP server

The one-minute version

  • The same server - one tool, one resource, one prompt - is 41 lines of Python and 66 lines of TypeScript.
  • The two languages disagree about where the contract comes from: one derives the schema from type hints and a docstring, the other from a schema you write.
  • Drive it by hand before any client touches it. Four requests over stdin and stdout, no handshake, and the wire stops being a mystery.
  • Mounting is one committed file, and in Claude Code a project-scoped server waits for a human to approve it before the model ever sees the schema.

1. The server, in TypeScript

Three files. The dependencies first, then the project shape, then the program. The tool is deliberately dull: count the lines in a file, so an agent can decide whether reading the whole thing is worth the budget from lesson 0200.

src/index.ts · written for this page, against @modelcontextprotocol/server 2.0.0 · CC BY 4.0 with the rest of this repository · compiles clean under strict
#!/usr/bin/env node
// A minimal MCP server: one tool, one resource, one prompt, over stdio.

import { McpServer } from "@modelcontextprotocol/server";
import { StdioServerTransport } from "@modelcontextprotocol/server/stdio";
import { promises as fs } from "node:fs";
import { z } from "zod";

const server = new McpServer({ name: "repo-facts", version: "1.0.0" });

server.registerTool(
  "count_lines",
  {
    description:
      "Count the lines in a UTF-8 text file and return the number. " +
      "Use it to size a file before deciding whether to read the whole thing. " +
      "It does not return the contents, and it fails on a file that is not UTF-8 text.",
    inputSchema: z.object({
      path: z.string().describe("Absolute path to the file to count"),
    }),
  },
  async ({ path }) => {
    try {
      const text = await fs.readFile(path, "utf8");
      const lines = text === "" ? 0 : text.split("\n").length - (text.endsWith("\n") ? 1 : 0);
      return { content: [{ type: "text", text: String(lines) }] };
    } catch (err) {
      return {
        isError: true,
        content: [{ type: "text", text: `cannot count ${path}: ${(err as Error).message}` }],
      };
    }
  },
);

server.registerResource(
  "conventions",
  "repo://conventions",
  { description: "The repository's coding conventions", mimeType: "text/markdown" },
  async (uri) => ({
    contents: [{ uri: uri.href, mimeType: "text/markdown", text: "# Conventions\n\n- One idea per commit.\n" }],
  }),
);

server.registerPrompt(
  "review_file",
  {
    description: "Ask for a focused review of one file",
    argsSchema: z.object({ path: z.string().describe("File to review") }),
  },
  ({ path }) => ({
    messages: [
      { role: "user" as const, content: { type: "text" as const, text: `Review ${path}. Name defects only, most severe first.` } },
    ],
  }),
);

async function main(): Promise<void> {
  await server.connect(new StdioServerTransport());
  console.error("repo-facts MCP server running on stdio");
}

main().catch((err: unknown) => {
  console.error("fatal:", err);
  process.exit(1);
});

Build it with npx tsc and you have build/index.js. Nothing here is framework: registerTool, registerResource and registerPrompt are the three primitives from lesson 0240, one call each.

2. The same server, in Python

install · the SDK, with the optional command-line extra
pip install "mcp[cli]"      # or: uv add "mcp[cli]"
repo_facts.py · written for this page, against mcp 2.1.1 · CC BY 4.0 with the rest of this repository · run with raw JSON-RPC while writing it
"""A minimal MCP server: one tool, one resource, one prompt, over stdio."""

from pathlib import Path

from mcp.server import MCPServer

mcp = MCPServer("repo-facts")


@mcp.tool()
def count_lines(path: str) -> str:
    """Count the lines in a UTF-8 text file and return the number.

    Use it to size a file before deciding whether to read the whole thing.
    It does not return the contents, and it fails on a file that is not
    UTF-8 text.

    Args:
        path: Absolute path to the file to count.
    """
    try:
        text = Path(path).read_text(encoding="utf-8")
    except (OSError, UnicodeDecodeError) as err:
        return f"cannot count {path}: {err}"
    return str(len(text.splitlines()))


@mcp.resource("repo://conventions", mime_type="text/markdown")
def conventions() -> str:
    """The repository's coding conventions."""
    return "# Conventions\n\n- One idea per commit.\n"


@mcp.prompt()
def review_file(path: str) -> str:
    """Ask for a focused review of one file."""
    return f"Review {path}. Name defects only, most severe first."


if __name__ == "__main__":
    mcp.run(transport="stdio")

Twenty-five fewer lines, and none of the difference is terseness. The Python SDK reads the type hints and the docstring and builds the schema and the description from them, so the contract is written where the function is. The TypeScript SDK asks you for a Zod schema and a description string, so the contract is written beside the function. Neither is better; they fail differently, and the next section shows how.

3. Drive it by hand, before a client touches it

Both servers speak stdio: newline-delimited JSON-RPC on stdin and stdout. So you can drive one from a script with no client, no editor and no model, which is the fastest way to find out whether your server works and the only way to see exactly what the model will be shown. Under revision 2026-07-28 there is nothing to do first: the four requests below are the whole session.

5. Mount it, from a file you commit

Both editors read a top-level mcpServers object, so a server moves between them with almost no edit. Claude Code takes the file at .mcp.json in the repository root as the project scope, which is the one shared through version control.

.mcp.json · Claude Code project scope · Anthropic documentation, quoted with attribution · reproduced verbatim in shape
{
  "mcpServers": {
    "repo-facts": {
      "type": "stdio",
      "command": "node",
      "args": ["./mcp-servers/repo-facts/build/index.js"]
    }
  }
}
.cursor/mcp.json · Cursor project scope · Cursor documentation, quoted with attribution · documented rather than run
{
  "mcpServers": {
    "repo-facts": {
      "command": "node",
      "args": ["./mcp-servers/repo-facts/build/index.js"]
    }
  }
}

Three differences are worth knowing before you copy one file to the other. Claude Code requires an explicit "type" on a url entry, and reads a typeless entry as stdio: the failure is a skipped server and a message naming it, not a guess. Cursor infers the transport from the presence of url. And the two expand variables differently: Claude Code uses ${VAR} and ${VAR:-default} plus ${CLAUDE_PROJECT_DIR}, while Cursor uses ${env:NAME}, ${workspaceFolder} and ${userHome}.

Quoted from the same page: "Verify you trust each server before connecting it. Servers that fetch external content can expose you to prompt injection risk." A mounted server is a program running on your machine as you, and its tool descriptions are text that reaches the model. Module 7 owns that attack in full, in The agent attack surface; the thing to hold from here is that the approval prompt is the last human gate and headless runs do not have it, so disabledMcpjsonServers and --strict-mcp-config exist for exactly that case.

6. What actually changed for the model

Nothing, except that there is one more tool schema in the request. No new capability arrived in the model, no protocol reached it, and the loop from module 1 runs exactly as it did before. That is the payoff of lesson 0240's layering and it is also the warning: you have just added a permanent per-turn cost to every task the agent does, useful or not. Lesson 0270 is when not to.

For what a server must never do once other people depend on it - durable state, isolation, what it may reach - Context and Protocol, in Production Agent Engineering, is the sibling that owns it, and this page deliberately stops short of it.

Check yourself

Retrieval practice

Answer from memory before revealing.

Your Python server works alone and every client call fails with a parse error. What do you check first?
On stdio the transport is the process's own standard output, and the rule is that nothing but a valid MCP message may go there, so one stray print corrupts the framing. The first option describes a handshake this revision does not have. The third and fourth are real quality questions about a tool definition and neither can produce a parse error, because both live inside a message that parses.
You write the same tool in both SDKs. Which difference costs context on every turn?
The output schema is part of the tool definition, so it is in the request on every turn whether or not the tool is called - which is why the Python entry measured 592 characters against 449. The first option is the convenience that produces it, not the cost. The second is a build-time difference the model never sees, and the third is in a result, so it is paid once per call rather than once per turn.

Practice about 45 minutes, with a terminal

Practice 1foundation

Write one MCP server exposing one tool your capstone repository actually wants: a test-runner summary, a schema lookup, a deploy-status check. Either language.

Drive it by hand first with a script that writes JSON-RPC to its stdin and reads its stdout, exactly as the trace above does. Then mount it from committed configuration in two clients and confirm the approval gate fires before the tool is usable.

Measure the definition your server sends: the length of its single tools entry, in characters. Divide by four for a rough token count.

Hint

Your probe script needs about twenty lines: spawn the server, write each request followed by a newline, and split the output on newlines. Give the process a moment before closing stdin, because a response can arrive out of order relative to the requests.

Show what a good pass looks like
  1. Pick a tool with a real answer. Something that returns a number or a short list. A tool that returns a whole file has spent your budget for you, which is the failure lesson 0260 opens with.
  2. Probe before mounting. Four requests, no handshake. If tools/list works from a script, every client failure after that is configuration rather than code.
  3. Read the description that came back, not the one you wrote. In Python they differ: the Args: block travels with it.
  4. Mount in both clients from files in the repository, not from a global config, so a colleague cloning the repository gets the same server.
  5. Watch the approval prompt. If it did not appear, you are in a non-interactive session or the choice is already remembered, and both are worth knowing about your own setup.
  6. Divide the entry length by four. That is roughly what this tool now costs on every turn of every task, forever.

Sanity check. One tool with a four-sentence description and a single string parameter lands somewhere around 400 to 700 characters, so roughly 100 to 175 tokens per turn. If yours is over 2,000 characters the schema is carrying something that belongs in the tool result instead, and if it is under 150 the description is almost certainly too thin for the model to know when to use it.

Your teacher. If the probe feels fiddly, ask your agent to write the twenty-line script for your language and then explain each line of the request it constructs. If you want to feel the difference the tool makes, ask the same agent the same question twice - once with the server mounted and once without - and compare how many tool calls each answer took.
