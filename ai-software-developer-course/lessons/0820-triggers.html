A trigger is an authorisation decision wearing an integration's clothes

working 10 min Read from the published trigger contracts of a code host, a chat integration and an issue tracker. · Claude Code GitHub Actions

The one-minute version

  • Four trigger families cover almost everything: a code-host event, a chat mention, a tracker delegation, and a schedule.
  • The question a trigger answers is not "how do I start an agent" but who may start one, on what, with what permissions.
  • Two checks run before the agent does: the triggering user needs write access, and a bot actor is rejected unless you allowlist it. The second is what stops a loop.
  • The trigger also decides what text reaches the model. An issue body written by a stranger is a trigger input, and it arrives in the same flat prompt as your instructions.

1. Four families, and what each one carries

A trigger family is defined by where the event comes from, because that decides both the authorisation check available to you and the text the agent will read.

FamilyWho can fire itWhat context it carriesThe authorisation check
Code-host eventanyone who can open an issue or commentthe issue or pull request, its body, its diffrepository write access, plus your own if: guard
Chat mentionanyone in the channelthe thread, and recent channel messageschannel membership, and whose account the session runs under
Tracker delegationanyone who can edit the issuethe issue, the comment, the projectthe app install, and the scopes it was granted
Schedulenobody, at run timeonly what the prompt namesnone at run time, so all of it is in the file

Read the last column downwards. The check gets weaker as you go down and the surface gets quieter, which is the opposite of the intuition that an automated trigger is the safest one.

2. The file, read line by line

The smallest real example of a code-host trigger is the workflow the vendor ships. Every line in it is either an event, a guard, or a permission, and there is nothing else in the file.

.github/workflows/claude.yml · anthropics/claude-code-action, examples/claude.yml · MIT · reproduced verbatim
name: Claude Code

on:
  issue_comment:
    types: [created]
  pull_request_review_comment:
    types: [created]
  issues:
    types: [opened, assigned]
  pull_request_review:
    types: [submitted]

jobs:
  claude:
    if: |
      (github.event_name == 'issue_comment' && contains(github.event.comment.body, '@claude')) ||
      (github.event_name == 'pull_request_review_comment' && contains(github.event.comment.body, '@claude')) ||
      (github.event_name == 'pull_request_review' && contains(github.event.review.body, '@claude')) ||
      (github.event_name == 'issues' && (contains(github.event.issue.body, '@claude') || contains(github.event.issue.title, '@claude')))
    runs-on: ubuntu-latest
    permissions:
      contents: write
      pull-requests: write
      issues: write
      id-token: write
      actions: read # Required for Claude to read CI results on PRs
    steps:
      - name: Checkout repository
        uses: actions/checkout@v6
        with:
          fetch-depth: 1

      - name: Run Claude Code
        id: claude
        uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}

Four things in that file are worth more than the rest of it put together.

The on: block is the trigger surface, and it is four events wide. The if: block is a guard whose job is not correctness but cost: the action checks the trigger phrase itself, and the guard exists so a runner never starts on a comment that does not mention the agent. id-token: write is required for the action's default GitHub App authentication, so it is not optional even though it looks like an extra. And permissions: is the whole blast radius of a run, written down in five lines that a reviewer can argue with.

Interactive mode is what that file selects, because it supplies no prompt. Add a prompt input and the same action switches to automation mode, which "runs without waiting for a mention, subject only to the checks on who can trigger runs" and can therefore hang off any GitHub event at all, including a cron schedule.

3. The two checks that run before the agent

This is the part that turns an integration into an authorisation contract, and it is the part nobody reads.

The documentation states both checks plainly. On write access: "on issue and pull request events, the triggering user must have write access to the repository", with allowed_non_write_users as the deliberate exception you take when a stranger's issue is the whole point. On the second: the action "rejects a bot actor unless you list it in allowed_bots, which keeps bots from triggering Claude in a loop". Scheduled runs skip the first check, because no user authored the event, and are still subject to the second.

4. Delegation, which is a different verb

An issue tracker adds a trigger family with its own vocabulary, and the vocabulary is the teaching. In Linear's agent model an issue is assigned to a human and delegated to an agent: the app "sets the app as the delegate, not the assignee", so ownership stays with a person while the action moves. Two scopes are what make an app an agent rather than an integration.

OAuth authorization URL · composed from the parameters at linear.app/developers/agents · this course, CC BY 4.0 · reproduced verbatim
https://linear.app/oauth/authorize
  ?client_id=<your client id>
  &redirect_uri=<your redirect uri>
  &response_type=code
  &scope=read,write,app:assignable,app:mentionable
  &actor=app

app:assignable is documented as "Allow the app to be assigned as a delegate on issues and made a member of projects" and app:mentionable as "Allow the app to be mentioned in issues, documents, and other editor surfaces". The ceiling is worth pointing at: an integration installed this way is "not able to also request admin scope". The delegation model has a deliberate limit written into the grant.

The lifecycle has one number in it that shapes how you build. A delegation fires a created session webhook, and the agent must "Emit a thought activity within 10 seconds to acknowledge the session has begun". Ten seconds is not enough to plan, so the acknowledgement and the work are two different things, and your integration has to answer before it knows what it is going to do.

5. A trigger also decides what text arrives

A chat trigger makes this concrete. A mention in Slack creates a session under the mentioning user's own account, "using your connected repositories and your plan limits", which makes channel membership the real access control rather than anything in a settings page. And the documentation carries its own warning: "Claude may follow directions from other messages in the context, so users should make sure to only use Claude in trusted Slack conversations."

That is the general shape. A trigger is not only an authorisation decision about who starts the run, it is also a decision about whose words are in the first turn.

The full treatment of untrusted text entering a turn is module 7's, and the general case - data crossing into an instruction position - is stated in Production Systems. What belongs here is narrower and specific to this module: the trigger you choose determines which foreign text is in the turn, before any prompt is written.

6. Schedules, the quietest family

A scheduled trigger has no actor, no context beyond its prompt, and nobody watching the first run that fails. It also has two documented behaviours that surprise people: "GitHub runs scheduled workflows only from the default branch and, in public repositories, disables the schedule after 60 days without repository activity."

Both of those fail silently. A schedule you develop on a branch never runs, and a schedule on a quiet public repository stops after sixty days without telling you. If you build anything on a schedule, build the check that it ran: a job that has produced no output in a week is indistinguishable from a job that has produced nothing to report.

Check yourself

Retrieval practice

Answer from memory before revealing.

Your agent opens a pull request, and its own comment on that pull request matches your trigger. What prevents an endless loop?
The human-actor check runs on every event and rejects a bot unless it is listed, which is documented as existing for exactly this reason. The second option ends one run and does nothing about the next one. The third is a cost guard rather than a loop guard, and it happily matches a mention written by a bot. The fourth is real but is a capacity control, so it would let the loop run and then be throttled rather than stopping it.
Which trigger family gives you the weakest authorisation check at the moment it fires?
A schedule has no triggering user, so the write-access check is skipped and the whole contract is whatever the file says. The other three all have a person behind them at the moment of firing, and therefore a check the platform can run. The fourth is the strongest of the four in practice, because channel membership is the access control - which is also why an invite is a grant.

Practice about 25 minutes, with a repository you own

Practice 1working

Write the trigger contract for your capstone repository before you write any workflow. Four sentences, one per row of the table below, and no YAML yet.

Who may start an agent here? On what may they start it? With what permissions does it run? What stops it firing on its own output?

Then translate each sentence into the line of a workflow file that enforces it, and mark the sentences that no line can enforce. Those are the ones that need a human process instead.

Hint

Three of the four have a direct spelling in a workflow file: the on: block, the permissions: block, and the actor checks the action performs for you. The fourth - "on what" - is usually a mix of the event type and your own if: guard, and it is the one people write loosest.

Show a worked contract
  1. Who. "Anyone with write access to this repository." That is the platform's default and needs no line at all. If you want anyone who can file an issue, that is allowed_non_write_users, and it is a deliberate widening rather than a convenience.
  2. On what. "An issue carrying the label agent:implement." In a file that is on: issues: types: [labeled] plus a guard on the label name. Labels are a good choice here because applying one already requires write access on most repositories, so the label is doing authorisation work as well as selection.
  3. With what permissions. "Write to contents and pull requests, read Actions, and nothing else." That is the permissions: block, and every entry in it should be one you can justify out loud. id-token: write is the exception you keep without arguing, because the action's authentication needs it.
  4. What stops it. "The bot-actor check, which is on by default." Write it down anyway: the sentence is what you will check against the day somebody adds allowed_bots to make an integration work.

Sanity check. If your permissions block has write against something the agent never touches, the contract is wider than the work. A run that only triages issues needs contents: read, not contents: write, and the shipped triage example is exactly that shape.

Your teacher. Paste your workflow file to your agent and ask it, for each line, which of the four contract questions that line answers. Any line that answers none of them is either boilerplate or a permission nobody decided on, and the second kind is worth finding.
