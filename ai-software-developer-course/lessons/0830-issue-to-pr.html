Module 08 · Background agents · Lesson 0830

The pipeline is the product and the agent is one stage in it

working 9 min Built on three workflow files that ship with the vendor's own action, read complete rather than in excerpt. · claude-code-action examples

The one-minute version

  • An issue becomes a pull request through eight stages, and the agent is one of them. The other seven are yours to design, and they decide whether the one in the middle is worth anything.
  • Triage comes first, because an agent given a bad issue produces a bad pull request faster than a person would.
  • Four stages can be automated - triage, implement, review, fix-CI - and each carries a different risk with a different named guard.
  • The most dangerous of them is the closed loop, where CI failure starts a run. The vendor ships that workflow with its own security warning in the file, and stripping the warning would be the wrong lesson.

1. Draw the path, then name who owns each stage

Eight stages, and the ownership pattern is the interesting part. Two are unambiguously a person's, four can be an agent's, and two belong to the platform.

2. Triage first, because a bad issue is worse than no issue

An agent given a vague issue does not stop to ask. It picks a reading and implements it, which produces a plausible pull request against the wrong requirement, and the review cost lands on you. Triage is therefore the highest-value stage to automate and the cheapest one to get right, because its output is a label and a comment rather than a diff.

The smallest real example ships with the action. Read the permissions block first.

.github/workflows/issue-triage.yml · anthropics/claude-code-action, examples/issue-triage.yml · MIT · reproduced verbatim
name: Claude Issue Triage
description: Run Claude Code for issue triage in GitHub Actions
on:
  issues:
    types: [opened]

jobs:
  triage-issue:
    runs-on: ubuntu-latest
    timeout-minutes: 10
    permissions:
      contents: read
      issues: write

    steps:
      - name: Checkout repository
        uses: actions/checkout@v6
        with:
          fetch-depth: 0

      - name: Run Claude Code for Issue Triage
        uses: anthropics/claude-code-action@v1
        with:
          # NOTE: /label-issue requires .claude/commands/label-issue.md and scripts/edit-issue-labels.sh in your repo (see this repo for examples)
          prompt: "/label-issue REPO: ${{ github.repository }} ISSUE_NUMBER: ${{ github.event.issue.number }}"

          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
          allowed_non_write_users: "*" # Required for issue triage workflow, if users without repo write access create issues
          github_token: ${{ secrets.GITHUB_TOKEN }}

Three lines in it carry the lesson. contents: read is a triage job that cannot write code, which is the permission block matching the work rather than the tool. timeout-minutes: 10 is a ceiling at the workflow level, which is a different ceiling from anything you set on the agent. And allowed_non_write_users: "*" is the deliberate widening from lesson 0820, with the file's own comment giving the reason: triage is worthless if it ignores issues from people without repository access.

3. The implementation stage is the least interesting one

It is the same loop from module 1, running in the box from lesson 0800. What makes it useful or useless is entirely outside it: the quality of the issue, the conventions in the repository, and the tools the run was allowed. Here is that stage as a file you can commit, built from the documented inputs.

Two of those parts are cost controls that people confuse. timeout-minutes caps the runner's wall clock, so it stops a run that is stuck. --max-turns caps how many times round the loop the agent goes, so it stops a run that is busy and wrong. A job can hit either without hitting the other, and only the second one is documented as a way to lower the token bill.

The --allowedTools list is module 7's permission model arriving here unchanged. It is worth noticing that it travels: the same syntax that narrows a local agent narrows an unattended one, and in a background run there is nobody to approve an exception.

4. The closed loop, and the warning that ships with it

The fourth automatable stage is the one that closes the circle: CI fails, a workflow starts an agent on the failing branch, and the agent pushes a fix. It is the most useful of the four and the most dangerous, and the vendor's own example says so in the file itself.

.github/workflows/ci-failure-auto-fix.yml · anthropics/claude-code-action, examples/ci-failure-auto-fix.yml · MIT · reproduced verbatim, comment block included
name: Auto Fix CI Failures

# ⚠️ SECURITY NOTE
#
# This workflow checks out the PR branch and runs build/test commands
# (npm, bun, etc.) against it with elevated permissions (contents:write,
# id-token:write). This means code from the PR branch executes in a
# trusted context with access to secrets and the ability to push to the
# repository.
#
# Only use this workflow in repositories where everyone with write access
# is fully trusted with these permissions. Do not use this in repositories
# that accept contributions from untrusted or semi-trusted collaborators.
#
# The pull_requests[0] check below limits this to same-repo PRs (fork PRs
# are excluded), but anyone who can push a branch to this repository can
# control what code runs here.

on:
  workflow_run:
    workflows: ["CI"]
    types:
      - completed

permissions:
  contents: write
  pull-requests: write
  actions: read
  issues: write
  id-token: write # Required for OIDC token exchange

jobs:
  auto-fix:
    if: |
      github.event.workflow_run.conclusion == 'failure' &&
      github.event.workflow_run.pull_requests[0] &&
      !startsWith(github.event.workflow_run.head_branch, 'claude-auto-fix-ci-')
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@v6
        with:
          ref: ${{ github.event.workflow_run.head_branch }}
          fetch-depth: 0
          token: ${{ secrets.GITHUB_TOKEN }}

      - name: Setup git identity
        run: |
          git config --global user.email "claude[bot]@users.noreply.github.com"
          git config --global user.name "claude[bot]"

      - name: Create fix branch
        id: branch
        env:
          HEAD_BRANCH: ${{ github.event.workflow_run.head_branch }}
          RUN_ID: ${{ github.run_id }}
        run: |
          SAFE_BRANCH=$(printf '%s' "$HEAD_BRANCH" | tr -cd 'a-zA-Z0-9/_.-')
          BRANCH_NAME="claude-auto-fix-ci-${SAFE_BRANCH}-${RUN_ID}"
          git checkout -b "$BRANCH_NAME"
          echo "branch_name=$BRANCH_NAME" >> "$GITHUB_OUTPUT"

      - name: Get CI failure details
        id: failure_details
        uses: actions/github-script@v7
        with:
          script: |
            const run = await github.rest.actions.getWorkflowRun({
              owner: context.repo.owner,
              repo: context.repo.repo,
              run_id: ${{ github.event.workflow_run.id }}
            });

            const jobs = await github.rest.actions.listJobsForWorkflowRun({
              owner: context.repo.owner,
              repo: context.repo.repo,
              run_id: ${{ github.event.workflow_run.id }}
            });

            const failedJobs = jobs.data.jobs.filter(job => job.conclusion === 'failure');

            let errorLogs = [];
            for (const job of failedJobs) {
              const logs = await github.rest.actions.downloadJobLogsForWorkflowRun({
                owner: context.repo.owner,
                repo: context.repo.repo,
                job_id: job.id
              });
              errorLogs.push({
                jobName: job.name,
                logs: logs.data
              });
            }

            return {
              runUrl: run.data.html_url,
              failedJobs: failedJobs.map(j => j.name),
              errorLogs: errorLogs
            };

      - name: Fix CI failures with Claude
        id: claude
        uses: anthropics/claude-code-action@v1
        with:
          prompt: |
            /fix-ci 
            Failed CI Run: ${{ fromJSON(steps.failure_details.outputs.result).runUrl }}
            Failed Jobs: ${{ join(fromJSON(steps.failure_details.outputs.result).failedJobs, ', ') }}
            PR Number: ${{ github.event.workflow_run.pull_requests[0].number }}
            Branch Name: ${{ steps.branch.outputs.branch_name }}
            Base Branch: ${{ github.event.workflow_run.head_branch }}
            Repository: ${{ github.repository }}

            Error logs:
            ${{ toJSON(fromJSON(steps.failure_details.outputs.result).errorLogs) }}
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
          claude_args: "--allowedTools 'Edit,MultiEdit,Write,Read,Glob,Grep,LS,Bash(git:*),Bash(bun:*),Bash(npm:*),Bash(npx:*),Bash(gh:*)'"

Three things in that file deserve to be read twice.

The comment block is the best short statement in this module of when not to automate. It says the workflow "checks out the PR branch and runs build/test commands ... against it with elevated permissions", which means "code from the PR branch executes in a trusted context with access to secrets and the ability to push to the repository", and concludes that you should only use it where "everyone with write access is fully trusted with these permissions".

The branch guard is the loop prevention from lesson 0820, spelled a second way. !startsWith(github.event.workflow_run.head_branch, 'claude-auto-fix-ci-') stops the workflow from firing on the branch it just created. The actor check would not have caught this one, because the CI run is attributed to the branch rather than to a commenting bot.

The branch name is sanitised before it is used. tr -cd 'a-zA-Z0-9/_.-' strips everything else out of a value that arrived in an event payload. A branch name is attacker-influenced input in a repository that accepts branches, and it is being pasted into a shell variable.

Do not copy that workflow into a repository that takes contributions from people you do not know. The file's own comment is the reason, and it is more specific than a general caution: the pull_requests[0] check excludes forks, "but anyone who can push a branch to this repository can control what code runs here". The version of this stage that is safe for an open repository runs with read-only permissions and posts a suggestion, which is a different pipeline rather than the same one with a flag flipped.

Retrieval practice

Answer from memory before revealing.

You have budget to automate exactly one stage of the pipeline. Which one usually returns most, and why?
Triage is upstream of everything and its output is a label rather than a diff, so it is both the highest leverage and the cheapest to contain. The first option is the standard mistake: an agent implementing the wrong requirement moves the cost to review rather than removing it. The third is a real gain and it is module 6's subject, and it still arrives after the wrong work has been done. The fourth is the highest-risk stage of the four, which is a poor place to start.
The auto-fix workflow's if: block rejects branches starting with claude-auto-fix-ci-. What is that guard for?
CI runs on the fix branch too, so without the guard a failure there starts another auto-fix run on another new branch, indefinitely. The first option describes worktree and merge-queue contention, which is the next lesson. The second is a review policy rather than anything this line does. The third is the neighbouring pull_requests[0] check, which is a genuinely different guard in the same block - a strong distractor because both live in the same four lines.

Practice about 30 minutes, with a repository you own

Practice 1working

Take the pipeline drawing above and mark your own repository against it. For each of the eight stages, write one of three words: person, agent, or nobody.

Most repositories score nobody on at least two stages, and the interesting ones are almost never the implementation stage. Find yours.

Then add the triage workflow to your repository, file one deliberately under-specified issue, and read what it produces. Do not fix the issue first: the point of the exercise is to see what triage says about an issue an agent could not have implemented.

Hint

The triage example depends on two files of its own, which its comment names: a command definition and a script that edits labels. Read that comment before you copy the file, or the run will fail on a prompt that invokes something that is not there.

Show what a good answer looks like
  1. The two stages that score nobody are usually triage and review. Both are unglamorous, both are the stages a small team quietly drops, and both are the ones an agent is best at. That is the finding, and it is more useful than any diff.
  2. An under-specified issue produces a revealing triage comment. A good one names what it could not determine - which component, what the expected behaviour is, how anyone would know it was fixed - and those three questions are exactly the ones lesson 0850 says must be answered before an unattended run.
  3. Read the permission block against the work it did. Triage wrote a label and a comment, and it had contents: read. If you widened that to write while copying the file, you granted a stage the ability to change code for no reason, which is the most common way a pipeline's blast radius grows.

Sanity check. If every stage in your marking scored person, the pipeline is a description of your team rather than a pipeline, and adding an agent to the middle of it will not change the throughput. Find the stage that is currently skipped rather than the stage that is currently slow.

Your teacher. Hand your agent the eight-stage drawing and your repository, and ask it which stage a change most often waits at. Then ask what evidence it used. If the evidence is the pull request timestamps, it is a real answer; if it is a general claim about software teams, ask again with the data.
