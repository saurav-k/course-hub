Three scanners, three questions, three kinds of noise

working 9 min Built from the vendors' own documentation for the three scanner families. · Semgrep, introduction

The one-minute version

  • SAST reads your first-party source and asks whether the code is shaped wrongly. It never opens a lockfile.
  • SCA reads your dependency manifests and asks whether any named package has a published advisory. It never reads your logic.
  • Secret scanning reads text, including history, and asks whether a live credential is sitting in it.
  • Each family has its own false-positive economy, and each has a documented fix for it: reachability for SCA, validation for secrets, and a rule you wrote yourself for SAST.
  • The rule the rest of this module uses: a finding you cannot act on costs more than no finding, because it trains the team to close the tab.

1. One commit, three red checks, three different reasons

Open a pull request on a repository with the usual gates and you can fail three checks at once without any two of them being about the same thing. One says your code passes a request parameter into a shell. One says a package four levels down your dependency tree has an advisory. One says the string in config/test_fixtures.py looks like an AWS key. Three tools, three inputs, three questions, and the only thing they share is the pull request they landed on.

The reason to hold them apart is not tidiness. It is that each family fails in a different direction, so the thing you do about a wall of findings is different in each case, and a team that treats "the security check is red" as one signal ends up muting all three.

2. SAST asks whether the code is shaped wrongly

Static application security testing reads source without running it and reports where the code matches a dangerous shape. Semgrep describes its own SAST product as detecting vulnerabilities "in your first-party code", and its community scanner as covering "over 30 programming languages". That is the whole promise and it is worth reading literally: first-party, and shape.

The noise here comes from shape being a proxy for danger. subprocess.run with a variable in it is a shape; whether the variable can hold anything an outsider chose is a different question, and a pattern match cannot answer it. That gap is what the next lesson closes with dataflow, and it is why the fix for SAST noise is usually a rule you narrowed yourself rather than a setting.

3. SCA asks whether a named package has an advisory

Software composition analysis reads what your manifests declare and matches it against a vulnerability database. OSV-Scanner is the officially supported front end to the OSV database, whose design goal is stated as "fewer, more actionable vulnerability notifications, which reduces the time needed to resolve them".

The noise here has a specific shape: the advisory is real, the package is genuinely in your tree, and the vulnerable function is never called from your code. Reachability is the documented answer. Semgrep Supply Chain classifies a finding three ways rather than two - reachable, unreachable, and no reachability analysis - and it is candid that it "does not perform reachability analysis" on transitive dependencies, where you get version matching alone.

Read that caveat next to your own dependency tree before you promise anybody a quiet backlog. Most advisories in a modern JavaScript or Python project arrive through packages you never named, and those are exactly the findings that come back with no reachability verdict at all.

4. Secret scanning asks whether the credential is live

A secret scanner reads text - the diff, the working tree, and the history behind both - and flags things shaped like credentials. TruffleHog classifies "over 800 secret types", which is a detector count rather than a claim about your repository.

The noise here is fixtures, rotated keys and example values. Validation is the documented answer: the detector calls the issuing service and reports what came back. TruffleHog's AWS detector "performs a GetCallerIdentity API call against the AWS API to verify if an AWS credential is active", and the result is verified, unverified or unknown, with --results deciding which of the three you are shown. Semgrep Secrets runs the same idea locally and is explicit that "No tokens are sent to Semgrep servers".

Notice what validation changes. It does not make the scanner better at finding strings. It replaces a guess about a string with a fact about an account, which is the only thing that turns a page of matches into a queue you can work down.

6. The rule the rest of this module uses

Every mechanism in the next seven lessons is chosen for the same reason: it turns a finding into something a person, or an agent, can act on without a meeting. Reachability does it by ranking. Validation does it by checking. A rule you wrote does it by encoding what your team actually cares about. Diff-aware scanning, which arrives in lesson 0750, does it by only showing you what this branch introduced.

The failure that all four are aimed at is one you have already lived through: a backlog whose size makes it unreadable, so nobody reads it, so a genuinely reachable finding sits in it for a year. Volume is a security control that fails open.

Check yourself

Retrieval practice

Answer from memory before revealing.

A dependency four levels down your tree carries a published advisory. Which scanner family raised it, and what makes the finding actionable?
Only SCA reads manifests, so only SCA can see a transitive package at all. Reachability is the documented way to rank such a finding - though Semgrep states plainly that transitive dependencies get version matching and no reachability verdict, which is why this exact case is the hard one. The first option describes a SAST remedy applied to a dependency SAST never reads; the second confuses a package advisory with a credential; the fourth is the mistake this page exists to prevent, since a lockfile is data to SAST and not code.
Your secret scanner reports 40 matches and your team ignores all of them. Which change most directly makes the list workable?
Validation replaces a guess about a string with a fact about an account, which is exactly the enrichment the verdict chart is about. Raising a threshold shortens the list by dropping real secrets as readily as fixtures, and you never learn which. Dropping history reads is worse than useless here, because a credential removed from the working tree is precisely the one still sitting in the objects. Moving the job changes when you ignore the list, not whether.

Practice about 20 minutes, with your own repository

Practice 1working

Open the security findings your capstone repository already has - the Dependabot alerts tab, an existing scanner report, or the output of one local run of osv-scanner.

Take the first ten findings and, for each one, write down two things: which of the three families it came from, and what a fix would actually be - a code change, a version bump, or a rotation. Then mark each one actionable today or not, and write one word for why not.

Hint

If you cannot tell which family a finding came from, look at what it names. A file and a line number is SAST. A package and a version range is SCA. A string and a commit is a secret finding.

Show what the ten usually look like
  1. Most of them are SCA. Dependency advisories outnumber everything else in a normal repository, because a single lockfile can pull thousands of packages and every one of them has a version number to match against.
  2. Their "why not" is nearly always the same word: unreachable, or unknown. That is the reachability gap, and it is where the noise fix belongs rather than in a mute button.
  3. The secret findings split cleanly in two once you ask whether anybody validated them. Unvalidated, they all look identical. That is the whole argument for validation.
  4. The SAST findings are the fewest and the most argued about, because a shape is a proxy and your team has opinions about whether this instance is real. Those opinions are what a rule you write yourself encodes.

Sanity check. If every one of your ten came out actionable, you are almost certainly reading a filtered view rather than the raw list. If none did, check whether the tool that produced them offers a verdict beyond "found" - that missing verdict is usually the whole problem.

Your teacher. Ask your agent to run one scanner of each family over a repository you own and to report only the counts, then to tell you which counts it would not trust and why. If it gives you a single combined number, ask it which of the three questions that number answers - the answer is that it answers none of them.
