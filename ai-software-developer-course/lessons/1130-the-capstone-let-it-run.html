Capstone · Read after module 08 · Lesson 1130

Let it run with a ceiling, then point it at a repository that is not yours

frontier 10 min The last of four capstone stops, and the one where the open-source contribution track begins. · Claude Code GitHub Actions

The one-minute version

  • You have just finished module 8, and modules 7 and 8 land together here: an unattended pipeline is only defensible once the thing it runs inside has a boundary.
  • A ceiling has four terms and they bound four different things: turns, wall-clock, concurrency, and what a command may touch. Three of the four are one line each.
  • The pipeline's honest test is that somebody who is not you starts it and the merge still needs a human.
  • Then run it against a project you did not write. Three public policies reach three different answers, and none of them is arguing about code quality.

1. Unattended means it cannot ask you anything

The definition is operational rather than philosophical: nobody is at the keyboard, so every question the agent would have asked has to already be answered in the repository. That is what stops one, two and three were for, and it is why this stop comes last.

Two checks decide who may start a run, and both are worth knowing by name because both fail closed. The documentation states that on issue and pull request events "the triggering user must have write access to the repository", and that on every event a bot actor is rejected "unless you list it in allowed_bots, which keeps bots from triggering Claude in a loop". The second one also applies to scheduled runs, which GitHub attributes to a repository user - usually whoever last edited the cron line.

.github/workflows/agent-on-label.yml · composed for this course from the documented action inputs · hub content, CC BY 4.0 · reproduce freely
name: Agent on label
on:
  issues:
    types: [labeled]

concurrency:
  group: agent-${{ github.event.issue.number }}
  cancel-in-progress: false

jobs:
  implement:
    if: github.event.label.name == 'agent:implement'
    runs-on: ubuntu-latest
    timeout-minutes: 20
    permissions:
      contents: write
      pull-requests: write
      issues: write
      id-token: write
    steps:
      - uses: actions/checkout@v6
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
          prompt: |
            Implement the issue below. Follow AGENTS.md. Run `make verify` and
            paste its last line. Open a pull request against `dev`. If the issue
            does not say enough to finish, open no pull request and comment with
            the single question you would have asked.
          claude_args: |
            --max-turns 40
            --model claude-sonnet-5

2. The ceiling has four terms

A spend ceiling is not one number, and treating it as one is how people end up with a runaway job and a bill they cannot attribute. Four independent limits bound four different quantities, and the workflow above carries three of them.

--max-turns bounds the loop, which is the unit the agent actually spends. timeout-minutes bounds wall-clock, which is what catches a turn that hangs rather than iterates. concurrency bounds how many runs exist at once, which is the term that matters the moment you label three issues in a minute. And the sandbox bounds reach - what any command inside the run may read, write or connect to - which is the only one of the four that is not about cost.

After the fact, read what it cost rather than estimating it. Claude Code's telemetry exports claude_code.cost.usage in USD and claude_code.token.usage in tokens, alongside claude_code.session.count, claude_code.pull_request.count and claude_code.commit.count, and it is turned on with CLAUDE_CODE_ENABLE_TELEMETRY=1. Those five names are enough to answer the only question that matters at this stop: what did the pipeline spend, and how many pull requests did it produce.

3. Module 7's pass, riding along

The security pass is not a separate exercise here. It is the fourth ceiling, and it is set in the same settings file the pipeline already loads.

.claude/settings.json · ours, written against the documented sandbox keys · hub content, CC BY 4.0 · reproduce freely
{
  "sandbox": {
    "filesystem": {
      "denyRead": ["~/"],
      "allowRead": ["."]
    },
    "network": {
      "allowedDomains": ["*.github.com", "registry.npmjs.org"],
      "strictAllowlist": true
    },
    "allowUnsandboxedCommands": false
  }
}

Read the defaults this replaces, because they are the surprising part. The documentation states that the sandbox's default read behaviour is "read access to the entire computer, except certain denied directories", and adds plainly that "this default still allows reading credential files such as ~/.aws/credentials and ~/.ssh/". Narrowing reads is therefore an active decision rather than a default you inherit. strictAllowlist makes the network side fail closed rather than prompt, which is what you want in a run nobody is watching, and allowUnsandboxedCommands: false removes the retry escape hatch that would otherwise let a blocked command run outside the boundary.

Do not turn filesystem isolation off to make a build pass. The documentation is direct about the consequence: with filesystem isolation disabled and commands auto-allowed, "a sandboxed command can write files that later commands run or read, such as shell startup files, executables on $PATH, or ~/.claude/settings.json, and use them to widen its own access on the next run." That is the whole of module 7 in one sentence, arriving as an operational temptation rather than as an attack: the failure is a green build today and a boundary that no longer exists tomorrow. If a tool needs to write outside the working directory, grant that path with filesystem.allowWrite and keep the layer on.

4. The track: a repository that is not yours

Everything so far has run against a repository where you decide the rules. The last move is to run it against one where somebody else does, and the first thing to read is not the issue tracker. It is the project's own AI policy, because those policies now exist and they disagree with each other.

Three public ones, read in full, reach three different answers to the same question.

ProjectAI-assisted codeDisclosureThe reason given
QEMU Declined. Project policy "is to DECLINE any contributions which are believed to include or derive from AI generated content". Not applicable; the contribution is not accepted. The Developer's Certificate of Origin. A contributor must "fully understand the copyright and license status of content they are contributing", and with generators that status "is ill-defined with no generally accepted, settled legal foundation".
LLVM Accepted, with a human in the loop. "Contributors must read and review all LLM-generated code or text before they ask other project members to review it." Expected, in the normal place: "use a commit message trailer like Assisted-by:". Reviewer time. "A contribution should be worth more to the project than the time it takes to review it." Autonomous agents acting in the project's spaces are banned, as are automated review comments published without human review.
curl Accepted on the normal bar. Code written with AI help is fine if it "must still follow coding standards, be written clearly, be documented, feature test cases and adhere to all the normal requirements". Mandatory for security reports. "If you asked an AI tool to find problems in curl, you must make sure to reveal this fact in your report", and you must validate the findings yourself first. Report quality. Generated findings "frequently generate inaccurate or fabricated results", and an unvalidated report spends a maintainer's day.

The useful reading is what they agree on rather than where they differ. None of the three is arguing about code quality. All three are arguing about provenance and about who is accountable, and each project's answer follows from what it has to certify: QEMU has to certify origin, LLVM has to protect finite reviewer attention, curl has to keep its security queue truthful. Read that way, a policy you disagree with is still legible, and you can predict a fourth project's answer from what it has to sign.

The trailer convention follows from the same distinction, and it is worth getting right because the two lines speak for different parties. Assisted-by: names a tool. Signed-off-by: certifies the Developer's Certificate of Origin, and only a person can make that certification. Do not repurpose a co-author trailer for a tool: a co-author is a party who could sign, and a tool is not.

a commit message · trailer conventions from the LLVM policy and the DCO · hub content, CC BY 4.0 · reproduce freely
http2: reject a zero-length continuation frame

The parser accepted a CONTINUATION frame with no payload and looped,
because the length check ran after the header was consumed. Move it
before, and add a case to the fuzz corpus.

Assisted-by: an AI coding agent, for the fuzz-corpus case only
Signed-off-by: Your Name <you@example.com>
A fourth policy is worth reading beside those three because it extends the same argument past code. The Fedora Council's policy states that "the contributor is always the author and is fully accountable for their contributions", that reviewers "may use AI tools to assist in providing feedback, but not to wholly automate the review process", and that such tools "must not be used to score or evaluate submissions for things like code of conduct matters, funding requests, conference talks, or leadership positions". The last clause is the one with no equivalent in the other three, and it is the clearest statement anywhere in this course of where the line sits: a tool may help a person decide, and may not be the thing that decided.

Check yourself

Retrieval practice

Answer from memory before revealing.

Your pipeline is capped at 40 turns and 20 minutes. What is still unbounded?
Reach is the one quantity the cost ceilings say nothing about, and it is set in the sandbox rather than in the workflow. The first is bounded by the run ending. The third is a real quantity but it is bounded in practice by the turn cap and the model. The fourth is the mistake the whole section exists to correct: a cheap run can still read a credential file.
Three projects reached three different answers on AI-assisted patches. About what?
None of the three policies argues about quality: QEMU's reason is the certification a contributor signs, LLVM's is finite reviewer attention, and curl's is whether a report can be trusted. The first two options are what people assume the argument is, and reading the policies is what corrects that. The third names something no policy raises, and it would not settle a provenance question if it were true.

Practice the two capstone deliverables, about a week each

Practice 1frontier

Run the pipeline unattended, with the ceiling, against your own repository.

Write three issues small enough to be fully specified, since an agent cannot ask you a question. Label them within a minute of each other and record what actually contended: runner concurrency, merge conflicts, the queue, or your own review time.

Hand in, in docs/factory.md: the workflow file, the sandbox settings, three pull request links, the cost and pull-request counts read from telemetry, and one paragraph naming the bottleneck you hit with the evidence for it.

Hint

If nothing contended, the three tasks were too independent. Rewrite two of them to touch the same file and run it again - the contention is the finding, and a fleet that never contends has not been tested.

Show what to look for, and the three traps
  1. Read the run that produced no pull request. The prompt above tells the agent to comment with the single question it would have asked rather than to guess. That comment is the most valuable output of the whole exercise: it is a line of your AGENTS.md that you have not written yet.
  2. Check that a human is still the gate. Required checks should include make verify and exclude anything the agent controls, and nothing in the workflow should be able to merge. If a pull request merged itself, the ceiling has a hole in it that no turn cap will close.
  3. Trap one: a run you started. If you pressed it, it was not unattended. Have a colleague apply the label, or use a schedule, and remember that a scheduled run is attributed to whoever last edited the cron line.
  4. Trap two: reporting an estimate as a cost. The client-side figures are estimates. Say so in the record, and give the telemetry number beside them when you have one.
  5. Trap three: widening the sandbox to make it pass. Grant the specific path with filesystem.allowWrite. Turning the layer off is the failure the warning above describes.

Sanity check. Compare against the baseline you recorded at stop one, on the same three task shapes. If discovery cost has not fallen, the contract you wrote at stop two answered questions the agent was not asking, and that is a finding to write down rather than a reason to rerun.

Practice 2frontier

Contribute one accepted change to a project you did not write, following that project's own AI policy exactly.

Start from a dependency you already use rather than a famous project, and read its AI policy before you read its issue tracker. Keep the diff small enough that a stranger can review it in ten minutes, and write the pull request description yourself.

Hand in: the merged pull request URL, the project's policy quoted with its URL, and three sentences on what you had to do differently because of it.

Hint

Set it up so you cannot violate the policy by accident: a project-local instruction file that states the policy in one line, a hook that adds the required trailer, and a permission deny rule on anything the project forbids. Stop two taught you all three.

Show what a pass looks like, including the one that sends no AI-assisted patch
  1. The strongest possible answer. If the policy forbade AI assistance and you contributed by hand, that is a pass, and your three sentences are about what the policy cost you and why the project pays it. Read QEMU's reasoning and say whether you find it convincing.
  2. The ordinary pass. A merged pull request with the trailer the project names, a description in your own words, and review comments answered as yourself. You should be able to point at the line in the policy that shaped your disclosure.
  3. Trap one: an AI-generated issue or review comment. Never open one on somebody else's project unless their policy says you may. At least one of the three policies bans exactly this, and it is the fastest way to be ignored permanently.
  4. Trap two: a "good first issue". Those are reserved for humans learning on them in at least one of the projects here, and taking one with an agent takes the ladder away.
  5. Trap three: a large diff. The agent will happily produce forty files. The extractive-contribution test is whether asking for this review is a good use of scarce maintainer time, and forty files is usually not.

Sanity check. Read your pull request description and ask whether you could defend every line of the diff in a conversation with no editor open. If you could not, the diff is too big or you have not read it, and both are the same fix.

Your teacher. Hand your agent the three policies and your own draft pull request, and ask it which sentence of which policy your contribution would violate. Then check its answer against the policy text yourself: this is exactly the class of question where a confident wrong answer costs a maintainer their afternoon, and where you remain accountable whatever it said.

Primary source to go deeper

The policy with the clearest chain from principle to rule, and the shortest: the LLVM AI Tool Use Policy. Read it beside QEMU's code provenance page and notice that the two projects agree completely about the problem and differ only in what they are able to certify.
