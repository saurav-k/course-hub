An unattended agent is defined by what starts it

frontier 10 min Four starters, read as a trust decision rather than a feature list. · Routines · Scheduled tasks · GitHub Actions

The one-minute version

  • Four things start an agent nobody is watching: a mention, a repository event, a clock, and an HTTP call. They differ on where they run, what they can reach, and who can fire them.
  • One input decides the mode. Supply a stored prompt and the run is automation; leave it out and the run waits for a mention.
  • Text handed in at trigger time arrives wrapped and labelled untrusted, and stays inert unless the stored prompt names the block. That one sentence of prompt is the whole defence against a stolen trigger token.
  • Every starter has a cap, and the caps are not the same: a session loop expires after seven days, a cloud routine will not run more often than hourly, and a public repository's schedule stops after sixty quiet days.

1. Four doors, and they are not interchangeable

The four starters differ on facts you can look up rather than on taste, and the table below is those facts. Read it downward, as a decision: the first row that says no to something you need eliminates that column.

2. One input decides whether it waits for you

In a workflow, the difference between an agent that answers you and an agent that runs on its own is a single input. With no prompt, the action runs in interactive mode and waits for the trigger phrase - @claude by default - in a comment, a review, or a newly opened issue. Supply a prompt and it runs in automation mode from that stored instruction, with no mention needed.

Two checks run on the triggering actor before either mode starts, and a run fails when either rejects it. The write-access check requires the triggering user to have write access on issue and pull-request events. The human-actor check rejects a bot actor on every event unless you list it in allowed_bots, which is what keeps two agents in one loop from triggering each other forever.

.github/workflows/claude.yml · anthropics/claude-code-action · MIT · reproduced verbatim
name: Claude Code

on:
  issue_comment:
    types: [created]
  pull_request_review_comment:
    types: [created]
  issues:
    types: [opened, assigned]
  pull_request_review:
    types: [submitted]

jobs:
  claude:
    if: |
      (github.event_name == 'issue_comment' && contains(github.event.comment.body, '@claude')) ||
      (github.event_name == 'pull_request_review_comment' && contains(github.event.comment.body, '@claude')) ||
      (github.event_name == 'pull_request_review' && contains(github.event.review.body, '@claude')) ||
      (github.event_name == 'issues' && (contains(github.event.issue.body, '@claude') || contains(github.event.issue.title, '@claude')))
    runs-on: ubuntu-latest
    permissions:
      contents: write
      pull-requests: write
      issues: write
      id-token: write
      actions: read # Required for Claude to read CI results on PRs
    steps:
      - name: Checkout repository
        uses: actions/checkout@v6
        with:
          fetch-depth: 1

      - name: Run Claude Code
        id: claude
        uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}

          # Optional: Customize the trigger phrase (default: @claude)
          # trigger_phrase: "/claude"

          # Optional: Trigger when specific user is assigned to an issue
          # assignee_trigger: "claude-bot"

          # Optional: Configure Claude's behavior with CLI arguments
          # claude_args: |
          #   --model claude-opus-4-1-20250805
          #   --max-turns 10
          #   --allowedTools "Bash(npm install),Bash(npm run build),Bash(npm run test:*),Bash(npm run lint:*)"
          #   --system-prompt "Follow our coding standards. Ensure all new code has tests. Use TypeScript for new files."

          # Optional: Advanced settings configuration
          # settings: |
          #   {
          #     "env": {
          #       "NODE_ENV": "test"
          #     }
          #   }

The same action with a prompt is a different animal. Below, an issue being opened is enough to start a run, and one extra input - allowed_non_write_users - deliberately relaxes the write-access check so that outside reporters can still have their issues triaged.

.github/workflows/issue-triage.yml · anthropics/claude-code-action · MIT · reproduced verbatim
name: Claude Issue Triage
description: Run Claude Code for issue triage in GitHub Actions
on:
  issues:
    types: [opened]

jobs:
  triage-issue:
    runs-on: ubuntu-latest
    timeout-minutes: 10
    permissions:
      contents: read
      issues: write

    steps:
      - name: Checkout repository
        uses: actions/checkout@v6
        with:
          fetch-depth: 0

      - name: Run Claude Code for Issue Triage
        uses: anthropics/claude-code-action@v1
        with:
          # NOTE: /label-issue requires .claude/commands/label-issue.md and scripts/edit-issue-labels.sh in your repo (see this repo for examples)
          prompt: "/label-issue REPO: ${{ github.repository }} ISSUE_NUMBER: ${{ github.event.issue.number }}"

          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
          allowed_non_write_users: "*" # Required for issue triage workflow, if users without repo write access create issues
          github_token: ${{ secrets.GITHUB_TOKEN }}
The reframing Read a trigger configuration as an access-control list. on: names the events, if: narrows them, and the actor checks name the people. Everything else in the file is what happens after somebody has already been let in.

3. Text handed in at trigger time is data, not instructions

The HTTP trigger is the one that makes people uneasy, and its design is the reason it should not. A routine gets its own endpoint and its own bearer token, and the request body accepts an optional text field for run-specific context - an alert body, a failing log. That text does not reach the session as a message.

So a routine that should act on alerts says so explicitly - "investigate the alert described in the routine-fire-payload block" - and a routine that says nothing about the block treats whatever was posted as context it may read and must not obey.

firing a routine over HTTP · written for this course from the documented endpoint, headers and body field · placeholders are ours
curl -X POST \
  https://api.anthropic.com/v1/claude_code/routines/trig_REPLACE_ME/fire \
  -H "Authorization: Bearer REPLACE_ME" \
  -H "anthropic-beta: experimental-cc-routine-2026-04-01" \
  -H "anthropic-version: 2023-06-01" \
  -H "Content-Type: application/json" \
  -d '{"text": "Alert ABC-1234 fired in production. Stack trace follows."}'

Three things about that request are worth holding. The token is per routine, so it starts one saved configuration and nothing else. The text value is freeform and never parsed, so posting JSON gets you a literal string rather than structure. And the response is a session URL, which is the only handle you get on what happened next.

4. The branch prefix is the second half of the trust story

Starting a run safely is only half of it. What the run may write is the other half, and for cloud routines it is a rule rather than a prompt: work is pushed to branches prefixed claude/, which are always accepted. A push anywhere else is checked first and rejected if the branch is protected, if somebody else has an open pull request from it, or if it carries commits authored by somebody other than you.

That is the same shape as the merge gate from the previous lesson, one level down. The agent has a lane, the lane is named, and leaving it requires a check to pass rather than a mind to change. Where an agent needs to reach past its own repository - a package registry, an internal service - that is a network policy on its environment, not a permission on its prompt.

5. Every starter expires, and none of them expire the same way

The caps are the part people discover after a runaway rather than before one. They are documented, they are different per starter, and one of them exists specifically to bound how long a forgotten loop can run.

6. What a schedule actually spends

A trigger you set and forget is a standing order. The arithmetic is linear and worth doing once, before rather than after.

Multiply by whatever your own per-token price is; the arithmetic of which model and how much of the context is a cache read belongs to lesson 0940, and this figure deliberately stops before the price so it cannot go stale. The blunt controls are worth knowing too: a cloud routine will not accept an interval shorter than an hour, an account has a daily run cap, and CLAUDE_CODE_DISABLE_CRON=1 turns the whole session scheduler off in one environment variable.

A schedule that fires while nothing is watching is the easiest way to build a bill nobody can explain, and the caps above are floors rather than budgets. Before you set an interval, set a spend alert you will actually see, and prefer an event trigger to a clock wherever an event exists: a routine that reacts to pull_request.opened costs nothing on a quiet day and an hourly one costs the same whether or not there is work.

Check yourself

Retrieval practice

Answer from memory before revealing.

An attacker steals a routine's trigger token. What can they make the routine do?
The token starts that one routine and supplies a text field, which arrives wrapped and labelled untrusted, so the attacker gets a run plus a paragraph of data. The first option is true only if the saved prompt itself tells Claude to act on the payload, which is the sentence this design makes you write on purpose. The second confuses a trigger token with account access. The third is wrong because the token authenticates - that is the problem.
Which starter is the wrong choice for a nightly job that must run whether or not you are logged in?
An in-session loop needs the session open, dies when the terminal closes, and expires seven days after creation, so it is a polling tool rather than a durable schedule. A cloud routine needs neither machine nor session. A scheduled workflow runs on a CI runner. A desktop task needs the machine on, which the question grants.

Practice about 25 minutes, with a repository

Practice 1frontier

Pick one recurring chore in your repository that a person does by hand every week - triaging new issues, checking for stale branches, summarising merged pull requests.

Choose its starter from the four in this lesson, and write down the one row of the comparison table that eliminated each of the other three.

Then write the trust story in three sentences: who can fire it, what the run may write, and what stops it if it goes wrong at three in the morning.

Hint

Start from what the chore needs to touch. Anything needing an uncommitted local file eliminates both cloud starters immediately, and anything that must survive your laptop closing eliminates both local ones. Most chores are eliminated down to one column by those two questions alone.

Show a worked choice
  1. Take issue triage as the chore. It needs no local file, must run when you are asleep, and reacts to an event rather than a clock. The local starters go on "needs the machine on", and the clock goes because issues.opened exists.
  2. Who can fire it. Anyone who can open an issue, which on a public repository is anyone at all. That is why the published triage workflow sets allowed_non_write_users deliberately rather than by accident, and why its permissions block grants contents: read and not write.
  3. What it may write. Labels on one issue. Nothing else is in the permission block, so nothing else is reachable however the run is prompted.
  4. What stops it. Deleting the workflow file stops the repository's copy, an organisation toggle stops routines, and revoking the credential stops everything that authenticates with it. Name yours before you turn it on.

Sanity check. If your three sentences never mention a permission block, a branch prefix or a token, you have written a description rather than a trust story. Each sentence should name a file or a setting somebody could go and read.

Your teacher. Ask your agent to read every file in .github/workflows/ and produce one table: the workflow, what event starts it, whether it supplies a stored prompt, and what its permissions block grants. Then ask which of those rows would let somebody outside your organisation start a run. That last column is the one nobody writes down.

Primary source to go deeper

The trigger documentation, including the wrapped payload and the branch rules, in the vendor's own words: Automate work with routines. Read the "Trigger a routine" section twice - once for the request shape and once for the two paragraphs on what the text field is allowed to be.
