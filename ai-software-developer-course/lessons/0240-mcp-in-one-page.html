The model never sees a protocol, only one more tool schema

foundation 10 min Written against protocol revision 2026-07-28, which removed the handshake most tutorials still teach. · MCP specification

The one-minute version

  • Three roles and one sentence each: the host is the application, a client is a connector inside it, a server provides context and capabilities.
  • Two transports: stdio for a local subprocess, Streamable HTTP for a remote service. Neither changes what the model sees.
  • Revision 2026-07-28 is stateless. No initialize handshake, no protocol session, no standalone GET stream. The version travels per request in _meta.
  • After all of it, the model is handed a tool schema exactly like the ones in module 1. That is the whole payoff, and it is why this page is short.

1. Three roles, and the analogy the spec itself uses

The specification defines the parties in three lines: "Hosts: LLM applications that initiate connections. Clients: Connectors within the host application. Servers: Services that provide context and capabilities." Your editor or terminal agent is the host. Inside it, one client per server it has mounted. Each server is a separate program.

The comparison the spec draws is to the Language Server Protocol, which "standardizes how to add support for programming languages across a whole ecosystem of development tools. In a similar way, MCP standardizes how to integrate additional context and tools into the ecosystem of AI applications." That analogy is the whole value proposition: N editors times M languages collapses to N plus M, and it does the same for agents and services.

2. Three server primitives, and who invokes each

The distinction that matters is who is in control, and it is a design decision rather than a naming convention.

PrimitiveWhat it isControlled byProtocol methods
Toolsfunctions the model may callthe modeltools/list, tools/call
Resourcesread-only data addressed by URIthe applicationresources/list, resources/read
Promptstemplates a person invokesthe userprompts/list, prompts/get

Roles and methods from Understanding MCP servers. Clients may offer one feature back: elicitation, by which a server asks the user for information mid-call.

Reach for the wrong one and the failure is quiet. A resource the model was supposed to read is never read, because resources are the application's to include. A prompt written as a tool fires when the model feels like it rather than when a person asks for it. Get this right and the rest of MCP is plumbing.

3. One exchange, on the wire

Step through the smallest useful conversation. Every request below is the shape the specification itself documents, with the _meta block that the current revision requires on every request.

tools/call request · MCP specification 2026-07-28, Streamable HTTP transport · Apache-2.0 or MIT · reproduced verbatim
POST /mcp HTTP/1.1
Content-Type: application/json
MCP-Protocol-Version: 2026-07-28
Mcp-Method: tools/call
Mcp-Name: get_weather

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "get_weather",
    "arguments": {
      "location": "Seattle, WA"
    },
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientInfo": {
        "name": "ExampleClient",
        "version": "1.0.0"
      },
      "io.modelcontextprotocol/clientCapabilities": {}
    }
  }
}

Three headers mirror three body fields, so a load balancer can route without parsing JSON. That mirroring is checked: if a header and the body disagree, the server must reject with HTTP 400 and JSON-RPC error code -32020, named HeaderMismatch. The reason is stated in the spec and is worth carrying: it "prevents potential security vulnerabilities when different components in the network rely on different sources of truth".

4. Two transports, and what actually differs

stdioStreamable HTTP
Where the server runsa subprocess you launcheda service someone operates
Framingone JSON-RPC message per line, no embedded newlinesone HTTP POST per message, to a single endpoint
Metadatainline in _meta, no header layer_meta plus mirrored HTTP headers
Trust boundaryyour machine, your user, your filesthe network, and whoever runs the endpoint
Cancellationnotifications/cancelled, because the channel is sharedclosing the response stream, which is unambiguous
Typical failurethe server printed to stdout and broke the framinga header does not match the body, giving -32020

From the stdio and Streamable HTTP transport pages of revision 2026-07-28.

The stdio failure in that last row is the one that will cost you an afternoon, and it is a one-line rule: "The server MUST NOT write anything to its stdout that is not a valid MCP message." A stray print() or console.log() anywhere in your server, including in a library you imported, corrupts the stream and the client reports something unrelated. Logging goes to stderr, which the spec explicitly allows and which clients are told not to read as an error.

5. Why the tutorial you found disagrees with this page

Protocol revisions are named by date, and 2026-07-28 is the current one. It made two changes that invalidate most third-party writing about MCP: "Removal of the GET stream endpoint. Removal of protocol-level sessions." Together with the earlier move of version negotiation into every request, that means there is no initialize exchange to perform: the base protocol is now described as "Stateless, self-contained requests" with "Per-request capability negotiation".

Old servers do not vanish, which is why the compatibility rules are part of the spec rather than folklore. A modern client probes with a normal request and reads the error body: a recognised modern JSON-RPC error means the server is modern and the client should correct the request, while an unrecognised error or none at all means fall back to initialize. A modern server meeting old traffic answers 405 Method Not Allowed to a GET or DELETE, ignores an Mcp-Session-Id, and ignores Last-Event-ID.

The hub's survey of how thirteen harnesses adopted this protocol is MCP and the tool ecosystem, and it is worth reading for the adoption depths and the two refusals. Note that its wire diagram shows the initialize handshake, which was current when it was written and is not part of revision 2026-07-28. For what a server must never do once it is running in production, Context and Protocol is the sibling that owns it.

Check yourself

Retrieval practice

Answer from memory before revealing.

Under revision 2026-07-28, what does a client do before it may send tools/list?
The base protocol is stateless with per-request capability negotiation, so the first request is the first request. The other three describe mechanisms this revision removed by name: the handshake, the standalone GET stream and protocol-level sessions. Each one was correct in an earlier revision, which is exactly why they make good distractors.
Your server exposes a coding-conventions document the agent should consult when it edits. Which primitive?
Read-only data addressed by a URI is a resource, and resources are application-controlled, which is the part to design around: the host decides when to include it. A prompt is a template a person invokes, so nothing would happen unless someone chose it. A tool would work and makes the model pay a schema and a round trip for a document that could simply have been in context. Elicitation runs the other way - it is the server asking the user for something.

Practice about 20 minutes, with a terminal

Practice 1foundation

Find one MCP server your team already runs, or one you have mounted in an editor, and answer four questions about it without running it, from its configuration and its README alone.

Which transport does it use? Which protocol revision does it claim? Which primitives does it expose, and is each one the right kind for what it does? And what would break if it were pointed at a client speaking only 2026-07-28?

Hint

The transport is usually decidable from the config entry alone: a command means stdio, a url means HTTP. For the revision, look for initialize, Mcp-Session-Id or a GET route in the source, any of which places it before the current revision.

Show what a good pass looks like
  1. Read the config entry first. A command plus args is a subprocess on your machine. A url is a service, and the trust boundary moved with it.
  2. Grep for the removed mechanisms. initialize, Mcp-Session-Id, Last-Event-ID or a GET handler on the MCP path each date the implementation to 2025-11-25 or earlier.
  3. List its primitives and check each control. Anything the model should call is a tool. Anything the application should include is a resource. Anything a person should trigger is a prompt.
  4. Find the mis-typed one. A "get the style guide" tool and a "run the deploy" prompt are the two most common inversions, and both change who is in control.
  5. Answer the compatibility question honestly. If it is session-based, a modern-only client gets no session and the server must ignore the header rather than fail, so the visible symptom is usually a missing capability rather than an error.

Sanity check. If every primitive on the server is a tool, that is worth a second look rather than a conclusion: some servers genuinely are all tools, and many are all tools because the author only knew about tools. The test is whether anything on the list would be better if the application decided when to include it.

Your teacher. If the statelessness is hard to believe, ask your agent to explain how a server would implement a shopping basket without a session, and check its answer against the spec's own guidance on state handles. If the primitives keep blurring, ask it to take three capabilities from your own repository and argue each into exactly one of tool, resource and prompt, naming who is in control in each case.

Primary source to go deeper

Read the specification index first, because it is one page and it settles the roles and the base protocol in a screen: Model Context Protocol, revision 2026-07-28. Then read the Streamable HTTP transport page, whose Backward Compatibility section is the clearest short account anywhere of what changed and how to detect which era a server is from. Versioning is where you check which revision is current before you trust anything else.
