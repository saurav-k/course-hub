When a team shares tools, the unit of governance stops being the server

frontier 9 min Built on Cloudflare's published enterprise MCP architecture and its own measured tool-context figures. · Enterprise MCP

The one-minute version

  • Three different products are called the same word. A registry is discovery, a gateway is isolation and credential injection, a portal is one endpoint plus one access policy.
  • A portal is a governance boundary rather than an infinite bus: Cloudflare caps one at 40 MCP servers, raisable on request.
  • The cost nobody budgets for is context. Four internal servers exposed 52 tools at roughly 9,400 tokens of definitions, before anyone asked a question.
  • Progressive disclosure collapses that to two tools and about 600 tokens, and holds it flat as servers are added.
  • A policy on the door does nothing for a server that is still reachable at its own URL. That is the trap, and it is documented.

1. Three words, three different products

Ask five engineers where the team's MCP servers should live and you will get three architectures wearing one word. They are not competitors and they do not substitute for each other, so the first move is to separate them.

A registry answers which servers exist. The community MCP Registry is a catalogue in which a publisher proves namespace ownership through GitHub OAuth, GitHub OIDC, DNS or HTTP, so that publishing under io.github.someone/server requires being that GitHub user. It holds no traffic and no credentials. Its API is frozen at v0.1 while feedback is gathered.

A gateway answers how a server runs. The Docker MCP Gateway is "a centralized proxy between clients and servers, managing configuration, credentials, and access control": it starts each server in an isolated container with restricted privileges and network access, injects the credentials the server needs, and traces every call. A --profile selects which servers a client sees.

A portal answers who may reach what. Cloudflare's MCP server portal "centralizes multiple Model Context Protocol (MCP) servers onto a single HTTP endpoint", and an administrator writes one access policy in front of all of them. A client connects once, over the ordinary OAuth authorization-code flow, and sees the servers and tools that policy leaves it.

The bypass is not a subtle failure mode, it is the first thing to check after a portal rollout. If a server was reachable at https://mcp.internal.example.com before the portal existed, it is reachable there afterwards, and a developer who was denied a tool at the door has a URL in their shell history. The fix is to put the server itself behind the same identity provider, not to write a better policy on the portal.

2. The bill is paid in context, not in requests

The argument that survives every product in this section is not about access at all. It is the one module 2 leaves you with in lesson 0270, when not to add a tool: every tool you mount is permanent context, charged on every turn, before the reader has asked anything.

Cloudflare measured its own installation and published the numbers. Connected to just four of its internal MCP servers, its portal exposed 52 tools, and those "52 tools that consume approximately 9,400 tokens of context just for their definitions". Under progressive disclosure, where the portal offers a search tool and an execute tool instead of the whole catalogue, "those 52 tools collapse into 2 portal tools consuming roughly 600 tokens, a 94% reduction". The second sentence is the one worth memorising: "this cost stays fixed. As we connect more MCP servers to the portal, the token cost of Code Mode doesn't grow."

Put your own numbers into it. The figure below multiplies servers by tools per server by the size of one definition, which is how the total is actually built, and prices the result at Claude Sonnet 5's list input rate of $2 per million tokens across a forty-turn session.

Already true on your machine Claude Code defers MCP tool definitions by default on Claude 4.5 generation models and later, so only tool names and server instructions enter context until a tool is actually used. Run /context to see what your own servers are costing before you argue about anybody else's. A custom ANTHROPIC_BASE_URL is one of the configurations that turns that deferral off, which is a real interaction between this lesson and the next four.

3. The policy is a file, and it is the product

A portal is only interesting because its policy is reviewable. On the client side, the same decision is expressed as settings your organisation deploys, and the shape below is the documented one for allowing and denying whole servers. It is a complete fragment of a managed settings file: every key in it is documented, and it can be dropped into the file lesson 0950 builds.

managed-settings.json · code.claude.com/docs/en/mcp · Anthropic documentation · reproduced verbatim, short excerpt with attribution
{
  "allowedMcpServers": [
    {
      "serverName": "claude.ai Slack"
    },
    {
      "serverUrl": "https://mcp.example.com/mcp"
    }
  ],
  "deniedMcpServers": [
    {
      "serverName": "claude.ai GitHub"
    }
  ]
}

Two things about it decide whether a rollout works. The list is matched by server name or by URL pattern, so a team that names its servers inconsistently cannot write a policy about them. And a denial is a denial from any source, which is what makes the file worth reviewing rather than merely worth writing. The tool-level half of the same decision, and the audit trail that proves it held, are the next lesson but one.

4. A portal is a boundary, so it has a size

Each Cloudflare portal supports up to 40 MCP servers, and organisations needing more are told to contact their account team. That limit reads like an implementation detail and is actually the design statement: a portal is a unit of governance, and a unit of governance that contains everything governs nothing.

The useful consequence is that you will end up with more than one. Finance reaches a portal that does not carry the deploy server; the platform team reaches one that does. Cloudflare's own account describes exactly that, with policies scoped by role group and by device. Two portals with narrow catalogues are easier to defend at a review than one portal with forty servers and a long policy, and they are cheaper in context for every person who is not on both.

Check yourself

Retrieval practice

Answer from memory before revealing.

Your team publishes an MCP server to a registry. What has that changed about who can call its tools?
A registry is a catalogue: it proves who owns a name and lists what exists, and it never sees a request or a credential. The first option confuses namespace ownership, which is about publishing, with access, which is about calling. The second describes a gateway's call tracing. The fourth describes a portal, which is the one shape that does sit in the request path.
A portal collapses 52 tool definitions into two. What happens to that 600-token cost when a fifth server joins?
The measured claim is that the cost stays fixed as servers are added, because what the model is handed is a search tool and an execute tool rather than a catalogue. The second and third options are what happens without progressive disclosure, and the third is a tempting half-truth: everyone on the portal pays the same two definitions whether they use the new server or not. The fourth invents a mechanism nobody published.

Practice about 20 minutes, with a terminal

Practice 1frontier

Measure your own tool surface before you argue about anyone else's, then decide what a door in front of it would be worth.

Run /context in a session with your usual MCP servers connected and write down the tokens attributed to tool definitions. Count the servers and the tools. Then compute what a forty-turn session pays for those definitions at your model's input price, and what it would pay at a fixed 600.

Finally, name one server on your list that a colleague on a different team should not be able to reach, and say in one sentence how you would stop them today.

Hint

The arithmetic is one multiplication and one division. Tokens times price per million times turns; the price per million is on the pricing page and Sonnet 5 is $2. For the last part, the honest answer is often "I could not", and that answer is the point of the exercise.

Show a worked example
  1. Read the definitions figure. Suppose /context reports 7,200 tokens of tool definitions across three servers.
  2. Price one session. 7,200 × 40 turns = 288,000 tokens. At $2 per million that is $0.58 of a session's bill spent before anybody typed anything.
  3. Price the searched catalogue. 600 × 40 = 24,000 tokens, which is $0.05. The difference, $0.53 a session, is what progressive disclosure is worth to one developer on one task.
  4. Answer the access question. If the only control you have is that the server's URL is not written down anywhere, you have discovered why the unit of governance has to move to the endpoint.

Sanity check. Your definitions figure should be in the thousands, not the hundreds: a single MCP server with a dozen tools rarely comes in under a thousand tokens. If it reads as a few hundred, your harness is deferring the definitions rather than sending them, which is a different and better answer to the same problem.

Your teacher. If the registry, gateway and portal distinction still blurs, ask your agent to take one tool call you made today and say, for each of the three, whether it would have been involved and what it would have seen. If the context arithmetic felt abstract, ask it to print your current /context breakdown and rank the rows by what you could actually remove this week.
