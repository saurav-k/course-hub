Exit 2 with a reason, or exit 0 with decision JSON - one per hook, never both

working 8 min Both protocols and the precedence order are from Anthropic's hooks reference and guide. · Hooks guide

The one-minute version

  • A hook is an ordinary program. It reads JSON on stdin, and for a Bash tool call that JSON carries tool_name, tool_input.command, session_id and cwd.
  • Exit 2 blocks and your stderr becomes the reason. Exit 0 with decision JSON gives you four outcomes instead of one.
  • The documentation's rule is one line: "Choose one approach per hook."
  • Every matching hook runs in parallel to completion, and the most restrictive answer wins: deny, defer, ask, allow.

1. What arrives on stdin

Every event delivers a JSON object to your script's standard input. For a PreToolUse hook watching Bash, the useful fields are the tool name and the command itself.

hook input · code.claude.com/docs/en/hooks-guide · Anthropic documentation · reproduced verbatim, complete
{
  "session_id": "abc123",
  "cwd": "/Users/sarah/myproject",
  "hook_event_name": "PreToolUse",
  "tool_name": "Bash",
  "tool_input": {
    "command": "npm test"
  }
}

Note cwd, because it is the answer to a trap. Scripts are usually referenced with ${CLAUDE_PROJECT_DIR} so the path works wherever the session starts, and that variable stays fixed at the project directory. When your hook needs to know where the agent actually is - a git worktree, a monorepo package - read the cwd field rather than the variable.

2. Two answers, and they are not equal

The first path is an exit code, and it is six lines. Write the reason to standard error and exit 2.

a PreToolUse hook · code.claude.com/docs/en/hooks-guide · Anthropic documentation · reproduced verbatim, complete
#!/bin/bash
INPUT=$(cat)
COMMAND=$(echo "$INPUT" | jq -r '.tool_input.command')

if echo "$COMMAND" | grep -q "drop table"; then
  echo "Blocked: dropping tables is not allowed" >&2  # stderr becomes Claude's feedback
  exit 2                                               # exit 2 = block the action
fi

exit 0  # exit 0 = no decision; the normal permission flow applies

The last line is the one people misread. Exit 0 is not an approval. The documentation is explicit that for a PreToolUse hook it "doesn't approve the tool call: the normal permission flow still applies". Silence means you have no opinion, not that you said yes.

The second path is structured output. Exit 0 and print a decision object, which buys you four outcomes rather than one.

PreToolUse decision output · code.claude.com/docs/en/hooks-guide · Anthropic documentation · reproduced verbatim, complete
{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "deny",
    "permissionDecisionReason": "Use rg instead of grep for better performance"
  }
}

"allow" skips the interactive prompt but does not make the action unconditional: deny and ask rules, including enterprise managed deny lists, still apply. "deny" cancels the call and sends your reason to the model. "ask" shows the prompt as normal. "defer" is the fourth, available only in a non-interactive -p run, and it exits with the tool call preserved so a wrapper can collect an answer and resume.

3. Several hooks, one event, and the most restrictive answer wins

Hooks are not a chain and there is no first-one-wins. Every matching handler runs, in parallel, to completion. Then the answers are combined: "For PreToolUse permission decisions, the most restrictive answer applies, in the order deny, defer, ask, allow."

The consequence the guide draws out is the useful one. Put a logging hook and a guardrail hook on the same event and the guardrail denies: the command is blocked, and the log entry is still written, because the logging hook already ran. Side effects are not rolled back by somebody else's refusal.

4. A gate you can commit

Here is a working guardrail, built out of four parts. Untick scope it to commits and you have written a hook that runs your linter before every ls; untick run the check and you have written one that refuses every commit unconditionally. Both are real mistakes and both look reasonable in a diff.

The settings block that registers it is three levels, exactly as lesson 0430 described.

.claude/settings.json · written for this course, from the documented schema · complete, registers the script above
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/lint-gate.sh"
          }
        ]
      }
    ]
  }
}
chmod +x .claude/hooks/lint-gate.sh is a numbered step in the documentation because it is the most common reason a hook silently does nothing. A non-executable script is not an error you will see: the gate is simply absent, and the first time you notice is when something it was supposed to stop gets through.

5. The same idea with a different contract

Cursor's hooks answer the same question and shape the answer differently, and the three differences are each a design decision worth recognising. It names the field permission, with allow, deny and ask, at the top level rather than nested under a hookSpecificOutput object. It carries a failClosed flag, defaulting to false, so you choose whether a crashed or timed-out hook blocks the action or waves it through. And it splits the message in two, user_message and agent_message, so the human and the model can be told different things.

The failClosed flag is the one to think about. Claude Code's protocol has no equivalent switch, so a hook that crashes is a non-blocking error and the action proceeds. If your gate must hold even when your own script is broken, the deny rule in permissions.deny is the belt to the hook's braces, and that is why the module keeps putting them in the same file.

Check yourself

Retrieval practice

Answer from memory before revealing.

Two hooks match one Bash call. One returns allow, the other exits 2. What happens?
Answers combine by strictness in the order deny, defer, ask, allow, and exit 2 blocks whether or not JSON was printed. The first option inverts the rule. The third describes a resolution that would make a guardrail depend on nobody else writing a permissive hook. The fourth is the reasonable guess for parallel work and is explicitly not how this combines - order of completion does not matter, only strictness.
Your PreToolUse hook exits 0 and prints nothing. What did you just say?
Exit 0 with no decision reports no objection through the exit code, and the permission flow runs as though your hook were not there. The first option is the most common misreading and turns a silent hook into an accidental approval in the reader's mental model. The second would make a broken script a denial of everything. The fourth would make it a prompt for everything, and neither escalation is in the protocol.

Practice about 25 minutes, with a terminal

Practice 1working

Write one hook for your capstone repository and prove it does both things a gate must do: fire, and block.

Pick the rule you classified as "must hold" in lesson 0430. Write the script, register it, make it executable, and then produce two transcripts: one where the hook runs and allows, and one where you deliberately break the condition and it refuses with your own reason text visible.

Hint

Test the script before you involve the agent at all. It reads JSON on stdin, so you can feed it a hand-written object and read the exit code: echo '{"tool_input":{"command":"git commit -m x"}}' | .claude/hooks/lint-gate.sh; echo $?. If that does not print 2 or a decision object, no amount of settings-file debugging will help.

Show the four things a finished answer has
  1. The script, tested off-line. Piped a fake input object in, read the exit code out. Two runs: one where the check passes and it exits 0, one where it fails and it exits 2 or prints a deny.
  2. The registration, proved. /hooks lists it, under the right event, with the right matcher. A hook that is not in that list is not installed, whatever the file says.
  3. The firing transcript. The condition holds, the agent does the thing, and the hook allowed it by staying silent. This one is boring and is the one people skip.
  4. The blocking transcript. The condition is broken on purpose, the agent tries anyway, and your own reason text appears in the conversation. If the model then works around the block by a different route, that is a finding about your matcher, and it is the finding worth having.

Sanity check. Two transcripts, and your reason text appearing word for word in the second. If you cannot find your own sentence in the blocking transcript, the block came from somewhere else - the permission flow, or a deny rule - and your hook may not be running at all.

Your teacher. Hand your agent your hook script and ask it to name every command that would reach the check and every command that would slip past the matcher. The second list is the useful one, and it is usually longer than you expect.
