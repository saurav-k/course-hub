The frontmatter is the contract, and the description is the whole of it

working 8 min Field constraints read from the specification, extensions read from Claude Code's own reference. · The specification

The one-minute version

  • Two fields are required by the standard: name, which must match the directory, and description, which is capped at 1,024 characters.
  • The description must say what the skill does and when to use it, because it is the only text the model sees before deciding whether to open the body.
  • Four optional fields are portable: license, compatibility, metadata, allowed-tools. Everything else is a client extension and does not travel.
  • The frontmatter is read only when the opening --- is the first line of the file. A blank line above it turns the whole file into skill content with no metadata at all.

1. The two required fields, exactly

The specification is short and its constraints are hard edges rather than advice. name must be one to sixty-four characters, lowercase letters, digits and hyphens only, may not start or end with a hyphen, may not contain two hyphens in a row, and must match the parent directory name. description must be one to 1,024 characters.

That is the entire required contract, and here is a real skill that uses nothing else.

internal-comms/SKILL.md · github.com/anthropics/skills · Apache-2.0 · reproduced verbatim
---
name: internal-comms
description: A set of resources to help me write all kinds of internal communications, using the formats that my company likes to use. Claude should use this skill whenever asked to write some sort of internal communications (status reports, leadership updates, 3P updates, company newsletters, FAQs, incident reports, project updates, etc.).
license: Complete terms in LICENSE.txt
---

## When to use this skill
To write internal communications, use this skill for:
- 3P updates (Progress, Plans, Problems)
- Company newsletters
- FAQ responses
- Status reports
- Leadership updates
- Project updates
- Incident reports

## How to use this skill

To write any internal communication:

1. **Identify the communication type** from the request
2. **Load the appropriate guideline file** from the `examples/` directory:
    - `examples/3p-updates.md` - For Progress/Plans/Problems team updates
    - `examples/company-newsletter.md` - For company-wide newsletters
    - `examples/faq-answers.md` - For answering frequently asked questions
    - `examples/general-comms.md` - For anything else that doesn't explicitly match one of the above
3. **Follow the specific instructions** in that file for formatting, tone, and content gathering

If the communication type doesn't match any existing guideline, ask for clarification or more context about the desired format.

## Keywords
3P updates, company newsletter, company comms, weekly update, faqs, common questions, updates, internal comms

Read that description against the rule. It says what the skill does and it spends most of its length on when: seven named document types plus an "etc.". The ## Keywords section at the foot is the same instinct applied a second time, in the body, where a reader can add to it without touching the contract.

2. What separates a description that fires from one that does not

The specification prints its own good and poor pair, and the difference is entirely about the when half.

DescriptionWhat it tells the modelWould it match "pull the tables out of this statement"?
"Helps with PDFs."A topic, and nothing about the triggerOnly if the model already guessed the file is a PDF
"Extracts text and tables from PDF files, fills PDF forms, and merges multiple PDFs. Use when working with PDF documents or when the user mentions PDFs, forms, or document extraction."Three named operations and four trigger wordsYes: "tables" and "extraction" are both in it

The rule that falls out of this is worth writing on the wall: put the words your colleagues actually say into the description. Not the words you would use in documentation. Claude Code's own troubleshooting page starts at exactly that point when a skill will not trigger: check the description includes keywords users would naturally say.

5. What travels, and what only works in one client

Claude Code accepts a much longer field list than the standard does: when_to_use, argument-hint, arguments, disable-model-invocation, user-invocable, disallowed-tools, model, effort, context, hooks, paths and more. Two of those are the ones you will reach for first: disable-model-invocation: true makes a skill manual only, for a workflow with side effects; user-invocable: false hides it from the slash menu, for background knowledge nobody should trigger by hand.

The cost of using them is portability, and it is a hard failure rather than a soft one. Uploading a skill to claude.ai, the Skills API, or packaging it with the repository's own package_skill.py accepts only the standard's six fields, and rejects anything else outright: Unexpected key(s) in SKILL.md frontmatter: argument-hint.

One more divergence is worth knowing before it surprises you. The standard makes name required and says it must match the directory; Claude Code makes every field optional, defaults name to the directory name, and for a personal or project skill uses the field only as a display label, so the command still comes from the directory. A skill whose name disagrees with its folder therefore works in Claude Code and fails skills-ref validate. Write them the same and the question never arises.

6. What real descriptions look like

The nineteen skills Anthropic publishes are the largest set of well-formed examples available. Measured at the commit current in this session, their descriptions run from 204 characters to 1,068, with a median of 324.

Answer from memory before revealing.

Your skill never fires on its own, but /my-skill works. What is the likeliest cause?
A malformed or unread frontmatter loads the body with empty metadata: the command still resolves from the directory name, and automatic matching has nothing to match against. The second option describes a cost, not a failure to trigger. The third would stop the slash command working too. The fourth invents a requirement: allowed-tools is optional and marked experimental.
Which of these descriptions is most likely to be opened for "tidy up this migration"?
Only the third names the object the request names, "migration", and an action the request implies. The first two are topic labels: true, and matched by nothing in particular. The fourth is a genuine description of real material, and it answers "how should I design this schema" rather than "tidy this up", which is the classic strong distractor: a good description of the wrong moment.

Practice about 20 minutes, with a terminal

Practice 1working

Take the procedure you found in the previous lesson and make it a real skill: a directory under .claude/skills/ or .agents/skills/, a SKILL.md, and nothing else yet.

Write the description last, not first, and hold it to a test: cover the body, hand the description alone to a colleague, and ask them to name three requests that should open it and one that should not. If they cannot, the description is a topic label.

Then invoke it two ways: by typing /<name>, and by making a request that only the description could route. The second one is the test that matters.

Hint

Write the second half of the description first. "Use when..." followed by the words a colleague would say is easier to write than a summary, and it is the half that does the routing.

Show what a passing description looks like
  1. Name the operations. Two or three verbs with their objects: "Collects the merged pull requests since the last tag and groups them under Added, Changed and Fixed."
  2. Name the moment. "Use when asked for release notes, a changelog entry, or what shipped in a version." Three phrasings, because your colleagues will use all three.
  3. Name the exclusion, if there is a near neighbour. If you also have a changelog-lint skill, one sentence saying which is which saves both of them from firing.
  4. Count it. Three sentences lands near the 324-character median of the published set, and well under the 1,024 cap.

Sanity check. Read your description and count how many of its characters are about when rather than what. If the answer is under a third, the model has been told what you built and not when you want it. Rewrite until the halves are roughly even.

Your teacher. Ask your agent to read your SKILL.md and answer one question only: "list five requests that should open this skill and five near misses that should not." If its five near misses are things you actually want it to catch, the description is too narrow; if its five matches include work you would not want it doing, it is too broad.
