Every token names exactly one server, and no server passes one on

frontier 9 min Read against the Model Context Protocol authorization specification at revision 2026-07-28, and its predecessor. · Authorization

The one-minute version

  • Nothing here is a new protocol. It is OAuth 2.1 with a short list of things made mandatory that OAuth leaves optional.
  • The whole discipline is the audience. A client MUST send a resource parameter naming one server, and a server MUST reject a token that does not name it.
  • An MCP server that calls an upstream API gets its own token for that API. Passing yours on is the confused deputy, and the specification forbids it.
  • A 403 insufficient_scope is a request, not a failure: re-authorize with the union of what you had and what was challenged.
  • Dynamic Client Registration is now MAY and deprecated. A tutorial that recommends it is describing the previous revision.

1. The 401 is a set of instructions

An MCP client's first request carries no token, and the interesting part of the flow is the refusal. The server answers with a challenge that tells the client where to go next, and since the 2026-07-28 revision it also carries a hint about which scopes to ask for.

HTTP response · MCP specification 2026-07-28, authorization · MIT-licensed specification project · reproduced verbatim with attribution
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer resource_metadata="https://mcp.example.com/.well-known/oauth-protected-resource",
                         scope="files:read"

Two fields, two jobs. resource_metadata is the address of the server's Protected Resource Metadata document, which RFC 9728 defines and which every MCP server MUST implement; the client MUST use it for discovery rather than guessing a well-known path. scope is the server saying which permissions this operation actually needs, and the specification is careful about how a client should treat it: clients "MUST treat the scopes provided in the challenge as authoritative for the current operation" and MUST NOT assume any set relationship between that list and the server's advertised scopes_supported.

Discovery then takes two hops. The client fetches protected-resource metadata from the server, which names one or more authorization servers, and then fetches that authorization server's own metadata. The server MUST offer at least one of RFC 8414 authorization-server metadata or OpenID Connect Discovery, and the client MUST support both, because it does not get to choose which one it meets.

2. The audience is the whole idea

Strip the flow back and one requirement is doing nearly all the work. A client MUST implement RFC 8707 resource indicators, and the resource parameter "MUST be included in both authorization requests and token requests", "MUST identify the MCP server that the client intends to use the token with", and MUST be the server's canonical URI. The specification adds the line that makes it a discipline rather than a feature: clients "MUST send this parameter regardless of whether authorization servers support it".

The server side is the mirror image. An MCP server MUST validate that a token was issued specifically for it, MUST only accept tokens valid for its own resources, and then the sentence the whole section exists for: "MCP servers MUST NOT accept or transit any other tokens."

This is the rule that a home-grown MCP server breaks first, and it breaks it for a good reason: forwarding the caller's token is the shortest path to a working prototype. It also means that anyone who can reach your MCP server can reach everything your callers can reach at the upstream API, with no record that your server was in the path. If you have written an MCP server that wraps an internal API, the question to answer today is whose token arrives at that API.

3. Read the revision before you read the tutorial

The authorization chapter moved substantially between the 2025-06-18 revision and 2026-07-28, and the changes are the kind that make an old tutorial confidently wrong rather than merely incomplete.

MechanismRevision 2025-06-18Revision 2026-07-28
Dynamic Client Registrationclients and servers SHOULD support RFC 7591MAY, and deprecated, retained for backwards compatibility
Client ID Metadata DocumentsabsentSHOULD be supported, and the first mechanism to try
Authorization-server discoveryRFC 8414 metadata, which clients MUST useRFC 8414 or OpenID Connect Discovery, and clients MUST support both
Issuer identification, RFC 9207absentservers SHOULD emit iss, clients MUST validate it against a recorded issuer
Scope challengesa 403 is defined, with no flowa step-up flow, with a scope hint on the 401 and a union rule on the 403

Two of the additions are worth knowing by name because they change client code. Client ID Metadata Documents let a client use an HTTPS URL as its client_id, which the authorization server fetches and validates, so a client no longer has to register itself with every authorization server it meets. That is what replaced Dynamic Client Registration, and it is why the deprecation was possible. RFC 9207 issuer identification makes the client record the issuer before it opens the browser and compare the iss that comes back, using simple string comparison with no normalisation, which is the defence against a mix-up attack where the response comes from an authorization server the client did not choose.

4. A 403 is a request for more, not a refusal

The last piece is the one that changes how an agent behaves at run time. When a token is valid but too narrow, the server SHOULD answer 403 with the scopes the operation needs.

HTTP response · MCP specification 2026-07-28, authorization · MIT-licensed specification project · reproduced verbatim with attribution
HTTP/1.1 403 Forbidden
WWW-Authenticate: Bearer error="insufficient_scope",
                         scope="files:write",
                         resource_metadata="https://mcp.example.com/.well-known/oauth-protected-resource",
                         error_description="File write permission required for this operation"

The client's correct response is a step-up authorization, and step two of the documented flow is the part people get wrong: determine the required scopes "by computing the union of the client's previously requested scope set and the scopes from the current challenge". A client that re-authorizes with only the challenged scope silently drops permissions it already had, and the next operation fails for a reason nobody can see. The flow also states its own stopping rule: retry the original request "no more than a few times and treat this as a permanent authorization failure", with clients tracking scope-upgrade attempts per resource and operation so a misconfigured server cannot become an infinite consent loop.

Servers carry a matching duty. They SHOULD include every scope the current operation needs in a single challenge, because challenging incrementally forces a separate authorization round trip for each missing scope, and each round trip is a browser window in a developer's face.

Check yourself

Retrieval practice

Answer from memory before revealing.

Your MCP server wraps an internal REST API. Which token should reach that API?
The MCP server acts as an OAuth client to anything upstream, so it holds a second grant with a second audience. The first option is token passthrough, which the specification forbids by name. The third is worse, because rewriting an audience means the signature no longer verifies or you are minting tokens. The fourth confuses network position with authorization, which is the assumption that makes a flat internal network expensive.
A tool call returns 403 insufficient_scope naming files:write. What should the client request next?
The step-up flow says the union, so the permissions already granted survive a per-operation challenge. The first option is the common bug: it works for this call and quietly breaks the previous one. The second over-asks, against the least-privilege rule the same chapter states, and scopes_supported is described as a minimal set rather than a menu. The third is right only after the retry limit is reached.

Practice about 25 minutes, with a terminal

Practice 1frontier

Read a real challenge rather than a documented one.

Pick a remote MCP server you already use that requires authorization, and send it an unauthenticated request with curl -i. Read the WWW-Authenticate header it returns and write down two things: the resource_metadata URL, and whether a scope hint is present.

Then fetch the protected-resource metadata document at that URL and answer three questions from it: which authorization servers does this server trust, what does it list in scopes_supported, and does the canonical resource identifier it publishes match the URL you connected to?

Hint

curl -i https://server.example.com/mcp is enough; you want the headers, not the body. If you get a 404 rather than a 401, you are talking to the wrong path, and the path matters because it is part of the canonical resource identifier.

Show what a good reading looks like
  1. Confirm the challenge is well formed. A 401 with no resource_metadata is a server that has not implemented RFC 9728, which the specification makes a MUST. You have found a bug rather than a configuration problem.
  2. Check for the scope hint. Its absence is legal, since it is a SHOULD. Its presence tells you the server was built against the current revision rather than the previous one, which is a faster answer than reading the vendor's changelog.
  3. Compare the identifiers. If you connected to https://server.example.com/mcp and the metadata publishes https://server.example.com, then the resource value your client must send is the published one, and a client sending the path form will be issued a token for an audience the server does not answer to.
  4. Read scopes_supported as a floor. It is described as the minimal set for basic functionality, so a server that lists everything it can do has misunderstood the field and will over-grant on first connection.

Sanity check. You should end with one URL, one list of authorization servers and one canonical identifier, and the canonical identifier should have no fragment and no trailing slash. If it has either, the server is publishing an identifier the specification calls invalid, and that is worth an issue on their tracker.

Your teacher. If the two-hop discovery still feels like ceremony, ask your agent to trace one connection of yours and label each request with which document it fetched and why it could not have skipped it. If token passthrough still seems like a reasonable shortcut, ask it to write the incident report for the day the shortcut is discovered.

The authorization chapter itself, which is short enough to read end to end in twenty minutes and is the only place the MUST and SHOULD levels are authoritative: MCP authorization, revision 2026-07-28.
