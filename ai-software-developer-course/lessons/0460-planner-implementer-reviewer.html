Module 04 · Customizing your agent · Lesson 0460

A fresh context is the reviewer's entire advantage, and it is the thing you are paying for

working 9 min The frontmatter is Anthropic's documentation and the multipliers are its own published measurements. · Subagents

The one-minute version

  • A subagent is a Markdown file in .claude/agents/. Only name and description are required, and the frontmatter is a capability contract rather than decoration.
  • It starts with no conversation history, no previously invoked skills and none of the files the main agent already read. That is the isolation you are buying.
  • The pattern has a name in the literature - orchestrator-workers - and its stated difference from parallelization is that the subtasks are decided at run time.
  • It is not free. Anthropic's own measurement is that multi-agent systems use about 15× more tokens than chats.

1. What a subagent is, on disk

A file with YAML frontmatter and a Markdown body. The body becomes the agent's system prompt; the frontmatter says what it may do. Only name and description are required, and the description is not documentation - it is what the main agent reads when deciding whether to delegate.

.claude/agents/code-reviewer.md · code.claude.com/docs/en/sub-agents · Anthropic documentation · reproduced verbatim, complete
---
name: code-reviewer
description: Reviews code for quality and best practices
tools: Read, Glob, Grep
model: sonnet
---

You are a code reviewer. When invoked, analyze the code and provide
specific, actionable feedback on quality, security, and best practices.

The tools line is the part to read as a constraint rather than as a convenience. Read, Glob, Grep is a reviewer that cannot edit anything, which is what stops a review turning into an unrequested refactor. Alongside it the documentation lists disallowedTools, model, permissionMode, maxTurns, skills, mcpServers, hooks, memory and isolation. Two are worth naming here: hooks puts lesson 0440's gate inside one agent only, and isolation: worktree gives the agent its own checkout of the repository.

2. What arrives, and what does not

The documented startup contents are short and the absences are the point. A non-fork subagent gets its own system prompt, the delegation message the main agent wrote, the whole CLAUDE.md hierarchy from lesson 0420, a git status snapshot, and any skills its skills field preloads.

It does not get the conversation history, the skills already invoked, the files already read, your output style, or the main conversation's auto memory. Its context window is sized by its own model, so delegating to a smaller model gives that subagent a smaller window rather than a slice of yours.

The reframing Every one of those absences is a cost when the subagent is doing the work, and every one is the product when the subagent is checking it. A reviewer that saw the reasoning is not a reviewer, it is the same agent asked twice.

Anthropic's own taxonomy states it in one sentence: "In the orchestrator-workers workflow, a central LLM dynamically breaks down tasks, delegates them to worker LLMs, and synthesizes their results", and "the key difference from parallelization is its flexibility - subtasks aren't pre-defined, but determined by the orchestrator based on the specific input."

3. The trio, complete

Three files, each constrained by its frontmatter rather than by its prompt. The planner may not write, the implementer may not browse, and the reviewer may not edit.

.claude/agents/planner.md · written for this course, from the documented field list · complete
---
name: planner
description: Produces an implementation plan without changing anything. Use before any change that touches more than one file, or when the approach is not obvious.
tools: Read, Glob, Grep
permissionMode: plan
model: opus
color: blue
---

You produce plans, never edits.

Read enough of the codebase to be specific before you write anything. Name the
files you would change and what would change in each. Name the existing pattern
you are following, with a path to an example of it.

Your output is a Markdown plan with exactly these sections:

1. **What we are changing** - one sentence.
2. **Files** - a table of path, change, and why.
3. **Out of scope** - what a reviewer might expect and will not get, and why.
4. **Risks** - what could break, and what would tell us it broke.
5. **Verification** - the exact command that proves this works end to end.

If the request is ambiguous in a way that changes the plan, add a sixth
heading, **Open questions**, and plan the most likely reading anyway.
.claude/agents/implementer.md · written for this course, from the documented field list · complete
---
name: implementer
description: Executes an approved plan file and nothing else. Use after a plan has been reviewed.
tools: Read, Glob, Grep, Edit, Bash
disallowedTools: WebFetch, WebSearch
model: sonnet
color: green
---

You implement an approved plan. The plan is the scope.

1. Read the plan file you were given. If it is missing, stop and say so.
2. Work file by file, in the order the plan lists.
3. Run the plan's verification command. Paste its real output. Never assert
   that it passed.
4. If verification fails, fix and re-run. If it fails the same way twice,
   stop and report what you tried.

Change nothing the plan does not name. If you find something that needs fixing
and is out of scope, list it at the end under **Noticed, not fixed**.
.claude/agents/reviewer.md · written for this course, from the documented field list · complete
---
name: reviewer
description: Reviews a diff against a plan in a fresh context. Use before treating a change as done.
tools: Read, Glob, Grep
model: opus
color: purple
---

You review a diff against the plan it claims to implement. You have not seen
the reasoning that produced it, and that is the point.

Check three things, in order:

1. Every requirement in the plan is implemented.
2. The plan's stated edge cases have tests that would fail without the change.
3. Nothing outside the plan's scope changed.

Flag only gaps that affect correctness or the stated requirements. Style
preferences and speculative hardening are out of scope. If you list them at
all, list them separately and mark them optional.

That last paragraph is not politeness, it is a documented failure mode: "A reviewer prompted to find gaps will usually report some, even when the work is sound, because that is what it was asked to do." The consequence the same note names is over-engineering - extra abstraction, defensive code, and tests for cases that cannot happen.

4. What it costs, in the vendor's own numbers

Anthropic published its measurements from running an orchestrator-worker system in production, and they are the most useful numbers in this module because they are the ones that argue against the pattern. "In our data, agents typically use about 4× more tokens than chat interactions, and multi-agent systems use about 15× more tokens than chats." The same post adds that "token usage by itself explains 80% of the variance" in performance on its evaluation.

The same post reports that "a multi-agent system with Claude Opus 4 as the lead agent and Claude Sonnet 4 subagents outperformed single-agent Claude Opus 4 by 90.2% on our internal research eval." That is a precisely stated result on an internal, unpublished evaluation, on a research task rather than on writing code, and no method, sample or task set is available to check it against. Quote it as what a vendor measured on its own bench, never as what the pattern will do to your pull requests. The claim that generalises is the 15×, because that one is about your bill.

Answer from memory before revealing.

What does a reviewer subagent get that makes its review worth having?
Isolation is the whole product: it never saw the reasoning, so it evaluates the result on its own terms. The first option is false and backwards - a subagent's window is sized by its own model, so a smaller model means a smaller window. The second describes exactly what would destroy the value, and it is the tempting mistake because handing over the transcript feels helpful. The fourth describes an implementer, and a reviewer with Edit stops being a review.
Which claim about the trio would you refuse to repeat to your team as measurement?
The 90.2% figure is a real result on an internal, unpublished research evaluation, and it says nothing about your codebase, so repeating it as a general improvement is the error this page warns against. The first is a vendor measurement of its own production system, offered as an approximation and safe to quote as one. The third and fourth are documented behaviour you can verify by reading the reference and running one subagent.

Practice about 30 minutes, with a terminal

Practice 1working

Write one reviewer and run it against a diff you already believe is finished.

Create .claude/agents/reviewer.md with read-only tools. Run it against a real change of yours, giving it the diff and the requirements and nothing else. Sort its findings into three piles: things that affect correctness, things that are style, and things that are wrong.

Hint

Give it a diff it can actually see. The cheapest way is to point it at a branch and let it run git diff itself, which needs Bash in its tools; the alternative is naming the changed files so it reads them with Read. Either is fine, and knowing which one you chose is part of the exercise, because it decides what the reviewer can and cannot look at.

Show what the three piles usually look like
  1. Correctness. Usually one or two, and they are the return on the whole exercise: an unhandled case, a requirement in the plan with no code behind it, a test that would pass without the change.
  2. Style. Usually the largest pile, and the one the documented failure mode predicts. If your reviewer's prompt does not say to keep these separate and mark them optional, they arrive mixed in with the first pile and you will act on them.
  3. Simply wrong. There will be some. A reviewer with no history invents context to fill the gap, and the fix is to give it the plan rather than to give it the transcript.
  4. Then count. Findings in the first pile, against a rough count of how many tokens the review cost. That ratio is the only number that tells you whether to keep doing this.

Sanity check. A reviewer that returns nothing at all on a real diff is usually badly scoped rather than confirming perfection - check it could see the change. A reviewer that returns fifteen findings on a twenty-line diff is the over-reporting failure mode, and the fix is in its prompt rather than in your code.

Your teacher. Ask your agent to run your reviewer twice on the same diff: once with the plan and once without it. Compare the two lists. The findings that appear only in the second run are what a reviewer invents when you give it no standard to check against, and seeing that once is worth more than any prompt advice.
