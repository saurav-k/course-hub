Module 06 · Agentic code review · Lesson 0630

What a reviewer may look at is the ceiling, and the prompt is only the ladder

working 11 min Three architectures read from the vendors' own documentation, with one published cost-against-quality table. · Factory review benchmark

The one-minute version

  • Three architectures, in increasing context: diff-only sees the patch, repo-aware can retrieve from an index of the whole repository, agentic runs tools during the review and chooses its own context.
  • A defect whose site is outside the diff is invisible to the first, retrievable by the second and reachable by the third. No prompt closes that gap.
  • A rules engine is the fourth machine and it is not a competitor: it gives a repeatable answer to a question you already knew to ask.
  • Depth is a dial with three vocabularies and one meaning, and it costs money: across thirteen models on the same benchmark, quality spans 15 F1 points while cost per pull request spans a factor of 37.

1. Three expanding boundaries around one diff

The three architectures are not three quality tiers. They are three answers to one question: what is in the reviewer's context when it decides whether to comment?

2. One bug, three machines

Take a real shape: a pull request adds a parameter to parse() in lib/header.go, updates the two callers in the same package, and leaves a third caller two directories away compiling but wrong. Watch each architecture meet it.

3. Four machines, side by side

The last row is not a worse version of the first three. A rules engine such as Semgrep gives a repeatable answer to a question you already knew to ask; a model gives an unrepeatable answer to a question you did not. Mature repositories run both, and 0640 writes one of each for the same intent so you can see where they diverge.

The reframing Repeatability is a feature, not a consolation. A check that fires identically every time belongs in CI where a merge depends on it. A reviewer that reasons belongs in a comment where a human decides.

4. One pass or several

The same reviewer can be run as a single pass or fanned out into subagents, and the open benchmark happens to contain both for one tool. The single pass emitted 93 comments, 90 of them real. The subagent run emitted 93 comments, 92 of them real - one false positive in the whole set, against three.

What you cannot read off those two rows is recall, because the two runs were scored against different golden sets: 158 bugs for the single pass and 171 for the subagent run. Their recall figures, 57.0% and 53.8%, are computed on different denominators and are not comparable. That is the caveat from 0620 biting inside a single vendor's own pair of runs.

5. Depth is a dial, and it is a budget decision

Every serious product exposes the same knob under a different name. Factory's CI reviewer takes deep - "thorough analysis with higher reasoning effort... but costs more per review" - or shallow, described as "faster, more cost-effective reviews that cover surface-level issues". Cursor exposes four effort levels, low through smart, and notes they are available only on usage-based plans. Same dial, three vocabularies.

Factory also publishes what the dial costs, by running thirteen models through the same fifty pull requests.

MARKETING. Both the thirteen-model ranking and the six-tool comparison are published by a company selling a reviewer, with a standardised prompt of its own choosing. Factory's own reading is that open models "deliver ~75-86% of GPT-5.2 quality at ~3-8x lower cost per PR". Treat the ordering as unverified and the spread as the finding: what nobody disputes is that quality varies far less than price does.

Check yourself

Retrieval practice

Answer from memory before revealing.

A caller two directories away breaks. Which architecture can confirm it rather than hedge?
Only the agentic reviewer can turn "something may call this" into a file and a line, because it fetches rather than receives. The first is the mistake this page exists to prevent: no prompt puts a file into a context that never contained it. The second gets the file only if retrieval ranks it highly, which is a guess. The third fires on a pattern you wrote and knows nothing about this rename.
Across thirteen models on the same fifty pull requests, what varied most?
Cost per pull request ran from $0.15 to $5.63 while mean F1 ran from 45.6 to 60.5, a band of fifteen points. The first option inflates the quality spread fourfold, which is exactly the misreading the chart is drawn to prevent. The third and fourth are both held constant by construction - one benchmark, one golden set - which is what makes the thirteen rows comparable at all.

Practice about 25 minutes, with your own repository

Practice 1working

Find a merged pull request in your repository that changed a function's signature, and work out which architecture would have been needed to review it properly.

List every call site of the changed function at the time of that pull request. Mark each one as inside the diff, in a file the diff touched, or somewhere else entirely.

Then say which of the three architectures would have had each call site in context, and whether the ones outside the diff mattered.

Hint

git log gives you the merge commit; git grep at its first parent gives you the call sites as they were. Counting them at today's HEAD will flatter the diff-only case, because later work has usually tidied up.

Show how the three answers usually come out
  1. Count sites inside the diff. These are the only ones a diff-only reviewer could have reasoned about, and in a well-factored repository they are often most of them.
  2. Count sites in untouched files. Each is a bug a diff-only reviewer could not have found however it was prompted. If this count is zero for every pull request you check, your repository is unusually local and a diff-only reviewer is a sound purchase.
  3. Ask what confirming one costs. A grep and one file read is a few thousand tokens. Compare that against the price band in the chart and you have your depth decision for this repository rather than in general.
  4. Write the sentence. "In this repository, N% of call sites live outside the diff, so a diff-only reviewer has a ceiling of roughly (100 minus N)% on this class of defect."

Sanity check. If your figure is near zero, check that you grepped the whole tree including tests and generated call sites rather than one package - the usual mistake is to search only the directory the change lives in, which measures the thing you are trying to test.

Your teacher. If the three machines still blur together, ask your agent to review one of your pull requests twice: once with only the output of git diff pasted in, then again with the repository checked out and tools allowed. Diff the two reviews. Every finding that appears only in the second is a finding a diff-only product could never sell you.
