How long an agent can run alone is decided by what verification costs

frontier 9 min Built only from Replit's own published engineering writing and product documentation. · Automated self-testing

The one-minute version

  • An agent that cannot check its own work needs a human at every step, so autonomy is bounded by verification cost, not by model quality.
  • The baseline they rejected is priced in public: roughly $0.50 and 30 to 90 seconds to fill a five-field form with a screenshot loop.
  • What they built instead is code, not clicks: Playwright helpers injected into a sandboxed JavaScript REPL whose state persists across cells.
  • Testing runs as a subagent, so the main agent's context receives a summary rather than a transcript.
  • The measured result is a median of $0.20 per session for multi-hundred-step testing. The 3x and 10x comparisons beside it have no published method.

1. Start from the choice, not the company

Every autonomous agent hits the same wall. It can produce a change quickly and it cannot tell whether the change worked, so a person has to look, and the length of an unattended run collapses to the interval between checks. Making the model better does not fix this: a better model still cannot see the rendered page. The only structural fix is to give the agent a way to check, and then the question becomes what one check costs.

Replit published its arithmetic for the obvious approach, which is to let the model drive a browser by looking at screenshots. Assuming Claude Sonnet 4, 1080p screenshot resolution and multi-step context accumulation with about a thousand tokens to represent the DOM, they put it at "roughly $0.50 and 30-90 seconds to fill out a 5-field form". That is one form. A signup flow with a date picker, a file upload and a confirmation step is many forms, and a regression suite is many flows.

2. Code, not clicks

The system they describe has four parts and each one removes a different cost. Playwright helper functions are injected into a Node sandbox, so the agent manipulates the browser by writing code rather than by emitting one tool call per click. The sandbox is a notebook: execution environments persist across interactions, so variables, the browser session and accumulated context carry forward between cells rather than being rebuilt. The state handed back is augmented rather than raw: stripped-down DOM representations with ARIA labels, database query utilities, and client and server logs, so the agent reads the application rather than a picture of it. And testing is a separate agent that receives a high-level plan and returns a summary.

The consequence for anything repetitive is the one to hold on to. A loop that clicks a date picker forward some number of months is a loop in code and one execution, where a screenshot-driven agent pays a model round trip and an image for each press. The cost of a test stops scaling with the number of interactions and starts scaling with the number of things you asked for.

DimensionScreenshot-driven loopCode in a persistent REPL
Unit of actionone tool call per interactionone execution per intention
What the model readsan image, plus a token budget for the DOMstripped DOM with ARIA labels, and logs
Repetitioncosts a round trip each timeis a loop, and costs nothing extra
State between stepsrebuilt, or carried in contextpersists in the environment
What breaks itanything that changes what the page looks likeanything that changes what the page is called

The last row is the honest cost of the trade. A screenshot loop is robust to a renamed test identifier and fragile to a redesign; a code-driven loop is the other way round. Neither is universally better, and a team choosing between them is choosing which kind of change it expects more of.

Two claims published alongside this work have no method behind them: "3x faster and 10x more cost-effective than Computer Use models", and "10x more autonomous" than the previous agent. The announcement carrying them cites no benchmark, names no baseline model and publishes no measurement, so they are marketing rather than evidence. What would make them evidence is small and specific: which computer-use model, on which task set, at which resolution, with the token counts. The $0.20 median and the $0.50 baseline in the engineering post are different, because that post states the assumptions behind them.

3. Autonomy shows up on the invoice

The measured payoff Replit reports is a median cost of $0.20 per session for testing that runs to hundreds of steps, and runs that continue independently for "200+ minutes", up from a twenty-minute baseline. Whatever one makes of the comparisons above, the direction is the interesting part: they bought a tenfold increase in unattended runtime by making one check cheap, not by changing model.

The product documentation makes the same point from the commercial side: autonomy is sold as a dial with a price. Free Mode is "optimized for getting started", Power Mode is "optimized for cost" and uses fewer credits per task, and Max Mode is "optimized for capability" and uses more. A user choosing more autonomy is choosing a larger bill, which is the honest shape of the trade and the same one lesson 0940 drew for your own fleet.

4. Where the leverage went

Set that beside the previous lesson's measurement and the argument closes. If commits rise 180% while releases rise 30%, the scarce input in software is no longer the writing. This next sentence is a reading rather than a finding, and worth labelling as one: if writing is cheap and shipping is not, then leverage moves to whatever gates shipping, which in most teams is specification, review and verification. Replit's decision to spend engineering effort on making an agent test its own work is one instance of that, made by a company whose product is agent-written software and which therefore feels the constraint before anyone else does.

Check yourself

Retrieval practice

Answer from memory before revealing.

Why does running the tester as a subagent lengthen how long the main agent can work alone?
A long unattended run is limited by the main agent's context, and a full test transcript would consume it quickly; a summary does not. The first option may be true of some designs and is not the mechanism described. The second describes parallelism, which is a different benefit. The third is isolation, which is real but does not explain a longer run.
Which of these published Replit figures should be labelled marketing rather than evidence?
The comparative claim names no baseline model, no task set and no method, so nothing about it can be checked. The first and third are numbers published with their assumptions stated, which is what makes them citable even though they are self-reported. The fourth is a mechanism rather than a number, and a mechanism described in enough detail to rebuild is the easiest kind of claim to check.

Practice two problems: one short, one the module assignment

Practice 1frontier

Price the human check in your own pipeline.

Name one verification step that a person currently performs before a change of yours can ship: a manual smoke test, a screenshot review, a staging click-through, a data check. Estimate how many minutes it takes and how many times a week it happens.

Then answer the question Replit answered: could an agent do this if it could run code against a live instance and read the logs? If yes, write down what it would need to be given.

Hint

The step you want is the one that makes people batch their work. If changes wait to be released together because the check is expensive, that check is the neck in the drawing above.

Show a worked example
  1. Name it concretely. "Somebody opens staging and clicks through checkout once before every release." Ten minutes, four times a week.
  2. Price it in the unit that matters. Forty minutes a week is not the cost. The cost is that releases wait for a person, which is why four a week is the number rather than forty.
  3. List what an agent would need. A staging URL it may reach, a seeded test account, the ability to run code against the browser, and read access to the server log for that window. Three of those four are permissions and one is a tool.
  4. Check the failure mode. If the check is really "does it look right", a code-driven agent will not do it and a screenshot loop might. Say which kind of check you have before choosing the mechanism.

Sanity check. If your named step turns out to take almost no time and blocks nothing, you have named a habit rather than a gate. Look further downstream: the real gate is usually the one nobody schedules because it happens whenever a particular person is free.

Practice 2 · the module assignmentfrontier

Put a gateway and a tool policy in front of your own agent, and prove both are working. This is the whole of module 9 in one pass, against the repository you chose for the capstone.

  1. Stand up a gateway locally with two model groups and a fallback from the expensive one to the cheap one, then point your agent at it with ANTHROPIC_BASE_URL and the credential variable your gateway reads.
  2. Force a failure and capture the log line proving the fallback fired.
  3. Write a managed-settings.json for a team of five: two deny rules that would have stopped a real mistake you have made, one ask rule, telemetry pointed at a local collector, and the version floor.
  4. Add one MCP server through policy rather than by hand: an allowedMcpServers entry and an mcpConnectorToolControls block blocking its most destructive tool.
  5. Run one real task through the whole stack and compute three numbers from the exported metrics: total cost, cache-read share of input tokens, and tokens spent on tool definitions.

Hand in four files, one log line, and five lines of prose giving the three numbers and saying which of them surprised you. Commit the result to your capstone repository as docs/agent-platform.md, with the managed settings file as a template under contrib/.

Hint

Do them in the order given. Steps three and four are quick once step one works, and step five is quick once step three has pointed telemetry somewhere. If step one fights you, the fault is almost always the credential variable choosing the wrong header.

Show how to check your own work
  1. The fallback line is binary. It is either in the log or it is not, and "the request succeeded" is not the same evidence. Read which deployment answered.
  2. Check the policy is in force, not merely written. /status names the setting source. If it does not name a managed source, everything downstream of it is untested.
  3. The three numbers need no judgement. Total cost and cache share come from the session block, and the tool-definition figure comes from /context. All three are read rather than estimated.
  4. Attack your own deny rule. Ask for the denied thing in different words. If rephrasing the request gets past it, you wrote guidance and not policy, and the fix is a permission rule or a hook rather than a better sentence.

Sanity check. The cache-read share on any session longer than a few turns should be high, often above 90%. A low share on a long session means the prefix is being invalidated every turn, and finding out what is rewriting it is worth more than everything else in this assignment.

Your teacher. If the marketing and evidence distinction still feels like nitpicking, ask your agent to rewrite the 3x claim as a sentence you could check, and notice how much has to be added. If the assignment stalls, ask it to run only step one and to print the first request the gateway received, headers included.
