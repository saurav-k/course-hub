Log everything, read a sample by risk, and keep one switch that stops it all

frontier 13 min The event shape you already emit, the layers underneath it, and the trap that only shows up once you have an allowlist. · Monitoring usage · Containment

The one-minute version

  • Nobody reviews every action of an unattended fleet, so the honest design is: log all of them, read a risk-weighted sample, and be able to stop everything at once.
  • You do not have to invent the event shape. Twelve event names and a standard attribute set already exist, and prompt.id ties every event from one prompt together.
  • Containment is layered and named: an OS sandbox, mount rules, an egress allowlist, and a defensive proxy - because an allowlisted domain is still an exfiltration path.
  • Five kill switches exist and they are not equivalent. Know which one you would reach for, and check that the list you wrote down is complete.

1. Log everything, and read almost none of it

The published framework states the policy in one sentence, and the sentence is doing more work than it looks: "Every automated approval, tool call, and agent-to-agent message is logged with the signals it used and lands in our SIEM." Note what is being logged - not the outcome, but the signals the decision used, which is what lets a reviewer disagree with a decision rather than merely notice it.

The reading half is the honest part. Nobody reads all of it. What gets read is a risk-weighted sample, by a person, on a schedule, and human reviewers move from inspecting routine changes to watching these loops and dashboards. That is the real answer to "who reviews the reviewer", and it is a sampling answer rather than a coverage one.

2. The event shape already exists

Before writing a bespoke log, look at what is already emitted. Eight metrics and twelve events, over OpenTelemetry, with a standard attribute set on every one of them. Three of those events are the interesting ones for supervision: claude_code.tool_decision, claude_code.api_error and claude_code.permission_mode_changed.

The attribute that turns a stream into a story is prompt.id, a UUID linking every event produced while one prompt is processed. Filter by it and you get the prompt, the API requests it caused and every tool result that came back - the whole turn, in order, without reconstructing anything.

one audit row · authored for this course · every field name and value is documented at code.claude.com/docs/en/monitoring-usage
{
  "event.name":      "tool_decision",
  "event.timestamp": "<ISO 8601, written by the exporter>",
  "event.sequence":  412,

  "session.id":      "01JXXXXXXXXXXXXXXXXXXXXXXX",
  "prompt.id":       "b6f0c3a2-0000-4000-8000-000000000000",
  "organization.id": "00000000-0000-0000-0000-000000000000",
  "user.email":      "fixer@acme.example",
  "team.id":         "platform",

  "tool_name":       "Bash",
  "tool_use_id":     "toolu_01XXXXXXXXXXXXXXXXXXXXXX",
  "tool_source":     "builtin",

  "decision":        "accept",
  "source":          "config"
}

Two fields carry the whole review. decision is accept or reject. source says who decided, and its documented values split cleanly into machine and human: config and hook on one side, user_permanent, user_temporary, user_abort and user_reject on the other. team.id is not built in - it is a custom resource attribute, which is how a fleet's rows become answerable by team rather than only by session.

Three queries are what the row is shaped for, and each one answers a question a reviewer would otherwise have to guess at.

  • What ran with no human anywhere in the loop. decision = "accept" AND source IN ("config", "hook"). Everything here was approved by a rule you wrote, which means every one of these is a rule you should be able to point at.
  • Which identity ran a shell, and under what rule. tool_name = "Bash" AND source = "config", grouped by user.email. An identity appearing here that your policy file says should never run a shell is the finding.
  • What each agent actually uses. group by user.email, tool_name over thirty days. Anything absent for a month is not part of that agent's job, and the list is the input to narrowing its allow rules.
Tool arguments are not in the row above, and that is the default rather than an omission: the parameters field appears only when OTEL_LOG_TOOL_DETAILS=1 is set, and it carries the full shell command among other things. Turning it on makes the second query far more useful and turns your log into a place where a secret typed into a command line now lives forever. Decide that deliberately, in the same conversation as your retention period, and never as a debugging convenience somebody leaves on.

3. What the log is a record of

A log of tool calls is only interesting if something underneath it was capable of refusing. The layers are documented and named, and they nest.

4. An allowlisted domain is still a way out

This is the measured trap worth the whole lesson, and it is the kind of thing you only find by running the system rather than by designing it.

An egress allowlist admits a host. It does not admit a purpose. The published account puts it exactly: "Allowing api.anthropic.com meant allowing file uploads to arbitrary Anthropic accounts." The domain was on the list for a good reason, and that same entry was a channel out.

The fix is a second proxy, positioned deliberately: a defensive man-in-the-middle proxy inside the machine that passes only requests carrying that machine's own provisioned session token, and rejects an attacker-embedded key. It has to sit inside because only the machine knows the provenance - from the server's side, a request from a compromised session looks like any other client.

Two more findings from the same account are worth keeping because both look like ordering details and both are escapes. Symlink resolution has to happen before path validation, not after, or a link inside an authorised folder points outside it and the check passes on the wrong path. And a project's own configuration is parsed only after the trust prompt is accepted, on the principle that opening a project, loading a config and listening on localhost should all be treated the way an inbound request from the internet is treated rather than implicitly trusted.

5. Five switches, and they are not the same switch

Every unattended system needs a way to stop, and "we would just turn it off" is not one until somebody has named which thing they would turn off. These five exist, they act at different scopes, and they take effect at different moments.

SwitchScopeTakes effectWhat survives it
Delete the workflow filesone repositoryimmediately, on the next eventroutines, desktop tasks, local sessions
A deny rule in managed settingsevery machine carrying the policythe next session on each machineanything not using that tool
CLAUDE_CODE_DISABLE_CRON=1one machine's sessionsimmediately - scheduled tasks stop firingcloud routines, CI workflows
The organisation Routines toggleevery member of the organisationimmediately - existing routines stopCI workflows, local sessions
Revoke the credentialeverything authenticating with itthe next run that needs itanything holding a different credential

Read the last column rather than the first. Each switch leaves something running, and the one people reach for in a hurry - deleting the workflow file - leaves every cloud routine untouched. A complete stop is a short ordered list, and the place to write that list is the policy file from the previous lesson, where it sits beside the identities it stops.

6. What watching is for, and one number about it

The point of all this is not tidiness. It is that review moves from being a thing people do to being a thing people supervise, and the measurable claim made for that shift is about depth rather than volume.

Both numbers above are self-reported, from one organisation about its own codebase, with no published method: no definition of "substantive", no baseline period stated, and no independent replication. They are worth printing because they are specific and attributable, and they are not evidence about your repository. What would make them evidence is exactly what is missing - the classifier that decided what counts as substantive, the population, and the same measurement taken somewhere else. Ask for those three before you quote either figure in a planning document.

Check yourself

Retrieval practice

Answer from memory before revealing.

Why does the defensive proxy sit inside the machine rather than in front of it?
The published reasoning is about provenance: from the server's side a request from a compromised session is indistinguishable from any other client, so only something inside the machine can tell whether the request carries the session's own provisioned token. The first option is wrong - TLS termination is a configuration choice available in either position. The third is true but is a deployment detail, not the reason. The fourth is simply false.
You want every tool call that was approved without a person in the loop. Which filter is right?
The source attribute is what names the decider, and its documented values split into config and hook for machine decisions against four user_ values for human ones. The first filter selects built-in tools rather than automatic approvals. The second selects everything, since every event carries a session identifier. The fourth finds human rejections, which is a different and also useful query.

Practice about 40 minutes, with telemetry turned on

Practice 1frontier

Turn on telemetry for one agent in your factory and capture a single unattended run end to end.

Find the run's prompt.id values and reconstruct one whole turn from them: the prompt, the API requests it produced, and every tool decision.

Then run the first of the three queries above - every acceptance whose source is config or hook - and, for each distinct rule it names, point at the file the rule lives in.

Finally, break it on purpose. Flip one kill switch from your policy file and confirm from the log that the agent stopped. Then check whether anything else did.

Hint

Start from the smallest possible run - one issue, one file changed - so the reconstruction is a dozen events rather than a hundred. The exercise is about the joins, not the volume.

Show what each step should turn up
  1. The reconstruction should have no gaps. If a tool call appears with no matching prompt, either the exporter dropped events or something started a turn you did not trigger. Both are worth a morning.
  2. Most acceptances should name a rule you can point at. An acceptance whose source is config and whose rule you cannot find in any settings file means the rule is coming from a layer you had forgotten about - managed settings, or a project file you did not write.
  3. Expect the kill switch to leave something running. The common surprise is that deleting the workflow leaves a cloud routine firing on its own schedule, or that revoking the model credential stops the agent while the trigger keeps starting empty runs.
  4. Then correct the switch list in your policy file. That correction is the whole deliverable. A stop procedure nobody has executed is a stop procedure that has not been tested.

Sanity check. A correct run of this exercise produces one reconstructed turn, a short list of named rules, and at least one surprise in step four. If step four produced no surprise, check whether the thing you stopped was actually running before you stopped it.

Your teacher. Ask your agent to list every place a permission decision could come from on your machine - managed settings, user settings, project settings, a hook, a session answer - and then ask which of them would appear in a tool_decision event as source: "config". The layers it names that you did not know about are the ones your audit log has been quietly attributing to you.
