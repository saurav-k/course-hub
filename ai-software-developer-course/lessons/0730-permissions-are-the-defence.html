Module 07 · Security · Lesson 0730

You narrow what the tools reach, not how politely you ask

working 9 min Written against Claude Code's published permission reference, as one worked instance of the mechanism. · Configure permissions

The one-minute version

  • A permission mode sets the session baseline - what runs without anyone being asked - and rules narrow it from there.
  • Rules are evaluated deny, then ask, then allow. The first match in that order decides, and being more specific does not change the order.
  • Deny wins in every mode, including the one that skips checks; allow rules have no effect in that mode at all.
  • The * stands in for whatever text is in its place, so a wildcard before the subcommand hands back the whole program.
  • File rules cover the agent's own tools and the file commands the harness recognises. They do not cover a script that opens the file itself, and that gap is the next lesson.

1. The mode is the baseline, and there are six

Before any rule of yours is consulted, the session has a posture. Claude Code publishes six, and reading them as a ladder is the fastest way to see what a mode actually is: a statement about who reviews an action - you, a classifier, or nobody.

ModeWhat runs without askingWho is reviewing
default (Manual)reads, and a built-in set of read-only commandsyou, on everything else
acceptEditsreads, file edits, common filesystem commandsyou, on everything else
planreads, plus classifier-approved commands where availableyou approve a plan before edits
autoeverything, with background safety checksa second model, the classifier
dontAskonly pre-approved toolsnobody at run time - your allowlist decided in advance
bypassPermissionseverythingnobody

Two properties of that last row are the ones to memorise, because they are what makes a checked-in policy worth writing at all. Deny rules block in every mode, including bypassPermissions. Allow rules have no effect in bypassPermissions. A deny list is therefore the only part of your policy that survives somebody launching the agent with the safety off, which is a good reason to put your genuinely dangerous cases there rather than relying on the absence of an allow.

2. The grammar, and the order that decides

A rule is a tool name, optionally narrowed: Bash matches every use of the tool, Bash(npm run *) matches a shape of command. Rules live in three lists - allow, ask and deny - and the documentation is explicit that they are "evaluated in order: deny, then ask, then allow", with the first match deciding and specificity changing nothing.

That last clause has a consequence people find counter-intuitive: a broad deny cannot carry an allowlisted exception. Bash(aws *) in deny blocks aws s3 ls even with an exact allow rule for it, because deny is consulted first and the first match wins.

3. The asterisk stands in for whatever is in its place

Here is the single most expensive misreading in the whole permission system, and it is documented in one sentence: the * stands in for whatever text is in its place. Put it after the program and before the subcommand, and you have not narrowed the rule - you have widened it to every subcommand that program has.

The documented example is Bash(git * main). It looks like a rule about the main branch. It matches git merge main, git push origin main, and git -c core.fsmonitor=<script> diff main - the last of which makes git run a program you name. And it does not match plain git log. The rule admits more than you meant in the dangerous direction and less than you meant in the harmless one.

Check yourself on three more, before reading on

Does Bash(ls *) match lsof? Does Bash(ls*)? Does Bash(* --help *) match npm --help?

No, yes, no. The space before a trailing asterisk is part of the rule, so ls * requires one and ls* does not. And a trailing asterisk matches the bare command only when it is the rule's only wildcard, which is why Bash(ls *) matches plain ls but Bash(* --help *) does not match plain npm --help. All three are in the documentation's matching table.

4. File rules, and the sentence that ends this lesson

Read and Edit rules use gitignore pattern syntax, so Read(.env) and Read(**/.env) are equivalent and both match at any depth. A leading / anchors at the settings file's own location rather than at the filesystem root, which is why the same rule means different things in user settings and project settings.

Two behaviours are worth knowing before you write your list. A Read deny rule also blocks the edit and write tools on the same path. And an output redirection - >, >>, 2> - is checked as a file write, so a rule that allows a command does not thereby allow its target.

Then the sentence that makes the next lesson necessary. Read and Edit deny rules apply to the agent's own file tools and to file commands the harness recognises in Bash, such as cat and head. They "don't apply to arbitrary subprocesses that read or write files indirectly, like a Python or Node script that opens files itself."

Read that limit as an engineer rather than as a reader of documentation. Your agent can write a file. Your agent can run an interpreter. A rule that matches command strings is therefore a rule about the commands somebody bothered to spell out, and two lines of Python are not one of them. Nothing on this page closes that gap, and the vendor says so in its own documentation rather than leaving you to find out. The gap is closed at the kernel, in the next lesson.

5. Put the policy in the repository

Permissions are a team artefact, not a preference. Checked in, they arrive with the clone, change through review like anything else, and mean the same thing on a colleague's machine and in an unattended run. The file below is this course's own, written against the documented keys, and it is the shape worth starting from: a short allow list of the commands your project actually needs, an ask list for the ones that leave the machine, and a deny list holding the cases you never want, in any mode.

.claude/settings.json · ours, written against the documented permission keys · hub content, CC BY 4.0 · reproduce freely
{
  "permissions": {
    "defaultMode": "default",
    "allow": [
      "Bash(npm run test:*)",
      "Bash(npm run lint)",
      "Bash(git status)",
      "Bash(git diff *)",
      "Bash(git commit *)"
    ],
    "ask": [
      "Bash(git push *)",
      "Bash(gh pr create *)"
    ],
    "deny": [
      "Read(.env)",
      "Read(**/.env.*)",
      "Read(~/.aws/**)",
      "Read(~/.ssh/**)",
      "Edit(.github/workflows/**)",
      "Bash(curl *)",
      "Bash(wget *)",
      "WebFetch",
      "WebSearch"
    ]
  }
}

Read the deny list as three separate decisions rather than one. The first four entries remove the private-data leg for the paths that matter most. The workflow entry stops the agent editing the thing that grants it permissions in CI, which is the self-escalation move you will meet again in lesson 0750. The last four remove the egress leg from the tools that have it by name - and, as the warning above says, not from a script that opens a socket itself.

Answer from memory before revealing.

Your settings deny Bash(aws *) and allow Bash(aws s3 ls). What happens when the agent runs aws s3 ls?
Rules are evaluated deny, then ask, then allow, and the first match decides - specificity is not part of the ordering at all. That is why a broad deny cannot carry exceptions, and why you narrow the deny rather than adding an allow beside it. The third option describes a conflict resolution that does not exist here, and the fourth invents a mode dependency: a mode changes what happens when no rule matches, not which list is read first.
You deny Read(~/.aws/**). Your agent then writes and runs a short Python script that opens that file. What happens?

This is the exact gap the sandbox closes at the operating system. The second option is plausible and wrong in a useful way - running the interpreter may well need approval, but that is a separate rule and a permitted python is common. The fourth imagines the path being inspected inside a file the agent writes, which nothing does.

Practice about 25 minutes, with your own repository

Practice 1working

Write the policy your capstone repository will keep for the rest of this course.

Start from the deny list, not the allow list: name the paths that would hurt if they left the machine, and the commands you never want run unattended. Then add the smallest allow list that lets a normal task finish without prompting you - build, test, lint, and the git commands short of a push.

Then audit your own asterisks. For every allow rule you wrote, name one command it admits that you did not have in mind. If you cannot find one, the rule is either exact or too loose, and you should be able to say which.

Hint

Take each rule and read the asterisk out loud as "anything at all". Bash(npm run *) becomes "npm run anything at all", which is exactly right if your package scripts are trustworthy and exactly wrong if one of them is a deploy.

Show the three findings this usually produces
  1. A script name you forgot. Bash(npm run *) admits every entry in scripts, including deploy, release and anything a dependency's postinstall added. Narrowing to Bash(npm run test:*) and Bash(npm run lint) costs you two lines and removes the surprise.
  2. An asterisk before the subcommand. If any rule has a wildcard earlier than the word that decides what the program does, rewrite it. The tool warns at startup about an allow rule shaped that way, which is worth knowing about but is not a substitute for reading your own file.
  3. A deny you assumed was covered by an allow's absence. Anything that must never run belongs in deny explicitly, because that is the only list that still applies if somebody starts the session with checks skipped.

Sanity check. Run one ordinary task with the policy in place. If you are prompted more than twice, your allow list is missing something routine; if you are never prompted at all, check that you have not simply written a rule broad enough to cover everything the task happened to do.

Your teacher. Hand your agent your own settings.json and ask it to list, for each allow rule, three commands the rule admits that a reader would not expect. Then ask it which single rule it would rewrite first. Check its answers against the matching rules yourself - this is a question about string matching, and it is a good place to catch a confident wrong answer.
