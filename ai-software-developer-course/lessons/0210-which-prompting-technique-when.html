Name the failure and the technique picks itself

foundation 11 min Written against the single prompting-best-practices page, because the per-technique pages were collapsed into it. · Prompting best practices

The one-minute version

  • These techniques are not a ranking. Reaching for the "best" one is how you end up paying for examples when the problem was an ambiguous instruction.
  • Start from the symptom. Wrong shape, wrong reasoning, unstable answer, wrong tone, mixed-up input and instruction, unparseable output, task too big. Seven failures, seven answers.
  • Two of the old habits are gone. Chain of thought is now mostly adaptive thinking, and prefill returns a 400 on Claude 4.6 and later.
  • Every technique costs tokens, and lesson 0200 is why that sentence has teeth.

1. The picker

Read down the left column until you recognise something you have watched an agent do this week, then open it. Nothing here needs to be memorised; the point is that the mapping exists at all.

The output has the right content in the wrong shape, and the shape drifts between runs.

Few-shot, also called multishot. Show three to five examples instead of describing the format. The guidance is exact about all three qualities: examples should be relevant ("mirror your actual use case closely"), diverse ("cover edge cases and vary enough that Claude doesn't pick up unintended patterns"), and structured - wrapped in <example> tags, several of them inside <examples>, "so Claude can distinguish them from instructions". Cost: the examples are input tokens on every call that carries them.

Multi-step reasoning arrives at a confidently wrong answer, and the working is not shown.

Chain of thought, which on current models you mostly do not write yourself. Wei and colleagues showed in Chain-of-Thought Prompting Elicits Reasoning in Large Language Models that "prompting a 540B-parameter language model with just eight chain of thought exemplars achieves state of the art accuracy on the GSM8K benchmark of math word problems, surpassing even finetuned GPT-3 with a verifier". Claude 4.6 and later use adaptive thinking, where the model decides when and how much to think, and the documentation states that "in internal evaluations, adaptive thinking reliably drives better performance than extended thinking". Manual chain of thought is now the fallback for when thinking is off. Cost: thinking tokens are billed as output and count toward the window.

The method is right and the answer moves between runs.

Self-consistency. Sample several reasoning paths and take the most common answer rather than the first one. The numbers are in the chart below. Cost: you pay for every path you sample, so this is the most expensive technique on the page by a wide margin.

The answer is correct and pitched wrong - too shallow, too verbose, wrong audience.

One sentence of role in the system prompt. The guidance is that "setting a role in the system prompt focuses Claude's behavior and tone for your use case. Even a single sentence makes a difference." Cost: about a dozen tokens, which makes this the cheapest thing on the page.

The model followed your example data as if it were an instruction, or vice versa.

XML tags. Wrap each kind of content in its own named tag so the boundaries are unambiguous: <instructions>, <context>, <input>. Use the same tag names across your prompts, and nest them where the content has a hierarchy. Cost: a few tokens per tag, and it is the highest-value few tokens in this list.

Your parser breaks on the response, sometimes.

Structured outputs, not a prompt. See section 3, which also carries the code. Cost: the schema is input tokens; the constraint is enforced rather than requested.

The task is too big and you cannot see where it went wrong.

Prompt chaining: break the task into sequential API calls so you can log, evaluate or branch between them. Anthropic's Building effective agents defines it as breaking a task "into a sequence of steps, where each LLM call processes the output of the previous one", and says it fits "where the task can be easily and cleanly decomposed into fixed subtasks". The best-known shape is draft, review, refine. Cost: more round trips and more latency, in exchange for a seam you can inspect. This is the technique lesson 0220 turns into a working habit.

2. The one technique with published numbers

Self-consistency is worth its own section because it is the one place in this list where the size of the effect is measured and public. Wang and colleagues, in Self-Consistency Improves Chain of Thought Reasoning in Language Models, replace greedy decoding with a decoding strategy that "samples a diverse set of reasoning paths instead of only taking the greedy one, and then selects the most consistent answer by marginalizing out the sampled reasoning paths".

3. When the output has to parse, constrain it rather than ask

Structured outputs constrain the response to a JSON Schema through the output_config parameter. This is not a prompting technique dressed up: the constraint is enforced, so there is no run in which the model decides to add a friendly preamble. Every object in the schema must carry additionalProperties: false.

extract.py · Claude API structured outputs · Anthropic documentation, quoted with attribution · reproduced verbatim in shape, with the field values written for this page
import anthropic

client = anthropic.Anthropic()

response = client.messages.create(
    model="claude-opus-5",
    max_tokens=1024,
    messages=[{
        "role": "user",
        "content": "Extract the key information from this email: ...",
    }],
    output_config={
        "format": {
            "type": "json_schema",
            "schema": {
                "type": "object",
                "properties": {
                    "name": {"type": "string"},
                    "email": {"type": "string"},
                    "plan_interest": {"type": "string"},
                    "demo_requested": {"type": "boolean"},
                },
                "required": ["name", "email", "plan_interest", "demo_requested"],
                "additionalProperties": False,
            },
        }
    },
)

print(response.content[0].text)

The parameter is output_config. output_format is the older name and survives only as a convenience argument on the SDK's messages.parse() helper, where it takes a Pydantic model rather than a raw schema.

4. The technique that now returns a 400

Prefill - supplying a partial trailing assistant turn for the model to continue from - was the standard way to force a JSON opening brace, skip a preamble, or steer around a refusal. It is no longer available, and the failure is loud rather than silent.

Quoted exactly: "Starting with Claude 4.6 models and Claude Mythos Preview, prefilled responses (providing a partial assistant message for Claude to continue from) on the last assistant turn are no longer supported. Requests with prefilled assistant messages to these models return a 400 error." Earlier models still accept prefill, and an assistant message anywhere other than the last turn is unaffected. If you inherited a prompt library, this is the line to grep for before you change the model id in it.
What prefill used to doWhat to do instead
Force JSON or YAML outputStructured outputs, or a tool with an enum field for classification
Skip a preambleA system instruction: "Respond directly without preamble"
Steer around a bad refusalNothing. Clear prompting in the user message is enough on current models
Continue an interrupted responseMove the continuation into the user turn, quoting the interrupted text
Re-inject context in a long chatInject into the user turn, hydrate through a tool, or use compaction

Paraphrased from the five migration cases on Prompting best practices, under "Migrating away from prefilled responses".

5. What the picker cannot do for you

The mapping is real and it is also only half the job. A technique is chosen against a failure you have observed, and the observation is the expensive part: you need the same task run more than once, with the output kept, before "the shape drifts" is a fact rather than an impression. If you have not got that, the honest move is to build it before reaching for any of the seven.

The other half is that several of these live better in a file than in a prompt. A role sentence you retype is a role sentence you will eventually forget; the same sentence in a repository instruction file arrives on every turn. Context engineering, in Coding Harness Engineering, measures which files thirteen harnesses actually read and in what order, which is the mechanism module 4 of this course builds on.

Check yourself

Retrieval practice

Answer from memory before revealing.

Your extraction pipeline breaks about one call in thirty on a stray preamble. Which fix is enforced rather than requested?
Only structured outputs constrains the response rather than asking for it, which is why the one-in-thirty case disappears instead of getting rarer. The first option is the technique that now returns a 400 on Claude 4.6 and later. The third and fourth both raise the odds and neither removes the tail, which is the failure you actually have.
Which of these techniques is the most expensive per answer, and why?
Self-consistency pays for several complete reasoning paths and keeps one, so its cost is a multiple of a normal answer rather than an addition to one. Few-shot is the runner-up and is a real cost, but three to five examples are input tokens once per call, not a whole extra generation. XML tags and a role sentence are each a handful of tokens.

Practice about 25 minutes, with a terminal

Practice 1foundation

Take one prompt you actually use - a commit-message generator, a test-name generator, a changelog summariser - and run it five times on the same input, keeping every output.

Classify what you see against the seven failures in the picker. Then apply exactly one technique, run it five more times, and say whether the failure you named is the one that changed.

Hint

Five runs is enough to tell drift from noise on a shape failure and not enough on a correctness failure. If your symptom is "sometimes wrong" rather than "differently shaped", you need a task where you know the right answer.

Show what a good pass looks like
  1. Name the symptom before choosing. Write one sentence describing what differs between the five outputs. If you cannot, the prompt has no observed failure and no technique is indicated.
  2. Match it to exactly one row. Shape drift goes to few-shot. Instruction and data bleeding into each other goes to XML tags. An unparseable field goes to structured outputs.
  3. Change one thing. Applying two techniques at once means neither run tells you anything, which is the mistake this whole page is arranged to prevent.
  4. Re-run five times and compare on the named symptom only. An improvement somewhere else is interesting and is not evidence about your hypothesis.
  5. Price it. Count the tokens the technique added, and multiply by how often the prompt runs in a week.

Sanity check. If the second five runs are identical to each other, you probably applied structured outputs or a strong few-shot set, and the drift is genuinely gone. If they still differ but differently, the failure you named was not the failure you had, and re-classifying is cheaper than adding a second technique on top.

Your teacher. If the picker feels like a list to memorise, ask your agent to take one of your real prompts and say which of the seven failures it is currently defended against, and which it is wide open to. If prefill is new to you as a concept, ask it to write the same classification task twice - once as a tool with an enum field, once with structured outputs - and to say which it would choose in a loop that already carries tools.
