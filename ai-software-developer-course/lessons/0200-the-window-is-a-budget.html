Module 02 · Advanced context engineering · Lesson 0200

The window is a budget, and something is always being evicted

foundation 10 min Every figure on this page is a published number, not an estimate. · Context windows

The one-minute version

  • A million tokens sounds like room to spare. It is not: accuracy and recall fall as the window fills, and the documentation has a name for that.
  • Everything counts. The system prompt, every message, every tool result, every image, and your tool definitions. A cached prefix counts too.
  • The overhead you did not write is published per model, so you can add it up before you send anything. On Claude Opus 5 the floor is 1,311 tokens for a tool-using turn with two standard tools.
  • You own two levers: what you put in, and what you let a tool return. The platform owns the third, which is compaction.

1. The number, and why it is not the good news

Start with the capacity, because it is the part everybody quotes. Claude Opus 5, Claude Sonnet 5 and every Claude 4.6-or-later model carry a 1M-token context window, with up to 128k output tokens in a single response. Claude Sonnet 4.5 and the older models carry 200k. For the 1M models that is the default rather than a beta: no header, and long-context requests are billed at the standard rate.

Now the part that is usually left out. The same page says plainly that "more context isn't automatically better. As token count grows, accuracy and recall degrade, a phenomenon known as context rot." That is the whole reason this module exists. If filling the window were free, context engineering would be a synonym for "paste more in", and the correct technique for every failure would be the same one.

The reframing A context window is not storage you fill. It is a budget you spend, and the currency buys attention rather than space. The question is never "will it fit"; it is "is this the best thing I could have spent those tokens on".

2. Everything counts, including the parts you did not write

The accounting rule is one sentence and it has no exceptions: "Everything in the request counts toward the context window: the system prompt, every message in messages (including tool results, images, and documents), and your tool definitions." The output counts too, thinking included, and every response reports what it consumed in its usage field.

Two consequences catch people out. The first is prompt caching, which looks like it should help here and does not: "Cached prompt prefixes still occupy the context window: prompt caching changes what you pay for those tokens, not whether they count." A cache read costs a tenth of the base input price and takes exactly as much room. The second is the tool-use system prompt: when a request carries any tool at all, the API adds a system prompt of its own to teach the model to use it, and that arrives before your first schema.

3. The tax on a tool-using turn, in published figures

Here is the arithmetic you can do before sending anything, all of it from the pricing page. A request that carries at least one tool picks up the tool-use system prompt: 286 tokens on Claude Opus 5 with tool_choice at auto, and 406 when you force a tool. Declare the bash tool and that adds 325 more on Opus 5. Declare the text editor tool and that adds 700. So a turn with those two standard tools starts at 1,311 tokens before your own system prompt, your own schemas, or a single word of the task.

Those figures move between releases, which is why this course carries versions in sentences rather than dates on pages. The same tool-use system prompt was 675 tokens on Claude Opus 4.7 and 354 on Claude Sonnet 5. Read the number for the model you are actually running.

4. Do the arithmetic on your own setup

The number that surprises people is not any single schema. It is the multiplication. A tool definition is input tokens on every turn of every task, forever, so its cost is the schema size times the number of tools times the number of turns. Move the sliders below to your own setup and read the second number rather than the first.

5. The two levers you own, and the one you do not

The first lever is admission: what you allow into the window at all. Instruction files, tool definitions, retrieved documents, examples. Every page after this one in the module is a way of pulling that lever.

The second is the size of what comes back. A tool result is a message, so a tool that returns a whole file has spent your budget on your behalf. Lesson 0260 is about designing the tool so it does not.

The third lever is eviction, and it is the platform's. When a conversation approaches the limit, server-side compaction summarises the earlier parts so the conversation can continue past it, and context editing can clear old tool results. That is a policy running on someone else's machine, and the harness you are using has one of its own. Context engineering, in Coding Harness Engineering, measures what thirteen harnesses actually do here, with compaction triggers spanning fifteenfold; this course does not re-derive that list.

Overflow is not graceful, and the two failures look nothing alike. If the input alone exceeds the window, every model returns a 400 invalid_request_error reading "prompt is too long". If the input fits but the generation runs into the limit, Claude 4.5 and later stop with stop_reason: "model_context_window_exceeded" and hand you a truncated answer that looks finished. An agent loop that does not branch on that stop reason will treat a cut-off response as a result.

6. What the rest of this module spends it on

Seven techniques follow, and each one answers a different failure rather than being better than the one before it. Lesson 0210 is the picker. Lesson 0220 and lesson 0230 spend the budget on deciding before implementing. Lessons 0240 to 0270 spend it on tools, and the last of them is about not spending it at all.

One habit is worth starting now. Before you mount anything, ask what it displaces. The window has no empty space in it, only things you have not yet noticed you are paying for.

Check yourself

Retrieval practice

Answer from memory before revealing.

Your 40k-token system prompt is a cache hit on every request. What has caching done to your context budget?
The documentation is explicit: caching changes what you pay for those tokens, not whether they count. The second and fourth options describe a cache that stores context outside the window, which is not what this is. The third confuses the price multiplier, which is 0.1x, with an effect on space, of which there is none.
On Claude Opus 5 you declare the bash tool and nothing else. How many input tokens does that cost before your own system prompt?
The tool-use system prompt applies whenever any tool is present, and the bash definition is charged on top of it, so 286 plus 325 is 611. The first two options each name one half of the sum and drop the other, which is exactly the mistake the pricing page warns about by listing them on separate pages. The fourth is the belief this section exists to remove.

Practice about 20 minutes, with a terminal

Practice 1foundation

You are running an agent on Claude Opus 5 with the bash tool, the text editor tool, and six tools of your own whose schemas average 400 tokens each. Your repository instruction file is 3,000 tokens. The task runs for 25 turns and nothing is cached.

Work out the total input tokens spent on things that are identical on every turn, and what that costs at the published Opus 5 base input rate. Then say which single change would cut it most.

Hint

Separate the per-turn fixed block from the growing history. Everything in the fixed block is charged once per turn, so multiply it by the turn count rather than counting it once.

Show the worked solution
  1. Add the published overhead. Tool-use system prompt 286, bash 325, text editor 700. That is 1,311 tokens.
  2. Add your own schemas. Six tools at 400 tokens is 2,400. Running total 3,711.
  3. Add the instruction file. Plus 3,000 gives a fixed block of 6,711 tokens on every single turn.
  4. Multiply by turns. 6,711 times 25 is 167,775 input tokens, none of which is the task.
  5. Price it. 167,775 divided by 1,000,000, times $5, is about $0.84 for the fixed block alone.
  6. Find the biggest lever. The instruction file at 3,000 is the largest single item and the one entirely under your control, but caching the whole fixed block is larger still: at 0.1x it takes the $0.84 to about $0.08, without removing anything.

Sanity check. Your fixed block should be roughly 6 to 7 thousand tokens, so 25 turns lands under 200k and comfortably inside a 1M window: the answer here is about money and about attention, not about running out of room. If your total is near 1M you have multiplied the history in as well, which grows rather than repeating.

Your teacher. If the fixed block still feels abstract, ask your agent to print the usage field of its first two API calls on a small task and to subtract one from the other. The difference is the growth; what is left is the block you pay for every turn. If context rot feels like a claim rather than a mechanism, ask it to explain why recall on a fact placed in the middle of a long context behaves differently from recall on the same fact placed at the end.
