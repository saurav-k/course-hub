Make the spec the unit of work, not the diff

foundation 9 min Every template quoted here is read from the repository at a pinned commit, not from a blog post about it. · github/spec-kit

The one-minute version

  • Lesson 0220's plan lived in a session. A spec is the same document committed, which is what makes it reviewable, diffable and reusable.
  • Two mechanisms make a spec agent-usable rather than merely written: prioritised, independently testable user stories, and a marker the generator uses to admit what it does not know.
  • The templates are small. The one that carries the requirements is 131 lines; the one that carries the task breakdown is twice that.
  • The failure mode has a name: a spec nobody reads is a longer prompt, and you pay for it on every turn.

1. Start from the review problem

Ask why review of agent-written code feels worse than review of human-written code, and the honest answer is not that the code is worse. It is that the reviewer has lost the conversation. A colleague's 400-line change arrives with a shared history: you were in the meeting, you know which of three approaches this is, you know what was ruled out. An agent's 400-line change arrives with a prompt you did not write and no record of what it decided along the way.

The spec is that record, written before rather than after. It gives the reviewer something to review that is smaller than the diff, earlier than the diff, and phrased in the domain rather than in the code.

2. A real spec template, complete

spec-kit is GitHub's MIT-licensed toolkit for this, and its value here is that its templates are short enough to read whole. This is the file its /speckit.specify command fills in. Read the comments as well as the headings: they are instructions to the agent that generates it, and they are where the two load-bearing mechanisms are stated.

3. The two lines that make it agent-usable

Most of that file is ordinary requirements-document furniture. Two parts are not, and they are the reason to copy this shape rather than any PRD template you already have.

The first is the independence rule on user stories. The template's own comment says each story "must be INDEPENDENTLY TESTABLE - meaning if you implement just ONE of them, you should still have a viable MVP", developed, tested, deployed and demonstrated on its own. That is a constraint on the writing, and its effect is on the work: a spec written this way decomposes into changes that can each be merged, which is what lets you hand one story to an agent rather than the whole feature.

The second is [NEEDS CLARIFICATION]. The template shows it inline in a requirement: "System MUST authenticate users via [NEEDS CLARIFICATION: auth method not specified - email/password, SSO, OAuth?]". This is the mechanism worth taking away even if you never install the tool. A generated spec has exactly two things it can do with a gap in what you told it: invent something plausible, or mark it. A marker is machine-findable, so a later command can search for them and a human can be asked precisely those questions - and the alternative is a confident invention buried in a requirement that nobody notices until it ships.

The reframing The valuable half of spec-driven development is not the spec. It is that the generator has a way to say "I do not know", and that saying so is cheaper than guessing. Any template you write yourself can have that; most do not.

4. The command chain, and where a person is asked

spec-kit is eight slash commands, each producing something the next one reads. Drawn as a chain it looks like a pipeline, and the useful reading is where the human gates are rather than the order of the boxes.

Kiro answers the same problem with three files rather than eight commands: requirements.md, which "captures user stories, acceptance criteria, or bug analysis in structured notation"; design.md, which "documents technical architecture, sequence diagrams, and implementation considerations"; and tasks.md, which "provides a detailed implementation plan with discrete, trackable tasks". The two designs disagree about how much process to encode and agree completely about what the artefacts are.

5. How much writing is this, really

The objection to all of this is that it sounds like a lot of documents. Measure it instead. These are the five templates in the repository, counted with wc -l at the pinned commit, and they include every comment and every placeholder.

The project's own claim that it "works with 30+ AI coding agents" is a count with no list and no compatibility method published, so treat it as marketing rather than as a fact about your harness. What matters for adoption is narrower and checkable: the commands write plain Markdown into your repository, so anything that can read a file in a repository can use the output, whether or not it can run the commands.

6. The smallest version that works

You do not need any of the tooling to get most of the benefit, and starting without it is the honest way to find out whether the benefit is real for your team. One committed file, three headings, and the marker.

specs/0001-rate-limit-the-webhook.md · written for this page · CC BY 4.0 with the rest of this repository · reproduced verbatim
# Rate-limit the inbound webhook

## Stories

- P1. As an operator, I can set a per-sender request ceiling, so one noisy
  integration cannot exhaust the worker pool.
  Independently testable: send 200 requests from one sender, observe 429s
  after the ceiling, and confirm a second sender is unaffected.
- P2. As an operator, I can see how often the ceiling was hit, so I can tell
  a misconfiguration from an attack.
  Independently testable: hit the ceiling, read the counter.

## Requirements

- FR-001: The service MUST reject requests from a sender above its ceiling
  with HTTP 429 and a Retry-After header.
- FR-002: The ceiling MUST be configurable per sender without a deploy.
- FR-003: Rejected requests MUST be counted, labelled by sender.
- FR-004: Ceilings MUST survive a process restart
  [NEEDS CLARIFICATION: in the existing Postgres table, or in Redis with the
  counters? The two differ on what happens during a Redis failover.]

## Success criteria

- SC-001: A single sender cannot occupy more than its configured share of
  worker capacity, measured under a two-sender load test.
- SC-002: Changing a ceiling takes effect within 30 seconds, with no restart.

## Out of scope

- Global rate limiting across all senders.
- Any change to how senders authenticate.

That file is shorter than the prompt you would otherwise have written, and it has three properties the prompt does not: it is in the repository, it is diffable, and its fourth requirement says out loud that a decision has not been made. The failure to avoid is the opposite one. A spec that is generated, never read, and then pasted into every prompt is a longer prompt that costs tokens on every turn - which takes you straight back to lesson 0200 with a bigger bill and no more information.

Check yourself

Retrieval practice

Answer from memory before revealing.

What does the [NEEDS CLARIFICATION] marker buy that a well-written prompt does not?
The marker is a findable admission of ignorance, which is what lets a later command collect the open questions and a human answer exactly those. It does not block anything - a permission mode does that, which is lesson 0220 - and it makes a requirement less testable rather than more, deliberately, because the alternative is a made-up answer that tests fine and is wrong.
A team generates a spec, never reads it, and pastes it into every implementation prompt. What have they built?
The spec is only doing work if somebody reads it and can disagree with it; unread, it is context you pay for continuously and learn nothing from. The third option is wrong twice over - caching changes the price, not the room, and it does not make an unread document informative. The fourth is generous: an artefact nobody reads is not waiting for a reviewer, it has already failed to be one.

Practice about 30 minutes, in a real repository

Practice 1foundation

Take the plan you produced in lesson 0220 and turn it into a committed spec in the smallest shape above: stories with an independence test each, numbered requirements, success criteria, out of scope.

Then do the part that matters. Read it as if you had not written it, and add a [NEEDS CLARIFICATION] marker at every point where you find yourself supplying an answer from memory rather than from the document. Count them.

Hint

The markers cluster where a requirement uses a word that has two implementations behind it: "persisted", "authenticated", "retried", "cached". Any of those in a requirement is a place to check whether the spec says which.

Show what a good pass looks like
  1. Write the stories with their independence test. If a story cannot be shipped alone, it is a piece of a story rather than one, and joining it to its neighbour is the fix.
  2. Number the requirements and use MUST. The numbering is not bureaucracy: it is what lets a review comment and a test both name the same line.
  3. Read for supplied answers. Every time you think "obviously it means X", that is a marker, and the fact that it is obvious to you is exactly why it is worth writing down.
  4. Make success criteria measurable and technology-free. "Under a two-sender load test" is a criterion; "uses Redis" is an implementation that has escaped into the wrong section.
  5. Write the out-of-scope list last and honestly. It is the cheapest section and the one that most often stops an agent widening the change.

Sanity check. A first honest pass over a real feature usually produces two to five markers. Zero means you read it as its author rather than as a stranger; a dozen means the feature is not one feature yet, and splitting it beats answering them all.

Your teacher. If your spec keeps drifting into implementation, ask your agent to rewrite it with every technology name removed and to tell you which requirements stopped making sense - those are the ones that were describing a solution. If you want to feel the review difference, hand an agent only the spec, have it implement, then review the diff against the spec rather than against your intent.
