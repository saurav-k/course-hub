Module 08 · Background agents · Lesson 0800

Take away the terminal and three things change at once

working 9 min Built on Anthropic's published description of its own cloud sessions and the environments they run in. · Claude Code on the web

The one-minute version

  • A background agent is the same loop from module 1 running somewhere you are not looking, returning a branch instead of a screen.
  • Every vendor converged on one shape: an isolated virtual machine, a fresh clone of your repository, the agent, then a pushed branch.
  • "Fresh clone" is the sentence that carries this module. Committed or absent - there is no third option, and nothing you configured only on your laptop is in there.
  • You gain parallelism and lose the ability to intervene mid-step. Everything in the rest of this module is a way of paying for that trade in advance.

1. What actually changes

Nothing about the loop changes. The model still asks for a tool, a program still runs it, and the result still goes back. What changes is everything around the loop, and it changes in three places at once.

Where it runs. Anthropic's description of its own product is the plainest published statement of the architecture: "each session runs in an isolated, Anthropic-managed VM", and each of those VMs is a fresh machine "running Ubuntu 24.04 on x86_64, regardless of your own operating system and CPU architecture, with your repository cloned and common toolchains pre-installed".

What it can reach. Network access stops being whatever your laptop can see and becomes a configured level on a saved cloud environment. There are four, and the useful thing about the list is that the tightest one is not "nothing".

How you find out what it did. You do not watch. You read a branch, a pull request, and a transcript, after the fact. That is a review problem rather than a supervision problem, and it is why module 6 comes before this one.

2. The shape every vendor converged on

A trigger fires, a machine is provisioned, the repository is cloned, a setup script installs what the base image does not ship, the agent works, a branch is pushed, and a pull request appears. Six products in the next lesson differ on almost everything except that sequence.

Two of those arrows are worth naming now, because the rest of the module is spent on them. The first arrow is the trigger, and lesson 0820 treats it as an authorisation decision rather than an integration. The last is the pipeline, and lesson 0830 argues that the pipeline is the product.

Starting one from a terminal is a flag rather than a new tool, which is worth seeing once so the mechanism stops feeling remote.

shell · code.claude.com/docs/en/claude-code-on-the-web · Anthropic documentation · reproduced verbatim
claude --cloud "Fix the authentication bug in src/auth/login.ts"

The documentation is explicit about what that clones, and the sentence is the whole lesson in one line: "The cloud VM clones your current directory's GitHub remote at your current branch, not your local checkout, so push first if you have local commits."

3. What travels, counted

Anthropic publishes a table of what carries over from a developer's own setup into a cloud session. It is fourteen rows long, and reading it as a count rather than as a list is the fastest way to internalise the rule.

4. What the box can reach, and for how long

A cloud environment sets one network access level, and the four are documented as None, Trusted, Full and Custom. Trusted is the default and means allowlisted domains only: package registries, GitHub, cloud SDKs. Custom takes your own list.

The interesting one is None, because it does not mean isolated. The documentation says that whichever level you pick, GitHub still reaches the session through its own proxy, and so does "The Anthropic API, for Claude Code's own requests, even at None". A session with no network can still send everything it has read to a model.

That last sentence is the honest limit of a network setting as a security control, and the documentation states it directly: when running with network access disabled, Claude Code "can still communicate with the Anthropic API, which may allow data to exit the VM". Treat the access level as a way of controlling what the agent can fetch, and treat what it may read as a permissions question, which module 7 of this course owns and Coding Harness Engineering compares across fifteen harnesses.

That last row is the one people meet by accident. Sessions stop after a period of inactivity and the VM is reclaimed; reopening one provisions a fresh machine with the conversation restored, but "Background work that was still running when the VM was reclaimed, such as subagents and shell commands, isn't restored." A session is durable, and the machine under it is not. Lesson 0860 is what happens when a vendor decides to close exactly that gap.

The trade You are buying parallelism with the ability to intervene. On your machine you can stop a bad plan on its third tool call. Here you read about it afterwards, in a diff, and the earliest point at which you could have prevented it was the moment you wrote the issue.

Check yourself

Retrieval practice

Answer from memory before revealing.

Your agent behaves well locally because of a skill in ~/.claude/skills/. You trigger the same task as a cloud session. What happens?
A cloud session starts from a fresh clone, and the carry-over table lists user-scope skills as unavailable because they "Live on your machine, not in the repo". The first two options describe a sync that does not exist in either direction; if it did, the fresh-clone rule would not be worth a lesson. The fourth invents a failure: nothing knows the skill was supposed to be there, which is exactly why the symptom is quiet under-performance rather than an error.
A cloud environment is set to network access None. Which statement is true?
GitHub travels through its own proxy and the model API is reachable "even at None", both independently of the level. The second option is the intuitive reading and it is what makes None misleading as a security boundary. The third describes Trusted, which is the default rather than the tightest. The fourth invents a mirror: at None, package installs simply fail, which the setup-script requirements say outright.

Practice about 25 minutes, with a repository

Practice 1working

Take the capstone repository you picked in lesson 0000 and predict, before running anything, what a background agent would find in it.

Write down three lists. First, every file in the repository that changes how your agent behaves. Second, every setting that changes how your agent behaves that is not in the repository - a user-scope memory file, a locally added MCP server, an installed CLI it depends on, an environment variable in your shell profile. Third, the commands a stranger would need to run to get from a fresh clone to a passing test.

Then check the second list against the documented carry-over table and mark each row available or unavailable.

Hint

The second list is usually the longest and the hardest to write, because none of it announces itself. Two quick ways to find entries: read your shell profile for anything that names your agent, and run claude mcp list or its equivalent and ask which of those servers is declared in a committed file.

Show what a good answer looks like
  1. The first list is short and usually complete. A memory file, a settings file, a skills directory, maybe a hooks configuration. If it is empty, that is the finding: your agent has been behaving well for reasons that are entirely local to you.
  2. The second list is where the surprise is. Anything in it that the table marks unavailable is a behaviour your background agent will not have. The usual four are a user-scope memory file, user-scope skills, a locally added MCP server, and a globally installed tool that your commands assume.
  3. The third list is the setup script. Everything a stranger would have to install is what the base image does not ship, and that is precisely what a setup script exists to do. Lesson 0850 turns this list into a file.

Sanity check. If the second list is empty, either the repository is unusually well prepared or you have not looked at your own machine hard enough. Almost every developer who has used an agent for a year has at least one user-scope habit in it, and the honest version of this exercise finds it now rather than in a pull request.

Your teacher. If the boundary still feels abstract, ask your agent to list every file it read in the first ten tool calls of an ordinary local task, then ask which of those paths would exist inside a fresh clone of the repository and which would not. The answer is this page, on your own machine.
