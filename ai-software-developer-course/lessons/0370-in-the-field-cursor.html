Four questions, four files, and one of them is the only one that can say no

working 9 min Built only from Cursor's own public documentation, read in this session. · Rules · Hooks

The one-minute version

  • Every agent setup answers four questions. Cursor answers them with four separate files, and looking at them side by side is what makes the four questions visible.
  • Always knows: .cursor/rules/*.mdc, whose three frontmatter fields form a truth table with four outcomes. Or a plain AGENTS.md.
  • Loads on demand: skills, in the same format module 3 has been writing. Cursor also reads .claude/skills/ and .codex/skills/ for compatibility.
  • Can stop it: .cursor/hooks.json, whose beforeShellExecution hook returns a permission of allow, deny or ask. This is the only one of the four that refuses.
How Cursor is built - four surfaces on one loop, its own models, the telemetry flywheel - belongs to Cursor trains its own models in Coding Harness Engineering. This page is only what a person does at the keyboard and in the repository, and everything on it comes from Cursor's published documentation.

1. Four questions, four files

2. What it always knows: a truth table with four outcomes

A Cursor project rule is a file with the .mdc extension under .cursor/rules, carrying three frontmatter fields. Those three fields do not each do a separate job; they combine, and the combination decides when the rule is included.

The vocabulary is worth noting: description on an "apply intelligently" rule is the same routing device as a skill's description. Cursor has said so out loud by shipping a built-in /migrate-to-skills that converts exactly those rules, and only those, into skills. Rules with alwaysApply: true or specific globs are not migrated, because they have explicit triggering conditions a skill has no way to express.

.cursor/rules/service-boundaries.mdc · written for this page against the documented format · this repository, MIT · complete
---
description: Conventions for adding or changing an RPC service in this repository
globs:
alwaysApply: false
---

- Every service gets its own file under `src/services/`, named after the service
- Validate inputs at the service boundary, before anything internal sees them
- Return a structured error with a `code` and a `message`, never a raw string
- A new service starts from `templates/service.ts`, which carries the standard
  boilerplate and the error shape above
A plain .md file in .cursor/rules is ignored by the rules system entirely, because it has no frontmatter to carry description, globs and alwaysApply. It sits in the right directory, it reads correctly, it is version controlled, and it reaches the model never. If you want plain Markdown, the documented answer is an AGENTS.md at the repository root instead.

3. What it loads on demand: the format won, the folder did not

Cursor implements the same Agent Skills standard this module has been writing against, with the same SKILL.md, the same scripts/, references/ and assets/, and the same progressive disclosure. Its own additions are small: paths to scope a skill by glob, and icon and color for when a skill is worn as a custom mode for a whole session.

The more interesting decision is that it reads four folders that are not its own. Alongside .agents/skills/ and .cursor/skills/, it loads .claude/skills/ and .codex/skills/, and their equivalents under the home directory, explicitly for compatibility. That is a vendor choosing to read its competitors' configuration directories, and it is the clearest evidence available that the format has settled and the folder name has not.

The reframing A rule and a skill are converging on the same mechanism from opposite ends. A rule started as always-on context and grew a description so it could be conditional. A skill started as conditional context and is now worn for a whole session as a custom mode. The axis underneath both is not "rule or skill", it is how much of a session a piece of context is resident for.

4. What can stop it

Cursor's hooks are spawned processes that communicate over standard input and output using JSON in both directions, at named points in the agent loop. There are twenty-one documented events; the one that matters for enforcement is beforeShellExecution, because its response carries a permission field with three values.

.cursor/hooks.json · the documented configuration shape · Cursor documentation, licence unstated · format quoted, paths written for this page
{
  "version": 1,
  "hooks": {
    "beforeShellExecution": [{ "command": ".cursor/hooks/guard.sh" }]
  }
}

Project hooks run from the project root, so the command path is relative to it rather than to the hooks directory. The script below is written for this page rather than quoted, and it implements the documented contract: read the JSON on standard input, decide, print a JSON object with a permission of allow, deny or ask.

.cursor/hooks/guard.sh · written for this page against the documented hook contract · this repository, MIT · complete
#!/usr/bin/env bash
# Refuse any shell command that force-pushes, and ask before anything that pushes.
# Everything else is allowed. Reads one JSON object on stdin, writes one on stdout.
set -euo pipefail

command=$(jq -r '.command // empty')

if [[ "$command" == *"push --force"* || "$command" == *"push -f"* ]]; then
  jq -n --arg c "$command" '{
    continue: true,
    permission: "deny",
    user_message: "A force push was blocked by .cursor/hooks/guard.sh.",
    agent_message: ("The command " + $c + " was refused by a repository hook. "
      + "Force-pushing a shared branch is not permitted here. Open a pull request instead.")
  }'
elif [[ "$command" == git*push* ]]; then
  jq -n --arg c "$command" '{
    continue: true,
    permission: "ask",
    user_message: ("Approve this push? " + $c),
    agent_message: "A repository hook is asking the user to approve this push."
  }'
else
  jq -n '{ continue: true, permission: "allow" }'
fi

Compare that with the rules file above and the difference this module keeps returning to is finally concrete. The rule is a sentence in the request; the hook is a process with an exit and a verdict. Only one of them is still true when the model is wrong.

5. Where it runs, and what travels there

Cursor's cloud agents run in isolated VMs, clone the repository, work on a branch and push it back, and are configured by .cursor/environment.json. What matters here is not the product but the general question: when the agent moves off your laptop, which of your four files goes with it?

Field note. Two limits on cloud hooks are documented and both are the kind you discover at the wrong moment. Cloud agents run command-based hooks only, because prompt-based hooks need authentication wiring that is not available there. And user-level hooks in ~/.cursor/hooks.json do not travel at all, because a cloud VM has no access to your home directory. A gate that lives in your personal configuration is a gate that protects you and nobody else.

Review is the fifth thing, and it belongs to a later module rather than this one. Cursor's pull-request reviewer takes its instructions from .cursor/BUGBOT.md files, always including the repository root one and any found while walking up from the changed files, with each rule truncated at 30,000 characters and the combined set capped at 100,000. Project rules in .cursor/rules/ do not apply to it, which is exactly the kind of separation module 6 is about.

6. Your own four answers

Check yourself

Retrieval practice

Answer from memory before revealing.

A rule file has no globs, no description, and alwaysApply: false. When is it included?
The published truth table's last row is the manual case: no globs and no description means the rule waits to be mentioned. The first inverts the meaning of alwaysApply: false. The second confuses an empty rule with an invalid one; the genuinely ignored file is a .md in that folder, which is a different failure. The third describes the globs row, which is the strongest distractor because it is what most people assume the default is.
Which of your local configuration files does a cloud agent not get?
A cloud VM has no access to your home directory, so user-level hooks simply are not there; project hooks in the repository are cloned and do run. The third is backwards: committed skills are in the repository, which is exactly what does travel. The fourth invents an editor dependency for a file that is read as context like any other.

Practice the module assignment, about 90 minutes

Module assignmentworking

Goal. Turn one procedure you currently retype into a skill, then run it from a pipeline with no terminal interface. This is the capstone repository's first committed agent configuration, and the shell script you write here becomes the first stage of the pipeline module 8 later moves to a background runner.

  1. Pick a procedure you have pasted into a chat at least twice. Write it as SKILL.md with name and description only.
  2. Read your own description back and ask whether it says when, not only what. Rewrite until it does.
  3. Move anything the agent needs only sometimes into references/. Move anything deterministic into scripts/, and add the instruction to run it with --help first and not read the source.
  4. Validate it: skills-ref validate ./<your-skill>.
  5. Invoke it interactively as /<name>. Then non-interactively, in bare mode, with JSON output and a scoped tool list.
  6. Wrap step 5 in a shell script that branches on the exit code and pulls one field with jq.
  7. Run step 5 again against one other CLI you have installed, using lesson 0360's table rather than your memory.

Hand in the skill directory, the shell script, a transcript of the non-interactive run, and three sentences on what you moved out of SKILL.md and why.

Hint

Do step 5 before step 3. A skill that works interactively and fails in --bare mode is telling you that discovery is coming from your home directory, and that is much easier to see before you have also restructured the file.

Show the self-check, and what each part proves
  1. skills-ref validate exits 0. The frontmatter parses, the name matches the directory, and the two required fields are within their limits. This is the only part of the assignment a machine can check for you.
  2. The -p run exits 0 and produces valid JSON. The skill was found, the turn completed, and your script has something to parse. Check the exit code first and the payload second; lesson 0350's three deliberate failures are the reason.
  3. The same command with --bare gives the same result. This is the load-bearing check. Bare mode skips personal skills discovery, so an identical result proves the skill is being found from the project rather than from your machine, which is what makes it a team artefact.
  4. The second CLI runs it too. The skill body did not change; only four flags did. If you had to change the skill, something in it was client-specific and belongs in a client-specific copy.

Sanity check. If the bare-mode run behaves differently from the ordinary one, do not adjust the skill. Find out which of the two is reading a file you did not intend, because that difference is exactly what will make the pipeline in module 8 behave differently from your laptop.

Your teacher. Ask your agent to look at your repository and answer the four questions of this page in order, naming a file for each or saying there is none. Then ask which of the four, if answered, would change its behaviour most on the task you gave it yesterday. Its answer is a hypothesis, and module 4 is where you test it.
