Module 08 · Background agents · Lesson 0860

In the field: when the agent's identity is the compute

working 10 min Built only from Cloudflare's own public documentation, its open-source example repository and its published pricing. · Agents API reference

The one-minute version

  • Lesson 0800 left one problem open: a cloud session's VM is reclaimed and running work is not restored. What would it take for an agent to persist?
  • One vendor's published answer is that the agent instance is an addressable stateful compute object, so there is nothing to reconstruct because nothing was ever externalised.
  • That single decision produces the rest of the platform: SQL storage inside the instance, scheduling owned by the agent, and an approval gate expressed in a runtime rather than a config file.
  • It also produces this module's only fully published per-unit price, which is worth reading precisely because lesson 0810 found four blanks in the same column.

1. The problem, restated from lesson 0800

A cloud session is durable and its machine is not. Reopening an expired session provisions a fresh VM with the conversation restored, and "Background work that was still running when the VM was reclaimed, such as subagents and shell commands, isn't restored". Anything an agent was in the middle of is gone.

The usual fix is to externalise: write the state to a database, key it by a session id, and rebuild the agent from that on the next run. That works, and it means every agent carries a serialisation format, a store and the bugs where the two disagree.

The alternative is to make the compute itself the durable thing.

2. The published answer: the instance is the store

Cloudflare's launch post describes agents that "run on top of Durable Objects - which you can think of as stateful micro-servers that can scale to tens of millions". A Durable Object is a single-threaded, addressable compute instance with storage attached to it. One agent instance is one object, reached by name.

The consequence the documentation claims is a strong one, and it is worth quoting because it is testable rather than decorative: each agent session has "a durable identity, local SQL storage, real-time connections, scheduled work, and recoverable execution", so there are "no sessions to reconstruct, no state to externalize".

The class shape is four lines, and everything a background agent needs hangs off this.

src/agent.ts · developers.cloudflare.com/agents/api-reference/agents-api · MIT (Cloudflare docs code) · reproduced verbatim
import { Agent, routeAgentRequest } from "agents";

export class MyAgent extends Agent<Env, State> {
	// Your agent logic
}

The lifecycle hooks are onStart, onRequest, onConnect, onMessage, onError, onClose, onEmail and onStateChanged. onStart is documented as running "When the instance starts, or wakes from hibernation", which is the sentence that tells you the object sleeps and wakes rather than starting and dying.

A cloud VM sessionthe conversation, restored onto a fresh machineeverything the run needs, committed in advance

3. The trigger family the agent owns

Lesson 0820 put the schedule family last, because it is the quietest and the easiest to get wrong: it lives in a CI system, runs only from a default branch, and can be disabled by inactivity. Here the same family is owned by the agent instead: schedule(), scheduleEvery(), getScheduleById() and listSchedules() are methods on the object, so a running agent can arrange its own next run and list what it has arranged.

That is a genuine change of location rather than a convenience. A schedule in a CI file is a fact about your repository; a schedule inside an instance is a fact about that one agent, and the reader worth being is the one who asks who can list them all.

4. One deployment instead of one per developer

Module 2 taught MCP over a local transport, where each developer runs the server themselves. A remote MCP server inverts that: one deployment, many clients, reached over HTTP. Cloudflare's current entry point for one is a stateless handler that needs no Durable Object at all.

examples/mcp-worker/src/server.ts · cloudflare/agents · MIT · reproduced verbatim
import { McpServer } from "@modelcontextprotocol/server";
import { createMcpHandler } from "agents/mcp/server";
import { z } from "zod";

function createServer() {
  const server = new McpServer({
    name: "Hello MCP Server",
    version: "1.0.0"
  });

  server.registerTool(
    "hello",
    {
      description: "Returns a greeting message",
      inputSchema: { name: z.string().optional() }
    },
    async ({ name }) => {
      return {
        content: [
          {
            text: `Hello, ${name ?? "World"}!`,
            type: "text"
          }
        ]
      };
    }
  );

  return server;
}

export default {
  fetch(request, env, ctx) {
    return createMcpHandler(createServer)(request, env, ctx);
  }
} satisfies ExportedHandler;
examples/mcp-worker/wrangler.jsonc · cloudflare/agents · MIT · reproduced verbatim

  "name": "mcp-worker",

Notice what is not in that configuration: there is no durable_objects block, because this server is stateless. A great deal of older material builds a remote MCP server on the McpAgent class, which did use a Durable Object per session, and the current guide says plainly of the templates that still use it: "Do not use that path for a new server." This matters for a reader of this course specifically: it would be easy to present the MCP example as the Durable Objects example, and it is the one part of this platform that deliberately is not.

A stateful agent's configuration does carry the block, and three lines in it are the whole difference: "ai": { "binding": "AI" } gives inference with no API key, a durable_objects binding registers the agent class, and "migrations": [{ "tag": "v1", "new_sqlite_classes": ["ChatAgent"] }] is what gives that class its own SQL storage.

5. Module 7's permission model, in a runtime

The chat-agent guide documents three tool patterns, and the third is the interesting one for this module. A tool with a server-side execute runs on its own. A tool with no execute is handled by the browser. And a tool carrying needsApproval raises a confirmation before it runs - in the guide's example, only when an argument exceeds a threshold.

That is the same decision as an --allowedTools list or a blocking hook, expressed in a different place: a predicate on the arguments, evaluated at call time, rather than a rule in a settings file. It is worth holding both shapes in mind, because a background agent gets neither for free - if nobody is there to approve, an approval gate is a stall rather than a safeguard.

6. One URL, and the hand-off to module 9

An LLM gateway sits in front of model providers and adds caching, rate limiting, retries, fallbacks, logging and cost tracking. Cloudflare's is reached by changing a base URL and keeping the provider's own request schema, and the documented shape is one line.

the gateway base URL · developers.cloudflare.com/ai-gateway/get-started · CC BY 4.0 (Cloudflare docs) · reproduced verbatim
https://gateway.ai.cloudflare.com/v1/{account_id}/{gateway_id}/{provider}

That is as far as this module goes with it. Module 9 owns gateways properly - what a token is for, who may revoke it, and where the model bill is paid - and re-deriving that here would be a second essay on somebody else's subject.

7. A published unit price, which is rarer than it should be

Lesson 0810 found four blank cells in a column of six. This platform publishes its unit: a Neuron is Cloudflare's measure of "the GPU compute needed to perform your request", the free allocation "allows anyone to use a total of 10,000 Neurons per day at no charge", and beyond that "Workers AI is priced at $0.011 per 1,000 Neurons".

Retrieval practice

Answer from memory before revealing.

What does "no state to externalize" actually claim about where an agent's data lives?
The instance holds its own SQL storage, reached through this.sql, so waking the object is loading its data and no serialisation layer exists. The second option is the ordinary architecture this one is contrasted with, and it is the strongest distractor because it is what almost every other system does. The third confuses durability with memory: the object hibernates and its data survives. The fourth describes a stateless service, which is what the MCP handler on this page is and the agent is not.
Which of these should you not take from this page into your own design?
The current handler is stateless and its configuration carries no durable-object block, and the older class that did is documented as the path not to use for a new server. The other three are all transferable readings: scheduling location is a real design choice, an argument predicate is a genuine third shape of permission gate, and the whole of lesson 0810 rests on the last one.

Practice 1working

Take the three-row table above - a terminal session, a cloud VM session, an addressable stateful instance - and add a fourth column: what happens to work in progress when the run is interrupted.

Fill it from the pages of this module rather than from intuition, and then say which of the four answers your own current setup gives.

Hint

Two of the three rows have a documented answer earlier in this module, and one of them is a direct quotation about subagents and shell commands. The third row's answer is implied by hibernation rather than stated as a failure mode, which is itself worth noting in your table.

Show the fourth column
  1. A terminal session. The process dies with the terminal, the working tree survives, and whether the work is recoverable depends entirely on whether anything was committed. That is why lesson 0840's fleet script keeps the branch when it removes a worktree.
  2. A cloud VM session. Documented: the conversation is restored onto a fresh machine and "Background work that was still running when the VM was reclaimed, such as subagents and shell commands, isn't restored". The branch survives if it was pushed.
  3. An addressable stateful instance. The object hibernates and onStart runs again on the wake, so state written through this.sql or setState is there. Anything held only in a local variable during a request is not, which is the same rule as the row above with a much smaller blast radius.

Sanity check. All three answers should reduce to the same sentence: what survives is what was written down. If one of your rows claims that in-flight work survives on its own, re-read the source for that row.

The module assignmentworking

This is module 8's assignment, and it is the last thing the capstone repository needs before the capstone page that lets it run. The goal: take one issue from filed to merged with an agent doing the implementation, then run three at once and find your own bottleneck.

  1. Add the label-triggered workflow from lesson 0830 to the capstone repository and create the agent:implement label.
  2. Write three issues, each small and each fully specified. An agent cannot ask you a question, so anything it would ask belongs in the issue body - including how a reader would know it was fixed.
  3. Commit an instruction file with the project's conventions and a .claude/settings.json carrying module 7's permission rules. They are the only interface the run gets.
  4. Label one issue. Watch the run, and record how long provisioning took, how many turns the agent used, and what the pull request looked like.
  5. Turn on a merge queue for the default branch and add merge_group to your CI workflow's triggers. Confirm that a queued pull request reports its check.
  6. Label all three issues within a minute of each other, and record what actually contends: runner concurrency, merge conflicts, the queue, or your own review time.
  7. Run the same three tasks locally with the worktree script from lesson 0840, and record the difference in setup cost and in what you could observe.

Hand in the workflow file, the three issue bodies, three pull request links, and one page on step six naming the bottleneck you actually hit, with the evidence for it.

Hint

Step six only works if the three tasks can genuinely collide. Three issues in three unrelated directories will run cleanly and teach you nothing, which is why the self-check below asks you to rewrite two of them.

Show what a good write-up names
  1. The bottleneck, named as one of four. Runner concurrency shows up as queued jobs; merge conflicts show up as three pull requests touching one file; the queue shows up as rebuilt temporary branches; your review time shows up as pull requests sitting open. They look different in the evidence, so the write-up should say which one it saw.
  2. The evidence, not the impression. Job start times for concurrency, the conflicted paths for merges, the queue's own build history for the third, and the interval between a pull request opening and your first real comment for the fourth.
  3. The local comparison, honestly. Worktrees cost setup and give you everything to look at; cloud runs cost nothing to set up and give you a transcript after the fact. Most people find they prefer one for debugging and the other for volume, and saying which and why is the point of step seven.

Self-check. If step six produced no contention at all, the tasks were too small or too independent: rewrite two of them so they touch the same file and repeat. And if the merge queue never reported a check, you skipped the merge_group trigger - that is the single most common cause and it is one line.

Your teacher. Ask your agent to compare the three-row state table on this page against the system you actually run, and to name the one change that would move your row down by one. Then ask what that change would cost. The second answer is usually the more interesting of the two.
