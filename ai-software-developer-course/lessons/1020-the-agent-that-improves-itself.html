A correction only counts if something written outlives the session

frontier 12 min Four durable surfaces, their per-turn cost, and the one of them that can actually refuse. · Memory and rules · A vendor's own account

The one-minute version

  • Each session starts with a fresh context window, so a correction you type into the chat is gone at the end of the turn. "The agent learned" is only ever shorthand for "somebody wrote something down".
  • Four surfaces can hold it, and they are not ranked: an eval, a rule you wrote, a memory the agent wrote, and a hook. Three are context and one is enforcement.
  • A path-scoped rule costs nothing until a matching file is read, which is why a growing instruction file should become several small scoped ones rather than one long one.
  • Automatic memory is deliberately narrow: it skips anything derivable from the codebase and anything your instruction file already says, and its index is read only to 200 lines or 25KB.

1. Four surfaces, and only one of them can refuse

The four differ on who writes them, when they enter the context window, what they cost per turn, and whether a failure is loud. That last column is the one that changes decisions.

Three of those rows are context: they change what the model is told and therefore what it is likely to do. The documentation is blunt about the difference - instructions and memories are "context, not enforced configuration", and to block an action regardless of what the model decides you use a PreToolUse hook. So the question a correction has to answer is not "where will it be remembered" but "does this need to be remembered or prevented".

2. A rule that costs nothing until it applies

A rule is a markdown file in .claude/rules/. Without frontmatter it loads at launch like the main instruction file. With a paths field it becomes conditional: it enters the context window only when the agent reads a file matching one of its glob patterns, and costs nothing on every turn that never touches that part of the tree.

3. What the agent writes for itself, and what it deliberately will not

Automatic memory is the surface the agent maintains. It saves four kinds of note, recorded as a type in each file's frontmatter: user for your role and working preferences, feedback for corrections you gave and approaches you confirmed, project for ongoing work and decisions that are not derivable from the code, and reference for where information lives outside the repository.

What it will not save is the more interesting half, and it is a rule rather than a tendency: it skips anything it can derive from the codebase - architecture, file paths, the shape of a fix - and anything your instruction files already say. That single constraint is what keeps a memory directory from silently becoming a second, worse copy of the repository.

The storage shape follows from the cost. One directory per repository, shared across every worktree of it; a MEMORY.md index of one line per memory; and one topic file per memory. Only the index loads at session start, and only its first 200 lines or first 25KB, whichever comes first. The topic files are read on demand with ordinary file tools when the agent decides it needs one.

The point here is narrower: the cost is real, it is measurable, and it is paid on every turn of every unattended run you start. A scoped rule and a memory topic file are the two ways of holding the same knowledge without paying for it constantly.

5. The only surface that fails loudly

Three of the four surfaces above are quiet by construction. An instruction can be read and not followed, a memory can be stale, a hook can be missing, and none of those announce themselves. An eval is the exception: it turns a regression into a red check, which means the failure arrives at the same place and in the same shape as a failing test.

Building that loop - a bad outcome captured, labelled, and turned into a case that runs forever after - is a pipeline in its own right, and this hub already teaches it. Read Evaluation and the data flywheel rather than a second account of it here; what belongs on this page is the choice, and the choice is that a correction you cannot check is a correction you will re-make.

The reframing After every correction, ask one question before the session ends: does this need to be remembered, scoped, checked, or prevented. The four answers are the four surfaces, and a correction that gets none of them was a conversation rather than a change.

6. What a self-improving loop looks like from inside a vendor

The strongest published account of agents improving their own tooling comes from Anthropic writing about Anthropic, and it is worth reading precisely because of that. It reports a campaign of more than 800 fixes that reduced a class of API errors by a factor of one thousand, and estimates that the same work would have taken a person four years.

That figure is self-reported, on a private codebase, with no published method for the counterfactual: no baseline error rate, no definition of the error class, and no account of how the four-year estimate was produced. Treat it as a claim about what one organisation believes it achieved, not as evidence about what your repository would achieve. What would make it checkable is small and specific: the error class defined, the rate before and after, and the estimating method. Ask for those three things of any similar number you are shown, including one produced by your own team.

Check yourself

Retrieval practice

Answer from memory before revealing.

Your agent keeps running a destructive command in one directory. Which surface actually stops it?
Only the hook is enforcement. The documentation states outright that instruction files and memories are context rather than enforced configuration, and names a PreToolUse hook as the way to block an action regardless of what the model decides. The other three all make the command less likely, which is a different property and not the one the question asks for.
Which of these would automatic memory deliberately not save?
Where files live is derivable from the codebase, and the documented rule is that the agent skips anything it can derive there, along with anything the instruction files already say. The first is a user preference, the third is a reference to something outside the repository, and the fourth is project context that no amount of reading the code would recover.

Practice about 20 minutes, with your own repository

Practice 1frontier

Open your repository's instruction file and run wc -l on it. Then read it line by line with one question in hand: which part of the tree is this line actually about?

Move every line whose honest answer names a subdirectory into a new file under .claude/rules/ with a paths frontmatter block that names it. Leave behind only the lines that are true everywhere.

Report three numbers: the line count before, the line count after, and how many of the moved lines you had to rewrite because they were vague enough to survive only by being general.

Hint

The third number is the interesting one. A line that cannot be scoped is often not a rule at all but a sentiment - "keep the code clean" scopes to nothing because it means nothing. Rewriting it into something you could check is usually what makes it scopable.

Show what a good split looks like
  1. Count first. A file over the documented 200-line target is the common case, not the exception, and the count is what tells you whether this exercise is worth doing at all.
  2. Sort each line by its subject, not its topic. "Use two-space indentation in TypeScript" scopes to **/*.ts. "Never push to main" scopes to nothing and stays. "Run the migration script before touching the schema" scopes to the migrations directory.
  3. Write one rule file per subject, not per line. Four scoped files of ten lines each beat forty files of one, because the agent loads a whole file when any pattern matches.
  4. Then re-measure. A typical result is that half the file was about part of the tree, so half the standing cost was being paid on turns that could never use it.

Sanity check. If nothing moved, either the file is genuinely universal - rare, and worth being proud of - or you sorted by topic rather than by subject. If everything moved, you have scoped rules that will never load together and the agent will not see the shape of the project at all.

Your teacher. Ask your agent to read your instruction file and, for each line, name the glob pattern that line is about, or say "everywhere". Then ask it which lines it would be unable to follow if it only ever read the file named by that pattern. The lines it names are the ones that were doing two jobs.
