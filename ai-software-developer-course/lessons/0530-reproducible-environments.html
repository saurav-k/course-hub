Module 05 · Agent-ready codebases · Lesson 0530

If the agent's environment differs from CI's, every failure it fixes is a guess

working 7 min Read against the devcontainer specification, a shipped container definition, and the documented constraints on one cloud agent's setup workflow. · containers.dev: the devcontainer.json reference

The one-minute version

  • Three layers make an environment a fact rather than a hope: a pinned image, pinned dependencies, and a pinned toolchain.
  • A lockfile is the difference between proving "it installed" and proving "it installed the same thing CI installed", and only the second one makes a failure informative.
  • The environment must come up with no secret at all, or the agent cannot start, which is a readiness property and not a security nicety.
  • A cloud agent's environment is a workflow file with hard constraints: a fixed job name, six settable keys and a 59-minute cap.

1. Three layers, and only one of them drifts quietly

An environment is reproducible when three separate things are stated rather than discovered. The image is the operating system and the system libraries. The dependencies are your language packages, and the lockfile is what makes them exact. The toolchain is the compiler or interpreter version, which is the one people leave implicit because it happens to be right on their own laptop.

2. A real devcontainer, read line by line

Here is one that ships, in a repository of about a gigabyte, and it is worth reading for what it does not contain as much as for what it does.

.devcontainer/devcontainer.json · discourse/discourse · GPL-2.0 · reproduced verbatim
{
  "name": "Discourse",
  "image": "docker.io/discourse/discourse_dev:20260812-0036",
  "workspaceMount": "source=${localWorkspaceFolder},target=/workspace/discourse,type=bind",
  "workspaceFolder": "/workspace/discourse",
  "postStartCommand": "./.devcontainer/scripts/start.rb",
  "forwardPorts": [
    9292, // bin/pitchfork
    3000, // bin/dev
    8025, // mailhog
    9229  // chrome remote debug
  ],
  "remoteUser": "discourse",
  "remoteEnv": {
    "RAILS_DEVELOPMENT_HOSTS": ".app.github.dev",
    "PGUSER": "discourse",
    "SELENIUM_FORWARD_DEVTOOLS_TO_PORT": "9229",
  },
  "mounts": [
    "source=${localWorkspaceFolderBasename}-node_modules,target=${containerWorkspaceFolder}/node_modules,type=volume",
    "source=${localWorkspaceFolderBasename}-pg,target=/shared/postgres_data,type=volume",
    "source=${localWorkspaceFolderBasename}-redis,target=/shared/redis,type=volume"
  ],
  "customizations": {
    "vscode": {
      "extensions": [
        "Shopify.ruby-lsp",
        "esbenp.prettier-vscode",
        "dbaeumer.vscode-eslint",
        "lifeart.vscode-glimmer-syntax",
        "typed-ember.glint2-vscode",
        "stylelint.vscode-stylelint"
      ]
    }
  }
}

The file format is JSON with comments and trailing commas, which the devcontainer specification permits and a strict JSON parser will not accept. Reproduced under GPL-2.0 with attribution to discourse/discourse.

Three decisions in it are the transferable part. The image tag names a build, 20260812-0036, rather than latest, so the environment is a fact you can go back to rather than a moving target. The three named volumes mean a rebuild does not re-download the world, which is what makes rebuilding cheap enough that people actually do it rather than nursing a broken container. And the setup logic is a script in the repository, reached through postStartCommand, so it is reviewed, version-controlled and runnable outside the container, instead of living as an unreadable string inside the JSON.

3. What setup has to do, and what it must not need

Whatever the container is, one command has to leave the tree ready. The parts below are the ones that keep coming back, and the last one is the part people leave out.

The rule The environment must come up with no secret at all. If bin/setup needs a production API key, the agent cannot start, and an unattended one cannot start at three in the morning either. Everything the environment needs is either in the repository, in a lockfile, or in a local service the compose file brings up. Anything that genuinely requires a credential belongs behind a feature flag that is off, or a fake that is on.

4. The same problem, in a cloud agent's shape

An agent running on someone else's machine has the same requirement and a stricter interface. GitHub's coding agent takes its environment from a workflow file whose constraints are documented and unforgiving: the job must be named copilot-setup-steps or it is ignored entirely, the file has no effect until it is on the default branch, timeout-minutes caps at 59, and exactly six keys may be set: steps, permissions, runs-on, services, snapshot and timeout-minutes.

.github/workflows/copilot-setup-steps.yml · written for this course · shape and constraints from GitHub Docs, CC BY 4.0
name: "Copilot Setup Steps"

on:
  workflow_dispatch:
  push:
    paths:
      - .github/workflows/copilot-setup-steps.yml
  pull_request:
    paths:
      - .github/workflows/copilot-setup-steps.yml

jobs:
  # The job MUST be called copilot-setup-steps or it is not picked up.
  copilot-setup-steps:
    runs-on: ubuntu-latest
    timeout-minutes: 20

    permissions:
      contents: read

    steps:
      - uses: actions/checkout@v5

      - uses: actions/setup-node@v4
        with:
          node-version-file: .node-version
          cache: pnpm

      - name: Install from the lockfile
        run: pnpm install --frozen-lockfile

      - name: Prove the environment before the agent starts
        run: pnpm run verify:smoke

Composed for this course. The trigger block, the job-name requirement and the settable-key list are documented behaviour; the steps are ordinary Actions syntax. GitHub's own example ends its steps block with an ellipsis, so nothing here is a reproduction of it.

Check yourself

Retrieval practice

Answer from memory before revealing.

Which change makes a development container reproducible rather than merely convenient?
Only the pinned tag makes the environment a fact you can return to. The first is ergonomics for humans and reaches no agent at all. The second makes the container usable and changes nothing about what is installed in it. The third is the strongest distractor because it is genuinely valuable, but it makes rebuilds cheap rather than making two rebuilds identical.
Your setup script needs a staging API token to complete. What is the readiness problem?
The property that matters is that setup completes with no human present, and a required secret breaks exactly that. The first and fourth are real operational risks that apply equally to a human developer, so neither is the readiness problem. The third is about a different failure, the token being committed, which is a security issue rather than a reason the agent cannot begin.

Practice about 30 minutes, with a clean checkout

Practice 1working

Find out whether your repository can be set up by somebody who knows nothing, which is the same test as being set up by an agent.

Clone it into a fresh directory, unset every environment variable your shell profile normally sets for it, and follow only what the repository says. Record every point at which you had to know something that is not written down.

Then write down which of the three layers is unstated: the image, the dependencies or the toolchain.

Hint

The fastest way to expose the toolchain layer is to check whether the repository states its language version anywhere a machine reads. A sentence in the README saying "Node 20" is not a pin; .node-version, .tool-versions or an engines field is.

Show the three findings and what each costs to close
  1. The toolchain is unstated. The cheapest of the three to close: add a version file the runtime and CI both read, and name it in the instruction file. Half an hour.
  2. The dependencies are not frozen. Add the frozen or deployment flag to the documented install command. Ten minutes, and it converts a class of "works here" bug into a loud install failure.
  3. The image is unstated. The expensive one. A container definition is an afternoon at best and a week if the repository needs system libraries nobody has written down. It is also the one that closes the most bugs, and the only one of the three that a cloud agent can use directly.

Sanity check. If the clean checkout worked first time, check whether it used a cache that a truly fresh machine would not have. A container image already on disk and a package cache already populated are both ways of passing this test without deserving to.

Your teacher. Ask your agent to read your CI workflow and your local setup instructions side by side, and to list every version that is stated in one and not in the other. That list is your drift surface, and it is usually shorter and more specific than you expect.
