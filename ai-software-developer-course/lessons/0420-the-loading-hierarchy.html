Module 04 · Customizing your agent · Lesson 0420

Nothing overrides anything - the files are concatenated, and yours is simply read last

working 8 min Every rule on this page is stated in Anthropic's memory documentation. · How CLAUDE.md files load

The one-minute version

  • Four scopes exist - managed policy, user, project and local - and they are loaded broadest first.
  • They are concatenated, not merged and not overridden. Two files that disagree both arrive, and the model picks.
  • Files above your working directory load at launch. Files in subdirectories load on demand, when the agent reads something there.
  • An @path import is expanded at launch, resolved relative to the importing file, and recursive to a maximum of four hops. Imported text costs full tokens.

1. Four scopes, and one of them you cannot remove

The documentation lists the locations in load order, broadest scope first. Managed policy sits at an operating-system path - /Library/Application Support/ClaudeCode/CLAUDE.md on macOS, /etc/claude-code/CLAUDE.md on Linux and WSL, C:\Program Files\ClaudeCode\CLAUDE.md on Windows - and is deployed by whoever manages the fleet. User is ~/.claude/CLAUDE.md, your own preferences across every project. Project is ./CLAUDE.md or ./.claude/CLAUDE.md, committed and shared. Local is ./CLAUDE.local.md, yours alone and gitignored.

One asymmetry is worth holding: a monorepo escape hatch called claudeMdExcludes lets you skip ancestor files by glob, its arrays merge across settings layers, and the documentation is explicit that "managed policy CLAUDE.md files cannot be excluded." That is the one band nothing local reaches.

2. Concatenated, which is not the same as overridden

Here is the sentence people expect and do not get. The documentation says: "All discovered files are concatenated into context rather than overriding each other. Across the directory tree, content is ordered from the filesystem root down to your working directory." Within each directory, CLAUDE.local.md is appended after CLAUDE.md, so your personal notes are the last thing read at that level.

The consequence is the whole lesson. If your project file says two-space indentation and your user file says four, both sentences are in the window. Nothing was replaced, nothing was resolved, and no error was raised. The documentation's own advice for that case is not a precedence table, it is housekeeping: "if two rules contradict each other, Claude may pick one arbitrarily."

The reframing "Closest wins" is a rule from CSS and from .gitignore, and it is not the rule here. Closest is read last, which is a position rather than a priority. A stale line in the file three directories up is not shadowed by your correction. It is sitting above it, in the same message, arguing.

3. Imports, and the three things that surprise people

An @path/to/file anywhere in an instruction file expands that file into context at launch. Three properties matter and each has bitten somebody.

First, relative paths resolve relative to the importing file, not to your working directory, so an import inside apps/web/CLAUDE.md is read from apps/web/. Second, imports are recursive to a maximum depth of four hops, so a chain of five files quietly stops one short. Third, import parsing skips Markdown code spans and fenced code blocks, which is the mechanism you need whenever a file has to mention a path without pulling it in.

CLAUDE.md · written for this course, from the documented rules · reproduced as an illustration, complete
<!-- Maintainer note: this comment never reaches the model. Edit the imports, not this file. -->

@AGENTS.md
@docs/release-checklist.md

The deploy job reads `@config/production.env` - that path is inside backticks,
so it is named here rather than imported.

Six lines, three behaviours. The comment is stripped before injection and costs nothing. The two bare @ paths are expanded and cost their full length. The backticked path is left as literal text, exactly as the documentation describes: "writing `@README` keeps the text literal, while @README outside backticks imports the file."

An import in a project file whose path resolves outside your working directory is treated as external, and the first time one appears Claude Code shows an approval dialog listing the files. The documentation says why in one line: "to protect you from files other people commit to a shared project." A committed CLAUDE.md is executable-adjacent input from everybody with write access to the repository, and this is the one place the tool stops and asks about it. Module 7 is where that thought is followed to the end.

4. Making instructions conditional, and the budget that governs it

The escape from a growing file is .claude/rules/. A rule with no paths: frontmatter loads at launch like the project file; a rule with one loads only when the agent touches a matching file. Glob patterns do the matching, and brace expansion is where the sharp edge is: "Each brace group multiplies the number of expanded patterns", so src/*.{ts,tsx} expands to two patterns and {a,b}/{c,d}/*.{ts,tsx} to eight.

A rule's whole paths list shares one budget of 1,000 expanded patterns and 4 MiB. Exceeding it does not raise an error. The documentation states the outcome plainly: "Claude Code uses any pattern that would exceed the budget unexpanded, and its literal braces match no files." The rule stays in the repository, matches nothing, and looks fine.

One more silent failure lives in the same field. Glob syntax reads [ as the start of a bracket expression, so a pattern like photos [2024/** is invalid, matches nothing, and leaves the rule's other patterns working. Escape it as photos \[2024/** when you mean the character.

Check yourself

Retrieval practice

Answer from memory before revealing.

Your user file says four spaces and the project file says two. What reaches the model?
The files are concatenated rather than overriding one another, so both instructions arrive and the model may pick either. The first two options each assume a precedence rule that the documentation says does not exist, and they are the two halves of the same misreading. The fourth assumes detection, and nothing scans the concatenation for contradictions - the documentation's advice is to review your own files periodically for exactly that reason.
When does an instruction file in a subdirectory below your launch point load?
Subdirectory files are discovered but load on demand, when the agent reads files in those directories. The first option describes ancestors, which do load at launch, and confusing the two is what makes a rule seem to switch on halfway through a session. The third is the belief this behaviour exists to disprove. The fourth invents a cadence and would make the file a per-turn cost, which is precisely what on-demand loading avoids.

Practice about 15 minutes, with a terminal

Practice 1working

Find out what your own machine is actually loading, and whether any two of those files disagree.

List every instruction file that reaches one of your sessions, in load order. Read the two that are furthest apart in the order. Name one instruction that appears in both and says something different, or state honestly that none does.

Hint

You do not have to reconstruct the order from the filesystem: /context prints what loaded under Memory files, and /memory lists the locations across scopes including ones that do not exist yet. Start there, then read the files themselves rather than trusting your memory of what you wrote in your user file two years ago.

Show what a good answer looks like
  1. Enumerate, do not guess. Run /context and copy the Memory files list. That is the ground truth for this session, and it is the only list that accounts for imports.
  2. Put them in order. Managed policy, then user, then each directory from the repository root down to where you launched, with a CLAUDE.local.md after the CLAUDE.md at each level.
  3. Look for the overlap. The common find is a personal preference in your user file - a commit-message convention, a formatting rule - that a project file states differently. Both are in the window.
  4. Fix it in the right place. If the project is right, delete your user line rather than strengthening it. Two contradicting instructions do not resolve by making one of them louder, and the emphasis rule from lesson 0410 says why.

Sanity check. The number of files in your list should match the number of directories between the repository root and your launch point, plus your user scope, plus any managed file, plus everything the imports pulled in. If /context shows fewer than you expected, an import did not resolve or a file is below your working directory rather than above it.

Your teacher. Ask your agent to quote back, verbatim, every instruction it has about one narrow topic - commit messages, say, or test commands - and to name the file each quotation came from. Contradictions that were invisible while you were reading files one at a time become obvious the moment they are listed side by side.
