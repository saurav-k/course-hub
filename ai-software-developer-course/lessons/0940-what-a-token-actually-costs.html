Module 09 · Building an AI-native team · Lesson 0940

Two terms carry the bill, and you can compute both in your head

frontier 8 min Every price and multiplier on this page is read from Anthropic's published pricing reference. · Pricing

The one-minute version

  • The price table has a shape rather than a list of numbers: output is five times input, on every model in the line-up.
  • Caching has three multipliers and one rule. Writing costs 1.25x for five minutes or 2x for an hour; reading costs 0.1x.
  • So a five-minute cache pays back after one read and a one-hour cache after two. That is the whole decision.
  • The other multipliers stack and are small: batch 0.5x, US-only inference 1.1x. Model choice dwarfs all of them.
  • A long session re-sends its whole context every turn. Clearing between unrelated tasks is the cheapest optimisation there is.

1. The table has a shape

Do not memorise the price list; memorise its geometry. Across the whole current line-up, output tokens cost five times input tokens. Claude Haiku 4.5 is $1 in and $5 out per million; Sonnet 5 is $2 and $10; Opus 5 is $5 and $25; Fable 5.1 is $10 and $50. The ratio holds, so the only question the table answers is which rung you are standing on.

That is why the first cost advice in the documentation is not a trick: Haiku for simple tasks, Sonnet for most production work, Opus for the hardest reasoning. Nothing else you can do to a request moves it by ten.

2. Caching is one comparison, not a strategy

A prompt cache has two priced halves. Writing costs 1.25x the base input price for a five-minute cache or 2x for an hour, and reading costs 0.1x, so a cache hit is a tenth of the standard input price. The documentation draws the conclusion for you: caching "pays off after one cache read for the 5-minute duration (1.25x write), or after two cache reads for the 1-hour duration (2x write)".

Where the cache actually breaks The cache is keyed on a prefix, so anything that rewrites the front of the conversation invalidates it. Claude Code counts a request as a miss when it re-processes more than 5% and at least 2,000 tokens of what it could have read, and reports the count in /usage along with the share of input tokens served from cache. A session left idle past the cache lifetime pays the whole prefix again on the next message, and the lifetime is five minutes by default on an API key or a cloud provider.

3. One session, worked

Here is the arithmetic on a shape you will recognise: a forty-turn session on Sonnet 5 carrying about 90,000 tokens of context. The point is not the total, it is which term dominates it.

  1. Count what is re-sent. The whole conversation goes with every request, so forty turns at 90,000 tokens is 3.6 million input tokens across the session.
  2. Price it uncached. 3.6 million × $2 per million = $7.20, for content the model has already read thirty-nine times.
  3. Price it as cache reads. At 0.1x, the same 3.6 million costs $0.72. The difference, $6.48, is what caching is worth on one session.
  4. Add the output. Forty turns producing 800 tokens each is 32,000 output tokens, at $10 per million, which is $0.32. Output is five times the price and a hundredth of the volume.

So on a long agent session the bill is dominated by re-reading context, not by writing answers, and the single largest control on it is how much context there is to re-read.

4. The multipliers that stack, and the ones that do not

Everything else is a multiplier on that arithmetic, and they are all smaller than the model choice.

Two smaller lines are worth knowing because they are billed outside tokens entirely. Web search is $10 per 1,000 searches on top of the tokens the results become. Code execution, used without web search or web fetch, is billed by container-hour with 1,550 free hours a month per organisation and $0.05 an hour after that. Neither will dominate a coding fleet's bill, and both will surprise whoever forgot they existed.

One line is a trap rather than a lever. Claude 4.7 and later models use a newer tokenizer that produces roughly 30% more tokens for the same text. A model whose per-token price is unchanged can therefore cost more per unit of work, and a cost comparison across that boundary that counts tokens rather than characters will be wrong in a direction nobody expects.

Check yourself

Retrieval practice

Answer from memory before revealing.

You will send the same 50,000-token document exactly once more, within a minute. What is cheapest?
A 1.25x write followed by a 0.1x read totals 1.35x against 2x for sending it twice uncached, so five minutes wins on the first read. The first option pays a 2x write and needs two reads to break even, so it loses on exactly one. The second is the intuition the multipliers exist to correct. The fourth is not wrong about batch halving the write, but batch is asynchronous and cannot serve a request you are waiting on.
A forty-turn session carries 90,000 tokens of context. Which change reduces the bill most?
Input volume dominates: 3.6 million input tokens against roughly 32,000 output tokens in the worked example, so halving the context saves about a hundred times what halving the output saves. The second option is the trap the five-times ratio sets. The third is a 1.1x increase, not a reduction. The fourth changes nothing on its own, because two sessions carrying the same context re-send the same tokens unless the split is also a clear.

Practice about 20 minutes, with a real session

Practice 1frontier

Price one of your own sessions from its own numbers, then find the free lever.

Finish a real task with your agent, then run /usage and record four figures: input tokens, output tokens, cache read tokens and cache write tokens. Compute the bill yourself from the price table and compare it with the total the tool reports.

Then compute the cache-read share of input tokens, and say in one sentence what would have to change for it to be ten points higher.

Hint

Four multiplications and an addition: input at 1x, cache writes at 1.25x or 2x, cache reads at 0.1x, output at 5x input, all divided by a million. If your figure is far above the reported total, check whether you have priced the cache reads at the full input rate.

Show a worked example
  1. Take a real block. Say Sonnet 5 reports 1,200 input, 5,300 output, 940,000 cache read and 50,000 cache write.
  2. Price each line. Input 1,200 × $2 per million = $0.0024. Output 5,300 × $10 = $0.053. Cache read 940,000 × $0.20 = $0.188. Cache write 50,000 × $2.50 = $0.125.
  3. Add them. The total is $0.37, and the two cache lines are 85% of it.
  4. Read the share. Cache reads are 940,000 of 941,200 input tokens, which is 99.9%. There is nothing left to win here, so the lever is not caching: it is that the prefix being cached is 940,000 tokens long.

Sanity check. Your computed total should land within a few percent of what the tool reports, because it computes the same arithmetic locally at list price. A large gap usually means your organisation has contracted rates configured, in which case the tool's total says so on the line itself.

Your teacher. If the cache multipliers still feel arbitrary, ask your agent to write the break-even inequality for you and solve it for the number of reads, then check that it gets one and two. If the session arithmetic felt abstract, ask it to read your last /usage block aloud line by line and name which lever would move each line.
