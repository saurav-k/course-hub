Module 06 · Agentic code review · Lesson 0640

Write the standard once, in the repository, where every reviewer reads it

working 13 min Four artefacts, each shown complete, each carrying its source and its licence verdict. · Cursor Bugbot rules

The one-minute version

  • A rule has three parts: a condition, a scope, and a required action including the finding's title and whether it blocks. Miss any one and the reviewer improvises.
  • The rules belong to the repository, not to the vendor - and one vendor has conceded it, because Devin Review reads its competitors' rules files as well as its own.
  • The section everybody forgets is "do not flag". Without it a rules file only ever grows, and precision decays every quarter.
  • A rule that can be expressed deterministically belongs in a scanner, in CI. A rule that needs judgement belongs in a comment. Write both for the same intent and the difference becomes obvious.

1. Every reviewer now reads a checked-in file

This is the quiet consensus of the field, and one product states it more clearly than any argument could. Cognition's Devin Review reads REVIEW.md, AGENTS.md, CLAUDE.md, CONTRIBUTING.md, .cursorrules, .windsurfrules, .cursor/rules, .coderabbit.yaml and greptile.json. A reviewer that reads its competitors' configuration files has conceded that the standard belongs to the repository.

2. A rule is a condition, a scope and an action

Cursor's own documented example has all three: if any changed file contains the pattern (condition), across the repository unless a glob narrows it (scope), then add a blocking Bug with title "Dangerous dynamic execution" (action, with the title supplied). The title matters more than it looks - it is what makes two findings of the same kind group in a reader's eye instead of arriving as two unrelated paragraphs.

.cursor/BUGBOT.md · shape from Cursor's Bugbot documentation · documentation licence not stated · paraphrased, written for this course
## Dangerous dynamic execution
If a changed file matches /\beval\s*\(|\bexec\s*\(/i, then:
- add a blocking Bug titled "Dangerous dynamic execution"
- quote the line and name the untrusted input that reaches it
- suggest the safe replacement already used elsewhere in this repo

## Migrations are append-only
For files matching db/migrate/**:
- if an existing migration is modified rather than added, add a
  blocking Bug titled "Edited a shipped migration"
- name the deployment that has already run it

## Missing tests for backend changes
If the change touches server/**, api/** or backend/** and no file
under **/*.test.*, **/__tests__/** or tests/** changed, then:
- add a blocking Bug listing the behaviours now unverified

## Do not flag
- formatting, which the formatter owns and CI enforces
- import ordering, which the linter owns
- naming preferences with no rule behind them

Cursor's docs say the combined rules for one review are "capped at 100,000 characters" and that beyond it "some rules may be omitted", silently. That is the context budget from module 2 arriving in a new costume: a rules file is charged against a window, and a file nobody prunes eventually loses its last rules without telling anybody.

3. The section every team forgets

A rules file that only ever gains rules makes the reviewer louder every quarter. "Do not flag" is how precision is defended, and it is the section that gets written last, after the bot has already annoyed everybody.

Write it from ownership rather than from taste. Formatting has an owner - the formatter - and it runs in CI, so a reviewer commenting on it is duplicating a check that already gates. The test for a line in this section is that some other tool already gives the same answer, deterministically, earlier.

The authoring rule Write rules from comments you have actually left twice. A rule that no real diff in your history would have violated is decoration, and it costs context on every review forever.

4. Scope is what makes a monorepo possible

One standard for a whole monorepo is either too loose for the payments service or too strict for the marketing site. Bugbot's answer is directory scoping: "Bugbot always includes the root .cursor/BUGBOT.md file and any additional files found while traversing upward from changed files", so a rules file deep in the tree applies only when something beneath it changed.

5. The same intent, written twice

Take the migration rule from the file above and write it as a scanner rule instead. Lesson 0710 is where scanner rules are taught properly - here it is only the contrast. Semgrep's syntax needs an id, a message, a severity from LOW to CRITICAL, a languages list and one pattern operator, plus an optional paths section.

.semgrep/shipped-migration-edited.yaml · written for this course against Semgrep's documented rule syntax · MIT (this repository) · reproduced verbatim
rules:
  - id: shipped-migration-edited
    languages: [generic]
    severity: HIGH
    message: >-
      A migration under db/migrate/ was modified. Migrations are
      append-only once deployed - add a new migration instead.
    paths:
      include:
        - "db/migrate/*"
    pattern-regex: ".*"

Read the two side by side. The Semgrep rule fires every time, identically, and returns an exit code a merge can depend on - but it cannot tell you that this particular edit is safe because the migration has not shipped yet. The Bugbot rule can say that, and it will say something slightly different next Tuesday. They are not competitors; a mature repository runs both, and the one you can require is the deterministic one.

6. A different axis: volume, not content

Some settings are not rules at all. CodeRabbit's profile takes quiet, chill or assertive, documented as choosing between "only the most important feedback" and "more feedback". That changes how much the reviewer says, not what it believes. Keep the two axes apart when you tune: a bot that is wrong needs a rule, and a bot that is right too often needs a profile.

.coderabbit.yaml · composed from CodeRabbit's documented keys and defaults · documentation licence not stated · paraphrased
language: "en-US"

reviews:
  profile: "chill"
  request_changes_workflow: false
  high_level_summary: true

  path_filters:
    - "!**/*.generated.ts"
    - "!**/vendor/**"
    - "!pnpm-lock.yaml"

  path_instructions:
    - path: "src/auth/**"
      instructions: >-
        Treat every change here as security-sensitive. Flag any new
        code path that reaches a session token without passing
        through the existing guard.

  auto_review:
    enabled: true
    auto_incremental_review: true
    auto_pause_after_reviewed_commits: 5
    drafts: false
    ignore_title_keywords: ["WIP", "DO NOT MERGE"]

  tools:
    semgrep:
      enabled: true
    gitleaks:
      enabled: true

knowledge_base:
  learnings:
    scope: "auto"

Two of those keys are the answer to "the bot commented forty times on my lockfile": path_filters and auto_pause_after_reviewed_commits, which the documentation gives a default of 5. Neither makes the reviewer cleverer. Both are the volume dial that 0650 treats as a setting in its own right. Note also that the tools block runs Semgrep and a secret scanner inside the review: the rules engine and the reasoner in one pipeline, which is the architecture 0630 argues for.

7. A rule about the reviewer, not the code

The last artefact is the reviewer's own definition. Claude Code's subagent format is a Markdown file under .claude/agents/ with a frontmatter block whose tools line is the architecture decision from 0630 written as one line.

.claude/agents/pr-reviewer.md · frontmatter fields per Claude Code's subagent documentation, body written for this course · MIT (this repository) · reproduced verbatim
---
name: pr-reviewer
description: Reviews a diff against this repository's written standards
tools: Read, Grep, Glob, Bash
model: opus
---

You are reviewing a diff you did not write. You cannot see the reasoning
that produced it, and that is the point - judge the result on its own terms.

Report only findings that affect correctness or a stated requirement.
For each one, give three things and nothing else:

- the file and the line
- the input or state that triggers the wrong behaviour
- the observable wrong result

Do not report style preferences, naming opinions or missing abstraction.
Formatting is owned by the formatter and import order by the linter - both
run in CI and neither is your job.

If the diff is correct, say so in one line. A reviewer asked to find gaps
will find some - resist that.

Three lines carry the whole design. tools: Read, Grep, Glob, Bash makes this an agentic reviewer with no write access, which is the correct default: a reviewer that edits is no longer a reviewer. The three-part finding format is 0610's anatomy turned into an instruction. And the closing line exists because the failure mode of a reviewer prompt is that asking for gaps produces gaps whether or not any are there.

Check yourself

Retrieval practice

Answer from memory before revealing.

Which section of a rules file is the one that defends precision over time?
Only "do not flag" removes output, and a file that only ever gains rules gets louder every quarter. The second and third both add findings, however precise each one is. The fourth makes findings easier to group and triage, which is real but does not change how many arrive.
Why can a Semgrep rule be a required check when a review rule cannot?
Repeatability is the property a gate needs: a check that can differ between two runs of one commit makes merging a lottery. The first is a scheduling detail you control and could reverse. The second is true of both - a review rule is also written by a person. The fourth invents a restriction that does not exist, and lesson 0650 shows exactly the ruleset where you choose not to require the review anyway.

Practice about 30 minutes, with your review history

Practice 1working

Write the first three rules of your own rules file, and earn each one.

Find three comments you or a colleague have left more than once in the last three months. Search your pull requests for a phrase you know you repeat.

Write each as a condition, a scope and a required action with a title, in the shape of the file above. Then write the "do not flag" section from the checks that already run in your CI.

Hint

If a candidate rule needs the words "usually" or "consider", it is not a rule yet. Either find the condition that makes it always true, narrow the scope until it is, or leave it out - a rule that fires on a judgement call spends its context and returns noise.

Show how the three rules usually come out
  1. Rule one is nearly always a path rule. Migrations, generated code, a vendored directory, or the workflow files themselves. These are the easy wins because the condition is a glob and needs no judgement at all.
  2. Rule two is usually a missing-artefact rule. Backend change with no test change, new endpoint with no entry in the API document, new feature flag with no default. Each is a condition over two sets of paths.
  3. Rule three is where the judgement lives. "This code path reaches a session token without passing the guard" cannot be a glob, and it is exactly the two thirds of a standard that the chart above says a linter cannot reach.
  4. Write "do not flag" from CI, not from taste. List every check that already runs and gates. Each of those is a line, and each line is one class of comment your reviewer will now not make.
  5. Decide which rule moves to Semgrep. Rule one almost certainly should, because it is deterministic and it can then be required.

Sanity check. If you could not find three comments you have repeated, you either have very consistent contributors or you are not reviewing much - either way, do not invent rules to fill the file. Two earned rules beat six imagined ones, and every imagined rule is paid for on every review.

Your teacher. Point your agent at the last hundred review comments in your repository and ask it to cluster them, then to write the three clusters that recur most as rules in the condition-scope-action shape. Read every rule it proposes against the authoring test: would a real diff in your history have violated this? Delete the ones that would not.
