An agent with no terminal interface is just another command in the pipe

working 8 min Every flag here was read from the documentation in this session and none is quoted from memory. · Run Claude Code programmatically

The one-minute version

  • -p runs one turn with no terminal interface. It reads stdin, writes stdout, and exits 0 on success and non-zero on failure, so a script can branch on it.
  • Three output formats: text, json with a result and a session_id, and stream-json for events. --json-schema puts a typed answer in structured_output.
  • --bare skips discovery of hooks, skills, commands, subagents, plugins, MCP servers, auto memory and CLAUDE.md, which is how a run gets the same result on every machine.
  • Scope what it may do with --allowedTools, and mind the space: Bash(git diff *) prefix-matches, and Bash(git diff*) also matches git diff-index.

1. The shape of a filter

The simplest useful form is a pipe and a redirect, and it is the one worth having in your fingers:

shell · Claude Code headless documentation · Anthropic documentation, licence unstated · quoted, complete command
cat build-error.txt | claude -p 'concisely explain the root cause of this build error' > output.txt

2. What actually fits in the pipe

Piped standard input is capped at 10MB, and exceeding it exits non-zero with an error rather than truncating. Ten megabytes is a great deal more than it sounds, which is worth seeing against real inputs rather than imagining.

That last point is the honest one. A 512KB diff fits the pipe comfortably and is still around 128,000 tokens before the agent has done anything with it. When an input is large, the documented move is to write it to a file and name the path in the prompt, so the agent reads the parts it needs.

3. Three formats, three jobs

FormatWhat you getWhat it needsWhat it is for
textThe answer, as proseNothing; it is the defaultA human reads it, or you grep it
jsonOne object with result, session_id, and total_cost_usd plus a per-model cost breakdownNothingA script that needs to branch, resume, or record spend
stream-jsonOne JSON object per line, ending in a result message--verbose, and --include-partial-messages for token deltasShowing progress, or reacting before the run ends

The cost figures in the json payload are documented as client-side estimates and can differ from the bill, which is worth knowing before you build a budget alarm on them.

shell · Claude Code headless and best-practices documentation · Anthropic documentation, licence unstated · quoted, complete commands
# Structured JSON, then pull one field
claude -p "Summarize this project" --output-format json | jq -r '.result'

# Constrained output against a JSON Schema
claude -p "Extract the main function names from auth.py" \
  --output-format json \
  --json-schema '{"type":"object","properties":{"functions":{"type":"array","items":{"type":"string"}}},"required":["functions"]}' \
  | jq '.structured_output'

# Stream the text deltas as they arrive
claude -p "Write a poem" --output-format stream-json --verbose --include-partial-messages | \
  jq -rj 'select(.type == "stream_event" and .event.delta.type? == "text_delta") | .event.delta.text'

# A reproducible CI run: no hooks, skills, plugins, MCP, auto memory or CLAUDE.md
claude --bare -p "Summarize README.md" --allowedTools "Read"

The smallest real example of that shape ships in Anthropic's own documentation as a package.json script. Note that the diff is piped rather than read: piping means the agent needs no shell permission to get it.

package.json · Claude Code headless documentation · Anthropic documentation, licence unstated · quoted, complete file fragment
{
  "scripts": {
    "lint:claude": "git diff main | claude -p \"you are a typo linter. for each typo in this diff, report filename:line on one line and the issue on the next. return nothing else.\""
  }
}

4. Scoping what it may do, and the space that matters

--allowedTools pre-approves tools for the run, using the same permission-rule syntax as your settings file. One detail in that syntax has bitten enough people to be documented explicitly: the trailing space before the asterisk.

shell · Claude Code headless documentation · Anthropic documentation, licence unstated · quoted, complete command
claude -p "Look at my staged changes and create an appropriate commit" \
  --allowedTools "Bash(git diff *),Bash(git log *),Bash(git status *),Bash(git commit *)"

Bash(git diff *) allows any command beginning git diff followed by a space. Bash(git diff*), with no space, also matches git diff-index and anything else starting with those eight characters. That is a wider grant than you meant, written by one absent keystroke, and nothing reports it.

To set a baseline for the whole run rather than listing tools, pass a permission mode. In -p the starting mode is Manual on every plan, so you must pass the one you want: --permission-mode dontAsk denies anything not in your allow rules or the read-only command set, which is the documented shape for a locked-down CI run.

5. Many of them at once

Because it is a program, the way to run it two thousand times is a loop. The documented pattern is to have the agent write the task list to a file first, then iterate it with the tools scoped.

shell · Claude Code best-practices documentation · Anthropic documentation, licence unstated · quoted, complete loop
for file in $(cat files.txt); do
  claude -p "Migrate $file from Python 2 to Python 3. Return OK or FAIL." \
    --allowedTools "Edit,Bash(git commit *)"
done

The advice attached to that loop in the documentation is the part people skip: refine the prompt against the first two or three files, then run the full set. Claude Code also ships a bundled way to do the same thing with parallelism, /batch, which splits a change across 5 to 30 subagents, each in its own worktree, each opening a pull request.

Without --bare, a -p session runs the hooks in a project's .claude/settings.json and connects the servers in its .mcp.json, even in a folder you have never trusted, and it shows no trust dialogue and no per-server approval. That is documented behaviour rather than a defect, and it means piping somebody else's repository through a scripted agent is an execution decision, not a reading one. In CI, pass --bare and add back exactly what you need.
Running many of these at once is a supervision problem before it is a scripting one: knowing which of ten agents is stuck, and reading them without switching windows. Knowing which agent is stuck in Herdr is that problem, and this course does not teach a terminal multiplexer.

Your CI job passes on your machine and fails on a colleague's. Which flag was missing?
Bare mode is the documented answer to "same result on every machine": without it, a -p run picks up hooks, skills, plugins, MCP servers, auto memory and CLAUDE.md from whichever machine it is on. The second changes what is printed, not what runs. The third changes the shape of the output. The fourth would change what is allowed, which can also differ per machine, but it is a narrower cause than the whole discovery surface.
What does --allowedTools "Bash(git diff*)" permit that the version with a space does not?
Without the space the prefix ends mid-word, so anything beginning with those eight characters matches, git diff-index included. The first is the belief that causes the bug. The second overstates it: git push still does not match. The third describes what you would get from a rule with no asterisk at all, which is the opposite mistake.

Practice about 25 minutes, with a terminal

Practice 1working

Wrap the skill you have been building in a shell script that branches on the exit code and pulls one field with jq.

The script takes a file path, pipes or names it, invokes claude --bare -p "/<your-skill> ..." --output-format json --allowedTools "...", and exits 0 or 1 of its own accord depending on what came back.

Then break it three ways and check each one produces a distinguishable failure: pass a flag that does not exist, revoke the tool the skill needs, and pipe it an empty file.

Hint

set -euo pipefail at the top will make the first of the three failures loud instead of silent. Capture the output in a variable before you parse it, so you can print it when jq finds nothing.

Show the three failures and what each proves
  1. A flag that does not exist. The error appears on standard error before the run starts, and the exit code is non-zero. Your script should print stderr and stop; nothing was charged.
  2. The tool revoked. The run starts, the agent cannot do the work, and the failure comes back as the result on standard output with a plausible exit code. This is the case that turns into a silent pass if you only check the exit code, and it is why the parse step exists.
  3. An empty file. The run succeeds and the result is about nothing. Neither the exit code nor a schema catches this: only your own check on the parsed field does, which is what the third branch of the script is for.
  4. Add --bare and re-run all three. If any result changes, something on your machine was participating that would not be there in CI, and finding out which is worth the five minutes.

Sanity check. Three failures should produce three different messages from your script. If two of them look the same, the script is checking one thing where the tool reports two, and it will report a broken agent as a clean run at least once.

Your teacher. Ask your agent to write the wrapper script for you and then to explain, line by line, which line survives a non-zero exit and which does not. If it cannot say what happens to a pipeline's exit status without pipefail, that is the thing to fix before the script goes near CI.
