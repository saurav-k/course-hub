Module 06 · Agentic code review · Lesson 0650

Trigger, volume and authority are three settings, and confusing them is how the bot gets muted

working 12 min Three complete artefacts: an MIT-licensed review workflow, a CODEOWNERS file, and the ruleset it pairs with. · anthropics/claude-code-action

The one-minute version

  • Trigger decides when the reviewer runs. Volume decides how much it says. Authority decides what its output is allowed to conclude. They are three files and three different mistakes.
  • Authority is the one that hurts. An automated comment is advice; a required status check is a gate, and a gate publishes a claim to every future reader of that pull request.
  • Given the recall ceiling from 0620, your test suite is required and your AI review is not. That single line is most of this page.
  • CODEOWNERS is the routing layer, and its two load-bearing rules are that the last matching pattern wins and that a pattern with no owner deliberately removes ownership.

1. Trigger: when it runs, and on whose behalf

The trigger is a list of pull-request events. Factory's CI reviewer fires on opened, synchronize, reopened and ready_for_review and "skips draft PRs to avoid noise during development". Devin Review offers the same decision as three modes: auto review, on pull-request creation only, or manual. Same choice, made twice, in two vocabularies.

Here it is as a file you can commit today. This one is worth reading line by line, because three of its lines are the architecture from 0630 written down.

.github/workflows/claude-auto-review.yml · anthropics/claude-code-action, docs/solutions.md · MIT · reproduced verbatim
name: Claude Auto Review
on:
  pull_request:
    types: [opened, synchronize]

jobs:
  review:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      pull-requests: write
      id-token: write
    steps:
      - uses: actions/checkout@v6
        with:
          fetch-depth: 1

      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
          prompt: |
            REPO: ${{ github.repository }}
            PR NUMBER: ${{ github.event.pull_request.number }}

            Please review this pull request with a focus on:
            - Code quality and best practices
            - Potential bugs or issues
            - Security implications
            - Performance considerations

            Note: The PR branch is already checked out in the current working directory.

            Use `gh pr comment` for top-level feedback.
            Use `mcp__github_inline_comment__create_inline_comment` (with `confirmed: true`) to highlight specific code issues.
            Only post GitHub comments - don't submit review text as messages.

          claude_args: |
            --allowedTools "mcp__github_inline_comment__create_inline_comment,Bash(gh pr comment:*),Bash(gh pr diff:*),Bash(gh pr view:*)"

Three annotations. permissions: contents: read is least privilege at the workflow level and it is what stops a review job becoming a write job. --allowedTools is the architecture decision as one line: this reviewer may read the diff and comment, and may not edit. And "Only post GitHub comments" exists because the natural failure of a reviewer in CI is that it writes a beautiful review into the job log where nobody will ever read it.

The cheapest volume control there is also lives in the trigger, because a path filter means the job never starts.

.github/workflows/review-critical-files.yml, the trigger block · same repository and file · MIT · reproduced verbatim
name: Review Critical Files
on:
  pull_request:
    types: [opened, synchronize]
    paths:
      - "src/auth/**"
      - "src/api/**"
      - "config/security.yml"

2. Volume: four knobs, four vocabularies

Every product ships the same four controls and none of them calls them the same thing. Learn the four and the documentation of any new tool reads in five minutes.

The knobCodeRabbitCursor BugbotFactory / Devin Review
Skip work in progressdrafts: false, ignore_title_keywordsautomations settingsskips drafts by default
Only review the new commitsauto_incremental_review: truereviews only changes since its last reviewauto review on new commits
Stop after a whileauto_pause_after_reviewed_commits: 5-a per-pull-request spend limit
Ignore some pathspath_filtersrule globsthe workflow's paths: list

Every one of these exists because somebody drowned. The one people find last is the pause: CodeRabbit's documented default stops automatic review after five reviewed commits, which is the setting that keeps a long-running branch from being reviewed forty times.

Volume also has a per-repository component nobody expects, because the same reviewer is not equally good everywhere.

3. Authority: advice or a gate

This is the beat that matters, and it is decided outside every tool's own settings. GitHub's branch rulesets are where a pull request's merge eligibility is actually written, and the relevant rules read plainly: required approvals; "Require reviews from code owners"; dismissal of stale approvals when new commits are pushed; and "Require an approval from someone other than the last person to push to a branch". There is also now a rule written for this era, enabled by default: "Require an additional approval for unattributed Copilot pull requests".

Routing is the other half of authority: which human sees the change at all. GitHub searches for CODEOWNERS in .github/, the root, then docs/ and uses the first it finds; "the last matching pattern takes the most precedence", and an approval from any one of the owners satisfies the requirement.

.github/CODEOWNERS · composed for this course - the semantics are GitHub's, from about code owners · GitHub Docs are CC BY 4.0 · reproduced verbatim
# .github/CODEOWNERS
# Order matters: the LAST matching pattern wins.

# Default owners for everything not claimed below.
*                       @acme/platform

# Frontend.
/web/                   @acme/web

# Anything security-sensitive needs the security team, whoever else owns it.
/src/auth/              @acme/security
/src/crypto/            @acme/security
**/*.pem                @acme/security

# Infrastructure, and the gates themselves.
/.github/workflows/     @acme/platform @acme/security
/.github/CODEOWNERS     @acme/platform

# Generated: nobody reviews it, because it is regenerated.
/src/api/generated/

Two lines carry the lesson. /.github/CODEOWNERS @acme/platform stops somebody editing their way out of ownership, which is the protection GitHub's own documentation recommends. And /src/api/generated/ with no owner after it removes ownership deliberately, so a regeneration does not block waiting on a human who has nothing to judge.

The ruleset that pairs with it is a set of switches rather than a file, so here it is written out as settings.

Branch ruleset for main · composed for this course from GitHub's available rules for rulesets · GitHub Docs are CC BY 4.0 · reproduced verbatim
Ruleset: protect main
  Target: default branch

  Require a pull request before merging
    Required approvals: 1
    Require review from Code Owners: on
    Dismiss stale pull request approvals when new commits are pushed: on
    Require approval of the most recent reviewable push: on
    Require an additional approval for unattributed Copilot pull requests: on

  Require status checks to pass
    Require branches to be up to date before merging: on
    Required checks:
      - verify            # lint, typecheck, tests
      - secret-scan
    NOT required:
      - ai-review         # advisory only - it must never gate

  Block force pushes: on
The NOT required line is the whole sample. Making an AI review a required check would gate every merge on an instrument whose best measured recall is 61.7% - so a green tick would mean "the thing that misses two of every five real bugs found nothing", while reading to everybody as "reviewed". It would also hand every flaky false positive the power to stop a release. Require what is deterministic and let the reviewer advise.

Check yourself

Retrieval practice

Answer from memory before revealing.

Your reviewer comments forty times on a long-running branch. Which dial is wrong?
Repeated review of the same branch is a volume problem, and both the incremental-review setting and the documented pause after five reviewed commits exist for it. The first changes nothing about how much it says. The third would reduce comments per review but not the number of reviews. The fourth inverts the draft rule - running only on drafts is the opposite of what any product does by default.
In CODEOWNERS, what does a path listed with no owner after it do?
An empty owner list deliberately un-owns the path, which is what you want for generated code nobody should be asked to judge. The first inverts the last-match-wins rule, which resolves to the empty entry rather than skipping it. The second is untrue - GitHub parses the line. The third describes the opposite of the documented behaviour, where an approval from any one owner is sufficient.

Practice about 40 minutes, with a repository you administer

Practice 1working

Install the three settings on your capstone repository, in order, and write down what each one changed.

Commit the review workflow, scoped with a paths: list to one directory rather than the whole repository. Open one pull request inside that directory and one outside it, and confirm the job ran exactly once.

Then write a CODEOWNERS entry that routes that directory to a specific reviewer, and configure the ruleset so verify is required and the review is not.

Hint

The workflow needs a secret before it will run at all, and a job that cannot authenticate fails in a way that looks like a trigger problem. Check the job actually started before you conclude your paths: list is wrong.

Show the order to install them in, and why
  1. Trigger first, scoped narrowly. One directory, drafts excluded. A reviewer installed repository-wide on day one is a reviewer somebody mutes in week two, and you will never get a second first impression from your team.
  2. Confirm it ran once. The pull request outside the scoped paths should show no job at all - not a skipped one, no job. If it ran, your paths: list did not match what you thought it did.
  3. Routing second. Add the CODEOWNERS line, and put it below the default line rather than above it, because the last matching pattern wins. Test it by opening a pull request and checking who GitHub requested.
  4. Authority last, and deliberately. Turn on required approvals, code-owner review and stale-approval dismissal. Leave the review job out of the required list, and write a one-line comment in the ruleset description saying why, so the next administrator does not "fix" it.
  5. Write down what changed. Comments per pull request, and whether anybody complained. That is the first row of the measurement table in 0660.

Sanity check. After all three, a pull request touching only files outside your scoped paths should merge with no AI comments at all, and a pull request inside them should be blocked only by verify and a missing code-owner approval. If the review job can block anything, the authority dial is still wrong.

Your teacher. Ask your agent to read your repository's current branch protection and CODEOWNERS and tell you, for one specific pull request you name, exactly which rule is stopping it merging. If it cannot answer without guessing, your gates are configured in more places than one and that is worth fixing before you add another.
