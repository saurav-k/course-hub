Capstone · Read after module 04 · Lesson 1110

Three artefacts, and each one is done only when a different kind of evidence says so

frontier 8 min The second of four capstone stops. It spends modules 3 and 4 on the repository you chose at stop one. · Claude Code hooks

The one-minute version

  • You have just finished module 4, so you know that an instruction asks and a hook decides. This stop is where you feel the difference on your own repository.
  • Three artefacts land today: an instruction file, one skill lifted from a procedure you have pasted twice, and one hook that blocks something real.
  • Each has its own proof, and they are not interchangeable. The file is proved by being loaded, the skill by activating unasked, the hook by refusing.
  • The deliverable is the deliberate failure: a transcript of your own hook stopping you, with your reason text visible in it.

1. Three artefacts, three proofs

The single most common way this stop goes wrong is that all three artefacts are checked the same way - by reading them and agreeing that they look right. They cannot be, because they act at three different points of a turn.

An instruction file is context. It is concatenated into what the model is told, on every turn, and its proof is that it was loaded at all: if the harness never read it, every sentence in it is decoration. A skill is conditional context. Its whole contract is the description, so its proof is that it activated on a task you phrased without naming it. A hook is a program that runs between the model asking and your machine acting, so its proof is a refusal - and only a refusal, because a hook that has never blocked anything is indistinguishable from a hook that is misconfigured.

2. The file, written as a budget

Write AGENTS.md and let the other filenames point at it. The open format is described as "a README for agents", it is used by over 60,000 public repositories, and its nesting rule is that the closest file to the edited file wins, so a monorepo can carry one at the root and one per package without anything overriding anything by surprise.

Fill it from your own baseline rather than from a template. The three tasks you recorded at stop one produced a list of questions you would have answered if the agent could have asked, and that list is the file. Everything else - the architecture essay, the history, the values - is context you pay for on every turn and that the repository can already show.

AGENTS.md · written for this course, from the reader's own baseline · hub content, CC BY 4.0 · reproduce freely
# AGENTS.md

Contract for coding agents working in this repository.
`CLAUDE.md` is a symlink to this file.

## Commands

- Install: `make setup`
- One test: `pytest tests/test_billing.py::test_proration -x`
- Whole check, and the definition of done: `make verify`

## Gotchas

- The default branch is `dev`. A diff against `main` succeeds and shows nothing.
- `config/settings.yaml` is generated. Edit `config/settings.yaml.in` and run `make config`.
- `SERVICE_TIMEOUT` in the environment overrides the value in the config file.

## Boundaries

**Always** run `make verify` before calling the work done, and paste the last line.
**Ask first** before adding a dependency to `packages/`, which ships to users.
**Never** commit to `dev` directly, and never commit a file matching `*.pem`.

Three sections, and each line in the second one is a question your baseline shows an agent could not answer. The last section is the interesting one: two of its three rules are still only asks, and the third is what the hook below turns into a decision.

3. The skill, from a procedure you have already pasted twice

Do not invent one. Find a procedure you have pasted into a chat at least twice - a release note, a migration, a triage walk, a data pull - and move it into .claude/skills/<name>/SKILL.md. The body is what you were pasting. The work is the description.

Read your own description back and ask whether it says when rather than only what. "Writes release notes" tells the agent what the folder contains; "Use when asked for release notes, a changelog entry, or what shipped in a version" tells it when to open it, and only the second one is executed. Anything the agent needs merely sometimes goes into references/; anything deterministic goes into scripts/, with an instruction to run it with --help rather than to read its source.

4. The hook, and the deliberate failure

Take one line from the Boundaries section and make it true whatever the model decides. The documented protocol gives you two ways to say no, and the difference matters: the documentation states that "Exit 0 means success, and is the intended exit code when you print JSON for structured control", while "Exit 2 means a blocking error" and, on events that can block, "exit 2 blocks whether or not you print JSON: even a JSON permissionDecision of "allow" can't override it". Pick one shape per hook and stay in it.

.claude/hooks/verify-gate.sh · ours, written against the documented hook protocol · hub content, CC BY 4.0 · reproduce freely
#!/usr/bin/env bash
# .claude/hooks/verify-gate.sh - refuse a commit to the default branch, and
# refuse any commit while `make verify` is failing. One rule, two clauses.
set -euo pipefail

INPUT=$(cat)
COMMAND=$(printf '%s' "$INPUT" | jq -r '.tool_input.command // empty')

deny() {
  jq -n --arg reason "$1" '{
    hookSpecificOutput: {
      hookEventName: "PreToolUse",
      permissionDecision: "deny",
      permissionDecisionReason: $reason
    }
  }'
  exit 0
}

case "$COMMAND" in
  git\ commit*) ;;
  *) exit 0 ;;
esac

if [ "$(git rev-parse --abbrev-ref HEAD)" = "dev" ]; then
  deny "Commit blocked: dev is the default branch. Create a branch first."
fi

if ! OUTPUT=$(make verify 2>&1); then
  deny "$(printf 'Commit blocked: make verify failed.\n%s' "$OUTPUT" | tail -c 4000)"
fi

exit 0
.claude/settings.json · ours, written against the documented settings schema · hub content, CC BY 4.0 · registers the script above
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/verify-gate.sh"
          }
        ]
      }
    ]
  },
  "permissions": {
    "deny": ["Read(./*.pem)", "Read(./.env)"]
  }
}

Two mechanisms, one rule. The hook stops the commit; the permission rule narrows what the tool could have reached in the first place. Prove the hook by making it fire on purpose: check out the default branch, ask your agent to commit, and keep the transcript with your reason text visible in it. That transcript is the deliverable of this stop, and it is the one artefact nobody can produce by reading a document.

A hook runs your script, on your machine, with your credentials, and its refusal text is read by the model. Both halves of that are easy to forget. A hook is not a sandbox: it runs whatever you wrote, so a hook that shells out to something the model influenced is a new way in rather than a defence, and module 7 is where that becomes the subject. The second half is subtler. The permissionDecisionReason you write is appended to the conversation as the tool result, so it is a prompt: it should name the next legal move, because a reason that only says "no" leaves the model to invent one. Write "create a branch first", not "not allowed".

Check yourself

Retrieval practice

Answer from memory before revealing.

Your skill runs correctly every time you type its name. Is the skill proved?
A skill's contract is its description, and naming the skill bypasses it entirely: you proved the body runs, not that the agent can tell when to open it. The first option mistakes the body for the contract. The third names a real budget concern that has nothing to do with activation. The fourth is portability, which is a separate and later question.
Which of these is evidence that your instruction file changed the agent's behaviour?
Only the fourth is evidence about the file: the agent used something it could only have learned from the file, on a task where it previously searched. The first is existence. The second confuses the outcome with its cause, since a good diff is exactly what your baseline recorded before the file existed. The third is a budget check, which is worth doing and says nothing about whether the file was read.

Practice about 90 minutes, with the repository open

Practice 1frontier

Commit the three artefacts to your capstone repository and produce the three proofs.

Write the instruction file from your stop-one baseline, with every command run from a clean checkout. Extract one skill from a procedure you have pasted twice, and phrase its description so it says when. Write one hook that enforces a line from your own Boundaries section, and register it.

Hand in, in docs/learning-records/0002-contract.md: the loaded-memory-files output, a transcript of the skill activating on a task that does not name it, and a transcript of the hook refusing with your reason text visible.

Hint

Write the hook before the instruction file. Choosing which single rule is worth a script forces the Boundaries section to be about things that matter, and the other two rules then almost write themselves.

Show what the three proofs look like, and the three traps
  1. Proof one, the file. A trace where the agent runs make verify at the end of a task you never mentioned it in. The negative version is just as good: run the same task with the file renamed and watch it stop happening.
  2. Proof two, the skill. A trace where you asked "what shipped in 2.4?" and the agent opened the release-notes skill without being told. If it did not, the description names the artefact rather than the trigger.
  3. Proof three, the hook. A transcript showing the model asking to commit, the refusal, your reason text, and the model's next move. The next move is the part to read: if it retried the same command, your reason did not name a legal alternative.
  4. Trap one: three rules, one mechanism. An instruction file with three Never lines and no hook has three suggestions. Pick the one that would actually hurt and spend the script on it.
  5. Trap two: a hook that never fires. A matcher that does not match is silent, so confirm the hook is registered before you test what it does.
  6. Trap three: writing the file for a reader. If a section would be useful to a new human colleague but is never needed to complete a task, it belongs in the README, where nobody pays for it every turn.

Sanity check. Re-run the hidden task from your stop-one baseline and compare the two traces. Reads before the first write should have fallen, and if it has not, your instruction file answered questions the agent was not asking. That is the most common outcome on a first attempt, and the fix is to write the file from the trace rather than from memory.

Your teacher. Hand your agent your stop-one transcripts and your new instruction file, and ask it which lines of the file would have changed which turns of the trace. Lines it cannot attach to a turn are lines to cut. Then ask which question it would still have had to ask, and put that answer in next.
