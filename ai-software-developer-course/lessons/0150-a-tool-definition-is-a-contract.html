The description is behaviour, not documentation

foundation 10 min Both descriptions compared below are Anthropic's own worked pair. · Define tools

The one-minute version

  • A tool definition is three things: a name, a plaintext description, and an input_schema. Only one of the three is prose, and it is the one that decides behaviour.
  • The published rule is a floor with a number in it: aim for at least three or four sentences, and more for a complex tool.
  • An unanswered question in a description becomes a guessed argument, and the API documents the model filling in values you never supplied.
  • You are writing for a reader who has one shot, cannot ask you a follow-up question, and will act on whatever it concludes.

1. The same tool, described twice

Anthropic publishes a good and a poor description of one tool, side by side. Nothing else on this page argues as well as reading them in that order.

get_stock_price, the good description · Anthropic, "Define tools" · Anthropic documentation, quoted as a short excerpt with attribution · reproduced verbatim
{
  "name": "get_stock_price",
  "description": "Retrieves the current stock price for a given ticker symbol. The ticker symbol must be a valid symbol for a publicly traded company on a major US stock exchange like NYSE or NASDAQ. The tool will return the latest trade price in USD. It should be used when the user asks about the current or most recent price of a specific stock. It will not provide any other information about the stock or company.",
  "input_schema": {
    "type": "object",
    "properties": {
      "ticker": {
        "type": "string",
        "description": "The stock ticker symbol, e.g. AAPL for Apple Inc."
      }
    },
    "required": ["ticker"]
  }
}
get_stock_price, the poor description · Anthropic, "Define tools" · Anthropic documentation, quoted as a short excerpt with attribution · reproduced verbatim
{
  "name": "get_stock_price",
  "description": "Gets the stock price for a ticker.",
  "input_schema": {
    "type": "object",
    "properties": {
      "ticker": {
        "type": "string"
      }
    },
    "required": ["ticker"]
  }
}

The second is not badly written. It is a perfectly good docstring, and that is exactly the trap: it answers the question a human reader asks, which is what does this do. The model has to answer four other questions before it can act, and the poor version answers none of them.

Which market, and is this symbol valid here?

The good description names NYSE and NASDAQ. Without that, a request about a company listed only in London produces a call the tool will reject, and the model has no way to know in advance.

What currency comes back?

The good description says USD. Without it the model may present a number in whatever currency the conversation was using, which is a wrong answer that looks right.

How fresh is "current"?

The good description says the latest trade price. Without it, a question about yesterday's close may be answered with this tool, confidently.

What else does it return?

The good description closes the door explicitly: it "will not provide any other information about the stock or company". A boundary stated is a tool the model stops trying to use for the wrong job.

That last one is the pattern worth generalising. A good description spends as much text on what the tool is not for as on what it is for, because the failure a description prevents is not a bad call, it is a call to the wrong tool.

2. The rule, and what happens when you break it

The published guidance names a number, which is unusual enough to quote exactly. Descriptions should explain what the tool does, when it should and should not be used, what each parameter means, and any caveats, and then: "Aim for at least 3-4 sentences for each tool description, more if the tool is complex." Providing extremely detailed descriptions is called out as "by far the most important factor in tool performance".

Break it deliberately and the failure has a documented shape. Given a tool with a required parameter and a request that does not supply it, the API's own note is that the model may invent a value rather than ask: it "might guess values you didn't supply", and the worked example shows a call carrying both a location and a temperature unit that nobody mentioned.

3. The typed half

The schema is ordinary JSON Schema, and three of its features do real work. required separates what the model must supply from what it may omit. enum turns a free string into a closed set, which removes a whole class of guess. And a description on each property is where a parameter's meaning goes, because the top-level description should not be explaining field formats.

get_weather, the reference schema · Anthropic, "Define tools" · Anthropic documentation, quoted as a short excerpt with attribution · reproduced verbatim
{
  "name": "get_weather",
  "description": "Get the current weather in a given location",
  "input_schema": {
    "type": "object",
    "properties": {
      "location": {
        "type": "string",
        "description": "The city and state, e.g. San Francisco, CA"
      },
      "unit": {
        "type": "string",
        "enum": ["celsius", "fahrenheit"],
        "description": "The unit of temperature, either 'celsius' or 'fahrenheit'"
      }
    },
    "required": ["location"]
  }
}

Two further options are worth knowing before you need them. input_examples takes an array of schema-valid example inputs and is documented as costing roughly 20 to 50 tokens for a simple one and 100 to 200 for a complex nested one, which makes it a deliberate purchase rather than a free win. And strict: true guarantees that a tool call matches your schema exactly, so a handler need not defensively re-validate what it was sent.

Here is one of the four tools from the agent in the next lesson, written to the rule. The third sentence is there because a model that does not know it will write cd build and then make as two calls and be baffled by the result.

agent.ts, the bash tool definition · written for this course, schema fields verified against the Messages API reference · MIT (this repository) · reproduced verbatim
schema: {
  name: "bash",
  description:
    "Run a shell command in the working directory and return its stdout and stderr. " +
    "Use it to run tests, a build, git, or a search. Each call is a fresh shell, so state such as " +
    "`cd` or an exported variable does not carry to the next call: put both steps in one command. " +
    "Commands time out after 60 seconds.",
  input_schema: {
    type: "object",
    properties: {
      command: { type: "string", description: "The shell command to run" },
    },
    required: ["command"],
  },
},

4. Whether it may choose at all

One request-level setting sits above every definition. tool_choice has four documented values: auto lets the model decide and is the default when tools are present; any requires some tool; tool requires a named one; none forbids all of them and is the default when no tools are passed.

Forced tool use is not universally available. Under manual extended thinking, any and tool are documented as unsupported and return an error, leaving auto and none; the same restriction applies on Claude Fable 5.1 and Claude Mythos 5.1, where the suggested substitutes are strict tool use or structured outputs. Check the restriction against the model you actually run before you design around forcing.

5. Grade one

The reframe worth leaving with: you are writing for a reader who cannot ask a follow-up question. Every ambiguity is resolved without you, silently, in a direction you will find out about from a trace. Score a description you already ship.

Check yourself

Retrieval practice

Answer from memory before revealing.

Your tool's required region parameter is not mentioned in the user's request. What does the model do?
The documentation is explicit that the model might guess values you did not supply, and shows a worked example doing exactly that. Asking is the behaviour you want and it is only more likely, never guaranteed. The third describes what strict tool use prevents and is not the default failure. The fourth is what a human collaborator would do and is precisely the assumption this page exists to remove.
You set tool_choice to any. What did you give up?
Forcing prefills the assistant message, so no natural-language text is emitted before the tool call, even if you ask for it. The first is untouched by tool_choice. The second is backwards: it is manual extended thinking that restricts forcing, not forcing that removes thinking. The third is what strict: true provides and is unrelated.

Practice about 20 minutes, with a terminal

Practice 1foundation

Take a tool description you or your team wrote - an MCP server's, a script the agent runs, anything with a schema - and score it on the six rows above.

Rewrite the lowest-scoring row into the description, changing nothing else and no code at all.

Then estimate what the rewrite costs per turn, and say how many wasted turns it has to prevent before it pays for itself.

Hint

For the cost, count the characters you added and divide by four. For the break-even, a wasted turn costs the whole current context, not just the failed call.

Show the worked arithmetic
  1. Price the rewrite. Two added sentences of about 160 characters is about 40 tokens, on every turn of every session for as long as the tool is mounted.
  2. Price a wasted turn. One failed call plus one recovery re-sends the whole conversation twice. On a modest 12,000-token context that is about 24,000 tokens.
  3. Find the break-even. 24,000 ÷ 40 = 600. The rewrite pays for itself if it prevents one wasted recovery in every 600 turns.
  4. Read the number. No real tool fails once in 600 turns because of an ambiguity a sentence would have closed. The economics of description length are not close, which is why the guidance sets a floor and no ceiling.

Sanity check. Your break-even should land in the hundreds of turns, not in single digits. If it came out below about twenty, you priced a wasted turn as the failed call alone and forgot that the entire conversation is re-sent with it.

Your teacher. Paste one of your tool descriptions to your agent and ask it to list every question it would have to guess an answer to before calling that tool. Do not ask it to improve the description - the list of questions is the useful artefact, and improving it yourself is the exercise.
