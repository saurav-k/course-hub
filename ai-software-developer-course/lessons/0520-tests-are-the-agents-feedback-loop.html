Module 05 · Agent-ready codebases · Lesson 0520

The suite is the agent's only sense organ, and its latency is the loop's clock speed

working 12 min Built on Anthropic's check taxonomy and on the selective-test instruction a large Python codebase gives its own agents. · Best practices for Claude Code

The one-minute version

  • A check is anything returning a signal the agent can read in the conversation: a suite, a build exit code, a linter, a fixture diff, a screenshot comparison.
  • Selectable beats comprehensive. A suite the agent can run on one file is in the loop; a forty-minute suite is a thing it runs once, at the end, having already decided it is finished.
  • Iterations per hour is sixty divided by the suite's minutes. That single division is the whole argument for selectability.
  • A flaky check is worse for an agent than no check. You remember the flake; the agent reads a failure and starts editing correct code.

1. A check is anything that can fail

The first correction is to stop reading "check" as "test suite". Anthropic's guidance names five kinds and treats them as interchangeable for this purpose: a test suite, a build exit code, a linter, a script that diffs output against a fixture, or a browser screenshot compared against a design. What they share is the only property that matters here: the agent runs it and reads the result inside the same turn.

This is liberating for repositories with weak test coverage, which is most of them. A build that fails on a type error is a check. A linter with a rule encoding the convention you keep repeating is a check. Neither is a test, and both close the loop for the class of mistake they cover.

2. Selectable, not comprehensive

The second correction is about latency, and it is the one that changes how a repository is built. A large Python codebase whose agent instructions are public puts it as an instruction rather than as advice, in a comment beside the command it wants run instead.

AGENTS.md · getsentry/sentry · licence NOASSERTION · short quoted excerpt
# Run a specific test file. Do not run pytest by itself; it'll take forever!
.venv/bin/pytest -n3 -svv --reuse-db tests/sentry/api/test_base.py

Every flag there is buying loop time. -n3 spreads the run over three workers. --reuse-db skips rebuilding the test database, which is usually the largest fixed cost in a Django suite. -svv makes the failure readable rather than merely present. And the path at the end is the whole point: one file, chosen because it is the file that was edited.

Turn the same arithmetic the other way and it becomes a design constraint you can hold in your head. Iterations per hour is sixty divided by the suite's minutes. There is nothing else in the formula, which is why halving the suite doubles the tries and why the curve falls off a cliff early.

3. Four ways to make the agent actually run it

A check that exists and is not run has closed nothing, and the ways of insisting on it differ in cost and in strength. They are worth knowing as a ladder, because most people only ever use the weakest one.

How you insistCostStrength
Ask for it in the promptOne sentence, every time.Advisory, and forgotten in a long session.
State it in the instruction fileOne paragraph, once.Advisory, and paid for in context on every turn.
Give the task a goal conditionRewriting the request as "until X passes".Strong, because it changes what "done" means.
Gate it with a hookA small program, and module 4 is where you write it.Deterministic. It is the only one that can refuse.
The reframing The point of a fast selectable test is not that the agent finishes sooner. It is that the agent changes what it does: with a four-second check it edits and verifies in small steps, and with a forty-minute check it writes the whole change from a guess and verifies once. The second behaviour looks like a model being careless and is a repository being slow.

4. Why flakes are an agent problem specifically

You have a memory across runs and the agent does not. When a test fails for you at random you think "that one again" and re-run it; you are carrying an undocumented exception list in your head. An agent arrives with no such list, reads a failure as information, and does the reasonable thing: it starts changing the code the failure named. That code was correct, so the change makes things worse, and the next run may pass for unrelated reasons, which teaches the agent that its bad change fixed something.

The rule that falls out is stricter than the one for humans. Every check the agent is told to run must be deterministic, and must name what failed rather than that something failed. A repository that cannot yet make its suite deterministic is better served by telling the agent which tests to skip, in the instruction file, by name, than by leaving it to discover them one wrong fix at a time.

The last requirement connects forward. The command the agent runs must be the command CI runs, or the agent is optimising against the wrong oracle and every green local run is a coin toss on the pull request. Lesson 0530 is that problem, and lesson 0540 is what CI has to say back.

Check yourself

Retrieval practice

Answer from memory before revealing.

Your suite takes sixteen minutes. What does the agent's behaviour become, and why?
Sixteen minutes buys under four tries an hour, so iterating is not available and the agent falls back to one long unverified stretch. The first option describes a cost difference where the real effect is a behaviour change. The second describes something an agent cannot do, since it has to read the result to act on it. The fourth is what you wish happened and is not what a model with a plausible plan does.
A test in your suite fails about one run in five for unrelated reasons. What is the agent-specific harm?
The agent has no memory of the flake across runs, so a false failure is indistinguishable from a real one and it acts on it. The second option is a cost, not the harm. The third describes a well-behaved agent that would in fact be safer than the real one. The fourth is false: rerunning is trivially available and does not help, because a pass on the rerun teaches the wrong lesson.

Practice about 25 minutes, with a terminal and a stopwatch

Practice 1working

Measure your repository's clock speed, then buy a faster one.

Time two things: the full gate that decides whether a change is acceptable, and the smallest run that would tell you whether one file you edited is correct. If the second does not exist, that is the finding.

Compute iterations per hour for each, using sixty divided by the minutes, and write both numbers down. Then write the selectable command into your root instruction file, next to the full one, with a sentence saying when each is used.

Hint

The smallest useful run is rarely the default. Look for the runner's own filter: a node id, a path argument, a regex filter, a changed-files flag. Any of them turns a whole-suite command into a selectable one without changing a single test.

Show the arithmetic on a realistic case
  1. Time the full gate. Say it is 12 minutes. Iterations per hour is 60 ÷ 12 = 5.
  2. Time the selectable run. Say one file takes 25 seconds, which is 0.42 minutes. Iterations per hour is 60 ÷ 0.42 = 143.
  3. Take the ratio. 143 ÷ 5 = about 29. Documenting one flag bought a factor of about twenty-nine in tries per hour, and cost nothing at all in test coverage.
  4. Write both down. The instruction file says: use the selectable form while iterating, run the full gate once before handing off. Without that second sentence the agent will use the fast one and stop there.

Sanity check. If your selectable run is not at least ten times faster than the full gate, you have probably measured a run that still boots the whole environment. The fixed setup cost, not the tests, is usually what you are actually timing.

Your teacher. Ask your agent to read your test configuration and report every way the runner can be asked for less than the whole suite: by path, by node id, by pattern, by marker, by changed files. Then ask it which of those is documented anywhere it would have looked. The gap between the two lists is this lesson's work.
