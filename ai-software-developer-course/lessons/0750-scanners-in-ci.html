Module 07 · Security · Lesson 0750

The gate is the pull request, not your laptop

working 9 min Assembled from the three vendors' own published CI configurations. · Semgrep sample CI configs

The one-minute version

  • One workflow, three jobs, one place to read the result. Each job answers its own question and fails for its own reason.
  • Diff-aware scanning is what makes the gate usable: on a pull request the scanner reads the change, not the history of every decision your team ever made.
  • SARIF is the format that puts a finding on a line in the code-hosting interface, and uploading it needs security-events: write.
  • Dependabot is the write side of SCA: it opens the pull request that fixes what the scanner reported, up to a default of five at a time.
  • Push protection is the only control here that prevents rather than reports, and it is the one with a bypass button, which tells you what it costs.

1. One workflow, three jobs, one summary

The shape is unglamorous and it is the whole design. Three independent jobs run on the same event, each reads its own input, and their results converge where a reviewer already looks. Nothing here is clever; what makes it work is that a human opening a pull request sees three named checks rather than one ambiguous red cross.

Here is what one of those vendors publishes for its own job, quoted whole because the comments are half the teaching - note the four separate triggers, and the path filter that re-scans the branch only when the workflow itself changes.

.github/workflows/semgrep.yml · docs.semgrep.dev/semgrep-ci/sample-ci-configs · Semgrep documentation example · quoted with attribution
# Name of this GitHub Actions workflow.
name: Semgrep

on:
  # Scan changed files in PRs (diff-aware scanning):
  pull_request: {}
  # Scan on-demand through GitHub Actions interface:
  workflow_dispatch: {}
  # Scan mainline branches if there are changes to .github/workflows/semgrep.yml:
  push:
    branches:
      - main
      - master
    paths:
      - .github/workflows/semgrep.yml
  # Schedule the CI job (this method uses cron syntax):
  schedule:
    - cron: '20 17 * * *' # Sets Semgrep to scan every day at 17:20 UTC.
    # It is recommended to change the schedule to a random time.

permissions:
  contents: read

jobs:
  semgrep:
    # User definable name of this GitHub Actions job.
    name: semgrep/ci
    # If you are self-hosting, change the following `runs-on` value:
    runs-on: ubuntu-latest

    container:
      # A Docker image with Semgrep installed. Do not change this.
      image: semgrep/semgrep

    # Skip any PR created by dependabot to avoid permission issues:
    if: (github.actor != 'dependabot[bot]')

    steps:
      # Fetch project source with GitHub Actions Checkout. Use either v3 or v4.
      - uses: actions/checkout@v6
      # Run the "semgrep ci" command on the command line of the docker image.
      - run: semgrep ci
        env:
          # Connect to Semgrep AppSec Platform through your SEMGREP_APP_TOKEN.
          # Generate a token from Semgrep AppSec Platform > Settings
          # and add it to your GitHub secrets.
          SEMGREP_APP_TOKEN: ${{ secrets.SEMGREP_APP_TOKEN }}

Two lines in there are decisions rather than boilerplate. permissions: contents: read at the top of the file sets the floor for every job, so a job that needs more has to say so and a reviewer can see which one did. And the if that skips pull requests opened by the dependency bot is a hint about the whole class: a workflow triggered by somebody else's change is a different trust problem from a workflow triggered by yours.

2. Diff-aware scanning is what makes a gate survivable

Run any scanner over a repository older than a year and you get a wall. Semgrep's platform scans "only changes in files when running on a pull request or merge request", which "keeps the scan fast and reduces finding duplication". That single behaviour is the difference between a check people read and a check people re-run until it goes green by luck.

The general form of the idea outlives any one tool: gate on the delta, not the total. Record what the tree already fails, fail the build on anything new, and fail it again when a recorded failure stops happening so the record cannot rot. This repository does exactly that for its own page checker, and the mechanism is worth reading because it is fifty lines rather than a product.

scripts/check_pages_gate.py, the docstring · this repository · content CC BY 4.0, code MIT · reproduced verbatim
It cannot simply be made a gate as it stands, because the hub carries failures
it already reported before anyone was listening. A gate that is red on the day
it lands teaches everyone to ignore it, so the failures that exist today are
recorded in ``scripts/check-pages-baseline.txt`` and the gate is on the
difference:

* a failure that is not in the baseline fails the run - that is a regression,
  and it is caught on the pull request that causes it;
* a failure in the baseline that no longer happens also fails the run, with the
  command to refresh the file - that is how the debt only ever gets smaller.

Apply that to your scanners and the arithmetic of adoption changes. The backlog stops being a reason not to turn the check on, because the check is not about the backlog. It is about whether this branch made things worse.

4. The write side: something has to open the fix

A scanner that only reports leaves every remedy to a human with a queue. Dependency updates are the one class where the fix is mechanical enough to automate, which is what Dependabot is: a bot that opens the pull request the SCA finding implies. Its published default is five open version-update pull requests at a time, and grouping combines several dependencies into one pull request instead of one each.

.github/dependabot.yml · docs.github.com, Dependabot configuration options · GitHub Docs code samples are MIT · reproduced verbatim
# Basic `dependabot.yml` file with
# minimum configuration for two package managers

version: 2
updates:
  # Enable version updates for npm
  - package-ecosystem: "npm"
    # Look for `package.json` and `lock` files in the `root` directory
    directory: "/"
    # Check the npm registry for updates every day (weekdays)
    schedule:
      interval: "daily"

  # Enable version updates for Docker
  - package-ecosystem: "docker"
    # Look for a `Dockerfile` in the `root` directory
    directory: "/"
    # Check for updates once a week
    schedule:
      interval: "weekly"

5. One control here prevents rather than reports

Every job in that workflow tells you about something that already happened. Push protection is different: it "blocks pushes that contain secrets before they reach your repository", across command-line pushes, edits in the web interface, uploads and API requests. When it fires, the developer gets a message explaining the block rather than an alert to triage later.

It also ships with a bypass, and the bypass is the honest part. Anyone with write access can push anyway by choosing a reason - it is a test, it is a false positive, they will fix it later - and organisations can delegate who may do that. Read that as a design statement rather than a weakness: a preventive control with no escape hatch gets turned off, and a bypass with a recorded reason is a control that survives contact with a deadline.

The most dangerous workflow you can write in this module is one that runs untrusted pull-request code with write permissions. A fork's branch is somebody else's code, and a job that checks it out, runs its build, and holds a token that can push or comment has handed that person your token. Keep permissions: contents: read at the file level, add write scopes on the single job that needs them, and never grant them to a job that executes code from the branch under test. This is also why the deny list in lesson 0730 includes Edit(.github/workflows/**): an agent that can edit the gate is an agent that is not gated.

Retrieval practice

Answer from memory before revealing.

Your secrets job reports nothing, though you know a key was committed and later deleted. What is the most likely cause?
A secret scanner reads history, and a default checkout is shallow, which is why the published step sets fetch-depth: 0. Rotation changes whether a finding is verified, not whether the string is found, so the first option would still leave an unverified result. The third describes a real failure mode for the SCA job but this job posts a check result rather than SARIF. The fourth describes diff-aware SAST behaviour applied to the wrong scanner.
A repository has 400 existing findings and your team refuses to turn the scanner on. Which change unblocks it?
Gating on the delta is the mechanism that lets a gate land green on a repository with a real backlog, and the second half - failing when a recorded failure stops happening - is what stops the record rotting. Raising a threshold hides the backlog and the new findings equally, and you never learn which. Moving the scan off the pull request removes the only moment somebody is looking at the change. An advisory check that can never fail is a report, and this whole page is about the difference.

Practice about 30 minutes, with a repository and a branch

Practice 1working

Land the gate on your capstone repository and make all three checks fail on purpose.

Add the workflow above. On a branch, plant three defects at once: a call your own rule from lesson 0710 catches, a dependency with a published advisory, and a credential-shaped string in a new file. Open a pull request.

Record three things: which check failed for which reason, whether the SCA finding appeared on a line in the Security tab, and how long the whole workflow took. Then fix all three and confirm green.

Hint

For the dependency, pin a deliberately old version of something you already depend on and let the scanner tell you whether that version carries an advisory. For the credential, generate a random string in the shape of a key rather than using a real one - an unverified finding is still a finding.

Show what the three failures should look like
  1. The SAST check fails with your rule's message. If it fails with somebody else's rule id instead, your registry configuration is doing the work and you have not yet proved that your own rule runs in CI - point semgrep at your rules directory explicitly.
  2. The SCA check fails and its finding is on a line. If the check is red but the Security tab is empty, the job is missing security-events: write, which is the single most common cause of a finding that exists in the log and nowhere a reviewer looks.
  3. The secrets check fails as unverified, because a random string in the shape of a key cannot be confirmed against any service. That is the correct outcome, and it is a good moment to decide whether your gate should fail on unverified results at all.
  4. Note the wall-clock time. A gate that takes eleven minutes is a gate people push past by merging first, which is a process defect you can only see by measuring it.

Sanity check. Three separate red checks, not one. If you see a single failing job, you have written one job with three steps, and the first failing step will hide the other two - which is the exact ambiguity lesson 0700 warned about.

Your teacher. Ask your agent to read your workflow file and list every job that can write to the repository, and what triggers each one. Then ask it which of those jobs runs code from the branch being tested. If the two lists overlap, you have found the thing to fix before anything else on this page.
