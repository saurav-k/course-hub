Module 01 · The internals of coding agents · Lesson 0160

Build it once and the magic never comes back

foundation 12 min Every block below is part of one file that typechecks under tsc --strict. · How to build an agent

The one-minute version

  • Six stages, 231 lines of TypeScript, one dependency. Nothing here is a simplification of a real agent - it is the same shape at a smaller size.
  • More than half the program is tools. The four definitions are 120 lines and the loop with its shell is 70.
  • You build this to read your own transcript afterwards. Every later module attaches something to it.
  • The one safety decision arrives at stage (e), and it is four lines: refuse any path that leaves the working directory.
Two builds, two purposes Coding Harness Engineering's capstone builds a minimal harness too, and the two pages are deliberately not the same exercise. That one builds in order to compare: its readout is a sixteen-row matrix of how every harness in that course answered the same four questions, and its reader has already read fifteen deep dives. This one builds in order to read your own transcript afterwards: its readout is that the trace on your screen tomorrow stops being opaque. Do that one if you want to understand harness design. Do this one if you want to stop guessing at your own tool.

1. Six stages

The order matters, because each stage adds exactly one idea and every stage runs. Do not write the whole file and then debug it.

Stage (a) - a chat loop, no tools

Start with something that is not an agent, so you can see what the next four stages add. This talks to the model and keeps a history, and nothing else.

src/agent.ts, stage (a) · written for this course, staging follows Ball's article · MIT (this repository) · reproduced verbatim
import Anthropic from "@anthropic-ai/sdk";
import { createInterface } from "node:readline/promises";

const client = new Anthropic();
const messages: Anthropic.MessageParam[] = [];
const rl = createInterface({ input: process.stdin, output: process.stdout, prompt: "you> " });

rl.prompt();
for await (const line of rl) {
  if (!line.trim()) { rl.prompt(); continue; }
  messages.push({ role: "user", content: line });

  const response = await client.messages.create({
    model: "claude-opus-5",
    max_tokens: 4096,
    messages,
  });

  for (const block of response.content) {
    if (block.type === "text") console.log(`\nagent> ${block.text}\n`);
  }
  messages.push({ role: "assistant", content: response.content });
  rl.prompt();
}

Run it and watch the history accumulate. The whole difference between this and a coding agent is the four tool definitions and the inner loop in stage (f).

Stage (b) - the tool contract, and read_file

One interface carries every tool: a schema the model reads and a handler your process runs. The path guard arrives here rather than at stage (e), because three of the four tools take a path.

src/agent.ts, stage (b) · written for this course · MIT (this repository) · reproduced verbatim
type Handler = (input: Record<string, unknown>) => Promise<string>;

interface ToolDef {
  readonly schema: Anthropic.Tool;
  readonly run: Handler;
}

const exec = promisify(execFile);

/** Refuse any path that escapes the working directory. */
function resolveInside(p: string): string {
  const root = process.cwd();
  const abs = path.resolve(root, p);
  if (abs !== root && !abs.startsWith(root + path.sep)) {
    throw new Error(`path escapes the working directory: ${p}`);
  }
  return abs;
}

const readFile: ToolDef = {
  schema: {
    name: "read_file",
    description:
      "Read the contents of a file at a path relative to the working directory. " +
      "Use it before editing a file so the edit is grounded in what is actually there. " +
      "Returns the whole file as UTF-8 text. It cannot read directories: use list_files for that.",
    input_schema: {
      type: "object",
      properties: {
        path: { type: "string", description: "Path relative to the working directory, e.g. src/index.ts" },
      },
      required: ["path"],
    },
  },
  run: async (input) => fs.readFile(resolveInside(String(input.path)), "utf8"),
};

Stage (c) - list_files, and the point about discovery

Discovery is a tool too. Without it the model can only read paths you have already named, which is a very short conversation.

src/agent.ts, stage (c) · written for this course · MIT (this repository) · reproduced verbatim
const listFiles: ToolDef = {
  schema: {
    name: "list_files",
    description:
      "List the files and directories directly inside a path, relative to the working directory. " +
      "Directory names end with a slash. Use it to find a file when you do not know its exact path. " +
      "It does not recurse: call it again on a subdirectory to go deeper.",
    input_schema: {
      type: "object",
      properties: {
        path: { type: "string", description: "Directory relative to the working directory. Defaults to '.'" },
      },
      required: [],
    },
  },
  run: async (input) => {
    const dir = resolveInside(String(input.path ?? "."));
    const entries = await fs.readdir(dir, { withFileTypes: true });
    return entries
      .map((e) => (e.isDirectory() ? `${e.name}/` : e.name))
      .sort()
      .join("\n");
  },
};

required: [] is the teaching point. An optional parameter still needs a description, or the model invents a value for it rather than omitting it.

Stage (d) - edit_file, the first tool that can break something

The two thrown errors are the design, for the reasons lesson 0120 gave. Each one names the next move.

src/agent.ts, stage (d) · written for this course, refusal shape follows opencode's · MIT (this repository) · reproduced verbatim
const editFile: ToolDef = {
  schema: {
    name: "edit_file",
    description:
      "Replace an exact string in a file with another string. " +
      "old_str must appear exactly once in the file, including whitespace, or the edit is refused: " +
      "read the file first and quote enough surrounding lines to make the match unique. " +
      "If the file does not exist and old_str is empty, the file is created with new_str as its contents.",
    input_schema: {
      type: "object",
      properties: {
        path: { type: "string", description: "Path relative to the working directory" },
        old_str: { type: "string", description: "Exact text to replace. Empty string creates a new file." },
        new_str: { type: "string", description: "Text to put in its place" },
      },
      required: ["path", "old_str", "new_str"],
    },
  },
  run: async (input) => {
    const file = resolveInside(String(input.path));
    const oldStr = String(input.old_str);
    const newStr = String(input.new_str);

    if (oldStr === "") {
      await fs.mkdir(path.dirname(file), { recursive: true });
      await fs.writeFile(file, newStr, "utf8");
      return `created ${input.path} (${newStr.length} bytes)`;
    }

    const before = await fs.readFile(file, "utf8");
    const hits = before.split(oldStr).length - 1;
    if (hits === 0) throw new Error("old_str not found in the file");
    if (hits > 1) throw new Error(`old_str appears ${hits} times; quote more context to make it unique`);

    await fs.writeFile(file, before.replace(oldStr, newStr), "utf8");
    return `edited ${input.path}`;
  },
};

Stage (e) - bash, and the first real safety decision

Here the agent gains the ability to do anything the shell can do, and the cwd and the timeout are the only limits in the file. That is not enough for anything unattended, which is the honest note this stage carries.

src/agent.ts, stage (e) · written for this course · MIT (this repository) · reproduced verbatim
const bash: ToolDef = {
  schema: {
    name: "bash",
    description:
      "Run a shell command in the working directory and return its stdout and stderr. " +
      "Use it to run tests, a build, git, or a search. Each call is a fresh shell, so state such as " +
      "`cd` or an exported variable does not carry to the next call: put both steps in one command. " +
      "Commands time out after 60 seconds.",
    input_schema: {
      type: "object",
      properties: {
        command: { type: "string", description: "The shell command to run" },
      },
      required: ["command"],
    },
  },
  run: async (input) => {
    const command = String(input.command);
    const { stdout, stderr } = await exec("bash", ["-lc", command], {
      cwd: process.cwd(),
      timeout: 60_000,
      maxBuffer: 10 * 1024 * 1024,
    });
    return [stdout, stderr].filter(Boolean).join("\n") || "(no output)";
  },
};

const TOOLS: readonly ToolDef[] = [readFile, listFiles, editFile, bash];
const BY_NAME = new Map(TOOLS.map((t) => [t.schema.name, t]));
resolveInside guards the three file tools and guards nothing about bash. A command can name any path on the machine, and cwd only decides where it starts. This agent is safe enough to run against a scratch directory on your own machine and is not safe to run unattended, against a repository you care about, or on anything that can reach a network you care about. Module 7 is where that gap is closed, and it is closed with a sandbox and a permission layer rather than with a better prompt.

Stage (f) - the loop

Twelve lines of control flow plus the error shaping around them. runTool is the whole of the agent's recovery behaviour.

src/agent.ts, stage (f) · written for this course, message shapes verified against the Messages API reference · MIT (this repository) · reproduced verbatim
/** Run one tool and shape the result the API expects, errors included. */
async function runTool(block: Anthropic.ToolUseBlock): Promise<Anthropic.ToolResultBlockParam> {
  const tool = BY_NAME.get(block.name);
  try {
    if (!tool) throw new Error(`no such tool: ${block.name}`);
    const output = await tool.run(block.input as Record<string, unknown>);
    const clipped =
      output.length > MAX_TOOL_OUTPUT
        ? `${output.slice(0, MAX_TOOL_OUTPUT)}\n... truncated at ${MAX_TOOL_OUTPUT} characters; narrow the request`
        : output;
    return { type: "tool_result", tool_use_id: block.id, content: clipped };
  } catch (err) {
    // An error is a normal turn: the model reads it and tries something else.
    return {
      type: "tool_result",
      tool_use_id: block.id,
      content: err instanceof Error ? err.message : String(err),
      is_error: true,
    };
  }
}

// Inside the outer read-a-line loop:
while (true) {
  const response = await client.messages.create({
    model: MODEL,
    max_tokens: MAX_TOKENS,
    system: SYSTEM_PROMPT,
    tools: TOOLS.map((t) => t.schema),
    messages,
  });

  for (const block of response.content) {
    if (block.type === "text") console.log(`\nagent> ${block.text}\n`);
    if (block.type === "tool_use") console.log(`  [${block.name} ${JSON.stringify(block.input)}]`);
  }
  messages.push({ role: "assistant", content: response.content });

  if (response.stop_reason !== "tool_use") break;

  const toolUses = response.content.filter((b): b is Anthropic.ToolUseBlock => b.type === "tool_use");
  const results = await Promise.all(toolUses.map(runTool));
  messages.push({ role: "user", content: results });
}

Those six blocks are the whole file. Two more are needed to run it, and both are shown complete because a fragment teaches nobody to write the file.

2. What the first real run looks like

Install one dependency, export a key, and give it a task in a scratch directory. The shape below is what you should see, and if you do not see it the trace will say why.

This program typechecks clean under tsc --strict and has been run end to end, and the run that produced the trace in lesson 0130 was driven against a local stand-in for the API rather than the live one, because no key was available where it was built. So the loop, the message shapes and the four handlers are verified, and how well Claude chooses among these four tools is not. You are about to be the first person to check the second half, which is the most interesting part of this practice.

3. What it will cost you

Check yourself

Retrieval practice

Answer from memory before revealing.

In this program, which line decides whether the loop runs again?
The break guarded by stop_reason is the only exit from the inner loop, so it is the decision. The second is unconditional and decides nothing. The third runs after the decision has already been made. The fourth is the outer loop, which decides whether there is another task, not another turn.
You delete runTool's catch block. What breaks first?
Without the catch, a thrown error propagates out of the loop and the process exits, so an ordinary ambiguous edit becomes fatal. The first is a real consequence of an unhandled rejection but it is downstream of the same cause and not what a reader notices. The second and fourth name code that lives elsewhere in the function and in the loop respectively.

Practice about 60 minutes, with a terminal and an API key

Practice 1foundation

Build the six stages, in order, running after each one. Do not write the whole file and then debug it: each stage is a program that works.

Stage by stage: get (a) talking, and watch the history accumulate. Add read_file and ask about a file - confirm it calls the tool rather than guessing. Add list_files and ask something that needs discovery first. Add edit_file, then deliberately give it an old_str that appears twice and read the error the model gets back. Add bash and the path guard, then ask it to read a file outside the tree.

Finish by pointing at the single line where the loop decides to stop, and at the single line where a tool failure stops being an exception and becomes a message.

Hint

If a stage will not run, print the request body rather than reading your source. Nearly every first-time failure is one of three things: tool results sent with the wrong role, an assistant turn appended without its tool_use blocks, or a result whose tool_use_id does not match a call.

Show the two lines, and what each stage should have shown you
  1. Stage (a). Ask two questions in a row and confirm the second answer uses the first. If it does not, you are not appending the assistant turn.
  2. Stage (b) and (c). Ask "what is in the config file" without naming a path. A working agent lists first and reads second, and that ordering is a decision it made from two descriptions.
  3. Stage (d). The ambiguous edit must come back with the count and the instruction, and the model's next call should quote more surrounding lines. That recovery is one turn.
  4. Stage (e). The refused path must appear as an ordinary turn and the session must continue. If your process exited, the catch in runTool is missing or the guard is outside it.
  5. The two lines. The loop stops at if (response.stop_reason !== "tool_use") break;. A failure becomes a message at return { ..., is_error: true } in runTool's catch.

Sanity check. The agent should complete "add a test for X and make it pass" without you re-explaining anything mid-task. If it asks you where a file is, the failure is in list_files's description rather than in the model, and lesson 0150 is where the fix is.

Your teacher. When a stage does not work, paste the request body from your log rather than your source, and ask what field is wrong.
