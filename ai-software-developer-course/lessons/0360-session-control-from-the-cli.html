Module 03 · Agent skills and the CLI · Lesson 0360

The one-shot run leaves a session behind, and that is your second turn

working 8 min Claude Code and Gemini CLI from their documentation; Codex read from Rust source at a pinned commit. · Claude Code headless

The one-minute version

  • A -p run creates a resumable session like any other. --continue picks up the most recent one; --resume <id> picks up a named one.
  • Capture the id from the JSON payload and you have a handle: later invocations can run from a different directory and still find it.
  • Four command-line agents answer the same eight questions with different spellings. Learn the questions, look up the spellings.
  • Look them up each time. At the commit read here, Codex has no --full-auto, and the flag is still widely printed.

1. The id is the handle

With --output-format json, the payload carries a session_id beside the result. Pull it out with jq and every later invocation can name that conversation instead of starting a new one.

shell · Claude Code headless documentation · Anthropic documentation, licence unstated · quoted, complete
session_id=$(claude -p "Start a review" --output-format json | jq -r '.session_id')
claude -p "Continue that review" --resume "$session_id"

Those two commands may run from different directories: Claude Code finds a session by its id in any project on the machine. That is a recent behaviour rather than an old one, and it is the difference between a script that must cd and one that need not.

Two related behaviours matter for anything unattended. A -p run persists a session unless you pass --no-session-persistence, so a long-lived script accumulates them. And if a supervisor stops a run with SIGTERM, Claude Code exits 143, leaves the turn unfinished, and continues that same turn when the session is resumed.

2. Permission modes are the session's baseline

A permission mode is a property of the session rather than of a command, and in -p the starting mode is Manual on every plan, whatever your interactive sessions do. So a script that never passes one is running with the strictest baseline, and a script that passes the wrong one is running with the loosest.

ModeWhat runs without askingThe case it is for
default (Manual)Reads onlyThe -p starting mode. Anything else needs an allow rule.
acceptEditsReads, file edits, and common filesystem commandsApplying a mechanical change across files
planReads, plus classifier-approved commands where auto mode is availableExploring before changing anything
autoEverything, with a classifier reviewing instead of youLong interactive tasks; not a CI posture
dontAskOnly pre-approved tools and the read-only command setLocked-down CI. Anything not allowlisted is denied rather than queued.
bypassPermissionsEverythingA container or VM, and nothing else

For an unattended run dontAsk is the interesting one, because its failure mode is a denial you can see rather than a prompt nobody is there to answer.

Gemini CLI also publishes something the others do not: distinct exit codes. 0 is success, 1 a general error or API failure, 42 an input error, and 53 a turn limit exceeded. A wrapper script can tell "you asked wrong" from "it ran out of turns" without parsing anything.

The flags you have seen quoted online may not exist. At commit 728cb12, --full-auto appears in none of Codex's shared_options.rs, exec/src/cli.rs or tui/src/cli.rs, and --ask-for-approval is on the interactive command only, not on codex exec. Both are still widely printed in write-ups. This is not a criticism of Codex; it is the reason every flag on this page names where it was read and at which commit, and the reason a script that hard-codes a flag deserves a comment saying when somebody last checked it.

Check yourself

Retrieval practice

Answer from memory before revealing.

Two scripted agent jobs run on one build machine. Why is --continue the wrong flag?
"Most recent" is a property of the machine, not of your job, so two concurrent jobs race for it. The first describes what happens with no flag at all. The second was true of --resume in older versions and is the strongest distractor because it is a real historical constraint. The fourth is backwards: capturing an id needs JSON, and --continue is the flag that does not.
You are porting a script from Claude Code to codex exec. Which step needs redesign rather than translation?
Codex's --json is newline-delimited events, and its -o writes only the last message to a file, so a caller expecting one object with a result and a session id has to be rewritten rather than re-spelled. The other three are all direct translations: codex resume <id>, --output-schema <FILE>, and --sandbox.

Practice about 25 minutes, with a terminal

Practice 1working

Extend the wrapper script from the previous lesson into two turns: the first invokes your skill and captures the session id, the second resumes that session and asks a follow-up that only makes sense with the first turn's context.

Prove the session is real. Run the second command from a different directory, and make the follow-up something the agent could not answer without the history, such as "which of the files you just listed was the largest".

Then port the first turn to one other CLI you have installed, using the table above rather than your memory, and record which flags translated directly and which did not.

Hint

If the follow-up answers correctly from a fresh session by accident, it was not a good follow-up. Ask about something the first turn produced and nothing on disk records.

Show what a working two-turn script proves
  1. The id is a string in the payload. If jq -r '.session_id' returns null, you asked for text output somewhere; only the JSON format carries it.
  2. The follow-up succeeds from another directory. That is the documented behaviour and it is what lets a CI job do stage two in a different checkout.
  3. The follow-up fails against a fresh session. Run it once without --resume as a control. If it still answers, your test question was answerable from the filesystem and proved nothing.
  4. The port. Print and format translate directly on all four. The two that usually do not are the schema and the exact resume spelling, and you should have hit at least one of them.

Sanity check. The captured id should be the same string in the second run's own JSON output. If it is different, you started a new session and the follow-up answered from general knowledge rather than from history, which reads exactly like success.

Your teacher. Ask your agent to print the --help of whichever CLI you are porting to and to tell you which flags in your script have no counterpart there. That list, rather than the list of matches, is the port.
