Nobody copies a good configuration, so it has to arrive on its own

frontier 9 min Every key, path and cadence here is read from the Claude Code settings and managed-settings references. · Deploy managed settings

The one-minute version

  • Managed settings sit above the command line, project and user levels, and the only documented exceptions let a stricter lower value count.
  • Four delivery mechanisms, and they differ mainly in how long a change takes to arrive: a file on change, a device policy in half an hour, a server policy in an hour.
  • Split the two halves. Settings enforce and a committed memory file guides, and putting a rule in the wrong half is why the rule does not hold.
  • allowManagedPermissionRulesOnly is the line that turns a suggestion into a policy: it drops permission rules from every other source.
  • Ship a workflow rather than describing one. A marketplace entry plus an enabled plugin is a capability that arrives, and a wiki page is not.

1. The ladder, and where it bends

Settings resolve top down through five levels: managed settings, then claude --settings on the command line, then project-local, then shared project, then the user's own file. Managed settings win, and the documentation states the consequence flatly: no user, project, local or --settings value overrides them.

The exceptions are worth knowing precisely, because they are not loopholes. For a handful of security-sensitive keys Claude Code honours a restrictive value from a scope that otherwise could not override managed settings: disableClaudeAiConnectors set to true from any scope, enableArtifact set to false from any scope, isolatePeerMachines set to true, remoteControlAtStartup set to false from a project or local file, and a stricter crossSessionInbound on the accept, hold, refuse ladder. In every case the direction is one way. A team may be stricter than the organisation and never looser.

2. Four ways to deliver it, and they differ in latency

The same keys travel by four routes. Server-managed settings are set in the claude.ai admin console or on a self-hosted gateway, fetched at startup and polled hourly. An MDM or OS-level policy is a macOS configuration profile or a Windows HKLM registry value, read at startup and checked every thirty minutes. A file-based policy is managed-settings.json in a system directory, read at startup and reloaded when the file changes. A Windows HKCU value is the fallback when you cannot write the machine-level key.

The file paths are worth having to hand: /Library/Application Support/ClaudeCode/managed-settings.json on macOS, /etc/claude-code/managed-settings.json on Linux and WSL, and C:\Program Files\ClaudeCode\managed-settings.json on Windows. The legacy Windows path under C:\ProgramData is not read.

Two of these delays are the ones that matter during an incident. Some keys are read only once at session start, and a session left open for weeks lags any rollout regardless of cadence. If your plan for a bad rule is "we will push a fix", write down how long it takes to reach a developer who has had a session open since Tuesday, and whether your answer is "restart everyone".

3. The enforcement half, complete

Here is a real managed settings file from the documentation, with one plausible value for each managed key. It is not a recommended baseline and the documentation says so: it is the shape.

managed-settings.json · code.claude.com/docs/en/settings-example · Anthropic documentation · reproduced verbatim with attribution
{
  "forceLoginMethod": "claudeai",
  "forceLoginOrgUUID": [
    "xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx"
  ],
  "availableModels": [
    "opus",
    "sonnet"
  ],
  "enforceAvailableModels": true,
  "permissions": {
    "deny": [
      "Bash(curl *)",
      "Read(./.env)",
      "Read(./secrets/**)"
    ],
    "disableBypassPermissionsMode": "disable"
  },
  "allowManagedPermissionRulesOnly": true,
  "allowedMcpServers": [
    {
      "serverUrl": "https://api.githubcopilot.com/*"
    }
  ],
  "allowManagedMcpServersOnly": true,
  "strictKnownMarketplaces": [
    {
      "source": "github",
      "repo": "acme-corp/approved-plugins"
    }
  ],
  "sandbox": {
    "enabled": true,
    "failIfUnavailable": true,
    "allowUnsandboxedCommands": false,
    "network": {
      "allowedDomains": [
        "registry.npmjs.org",
        "github.com"
      ],
      "allowManagedDomainsOnly": true
    }
  },
  "requiredMinimumVersion": "2.1.150",
  "cleanupPeriodDays": 7,
  "companyAnnouncements": [
    "Welcome to Acme Corp! Review our code guidelines at docs.example.com"
  ]
}

Three keys in it are the ones that decide whether the rest is a policy or a suggestion. allowManagedPermissionRulesOnly makes managed settings the only source of permission rules, dropping allow rules from user, project and local settings as it reads them. allowManagedMcpServersOnly does the same for the server allowlist, which is why the allowlist pins a URL rather than a name: a developer can call any server github. And requiredMinimumVersion refuses to start an outdated binary, which is how a fleet stops carrying versions that predate a control you rely on.

When several teams own parts of one policy, do not edit one shared file. Put each part in managed-settings.d/ beside it, named with numeric prefixes such as 10-telemetry.json and 20-security.json. The merge rules are documented and worth knowing before you rely on them: single values are replaced by the later file, lists combine with duplicates removed, and nested blocks merge key by key.

4. The guidance half, and why it is a different file

Settings enforce; they do not explain. Everything the agent should know but nothing needs to stop belongs in a memory file committed to the repository, where it is reviewed like code and arrives with the clone. The two halves fail in opposite ways: a convention written as a permission rule blocks work nobody meant to block, and a security rule written as a sentence in a memory file is advice the model may reason past.

That file is also a per-turn cost, which is the module 2 lesson arriving in a new place. The documented guidance is to keep it under 200 lines and to move specialised workflow instructions into skills, which load only when invoked. Tick the sections below and watch the cost of the file move with them.

The last piece is the cheapest and the most often skipped: ship the workflow rather than describing it. A committed project settings file can register a plugin marketplace with extraKnownMarketplaces and switch one on with enabledPlugins, so a formatter or a review workflow arrives with the clone instead of appearing in an onboarding document. The organisation-level counterpart, strictKnownMarketplaces, says plugins may come from that marketplace and nowhere else.

Practice about 25 minutes, on one machine

Practice 1frontier

Deploy a policy to yourself, then prove it holds against your own attempt to undo it.

Write a managed-settings.json for a team of five containing two deny rules that would have stopped a real mistake you have made, one ask rule, and allowManagedPermissionRulesOnly set to true. Place it at the system path for your operating system and confirm it applied.

Then attack it. Add an allow rule to your own user settings that contradicts one of the deny rules, restart, and check which one holds. Record what /status reports as the setting source.

Hint

Writing to the system directory needs elevated permissions, which is the point of the mechanism. Confirm the policy applied before you try to break it: the Setting sources line in /status names the managed source when the file was read, and its absence is a placement problem rather than a policy one.

Show what a good run looks like
  1. Confirm arrival first. If /status does not name a managed source, nothing else you observe means anything. The usual cause is the file being in a user directory rather than the system one.
  2. Test the deny rule the boring way. Ask for the denied read directly. A denial that names your organisation rather than the session is the one that came from the file.
  3. Watch the allow rule vanish. With allowManagedPermissionRulesOnly set, your user allow rule is dropped as the settings are read, so it does not lose an argument at call time. It is never in the resolved set at all.
  4. Now remove that key and repeat. The allow rule reappears and still loses to the deny rule, because denials win from any source. Two different mechanisms produced the same outcome, and knowing which one you are relying on matters when only one of them is deployed.

Sanity check. You should finish able to name, for one rule, both why it held and which key would have to be removed for it to stop holding. If your answer is only "because managed settings win", you have not yet distinguished precedence from the lock, and the difference shows up the first time a project needs an exception.

Your teacher. If the two halves still blur, ask your agent to sort your existing repository rules into "a permission rule could enforce this" and "only a sentence can say this", and to flag any rule in the second pile that you believed was enforced. If the delivery mechanisms feel interchangeable, ask it how each one would behave on a laptop that has been offline for a week.
