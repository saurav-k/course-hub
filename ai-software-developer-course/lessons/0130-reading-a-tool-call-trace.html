Read the trace before you touch the prompt

foundation 9 min Every block below was captured from the agent this module builds. · Handle tool calls

The one-minute version

  • A trace is the messages array over time. It is not a log of your agent, it is the agent's entire memory.
  • It answers three questions in order: what did it know, what did it try, what did it get back. Almost every "why did it do that" is one of those.
  • An error in a trace is a turn, not a crash: is_error: true travels through the same channel as a success and the loop keeps going.
  • In the captured trace below, the fixed part of the request is 92% of the largest thing sent. The whole conversation is the other 8%.

1. One task, five turns

Here is what the terminal printed during a real run of the 231-line agent from lesson 0160. The agent listed a directory, read a file, ran a command, edited the file, and then tried to read a path outside the working directory.

terminal transcript · captured from the agent in lesson 0160, run against a recorded stand-in for the API · MIT (this repository) · reproduced verbatim
Chat with the agent. Ctrl-D to quit.

you>
agent> Let me look at the directory first.

  [list_files {"path":"."}]
  [read_file {"path":"hello.txt"}]
  [bash {"command":"echo built-ok"}]
  [edit_file {"path":"hello.txt","old_str":"world","new_str":"agent"}]
  [read_file {"path":"../../etc/passwd"}]

agent> Done: hello.txt now greets the agent.

The prompt line is empty because the run was driven by a recorded script rather than a person, which is also why it could run with no API key. The file on disk went from hello world to hello agent, so the edit really happened.

What the terminal shows is a summary somebody wrote. What the model saw is a different document, and the difference is the whole skill.

Two facts fall straight out of it. The first assistant turn carries two tool_use blocks and is answered by one user message carrying two results, matched by tool_use_id: parallelism, on the wire. And the last result is a refusal that arrived as an ordinary message with a flag on it.

3. An error is a turn

The refusal above did not stop the run. The path guard in the tool handler threw, the loop caught it, and the exception's message went back as the tool's content with is_error: true. From the model's point of view nothing unusual happened: it asked for something, it got an answer, and the answer said no.

That makes the wording of your errors control flow. Anthropic's guidance is direct about it: "Write instructive error messages. Instead of generic errors like "failed", include what went wrong and what Claude should try next". The refusal above names the path and the boundary, so the model's next move is obvious and costs one turn. A message reading "read failed" costs two or three, because the model has to hypothesise a cause first.

This trace proves the loop, the message shapes and the tool handlers, and it does not prove that Claude picks these tools well. It was captured by pointing the agent at a local stand-in that replays real Messages API response shapes, because no API key was available in the environment where it was built. So the structure on this page is KNOWN and the model's judgement in it is not evidenced. Run the agent in lesson 0160 against the real API and compare, which is the only way to settle the second half.

4. Three questions, in order

When an agent does something you did not expect, work down the trace asking these three. Nearly every case is answered by the first or the third, and almost none by rewriting your prompt.

  1. What did it know? Look at what was in context at the moment it decided. A model that never listed a directory cannot know a file exists, and no amount of instruction will make it.
  2. What did it try? Read the input of each tool_use block, not the prose beside it. The prose is a claim about intent; the input is the intent.
  3. What did it get back? Read the tool_result exactly as the model read it, including the truncation your tool applied. A tool that returned the first 2,000 lines of a 6,000-line file told the model something false by omission.

The habit is worth stating as a rule because the alternative is so tempting: read the trace before you edit the prompt. Editing the prompt changes one of four fields and then re-runs a non-deterministic process, so a run that then succeeds has told you very little.

Check yourself

Retrieval practice

Answer from memory before revealing.

Your agent edited the wrong file. Which part of the trace do you read first?
What it knew comes before what it tried: if a listing or a search returned the wrong file, the edit call was correct given its evidence, and nothing about the edit will tell you that. The third option is the natural instinct and answers a later question. The second is a claim about intent written after the fact. The first is where people go instead of reading the trace, which is the habit this page exists to replace.
A tool_result comes back with is_error: true. What happens to the loop?
is_error is a field on a result, not a stop reason, so the loop's one decision is unaffected and the model gets a turn to react. The first confuses the two mechanisms, which is the most common misreading. The third and fourth are behaviours a harness may add on top, and both are choices you would have to write - neither is what the loop does.

Practice about 20 minutes, with a terminal

Practice 1foundation

Give your usual agent a task in a repository you know, and pick one where you expect it to go slightly wrong: a rename in a codebase with two similarly named things, or a fix in a file that has a near-duplicate.

Capture the trace however your harness allows, then answer the three questions above for the first turn that surprised you, in that order, writing one sentence each.

Then name the smallest change that would have prevented it, and say which of the four request fields it lives in.

Hint

The answer to the last part is almost never "the user message". Work through the other three fields: was the system prompt missing a fact about this repository, was a tool description missing a limit, or had the history already filled with something misleading?

Show a worked example
  1. What did it know? "It had listed src/ but never internal/, so the second definition of the symbol was never in context."
  2. What did it try? "It called edit_file on src/user.go with a three-line quote, which matched once there and would have matched in the other file too."
  3. What did it get back? "Success. Nothing in the result said the change was incomplete, because the tool has no way to know that."
  4. Name the change. A search tool, or a line in the instruction file saying that this repository keeps a second copy of the domain types under internal/. Both live in the fixed part of the request rather than in your sentence, which is the point: the fix is a file you commit once, not a prompt you retype.

Sanity check. If your answer to the last part was a better prompt, look again: a prompt fix that works once and has to be repeated next week is a symptom, and the artefact it is standing in for is what modules 3 and 4 are about.

Your teacher. Ask your agent to show you the raw content blocks of its last three turns rather than its rendered output, and to point out every place where what it printed differs from what it stored. If it cannot show you, ask where its session transcript is written on disk, and open that.
