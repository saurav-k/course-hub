Without a check it can run, "looks done" is the only signal the agent has

working 9 min The four gates and the eight-block cap are Anthropic's, and the arithmetic is this page's. · Give Claude a way to verify its work

The one-minute version

  • Anthropic's own first recommendation is one sentence: "Claude stops when the work looks done. Without a check it can run, 'looks done' is the only signal available."
  • Four gates exist, in ascending cost: ask in the prompt, set a goal condition, write a Stop hook, or send a verification subagent.
  • A Stop hook returns a top-level decision: "block" with a reason, and the reason is what the model is told to act on.
  • It is not a while-true. Claude Code overrides the hook and ends the turn after 8 consecutive blocks.

1. What "done" means to an agent with nothing to run

An agent finishes a turn when it judges the work complete. If nothing in the environment can contradict that judgement, the judgement is the whole verification, and you are the loop: every mistake waits for you to notice it. Give it something that produces a pass or a fail and the loop closes on its own - it does the work, runs the check, reads the result, and iterates.

The gates differ in what they cost to set up and in whether they survive your absence.

GateSetup costWhat it catchesWorks unattended
Ask in the promptNone - one sentenceWhatever you remembered to ask for, this onceNo
A goal conditionOne command per sessionA condition re-checked after every turnWithin the session
A Stop hookA script, committed onceAnything that exits non-zero, every turn, every sessionYes
A verification subagentA definition, plus tokensJudgement a script cannot expressYes, at a price

2. What a Stop hook receives, and what it may say back

A Stop hook runs when the agent has finished responding. Two of its input fields matter on day one. last_assistant_message carries the text of that final response, so a hook can read what the agent claimed without parsing the transcript file. stop_hook_active is true when Claude Code is already continuing as a result of a stop hook, and it is the flag that stops you writing a loop that cannot terminate.

The output shape is different from the PreToolUse one in lesson 0440, and getting it wrong is a hook that does nothing. Stop uses top-level fields:

Stop decision output · code.claude.com/docs/en/hooks · Anthropic documentation · reproduced verbatim, complete
{
  "decision": "block",
  "reason": "Must be provided when Claude is blocked from stopping"
}

There is a softer sibling worth knowing. Returning hookSpecificOutput.additionalContext instead keeps the conversation going through the same loop protections, but the transcript labels it Stop hook feedback rather than a hook error. Use block when the work is genuinely not finished, and additionalContext when your hook is working as designed and simply has something to say.

3. Write one

The gate below runs the suite when the working tree has changed, and blocks the turn with the failing output as its reason. It is written against the documented input and output and it is this course's, not a quotation.

.claude/hooks/tests-must-pass.sh · written for this course, from the documented protocol · complete and runnable
#!/usr/bin/env bash
# .claude/hooks/tests-must-pass.sh - do not let a turn end while the suite is red.
set -euo pipefail

INPUT=$(cat)

# Already continuing because of this hook: say nothing, and let the turn end.
if [ "$(printf '%s' "$INPUT" | jq -r '.stop_hook_active // false')" = "true" ]; then
  exit 0
fi

# Nothing changed in the working tree, so there is nothing to verify.
if git diff --quiet && git diff --cached --quiet; then
  exit 0
fi

if OUTPUT=$(npm test 2>&1); then
  exit 0
fi

REASON=$(printf 'Tests are failing. Fix them before finishing.\n%s' "$OUTPUT" | tail -c 4000)
jq -n --arg reason "$REASON" '{ decision: "block", reason: $reason }'
.claude/settings.json · written for this course, from the documented schema · complete, registers the script above
{
  "hooks": {
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/tests-must-pass.sh",
            "timeout": 600
          }
        ]
      }
    ]
  }
}

Three details are load-bearing. There is no matcher, because Stop is not about a tool. The timeout is generous because the handler runs your whole suite, and a hook that is killed mid-run reports an error rather than a verdict. And the early exit on stop_hook_active follows the documentation's own troubleshooting advice: it means the gate blocks once and then trusts the agent's second attempt, rather than leaning on the cap to break a cycle.

That early exit is a real trade and it should be a decision rather than a copy. Exiting early caps you at one block per turn, so a second failing attempt ends the turn with the suite still red. Leaving it out lets the hook block up to eight times, which is more thorough and is also how a hook that can never be satisfied burns eight full test runs before Claude Code ends the turn anyway. Pick one deliberately, and if you choose the second, raise or lower the ceiling on purpose with CLAUDE_CODE_STOP_HOOK_BLOCK_CAP rather than discovering it.

4. What the gate costs in wall clock

A Stop hook runs your check once per turn, so its cost is the suite's runtime multiplied by how many turns the session takes. That is the everyday number. The worst case is different and is bounded by the documented cap.

  1. Take the ceiling. Claude Code overrides the hook after 8 consecutive blocks, so the most time one turn can lose to a failing gate is eight suite runs.
  2. Multiply by a fast suite. Five seconds a run gives 5 × 8 = 40 seconds, or about 0.7 minutes. Nobody will ever notice it.
  3. Multiply by a slow one. Six minutes a run gives 360 × 8 = 2,880 seconds, which is 48 minutes of a turn spent re-running a suite that keeps failing.

5. The gap the matcher leaves

A PreToolUse hook matched on Edit|Write never sees a file that a Bash command wrote, as lesson 0430's first quiz showed. A Stop hook has no matcher and does not care which tool did what: it scans the state of the working tree once per turn, whatever produced it. That is the coverage argument for putting the compliance-grade check here rather than on the edit tools, and it is why the two hooks in this module are complements rather than alternatives.

Cursor's equivalent event is weaker on purpose and worth seeing beside it: its stop hook returns a followup_message, which is submitted as the next user message, rather than a block that refuses to let the turn end. That is a nudge rather than a gate, and if your verification has to hold, the difference is the whole point.

Check yourself

Retrieval practice

Answer from memory before revealing.

Your Stop hook blocks on a condition that can never be satisfied. What happens?
Claude Code overrides the hook and ends the turn after 8 consecutive blocks, which is a documented safety valve rather than something your script arranges. The first option is the failure the cap exists to prevent. The second would be a reasonable design and is not this one - the hook stays installed and blocks again on the next turn. The third inverts the behaviour, and a gate that is ignored on its first attempt would be worse than no gate.
Which output does a Stop hook use to refuse to let the turn end?
Stop and SubagentStop use top-level decision and reason fields, and the reason is required when the decision is block. The second and fourth options are the PreToolUse shape from lesson 0440, which is the genuine confusion here: two events, two output shapes, and a hook using the wrong one simply has no effect. The third names a real field that belongs to PreToolUse and rewrites a tool's arguments, not a message.

Practice about 25 minutes, with a terminal

Practice 1working

Put a gate on the end of the turn in your capstone repository, and then measure what it costs you.

Install a Stop hook that runs your fastest meaningful check. Break something on purpose and confirm the turn refuses to end, with your reason visible. Time one full session with the gate installed and work out the seconds it added.

Hint

Pick the check by its runtime rather than by its thoroughness for this first one. A three-second type-check that runs on every turn changes behaviour; a nine-minute end-to-end suite gets uninstalled within a week, and an uninstalled gate catches nothing. You can always add a second, slower gate in continuous integration later.

Show the arithmetic on a worked session
  1. Measure the check alone. time npm run typecheck, say, three times. Take the slowest: 6 seconds.
  2. Count the turns. A session of fourteen turns, which you can count from the transcript rather than estimating.
  3. Multiply. 6 × 14 = 84 seconds added across the whole session, or about a minute and a half.
  4. Take the worst case too. 6 × 8 = 48 seconds is the most any single turn can lose to a failing gate, which is the number that tells you whether the cap is something to think about at all.

Sanity check. Your per-session number should be small enough that you would not remove the gate to get it back. If it is more than a couple of minutes, the check is too slow rather than the gate being wrong, and that is a module 5 problem rather than a module 4 one.

Your teacher. Ask your agent to run your Stop hook script directly against a hand-written input object with stop_hook_active set both ways, and to tell you what it printed and what it exited with in each case. That is the fastest way to find out whether your early-exit guard does what you think it does.
