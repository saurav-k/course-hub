Module 10 · The software factory · Lesson 1000

A factory is your delivery loop with a human on exactly one gate

frontier 9 min Built on the published action workflows and one measurement of what agents changed about shipping. · claude-code-action examples · NBER w35275

The one-minute version

  • A software factory is not a new pipeline. It is the loop you already run - issue, branch, pull request, review, merge, deploy, monitor - with an agent walking some of the arcs.
  • Every arc can be automated. Exactly one must not be, and the design question is which. For nearly every team the answer is merge: everything before it is a proposal and everything after it is production.
  • The gate is also the bottleneck, and it is measured. Autonomous agents raised commits by 180% and releases by 30% across more than 100,000 developers.
  • You can enforce the gate in one file: a required status check that counts human approvals and cannot be edited by the pull request it is checking.

1. Draw the loop first, because you already have one

Nothing in a software factory is new machinery. Your team already turns a signal into a change and a change into something running: an issue becomes a branch, the branch becomes a pull request, the pull request is reviewed, merged, deployed, and then watched until the watching produces the next issue. That circuit has existed since before any of this. What agents change is who walks each arc, and nothing else about its shape.

2. One turn of the factory, step by step

Reading the shape is not the same as watching one task travel it. Play the trace below and watch the second readout rather than the prose: the number is machine time, and the arc that costs the most wall-clock contributes nothing to it.

3. Every hop is a different identity

An arc walked by an agent is an arc walked by a credential, and the credentials are not the same one. The workflow's own token, the app the action authenticates as, and the model provider's key are three separate things, and a factory that confuses them fails in a way that looks like a mystery rather than a permissions error.

The failure worth knowing before you meet it is documented and silent: GitHub does not trigger workflows on commits made with the default GITHUB_TOKEN. Hand that token to the action and the agent's pull requests arrive with no CI at all - green because nothing ran, not because anything passed.

4. Make the gate a file, not a norm

A gate that exists because everyone agrees to it is not a gate. The version that holds is a required status check - a workflow that counts human approvals on any pull request carrying agent-authored commits, and fails until it has enough of them.

The workflow below is published as a working example. Two things in it are the whole design and both are in its own comments: it runs from the base branch rather than from the pull request's merge ref, so a pull request cannot edit the check that is judging it; and it identifies agent commits by author, so the rule reaches every agent rather than one product.

.github/workflows/agent-approval-check.yml · anthropics/claude-code-action · MIT · reproduced verbatim
# Require human approvals on PRs that contain agent-authored commits.
#
# Both triggers run the workflow file from the BASE/DEFAULT branch, so a PR
# cannot edit this check to approve itself. (`pull_request_review` is not
# used because it runs from the merge ref, not the default branch; native
# Approve reviews are picked up on the next synchronize or `/approve`
# comment.)
#
# After adding this workflow, mark `agent-approval-check` as a required
# status check on your protected branches.

name: agent-approval-check

on:
  pull_request_target:
    types: [opened, synchronize, reopened, ready_for_review]
  issue_comment:
    types: [created]

permissions:
  contents: read
  pull-requests: write
  statuses: write

jobs:
  check:
    # issue_comment also fires on plain issues; skip those early.
    if: github.event_name != 'issue_comment' || github.event.issue.pull_request
    runs-on: ubuntu-latest
    steps:
      - uses: anthropics/claude-code-action/agent-approval-check@main
        with:
          required_approvals: 2
          agent_emails: noreply@anthropic.com
          agent_logins: claude[bot],claude-code[bot]
          # Uncomment to tune:
          # excluded_approvers: dependabot[bot]
          # exempt_path_prefixes: docs/
          # protected_bases: main,release
The reframing You do not decide how much to automate. You decide where the gate is, and everything on the far side of it is automated by definition.

5. The gate is also where the gains stop

The strongest argument for putting the human at merge is also the strongest argument that merge is your bottleneck, and it is measured rather than asserted. Demirer, Musolff and Yang matched more than 100,000 GitHub developers against their AI usage telemetry and followed the effect down the production chain: each generation of tool raised coding activity more than the last, and each gain shrank as it moved toward something a user could actually run.

A green run in an unattended pipeline means the session started and exited without an infrastructure error. It does not mean the task in the prompt succeeded. Blocked network requests, missing tools and outright task failure all read as green, and the only way to tell is to open the run. Build your factory so that a real check - a test, a linter, a scanner - is what turns the status green, never the fact that the agent finished talking.

6. What the rest of this module adds

Each of the next five lessons repairs one arc of the drawing above. Triggers decide what starts a run when nobody is there, and each kind carries a different trust story. Durable corrections decide whether the agent that got it wrong this morning still gets it wrong tonight. Identity decides how far a compromised run reaches, and it is the only control that survives the model being wrong. Watching decides whether you would know, and gives you a switch that stops everything. The trend lines decide what you should believe about any of it, and they are the reason this module carries evidence rather than a forecast.

None of them changes the shape. All of them change what happens on one arc when you are asleep, which is what a factory means and all it means.

Retrieval practice

Answer from memory before revealing.

Your agent's pull requests arrive with no CI results at all. What is the likeliest cause?
GitHub does not trigger workflows on commits made with the default GITHUB_TOKEN, so a push authenticated that way starts nothing and the pull request looks green because nothing ran. Exhausted minutes would fail loudly with a billing message rather than silently. The reviewer's permissions govern what it may write, not what CI does. A draft pull request suppresses some review automation but does not stop a push-triggered workflow.
What does the NBER measurement of 180 percent more commits and 30 percent more releases argue for?
The paper's own reading is the weak-link hypothesis: task-level gains are capped by the least-improved stage, with an estimated elasticity of substitution of 0.25. The second option is a claim about quality that the study did not measure. The third reverses the finding - releases rose by 30 percent, they did not fall. The fourth rejects the measurement the authors made rather than reading it.

Practice about 30 minutes, with a repository

Practice 1frontier

Take the repository you chose for the capstone and draw its real loop - not the one in the drawing above, the one it actually runs today.

Name, for each of the seven arcs, who walks it right now: a person, a scheduled job, CI, or nobody. Then mark every arc that is already unattended.

Then answer one question in writing: if you put an agent on the branch and pull-request arcs tomorrow, which single step would still be a person, and what enforces that today - a rule in a file, or a habit?

Hint

Look at branch protection settings rather than at your team's agreements. A gate you can describe but cannot point at in a settings page or a workflow file is a habit.

Show what a good answer looks like
  1. Most repositories already run five of the seven arcs unattended. CI, deploy and monitoring are almost always automated already, and issue creation is often automated by an alerting system. That is the useful surprise: you are not building a factory, you are filling in two arcs of one.
  2. The gate is almost never written down. The common answer is "we review each other's pull requests", which is a habit. A rule is a required status check, a protected branch, or a CODEOWNERS file that blocks the merge button.
  3. Write the rule down before the agent arrives. An unenforced gate holds while a person opens every pull request and stops holding on the first day something else does.

Sanity check. If your answer to the last question was "nothing enforces it, we just do it", you have found the one change this module asks for and you have found it in half an hour. If your answer was "the branch is protected and needs two approvals", check whether an agent's own approval would count.

Your teacher. If the seven arcs still feel abstract, ask your agent to read your repository's .github/workflows/ directory and list, for each workflow, what event starts it and what it is allowed to write. Then ask it which arc of the loop that workflow sits on. The disagreements between its answer and yours are the arcs nobody on your team owns.
