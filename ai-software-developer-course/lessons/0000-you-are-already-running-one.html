Module 00 · Start here · Lesson 0000

You have been driving an agent loop for two years without seeing it

foundation 10 min Framed against the loop Anthropic documents for its own API. · How tool use works

The one-minute version

  • You have thousands of hours of driving an agent and no picture of the machine. That gap, not inexperience, is what this course closes.
  • The machine is an agent loop: your program sends a request, the model asks for a tool, your program runs it, the result goes back, and round it goes again.
  • Every lever this course teaches is a file you write or a rule you install on your own machine. None of them is a better sentence in the chat box.
  • You will pick one repository you actually own before module 1 and make it agent-ready across the whole course. Pick it while reading this page.

1. The chat box is not the machine

The story most daily users carry is simple: there is a model, it is clever, you type at it, and if the answer is poor you type better. That story is not wrong about the model. It is wrong about where you are standing.

What actually leaves your machine is one HTTP request carrying four things: a system prompt you did not write, a set of tool definitions you did not write, the conversation so far, and your sentence. Anthropic's own documentation for the loop puts the consequence plainly: "The model never executes anything on its own." It emits a structured request to call a tool; your code executes the operation and sends back a tool_result; and the program you are sitting in front of does that in a loop until the model stops asking.

2. Everything here is something you do at a keyboard

That is the promise the whole course is built on, and it is worth stating as a constraint rather than as a slogan: if a lesson here cannot end with you writing a file, installing a rule, or running a command, it does not belong in this course.

The levers are all ordinary artefacts, and each one enters the loop at a different point. A repository instruction file - AGENTS.md, "a README for agents" - is prepended to the system prompt on every turn, so it is context you pay for continuously. A skill is a folder the agent opens only when your task matches its description, so it is context you pay for once. A hook is a program that runs between the model asking and your machine acting, so it is the only one of the three that can refuse. A permission rule narrows what the tool could have reached in the first place.

3. The ten modules, and why this order

The order is a dependency chain rather than a list. Modules 1 and 2 are the machine and its budget, and everything after them assumes both: you cannot argue about what belongs in a repository contract without knowing it is prepended to every request. Skills come before repository contracts because a skill is one file you write for yourself and a contract is a file a team argues about, and the smaller artefact teaches the mechanism. Agent-readiness comes after both, because "ready" means the files from those two modules exist and their checks pass; review comes after readiness, because review is a check running on the repository you just prepared; security comes after review, because you now have an agent with real reach; and background agents come last of the working modules, because you should not run ten unattended agents before you know where hostile text enters.

4. The capstone: one repository you already own

Pick a repository now, before module 1, and pick a real one: something you have write access to, that you would be annoyed to see broken, and that has at least one test you can run. A toy repository will let every technique in this course succeed, which teaches you nothing about any of them.

You will do four things to it, each landing at the end of the module that supplies it. After module 1 you record a baseline: three tasks, one honest transcript each. After module 4 you write the contract - an instruction file, one skill, one hook that actually blocks something. After module 6 you score it for agent-readiness twice, before and after, and put an AI reviewer on your own pull requests. After module 8 you let one unattended pipeline run against it with a spend ceiling, with module 7's security pass already applied.

The one deliberate discomfort is at the end: that last pipeline runs against a repository that is not yours, which is where module 7 stops being theoretical and the open-source contribution track begins.

5. What this course is not

Four neighbours in this hub already own material that would otherwise leak into these pages. Every one of them is a link rather than a summary, because a second essay on someone else's subject goes stale in a place nobody is watching.

  • How a harness is built inside belongs to Coding Harness Engineering, which takes fifteen of them apart at source level. This course is what you do with one.
  • Running an agent system in production - durable state, evaluation, isolation, cost kill-switches - belongs to Production Agent Engineering.
  • Whether to build it at all, what it costs, and how far the blast radius reaches belongs to The Staff AI Engineer, which owns the prompt-injection argument this course names and does not re-derive.
  • What a language model actually is belongs to LLM Papers, In Order and How Language Models Happened. Nothing here explains attention.

Two things this course owns that no sibling does: what makes a codebase agent-ready, and what an AI reviewer catches and misses. Modules 5 and 6 exist because nothing in this hub covered either.

6. Nothing here is dated, and that is a decision

No page in this course carries a date, a schedule, or an "as of". A version-sensitive claim carries its version in the sentence instead. That looks like fussiness until you watch one number move.

When you send tool definitions, the API adds a system prompt of its own to teach the model to use them, and its size is published per model. On Claude Opus 4.7 that overhead was 675 tokens before your first schema; on Claude Opus 5 it is 286. A page that had baked in the larger figure would have been wrong by a factor of 2.4 within a few releases, and it would not have looked wrong.

The protocol you will meet in module 2 removed its own connection handshake inside this course's lifetime: the 2026-07-28 revision of the Model Context Protocol deletes the initialize exchange and protocol-level sessions outright. Treat every version-sensitive claim in these pages the same way you would treat a pinned dependency: check the version in the sentence against the version you are running, and expect the two to diverge.

Retrieval practice

Answer from memory before revealing.

The model replies asking to read a file. In the loop this course teaches, what happens next?
A tool call is a structured request, and the documentation is explicit that the model never executes anything on its own: your code runs the operation and returns a tool result. The first option describes a server-executed tool, which is a real thing but not what a file read is. The third skips your program entirely, which is the mental model this page exists to replace. The fourth has the loop asking the party that cannot act.
You want your agent to stop before it deletes a directory. Which of these actually stops it?
Only the hook runs between the model asking and your machine acting, so only the hook can refuse. The first two are context: they change what the model is told and therefore what it is likely to do, which is not the same as what it is able to do. The third is context the model may never even read, since nothing guarantees that file enters the request at all.

Practice about 20 minutes, with a terminal

Practice 1foundation

This is the capstone's first move, and doing it now costs you twenty minutes and saves you a module.

Choose one repository you have write access to, that has at least one runnable test, and that you would be annoyed to see broken. Then give your usual agent one small, real task in it - a task you would otherwise have done yourself in half an hour.

Record three things while it works: how many times it read or ran something before it changed a file, whether anything stopped it and asked, and whether it could tell on its own that it had finished correctly. Write the three answers down; you will compare against them at the end of module 8.

Hint

You do not need any tooling for this. Most agents print each tool call as they make it, and the count you want is simply how many appeared before the first edit. For the third question, the test is whether the agent ran something that could have failed.

Show what a good baseline looks like
  1. Count the reads before the first write. A handful means the repository told the agent where things were. Fifteen or twenty means it was searching, and module 5 is about why.
  2. Note every point at which it stopped and asked. Each one is a permission decision somebody already made for you, and module 4 and module 7 are about moving those decisions into files you control.
  3. Ask whether it could check its own work. If it finished by saying it was done rather than by running something that could have failed, its loop never closed. That single observation is most of module 5.

Sanity check. If all three answers were comfortable, the task was too easy or the repository is unusually well prepared. Pick a harder task rather than a different repository: the discomfort is the measurement.

Your teacher. If the loop still feels abstract, ask your agent to print its own tool calls for one small task and then walk you through why it made each one, in order. If the module map felt like a list rather than a chain, ask it to name, for each module, the one thing you would be unable to do if you skipped the module before it.
