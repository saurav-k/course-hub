An instruction asks and a hook decides, and only one of them holds when the model is wrong

working 9 min Counted from the 33 lifecycle events Anthropic's hooks reference documents. · Hooks reference

The one-minute version

  • The documentation draws the line itself: instruction files are context, not enforced configuration, and a PreToolUse hook is what blocks an action regardless of what the model decides.
  • A hook configuration has exactly three levels: an event, a matcher, and a list of handlers.
  • 33 events are documented. You need about six of them, and knowing the cadence of each is what tells you which.
  • Hooks in a project's settings file run in a folder you have never trusted when the session is non-interactive. That is the security fact of this lesson.

1. The sentence that divides the module

Every file in this module so far is delivered as text and is treated as text. The memory documentation says so without softening it: "Claude treats them as context, not enforced configuration. To block an action regardless of what Claude decides, use a PreToolUse hook instead."

That is not a criticism of instruction files. It is the correct description of what they are, and it means that the same rule takes two completely different shapes depending on what you need from it. "Never force push to main" in an instruction file is a strong default that a confused model on a bad turn can walk through. The same rule as a hook is a program on your machine that reads the proposed command and exits before anything happens.

The reframing Ask which failure you are defending against. If the failure is the model not knowing, the answer is a line in a file. If the failure is the model being wrong, no amount of text helps, and you need something that runs.

2. The shape is always the same three levels

Every hooks block in every settings file has the same structure, and reading it as three levels rather than as nested JSON makes it memorable. The event says when. The matcher says which. The handler list says what runs, and it is a list because several handlers may fire on one match.

A matcher is read one of two ways, and the rule is mechanical. A matcher containing only letters, digits, underscores, hyphens, spaces, commas and pipes is an exact-match list: Bash matches the Bash tool and Edit|Write matches those two. Anything containing another character is treated as an unanchored regular expression, which is how mcp__memory__.* reaches every tool on one MCP server, since those tools are named mcp__<server>__<tool>.

3. Thirty-three events, grouped by how often they fire

The reference documents 33 named lifecycle events, which is far more than anybody needs on the first day. Grouping them by cadence is what makes the list tractable, because cadence is what decides the cost of putting a program there.

Six events carry nearly everything a first setup needs. SessionStart and SessionEnd bracket the session. UserPromptSubmit and Stop bracket the turn. PreToolUse and PostToolUse bracket every tool call, and they are the two that this module's remaining pages are built on.

Cursor documents a comparable but smaller surface - 18 agent hooks, 2 tab hooks and one application-lifecycle hook - with different names for the same joints, beforeShellExecution where Claude Code has a PreToolUse matched on Bash. The count is not the interesting difference. Lesson 0440 compares what the two contracts let a hook say, which is where they genuinely diverge.

4. Where a hook lives decides who gets it

Five handler types exist - command, http, mcp_tool, prompt and agent - and the last two are worth naming precisely because they surprise people: a prompt hook sends a single-turn question to a model and reads its decision back as JSON, and an agent hook spawns a subagent with read-only tools to check something before answering. Both put a model back into the decision at a point you chose deliberately, which is a different thing from the model deciding by default.

Location decides distribution. ~/.claude/settings.json is yours on this machine. .claude/settings.json is committed and shared with the team. .claude/settings.local.json is gitignored. Managed policy settings are organisation-wide, and a plugin's hooks/hooks.json travels with the plugin. Skill and subagent frontmatter can carry hooks too, scoped to the life of that skill or that subagent.

A committed settings file is where permissions and hooks appear together, and seeing them in one file is what makes the module's argument concrete: a Never line in your instruction file should also exist as a deny rule, and often as a hook.

.claude/settings.json · code.claude.com/docs/en/settings-example · Anthropic documentation · reproduced verbatim, complete
{
  "permissions": {
    "allow": [
      "Bash(npm run *)"
    ],
    "ask": [
      "Bash(git push *)"
    ],
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)",
      "Read(./secrets/**)"
    ]
  },
  "env": {
    "CLAUDE_CODE_ENABLE_TELEMETRY": "1",
    "OTEL_METRICS_EXPORTER": "otlp",
    "OTEL_EXPORTER_OTLP_PROTOCOL": "grpc",
    "OTEL_EXPORTER_OTLP_ENDPOINT": "http://collector.example.com:4317"
  },
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/block-rm.sh"
          }
        ]
      }
    ]
  },
  "extraKnownMarketplaces": {
    "acme-tools": {
      "source": {
        "source": "github",
        "repo": "acme-corp/claude-plugins"
      }
    }
  },
  "enabledPlugins": {
    "code-formatter@acme-tools": true
  },
  "sandbox": {
    "enabled": true,
    "filesystem": {
      "allowWrite": [
        "/tmp/build"
      ]
    },

        "registry.npmjs.org",
        "*.example.com"
      ]
    }
  },

Two documented asymmetries in that file are worth carrying. Allow rules wait for trust and deny and ask rules do not: allow entries take effect only once each teammate accepts the workspace-trust dialog for that folder, while restrictions apply in every session. And permission lists such as permissions.allow merge across settings layers rather than replacing one another, exactly as the instruction files did in lesson 0420.

The same trust table carries a fact worth reading twice. In a claude -p or SDK session, in a folder you have never trusted, project allow rules are not used - and hooks in that repository's settings files are used. A repository you cloned to look at, driven non-interactively, runs its own hook scripts. That is a deliberate trade so that automation works, and it means a settings file is code review material rather than configuration. Module 7 is where this stops being a footnote.

Check yourself

Retrieval practice

Answer from memory before revealing.

Your matcher is Edit|Write. A Bash command writes to the same file. What fires?
A matcher tests the tool name, and a Bash call is neither Edit nor Write, so your handler never runs. The second option is the wish rather than the mechanism, and it is the gap lesson 0450 closes with a check that scans the working tree instead. The third is a real trap in the other direction: a pipe is one of the characters that keeps a matcher in the exact-match set, so Edit|Write is a list of two names rather than a pattern. The fourth is wrong because PreToolUse fires before every tool call, including this one - it simply found no matching handler.
Which is the honest reason to write a rule as a hook rather than as a line in the file?
Enforcement is the whole difference, and the documentation states it in one sentence. The first option confuses when things load: the file is delivered at session start and a hook is not delivered to the model at all. The second is true as a side effect - a hook costs no window - but it is the small reason, and choosing enforcement for its token saving means you will drop it the moment context is cheap. The third is false, since both are committed files.

Practice about 15 minutes, with a terminal

Practice 1working

Take the three rules you care about most in your capstone repository's instruction file and sort them, with a reason for each.

For every rule ask: is this a fact the agent needs to know, or a rule that must hold whatever it decides? Then, for anything in the second column, write the event and matcher it would need - not the script yet, just the two lines that say when it fires and on what.

Hint

The event follows from the timing. If the rule should stop an action, it is PreToolUse. If it should react to something that already happened, it is PostToolUse. If it should stop the turn from ending, it is Stop, which is lesson 0450. The matcher follows from which tool would do the thing, and if you cannot name one tool, that is a finding rather than a failure.

Show a worked sort
  1. "Run the linter before committing." A rule that must hold, and the action to intercept is a Bash git commit. Event PreToolUse, matcher Bash. The command-shape test goes inside the script, because a matcher tests the tool name and not the command.
  2. "Never edit the generated API client." A rule that must hold, and the tools are the editing ones. Event PreToolUse, matcher Edit|Write. Note the gap the quiz named: a Bash sed writing the same file is not covered by this matcher.
  3. "Handlers live under src/api/." A fact, and one that would be checked at review time rather than at action time. It stays text, and it belongs in a path-scoped rule rather than in the root file.

Sanity check. If all three of your rules turned out to be facts, look again at whether any of them has ever actually been broken; if none has, your file may be describing the repository rather than constraining it. If all three turned out to need hooks, you have probably classified a preference as a requirement, and the first time the hook blocks something reasonable you will delete it.

Your teacher. Ask your agent to list the hooks currently configured for the repository you are in, where each one is defined, and which event and matcher it uses - /hooks is the menu that shows this. Then ask it which of your instruction file's rules could be expressed as one of them, and argue with the answers you disagree with.
