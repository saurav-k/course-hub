Put the expensive decision before the expensive tokens

foundation 9 min The name has one public origin, and this page says so before it teaches the loop. · Mihail Eric, RePPIT

The one-minute version

  • The failure this answers is the one you have watched: the agent starts editing before anybody has decided what to build.
  • Five moves - Research, Propose, Plan, Implement, Test - and the whole design is that the human choice happens between the second and the third.
  • Each move leaves an artefact you can read. A 100-to-300-line map of the code, two approaches with trade-offs, a design document, a diff, a review.
  • The first three moves can be enforced by the harness rather than by your discipline. Plan mode is exactly that, and the agent physically cannot edit while it is in one.

1. Where the name comes from, before anything else

RePPIT is a named framework with a public write-up and a single author: Mihail Eric's article, which expands it as "Research the codebase, Propose solutions, Plan the chosen one, Implement it, Test it". It is not an industry standard, it is not a coinage of this course, and searching for it turns up that article, two repositories that use the name, and a newsletter referring back to the same piece. You should know that before you take the loop into a team, because the loop is worth defending on its mechanics and the name is not evidence of anything.

The article's headline claim is that "shipping 2-3X faster on generating production-quality code is realistic". That is a vendor-style claim with no method shown: no benchmark, no case study, no metric, no sample size. Quote it as its author's claim if you quote it at all, and do not repeat it as a finding. What would make it evidence is the ordinary thing - a task set, a control arm without the loop, and the measurement rule stated before the runs.

2. The five moves and the artefact each one leaves

Play the loop through once. The rule that makes it work is that every move ends in something written down, so the next move starts from a document rather than from whatever survived in the window.

3. The gate is the design

Every part of this loop except one is something an agent can do unattended. The Propose-to-Plan boundary is where a person is worth the interruption, and the reason is about what you are choosing between rather than about caution.

Review a finished 400-line change and you are arguing against work that already exists, which is a bad position: the sunk cost is real, the alternative is hypothetical, and the reviewer's honest verdict is usually "fine, I suppose". Choose between two written approaches and neither of them has cost anything yet. That is the same asymmetry a design review has always had, and the loop is a way of getting it back from an agent that would otherwise go straight to a diff.

4. Let the harness enforce it, not your discipline

Doing this by hand works and it degrades, because on the fourth task of the day you will type "just fix it" and the loop is gone. A harness can hold the boundary for you. Claude Code ships six permission modes, and one of them is exactly the first half of this loop: in plan, "Claude reads files and runs read-only shell commands to explore but doesn't edit your source files".

The teaching point is not that this product has a mode. It is that the Research and Propose moves are a permission posture, and any harness that can express "read but do not write" can hold them. That is why the plan an agent produces in such a mode is worth reading: it was written by something that could not quietly start the work instead. Permission postures, in Coding Harness Engineering, compares how fifteen harnesses express the same idea.

Check yourself

Retrieval practice

Answer from memory before revealing.

Why does the human gate sit between Propose and Plan rather than after Implement?
The gate exists so the person is choosing between two written options rather than approving one finished change, which is the asymmetry the whole loop is built around. The first option is true and is not the reason - a plan being shorter would not help if there were only ever one of them. The second is a claim about capability the loop does not make, and the fourth is false: a plan names its test strategy.
What does running the Plan move inside a read-only permission mode actually buy you?
The mode is a permission posture, so its one guarantee is that no source file was edited while the plan was being written. The second and fourth describe things a slash command or a skill could do and the mode does not. The third would need the change to exist, which is precisely what the mode prevents.

Practice about 40 minutes, in a real repository

Practice 1foundation

Pick a small real change in your capstone repository - one that would take you an hour by hand and that you have not already designed in your head.

Run the loop as four prompts, saving each artefact as a file in the repository: the research map, the two proposals, the plan for the one you chose, and the implementation. Then run the Plan move a second time in a read-only permission mode and diff the two plans.

Write one sentence saying where the enforced read-only exploration changed what the agent proposed, or saying honestly that it did not.

Hint

Ask for two approaches that differ in a way you can name, not two that differ in wording. "One that changes the schema and one that does not" is a real fork; "a simple version and a thorough version" is the same plan twice.

Show what a good pass looks like
  1. Research first, and read what comes back. If the map is confidently wrong about your own code, that is the finding, and it is module 5's subject rather than this loop's failure.
  2. Force the fork. Reject a proposal pair whose two halves would produce the same diff. Two approaches that cannot both be right is the bar.
  3. Choose out loud, in the plan prompt. Name the option and the reason in one sentence, so the plan carries your reasoning rather than only your verdict.
  4. Keep the implement prompt to one sentence. If you cannot, the plan is missing something, and adding it to the plan beats adding it to the prompt.
  5. Diff the two plans. Look for content rather than wording: a file the unconstrained run did not mention, or a step it skipped because it had already half-built it.

Sanity check. Four artefacts, and the implement prompt fits on one line. If your two plans are word-for-word identical, either the task was too small for the fork to matter or the read-only run was not actually read-only, and the second is worth checking before you conclude the first.

Your teacher. If the loop feels like ceremony, ask your agent to do the same task twice - once straight from a sentence, once through the five moves - and to diff the two results for you. If the two proposals keep coming back as the same idea in different words, ask it to name the one decision the two approaches disagree about, and to rewrite them so that decision is the only difference.
