Module 10 · The software factory · Lesson 1030

An agent is a principal, and its own credential is what contains it

frontier 10 min One published security framework, one published federation workflow, and the offboarding test that checks both. · Securing an AI-native SDLC · Action authentication

The one-minute version

  • The rule fits in one sentence, and it is somebody's published operating principle rather than this course's opinion: give every agent a single-purpose identity with the minimum permissions for its job.
  • The separation that matters most is between proposing and deploying. An agent that can investigate, write and even draft the fix still must not be the thing that ships it.
  • A long-lived key in a repository is avoidable. Workload identity federation exchanges the workflow's own short-lived token for provider access, so there is no secret to steal and none to rotate.
  • The test of the whole design is offboarding: revoke exactly one credential and name everything that stops. If more stops than you expected, the identities were never separate.

1. One job per agent, and the job names the permissions

The temptation with an unattended pipeline is one powerful identity that can do everything, because it is one thing to configure and one thing to debug. It is also one thing to compromise, and the whole of its reach becomes the blast radius of any single failure - a prompt injection, a bad merge, a stolen token.

The alternative is boring and it works: a role per agent, and each role's permissions derived from what that role actually does. Below is the split most teams end up with, and the last row is the one people argue about.

RoleWhat it doesMust be able toMust not be able to
Reviewercomments on pull requestsread code, write commentswrite code, push a branch
Triagerlabels and routes new issuesread code, write labelstouch any branch
Fixeropens pull requests from issuespush to one branch prefix, open pull requestspush to a protected branch, merge
Deployernothing - there is no deployer agent-exist

The published framework this page draws on makes the same cut with a worked example. Its incident-response agent can write new docs, post in company channels, and read production logs, and it can draft a code fix. It cannot deploy one; deployment goes through a separate reviewer arrangement. The account also records what happened when that boundary was tested from the inside: the incident agent asked another agent to deploy a fix on its behalf, and "this was caught at a human review gate as designed". Two things made that visible - the gate, and the fact that agent-to-agent conversation happens in a channel people can read rather than over a private API call.

2. You are usually granted more than the job needs

A GitHub App has one permission set covering all of its features, and installation is all-or-nothing: the platform does not let you accept a subset. The shared Claude app is used by several products, so its set is the union of what all of them need.

The action itself relies on three of those permissions - Contents, Issues and Pull requests. The other eight are granted because another feature of the same app needs them.

3. The best-kept secret is the one that does not exist

A provider key stored as a repository secret is a long-lived credential sitting where a great many people and a great many workflows can reach it. Workload identity federation removes it: the workflow asks GitHub for a short-lived OpenID Connect token naming itself, and that token is exchanged through a federation rule for access as one service account.

.github/workflows/claude-wif.yml · anthropics/claude-code-action · MIT · reproduced verbatim
name: Claude Code (Workload Identity Federation)

# Authenticates to the Claude API by exchanging the workflow's GitHub OIDC
# token for a short-lived access token - no ANTHROPIC_API_KEY secret needed.
# One-time Console setup (issuer, service account, federation rule):
# https://platform.claude.com/docs/en/manage-claude/workload-identity-federation
# See also docs/setup.md#workload-identity-federation in this repository.

on:
  issue_comment:
    types: [created]
  pull_request_review_comment:
    types: [created]
  issues:
    types: [opened, assigned]
  pull_request_review:
    types: [submitted]

jobs:
  claude:
    if: |
      (github.event_name == 'issue_comment' && contains(github.event.comment.body, '@claude')) ||
      (github.event_name == 'pull_request_review_comment' && contains(github.event.comment.body, '@claude')) ||
      (github.event_name == 'pull_request_review' && contains(github.event.review.body, '@claude')) ||
      (github.event_name == 'issues' && (contains(github.event.issue.body, '@claude') || contains(github.event.issue.title, '@claude')))
    runs-on: ubuntu-latest
    permissions:
      contents: write
      pull-requests: write
      issues: write
      id-token: write # Required: used to fetch the GitHub OIDC token for the federation exchange
      actions: read # Required for Claude to read CI results on PRs
    steps:
      - name: Checkout repository
        uses: actions/checkout@v6
        with:
          fetch-depth: 1

      - name: Run Claude Code
        id: claude
        uses: anthropics/claude-code-action@v1
        with:
          # These values are identifiers, not secrets - they can live directly
          # in the workflow file or in repository variables.
          anthropic_federation_rule_id: fdrl_xxxxxxxxxxxx
          anthropic_organization_id: 00000000-0000-0000-0000-000000000000
          anthropic_service_account_id: svac_xxxxxxxxxxxx

          # Optional: only needed when the federation rule targets more than
          # one workspace.
          # anthropic_workspace_id: wrkspc_xxxxxxxxxxxx

          # Optional: audience requested on the GitHub OIDC token. Defaults to
          # https://api.anthropic.com - only set this if your federation rule
          # expects a different audience.
          # anthropic_oidc_audience: https://example.com/custom-audience

Note the one permission that is not optional: id-token: write, which is what lets the workflow request its own OIDC token. It is needed for the federation exchange even when you supply your own GitHub token.

4. Credentials the agent should never see at all

Scoping the agent's own key is half the job. The other half is the keys already sitting on the machine it runs on - a cloud credentials file, an SSH directory, a registry token in the environment.

Two modes are documented and they answer different questions. deny removes the thing: a file path is blocked for reads inside the sandbox, an environment variable is unset before each sandboxed command runs. That is the right answer when nothing the agent does needs it, and the wrong one when a tool it must run authenticates with it. mask is the answer for that case: the command sees a per-session placeholder, and the proxy substitutes the real value only on outbound requests to hosts you named in injectHosts. The command, and anything it logs, never holds the real credential, and its requests still authenticate.

settings.json · composed for this course from the documented sandbox keys at code.claude.com/docs/en/sandboxing
{
  "sandbox": {
    "enabled": true,
    "failIfUnavailable": true,
    "allowUnsandboxedCommands": false,
    "network": {
      "tlsTerminate": {},
      "allowedDomains": ["*.github.com", "registry.npmjs.org"]
    },
    "credentials": {
      "files": [
        { "path": "~/.aws/credentials", "mode": "deny" },
        { "path": "~/.ssh", "mode": "deny" }
      ],
      "envVars": [
        { "name": "GH_TOKEN", "mode": "mask", "injectHosts": ["api.github.com"] },
        { "name": "NPM_TOKEN", "mode": "mask" }
      ]
    }
  }
}

Three details in that file are the difference between a policy and a wish. failIfUnavailable makes a sandbox that cannot start a hard failure rather than a warning followed by an unsandboxed run. allowUnsandboxedCommands: false removes the escape hatch that lets a failing command retry outside the sandbox. And tlsTerminate is required by masking, because a proxy can only substitute a credential inside a request it can read.

5. Write the whole arrangement down in one file

Every control above lives somewhere different - a GitHub App, a workflow file, a settings file, a branch protection rule. Nobody can hold that in their head, and an arrangement nobody can read is an arrangement nobody reviews.

So write it down. The file below is a course artefact: no tool reads it, and that is deliberate. Its job is to be one reviewable page where each field names a control that genuinely exists somewhere else, so a reviewer can check the file against the system rather than against their memory of it.

.agents/policy.yaml · authored for this course · every field names a control documented elsewhere · no tool reads this file
# .agents/policy.yaml - one entry per agent principal in this repository.
# Read by people. Each field points at a control that exists somewhere real,
# named in the comment beside it.
version: 1

agents:
  - name: reviewer
    purpose: Comment on pull requests. Never change code.
    identity:
      kind: github-app                 # a custom app, so the permission set is ours
      app: acme-claude-reviewer
      permissions: { contents: read, pull_requests: write, issues: read }
      credential: oidc-federation      # no long-lived secret in this repository
    tools:
      allow: ["mcp__github_inline_comment__create_inline_comment"]
      deny:  ["Bash", "Write", "Edit"] # enforced by --allowedTools in claude_args
    escalation: none
    audit: { sink: siem, sample_rate: 0.05 }

  - name: fixer
    purpose: Open pull requests from labelled issues. Never merge one.
    identity:
      kind: github-app
      app: acme-claude-fixer
      permissions: { contents: write, pull_requests: write, issues: read }
      credential: oidc-federation
      branch_prefix: claude/           # may push nowhere else
    tools:
      allow: ["Bash(npm test:*)", "Edit", "Write", "mcp__github__create_pull_request"]
      deny:  ["Bash(git push:*)", "Bash(curl:*)"]
    sandbox:                           # keys from the documented sandbox settings
      network: { allowedDomains: ["registry.npmjs.org", "*.github.com"] }
      credentials:
        files:
          - { path: "~/.aws/credentials", mode: deny }
          - { path: "~/.ssh", mode: deny }
    escalation: human-merge-required   # enforced by agent-approval-check
    audit: { sink: siem, sample_rate: 0.20 }

  - name: deployer
    purpose: There is no deployer agent. Deployment is a human action.
    identity: none

kill_switches:
  - { scope: repository,   action: "delete .github/workflows/claude*.yml" }
  - { scope: organisation, action: "turn off the Routines toggle in admin settings" }
  - { scope: machine,      action: "CLAUDE_CODE_DISABLE_CRON=1" }
  - { scope: credential,   action: "revoke the federation rule" }
The reframing A new agent does not start with the permissions its job needs. It starts in shadow mode - proposing, commenting, and changing nothing - and earns more only once its record justifies it. The published framework adds a second step worth copying: red-team the new reviewer by trying to slip a malicious change past it before you widen anything.

6. The test is offboarding, and you can run it this week

Every claim on this page reduces to one check you can perform without a security team. Revoke exactly one credential and write down what stops.

Least privilege applied to the model provider is not least privilege applied to the connectors. A cloud run can use every tool an included connector exposes, writes included, without asking permission during the run, and the connectors attached by default are all the ones on your account. So the reviewer agent with no repository write permission can still be holding a chat connector that posts as you, and a ticket connector that closes issues. Remove the connectors a routine does not need at the moment you create it, because nothing later will ask you to.

Check yourself

Retrieval practice

Answer from memory before revealing.

A build tool inside the sandbox needs a registry token to authenticate. Which setting keeps it working without exposing the token?
Masking shows the command a per-session placeholder and lets the proxy substitute the real value on requests to the named host, so the tool authenticates and nothing it logs holds the secret. A deny entry unsets the variable, which protects it and breaks the tool - the documentation names exactly that trade-off. The allowlist decides which hosts are reachable, not what is sent to them. A permission rule decides whether the command runs at all.
Why does the published framework put agent-to-agent messages in a team chat channel?
The account records an incident agent asking another agent to deploy a fix, and that request being caught at a human review gate. A visible channel is what made an unusual request reviewable rather than invisible. The second option is a capability claim the source does not make. The third is a real benefit but not the reason given. The fourth is not a claim anybody makes.

Practice about 30 minutes, with a repository you administer

Practice 1frontier

Write .agents/policy.yaml for your own repository, with exactly two agents: a reviewer that cannot write code, and a fixer that can push only to one branch prefix.

Then run the offboarding test. Revoke or disable the reviewer's credential only. Trigger both agents. Write down what happened to each.

Then flip one kill switch from the list at the foot of your policy file, and confirm that both stop.

Hint

If you cannot revoke one without the other, you have found the answer without needing to run the test. Two agents sharing one secret are one agent, and the policy file you just wrote is fiction until they are separated.

Show what each outcome means
  1. Reviewer stops, fixer keeps running. The identities are genuinely separate. This is the outcome the file claims, and now you have seen it rather than asserted it.
  2. Both stop. They share a credential. The names in the file are labels on one principal, and every blast-radius claim you make about the reviewer is actually a claim about the fixer's permissions.
  3. Neither stops. Something else is authenticating - a cached token, an organisation secret, or a connector attached to the account rather than to the agent. Find it before you write anything else down.
  4. The kill switch left something running. The list at the foot of your policy file is wrong, which is more useful to discover now than during an incident.

Sanity check. A correct run produces exactly one broken agent and one working one, and takes under half an hour. If it took longer, the time went into finding out where a credential actually lives, which is the finding rather than the delay.

Your teacher. Ask your agent to read every workflow file in your repository and list, per workflow, the identity it authenticates as and the permissions that identity holds. Then ask it which two workflows would both stop if one secret were revoked. That list is your real identity map, whatever the policy file says.
