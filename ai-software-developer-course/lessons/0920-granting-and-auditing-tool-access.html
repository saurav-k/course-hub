A grant is a file somebody reviewed, and an audit is a log of single calls

frontier 8 min Every key shown is documented in the Claude Code MCP and managed-settings references. · MCP in Claude Code

The one-minute version

  • A project .mcp.json is a proposal. Managed settings are the decision, and nothing a developer writes overrides them.
  • Control comes at two grains: whole servers by name or URL, and single tools set to blocked or ask.
  • blocked is stronger than a refusal: the tool is filtered out before Claude sees it, so it costs nothing and is never planned against.
  • One string names a tool everywhere - mcp__server__tool - in permission rules, skill allow-lists, subagent tool lists and hook matchers.
  • The audit is per call: time, status, server, capability, duration. The honest limit is that a hidden tool is not an unreachable server.

1. A proposal, and a decision

A repository can ship an MCP server configuration, and it should: a project .mcp.json is how a team says "this server is part of working here". Every field in it is documented, and three of them are the ones that make it safe to commit.

.mcp.json · code.claude.com/docs/en/mcp · Anthropic documentation · reproduced verbatim with attribution
{
  "mcpServers": {
    "api-server": {
      "type": "http",
      "url": "${API_BASE_URL:-https://api.example.com}/mcp",
      "headers": {
        "Authorization": "Bearer ${API_KEY}"
      },
      "oauth": {
        "scopes": "channels:read chat:write search:read"
      }
    },
    "internal-api": {
      "type": "http",
      "url": "https://mcp.internal.example.com",
      "headersHelper": "/opt/bin/get-mcp-auth-headers.sh"
    }
  }
}

${VAR} and ${VAR:-default} expansion is what lets the file be committed without a secret in it. headersHelper goes further and names a program that prints the headers, so a rotating credential never lands in the file at all. And oauth.scopes is scope minimisation moved to the client: the server may be willing to grant more, and this line says what your agent is allowed to ask for. That is the same least-privilege discipline the previous page's step-up flow assumes.

What the file cannot do is bind anybody. It sits in the repository, at a scope a developer can edit, and a developer who wants a different server writes one. The decision lives one level up, in the managed settings your organisation deploys, where two lists answer the question of which servers may load at all.

2. Tool grain, and the string that names a tool

Denying a whole server is blunt: most servers carry one destructive tool and a dozen harmless ones. The tool-level control is a small block with two verbs.

managed-settings.json · code.claude.com/docs/en/mcp · Anthropic documentation · reproduced verbatim with attribution
{
  "mcpConnectorToolControls": {
    "claude.ai Slack": {
      "tools": {
        "send_message": "blocked",
        "read_channel": "ask"
      }
    }
  }
}

The two verbs do genuinely different things. blocked filters the tool out before Claude sees it. ask leaves it in place and prompts on every call, with the reason shown as "Your organization requires approval for this tool". So ask is a speed bump for a tool you want used carefully, and blocked is for a tool you do not want planned around.

Elsewhere, a tool is named by one string: mcp__<server-name>__<tool-name>, and for a server a plugin brought with it, mcp__plugin_<plugin-name>_<server-name>__<tool-name>. The same string is used in permission rules, in a skill's allowed-tools, in a subagent's tools field and in hook matchers, which is why getting server names consistent across a fleet is a governance decision rather than a naming preference. A team whose servers are called github on some machines and gh on others cannot write one policy about them.

None of the five rows stops a determined developer who can reach the server directly and has a token for it. A tool policy is a control over your agent's behaviour, not over your network. If the tool would be dangerous in a shell as well as in an agent, the control belongs at the server or at the identity provider, and this file is a convenience on top of it.

3. The policy is also a context budget

Because blocked removes a tool from the list rather than refusing it later, a tool policy and a context budget are the same decision written once. Cloudflare's published pair gives the exchange rate: 52 tool definitions cost roughly 9,400 tokens, which is about 181 tokens for one definition. Every tool you take out of a persona's catalogue is that much off every turn they take.

4. The audit is a log of single calls

A grant you cannot check is a hope. The unit that makes an audit useful is not the session and not the server: it is the individual tool call. Cloudflare's portal logs record time, status, server name, capability - which is the tool that ran - and duration in milliseconds, and those five fields are enough to answer the questions a review actually asks. Which people called the deploy tool this month. Which calls failed, and did anybody notice. Which server accounts for the tail of slow turns.

On the client side the equivalent surface is OpenTelemetry, which the next two lessons use for cost. It is worth knowing now that the two are different evidence: the portal log proves what reached the server, and the client telemetry proves what your fleet did. A gap between them is not a discrepancy to reconcile, it is the shape of everything that went around the door.

Practice about 20 minutes, in a repository you own

Practice 1frontier

Turn one server you already use into something a reviewer could sign off.

Write a project .mcp.json for it with no literal secret in the file, using expansion or a headers helper, and an oauth.scopes line naming the narrowest set of scopes that still lets your usual task finish.

Then write the managed-settings half: an allowedMcpServers entry for that server, and an mcpConnectorToolControls block setting its most destructive tool to blocked.

Finally, run your usual task and record what broke. Something usually does, and what broke tells you which scope or which tool was load-bearing.

Hint

Start from the scopes the server asked for on first connection, then remove one at a time. The tool to block is the one whose name you would not want to read out at an incident review.

Show a worked example
  1. Start too narrow on purpose. Ask for channels:read alone. The first search fails, and the failure names the scope it wanted, which is faster than reading the server's documentation.
  2. Widen once. Add exactly the challenged scope to the set you already had. That is the union rule from lesson 0910, applied by hand rather than by the client.
  3. Block, then measure. Block the write tool and run /context again. The definitions figure should fall by roughly 180 tokens for each tool removed, which is the rate the chart above fixes.
  4. Check the file is publishable. Search the finished .mcp.json for anything that looks like a key. If your answer is "the helper prints it", the file is ready to commit.

Sanity check. If nothing at all broke when you narrowed the scopes, you have not narrowed them: the server was probably granting a fixed set and ignoring your request, which is a finding worth writing down rather than a pass.

Your teacher. If the difference between the two grains still blurs, ask your agent to list every MCP tool it can currently see and mark each one as "would be fine in a transcript" or not. If the audit half feels theoretical, ask it to write the query you would run against your call log to answer "who used the deploy tool last month", and notice whether you have anywhere to run it.
