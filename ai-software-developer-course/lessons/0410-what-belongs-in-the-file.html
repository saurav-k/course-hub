Module 04 · Customizing your agent · Lesson 0410

The instruction file is a budget, and a bloated one buries the rule you cared about

working 9 min Measured against six real instruction files, including this repository's own. · Claude Code best practices

The one-minute version

  • The file is loaded at the start of every session and consumes tokens alongside your conversation, so length is a running cost rather than a one-off.
  • The documented target is under 200 lines per file, and the stated consequence of missing it is not an error but reduced adherence.
  • The test for each line is one question: would removing this cause a mistake? If not, cut it.
  • What survives the test is not always a line. A procedure becomes a skill, a subtree rule becomes a path-scoped rule, and a rule that must hold becomes a hook.

1. Every line is charged on every turn

An instruction file is not read when it becomes relevant. It is delivered as a user message after the system prompt at the start of the session, and it stays in the window for the whole conversation. A hundred lines you added for one awkward migration are still being paid for six weeks later on a task that has nothing to do with them.

The documentation states the target and its reason in one sentence: "target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence." Read the second half carefully, because it is the surprising part. Over-length is not rejected and does not warn. It quietly makes the agent worse at following the file, which is a failure you will attribute to the model.

The reframing A long instruction file does not fail loudly, it dilutes. The best-practices page names the pattern outright: "If your CLAUDE.md is too long, Claude ignores half of it because important rules get lost in the noise." Every line you add makes every other line a little less likely to be followed.

2. The test for one line, and the table behind it

Anthropic's best-practices page gives the test in nine words: "For each line, ask: 'Would removing this cause Claude to make mistakes?' If not, cut it." It also publishes the include and exclude columns, and they are the most useful single artefact in this module. Reproduced here as published:

IncludeExclude
Bash commands Claude can't guessAnything Claude can figure out by reading code
Code style rules that differ from defaultsStandard language conventions Claude already knows
Testing instructions and preferred test runnersDetailed API documentation (link to docs instead)
Repository etiquette (branch naming, PR conventions)Information that changes frequently
Architectural decisions specific to your projectLong explanations or tutorials
Developer environment quirks (required env vars)File-by-file descriptions of the codebase
Common gotchas or non-obvious behaviorsSelf-evident practices like "write clean code"

One rule sits underneath the whole table and it is about emphasis rather than content: "If you emphasize many lines, none of them stands out." A file where every third bullet is marked IMPORTANT has no important lines left in it.

3. What the files people actually ship look like

Five open repositories and this one, measured with wc -l against the checkouts named in the caption. Two of the six clear the target, and one of the two over it by the widest margin is the repository you are reading.

4. The honest counter-example is this repository

The tallest bar is the file governing the pull request that adds this page. This repository's root AGENTS.md runs to 787 lines and 62,412 bytes, which is 3.9 times the documented target, and its content is CC BY 4.0 so it can be quoted rather than described. Two things follow, and neither is that the guidance is wrong.

The first is that the cost is real and visible. Roughly 15,600 tokens of estimated context arrive before your first sentence in every session in this repository, on every task, including a task that only edits a stylesheet. The file earns much of that: it carries thirteen numbered traps in the design system that each cost somebody an afternoon, which is precisely the "common gotchas or non-obvious behaviors" row of the include column. It is a working file rather than a bloated one, and it is still four times the target.

The second is what happens to a long file over time, and it is a case study rather than an accusation. Before the pull request that added this lesson, line 4 of that file read:

AGENTS.md line 4 · this repository, before this lesson landed · CC BY 4.0 · reproduced verbatim
`CLAUDE.md` is a symlink to this file, so Claude Code, Codex, Cursor, and any
agent honouring `AGENTS.md` all read the same contract.

Measured in the working tree, the root CLAUDE.md is a 90-byte regular file containing an HTML comment and an @AGENTS.md import. Both mechanisms are documented and both work, as lesson 0400 showed. The file had simply moved on from its own description, and nothing detects that: the sentence is prose, the load path is correct, every check in the repository stays green. The same pull request that carries this page changes one word, from symlink to imports, and the case study is what the drift cost to notice - a reader going and looking, because a lesson needed the sentence to be true.

A long instruction file has a second cost the token count does not show: nothing verifies its prose. A line that describes the repository can be wrong for a year while every test passes, and the longer the file the more such lines it holds. This is the argument for moving anything you can prove into something that runs - which is the rest of this module.

5. What survives the test is not always a line

Cutting is only half the answer. Most of what you would remove is not worthless, it is filed in the wrong place, and each destination has a different cost profile.

A path-scoped rule is a Markdown file in .claude/rules/ carrying a paths: list in its frontmatter, and it loads only when the agent touches a matching file. It is the documented escape route for a file that is growing.

.claude/rules/api.md · code.claude.com/docs/en/memory · Anthropic documentation · reproduced verbatim, complete
---
paths:
  - "src/api/**/*.ts"
---

# API Development Rules

- All API endpoints must include input validation
- Use the standard error response format
- Include OpenAPI documentation comments

When you are ready to cut rather than to reorganise, the /doctor checkup will do a first pass on a checked-in file: the documentation says it "cuts content Claude can derive from the codebase, such as directory layouts, dependency lists, and architecture overviews, and keeps pitfalls, rationale, and conventions that differ from tool defaults." That is the include and exclude table applied by machine, and it is a good second opinion rather than a verdict.

Check yourself

Retrieval practice

Answer from memory before revealing.

Your instruction file is 600 lines. What does the documentation say goes wrong?
The stated consequence is that longer files consume more context and reduce adherence, which is a quiet degradation rather than an event. The first option confuses the 200-line target with a truncation, and the only 200-line truncation documented anywhere near here applies to the auto-memory index, not to your file. The second is wrong: the only hard limit is 4 MiB, above which the file is skipped entirely. The third is invented.
Which of these four lines has the strongest claim to a place in the file?
A required piece of developer environment that nothing in the repository states is the case the include column is written for, and removing it does cause a mistake. The second is a directory layout the agent finds by listing the tree. The third is the self-evident practice the exclude column names outright. The fourth describes what one function does, which is the file-by-file tour row, and it is also the line most likely to be wrong a year from now.

Practice about 20 minutes, with a terminal

Practice 1working

Take your capstone repository's instruction file and put a number on it, then reduce that number without losing anything.

Count its lines. Classify every entry as a fact, a procedure, a rule for one subtree, or a rule that must hold. Move at least one entry out to its proper home, and count the lines again.

Hint

The classification is easier than it sounds if you ask what the entry is trying to make happen. If it is trying to make the agent know something, it is a fact. If it is trying to make the agent do a sequence, it is a procedure. If it only applies to some files, it is a subtree rule. If you would be angry to find it had been ignored, it is a rule that must hold, and the rest of this module is about those.

Show the arithmetic on a worked example
  1. Count first. A 240-line file, say, against a 200-line target - 40 lines over, which is 20% more context than the guidance asks for on every turn of every session.
  2. Classify. Suppose 30 of those lines are a release procedure and 25 are rules that only apply under one directory. That is 55 lines, none of which is a fact.
  3. Move the procedure. Into .claude/skills/release/SKILL.md, where it is read only when a task matches the description. The file is now 210 lines.
  4. Move the subtree rules. Into .claude/rules/ with a paths: list, loaded when a matching file is touched. The file is now 185 lines, inside the target, and nothing was deleted.
  5. Estimate the saving. 55 lines at roughly 60 characters each is about 3,300 characters, or about 825 tokens by the four-characters-per-token estimate this course uses for rough work. That is the per-turn saving, paid back on every turn.

Sanity check. Your line count should have fallen and your total content should not have. If you deleted more than you moved on the first pass, you were cutting rather than classifying, and the entries you cut will come back as corrections you type into chat.

Your teacher. Paste your instruction file to your agent and ask it to apply the published test to every line - "would removing this cause a mistake?" - and to answer in three columns: keep, move and where to, cut and why. Then argue with it about the ones you disagree on, because those are the lines that carry your real conventions.
