A scanner rule is a small program, and you can read it

working 10 min Written against Semgrep's published rule syntax and one MIT-licensed CodeQL query. · Semgrep rule syntax

The one-minute version

  • A working Semgrep rule is six lines: an id, a language, a message, a severity and one pattern.
  • A pattern matches shape, not text. $METAVAR stands for an unknown value and ... for an arbitrary sequence.
  • Shape alone cannot say where a value came from, so mode: taint adds sources, sinks and sanitizers.
  • A CodeQL query reaches further and costs more: its metadata block is the contract with the code-scanning UI, and its power comes from libraries it imports rather than from the file you wrote.
  • The reason to read one is control. A rule you can read is a scanner you can steer; a rule you cannot is a vendor's opinion running on your pull requests.

1. The smallest rule that works

Semgrep's own documentation opens with a rule you can hold in your head. Every top-level field here is required: id, message, severity, languages, and exactly one pattern operator.

A Semgrep rule · docs.semgrep.dev/writing-rules/rule-syntax · Semgrep documentation example · quoted with attribution
rules:
  - id: md5-usage
    languages: [python]
    message: Found md5 usage
    pattern: hashlib.md5(...)
    severity: HIGH

Run that and you get every call to hashlib.md5 in the tree, whatever its arguments. The ... is doing the work: it matches an arbitrary sequence, so one line covers a call with no arguments, three arguments, or a keyword argument you have never seen.

The other half of the pattern language is the metavariable. A name written $LIKE_THIS matches an unknown value and, within a single logical AND, the same metavariable has to match the same thing everywhere it appears. That constraint is what makes patterns behave like a small program rather than a fuzzy search.

2. Four operators, and they are boolean

One pattern is rarely enough, so the operators combine them. patterns is a logical AND over its children and pattern-either is a logical OR. pattern-not subtracts a case you have decided is fine. pattern-inside keeps only findings that sit within some larger shape - a route handler, a class, a with block - which is how a rule is scoped without listing filenames.

The documentation's second example is the shape almost every real rule ends up in: find the dangerous call, then subtract the safe spelling of it.

A rule with an exclusion · docs.semgrep.dev/writing-rules/rule-syntax · Semgrep documentation example · quoted with attribution
rules:
  - id: unverified-db-query
    patterns:
      - pattern: db_query(...)
      - pattern-not: db_query(..., verify=True, ...)
    message: Found unverified db query
    severity: HIGH
    languages: [python]

Read the two children as one sentence: every db_query call, minus the ones that pass verify=True. That subtraction is where a scanner stops arguing with your team. If your codebase has a blessed wrapper, the pattern-not naming it is the shortest honest way to say so, and it lives in version control where the argument can be reviewed like any other change.

3. Shape cannot see where a value came from

Here is the wall. subprocess.run(cmd, shell=True) is a dangerous shape, but only if cmd can hold something an outsider chose. A pattern sees the call; it cannot see the twelve lines above it.

Taint mode is the answer, and it changes what the rule is about. With mode: taint you stop describing one expression and start describing a flow: pattern-sources marks where untrusted data enters, pattern-sinks marks where it must not arrive, and pattern-sanitizers marks the code that makes it safe on the way. Semgrep notes one asymmetry worth remembering: sinks default to exact matching, sources do not.

A fourth operator, pattern-propagators, says how taint crosses a function you did not write. The documentation's example is the clearest one-liner in the whole rule language.

A taint propagator · docs.semgrep.dev/writing-rules/data-flow/taint-mode · Semgrep documentation example · quoted with attribution
pattern-propagators:
- pattern: strcpy($DST, $SRC)
  from: $SRC
  to: $DST

4. A taint rule of our own

Semgrep ships a large registry of rules for exactly this class of bug. We are not reproducing one: semgrep/semgrep-rules carries a bespoke Semgrep Rules License v1.0 rather than a standard open-source licence, and a licence you have not read is not a licence you may publish under. The shipped Python and Flask rule for this bug is worth reading in place, and it is considerably longer than what follows, because it enumerates every accessor Flask offers and every safe spelling of a subprocess call.

The rule below is this course's own, written against the documented syntax. It is deliberately small enough to read in one pass, and small enough to be wrong in ways you can name - which is the point of the practice problem at the foot of the page.

Read it as a claim Every line of that rule is an assertion about your codebase that somebody can disagree with in review. shell=True is the only sink spelling listed, so a call that builds a list and passes it to a shell interpreter walks straight past. That is a real gap and it is visible precisely because the rule is short.

5. What a CodeQL query buys, and what it costs

The other family of rule is a query over a database built from your code. GitHub's JavaScript SQL-injection query is MIT-licensed and short enough to read whole. Read the comment block first: it is not documentation, it is the contract with the code-scanning interface, and every field in it drives something visible.

SqlInjection.ql · github/codeql · MIT · reproduced verbatim
/**
 * @name Database query built from user-controlled sources
 * @description Building a database query from user-controlled sources is vulnerable to insertion of
 *              malicious code by the user.
 * @kind path-problem
 * @problem.severity error
 * @security-severity 8.8
 * @precision high
 * @id js/sql-injection
 * @tags security
 *       external/cwe/cwe-089
 *       external/cwe/cwe-090
 *       external/cwe/cwe-943
 */

import javascript
import semmle.javascript.security.dataflow.SqlInjectionQuery as Sql
import semmle.javascript.security.dataflow.NosqlInjectionQuery as Nosql

module Merged =
  DataFlow::MergePathGraph<Sql::SqlInjectionFlow::PathNode, Nosql::NosqlInjectionFlow::PathNode,
    Sql::SqlInjectionFlow::PathGraph, Nosql::NosqlInjectionFlow::PathGraph>;

import DataFlow::DeduplicatePathGraph<Merged::PathNode, Merged::PathGraph>

from PathNode source, PathNode sink, string type
where
  Sql::SqlInjectionFlow::flowPath(source.getAnOriginalPathNode().asPathNode1(),
    sink.getAnOriginalPathNode().asPathNode1()) and
  type = "string"
  or
  Nosql::NosqlInjectionFlow::flowPath(source.getAnOriginalPathNode().asPathNode2(),
    sink.getAnOriginalPathNode().asPathNode2()) and
  type = "object"
select sink.getNode(), source, sink, "This query " + type + " depends on a $@.", source.getNode(),
  "user-provided value"

@kind path-problem is why the interface can show you the whole path rather than one line. @security-severity 8.8 is the number a branch protection rule can be set against. @id js/sql-injection is how the alert is identified for the rest of its life, including by the auto-fix machinery in lesson 0760.

Then look at what the body actually does. It defines no sources and no sinks. It imports two library modules that already know what a SQL sink is in every JavaScript database driver anybody uses, merges their two path graphs, and selects from the result. The file is 36 lines and four of them are imports, which is the honest picture of the trade: your rule is short because somebody else's model of the language is long.

The choice is not which is better. It is which rule is yours. A team standard - never call this helper without that flag - is a Semgrep rule and takes ten minutes. A general model of injection across every ORM in an ecosystem is not a thing you should be writing at all, and importing it is the whole point.

Check yourself

Retrieval practice

Answer from memory before revealing.

Your rule flags every call to a helper, including the safe calls that pass a validated argument. Which operator is the correct fix?
Subtraction is exactly what pattern-not is for, and putting it in the rule puts the team's decision in version control. Taint mode is the right answer to a different complaint - not knowing where a value came from - and it costs you a source list you may not need. Severity changes the label on a finding and nothing about which findings exist. pattern-either is a logical OR, so listing the same pattern twice under it matches exactly what it matched before.
You are reading a CodeQL query and want to know why its alerts show a full path in the interface rather than a single line. Where does that come from?
The kind is what tells the interface that each result is a path with a source and a sink rather than one location. Precision is a confidence label used for filtering and query-suite membership, not a display mode. The select clause supplies the nodes the path is drawn from, but nothing renders them as a path unless the kind says so - which is why the metadata block is a contract rather than a comment. The severity score drives gating, not layout.

Practice about 30 minutes, with a terminal

Practice 1working

Plant one vulnerability and catch it with a rule you wrote, not one you downloaded.

In your capstone repository, add a route that takes a query parameter and passes it into a shell-interpreted subprocess call. Then write your own rule file, in the shape of the one above, and run semgrep --config ./rules/ . until it reports exactly one finding.

Then break it deliberately. Rewrite the planted call so it still passes attacker input to a shell but no longer matches your rule, and record what you had to change. That second half is the exercise.

Hint

The easiest way to walk past a shape rule is to change the shape without changing the danger: assign the call to a variable first, take a different route through the same library, or hand the shell a list rather than a string.

Show the shapes that walk past a small rule
  1. Rename the import. import subprocess as sp and the pattern that spells out subprocess.run stops matching. Semgrep's own symbolic propagation option exists for exactly this class of evasion, which tells you the class is common.
  2. Change the sink spelling. subprocess.run(["sh", "-c", cmd]) hands the same string to the same shell and never writes shell=True. This is why the shipped registry rule enumerates interpreter names in a metavariable-regex rather than trusting one keyword.
  3. Change the source spelling. A route argument bound by the decorator - @app.route("/x/<name>") - is attacker-controlled and is not any flask.request accessor at all, so no source in our rule matches it.
  4. Add the missing case you found to your own rule, and re-run. One of the three is enough; the habit is what matters.

Sanity check. Your first run should report one finding, not zero and not four. Zero usually means the source and the sink are in different functions with nothing joining them, and four usually means you wrote a shape rule when you meant a taint rule and are now flagging every subprocess call in the repository.

Your teacher. Paste your rule to your agent and ask it for three code samples that are dangerous and do not match. Then ask which of the three you should actually add, and why the others are somebody else's problem - a rule that tries to catch everything is the vendor registry you already have.
