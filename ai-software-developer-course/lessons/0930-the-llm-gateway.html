Move one credential server-side, and four other problems move with it

frontier 11 min Built on the Claude Code gateway documentation and on LiteLLM's own routing and reliability references. · Other LLM gateways

The one-minute version

  • A gateway is a proxy holding the provider credential. Developers hold a gateway credential instead, and offboarding revokes one thing.
  • Four more properties fall out of that: attribution, budgets, audit logging and provider switching, all in one place.
  • The trade is real: the gateway becomes infrastructure you operate, and one that does not forward a new capability breaks the feature that needs it.
  • Two variables connect a client, and the credential variable decides the header: bearer or x-api-key. The wrong one is a 401.
  • Fallbacks are keyed by error class, not by preference. Rate limit, context window and content policy are three different lists.

1. One move, five consequences

The documentation lists what a gateway gives an organisation, and the order is the useful part because each later item depends on the first. Credentials: the provider key stays server-side and developers hold gateway credentials instead. Usage tracking: usage is attributed by developer or by team, whichever provider served the request. Cost controls: budgets and rate limits enforced in one place. Audit logging: every model request logged for compliance. Provider switching: the provider changes in gateway configuration, without touching developer machines.

Notice that only the first is a property of the proxy itself. The other four are properties of there being one place, and you would get them from any single chokepoint. That is why this lesson is not about a product: if every developer holds their own provider key, none of the four is available to you at any price.

2. Two variables, and one of them decides a header

Connecting a client is two environment variables, and the subtleties are worth more than the syntax.

shell · code.claude.com/docs/en/llm-gateway-connect · Anthropic documentation · reproduced verbatim with attribution
export ANTHROPIC_BASE_URL=https://llm-gateway.example.com
export ANTHROPIC_AUTH_TOKEN=sk-gateway-key

The credential variable is a choice with a consequence: ANTHROPIC_AUTH_TOKEN sends the credential in Authorization: Bearer, ANTHROPIC_API_KEY sends it in x-api-key, and an apiKeyHelper sends it in both. A credential in the wrong variable reaches the gateway in a header it does not read, and the request fails with a 401 that looks like a bad key. If nobody told you which kind your gateway is, the documentation's advice is to start with ANTHROPIC_AUTH_TOKEN and switch if the verification request returns 401.

The second subtlety catches teams that think they have rolled out a gateway and have not. Setting the base URL alone, with no gateway credential, does not replace a claude.ai subscription: requests still route through the gateway, but the saved login remains the active credential, so the subscription's usage limits and billing still apply. The credential variable is what moves the billing, and the base URL is only what moves the traffic.

The rollout, in four steps The documented sequence is worth following in order: deploy the gateway with your provider credential, issue each developer their own gateway credential so that usage is attributed and offboarding revokes one thing, distribute the base URL and the credential through managed settings and your secrets tooling, and have each developer confirm the configuration arrived before anybody depends on it. Step four is the one teams skip, and it is the one that turns a distribution bug into a support queue.

3. Routing is a policy, and fallbacks are keyed by error

Once traffic passes through one place, that place can choose which deployment answers. LiteLLM's router names its strategies plainly: simple-shuffle weighted by requests or tokens per minute, latency-based routing, usage-based routing on the lowest tokens-per-minute for that minute, least-busy on concurrent requests, and cost-based routing on the cheapest deployment. Each is wrong somewhere. Cost-based routing on a latency-sensitive path buys pennies and spends seconds; least-busy on a fleet of unequal machines pours traffic into the slowest one, because a machine nobody is waiting on is a machine nobody wants.

Fallbacks are the part worth writing carefully, because there are three separate lists and they catch different errors. fallbacks catches the remaining errors, rate limits among them. context_window_fallbacks catches a context-window-exceeded error, and its answer is a bigger model rather than a cheaper one. content_policy_fallbacks catches a content-policy refusal. Collapsing all three into one list means a context overflow is answered by a model with the same window, which fails identically, twice as slowly.

config.yaml · docs.litellm.ai routing and reliability references · LiteLLM, MIT · composed from the documented keys, each block matching the published shape
model_list:
  - model_name: primary
    litellm_params:
      model: anthropic/claude-sonnet-5
      api_key: os.environ/ANTHROPIC_API_KEY
      rpm: 1000
    model_info:
      id: anthropic-direct

  - model_name: primary
    litellm_params:
      model: bedrock/us.anthropic.claude-sonnet-4-6
      aws_region_name: us-east-1
      rpm: 1000
    model_info:
      id: bedrock-backup

  - model_name: cheap
    litellm_params:
      model: anthropic/claude-haiku-4-5
      api_key: os.environ/ANTHROPIC_API_KEY
    model_info:
      id: haiku-direct

router_settings:
  routing_strategy: simple-shuffle
  num_retries: 3
  allowed_fails: 3
  cooldown_time: 30
  enable_pre_call_checks: true

litellm_settings:
  num_retries: 3
  request_timeout: 600
  fallbacks: [{"primary": ["cheap"]}]
  context_window_fallbacks: [{"cheap": ["primary"]}]
  content_policy_fallbacks: [{"primary": ["cheap"]}]
  default_fallbacks: ["primary"]

general_settings:
  master_key: os.environ/LITELLM_MASTER_KEY
  database_url: os.environ/DATABASE_URL

Two deployments share the model name primary, which is what makes a fallback between providers possible without a client change. allowed_fails and cooldown_time are the pair that stops a fallback storm: after three failures a deployment is taken out for thirty seconds rather than being retried by every request that arrives in the meantime. And database_url is not optional decoration - per-key and per-team budgets need somewhere to keep a running total, so a database-less deployment can route and cannot cap.

4. The gateway is now infrastructure you operate

The documentation states the trade in one sentence: the gateway becomes infrastructure your organisation operates, Claude Code adds capabilities with each release, and a gateway that does not forward them breaks the corresponding features. That is abstract until you meet an instance of it, so here is one that is documented in full.

Amazon Bedrock streams responses in a binary event-stream format carrying Content-Type: application/vnd.amazon.eventstream. A proxy in the path must forward the body and that header unchanged. If it rewrites the header to text/event-stream, which an integration that re-emits the stream as server-sent events will do, the client rejects the response outright. If it drops the header and also re-emits the stream, the client cannot decode the body and quietly falls back to a slower non-streaming path on every turn, so answers appear complete rather than streaming and nothing reports an error.

That second failure is the shape to fear: nothing breaks, nothing logs, and every developer on the fleet gets a worse experience that they will describe as "it feels slow lately". A gateway rollout needs a check that a capability still works, not only a check that requests still succeed. Pick two or three features you actually rely on, and test them explicitly after every gateway upgrade.

5. What the fleet actually costs

The point of one meter is that the bill becomes arithmetic. Anthropic publishes what its enterprise deployments observe: $13 per developer per active day, $150 to $250 per developer per month, with costs staying below $30 per active day for 90% of users. Those are the numbers to start a pilot from, and the gateway is what replaces them with your own.

The same publication gives the other number a gateway rollout needs, which is how much capacity to ask for. Per-user token-per-minute recommendations fall sharply as a team grows, because fewer people use an agent concurrently in a large organisation than in a small one, and the limits apply at the organisation level so an individual can still burst above their share.

Check yourself

Retrieval practice

Answer from memory before revealing.

A developer sets only ANTHROPIC_BASE_URL and keeps their claude.ai login. Who is billed?
The base URL moves the traffic and the credential variable moves the billing. With no gateway credential set, the saved login stays active and its limits and billing apply. The first option is the intuition the documentation exists to correct. The second is wrong because there is a credential, just not the gateway's. The third invents a billing relationship that nothing establishes.
Requests fail with a context-window-exceeded error. Which fallback list should name the replacement?
Each list is keyed by the error class it catches, and a context overflow needs a model with a bigger window rather than a cheaper one. The first would work only by accident and usually sends the request to something no larger. The third catches a policy refusal, which is a different error entirely. The fourth is the catch-all for a misconfigured model group, so it fires when there is nothing better to do rather than when there is.

Practice about 30 minutes, with a terminal

Practice 1frontier

Stand up the smallest gateway that can prove a fallback fired.

Run a LiteLLM proxy locally with two model groups: an expensive primary and a cheap fallback, using the shape above. Point your agent at it with ANTHROPIC_BASE_URL and the credential variable your gateway reads.

Then force a failure - revoke the primary key, or set rpm: 1 on it - and capture the gateway log line that proves the fallback served the request. Write down which deployment answered and how long the cooldown held.

Hint

An impossible rate limit is easier to undo than a revoked key. Set rpm: 1 on the primary deployment, send three requests quickly, and read the log rather than the answers. If nothing falls back, check that both deployments share one model_name: a fallback between two different names is a different mechanism.

Show what a good run looks like
  1. Confirm the client is actually pointed at you. Before forcing anything, check that the gateway logs a request at all. A 401 here is almost always the header mismatch: swap ANTHROPIC_AUTH_TOKEN for ANTHROPIC_API_KEY and try again.
  2. Break exactly one thing. Cap the primary at one request per minute and leave everything else alone, so that the only variable is the one you changed.
  3. Read three log lines, not one. The first is the failure, the second is the cooldown decision, the third is the successful retry on the second deployment. A run that shows only the first and third has retried rather than cooled down, and will hit the same limit on the next request.
  4. Time the recovery. Wait past cooldown_time and send one more request; it should return to the primary. If it does not, your allowed_fails window has not reset and the deployment is being held out longer than you intended.

Sanity check. The whole exercise should produce one log line you would be willing to paste into an incident review. If your evidence that the fallback works is that the answer came back, you have proved only that something answered, which is exactly what the cf-aig-step-style header exists to disambiguate.

Your teacher. If the five properties still feel like a feature list, ask your agent which of the five you would lose first if you removed the gateway and gave everyone a provider key, and to rank the rest by how long it would take to notice. If the fallback lists blur, ask it to name a real error message for each of the three and say which list catches it.
