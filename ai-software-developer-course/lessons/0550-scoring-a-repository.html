Module 05 · Agent-ready codebases · Lesson 0550

Every point in a readiness score is a file path, or it is not a point

working 14 min A rubric derived from the published pillars rather than copied from them, worked against a repository whose every artefact is public. · discourse/discourse

The one-minute version

  • Ten dimensions, scored 0 to 3, maximum 30. The rubric is derived from the nine published pillars and from two vendors' agent guidance; it is not anybody's official rubric.
  • The rule that makes it work: a score is a file path or a command, never an impression. A score with no evidence is a zero.
  • The worked example scores 26 of 30 and its two weak dimensions are the interesting part, because both are things you would have guessed were fine.
  • The output is not the number. It is the cheapest dimension below 2, which is the one thing to do next.

1. The rule that makes a score mean anything

Every readiness checklist ever written fails the same way: the scores become vibes. Somebody rates documentation a 2 because it feels roughly adequate, and the number carries no information anybody else can check, reproduce or argue with.

One rule fixes it. Every point must be evidence you can point at: a path in the repository, or a command you ran and watched succeed. Not "we have decent tests" but bin/qunit path/to/test-file.js, which either runs or does not. Not "setup is documented" but .devcontainer/devcontainer.json, which either exists or does not. A dimension where you cannot name the evidence scores zero, even when you are certain the thing is fine, because "certain the thing is fine" is exactly the state this exercise exists to interrupt.

2. The rubric, and a repository to point it at

Answer the ten below for a repository you actually own. The fix line under each is visible whatever you answer, because the fixes are the teaching and the number is only the index into them.

3. The same ten, worked against a real repository

A rubric that has never been pointed at anything is a wish list. Here it is applied to discourse/discourse, a GPL-2.0 repository of about a gigabyte, with every score's evidence read from the public tree.

The contrast case makes the rubric's discrimination visible. keycloak/keycloak has no root AGENTS.md, no CLAUDE.md, no container definition and no root lockfile. It does have .github/copilot-instructions.md, so it scores on dimension 1 rather than zeroing it, but at 2 at best: its entry point is readable by one vendor's tool rather than by the open format the other four repositories in the same sweep all adopted. That single difference is the entire argument for the open filename, made in one comparison.

4. What to do with the number

The number is not the output and should not be reported as one. The output is the cheapest dimension scoring below 2, because that is a decision, and everything else on the page is the working that justifies it.

On the worked example, the cheapest next move is dimension 8. Generating a CODEOWNERS coverage baseline the way Sentry does converts an unmeasured gap into a number that can only go down, and it is a script rather than an organisational negotiation.

Agent-readiness and AI-reviewability are different properties, and this score does not measure the second one. In the open benchmark that module 6 works through, the most agent-ready repository in the sample was the repository where AI reviewers did worst on recall, and the least agent-ready one was where several scored their best precision. A tidy, well-instructed codebase does not make a machine reviewer better at finding real bugs in it, and there is no published study relating a readiness level of any kind to an agent's actual success rate. That is why the scorecard above is a teaching instrument and a work list, and never a verdict. The same caution about measurement generally is worked through in The Staff AI Engineer, proving it works, whose central finding is that most reported improvements sit inside the noise.

Check yourself

Retrieval practice

Answer from memory before revealing.

You are certain your setup is well documented but cannot name the file. What is the score?
The evidence rule is the only thing keeping the rubric reproducible, so unnamed evidence is no evidence. The first two options both award partial credit for a memory, which is the exact failure mode the rule exists to stop. The fourth quietly raises your percentage by shrinking the denominator, which is worse than a low score because it hides the gap.
Your score is 21 of 30 and three dimensions are below 2. Which do you close first?
Ranking by cost is what keeps the loop turning, because a first pass that takes an afternoon gets a second pass. The first option is intuitive and routinely picks a dimension nobody can finish. The second picks the quarter of platform work. The third abandons the before-and-after comparison, which is the only thing that turns the score into a measurement rather than an opinion.

Practice about 30 minutes, with the repository open

Practice 1working

Score your capstone repository against the ten dimensions above, under the evidence rule.

Write a table with four columns: number, dimension, score, and the file path or command that is your evidence. Where you cannot fill the fourth column, the third column is 0. No exceptions, including for the dimensions you are sure about.

Then produce one line: the cheapest dimension below 2, and the single artefact that would raise it.

Hint

Score dimension 2 last and score it honestly by running each command from a clean checkout. In most repositories at least one of the six commands in that row has quietly stopped working, and finding out is worth more than the point it costs you.

Show what a filled-in row looks like, and the three traps
  1. A row done properly. 7 | CI legibility | 1 | .github/workflows/ci.yml runs three checks and prints only logs; no annotations, no summary step, no baseline file. The evidence names what is there and what is not, which is what makes the score reproducible by somebody else.
  2. Trap one: scoring the intention. A pull-request template asking for tests is not dimension 4 evidence. It asks a human for something; it gives an agent nothing to run.
  3. Trap two: crediting CI for local work. A command that only exists inside a workflow file scores on dimension 7, never on dimension 2, because an agent working locally cannot reach it without reading YAML and guessing.
  4. Trap three: averaging. The total is a sum, not a mean, and it is deliberately not a percentage. Twenty-six of thirty with a 1 on ownership is a specific finding; 87% is not.

Sanity check. If you scored above 24 on the first pass, re-read your evidence column and check how many entries are a directory rather than a file or a command. A directory is where evidence goes to hide.

Your teacher. Give your agent the ten dimensions and ask it to score your repository with a path per point, then score it yourself without looking at its answer. Compare. The rows where you disagree are almost always rows where the artefact exists but is not where a first-time reader would look, which is itself the finding.

Primary source to go deeper

The published model this rubric was derived from, so you can see what was taken and what was changed: Agent Readiness. The nine pillars there include two, observability and experimentation, that this ten-dimension rubric deliberately drops, because neither is a property of a repository you can read from its tree.
