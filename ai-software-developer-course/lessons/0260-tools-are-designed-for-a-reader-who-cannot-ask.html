Write the description for a caller who cannot ask you what you meant

foundation 12 min Every principle here is one somebody published after measuring it, not a style preference. · Writing effective tools for agents

The one-minute version

  • A tool is a contract between a deterministic system and a non-deterministic caller, and the caller cannot ask a follow-up question.
  • The description is not documentation. It is the only thing the model plans against, so the floor is three to four sentences and the ceiling is your context budget.
  • An error the model can act on is a different object from an error your client should log. MCP separates them, and only one of the two lets the model recover.
  • The biggest single lever is what comes back. Claude Code truncates a tool response at 25,000 tokens by default, and a tool that needs truncating has already lost.

1. The frame, and why it changes the writing

Every API you have designed assumed a reader who could go and look something up: read the source, ask a colleague, try it in a console. A model has none of those. It sees a name, a description and a schema, in one block, once, and then it either calls the tool correctly or it does not. Anthropic's own guidance puts five principles around that, and every one of them is a consequence of the caller's situation rather than a matter of taste.

The headline sentence from that post is worth carrying whole, because it contradicts the instinct everyone has when they first build a server: "More tools don't always lead to better outcomes." That is lesson 0270's subject and this page's constraint.

2. The description, sentence by sentence

The floor is stated exactly: "Aim for at least 3-4 sentences for each tool description, more if the tool is complex." Anthropic's documentation gives a matched pair for the same tool, and the difference is instructive because the poor one is not wrong about anything.

get_stock_price · the poor description · Anthropic documentation, quoted with attribution · reproduced verbatim
{
  "name": "get_stock_price",
  "description": "Gets the stock price for a ticker.",
  "input_schema": {
    "type": "object",
    "properties": {
      "ticker": {
        "type": "string"
      }
    },
    "required": ["ticker"]
  }
}
get_stock_price · the good description · Anthropic documentation, quoted with attribution · reproduced verbatim
{
  "name": "get_stock_price",
  "description": "Retrieves the current stock price for a given ticker symbol. The ticker symbol must be a valid symbol for a publicly traded company on a major US stock exchange like NYSE or NASDAQ. The tool will return the latest trade price in USD. It should be used when the user asks about the current or most recent price of a specific stock. It will not provide any other information about the stock or company.",
  "input_schema": {
    "type": "object",
    "properties": {
      "ticker": {
        "type": "string",
        "description": "The stock ticker symbol, e.g. AAPL for Apple Inc."
      }
    },
    "required": ["ticker"]
  }
}

Read the second one for what each sentence rules out. The exchange sentence rules out a European ticker. The currency sentence rules out asking again in another currency. The "when the user asks" sentence rules out calling it during unrelated work. The last sentence rules out using it for market cap, which is the failure that would otherwise reach production. A description with no negative space in it is a description that will be used for the wrong thing.

Build one and watch what it costs. Untick a part and ask yourself which question the model now has to guess the answer to.

3. The schema is a second description

Two habits do most of the work, and both are about removing ambiguity rather than adding validation.

Name the thing, not its category. A parameter called user could take a name, an email, an id or an object; a parameter called user_id could take one of those. The same rule reaches the return value: Anthropic's guidance is to "return semantic, stable identifiers (for example, slugs or UUIDs) rather than opaque internal references", because the model has to carry them forward into the next call and it cannot look one up.

Use enum rather than a sentence. A description saying "must be celsius or fahrenheit" is a hope. An enum is a constraint, and it is shorter. Where a format is genuinely hard to describe, input_examples carries schema-validated examples of a well-formed call - at a published cost of "~20-50 tokens for simple examples, ~100-200 tokens for complex nested objects".

4. Two kinds of error, and only one of them helps

This is the distinction most first servers get wrong, and MCP names it explicitly. A protocol error is a JSON-RPC error: an unknown tool, a malformed request, a server fault. A tool execution error is a normal result carrying isError: true.

The spec is direct about what each is for. Protocol errors "indicate issues with the request structure itself that models are less likely to be able to fix". Tool execution errors "contain actionable feedback that language models can use to self-correct and retry with adjusted parameters", and clients "SHOULD provide tool execution errors to language models to enable self-correction".

What goes in the text matters as much as the channel. "Invalid input" tells the model nothing. The spec's own example does the work: "Invalid departure date: must be in the future. Current date is 08/08/2025." Name the field, name the rule, and give the value that would satisfy it.

5. The response is the expensive half

A tool definition costs you a hundred tokens or so on every turn. A tool result can cost you twenty thousand in one call. Claude Code restricts tool responses to 25,000 tokens by default, which is a ceiling rather than a design: a response that hits it has already filled a quarter of a 100k working context with one call.

Three moves, in the order to try them. Filter, so the tool returns what was asked for rather than everything. Paginate, with a sensible default page size. And where you must truncate, make the truncation message a signpost.

The same post reports a fourth move that is worth knowing about before you need it: exposing a response_format parameter with concise and detailed values, where the concise form is reported at roughly a third of the tokens. The model then chooses the resolution, which is the correct place for that decision because only the model knows what it is about to do with the answer.

Tool annotations are documentation, not a permission system. MCP's schema carries readOnlyHint, destructiveHint, idempotentHint and openWorldHint, and its own comment says: "NOTE: all properties in ToolAnnotations are hints. They are not guaranteed to provide a faithful description of tool behavior (including descriptive properties like title). Clients should never make tool use decisions based on ToolAnnotations received from untrusted servers." A server declares its own annotations, so a hostile one declares whatever it likes. Use them to tell a human reviewer what a tool does; never to decide what a tool is allowed to do. That decision belongs to a permission rule, which is lesson 0730.

6. One tool, one job, and a name that says which

Two failures remain and both are about the library rather than the tool. Collisions: mount three servers and each one may offer a search. MCP's own note says tool-name uniqueness is scoped to a single server and that an aggregating client "SHOULD implement a disambiguation strategy such as prefixing tool names with a server identifier" - so prefix them yourself and stop relying on somebody else's strategy. Overlap: two tools that could both do the job make the model choose badly, and neither description is at fault. The fix is consolidation, and it is the subject of the next page.

For how the tool-and-skill distinction plays out across fifteen harnesses, Four customization primitives is the survey; this page stays on the one artefact you are writing.

Check yourself

Retrieval practice

Answer from memory before revealing.

Your tool is asked for a departure date in the past. How should it report that?
This is a tool execution error: the model can fix it by supplying a different date, and only that channel is reliably shown back to the model for self-correction. A protocol error is for things the model cannot fix, like an unknown tool. An empty result is the worst of the four because it looks like a successful search that found nothing, and an uncaught exception is the same failure with a stack trace attached.
Which of these is charged on every turn, whether or not the tool is ever called?
A tool definition is part of the request, so it is input tokens on every turn from the moment it is mounted. The other three are all parts of a result: they are paid once when the call happens and then carried in the history, which is a real cost and a different one. Confusing the two is what makes a large tool library feel free until the bill arrives.

Practice about 30 minutes, with a terminal

Practice 1foundation

Take the tool you wrote in lesson 0250 and rewrite its description under the five principles: what it does, when to use it, what it returns, what it does not do, and what calling it costs.

Then measure. Run the same real task twice against your agent, once with each description, and record two numbers each time: how many turns it took, and how many times it called the tool. Say honestly whether the rewrite moved either number, and if it did not, say what you think the task was not sensitive to.

Hint

Pick a task where the tool is optional rather than required. If the agent has no other way to answer, it will call the tool whatever the description says, and you will measure nothing.

Show what a good pass looks like
  1. Write the negative sentence first. "It does not..." is the sentence most descriptions lack, and it is the one that stops a wrong call rather than improving a right one.
  2. Replace every free-text constraint with a schema one. An allowed set becomes an enum, a required field becomes required, and both get shorter as well as stricter.
  3. Run the same task twice, from the same starting state. A dirty working tree between runs makes the second measurement worthless.
  4. Count turns and tool calls, not tokens. Tokens move with the answer's length and will hide the effect you are looking for.
  5. Accept a null result. "No change, because the task always needed the tool exactly once" is a real finding, and it tells you where to look for a task that would show one.

Sanity check. A rewrite that adds three sentences typically adds 30 to 60 tokens per turn, so it has to save at least one wasted call over a long task to pay for itself. If your rewritten description is four times the length of the original, you have written the tool's manual rather than its contract, and the extra is now permanent context.

Your teacher. Ask your agent to read only your tool's description and schema, with the implementation hidden, and to list every question it would have to guess the answer to before calling it. Each item on that list is a missing sentence. Then ask it to name the situation in which it would call your tool by mistake - that answer is the negative sentence you have not written yet.
