Module 08 · Background agents · Lesson 0850

It cannot ask you a question, so answer them all in advance

working 9 min Built on the documented carry-over table, the setup-script contract, and one convention two vendors share. · Configure cloud environments

The one-minute version

  • The fresh-clone rule from lesson 0800, taken seriously: committed or absent. A question the agent would have asked you has to already be answered in a file.
  • Four artefacts are the whole interface: an instruction file, a settings file, a skills directory, and a setup script. Three are in the repository and one is on the environment.
  • The instruction file is one convention across vendors: AGENTS.md at the repository root is read by more than one of the products in lesson 0810.
  • The other half of the contract is what the agent cannot do: no interactive prompt, usually one branch and one pull request, and a clock it does not control.

1. The rule, restated and taken seriously

An interactive agent that hits an ambiguity asks. A background agent that hits an ambiguity picks. There is no third behaviour, because there is no channel: the session may support a follow-up message, but nobody is going to read the question for hours, and Anthropic's documentation notes that a session sitting idle waiting for an answer runs until "environment expiry".

So the design question inverts. Instead of "what should I tell the agent", it becomes "what will it need to know, and where in the repository will it find that?"

The third row is the one that surprises a developer with a good local setup, because user-scope skills are exactly what a heavy agent user accumulates. The documented carry-over table is blunt about it: user-scope skills, agents and commands "Live on your machine, not in the repo. Commit them to the repo's .claude/ directory instead."

The first row has a nice property that is worth naming, because conventions across vendors are rare. Google's Jules documentation says it "automatically looks for a file named AGENTS.md in the root of your repository", and the same filename is the open format this course's module 4 is built on. One file at the root is read by more than one of the six products in lesson 0810.

3. The setup script, which is the one that fails loudly

A setup script "is a Bash script that runs when a new cloud session starts, before Claude Code launches", and it runs "as root on Ubuntu 24.04, so apt install and most language package managers work". It has three documented constraints and each one has a matching mistake.

The constraints, and what to do about each. Exit zero: "if the script exits non-zero, the session fails to start", so append || true to anything that is not essential. Finish within five minutes, because the environment snapshot is built from a completed script, so run independent installs in parallel. Reach a registry: package installs need network, and "with None network access, installs fail".

setup.sh · written for this course against the documented setup-script constraints · CC BY 4.0 · reproduced verbatim
#!/usr/bin/env bash
# Runs as root on Ubuntu 24.04 before the agent starts.
# Three rules: exit zero, finish inside about five minutes, and remember
# that a package install needs the environment's network level to allow it.
set -euo pipefail

# 1. Toolchains the image does not ship. Parallel, because the clock is short.
apt-get update -qq
apt-get install -y -qq shellcheck jq &
curl -fsSL https://example.invalid/toolchain.tar.gz -o /tmp/toolchain.tar.gz &
wait

# 2. Project dependencies. Non-critical, so a flaky registry does not fail
#    the session: the agent can install them again in its first turn.
npm ci --no-audit --no-fund || true

# 3. A warm cache the snapshot will keep. Only files survive, never processes,
#    so pull images here and start them from a SessionStart hook instead.
docker compose pull --quiet || true

# 4. Prove the environment before the agent trusts it. This one is deliberately
#    allowed to fail: a red suite at setup time is information, not a blocker.
npm test --silent || echo "setup: the suite is red before any agent change" >&2
The environment cache is a filesystem snapshot, so it "keeps what the setup script writes to disk and loses anything that was only running". A script that starts a database and a script that installs one look identical while you are writing them, and only the second one works on the second session. The documented split is worth learning once: a setup script provisions the machine, and a SessionStart hook starts what has to be running - and the hook is the half that also works on your own laptop.

4. The other half of the contract

What the agent cannot do is as much a part of the design as what it can. Three limits recur across the products in lesson 0810 and all three change how you write the task.

No interactive prompt. A permission dialogue with nobody to answer it is a stalled run. This is why the --allowedTools list from lesson 0830 is not a nicety: an unapproved tool call is a dead end rather than a question.

Usually one branch and one pull request. Copilot's documentation states it as a hard scope - "Copilot can only work on one branch at a time and can open exactly one pull request to address each task" - and Claude in Slack lists "One PR at a time: each session can create one pull request". A task that needs two pull requests is two tasks.

A clock it does not control. Either a published ceiling, or an inactivity reclaim, or a workflow timeout you set. Work that cannot be resumed from a commit will be lost at that boundary.

5. The issue is the last artefact

The four artefacts above are the standing context, and the issue body is the per-run context. An issue that would take a colleague two clarifying questions produces a pull request that takes you twenty minutes to reject.

Three sentences in an issue do most of the work: what is wrong, what should be true instead, and how a reader would know. The third is the one that is nearly always missing and the one an unattended agent cannot do without, because it is the only stopping condition it has.

Check yourself

Retrieval practice

Answer from memory before revealing.

Your setup script starts a database with docker compose up -d. It works on the first session and every later session finds no database. Why?
After the first run the filesystem is snapshotted and later sessions skip the script, and the snapshot "keeps what the setup script writes to disk and loses anything that was only running". The first two would have failed the first session as well, which the symptom rules out. The third inverts the documented order: the script runs after the clone, before the agent. The documented fix is a SessionStart hook, which runs every session.
Which of these is the strongest single predictor that an unattended run will produce something useful?
A verification command is the agent's only way to distinguish finished from broken, and without one the run ends by asserting success. The first and fourth both raise the ceiling on what a run could do and do nothing about whether it can tell that it did it. The third is genuinely valuable and is the strongest distractor, but a design description without a check still leaves the agent judging its own work.

Practice about 40 minutes, with the capstone repository

Practice 1working

Score the scorecard above against your capstone repository, honestly, and then close the two lowest-weighted gaps you can finish today.

Then run the fresh-clone test, which is the only version of this that cannot be fooled. Clone your repository into an empty directory, on a machine or container that has never built it, and try to reach a passing test suite using only what is in the clone plus what your setup script installs. Every command you had to invent is a line missing from one of the four artefacts.

Record the commands you needed and where each one belongs: the instruction file, the setup script, or a skill.

Hint

A container is the honest way to do this, because a second directory on your own machine still has your PATH, your language version manager and your credentials. If you have no container to hand, the next best thing is to read your shell profile and temporarily unset everything in it that names a tool your build uses.

Show what the fresh-clone test usually finds
  1. A language version nobody wrote down. The build works on the version you happen to have and fails on the image's. This belongs in the setup script, pinned, and the pin belongs in the repository too so the two cannot drift.
  2. A credential or a private registry. Everything installs until one package needs an authenticated fetch. That is an environment variable or an API credential on the environment, and never a value committed to the repository.
  3. A command you know and the repository does not. The suite runs with a flag you always pass. Put the full command in AGENTS.md, exactly as you would type it, and make it the only one named there.
  4. Nothing at all, on a well-prepared repository. If the fresh clone builds and tests cleanly, you have the property module 5 calls agent-ready, and the remaining gaps on the scorecard are about the issue rather than the repository.

Sanity check. Count the commands you had to invent. Zero means you are ready to trigger something unattended; more than five means the next background run will spend its whole turn budget doing environment archaeology, and no prompt will fix that.

Your teacher. Give your agent the last five issues from your tracker and ask, for each one, what question it would have had to ask before starting. Then ask where in the repository that answer should live. The list you get back is this page applied to your own backlog.
