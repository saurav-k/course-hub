Four tools are enough, and the interesting one refuses

foundation 10 min Tool descriptions below are read from opencode at commit b578b72. · opencode edit.txt

The one-minute version

  • Four tools cover the job: list answers where is it, read answers what does it say, edit changes it, bash proves the change.
  • They are enough because a filesystem plus a shell is a universal interface: every language, build system and test runner already speaks it.
  • Bash alone is not enough, because an unbounded cat puts a whole file in the context window at full price, on every later turn.
  • The edit tool is the one with real depth, and its depth is refusal: zero matches and many matches are both errors, and each error tells the model what to do next.

1. Four tools, four questions

Each of the four answers a question the model cannot answer from its own weights, and the four questions are the whole of working in a repository.

The reason four is enough is not a claim about models. It is a claim about interfaces. A filesystem plus a shell is where every language toolchain already terminates: a build is a command, a test run is a command, a dependency install is a command, and every artefact any of them produces is a file. An agent that can read files and run commands inherits every tool your project already has, without any of them being taught to it.

2. Why bash alone is not enough

The obvious economy is to drop three tools and keep bash: ls, cat and sed -i already exist. Several early agents did exactly that, and the reason it loses is a budget rather than a capability.

A tool result is text appended to the conversation, and the conversation is re-sent on every later turn. So cat on a 4,000-line file does not cost one read: it costs that file, again, on every remaining turn of the task. A purpose-built read tool can offer an offset, a line limit and a per-line truncation, and every one of those is a lever on the budget that cat does not have.

opencode's read tool is a good specimen because its description states every one of those limits in the text the model actually plans against.

read.txt, the whole tool description · sst/opencode, packages/opencode/src/tool/read.txt at commit b578b72 · MIT · reproduced verbatim
Read a file or directory from the local filesystem. If the path does not exist, an error is returned.

Usage:
- The filePath parameter should be an absolute path.
- By default, this tool returns up to 2000 lines from the start of the file.
- The offset parameter is the line number to start from (1-indexed).
- To read later sections, call this tool again with a larger offset.
- Use the grep tool to find specific content in large files or files with long lines.
- If you are unsure of the correct file path, use the glob tool to look up filenames by glob pattern.
- Contents are returned with each line prefixed by its line number as `<line>: <content>`. For example, if a file has contents "foo\n", you will receive "1: foo\n". For directories, entries are returned one per line (without line numbers) with a trailing `/` for subdirectories.
- Any line longer than 2000 characters is truncated.
- Call this tool in parallel when you know there are multiple files you want to read.
- Avoid tiny repeated slices (30 line chunks). If you need more context, read a larger window.
- This tool can read image files and PDFs and return them as file attachments.

Four of those thirteen lines are budget policy, one is a parallelism instruction, and one - the line-number prefix - exists so that a later edit can be aimed. None of it is documentation for a human. All of it is behaviour.

3. Why read alone is not enough

The mirror-image economy is to drop bash and keep the three file tools, which looks safer and is the more tempting mistake. It fails because nothing verifies. An agent that can read and write but cannot run anything has no way to find out whether its change compiles, passes or even parses, so its only signal that the work is done is its own confidence.

That is a real architectural claim rather than a preference, and it is the seed of module 5: a test suite is not quality assurance to an agent, it is the only sense organ it has. Take bash away and the loop cannot close.

4. The edit primitive, and why it refuses

Editing is where a tool set stops being obvious. Handing the model a line number invites off-by-one errors against a file it read three turns ago; handing it a unified diff invites malformed hunks. The primitive that won across most shipped harnesses is exact string replacement: quote the text you want gone, give the text to put there, and let the tool refuse if the quote is not unique.

edit tool parameters · sst/opencode, packages/opencode/src/tool/edit.ts lines 47-56 at commit b578b72 · MIT · reproduced verbatim
export const Parameters = Schema.Struct({
  filePath: Schema.String.annotate({ description: "The absolute path to the file to modify" }),
  oldString: Schema.String.annotate({ description: "The text to replace" }),
  newString: Schema.String.annotate({
    description: "The text to replace it with (must be different from oldString)",
  }),
  replaceAll: Schema.optional(Schema.Boolean).annotate({
    description: "Replace all occurrences of oldString (default false)",
  }),
})

Four fields, and the fourth exists precisely because the third failure mode is common enough to need an answer. The tool's own description states both failures in the words the model will read back as an error: the edit "will FAIL if oldString is not found in the file", and it "will FAIL if oldString is found multiple times in the file", with instructions to provide more surrounding context or to set replaceAll.

Here is the same rule as running code, in the agent this module builds. The two throw lines are the whole design.

agent.ts, the edit handler · written for this course, refusal shape follows opencode's · MIT (this repository) · reproduced verbatim
run: async (input) => {
  const file = resolveInside(String(input.path));
  const oldStr = String(input.old_str);
  const newStr = String(input.new_str);

  if (oldStr === "") {
    await fs.mkdir(path.dirname(file), { recursive: true });
    await fs.writeFile(file, newStr, "utf8");
    return `created ${input.path} (${newStr.length} bytes)`;
  }

  const before = await fs.readFile(file, "utf8");
  const hits = before.split(oldStr).length - 1;
  if (hits === 0) throw new Error("old_str not found in the file");
  if (hits > 1) throw new Error(`old_str appears ${hits} times; quote more context to make it unique`);

  await fs.writeFile(file, before.replace(oldStr, newStr), "utf8");
  return `edited ${input.path}`;
},
Where the depth is Exact-string replacement is the primitive, not the end of the story: shipped harnesses disagree about fuzzy matching, whitespace normalisation, indentation repair and how many attempts a failed edit gets. The edit problem in Coding Harness Engineering takes four expressions of an edit and ten pinned matchers apart at source level. This page needs you to know only that the refusal is deliberate.

5. What the four do not cover

Every harness that ships adds a fifth tool of a different kind, and it is worth naming because it looks redundant. It is a plan tool: something the model calls to write down a to-do list, which is then kept in the conversation and updated. It touches no file and runs no command. Its only effect is on the model's own context.

opencode's prompt tells the model to use its task-management tool "VERY frequently"; Codex CLI spends about sixty lines of its system prompt on one update_plan tool. The rest of that argument belongs to the next page but one, where five prompts are read side by side.

Check yourself

Retrieval practice

Answer from memory before revealing.

Why does a purpose-built read tool beat asking bash to run cat?
Offset, line limit and per-line truncation are budget levers, and the budget is what the whole conversation is re-sent against. The second is true and trivial next to the token cost. The third is a property of the path check you wrote, not of the tool being a read tool, and you could write the same check around a shell command. The fourth is a real effect of a good description but it is not why the tool exists.
An edit is refused because old_str matched three times. What has the model learned?
Several matches means the quote is ambiguous, and the fix named in the error is to quote more surrounding lines. The first describes the zero-match case, which is the other refusal and has a different fix. The second and fourth are conditions some harnesses check, but neither produces this error, and inventing a cause is exactly what a vague error message makes a model do.

Practice about 20 minutes, with a terminal

Practice 1foundation

Take a repository you know and pick a file with a name that appears several times inside itself - a constant, a struct field, a route.

Ask your agent to rename that identifier, and watch for the first refused edit. Then read the error it got back, in whatever form your harness shows tool results.

Answer two questions from the refusal alone. Did the message name the fix, or only the failure? And how many turns did the recovery cost?

Hint

If nothing is refused, the identifier was too rare. Pick one that appears in at least four places on lines that look alike, such as a field name repeated in a struct definition and in three literals.

Show what a good refusal looks like
  1. Read the error as the model read it. A good one names the count and the next move: "appears 4 times - quote more context to make it unique". A poor one says "edit failed".
  2. Count the recovery turns. A named fix usually costs one: the model re-quotes with surrounding lines and the second edit lands. An unnamed one costs two or three, because the model has to guess what went wrong first, often by re-reading the file it already has.
  3. Price the difference. One wasted turn re-sends the whole conversation, so on a task with a 20,000-token context that is 20,000 input tokens for nothing, which is $0.10 at Claude Opus 5's $5 per million.
  4. Generalise it. The wording of an error is not politeness, it is control flow. That is the whole of lesson 0150, arrived at from the other end.

Sanity check. Recovery should cost one or two turns, not zero and not six. Zero means nothing was actually refused and you picked too rare an identifier. Six means the error your harness returns is not telling the model anything, which is a finding worth keeping for module 4.

Your teacher. Ask your agent to list every tool it currently has and sort them into the four questions in the table above. Anything that does not fit is either a plan tool, a search tool or something mounted from an MCP server, and asking it which is a good way to discover what you are paying for on every turn.
