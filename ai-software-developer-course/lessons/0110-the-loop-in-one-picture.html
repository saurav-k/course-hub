Module 01 · The internals of coding agents · Lesson 0110

An agent is a while-loop around one API call

foundation 9 min The loop shape below is the one Anthropic documents for its own API. · How tool use works

The one-minute version

  • The loop is keyed on one field: while stop_reason is tool_use, run the tools and send the conversation again.
  • A response carries either text to print or tool calls to run, and often both in the same turn.
  • Tool output goes back in a user message. That is not a workaround; it is how the API represents the round trip.
  • Several tool calls in one turn come back as several results in one message, so parallelism costs one round trip rather than four.

1. The shape, before the code

Thorsten Ball's write-up of building one from nothing puts it in eight words: "It's an LLM, a loop, and enough tokens." The claim is not that agents are simple to make good; it is that the control flow is not where the difficulty lives.

The agent loop is a cycle with exactly one decision in it. Your program sends the request. The response comes back with a stop_reason. If that field says tool_use, your program runs whatever the model asked for, appends the results, and sends the whole conversation again. If it says anything else, the loop is over and you print the text.

2. The same thing in twelve lines

Written out, the loop is unremarkable. Three things in it surprise people the first time, and all three are visible below.

agent.ts, the loop · written for this course, message shapes verified against the Messages API reference · MIT (this repository) · reproduced verbatim
// Keep going while the model is still calling tools.
while (true) {
  const response = await client.messages.create({
    model: MODEL,
    max_tokens: MAX_TOKENS,
    system: SYSTEM_PROMPT,
    tools: TOOLS.map((t) => t.schema),
    messages,
  });

  messages.push({ role: "assistant", content: response.content });
  if (response.stop_reason !== "tool_use") break;

  const toolUses = response.content.filter(
    (b): b is Anthropic.ToolUseBlock => b.type === "tool_use"
  );
  const results = await Promise.all(toolUses.map(runTool));
  messages.push({ role: "user", content: results });
}

First, the assistant turn is appended whole, structured blocks and all, before anything is run. Drop the text block and keep only the tool calls and later turns lose the model's own account of why it did what it did.

Second, the results go back with role: "user". There is no tool role in this API: the documentation is explicit that tool use is integrated "directly into the user and assistant message structure". Your program is speaking on the user's behalf when it reports what a tool returned, which is worth holding on to for module 7.

Third, Promise.all over several tool calls is not an optimisation somebody bolted on. One assistant turn may carry several tool_use blocks, and the rule for answering them is one message: "return one tool_result for each tool_use block, all together in the next user message", matched by tool_use_id. Four reads in one turn cost one round trip.

That last point is worth stating plainly, because it is the difference between a loop that recovers and one that dies. The documented exit is "any other stop reason ("end_turn", "max_tokens", "stop_sequence", or "refusal")". A tool that fails is not one of them.

Notice what the loop does not need. There is no session, no server-side conversation id, no reconnection logic and nothing to clean up if the process dies mid-task, because the entire state of the agent is one array in memory. That is why a harness can offer you a transcript file, a resumable session and a fork of a conversation without any cooperation from the provider: all three are operations on a list you own.

It is also why the loop is the right place to put a rule. A hook that refuses a command, a permission check, a spend ceiling and a log of every call all live on the arc between the model asking and your process acting, and that arc is entirely yours. Nothing in the request can move them, and no wording in the system prompt can talk past them. Modules 4 and 7 are that observation spent.

3. What the loop costs, and why the shape matters

Because the API is stateless, every pass re-sends the whole conversation. So the tokens you pay for over a task are not the size of the final context: they are the sum of every intermediate context, which grows faster than the transcript does.

This is the reason a whole module of this course is about context as a budget, and it is why the next page cares so much about tools that return a slice rather than a file.

Agent or workflow Anthropic's own vocabulary separates two things this course keeps apart. "Workflows are systems where LLMs and tools are orchestrated through predefined code paths", while "agents... are systems where LLMs dynamically direct their own processes and tool usage". The loop above is the second kind: nothing in it decides which tool runs next. For sixteen production loops taken apart side by side, read the turn cycle in Coding Harness Engineering rather than anything here.

4. Play one through

Check yourself

Retrieval practice

Answer from memory before revealing.

Your tool throws an exception while the loop is running. What should the loop do?
A failed tool still produces a result, flagged as an error, and the model reads it and tries something else. The first option throws away the model's only chance to recover. The third repeats a call whose arguments were the problem. The fourth leaves a tool_use block unanswered, which the API rejects: every call needs a result, even one that says it was not run.
A response contains three tool_use blocks. How many messages carry the three results?
All the results go together in the next user message, matched to their calls by tool_use_id. The first two options describe a per-call message, which is what the ordering intuition suggests and what the API rejects. The third has no rule behind it at all. Note that how you run the three is your decision; how you report them is not.

Practice about 15 minutes, with paper

Practice 1foundation

An agent is asked to rename a function across a repository. It lists the tree, greps for the old name, reads four files, edits four files, then runs the test suite and answers.

Count the API calls the loop makes, first if every tool call sits alone in its own turn, and then if the model batches the four reads into one turn and the four edits into another.

Then say which of the two numbers you can influence, and how.

Hint

Count the passes through the while, not the tool calls. Each pass is one API call, and the loop needs one final pass to discover that the model has stopped asking.

Show the worked count
  1. List the tool calls. One list, one grep, four reads, four edits, one test run: eleven calls.
  2. Serial case. Eleven turns each carrying one call, plus one final turn where stop_reason is end_turn: 12 API calls.
  3. Batched case. List, grep, four reads as one turn, four edits as one turn, the test run: five turns of tool use, plus the final one: 6 API calls.
  4. What you can move. Not the eleven tool calls, which the task requires. The number of round trips, by giving the model tools it can call in parallel and descriptions that say so - opencode's read tool ends with "Call this tool in parallel when you know there are multiple files you want to read", which is exactly this lever.

Sanity check. The batched number must be smaller than the serial one and larger than one, and both must exceed the number of turns that carried a tool, because the loop always pays one extra call to learn that it is finished. If you got 11 and 5 you forgot that call.

Your teacher. Ask your agent to run a small task and then tell you how many times it called the model, as distinct from how many tools it ran. If the two numbers are equal, ask it why it never batched anything, and read the answer as a claim about its tool descriptions rather than about its judgement.
