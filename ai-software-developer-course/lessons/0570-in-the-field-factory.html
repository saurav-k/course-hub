Module 05 · Agent-ready codebases · Lesson 0570

One company bet that readiness is measurable, so it shipped a ruler

working 13 min Built only from Factory's own public documentation and posts. No private material, and nobody is named. · Factory: the readiness report command

The one-minute version

  • The bet is that agent-readiness is a property of a repository you can measure, so the model ships as a slash command, an organisation dashboard and an API rather than as a blog post.
  • The command's design decision worth stealing is that it discovers deployable applications first and scores per application, because a monorepo is not one thing.
  • What is published: five levels, nine pillars, three difficulty bands, six detected languages, two scopes, the 80% gate and the aggregation formula. What is not published: the criteria themselves.
  • Take the pillars as a better checklist than you would write from scratch, and take the 80% rule as a good answer to "when am I done with this rung".

1. The bet, and what it commits them to

Factory sells agent-driven development: a coordinator dispatching to specialist agents across the delivery lifecycle, with integrations into the ordinary places work already lives. Its own framing of the market is worth quoting because it is the argument this whole module rests on, from the other side: "Autonomy is a maturation process that is gradual and specific to every organization's readiness and comfort level."

Selling that is a commitment. If autonomy is gated on readiness, and readiness is a property of the customer's own repositories, then the vendor needs a way to say which repositories are ready and what would make the others ready. That is why the ruler exists, and it is why it is a shipped surface with an API rather than a conference slide.

2. Readiness as a command, not a questionnaire

The strongest design decision in the product is that the report is a slash command that runs in the repository, with one prerequisite: a git origin remote, used to associate the report with a project. It runs five steps, and the second one is the one worth stealing.

A second command, /readiness-fix, reads the stored report and works through the failing criteria as an ordinary agent session, with the same review and approval you would give any other run. The interesting part is not the automation. It is that the report is stored, so remediation has something to aim at and a re-run is a before-and-after rather than a second opinion.

3. Readiness as an organisation metric

The dashboard turns the same score into a management surface: an organisation score, a count of repositories tracked, a progress graph over time, and a per-repository table showing level and percentage complete toward the next one. Levels are shown as accordions with a lock status, so a repository can see exactly which gate it is behind.

The organisation score is the mean of the repository levels, rounded down, which lesson 0510 drew. Read as engineering, that is a deliberate decision to report the weakest picture, and it makes one bad repository impossible to hide behind eight good ones. Read as a quarterly target, it is a number that will not move for a year, and pointing an incentive at it is how a useful diagnostic becomes a thing people game.

4. What is published, and what is not

An "in the field" page owes an honest inventory of the evidence, because the difference between a documented mechanism and a vendor claim is the difference between something you can build on and something you can only believe.

Two claims here are vendor claims and one is documented mechanism, and the page should not blur them. KNOWN, because they are in the documentation and checkable: the five levels, the nine pillars, the 80% gate, the two scopes, the six detected languages, the three difficulty bands, the aggregation formula and what the command does. MARKETING, because no method and no data are published behind them: that a higher readiness level produces better agent outcomes, and the customer list that accompanies the general-availability announcement, which carries no numbers at all. For the second class to become evidence, what would have to be published is a study relating a repository's level to an agent's measured success rate on tasks in it. Nothing of that kind exists from this vendor or any other.

5. What to take, whether or not you ever run it

Three things survive the product entirely. The nine pillars are a better checklist than most teams would write unaided, because they include the two categories everybody forgets: task discovery, and the boundary between what an agent may do and what it must ask about. The 80% rule is a good answer to a question checklists usually leave open, which is when you are finished with a rung and may stop. And scoring per deployable application is the single correction that makes any of this true of a monorepo.

What does not survive is the number itself. A level is a summary of a vendor's unpublished criteria; the ten-dimension rubric in lesson 0550 is a summary of criteria you can read. Both are instruments and neither is a verdict.

Check yourself

Retrieval practice

Answer from memory before revealing.

Which part of the published readiness model can a reader not independently apply?
The gate is arithmetic over a set nobody outside the vendor has, which makes it the one rule that cannot be applied from the documentation. The first is a documented formula that anybody with several scores can compute. The second is fully described and is the model's best idea. The third is published as a named three-value axis, so it is applicable even though the assignment of a criterion to a band is a judgement.
Why does the report command discover applications before it evaluates anything?
Discovery establishes the denominator, so a criterion can come back as three of four rather than as a pass. The first inverts the order, since language detection runs first and does not need the boundary. The third is false: the dashboard's table is per repository. The fourth is the most plausible distractor and describes a model that varies its criteria by project type, which this one does not do.

Practice the module assignment, about two hours, spread over two sittings

Module 05 assignmentworking

Goal. Score a repository you actually work in, close the cheapest gap, and prove the fix with a command.

Do all five.

  1. Score your repository against the ten dimensions in lesson 0550. For every score, write the file path or the command that is your evidence. A score with no evidence is a zero.
  2. List every dimension below 2 and rank them by hours to close, not by importance.
  3. Close the cheapest one. Concretely, one of: correct the command block in the root instruction file; add a verify script that is the definition of done; add and document a selectable single-test command; generate an ownership coverage baseline; add annotations and a summary to one CI job.
  4. Re-score that one dimension, with new evidence.
  5. Run an agent on a small real task in the repository, before and after, and record what changed in what it had to ask you.

Hand in one Markdown file: the scored table with evidence, the diff that closed the gap, and a short before-and-after note on the agent run.

This feeds the capstone. It is the readiness baseline for the repository you carry through the course, and the capstone page "close the gaps", read after module 6, is where you take the same score a second time with review running on your pull requests. Dimensions 7 and 8, CI legibility and ownership, are the two that module 6's review workflow plugs straight into.

Hint on step 5, which is the one people skip

"What it had to ask you" is countable without any tooling. Count the messages you sent that were not the original task: a command, a file location, a correction of an environment assumption. That number, before and after, is the only measurement in this assignment that is about the agent rather than about the repository.

Show the self-check, and what a weak submission looks like
  1. The self-check. The fix is real if a fresh agent session, given only the repository and one sentence of task, can run install, test and lint without asking, and can name the one command that says whether it is done. If you had to answer a question, the gap is not closed.
  2. Weak submission one: no evidence column. A table of ten numbers is an opinion with a total. The evidence column is the whole artefact, and it is what makes the second scoring comparable to the first.
  3. Weak submission two: the important gap instead of the cheap one. Choosing observability over a missing test command means step 3 is unfinished, step 4 has nothing to re-score, and step 5 never happens. The ranking in step 2 exists to prevent exactly this.
  4. Weak submission three: no before run. Step 5 has two halves and the first one has to happen before the fix. If you have already closed the gap, run the before-comparison on a second gap rather than reconstructing it from memory.

Sanity check. Your after-count of questions asked should drop by at least one, and if it drops to zero on the first pass, the task was too small to touch the gap you closed. A useful task is one that requires the agent to set up, change and prove, which is the module's definition read backwards.

Your teacher. Ask your agent to read the nine pillars and propose, for your repository, what evidence it would look for under each one. Then ask it which pillars it could not evaluate at all from the repository alone. Its answer to the second question should be two, and if it is more than two you have found something your repository keeps outside the tree.
