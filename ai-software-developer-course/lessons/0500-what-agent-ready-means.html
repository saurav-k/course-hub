Module 05 · Agent-ready codebases · Lesson 0500

A repository is agent-ready when the agent can prove its own work

working 12 min Built on Anthropic's own statement of the verification loop, and on two repositories that publish their agent instructions. · Best practices for Claude Code

The one-minute version

  • Agent-ready is not tidy. It is closeable: the agent can set up, change, and prove the change, without asking a human anything.
  • The property that decides it is a check the agent can run. Without one, "looks done" is the only signal it has, and you become the verification loop.
  • The second property is the perception gap: everything you can see and the agent cannot has to become a file or a command, or it does not exist.
  • Documentation an agent uses is a different artefact from documentation for humans, with a different bar and a different failure mode.

1. The failure is a repository with no oracle

Start from the failure rather than the definition, because you have already watched it happen. An agent works for eleven minutes, edits four files, and finishes by telling you it is done. It is not done. Nothing it did was checked by anything.

Anthropic's own guidance for Claude Code names the mechanism behind that exactly: "Claude stops when the work looks done. Without a check it can run, 'looks done' is the only signal available, and you become the verification loop." The fix is stated just as plainly: give the agent something that produces a pass or a fail, and the loop closes on its own. The oracle is that something: a test suite, a build exit code, a linter, a script that diffs output against a fixture, a screenshot compared against a design. Any of them will do, as long as the agent can run it and read the answer in the same turn.

2. Tidy is not the same as legible

The word people reach for is "clean", and it is the wrong axis. A repository can be beautifully organised for a human reader and still be opaque to an agent, because the two readers want different things. A human reader wants orientation and will tolerate looking around; an agent wants addresses and commands, and every minute it spends looking around is context it no longer has for the task.

ArtefactTidy, for a human readerLegible, for an agent
The READMEExplains what the product is and why it exists.Names the exact install, test, lint and build commands, and nothing else it cannot run.
A screenshotShows the reader the feature working.Unreadable. It has to become a fixture diff or a script that returns an exit code.
The test suiteRuns in CI, which is where it matters.Runs on one file in seconds, because a forty-minute suite is not in the loop.
The architecture docRecords the reasoning behind a decision.Says which directory a new handler goes in, by path.
The onboarding guideA week of context, absorbed once.Charged against the context window on every single turn.
The reframing Documentation an agent uses is a different artefact from documentation for humans, not a shorter version of it. Human documentation is read once by a person who then remembers it. Agent documentation is re-read on every turn by a reader with no memory, and it is paid for in context every time. That is why the good ones are short, imperative and full of exact commands, and why a repository usually needs both files rather than one.

3. The agent cannot see what you can see

The third property is the one that surprises people, and it has a name worth keeping: the agent perception gap. You have a development server running in a second terminal. You can see its stack traces scroll past. The agent cannot, because that terminal is not a file and not a command it ran.

Sentry's own agent instructions solve it in one paragraph, and the solution is the shape of every fix in this module: convert the thing you can see into a thing the agent can read. Their file states plainly that "Agents can't see the devserver terminal", and then names the file to grep instead.

AGENTS.md · getsentry/sentry · licence NOASSERTION · short quoted excerpt
When the devserver runs, its full console output is teed to `.artifacts/dev.log`
(ANSI-stripped, gitignored, truncated per process start; override with
`SENTRY_DEV_LOG_FILE`).

The GitHub API reports no recognised licence for getsentry/sentry, so this course quotes short excerpts with attribution and reproduces nothing longer. The full file is at raw.githubusercontent.com/getsentry/sentry/master/AGENTS.md.

4. The working definition, and what it costs

Put the three together and the definition the rest of this module uses falls out. A repository is agent-ready when an agent can do three things by running commands the repository names: set up, change, and prove. Not "is well documented", not "has good tests": those are means. The property is that all three are reachable without a human.

It has a real cost and the module should say so on the first page. Every one of these artefacts is a file somebody maintains, and a stale one is worse than none: an instruction file naming a command that no longer exists sends the agent confidently into a wall, and it will not question the file. The honest trade is that you are moving effort from answering the same three questions repeatedly to writing them down once and keeping them true.

5. How common is any of this

It is worth knowing how thin the ground is before you assume your own repository is unusual. Five widely-read open-source repositories, swept through the GitHub trees API for the six artefacts this module cares about, disagree with each other on almost every one. Four of the five carry a root AGENTS.md; exactly one ships a development container.

A useful second reading, once the loop is clear: Coding Harness Engineering, context engineering measures what a harness does with repository structure when nobody has told it anything, which is the mechanism under why layout costs tokens at all.

Retrieval practice

Answer from memory before revealing.

Which of these is the single property that makes an agent's loop close without you?
Only a runnable check produces a signal the agent can read inside its own turn. The first and fourth are context: they change what the agent is likely to do and never tell it whether it succeeded. The third is the strongest distractor and it is a different question, because a suite that only runs in CI reports minutes later to a pull request the agent is not reading.
Your dev server prints the error you need in a second terminal. What is the agent-ready fix?
A perception gap closes when the invisible thing gets an address the agent can read. The first works once and closes nothing. The second describes a value that changes every run. The third is the same gap in a new format, because an agent cannot read a picture of a terminal any more than the terminal itself.

Practice about 20 minutes, with a terminal

Practice 1working

Take the repository you chose for the capstone and answer one question about it: can an agent prove a change in it?

Do it by writing down, from memory and without opening the repository, the exact command that would tell an agent whether a change to one file is correct. Then open the repository and check whether that command is written down anywhere an agent would read: the root instruction file, the README, or a script with an obvious name.

Record three things: the command, where it is written down, and how long it takes to run.

Hint

"Written down anywhere an agent would read" is stricter than it sounds. A command that lives in a CI workflow file is written down for CI, not for an agent, and an agent that finds it there has spent a search and several thousand tokens to get it.

Show what the three answers mean
  1. You could not name a command. Then neither can an agent, and the loop in your repository cannot close at all. This is the most common answer and it is what lesson 0520 is about.
  2. You named one but it is nowhere an agent reads. The gap is one paragraph in an instruction file, and it is the cheapest fix in this module.
  3. You named one and it takes longer than about two minutes. The loop exists but its clock is too slow to iterate on, so the agent will run it once at the end rather than after each edit. That is a selectability problem rather than a documentation problem.

Sanity check. If your answer to the third question is a number you had to guess at, you have never watched the agent wait for it, which is itself the finding. Time it once before you decide it is fine.

Your teacher. Ask your agent to make a small change in your repository and, before it edits anything, to tell you exactly which command it intends to run to prove the change. If it cannot name one, ask it what it would need. The list it gives back is your first draft of this module's work.
