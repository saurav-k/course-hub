The cheapest tool is the one you did not add

foundation 11 min Closes the module, and carries its assignment. · Tool search tool

The one-minute version

  • A tool definition is input tokens on every turn of every task, called or not. Mounting is a permanent decision with a recurring bill.
  • It is not only money. Selection accuracy degrades once you exceed 30 to 50 available tools, so a large library makes the model worse at using the tools it needed.
  • Five ordinary servers can cost 55,000 tokens of definitions before the agent does anything.
  • Two moves before the escape hatch: consolidate overlapping tools behind one action parameter, and namespace what remains. Deferred loading is third, not first.

1. Do the arithmetic before the design

The rule from lesson 0200 was that everything in the request counts. Apply it to a tool library and the cost is a product rather than a sum: schema size, times number of tools, times number of turns, times every task you will ever run. Nothing in a transcript shows it to you, which is why teams discover it on an invoice.

2. The part that is not money

If the bill were the whole story you could cache your way out of it. The measured failure is worse: "Claude's ability to pick the right tool degrades once you exceed 30-50 available tools." A library past that point is not a bigger toolbox, it is a harder choice, and the tool you actually needed is now competing with forty near-misses.

The scale of the first problem is published too. "A typical multiserver setup (GitHub, Slack, Sentry, Grafana, and Splunk) can consume ~55k tokens in definitions before Claude does any work." That is five servers a working team plausibly has, and 5.5% of a 1M window spent before the first sentence of the task.

That right-hand pair is the strongest single argument in module 9, where Lesson 0900, "One door for every tool", takes it up as a governance question rather than a budget one: if one endpoint sits in front of every server, the collapse is available to everybody at once and so is the audit log. The measurement is Cloudflare's, in its reference architecture for enterprise MCP deployments, and the two pages are a pair on purpose: this one is why you would want a portal, and that one is what a portal costs.

3. Consolidate before you defer

The first move is free and most teams skip it. Anthropic's guidance is direct: "Rather than creating a separate tool for every action (create_pr, review_pr, merge_pr), group them into a single tool with an action parameter. Fewer, more capable tools reduce selection ambiguity and make your tool surface easier for Claude to navigate."

Note the reason given. It is not "fewer tokens", although it is that too. It is selection ambiguity: three tools whose descriptions each begin "operates on a pull request" force a choice the model has no good basis for, and no amount of rewriting any one of the three fixes a problem that lives between them.

The second move is namespacing, and it costs a prefix. github_search and slack_search are unambiguous where two search tools are not, and the MCP specification's own note is that tool-name uniqueness is only scoped to one server, so an aggregating client "SHOULD implement a disambiguation strategy such as prefixing tool names with a server identifier". Do it yourself and you know what the prefix is.

4. The escape hatch, and when it is worth it

When a library is genuinely large, the platform offers deferred loading: mark a tool defer_loading: true and it stays out of the context window until the model searches for it. Two things about the mechanism are worth knowing before you reach for it. You still send every definition on every request - the API needs them to run the search - so this changes what enters the window rather than what leaves your machine. And at least one tool must stay loaded, normally the search tool itself, with the advice to keep your three to five most-used tools non-deferred so they can be called without a search first.

Reach for it whenDo not, when
you have 10 or more toolsyou have fewer than 10
definitions exceed 10k tokensdefinitions total under 100 tokens
selection accuracy drops as the set growsevery tool is used in every request
you aggregate several servers, 200 or more toolsconsolidation would have removed the problem

The first three rows of each column are Anthropic's stated conditions on Tool search tool, "When to use tool search". The fourth row of the right-hand column is this page's addition, and it is the one that comes first in practice.

The second branch is where module 3 begins. A skill is a folder the agent opens only when the task matches its description, so knowledge costs nothing until it is needed - which is the same problem this page has been circling, solved by a different artefact. A tool is for an action; if what you were about to mount is really a document, you wanted a resource or a skill.

Every mounted server is also a trust boundary, and this page has only priced it. A server's tool descriptions are text that reaches the model on every turn, its results are text the model acts on, and a stdio server runs on your machine as you. Module 7 owns that attack in full, in The agent attack surface; The blast radius is the hub's argument for sizing it before you mount anything. The rule to carry from here: a tool you removed for costing too much has also stopped being an attack surface, which is the only security fix in this course that saves money.

5. The module assignment

This module's assignment runs across all eight lessons and lands in your capstone repository, the one you chose after lesson 0000. The goal is one sentence: give your agent a spec habit and one tool it did not have. It is written out as the practice block below, and its artefacts are the ones module 9 mounts behind a portal and module 7 attacks.

Check yourself

Retrieval practice

Answer from memory before revealing.

You mount a tool that turns out to be useful on one task in twenty. What have you paid?
A tool definition is part of the request, so it is charged whether or not the tool is called, on every turn of every task. The first option prices the call and forgets the definition, which is the whole error this page exists to correct. Nothing prunes an unused tool unless you defer it, and caching changes the price rather than the room, which is lesson 0200's rule.
Your agent keeps calling review_pr when it meant merge_pr. What fixes it?
The ambiguity is between two similar tools, so consolidating them into one with an enumerated action turns a description problem into a schema constraint. Sharpening one description leaves the other one just as close to it. Deferring the pair moves them out of context without making the choice any easier once both are found, and adding a router is a third overlapping description.

Practice the module assignment, about two hours across several sessions

Module 02 assignmentfoundation

Goal. Give the agent working on your capstone repository a spec habit and one tool it did not have.

  1. Pick a small real feature in the repository you chose after lesson 0000.
  2. Run the five moves by hand as four prompts - research, propose two approaches, plan the one you chose, implement - and keep every artefact as a committed file.
  3. Do the Plan move again in a read-only permission mode and diff the two plans. Note where the enforced exploration changed what was proposed.
  4. Write an MCP server exposing one tool your repository actually wants: a test-runner summary, a schema lookup, a deploy-status check. Either language.
  5. Mount it in two clients from committed configuration, .mcp.json and .cursor/mcp.json, and confirm the approval gate fires before the tool is usable.
  6. Rewrite the tool's description under the five principles, then measure: run the same task before and after, and compare turn count and total tokens.

Hand in the four artefacts, the server, both client configurations, and the before-and-after description with its two measurements.

Hint

Do step 6 last and on a task the tool is optional for. If the agent has no other route to the answer it will call the tool whatever the description says, and the measurement will be flat for a reason that has nothing to do with your writing.

Show the self-check, and how this feeds the capstone
  1. The plan is specific enough that the implement prompt is one sentence. If it is not, the plan is where the missing detail belongs, not the prompt.
  2. The server survives being driven by hand. Four raw JSON-RPC requests over stdin, no handshake, and the responses parse. Anything that fails after that is configuration.
  3. The approval gate actually fired. If it did not, find out whether you were in a non-interactive session, because that is the case where nobody is there to withhold trust.
  4. The rewritten description moved a number, or you can say why not. A null result with a stated reason is a pass; an unmeasured claim is not.
  5. Price what you added. Divide the tool definition's length in characters by four, multiply by your turns per week, and decide again whether you would mount it.
  6. Carry it forward. The four artefacts become your capstone's decision record, and the server is the first thing your repository exposes to every agent that touches it. Module 9 puts it behind a portal, and module 7 attacks it.

Sanity check. One tool with a four-sentence description lands around 400 to 700 characters, so roughly 100 to 175 tokens per turn. If the rewrite made the description four times longer and saved no turns, you have bought a permanent cost with a one-off improvement in your own confidence, and reverting it is the right call.

Your teacher. Ask your agent to list every tool currently available to it, with a one-line guess at what each is for, and then to say which three it has never used in your repository. That list is your first consolidation candidate. If you want the arithmetic to land, ask it to estimate the total character length of all its tool definitions and divide by four - most people are surprised by their own setup before they are surprised by anybody else's.
