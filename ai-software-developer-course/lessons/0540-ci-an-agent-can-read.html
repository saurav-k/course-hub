CI output is an API, so make it addressable rather than scrollable

working 7 min Built on GitHub's documented workflow commands and on a shipped ratchet baseline of 2,481 lines. · GitHub: workflow commands

The one-minute version

  • A failing job that produces only a log makes the agent read the log, which costs tokens it cannot spare and gives an answer it has to guess at.
  • An annotation carries file, line, column, title and message as structured output. It is one echo and it is addressable.
  • A job summary is Markdown you append to a file, capped at 1 MiB per step with at most 20 shown per job. It is the right home for the fix command.
  • A ratchet baseline is a committed list of known failures, so a new defect fails and old debt does not, and a fixed recorded failure must also fail or the list never shrinks.

1. Three forms of the same failure

A job can report the identical failure in three ways, and they are not stylistic variants: they differ in whether the next actor can act without re-reading anything.

The syntax for the second row is one line and it is documented as a stable interface. GitHub's workflow commands define ::error file={name},line={line},endLine={endLine},title={title}::{message}, with ::warning and ::notice taking exactly the same parameters, plus col and endColumn. Anything a step prints in that form becomes an annotation attached to the file and line, which is a place rather than a paragraph.

2. What reading a log actually costs

The argument for annotations is usually made on taste. It is better made on arithmetic, because the numbers are not close.

The other half of the interface is the job summary: Markdown appended to the file named by $GITHUB_STEP_SUMMARY, rendered on the run page. Two documented limits shape what belongs in it. Each step is capped at 1 MiB, and content over that fails the upload for that step without failing the job. At most 20 job summaries are shown per job. Both numbers push the same way: a summary is a table of verdicts, not a second copy of the log.

.github/workflows/verify.yml · written for this course · syntax from GitHub Docs, CC BY 4.0
name: Verify
on: [pull_request]

jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5

      - name: Set up the toolchain
        uses: actions/setup-node@v4
        with:
          node-version-file: .node-version
          cache: pnpm

      - name: Install from the lockfile
        run: pnpm install --frozen-lockfile

      # Each finding is emitted as an annotation the agent can act on without
      # re-reading the log: file, line, rule, message.
      - name: Lint
        id: lint
        run: pnpm run lint --format=github

      - name: Type check
        id: types
        run: pnpm run typecheck

      - name: Tests
        id: tests
        run: pnpm test

      # A new failure is red. A failure already recorded in the baseline is not.
      # A recorded failure that has stopped happening is also red, which is the
      # only reason the list ever gets shorter.
      - name: Compare against the recorded baseline
        run: ./bin/ratchet check .ci/known-failures.txt

      - name: Write the summary the agent reads instead of the log
        if: always()
        run: |
          {
            echo "## Verify"
            echo ""
            echo "| check | result | fix with |"
            echo "|---|---|---|"
            echo "| lint | ${{ steps.lint.outcome }} | \`pnpm run lint:fix\` |"
            echo "| typecheck | ${{ steps.types.outcome }} | see the annotations |"
            echo "| tests | ${{ steps.tests.outcome }} | \`pnpm test -- \` |"
          } >> "$GITHUB_STEP_SUMMARY"

Written for this course and complete as shown. The annotation format, the $GITHUB_STEP_SUMMARY file and the two limits above are GitHub's documented interface; GitHub Docs is CC BY 4.0. The fix with column is the part worth arguing for in your own repository.

3. The ratchet, and the half everybody forgets

Turning a check on in a repository with existing debt is where most of these efforts die: the first run is red on two thousand pre-existing problems and gets switched off by lunchtime. The ratchet baseline is the standard answer. Commit a file listing every known failure, fail the build on anything not in it, and the debt stops growing while nobody has to fix it today.

.github/codeowners-coverage-baseline.txt · getsentry/sentry · licence NOASSERTION · short quoted excerpt
# CODEOWNERS Coverage Baseline
# Files lacking CODEOWNERS coverage (sorted)
# Goal: Reduce this list to zero

That header sits on top of 2,481 lines. It is worth looking at what is actually in them, because the shape of a baseline tells you where the ownership gap is rather than merely how big it is.

The half people leave out is the second rule, and without it a ratchet is a permanent excuse. A recorded failure that stops happening must also fail the build. Otherwise nothing ever forces the line out of the file, the list stays at its original length forever, and the goal in the header is decoration.

The design rule A check the agent can use names four things: the file, the line, the rule, and the one command that fixes it. Three of the four are what a linter already knows and merely does not print in a structured way. The fourth is yours to write, once, per check, and it is the one that changes what the agent does next.

Check yourself

Retrieval practice

Answer from memory before revealing.

A recorded failure in your ratchet baseline stops happening. What should the build do?
Failing is the only rule that forces the file to shrink, which is the whole purpose of a baseline over a permanent ignore list. The second option is the intuitive answer and it is exactly how a baseline calcifies. The third makes CI a writer to the branch it is checking, which is a much larger decision than it looks. The fourth produces a signal nobody has to act on, so nobody does.
Which of these belongs in the job summary rather than in an annotation?
The summary is where a whole-run verdict and its remedies belong, because it is one place rather than one per finding. The first, second and fourth are all per-finding facts, and every one of them is a parameter an annotation already carries, so putting them in the summary means the agent has to correlate two outputs instead of reading one.

Practice about 30 minutes, on a real pull request

Practice 1working

Make one of your CI jobs addressable, and measure the difference in what it takes to act on it.

Before: open your most recent red job and count how many lines of log stand between the top and the first line naming a file you would actually open. Multiply by roughly ninety characters and divide by four to get a token figure.

Change: add a job summary step to that one job. Three rows is enough: the check, its outcome, and the command that fixes it.

After: break the same check on a scratch branch and count the characters in the summary.

Hint

You do not need the tool to emit annotations to get most of this. Many linters already have a GitHub output format behind a flag, and where none exists, one echo in the right format from the step's own failure branch is a legitimate first version.

Show a worked before and after
  1. Count the before. Say 1,400 lines precede the first useful one. 1,400 × 90 = 126,000 characters, which is about 31,500 tokens at four characters per token.
  2. Count the after. A three-row summary table with a heading is around 250 characters, or about 63 tokens.
  3. Take the ratio. 31,500 ÷ 63 = 500. The same decision now costs about one five-hundredth of the context, and one echo block bought it.
  4. Notice what changed besides the number. The agent no longer has to decide which part of the log matters, which was the step it was most likely to get wrong.

Sanity check. If your before-count is under a hundred lines, your job is already legible and this exercise has nothing to teach you. Try it on the noisiest job you have instead, which is usually the integration suite.

Your teacher. Point your agent at a red CI run in your repository and ask it, before it looks at any code, to tell you exactly which file and line it would open first and what in the output told it. If its answer is a guess, you have just watched the cost this lesson is about.
