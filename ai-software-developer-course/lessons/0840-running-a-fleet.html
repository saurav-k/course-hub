Ten agents is not one agent ten times

working 10 min Built on git's own worktree contract and GitHub's published merge-queue behaviour. · git-worktree

The one-minute version

  • Four things a fleet contends for: the working tree, the branch, the merge target, and your attention.
  • The first two have one answer, and git enforces it for you: git worktree add refuses a branch another worktree already holds. That refusal is the cheapest lock you will ever get.
  • The merge target has an answer too, and it costs one line in your CI workflow. Without merge_group, a merge queue silently does nothing.
  • Cost is not compute. Runner minutes are pennies; the bill is tokens, and the real ceiling is how many pull requests a person can honestly review.

1. Four contention points

Write them in this order, because each one binds later than the one before it and people plan for them in exactly the wrong sequence.

The working tree. Two agents editing the same checkout is the failure everyone meets on day one, and it is the only one with a complete mechanical fix.

The branch. Two agents on one branch is a race with no winner. Git makes this one impossible rather than merely discouraged.

The merge target. Ten green pull requests against a moving main are not ten mergeable pull requests, because each was tested against a commit that is no longer the tip.

Your attention. Ten runs producing work you cannot read is worse than three runs producing work you can. This one has no mechanism, and it is the one that actually binds.

2. The working tree, and the refusal that is the lock

A linked worktree is a second working directory on one repository. Git's own description: "A repository has one main worktree (if it's not a bare repository) and zero or more linked worktrees", and each one gets "per-worktree files such as HEAD, index". One repository on disk, several checkouts, one object store.

The guarantee is in git's documentation rather than in a convention: "By default, add refuses to create a new worktree when <commit-ish> is a branch name and is already checked out by another worktree". --force "overrides these safeguards", which is exactly the flag a fleet script must never carry.

Two more behaviours make a script worth writing. remove refuses an unclean tree - "Only clean worktrees (no untracked files and no modification in tracked files) can be removed" - so nothing is lost silently when an agent is torn down. And prune cleans up metadata for trees whose directories are gone, which is what happens when somebody deletes a folder by hand.

fleet.sh · written for this course against the git-worktree documentation · CC BY 4.0 · reproduced verbatim
#!/usr/bin/env bash
# fleet.sh - one linked worktree per agent, one branch each.
# git itself enforces the isolation: `git worktree add` refuses a branch
# that another worktree already has checked out. That refusal is the lock.
set -euo pipefail

ROOT="$(git rev-parse --show-toplevel)"
FLEET_DIR="${FLEET_DIR:-$ROOT/../.fleet}"

usage() {
  cat <<'USAGE'
fleet.sh start <task-slug>   create a worktree and branch for one agent
fleet.sh list                show every worktree and the branch it holds
fleet.sh finish <task-slug>  remove the worktree, keeping the branch
fleet.sh sweep               drop metadata for worktrees whose directory is gone
USAGE
}

start() {
  local slug="$1"
  local branch="agent/$slug"
  local path="$FLEET_DIR/$slug"

  mkdir -p "$FLEET_DIR"
  git -C "$ROOT" fetch --quiet origin

  # Refuse early with a readable message rather than letting `add` fail.
  if git -C "$ROOT" worktree list --porcelain | grep -qx "branch refs/heads/$branch"; then
    echo "fleet: $branch is already checked out in another worktree" >&2
    exit 1
  fi

  git -C "$ROOT" worktree add -B "$branch" "$path" origin/main
  echo "$path"
}

finish() {
  local slug="$1"
  # Refuses on uncommitted changes, which is the point: nothing is lost silently.
  git -C "$ROOT" worktree remove "$FLEET_DIR/$slug"
}

case "${1:-}" in
  start)  shift; start "$@" ;;
  list)   git -C "$ROOT" worktree list ;;
  finish) shift; finish "$@" ;;
  sweep)  git -C "$ROOT" worktree prune -v ;;
  *)      usage; exit 1 ;;
esac

Run start twice with the same slug and the second call fails on the branch check. That failure is the demonstration, not a bug to work around.

Supervising several of these from one terminal is a separate problem with its own answer, and this course does not own it: Herdr's sessions, workspaces and panes is the runtime, and Knowing which agent is stuck is the observability half of the fourth contention point.

3. The merge target, and the one line everybody skips

A merge queue is the answer to the third contention. It builds each queued pull request against the target branch plus every pull request ahead of it, on a temporary branch prefixed gh-readonly-queue/, so the branch that gets merged is the one that was actually tested. If a queued pull request fails, it is removed and the temporary branches for the rest are rebuilt without it.

A merge queue is a repository setting rather than a file, so the checked-in half is the workflow that answers it. GitHub's documentation is unambiguous: "You must use the merge_group event to trigger your GitHub Actions workflow when a pull request is added to a merge queue", and without it "The merge will fail as the required status check will not be reported".

.github/workflows/ci.yml · written for this course against GitHub's merge-queue documentation · CC BY 4.0 · reproduced verbatim
name: CI

on:
  pull_request:
  merge_group:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
      - run: npm ci
      - run: npm test
merge_group: is one line and its absence is silent. The queue accepts your pull request, builds its temporary branch, waits for a check that will never be reported, and times out. Nothing warns you, because from the workflow's point of view nothing happened. If a queued pull request never reports a check, this is the first thing to look at and it is usually the only thing.

Two settings on the queue itself are worth knowing before you turn it on, and both have documented ranges. Build concurrency is how many temporary branches are built at once, "between 1 and 100". Merge limits, the minimum and maximum pull requests merged in one group, are also "between 1 and 100". A fleet of ten agents wants a concurrency above one; a repository with a slow test suite wants a maximum group size above one, so that ten pull requests are not ten sequential full builds.

4. The bill, and what is actually on it

Parallel agents cost three separable things, and the one people budget for is the smallest.

That third row is the one that catches people, and it is a different shape from the other two. On Claude Code's cloud sessions "There is no separate compute charge for the cloud VM", so a fleet does not cost more compute - it costs the same account budget your interactive work draws on, at the same time. Devin's unit is the ACU, and Devin's own billing page says enterprise customers "are billed in Agent Compute Units (ACUs) at the rate set in their order form", which means the price is not something you can plan with from the outside.

5. The ceiling is review, and it arrives early

The fourth contention has no mechanism. A pull request that nobody reads is not throughput, and an agent fleet reaches that point long before it reaches any vendor limit.

merged(n) = min(n ÷ d, r) Read as: with n agents, each finishing one task every d hours, against a reviewer who can honestly take r pull requests an hour, the number that actually merges is whichever of the two is smaller. The chart uses d = 2 and r = 2, so the knee sits at n = 4.

Both assumptions are mine and both are arguable. What is not arguable is the shape: production is linear in the fleet and review is not, so a ceiling exists at some n, and it is reached at a smaller number than anybody expects. Measure your own r before you buy a bigger n.

Check yourself

Retrieval practice

Answer from memory before revealing.

Why is git worktree add refusing an already-checked-out branch described here as a feature?
The refusal gives a fleet branch-level isolation with no coordinator, no lock file and no daemon, which is why worktree-per-agent is the standard local pattern. The first option confuses worktrees with the object store, which is shared and unaffected. The second describes a read, and concurrent reads were never the problem. The fourth is a naming convention you impose in your own script - the fleet script here does it - rather than anything git enforces.
You turn on a merge queue and queued pull requests sit forever without their required check reporting. What is the first thing to check?
Without a merge_group trigger the workflow never runs for a queued group, so the required check is never reported and the merge fails on a timeout - which is exactly the symptom described. The second would make the queue slow rather than silent. The third is a real misconfiguration and produces a different symptom: a check that reports and is then ignored. The fourth affects batching and never prevents a check from being reported at all.

Practice about 30 minutes, with a terminal

Practice 1working

Prove the isolation guarantee rather than believing it, then find your own review ceiling.

Part one. Save the fleet script above, run fleet.sh start parser, then run it again with the same slug. Record the exact failure. Then edit a tracked file inside the first worktree and run fleet.sh finish parser. Record that failure too.

Part two. Take the last ten pull requests you reviewed properly - not approved, reviewed - and work out how many hours that took. Divide to get your own r, in pull requests an hour. Then use the formula above to find the fleet size at which your queue stops draining.

Hint

For part two, "reviewed properly" is doing the work in the exercise. A useful test: could you name, from memory, one thing you asked to be changed and why? If not, that review was an approval, and counting it will give you an r that flatters you and a fleet size that does not work.

Show what both parts should produce
  1. The first failure is the script's own message, because the guard runs before git does: fleet: agent/parser is already checked out in another worktree. Delete that guard and git produces its own refusal instead, which is the mechanism the guard is only making readable.
  2. The second failure comes from git. worktree remove refuses a tree with modifications, since "Only clean worktrees ... can be removed". A fleet teardown that passes --force to get past this is a fleet teardown that will one day discard an agent's work without saying so.
  3. A typical honest r is well under two. Ten genuine reviews in eight hours is 1.25 an hour, and with a two-hour task that puts the knee at two and a half agents. That number feels wrong, which is the point of computing it rather than guessing it.

Sanity check. If your computed fleet size is larger than the number of agents you have ever actually run at once, recheck the review figure rather than the arithmetic: an r above three pull requests an hour usually means approvals were counted as reviews.

Your teacher. Ask your agent to run git worktree list --porcelain and explain each field, then ask it what would happen if two of the listed trees named the same branch. The answer it gives you should be that the state is unreachable, and the follow-up worth asking is which command would have had to be forced to produce it.
