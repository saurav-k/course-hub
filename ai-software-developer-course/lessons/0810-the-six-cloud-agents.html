Module 08 · Background agents · Lesson 0810

Six products, one architecture, and three questions that tell them apart

working 8 min Every claim below is read from the vendor's own published documentation, and a blank cell means the vendor publishes nothing. · Jules usage limits

The one-minute version

  • All six clone a repository into a sandbox and hand back a branch, so the architecture is not the differentiator and a table of features would be stale before you finished reading it.
  • Three questions do tell them apart: where the sandbox is, what may start it, and what it may write.
  • A fourth question separates them more sharply than any feature: how much of the operating envelope the vendor publishes at all. One of the six publishes a concurrency number.
  • The skill this page is really teaching: when a limit is not published, plan for the number you can observe, not the one you hope for.

1. Three questions, not a feature list

A product tour goes stale. An axis does not, because it is a question you can put to something that does not exist yet. Three of them cover almost everything that matters operationally.

Where is the sandbox? A provider-managed virtual machine, a runner inside your own CI, or something you host. This decides whose network the agent sits on, who patches the image, and who is billed for the compute.

What may start it? The trigger surface: the set of events that can cause a run. Lesson 0820 argues that this is an authorisation decision, and the size of the surface is the size of the decision.

What may it write? One branch or many, one repository or several, a pull request or a merge. This is the blast radius of a run that goes wrong, and it is the axis vendors state most plainly because it is also their scope limitation.

2. One architecture, six ways in

Draw the architecture once and the six become six labelled arrows into it. That is not a simplification for teaching; it is what the documentation of all six describes. Copilot's cloud agent has "its own ephemeral development environment, powered by GitHub Actions". Cursor's cloud agents run in "isolated VMs in the cloud with full development environments". Jules "runs in a virtual machine where it clones your code, installs dependencies, and modifies files". Codex runs tasks in "isolated cloud environments". Devin's is a cloud workspace with an embedded editor, a shell and a browser. Anthropic's is "an isolated, Anthropic-managed VM".

Four of the six cells in the last column are either blank or a scope statement rather than a number. That asymmetry is the single most useful thing on this page, and it is why the lesson is written on the axes rather than as six product sections.

MARKETING Cursor's documentation states that "You can run as many agents as you want in parallel". No mechanism is shown, no number is given, and no statement is made about what happens when the underlying capacity runs out - so this is a claim rather than a limit, and it cannot be planned against. What would make it evidence: a published concurrency ceiling, or a documented queueing behaviour with an observable signal when you reach it. Until then, measure your own.

4. What to do about a blank cell

An unpublished limit is still a limit. Somebody's capacity planner knows the number and you do not, which means your options are to discover it or to be surprised by it.

Anthropic's statement is a good example of a cell that looks like a limit and is not one: cloud sessions "shares rate limits with all other Claude and Claude Code usage within your account. Running multiple tasks in parallel consumes more rate limits proportionately. There is no separate compute charge for the cloud VM." That tells you the shape of the cost - rate-limit coupling, where parallelism is paid for out of the same account budget your interactive work draws on - without telling you how many sessions is too many. Both halves are useful and only one is a number.

Retrieval practice

Answer from memory before revealing.

Which of these is the strongest reason to compare cloud agents on their trigger surface rather than on their sandbox?
Every one of the six documents the same shape - an isolated machine, a clone, the loop, a pushed branch - so the sandbox is where they agree and cannot be what separates them. The first option overstates it: each vendor publishes a good deal about its sandbox, including image and machine size in two cases. The second is true and irrelevant, since the question is about comparison rather than migration. The third is a performance claim nobody publishes and that this page has no evidence for.
A vendor publishes no concurrency limit. What follows?
Capacity is finite whether or not it is documented, so an unpublished ceiling is a number you do not know rather than a ceiling that does not exist. The first option is the mistake this section exists to prevent. The third confuses your own concurrency controls, which cap runs you start, with the provider's capacity. The fourth is true of the machine and irrelevant to the ceiling: a dedicated VM per session says nothing about how many VMs you may hold at once, and on one of the six the binding constraint is a shared account rate limit rather than compute at all.

Practice about 20 minutes, with vendor documentation open

Practice 1working

Pick the cloud agent your team is most likely to use, and fill in a row of the table above from its own documentation only. Four cells: where the sandbox is, what may start it, what one run may write, and every published ceiling.

Rule: a cell you cannot fill from the vendor's documentation stays blank. Not "probably unlimited", not a number from a blog post, not a figure from a comparison site. Blank.

Then write one sentence per blank cell saying what you would measure to fill it, and how long that measurement would take.

Hint

The "what it may write" cell is usually the easiest to fill and the most valuable, because vendors state scope limitations plainly - they are constraints on the product rather than claims about it. Search their documentation for the words "one", "only" and "cannot" before anything else.

Show a worked row
  1. Sandbox. For the Copilot cloud agent: "its own ephemeral development environment, powered by GitHub Actions". That single sentence also tells you whose minutes are consumed and whose runner image you are on, which no other cell would have told you.
  2. Trigger surface. Assigning an issue, mentioning it on a pull request, Copilot Chat, chat integrations, scheduled or event-triggered workflows, and a security alert assignment. Six entries is a large surface, and lesson 0820 is about narrowing it deliberately.
  3. What it may write. "Copilot can only work on one branch at a time and can open exactly one pull request to address each task", and changes are limited to the repository the task was started in. That is a scope statement precise enough to design around.
  4. Ceilings. "Each Copilot cloud agent session has a maximum execution time of 59 minutes. This is a hard limit that cannot be extended or bypassed." No concurrency number is published, so that cell stays blank, and the measurement is to queue tasks until one waits.

Sanity check. If your finished row has no blanks, check that you did not fill one from a source outside the vendor's own documentation. Across the six products in the table above, four have a blank in the ceiling column, so a row with none is unusual enough to be worth re-reading.

Your teacher. Ask your agent to read one vendor's documentation and produce the four-cell row for you, then check every cell against the page yourself. The disagreements are the interesting part: the usual one is a plausible concurrency number that appears in no vendor document at all.

Primary source to go deeper

The one fully published operating envelope among the six, and the best short illustration of what a vendor can tell you when it chooses to: Jules usage limits. Read it and then try to find the equivalent page for any of the other five.
