Module 07 · Security · Lesson 0770

When the scanner stops being a report and becomes a gate the agent must satisfy

frontier 10 min Built only from Semgrep's own public documentation, engineering posts and open-source repositories. · Semgrep, on hooks in the agent loop

The one-minute version

  • One vendor spans all three scanner families, which makes it the clearest place to see what changes when the reader is an agent rather than a person.
  • Every product answers the same design question: how do you make a finding actionable - a readable rule, a reachability verdict, a local validator.
  • The turn this page is about: the scanner moves from CI into the agent's own loop, as an MCP tool it calls and a hook it cannot finish without satisfying.
  • The published mechanism is one sentence: on stop, scan the changed files, and the agent regenerates until the findings are gone.
  • The most useful thing on their blog is the path traversal they found in their own MCP server, published in their own words.

1. One engine, four products, three questions

Semgrep's own introduction names the family plainly: Code detects vulnerabilities "in your first-party code", Supply Chain detects those "introduced by open source dependencies", Secrets finds "exposed API keys, passwords, and other credentials", and Multimodal supplies "AI-powered security recommendations". The scanner underneath is the same one, and its community edition "supports over 30 programming languages".

That is unusual and it is why this is the useful page to write. The three questions from lesson 0700 normally come from three vendors with three interfaces and three ways of expressing a verdict. Here they share a rule language, which makes the comparison legible: you can see the same design instinct applied to three different noise problems.

Two of those enrichments are worth restating in the vendor's own words, because both come with a limit attached. Reachability sorts a dependency finding into reachable, unreachable or no reachability analysis - and Supply Chain "does not perform reachability analysis" on transitive dependencies. Validation calls the issuing service to decide whether a secret is live, and "All validations, such as API calls, are done locally in your environment. No tokens are sent to Semgrep servers."

That second sentence is a design decision worth noticing. Verification requires touching the credential; doing it locally means the vendor never holds one. A team evaluating any validating scanner should be asking that question first, and this is the shape of a good answer.

2. The scanner becomes a tool the agent calls

Everything so far has the scanner running around the developer: on their machine, or on their pull request. The turn is to put it inside the loop, where the agent calls it mid-task rather than being told about it afterwards. Semgrep ships an MCP server for that, MIT-licensed and open, and reading its tool list tells you exactly what it thinks an agent needs.

3. The strongest published version: a hook the agent cannot finish past

Calling a tool is a choice the model makes, and a choice is not a gate. The stronger mechanism Semgrep publishes uses an editor's hooks instead: afterFileEdit records which files changed, and then, in their own words, "When an agent completes its loop, a stop hook triggers a Semgrep scan on all changed files. The agent is prompted to remediate all findings, and will regenerate code until all findings are fixed."

Read that against lesson 0740 and it is the same idea one level up. A PreToolUse hook decides whether an action happens. A stop hook decides whether the agent is finished. Neither asks the model to be careful; both change what is possible.

The transferable move Nothing here depends on this vendor or that editor. The move is: take the deterministic check you already trust, and attach it to the moment the agent claims to be finished. Your own rule from lesson 0710 and a stop hook from module 4 are enough to build it, and the loop then closes without you in it.

4. The bug they found in themselves

The most useful page a security vendor publishes is one where its own tooling was wrong. Semgrep's security engineer's guide to MCP works through the threat model this module's lesson 0720 covers - tool poisoning, shadowing, rug pulls, ordinary web vulnerabilities in HTTP transports, sampling without isolation - and then reports what they found in their own server: "Our MCP server was (improperly) doing root checking in one codepath that would have allowed you to run Semgrep scans on an arbitrary file."

Sit with what that class of bug is. It is a path check applied on one code path and not another - the plainest, oldest defect in the book, in a security company's own agent-facing service, found by the people who wrote it. Their containerisation limited the blast radius, which is the layered argument from lesson 0740 paying off in somebody else's incident.

The mounting decision has not gone away. An MCP server that scans your code is an MCP server that reads your code, its description enters your context at connection, and it runs with whatever reach you granted it. None of that is an argument against mounting one. It is an argument for mounting it the way lesson 0730 and lesson 0740 describe - reviewed, narrowed, and inside a boundary - and for noticing that the vendor best placed to get this right published a case where it did not.

Check yourself

Retrieval practice

Answer from memory before revealing.

Why is a stop hook a stronger control than exposing the same scanner as a tool the agent may call?
A tool is an option the model may take or skip, and a hook is a condition on the event itself - which is the same distinction as an instruction against a permission rule, one level up. The second option invents a capability difference that does not follow from the mechanism: both run as processes you configured. The third may or may not be true and would not matter. The fourth is true of both, since a tool result and a hook's output both come back as text.
A vendor publishes a path-traversal bug it found in its own agent-facing server. What should you take from it?
The transferable lesson is that a server you mount is ordinary software with ordinary bugs, running with the reach you gave it - so it belongs inside the same boundary as everything else. The first option over-corrects into refusing a useful mechanism. The third takes the containment that limited this one incident as a general guarantee, which the post does not claim. The fourth generalises one bug class into the protocol's main risk, when the same post lists tool poisoning and sampling isolation alongside it.

5. The module assignment

This is the assignment for module 07, and it is the security pass your capstone repository needs before module 8 runs unattended agents against it. Its last step is the one that matters: prove that a rule you wrote no longer fires against a defect you planted.

Practice about 2 hours, with your capstone repository

Module assignmentfrontier

Goal. Plant a vulnerability, catch it three ways, then prove that a permission rule alone does not stop an exfiltration path.

  1. In your capstone repository, add a route that passes a request parameter into a shell-interpreted subprocess call, add a hardcoded credential to a config file, and add one dependency with a published advisory.
  2. Write your own Semgrep rule - not a registry one - that catches the subprocess sink from your route's source. Run semgrep --config ./rules/ . and get exactly one finding.
  3. Add the combined workflow from lesson 0750. Push a branch. Confirm three checks fail, each for its own reason, and that the SCA finding lands on a line in the Security tab.
  4. Write a PreToolUse hook that denies any Bash command containing both a credential path and a network egress verb. Prove it fires.
  5. Now defeat your own hook. Ask the agent to write a two-line script that reads the file and posts it. Record that it succeeds.
  6. Enable the sandbox with denyRead: ["~/"], allowRead: ["."] and an empty allowedDomains. Repeat step 5 and record the exact violation message.
  7. Fix all three planted defects. Confirm CI is green and that your own rule no longer fires.

Hand in. The repository URL, the rule file, the hook script, the two settings states, and a short write-up of steps 5 and 6 with the two transcripts side by side.

Hint

Do step 2 before step 3. A rule that works locally and never runs in CI is the most common way this assignment produces a green pipeline that proves nothing - point the CI job at your rules directory explicitly rather than assuming the registry configuration picks it up.

Show what each step is actually testing
  1. Steps 1 to 3 test that you can tell the three questions apart. Three defects, three scanners, three separate red checks. One aggregate failure means the workflow is one job with three steps, and the first failure is hiding the other two.
  2. Step 4 tests that you can write a deterministic rule. The denial reason you wrote is what the model is told, so write a sentence that tells it what to do instead - a good denial changes the next attempt.
  3. Step 5 is the point of the whole assignment. It must succeed. A hook reads a command string, and the next spelling is always one edit away. If it fails, your regular expression is over-broad and you have proved nothing except that you can block yourself.
  4. Step 6 tests the layer that actually holds. The failure message names a filesystem or network violation rather than a policy decision, because no component decided anything - the read simply returned an error to a child process.
  5. Step 7 closes the loop the module opened. The proof that a fix is a fix is the deterministic check that found the defect, re-run. Not a model's assurance, and not a green tick from a tool whose rule the fix may simply have moved out of reach.

Sanity check. Step 5 must succeed and step 6 must fail. If step 5 fails, the hook is over-broad; if step 6 succeeds, the sandbox is not on - check that the settings file carrying the relative allowRead is the project one rather than your user settings.

Feeds the capstone. Your repository now has a security gate in CI and a checked-in agent policy. Module 8 runs background agents against exactly that, and the open-source contribution track is where the policy stops being theoretical, because the repository at the other end is not yours.

Your teacher. Ask your agent to run your own rule over its own last three changes and report what it finds, then to attach that scan to its stop condition rather than to your review. If it cannot, ask it what in your setup would have to change - the answer is a hook, and you wrote one in lesson 0740.
