Your sentence is the smallest field in the request

foundation 9 min Every field named here is a documented parameter of the Messages API. · Tool use with Claude

The one-minute version

  • One turn is one HTTP request carrying four fields: system, tools, messages, and the model and length settings.
  • You typed the last string of the last message. The other three fields were written by the program you launched, and you can read that program.
  • Everything in the request is charged and budgeted, tool definitions included, and the fixed part is paid again on every turn.
  • Passing tools at all adds a system prompt you never write and never see: 286 tokens on Claude Opus 5, before your first schema.

1. Four fields, and one of them is yours

Here is a complete request body, in the shape the Messages API documents. It is short enough to read in full, and reading it in full is the point of this page.

One request body · written for this course, fields verified against the Messages API reference · MIT (this repository) · reproduced verbatim
{
  "model": "claude-opus-5",
  "max_tokens": 4096,

  "system": "You are a coding agent working in /srv/api.\nRead before you write. Prefer the smallest edit that solves the problem.\nWhen a task is done, say so in one sentence and stop calling tools.",

  "tools": [
    {
      "name": "read_file",
      "description": "Read the contents of a file at a path relative to the working directory. Use it before editing a file so the edit is grounded in what is actually there. Returns the whole file as UTF-8 text. It cannot read directories: use list_files for that.",
      "input_schema": {
        "type": "object",
        "properties": {
          "path": { "type": "string", "description": "Path relative to the working directory, e.g. src/index.ts" }
        },
        "required": ["path"]
      }
    }
  ],

  "messages": [
    { "role": "user", "content": "The parser test is failing. Fix it." },
    { "role": "assistant", "content": [
      { "type": "text", "text": "Let me read the test first." },
      { "type": "tool_use", "id": "toolu_01", "name": "read_file", "input": { "path": "parser_test.go" } }
    ] },
    { "role": "user", "content": [
      { "type": "tool_result", "tool_use_id": "toolu_01", "content": "package parser\n\nfunc TestHeader(t *testing.T) {\n ..." }
    ] },
    { "role": "user", "content": "Run the suite before you tell me it works." }
  ]
}

The last line is the only one you typed. A request is that whole object: one JSON body, sent over one HTTPS connection, answered once. The model has no memory between requests and no access to your disk, so anything it appears to remember is text sitting in messages because your program put it there.

The system field is the system prompt: instructions that sit above the conversation rather than inside it. In a chat box you never see it; in a harness it is assembled at run time from parts, which is lesson 0140.

The tools field is an array of tool definitions, each a name, a plaintext description, and an input_schema that is ordinary JSON Schema. The documentation is blunt about which of the three matters: providing extremely detailed descriptions is "by far the most important factor in tool performance". Lesson 0150 is that sentence taken seriously.

The messages array is the history, and it holds more than the two roles you can see in the transcript. An assistant turn that called a tool is stored whole, structured blocks and all, and the tool's output comes back as a user message. That is not a quirk of this example: it is how the API represents the round trip, and it is the part everyone gets wrong on their first loop.

2. The fixed part is paid on every turn

The reason this matters in practice is arithmetic rather than architecture. Everything in the request counts toward the context window: the system prompt, every message including tool results, and your tool definitions. The whole body is re-sent on every turn, because the API is stateless and the conversation lives in your process.

So the request has two halves with different behaviour. The fixed part - the system prompt and the tool schemas - is roughly the same size on turn one and turn forty. The growing part is messages, which is where a 4,000-line file lands the moment a tool reads one.

3. The system prompt you never wrote

There is a fifth thing in the request that is not a field you can set. When a request carries tools, the API builds a tool-use system prompt out of your definitions and your own system prompt, and sends the concatenation. The documentation publishes the template with its substitution points left as placeholders.

The tool-use system prompt template · Anthropic, "Define tools" · Anthropic documentation, quoted as a short excerpt with attribution · reproduced verbatim
In this environment you have access to a set of tools you can use to answer the user's question.
{{ FORMATTING INSTRUCTIONS }}
String and scalar parameters should be specified as is, while lists and objects should use JSON format. Note that spaces for string values are not stripped. The output is not expected to be valid XML and is parsed with regular expressions.
Here are the functions available in JSONSchema format:
{{ TOOL DEFINITIONS IN JSON SCHEMA }}
{{ USER SYSTEM PROMPT }}
{{ TOOL CONFIGURATION }}

Two things fall out of that template and both are load-bearing for the rest of the module. Your system prompt is inside a larger one rather than being the top of the request, and a tool call is parsed structured text rather than a special channel. The wording is explicit that the output "is parsed with regular expressions", which is the least magical sentence in the whole API.

It also has a price, published per model, and the price is not stable across releases. On Claude Opus 5 a request with any tool at all carries 286 extra system-prompt tokens under the default tool_choice of auto; forcing a tool with any or tool raises it to 406. Two of the tools Anthropic publishes schemas for cost more than that on their own.

Anthropic publishes the template above with {{ FORMATTING INSTRUCTIONS }} and {{ TOOL CONFIGURATION }} left as placeholders, and does not publish what they expand to. So the shape of the assembled prompt is KNOWN and its exact wording is not. Nothing on this page infers the missing text, and neither should you when you are estimating a budget: count the published overhead and treat the rest as opaque.

4. Assemble one yourself

The parts are independent, which is easiest to believe by switching them off. Untick the tool schemas and the request still works and the agent loses every capability at once; untick the history and it works and forgets the task.

Check yourself

Retrieval practice

Answer from memory before revealing.

Your agent read a 300-line file on turn three. On turn nine, where is that file?
The API is stateless, so your program re-sends the whole history each turn and the file travels with it. The first option describes what a reader assumes and no harness does by default. The second confuses caching, which changes the price of those tokens rather than whether they are sent. The fourth describes compaction, which is a separate feature a harness has to ask for.
Which part of the request did nobody on your side of the wire write?
The tool-use system prompt is built by the API out of your definitions, and you can read its template but never set it. The second and third are written by the program you launched, which is not you but is on your side of the wire and is readable. The fourth is written by your own tool handlers.

Practice about 15 minutes, with a terminal

Practice 1foundation

Your harness mounts four tools of your own plus the Anthropic bash and text_editor tools, and its system prompt is 900 characters long. You are on Claude Opus 5 with the default tool_choice.

Estimate the fixed cost of one turn in tokens, before a single message. Your four schemas total roughly 2,000 characters of description and JSON.

Then answer the question that matters: at what number of turns does that fixed cost exceed the whole 4,096-token budget you gave the model for one reply?

Hint

Three of the four numbers are published and one you have to derive. For the derived one, the documented rule of thumb is that a token is about four characters of English. Add the published overheads rather than guessing at them.

Show the worked estimate
  1. Take the published overheads. Tool-use system prompt on Opus 5 at auto: 286. The bash definition: 325. The text_editor_20250429 definition: 700. Total so far, 1,311.
  2. Derive your own two. 900 characters of system prompt at about four characters per token is about 225 tokens. 2,000 characters of schema is about 500. Both are estimates and are marked as such.
  3. Add them. 1,311 + 225 + 500 = about 2,036 tokens before the conversation starts, every turn.
  4. Compare against the reply budget. 4,096 ÷ 2,036 is a little under 2, so the fixed cost passes one whole reply budget on the second turn and keeps going.

Sanity check. Two thirds of the estimate is published rather than derived, so a wrong guess at the character-per-token ratio moves the answer by a few hundred tokens and not by a factor. If your total came out under 1,311 you dropped a published constant, and if it came out over 4,000 you probably counted your schemas in characters.

Your teacher. Ask your agent to print the exact request body it is about to send for one small task, and then to point at which bytes of it you typed. If it cannot, ask it to explain where in its own configuration the system prompt is assembled, and read that file.
