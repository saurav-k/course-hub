Pick a repository that can prove things, then record what it costs you today

frontier 9 min The first of four capstone stops. Nothing here is graded and nothing here is dated. · Run Claude Code programmatically

The one-minute version

  • You have just finished module 1, so you can read a trace. That is the only skill this stop needs, and it is the reason the capstone opens here rather than at the end.
  • Choose the repository by what it can prove: write access, one command that can fail, and enough real history that a change is inconvenient.
  • The baseline is three tasks, not one, chosen for three different shapes of difficulty. One task measures the task; three measure the repository.
  • Record four numbers per task and keep the raw transcript. Everything modules 4, 6 and 8 do is measured against this file, and you cannot go back and take it later.

1. Choose for what the repository can prove

The temptation is to start something clean. Resist it: a fresh repository lets every technique in this course succeed, which teaches you nothing about any of them. A repository is a good capstone when it can contradict you, and four properties are what give it that power.

Write access, because module 4 asks you to commit a hook that blocks and module 8 asks you to let something merge. One command that can fail, because an agent with no failing check cannot tell that it is done, and half of module 5 is about that sentence. History somebody else wrote, because a repository whose every line you remember hides exactly the discovery cost the course exists to measure. And consequence: you should be mildly annoyed to see it broken, or you will not read the diffs.

Scope it to one repository rather than to a whole organisation. Factory's published readiness model, which module 5 works through, splits its criteria into repository-scoped and application-scoped precisely because the two are evaluated differently: a CODEOWNERS file is a fact about the repository, while a linter configuration is a fact about each application inside it. Choosing one repository means every measurement you take has one subject.

2. Three tasks, and why one is not enough

A single task tells you about that task. Three tasks chosen for different shapes tell you about the repository, because the thing that varies between them is what the repository had to supply.

The answered task is one where the repository already says what to do: a change in a well-trodden area with a test beside it. The hidden task is one where the answer exists but is somewhere unobvious - a generated file, an undocumented environment variable, a second config that overrides the first. The unverifiable task is one where nothing in the repository can tell the agent whether it succeeded: a change to a script with no test, a documentation fix, a piece of formatting that only a human notices.

Those three shapes are the three failure modes the rest of the course closes, in order. Module 4 gives the agent an instruction file so the hidden task stops being hidden. Module 5 gives it a check so the unverifiable task stops being unverifiable. Module 8 gives it a pipeline so the answered task stops needing you.

3. Record it so a later you can read it

Watching is not recording. Run each task non-interactively and keep the file, because in six modules' time you will want the transcript rather than your memory of it.

Claude Code's non-interactive mode takes -p with the prompt and --output-format json, and the documentation states that the JSON payload "includes total_cost_usd and a per-model cost breakdown, so scripted callers can track spend per invocation". The same page is explicit that both figures are client-side estimates and can differ from the actual bill, which is exactly the kind of label to carry forward: it is a number good enough to compare against itself, and not good enough to quote at your finance team.

baseline.sh · written for this course against the documented flags · hub content, CC BY 4.0 · reproduce freely
#!/usr/bin/env bash
# baseline.sh - record one capstone task, before anything in this course is applied.
set -euo pipefail

TASK_ID="$1"          # answered | hidden | unverifiable
PROMPT="$2"           # the task, in one sentence
OUT="docs/learning-records/baseline-${TASK_ID}"

mkdir -p "$(dirname "$OUT")"

claude -p "$PROMPT" \
  --output-format stream-json --verbose \
  --allowedTools "Read,Glob,Grep,Edit,Bash" \
  | tee "${OUT}.jsonl"

# The last line of a stream-json run is the result message.
tail -n 1 "${OUT}.jsonl" | jq '{
  session_id, num_turns, total_cost_usd, duration_ms
}' | tee "${OUT}.json"

# Reads and searches that came back before the first edit.
jq -r 'select(.type == "user") | .message.content[]? | select(.type == "tool_result") | "result"' "${OUT}.jsonl" > /dev/null

Four numbers per task, and write them by hand even though the script prints three of them. Turns, because it is the loop's own unit. Reads before the first write, because that is discovery cost and it is the number module 5 moves. Whether anything stopped and asked you, because each stop is a permission decision somebody has already made on your behalf, and modules 4 and 7 are about moving those decisions into files you own. And whether the agent could tell it had finished, which is a yes or a no and is the single most useful line in the whole record.

A baseline measures your repository on the day you took it, and nothing else. It is not a benchmark, it is not comparable to anybody else's, and it is not a measurement of the model: change the model between now and module 8 and the comparison quietly stops meaning what you think it means. Record which model and which harness version produced each trace in the same file, in the sentence rather than as a date, and re-run the baseline rather than reasoning about it if either changes. The only claim this file can support is this repository, these three tasks, this agent, before and after, and that claim is enough.

4. What lands in the repository today

One directory, committed, and it is the deliverable rather than the code around it: docs/learning-records/, holding one short file per capstone stop. Today's file names the repository, the three tasks in one sentence each, the four numbers per task, and the two traces you kept.

Commit it before you read module 2. A baseline that lives in a scratch directory is a baseline that will be gone by module 4, and the whole point of this stop is that it is the only stop you cannot take late.

Check yourself

Retrieval practice

Answer from memory before revealing.

Why does this stop ask for three baseline tasks rather than one good one?
The three shapes - answered, hidden, unverifiable - hold the agent roughly constant and vary what the repository supplies, which is the only way a trace says anything about the repository. The second option treats this as sampling noise, but three is far too few for that and the tasks are deliberately different rather than repeated. The third is true and irrelevant. The fourth invents a structure the course does not have: every later stop re-runs all three.
Your agent finished the task and said so. What does the baseline record?
The fourth question asks whether the agent could close its own loop, and an agent that ends by asserting rather than by running something that could have failed could not. The first two both record your judgement instead of the agent's evidence, which is the substitution the row exists to prevent. The fourth leaves the most valuable row of the baseline empty, and a missing row cannot be compared against anything in module 8.

Practice about 45 minutes, with the repository open

Practice 1frontier

Choose the repository, write the three tasks, and record the baseline.

Write docs/learning-records/0001-baseline.md containing: the repository and why it clears all four properties; the three tasks, one sentence each, labelled answered, hidden and unverifiable; and a four-column table of turns, reads before the first write, permission stops, and could-it-tell-it-was-done.

Keep the raw transcript of at least the hidden task beside it, and name the model and harness version in the file.

Hint

The hidden task is the hard one to invent, because you know your own repository too well. Ask a colleague which thing they always have to explain to a new starter, or look for the last question in your team chat that was answered with a file path.

Show what a filled-in baseline looks like, and the three traps
  1. A row done properly. hidden | 9 turns | 6 reads before first write | 1 permission stop (build) | no, with one sentence naming what it searched for. The sentence is what makes the row readable in six modules' time, and it costs nothing to write now.
  2. Trap one: helping. If you answered a question mid-run, the trace measures you and the agent together. Let it fail, record the failure, and note the question you would have answered - that question is a line of your future AGENTS.md.
  3. Trap two: three tasks of the same shape. Three answered tasks produce three nearly identical rows and no information. If your table has three rows that agree, at least two of the tasks were the same shape.
  4. Trap three: recording the outcome instead of the loop. "It worked" is not a baseline. Every column is a property of the run, and the last one is deliberately about evidence rather than about correctness.

Sanity check. If all three rows answer "yes" to the last column and show few reads, you picked a repository that is already agent-ready, or three tasks that are too small. That is a real finding and it is worth one sentence, but pick a harder set before module 4, because a capstone with nothing to close has nothing to show at module 8.

Your teacher. If the three shapes are hard to tell apart in your own repository, hand your agent the three definitions and ask it to propose one candidate task of each shape from the open issues, naming the evidence for the shape it assigned. Disagree with it out loud: the tasks where you and it disagree about the shape are usually the most informative ones to run.
