The readiness scorecard

10 dimensionsprint-friendly The rubric from lesson 0550 as a sheet you can take into a room. Print it, score one repository, and bring the evidence column rather than the total.

The one-minute version

  • Ten dimensions, scored 0 to 3, maximum 30. Derived from nine published pillars and two vendors' agent guidance; it is nobody's official rubric.
  • One rule makes it work: a score is a file path or a command, never an impression. A dimension with no evidence you can name is a zero.
  • The output is not the number. It is the cheapest dimension below 2, which is a decision; everything else on the sheet is the working behind it.
  • Score it twice. One score is an opinion about a repository; two scores with a change between them is a measurement.
The evidence rule Every point must be evidence you can point at: a path in the repository, or a command you ran and watched succeed. Not "we have decent tests" but bin/qunit path/to/test-file.js, which either runs or does not. Not "setup is documented" but .devcontainer/devcontainer.json, which either exists or does not. A dimension where you cannot name the evidence scores zero, even when you are certain the thing is fine - because "certain the thing is fine" is exactly the state this exercise exists to interrupt.

The sheet

Answer for a repository you actually own. Every fix line is visible whatever you answer, because the fixes are the teaching and the number is only the index into them.

What each band means

The four bands read the same way on every row, and the wording is deliberately about artefacts rather than about quality. A band that describes a feeling is a band two people cannot score the same way twice.

BandOn any dimensionWhat moves you off it
0 · noNothing exists, or nothing exists that you can name.Create the artefact, however roughly. Most of the distance from 0 to 1 is one file.
1 · partlyIt exists, and an agent cannot use it: undocumented, unaddressable, or reachable only by reading configuration and guessing.Write down the exact invocation, in the place the agent already reads.
2 · mostlyDocumented and usable. An agent given the repository and one sentence can reach it.Make it fast and selective, and say in the instruction file which form to use when.
3 · yesDocumented, fast, deterministic, and the instruction file names which to use when.Nothing. Spend the time on a dimension below 2 instead.

Dimension 4 is the one worth seeing written out in full, because it is the dimension where the difference between bands is most concrete: 0 is no tests, or none an agent can run; 1 is the full suite only, and slow; 2 is selectable single-file runs, documented; 3 is selectable, fast, deterministic, and the file says which to run when. Two is where the agent's loop closes. Three is where it closes quickly.

How to use it in a review

  • Fill the evidence column first and the score second. Writing the path is what stops the number becoming a vibe, and it is the column somebody else will argue with.
  • Score dimension 2 last, and score it by running each command from a clean checkout. In most repositories at least one of the six has quietly stopped working, and finding out is worth more than the point it costs.
  • Rank what is below 2 by hours, not by importance. The most important dimension is usually observability, which is a quarter of a platform team's year; the cheapest is usually one paragraph in one file. The loop only turns if the first pass takes an afternoon.
  • Re-score only the dimension you changed. If three other rows moved too, the first pass was careless and the difference means nothing.
  • Report the total as a sum, never as a percentage. Twenty-six of thirty with a 1 on ownership is a specific finding; 87% is not.
  • Take the sheet, not the score, to the meeting. The fix lines are what a room can act on, and they are the reason this page prints.
Agent-readiness and AI-reviewability are different properties, and this sheet does not measure the second one. In the one open benchmark module 6 works through, the most agent-ready repository in the sample was where AI reviewers did worst on recall, and the least agent-ready one was where several scored their best precision. A tidy, well-instructed codebase does not make a machine reviewer better at finding real bugs in it, and there is no published study relating a readiness level of any kind to an agent's actual success rate. So this is a teaching instrument and a work list. It is not a verdict, and a score from it should never be reported as one.
Your teacher. Give your agent the ten rows and ask it to score your repository with a path per point, then score it yourself without looking at its answer. The rows where you disagree are almost always rows where the artefact exists but is not where a first-time reader would look, which is itself the finding.
