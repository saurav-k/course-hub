Terraform determines safe parallel infrastructure provisioning through dependency graph construction and concurrent DAG walkers

foundation 12 min The graph evaluation engine inside HashiCorp Terraform · hashicorp/terraform

The one-minute version

  • Infrastructure provisioning cannot be executed in arbitrary order: a virtual machine cannot be launched before its virtual private cloud (VPC) network exists.
  • HashiCorp Terraform parses HCL into an internal Directed Acyclic Graph (DAG) where each resource is a vertex and resource references form directed dependency edges.
  • To prevent unnecessary serialization, Terraform runs transitive reduction, pruning redundant indirect dependency paths and validating that the graph contains zero circular cycles.
  • The execution engine walks the graph concurrently using a worker semaphore: any vertex whose upstream dependency count reaches zero executes immediately, maximizing parallel cloud API throughput.

1. Representing infrastructure as a graph

In procedural shell scripts, infrastructure creation is rigid: creating 50 AWS resources sequentially can take 20 minutes. But many resources (such as separate subnets in different availability zones, S3 buckets, or DNS records) have zero dependency on each other and can be created simultaneously.

Terraform models cloud resources as mathematical graphs using the internal terraform/dag package. Every resource block becomes a Vertex:

// Foundational graph structures from terraform/dag
type Graph struct {
	vertices Set
	edges    Set
}

type Vertex interface{}

type NamedVertex interface {
	Name() string
}

type Edge struct {
	Source Vertex
	Target Vertex
}

2. Transitive reduction and cycle elimination

When compiling references, graphs often develop redundant edges. Suppose resource $C$ references both $B$ and $A$, while $B$ references $A$:

  • Edge 1: $B \rightarrow A$
  • Edge 2: $C \rightarrow B$
  • Edge 3: $C \rightarrow A$

Because $C$ already depends on $B$, and $B$ depends on $A$, the direct edge $C \rightarrow A$ is redundant. Terraform applies transitive reduction to prune Edge 3. This simplifies the graph topology and prevents scheduler contention.

Next, Terraform verifies that the graph is strictly acyclic using Tarjan's algorithm. If a user writes a circular dependency (e.g. Security Group 1 references Security Group 2, which references Security Group 1), Terraform catches the cycle at compile time before making any destructive cloud API calls.

3. The concurrent DAG walker

In terraform/dag/walk.go, the graph walker executes using an event-driven channel architecture:

// Pattern from terraform/dag/walk.go
type Walker struct {
	Callback WalkFunc
	Reverse  bool

	// Semaphore limits concurrent cloud API requests
	Semaphore *semaphore.Weighted

	graph *Graph
	deps  map[Vertex]int // Pending upstream dependency count
	mu    sync.Mutex
}

func (w *Walker) Walk() error {
	ready := make(chan Vertex, len(w.graph.Vertices()))

	// 1. Enqueue all initial root vertices (in-degree == 0)
	for _, v := range w.graph.Vertices() {
		if w.deps[v] == 0 {
			ready <- v
		}
	}

	// 2. Worker pool consumes ready vertices
	for v := range ready {
		go func(vertex Vertex) {
			_ = w.Semaphore.Acquire(context.Background(), 1)
			defer w.Semaphore.Release(1)

			// Execute cloud resource creation
			w.Callback(vertex)

			// Decrement dependencies for all outgoing targets
			w.notifyDownstream(vertex, ready)
		}(v)
	}
	return nil
}

Why does Terraform build a Directed Acyclic Graph before provisioning resources?
Building a DAG enables Terraform to identify which resources depend on others and which are completely independent, allowing safe parallel execution across multiple goroutines.
What role does transitive reduction play during Terraform graph compilation?
Transitive reduction prunes indirect duplicate edges (if A->B and B->C, a direct A->C edge is redundant), simplifying the execution graph and eliminating unnecessary synchronization locks.
How does Terraform's graph walker know when a resource is ready to provision?
A vertex is ready for execution as soon as its remaining in-degree (pending upstream dependencies) reaches zero, triggering dispatch to the worker goroutine pool.
Systems insight. Whenever you have complex multi-step workflows with interdependencies, avoid hardcoded procedural loops. Build a lightweight DAG package in Go with topological sorting and worker semaphores; it turns slow sequential tasks into highly optimized concurrent pipelines.
