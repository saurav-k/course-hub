Caddy powers automated HTTPS and zero-downtime configuration reloads through unified module lifecycles and socket pool handovers

foundation 12 min Extensible web architecture and automated TLS inside Caddy · caddyserver/caddy

The one-minute version

  • Every component in Caddy 2 is a Module: HTTP handlers, TLS managers, storage drivers, and config adapters all share a standardized lifecycle (Provision → Validate → Cleanup).
  • Caddy democratized the web by embedding certmagic, completely automating ACME certificate issuance, renewal timers, and OCSP stapling with zero manual intervention.
  • When updating configuration via POST /load, Caddy compiles and provisions the new generation first; if any module fails validation, the load is rejected atomically, and the old server stays live.
  • To achieve true zero-downtime reloads without dropping TCP handshakes, Caddy maintains an internal listener pool: new configurations inherit open socket file descriptors from the pool rather than rebinding ports.

1. The unified module lifecycle

Most server architectures separate plugins by category: authentication plugins, logging plugins, storage plugins. Caddy simplifies its entire codebase into a single universal abstraction in caddy.go:

// The universal module contracts from caddyserver/caddy/v2
type Module interface {
	CaddyModule() ModuleInfo
}

type Provisioner interface {
	Provision(Context) error
}

type Validator interface {
	Validate() error
}

type CleanerUpper interface {
	Cleanup() error
}

Any Go struct implementing CaddyModule() can register itself in an init() function via caddy.RegisterModule(). When Caddy starts up or reloads, it walks the module tree and executes lifecycle hooks in strict order:

  1. Provision(ctx): Modules allocate memory, open database pools, and compile regex patterns.
  2. Validate(): Modules check that all required fields are valid and dependencies exist.
  3. Cleanup(): When a configuration generation is replaced, retired modules close sockets and flush disk buffers.

2. Automated HTTPS with certmagic

Before Caddy, setting up HTTPS required generating private keys, creating certificate signing requests (CSRs), running separate cron scripts (like certbot), and reloading NGINX. If a renewal cron job failed, the site went dark with an expired certificate warning.

Caddy solved this natively with certmagic. When Caddy starts:

  • It inspects all hostnames in the routing tree (e.g. example.com).
  • It checks local storage for an existing certificate; if missing or within 30 days of expiration, it contacts Let's Encrypt or ZeroSSL using the ACME protocol.
  • It solves HTTP-01 challenges by intercepting requests on port 80, or TLS-ALPN-01 challenges directly inside the TLS handshake state machine.
  • Renewals run continuously in background goroutines, coordinating distributed file locks across multi-instance clusters.

3. Zero-downtime socket handovers

What happens when a web server tries to reload and open port 443 while the old process is still listening? On POSIX systems, calling net.Listen("tcp", ":443") returns an immediate error: bind: address already in use.

Caddy bypasses this using an internal listener pool. In listeners.go, Caddy tracks active net.Listener instances in a thread-safe registry keyed by network address. When a reload occurs:

  • The new configuration asks the pool for ":443".
  • The pool notices that an active listener already exists, increments its reference count, and hands the live net.Listener directly to the new HTTP server.
  • The new server begins calling listener.Accept() immediately.
  • The old server calls server.Shutdown(ctx), stopping new accepts while allowing existing HTTP connections to finish naturally.

How does Caddy reload configuration without dropping active TCP connections?
Caddy maintains an internal socket pool; new configuration generations inherit existing open net.Listener instances directly rather than closing and rebinding the port.
What happens if a newly loaded Caddy configuration fails validation?
Because Caddy provisions and validates new configurations before swapping them active, a failed configuration is rejected atomically with zero impact on the running server.
How does Caddy's certmagic library automate HTTPS certificate renewals?
certmagic tracks certificate expiration dates in background goroutines, initiating automated ACME HTTP-01 or TLS-ALPN-01 challenges 30 days prior to expiration.
