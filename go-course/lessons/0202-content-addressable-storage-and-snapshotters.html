containerd mounts immutable OCI layer tarballs into writable container root filesystems through content-addressable storage and overlayfs

foundation 12 min The storage and snapshotter engine inside containerd · containerd/containerd

The one-minute version

  • Container images are not monolithic virtual machine disks; they are immutable trees of content-addressed blobs verified by their cryptographic SHA-256 digests.
  • containerd separates blob storage from directory mounting: the Content Store saves raw compressed tarball blobs, while Snapshotters unpack and layer those blobs into file trees.
  • On Linux, the default snapshotter uses overlayfs: stacking read-only parent directories (lowerdir) under a single writable directory (upperdir) with a temporary state directory (workdir).
  • File modifications copy the file up to the upperdir on demand (copy-on-write), and file deletions create specialized character device whiteouts (`0/0` device nodes) without ever altering underlying image layers.

1. Content-Addressable Storage (CAS) in Go

An OCI container image contains no filenames in its storage layout. Everything stored in containerd's content store (located at /var/lib/containerd/io.containerd.content.v1.content/blobs/sha256/) is keyed strictly by its cryptographic hash.

In Go, containerd defines this contract via the content.Store interface in package core/content:

// Pattern from containerd/core/content/content.go
type Store interface {
	Info(ctx context.Context, dgst digest.Digest) (Info, error)
	ReaderAt(ctx context.Context, desc ocispec.Descriptor) (ReaderAt, error)
	Writer(ctx context.Context, opts ...WriterOpt) (Writer, error)
	Delete(ctx context.Context, dgst digest.Digest) error
	Walk(ctx context.Context, fn WalkFunc, filters ...string) error
}

When an image is pulled, containerd streams the incoming HTTP body into a hash-verifying writer (crypto/sha256). If a single byte is corrupted in transit, the calculated digest will not match the requested descriptor, and the transaction is aborted. Because blobs are indexed by content rather than name, two completely different images that share the same Ubuntu base layer store that layer on disk exactly once.

2. The Snapshotter interface and Overlayfs

A compressed layer tarball cannot be directly mounted by the Linux kernel. Before a container can boot, the tarballs must be unpacked into directories and assembled into an active filesystem mount. This is the responsibility of containerd's Snapshotter.

// Pattern from containerd/core/snapshots/snapshotter.go
type Snapshotter interface {
	Stat(ctx context.Context, key string) (Info, error)
	Prepare(ctx context.Context, key, parent string, opts ...Opt) ([]mount.Mount, error)
	View(ctx context.Context, key, parent string, opts ...Opt) ([]mount.Mount, error)
	Commit(ctx context.Context, name, key string, opts ...Opt) error
	Remove(ctx context.Context, key string) error
	Mounts(ctx context.Context, key string) ([]mount.Mount, error)
}

On modern Linux hosts, containerd implements this using overlayfs. Overlayfs combines multiple directories into a single unified mountpoint:

  • lowerdir: A colon-separated list of read-only directories containing the unpacked parent image layers.
  • upperdir: A single writable directory where all runtime file creations, edits, and deletions are isolated.
  • workdir: A private auxiliary directory used by the Linux kernel to stage atomic operations (like rename and copy-up).

3. Copy-on-write and character whiteouts

Overlayfs operations are designed for high performance through copy-on-write (CoW). When a process inside a container opens an existing file for reading, the kernel resolves the path in the top-most lowerdir where it exists, reading directly from the base image.

When the process attempts to write to an inherited file, the kernel intercepts the system call, allocates a new inode in the container's private upperdir, copies the entire contents from the lower layer, and applies the mutation. Subsequent reads and writes hit the copy in upperdir.

What happens when a container runs rm -rf /bin/sh? The container cannot delete the binary from the read-only lowerdir layer. Instead, the Linux kernel creates a whiteout device file in upperdir: a character device with major and minor numbers set to 0/0:

// Creating an overlayfs whiteout device in pure Go
func createWhiteout(path string) error {
	// S_IFCHR | 0666 with dev 0 creates an overlayfs deletion marker
	dev := int(unix.Mkdev(0, 0))
	return unix.Mknod(path, unix.S_IFCHR|0666, dev)
}

When overlayfs traverses the merged directory, encountering a 0/0 character device causes it to hide any matching filename in lower layers, creating the transparent illusion that the file was deleted.

Answer from memory before revealing.

Why are OCI container image layers stored by their cryptographic SHA-256 hash?
Content-Addressable Storage (CAS) keys data by hash, meaning identical layer blobs across different images are downloaded and stored on disk exactly once.
How does an overlayfs snapshotter isolate container writes from the base image?
Overlayfs leaves parent image layers in read-only lowerdirs and directs all writes, file creations, and edits into an isolated upperdir directory.
What happens when a container deletes a file inherited from a lower read-only layer?
Because lower layers cannot be modified, the kernel creates a character whiteout device (dev 0/0) in the upperdir, instructing overlayfs to hide the file from directory listings.
Systems insight. If a container image is 2 GB in size, starting 1,000 containers does not consume 2 TB of storage. Because of overlayfs and CAS, starting 1,000 containers consumes 2 GB for the shared read-only lowerdirs, plus only the small delta of modified files in each container's upperdir.
