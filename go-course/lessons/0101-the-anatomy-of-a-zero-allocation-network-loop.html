Go turns non-blocking epoll events into synchronous goroutine calls through its netpoller and sync.Pool

foundation 12 min High-throughput I/O under Traefik, Caddy, and CoreDNS · traefik/traefik

The one-minute version

  • Go gives developers the illusion of synchronous blocking network I/O, but sets every underlying socket to non-blocking mode (`O_NONBLOCK`).
  • When a read would block (`EAGAIN`), the Go runtime parks the goroutine via gopark() and registers its file descriptor with the operating system’s event loop (epoll on Linux, kqueue on macOS).
  • A background runtime thread polls epoll and calls goready() to awaken the exact goroutine when bytes arrive, freeing operating system threads to run other work.
  • In servers handling 100,000 requests per second, allocating new byte slices for each connection triggers severe garbage collection pauses. Systems like Traefik, Caddy, and MinIO eliminate allocations completely by recycling byte slices using sync.Pool.

1. The illusion of synchronous I/O

In standard C or POSIX programming, network programmers must choose between two models: either dedicate one OS thread per connection using blocking I/O (which collapses under tens of thousands of open connections due to thread stack memory), or write complex asynchronous callback state machines around raw epoll or select.

Go eliminates this tradeoff. To an application developer, reading from a TCP socket looks like ordinary linear code:

buf := make([]byte, 4096)
n, err := conn.Read(buf) // Looks like a blocking system call
if err != nil {
    return err
}

Under the hood, the Go runtime never executes a blocking read system call. When a socket is opened via net.Dial or net.Listen, Go automatically sets the file descriptor to non-blocking mode using fcntl(fd, F_SETFL, O_NONBLOCK) and registers the descriptor with the runtime netpoller.

2. Inside the netpoller: gopark and goready

When conn.Read() is invoked, Go attempts a non-blocking read. If bytes are already present in the kernel socket receive buffer, the call returns immediately with zero delay. But if no data is ready, the Linux kernel returns the error code EAGAIN (or EWOULDBLOCK).

Instead of yielding the operating system thread or spinning in a busy loop, the Go runtime performs a clean context switch:

  1. The socket file descriptor and current goroutine pointer are registered with the runtime’s epoll descriptor via epoll_ctl(EPOLL_CTL_MOD, fd, EPOLLIN|EPOLLONESHOT).
  2. The runtime calls gopark(). This parks the current goroutine, removes it from the processor’s local run queue (the P in Go’s G-M-P scheduler), and assigns the operating system thread (M) to immediately execute another waiting goroutine.
  3. During idle periods or periodic runtime monitoring ticks, the runtime netpoller thread invokes epoll_wait() to fetch descriptors with pending network activity.
  4. For every ready descriptor, the runtime extracts the parked goroutine pointer and calls goready(gp), placing it back onto an active processor run queue.

3. The allocation problem in high-speed servers

While the netpoller solves the concurrency scaling problem, high-throughput network proxies (like Traefik and Caddy) and object stores (like MinIO) quickly run into a secondary bottleneck: memory allocations. If a server receives 50,000 HTTP requests per second, and each connection allocates a fresh 32 KB buffer to read headers and payloads, the application generates 1.6 GB of garbage every second.

The Go garbage collector must constantly trace and reclaim these ephemeral byte slices, stealing CPU cycles from active request handlers and causing latency spikes. To eliminate this overhead, production Go systems use buffer pools via sync.Pool.

package main

import (
	"io"
	"net"
	"sync"
)

// Global pool of reusable 32KB byte buffers
var bufferPool = sync.Pool{
	New: func() any {
		b := make([]byte, 32*1024)
		return &b
	},
}

func handleConnection(conn net.Conn) error {
	defer conn.Close()

	// Acquire buffer from pool without heap allocation
	bufPtr := bufferPool.Get().(*[]byte)
	defer bufferPool.Put(bufPtr) // Guarantee return on exit

	buf := *bufPtr
	for {
		n, err := conn.Read(buf)
		if err != nil {
			if err == io.EOF {
				return nil
			}
			return err
		}
		// Process received bytes (slice view without copying)
		if err := processPayload(buf[:n]); err != nil {
			return err
		}
	}
}

func processPayload(data []byte) error {
	return nil
}

4. Zero-copy transfer: splice and sendfile

In proxies like Traefik or caching file servers like Caddy, data often flows directly from an incoming network connection to an outgoing socket or from disk to a socket. Reading bytes into user-space memory only to immediately write them back out wastes memory bus bandwidth.

The Go standard library detects when source and destination file descriptors support operating system zero-copy primitives. When calling io.Copy(dstSocket, srcFile), Go automatically invokes sendfile(2) or splice(2) through package internal/poll, allowing the Linux kernel to transfer pages directly inside kernel memory buffers without copying bytes into userspace memory.

How does Go's netpoller handle a blocking socket read without blocking OS threads?
When read returns EAGAIN, the runtime parks the calling goroutine via gopark and registers the file descriptor with epoll, allowing the underlying OS thread to execute other goroutines.
Why does using sync.Pool for byte buffers prevent garbage collection pauses?
By reusing existing byte slices instead of allocating new buffers on every request, the application generates zero garbage on the heap, eliminating GC sweep overhead.
What happens to buffers stored in a sync.Pool during a garbage collection cycle?
Objects in a sync.Pool are weakly retained and may be evicted during garbage collection if memory pressure arises, making sync.Pool safe against memory leaks.
Systems insight. When tuning network servers in Go, the two most impactful levers are eliminating per-request buffer allocations with sync.Pool and verifying that your write loops do not trigger small buffer flushes. Profiling with go tool pprof -alloc_space immediately shows whether your net loop is truly zero-allocation.
