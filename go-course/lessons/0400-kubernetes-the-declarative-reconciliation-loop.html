Kubernetes drives cluster convergence through client-go Informers, local Indexer caches, and rate-limited Workqueues

foundation 12 min The control plane loop inside Kubernetes and custom operators · kubernetes/kubernetes

The one-minute version

  • Kubernetes does not execute imperative commands (e.g. "create one pod"); it continuously reconciles observed actual state against declared desired state until they match.
  • To protect the API server and etcd from being overwhelmed by thousands of controllers, client-go uses SharedInformers with a two-phase ListWatch pattern: an initial HTTP List followed by a streaming chunked HTTP Watch.
  • Watched events populate an in-memory Indexer cache (allowing instant local queries via Listers) and push lightweight resource keys (`namespace/name`) into a Workqueue.
  • The Workqueue provides key deduplication (multiple events for the same pod collapse into one work item), exponential backoff rate limiting, and parallel processing locks.

1. Declarative reconciliation vs imperative actions

In classical deployment scripts, provisioning is imperative: createPod(), attachDisk(), startNetwork(). If step 2 fails due to a network timeout, the script crashes, leaving the system in an ambiguous, half-created state.

Kubernetes fundamentally rethinks automation around Level-Triggered Declarative Convergence:

// The universal controller contract in controller-runtime
func (r *DeploymentReconciler) Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error) {
	// 1. Fetch current desired spec and observed status from local cache
	var deploy appsv1.Deployment
	if err := r.Get(ctx, req.NamespacedName, &deploy); err != nil {
		return ctrl.Result{}, client.IgnoreNotFound(err)
	}

	// 2. Count active pods matching deployment selector
	activePods := r.countActivePods(ctx, &deploy)

	// 3. Reconcile delta between desired replicas and observed pods
	if activePods < deploy.Spec.Replicas {
		return ctrl.Result{}, r.createPod(ctx, &deploy)
	} else if activePods > deploy.Spec.Replicas {
		return ctrl.Result{}, r.terminatePod(ctx, &deploy)
	}

	// Desired matches observed; nothing to do
	return ctrl.Result{}, nil
}

The controller does not care whether a pod crashed, was deleted by a user, or was evicted by an OOM killer. On every iteration, it simply measures the delta between what the spec asks for and what exists, and takes a single corrective step.

2. Inside client-go: Reflector, DeltaFIFO, and Indexer

If every controller in a 5,000-node cluster polled the API server every second, etcd would instantly collapse under read load. Kubernetes prevents this using client-go/tools/cache:

  • Reflector: Issues an initial HTTP GET /api/v1/pods to capture a full baseline, extracting the latest resourceVersion token. It then opens an indefinite HTTP stream (GET /api/v1/pods?watch=true&resourceVersion=14920). Every creation, modification, and deletion streams over this single long-lived connection.
  • DeltaFIFO: A specialized thread-safe FIFO queue that buffers incoming deltas (Added, Updated, Deleted, Sync) keyed by object identity.
  • Indexer: An in-memory cache that stores the full Go structs. When a worker invokes lister.Pods(ns).Get(name), the call reads directly from local memory pointers with zero network I/O and sub-microsecond latency.

3. Workqueue: deduplication and rate limiting

Resource event handlers do not pass full object copies to workers. They extract the object's key string (e.g. "prod/payment-service") and push it into a workqueue.RateLimitingInterface.

The Workqueue solves three massive distributed systems challenges:

  • Deduplication: If a deployment's pods crash 50 times in two seconds, the event handler calls queue.Add("prod/payment-service") 50 times. The workqueue maintains an internal set; if the key is already queued, the duplicates are collapsed into a single execution.
  • Parallel Processing Protection: If worker 1 is actively processing "prod/payment-service", the workqueue marks the key as dirty but will not yield it to worker 2 until worker 1 calls queue.Done(key). This guarantees that two worker goroutines never execute concurrent reconciliations for the same resource.
  • Exponential Backoff Rate Limiting: If reconciliation fails (e.g. cloud provider quota exceeded), the key is re-queued with exponential backoff (e.g. 5ms, 10ms, 20ms, capped at 1000s), preventing crash-looping controllers from hammering the API server.

Why does a Kubernetes controller query its local Informer cache instead of the API server?
If hundreds of controllers constantly queried the API server directly, the central database (etcd) would become saturated; reading from local Indexer memory eliminates read pressure.
What happens when five rapid watch events arrive for the same Kubernetes resource?
The client-go Workqueue deduplicates keys; if multiple events arrive for the same resource while it is waiting in the queue, it is processed only once.
What distinguishes declarative reconciliation from imperative command execution?
Declarative reconcilers compare observed state against desired state on every iteration, self-healing any drift regardless of how or why the discrepancy occurred.
Systems insight. The level-triggered reconciliation loop is the single most resilient design pattern in cloud software. Never write an edge-triggered system that assumes every network event arrives in order. Always build your controllers so that reading current state from a cache and applying idempotent convergence produces the correct system state.
