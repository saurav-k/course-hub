Module 03 · Distributed Consensus · Lesson 0300

etcd decouples consensus logic from disk and network I/O through the pure-state-machine Ready channel pattern

foundation 12 min The consensus core of Kubernetes and CockroachDB · etcd-io/etcd

The one-minute version

  • etcd's Raft implementation (go.etcd.io/raft) is one of the most widely copied designs in distributed systems because it contains zero network calls and zero disk writes.
  • Instead of executing I/O, the Raft state machine runs purely in memory and exports a single output channel: <-node.Ready().
  • Each Ready struct informs the outer application loop of entries that must be written to the Write-Ahead Log (WAL), outbound peer messages that must be sent over the network, and committed entries ready to apply to the database.
  • Once the application finishes writing to disk and dispatching network messages, it calls node.Advance() to signal the state machine to proceed, ensuring strict linearizability and deterministic unit testing.

1. Why consensus engines drown in I/O

In classical distributed systems implementations, consensus algorithms (like Paxos or early Raft prototypes) intertwine state transitions with socket calls and file descriptors. A function that increments a term or casts a vote also calls net.Dial() or file.Write().

This coupling introduces severe architectural problems:

  • Non-deterministic testing: Testing edge cases (split brains, dropped packets, slow disk flushes) requires mocking operating system sockets and timers, making edge cases notoriously difficult to reproduce.
  • Thread contention: Network timeouts and disk fsync latencies block core state machine goroutines, creating head-of-line blocking during elections.
  • Zero portability: A Raft engine tied to standard TCP sockets cannot be easily reused by systems using different transports (such as CockroachDB's Multi-Raft gRPC multiplexers).

The architects of etcd resolved this by designing go.etcd.io/raft as a pure, deterministic state machine driven entirely by discrete function steps (Step()) and output notifications (Ready()).

2. The Ready contract

The central interface of the etcd consensus engine is the Ready struct. When internal events occur (such as a heartbeat tick, an incoming proposal, or a peer vote), the state machine prepares a Ready snapshot:

// Pattern from go.etcd.io/raft/v3/node.go
type Ready struct {
	// SoftState contains volatile state: Leader ID and current Role
	*SoftState

	// HardState contains persistent state: Term, Vote, and Commit Index
	pb.HardState

	// Entries must be saved to the Write-Ahead Log (WAL) before sending messages
	Entries []pb.Entry

	// Snapshot specifies the point-in-time snapshot to save to disk
	Snapshot pb.Snapshot

	// CommittedEntries must be applied to the key-value state machine
	CommittedEntries []pb.Entry

	// Messages must be sent to peer nodes over the network
	Messages []pb.Message

	// MustSync indicates whether Entries and HardState must be fsync'd to disk
	MustSync bool
}

3. The driver loop in production

In etcdserver/server.go, etcd runs a dedicated goroutine that processes the Ready channel in an endless loop. Notice how clean and linear the driver loop becomes when the state machine contains no internal I/O:

func runRaftLoop(n raft.Node, wal *wal.WAL, transport Transport, kvStore KV) {
	ticker := time.NewTicker(100 * time.Millisecond)
	defer ticker.Stop()

	for {
		select {
		case <-ticker.C:
			n.Tick() // Drive election and heartbeat timers

		case rd := <-n.Ready():
			// 1. Save uncommitted entries and hard state to disk WAL
			if err := wal.Save(rd.HardState, rd.Entries); err != nil {
				log.Fatalf("failed to save WAL: %v", err)
			}
			if rd.MustSync {
				if err := wal.Sync(); err != nil {
					log.Fatalf("failed to fsync WAL: %v", err)
				}
			}

			// 2. Dispatch network messages to cluster peers
			transport.Send(rd.Messages)

			// 3. Apply committed entries to the user key-value state machine
			for _, entry := range rd.CommittedEntries {
				if entry.Type == pb.EntryNormal && len(entry.Data) > 0 {
					kvStore.Apply(entry.Index, entry.Data)
				}
			}

			// 4. Signal Raft that the batch has landed
			n.Advance()
		}
	}
}

Why does etcd's core Raft package perform no network or disk I/O directly?
By stripping all network sockets, disk operations, and clocks from the Raft package, the consensus engine becomes completely deterministic, making it easy to test and embed in other applications.
In the Ready channel pattern, what must occur before calling node.Advance()?
The application must persist new entries to the Write-Ahead Log (WAL) and send pending messages to peers before calling Advance to confirm the batch is handled.
How does a Raft leader establish that an entry is safe to apply to the KV store?
A proposed log entry is committed only when the leader receives acknowledgements that the entry has been replicated to a majority quorum of nodes.
Systems insight. The Ready pattern is the gold standard for Go systems architecture. Whenever you build complex distributed algorithms, isolate state transitions into a pure data struct that returns commands to execute rather than letting functions perform external I/O directly.
