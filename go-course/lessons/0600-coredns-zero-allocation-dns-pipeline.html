CoreDNS routes high-throughput DNS requests through composable plugin.Handler pipelines and zero-copy binary wire decoding

foundation 12 min The DNS backbone of Kubernetes clusters · coredns/coredns

The one-minute version

  • CoreDNS is the default cluster DNS server in Kubernetes, engineered in pure Go to replace complex C++ DNS stacks like bind and dnsmasq.
  • All server functionality is structured as an ordered chain of plugin.Handler instances: logging, metrics, caching, Kubernetes service discovery, and upstream forwarding.
  • If a plugin can satisfy a request (e.g. cache finding an unexpired record), it writes the DNS response packet and halts the chain; otherwise, it calls plugin.NextOrFailure to delegate to the next handler.
  • Underneath, CoreDNS relies on miekg/dns, using pre-allocated byte slices and zero-copy parsing of the 12-byte binary DNS wire header to process 100k+ QPS per core without GC pauses.

1. The plugin.Handler chain pattern

In many web frameworks, middleware handles HTTP requests via http.Handler. CoreDNS adapts this architectural pattern to the high-performance world of DNS packets via plugin.Handler in coredns/plugin/plugin.go:

// The core interface implemented by every CoreDNS feature
type Handler interface {
	ServeDNS(context.Context, dns.ResponseWriter, *dns.Msg) (int, error)
	Name() string
}

The ServeDNS function receives the incoming parsed DNS message (*dns.Msg) and a dns.ResponseWriter. If the plugin handles the query, it populates the answer section and writes the packet. If not, it hands control to downstream plugins:

// Pattern from coredns/plugin/cache/handler.go
func (c *Cache) ServeDNS(ctx context.Context, w dns.ResponseWriter, r *dns.Msg) (int, error) {
	state := request.Request{W: w, Req: r}
	qname := state.Name()
	qtype := state.QType()

	// 1. Check in-memory LRU cache
	if item := c.get(qname, qtype); item != nil {
		resp := item.toMsg(r)
		w.WriteMsg(resp)
		return dns.RcodeSuccess, nil
	}

	// 2. Cache miss: pass to downstream plugin in chain
	crw := &ResponseWriter{ResponseWriter: w, Cache: c}
	return plugin.NextOrFailure(c.Name(), c.Next, ctx, crw, r)
}

2. Binary DNS wire decoding: miekg/dns

At 100,000 requests per second, allocating new memory objects for every query string causes massive garbage collection pauses. CoreDNS uses Miek Gieben's high-performance miekg/dns library, parsing raw UDP datagrams according to RFC 1035:

// 12-byte DNS wire header layout
// 0               1               2               3
// +-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+
// |                      ID (16 bits)                             |
// +-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+
// |QR|   Opcode  |AA|TC|RD|RA|   Z    |RCODE| (Flags 16 bits)     |
// +-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+
// |                    QDCOUNT (16 bits)                          |
// +-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+
// |                    ANCOUNT (16 bits)                          |
// +-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+
// |                    NSCOUNT (16 bits)                          |
// +-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+
// |                    ARCOUNT (16 bits)                          |
// +-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+

Rather than converting domain names to heap-allocated strings immediately, miekg/dns validates labels directly within the raw byte slice, copying memory only when a plugin specifically mutates or stores the record.

How does CoreDNS structure internal features like caching, metrics, and forwarding?
CoreDNS structures all capabilities as plugins implementing plugin.Handler, chained sequentially in a pipeline configured by the Corefile.
Why does CoreDNS avoid heap allocations when parsing UDP DNS queries?
At high query rates (over 100k QPS), frequent heap allocations trigger Go garbage collection pauses, causing lookup latencies and client timeouts to spike.
What happens when a plugin in the CoreDNS chain cannot answer a query?
If a plugin cannot resolve the query, it invokes plugin.NextOrFailure, transferring execution to the next plugin in the chain.
Systems insight. The Chain of Responsibility pattern used by CoreDNS is ideal for protocol proxies. By keeping the handler interface minimalistic (ServeDNS) and providing a standard next-delegation mechanism, developers can add custom routing and filtering logic without touching core network code.
