etcd guarantees durability through sequential WAL segment framing and multi-version B+tree concurrency in bbolt

foundation 12 min The persistence engine behind Kubernetes state · etcd-io/etcd

The one-minute version

  • Before any proposal is committed or replicated, etcd appends the raw entry to a Write-Ahead Log (WAL) using sequentially framed binary records with CRC32 checksums.
  • To prevent filesystem allocation latency spikes during peak workloads, etcd pre-allocates 64 MB segments on disk using fallocate, turning random fragmentation into sequential disk writes.
  • For key-value storage, etcd does not overwrite data in place; it uses Multi-Version Concurrency Control (MVCC) where every mutation increments a 64-bit cluster revision counter.
  • An in-memory B-tree index (keyIndex) maps human-readable keys to revision numbers, while the underlying data is stored inside bbolt, an embedded zero-copy B+tree database using Linux memory-mapped files (mmap).

1. WAL architecture: framing and pre-allocation

In distributed databases, the Write-Ahead Log (WAL) is the single source of truth. If an etcd node loses power mid-write, memory structures vanish, but the WAL on disk guarantees that uncorrupted entries can be replayed during crash recovery.

etcd structures its WAL files as 64 MB segments in server/storage/wal/wal.go. Every record written to the log is framed with an 8-byte length header followed by a CRC32 checksum:

// WAL record framing layout
// 0               1               2               3
// +-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+
// |                          Length (56 bits)             | Type  |
// +-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+
// |                        CRC-32 Checksum (32 bits)              |
// +-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+
// |                        Record Data (Protobuf)                 |
// +-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+

Why pre-allocate 64 MB? On standard filesystems like ext4 or XFS, extending a file dynamically forces the kernel to update disk metadata (block bitmaps and inode tables). This metadata update can cause write latencies to spike from 200 microseconds to over 100 milliseconds. By calling fallocate() in Go when opening a segment, etcd guarantees all disk sectors are contiguous, allowing the storage hardware to write sequentially at bus speed.

2. Multi-Version Concurrency Control (MVCC)

Traditional key-value stores update values in place: setting key="alice" to "bob" overwrites the previous memory or disk block. In etcd, updating a key never mutates the existing value. Instead, etcd increments a global 64-bit counter called the revision.

Every revision is represented by a pair: {main, sub}. The main revision increments with every committed transaction; the sub revision differentiates multiple operations executed within the same transaction batch.

To balance speed and capability, etcd splits storage into two distinct layers:

  • In-Memory keyIndex: A Google B-tree storing lightweight metadata in RAM. It maps a key (e.g. "/registry/pods/default/web") to an array of revision generations, allowing etcd to find which revisions hold historical values.
  • bbolt Backend: An embedded ACID B+tree database written in pure Go. In bbolt, the primary key is not the string key; the primary key is the binary-encoded revision number, and the value contains the full protobuf payload.
// Excerpt from etcd/server/storage/mvcc/key_index.go
type keyIndex struct {
	key         []byte
	modified    revision // Revision of last modification
	generations []generation
}

type generation struct {
	ver         int64      // Mutation count within this generation
	created     revision   // When key was created
	revs        []revision // All revisions in this generation
}

3. Why bbolt uses memory-mapped files (mmap)

Many databases use complex buffer pool managers with LRU caches to juggle disk pages in user memory. bbolt takes a radical, high-performance approach: it delegates all page caching to the Linux kernel via mmap(2).

When etcd opens bbolt, the database maps the entire file into the process's virtual memory address space. Reading a key is a direct pointer dereference in Go: zero serialization, zero user-space cache copying, and zero allocation. The operating system page cache automatically caches hot pages in physical RAM and pages out cold data when memory is needed.

Because reads hit memory-mapped pages without acquiring database locks, readers in etcd never block writers, and writers never block readers. This provides Kubernetes controllers with instant snapshot reads of thousands of pods without stuttering cluster writes.

Why does etcd pre-allocate 64MB disk files for its Write-Ahead Log segments?
Extending files dynamically requires filesystem metadata updates (block allocation) which cause severe latency spikes; pre-allocating ensures sequential sector writes.
How does etcd's MVCC model support point-in-time historical range queries?
Because mutations never overwrite existing values and are indexed by 64-bit revision numbers, readers can query the exact state of the database at any past revision until compaction runs.
What role does the in-memory keyIndex tree play in etcd's storage layer?
The in-memory keyIndex B-tree maps user string keys to their corresponding revisions, allowing etcd to look up the exact revision keys stored inside the bbolt B+tree.
Systems insight. Because MVCC retains every historical modification, etcd databases grow continuously on disk even if you are only updating the same 10 keys. Production Kubernetes clusters must run automated compaction jobs (e.g. etcdctl compact) and defragmentation (etcdctl defrag) to release empty bbolt database pages back to the filesystem.
