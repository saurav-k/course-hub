The Docker daemon decouples client commands from process execution through an asynchronous multiplexed stream engine

foundation 12 min Inside the Moby engine architecture · moby/moby

The one-minute version

  • The Docker CLI does not manage containers directly; it is a thin REST client communicating over a Unix domain socket (/var/run/docker.sock) with dockerd.
  • Container state is tracked in memory through a strictly synchronized state machine protecting transitions between Created, Running, Paused, and Exited.
  • Interactive terminal sessions (`docker run -it` or `docker exec -it`) use HTTP hijacking: upgrading the HTTP connection into a raw bidirectional TCP stream multiplexed with an 8-byte binary framing header (`stdcopy`).
  • The daemon does not supervise container processes itself; it delegates runtime execution to containerd and detached shim processes, ensuring daemon crashes or restarts do not kill active workloads.

1. Client-server separation in Moby

When you type docker run -d nginx, your terminal process does not fork a web server. The docker binary is a command-line client built in Go that packages your command flags into a JSON payload and makes an HTTP POST request to /containers/create followed by /containers/{id}/start.

The server daemon, dockerd (maintained in the open-source moby/moby repository), listens on a local Unix socket. It handles image pulling, network interface creation, volume attachment, and state persistence, before delegating the physical process creation to containerd via gRPC.

2. The container lifecycle state machine

Inside moby/moby/daemon/container.go, each container is represented by a Container struct wrapped with a mutual exclusion lock (sync.Mutex) and a dedicated State object. Containers transition through discrete states, and invalid transitions return immediate errors.

// Simplified excerpt from moby/moby/container/state.go
type State struct {
	sync.Mutex
	Running           bool
	Paused            bool
	Restarting        bool
	OOMKilled         bool
	Dead              bool
	Pid               int
	ExitCode          int
	Error             string
	StartedAt         time.Time
	FinishedAt        time.Time
	Health            *Health
}

func (s *State) SetRunning(pid int, initial bool) {
	s.Lock()
	defer s.Unlock()
	s.Running = true
	s.Paused = false
	s.Restarting = false
	s.ExitCode = 0
	s.Pid = pid
	if initial {
		s.StartedAt = time.Now().UTC()
	}
}

3. TTY hijacking and the stdcopy framing protocol

One of the most elegant systems patterns in Docker is how interactive sessions work without running SSH daemons inside containers. When you execute docker run -it ubuntu bash, the client needs a full bidirectional terminal connection capable of passing keyboard strokes to standard input while separating output text into standard out and standard error.

Standard HTTP request/response semantics cannot support streaming full-duplex byte streams. To solve this, Docker implements HTTP Hijacking using Go's http.Hijacker interface. Once the HTTP headers are validated, the server extracts the raw underlying net.Conn TCP socket from the HTTP server:

// Upgrading an HTTP connection to a raw hijacked byte stream
hijacker, ok := w.(http.Hijacker)
if !ok {
    http.Error(w, "hijack not supported", http.StatusInternalServerError)
    return
}
conn, bufrw, err := hijacker.Hijack()
if err != nil {
    http.Error(w, err.Error(), http.StatusInternalServerError)
    return
}
// Respond with HTTP 101 Switching Protocols
bufrw.WriteString("HTTP/1.1 101 UPGRADED\r\nContent-Type: application/vnd.docker.raw-stream\r\n\r\n")
bufrw.Flush()

Because stdout and stderr share this single hijacked TCP connection, Docker frames all downstream packets using the pkg/stdcopy protocol. Every chunk is prefixed with an 8-byte binary header:

  • Byte 0: Stream type indicator (0x00 for stdin, 0x01 for stdout, 0x02 for stderr).
  • Bytes 1–3: Reserved zeros.
  • Bytes 4–7: Big-endian 32-bit unsigned integer stating the exact byte length of the payload that follows.

4. Why dockerd does not supervise processes

In early versions of Docker (0.x to 1.10), the Docker daemon was a monolithic parent process that owned all container child processes directly. This created a critical production vulnerability: if the Docker daemon crashed, threw a panic, or was restarted during an operating system upgrade, the kernel terminated every running container on the host.

To eliminate this single point of failure, Docker re-architected its execution model around containerd and detached shim processes. When dockerd starts a container, it requests containerd to spawn an independent process called containerd-shim-runc-v2. The shim acts as the container's parent, holding open its pseudo-terminal file descriptors and exit status pipes.

If dockerd restarts, the containers continue executing undisturbed. When dockerd comes back online, it reconnects to containerd over gRPC and re-attaches to the running shims without losing state.

Why does the Docker daemon use an 8-byte header for multiplexed terminal output?
The stdcopy 8-byte header specifies stream type (stdin, stdout, stderr) and payload size, allowing both output streams to flow over a single hijacked TCP connection without collision.
How does Docker's REST engine maintain an interactive terminal session with a container?
The Docker daemon uses the Go http.Hijacker interface to take ownership of the underlying TCP/Unix socket, upgrading HTTP into a persistent full-duplex byte stream.
What architectural component supervises a container process when Docker daemon restarts?
Each container is parented by an isolated containerd-shim process that holds file descriptors and exit codes, surviving Docker daemon crashes and upgrades.
Systems insight. The separation of client, daemon, supervisor (containerd), and runtime (runc) is the blueprint for modern cloud-native systems. When debugging Docker issues, isolating whether a failure is an API problem (dockerd), an execution problem (containerd), or a kernel isolation problem (runc) saves hours of troubleshooting.
