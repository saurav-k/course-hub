Prometheus TSDB compresses millions of time-series samples into memory-mapped chunks using Gorilla float64 XOR encoding and inverted label posting lists

foundation 12 min The time-series storage engine powering cloud observability · prometheus/prometheus

The one-minute version

  • Storing raw time-series metrics (8-byte timestamp + 8-byte float64 value = 16 bytes per sample) at million-sample ingestion rates consumes terabytes of RAM and disk every week.
  • Prometheus TSDB uses the Gorilla compression algorithm: timestamps are compressed using double-delta encoding ($\Delta(\Delta t)$), while float64 values are bitpacked using XOR differences against previous values.
  • Gorilla reduces 16-byte raw samples down to an average of 1.37 bytes per sample - an astonishing 91% compression ratio achieved in pure Go bit-manipulation routines.
  • Incoming metrics hit an in-memory Head Block backed by a Write-Ahead Log (WAL); every 2 hours, the head cuts an immutable on-disk block queried via memory-mapped files (mmap) with inverted label posting lists.

1. Gorilla compression: double-delta timestamps

In monitoring systems, targets are scraped on regular schedules (e.g. every 15 seconds). This predictable rhythm allows radical timestamp compression:

  1. Let $D = t_n - t_{n-1}$ be the first delta (e.g. 15,000 ms).
  2. Let $D' = (t_n - t_{n-1}) - (t_{n-1} - t_{n-2})$ be the delta-of-deltas.
  3. If the scrape arrived exactly on time, $D' = 0$. Instead of writing a 64-bit integer, Prometheus writes a single bit: 0!
  4. If jitter occurs (e.g. network latency shifts the scrape by 100 ms), $D'$ falls between -63 and 64, fitting into a 2-bit prefix followed by a tiny 7-bit signed integer.

2. Gorilla compression: floating-point XOR encoding

Standard data compression algorithms like gzip or zstd are too slow for real-time streaming ingestion. Prometheus uses bitwise XOR operations ($v_{curr} \oplus v_{prev}$) directly on IEEE 754 float64 representations:

// Pattern from prometheus/tsdb/chunks/xor.go
func (a *xorAppender) Append(t int64, v float64) {
	// 1. Double-delta timestamp encoding
	// ...

	// 2. Float64 XOR value encoding
	valBits := math.Float64bits(v)
	prevValBits := math.Float64bits(a.val)
	xor := valBits ^ prevValBits

	if xor == 0 {
		// Value unchanged: emit single 0 bit
		a.b.writeBit(zero)
	} else {
		a.b.writeBit(one)
		leading := bits.LeadingZeros64(xor)
		trailing := bits.TrailingZeros64(xor)

		if leading >= a.leading && trailing >= a.trailing {
			// Bits fit within previous variable bit window
			a.b.writeBit(zero)
			bitsToWrite := xor >> a.trailing
			a.b.writeBits(bitsToWrite, 64-a.leading-a.trailing)
		} else {
			// New bit window
			a.b.writeBit(one)
			a.b.writeBits(uint64(leading), 5)
			significant := 64 - leading - trailing
			a.b.writeBits(uint64(significant), 6)
			a.b.writeBits(xor>>trailing, significant)
			a.leading, a.trailing = leading, trailing
		}
	}
	a.val = v
}

Because metrics often stay constant or change by small increments, successive floating point numbers share identical sign, exponent, and high-order mantissa bits. The XOR yields large sequences of leading and trailing zeroes, which Gorilla discards.

3. Inverted index and posting lists

How does Prometheus find which time series match http_requests{method="POST", status="500"} among 10 million active series in sub-millisecond time?

In tsdb/index/index.go, Prometheus maintains an inverted index. Each label name and value pair (e.g. method="POST") points to a sorted list of 32-bit Series IDs called a Posting List.

When executing a PromQL query with multiple label selectors, Prometheus fetches the posting lists for each label and computes a set intersection using roaring bitmaps. Because Series IDs are strictly sorted integers, intersection is an $O(N)$ linear walk across CPU cache lines.

How does Gorilla double-delta encoding compress timestamps in Prometheus?
Double-delta encoding measures the change in delta between successive timestamps; when scrapes occur at regular intervals, the delta-of-delta is 0, stored as a single bit.
Why does Gorilla float64 XOR compression compress metrics so effectively?
Consecutive measurements of physical metrics share the same sign, exponent, and upper mantissa bits; bitwise XORing them zeroes out common prefixes, leaving only a small variable bit window.
What role do inverted index posting lists play in Prometheus TSDB?
Posting lists map each label key-value pair to a sorted list of Series IDs, allowing Prometheus to locate matching series via fast set intersections without scanning the database.
Systems insight. Prometheus TSDB demonstrates the power of domain-specific encoding. By recognizing the mathematical properties of time series (regular intervals and small incremental changes), Prometheus achieved 10x better compression and speed than generic databases could ever match.
