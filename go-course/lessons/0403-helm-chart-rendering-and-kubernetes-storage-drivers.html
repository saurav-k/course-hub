Helm coordinates Kubernetes application releases using hermetic template sandboxing, secret-backed storage drivers, and three-way strategic merge patches

foundation 12 min Package management and release engineering in Helm · helm/helm

The one-minute version

  • Helm v3 eliminated the server-side Tiller pod completely, transforming Helm into a pure client-side CLI that coordinates releases directly via k8s.io/client-go.
  • Template compilation uses Go's standard text/template library extended with the Sprig function suite, running hermetically without external shell or filesystem side effects.
  • Release state is stored natively inside Kubernetes: each release revision is serialized into a gzipped, base64-encoded Protobuf payload stored as a Kubernetes Secret in the target namespace.
  • To avoid overwriting runtime mutations (such as Horizontal Pod Autoscalers changing replica counts), Helm applies a three-way strategic merge patch comparing the previous chart, the live cluster state, and the new target chart.

1. Hermetic template rendering in pure Go

Rather than introducing a custom domain-specific language (DSL), Helm builds on Go's built-in text/template engine. In pkg/engine/engine.go, Helm wraps template execution in a sandboxed runtime, injecting values, release metadata, and over 100 helper functions from the open-source Sprig library.

// Pattern from helm/pkg/engine/engine.go
func (e *Engine) Render(chrt *chart.Chart, values chartutil.Values) (map[string]string, error) {
	t := template.New(chrt.Name()).Funcs(e.FuncMap)

	// Add all chart templates to the Go template set
	for _, file := range chrt.Templates {
		if _, err := t.New(file.Name).Parse(string(file.Data)); err != nil {
			return nil, fmt.Errorf("parse error in %s: %w", file.Name, err)
		}
	}

	rendered := make(map[string]string)
	for _, file := range chrt.Templates {
		var buf bytes.Buffer
		if err := t.ExecuteTemplate(&buf, file.Name, values); err != nil {
			return nil, fmt.Errorf("render error in %s: %w", file.Name, err)
		}
		rendered[file.Name] = buf.String()
	}
	return rendered, nil
}

To keep rendering hermetic and deterministic across team members and CI pipelines, Helm strictly restricts template execution: templates cannot execute external processes, read arbitrary local files outside the chart tarball, or access network sockets.

2. Secret-backed release storage

Where does Helm remember what is currently installed in the cluster? In Helm v2, this state was managed by an in-cluster pod named Tiller. Helm v3 abolished Tiller, delegating all state persistence directly to Kubernetes itself.

In pkg/storage/driver/secrets.go, Helm implements a storage driver using standard Kubernetes v1.Secret resources:

  • Each release revision creates a dedicated Secret named sh.helm.release.v1.{release-name}.v{revision}.
  • The release payload (containing release history, raw manifests, and values) is marshaled to binary Protobuf, compressed with gzip, and base64-encoded into the Secret's data.release field.
  • Secrets are labeled with owner=helm and name={release-name}, allowing instant retrieval via Kubernetes label selectors without external databases.

3. The three-way strategic merge patch

Consider what happens during a chart upgrade using a naive two-way diff between old chart and new chart:

  1. Your chart originally specified replicas: 2.
  2. A Horizontal Pod Autoscaler (HPA) observed high traffic and scaled the deployment live in Kubernetes to replicas: 10.
  3. You update the container image tag in your chart and run helm upgrade.

If Helm performed a naive two-way overwrite, it would reset replicas back to 2, causing an immediate service outage during peak traffic!

By computing a three-way strategic merge patch between (1) the original chart manifest, (2) the live API server state, and (3) the new chart manifest, Helm accurately distinguishes between intentional chart changes and runtime controller mutations.

Why does Helm perform a three-way strategic merge patch during chart upgrades?
A three-way merge compares the original chart, the live cluster object, and the target chart, ensuring runtime modifications (like HPA scaling) are not accidentally overwritten.
Where does Helm v3 store release history records and revision manifests?
Helm v3 persists release records as gzipped, base64-encoded Protobuf payloads directly inside standard Kubernetes Secrets in the application namespace.
What mechanism does Helm use to render dynamic Kubernetes manifest files?
Helm renders manifests using Go's built-in text/template package enriched with over 100 mathematical, cryptographic, and string functions from the Sprig library.
Systems insight. By eliminating the central Tiller server in Helm v3, Helm embraced the UNIX philosophy: do one thing well as a stateless client tool. Storing state directly in the system you manage (Kubernetes Secrets) eliminates synchronization drift between the manager and the managed platform.
