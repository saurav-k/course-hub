Module 01 · Kernel Primitives · Lesson 0100

Go manipulates Linux namespaces, cgroups, and syscalls directly through os/exec and sys/unix

foundation 12 min The substrate under Docker, containerd, and runc · moby/moby

The one-minute version

  • Containers do not exist as kernel entities; a container is an ordinary Linux process wrapped in namespaces for visibility and cgroups for resource quotas.
  • In Go, process isolation begins before `execve` by configuring syscall.SysProcAttr with clone flags like CLONE_NEWPID, CLONE_NEWNS, and CLONE_NEWNET.
  • Control groups (cgroups v1 and v2) are not managed via custom syscalls; Go daemons read and write plain text files in the virtual /sys/fs/cgroup filesystem tree.
  • The Go runtime’s multi-threaded scheduler creates a severe obstacle for namespace manipulation: Go threads share kernel state, forcing tools like runc and containerd to use Cgo constructors or re-exec binaries before the Go runtime fully initializes.

1. The illusion of the container

There is no Linux system call named create_container(). Every container running under Docker, Kubernetes, or containerd is an ordinary Linux process spawned by the Linux kernel via clone(). What makes a process look and feel like an independent virtual machine is the selective restriction of what that process can see and what resources it can consume.

Visibility is governed by namespaces. Resource consumption is governed by control groups (cgroups). File system hierarchy is governed by mount namespaces and pivot_root. In the Go ecosystem, systems like Docker (Moby) and containerd do not rely on heavy hypervisors; they orchestrate these exact kernel primitives directly through Go's os/exec, syscall, and golang.org/x/sys/unix packages.

2. Configuring namespaces via SysProcAttr

When launching a child process in Go using the standard library's os/exec.Command, you can supply low-level operating system attributes via the SysProcAttr struct. On Linux systems, this struct exposes Cloneflags, which maps directly to the flags accepted by the clone(2) system call.

package main

import (
	"os"
	"os/exec"
	"syscall"
)

func createIsolatedProcess() *exec.Cmd {
	cmd := exec.Command("/bin/sh")
	cmd.SysProcAttr = &syscall.SysProcAttr{
		Cloneflags: syscall.CLONE_NEWUTS | // Hostname isolation
			syscall.CLONE_NEWPID |  // Process ID tree isolation
			syscall.CLONE_NEWNS |   // Mount namespace isolation
			syscall.CLONE_NEWNET |  // Network devices and routes
			syscall.CLONE_NEWIPC,   // System V IPC and POSIX message queues
	}
	cmd.Stdin = os.Stdin
	cmd.Stdout = os.Stdout
	cmd.Stderr = os.Stderr
	return cmd
}

When the kernel creates the process, CLONE_NEWPID causes the child to become PID 1 inside its own private process tree. Outside on the host system, the process receives an ordinary PID (e.g. PID 48210). If the child calls ps aux, however, it will still see host processes until its mount namespace is populated with a fresh /proc filesystem mount.

3. Managing cgroups through the filesystem tree

While namespaces partition what a process can see, control groups (cgroups) dictate how much CPU time, physical memory, and I/O bandwidth that process is permitted to consume. Linux implements cgroups as a pseudo-filesystem mounted at /sys/fs/cgroup.

To place a process into a cgroup, a Go daemon does not invoke an esoteric system call. Instead, it interacts with standard file I/O: creating directories and writing process IDs into control files. In modern cgroups v2, assigning limits is purely a matter of file manipulation:

package main

import (
	"os"
	"path/filepath"
	"strconv"
)

func attachProcessToCgroup(cgroupPath string, pid int, memoryLimitBytes int64) error {
	// Create cgroup hierarchy directory
	if err := os.MkdirAll(cgroupPath, 0755); err != nil {
		return err
	}
	// Set memory high water mark (e.g. 512 MB)
	memFile := filepath.Join(cgroupPath, "memory.max")
	if err := os.WriteFile(memFile, []byte(strconv.FormatInt(memoryLimitBytes, 10)), 0644); err != nil {
		return err
	}
	// Attach the process by writing its PID to cgroup.procs
	procsFile := filepath.Join(cgroupPath, "cgroup.procs")
	return os.WriteFile(procsFile, []byte(strconv.Itoa(pid)), 0644)
}

Once a process ID is appended to cgroup.procs, all future child threads and spawned processes automatically inherit membership in that control group. If the process exceeds its memory quota, the kernel's Out-Of-Memory (OOM) killer terminates the process group without destabilizing the host.

4. The fork/exec dilemma in multi-threaded Go

In standard C, setting up a container follows a clean sequence: call fork(), configure namespaces and mounts in the child process, and then call execve(). In Go, this pattern presents a notorious design challenge.

The Go runtime is inherently multi-threaded. It launches background OS threads for the garbage collector, network poller, and G-M-P work-stealing scheduler. Linux system calls like setns() and unshare() operate on the calling OS thread, not on the process as a whole. If a goroutine calls setns() on OS thread M1, and the Go scheduler later moves that goroutine to OS thread M2, the goroutine loses its namespace context!

Furthermore, executing raw fork() in a multi-threaded process is dangerous in POSIX: only the calling thread is duplicated, leaving locks held by other threads permanently deadlocked in the child. To solve this, low-level container runtimes written in Go (such as runc) employ a specialized architecture:

  • Cgo constructor hooks: runc embeds a C constructor (__attribute__((constructor)) void init(void)) in package libcontainer/nsenter. This C code executes before the Go runtime boots, while the process is still single-threaded, safely calling setns() and clone().
  • Self-re-exec: The Go process re-executes its own binary (/proc/self/exe) with special environment variables, jumping directly into container setup before the full Go runtime scheduler starts competing for OS threads.

Retrieval practice

Answer from memory before revealing.

Why can a Go goroutine not safely call setns to switch namespaces during runtime?
Linux namespaces are thread-bound kernel objects; because Go's G-M-P scheduler can transparently migrate a goroutine to a different OS thread (M), the goroutine will silently lose the namespace context of the original thread.
How does containerd write resource limits to cgroups v2 on modern Linux hosts?
Cgroups are exposed to userspace as a virtual filesystem mounted at /sys/fs/cgroup; limits like memory.max and cpu.max are configured by opening and writing plain text numeric values to those files.
What role does the OCI runc Cgo constructor play during container startup?
runc uses a C constructor function (__attribute__((constructor))) in libcontainer/nsenter to execute namespace configuration before the multi-threaded Go runtime boots.
Systems insight. Every container abstraction you interact with in Kubernetes or Docker is ultimately a series of file descriptor manipulations and clone flags in Go. When debugging container startup latency or OOM kills, look directly at /sys/fs/cgroup and the process's /proc/[pid]/ns links rather than searching through abstraction layers.
