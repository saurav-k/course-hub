Module 04 · Workload Orchestration · Lesson 0402

Nomad achieves extreme scheduling throughput through parallel optimistic evaluation workers and transactional plan commits

foundation 12 min High-throughput cluster scheduling in HashiCorp Nomad · hashicorp/nomad

The one-minute version

  • Pessimistic schedulers lock cluster nodes while computing placements, creating severe head-of-line bottlenecks as cluster size and scheduling frequency grow.
  • HashiCorp Nomad uses Optimistic Concurrency Control (OCC): parallel scheduler worker goroutines evaluate placement plans concurrently against in-memory state snapshots without locking machines.
  • State changes are buffered in an Evaluation Broker, a thread-safe priority queue that distributes evaluations across scheduler workers according to job priority and type.
  • Each worker submits an allocation Plan to the Raft leader. The leader commits the plan transactionally; if a resource conflict is detected (e.g. another worker claimed the same CPU cores), the loser's plan is rejected and re-evaluated immediately.

1. Why pessimistic scheduling fails at scale

In centralized cluster architectures, a scheduler locks the target node, checks CPU and memory availability, binds the container, and releases the lock. While simple, this serializes all decisions through a single thread.

When deploying 100,000 tasks across 10,000 nodes, pessimistic locking spends more time waiting on mutexes than computing optimal bin-packing algorithms. Nomad breaks this bottleneck by adopting Google's Omega scheduling paradigm: optimistic evaluation with transactional commit.

2. The Evaluation Broker

Whenever an event occurs (a job is submitted, a deployment is rolled out, or a machine crashes), Nomad creates an Evaluation. Evaluations encapsulate the intent to reconcile a specific job.

In nomad/nomad/eval_broker.go, Nomad maintains a specialized, thread-safe priority queue called the EvalBroker:

// Pattern from nomad/nomad/eval_broker.go
type EvalBroker struct {
	// Priority queues indexed by scheduler type (service, batch, system)
	pool map[string]*priorityQueue

	// In-progress evaluations currently being processed by workers
	inProgress map[string]*structs.Evaluation

	// Unblocks worker goroutines when work arrives
	readyCh chan struct{}
	mu      sync.RWMutex
}

func (b *EvalBroker) Dequeue(types []string, timeout time.Duration) (*structs.Evaluation, error) {
	// Dequeue highest priority evaluation matching worker capabilities
	b.mu.Lock()
	defer b.mu.Unlock()

	for _, schedType := range types {
		if eval := b.pool[schedType].Pop(); eval != nil {
			b.inProgress[eval.ID] = eval
			return eval, nil
		}
	}
	return nil, ErrNoWork
}

3. Parallel planning and conflict detection

Multiple scheduler workers dequeue evaluations simultaneously. Each worker evaluates placement against an immutable snapshot of cluster state, calculating the optimal node placements based on constraints, affinities, and bin-packing algorithms.

Once placement is determined, the worker generates a Plan. The plan is not written to the node; it is submitted to the Raft leader's plan queue.

Because node conflicts are rare in large clusters (the probability of two workers picking the exact same node at the exact same millisecond is small), over 99% of plans commit on the first try. This architecture allowed Nomad to schedule 2 million containers across 61 host regions in under 22 minutes.

Answer from memory before revealing.

Why does Nomad use optimistic concurrency instead of pessimistic locking during scheduling?
Optimistic concurrency allows multiple worker threads to evaluate placement plans simultaneously against state snapshots without lock contention.
What happens when two Nomad scheduler workers propose placing tasks on the same node CPU?
The Raft leader commits the first plan that arrives; the second conflicting plan is rejected and its evaluation is re-enqueued to re-evaluate with fresh cluster state.
What role does Nomad's Evaluation Broker play in cluster orchestration?
The Evaluation Broker maintains prioritized queues of evaluations, feeding work to available scheduler goroutines based on job type and priority.
Systems insight. Contrast Nomad with Kubernetes: Kubernetes separates concerns across multiple decoupled controllers (deployment controller, replicaset controller, scheduler), using workqueues and informers. Nomad centralizes scheduling through parallel evaluation workers coordinated by a transactional Raft leader, maximizing raw allocation velocity.
