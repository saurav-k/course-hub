Module 02 · Container Runtimes · Lesson 0201

containerd decouples container runtimes through the v2 shim API and a topic-based TTRPC event bus

foundation 12 min The runtime backbone under Docker and Kubernetes CRI · containerd/containerd

The one-minute version

  • containerd is the industry-standard container supervisor, sitting directly between high-level engines (Docker, Kubernetes CRI) and low-level kernel runtimes (runc, Kata, gVisor).
  • To eliminate daemon failure coupling, containerd uses the Shim v2 pattern: every container (or Kubernetes pod) is parented by an independent, lightweight Go process that holds its standard I/O pipes and exit status.
  • Because standard gRPC incurs substantial memory and reflection overhead when multiplied across hundreds of shims per node, containerd engineers invented TTRPC, a stripped-down RPC protocol optimized for low memory footprints over Unix sockets.
  • State transitions (creation, start, OOM, exit) are broadcast through an internal topic event bus, allowing consumers to react asynchronously without polling container state.

1. Why the shim exists: the subreaper pattern

In Unix systems, when a parent process exits, its orphan child processes are automatically reparented to PID 1 (usually systemd or init). If containerd were the direct parent of all containers, restarting containerd would leave container processes orphaned and reaped by PID 1, severing their stdio file descriptors and losing exit codes.

To solve this, Linux provides the PR_SET_CHILD_SUBREAPER system call (accessible in Go via unix.Prctl(unix.PR_SET_CHILD_SUBREAPER, 1, 0, 0, 0)). When containerd spawns a container, it first forks a tiny dedicated daemon: containerd-shim-runc-v2. The shim sets itself as a subreaper, invokes runc to construct the container namespaces, and remains alive as the container's permanent parent.

The shim performs three critical duties:

  • It holds open the container's stdin, stdout, and stderr FIFOs or pseudo-terminal (pty) master file descriptors even if containerd restarts.
  • It waits on the container process using wait4(), capturing the exit code without letting zombie processes leak into the operating system table.
  • It serves a local Unix domain socket implementing the Shim v2 Task API over TTRPC.

2. TTRPC: stripping gRPC for low-memory shims

Standard gRPC in Go is feature-packed: it includes HTTP/2 framing, dynamic name resolution, TLS negotiation, and reflection. However, running a standard gRPC server inside 200 shims on a single Kubernetes node would consume over 3 GB of RAM just for RPC plumbing.

To keep the shim's memory footprint under 3 MB, containerd authored TTRPC. TTRPC replaces HTTP/2 with a simple binary protocol:

// TTRPC message frame layout (10-byte header)
// 0               1               2               3
// +-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+
// |                          Length (32 bits)                     |
// +-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+
// |           Stream ID (16 bits) |   Type (8)    |   Flags (8)   |
// +-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+
// |                        Payload (Protobuf)                     |
// +-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+

By compiling Protocol Buffers into code that reads and writes this compact binary header directly over Unix domain sockets, TTRPC cuts memory allocations to near zero and eliminates HTTP/2 state machines.

3. The topic-based event bus

In large Kubernetes clusters running hundreds of microservices per node, constantly polling container statuses would thrash CPU caches. Instead, containerd implements an internal publish-subscribe event exchange located in package events/exchange.go.

State changes are published as typed Protobuf events categorized under hierarchical topics:

  • /tasks/create: Container task allocated in shim.
  • /tasks/start: Process execution initiated.
  • /tasks/oom: Process killed by kernel out-of-memory controller.
  • /tasks/exit: Process exited with status code and exit timestamp.
  • /images/create: New OCI image ingested into content store.
// Pattern from containerd/events/exchange.go
type Exchange struct {
	mu          sync.RWMutex
	subscribers map[chan *events.Envelope]matcher
}

func (e *Exchange) Publish(ctx context.Context, topic string, event any) error {
	envelope := &events.Envelope{
		Timestamp: time.Now().UTC(),
		Topic:     topic,
		Event:     mustMarshal(event),
	}

	e.mu.RLock()
	defer e.mu.RUnlock()

	for ch, match := range e.subscribers {
		if match(topic) {
			select {
			case ch <- envelope:
			default:
				// Non-blocking drop or buffer warning prevents slow subscribers
			}
		}
	}
	return nil
}

Why did containerd invent TTRPC instead of using standard gRPC for shim communication?
TTRPC eliminates HTTP/2 parsing and reflection, shrinking the memory footprint of each shim process from tens of megabytes to under 3 MB.
What role does the containerd v2 shim play during a container's execution lifetime?
The shim sets PR_SET_CHILD_SUBREAPER, parenting the container process, holding open its stdio FIFOs, and reaping its exit code even if the containerd daemon restarts.
How does containerd's event bus notify subscribers of container state changes?
The containerd exchange matches event topics (e.g. /tasks/exit) and pushes typed Protobuf envelopes into subscribed Go channels without blocking the publisher.
Systems insight. The shim v2 architecture is why you can restart or upgrade containerd and dockerd on a live production server without interrupting a single HTTP request in running pods. Always verify that systemd is configured with KillMode=process so it does not sweep away the detached shims when stopping the daemon unit.
