Rolling back is a traffic shift in reverse, which is why the strategy is chosen before the release

working 11 min Capability area iac-deployment, matrix rows cicd-pipeline, artifact-registry and progressive-delivery.

The one-minute version

  • The DevOps service is the native pipeline: managed repositories or mirrors of external ones, build runners, artifact delivery, and deployment pipelines.
  • It deploys to Kubernetes clusters, instance groups and functions, with manual approval gates and validation stages that invoke a function between steps.
  • Two progressive strategies are built in: blue-green, which swaps namespaces and shifts an ingress, and canary, which shifts weighted traffic.
  • Blue-green on Kubernetes requires an ingress controller to already be present. The strategy does not install one for you.
  • Rollback is the traffic shift run backwards, so the ability to roll back is a property of the strategy you chose rather than a separate feature.

The mental model: the path a change takes

Artifact Registry holds the generic artefacts, containers go to the registry from lesson 0302, and images are scanned as they are pushed there, which is the check from lesson 1102 arriving before a deployment rather than after.

The mechanism: two strategies, two different traffic moves

The reframing A deployment strategy is really a decision about what stays running. Blue-green keeps a whole second copy and switches once. Canary keeps both and moves gradually. Both spend capacity to buy a fast reversal, and a strategy that keeps nothing has bought a redeploy instead of a rollback.
The managed service mesh that would once have offered mesh-level traffic splitting has reached end of life, and the vendor page names the open-source project as its replacement. So an advanced progressive delivery approach beyond the two built-in strategies is a component you run on the cluster rather than a service you enable. This is lesson 0103's retired-service trap again, and the tutorials describing the old service still rank well.

The mechanism: a realistic path end to end

A production path on this platform looks like: a change reviewed in a repository, a build producing an image, the image pushed and scanned, a deployment pipeline with an approval gate, a traffic shift by the chosen strategy, alarms watching the new version's metrics, and a reverse shift if those alarms fire. Infrastructure changes ride the stacks of the previous lesson with drift jobs on a schedule.

Every element of that sentence is a service this course has already covered, which is the point: the pipeline is glue between things you already know rather than a world of its own.

Retrieval practice

Answer from memory before revealing.

What does a blue-green deployment on a cluster require that must already exist?
The documented precondition is an ingress controller on the cluster. The first names a service that has reached end of life. The third doubles the cluster rather than the namespace. The fourth describes a plausible arrangement the strategy does not use.
How is a release rolled back with either built-in strategy?
Both strategies leave the previous version running, so rollback is a reverse shift. The first is what you do without a progressive strategy. The second confuses a deployment with disaster recovery. The third invents automation the pipeline does not perform on its own.
Where do container images and other build artefacts go?
There are two registries with two jobs. The second and third each collapse them into one, and a deployment pointed at the wrong one simply finds nothing. The fourth invents internal storage the service does not offer.

Practice about 15 minutes, with paper

Practice 1working

A team deploys a public service onto a cluster by replacing every pod at once. When a release is bad they notice from customer reports about twenty minutes later, and recovery means building and deploying the previous version again. They keep their code on an external repository host and do not want to move it. They ask for faster recovery.

Design the change, name the precondition it depends on, and say which service tells them a release is bad before a customer does.

Hint

Recovery time here is dominated by a rebuild, so the fix is a strategy that keeps the old version alive. Then ask what has to be on the cluster for that strategy to work, and which module supplies the signal that replaces the customer report.

Show the worked solution
  1. Keep the repository where it is. The pipeline can mirror an external repository, so their review process is untouched and only the deployment side moves.
  2. Choose a strategy that keeps the old version. Either built-in strategy works. Canary limits the exposed share while the new version proves itself, which suits a public service with customers noticing.
  3. Name the precondition. If they choose blue-green on the cluster, an ingress controller must already be present, because the strategy shifts it rather than installing it.
  4. Replace the customer report. Alarms on the new version's metrics, from module 10, with the destination chosen deliberately given how many resources a fleet-wide alarm could match.
  5. Work out the new recovery time. A reverse traffic shift rather than a rebuild and redeploy, so recovery is bounded by the shift and by how quickly the alarm fires rather than by a build.

Sanity check. The rebuild should disappear from the recovery path entirely. If your answer still deploys anything during a rollback, the old version was not kept running.

Your teacher. Ask an agent how long a rollback actually takes for each deployed service, measured from the decision rather than from the first command. Services whose answer includes a build are the ones a progressive strategy would help most.
