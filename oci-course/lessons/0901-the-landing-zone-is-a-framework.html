The landing zone is code you run, and drift is only visible where a stack owns the resource

working 10 min Capability area governance-policy, matrix rows landing-zone, config-drift-assessment, policy-as-code and resource-graph-query.

The one-minute version

  • The landing zone is a published Terraform framework, not a service you enable. It is deployed through Resource Manager stacks and it is maintained by Oracle as code.
  • It lays down compartments, policies, budgets, Cloud Guard and a network baseline, and modern blueprints compose Security Zones and packet-routing policy into it.
  • Drift detection is a stack-level job, comparing live infrastructure with the last applied state, per resource. It sees only what a stack owns.
  • There is no general-purpose policy engine for writing arbitrary rules. Customisation happens by choosing recipes, writing detector rules, and validating templates in your own pipeline.
  • Search answers "what exists" with a small query language across subscribed regions, and it is eventually consistent and limited to what you may inspect.

The mental model: a framework, and what it puts down

The mechanism: what drift detection can and cannot see

That is the boundary to hold. Outside a stack, the equivalent check is running a plan in your own pipeline, and Cloud Guard's configuration findings cover some of the same ground from the other direction, as module 11 describes.

The mechanism: asking what exists

The reframing Three different questions get three different tools here. What should exist is the landing zone templates. What a stack believes exists is drift detection. What actually exists is Search. An estate is healthy when all three agree, and nothing on this platform compares them for you.
Say the policy-engine position accurately, because it is easy to overstate in either direction. There is no engine for writing arbitrary custom rules in a general policy language. What exists instead is a set of maintained recipes to select from, custom detector rules in Cloud Guard, and whatever validation you run against your own templates in your own pipeline. The compliance side is similar: a benchmark recipe is provided ready-made, and attestation documents are downloadable from the console under governance.

The trade-off: code you own against a service that owns itself

A landing zone as code means every decision it made is readable, reviewable and changeable, and it fits the deployment pipeline of module 12 like any other template. Nothing about it is opaque.

What you give up is the maintenance. A managed baseline would keep pace with the platform on its own; a framework you deployed once tracks the platform only as far as your next pull of the upstream templates. Whoever adopts it inherits that job, and the honest question at adoption time is who that is.

Check yourself

Retrieval practice

Answer from memory before revealing.

What is the OCI landing zone, precisely?
It is a maintained code framework rather than a service. The first is the assumption that leads teams to expect updates they will not receive. The second invents an automatic action. The third confuses a deployment pattern with an attestation.
Someone creates a bucket by hand. What does drift detection report about it?
Drift compares a stack's managed resources with their last applied state, so an unmanaged resource is outside the comparison entirely. The other three all assume the tool has a view of the whole tenancy, which is the misconception the page is built around.
Which limitation applies to a Search query for recently created resources?
The index is eventually consistent, so a very recent resource may be missing. The first denies the where clause. The second understates the regional reach. The fourth inverts the permission filter, which restricts results to types you may inspect.

Practice about 15 minutes, with paper

Practice 1working

A tenancy was built from the landing zone framework a while ago. Since then, three things have happened: an engineer created several instances directly in the console, the upstream framework gained new modules, and a compartment's policy was edited by hand. An auditor asks for evidence that the tenancy matches its intended design.

Say which of the three changes each tool would reveal, and name what the auditor is asking for that no single tool here provides.

Hint

Take the three tools of the reframing callout in turn and ask, for each of the three changes, whether that tool has any view of it. One of the three changes is invisible to two of the three tools.

Show the worked solution
  1. The hand-made instances. Invisible to drift detection, because no stack manages them. Visible to Search, which reports what actually exists. Not represented in the templates at all.
  2. The upstream framework gaining modules. Invisible to both drift detection and Search, because both compare against what you deployed rather than against what is now published. Only a comparison with the upstream repository shows it.
  3. The hand-edited policy. Visible to drift detection if that policy is managed by a stack, since the live state now differs from the last applied state. Search would show the policy exists but not that it changed.
  4. What the auditor actually wants. A comparison of intended design against reality, which is three separate comparisons: templates against upstream, stack state against live resources, and live resources against what any stack owns. No tool here performs all three.
  5. What to build instead. Run drift jobs on a schedule, run a Search query for resources in governed compartments that no stack manages, and track the upstream framework version you are on. Three cheap habits cover the three gaps.

Sanity check. Each of the three changes should be caught by a different mechanism, and one of them should be caught by nothing on this platform. If drift detection caught the hand-made instances, re-read what a stack's comparison covers.

Your teacher. Ask an agent to search for every resource in a governed compartment and cross it against the resources any stack manages. The difference is the part of the estate that no template describes, and it is usually where the surprises live.
