Module 05 · Databases · Lesson 0500

The databases sort by how much of the job you keep, and the top rung is a separate product

working 10 min Capability area databases, matrix rows relational-managed and relational-serverless.

The one-minute version

  • Three relational engine families are offered: Oracle Database, MySQL and community PostgreSQL. Everything else in this module is a non-relational store or a tool that moves data between them.
  • Oracle Database arrives twice. Base Database Service and Exadata Database Service are customer-managed; Autonomous Database is fully managed. They are different products, not two settings of one.
  • The ladder measures who does the administration, not how large the database is. Exadata Database Service is the largest thing here and still leaves the database administrator's job with you.
  • Managed and off-premises are separate axes. Exadata Cloud@Customer puts the customer-managed rung inside your own building, and Autonomous has a dedicated-infrastructure deployment as well as a shared one.
  • Bring-your-own-licence is a common commercial shape on the customer-managed rung, so the choice of rung is a licensing decision as well as an operational one.

The mental model: engine first, then who administers it

The customer-managed rung is Base Database Service and Exadata Database Service. Oracle runs the infrastructure; you run the database. That rung includes Exadata Cloud Infrastructure and Exadata Cloud@Customer, uses Data Guard for high availability, and offers Real Application Clusters on Exadata.

Autonomous Database is the self-driving rung: billed in ECPUs, scaled without a maintenance window, and administered by the platform rather than by you. It deploys either on shared multitenant infrastructure or on Exadata infrastructure dedicated to your tenancy, and the next lesson is about what that costs you.

The mechanism: two axes that are easy to collapse into one

The reframing Ask which job you are trying to stop doing, not which product sounds most modern. If the answer is patching, backup scheduling and index tuning, the ladder has a rung for that. If the answer is buying hardware, the ladder is the wrong instrument and the isolation axis is the one to move along.

The trade-off: the rung is a licensing decision too

Bring-your-own-licence is the common commercial model on the customer-managed rung, which is exactly why teams with existing Oracle Database licences arrive at Base Database Service rather than at Autonomous. That is a legitimate reason to stay low on the ladder, and it has nothing to do with the technical merits of the rung above.

Going up the ladder gives away control of the maintenance schedule, the cluster topology and host-level access. Staying low keeps all three and keeps the work that comes with them. Oracle's own framing is that Autonomous is the fully managed one and the Base and Exadata services are the customer-managed ones, so the two are documented separately and configured separately.

The most common mistake here is reading Autonomous as "the small one" and Exadata as "the big one". They are not points on a size axis at all. Autonomous Database deploys onto dedicated Exadata infrastructure when you ask it to, and Exadata Cloud@Customer runs the customer-managed rung on a rack in your own building. Size, isolation and administration are three separate questions and this platform lets you answer them independently.

Check yourself

Retrieval practice

Answer from memory before revealing.

What separates Base Database Service from Autonomous Database?
The dividing line is who administers it: Base Database is customer-managed and Autonomous is self-driving. The first reads the pair as a size ladder, which it is not. The second and fourth name properties that vary within each product rather than between them.
A team wants a fully managed Oracle Database on hardware nobody else shares. Possible?
Autonomous deploys either on shared multitenant infrastructure or on Exadata infrastructure dedicated to the tenancy, so the two questions are answered separately. The second and third both collapse the two axes into one. The fourth describes a customer-managed rung, which gives up the management.
Which engine branch of the ladder forks on who does the administration?
Only the Oracle Database branch carries both a customer-managed product and a self-driving one. The first is the tempting symmetry and the diagram refutes it. The second and third name single managed offerings that have no customer-managed twin on this platform.

Practice about 15 minutes, with paper

Practice 1working

Four teams describe what they want. (a) "We have Oracle Database licences already and a database administrator who wants to keep tuning it." (b) "We want an Oracle Database and we never want to think about patching it again." (c) "Our regulator requires the database hardware to sit in our own building." (d) "The application speaks the MySQL wire protocol and we also want to run analytics over the same rows."

Place each on the two axes of the quadrant figure, and for any team whose statement does not fix a rung, say which second question you would ask.

Hint

Read each statement for which of the two axes it constrains. A statement that constrains only one axis leaves the other open, and the missing question is the one about the axis it did not mention.

Show the worked solution
  1. Team (a). Existing licences and a willing administrator both point at the customer-managed rung: Base Database Service, on the left of the horizontal axis. The vertical axis is untouched, so ask whether they need Exadata or whether a VM DB system is enough.
  2. Team (b). "Never think about patching" is a statement about the horizontal axis only, so Autonomous Database. Ask about the vertical axis next: shared multitenant infrastructure, or Exadata infrastructure dedicated to the tenancy.
  3. Team (c). This constrains only the vertical axis, and Exadata Cloud@Customer is the answer to it. Notice they have said nothing about administration, so the horizontal question is still open and worth asking.
  4. Team (d). The engine is fixed by the application, so the first fork is taken before either axis matters, and MySQL HeatWave is the branch. Analytics beside transactions is the next lesson but two.

Sanity check. Exactly two of the four statements should have pinned only one axis and left the other open. If you produced a single product name for all four teams with no follow-up question, you collapsed the two axes back into one.

Your teacher. Ask an agent to list every database in a tenancy with its service name beside it. The useful surprise is a database that everyone calls "the Autonomous one" and that turns out to be a Base Database system somebody built in a hurry, because the two are administered by entirely different people after that point.

Primary source to go deeper
