The file system and the way in are two objects with two different boundaries

working 9 min Capability area storage, matrix row file-storage.

The one-minute version

  • File Storage serves NFS version 3 and version 4, fully managed, with snapshots, clones and cross-region replication.
  • The service is three objects, not one: the file system holding the data, the mount target that gives it an address in a subnet, and the export that joins them.
  • Their boundaries differ. The data is spread across availability domains within the region; the mount target lives in one subnet.
  • Capacity is not provisioned. The file system grows and shrinks with what is stored, so there is no size to get wrong.
  • Its encryption keys are now reached through resource principals, replacing an older service-principal policy - a live example of why the service change log is worth reading.

The mental model: three objects

File Storage is fully managed on both sides of that split. Capacity is elastic rather than provisioned, growing and shrinking with what is actually stored, so there is no volume size to size wrongly and no resize to schedule.

The reframing Durability and reachability are different boundaries on the same service. The data spans availability domains inside the region; the mount target is an address in one subnet. A resilience conversation about File Storage that only discusses the data has answered half the question.

The mechanism: what a client actually does

What the service gives you for free, and what it does not

The encryption-key path for File Storage changed: keys are now reached through resource principals, and the older service-principal policy is recorded as deprecated on Oracle's service change announcements page. An estate whose policies were written against the old shape still works today and is running on a deprecated mechanism, which is exactly the situation the change log exists to surface.

Retrieval practice

Answer from memory before revealing.

A client cannot mount a file system. Which object should be checked first?
The mount goes to an address in a subnet, so reachability is the first gate and the export rules are the second. The first option names the object with no location at all, and the second and third invent interactions between features that do not block a mount.
How much capacity does an OCI file system have to be created with?
Capacity is elastic, so there is no size to pick and none to get wrong. The first describes a block volume, the third invents a support path, and the fourth borrows the ladder idea from the function memory settings - three plausible models, none of which this service uses.
Which statement matches how File Storage spreads risk?
The data is spread across availability domains within the region while the mount target is an address in one subnet, so the two boundaries genuinely differ. The first and second collapse them together in opposite directions, and the fourth reverses them - which would make the mount the resilient half and the data the fragile one.

Practice about 15 minutes, with paper

Practice 1working

A shared build cache lives on File Storage. Sixty build agents mount it, spread across three availability domains for resilience. A review asks: "if we lose an availability domain, what happens to the builds?"

Answer it properly: separate what happens to the data from what happens to the mount, say which of the two the current design has actually planned for, and name the vendor page that settles the remaining question.

Hint

Answer for each of the three objects in turn rather than for the service as a whole. Two of the three have a location, and only one of those is in the failing availability domain.

Show the worked solution
  1. Take the data. The file system's data is spread across availability domains within the region, so losing one availability domain is not the same event as losing the data. That half of the question has a reassuring answer and it is the half people ask about.
  2. Take the agents. They are spread across three availability domains, so losing one removes roughly a third of the fleet. That is the part the current design has explicitly planned for, and it is working.
  3. Take the mount target. It is an address in one subnet. If that subnet's availability domain is the one lost, every surviving agent in the other two loses its path to the file system - the data is intact and nobody can reach it. Nothing in the described design addresses this.
  4. Name what settles it. How many mount targets a file system may have, and how a client is pointed at a second one, is a vendor question rather than an architectural one. The File Storage documentation is the authority, and the review should be answered from it rather than from an assumption in either direction.

Sanity check. The answer should identify the mount target as the exposure, not the data and not the agents. If it concluded that the builds are safe because the data spans availability domains, the object with a location was never separated from the object without one.

Your teacher. Ask an agent to draw one file system, its mount target and its export as three separate resources with their compartments and subnets. Any diagram that draws them as one box has already lost the distinction this page is about.

Primary source to go deeper

Read the File Storage documentation home and follow it into the mount target and export pages specifically. Those two are where the reachability half of the service lives, and they are the half a storage-shaped reading of the service skips.
