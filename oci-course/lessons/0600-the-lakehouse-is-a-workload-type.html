The warehouse is a workload type and the lake is a bucket, so the query engine owns the table

working 11 min Capability area analytics, matrix rows data-warehouse, data-lake and data-catalog.

The one-minute version

  • The analytical warehouse is the Lakehouse workload type of Autonomous Database, the product formerly called Autonomous Data Warehouse. It is not a separate service.
  • Its defining feature is the external table: rows that live as files in Object Storage and are queried in place, with no load step.
  • The data lake is therefore a pattern rather than a product: open table formats sitting on Object Storage, read by the warehouse, by Spark, or by an engine of your own.
  • There is no first-party control plane that owns those tables. Iceberg tables are ordinary objects and the query engine maintains them.
  • Data Catalog holds the metadata and serves the Hive metastore role for Spark engines, which is the closest thing to a shared table registry here.

The mental model: four places an analytical answer comes from

The Autonomous Database billing summary is the page that names Lakehouse as one of the four workload types. That is the whole of the warehouse story on this platform: the same self-driving database from lesson 0501, tuned for analytical work and given Iceberg support.

The lakehouse reference architecture is the other half. It describes open table formats sitting directly on Object Storage and queried by the Autonomous Lakehouse, by Data Flow Spark, or by external engines, which is why there is nothing to buy in order to have a data lake here.

The mechanism: what an external table read actually does

Data Catalog holds technical, business and operational metadata and exposes a Hive metastore interface, which is what lets Spark engines see the same tables the warehouse sees. It harvests Object Storage and Autonomous Database among other sources.

The mechanism: who maintains the table

The reframing Ask who maintains the table, not which product stores it. On a platform where a table is a set of objects plus a convention, the answer to "where does the data live" is always Object Storage, and the interesting question is which engine is responsible for keeping the convention true.

The trade-off: no per-query engine, and what fills the gap

Some platforms sell a standalone query engine that charges per query against files in object storage. The verified inventory behind this course records that OCI does not, and names what delivers the capability instead: external tables in the Autonomous Lakehouse, and Spark SQL over Object Storage in Data Flow. The capability exists; the packaging is different, and a design that assumes a per-query billing line will not find one.

The genuine absence to state carefully is the table-aware storage type. Object Storage has no table type of its own: an Iceberg table is a set of ordinary objects and the query engine is what maintains it. That matters operationally, because compaction, snapshot expiry and manifest upkeep are jobs somebody must schedule rather than properties the storage layer provides. The inventory behind this course records the same absence for a multi-party clean room, where nothing on this platform fills the role.

What is the analytical warehouse on this platform?
The warehouse is the Lakehouse workload type of the same Autonomous Database from module 05. The first is the assumption a reader carries in from other platforms. The third describes a self-run design. The fourth names a per-query engine, which the inventory records as absent here.
An Iceberg table sits in Object Storage. What keeps it consistent?
The files are ordinary objects and the writing engine maintains the table. The first credits the storage layer with a table type it does not have. The second overstates the catalogue, which describes rather than maintains. The third invents a service the inventory records as absent.
What does Data Catalog give a Spark engine that a bucket alone does not?
The catalogue serves the metastore role, which is how Spark discovers what tables exist. The second is Data Flow's job, covered two pages later. The third invents a guarantee. The fourth is a networking mechanism from module 07 and has nothing to do with metadata.

Practice about 15 minutes, with paper

Practice 1working

A team lands about a terabyte of event files into Object Storage each day. Two groups want to read them: analysts who write structured queries and expect a familiar database connection, and a data science group who write Spark. A third group wants to know what tables exist without asking either of the first two.

Design the smallest arrangement that serves all three, naming the OCI service for each group, and say which single job the design still owes an owner.

Hint

Start from the observation that the files never have to be copied. Then ask, for each group, which engine reads those same objects. The job the design owes an owner is the one that no service on this platform performs for you.

Show the worked solution
  1. The files stay where they are. Object Storage is the lake, and nothing needs to be loaded anywhere for either group to read it.
  2. The analysts. An Autonomous Database on the Lakehouse workload type, with external tables pointing at the bucket. They get an ordinary database connection and no load step.
  3. The data science group. Spark reading the same objects, with Data Catalog serving as its metastore so both groups see the same table definitions.
  4. The third group. Data Catalog again, this time as its intended self: the place that records what tables exist and what they mean.
  5. The job with no owner. Table maintenance. Compaction and snapshot upkeep for the open table format belong to whichever engine writes, and no service on this platform performs them unasked.

Sanity check. Your design should copy the terabyte exactly zero times. If it has a nightly job moving files into a warehouse, you have rebuilt the two-system shape that external tables exist to remove.

Your teacher. Ask an agent which engine writes each table in a lake and which one only reads. A table with two writers and no named owner is the one that will drift, and the answer is almost never written down anywhere except in the memory of whoever built the second writer.
