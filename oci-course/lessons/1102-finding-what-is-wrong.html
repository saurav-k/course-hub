Module 11 · Security services · Lesson 1102

Several services find problems and one service collects them, and nothing joins them for you

working 11 min Capability area security-services, matrix rows posture-management, vulnerability-scanning, threat-detection and data-classification.

The one-minute version

  • Cloud Guard is the collection point: detectors raise problems and responders react, with a reporting region that aggregates every scan in the tenancy.
  • Vulnerability scanning checks hosts on a schedule and container images when they are pushed, and its findings roll up into Cloud Guard.
  • Its agentless fallback scans only the most common ports, so a host without the agent is checked far less thoroughly than one with it.
  • Threat intelligence is a curated reputation feed you can join against flow and firewall logs, and it also feeds the detectors.
  • Data Safe is the database-facing one: discovering sensitive data, assessing users, collecting database activity and masking values.

The mental model: producers, a collector, and a reaction

The mechanism: how much less the agentless scan sees

Container images are scanned when they are pushed to the registry from lesson 0302, which is the other half of the same service and the half that catches a problem before it is deployed rather than after.

The mechanism: intelligence is a join, not an alert

The reframing A finding is not an incident and not a task until somebody decides it is. The value of the collection point is that every producer lands in one queue with one triage process. Without that decision the estate has four services generating findings that four different people ignore separately.
Data Safe is easy to leave out of a security design because it belongs to the database world rather than the infrastructure one. It discovers and classifies sensitive data, assesses database users, collects database activity and masks values for non-production copies. Only registered targets are covered, so a database nobody registered is absent from every report it produces, and its absence looks identical to a clean result.

The trade-off: responders that act, and responders that wake somebody

A responder recipe that remediates automatically closes the window between detection and fix, and that window is where most of the harm from a misconfiguration occurs. It is also a change made to production by a rule, at a moment nobody chose, and the first time it acts on something legitimate the trust in it drops sharply.

The usual arrangement is to remediate the class of problems whose fix is unambiguous and reversible, such as a bucket that has become publicly readable, and to notify for everything else. That division is worth writing down before the first responder is enabled rather than after.

Check yourself

Retrieval practice

Answer from memory before revealing.

A host has no scanning agent installed. What still gets checked?
The agentless fallback is a port check only. The first describes the agent-based scan. The second overstates the loss, since the fallback exists. The third names the registry half of the service, which is unrelated to the host.
Where do findings from the scanning service end up?
Scanning findings roll up into Cloud Guard, which is the collection point. The second confuses findings with API records. The third invents a parallel workflow. The fourth reverses the direction: intelligence feeds detectors rather than receiving findings.
How is an investigation spanning several findings assembled here?
There is no correlated investigation graph, so joining is manual or happens downstream. The first names the thing the inventory records as absent. The second gives responders a grouping role they do not have. The fourth makes a reputation lookup into a case management tool.

Practice about 15 minutes, with paper

Practice 1working

An estate has fifty instances, of which thirty run the scanning agent, a container registry that receives about twenty image pushes a day, three databases of which two are registered with the database security service, and a security team of two people. Cloud Guard is enabled and nobody has configured a responder or a reporting region.

List what this estate can and cannot currently see, then propose the three changes that would improve it most, in order.

Hint

Go service by service and ask what each one covers and what it silently omits. Two of the omissions are about things that were never registered or never had an agent installed, and both look identical to a clean result.

Show the worked solution
  1. What it sees. Thirty hosts fully scanned, every pushed image scanned at the registry, two databases assessed and audited, and Cloud Guard detectors running across the tenancy.
  2. What it does not see. Twenty hosts checked only for common open ports, one database entirely absent from database security reporting, and no aggregated view of any of it because no reporting region is configured.
  3. Change one: the reporting region. Cheapest and most valuable. Without it there is no single place for two people to triage from, so every other improvement produces findings nobody reads together.
  4. Change two: register the third database. Its absence is indistinguishable from a clean assessment, which is the most dangerous kind of gap in this list.
  5. Change three: the twenty agentless hosts. Install the agent so they are checked for known vulnerabilities and benchmark settings rather than for open ports alone. Leave responder automation until after a triage process exists, because a team of two cannot yet judge what a responder should be trusted to change.

Sanity check. Your first change should cost almost nothing and should not generate a single new finding. If your ordering started with enabling automatic remediation, ask who would review what it did.

Your teacher. Ask an agent which instances lack the scanning agent and which databases are unregistered. Both lists are made of resources that produce no findings, which is exactly why they never appear in a report of findings.
