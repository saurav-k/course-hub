Similarity search is a datatype here, so the vector store is a database you are already running

working 10 min Capability area ai-ml, matrix row vector-store.

The one-minute version

  • There is no standalone vector database product. Similarity search is a datatype, a set of operators and in-database embedding generation inside the Oracle database engine.
  • That makes an Autonomous Database the vector store, with the vectors sitting beside the rows they describe rather than in a separate system.
  • Vector search also appears in MySQL HeatWave, in Search with OpenSearch, and in the managed cache, so four services on this platform can hold vectors.
  • The consequence is a design pattern rather than a product choice: put the vectors where the data already is, and there is usually nothing new to run.
  • The retrieval pipeline itself is delivered inside the agent platform of the next lesson, whose knowledge bases index object storage and search content.

The mental model: four places a vector can live

The mechanism: the vectors sit beside the rows

The reframing A separate vector database forces a design to answer "which rows may this user see" twice, in two systems, with two copies of the permission model. Keeping vectors in the database that already holds the rows makes that question a clause in the query, which is why this framing is worth more than it first appears.

The mechanism: choosing among the four

One related capability is delivered elsewhere rather than absent. There is no separate managed retrieval pipeline product on this platform: that capability lives inside the agent platform, whose knowledge bases index content held in object storage and in a search cluster. The next lesson covers it. Stating it as an absence would be wrong, and stating it as its own service would be wrong too.

The trade-off: one engine for two very different loads

Keeping vectors in the transactional database removes a system, removes a synchronisation job and keeps permissions in one place. It also means a similarity search competes for the same engine that is serving transactions, which is the same coupling that lesson 0502 raised about analytics beside transactions.

The mitigations are the ones this course has already taught: the autoscaling switches from lesson 0501 decide whether a heavy retrieval hour is absorbed or throttled, and the search cluster from lesson 0604 is the natural home when the source material is documents rather than rows.

Practice about 15 minutes, with paper

Practice 1working

Three teams want similarity search. The first has customer support tickets already in an Autonomous Database, with strict rules about which agents may see which customers' tickets. The second has ten years of scanned documents in a bucket. The third wants to match a user against similar users within a few milliseconds, and already runs a cache for session data.

Place the vectors for each, and say which team would be worst served by a separate vector database and why.

Hint

Follow the source data in each case rather than the workload. Then look hard at the first team's requirement: one word in it describes a problem that a second system makes much harder.

Show the worked solution
  1. The support tickets. A vector column on the ticket rows in the Autonomous Database they already run. Nothing new is deployed.
  2. The scanned documents. These are documents rather than rows, so a search cluster is the natural home, with vector search beside the full-text index. The bucket stays the source of truth.
  3. The user matching. The cache they already run supports vector search in its current engine, and the latency requirement is exactly what a cache is for.
  4. Who suffers most from a separate system. The first team. Their access rules decide which tickets an agent may see, and a separate vector store would need its own copy of that model. Every ranking would then have to be re-filtered afterwards, and any mismatch between the two copies is a customer's ticket shown to the wrong person.
  5. The general rule. Put the vectors where the permission model already lives, and only move them when the source material genuinely belongs somewhere else.

Sanity check. Three teams, three services, and no new components for two of them. If the first team ended up with a separate store, work through what happens when an agent's permissions change.

Your teacher. Ask an agent where a proposed retrieval design would apply its permission filter. If the answer is "after the search returns", the vectors are in the wrong place, and the fix is usually to move them rather than to add a filtering step.
