Module 12 · Delivery and integration · Lesson 1202

Five services look like messaging, and the difference is how long a message survives

working 11 min Capability area integration-messaging, matrix rows message-queue, pub-sub and event-bus.

The one-minute version

  • Queue is the work queue: serverless, reachable over two protocols, at-least-once delivery and best-effort ordering, with messages persisting until they are deleted or expire.
  • Notifications is push-only fan-out to people and endpoints. It is not a durable event log, and it gives up on a silent endpoint after a bounded retry window.
  • Events is the reaction stream: rules matching structured service events and triggering something. It matches what is happening now rather than storing history.
  • Streaming from module 06 is the replayable log, and Connector Hub from module 10 is the managed pipeline between services.
  • The trap is picking by name. Ask whether the message needs to be replayed, fanned out, or worked on once, and only one of the five fits each answer.

The mental model: three questions decide it

The mechanism: how long a message lives

Queue is reachable over a messaging protocol and over an ordinary web interface, delivers at least once with best-effort ordering, and offers channel-based consumption so that one noisy producer does not starve the rest. It pairs naturally with functions as workers. Note that the database engine also carries a queuing feature of its own, which is a different tool for transactional work close to the data.

The mechanism: the event that has to be switched on

The reframing Read Notifications as a delivery mechanism, not a store. Nothing is retained for a consumer to come back to; a message is pushed at subscribers, retried for a bounded window, and then gone. Any design that needs to answer "what did we send last week" needs a second service beside it.

The trade-off: at least once means your consumer must not mind

Queue delivers at least once, so a consumer may see the same message twice, and ordering is best effort rather than guaranteed. That is the standard trade for a service that survives a consumer crashing mid-work, and it puts a real requirement on the worker: the operation it performs must be safe to repeat.

Where exactly-once semantics feel necessary, the usual answer is to make the work idempotent rather than to look for a service that promises otherwise. None of the five here does, and a design that assumes one does will fail rarely enough to be very hard to diagnose.

Check yourself

Retrieval practice

Answer from memory before revealing.

A subscriber was offline for a day. Which service still has the messages?
A stream keeps records for its retention and a queue message persists until removed. The first exceeds the bounded retry window. The second treats a reaction stream as an archive. The fourth is the assumption this page exists to correct.
A rule for object creation never fires. What is the likely cause?
Buckets emit object events only once enabled to. The second borrows subscription confirmation from a different service. The third invents a compartment restriction. The fourth invents a routing rule that would make the events service useless for storage.
What does at-least-once delivery require of a queue consumer?
Duplicates are possible, so the work must be safe to repeat. The first names a mechanism rather than the requirement it creates. The third contradicts best-effort ordering. The fourth names a common pairing as if it were a rule.

Practice about 15 minutes, with paper

Practice 1working

An application needs four things. A thumbnail generated whenever a customer uploads an image. An order handed to exactly one worker for fulfilment, where the worker sometimes crashes halfway. An alert sent to an on-call engineer and to a chat channel at once. And an analytics team who want to reprocess the last three days of order events after fixing a bug in their consumer.

Pick a service for each, and name the one enabling step and the one consumer property this design depends on.

Hint

Run each requirement through the three questions in the decision figure. The word "reprocess" settles one of them immediately, and the words "sometimes crashes halfway" settle another.

Show the worked solution
  1. The thumbnail. Events, with a rule matching object creation and triggering a function. This is the platform reacting to something it did.
  2. The order for one worker. Queue. Delivery is at least once, so a worker that crashes halfway leads to the message being seen again, which is exactly the behaviour wanted here.
  3. The alert to two places. Notifications, with both subscribers on one topic. Nothing is retained afterwards, which is acceptable because the alert is also recorded elsewhere.
  4. The analytics reprocessing. Streaming, because replay is the property being asked for and no other service on this page provides it.
  5. The enabling step and the consumer property. The bucket must be enabled to emit object events, or the thumbnail rule silently never fires. And the fulfilment worker must be safe to run twice on the same order, because at-least-once delivery is what makes the crash recoverable.

Sanity check. Four requirements should produce four different services. If two landed on the same one, check whether you asked the replay question of the analytics requirement.

Your teacher. Ask an agent which of these five services each part of an application uses and why that one was chosen. A component using Notifications where a queue was meant is the commonest version of this mistake, and it shows up as messages that are simply missing rather than as an error.
