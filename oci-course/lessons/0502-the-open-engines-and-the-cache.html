MySQL HeatWave removes the extract step, and the managed cache is no longer missing

working 10 min Capability area databases, matrix rows relational-managed and in-memory-cache.

The one-minute version

  • MySQL HeatWave is fully managed MySQL Enterprise Edition with an in-memory accelerator, so transactional and analytical queries run over the same rows.
  • That removes the extract-transform-load hop a two-system design needs, and it is the reason to pick HeatWave over a plain managed MySQL.
  • OCI Database with PostgreSQL is fully managed community PostgreSQL. It is the newest engine here, so check shape and regional availability before promising a feature on it.
  • OCI Cache is the managed in-memory service, compatible with Valkey and Redis version 7, in sharded or non-sharded topologies.
  • OCI Cache is the row that changed answer: this platform genuinely had no managed cache for years, and a design written from older material still routes around one that now exists.

The mental model: HeatWave collapses two systems into one

MySQL HeatWave is fully managed MySQL Enterprise Edition carrying an in-memory HeatWave accelerator for analytics, machine learning, generative AI and lakehouse queries over Object Storage. High availability comes from read replicas and a standby, and the same service runs on other clouds as well as this one.

OCI Database with PostgreSQL is the community PostgreSQL engine, fully managed, with a pluggable engine and monitor. It is a newer arrival than the other engines on this platform and its surrounding ecosystem is correspondingly smaller, so confirm the shapes and regions you need on the vendor page before a design depends on it.

The mechanism: what the cache actually is, and how big it goes

OCI Cache offers Valkey and Redis version 7 compatible clusters in sharded and non-sharded topologies, and the product page carries the size range above. Current versions add a Valkey 8.1 engine, a JSON module and vector search. The service is the successor to the earlier Redis-branded one, renamed after the upstream licence change.

The reframing This page carries the clearest example in the course of a stale absence. Material written before OCI Cache existed will tell you to run your own Redis on Compute, and it will sound authoritative because it once was. Before designing around a missing capability, open the vendor page and check that it is still missing.

The trade-off: one system is simpler until it is not

Collapsing transactions and analytics into HeatWave removes a moving part and a staleness window. What it also removes is the isolation that a separate analytical store gave you, because an expensive report and a customer's checkout now share one service. The accelerator exists precisely to make that survivable, and it is still a coupling that a two-system design did not have.

The PostgreSQL service is the one to write about carefully. It is fully managed community PostgreSQL and that is exactly what the vendor page says, but it is newer than its equivalents elsewhere and the inventory behind this course flags its ecosystem as smaller. Treat any extension or shape you need as something to verify on the vendor page rather than assume from another cloud's PostgreSQL offering.

Practice about 15 minutes, with paper

Practice 1working

A team runs a MySQL application on Compute instances they patch themselves. Every night an extract job copies the day's orders into a second database so that the morning report can be run. They also run their own Redis on two more instances for session state. They ask you to move all of this onto managed services with as few moving parts as possible.

Write down the target design, name the services, and say which of their current components disappears rather than being replaced.

Hint

Deal with each of their three components separately. Two of them have a direct managed equivalent on this platform. The third is not a component at all once its reason for existing is removed.

Show the worked solution
  1. The MySQL application database. This becomes MySQL HeatWave, which is fully managed MySQL Enterprise Edition, so the patching work goes with it.
  2. The self-run Redis. This becomes OCI Cache, which is compatible with Redis version 7 and with Valkey, so the two instances and their upkeep go.
  3. The second database and the nightly extract. These are the ones that disappear rather than move. The accelerator runs the analytical query over the transactional rows, so there is nothing left for the extract job to copy and nowhere for it to copy it to.
  4. Count the components. Five things become two, and the morning report stops being a day behind as a side effect rather than as a separate project.

Sanity check. Exactly two of their components should have been replaced by a named service and exactly two should have vanished. If your answer still contains a scheduled job that copies rows between two managed databases, you replaced the two-system design instead of collapsing it.

Your teacher. Ask an agent to find every scheduled job in a tenancy whose only purpose is copying rows from one database into another. Each one is a candidate for deletion rather than migration, and each one is also a small piece of undocumented business logic that nobody has read in years.
