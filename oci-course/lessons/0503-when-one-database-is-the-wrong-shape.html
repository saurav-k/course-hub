Three of the five non-relational answers live inside a database you have already met

working 11 min Capability area databases, matrix rows nosql-keyvalue, nosql-document, globally-distributed-sql, graph-database and ledger.

The one-minute version

  • NoSQL Database Cloud is the standalone key-value store: serverless tables, single-digit millisecond latency, on-demand or provisioned capacity, and regional tables that replicate active-active.
  • The document answer is Autonomous JSON Database, a workload type of Autonomous Database that speaks the Oracle Database API for MongoDB drivers.
  • The graph answer is Property Graph in Graph Studio, which runs inside an Autonomous Database rather than as a separate service.
  • The ledger answer splits by party count: Oracle Blockchain Platform for a multi-party network, and Autonomous Database blockchain tables for a single-party append-only journal.
  • Globally Distributed Autonomous Database shards one logical database across availability domains or regions, and the design work moves to choosing the sharding key.

The mental model: which answers are services and which are features

NoSQL Database Cloud is the one unambiguous standalone. Its tables are serverless and fixed-schema, its latency target is single-digit milliseconds, capacity is either on-demand or provisioned, and its global active tables replicate across regions in both directions at once. Its client libraries look far more like a key-value interface than like a structured query language, so porting to it is an application change rather than a connection-string change.

The document answer is the JSON workload type of Autonomous Database, which serves an Oracle Database API that MongoDB drivers can talk to. Read that carefully: it is a JSON document store reachable with Mongo-style drivers, and it is not wire-compatible with every MongoDB feature, so a migration is a compatibility exercise rather than a redirect.

The mechanism: one logical database over many shards

The distributed database overview names data residency as the headline use case: shards placed per region keep each region's rows in that region while the application still sees one database. That is a different promise from a single globally synchronised image, and reading it as one is the trap this row carries.

The mechanism: two ledgers for two different problems

The reframing On this platform, "is there a service for X" is the wrong question and "where does X live" is the right one. Graph queries live in Graph Studio inside Autonomous Database, documents live in a workload type, and a single-party ledger lives in a table shape. All three are real capabilities and none of them has a product page of its own.

The trade-off: a feature inside a database is not a product beside it

Getting a capability as a feature of a database you already run is cheaper to operate and cheaper to secure, because there is one service to patch, one identity boundary and one backup. It also means the capability inherits that database's sizing, its region and its failure boundary, and it cannot be scaled or moved on its own. A graph workload that grows until it wants its own hardware has nowhere to go inside Graph Studio.

One genuine absence is worth stating plainly, because the surrounding shapes make it easy to assume otherwise: the verified inventory behind this course records no managed time-series database on this platform. The nearest capabilities are the Monitoring service's metrics store for platform telemetry, which module 10 covers, and a time-series feature of the Oracle database engine itself for a self-managed workload. Neither is a managed multi-model time-series database, and a design that needs one should say so rather than stretch either of these to fit.

Check yourself

Retrieval practice

Answer from memory before revealing.

Where does a property graph query run on this platform?
Graph is a feature of Autonomous Database reached through Graph Studio. The first invents a separate product. The second confuses a key-value store with a graph model. The third names a ledger platform, which stores an agreed history rather than a traversable graph.
One company wants a tamper-evident record of its own transactions. What fits?
Blockchain tables give append-only rows with chained hashes inside an ordinary database, which is the single-party answer. The first buys a multi-party network for a single-party problem. The third confuses access control with tamper evidence. The fourth misuses sharding as an archive scheme.
What does Globally Distributed Autonomous Database ask you to decide?
The distribution is transparent to the application, so the sharding key is the design decision left. The first describes a primary-and-standby shape, not shared-nothing sharding. The second is unchanged by the service. The fourth names a knob the documentation does not present as the central choice.

Practice about 15 minutes, with paper

Practice 1working

Four requirements land on the same platform team. (a) A session store read tens of thousands of times a second where every read is by primary key. (b) A customer record whose fields differ per country, already written against MongoDB drivers. (c) A regulator requiring that each country's customer rows never leave that country, while the application keeps one connection. (d) A shared shipment record that a carrier, a customs broker and a retailer must all be able to trust.

Name the OCI answer for each, and mark which of the four answers is a service of its own and which is a feature or deployment of something already on the ladder.

Hint

Read each requirement for its access pattern first, then for how many organisations have to trust the result. The last one is the only requirement in the list where the answer changes because of who is reading it.

Show the worked solution
  1. Requirement (a). Every read is by key and the rate is high, so NoSQL Database Cloud. This is a service of its own, and moving to it is an application change because its interface is not a structured query language.
  2. Requirement (b). Documents with Mongo-style drivers means the JSON workload type of Autonomous Database. This is a workload type rather than a separate product, and the compatibility surface has to be checked feature by feature.
  3. Requirement (c). Per-country residency behind one connection is the headline case for Globally Distributed Autonomous Database. This is a deployment of Autonomous, and the country is the natural sharding key.
  4. Requirement (d). Three organisations must trust one record, so Oracle Blockchain Platform, with each organisation keeping its own peer. This is the second service of its own on the list, and it is the only requirement where blockchain tables would not do.

Sanity check. Exactly two of the four should be services of their own and two should be Autonomous Database in another form. If requirement (d) came out as blockchain tables, re-read it and count the organisations that have to trust the record.

Your teacher. Ask an agent which of these five shapes a workload actually needs before asking which service to use. The commonest finding is that a team asked for a document database because their first sketch used nested JSON, and the rows turned out to be perfectly rectangular once someone drew them.
