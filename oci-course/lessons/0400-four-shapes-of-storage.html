Module 04 · Storage · Lesson 0400

The four storage shapes differ by failure boundary, and one of them is chosen once

working 10 min Capability area storage, matrix rows object-storage, block-storage, file-storage and archive-storage.

The one-minute version

  • Four shapes: Object Storage for anything addressable by name, Block Volume for a disk attached to a machine, File Storage for a shared filesystem, and Archive for bytes you must ask for before you read.
  • They differ by failure boundary before they differ by interface. Object Storage is regional and replicated across availability or fault domains without being asked.
  • A Block Volume is attached to one machine at a time, so its resilience is a copy rather than a property.
  • A bucket's default storage tier is fixed when the bucket is created and cannot be changed afterwards. That is the one irreversible decision in this module.
  • Object Storage speaks its own interface and an S3-compatible one, so existing tooling usually moves without a rewrite.

The mental model: what each shape is attached to

Object Storage is unbounded and regional, and Oracle's own storage tiers page carries an eleven-nines durability claim for it. It offers an S3-compatible interface alongside its own, and supports versioning, retention rules and replication.

File Storage is the shared-filesystem shape, serving NFS version 3 and version 4 with snapshots, clones and cross-region replication. Its data is spread across availability domains within the region - the next-but-one page is about the part of it that is not.

The same four shapes exist on every cloud with different failure boundaries behind them, and the four-way view is in the comparison course. The rest of this module stays inside OCI.

Block Volume is the disk shape, attachable to virtual machines and to bare metal, and the page after this one is about how its performance is bought.

The mechanism: the decision a bucket cannot revisit

The reframing Choose the shape by what has to survive what, not by the interface. An application that wants a filesystem can usually be given one; an application whose data must survive losing a machine cannot be given a block volume and left there.

The trade-off: reading Archive costs a request

Archive Storage is the cold tier, and its defining property is not its price but its access pattern: an object must be restored before it can be read, and Oracle documents the first byte arriving in about an hour. A restored object is billed at the standard rate while it is restored.

That hour is a design constraint and not an inconvenience. An application that reads archived data on a user's request has to be written to accept a refused read and to come back later, which is a different program from one that accepts a slow read. If the code cannot do that, the data is not archivable however cold it is.

Check yourself

Retrieval practice

Answer from memory before revealing.

Which of the four shapes has its availability tied to something you launched?
A block volume attaches to one machine at a time, so a deliberate copy is what gives it resilience. The first and third name shapes that are regional by construction. The fourth confuses an access step with an availability boundary - a restore delays a read, it does not decide whether the bytes exist.
A bucket was created with the wrong default storage tier. What can be done?
The default tier is immutable once the bucket exists, so the fix is a new bucket and a copy. The first states the thing the documentation rules out. The second invents a support path, and the third confuses moving individual objects, which lifecycle rules do, with changing the bucket's own default.
What does an application have to handle before its data can live in Archive?
Archive requires an explicit restore before the object can be read at all, so the code has to accept a refusal and come back. The second is the most tempting wrong answer and describes a different design entirely. The third invents a streaming behaviour, and the fourth names a cost rather than a program change.

Practice about 15 minutes, with paper

Practice 1working

Four datasets need a home. (a) A database's data files, on one machine. (b) A shared working directory that six render nodes mount at once. (c) Uploaded customer documents, read often for thirty days and rarely afterwards. (d) Seven years of regulatory records that are read about twice a year, on request from a compliance officer who can wait.

Assign each to a shape, and for the two that involve a bucket say what has to be decided at creation and what can be changed later.

Hint

Ask of each dataset what has to be able to reach it and what it must survive. Then, for anything that lands in a bucket, separate the bucket-level decision from the object-level one.

Show the worked solution
  1. The database files. One machine reads them and they need a block device, so this is a Block Volume. Its availability is tied to that machine, so the design owes a second copy - which is the subject of the last page in this module.
  2. The shared working directory. Six machines mount it at once, which is the definition of the file shape, so this is File Storage over NFS. No bucket decision is involved.
  3. The customer documents. Object Storage, in a bucket whose default tier is Standard. What is decided at creation is that default; what can change later is which tier individual objects sit in as they cool.
  4. The regulatory records. Object Storage again, and the reader can wait about an hour, so Archive is genuinely available here. Because they are always cold, the bucket's default tier can be Archive at creation - and that choice is the irreversible one, so it must be made now rather than discovered later.

Sanity check. Two of the four should have been buckets and only one of those two should have been created with an Archive default. If the customer documents ended up in an Archive-default bucket, the thirty days of frequent reading was traded away for an hourly restore on every one of them.

Your teacher. Ask an agent for the default storage tier of every bucket in a tenancy. Any bucket whose default surprises its owner is carrying a decision nobody remembers making, and it is the only storage decision on this platform that a later change cannot repair.
