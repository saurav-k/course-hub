Module 08 · Identity and access · Lesson 0802

A workload authenticates as itself, and whoever reaches the host inherits that identity

working 11 min Capability area identity-workload, matrix rows workload-identity, workload-identity-federation and short-lived-credentials.

The one-minute version

  • An instance principal lets a compute instance authenticate as itself with certificates the platform rotates. No key is stored on disk.
  • Authorisation is two steps: the instance must match a dynamic group rule, and a policy must grant that dynamic group its verbs.
  • Oracle documents two caveats on the same page. Anyone who can reach the instance inherits its privileges, and every instance principal holds an irrevocable permission to inspect compartments tenancy-wide.
  • Resource principals are the same idea for services, and a function receives its token through the development kit's context rather than from a file.
  • On enhanced Kubernetes clusters, a pod authenticates with its own service account. On basic clusters, pods fall back to the node's instance principal, which over-grants.

The mental model: three mechanisms, one idea

The mechanism: an instance principal call, in order

Two sentences on that same vendor page change how an instance principal should be scoped. The first is that any user who can reach the instance automatically inherits the privileges granted to it, which makes access to the host equivalent to holding its permissions. The second is that every compute instance principal carries a permission to inspect compartments that cannot be revoked, so a compromised instance can enumerate compartment names, descriptions and free-form tags across the whole tenancy. Neither is a defect to report; both are documented behaviour to design around.

That first caveat pairs with an absence worth naming. This platform has no identity-controlled authorisation for host sign-in: keys are supplied when the instance is launched and managed inside the guest, and the Bastion service brokers the session. So who may reach a host is decided by the guest's own key management, not by the policy language of the previous lesson, while what that host may do is decided by policy.

The mechanism: what a pod gets depends on the cluster kind

The reframing Ask what is the smallest thing this platform can name, then scope permissions to it. A machine, a service, or a pod: the mechanism you pick decides the answer, and no amount of careful policy writing can address something smaller than the mechanism can identify.

The trade-off: no stored secret, and a wider identity

The gain is unambiguous. There is no key file to leak, no rotation to schedule and no secret in an image or a repository, and the platform refreshes the token without anyone writing code to do it. Databases join in too, since clients can present an identity token instead of a password.

The cost is that the identity now belongs to the host rather than to the program. Two programs on one instance are one principal, and a person who can reach the instance is that principal as well. The remedy is smaller units, which usually means one instance per job or an enhanced cluster with per-pod identity, and both cost more than putting everything on one machine.

Check yourself

Retrieval practice

Answer from memory before revealing.

An instance principal call is refused. Which step most likely failed?
Authentication is handled by the platform, so a refusal is almost always the dynamic group match or the policy behind it. The first and second describe credential problems the mechanism is designed to remove. The fourth confuses refreshing with authorisation.
Who effectively holds the permissions granted to a compute instance?
The documentation states that a user with access to the instance inherits its privileges. The second is the assumption most designs carry and the page contradicts it directly. The third and fourth name plausible-sounding identities that have nothing to do with the mechanism.
Which permission does every compute instance principal hold and keep?
The documented irrevocable permission is compartment inspection, which exposes names, descriptions and free-form tags. The other three are all things a policy could grant and none of them is held by default, which is what makes them plausible.

Practice about 15 minutes, with paper

Practice 1working

One instance runs two programs. The first reads a bucket of customer files. The second is a small internal web tool that several engineers sign into and that can run shell commands on request. A single dynamic group matches the instance and a policy grants it read on the bucket. The team believes only the first program can read customer files.

Explain why that belief is wrong in two separate ways, then give two designs that fix it and say what each one costs.

Hint

The identity is attached to the machine, so ask what else is on the machine. Then ask, separately, what the second program lets a person do once they are signed into it. Both answers point at the same boundary.

Show the worked solution
  1. The first way it is wrong. The principal is the instance, not the program. Both programs run on the instance, so both can obtain the token and both can read the bucket.
  2. The second way. The web tool runs shell commands for signed-in engineers, and the documentation states that a user who can reach the instance inherits its privileges. Every engineer who can use that tool can read customer files.
  3. Fix one: separate the machines. Two instances, two dynamic groups, and the bucket grant attached only to the first. The cost is a second instance to run, patch and pay for.
  4. Fix two: separate the workloads on a cluster. Run both as pods on an enhanced cluster with workload identity, so each service account is a distinct principal and only one is granted the bucket. The cost is that basic clusters cannot do this, so the cluster kind has to be right, and lesson 0300 explains why that is not a setting to change casually.
  5. What neither fix removes. The irrevocable compartment inspection permission stays on any instance principal, so compartment names and free-form tags remain readable by whatever runs there.

Sanity check. Both explanations should end at the same place: the identity is the host. If your second reason was about the policy being written too broadly, re-read what the web tool lets a person do once they are on the machine.

Your teacher. Ask an agent which instances match more than one dynamic group, and what the union of those grants is. Rules written months apart overlap without anyone intending it, and the union is a permission nobody ever wrote down in a single place.
