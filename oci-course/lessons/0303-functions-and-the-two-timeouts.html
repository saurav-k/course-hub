Functions has two ceilings, and most designs are drawn against the wrong one

working 10 min Capability area serverless-app, matrix row functions-faas.

The one-minute version

  • OCI Functions is built on the Fn Project, bills per invocation and scales to zero, so an idle function costs nothing.
  • A synchronous invocation defaults to a thirty-second timeout and may be raised to three hundred seconds. That is the ceiling everyone quotes.
  • A detached invocation runs from five seconds up to three thousand six hundred seconds. That is the ceiling almost nobody quotes, and it is twelve times higher.
  • Memory is chosen from a fixed ladder of six values ending at 3072 MB, not typed as a free number.
  • A function proves its identity with a resource principal: the platform hands the code a delegation token, so no key is stored anywhere.

The mental model: two doors into the same code

The reframing "Functions is for work under five minutes" is a statement about who is waiting, not about what the platform will run. If nothing is waiting for the answer, the ceiling is an hour, and a large class of jobs that get pushed onto a container fits comfortably underneath it.

The mechanism: the memory ladder

Language choice is wide - Java, Python, Node, Go, Ruby and C# are supported directly - and a function may instead ship as your own Dockerfile, which is the escape hatch when the runtime you want is not on the list.

Identity, and the log that is off until you ask

Function invocation logs are off until they are enabled, per application. The wording in the documentation invites the opposite reading: once logging is enabled, default invocation entries appear automatically - but the console action to reach that state is an explicit enable. A function running in production with nothing in the Logging service has not failed to log, it was never asked to.

Provisioned concurrency is available where a cold start matters, and distributed tracing integrates with the Application Performance Monitoring service using standard trace-context propagation, so a function call can be seen inside a wider trace rather than only in its own logs.

Check yourself

Retrieval practice

Answer from memory before revealing.

A job takes about twenty minutes and nothing waits for its result. What does the Functions limits table allow?
Twenty minutes is 1,200 seconds, well inside the detached ceiling of 3,600. The second option cannot work because the synchronous maximum is 300 seconds. The third invents a chaining requirement, and the fourth is the conclusion most teams reach by reading only the synchronous number.
How much memory can be assigned to a single function?
Memory is picked from a ladder of six values and the top rung is 3072 MB. The first two options treat it as a free number, which is what a flexible compute shape offers and a function does not, and the fourth gets the shape of the answer right and the top rung wrong.
A production function shows no entries in the Logging service. What is the most likely explanation?
Invocation logging is off until it is enabled, per application, so the ordinary explanation is that nobody enabled it. The first is possible but far less common, the third invents a difference between the two invocation modes that the documentation does not make, and the fourth would require the entries to have existed first.

Practice about 15 minutes, with paper

Practice 1working

Three pieces of work are proposed for Functions. (a) An interactive lookup that answers a user in under two seconds. (b) A monthly reconciliation that takes about fifty minutes. (c) A thumbnail generator that takes about ninety seconds per image and is triggered by an object being written.

Decide for each one whether Functions fits, which invocation mode it uses, and for the one that does not fit, name the runtime it belongs on and why.

Hint

For each job ask two questions in order: how long does it take, and is anybody waiting. The first question is only decisive after the second one has been answered.

Show the worked solution
  1. Take the lookup. Under two seconds, and a user is waiting, so it is synchronous. The default thirty-second timeout is already ten times the requirement and nothing needs changing. Functions fits.
  2. Take the reconciliation. Fifty minutes is 3,000 seconds. Nobody is waiting, so it can be detached, and 3,000 is under the detached ceiling of 3,600. Functions fits - but with only ten minutes of margin, so a job that grows with the business will cross the ceiling and the design should say what happens then.
  3. Take the thumbnail generator. Ninety seconds, triggered by an event rather than by a waiting caller. Detached suits it, and it is comfortably inside both ceilings. Functions fits, and the trigger is an Events rule on the object write.
  4. Find the one that does not fit. None of the three exceeds the ceilings, which is the point of the exercise. The reconciliation is the one to watch: if it reached seventy minutes it would exceed 3,600 seconds, and the runtime for it then is Container Instances, which runs a container for work that outgrows a function.

Sanity check. Only one of the three should have been close to a ceiling, and the close one should be the fifty-minute job at about 83 per cent of the detached limit. If any job was rejected for exceeding 300 seconds, the synchronous ceiling was applied to work nobody was waiting for.

Your teacher. Ask an agent for the timeout currently set on a function you run, and then whether its callers are waiting for the result. A synchronous invocation for work nobody reads is the most common way a design ends up bounded at five minutes for no reason.
