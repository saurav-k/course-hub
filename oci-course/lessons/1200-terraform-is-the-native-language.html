There is no proprietary template language here, because Terraform already is the native one

working 10 min Capability area iac-deployment, matrix rows native-iac-template, terraform-provider and iac-in-code-sdk.

The one-minute version

  • OCI has no proprietary declarative template language. Terraform is the native infrastructure as code, and that is a design decision rather than a gap.
  • Resource Manager is Terraform as a managed service: stacks built from an archive, a repository or a scan of an existing compartment.
  • Its job types are plan, apply, destroy, import state and drift detection, with server-side state locking so two people cannot apply at once.
  • It supports rollback of an apply, and it can reach resources with no public address through private endpoints. The service itself carries no charge.
  • The in-code path is the same provider driven from a general-purpose language. There is no separate construct library of the kind other platforms ship.

The reframing On a platform whose native language is the portable one, the interesting question stops being which language to learn and becomes who runs the plan and who holds the state. Those two answers decide whether infrastructure changes are reviewable, and the language decides nothing.
One absence is easy to misread. There is no first-party library that lets you compose infrastructure from objects in a general-purpose language the way some platforms offer. The supported in-code path is a general framework driving the same provider, and imperative software development kits exist for several languages with request signing and retries handled. Saying "there is no way to define infrastructure from code" would be wrong; saying "there is no proprietary construct library" is accurate.

The trade-off: a managed runner against your own pipeline

Running plans and applies inside Resource Manager gives state locking, a rollback job, drift detection and private endpoints reaching resources with no public address. None of that has to be built, and the service itself costs nothing beyond the resources it creates.

Running your own gives the integration a team already has: the same pipeline that builds the application, the same review gates, the same secret handling. The usual arrangement is not to choose but to split, with foundational infrastructure in managed stacks and application infrastructure in the delivery pipeline of the next lesson.

Answer from memory before revealing.

Which declarative language describes OCI infrastructure natively?
Terraform is the native language and there is no proprietary alternative. The first invents a format. The second describes an in-code library this platform does not ship. The fourth ignores a managed declarative service.
An estate was built by hand. How does it become described in code?
The compartment scan is a documented stack source. The second confuses drift reporting with generation. The third invents an export. The fourth is the expensive path the scan exists to avoid.
What stops two people applying changes to the same stack at once?
The service locks the state, which is one of the main reasons to use it rather than a self-managed state file. The first invents queuing. The second names a pipeline feature from the next lesson. The third is what happens when you hold your own state carelessly.

Practice about 15 minutes, with paper

Practice 1working

A team has three kinds of infrastructure. A network and compartment layout that changes twice a year and must be reviewed by two people. Application resources that change with every release and are already reviewed in the application's own pull requests. And a set of resources somebody built by hand last year that nobody has a description of.

Assign each to a path, say who holds the state in each case, and describe the first step for the third one.

Hint

Ask, for each kind, where the review already happens. Two of the three have an obvious home for that reason. The third is not a placement question yet, because there is nothing to place.

Show the worked solution
  1. The network and compartments. A Resource Manager stack. It changes rarely, needs deliberate review, and benefits from server-side state locking, drift jobs and the rollback job. The service holds the state.
  2. The application resources. The same provider run inside the application's own pipeline, so infrastructure changes are reviewed in the same pull request as the code that needs them. The team holds the state, and that is a responsibility to design for.
  3. The hand-built resources, first step. Create a stack from a scan of the compartment holding them. That produces a description of what actually exists, rather than one written from memory.
  4. The hand-built resources, second step. Run a plan and expect it to be untidy. The scan describes reality including whatever nobody meant to create, so the review of that first plan is the real work.
  5. What to avoid. Do not start by writing a template of what the resources should be. That produces a plan proposing to replace things, and the difference between describing and prescribing is what makes adoption safe or destructive.

Sanity check. Two paths, two different holders of state, and the third case beginning with a scan rather than with a template. If the third started with new code, ask what its first apply would do to the running resources.

Your teacher. Ask an agent which compartments contain resources that no stack manages. That list is the part of the estate that cannot be rebuilt, and the compartment scan is a cheap first move against each entry on it.
