Work that ends does not need a server that does not

working 10 min Capability areas containers and compute-iaas, matrix rows serverless-containers and batch-compute.

The one-minute version

  • Container Instances runs a container, or a small group of them, with no cluster and no node to own, billed by the second of OCPU and memory used.
  • It is a container host and not an orchestrator. The cap is sixty containers per instance, and anything that needs scheduling goes to Kubernetes.
  • Image pull credentials for a private registry come from Vault secrets, so no registry password sits in the resource definition.
  • OCI Batch is the layer above: it provisions compute for a job, runs containerised tasks on it and tears the compute down when the job is done.
  • Between them they answer the shape of work that has an end - which is exactly the work an always-on instance bills you most unfairly for.

The mental model: how long does the work last

Container Instances is the middle door. You hand it an image, a flexible shape and the memory you want, and it runs the container with virtual-machine-level isolation and no node for you to patch. It is billed per second of the OCPU and memory it uses.

The reframing Container Instances is a container host, not a small orchestrator. It has no scheduler, no service discovery and no rolling update. The verified inventory records that plainly: OCI ships no proprietary non-Kubernetes orchestrator, so anything that needs orchestration goes to Kubernetes and anything that does not should not pay for one.

The mechanism: what per-second billing actually buys

The other half of the mechanism is the secret. A container instance pulling from a private registry takes its credentials from a Vault secret rather than from a field on the resource, so the definition can be committed and the credential cannot.

The lifecycle, and where the billing stops

Batch is the layer that decides when to run them

OCI Batch is a managed batch job orchestration engine: it provisions compute, runs containerised tasks on it and tears the compute down afterwards. That is a different job from Container Instances, which runs one thing you asked for right now. Batch is the answer when the unit of work arrives as a queue of many, each needing capacity that should not outlive it.

Read the pair as complementary rather than competing. Container Instances answers "run this container now". Batch answers "run these thousand containers, on capacity you create for them and destroy afterwards". Choosing Container Instances plus a hand-written scheduler is how a team ends up maintaining the second one badly.

Practice about 15 minutes, with paper

Practice 1working

A nightly pipeline runs 400 independent extract jobs. Each takes about four minutes on two OCPUs. Today they run sequentially on one always-on instance that is otherwise idle, and the whole pipeline takes just over 26 hours, which no longer fits in a night.

Redesign it on OCI: pick the runtime, work out the wall-clock time if 50 jobs run at once, and say what fraction of the day the redesigned version is paying for.

Hint

Work out the total compute time first and keep it fixed; concurrency changes the wall clock, not the total. Then ask which runtime lets you buy that total without buying the gaps.

Show the worked solution
  1. Total the compute. 400 jobs at 4 minutes each is 1,600 job-minutes, which is 26.7 hours of two-OCPU time. That total does not change with the design.
  2. Apply the concurrency. Running 50 at once means 400 ÷ 50 = 8 waves of 4 minutes, so the wall clock is 32 minutes plus startup - comfortably inside a night.
  3. Pick the runtime. The jobs are independent, containerised and finite, and there are hundreds of them needing capacity created and destroyed. That is the Batch shape: it provisions the compute, runs the tasks and tears the compute down. Container Instances alone would leave you writing the wave logic.
  4. Work out what is paid for. The old design paid for 24 hours a day to use 26.7 hours of compute spread across more than a day. The new one pays for about 26.7 hours of compute concentrated into roughly half an hour of wall clock, so the idle share falls from most of the day to the startup overhead alone.

Sanity check. The total compute time should be identical in both designs - only the wall clock and the idle time change. If your redesign reduced the 26.7 hours of compute, something other than scheduling was changed.

Your teacher. Take a scheduled job you run on a standing instance and ask an agent how many seconds a day it actually spends working. The ratio between that number and 86,400 is what this page is about, and it is usually worse than anybody guesses.
