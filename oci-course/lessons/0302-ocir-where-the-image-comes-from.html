Module 03 · Containers and serverless · Lesson 0302

One registry feeds every runtime, and its private path is a gateway rather than the internet

working 9 min Capability areas containers and iac-deployment, matrix rows container-registry and artifact-registry.

The one-minute version

  • Container Registry is the Oracle-managed registry, built to the open registry specification, and it holds container images, Helm charts and multi-architecture manifest lists.
  • All three runtimes in this module pull from it, so it is the one shared dependency of Kubernetes, Container Instances and Functions alike.
  • Pulling privately from inside a virtual network means a service gateway, which is the same mechanism used to reach the rest of the Oracle Services Network.
  • The regional defaults are 500 repositories and 500 GB. Both can be raised, and a pipeline that never deletes a tag will need them raised.
  • Images are scanned on push by the Vulnerability Scanning service, and its findings surface alongside host findings rather than in a separate place.

The mental model: one store, three consumers, two kinds of artefact

Container Registry follows the open registry specification, so ordinary tooling works against it without a vendor client, and it holds Helm charts and multi-architecture manifest lists beside plain images.

The mechanism: push, scan, pull privately

The service gateway is worth naming precisely, because module 07 will meet it again: there is one per virtual cloud network, it reaches only the same region, and its service labels are mutually exclusive - the label covering the whole Oracle Services Network and the narrower one covering only object storage cannot both be set. A cluster that pulls images privately is therefore taking a decision about the whole network's private path, not only about the registry.

The reframing Scanning on push means the finding exists before the deployment does. That reverses the usual order, in which an image is deployed and then assessed, and it is the reason the registry is a control point rather than a storage bucket that happens to hold images.

The trade-off: the defaults are smaller than a pipeline

Both defaults are per region, not per tenancy, and a multi-region deployment multiplies the repositories rather than the storage - each region keeps its own copy of the images it serves. Sizing the registry from a single region's numbers understates a multi-region estate by exactly the number of regions.

Check yourself

Retrieval practice

Answer from memory before revealing.

Worker nodes sit in a subnet with no internet route and must pull images from Container Registry. What makes that work?
The service gateway is the private path to Oracle's own services, and the registry is one of them. The first option would give the subnet outbound internet, which is exactly what the design is avoiding. The second invents a mirror, and the fourth solves authentication rather than reachability.
A build produces a container image and a signed jar. Where does each artefact belong?
OCI splits the two stores by artefact type: containers and charts in the container registry, generic build outputs in the artifact registry. The first and third each collapse the split in one direction, and the fourth reverses it, which would leave the image un-pullable by every runtime in this module.
When is an image in Container Registry scanned for vulnerabilities?
Scanning happens on push, so the finding exists before anything is deployed. The first and second describe scanning after the fact, which is the ordering this design deliberately inverts, and the third borrows the recipe idea from the host-scanning half of the same service.

Practice about 15 minutes, with paper

Practice 1working

A team runs three services, deploys each about eight times a day, and keeps every tag for rollback. Their images average 600 MB. They deploy into two regions and their nodes sit in private subnets.

Work out how long the regional storage default lasts, how many repositories they need, and the two network facts that decide whether the private nodes can pull at all.

Hint

Do the storage arithmetic per region rather than in total, because the limit is per region. Then count repositories separately, and remember that a second region does not share the first one's gateway.

Show the worked solution
  1. Count the daily storage. Three services at eight deploys a day is 24 images a day. At 600 MB each that is 24 × 0.6 = 14.4 GB a day, in each region.
  2. Divide into the default. 500 ÷ 14.4 is about 35 days. Both regions fill at the same rate, so the limit is reached in about five weeks in each - the second region does not double the rate, it doubles the number of places hitting it.
  3. Count the repositories. Three services means three repositories per region, against a default of 500. The repository count is nowhere near binding, which is the usual shape: storage runs out long before repositories do.
  4. Name the network facts. First, each virtual cloud network needs its own service gateway, and there is one per network - so two regions means two networks and two gateways. Second, the gateway's service label has to cover the Oracle Services Network rather than only object storage, because the two labels are mutually exclusive and the narrower one does not reach the registry.

Sanity check. The storage answer should be in weeks and the repository answer should be in single digits against a limit of hundreds. If both came out close to their limits, the per-region nature of the storage figure was probably applied to the repository count as well.

Your teacher. Ask an agent for the total size of one registry region and the age of its oldest tag. If the oldest tag predates the current service by a major version, the lifecycle policy this page is about does not exist yet, and the arithmetic above is already running.
