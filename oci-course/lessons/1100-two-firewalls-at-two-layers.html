Module 11 · Security services · Lesson 1100

Two firewalls sit at two layers, and neither one sees what the other sees

working 10 min Capability area security-services, matrix rows waf and cloud-firewall.

The one-minute version

  • The web application firewall works on requests. It enforces either as an edge policy or regionally on a flexible load balancer, with a standard rule set, bot management and reputation feeds.
  • The network firewall works on packets. It is a managed next-generation appliance that autoscales, placed in a hub network and reached by a route rule.
  • The network firewall is the managed alternative to running an appliance yourself, and both are inserted the same way: a route rule pointing at something in the path.
  • Its placement means it can inspect traffic between networks, which the request-level firewall never sees at all.
  • Request firewall logs are kept for seven days on the service side, with an option to deliver them to a standard-tier bucket. The archive tier is not supported for that delivery.

The mental model: one reads requests, one reads packets

The mechanism: a request meets one, packets meet the other

The managed network firewall autoscales and is offered as an alternative to running a vendor appliance yourself from the marketplace. Both are inserted the same way, so the choice is about who operates the appliance rather than about how traffic reaches it, and both send their metrics and logs into the stores of module 10.

The mechanism: where the request logs go, and how long they last

The reframing Ask what each firewall can read, not which is stronger. A request firewall reads a request and can act on its path, its method and its body. A network firewall reads packets and can act on where they are going. Neither can do the other's job, and a rule written for the wrong layer looks configured and does nothing.

The trade-off: managed inspection against an appliance you know

The managed network firewall removes the sizing, patching and high-availability work of running an appliance, and it scales without anyone deciding when. Teams that already operate a particular vendor's appliance elsewhere give up their existing configuration language and operational habits in exchange for that.

The insertion mechanism is identical either way, so this is a genuinely reversible decision: a route rule points at a managed firewall or at an instance, and changing which is a route table edit rather than a redesign. That is unusually forgiving for a security control, and it is worth knowing before the choice feels permanent.

Check yourself

Retrieval practice

Answer from memory before revealing.

Traffic flows from one of your networks to another. Which firewall can inspect it?
Traffic between networks is routed through the network firewall by a rule. The first names a control that only sees requests reaching it. The third assumes ambient inspection that neither service performs. The fourth denies a documented placement.
Where can the request firewall's logs be delivered for a longer keep?
Direct delivery is to a standard-tier bucket and the archive tier is not supported. The first is the trap, because archive would be the natural instinct for cheap long retention. The second invents a destination. The third denies the option entirely.
How is a managed network firewall placed into a traffic path?
Insertion is routing, the same mechanism as for any appliance. The first and second confuse filtering constructs with routing. The fourth invents a tenancy-wide switch that would remove the placement decision entirely.

Practice about 15 minutes, with paper

Practice 1working

A public application is fronted by a proxy load balancer with a firewall policy attached. Its backends call a partner service over the private circuit from lesson 0702, and they also call a shared services network for authentication. A review asks whether outbound traffic is inspected and whether the last month of blocked requests can be examined.

Answer both questions honestly for the design as described, and say what you would add for each.

Hint

For the first question, trace where each of the two outbound calls goes and ask which inspection point is on that path. For the second, count backwards from today against the service-side retention.

Show the worked solution
  1. Outbound to the partner. Not inspected. It leaves over the private circuit and never passes a load balancer, so the request firewall has no view of it. Add a network firewall in the hub and a route rule sending that traffic through it.
  2. Outbound to shared services. Also not inspected, for the same reason. The same firewall placement covers it, since both paths already traverse the hub.
  3. The last month of blocked requests. Not available. The service-side retention is seven days, so anything older than a week is gone unless delivery was configured.
  4. What to add for the logs. Direct delivery to a standard-tier bucket, or a connector from module 10 carrying the logs onward. Note the tier restriction: an archive-tier destination is not supported for the direct delivery path.
  5. What the review actually found. The design protected the front door thoroughly and inspected nothing that the application itself initiated, which is the commonest shape of this mistake.

Sanity check. Both answers should be no, and both fixes should be things nobody would notice were missing from a diagram of the front door. If you found the outbound traffic inspected, check which component is actually on that path.

Your teacher. Ask an agent which route rules in a tenancy point at a firewall, managed or otherwise. Every path with no such rule is uninspected, and the list of such paths is usually much longer than the diagram on the wall suggests.
