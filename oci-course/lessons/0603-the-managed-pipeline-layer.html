The pipeline layer designs the movement and pushes the transformation somewhere else

working 10 min Capability area analytics, matrix row etl-service.

The one-minute version

  • Data Integration is the serverless visual designer for extract, transform and load work, and it is the default answer for managed pipelines on this platform.
  • It carries schema drift protection, so a pipeline is designed against a source shape that is expected to change.
  • Its most consequential behaviour is pushdown: transformation runs inside the Oracle target rather than inside the pipeline.
  • It orchestrates other services as tasks, including Data Flow, Data Science and Container Instances, so a pipeline can call the Spark from the previous page.
  • A general workflow orchestrator is not a product here. The verified inventory records a name that was announced and never documented, and names what to use instead.

The mental model: a designer that mostly delegates

The mechanism: pushdown moves the work, not the plan

The reframing A pipeline tool on this platform is a plan plus a set of calls. Where the compute happens is a separate question with three answers: inside the pipeline, inside a service it calls, or inside the target database. Knowing which one applies is how you find a slow step.

The mechanism: three things that look like orchestration

One name is worth recognising and avoiding. The inventory behind this course records a workflow service that was announced and never given documentation on the vendor's documentation site, and third-party writing about it still circulates. This is lesson 0103's announced-but-undocumented state in its purest form: there is no page to design against. Use Oracle Integration 3 process automation for integration and approval flows, or a chain of Functions and Events, both of which module 12 covers.

The trade-off: a visual designer is a shared artefact and an opaque one

A visual canvas is readable by people who do not write code, which is most of the reason this category of tool exists. It is also harder to review in a pull request, harder to diff and harder to generate, and those costs land on the engineering side of the same team.

The counterweight on this platform is that the heavy steps are usually not in the canvas at all. A Spark application under a Data Flow task, or a transformation pushed into the target database, is ordinary code held in ordinary version control, and the canvas is only the plan that calls it.

Retrieval practice

Answer from memory before revealing.

A transformation pushed down to an Oracle target runs where?
Pushdown means the target executes the transformation on its own compute. The first is where it was designed, not where it runs. The second and fourth name real Data Integration task types, which is what makes them plausible, but neither is what pushdown does.
Which of these can Data Integration run as a task in a pipeline?
Data Flow, Data Science and Container Instance tasks are all orchestrated by it. The second understates it and misses the point of the service. The third invents a target restriction. The fourth overstates it into cluster orchestration, which is not what the documentation describes.
A team needs a general workflow orchestrator on OCI. What is the honest answer?
There is no generally available first-party workflow orchestrator with documentation, and the substitutes are named. The first stretches a data pipeline tool past its job. The second repeats the announced-but-undocumented name. The third is the absence error: chaining steps is very much possible, just not in a product with that name.

Practice about 15 minutes, with paper

Practice 1working

A nightly pipeline must do four things in order: pull files from a partner's bucket, run a Spark job that cleans them, load the result into an Autonomous Database, and then run a large aggregation over the loaded rows. The team also wants a fifth step that pauses for a human approval before publishing the results to a wider audience.

Say which service owns each of the five steps, and name the one step that does not belong in this pipeline tool at all.

Hint

Four of the steps are data movement or data computation. The fifth is a different category of work entirely, and the three-way mindmap on this page is where to place it.

Show the worked solution
  1. Pull the files. A Data Integration data flow, designed in its canvas against the partner's bucket, with schema drift protection because a partner's file shape is not under your control.
  2. Clean them with Spark. A Data Flow task orchestrated by the same pipeline, so the Spark code stays in version control and the pipeline only calls it.
  3. Load into the database. Data Integration again, this time as the load half of its own job.
  4. The large aggregation. Pushdown into the Autonomous Database, so it runs on database compute. Expect to find its cost and its duration in the database's monitoring rather than the pipeline's.
  5. The human approval. This is the step that does not belong here. It is workflow rather than data movement, so it belongs in Oracle Integration 3 process automation, or in a Functions and Events chain that the pipeline signals.

Sanity check. Four steps should sit inside the pipeline tool and exactly one should be handed off. If the approval ended up as a pipeline task, ask what the pipeline is doing during the hours the approver is asleep.

Your teacher. Ask an agent where the longest step of a pipeline actually executed. Pushdown makes a pipeline look fast while a database looks slow, and the two teams involved usually do not compare notes until somebody draws the whole path.
