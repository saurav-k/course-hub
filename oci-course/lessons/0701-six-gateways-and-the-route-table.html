Each gateway does exactly one thing, and the route table is where you choose between them

working 11 min Capability area networking-core, matrix rows nat-gateway, private-endpoint and route-table.

The one-minute version

  • The internet gateway is the only bi-directional door. The NAT gateway is outbound only, and its ceiling is twenty thousand concurrent connections per destination address and port.
  • A peered network or an on-premises network cannot use another network's NAT gateway, which is the single most surprising restriction in this list.
  • The service gateway gives a private path to Oracle's own services in the same region. There is one per network, and its two scope labels are mutually exclusive.
  • Individual services also publish their own private endpoints, which is a separate mechanism from the service gateway and reaches a different set of things.
  • A route rule can point at a private address, which is how a firewall or routing appliance is inserted into a path.

The mental model: the doors, and which way each one opens

The NAT gateway carries the restriction that matters most in a hub design: a peered network or an on-premises network cannot send its traffic through another network's NAT gateway. Each network that needs outbound access needs its own, or the traffic has to be routed through something else entirely.

The mechanism: the NAT ceiling is scoped, not global

The mechanism: two different private paths, easily confused

The reframing A gateway is a destination class, not a capability. You do not turn on internet access; you attach a door for a class of destination and then write a route rule that sends that class through it. Both halves are needed, and a gateway attached with no route rule pointing at it does nothing at all.

The mechanism: what a route rule may name

The verified inventory records that there is no transparent appliance-insertion load balancer on this platform, and names the route rule to a private address as how appliances are inserted instead. That is a difference in packaging rather than a missing capability, and it is worth saying the right way round: the appliance path exists, and it is built from route rules you write.

The trade-off: single-purpose gateways cost objects and buy clarity

Because each door does one thing, a realistic network accumulates several of them, and a hub design accumulates a set per spoke since a NAT gateway cannot be shared across peered networks. That is more objects to create and more route tables to keep straight than a design with one general-purpose gateway would need.

What it buys is that exposure is readable. The question "can anything on the internet start a connection to this subnet" has a one-line answer on this platform, and the answer does not depend on reading every rule in every list.

Check yourself

Retrieval practice

Answer from memory before revealing.

A spoke network needs outbound internet access through the hub's NAT gateway. Possible?
The documentation states that peered and on-premises networks cannot traverse another network's NAT gateway. The first three all describe conditions that sound like they would fix it and none of them changes the restriction, which is exactly why hub designs are caught by it.
Twenty thousand concurrent connections through a NAT gateway is a limit on what?
The figure is per destination address and port, so many destinations multiply it. The first is the reading that makes the gateway look far smaller than it is. The third and fourth invent scopes that the documentation does not use.
How is a firewall appliance inserted into a path on this platform?
Route rules may target a private address, and that is the insertion mechanism. The second names a product the inventory records as absent here. The third confuses filtering with routing. The fourth misuses a gateway whose destination class is Oracle's own services.

Practice about 15 minutes, with paper

Practice 1working

A private subnet holds worker instances with no public addresses. They must (a) fetch operating system updates from the internet, (b) read and write an Object Storage bucket in the same region, (c) reach an Autonomous Database that publishes a private endpoint, and (d) never be reachable from the internet. A colleague suggests one internet gateway plus tight rules.

List the gateways and route rules you would create instead, and say why the colleague's suggestion fails requirement (d) even with perfect rules.

Hint

Take the four requirements one at a time and ask which destination class each one names. Three of them name different classes, and the fourth is a statement about direction rather than about a destination.

Show the worked solution
  1. Requirement (a). A NAT gateway, plus a route rule sending internet-bound traffic through it. Outbound only, which is exactly what fetching updates needs.
  2. Requirement (b). A service gateway with the label covering Object Storage, plus a route rule for that service's address range. The traffic never touches the internet.
  3. Requirement (c). Nothing new at the gateway level. The database publishes its own private endpoint inside the network, so it is reached over ordinary private addressing.
  4. Requirement (d). Satisfied by construction: with no internet gateway attached, no connection from the internet can begin.
  5. Why the colleague's version fails. An internet gateway is bi-directional. Perfect rules can block inbound traffic today, but the door exists, and requirement (d) then depends on nobody ever editing a rule wrongly. Removing the door removes the dependency.

Sanity check. Two gateways, two route rules and no internet gateway. If your answer has three gateways, check whether the private endpoint made you reach for one that was not needed.

Your teacher. Ask an agent which subnets in a tenancy have a route rule pointing at an internet gateway. That list, not the security rules, is the honest answer to which subnets are reachable from outside, and it is short enough to read.
