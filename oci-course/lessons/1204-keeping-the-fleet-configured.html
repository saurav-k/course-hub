Module 12 · Delivery and integration · Lesson 1204

A patch is promoted through stages, and the software source is versioned so a stage means something

working 10 min Capability area iac-deployment, matrix row config-management.

The one-minute version

  • OS Management Hub patches and configures fleets of Linux and Windows machines, on this platform, in your own building, and on other clouds.
  • Its structure is groups, lifecycle stages and versioned software sources, so a patch set is promoted from one stage to the next rather than applied everywhere at once.
  • Versioning the software source is what makes a stage meaningful: two machines in the same stage see the same packages, whenever they are patched.
  • Run Command remains the imperative escape hatch for the thing that does not fit a managed workflow.
  • The name is a trap. An older operating system management service has reached end of life, and material describing it is describing a product that is gone.

The mental model: a stage is a promise about content

The mechanism: three ways a change reaches a machine

The reframing Patching is a release process for software nobody on your team wrote. It deserves the same stages, the same small first group and the same ability to stop that the previous lesson gave your own code, and this service exists to make that possible without inventing it.
Two absences shape the automation around this. There is no general scheduled-job service: a resource scheduler starts and stops resources on a schedule, and anything else is a function triggered by a rule, as lesson 0603 described. And there is no curated self-service catalogue of approved offerings; the nearest paths are stacks from lesson 1200 and private listings in the marketplace. Both capabilities are reachable and neither has a product with that name.

The mechanism: a service name that outlived itself

The trade-off: patching in place keeps a machine that remembers

Replacing a machine gives a known starting point every time, which is why it is the pattern this course has favoured since module 02. It also throws away whatever the old machine had accumulated, and for a stateful workload that is precisely the problem rather than the goal.

Patching in place keeps the machine and its history, at the cost of that history diverging over time between machines that were once identical. Versioned software sources and stages are the mechanism that limits the divergence, and they only work if nobody reaches for the imperative escape hatch when a stage is inconvenient.

Check yourself

Retrieval practice

Answer from memory before revealing.

Why does a versioned software source matter for lifecycle stages?
Versioning is what makes a stage a statement about content rather than about timing. The first names live patching, a separate capability. The second names the service's reach, which does not depend on versioning. The fourth invents a bandwidth benefit.
Which machines can this service manage?
Its documented reach covers this platform, on-premises machines and third-party clouds. The other three each narrow the scope in a different plausible way, and all three would make it a much less interesting service than it is.
A tutorial describes an operating system management service. What should you check?
An earlier service of that description has reached end of life, so the first check is whether the name is current. The other three are all sensible later checks, and every one of them wastes time if the product itself is gone.

Practice about 15 minutes, with paper

Practice 1working

An estate has sixty stateless application instances behind a load balancer, eight database hosts that cannot be replaced casually, and four machines in a data centre that nobody has patched in a year. A security finding requires a package update everywhere within a month.

Choose a route for each group, describe the stage arrangement you would use, and say what you would do about the machine that fails after patching.

Hint

Ask, for each group, whether the machine can be replaced. Then design the stages so that the first group patched is the one whose failure would matter least, and remember that one of the three groups is not in this tenancy at all.

Show the worked solution
  1. The sixty stateless instances. Replace rather than patch. Build a new image with the update, apply it through the stack, and let the pipeline roll it out with one of the strategies from lesson 1201.
  2. The eight database hosts. Patch in place through lifecycle stages, since they cannot be replaced casually. Put one of them in the first stage, a second pair in the next, and the rest in the last.
  3. The four machines off-platform. The same service reaches them, so they join the same stage arrangement rather than becoming a separate manual project.
  4. Fix the source first. Use a versioned software source so that the machine patched in week one and the machine patched in week three receive the same packages. Without that, the first stage proves nothing about the last.
  5. The machine that fails. Stop the promotion. That is what the stages are for. Investigate on the failed machine, using the imperative escape hatch if necessary, and record what you did, because a command run by hand is a change with no description.

Sanity check. The largest group should not be patched at all, and the off-platform machines should be in the same stage plan as the databases. If the four remote machines became a separate manual exercise, re-read where this service can reach.

Your teacher. Ask an agent when each instance in a tenancy was last replaced rather than when it was last patched. Long-lived machines are the ones this page is about, and the list of them is usually a surprise to whoever believes the estate is immutable.
