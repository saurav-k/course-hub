Module 07 · Networking and delivery · Lesson 0703

One balancer proxies and one does not, and the global front door is a DNS answer

working 11 min Capability area networking-lb-edge, matrix rows l4-load-balancer, l7-load-balancer, global-front-door and ddos-protection.

The one-minute version

  • The Network Load Balancer is a layer-four passthrough. It is not a proxy, so it preserves the client address and carries TCP and UDP.
  • The Flexible Load Balancer is a proxy for HTTP, HTTPS and TCP. It does certificate offload and path routing, and it is where a web application firewall policy attaches.
  • Its bandwidth is chosen from 10 megabits to 8 gigabits per second, so capacity is a dial rather than a class.
  • Global steering here is Traffic Management, which changes the DNS answer. There is no proxy-based edge front door and therefore no certificate termination at the edge.
  • Volumetric denial-of-service protection is always on at the edge at no charge, and application-layer filtering comes from the firewall rather than from a purchased tier.

The mental model: proxy or not is the whole decision

The Network Load Balancer is highly available across fault domains and supports both HTTP and TCP health checks. It can be zonal or regional, and the regional shape needs the regional subnets from lesson 0700. The Flexible Load Balancer is the proxy, and its access and error logs are the ones module 10 returns to.

The mechanism: what a DNS front door does and does not do

The reframing Three separate things answer to the phrase "global front door" elsewhere: steering, edge caching and edge filtering. On this platform steering is a DNS product, filtering is a firewall policy on the proxy balancer, and general-purpose caching is not a first-party product at all. Name which of the three a design actually needs and each one has a clear answer.
The content delivery network is a genuine absence and it is worth stating exactly. The verified inventory behind this course records that OCI has no first-party general-purpose content delivery network, and that an announced offering never became a durable product. What it names instead: partner and marketplace delivery networks placed in front of OCI origins, the web application firewall at the edge, Traffic Management steering, and Media Streams for media delivery. The capability is reachable, and it is reached by composing rather than by enabling a service.

The trade-off: always-on protection with no tier to buy

Volumetric denial-of-service protection is included on the edge for public endpoints at no charge, with monitoring behind it. That removes a purchase decision that other platforms make you take, and it also means there is no higher tier to escalate to. Application-layer attacks are handled by the web application firewall policy attached to the proxy balancer, which module 11 covers properly.

The corresponding cost is in the steering layer. Without an edge proxy, a regional failover changes a DNS answer rather than a route, so the record's time to live sets how quickly clients move. A short value fails over faster and asks the resolvers more questions; a long one is quieter and slower to react, and that trade is yours to set rather than the platform's to absorb.

Practice about 15 minutes, with paper

Practice 1working

A public service runs in two regions. It needs certificates terminated, requests routed by path to two backend groups, request filtering against common web attacks, users sent to the nearer healthy region, and a separate internal endpoint that a partner reaches over a private circuit and whose logs must show the partner's real address.

Name every component in the path for the public users and for the partner, and say which requirement decides each choice.

Hint

Sort the requirements into the three things this page separated: steering, filtering and proxying. Then handle the partner endpoint on its own, since one word in its requirement rules out a proxy entirely.

Show the worked solution
  1. Certificates and path routing. A Flexible Load Balancer in each region. Reading the request is what both requirements need, so the proxy is the only option.
  2. Request filtering. A web application firewall policy attached to that balancer, which is where such a policy attaches on this platform.
  3. Nearer healthy region. Traffic Management steering across the two regional balancer addresses, with Health Checks probes deciding which is healthy. Set the record's time to live deliberately, because it is what sets failover speed.
  4. The partner endpoint. A Network Load Balancer, because the requirement that logs show the partner's real address rules out a proxy. It sits on the private path from lesson 0702 rather than on a public address.
  5. What was not used. No edge caching component, because none is offered first-party. If caching turns out to matter, it is a partner network in front of the public balancer, added as its own decision.

Sanity check. The public path should use both a proxy and DNS steering, and the partner path should use the passthrough balancer and no steering at all. If both paths ended on the same balancer type, re-read which requirement mentions a real client address.

Your teacher. Ask an agent for the time to live on every record that Traffic Management steers. That number is the true failover time of the design, and it is usually inherited from a default rather than chosen by anyone.
