Three tools watch from outside, and only two of them send a packet

working 11 min Capability area observability, matrix rows distributed-tracing, synthetic-monitoring, network-diagnostics and telemetry-agent.

The one-minute version

  • Distributed tracing collects open-standard spans into an application performance domain, and its explorer follows one request from the browser through to a database.
  • Availability monitoring runs scheduled checks from public vantage points, dedicated ones, or workers in your own building, keeping screenshots and network traces per run.
  • Health Checks is the lighter probe, and it is what feeds the health stage of the DNS steering policies from lesson 0704.
  • Network Path Analyzer sends no packets. It reads the configuration and names what would block a path, so a path can be checked before the workload exists.
  • One management agent carries plug-ins for several services and runs off this platform too, which is how an on-premises estate is watched from here.

The mental model: a trace is one request, not one component

The mechanism: three ways of looking from outside

Health Checks is the lighter of the two probes, with a basic and a premium interval, and it is limited to a documented number of endpoint tests per account. Availability monitoring is richer and heavier, and the two are complements rather than alternatives.

The mechanism: one agent, several jobs

The reframing Sort observability tools by what they can see that the others cannot. Logs see events. Metrics see rates. Traces see one request across components. External probes see what a stranger sees. The path analyzer sees intent. An estate missing one of those five has a class of question it cannot answer at all.
Two absences here are worth naming rather than working around silently. There is no managed continuous profiler covering many languages; the nearest capabilities are specific to the Java runtime, being recording-based and a thread-snapshot feature of the performance monitoring service. And there is no service that groups application exceptions automatically: the raw errors are in traces and in logs, and any grouping is something you build. Both are real absences rather than features hiding under another name.

The mechanism: knowing the platform itself is unwell

Console announcements are the tenancy-scoped feed of service events, planned maintenance and required actions, filtered to the services and regions the tenancy actually uses, and subscribable through the notifications service. The filtering is at the tenancy and service level rather than per resource, so an announcement tells you the service is affected and not which of your resources are.

The trade-off: instrumentation is code you have to write

Traces are the most informative telemetry on this platform and the only one that requires changing an application. Everything else is a setting; this is a dependency, a header to propagate and a decision about what to name a span. The free allowance is generous enough to learn on and small enough that a busy service will exceed it.

The counterweight is that a trace answers questions that nothing else can. When a request is slow and every component's metrics look healthy, the answer is nearly always in the hop between two of them, and only a trace can see a hop.

Check yourself

Retrieval practice

Answer from memory before revealing.

Which tool can tell you a path is blocked before any workload exists?
The path analyzer evaluates configuration rather than sending packets, so it works before anything is running. The other three all require something to be there to observe, which is exactly the difference.
A request is slow but every component's metrics look healthy. What sees the cause?
Only a trace spans components and shows the gap between them. The first watches for a component vanishing. The second records control-plane calls. The third confirms the service answers, which is already known.
How does a metric-exposing endpoint get its data into this platform?
The agent performs the scrape and the ordinary monitoring service holds the result. The second names a managed store this platform does not have. The third invents a pull from the service. The fourth is the absence error and would rule out custom metrics entirely.

Practice about 15 minutes, with paper

Practice 1working

A new public service is going live. The team wants to know within a minute if it stops answering from the internet, to be able to follow a slow customer request through three internal services, to confirm before launch that a new subnet can reach the database subnet, and to watch the two legacy machines still running in their own data centre.

Name the mechanism for each requirement, and say which one requires a change to the application code.

Hint

Four requirements, four different tools from this page. Sort them by whether the answer comes from outside the service, from inside it, from the configuration, or from a machine this platform did not launch.

Show the worked solution
  1. Answering from the internet. Health Checks for the lightweight case, or availability monitoring if the check needs to be a scripted browser session. Both watch from outside, and the health feed also drives DNS steering if the service is steered.
  2. Following a slow request. Distributed tracing, with spans emitted by all three services and the identifier propagated between them. This is the requirement that needs application changes.
  3. Confirming reachability before launch. Network Path Analyzer. It reads gateways, route tables and rule sets, so it answers before anything is deployed, and the analysis can be saved and re-run after the next change.
  4. The two legacy machines. The management agent installed on them, shipping host metrics and logs into the same stores as everything else.
  5. Notice the pattern. Three of the four are configuration and one is code. That ratio is why tracing is the capability most often left until after the first incident that needed it.

Sanity check. Exactly one requirement should touch the application. If two did, check whether you were planning to instrument the external probe as well, which is not necessary.

Your teacher. Ask an agent to run a path analysis between two subnets you believe are connected, before anyone reports a problem. It is the cheapest observability action on this platform, it needs no running workload, and it regularly finds a route rule nobody remembered.
