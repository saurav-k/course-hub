The cluster kind is chosen once, defaults differently in the console and the API, and only upgrades one way

working 11 min Capability area containers, matrix row managed-kubernetes.

The one-minute version

  • Container Engine for Kubernetes sells two cluster kinds: basic and enhanced. The kind is fixed at creation and shapes everything after it.
  • The defaults disagree. The console defaults to enhanced and the command line and API default to basic, so the same team gets different clusters from different doors.
  • Enhanced adds virtual nodes, self-managed nodes, add-on management, node cycling, higher node limits and a financially backed service level agreement. Basic carries an objective instead.
  • Pod-level identity is on the enhanced side. A basic cluster falls back to node-level instance principals, which grant every pod on the node the same access.
  • Basic upgrades to enhanced only if the cluster is virtual-network-native, and nothing downgrades.

The mental model: one word, two products

The reframing "Enhanced" reads like a paid tier and behaves like a different product with the same API. Choosing basic to save money is really choosing to run the cluster's own lifecycle yourself and to grant access at the node rather than at the pod, and both of those are paid for somewhere else.

The mechanism: the trap in the defaults

The consequence arrives later and looks unrelated. A pipeline creates a basic cluster, a service is written expecting pod-level identity, and the access it needs has to be granted to the node instead - which means every pod on that node inherits it.

Identity is the difference that outlives the others

Node-level identity over-grants by construction, and the over-grant is invisible in a policy review: the statements look tight because they are written against one dynamic group, and the blast radius is whatever else happens to land on that node. Module 08 takes this apart properly - what matters here is that the cluster kind decides whether the option exists at all.

The trade-off: a one-way door with a precondition

What sits around the cluster

Node pools are ordinary compute, so everything from module 02 applies: shapes, fault domains and, unusually, preemptible worker nodes, which the platform cordons and drains before reclaiming. Cluster telemetry follows the platform pattern: the Kubernetes control-plane audit stream is on, and the other log categories are enabled per cluster.

Four capabilities that other platforms package separately are not products here, and the verified inventory records each as a genuine absence with its substitute. There is no workload-aware Kubernetes backup service - Block Volume backup policies protect the persistent volumes and not the cluster objects. There is no fleet abstraction across clusters. There is no first-party operator exposing OCI resources as Kubernetes custom resources. And node scaling is covered by the cluster autoscaler add-on and by virtual nodes rather than by a just-in-time right-sized node provisioner.

Retrieval practice

Answer from memory before revealing.

A team creates clusters in the console and their pipeline creates clusters with Terraform. What differs if neither sets the cluster type?
The two surfaces default differently, which is why the field belongs in every template explicitly. The first two options assume one platform-wide default, and the fourth would at least be safe - the real danger is that both calls succeed and produce different products.
On a basic cluster, what is the smallest unit that an IAM grant can be scoped to?
Without workload identity the pods authenticate as the node they sit on, so every pod on that node shares the grant. The second option is exactly what enhanced clusters add. The third and fourth name plausible boundaries that OCI policy does not use as principals at all.
A production basic cluster now needs virtual nodes. What does the documentation allow?
The upgrade runs one way and only for a virtual-network-native cluster; anything else is rebuilt. The first and second invent a reversibility the documentation denies, and the third would make the cluster kind meaningless, which is precisely why it is not offered.

Practice about 15 minutes, with paper

Practice 1working

An estate has eleven basic clusters created by a Terraform module that never set the cluster type. Two of them run a payments service whose pods must each reach a different vault secret. Three of the eleven predate the module's move to virtual-network-native networking.

Plan the remediation: what changes in the module, which clusters can be promoted, what the payments service has to do until it is promoted, and what the three older clusters cost.

Hint

Separate the fix that stops the problem growing from the fix that repairs what exists. Then split the existing clusters by the precondition rather than by their workload.

Show the worked solution
  1. Stop it growing. Set the cluster type explicitly in the Terraform module. Every cluster created from now on is enhanced by declaration rather than by whichever default the surface happens to carry.
  2. Split the eleven by the precondition. Eight are virtual-network-native and can be upgraded in place. Three are not, so they are rebuilt and their workloads migrated - that is a project, not a setting, and it is the real cost of the original omission.
  3. Handle the payments service in the meantime. Per-pod secret access is unavailable on a basic cluster, so either the two pods each get their own node pool with its own dynamic group and policy - restoring separation through scheduling rather than through identity - or the promotion of those two clusters is done first.
  4. Price the residue. Promoting eight clusters is an in-place change. Rebuilding three is eleven-elevenths of the work concentrated in three-elevenths of the estate, and none of it would have existed if one field had been set at the start.

Sanity check. The remediation should split eight against three on the networking precondition and not on the workload. If your split followed which clusters run payments, the precondition was read as a preference rather than as a gate.
