Spark arrives twice, and the second one exists for the things that are not Spark

working 10 min Capability area analytics, matrix row managed-spark.

The one-minute version

  • Data Flow runs Apache Spark and Spark Streaming with no cluster to manage, billed per second of execution.
  • Big Data Service is the persistent-cluster alternative: Hadoop, Spark, Trino and Flink, with Kerberos security and autoscaling.
  • The reason to keep a cluster is usually something other than Spark: a component Data Flow does not run, or a tool that expects to live on the cluster.
  • This is the same fork as the previous page. Serverless against sized cluster is a shape this platform offers repeatedly, and recognising it saves a comparison each time.
  • There is no dedicated streaming SQL product. That capability is delivered by Spark Streaming in Data Flow and by GoldenGate Stream Analytics.

The mental model: two compute lifecycles

Data Flow runs Spark and Spark Streaming applications with no cluster to manage and charges per second of execution. It offers an NVIDIA RAPIDS acceleration option and pairs with Data Catalog as its Hive metastore, so it sees the same tables as the warehouse from lesson 0600.

The mechanism: what a persistent cluster is actually for

The reframing This is the second time in two pages that the platform has offered one capability in a serverless wrapper and again as a cluster you size. Once you have seen the pattern, the comparison stops being per-service: the questions are always whether an idle state buys you anything and whether you need a component the serverless version does not run.

The mechanism: where streaming SQL actually lives

The trade-off: per-second billing changes what you are allowed to try

Paying per second of execution makes an experiment nearly free, which changes behaviour: a job that runs for four minutes once a week costs four minutes once a week. On a persistent cluster the same job costs whatever the cluster costs, and the pressure is then to find more work for the cluster rather than to ask whether the job is worth running.

The other side is start-up. A serverless run has to acquire capacity before it does anything, and a cluster that is already up does not. For an interactive session where somebody is waiting, that difference is felt on every query, which is one of the honest reasons to keep a cluster.

Check yourself

Retrieval practice

Answer from memory before revealing.

A team runs only Spark batch jobs, a few times a day. What does the guidance favour?
Oracle's guidance is to prefer Data Flow unless something needs the persistent cluster, and nothing here does. The first names a feature that does not answer the question. The second is a true statement about history that does not decide anything. The third is the most tempting: both do run Spark, and that is exactly why the choice turns on the idle state instead.
Where does a continuous query over a stream run on this platform?
The capability is delivered inside Data Flow and GoldenGate rather than as its own product. The first invents a service. The third is the absence error this page warns against. The fourth credits the event log with a processing engine it does not have.
What does the idle state of a persistent cluster actually buy?
The idle state buys immediate availability and a home for on-cluster tooling. The first inverts the economics for intermittent work. The second describes a different axis entirely. The fourth promises correctness from caching, which is not what either service claims.

Practice about 15 minutes, with paper

Practice 1working

Three workloads arrive together. (a) A nightly Spark job that reads the lake and writes a summary table, taking about twenty minutes. (b) An interactive exploration session where analysts run Trino queries all afternoon and expect each one to start immediately. (c) A continuous job that reads the Kafka topic from the previous lesson and writes aggregates every minute.

Assign each to a service, and for the one that could reasonably go either way, name the property that decides it.

Hint

For each workload ask two questions in order: does it need a component beyond Spark, and does anyone sit waiting while it starts. Only one of the three answers yes to either.

Show the worked solution
  1. Workload (a). Twenty minutes once a night, pure Spark, nobody waiting. Data Flow, and the cost is twenty minutes of execution rather than a day of cluster.
  2. Workload (b). Trino is not Spark and the analysts are waiting on each query, so both reasons for a persistent cluster apply at once. Big Data Service.
  3. Workload (c). This is Spark Streaming, which Data Flow runs, so the streaming SQL capability is delivered without a separate product.
  4. The one that could go either way. Workload (c), because a continuously running job has no idle state to save, so the per-second billing advantage largely disappears. What decides it is whether anything else about the cluster is wanted, and here nothing is.

Sanity check. Exactly one of the three should land on the persistent cluster, and the reason should be Trino and the waiting analysts rather than the volume of data. If workload (a) landed on a cluster, check what the cluster is doing for the other twenty-three hours.

Your teacher. Ask an agent how many hours a week a persistent analytics cluster actually runs a job. The answer is usually a single-digit percentage, and the useful follow-up is which of the four reasons for keeping it is still true.

Primary source to go deeper

Read the Big Data Service documentation. It is the clearest list of what a persistent cluster brings beyond Spark, which is the only thing that should ever justify choosing it over the serverless option.
