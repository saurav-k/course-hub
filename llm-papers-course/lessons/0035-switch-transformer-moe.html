Module 09 · Mixture of Experts · Lesson 35

Switch Transformer (MoE)

2021 William Fedus, Barret Zoph, Noam Shazeer (Google Research / Google Brain). · arXiv:2101.03961

The one-minute version

  • A normal Transformer block sends every token through the same feed-forward network (FFN). That one FFN holds all the model's "knowledge", and every token pays for all of it.
  • A Mixture of Experts replaces the single FFN with many expert FFNs plus a small router. The router picks which experts a token visits, so most experts stay idle for any given token.
  • Switch simplifies MoE to top-1 routing: each token goes to exactly one expert. That cuts routing math and the cross-device traffic of moving tokens around.
  • Two safety valves keep it working: an expert-capacity limit that drops overflow tokens, and an auxiliary load-balancing loss that pushes the router to use experts evenly.
  • The payoff is sparse activation: parameter count grows into the trillions while the FLOPs each token pays stay roughly fixed. Switch trained up to 7x faster than a dense T5 baseline.

1. Why this paper exists

By 2021 the recipe for a better language model was blunt: add parameters. But in a dense Transformer, every extra parameter is used on every token. Double the width of the feed-forward network and you double the compute for every token in every forward pass. Capacity and cost were welded together, and that made scaling brutally expensive.

The escape hatch is an old idea, conditional computation: only run the part of the network a given input actually needs. If a token about French grammar could skip the experts specialised in Python code, you could hold far more total knowledge while each token still touches only a slice of it. Switch Transformer makes that idea simple enough to train stably at scale.

2. What a Mixture of Experts actually is

Inside a Transformer block, the attention layer lets tokens share information, and then a feed-forward network processes each token on its own (you met this in Lesson 1). MoE only touches that second part. It swaps the single FFN for a set of N expert FFNs, each with identical shape but its own weights, and adds a tiny gating network (the router) that decides where each token goes.

The router is just one small linear layer. It reads a token's vector and produces a score for each expert. In classic MoE you keep the top-k experts and blend their outputs. Switch's contribution is to set k = 1: keep only the single best expert. That was thought to hurt quality, but the paper shows top-1 works well and is far cheaper.

3. Routing, in plain steps

Follow one token end to end. The router turns the token into a preference over experts, one expert wins, that expert does the work, and the result is scaled by how confident the router was.

Now the catch. Tokens are routed independently, so nothing stops thousands of tokens in a batch from all picking expert 3 while expert 7 sits empty. On real hardware each expert lives on a device with a fixed buffer. If too many tokens land on one expert, some cannot fit. Switch handles this with two mechanisms working together: a hard capacity limit, and a soft loss that discourages the imbalance in the first place.

4. Expert capacity and token dropping

Each expert gets a fixed number of slots per batch, its capacity. Capacity is set by a capacity factor: if tokens were split perfectly evenly, each expert would receive tokens / experts of them, and the capacity factor multiplies that even share to leave some slack.

capacity = capacity_factor × (tokens_per_batch / num_experts) tokens_per_batch / num_experts: the fair share each expert would get under a perfectly even split. capacity_factor: a slack multiplier (Switch uses values like 1.0, 1.25, or 2.0). Above 1.0 you leave headroom so small imbalances do not overflow; the cost is padding buffers with empty slots. Below 1.0 you save memory but drop more tokens.

When an expert's slots fill up, extra tokens are dropped: they skip the expert entirely and pass through on the residual connection unchanged. Dropping sounds alarming, but the residual path means a dropped token still moves forward with its attention update; it just misses this one FFN. A higher capacity factor drops fewer tokens but wastes more memory on padding. It is a direct dial between compute waste and information loss.

5. The load-balancing loss

Dropping is a last resort. The real fix is to stop the imbalance forming, and that job falls to an auxiliary load-balancing loss added to the training objective. It rewards the router for spreading tokens evenly across experts. Left alone, routers collapse - they learn to favour a few experts, which then hog all the training signal and get better, which makes the router favour them even more. The auxiliary loss breaks that feedback loop.

For a batch, look at two quantities per expert i: the fraction of tokens actually dispatched to it, fi, and the average router probability it received, Pi. The loss multiplies them together and sums, scaled so the ideal is a flat, uniform assignment.

L_aux = α · N · ∑i=1..N fi · Pi N: number of experts. fi: fraction of the batch's tokens that were routed to expert i (a hard count, from argmax). Pi: the mean softmax probability the router assigned to expert i across the batch (soft, differentiable). ∑ fi Pi: this product is minimised when both are flat at 1/N, i.e. perfectly balanced. α: a small weight (the paper uses 0.01) so balancing nudges the router without overwhelming the real language-modelling loss. Multiplying by N keeps the target value near 1 regardless of expert count.
Why f times P You cannot backpropagate through the hard argmax that produces fi. But you can through the soft probabilities Pi. Pairing the two - a non-differentiable count with a differentiable probability - gives a loss whose gradient flows into the router and whose minimum is exactly the uniform assignment you want. It is a small, clever trick that makes balance learnable.

6. Sparse activation: the whole point

Put it together and you get the property that makes MoE worth the trouble. The model's total parameters equal all experts combined, which can be enormous. But the parameters active for any one token are just its single chosen expert plus the shared attention and router. So you can grow capacity almost for free in FLOPs.

7. Implement it: a top-1 Switch layer in PyTorch

Here is a compact but faithful Switch MoE layer. It builds the experts, routes each token top-1, enforces capacity with dropping, blends by the router probability, and returns the auxiliary load-balancing loss so the training loop can add it. Read it against the diagrams above.

switch_moe.py · runnable with torch
import torch, torch.nn as nn, torch.nn.functional as F

class Expert(nn.Module):
    """A standard Transformer FFN: expand, activate, project back."""
    def __init__(self, d_model, d_ff):
        super().__init__()
        self.net = nn.Sequential(
            nn.Linear(d_model, d_ff), nn.ReLU(),
            nn.Linear(d_ff, d_model),
        )
    def forward(self, x):
        return self.net(x)

class SwitchMoE(nn.Module):
    def __init__(self, d_model=128, d_ff=512, num_experts=8,
                 capacity_factor=1.25, aux_weight=0.01):
        super().__init__()
        self.num_experts = num_experts
        self.capacity_factor = capacity_factor
        self.aux_weight = aux_weight
        self.router  = nn.Linear(d_model, num_experts)          # the gating network
        self.experts = nn.ModuleList(
            [Expert(d_model, d_ff) for _ in range(num_experts)])

    def forward(self, x):                       # x: (B, N, d_model)
        B, N, d = x.shape
        x_flat = x.reshape(B * N, d)            # treat every token independently
        T = x_flat.size(0)                      # total tokens in the batch

        # ---- route: one score per expert, then top-1 ----
        logits = self.router(x_flat)            # (T, num_experts)
        probs  = logits.softmax(dim=-1)         # router probabilities
        gate, idx = probs.max(dim=-1)           # top-1 gate value and expert index

        # ---- auxiliary load-balancing loss:  alpha * N * sum_i f_i * P_i ----
        # f_i = fraction of tokens sent to expert i (hard, from argmax)
        # P_i = mean router probability for expert i (soft, differentiable)
        one_hot = F.one_hot(idx, self.num_experts).float()      # (T, E)
        f_i = one_hot.mean(dim=0)               # dispatch fraction per expert
        P_i = probs.mean(dim=0)                 # mean probability per expert
        aux_loss = self.aux_weight * self.num_experts * (f_i * P_i).sum()

        # ---- capacity: fixed slots per expert; overflow is dropped ----
        capacity = int(self.capacity_factor * T / self.num_experts)
        out = torch.zeros_like(x_flat)
        for e in range(self.num_experts):
            token_ids = (idx == e).nonzero(as_tuple=True)[0]     # tokens picking expert e
            if token_ids.numel() == 0:
                continue
            keep = token_ids[:capacity]         # first `capacity` fit; rest overflow
            y = self.experts[e](x_flat[keep])   # only kept tokens run the FFN
            out[keep] = gate[keep].unsqueeze(-1) * y   # scale by router probability
        # dropped tokens keep out=0 here; the residual add outside restores them

        return out.reshape(B, N, d), aux_loss

# smoke test
layer = SwitchMoE(d_model=128, num_experts=8)
x = torch.randn(2, 16, 128)                     # batch 2, seq 16, d_model 128
y, aux = layer(x)
print(y.shape, float(aux))                      # torch.Size([2, 16, 128]) 

# in a real block you would use it as a residual sub-layer, and add aux to the loss:
#   moe_out, aux = layer(h)
#   h = h + moe_out                    # dropped tokens survive via this residual
#   loss = task_loss + aux             # balance is trained jointly

Two lines carry the whole idea. keep = token_ids[:capacity] is token dropping: any token past an expert's slot count is simply not processed. And out[keep] = gate[keep] * y scales each expert's output by the router probability, which is how the router gets a gradient and learns to route better. The residual add outside the layer is what saves dropped tokens from vanishing.

Real systems In production the experts sit on different devices, and routing becomes an all-to-all network shuffle: tokens are sent to wherever their expert lives, processed, and sent back. Top-1 routing halves that traffic compared to top-2. Frameworks like GShard, Mesh-TensorFlow, and later Megablocks handle the sharding; the math above is unchanged.

The Switch paper reports up to 7x faster pre-training than a dense T5 baseline at matched compute, and scales a sparse model to one trillion parameters, all trained on the Colossal Clean Crawled Corpus (C4). The simplification to top-1 is what made that stable and cheap enough to be practical.

Check yourself

Retrieval practice

Answer from memory before revealing.

What does Switch routing do differently from earlier Mixture-of-Experts designs?
Switch uses top-1 routing: each token visits exactly one expert, which cuts routing compute and cross-device traffic.
What happens to a token when its chosen expert is already at capacity?
Overflow tokens are dropped: they skip the FFN and continue on the residual connection, missing just that one expert.
Why does Switch add an auxiliary load-balancing loss during training?
Without it, routers favour a few experts in a runaway loop. The loss rewards uniform usage so every expert is trained and fewer tokens drop.
What is the defining benefit of sparse activation in an MoE model?
Each token touches one expert, so capacity (total params) scales while the compute paid per token stays nearly constant.

How this connects

  • The feed-forward network that MoE replaces is the one from Attention Is All You Need. MoE leaves attention untouched and only swaps the per-token FFN.
  • Next up, DeepSeekMoE keeps this machinery but splits experts into many fine-grained ones and adds always-on shared experts for sharper specialisation.
  • Switch's trade of capacity for constant compute is the same lever behind scaling laws and Chinchilla - just spent on parameters instead of FLOPs.
  • The cross-device token shuffle that top-1 routing minimises is a systems cousin of the memory tricks in FlashAttention and PagedAttention.
Your teacher. The two safety valves trip people up. Ask the agent to run the code with a deliberately imbalanced batch and watch tokens drop, then turn the auxiliary loss on and off and see the dispatch fractions flatten. If the fi · Pi trick feels like magic, ask why you cannot just backprop through the argmax directly.
