GraphRAG

working 2024 16 min Edge, Trinh, Cheng, Bradley, Chao, Mody, Truitt, Metropolitansky, Ness, Larson · Microsoft Research · arXiv:2404.16130

The one-minute version

  • The name misleads. GraphRAG is not "RAG with a graph database", it is a different task. "What are the main themes in this corpus" is query-focused summarisation, and no ranking of chunks answers it.
  • The mechanism is two offline stages: an LLM extracts entities and relationships from every text unit, then community detection groups them and an LLM pregenerates a summary for each community. A global question is answered by map-reduce over those summaries.
  • The measured cost is the headline. A benchmark reports roughly 331,000 prompt tokens per global query against about 900 for vanilla retrieval - and vanilla retrieval wins on plain fact lookup.
  • So the question is never "should we use GraphRAG". It is what fraction of your queries are sensemaking rather than lookup. If that fraction is near zero this is a tax.

1. Why this paper exists

Ordinary retrieval embeds the question, finds the nearest chunks, and puts them in the prompt. That works whenever the answer is written down somewhere in particular. It fails on a whole class of question, and the paper names the class precisely: conventional retrieval "fails on global questions directed at an entire text corpus, such as 'What are the main themes in the dataset?', since this is inherently a query-focused summarization (QFS) task, rather than an explicit retrieval task."

Sit with that sentence, because it is the lesson. If the answer is a property of the whole corpus, then no top k contains it. Better embeddings do not help, a larger k does not help, and a reranker does not help, because the failure is not in the ranking. You asked a retrieval system to do summarisation.

2. The mechanism: two offline stages, then map-reduce

Both expensive stages run before any user asks anything.

At query time, a global question is not answered from the corpus at all. It is answered from the summaries. The paper describes the reduction step directly: "each community summary is used to generate a partial response, before all partial responses are again summarized in a final response to the user."

The published tooling ships four query modes, and is candid about the cost of one of them. Local Search is for "questions that require an understanding of specific entities". Global Search runs across community reports and is described verbatim as "a resource-intensive method". DRIFT Search widens a local search with community information and generated follow-up questions. Basic Search is plain vector retrieval, included so you can compare against it.

That last mode is worth noticing. The project ships the baseline that competes with it and tells you to measure. The repository's own README carries the warning: "GraphRAG indexing can be an expensive operation, please read all of the documentation to understand the process and costs involved, and start small." The hype around this method is not coming from the people who built it.

3. What it costs, measured

An independent benchmark measured prompt tokens per query across methods. The spread is not a detail, it is the design constraint.

The same benchmark reports that the cost is not flat either: "MS-GraphRAG(global)'s prompt size expands from 7,800 to 40,000 tokens across tasks of increasing difficulty". Harder questions visit more, so the worst queries are the expensive ones.

The benchmark's own first observation states it without hedging: "basic RAG is comparable to or outperforms GraphRAG in simple fact retrieval tasks that does not require complex reasoning across connected concepts." On the same set, Microsoft's global mode scored 49.29% on fact retrieval against basic retrieval's 60.92%.

Read the two tables together Global graph search costs roughly three hundred times the tokens per query and loses on fact retrieval, while graph methods win by ten to thirteen points on the reasoning and summarisation tasks they were designed for. That is not an argument for or against the technique. It is a routing decision, and it is the whole content of this lesson.

5. The five failure modes, in the order they bite

  1. Indexing cost is unbounded in corpus size, and it is model cost. Every text unit needs extraction and every community needs a summary. Double the corpus and you double the bill.
  2. Re-indexing on change. The graph and its summaries are built from the whole corpus, so adding a document can shift the communities. For a corpus that changes daily this is the killer, not the query cost.
  3. Extraction quality is the ceiling. An LLM decides what the entities are. Deciding that three spellings of a company name are one node is a classic hard problem being handed to a prompt, and nothing downstream recovers from a graph that is confidently wrong.
  4. Query cost on global search. Roughly 331,000 prompt tokens, measured, and the map step varies with the question so caching does not rescue it.
  5. It loses on the queries you actually get. If your users ask where the notice period is in one contract, the graph is pure overhead, and that loss has been measured rather than argued.

6. Does this still matter in 2026?

Yes for one query shape, and no as a default. Here is the decision, as a procedure rather than an opinion.

Start lazy. Microsoft themselves published a cheaper variant, claiming that "LazyGraphRAG data indexing costs are identical to vector RAG and 0.1% of the costs of full GraphRAG" with "more than 700 times lower query cost", while keeping "comparable answer quality to GraphRAG Global Search for global queries". The mechanism is to defer model use to query time and use noun-phrase extraction during indexing instead of pregenerating summaries.

Those numbers are a vendor's claim about its own system, and they are quoted here as such rather than as an independent measurement. Treat them as a reason to try the lazy path first, not as a settled benchmark. One widely repeated figure has been left out of this lesson entirely: a much-quoted dollar cost for indexing a GraphRAG dataset traces only to a blog post with no primary citation, so it does not appear here.

Check the update path before the quality. Outside Microsoft, LightRAG attacks the same problem with dual-level retrieval and, more importantly for an operator, "an incremental update algorithm that ensures the timely integration of new data". That feature is a direct response to failure mode two, and for a live corpus it decides whether the system survives contact with production.

On adoption, be honest. The research activity is real and the ecosystem around it is real. What could not be found, while this lesson was written, is a named large company publishing that GraphRAG in its original form runs its production retrieval. Secondary write-ups consistently describe the production pattern as hybrid - vector search and graph traversal behind a router, chosen per query - but no primary operator source was found for that either, so treat it as the field's reported consensus rather than as measured fact.

Check yourself

Retrieval practice

Answer from memory before revealing.

Why does ordinary retrieval fail on a global question?
The failure is in the task, not the ranking: a property of the whole corpus is written nowhere in particular. Better embeddings, rerankers and bigger windows all leave it unfixed.
What does the indexing stage actually build?
An LLM extracts entities and relationships, communities are detected over that graph, and an LLM pregenerates a summary per community. No fine-tuning and no answer cache is involved.
Roughly how do measured per-query token costs compare?
About 331,000 prompt tokens per global query against roughly 900 for vanilla retrieval, which is close to a three-hundred-fold difference. Some graph methods do sit near vanilla cost, which is why the method matters more than the label.
For a corpus that changes daily, what do you check first?
Communities are built from the whole corpus, so a change can shift them and force a rebuild. That decides maintainability, and it makes the quality comparison moot if it fails.

How this connects

  • Retrieval-Augmented Generation is the prerequisite and the baseline you keep live beside this.
  • The map-reduce over summaries is a search over generated intermediate results, which is the same shape as Tree of Thoughts and the budget argument in Test-Time Scaling.
  • Indexing writes summaries with a model and then trains nothing, which puts it beside Self-Instruct as a use of models to manufacture data.
  • The cost per query is a token-budget problem, so the economics of KV cache and PagedAttention apply directly.
Your teacher. Take a hundred real queries from a system you run and ask the agent to classify each as lookup or sensemaking. That ratio is the decision this lesson is about, and it is usually more lopsided than people expect. Then ask it to estimate the token cost of answering the sensemaking ones by map-reduce over summaries, using the figures above.
