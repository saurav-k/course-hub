FlashAttention

2022 Tri Dao, Daniel Y. Fu, Stefano Ermon, Atri Rudra, Christopher Ré (Stanford; Atri Rudra at SUNY Buffalo). · arXiv:2205.14135

The one-minute version

  • Standard attention writes the full N×N score matrix to slow GPU memory, then reads it back. On long sequences that back-and-forth traffic, not the math, is the bottleneck.
  • FlashAttention is IO-aware: it counts reads and writes between fast on-chip SRAM and slow HBM, and rewrites attention to touch HBM as little as possible.
  • It uses tiling (process attention block by block inside SRAM) plus online softmax (a running-max / running-sum trick) so it never materialises the whole N×N matrix.
  • The result is the exact same answer as normal attention, with memory linear in N instead of quadratic, and real wall-clock speedups: 15% on BERT-large, 3× on GPT-2, 2.4× on Long-Range Arena.
  • In the backward pass it recomputes the score matrix instead of storing it - trading cheap on-chip math for expensive memory.

1. Why this paper exists

By 2022 everyone knew attention cost O(N²) in both compute and memory (Lesson 01). Dozens of papers tried to beat that by approximating attention - sparse patterns, low-rank tricks, kernels. They reduced the FLOP count on paper, yet most were no faster on an actual GPU. FlashAttention starts from a sharper diagnosis: for real sequence lengths, attention is not compute-bound, it is memory-bound. The GPU spends most of its time moving the giant N×N matrix between memory tiers, not multiplying numbers.

A GPU has a steep memory hierarchy. On-chip SRAM is tiny but blisteringly fast. Off-chip HBM (high-bandwidth memory) is large but roughly an order of magnitude slower to reach. Standard attention builds the N×N scores in HBM, reads them back for softmax, writes them again, reads them again to multiply by V. Every one of those round trips crawls at HBM speed.

2. The core problem with softmax: it seems to need the whole row

Why can we not just chop attention into blocks trivially? Because of softmax. To normalise a row of scores you appear to need every score in that row at once: you subtract the row maximum (for numerical stability), exponentiate, then divide by the row sum. If you only have a block of the row, you do not yet know the true maximum or the true sum. Compute a "local" softmax and it will be wrong once a later block reveals a bigger score.

FlashAttention's key mathematical move is the online (streaming) softmax: keep a running maximum and a running sum, and correct the partial result each time a new block arrives. This lets you stream through the keys and values one block at a time and still land on the exact softmax.

3. The online softmax trick, exactly

Say the scores for one query, split across blocks, arrive as vectors s₁, s₂, .... After seeing blocks up to j we hold three running quantities: the max mj, the sum of exponentials ℓj, and the weighted value accumulator oj. When block j+1 arrives we update them.

mnew = max( mj, rowmax(sj+1) ) mnew: the new running maximum. Take the larger of the old max and the biggest score in the fresh block. Subtracting this before exponentiating is what keeps the numbers from overflowing.
α = exp( mj − mnew )   ℓnew = α · ℓj + rowsum( exp(sj+1 − mnew) ) α: a correction factor. Because the max moved from mj to mnew, every earlier exponential was computed against the wrong baseline; multiplying by α = exp(mj − mnew) fixes them in one shot. ℓnew: rescale the old sum by α, then add the fresh block's exponentials.
onew = α · oj + exp(sj+1 − mnew) · Vj+1   output = ofinal / ℓfinal onew: rescale the old value accumulator by the same α, then add this block's exponential-weighted values. output: at the very end divide the accumulator by the running sum ℓ to complete the softmax normalisation. No full N×N matrix ever exists - only these three small running vectors per query block.
The one insight Softmax looks like it needs the whole row, but a running max plus a running sum plus one correction factor α lets you fold in the row one block at a time and reach the exact answer. That is the entire reason attention can be tiled without approximation.

4. Tiling: the two-loop kernel

FlashAttention wraps that online softmax in two nested loops. The outer loop walks over blocks of queries; the inner loop streams every block of keys and values through SRAM, updating the running quantities. Because a query block and a key/value block both fit in SRAM, all the arithmetic for a tile happens on-chip. Only the final output block is written back to HBM.

Why memory becomes linear The full attention matrix would be O(N²) to store. FlashAttention keeps only per-query running statistics of size O(N) and reconstructs scores block by block. Memory is now linear in sequence length, which is what lets Transformers reach 16K and 64K token contexts in the paper's Path-X / Path-256 experiments.

5. The backward pass: recompute, do not store

Training needs gradients, which normally means keeping the N×N attention matrix around from the forward pass so the backward pass can use it. That would throw away the memory win. FlashAttention instead recomputes the scores block by block during the backward pass, using the tiny per-row statistics (the max and the sum) it saved. Recompute is cheap on-chip math; storing an N×N matrix is expensive HBM traffic. Trading the second for the first is a net win.

6. Implement it: tiled online-softmax attention

The real FlashAttention is a fused CUDA kernel - one GPU program that does scores, softmax, and the value multiply without ever returning to HBM in between. We cannot write CUDA here, but we can write the algorithm in numpy so you can see that the tiled online-softmax version returns the exact same numbers as textbook attention. Run it: the two outputs match to floating-point precision.

flash_attention.py · runnable with numpy
import numpy as np

def standard_attention(Q, K, V):
    """Textbook attention: builds the full N x N score matrix."""
    d = Q.shape[-1]
    S = Q @ K.T / np.sqrt(d)                 # (N, N)  <- the big matrix
    S = S - S.max(axis=-1, keepdims=True)    # stability: subtract row max
    P = np.exp(S)
    P = P / P.sum(axis=-1, keepdims=True)    # softmax
    return P @ V                             # (N, d)

def flash_attention(Q, K, V, block=16):
    """Tiled + online softmax. Never forms the full N x N matrix."""
    N, d = Q.shape
    scale = 1.0 / np.sqrt(d)
    O = np.zeros((N, d))
    for i in range(0, N, block):                 # outer loop: query blocks
        Qi = Q[i:i+block]                         # (b, d) - lives in "SRAM"
        m = np.full((Qi.shape[0], 1), -np.inf)   # running max per query
        l = np.zeros((Qi.shape[0], 1))           # running sum of exp
        acc = np.zeros((Qi.shape[0], d))         # running weighted values
        for j in range(0, N, block):             # inner loop: key/value blocks
            Kj, Vj = K[j:j+block], V[j:j+block]
            S = (Qi @ Kj.T) * scale              # (b, b) block scores only
            m_new = np.maximum(m, S.max(axis=1, keepdims=True))
            p = np.exp(S - m_new)                 # exponentials vs the new max
            alpha = np.exp(m - m_new)             # correction for old totals
            l = alpha * l + p.sum(axis=1, keepdims=True)
            acc = alpha * acc + p @ Vj            # rescale old, add new
            m = m_new                             # advance the running max
        O[i:i+block] = acc / l                    # finish the softmax
    return O

np.random.seed(0)
Q, K, V = (np.random.randn(64, 32) for _ in range(3))
ref  = standard_attention(Q, K, V)
flsh = flash_attention(Q, K, V, block=16)
print("max abs difference:", np.abs(ref - flsh).max())   # ~1e-15: EXACT

The two functions are numerically identical because online softmax is exact, not approximate. The difference on a GPU is where the work happens: standard_attention materialises S (the N×N matrix) in HBM; flash_attention only ever holds a small (block, block) tile plus three running vectors. A real kernel also fuses the inner loop into one launch and keeps everything in registers and shared memory.

In production You almost never call this directly. torch.nn.functional.scaled_dot_product_attention(q, k, v) dispatches to a fused FlashAttention kernel automatically when the shapes and dtypes qualify. Same math as Lesson 01, delivered with FlashAttention's IO discipline.

What does FlashAttention actually change about attention?
FlashAttention is exact. It is IO-aware: same math, but tiled so the N×N matrix never lands in slow HBM.
Why can attention be computed block by block despite softmax?
Online softmax keeps a running max and sum, rescaling earlier partial results by a factor as each block arrives.
What does the backward pass do instead of storing the matrix?
Recomputation trades cheap on-chip math for expensive HBM storage, preserving the linear-memory win.
Which pair correctly describes the GPU memory hierarchy here?
On-chip SRAM is tiny but extremely fast; off-chip HBM is large but roughly ten times slower to reach.

How this connects

  • The O(N²) grid flagged in Attention Is All You Need is exactly what FlashAttention refuses to store.
  • Next, FlashAttention-2 keeps the same idea but repartitions the work across the GPU for another ~2×.
