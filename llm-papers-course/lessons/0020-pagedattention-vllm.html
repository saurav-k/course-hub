PagedAttention (vLLM)

2023 Kwon, Li, Zhuang, Sheng, Zheng, Yu, Gonzalez, Zhang, Stoica (UC Berkeley). · arXiv:2309.06180 · "Efficient Memory Management for Large Language Model Serving with PagedAttention"

The one-minute version

  • The previous lesson made the KV cache smaller. This one manages it without waste. Older serving systems stored each sequence's cache in one contiguous block sized for the worst case, wasting 60-80% of it to fragmentation and over-reservation.
  • PagedAttention borrows the oldest trick in operating systems: virtual memory paging. It splits the KV cache into fixed-size blocks (pages) that need not be contiguous, and a block table maps each sequence's logical positions to scattered physical blocks.
  • Fragmentation nearly vanishes, so you fit far more sequences in the same GPU memory, which means bigger batches and higher throughput.
  • Blocks can also be shared. Sequences with a common prefix point at the same physical blocks (copy-on-write when one diverges), so parallel samples of one prompt store the prompt once. The result was a 2-4× throughput gain, and the system is vLLM.

1. Why this paper exists

Before PagedAttention, a serving system had to reserve KV cache space up front. Because it could not know how long a reply would be, it reserved room for the maximum possible length, in one contiguous chunk, per sequence. Two kinds of waste followed. Internal fragmentation: the reserved-but-unused tail of each sequence's block. External fragmentation: leftover gaps between blocks too small to hold a new sequence. The paper measured that existing systems wasted 60% to 80% of KV memory this way. Most of your expensive GPU memory sat empty.

2. The idea: KV cache as virtual memory

Operating systems solved exactly this problem decades ago. A program sees a clean, contiguous virtual address space, but physically its memory is scattered across non-contiguous pages. A page table translates virtual addresses to physical ones. PagedAttention maps this idea onto the KV cache almost one to one.

A "block" holds the keys and values for a fixed number of tokens (say 16). A sequence is just a list of logical blocks; the block table records which physical block each logical block currently lives in. To append a token, you write into the current block, and when it fills you grab any free physical block and add it to the table. Nothing needs to be contiguous, so there is nothing to fragment.

blocks(seq) = ceil( S / B )   internal_waste ≤ (B − 1) tokens per sequence S: tokens in the sequence so far. B: block size (tokens per block, e.g. 16). ceil(S / B): number of blocks the sequence needs. Only the final block can be partly empty, so wasted space is at most B minus 1 tokens for the whole sequence - a tiny bounded amount, versus the worst-case full reservation of the old contiguous scheme.

3. Prefix sharing and copy-on-write

Paging unlocks a second win that contiguous allocation could never allow. If two sequences share a prefix - the same system prompt, or several samples of one user prompt - their early logical blocks hold identical keys and values. So point them at the same physical blocks. Store the shared prefix once. This is copy-on-write from operating systems: the blocks are shared read-only until one sequence writes a divergent token, at which point that single block is copied and the writer edits its private copy.

4. Implement it: a block-table KV allocator

This is a small but faithful simulation of the mechanism: a pool of fixed-size physical blocks, per-sequence block tables, per-block reference counts for sharing, and copy-on-write on divergence. It prints the memory saved by prefix sharing.

paged_kv.py · runnable, pure Python
class PagedKVAllocator:
    def __init__(self, n_blocks, block_size):
        self.block_size = block_size
        self.free = list(range(n_blocks))     # pool of physical block ids
        self.refcount = {}                    # physical block -> how many seqs use it
        self.tables = {}                      # seq id -> list of physical block ids

    def _alloc(self):
        blk = self.free.pop()                 # take any free physical block
        self.refcount[blk] = 1
        return blk

    def new_seq(self, seq_id):
        self.tables[seq_id] = []

    def append_token(self, seq_id, pos):
        table = self.tables[seq_id]
        if pos % self.block_size == 0:        # current block full -> need a new one
            table.append(self._alloc())
        # (writing the K,V into table[-1] happens here in a real system)

    def fork(self, parent, child):
        """Share the parent's blocks with a child (prefix sharing)."""
        self.new_seq(child)
        self.tables[child] = list(self.tables[parent])
        for blk in self.tables[child]:
            self.refcount[blk] += 1           # now shared, read-only

    def write_cow(self, seq_id, logical_blk):
        """Copy-on-write: divergent write to a shared block."""
        table = self.tables[seq_id]
        blk = table[logical_blk]
        if self.refcount[blk] > 1:            # shared -> must copy before editing
            self.refcount[blk] -= 1
            table[logical_blk] = self._alloc()

    def used_blocks(self):
        return len(self.refcount)

# --- demo: one 64-token prompt, sampled 4 ways ---
alloc = PagedKVAllocator(n_blocks=256, block_size=16)
alloc.new_seq("prompt")
for pos in range(64):                          # 64 tokens = 4 full blocks
    alloc.append_token("prompt", pos)
shared_blocks = alloc.used_blocks()

for s in ["A", "B", "C", "D"]:                 # 4 samples share the prompt
    alloc.fork("prompt", s)
alloc.write_cow("A", logical_blk=3)            # sample A diverges in its last block

naive = 4 * 4                                  # 4 samples * 4 blocks each, no sharing
print(f"prompt blocks stored once : {shared_blocks}")
print(f"physical blocks with sharing: {alloc.used_blocks()}")
print(f"naive copies would need     : {naive} blocks "
      f"({naive/alloc.used_blocks():.1f}x more)")

The output shows the prompt stored once, four samples sharing it, and exactly one extra block spent when sample A diverges. Naive per-sample copies would need several times more memory. That saved memory is what lets vLLM pack a much larger batch onto the same GPU, which is where the throughput comes from.

5. What it bought

ConcernContiguous allocationPagedAttention
Internal fragmentationLarge reserved tailsAt most one partial block
External fragmentationUnusable gaps formNone; blocks are uniform
Memory wastedRoughly 60-80%Near zero
Shared prefixesCopied per sequenceShared with copy-on-write

The paper reports a 2-4× throughput improvement at the same latency versus prior serving systems, with bigger gains on longer sequences and parallel decoding. PagedAttention did not change the model or the math at all - it changed only how the cache is stored - and it became the default memory manager for open-source LLM serving.

What classic systems idea does PagedAttention borrow?
It maps logical KV blocks to scattered physical blocks through a block table, exactly like OS paging.
Why did contiguous allocation waste so much memory?
Reserving one contiguous max-length block per sequence left large unused tails and gaps: 60-80% waste.
How do two samples of one prompt share its KV cache?
Prefix sharing points both block tables at the same physical blocks; the prompt is stored once.
What happens on a copy-on-write divergence?
Shared blocks stay read-only until a write; then just that block is copied for the writer to modify.

How this connects

  • Complements KV cache compression - that lesson shrinks the cache; PagedAttention stops wasting whatever cache you have.
  • Stacks with GQA and MQA - fewer KV heads plus paged blocks compound into more sequences per GPU.
  • Pairs with FlashAttention - Flash speeds the attention kernel; vLLM feeds it well-managed blocks.
  • Sets up Speculative Decoding - another serving-layer speedup that leaves the model's output unchanged.
