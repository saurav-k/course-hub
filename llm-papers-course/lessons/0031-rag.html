Retrieval-Augmented Generation

2020 Lewis, Perez, Piktus, Petroni, Karpukhin, Goyal, Kuttler, Lewis, Yih, Rocktaschel, Riedel, Kiela (Facebook AI Research / UCL). · arXiv:2005.11401

The one-minute version

  • A language model stores everything it knows inside its weights - parametric memory. That memory is fixed at training time, hard to update, and prone to confidently making things up.
  • RAG bolts on a second, non-parametric memory: a searchable index of documents (a dense vector index of Wikipedia) that the model can look things up in.
  • Given a question, a retriever (DPR) pulls the top-k relevant passages, and a generator (BART) writes an answer conditioned on both the question and those passages.
  • Result: more specific, factual answers, fewer hallucinations, and knowledge you can update by swapping the index - no retraining. This is the blueprint behind almost every modern "chat with your documents" system.

1. Why this paper exists

A pretrained model is a compression of its training corpus into weights. Ask it a fact and it reconstructs an answer from those weights. This works impressively often, but it has three deep flaws. The knowledge is frozen at the training cutoff. It is opaque - you cannot point to where an answer came from. And when the weights do not actually contain the fact, the model does not say "I don't know"; it hallucinates a plausible-sounding wrong answer.

The paper's idea is to separate knowing from saying. Keep the language model's fluency and reasoning, but let it fetch facts from an external store at query time instead of relying only on memory. Swap the store and the model instantly "knows" new things.

2. Two kinds of memory

RAG combines two memories that had usually been used alone.

  • Parametric memory - a pretrained sequence-to-sequence model, BART, whose weights hold general language ability and background knowledge. This is the generator.
  • Non-parametric memory - a dense vector index of a Wikipedia dump, split into ~21 million 100-word passages. Each passage is stored as a vector so it can be searched by meaning, not just keywords.

The retriever is Dense Passage Retrieval (DPR): two BERT-based encoders, one for questions and one for passages, trained so that a question vector lands close to the vectors of passages that answer it. Closeness is measured by dot product, and finding the top matches is a fast nearest-neighbour search.

3. The full retrieve-then-generate pipeline

Put the pieces in order. A question comes in. DPR encodes it and retrieves the top-k passages (the paper uses small k like 5 or 10). Each retrieved passage is concatenated with the question and fed to BART, which generates an answer. The retrieved documents act as an evidence packet the generator reads before writing.

4. RAG-Sequence vs RAG-Token

There is a subtle choice: should the whole answer come from one retrieved passage, or can different parts of the answer draw on different passages? The paper defines both.

  • RAG-Sequence: pick the retrieved documents, then generate the entire answer conditioned on the same document(s). Simple and coherent.
  • RAG-Token: for each generated token, the model can blend over all retrieved documents. More flexible - a single answer can stitch facts from several sources.

5. The math, read in plain English

RAG treats the retrieved document as a hidden variable and marginalizes over the top-k. The two variants differ only in where the sum sits.

pRAG-Seq(y ÷ x) = Σz ∈ top-k pret(z ÷ x) · pgen(y ÷ x, z) x: the question. y: the full answer sequence. z: a retrieved passage. pret(z ÷ x): how relevant the retriever judged passage z (its retrieval score, softmaxed over the top-k). pgen(y ÷ x, z): how likely BART is to produce the whole answer y when reading question x and passage z. Σ: average over the top-k passages, weighted by relevance - so a better-matched passage counts more.
pRAG-Tok(y ÷ x) = ∏i Σz ∈ top-k pret(z ÷ x) · pgen(yi ÷ x, z, y<i) ∏i: multiply across answer positions - the answer is generated token by token. yi: the i-th token; y<i: the tokens already written. The document sum Σz now sits inside the per-token product, so each token can lean on a different passage. That is the one difference from RAG-Sequence.

6. Implement it: a minimal RAG in numpy

The essence of RAG needs no heavy libraries. Below: chunk documents, embed them, embed the query, take cosine top-k, and stuff the winners into a prompt. The embedder here is a toy bag-of-words for offline running; in practice you would call a real embedding model, but the pipeline shape is identical.

minimal_rag.py · runnable with numpy
import numpy as np, re
from collections import Counter

# --- 1. chunk documents into small passages ---
def chunk(text, size=12):
    words = text.split()
    # slide a window so each chunk is a retrievable passage
    return [" ".join(words[i:i+size]) for i in range(0, len(words), size)]

docs = [
    "The Eiffel Tower is in Paris and was completed in 1889 for the World's Fair.",
    "The Great Wall of China is over 13000 miles long and was built over many centuries.",
    "Python is a programming language created by Guido van Rossum in 1991.",
]
passages = [c for d in docs for c in chunk(d)]

# --- 2. a toy embedder: bag-of-words vector over a shared vocabulary ---
def tokenize(s): return re.findall(r"[a-z0-9]+", s.lower())
vocab = sorted({t for p in passages for t in tokenize(p)})
index = {w: i for i, w in enumerate(vocab)}

def embed(text):
    v = np.zeros(len(vocab))
    for w, c in Counter(tokenize(text)).items():
        if w in index:
            v[index[w]] = c
    n = np.linalg.norm(v)
    return v / n if n > 0 else v          # unit vectors -> dot product = cosine

# --- 3. build the index once (offline) ---
doc_vecs = np.stack([embed(p) for p in passages])

# --- 4. retrieve top-k by cosine similarity ---
def retrieve(query, k=2):
    q = embed(query)
    sims = doc_vecs @ q                    # cosine sim to every passage
    top = np.argsort(-sims)[:k]            # highest similarity first
    return [(passages[i], float(sims[i])) for i in top]

# --- 5. stuff retrieved passages into a grounded prompt ---
def build_prompt(query, k=2):
    hits = retrieve(query, k)
    context = "\n".join(f"- {p}" for p, _ in hits)
    return (f"Use ONLY the context to answer.\n"
            f"Context:\n{context}\n\nQuestion: {query}\nAnswer:")

question = "When was the Eiffel Tower completed?"
for p, s in retrieve(question):
    print(f"{s:.2f}  {p}")
print("\n--- prompt sent to the generator ---")
print(build_prompt(question))
# the generator now reads the 1889 passage and answers from it, not from memory

Two practical points the code makes concrete. Chunking matters: passages must be small enough to be specific but large enough to be self-contained, which is why real systems tune chunk size and overlap. And embeddings are the whole magic of dense retrieval - a good embedding puts "completed in 1889" near "When was it finished?" even with no shared words. Replace the toy embed with a real sentence-embedding model and this becomes a usable RAG system.

Why it curbs hallucination A plain model answers from fuzzy memory. RAG puts the actual source text in the prompt and instructs the generator to answer from the context. The model's job shifts from "recall the fact" to "read and summarize the passage," which is far easier and far more faithful - and you can show the user which passage the answer came from.

RAG set the state of the art on three open-domain question-answering benchmarks and produced more specific, diverse, and factual generations than a same-size parametric-only baseline. More lasting than the numbers is the pattern: separate the knowledge store from the reasoner, and you get updatable, attributable, grounded generation. Every "chat over your PDFs" product today is a descendant of this paper.

Check yourself

Retrieval practice

Answer from memory before revealing.

What is the non-parametric memory in a RAG system?
Non-parametric memory is the external document index the model looks things up in, separate from the knowledge baked into weights.
What does the DPR retriever actually compare to find passages?
DPR encodes both sides into dense vectors and finds passages whose vectors are nearest the question vector, matching by meaning not spelling.
How does RAG-Token differ from RAG-Sequence?
RAG-Token puts the document sum inside the per-token product, so different tokens of one answer can lean on different passages.
Why does retrieval reduce hallucination?
With the real passage in context, the task becomes read-and-summarize rather than recall-from-memory, which is far more faithful.

How this connects

  • RAG's retriever is built from BERT encoders; its generator is a sequence-to-sequence descendant of the Transformer.
  • ReAct makes retrieval an explicit action the model chooses mid-reasoning, rather than a fixed first step.
  • Grounding answers in evidence complements Chain-of-Thought: reason over facts you retrieved rather than facts you guessed.
  • Because it needs no retraining to add knowledge, RAG pairs naturally with cheap adapters like QLoRA for the style layer.
Your teacher. Swap the toy embedder for a real one in your head: ask the agent why "finished" and "completed" get similar vectors from a trained embedding model but not from the bag-of-words stub. Then ask it to break RAG on purpose by chunking too coarsely, and watch retrieval return an irrelevant passage. Feeling the failure modes is how you learn to tune a real system.
