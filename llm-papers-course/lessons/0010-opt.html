OPT: Open Pre-trained Transformer Language Models

2022 Zhang, Roller, Goyal, Artetxe, Chen, and others (Meta AI). · arXiv:2205.01068

The one-minute version

  • OPT is an open reproduction of GPT-3: a suite of decoder-only models from 125M to 175B parameters, released with weights so researchers could finally study a GPT-3-scale model directly.
  • The 175B version matches GPT-3 quality while costing about one-seventh the carbon to develop.
  • Its most unusual contribution is honesty: Meta published a training logbook documenting the real mess of a large run - loss spikes, hardware failures, and learning-rate restarts.
  • The lasting lesson is not the model but the practice: reproducibility, openness, and a candid record of how large-scale training actually behaves.

1. Why this paper exists

GPT-3 (Lesson 06) was a landmark, but it was a closed landmark. You could rent it through an API, but you could not inspect its weights, probe its failure modes, or study its biases. For a research community trying to understand large language models, that was a wall. OPT was Meta AI's answer: build a model of the same class, and give it away - weights, code, and, crucially, the diary of what went wrong.

2. A suite, not a single model

OPT is not one model but a family spanning three orders of magnitude: 125M, 350M, 1.3B, 2.7B, 6.7B, 13B, 30B, 66B, and 175B. This matters for science. If you only release the biggest model, researchers cannot study how behaviour changes with scale. A ladder of sizes lets you plot trends - where a capability first appears, how loss falls, where bias grows.

3. The logbook: training as it really is

Papers usually present a clean final run. OPT did the opposite. Meta released the actual chronological logbook from training the 175B model, and it reads like a ship's log through a storm. Training a model this large over weeks on hundreds of GPUs is not a smooth curve - it is a fight against instability and failing hardware.

Three failure modes dominate the logbook, and they are worth naming because you will hit them yourself at any serious scale:

  • Loss spikes - the training loss suddenly shoots up, sometimes diverging. Left alone the run is ruined. The fix is usually to roll back to a checkpoint and resume past the offending data with a lower learning rate.
  • Hardware failures - over weeks on hundreds of GPUs, nodes crash. Without frequent checkpoints you lose days of compute.
  • Learning-rate restarts - the team repeatedly adjusted the learning rate mid-run to nurse training past unstable regions.

4. Anatomy of a loss spike

A loss spike is the villain of large-scale training. The gradient of a single bad batch, or an unlucky accumulation, blows up the weights; the model's predictions collapse; loss rockets. The standard defences are gradient clipping (cap the size of the update) and checkpoint-and-restart (save often, roll back when things break).

5. Why gradient clipping works

Gradient clipping puts a ceiling on how far one step can move the weights. You compute the overall size (the norm) of the gradient vector; if it exceeds a threshold, you scale the whole vector down so its norm equals the threshold. Direction is preserved, magnitude is capped.

if ‖g‖ > c :   g ← g · ( c / ‖g‖ ) g: the gradient - the vector of updates for every parameter this step. ‖g‖: its norm, a single number for the overall update size. c: the clip threshold you choose. If the update is bigger than c, multiply g by c / ‖g‖ so its new norm is exactly c. The direction is unchanged; only the length is capped, so one freak batch cannot detonate the weights.
The core intuition Training is a walk downhill. A loss spike is a single giant, wrong step off a cliff. Gradient clipping is a leash on step size; checkpointing is a rope back to the last safe ledge. Neither prevents rough terrain - they let you survive it. OPT's logbook is the honest map of that terrain.

6. Implement it: a training-stability toolkit

Everything in the logbook reduces to a handful of mechanisms. Here is a compact, runnable toolkit: gradient clipping, a loss-spike detector, and checkpoint/restart logic - the exact tools that kept OPT-175B alive.

stability_toolkit.py · runnable with torch
import torch, os

class SpikeGuard:
    """Detects loss spikes and restores the last good checkpoint."""
    def __init__(self, model, opt, ckpt_dir="ckpts", spike_factor=1.5):
        self.model, self.opt = model, opt
        self.dir = ckpt_dir; os.makedirs(ckpt_dir, exist_ok=True)
        self.spike_factor = spike_factor      # spike = loss > factor x recent avg
        self.recent = []                      # rolling window of good losses
        self.last_good = None

    def save(self, step):
        path = f"{self.dir}/step_{step}.pt"
        torch.save({"model": self.model.state_dict(),
                    "opt":   self.opt.state_dict(), "step": step}, path)
        self.last_good = path                 # remember the newest safe point

    def restore(self):
        s = torch.load(self.last_good)
        self.model.load_state_dict(s["model"])
        self.opt.load_state_dict(s["opt"])
        return s["step"]

    def is_spike(self, loss):
        if len(self.recent) < 5:              # need a baseline first
            self.recent.append(loss); return False
        avg = sum(self.recent) / len(self.recent)
        if loss > self.spike_factor * avg:    # loss jumped too far, too fast
            return True
        self.recent = (self.recent + [loss])[-20:]   # keep last 20 good losses
        return False

def train_step(model, opt, batch, guard, clip=1.0, lr_backoff=0.5):
    opt.zero_grad()
    loss = model(batch)                       # your forward returns a scalar loss
    loss.backward()
    # 1) GRADIENT CLIPPING: cap the update size before it lands
    grad_norm = torch.nn.utils.clip_grad_norm_(model.parameters(), clip)
    # 2) SPIKE DETECTION + 3) RESTART
    if guard.is_spike(loss.item()) or not torch.isfinite(grad_norm):
        step = guard.restore()                # roll back to last checkpoint
        for g in opt.param_groups:            # nurse past the bad patch
            g["lr"] *= lr_backoff             # lower the learning rate
        return {"restored": True, "step": step}
    opt.step()
    return {"restored": False, "loss": loss.item(), "grad_norm": float(grad_norm)}

Trace the three defences. clip_grad_norm_ is the leash from section 5 - it caps the update and also hands back the gradient norm, so a non-finite value (a full-blown explosion) is caught too. SpikeGuard.is_spike flags a loss that jumps past a multiple of the recent average. And restore plus the learning-rate backoff is the checkpoint-and-restart dance the logbook performs again and again.
