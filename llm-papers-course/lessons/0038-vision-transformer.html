Vision Transformer (ViT)

working 2020 13 min Dosovitskiy, Beyer, Kolesnikov, Weissenborn, Zhai, Unterthiner, Dehghani, Minderer, Heigold, Gelly, Uszkoreit, Houlsby · Google Research · arXiv:2010.11929

The one-minute version

  • Cut the image into a grid of fixed-size squares, flatten each square, project it to the model width, add a position embedding. You now have a sequence of vectors, and a standard Transformer encoder does not know it came from a picture.
  • There is no convolution anywhere. The paper's own claim is that "a pure transformer applied directly to sequences of image patches can perform very well on image classification tasks".
  • The price is data. A convolution hands you locality and translation equivariance for free; a ViT has to learn them, and the paper is explicit that its result holds "when pre-trained on large amounts of data".
  • Still matters in 2026, and you will never train one. Every vision tower you would ship is a ViT or a close variant, so the live question is which pretrained one, at what resolution, and what the patch count does to your token bill.

1. Why this paper exists

Before this paper, accuracy was not the problem. Convolutional networks were already very good at recognising objects. The problem was that vision and language had grown two of everything: two architectures, two sets of engineering tricks, two scaling stories, two communities. Improving one taught you nothing about the other.

A Transformer eats a sequence of vectors and does not care what those vectors mean. So the question is not "how do we build attention for images" but the much smaller one: what is an image a sequence of? The paper's answer is a grid of square patches, and the rest of the architecture is left alone.

2. The mechanism, in five steps

Everything below happens before the first attention layer. After it, the model is the encoder from Lesson 01, unchanged.

Why a position embedding is needed at all. Attention is permutation invariant: shuffle the patches and the encoder computes the same thing. A picture with its patches shuffled is a different picture, so the grid position has to be added back explicitly, exactly as token position is added back for text.

Why a class token. The encoder returns one vector per patch, and classification wants one vector per image. The paper prepends an extra learned token whose output is used as the image summary, so the classifier head reads a single position.

3. The maths: patch count is your token bill

There is only one equation in this lesson and it is arithmetic, not calculus. It is also the number that decides what a vision model costs you, which is why it is worth working rather than quoting.

N = (H · W) / P² N: how many patch tokens the encoder receives. H and W: the height and width of the input image in pixels. P: the side length of one square patch in pixels, so P² is the pixel count of a single patch. Read it as: the number of tokens is the number of pixels divided by the number of pixels per patch. A class token adds one more.
  1. The paper's own setting. A 224 by 224 image at a patch side of 16 gives a grid of 224 ÷ 16 = 14 patches per side, so N = 14 × 14 = 196 tokens, plus the class token, which is 197.
  2. Raise the resolution and the cost is quadratic in the side. At 336 by 336 with the same 16-pixel patch the grid is 21 per side, so N = 21 × 21 = 576 tokens. The image got 1.5 times wider and the token count roughly tripled.
  3. Now tile a document page. Four 336-pixel crops plus one whole-page thumbnail is 5 × 576 = 2,880 tokens before the reader's question is appended. Attention within the vision tower is quadratic in N on top of that.

4. What it did not solve

Two limits, and the first is the one that decides how you will actually use a ViT.

It threw away the free assumptions. A convolution is built to slide the same small filter everywhere, so locality and translation equivariance come for nothing. A ViT has neither and must learn both from examples. The paper states the condition plainly - the result holds "when pre-trained on large amounts of data" - and the consequence is that on a small dataset a ViT trained from scratch loses to a convolutional network. Read the efficiency claim in the same light: ViT matches convolutional networks "while requiring substantially fewer computational resources to train", and that is measured at the large-pretraining end, not on your own labelled folder.

It did nothing about the cost of attention. Attention is quadratic in the number of patches, and the number of patches is quadratic in the resolution. That is why high-resolution vision is still expensive and why practical vision-language models play games with tiling, patch pruning and resamplers.

The commonest way to get this wrong is to read "Transformers beat convolutions" and reach for a randomly initialised ViT on ten thousand of your own images. The paper's result is a claim about pretraining scale, not about the architecture in isolation, and at small scale it points the other way.

5. Implement it: the patch embedding

The only new module is the tokeniser. A convolution whose kernel and stride both equal the patch size is exactly "cut into non-overlapping patches and apply one linear projection", so the whole of step one to three is a single layer.

vit_patches.py · runnable with torch
import torch
import torch.nn as nn

class PatchEmbed(nn.Module):
    """Image -> sequence of patch vectors. Kernel == stride == patch size,
    so this convolution IS the cut-and-project step, done in one op."""
    def __init__(self, img=224, patch=16, in_ch=3, dim=768):
        super().__init__()
        self.n_patches = (img // patch) ** 2          # 14 * 14 = 196
        self.proj = nn.Conv2d(in_ch, dim, kernel_size=patch, stride=patch)
        self.cls = nn.Parameter(torch.zeros(1, 1, dim))              # image summary
        self.pos = nn.Parameter(torch.zeros(1, self.n_patches + 1, dim))

    def forward(self, x):                              # x: (B, 3, 224, 224)
        x = self.proj(x)                               # (B, dim, 14, 14)
        x = x.flatten(2).transpose(1, 2)               # (B, 196, dim)
        cls = self.cls.expand(x.size(0), -1, -1)       # (B, 1, dim)
        x = torch.cat([cls, x], dim=1)                 # (B, 197, dim)
        return x + self.pos                            # positions added back

class ViT(nn.Module):
    """Patch embedding, then the ordinary text encoder, then a head."""
    def __init__(self, img=224, patch=16, dim=768, depth=12, heads=12, classes=1000):
        super().__init__()
        self.embed = PatchEmbed(img, patch, 3, dim)
        layer = nn.TransformerEncoderLayer(dim, heads, dim * 4,
                                           batch_first=True, norm_first=True)
        self.encoder = nn.TransformerEncoder(layer, depth)
        self.norm = nn.LayerNorm(dim)
        self.head = nn.Linear(dim, classes)

    def forward(self, x):
        x = self.encoder(self.embed(x))
        return self.head(self.norm(x[:, 0]))           # read the class token only

model = ViT()
out = model(torch.randn(2, 3, 224, 224))
print(model.embed.n_patches, out.shape)   # 196  torch.Size([2, 1000])

Count the vision-specific lines. There are three, all inside PatchEmbed, and the rest is nn.TransformerEncoder. That ratio is the paper.

6. Does this still matter in 2026?

Yes, universally, and almost nobody implements one. Every vision tower in every vision-language model you would ship is a ViT or a close variant, and the diffusion models in Lesson 43 put a ViT in the denoiser as well. The architecture is load-bearing infrastructure.

But your relationship to it is consumption. The pretrained encoders come in a small number of sizes - SigLIP 2, the current default family, ships at 86M, 303M, 400M and 1B parameters - and you pick one rather than design one. The staff-level question is never "should I use a ViT". It is: which pretrained encoder, at what input resolution, and what does the resulting patch count do to my context window and my bill.

Retrieval practice

Answer from memory before revealing.

What does a Vision Transformer feed into the encoder?
The image is cut into fixed square patches, each flattened and linearly projected. The first option describes a hybrid the paper contrasts with, the third and fourth are hand-built inputs nobody uses here.
Why does a ViT need a lot of pretraining data?
A convolution builds in locality and translation equivariance; a ViT learns them from examples. The other three name mechanisms that are either false or not what the paper points at.
A 224px image at 16px patches gives how many patch tokens?
224 divided by 16 is 14 per side, so 196 patches plus a class token. 576 is the count at 336px, and 768 is the length of one flattened patch, not the token count.
What is the practical 2026 relationship to ViT for most engineers?
Pretrained ViTs are consumed, not trained: the live decisions are which encoder and what resolution. Training from scratch is the failure mode the paper warns about, and convolutions do not win at large scale.

How this connects

  • The encoder ViT reuses is exactly the one from Attention Is All You Need. Only the tokeniser is new.
  • The masked objective of BERT is the ancestor of masked image pretraining, one of the two ways ViTs are pretrained.
  • CLIP trains a ViT as its image encoder, which is what puts pictures and words in one space.
  • Latent Diffusion and its successors put a ViT inside the generator itself, so the same block draws as well as reads.
  • Patch count is a context-length problem, so FlashAttention and KV cache economics apply here unchanged.
