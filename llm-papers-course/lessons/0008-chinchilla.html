Chinchilla: Compute-Optimal Scaling

2022 Hoffmann, Borgeaud, Mensch, Buchatskaya, Cai, Rutherford, et al. (DeepMind). · arXiv:2203.15556 · "Training Compute-Optimal Large Language Models"

The one-minute version

  • Everyone had been building bigger and bigger models on roughly the same amount of data. Chinchilla says that is the wrong trade.
  • For a fixed compute budget, model size and training tokens should grow together, in roughly equal proportion.
  • The rule of thumb: about 20 training tokens per parameter. Most famous models were far too big and badly under-trained.
  • Proof: a 70B model (Chinchilla) trained on 1.4T tokens beat the 280B Gopher and GPT-3 175B, using the same compute.

1. Why this paper exists

Lesson 05 (Scaling Laws) told everyone that loss falls as a power law with model size, and it was read as "make the model as big as you can afford". So the field raced to hundreds of billions of parameters - GPT-3 (175B), Gopher (280B), MT-NLG (530B) - while keeping training data at a few hundred billion tokens. Chinchilla asked a sharper question: given a fixed number of FLOPs, what split between parameters and data actually minimises loss?

2. Three ways to find the optimum

The paper estimates the compute-optimal frontier three independent ways and gets the same answer, which is what makes it convincing.

3. The parametric loss surface

Approach 3 fits an explicit formula for loss as a function of parameters N and tokens D. Reading it in plain English: there is a floor you can never beat (the entropy of language itself), plus a penalty for having too few parameters, plus a penalty for having seen too little data.

L(N, D) = E + A / Nα + B / Dβ E: the irreducible loss, the noise floor of natural text. A / Nα: how much extra loss comes from a limited number of parameters (shrinks as the model grows). B / Dβ: how much extra loss comes from limited data (shrinks as you train on more tokens). Fitted exponents are small and similar, α ≈ 0.34 and β ≈ 0.28, which is why the two terms want to be balanced.
Why balance falls out Because the two exponents are close, spending your next FLOP on parameters or on data buys almost the same loss reduction only when the two penalty terms are kept roughly equal. Let one lag and the lagging term dominates the loss. Hence: scale both together.

4. The headline result

Chinchilla used the same compute as Gopher but reallocated it: a quarter of the parameters, over four times the data. It then outperformed Gopher, GPT-3, and MT-NLG across a wide benchmark suite. A smaller, better-fed model won. As a bonus, being smaller, it is cheaper to run at inference forever after.

5. Compute it yourself

Given a compute budget in FLOPs, the compute-optimal split is a short calculation. This code uses the C ≈ 6 N D rule and the paper's finding that the optimal ratio D/N is about 20 to hand you the recommended model size and token count.

chinchilla.py · runnable with plain python
def compute_optimal(budget_flops, tokens_per_param=20.0):
    # Compute rule of thumb: C = 6 * N * D  (N params, D tokens)
    # Chinchilla-optimal keeps D / N ~ 20.
    # Substitute D = r * N  =>  C = 6 * N * (r * N) = 6 r N^2
    r = tokens_per_param
    N = (budget_flops / (6.0 * r)) ** 0.5      # optimal parameter count
    D = r * N                                   # optimal token count
    return N, D

for exp in [21, 22, 23, 24]:                    # a range of FLOP budgets
    C = 10 ** exp
    N, D = compute_optimal(C)
    print(f"budget 1e{exp} FLOPs -> {N/1e9:6.1f}B params, {D/1e12:5.2f}T tokens")

# Contrast: what GPT-3 actually did with its ~3.1e23 FLOP budget.
N_opt, D_opt = compute_optimal(3.1e23)
print(f"\nGPT-3 budget optimum: {N_opt/1e9:.0f}B params, {D_opt/1e12:.2f}T tokens")
print("GPT-3 actual:         175B params, 0.30T tokens  (too big, too little data)")

Run it and you will see the same story the paper tells: at GPT-3's compute budget, the optimal model is far smaller than 175B and should have seen far more than 300B tokens. The extra parameters were largely wasted capacity.

6. What changed after this paper

Chinchilla reset the field's defaults. Models got smaller and more thoroughly trained. It directly set up the next lesson: LLaMA pushed even past 20 tokens/param, training small models on trillions of tokens because, once you also care about inference cost, over-training a small model is a bargain.

What is Chinchilla's central recommendation?
At fixed compute, loss is minimised when parameters and data scale at nearly the same rate.
Roughly how many training tokens per parameter is compute-optimal?
The famous ratio is about 20 tokens per parameter; Chinchilla 70B saw 1.4T tokens.
Why did Chinchilla beat Gopher on the same compute?
Same compute, reallocated: 70B params (vs 280B) on 1.4T tokens (vs 300B). Better-fed won.
In L(N,D)=E+A/N^α+B/D^β, what does E represent?
E is the noise floor of language you can never beat; the other two terms are the size and data penalties.

How this connects

  • Revises Scaling Laws - same power-law framework, but a corrected recipe for spending compute.
  • Sets up LLaMA - which over-trains small models even further, weighing inference cost too.
  • Explains GPT-3's inefficiency - a huge model starved of data.
  • Data quality still matters alongside quantity - see The Pile.
