Grouped-Query Attention

2023 Ainslie, Lee-Thorp, de Jong, Zemlyanskiy, Lebrón, Sanghai (Google Research). · arXiv:2305.13245 · "GQA: Training Generalized Multi-Query Transformer Models from Multi-Head Checkpoints"

The one-minute version

  • Multi-Query Attention shrinks the KV cache to one shared key/value head, which is fast but loses a little quality. Full Multi-Head Attention keeps quality but keeps the big cache.
  • Grouped-Query Attention (GQA) sits between them: it uses G key/value heads where 1 < G < n_heads. Each KV head is shared by a small group of query heads.
  • This one knob interpolates the whole spectrum. With a handful of groups you recover almost all of MHA's quality while keeping almost all of MQA's speed.
  • You do not retrain from scratch. You uptrain an existing MHA checkpoint: mean-pool its KV heads into G groups and fine-tune with about 5% of the original pre-training compute. GQA is now the default in LLaMA-2 and LLaMA-3.

1. Why this paper exists

The previous lesson left us with two extremes. Standard multi-head attention gives every query head its own key and value head - best quality, biggest KV cache. Multi-query attention collapses all key/value heads into one - smallest cache, fastest decoding, but a measurable dip in quality and sometimes training instability. The obvious question: is there something in the middle?

GQA fills that gap, and it does it without paying the enormous cost of pre-training a fresh model. That second contribution - a cheap conversion recipe - is why the technique spread so fast.

2. The idea: groups of query heads share a KV head

Recall that a query head is "what am I looking for", while a key/value head is "the library everyone reads from". MHA gives each query head its own private library. MQA forces all query heads to share one library. GQA takes the middle road: split the query heads into G groups, and give each group its own shared key/value head.

Notice the beautiful property: GQA is a strict generalisation. Set G equal to the number of heads and every group has one query head, which is plain MHA. Set G to 1 and every query head shares the single library, which is plain MQA. One equation, both extremes, and every useful point between.

Why the middle wins Going from n heads down to a few groups removes almost all of the KV cache, because cache size is proportional to the number of KV heads, not query heads. But keeping more than one group preserves most of the expressive variety that MQA throws away. The quality loss is roughly flat until you drop toward one group, so a small G captures the whole bargain.

3. How big is the cache, exactly

The KV cache formula from the last lesson had a factor for the number of heads. GQA simply replaces the query-head count H with the group count G in the key/value storage term.

cache_bytes = 2 · L · G · dhead · S · B · bytes 2: one key and one value. L: number of layers. G: number of KV groups (this is the term GQA controls; MHA uses G = n_heads, MQA uses G = 1). dhead: width of one head. S: tokens seen so far. B: batch size. bytes: 2 for fp16. Query heads still number n_heads - only the stored keys and values shrink.

So a 64-head model that adopts 8 groups shrinks its KV cache 8× (not 64× like MQA), and in exchange keeps quality that the paper shows is essentially indistinguishable from full MHA. That 8× is enough to matter for long contexts and large batches, which is why production models land here.

4. The conversion trick: uptraining by mean-pooling

Here is the second, quieter contribution, and arguably the more practical one. You already have an expensive MHA checkpoint. You do not want to pre-train a new GQA model from zero. So the paper converts the existing weights: take the H trained key heads, split them into G groups, and average (mean-pool) each group's key projections into one. Do the same for values. Then fine-tune briefly.

Why average, rather than just pick one head or start random? Because mean-pooling keeps information from every head in the group. The paper found this initialises the shared head far better than a fresh random projection, so the short uptrain recovers quality quickly. It is a cheap, boring, extremely effective trick.

5. Implement it: GQA with a mean-pool converter

This module runs attention with any number of KV groups, and includes the exact conversion that turns MHA weights into GQA weights by averaging. Read the expand step: each KV group is repeated to cover every query head in its group, so the attention math is unchanged - only the storage differs.

gqa.py · runnable with torch
import torch, torch.nn as nn, torch.nn.functional as F

class GroupedQueryAttention(nn.Module):
    def __init__(self, d_model=512, n_heads=8, n_kv_heads=2):
        super().__init__()
        assert n_heads % n_kv_heads == 0          # groups must divide heads evenly
        self.h, self.g = n_heads, n_kv_heads
        self.dk = d_model // n_heads
        self.rep = n_heads // n_kv_heads          # query heads per KV group
        self.wq = nn.Linear(d_model, n_heads   * self.dk, bias=False)
        self.wk = nn.Linear(d_model, n_kv_heads * self.dk, bias=False)   # only G heads
        self.wv = nn.Linear(d_model, n_kv_heads * self.dk, bias=False)
        self.wo = nn.Linear(d_model, d_model, bias=False)

    def forward(self, x):
        B, N, _ = x.shape
        q = self.wq(x).view(B, N, self.h, self.dk).transpose(1, 2)     # (B, H, N, dk)
        k = self.wk(x).view(B, N, self.g, self.dk).transpose(1, 2)     # (B, G, N, dk)
        v = self.wv(x).view(B, N, self.g, self.dk).transpose(1, 2)
        # repeat each KV group to cover its query heads -> (B, H, N, dk)
        k = k.repeat_interleave(self.rep, dim=1)
        v = v.repeat_interleave(self.rep, dim=1)
        o = F.scaled_dot_product_attention(q, k, v, is_causal=True)
        return self.wo(o.transpose(1, 2).reshape(B, N, -1))

def convert_mha_to_gqa(wk_mha, n_heads, n_kv_heads, dk):
    """Mean-pool the trained MHA key (or value) weight into G grouped heads."""
    rep = n_heads // n_kv_heads
    W = wk_mha.view(n_heads, dk, -1)                 # split into per-head slabs
    W = W.view(n_kv_heads, rep, dk, -1).mean(dim=1)  # average within each group
    return W.reshape(n_kv_heads * dk, -1)            # (G*dk, d_model)

# cache size scales with the KV-head count, not the query-head count
def kv_cache_mb(layers, kv_heads, d_head, seq, batch=1, fp=2):
    return 2 * layers * kv_heads * d_head * seq * batch * fp / 1e6

mha = kv_cache_mb(32, 32, 128, 4096)   # 32 KV heads
gqa = kv_cache_mb(32,  8, 128, 4096)   # 8 KV groups
mqa = kv_cache_mb(32,  1, 128, 4096)   # 1 KV head
print(f"MHA {mha:6.0f} MB | GQA {gqa:6.0f} MB ({mha/gqa:.0f}x) | MQA {mqa:6.0f} MB ({mha/mqa:.0f}x)")

The convert_mha_to_gqa function is the whole paper in six lines: reshape the trained weight into per-head slabs, average the slabs inside each group, and stack the results. Run it on the key and value projections of any MHA checkpoint and you have GQA weights ready for a short uptrain.

6. The trade-off, filled in

GQA is the middle row the last lesson promised. It is not a compromise so much as a free lunch: the quality curve stays flat as you cut heads, right up until you approach a single group. Pick a modest G (LLaMA-2 70B uses 8 KV heads), pool an existing checkpoint into it, uptrain briefly, and ship.

What does Grouped-Query Attention share, and among whom?
GQA splits the query heads into G groups; each group reads from one shared key/value head.
What do the extreme settings of G recover exactly?
One query head per group is MHA; a single group shared by all query heads is MQA.
How is an MHA checkpoint turned into a GQA model?
Average the trained KV heads within each group, then fine-tune with about 5% of pretrain compute.
In the cache formula, which count does GQA reduce?
Cache size scales with the KV-head count; GQA sets that to G while keeping all query heads.

How this connects

  • Generalises Multi-Query Attention - GQA is MQA with more than one KV group, filling the gap to MHA.
  • Modifies Attention Is All You Need - it changes only the key/value projections of multi-head attention.
  • Sits alongside KV cache compression and PagedAttention as a way to tame decode-time memory.
  • Adopted by LLaMA-2 and LLaMA-3 as the default attention, which is why nearly every recent open model ships with it.
