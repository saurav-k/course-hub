Module 09 · Mixture of Experts · Lesson 36

DeepSeekMoE

2024 Dai, Deng, Zhao, Xu, Gao, Chen, Li, Zeng, Yu, Wu, Xie, and colleagues (DeepSeek-AI). · arXiv:2401.06066

The one-minute version

  • A Mixture of Experts (Lesson 35) gives a model many expert feed-forward networks and routes each token to a few. But experts often overlap: they learn the same common facts, and each is too big to specialise sharply.
  • DeepSeekMoE fixes this with two ideas. First, fine-grained expert segmentation: chop each expert into several smaller ones and route to more of them, so the router can mix and match far more combinations.
  • Second, shared expert isolation: set aside a few always-on shared experts that every token uses. They soak up the common knowledge, freeing the routed experts to specialise.
  • The result is sharper expert specialisation at the same compute. DeepSeekMoE 16B matched LLaMA2 7B while doing about 40% of the FLOPs, and this design is the backbone of DeepSeek-V2 and V3.

1. Why this paper exists

Switch Transformer showed that a Mixture of Experts (MoE) can grow a model's total parameters without growing the compute each token pays. But when the DeepSeek team looked closely at how the experts were used, they found two kinds of waste. The experts were not specialising the way the story promised.

The first problem is knowledge redundancy. Every token, whatever it is about, needs some common knowledge: grammar, basic word meanings, sentence structure. In a plain MoE each routed expert has to learn that shared background on its own, so many experts end up storing near-duplicate copies of the same basics. Parameters wasted on repetition.

The second problem is coarse routing. If a block has only 8 or 16 large experts and each token visits 1 or 2, there are very few ways to combine them. A token whose meaning sits between two specialities has no expert that fits, and no fine control to blend the right pieces. The experts are too few and too chunky to carve knowledge finely.

2. Idea one: fine-grained expert segmentation

Start from a normal MoE layer with N experts, each a full-size feed-forward network, and each token routed to the top K. DeepSeekMoE slices every expert into m smaller pieces. Each small expert has a hidden width 1/m as large, so the total parameters are unchanged. There are now mN experts, and to keep the compute per token identical you route to mK of them instead of K.

Same parameters, same FLOPs per token. What changed is flexibility. The router now has many more experts to choose from and picks more of them, so it can assemble a token's computation from finer parts. A token that is 70% about law and 30% about medicine can grab a few legal experts and a couple of medical ones, rather than being forced into one lump that does both badly.

The combinatorial payoff With N = 16 experts and top-K = 2, there are only C(16, 2) = 120 possible expert teams. Split by m = 4 into 64 experts routed 8 at a time, and there are C(64, 8) ≈ 4.4 billion possible teams. Same parameters, same FLOPs, an astronomically richer set of ways to combine knowledge for each token.

3. Idea two: shared expert isolation

Fine-grained routing lets experts specialise, but it does not stop them from all wasting capacity on the same common basics. That is the job of the second idea. DeepSeekMoE reserves a small number of experts, Ks of them, as shared experts that are always active for every token, with no routing decision at all.

Because the shared experts see every token, they naturally learn the knowledge every token needs: grammar, common words, general structure. The routed experts no longer have to. Freed from carrying the basics, each routed expert can devote its full (small) capacity to one narrow speciality. The output for a token is the sum of its shared experts plus its selected routed experts.

4. One token, end to end

Put both ideas together and follow a single token through a DeepSeekMoE layer. The shared experts always fire. The router scores the many fine-grained routed experts, keeps the top few, and their gated outputs are added on.

The concrete numbers from the paper's 16B model make it real. Each MoE layer has 2 shared experts and 64 routed experts, and every expert is 0.25× the width of a standard feed-forward network (so m = 4). Each token uses both shared experts plus the top 6 of the 64 routed ones, for 8 active experts in total, while the total parameter count stays large and the per-token compute stays small.

5. The math, kept honest

Here is a DeepSeekMoE layer written out. For a token x, the output adds the shared experts and the gated top-K routed experts. Only experts with a non-zero gate contribute, so all the others cost nothing for this token.

y = x + ∑i=1..Ks Sharedi(x) + ∑j=1..mN gj · Routedj(x) x + the residual connection carries the token forward unchanged. ∑ Sharedi(x): the Ks shared experts, always summed in. ∑ gj Routedj(x): over all mN routed experts, but the gate gj is zero for every expert not in this token's top-K, so only mK terms are actually computed. gj is the router's softmax score for expert j when it is selected, and 0 otherwise.

The gate itself is a softmax over the routed experts, kept only for the top-K:

sj = softmaxj( x · Wr ),   gj = sj if j ∈ TopK(s), else 0 x · Wr: the router is one small linear layer producing a score per routed expert. softmax: turns the scores into probabilities. TopK: keep the K highest, discard the rest by setting their gate to 0. In practice the kept gates are renormalised to sum to 1 so the blend is well-scaled.
Why segmentation preserves compute Splitting an expert by m makes each 1/m as expensive. Routing to mK of them instead of K multiplies the count back by m. The two cancel: m × (1/m) = 1. So fine-grained segmentation buys combinatorial flexibility for free in both parameters and FLOPs.

6. Balancing many small experts

With dozens of routed experts, the collapse risk from Lesson 35 is worse, not better: it is even easier for a few experts to hog the traffic. DeepSeekMoE keeps a Switch-style load-balancing loss that pushes routed usage toward uniform, and adds a second, device-level balance term so no single hardware shard is overloaded. The shared experts sit outside all of this, since they are never routed.

7. Implement it: a DeepSeekMoE layer in PyTorch

This layer has both innovations. The experts are fine-grained (their width is divided by m), a couple of shared experts always run, and each token adds its top-K routed experts. It returns the auxiliary load-balancing loss for the training loop. Read it against the diagrams.

deepseek_moe.py · runnable with torch
import torch, torch.nn as nn, torch.nn.functional as F

class Expert(nn.Module):
    """A fine-grained FFN: the SAME shape as a normal FFN but width / m."""
    def __init__(self, d_model, d_ff):
        super().__init__()
        self.net = nn.Sequential(
            nn.Linear(d_model, d_ff), nn.GELU(),
            nn.Linear(d_ff, d_model),
        )
    def forward(self, x):
        return self.net(x)

class DeepSeekMoE(nn.Module):
    def __init__(self, d_model=128, d_ff_full=512, m=4,
                 num_shared=2, num_routed=64, k_routed=6, aux_weight=0.01):
        super().__init__()
        d_ff = d_ff_full // m                     # fine-grained: each expert is 1/m wide
        self.num_routed = num_routed
        self.k_routed   = k_routed
        self.aux_weight = aux_weight
        # shared experts run for EVERY token, no routing
        self.shared = nn.ModuleList([Expert(d_model, d_ff) for _ in range(num_shared)])
        # many small routed experts; a token visits only its top-k
        self.routed = nn.ModuleList([Expert(d_model, d_ff) for _ in range(num_routed)])
        self.router = nn.Linear(d_model, num_routed)   # scores routed experts only

    def forward(self, x):                         # x: (B, N, d_model)
        B, N, d = x.shape
        xf = x.reshape(B * N, d)                  # every token independent
        T  = xf.size(0)

        # ---- shared experts: unconditional, always paid for ----
        out = sum(exp(xf) for exp in self.shared)

        # ---- route to top-k of the many fine-grained experts ----
        probs = self.router(xf).softmax(dim=-1)   # (T, num_routed)
        topv, topi = probs.topk(self.k_routed, dim=-1)     # gate values & indices
        topv = topv / topv.sum(dim=-1, keepdim=True)       # renormalise the k gates

        for slot in range(self.k_routed):         # k selected experts per token
            idx  = topi[:, slot]                  # which routed expert this slot picked
            gate = topv[:, slot].unsqueeze(-1)    # its renormalised weight
            for e in range(self.num_routed):
                sel = (idx == e).nonzero(as_tuple=True)[0]
                if sel.numel() == 0:
                    continue
                out[sel] = out[sel] + gate[sel] * self.routed[e](xf[sel])

        # ---- load-balancing loss over routed experts (Switch-style) ----
        chosen = F.one_hot(topi, self.num_routed).float().sum(dim=1)  # (T, E) 0/1
        f_i = (chosen > 0).float().mean(dim=0)    # fraction of tokens using expert i
        P_i = probs.mean(dim=0)                   # mean router probability for i
        aux = self.aux_weight * self.num_routed * (f_i * P_i).sum()

        return out.reshape(B, N, d), aux

# smoke test: matches the paper's 16B layer shape (2 shared, 64 routed, top-6, m=4)
layer = DeepSeekMoE(d_model=128, d_ff_full=512, m=4,
                    num_shared=2, num_routed=64, k_routed=6)
x = torch.randn(2, 16, 128)                       # batch 2, seq 16, d_model 128
y, aux = layer(x)
print(y.shape, float(aux))                        # torch.Size([2, 16, 128]) <small number>

Two design choices carry the paper. The line d_ff = d_ff_full // m is fine-grained segmentation: every expert is small, so there can be many of them and each specialises. The unconditional out = sum(exp(xf) for exp in self.shared) is shared isolation: those experts run for all tokens and absorb the common knowledge, so the routed experts do not have to. The residual add lives one level up, as with any Transformer sub-layer.

In DeepSeek-V2 and V3 This exact layer, scaled up, is the MoE block inside DeepSeek-V2 (236B total, 21B active) and DeepSeek-V3 (671B total, 37B active). V3 also drops the auxiliary loss in favour of an auxiliary-loss-free bias-adjustment trick for balancing, but the fine-grained plus shared-expert skeleton is unchanged.

The measured payoff is strong. DeepSeekMoE 2B matched the much larger GShard 2.9B, DeepSeekMoE 16B reached LLaMA2 7B quality using roughly 40% of the computation, and DeepSeekMoE 145B approached DeepSeek 67B while spending about 28.5% of the FLOPs. Same sparse-activation bargain as Switch, but with far better use of each parameter.

Retrieval practice

Answer from memory before revealing.

What are the two core ideas DeepSeekMoE adds to a Mixture of Experts?
DeepSeekMoE combines fine-grained expert segmentation (many small experts) with shared expert isolation (a few always-on experts).
What does fine-grained expert segmentation actually change?
Each expert is cut into m smaller experts and the token is routed to m times as many, so compute stays fixed but combinations explode.
Why does DeepSeekMoE reserve a few always-on shared experts?
Shared experts run for every token and absorb common knowledge, freeing each routed expert to specialise instead of relearning basics.
How does DeepSeekMoE routing differ from Switch top-1 routing?
Switch picks one full expert; DeepSeekMoE runs a couple of shared experts plus the top-K of many fine-grained routed experts.

How this connects

  • Previously, Switch Transformer introduced sparse top-1 routing and the load-balancing loss. DeepSeekMoE keeps that machinery and refines what the experts are.
  • The feed-forward network being split into experts is the one from Attention Is All You Need. Attention is untouched; only the per-token FFN becomes an MoE.
  • The sparse-activation bargain - more parameters, flat per-token FLOPs - is the same lever as the scaling laws and Chinchilla, spent on capacity rather than compute.
  • Next up, Muon Optimizer leaves the architecture alone and speeds up how the weights themselves are trained.
Your teacher. The combinatorics are the aha moment. Ask the agent to compute how many expert teams exist before and after segmentation for a few values of m and K, and watch the number explode. Then ask it to run the code with the shared experts removed and reason about what knowledge the routed experts would now be forced to duplicate.
