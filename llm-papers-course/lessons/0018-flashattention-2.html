FlashAttention-2

2023 Tri Dao (Princeton University & Together AI). · arXiv:2307.08691

The one-minute version

  • FlashAttention (Lesson 17) already fixed the memory traffic. But it was still only reaching 25-40% of a GPU's peak math throughput, while a plain matrix multiply hits 80-90%.
  • FlashAttention-2 keeps the exact same tiling and online softmax, and squeezes out the remaining inefficiency in three ways.
  • Fewer non-matmul FLOPs: GPU tensor cores are built for matrix multiplies, so the paper minimises the slow "other" operations (rescaling divides) around them.
  • Parallelise over sequence length: v1 split work across batch and heads only; v2 also splits across the sequence dimension, keeping the GPU busy even with a small batch or long context.
  • Better work partitioning between warps: reorganising which threads own which sub-block cuts shared-memory traffic. Net effect: about 2× faster than v1, reaching 50-73% of A100 peak and up to 225 TFLOPs/s.

1. Why this paper exists

FlashAttention solved the right problem - memory movement - and the field adopted it fast. But Tri Dao noticed the kernel still left performance on the table. A well-tuned matrix multiply (GEMM) on an A100 runs near the hardware's theoretical peak. FlashAttention-1, doing morally the same amount of math, was reaching only a quarter to two-fifths of that peak. The gap was not the algorithm; it was how the work was scheduled onto the GPU's parallel units.

2. Background: how a GPU runs a kernel

To see the three improvements you need three words. A GPU runs many thread blocks, each pinned to one physical unit (an SM, or streaming multiprocessor). Inside a block, threads march in lockstep groups of 32 called warps. And the fast scratchpad a block shares is shared memory (SRAM). Performance depends on keeping every SM busy (enough parallel work) and keeping warps from stepping on each other in shared memory.

3. Improvement one: fewer non-matmul FLOPs

Tensor cores multiply matrices absurdly fast, but they only accelerate matrix multiply. Everything else - the exponentials, the divides that rescale the running softmax - runs on the ordinary, much slower path. On an A100 a non-matmul FLOP can be roughly an order of magnitude more expensive than a matmul FLOP. So even though softmax is a tiny share of the FLOP count, it can eat a large share of the time.

FlashAttention-2 rewrites the online-softmax bookkeeping so the per-block division is deferred. Instead of dividing the accumulator by the running sum on every block, it accumulates un-normalised and divides once at the very end. Same answer, far fewer of the expensive non-matmul operations in the hot loop.

4. Improvement two: parallelise over the sequence dimension

FlashAttention-1 handed one attention head of one batch element to each thread block. That gives batch × heads parallel jobs. Fine when the batch is large. But inference and long-context training often have a small batch and a very long sequence - so there were fewer jobs than the GPU has SMs, and some SMs sat idle.

FlashAttention-2 adds a third axis of parallelism: it splits each head's work across blocks of the query sequence too. Now the number of parallel jobs is batch × heads × query-blocks, which stays large even when the batch is one. Different query blocks are independent - each computes its own output rows - so they map cleanly onto separate SMs with no coordination.

5. Improvement three: better work partitioning between warps

Within a thread block, FlashAttention-1 split the key/value tile across warps (a "split-K" scheme). Each warp computed a partial result that then had to be combined through shared memory, so warps kept writing and reading intermediate sums - traffic and synchronisation. FlashAttention-2 flips it: it splits the query tile across warps instead. Now each warp owns a full slice of the output and needs no cross-warp reduction, cutting shared-memory round trips.

6. Putting the numbers in context

How fast is "fast"? A GPU has a peak FLOPs rating - the most floating-point math it could ever do per second. Real kernels reach a fraction of that. The metric is utilisation: achieved FLOPs / peak FLOPs. Matrix multiply hits ~80-90%. FlashAttention-1 hit 25-40%. FlashAttention-2 hits 50-73%, and up to 225 TFLOPs/s per A100 at 72% model-FLOPs-utilisation when training GPT-style models end to end.

utilisation = achieved_FLOPs_per_second / peak_FLOPs_per_second achieved: how much math the kernel actually did per second, measured. peak: the chip's advertised maximum. The ratio tells you how much of the silicon you are really using. FlashAttention-2 roughly doubled this ratio over v1 without changing the answer - pure engineering, no accuracy trade.

7. Implement it: a benchmark harness

You cannot feel a kernel speedup by reading about it, so measure one. This harness times naive attention against PyTorch's fused FlashAttention path (scaled_dot_product_attention, which uses a FlashAttention-2 kernel on supported hardware) and reports both time and peak memory. On a GPU the fused path is dramatically faster and uses far less memory as the sequence grows; on CPU you still see the memory gap.

bench_attention.py · runnable with torch (best on a CUDA GPU)
import torch, torch.nn.functional as F, time

def naive_attention(q, k, v):
    # materialises the full N x N score matrix - the thing FlashAttention avoids
    d = q.shape[-1]
    scores = (q @ k.transpose(-2, -1)) / d ** 0.5   # (B, H, N, N)
    weights = scores.softmax(dim=-1)
    return weights @ v

def bench(fn, q, k, v, iters=20):
    dev = q.device
    if dev.type == "cuda":
        torch.cuda.synchronize(); torch.cuda.reset_peak_memory_stats()
    t0 = time.perf_counter()
    for _ in range(iters):
        out = fn(q, k, v)
    if dev.type == "cuda":
        torch.cuda.synchronize()
    dt = (time.perf_counter() - t0) / iters * 1e3       # ms per call
    mem = (torch.cuda.max_memory_allocated() / 1e6      # MB
           if dev.type == "cuda" else float("nan"))
    return out, dt, mem

dev = "cuda" if torch.cuda.is_available() else "cpu"
B, H, N, D = 4, 8, 2048, 64                              # long sequence
q, k, v = (torch.randn(B, H, N, D, device=dev, dtype=torch.float16
                       if dev == "cuda" else torch.float32) for _ in range(3))

_, t_naive, m_naive = bench(naive_attention, q, k, v)
# fused path -> FlashAttention-2 kernel on supported GPUs:
_, t_flash, m_flash = bench(lambda a,b,c: F.scaled_dot_product_attention(a,b,c),
                            q, k, v)

print(f"naive : {t_naive:6.2f} ms   peak {m_naive:8.1f} MB")
print(f"flash : {t_flash:6.2f} ms   peak {m_flash:8.1f} MB")
print(f"speedup x{t_naive / t_flash:.1f}")

The naive version's peak memory climbs with N² because of the score matrix; the fused version's does not. That memory curve is the whole point of the FlashAttention line of work, and FlashAttention-2 is the version that also makes the compute reach a large fraction of the hardware's ceiling.

The through-line FlashAttention made attention memory-efficient. FlashAttention-2 made that same memory-efficient kernel compute-efficient too, by scheduling its work to match how GPUs are actually built: keep tensor cores fed, keep every SM busy, keep warps out of each other's way.

Retrieval practice

Answer from memory before revealing.

What did FlashAttention-2 change relative to version one?
The algorithm and result are unchanged. v2 improves how the identical computation maps onto GPU cores.
Why minimise non-matmul operations like the rescaling divide?
Tensor cores only speed up matrix multiplies; other ops use the slow path, so they dominate time even when few.
What extra axis of parallelism did version two add?
v1 parallelised over batch and heads; v2 also splits over query-sequence blocks, filling idle SMs on long sequences.
Roughly what A100 peak utilisation did FlashAttention-2 reach?
v2 reaches 50-73% of A100 peak (up to 225 TFLOPs/s), roughly 2× the 25-40% of v1.

How this connects

  • Builds directly on FlashAttention - same tiling and online softmax, better GPU scheduling.
  • Both target the attention math flagged as O(N²) in Attention Is All You Need.
  • Complementary to GQA: fewer K/V heads to stream means each FlashAttention-2 job does less work.
