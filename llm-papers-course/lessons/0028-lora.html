Module 07 · Parameter-Efficient Fine-Tuning · Lesson 28

LoRA: Low-Rank Adaptation of Large Language Models

2021 Hu, Shen, Wallis, Allen-Zhu, Li, Wang, Wang, Chen (Microsoft). · arXiv:2106.09685

The one-minute version

  • Fully fine-tuning a big model means updating every weight and storing a whole new copy per task. That is expensive and does not scale to many tasks.
  • LoRA freezes the pretrained weight matrix W and learns a small low-rank update instead: ΔW = B A, where B and A are skinny matrices with an inner rank r much smaller than the layer size.
  • You train roughly 0.01 to 1% of the parameters. The paper reports up to a 10,000× cut in trainable parameters and a 3× cut in GPU memory versus full fine-tuning.
  • Because the update is just a matrix, you can merge B A back into W after training, so there is no extra inference latency. Swap a different tiny adapter per task on the same frozen base.

1. Why this paper exists

By 2021 the winning recipe was: pretrain one huge model, then fine-tune it on your task. But full fine-tuning has a brutal cost. GPT-3 has 175 billion parameters. Fine-tuning it updates all 175 billion, needs optimizer state for all of them, and produces a fresh 175-billion-parameter checkpoint for every task you care about. Ten tasks means ten full copies. That is a storage and serving nightmare.

The insight behind LoRA: when you adapt a big model to a narrow task, the change in the weights is far simpler than the weights themselves. The authors argue this update has a low "intrinsic rank" - it can be captured by a small number of directions. So do not learn a full dense update. Learn a low-rank one.

2. The one idea: a low-rank detour around a frozen weight

Take any linear layer with weight matrix W of shape d × k. Normally fine-tuning nudges W to W + ΔW, where ΔW is also d × k and dense. LoRA replaces that dense update with a product of two thin matrices: ΔW = B A, where B is d × r and A is r × k, with the rank r tiny (often 4, 8, or 16).

Why is B A so much smaller? A dense d × k update has d × k numbers. The two thin matrices have only r × (d + k) numbers. For a 4096 × 4096 layer with r = 8, that is 65,536 trainable numbers instead of 16.7 million - about 256× fewer, in one layer.

3. The forward pass, exactly

Plain English first: send the input through the frozen weight, and separately through the small B A detour, then add them. The detour is scaled by alpha / r so you can tune its strength without re-tuning the learning rate.

h = W x + (alpha / r) · B A x W x: the original frozen layer output; this never changes during training. A x: project the input down into an r-dimensional space (A is r×k). B (A x): project that back up to the output size (B is d×r). alpha / r: a fixed scale factor; alpha is a chosen constant, dividing by r keeps the update size stable as you change the rank. At the start B is initialised to zero, so B A = 0 and the model behaves exactly like the pretrained one - training only adds on top.
Why B starts at zero A is initialised with small random numbers and B is initialised to all zeros. So on step 0 the update B A is exactly zero and the model is identical to the pretrained one. Training then grows the adapter from nothing, which makes fine-tuning stable and never worse than the starting point.

4. Merge for free: no inference tax

Older "adapter" methods inserted extra little layers into the network, which added latency at every forward pass. LoRA avoids this because its update is a plain matrix that lives in the same space as W. After training you can compute W' = W + (alpha/r) B A once and store W'. Now inference uses a single matrix, exactly like the original model. Zero added cost.

5. Where to put it: the attention projections

LoRA can wrap any linear layer, but the paper found the best bang-for-buck is on the attention projection matrices - the query and value projections in particular. You do not need to adapt the feed-forward layers to get most of the benefit, which keeps the adapter even smaller.

6. Implement it: a LoRALinear layer in PyTorch

Here is a drop-in wrapper around nn.Linear. It freezes the base weight, adds the low-rank A and B, does the scaled forward pass, and offers a merge(). Run it and watch the trainable-parameter count collapse.

lora_linear.py · runnable with torch
import torch, torch.nn as nn

class LoRALinear(nn.Module):
    def __init__(self, in_features, out_features, r=8, alpha=16):
        super().__init__()
        # the pretrained layer we adapt - its weight is FROZEN
        self.base = nn.Linear(in_features, out_features, bias=False)
        self.base.weight.requires_grad = False

        self.r, self.alpha = r, alpha
        self.scale = alpha / r                       # the (alpha / r) factor
        # A: down-project k -> r  (small random init)
        self.A = nn.Parameter(torch.randn(r, in_features) * 0.01)
        # B: up-project r -> d    (init to ZERO so B A = 0 at start)
        self.B = nn.Parameter(torch.zeros(out_features, r))
        self.merged = False

    def forward(self, x):                            # x: (..., in_features)
        out = self.base(x)                           # frozen path: W x
        if not self.merged:                          # detour: (alpha/r) B A x
            out = out + self.scale * (x @ self.A.t() @ self.B.t())
        return out

    def merge(self):
        # fold the adapter into the base weight: W' = W + (alpha/r) B A
        delta = self.scale * (self.B @ self.A)       # shape (out, in)
        self.base.weight.data += delta
        self.merged = True                           # now a single matrix

# param-count demo on one 4096 x 4096 layer
layer = LoRALinear(4096, 4096, r=8)
trainable = sum(p.numel() for p in layer.parameters() if p.requires_grad)
frozen    = sum(p.numel() for p in layer.parameters() if not p.requires_grad)
print(f"trainable: {trainable:,}")   # 65,536  (A + B)
print(f"frozen:    {frozen:,}")      # 16,777,216  (the base W)
print(f"trainable fraction: {trainable / (trainable + frozen):.4%}")  # ~0.39%

# check merge preserves the output
x = torch.randn(2, 4096)
before = layer(x)
layer.merge()
after = layer(x)
print("max diff after merge:", (before - after).abs().max().item())  # ~0

Two things to notice. First, the trainable fraction is well under one percent for a single layer, and it only shrinks as the model grows. Second, merge() leaves the output identical - proof that the deployed model pays no latency tax. During training you keep A and B separate so gradients only touch them; at serving time you fold them in.

In practice You rarely hand-write this. Libraries like Hugging Face peft attach LoRA to a named set of modules (for example q_proj and v_proj) with one config. But the module above is what they do underneath, so you can see there is no magic - just a frozen matrix plus a rank-r detour.

7. LoRA versus the alternatives

PropertyFull fine-tuningAdapter layersLoRA
Trainable parameters100%~1-5%~0.01-1%
Extra inference latencyNoneYes (added layers)None (can merge)
Storage per new taskFull model copySmallTiny (a few MB)
Swap tasks at serve timeReload whole modelToggle adaptersHot-swap adapters
Quality vs full fine-tuneBaselineCloseOn par or better

The headline result: on RoBERTa, DeBERTa, GPT-2, and GPT-3, LoRA matched or beat full fine-tuning quality while training a fraction of a percent of the weights. That combination - same quality, tiny footprint, no latency - is why LoRA became the default way to fine-tune large models.

Retrieval practice

Answer from memory before revealing.

During LoRA training, which parameters actually receive gradient updates?
W is frozen. The training updates only the thin A and B matrices, which is why the trainable count is tiny.
Why can LoRA add zero extra latency at inference time?
Because B A lives in the same space as W, you fold it in once: W' = W + (alpha/r) B A. Then serving uses a single matrix.
What is the effect of choosing a smaller rank r for the adapter?
A smaller r means fewer parameters (cheaper) but a narrower bottleneck, so the update captures fewer distinct directions.
Why is the B matrix initialised to all zeros at the start?
With B = 0 the product B A is zero, so at step 0 the model equals the pretrained one and training only adds on top.
