KV Cache Compression & Optimization

2023-2024 A family of methods (survey lesson): H2O, StreamingLLM, KIVI/KVQuant, DeepSeek-V2 MLA. · 2306.14048 · 2309.17453 · 2405.04434

The one-minute version

  • This lesson is a family survey, not one paper. At long context lengths the KV cache dominates GPU memory - it grows with every token, layer, and head, and it is the wall you hit first.
  • There are four families of ways to shrink it. Eviction: throw away KV entries you will not need. Quantization: store each entry in fewer bits. Head sharing: keep fewer KV heads. Low-rank: compress KV into a small latent vector.
  • Eviction methods like H2O (keep the "heavy hitter" tokens) and StreamingLLM (keep the first "attention sink" tokens plus a recent window) can drop most of the cache with little quality loss.
  • These stack. A real serving stack often combines GQA head sharing, int8 quantization, and a windowed eviction policy at once. This lesson maps the landscape and codes two of the four families end to end.

1. Why this family exists

Every previous efficiency lesson has circled the same enemy: the KV cache. During generation the model stores a key and value vector for every past token, in every layer, in every head, so it never recomputes them. That cache is fixed-cost per token, and at long context it eclipses the model weights themselves. A 7B model in fp16 is about 14 GB of weights, but its KV cache at 128k tokens can be tens of gigabytes on its own. Long context is a memory problem before it is a compute problem.

2. The four families

Broadly, you can make the KV cache smaller in four independent ways. They are orthogonal, which means a production system can apply several at once.

cache_bytes = 2 · L · G · dhead · S · bytes 2: key and value. L: layers. G: KV heads (head sharing shrinks this - lessons 15-16). dhead: per-head width (low-rank/MLA shrinks the stored version of this). S: tokens kept (eviction shrinks this). bytes: precision, 2 for fp16 (quantization shrinks this to 1 for int8 or 0.5 for int4). Each family targets a different letter.

3. Family 1 - eviction: keep the tokens that matter

The simplest question: do you actually need every past token's key and value? Empirically, no. Attention is sparse - most tokens receive almost no weight most of the time. Two influential papers exploit this differently.

H2O (Heavy-Hitter Oracle) observed that a small set of tokens - the "heavy hitters" - soak up most of the attention mass across the whole sequence. Keep those, plus a window of recent tokens, and evict the rest. StreamingLLM found something stranger: the very first tokens accumulate huge attention scores even when they carry no semantic meaning. They act as an attention sink, a place for the softmax to dump probability. Keep a few sink tokens at the front plus a sliding recent window, and a model trained on short contexts streams to millions of tokens without recomputation.

4. Family 2 - quantization: fewer bits per entry

A different lever: keep every token, but store its key and value in lower precision. Methods like KIVI and KVQuant push the KV cache from fp16 (16 bits) down to int8 or even int4, often quantizing keys and values with different strategies because they have different statistics. Halve the bits, halve the cache, with careful scaling to keep quality.

5. Families 3 and 4 - share heads, or compress to a latent

Head sharing is the pair of lessons you just finished: MQA keeps one KV head, GQA keeps a few. That cuts the G term directly and is now standard. Low-rank compression goes further on the d_head term: DeepSeek-V2's Multi-head Latent Attention (MLA) projects the keys and values down into a single small latent vector per token, stores only that, and reconstructs the full keys and values on the fly. The paper reports the KV cache shrinks by 93.3% versus the previous model, while quality holds.

6. Implement two families: eviction cache + int8 quantizer

This code builds a fixed-size streaming cache (attention sinks plus a recent window) and a simple symmetric int8 quantizer for the entries you keep, then measures the memory saved against a naive full-precision cache. Read it as the eviction and quantization families combined.

kv_optim.py · runnable with torch
import torch

class StreamingKVCache:
    """Attention-sink + sliding-window eviction (StreamingLLM style)."""
    def __init__(self, n_sink=4, window=1024):
        self.n_sink, self.window = n_sink, window
        self.k, self.v = [], []                      # lists of per-token tensors

    def append(self, k_t, v_t):
        self.k.append(k_t); self.v.append(v_t)
        # keep the first n_sink tokens forever; keep only the last `window` others
        if len(self.k) > self.n_sink + self.window:
            drop = len(self.k) - (self.n_sink + self.window)
            self.k = self.k[:self.n_sink] + self.k[self.n_sink + drop:]
            self.v = self.v[:self.n_sink] + self.v[self.n_sink + drop:]

    def size(self):
        return len(self.k)

def quantize_int8(x):
    """Symmetric per-tensor int8 quantization: fp16 -> int8 + one scale."""
    scale = x.abs().max() / 127.0
    q = torch.clamp((x / scale).round(), -127, 127).to(torch.int8)
    return q, scale

def dequantize_int8(q, scale):
    return q.to(torch.float16) * scale

# --- demo: stream 100k tokens through the fixed-size cache ---
d_head = 128
cache = StreamingKVCache(n_sink=4, window=1024)
for t in range(100_000):
    cache.append(torch.randn(d_head), torch.randn(d_head))

kept = cache.size()                                  # bounded, not 100k
full_fp16 = 100_000 * d_head * 2 * 2                 # tokens*d*2(K,V)*2 bytes
evicted_fp16 = kept * d_head * 2 * 2
evicted_int8 = kept * d_head * 2 * 1                 # int8 = 1 byte
print(f"tokens streamed : 100000, tokens kept: {kept}")
print(f"full fp16 cache : {full_fp16/1e6:8.1f} MB")
print(f"+ eviction      : {evicted_fp16/1e6:8.1f} MB "
      f"({full_fp16/evicted_fp16:.0f}x smaller)")
print(f"+ eviction+int8 : {evicted_int8/1e6:8.1f} MB "
      f"({full_fp16/evicted_int8:.0f}x smaller)")

The measurement makes the stacking visible: eviction caps the token count at a constant no matter how long you stream, and int8 halves whatever is left. Two orthogonal families multiply into a large combined saving, and you could still add GQA head sharing on top.

No single family is "the answer". Which you reach for depends on the workload - streaming chat leans on eviction, memory-starved serving leans on quantization, new model designs bake in head sharing or low-rank from the start. Why does the KV cache dominate memory at long context?
Weights are a fixed cost; the cache adds a key and value per token, so it overtakes them.
What is an "attention sink" in StreamingLLM?
The first tokens accumulate large attention weight; keeping them stabilises windowed streaming.
Which lever does KV quantization pull to shrink the cache?
Quantization keeps every entry but in lower precision - fp16 to int8 or int4 - halving or quartering bytes.
What does Multi-head Latent Attention actually cache?
MLA stores a low-rank latent per token and reconstructs full K/V on the fly, cutting cache over 90%.
