The design system, rendered by itself

Every colour, size, distance, shape and duration this hub owns has a name. This page is the list of those names, and each one is shown doing its own job rather than described. Change the appearance controls in the bar above and watch the page change with them: that is the whole framework, working, on the page that documents it.

The one-minute version

  • There is one stylesheet and one script, assets/hub.css and assets/hub.js, and every page on the hub links both. A page carries no design of its own.
  • A rule reads a token, never a literal. That is what lets a second design be a list of values instead of a second copy of the sheet.
  • The vocabulary of classes is closed. If a shape you need is not on this page, it does not exist yet, and adding it is a pull request rather than a class you invent.
  • The axes compose and never multiply: mode, palette, design, course and the reading face. Colour belongs to the first two, type and rhythm to the third, one hue to the fourth, and three measured constants to the fifth.
  • Anything a reader can set lives in three layers, and the reader's layer is an input to a token rather than a competitor to it.

The rules, before the lists

A rule reads a token, never a literal

A hard-coded 1.05rem in a rule is a value a second design cannot reach. The hub already paid once to remove a fork like that, when six byte-identical course.css files became one, and the token layer is what stops the next one. If nothing in the list below fits what you are adding, add a token beside the ones it belongs with, give it a call-site comment, and say so in the pull request.

Space has two layers and a rule only ever reads the second

Layer one is --sp-1 to --sp-8, a ramp of ratio about 1.41 anchored on the modal spacing value in the sheet. Layer two is the roles: the reading column's rhythm, the component insets, the gap ladder and the offset ladder. Never write padding: var(--sp-3). A ramp step in a rule is a distance with no name, and it puts a reading-rhythm distance and a chrome distance on one token, which is exactly what the split exists to prevent.

Anything a reader can set has three layers

hub.css declares an --x-default, hub.js writes only an --x-user property inline on <html>, and one resolved token --x: var(--x-user, var(--x-default)) is what every rule reads. Only that resolution line may name an --x-user property.

This rule is a measured trap rather than a preference. Until August 2026 the two reading preferences were applied as inline styles on <html>, and an inline style beats every rule that is not !important. A reader who had widened the column was pinned there for good, and any later rule that set the measure lost silently. As an input to the token instead, the reader's choice composes with the stylesheet, and "back to defaults" is the removal of one property with no second value to unwind.

A design-axis token is declared in a design block and nowhere else

A design block is :root[data-design="house"], which is specificity (0,2,0), against a bare :root at (0,1,0). So a second declaration of a design-axis token - in a media query, most easily - is out-argued in every viewport and goes silently dead. Anything that needs a viewport arm gets that arm on the same two selectors. scripts/validate_site.py checks this rather than trusting it.

The audit, run on this page. This page names its tokens by hand, so it can fall behind a stylesheet that gains one. With the script running, this line counts the custom properties assets/hub.css declares and names any this page misses.

Colour

Colour is the palette and the mode axes and nothing else. A palette states fourteen raw colours twice, once as its light values and once as its dark ones; the mode layer maps one of those two sets onto the semantic names, and it is written once for the whole system. Adding a palette is therefore one block of raw values and no other change. A design carries no colour, deliberately: a design that did would multiply the contrast matrix by the number of designs.

The palette's raw layer

These are the values of the palette the reader has chosen, both halves of it, whichever mode they are in. Nothing downstream reads them except one sanctioned case: .term is drawn from the dark set in both modes, because a terminal reads as a terminal only while it is dark.

Type

The faces, by role

Three families are loaded and four roles name them. A rule names a role, so the reading face can change without touching the fifty-three rules that set it. --font-ui is the hub's own fourth role: the chrome is set in the sans face for reasons that have nothing to do with the heading voice, and without a name of its own a design that gave headings a display serif would drag the whole rail with it.

The three families above the roles are the registry of what is loaded. Do not name those in a rule.

They are self-hosted as woff2 beside the stylesheet and served from nowhere else, which is what lets a page opened straight off disk look like the published one and why no reader is ever visible to a font service. Eight files, 459.3K on disk, and no page fetches more than four of them: the -ext cuts are gated by unicode-range, so a page with no italic in its prose fetches 152.8K and a page with an <em> in it fetches 241.0K. Every face declares font-display: swap, which is the only value this hub may use, and the validator holds the payload against two recorded ceilings so that a fourth face is added against a known figure. The per-file table and the refresh procedure are in assets/fonts/README.md.

A face is not a name. It is a name plus three measured constants - the average prose advance, the x-height per em, and the apparent size against the reference face - and the four properties are declared together, once per face, in the face registry below. A design selects a reading face by restating a whole entry, never by setting --font-body on its own, and scripts/type_invariants.py fails the build on an entry that names a family without all three constants. That is also why the reading face is an axis attribute rather than an --x-user property: a single value composes through the cascade, and three numbers that have to travel together do not.

The derived axes

Four of the reading axes are not independent, and every coupling is measured. A framework that offered the four as free settings would let a reader move one control and silently move a second, and then build a page that no single setting explains. So all four are derived, in one block, in pure CSS - none of them needs the script, which is what keeps the promise that a page renders correctly with hub.js removed.

  • The measure names real characters and its width is computed, because ch is the advance of the digit zero rather than of a character, and the two part company by face.
  • The body size names apparent size on the reference scale, because the same nominal size is noticeably larger to the eye in a sans face than in the serif.
  • The code size follows the reading face's x-height, so code and prose keep the same optical size whichever face the prose is set in.
  • The leading gets a nudge above a stated character count, which any explicit reader choice suppresses.

The type scale

Hand-tuned and left that way. The measured ratios are 1.347 then 1.594 from body to h2 to h1, which is not one geometric scale; it is a scale anchored on a large h1. Below the named roles sit the component sizes, each a separate hand-tuned decision that happens to land where it does. Several share a value today and are still separate tokens, because a design that moves one has no business moving the rest.

A heading's tag and its size are separate decisions. h1 to h4 set the outline a screen reader navigates by. .h-sub is the h3 face and .h-label is the small uppercase h4 face. Fix a broken heading order by retagging the heading and adding the matching class, never by leaving the tag wrong because the right one looks wrong.

Three sizes are written in em on purpose, so each resolves against the text it sits in rather than against the root. --fs-mono is the one that matters: both pre and inline code read it, so both track whatever prose surrounds them. pre used to carry a rem value against inline code's em, the two rendered seventeen per cent apart, and only the em half survived a change to the body size at all. Do not re-express either in rem.

Open it and move any control: this page repaints, the value column above follows, and every specimen changes with it. That is the point of building the reference on the hub rather than beside it.

Six controls, plus motion in the accessibility defaults and one reset. Eleven reading axes were assessed and these are the ones that earned a control: readers genuinely differ on it, the reader can perceive the difference and judge it, and a wrong setting is recoverable. The display face, the mono face and the eyebrow treatment fail all three the same way - a reader sets one once and never returns to it, while a course has every reason to differ on it - so they are author tokens on the course contract instead. The accent is not a control either, because expanding it into a colour picker would put a contrast criterion in the reader's hands.

Five of them are axis attributes on <html> and three are --x-user properties written into its inline style. Nothing else may be written there, and scripts/validate_site.py checks both halves. The two reading axes are attributes rather than properties because what they carry does not compose into a single value: the reading face selects a family together with the three measured constants that have to travel with it, and motion selects a block of rules.

A stored step is validated against its own table exactly as a palette key is, so a value from a step that was later withdrawn falls back to the default rather than leaving one reader with a page nobody else can see. Withdrawing a design is deleting its entry from the registry in hub.js: no deploy, and no page edit. Every registry above is data and no code branches on a known key, so registering a face, a spacing step or a density is an entry and no framework code.

No control writes an output. The measure names characters and the width is derived from the face; the body size names apparent size and the rendered px is derived from the face; the code size follows the face on its own. --measure, --fs-body, --fs-mono and the per-face constants are computed from the controls above them, and a control that wrote one would put back the coupling the derived layer removed - a reader who set 72 and then changed the face would have moved their line length without touching the measure control.

Density is the one control with a hard limit. It scales the twenty prose-rhythm roles and reaches nothing else, and that is structural rather than promised: hub.js can write only --*-user names that hub.css resolves, and those are the twenty-four reader-reachable tokens. There is no headroom in the chrome for a compact mode - one control already fails SC 2.5.8, seven more pass on the spacing exception alone, and the smallest compliant control has two pixels of margin.

The panel moves, and its position is a preference like any other. The title bar is the pointer surface and the grip inside it takes the arrow keys, because a panel only a mouse can move is a panel some readers cannot move. What is stored is an intention and what is rendered is that intention clamped into whatever viewport is in front of the reader, against a band measured off the sticky topbar and the pre-production strip rather than assumed. It is a non-modal dialog - no aria-modal, no focus trap, and an outside click does not close it - because a reader parks it in order to keep reading with it open.

The ground a reader can choose is a registered discrete set, and that is an accessibility mechanism rather than a convenience. For a ground of a given lightness the best contrast reachable with any ink at all is bounded, and with this hub's real inks no ground between L* 43.8 and L* 54.1 reaches AA with either of them. A slider could land inside that band; a list of six checked palettes cannot. The framework prevents the band rather than warning about it, and there is no override path.

What is forbidden, and why

  • A continuous ground control. With this hub's real inks no ground between L* 43.8 and L* 54.1 reaches AA with either ink, so the ground is chosen from a registered discrete set and there is no input event that can land inside the band.
  • Choosing the ink. A reader choosing a ground is choosing a ground; the framework picks the ink, and for every registered palette that pairing is measured.
  • An all-caps option for body text or for any heading that runs to a line. Capitals are 9.53% to 19.01% slower to read. The eyebrow is the one place the trade is worth making.
  • Tightening anything in the topbar or the rail. Seven pointer targets there pass SC 2.5.8 only on the spacing exception, and the smallest compliant control has two pixels of headroom. .spine .home carries an explicit minimum height because it was the hub's one outright failure.
  • A route around prefers-reduced-motion. Every transition is killed outright under it, near the head of the sheet.

Three floors in the sheet that look like rules you could delete

  • .chart text pins letter-spacing and word-spacing to normal !important, so a reader's own text-spacing stylesheet cannot push a fixed-coordinate label past the clip at the edge of the viewBox.
  • .mermaid svg foreignObject carries overflow: visible on the screen sheet and not only in print, because Mermaid writes each label's measured width onto the box and any later re-space clips what no longer fits.
  • .spine .home carries a minimum height of 24px, which is the one target that was failing.
