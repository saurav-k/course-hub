Two products remove the instance class, and only one removes the cluster

working 7 min Capability keys relational-serverless and globally-distributed-sql. · Aurora Serverless v2

The one-minute version

  • Aurora Serverless v2 is a capacity configuration, not a product. The cluster, its writer and its readers are all still yours to design; what changes is that each instance is sized in Aurora Capacity Units instead of an instance class.
  • Capacity moves in half-ACU increments between a minimum and maximum you set, and a minimum of zero lets an idle instance pause entirely.
  • A paused instance resumes in roughly fifteen seconds, and attaching RDS Proxy stops it pausing at all.
  • Aurora DSQL removes the instance class outright. There is nothing to size, writes are active-active across Regions and strongly consistent, and the published availability is 99.99 percent in one Region and 99.999 percent across Regions.
  • What it costs: DSQL uses optimistic concurrency, so a write conflict is not a lock you wait on - it is an error your application receives at commit and has to retry.
"Serverless" names three unrelated things on AWS and they are not interchangeable: Fargate is a capacity mode for containers, Lambda is a function runtime, and Aurora Serverless v2 is a capacity configuration inside a cluster you still design. Aurora Serverless v2 is not a per-request database, and reading it as one is the single most common misunderstanding of this page.

1. The mechanism: a dial with a floor of zero

2. The other answer: no cluster to size at all

Aurora DSQL is PostgreSQL-compatible distributed SQL with an active-active design. Compute, I/O and storage scale with the workload and there is no instance class to choose, and writes are strongly consistent across Regions rather than replicated to a read-only secondary (What is Aurora DSQL). That is the capability the previous page ended without: two Regions that both accept writes.

The reframing These two products answer different questions. Aurora Serverless v2 answers "how do I stop paying for capacity I am not using" and leaves the cluster's shape and its single writer exactly where they were. Aurora DSQL answers "how do I write in more than one Region" and charges for it in the concurrency model your application sees. Neither is the serverless version of the other.

Check yourself

Retrieval practice

Answer from memory before revealing.

A development Aurora cluster is set to a minimum of zero ACUs but never pauses overnight. What is the likeliest reason?
RDS Proxy keeps connections established, so the cluster is never idle and never pauses. The maximum setting bounds how high capacity climbs and says nothing about the floor, pausing is a capacity setting rather than a Multi-AZ one, and the number of readers does not decide whether an idle instance pauses.
Which requirement points at Aurora DSQL rather than at Aurora Serverless v2?
Active-active writes across Regions are what DSQL adds. Pausing when idle and following the workload are both Aurora Serverless v2 behaviours, PostgreSQL compatibility is common to both rather than a reason to pick either.
What does optimistic concurrency change about application code on Aurora DSQL?
Conflicts surface at commit rather than as a wait on a row lock, so retry handling is required. Routing writes to one Region would give up the active-active property that the model exists to provide, and neither read transactions nor per-Region schema work follows from the concurrency model.

Practice about 15 minutes, with paper

Practice 1working

A platform team runs sixty ephemeral test databases. Each one is used for about ninety minutes on a working day and is untouched the rest of the time. They currently run as small provisioned Aurora instances and the bill is flat.

Separately, the same team is asked to build a session store for a product with users on two continents, where a session written on either continent must be visible immediately on the other.

Pick a configuration or product for each, and for each one name the specific operational cost your choice introduces that the current design does not have.

Hint

One of these is a question about time - how much of the day is capacity actually wanted. The other is a question about geography - where a write must be accepted. Do not let the word serverless carry both.

Show the worked solution
  1. Size the first problem. Ninety minutes out of twenty-four hours is a little over six percent of the day. The remaining ninety-four percent is capacity bought and not used, which is what makes the flat bill flat.
  2. Choose for the first. Aurora Serverless v2 with a minimum of zero ACUs, so each idle test database pauses. The cluster shape does not change; only the sizing does.
  3. Name its cost. The first connection after a pause waits roughly fifteen seconds while the instance resumes. A test suite that opens a connection and times out in five seconds will now fail intermittently, and that is a test-harness change, not a database setting. Note too that pausing needs a recent engine version, so the oldest clusters may have to be upgraded first.
  4. Choose for the second. Aurora DSQL. The requirement is that a write on either continent is immediately visible on the other, which is a strongly consistent multi-Region write - not something a read-only secondary Region provides.
  5. Name its cost. Optimistic concurrency. Two sessions touching the same row concurrently will see one commit rejected, so the session store needs retry logic around every write path before it goes live.

Sanity check. Each answer should name one cost that is code or process rather than money. If both costs you wrote down were about price, look again: the interesting cost of pause-to-zero is the resume, and the interesting cost of active-active is the retry.
