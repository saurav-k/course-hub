Module 04 · Storage · Lesson 0401

S3 stopped being one kind of bucket, and each new type absorbs a job from above it

working 6 min Capability keys object-storage-highperf, object-storage-tables and vector-store. · S3 Express One Zone

The one-minute version

  • "A bucket" now names several different objects. The general-purpose bucket from the last lesson is one of them.
  • A directory bucket holds the S3 Express One Zone class: single zone, consistent single-digit millisecond latency, and up to ten times faster than Standard.
  • A table bucket stores Apache Iceberg tables natively and maintains them, so compaction stops being a job your pipeline runs.
  • A vector bucket stores and queries embeddings with strongly consistent writes, which is why the storage service now appears in AI architectures.
  • What it costs: each type is a different surface. The fast one authenticates by session rather than per request, and the vector one keeps public access blocked with no way to relax it.

1. The mental model: same service, four surfaces

2. The fast one, and what it asks of you

The reframing The single-zone trade from lesson 0400 comes back here in a different costume. One Zone-IA gives up redundancy to be cheaper; a directory bucket gives up the same redundancy to be faster. Same sacrifice, two different reasons, and the same question in both cases: what happens to this workload if that one zone is unavailable?

3. The one that understands tables

A table bucket stores Apache Iceberg tables as tables rather than as opaque files, and it performs the maintenance those tables need - compaction in particular - on its own. Its catalogue federates into the Glue Data Catalog, so query engines find the tables without a separate registration step (integrating S3 Tables with AWS analytics). A related capability writes object metadata into Iceberg tables automatically, so a bucket's own contents become queryable (S3 Metadata tables).

Module 06 is where the analytics side of that belongs. What matters for a storage decision is narrower: the compaction job that a lakehouse pipeline normally owns has moved into the storage service.

4. The one that stores vectors

A vector bucket stores and queries embeddings with strongly consistent writes, under its own API namespace, and public access is blocked on it with no option to change that (vector buckets). It is one of several places AWS will store vectors, and Module 13 is where that comparison belongs.

Do not read these types as tiers of one bucket. They are separate surfaces with separate rules, and an assumption carried across from the general-purpose bucket - a storage class, a lifecycle rule, a public-access setting - may simply not apply. When a design names a bucket, make it name the type as well.

Check yourself

Retrieval practice

Answer from memory before revealing.

What does a directory bucket ask of the workload that a general-purpose bucket does not?
A directory bucket holds data in one zone and reaches its latency target only when the compute is co-located there, so the storage choice becomes a placement decision. Storage classes and lifecycle rules belong to the general-purpose bucket's model, and nothing about this type requires writing through a queue.
Which job does a table bucket take over from the layer above it?
A table bucket stores Iceberg tables natively and maintains them, so compaction stops being a pipeline job. Query planning stays with the engine, access control is not replaced, and nothing infers a schema on your behalf - each of those would be a much larger claim than the service makes.
A team wants a vector bucket reachable directly from the public internet. What is the position?
Block Public Access is always on for a vector bucket, so the requirement cannot be met by configuration and the design has to put something in front of it. The three wrong options each describe how a general-purpose bucket behaves, which is exactly the assumption this bucket type does not honour.

Practice about 10 minutes, with paper

Practice 1working

A team is designing a retrieval system. It ingests documents, stores the originals for years, keeps a working set that an inference service reads thousands of times a second at very low latency, holds embeddings for similarity search, and publishes a daily analytics table that a query engine reads.

Assign a bucket type to each of the four jobs, and name for each the specific property that decided it. Then say which single assignment adds a new availability risk and what you would do about it.

Hint

Four jobs, four types. Then look back at which of the four types stores its data in one zone.

Show the worked solution
  1. Originals: a general-purpose bucket. The deciding property is a long life with rare reads, which is exactly what the storage-class ladder and lifecycle rules from lesson 0400 exist for. None of the newer types offers that ladder.
  2. Working set: a directory bucket. The deciding property is thousands of very low latency reads a second. This is the type that publishes consistent single-digit millisecond latency, and the design must place the inference compute in the same zone to get it.
  3. Embeddings: a vector bucket. The deciding property is similarity search over embeddings with consistent writes. Note that public access is blocked with no way to relax it, so anything outside the account reaches it through a service you put in front.
  4. Analytics table: a table bucket. The deciding property is that a query engine reads it as a table. The service maintains the Iceberg table itself and the catalogue federates into the Glue Data Catalog, so the daily pipeline no longer owns compaction or registration.
  5. Name the new risk and answer it. The directory bucket stores in a single zone, so losing that zone takes the working set with it. Because the working set is derived from the originals, the answer is a documented rebuild path rather than replication: measure how long repopulating it takes and treat that number as the recovery time for the fast path.

Sanity check. Each job should map to a different type, and the only availability risk should sit on the derived data rather than on the originals. If your answer put the originals in the single-zone type because it was fastest, you have put the one irreplaceable copy on the one surface that accepts losing a zone.
