Two in-memory services, and the question is which one you may lose

working 6 min Capability key in-memory-cache. · Amazon ElastiCache

The one-minute version

  • Two products sit under the same capability key and speak the same protocols. ElastiCache runs managed Valkey, Redis OSS and Memcached; MemoryDB runs Redis OSS and Valkey as a durable primary database.
  • The difference is what happens to a write. MemoryDB persists every write to a Multi-AZ transactional log before acknowledging it, which is what lets it be the system of record.
  • The old rule that caches never persist is out of date: an ElastiCache Valkey cluster can add a distributed Multi-AZ transactional log of its own for zero data loss.
  • ElastiCache comes in two forms - serverless, which AWS documents as scaling in under a minute, and node-based, where you choose the instances.
  • What it costs: durability is paid for on the write path, so choosing the durable product for data you were happy to lose buys latency you did not need.

1. The mental model: where a write is safe

The familiar rule that "a cache never persists" no longer separates these two products. An ElastiCache Valkey cluster can be configured with a distributed Multi-AZ transactional log for zero-data-loss durability (ElastiCache durability). The distinction that survives is one of positioning: MemoryDB is sold and documented as the primary database, ElastiCache as the cache with a durability option.

2. The mechanism: two forms, and the engine underneath

MemoryDB carries one capability ElastiCache does not: vector search over data held in memory (MemoryDB vector search). That matters for retrieval workloads in front of a model, and module 13 returns to where vectors are stored across the platform.

The reframing These two are not fast and faster. They are the same data structures with different promises about a lost node. Ask what has to be true after a node disappears: if the answer is "the application refills it", the cache is correct; if the answer is "the data is gone", the cache was being used as a database and should be one.

Check yourself

Retrieval practice

Answer from memory before revealing.

A leaderboard is held only in memory and cannot be rebuilt from anywhere. Which service is correct, and why?
Nothing else holds this data, so the store is the system of record and needs a durable write path. Read-heaviness and the availability of sorted sets are true of both products and decide nothing, and MemoryDB is chosen for durability rather than for being quicker on reads.
Which statement about persistence is accurate for these two services?
An ElastiCache Valkey cluster can be given a distributed Multi-AZ transactional log, so the blanket rule in the second option is out of date. Durability is a cluster configuration rather than a Region-level setting, and it is not something the serverless form confers on Memcached.
A team must run an existing Memcached workload without changing its protocol. What are their options?
Memcached appears in the ElastiCache engine list and not in the MemoryDB one, so the choice is made for them. Memcached is still offered, it carries no durability requirement of its own, and MemoryDB's engines are Redis OSS and Valkey.

Practice about 15 minutes, with paper

Practice 1working

A retail application holds four things in memory today, all in one Redis-compatible cluster: rendered category pages, shopping baskets that customers expect to survive a browser restart, a rate-limit counter per client, and a queue of orders waiting to be handed to the payment system.

Sort the four into what belongs on a cache and what belongs on a durable store, and for each one name the observable consequence of losing the node it sits on.

Hint

For each item ask one question and only that question: if this node vanished, could the application recompute the value from somewhere else? Do not let "it would be annoying" count as "it is gone".

Show the worked solution
  1. Rendered category pages - cache. They are derived from the catalogue, so losing the node costs a burst of re-rendering and slower pages until it refills. Nothing is lost.
  2. Rate-limit counters - cache. They are recomputed from the next window of traffic. Losing the node briefly relaxes the limit, which is a security and cost consideration rather than a data-loss one, and worth stating out loud rather than assuming.
  3. Shopping baskets - durable. The customer expects them to survive, and nothing else holds them, so a lost node is lost customer data and, in a checkout flow, lost revenue. This is a system of record wearing a cache's clothes.
  4. Order queue - durable, and probably not here at all. Losing a node loses orders that were accepted and not yet paid for, which is the worst outcome on the list. A durable in-memory store removes the data-loss risk; module 12 covers the queue services that are built for this shape of work in the first place.
  5. Split the deployment. Two of the four are correctly on ElastiCache. The other two need a durable write path, which is either MemoryDB or an ElastiCache Valkey cluster configured with its transactional log - and the deciding factor between those is whether the data is being treated as a primary database, because that is what MemoryDB is documented as being.

Sanity check. Exactly two items should be on each side, and every consequence you wrote for the cache side should be a word like "slower" or "refills" while every consequence on the durable side should be a word like "lost". If any consequence on the cache side reads as data loss, that item is on the wrong side.
