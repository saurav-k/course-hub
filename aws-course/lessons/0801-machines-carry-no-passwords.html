Every machine identity is the same move, made four ways

working 7 min Capability keys workload-identity and short-lived-credentials. · IAM roles for EC2

The one-minute version

  • The role is the universal delegation primitive. A trust policy names who may assume it, and STS mints temporary credentials for whoever qualifies.
  • Compute services do it for you: an instance profile wraps exactly one role, Lambda assumes its execution role at invoke, and ECS splits two roles - the task role for the application and the task execution role for the agent.
  • EC2 credentials rotate through instance metadata, with new credentials available at least five minutes before the old ones expire.
  • Kubernetes has two generations: IRSA registers a per-cluster OIDC provider, and Pod Identity skips OIDC entirely with one reusable trust principal and up to 5,000 associations per cluster.
  • What it costs: a session runs from 15 minutes to 12 hours, but role chaining caps any session at one hour whatever the role's maximum says.

1. The mental model: four lanes, one destination

2. The mechanism: how long a session lasts

Two more properties belong with the duration. MFA context rides only on AssumeRole and GetSessionToken, so a long-term access key can never carry it, and a resource policy condition requiring MFA is satisfiable specifically with GetSessionToken credentials (MFA-protected API access). And STS itself carries a request quota of about 600 requests per second per account per Region, which a fleet that assumes a role on every request will find (IAM quotas).

3. The two Kubernetes generations

The reframing There is no "machine credential" product on AWS to go and find. There is one primitive - a role with a trust policy - and a set of integrations that assume it on your behalf. When a new service asks how it should authenticate, the answer is always the same shape, and the only real question is what its trust policy should name.

Check yourself

Retrieval practice

Answer from memory before revealing.

A job assumes role A, then uses those credentials to assume role B, whose maximum session is twelve hours. How long do B's credentials last?
Role chaining caps any session at one hour regardless of the target role's maximum. The role maximum applies to a session assumed directly, the minimum is a floor rather than what chaining produces, and a chained session is not limited to the remainder of the first one.
Which role does an ECS agent use to pull the container image and write logs?
ECS deliberately splits the two: the task execution role covers the agent's pulls and logging, and the task role covers what the application may do. Using an instance profile puts the permission on the host rather than the task, and there is no shared cluster role standing in for either.
Why does a new EKS design usually choose Pod Identity over IRSA?
Pod Identity skips the per-cluster OIDC provider and lets EKS manage the associations, which is what makes it simpler at scale. Fargate is the exception that still requires IRSA, session length is unchanged, and there is still a trust policy - it names one reusable service principal.

Practice about 15 minutes, with paper

Practice 1working

A nightly reconciliation job runs for about four hours. It starts on an EC2 instance, assumes a role in a second account to read a bucket, and writes results back locally. Two problems are reported: the job fails roughly an hour in with expired-credential errors, and a security review has found a long-lived access key in the instance's configuration file used as a fallback.

Explain both failures, propose a design with no stored key, and say what the job's code has to do differently.

Hint

Count the role assumptions in the description. The one-hour figure in the problem is not a coincidence, and the fix is not a longer session.

Show the worked solution
  1. Count the hops. The instance already has a role through its instance profile. Assuming the second account's role from those credentials is a chained assumption, so the resulting session is capped at one hour whatever the target role's maximum is set to.
  2. Match that to the symptom. A four-hour job failing about an hour in is exactly the chaining ceiling expiring mid-run, which is why raising the target role's maximum session changes nothing.
  3. Fix the expiry in code, not in configuration. The job must refresh credentials rather than fetch them once at start-up - assume the role again when the session is close to expiry. Most AWS SDKs will do this for you if the role is configured as a profile rather than assumed by hand and cached.
  4. Remove the stored key. The instance profile already provides credentials through instance metadata, rotated automatically with new ones available at least five minutes before the old ones expire. The fallback key is not a safety net; it is a long-lived secret sitting on a host that already has a better mechanism.
  5. Check what the key was for. Fallback keys are usually there because someone met the expiry problem in step two and worked around it. Deleting the key without fixing the refresh will simply reintroduce the failure, so the two problems have to be fixed in that order.

Sanity check. Your explanation should use the one-hour chaining ceiling rather than the role's maximum, and your fix should change the job's credential handling rather than any duration setting. If your answer was "increase the session duration", check what chaining does to that number.
