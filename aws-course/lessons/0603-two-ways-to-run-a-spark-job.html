Two services run Spark, and the difference is how much framework you keep

working 6 min Capability keys etl-service, managed-spark and workflow-orchestration. · AWS Glue

The one-minute version

  • Glue is serverless Spark shaped for ETL: crawlers that populate the catalogue, a visual studio, a Schema Registry, a Real-Time Mode and support for the Iceberg, Hudi and Delta table formats.
  • EMR is the framework platform: Hadoop, Spark and Hive, run on EC2, on EKS, or as EMR Serverless with no cluster to manage.
  • AWS states the selection rule plainly: Glue for simpler serverless ETL, EMR for framework control.
  • Glue pins its own engine version - Spark 4.1.1 on Python 3.12 at this snapshot - so the version is a property of the service rather than a choice you make.
  • MWAA runs managed Apache Airflow above both, with the scheduler and workers running as Fargate tasks inside your VPC.

1. The mental model: what each one hands you

2. The mechanism: three deployment targets on one side

Glue's engine version is the service's choice, not yours: Spark 4.1.1 on Python 3.12 at this snapshot, moving when AWS moves it. That is fine for jobs written against stable APIs and hostile to a job pinned to a library that has not caught up, which is the single most common reason a team that started on Glue ends up on EMR (AWS Glue).

3. The layer above both

The reframing Do not choose between these on performance. Choose on which versions and settings your team needs to be able to change. If the honest answer is "none of them", Glue removes work you would otherwise do forever. If the answer names even one library or framework version, EMR is the cheaper choice long before the first tuning argument.

Check yourself

Retrieval practice

Answer from memory before revealing.

A job depends on a Spark library version that Glue's pinned engine does not carry. What follows?
Glue pins its own engine version, so version control is exactly the capability EMR exists to provide. There is no engine-version dial on a Glue job to set or request, and bundling a library does not change the Spark runtime the service supplies.
Which option gives framework control without a cluster to manage?
EMR Serverless accepts Spark and Hive jobs with no cluster to manage while keeping the framework choices EMR gives. Glue hides the cluster and the framework choices together, MWAA schedules work rather than running it, and EMR on EKS still puts the job on a cluster somebody operates.
Where does MWAA run its scheduler and workers?
MWAA runs the scheduler and workers as Fargate tasks in your VPC, which is what lets a DAG reach private resources. It does not borrow EMR capacity, does not run outside your account's network, and is not built on functions.

Practice about 15 minutes, with paper

Practice 1working

A data team has three jobs. One flattens nightly JSON exports into Iceberg tables and has no unusual dependencies. One runs a Hive workload inherited from an on-premises cluster whose settings were tuned over years. One is an experimental job that a research group rewrites weekly against a fast-moving library. All three must run in a fixed order, with the third allowed to fail without stopping the others.

Place each job, and say which part of the requirement is not satisfied by any of the placements on its own.

Hint

Ask of each job only this: does anyone need to change a framework version or a tuning setting? Then read the last sentence of the problem again - it is not about engines at all.

Show the worked solution
  1. Nightly flattening - Glue. No unusual dependencies, and the target is a table format Glue supports directly. This is the case where the service's pinned engine costs nothing and its catalogue integration saves real work.
  2. Inherited Hive workload - EMR. Years of tuning is a statement that the settings matter, which is the definition of needing framework control. If the estate already runs Kubernetes, EMR on EKS keeps it on the cluster the team already operates; otherwise EMR on EC2 or EMR Serverless, depending on whether anything in the tuning reaches the nodes themselves.
  3. Experimental job - EMR Serverless. A fast-moving library means the version has to be the team's choice, which rules out Glue. Nothing here needs a long-lived cluster, so the serverless target gives the control without the operations.
  4. Name what is missing. Ordering, and the rule that the third job may fail without stopping the first two. That is not a property of any engine - it is orchestration, and it belongs in MWAA where the dependency graph and the failure policy are visible.
  5. Put the failure rule where it can be read. Encoding "this one may fail" inside the third job means the next person debugging the pipeline has to open the job to learn the pipeline's rules. In the DAG it is one declared dependency.

Sanity check. Two jobs should end up on EMR and one on Glue, and your last answer should name a service that processes no data. If you put the experimental job on Glue because it is small, re-read the requirement: size was never the deciding property on this page.
