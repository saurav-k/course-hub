The shape of the tree is a blast-radius decision

working 7 min Capability keys org-hierarchy and cross-account-resource-sharing. · AWS Organizations

The one-minute version

  • An organisational unit is not a folder for tidiness. It is the level policy inherits from, so where an account sits decides what can be done inside it.
  • AWS documents a layout worth copying: a Security OU for log archive and tooling, an Infrastructure OU for shared networking, separate Workloads OUs for production and pre-production, and a Sandbox OU that can be detached.
  • The tree has hard bounds: OUs nest five levels deep, up to 2,000 of them, and an organisation holds up to 50,000 accounts once the default limit is raised.
  • The management account is radioactive: it holds org-wide billing and full authority, guardrails do not apply to it, and it should run no workloads.
  • What it costs: keeping it empty means delegated administrators, so services are administered from member accounts rather than from the one account nothing can constrain.

1. The mental model: containment by level

2. The mechanism: the layout AWS documents

The management account is outside every guardrail: the organisation's own ceilings do not apply to it, so a mistake made there has nothing above it to catch. Treat it as break-glass only - no workloads, strong multi-factor authentication, and as few people as the business can tolerate.

3. Keeping the management account empty

Two numbers bound the design. The hierarchy nests five levels below the root, with up to 2,000 organisational units, and an organisation starts with a low account limit that is adjustable up to 50,000 (Organizations quotas). Depth is the one that constrains real designs: a layout that needs six levels needs rethinking rather than a quota increase.

The reframing Draw the tree by asking "what should never be able to affect what", and only then ask who owns each account. An organisation chart changes every year; a containment boundary should not. That is why the documented layout is arranged by function and environment rather than by department.

Check yourself

Retrieval practice

Answer from memory before revealing.

Why should the management account run no workloads?
The organisation's ceilings skip the management account, so nothing above a mistake made there can catch it. Billing rates are the same, cross-account access is a policy question rather than a property of that account, and it is not restricted to one Region.
A design calls for six levels of organisational unit below the root. What follows?
Five levels is the documented depth, so the layout has to change rather than the quota. There is exactly one root per organisation, and the management account is not a place to hang further hierarchy.
What is created automatically inside a newly vended member account?
Member account creation makes an organisation access role automatically, which is a standing path in from the management account. Policies attached to a parent apply by inheritance rather than being copied in, delegation is configured deliberately, and tag policies are not duplicated per account.

Practice about 15 minutes, with paper

Practice 1working

A company has thirty accounts in a flat organisation, arranged one per team. Shared networking lives in the management account, which also runs the security tooling and a small internal web application. Auditors have asked that production be separable from everything else, and a research group wants an environment it can experiment in freely.

Redraw the tree, say what moves out of the management account and where each thing goes, and name the property the research group's placement gives the company.

Hint

Start from the documented layout rather than from the current one. For each thing in the management account, ask which of the documented units it belongs to, and remember that one unit exists precisely so it can be cut loose.

Show the worked solution
  1. Start from function, not from teams. Create a Security unit, an Infrastructure unit, workload units split into production and pre-production, and a sandbox unit. Team ownership becomes an account attribute rather than the organising principle.
  2. Move shared networking. It goes to an account in the Infrastructure unit, and reaches the workload accounts through resource sharing rather than by living somewhere everyone can already reach.
  3. Move security tooling and log archive. Both go to accounts in the Security unit, where a guardrail can protect them from the very administrators who run the workloads.
  4. Move the internal web application. Into a workload account under the appropriate environment unit. It is the clearest case of all: an application in the management account is an application no guardrail can constrain.
  5. Place the research group and name the property. The sandbox unit, with its own guardrails, and its value is that it is detachable - the whole unit can be cut loose from the organisation without unpicking production, which is exactly what "experiment freely" has to mean if it is to be safe.
  6. Answer the auditors. Production is now a unit with its own inherited policy rather than a set of accounts distinguished only by name, which is what makes "separable" checkable rather than asserted.

Sanity check. Nothing should remain in the management account except billing and break-glass access, and your sandbox answer should use the word detachable. If any team name appears as an organisational unit, the layout will need redrawing the next time the company reorganises.
