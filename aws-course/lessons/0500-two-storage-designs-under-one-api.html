Relational on AWS is one control plane over two storage designs

working 7 min Capability key relational-managed. · Amazon RDS

The one-minute version

  • One managed service runs six engines - MySQL, PostgreSQL, MariaDB, Oracle, SQL Server and Db2 - and picking the engine is rarely the decision that matters.
  • An RDS instance owns a storage volume of its own. An Aurora cluster's instances share one distributed storage volume, which is why a reader is cheap to add and a writer is not duplicated.
  • "Multi-AZ" names two different deployments. A Multi-AZ DB instance has one standby that serves nothing; a Multi-AZ DB cluster has two standbys you can read.
  • Failover on a Multi-AZ DB cluster is documented as typically under 35 seconds, and what decides it is how far behind the reader being promoted has fallen.
  • What it costs: readable standbys are extra instances on the bill, and a lagging reader makes failover slower rather than faster.

1. The mental model: the volume, or the shared volume

The consequence shows up the moment you want a second copy for reading. On the left-hand design that is a second volume being written twice. On the right it is a process attaching to storage that is already there, which is why Aurora carries up to fifteen readers and RDS does not.

2. The mechanism: four deployment shapes, not two

Storage type is the other dial on the RDS side, and it is chosen separately from the deployment shape. AWS recommends gp3 as the general-purpose volume and offers io2 Block Express where sustained provisioned IOPS matter; magnetic storage remains only for old instances (RDS storage).

3. What a failover actually waits for

The reframing Choosing a relational database here is choosing how many machines may read the same bytes, and what it costs to add one. The engine name decides which SQL dialect your application speaks; the storage design decides what the database can grow into. Ask the second question first.
Aurora's Global Database replicates a cluster to up to ten secondary Regions with typical lag under one second (Aurora Global Database). Typical is not guaranteed, and a secondary Region is a read endpoint, not a second writer. A design that needs writes in two Regions at once needs a different engine, which lesson 0501 reaches.

Check yourself

Retrieval practice

Answer from memory before revealing.

A team asks for "Multi-AZ RDS" so that reporting queries stop competing with the application. What must be specified?
Only the Multi-AZ DB cluster shape gives readable standbys. The Multi-AZ DB instance standby is synchronous but serves no reads, so the first option describes the shape the team will get by accident and be disappointed by. A bigger instance and a faster volume both raise capacity on one machine without separating the two workloads.
Why can an Aurora cluster carry up to fifteen readers when an RDS instance deployment cannot?
Aurora's instances share a single distributed storage volume, so a reader costs compute and no new copy of the data. The engines are the familiar MySQL and PostgreSQL ones rather than something different, readers run ordinary queries, and page compression is not what the reader count rests on.
A Multi-AZ DB cluster failover takes far longer than usual. What is the most likely cause?
Promotion waits for the chosen reader to catch up, so replica lag is what stretches the documented sub-35-second window. A Multi-AZ DB cluster spans three zones by definition, storage type changes throughput rather than promotion order, and instances in one cluster run one engine version.

Practice about 15 minutes, with paper

Practice 1working

An order service runs on PostgreSQL. It takes roughly 400 writes a second at peak. A finance team wants to run heavy month-end reports against the same data, and the business states a recovery time objective of one minute for the writer. A second engineering team, in another Region, wants to serve a read-only product catalogue from the same database.

Choose a deployment shape for the order service, say what you would put the reporting queries on, and name the one requirement in this list that the shape you chose does not satisfy on its own.

Hint

Three of these requirements are about copies of the data and one is about time. Deal with the copies first, then check the recovery objective against the number the vendor publishes, then look at what is left over.

Show the worked solution
  1. Separate the requirements. Reporting needs a readable copy. Recovery needs a fast promotion. The catalogue needs a copy in another Region. Three requirements, and no single sentence answers all three.
  2. Check the recovery objective against the published number. The stated objective is 60 seconds and a Multi-AZ DB cluster failover is documented as typically under 35 seconds, so the shape clears the objective with margin - provided replica lag stays small, because lag is what consumes the margin.
  3. Choose the shape. A Multi-AZ DB cluster gives two readable standbys across three zones and the failover behaviour above. That satisfies reporting and recovery together.
  4. Place the reporting queries. On a readable standby, not on the writer. This is the whole reason to prefer the cluster shape over the DB instance shape here.
  5. Name what is left. The other Region. A Multi-AZ DB cluster is a single-Region shape, so the cross-Region catalogue is not covered. Aurora Global Database is the mechanism that is - up to ten secondary Regions, typical lag under one second, read endpoints only - and reaching for it means moving the workload from RDS to Aurora, which is a migration rather than a setting.

Sanity check. Your answer should name exactly one shape, put reporting somewhere other than the writer, and end with the cross-Region requirement flagged as unmet. If you satisfied all three requirements without changing product, re-read what "Multi-AZ" spans: three zones inside one Region, and never two Regions.
