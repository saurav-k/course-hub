The tail is fast and the delivery leg is the honest bottleneck

working 7 min Capability keys log-store, control-plane-audit-log and telemetry-export-pipeline. · CloudWatch Logs Live Tail

The one-minute version

  • Live Tail streams new log events at a one-second cadence over any log group, through a first-party API rather than as a console convenience.
  • The CDN's real-time logs reach a stream in seconds, sampled at a rate you choose, and the platform event bus carries service events at the same scale.
  • Most streams are minutes: audit records typically about five minutes, flow logs about five to the log store and ten to object storage, function logs five to ten.
  • So the honest limit is not the tail, it is the delivery leg into a store you can query, and a detection design has to be built against that number.
  • What it costs: subscription-filter deliveries retry for up to 24 hours and then drop, so a downstream consumer that is down long enough loses events with no replay.

1. The mechanism: where each stream lands on the clock

2. The mental model: two legs, not one

Where AWS publishes no figure, this course does not invent one. CloudWatch metric streams are documented only as "near-real-time delivery and low latency" with no number attached, so any minute-scale estimate you meet is somebody's measurement rather than a commitment - measure your own pipeline instead (metric streams).

3. The pipeline that quietly gives up

Three more timing facts belong on the same page. Flow log aggregation is configured at one minute or ten, and the interval is added to the delivery time rather than replacing it. Load balancer access logs are written in five-minute batches per node. And a change to the CDN's standard logging settings takes effect within twelve hours, which is a configuration delay rather than a delivery one and catches people who enable logging during an incident.

The reframing Write the response time you need, then subtract the delivery leg of the stream you plan to use. What is left is the budget for your own evaluation, and if it is negative the answer is a different stream rather than a faster alarm. That single subtraction settles most arguments about whether a control can be automated.

Check yourself

Retrieval practice

Answer from memory before revealing.

A requirement asks for automated response within thirty seconds of an unusual API call. What is the obstacle?
The delivery leg is the obstacle: audit records typically arrive about five minutes after the call, so nothing downstream can respond in thirty seconds. Audit records are not sampled, retention governs how far back you can look rather than how fast records arrive, and the evaluation period is the smaller half of the sum.
Which first-party path delivers log events at a one-second cadence?
Live Tail is a streaming tail with a documented one-second cadence and its own API, available over any log group. A metric filter produces a metric rather than a stream of events, an export task is a batch operation, and a query returns what has already been stored.
A consumer behind a subscription filter is offline for two days. What happens to the events?
Subscription filters retry for up to twenty-four hours and then drop the deliveries, with no replay. The events remain in the log group, but nothing re-sends them, and export tasks are a separate mechanism that is not a fallback.

Practice about 15 minutes, with paper

Practice 1working

A security team writes three requirements. A publicly exposed storage bucket must be corrected within ten minutes of being made public. A suspicious sign-in must page a human within one minute. A sudden surge of errors at the CDN edge must be visible to an on-call engineer within a minute of starting.

For each, name the stream you would build on, do the subtraction, and say which requirement cannot be met as written.

Hint

Write the delivery leg of each candidate stream first, then subtract from the stated deadline. Two of the three have a stream in the seconds cluster available; one does not.

Show the worked solution
  1. The public bucket - ten minutes, on an audit stream. The configuration change is an API call, so the audit trail is the source, with a typical delivery of about five minutes. Ten minutes minus five leaves about five minutes for evaluation and remediation, which is workable but has no margin, so the remediation itself must be automatic rather than a ticket.
  2. Consider the alternative for the same requirement. A detective configuration rule also sees this, but it is evaluating recorded configuration rather than the call, so it is not the faster path. Keep it as the backstop that catches whatever the first path misses.
  3. The suspicious sign-in - one minute, and this is the one that fails. Sign-in events reach the audit stream, whose delivery leg is typically about five minutes. One minute minus five is negative, so the requirement cannot be met from that source however the alarm is configured. Say so plainly and renegotiate the number, or find a source that emits the signal on the event bus.
  4. The CDN error surge - one minute, and this one is comfortable. Real-time CDN logs deliver in seconds to a stream, so a minute is achievable with room to spare. Note that they are sampled at a rate you choose, so pick a sampling percentage high enough for the surge to be visible.
  5. Record the trap that catches people mid-incident. If real-time logging is not already enabled, turning on the CDN's standard logging during the incident will not help either - that setting takes effect within twelve hours.

Sanity check. Exactly one requirement should come out negative, and it should be the one-minute sign-in requirement rather than the ten-minute bucket one. If all three looked achievable, you subtracted the evaluation period rather than the delivery leg.
