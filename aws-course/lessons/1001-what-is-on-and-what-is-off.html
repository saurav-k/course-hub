Module 10 · Observability and audit · Lesson 1001

Almost nothing is recorded until you say so

working 7 min Capability keys control-plane-audit-log, data-plane-access-log, network-flow-log, load-balancer-access-log, dns-query-log and service-specific-log. · How CloudTrail works

The one-minute version

  • Control-plane audit is on by default as a free, immutable 90-day event history - and that history is not a trail, so it holds management events only and cannot be kept longer.
  • Data events are off everywhere and require selectors. They are the high-volume ones - object reads, function invocations, item-level database calls - and they dominate audit cost when scoped loosely.
  • Network, load-balancer, CDN, DNS and most service logs are all off by default, each with its own switch in its own service.
  • Flow logs do not see everything on the wire. DNS resolver traffic, instance metadata, NTP, DHCP and ARP are excluded by design.
  • What it costs: two widely used streams are explicitly best-effort, so neither is a complete accounting and neither should be the basis of a billing-grade claim.

1. The mechanism: the default column

2. The stream that is on, and what it is not

Data events are the other half of the audit story and they behave in the opposite way: off everywhere, selectors required, and priced per hundred thousand delivered. Advanced selectors filter by event name, resource ARN and whether the call was read-only, with up to 500 values per field, which is the mechanism that keeps a bucket's audit trail affordable (logging data events). CloudTrail Insights adds anomaly detection over call rates and error rates, also off by default, and its first findings can take up to thirty-six hours to appear after it is enabled.

3. What the network log does not see

Two streams are documented as best-effort and should never be treated as complete. Load balancer access logs carry an explicit warning that they are not a complete accounting, and legacy object-store server access logging is delivered within a few hours with duplicates possible. For reliable object access auditing, use data events instead.
The reframing Read the default column before the feature list. The question is never "can AWS log this" - it almost always can - but "was it logging this on the day it mattered", and that is decided by a switch somebody either did or did not set, in a service that has nothing to do with the incident.

Check yourself

Retrieval practice

Answer from memory before revealing.

An investigation needs to know who read a particular object four months ago. What decides whether that is answerable?
Object reads are data events, which are off by default and require selectors, so the question is answerable only if somebody enabled them beforehand. Event history retention cannot be extended and covers management events only, flow logs record IP flows rather than object access, and a trail without data-event selectors records no object reads.
Which activity is invisible to VPC flow logs?
Instance metadata traffic is excluded by design, along with DNS resolver, NTP, DHCP and ARP. Rejected flows are recorded, and service-owned interfaces such as NAT gateways and load balancers appear in flow logs like any other interface.
What is the difference between the default event history and a trail?
Event history is free, immutable, on by default and capped at ninety days of management events, while a trail is what delivers records durably to a destination you keep. Data events require selectors on a trail rather than being its defining feature, the history is immutable too, and neither is defined by Region coverage.

Practice about 15 minutes, with paper

Practice 1working

A new organisation is being set up. The security team asks for four guarantees: every administrative action is retained for two years, access to one sensitive bucket is auditable, unusual outbound network connections can be investigated, and nothing costs more than it has to.

Specify the streams to enable for each guarantee, name the one that must be scoped narrowly and why, and state one thing the fourth guarantee cannot cover.

Hint

Take the guarantees in order and ask, for each, whether the stream is on already, and whether it is charged by volume. One of the four is charged by volume and is the reason audit bills surprise people.

Show the worked solution
  1. Two years of administrative actions - a trail. The default event history stops at ninety days, so a trail delivering management events to object storage is what makes two years possible. The first copy of management events in a trail carries no charge, and the object storage lifecycle of lesson 0400 controls what the two years actually cost.
  2. Auditing the sensitive bucket - data events, scoped. This is the stream that must be narrow. Data events are charged per hundred thousand delivered and object access is high volume, so use advanced selectors to name that bucket's ARN specifically rather than enabling data events account-wide.
  3. Say why the scoping matters. Enabling data events across every bucket in a busy account produces a stream orders of magnitude larger than the management-event stream, and it is the single most common cause of an unexpected audit bill.
  4. Outbound network investigation - flow logs. Off by default, so they must be enabled per network, and the destination decides the cost: object storage in a columnar format is cheaper at volume than the log store.
  5. State the gap. Flow logs do not record traffic to the DNS resolver or to the instance metadata service. So a workload resolving an unexpected name, or a process reading credentials from metadata, is outside this guarantee - DNS resolver query logging is a separate switch, and metadata access has no flow-log record at all.

Sanity check. Exactly one of your four streams should be scoped by selector, and your gap should name something a flow log cannot see rather than something it records badly. If your answer relied on the ninety-day event history for the two-year requirement, re-read what that history is.
