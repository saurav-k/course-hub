Most declarative infrastructure here resolves to one engine

working 7 min Capability keys native-iac-template, terraform-provider, iac-in-code-sdk, config-management and kubernetes-config-management. · AWS CloudFormation

The one-minute version

  • CloudFormation is the engine. The CDK synthesises into it and the serverless model is a transform over it, so three languages produce one kind of deployment.
  • Its safety features are the reason to prefer it over scripting: change sets preview a destructive change, a failed create or update rolls back automatically, and drift detection reports divergence.
  • StackSets deploy across accounts and Regions, in a self-managed or a service-managed permission model.
  • The third-party path is Terraform, with the community-standard provider and a generated awscc provider that ships new services on the day they appear. No AWS-managed Terraform-compatible service exists.
  • What it costs: SDK calls provision imperatively and describe nothing, so declarative infrastructure belongs in a template - and what lives inside an instance belongs to Systems Manager instead.

1. The mental model: three languages, one engine, one alternative

2. The mechanism: what a stack does that a script does not

Two more capabilities decide how far a template reaches. StackSets deploy one template across accounts and Regions, with either a self-managed permission model or a service-managed one that uses the organisation. And an IaC generator imports resources that were created by hand into a template, which is how an estate that started by hand is brought under description without recreating anything.

A verified negative worth stating plainly: there is no AWS-managed Terraform-compatible service at general availability. AWS partners around Terraform - launch-day provider support and Terraform products in the service catalogue - and the state file and the runner remain yours to operate.

3. What lives inside the instance

For estates that run everything through Kubernetes, AWS Controllers for Kubernetes expose AWS resources as custom resources so that kubectl and GitOps manage cloud objects. It is open source installed into your cluster rather than a managed control plane, one controller per service, each versioned separately - so coverage and maturity differ service by service, and permissions come from the pod identity mechanisms of lesson 0801.

The reframing Choose the description language for the team, and choose the deployment engine for its safety properties. Preview before applying, roll back on failure, detect drift, reach every account: those four are what separate infrastructure as code from a script that happens to be in version control, and they are the questions to ask of whatever tool you pick.

Check yourself

Retrieval practice

Answer from memory before revealing.

What does a change set tell you that running the update would not?
A change set previews the operations, including replacements, which is the difference between a routine update and an outage. Drift detection is a separate feature, scope is a StackSets concern, and template history is version control's job.
Which statement about Terraform on AWS is accurate?
The awscc provider is generated from the CloudFormation registry and reaches new services through Cloud Control, while the classic provider lags. There is no AWS-managed Terraform service, and state remains yours to store and operate.
An engineer needs a shell on a private instance with no inbound port open. What provides it?
The agent-brokered session needs no open port, no public address and no jump host, and it is recorded. There is no AWS bastion product - that is precisely the gap the session manager fills - and neither a stack output nor a Kubernetes controller provides interactive access.

Practice about 15 minutes, with paper

Practice 1working

A company has 200 resources created by hand over three years, a shell script that provisions new environments with SDK calls, and a requirement to apply one logging configuration to every account including future ones. Engineers write TypeScript and do not want to write YAML. Operators still connect to instances over SSH using a shared key.

Propose the target state, saying what each of the four situations becomes, and name the one change that removes a standing credential.

Hint

Take the four in order and ask what each one is missing: a description, a preview, a reach across accounts, or a broker. Only one of the four is about a credential.

Show the worked solution
  1. The 200 hand-made resources - import them. The IaC generator produces a template from existing resources, so the estate comes under description without being recreated. Nothing is destroyed and nothing is rebuilt, which is what makes this palatable to the team who own those resources.
  2. The provisioning script - replace it with a template. SDK calls provision and describe nothing, so the script has no preview, no automatic rollback and no drift detection. Converting it to a stack buys all three, and that is the argument rather than tidiness.
  3. The TypeScript preference - use the CDK. It synthesises to the same engine, so the team writes TypeScript and still gets change sets, rollback and drift. Note that they are choosing an authoring language rather than a different deployment model, which is worth saying out loud so nobody expects different semantics.
  4. Logging in every account including future ones - StackSets. One template deployed across the organisation with the service-managed permission model, so accounts vended later come into scope without anybody revisiting it.
  5. Name the credential change. The shared SSH key. Replacing SSH with brokered sessions through Systems Manager removes the key entirely: no inbound port, no public address, no shared secret, and the sessions are recorded rather than merely allowed.

Sanity check. Three of your four answers should be about the same engine reached different ways, and exactly one should remove a secret. If you proposed recreating the 200 resources, check what the import path exists for.
