One workflow engine with two very different clocks, and three ways to present an API

working 7 min Capability keys workflow-orchestration, api-gateway, graphql-api and realtime-messaging. · AWS Step Functions

The one-minute version

  • A workflow is a state machine written in a declarative language, and its two execution models differ in guarantee, duration and billing at once.
  • Standard is exactly-once, runs up to a year and is billed per state transition. Express is at-least-once, stops at five minutes and is billed per request.
  • Two integration patterns carry most designs: run a job and wait for it, and wait for a callback token - which is how a human approval fits inside a workflow.
  • The API layer has three surfaces: REST with usage plans, mapping templates, a firewall attachment and canary stages, HTTP which is leaner and cheaper per call with a native token authoriser, and WebSocket for two-way connections.
  • What it costs: a WebSocket API keeps no subscriber registry, so your application stores connection identifiers itself.

1. The mechanism: two clocks, a hundred thousand apart

2. Three surfaces, and what each buys

A WebSocket API gives you connect, disconnect and default routes and keeps no subscriber registry: your application stores connection identifiers itself and uses a management API to push messages back. Billing is per message and per connection-minute, so idle connections cost something. The GraphQL service's event channels cover the same fan-out with server-side namespaces, which removes that bookkeeping (WebSocket APIs).

One account-wide number belongs with all of these: the API layer has a default request-rate throttle per Region, with a burst allowance below it. It is adjustable, and it is an account-level default rather than a per-API one, so a new high-volume API shares it with everything else already running.

The reframing Both choices on this page look like price comparisons and are really guarantee comparisons. Express against standard is at-least-once against exactly-once before it is cheap against expensive; HTTP against REST is a feature set before it is a per-call rate. Decide on the guarantee and the features you need, then check that the price follows - not the other way round.

Check yourself

Retrieval practice

Answer from memory before revealing.

A process must pause for a manager's approval, sometimes for days. Which execution model fits?
The standard model runs up to a year and can suspend on a callback token, which is exactly the human-approval pattern. Express stops at five minutes however the approval is arranged, and restarting a workflow loses the state that made it a workflow.
What must an application do that a WebSocket API does not?
No subscriber registry is kept, so the application stores connection identifiers and uses the management API to push. Inbound frames are routed by route key, per-frame authentication is not required by the surface, and billing per connection-minute is a cost consideration rather than something the application must implement.
What is the substantive difference between the two request-response API surfaces?
The REST surface carries usage plans, mapping templates, a firewall attachment and canary stages, while the HTTP surface trades several of those for a lower per-call price and a native token authoriser. Both reach functions, and neither is limited to one endpoint kind in the way the other options suggest.

Practice about 15 minutes, with paper

Practice 1working

An insurance claim process has four steps: validate the submission in under a second, run a fraud check taking up to ten minutes, wait for a human assessor who may take three days, then pay out. Claims arrive from a mobile application, and assessors want the claim list to update live as new claims arrive. Peak submission rate is 300 per second.

Choose an execution model and API surfaces, place each of the four steps, and name the number you would check before promising the peak rate.

Hint

Find the longest wait in the process first - it decides the execution model on its own. Then handle the live list separately, because it is not a request-response problem.

Show the worked solution
  1. The three-day wait decides the model. Only the standard execution model reaches beyond five minutes, so the claim process is a standard workflow. Billing per state transition is acceptable because the workflow has few states and each claim passes through them once.
  2. Place the steps. Validation is a fast task. The fraud check runs as a job the workflow waits for, since ten minutes exceeds a single function's ceiling and should not be inlined. The assessor step waits for a callback token, returned when the assessment is submitted. Payment is the final task.
  3. Consider the fast path separately. If sub-second validation is wanted before a claim is accepted at all, an express workflow or a plain function in front of the standard workflow is reasonable - and it must be a separate execution rather than a state inside the long one, because the two models cannot be mixed in one execution.
  4. Choose the surfaces. The mobile application submits over a request-response API, and the lean HTTP surface fits unless usage plans, request mapping, a firewall attachment or canary stages are required. The live assessor list is a two-way problem: either a WebSocket API, remembering that connection identifiers are yours to store, or the GraphQL service's subscriptions, which remove that bookkeeping.
  5. Name the number to check. The account-level request-rate throttle for the API layer in that Region, and its burst allowance. It is an account default shared with every other API in the account, so 300 per second must be checked against what is already consumed rather than against the limit in isolation.

Sanity check. Your workflow should be standard because of the three days rather than because of the ten minutes, and your live-list answer should not be a request-response API. If you put the assessor wait in an express workflow, compare three days against five minutes.
