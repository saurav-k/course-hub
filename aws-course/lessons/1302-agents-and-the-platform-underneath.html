An agent platform is seven components, and one of them is identity

working 6 min Capability key agent-platform. · Bedrock AgentCore

The one-minute version

  • The agent platform is modular: a runtime, a gateway that exposes tools, memory, identity, a code interpreter, a browser, and observability.
  • It is framework-agnostic and model-agnostic - it hosts agents written with the common open-source frameworks and calls whichever model you choose.
  • Its runtime allows eight-hour windows, which is far beyond a function's fifteen minutes and lets an agent work rather than merely answer.
  • There is no separate agent directory object on this platform: agent credentials are issued and scoped by the platform's own identity component.
  • What it costs: the earlier generation of agents is in maintenance, and two adjacent products are closed to new customers with named successors.

1. The mental model: seven components, not one product

2. The mechanism: how long an agent may work

3. What a run actually does

Three lifecycle facts belong with any design here. The earlier generation of agents is in maintenance. The enterprise assistant product and the enterprise search service are both closed to new customers, with named successors - knowledge bases for the search workloads, and a successor product for the assistant. Material recommending any of the three is describing an earlier state of the platform.
The reframing Read the component list as a checklist of the problems an agent creates. Where does it run, what may it use, what does it remember, who is it, and how do you watch it - those questions arrive whether or not you adopt this platform, and building the answers yourself is the alternative rather than avoiding them.

Check yourself

Retrieval practice

Answer from memory before revealing.

Where does an agent's identity come from on this platform?
There is no separate agent directory object here - credentials are issued and scoped by the platform's identity component. The workforce and customer directories hold people, and a stored key is precisely what this arrangement removes.
Why is an agent runtime a separate product rather than a longer function timeout?
An eight-hour window is far beyond the fifteen-minute function ceiling, which is what a tool-using loop needs. Functions call APIs freely, assume an execution role for credentials, and are not restricted to different languages.
What does the tool gateway provide?
The gateway exposes tools over the model context protocol so they are registered once and reused. Memory, the browser and observability are three other components of the same platform, each answering a different question.

Practice about 15 minutes, with paper

Practice 1working

A team builds an agent that reconciles invoices. It reads a shared mailbox, queries two internal APIs, occasionally runs a short calculation script, and sometimes needs a person to confirm an exception. A run can take several hours. The team currently plans to host it as a function, with an access key in an environment variable and no logging beyond the function's own output.

Review the plan against the seven components, name the three things that will fail first, and say where the human confirmation belongs.

Hint

Check the plan against the runtime ceiling first, then against the credential, then against what happens when a run misbehaves. The human step is a pattern from an earlier module.

Show the worked solution
  1. The duration fails first. A run taking several hours cannot be a function - the ceiling is fifteen minutes. This is not a tuning problem, so the runtime choice has to change before anything else is discussed.
  2. The credential fails next. An access key in an environment variable is a long-lived secret on a component that calls internal APIs, which is exactly what the platform's identity component removes by issuing credentials scoped to the agent. It also means the agent's permissions cannot be reasoned about separately from whoever created the key.
  3. Observability fails third, and most quietly. A multi-hour loop that calls tools and runs code produces very little useful signal from a function's own output. Traces and metrics from the platform's observability component are what make a bad run explicable afterwards.
  4. Tidy the tool access. The two internal APIs and the calculation script are the gateway and the code interpreter. Registering the APIs as tools once means a second agent can use them without the wiring being repeated, and the interpreter removes the need to package a script runtime.
  5. Place the human confirmation. Not inside the agent. A pause for a person is the callback-token pattern of lesson 1204, in a standard workflow that can wait far longer than any run window - the agent does the work, and the workflow holds the process open while a human decides.

Sanity check. Your three failures should be duration, credential and observability, in that order of obviousness, and the human step should end up outside the agent. If the human confirmation stayed inside the run, compare several hours of waiting against the eight-hour window and against a workflow's year.
