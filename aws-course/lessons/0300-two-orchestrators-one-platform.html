AWS ships two orchestrators, and the choice is about whose API you commit to

working 7 min Capability keys container-orchestrator-nonk8s, managed-kubernetes and kubernetes-node-autoscaler. · Amazon ECS

The one-minute version

  • AWS is the only one of the four major clouds that ships a proprietary container orchestrator alongside managed Kubernetes. Both are first-class and neither is a migration path to the other.
  • ECS is built from three objects - task definition, service and capacity provider - and its vocabulary is AWS's own.
  • EKS is upstream Kubernetes with the control plane managed, so the vocabulary is Kubernetes' and the portability is real.
  • Each Kubernetes minor version gets a fourteen-month standard support window, then a paid extended window. Upgrading is a recurring obligation rather than an option.
  • What it costs: EKS gives you Kubernetes, not a Kubernetes platform. There is no fleet object across clusters and no workload-aware cluster backup service, and both gaps are yours to fill.

1. The mental model: three objects, twice

ECS also reaches outside the cloud and into a simpler entry point. ECS Anywhere runs tasks on your own hardware through an external launch type, and ECS Express Mode provisions a service, a load balancer and scaling from a single call naming an image, which is the successor AWS names for its closed managed web runtime.

2. How much of the cluster you operate

Auto Mode's nodes are not ordinary instances. They run a locked-down operating system and are replaced on a maximum lifetime of twenty-one days, which turns node patching from a project into a property of the platform. The autoscaling underneath it is Karpenter, an open-source node lifecycle manager that provisions right-sized nodes directly from unschedulable pods and then consolidates them away again. On EKS you can adopt Karpenter on its own or take it built in through Auto Mode.

The reframing Karpenter inverts the usual scaling question. A node group asks "how many of this node shape should exist?" and Karpenter asks "what shape of node would let these specific pending pods run?" That is why it can both create an unusual node and delete it again minutes later, and why fleet sizing stops being a number you maintain.

3. The obligation nobody mentions at the start

A managed control plane does not mean a control plane you never touch. Each Kubernetes minor version carries a fourteen-month standard support window, after which the cluster moves onto a paid extended window rather than simply continuing (EKS Kubernetes versions). Upgrades are therefore a scheduled, recurring piece of work with a cost attached to being late.

4. What EKS does not give you

Two capabilities that other clouds package are, on AWS, yours to assemble. Saying so precisely matters, because both are real absences rather than services with unfamiliar names.

What is missingWhat AWS expects instead
Workload-aware Kubernetes backup. AWS Backup does not cover EKS cluster objects. Teams run an open-source tool such as Velero themselves, and own its schedule, its storage and its restore testing.
A fleet object across clusters. There is no grouping that applies policy or upgrades to many clusters at once. Clusters are managed one at a time, and consistency comes from the account and organisation layers of Module 01 rather than from a cluster-fleet service.
These two gaps compound. Without a fleet object, every cluster is upgraded on its own timetable, and without a backup service, every cluster's recovery story is a tool somebody installed. An estate of thirty clusters therefore has thirty upgrade windows and thirty restore procedures unless you build the missing layer deliberately. Count clusters before you choose a per-team cluster topology.

Check yourself

Retrieval practice

Answer from memory before revealing.

Which pairing of ECS objects matches the Kubernetes objects they play the part of?
A task definition describes the work in the way a pod spec does, and a service keeps a number of copies running in the way a deployment does. The capacity provider is the node-supply layer. The wrong options each shuffle those three roles, which is exactly the confusion a team hits on its first cross-orchestrator conversation.
A team wants the upstream Kubernetes API but does not want to operate nodes. What fits?
Portability and operational load are independent, and Auto Mode is the corner that answers both: upstream API, and AWS operating nodes, autoscaling, load balancing, DNS and storage. Both ECS options give up the upstream API. Managed node groups keep the API and hand the nodes back to the team.
What does AWS expect you to do about backing up Kubernetes cluster objects on EKS?
AWS Backup does not cover EKS cluster objects and there is no per-cluster setting for it, so the documented expectation is that teams run a tool such as Velero themselves. The control plane is managed and is not a thing you snapshot. This is a genuine absence rather than a service under an unfamiliar name.

Practice about 15 minutes, with paper

Practice 1working

An organisation has eight product teams. Each wants its own isolated cluster. Nobody has Kubernetes experience, but two teams expect to run the same workload on a customer's own hardware next year, and the platform group is three people.

Recommend an orchestrator and a topology, then cost your recommendation honestly: name every recurring obligation the platform group takes on, and say which requirement would flip your answer if it were dropped.

Hint

Separate the two questions this page keeps apart. Then multiply every per-cluster obligation by eight and ask whether three people can carry it.

Show the worked solution
  1. Answer the API question first. Two teams need the same workload to run on a customer's hardware, and the upstream Kubernetes API is what makes that portable. That requirement alone selects EKS over ECS for those teams.
  2. Answer the operations question second. Nobody has Kubernetes experience and the platform group is three people, so the node-operating work should go to AWS. That selects EKS Auto Mode, where the data plane, autoscaling, load balancing, DNS and storage are operated for you and nodes roll on a twenty-one day maximum lifetime.
  3. Cost the topology. Eight clusters means eight upgrade windows, because there is no fleet object that upgrades many clusters at once, and each Kubernetes minor version leaves standard support after fourteen months. It also means eight backup and restore procedures, because AWS Backup does not cover cluster objects.
  4. Say what three people can actually carry. Sixteen recurring obligations against three people is the finding. Either the topology drops to a smaller number of shared clusters separated by namespace and account boundaries, or the platform group builds the missing fleet layer as a deliberate product with its own time budget.
  5. Name the requirement that flips the answer. The customer-hardware requirement. Without it, no team needs the upstream API, and ECS on Fargate removes both the upgrade obligation and most of the operational surface - at the price of an AWS-specific vocabulary.

Sanity check. Your answer should recommend a specific orchestrator and then argue against your own topology, and the two gaps should appear as multiplied work rather than as footnotes. If your recommendation has no recurring cost in it, you have described a product page rather than a design.
