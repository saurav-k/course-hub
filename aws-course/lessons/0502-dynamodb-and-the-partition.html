The table has no size limit and the partition has three

working 7 min Capability key nosql-keyvalue. · Amazon DynamoDB

The one-minute version

  • DynamoDB is a serverless key-value and document store that AWS positions at single-digit millisecond latency at any scale, and there is no instance, cluster or storage to size.
  • The scale is at the table level. Every hard limit that shapes a design is at the partition level, and the partition key is what decides which partition a request lands on.
  • Those limits are about 3,000 read units and 1,000 write units per partition, softened but not removed by adaptive capacity, and a 400 KB ceiling on a single item.
  • Global Tables make replicas in several Regions that all accept writes, with a strongly consistent mode available alongside the eventually consistent one.
  • What it costs: a badly chosen key concentrates traffic on one partition, and the table looks under-used while requests are throttled.

1. The mental model: the key picks the machine

2. The mechanism: where the ceilings actually are

The third ceiling is on the item itself: a single item may not exceed 400 KB (DynamoDB quotas and constraints). Designs that would grow an item without bound - an append-only list of events on one record, a document that accumulates comments - meet that wall as a hard failure rather than as a slowdown, so the item ceiling is a modelling constraint rather than a tuning one.

The reframing DynamoDB does not remove capacity planning. It moves it from the deployment into the data model, where it is decided once, early, and by whoever chose the partition key. That is why "it scales automatically" and "our table is throttling at ten percent of its provisioned throughput" are routinely true at the same time.

3. Beyond one Region, and the two consistency modes

Two attachments are worth knowing by name because designs lean on them. DynamoDB Streams exposes an ordered change feed of a table with 24 hours of retention, which makes it a trigger source and not an archive. DAX is an in-front cache that AWS positions in microseconds rather than milliseconds. Both carry their own limits on the quotas and constraints page.

Check yourself

Retrieval practice

Answer from memory before revealing.

A table provisioned well above its measured load is throttling requests. What is the first thing to inspect?
Throughput ceilings apply per partition, so traffic concentrated on few key values throttles while the table looks idle. An oversized item fails outright rather than throttling, replicas in a Global Table do not divide a table's throughput between them, and stream retention governs how long changes stay readable rather than whether writes are accepted.
Which design meets the item ceiling as a hard failure rather than as a gradual slowdown?
An unbounded list inside one item eventually crosses 400 KB and the write is rejected. A small key set concentrates throughput and throttles rather than failing outright, extra Regions raise cost rather than item size, and a scan-heavy pattern consumes capacity rather than breaking a size limit.
What does adaptive capacity change about the per-partition throughput ceiling?
Adaptive capacity moves throughput towards the partitions that need it, which absorbs uneven traffic without lifting what one partition can do. It does not remove the ceiling, does not apply asymmetrically to reads, and cannot spread a single key value over more than one partition, because the key is the routing decision.

Practice about 15 minutes, with paper

Practice 1working

A payments team stores transactions in DynamoDB. The partition key is the merchant identifier. Ninety percent of the volume comes from four large merchants, and the peak is 6,000 writes a second across the whole table. The table is provisioned far above that and requests are being throttled.

Show the arithmetic that explains the throttling, propose a key change, and say what the change costs the read path.

Hint

Work out how much of the peak lands on the busiest single key, then compare that with what one partition can absorb. The fix is always to give the key more distinct values, and the question is what those extra values break.

Show the worked solution
  1. Find the traffic on one key. Ninety percent of 6,000 writes a second is 5,400, spread across four merchant identifiers. Evenly split that is 1,350 writes a second per key, and real traffic is never even, so the largest is higher still.
  2. Compare with the ceiling. A partition absorbs about 1,000 write units a second. 1,350 is already above it, so at least the busiest merchants throttle continuously, whatever the table is provisioned for.
  3. Confirm the table-level number is a red herring. The other ten percent, 600 writes a second, is spread over many merchants and lands on many partitions, so the table's overall utilisation looks low. The console showing headroom and the application seeing throttles are the same fact.
  4. Change the key. Give the partition key more distinct values by combining the merchant identifier with something that varies per item - a date, or a small suffix chosen at write time. Four hot keys becoming, say, forty spreads 1,350 writes a second down to about 135 each, comfortably inside the ceiling.
  5. Say what it costs the read path. A single get by merchant is no longer a single get. Every read that used to name one key must now name, or iterate over, every variant of it, so the reading code changes, the request count per read rises, and any code path that assumed one item per merchant has to be found and fixed.

Sanity check. Your arithmetic should show a per-key figure above 1,000 before the change and comfortably below it after, and your cost should be paid by the reader rather than the writer. If your fix raised provisioned throughput instead of changing the key, re-read where the ceiling is: raising a table-level number does not raise a partition-level one.
