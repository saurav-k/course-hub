The retrieval pipeline is managed, and the vectors have five possible homes

working 6 min Capability keys managed-rag-pipeline and vector-store. · Bedrock Knowledge Bases

The one-minute version

  • A knowledge base is a managed retrieval pipeline: connectors to the sources, embedding, retrieval, and generation with citations back to the passage.
  • In its managed form, hybrid keyword and semantic search is always on, so exact-match terms are not lost to a purely semantic index.
  • The vector store underneath is a choice, not a fixture: a managed store, or one you already run - a search collection, a relational extension, a graph analytics engine, or an in-memory database.
  • S3 Vectors is a bucket type that stores and queries embeddings with strongly consistent writes, and integrates with both the knowledge base and tiered search.
  • What it costs: the enterprise search service that used to answer this need is in maintenance and closed to new customers, with knowledge bases named as the migration target.

1. The mechanism: what the managed pipeline does for you

2. The mental model: five homes for the same vectors

The enterprise search service that used to be the answer for "search our documents" is in maintenance and closed to new customers, and AWS names knowledge bases as the migration target. Material recommending it is describing an earlier state of the platform, so a new design should not start there.
The reframing Retrieval-augmented generation is a search problem with a model on the end. The quality of the answer is set by chunking, embedding and retrieval long before the model sees anything, which is why the managed pipeline is worth using: it makes those three consistent, and it leaves you the one decision that is genuinely yours - where the vectors live.

Check yourself

Retrieval practice

Answer from memory before revealing.

Users searching by exact product code get poor results from a semantic index. What addresses that?
Combining keyword matching with semantic similarity is what recovers exact terms, and the managed pipeline has it on by default. A different embedding model or chunk size may help marginally, and inference capacity has nothing to do with retrieval quality.
Which is not one of the vector homes named in this course?
Archive storage classes hold cold objects and have nothing to do with vector search. The vector bucket type, a vector search collection, the in-memory database and the graph analytics engine are all recorded vector homes, alongside the relational engine's extension.
What makes an answer from a knowledge base checkable?
Citations let a reader follow an answer back to the passage it came from, which is what makes it verifiable. Consistent writes and ingestion connectors affect freshness, and a guardrail filters content rather than evidencing it.

Practice about 15 minutes, with paper

Practice 1working

A company wants an internal assistant over 400,000 support articles and product manuals. Engineers already run a search cluster for the support portal and a relational database holding product metadata. Answers must be traceable to a source document, and searches by part number must work exactly.

Design the retrieval, choose the vector home with a reason, and name the requirement that is satisfied by the pipeline rather than by the store.

Hint

List what the team already operates before considering anything new. Then check each stated requirement against whether it is a property of the store or of the pipeline around it.

Show the worked solution
  1. Use the managed pipeline. Connectors, chunking, embedding, retrieval and citation are all things this team would otherwise build and then maintain, and none of them is where their product value lies.
  2. Choose the vector home from what exists. They already run a search cluster, so a vector collection there keeps the number of systems constant and puts the embeddings beside the keyword index the portal already uses. The relational database is a reasonable second choice if the metadata and the embeddings are queried together.
  3. Say when a new store would be right instead. If neither existing system is a good fit - or if the volume makes a purpose-built store cheaper - the vector bucket type is the low-operations option, with strongly consistent writes and direct integration into the pipeline.
  4. Handle the part numbers. Hybrid retrieval, which the managed pipeline runs by default, combines keyword matching with semantic similarity. That is why exact part numbers survive, and it is a property of the pipeline rather than of whichever store was chosen.
  5. Name the requirement satisfied by the pipeline. Traceability. Citations back to the retrieved passages come from the retrieval pipeline, not from the vector store, so changing the store later does not put that requirement at risk.

Sanity check. Your vector home should be a system the team already runs, and both stated requirements should turn out to be pipeline properties. If you chose a store because of a benchmark, note that neither stated requirement was about speed.
