Module 08 · Identity and access · Lesson 0800

Every request is judged by a fixed sequence of gates

working 8 min Capability keys iam-principals, iam-roles, iam-policy-language, permission-boundary and privileged-access. · IAM policy evaluation logic

The one-minute version

  • The default answer is implicit deny. Every allow has to be granted by something, and the root user is the one exception to the default.
  • An explicit deny anywhere is final. No later gate can undo it, which makes deny the strongest statement any policy can make.
  • The gates run in order: ceilings first, then the union of identity and resource policies in the same account, then the intersection of a permissions boundary and a session policy.
  • Cross-account is two evaluations, not one. The caller's side and the resource's side must each reach Allow independently.
  • What it costs: a boundary grants nothing on its own and can only take away, so a policy that looks correct in isolation can still produce no access at all.

1. The mechanism: the gates, in order

2. The gate that grants nothing

One nuance that decides real investigations: a resource policy grant made directly to a session ARN or a user ARN survives a boundary's implicit deny, while the same grant made to the bare role ARN does not. Two policies that look equivalent produce different answers, and the difference is which ARN form the resource policy names.

3. Across an account line, it happens twice

Two tools make this reviewable rather than theoretical. IAM Access Analyzer reports external access and unused access, validates policies, and generates a least-privilege policy from observed CloudTrail activity, so a policy can be narrowed from evidence rather than from guesswork (Access Analyzer). And a practical limit: a managed policy is capped at 6,144 characters, which is what eventually forces a large permission set to be split.

The reframing Do not read AWS authorisation as "who has permission". Read it as a request walking a fixed sequence of gates, where two gates add and two gates subtract. Every confusing outcome - a policy that grants nothing, a guardrail that breaks a partner integration, a deny nobody can override - is one of those four behaviours arriving where it was not expected.

Check yourself

Retrieval practice

Answer from memory before revealing.

A role has an identity policy allowing an action, and a permissions boundary that does not mention it. What happens?
A boundary intersects, so anything it does not allow is outside the effective permissions even without a deny statement. The first two answers treat the boundary as advisory, and the third invents an explicit deny where the boundary simply stays silent.
Which statement can never be overridden by a later gate in the evaluation?
An explicit deny ends the evaluation wherever it appears. Allows can be narrowed by a boundary or a session policy further down, and a ceiling that stays silent is an implicit deny, which is weaker than an explicit one and different in kind.
A resource policy in account B allows a role in account A, but the call fails. What must also be true?
Cross-account access needs both halves to reach Allow independently, so the caller's identity policy has to permit the action as well. Boundaries are attached by the account owning the principal, resource ownership is what makes this cross-account in the first place, and shared organisation membership is not required.

Practice about 15 minutes, with paper

Practice 1working

An analytics role in the data account must read one bucket in the platform account. The bucket policy allows the role's ARN. The role's identity policy allows the read. The call is denied. Investigation finds three more facts: the data account has a permissions boundary attached to the role that allows only actions on a different bucket, the platform account's organisation applies a resource control policy denying access from outside the organisation, and both accounts belong to the same organisation.

Walk the evaluation for both halves, say which gate produces the denial, and name the smallest change that fixes it.

Hint

Do the two halves separately and in the documented order. One of the three extra facts is a red herring, one is decisive, and one only matters if you get the first two wrong.

Show the worked solution
  1. Caller side, gate by gate. Default deny. No explicit deny is reported anywhere. Ceilings are not reported as blocking. The identity policy allows the read, so the union gate passes.
  2. Caller side, the intersect gates. The boundary allows actions only on a different bucket, so the requested action is outside the intersection. The caller side therefore reaches Deny, and it does so without any policy containing the word deny.
  3. Resource side, for completeness. The bucket policy allows the role. The resource control policy denies access from outside the organisation, and both accounts are inside it, so that policy does not apply here - the red herring.
  4. Name the deciding gate. The permissions boundary on the analytics role. Both halves had to reach Allow and the caller half did not.
  5. Name the smallest fix, and check it against the trap. Add the target bucket to the boundary, so the intersection contains the read. Do not widen the bucket policy: the resource side already allowed the call, and widening it would grant more access while fixing nothing. Note the ARN nuance as well - had the bucket policy named a session ARN rather than the role ARN, the boundary's implicit deny would have been survivable, which is exactly the kind of difference that makes two apparently identical setups behave differently.

Sanity check. Your answer should blame a gate that contains no deny statement, and your fix should change the data account rather than the platform account. If you widened the bucket policy, re-read which half of the evaluation was actually failing.
