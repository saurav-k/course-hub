The registry is where a container estate's supply chain either exists or does not

working 6 min Capability key container-registry. · Amazon ECR

The one-minute version

  • Elastic Container Registry is the private image registry every runtime in this module pulls from, and it authenticates with IAM rather than with a password somebody stored.
  • It scans on push, so a vulnerable image is found at the moment it enters the estate rather than at the moment it is deployed.
  • Replication copies repositories across regions and accounts, which is what stops a region's deployments depending on another region's registry.
  • Pull-through cache rules mirror an upstream public registry into your own, so a public outage or a rate limit stops being your outage.
  • What it costs: the cache has a real gap. Lambda cannot pull an image through a pull-through-cache rule, so one consumer needs the image pushed rather than cached.

1. The mental model: one supply point, three jobs

2. The mechanism: what a cached pull actually does

The reframing Scanning on push and caching on pull are the same idea applied at two boundaries: every image entering the estate should be examined once, at the door, rather than repeatedly at the point of use. That is why the registry, not the cluster, is where a container supply chain is actually governed.

3. What it costs: the consumer that cannot use the cache

Functions packaged as container images pull from ECR like anything else, with one documented exception: Lambda cannot pull an image through a pull-through-cache rule. An estate that standardised on cache rules for every base image therefore needs a real push into a repository for anything a function will run.

This is the kind of gap that survives a design review and fails at deployment, because the same image reference works for ECS and EKS and fails only for Lambda. Decide the rule once, estate-wide: base images that functions use get built and pushed, and cache rules cover only what containers pull.

The registry has a public face as well. ECR Public serves anonymous pulls from a gallery, which is how an image you publish becomes usable by people with no account of yours - and it is also, from the other direction, one of the upstream registries somebody else might be caching.

Check yourself

Retrieval practice

Answer from memory before revealing.

A public registry rate-limits your cluster during a deployment. Which ECR feature removes that dependency?
A cache rule mirrors the upstream image into your own registry on first pull and serves your copy afterwards, so the upstream leaves your deployment path. Scanning inspects images and changes nothing about where they come from. Replication moves your own repositories. IAM authentication changes how you prove identity, not who hosts the bytes.
Which consumer cannot pull an image through a pull-through-cache rule?
Lambda is documented as unable to pull through a cache rule, so images for functions have to be pushed into a repository. Both container runtimes and ordinary build jobs use cache rules normally, which is what makes this asymmetry easy to miss until a function deployment fails.
How often does a pull-through cache re-check the upstream registry for a given tag?
The rule re-checks upstream at most once a day per tag and serves your own copy in between, which is what keeps the upstream out of the deployment path. Re-checking every pull would put it straight back in. And the cache does refresh, so neither a delete-only nor a frozen model is right.

Practice about 10 minutes, with paper

Practice 1working

An estate deploys into two regions. Its pipelines currently pull base images straight from a public registry, push application images to one registry in one region, and run a mixture of ECS services, EKS pods and container-packaged Lambda functions.

Redesign the supply chain: name what you would change at each of the three boundaries - what enters, what is stored, what is consumed - and name the one workload that needs a different rule from the others.

Hint

Three boundaries, three ECR features. Then check your answer against the one documented consumer exception before you call it done.

Show the worked solution
  1. What enters: cache rules for every upstream. Replace direct pulls from the public registry with pull-through cache rules, so the first pull mirrors the image into your own registry and later pulls are served from your copy, re-checked upstream at most once a day.
  2. What is stored: scanning at the door. Scan on push means every image entering the estate is examined once, on arrival, rather than repeatedly at deployment, and it covers the cached upstream images as well as your own builds.
  3. What is consumed: replication into the second region. A single registry in one region makes the second region's deployments depend on the first region's availability. Replicating the repositories removes that cross-region dependency at start-up time.
  4. Fix the authentication story while you are here. ECR authenticates with IAM, so the pipelines and nodes stop holding a long-lived registry password and start using the role they already have.
  5. Name the exception. The container-packaged Lambda functions. They cannot pull through a cache rule, so their base images have to be built and pushed into a repository rather than covered by the estate-wide cache rule.

Sanity check. After your redesign, no arrow in the deployment path should start outside your own registry, and exactly one workload should have its own rule. If every workload has the same rule, you have not yet accounted for the function exception.
