Two versioned objects stamp every instance, and one of them stops at the region line

working 7 min Capability keys vm-images and instance-template. · Amazon Machine Images

The one-minute version

  • An Amazon Machine Image holds the operating system, the software and the block-device mapping an instance boots from. It belongs to one region and has to be copied to reach another.
  • A launch template holds everything else about the launch - image, type, network, user data - as a versioned object that scaling groups, fleets and direct launches all consume.
  • EC2 Image Builder is the pipeline that builds, tests and distributes hardened images, and its distribution step can update the launch templates that point at them.
  • The older launch configuration is being withdrawn in stages that depend on how old your account is and on how recent the instance type is, not on one announcement everybody sees.
  • What it costs: one image attribute, the one that forces the hardened metadata service, cannot be undone once it is set.

1. The mental model: a stamp and a form

The image is region-bound. An identifier that works in one region names nothing in another, so a multi-region estate copies the image and keeps a map of identifiers, and a template that hard-codes an identifier is a template that only works in one region. Images can also be shared with other accounts, which is what makes a central image-building account possible (Amazon Machine Images).

2. The mechanism: a pipeline that ends at the template

3. The template is the only forward path

AWS has two objects that look like a launch specification, and only one of them has a future. A launch template is versioned, is consumed by scaling groups, fleets and direct launches alike, and is the only one of the two that supports mixed purchase options and warm pools. The older launch configuration supports none of that.

Launch templateLaunch configuration
Versioned, so a fleet can roll forward and backImmutable, so a change means a new object
Consumed by scaling groups, fleets and direct launchesConsumed by scaling groups only
Supports mixed purchase options and warm poolsSupports neither of them
The go-forward path for every accountBeing withdrawn in stages

That withdrawal is worth understanding as a shape rather than as a fact to memorise, because it is the clearest example on the platform of a retirement that does not arrive as one announcement. Whether you can create a launch configuration at all depends on how old your account is; whether you can create one in the console depends on the same thing at a different threshold; and whether a given instance type works inside one depends on how recently that type launched (launch configuration retirement).

The reframing Two engineers in the same organisation can run the same command against the same region and get different answers, because the account's own age is an input. When a colleague says "that works for me", the useful next question is which account they were in, not whether they typed it correctly.

4. What it costs: the attribute you cannot take back

The instance metadata service is where an instance reads its own identity and its temporary credentials, and the hardened version of it can be required in two places: as an account-level default, or as an attribute baked into the image itself. Setting the image attribute is the stronger guarantee because it travels with the image. It is also irreversible for that image (configuring instance metadata options).

Irreversible means the image, not the instance. If some tool in your estate still speaks the older metadata protocol, an image baked with the hardened attribute will never work with it and cannot be edited back. Set the account-level default first, watch what breaks, and bake the attribute into the image only once nothing does.

Check yourself

Retrieval practice

Answer from memory before revealing.

A launch template works in one region and fails in another with an image error. What is the most likely reason?
An image belongs to one region, so its identifier is meaningless elsewhere until the image is copied and the new identifier is used. A missing type would raise a type error rather than an image error. And sharing governs cross-account access rather than cross-region identity, which is a different failure.
Which capability is available only through a launch template and never through a launch configuration?
Mixed purchase options and warm pools are template-only, which is the practical reason a design that wants both on-demand and reclaimable capacity in one fleet must use templates. The other three are ordinary launch parameters that both objects can express, which is what makes them convincing distractors.
What makes the launch-configuration retirement unusual compared with an ordinary service retirement?
The withdrawal depends on when your account was created and on how recent the instance type is, so two accounts see different behaviour on the same day. Existing configurations are not deleted, the staging is not regional, and nothing about it is opt-in - which is precisely why it surprises people.

Practice about 15 minutes, with paper

Practice 1working

A platform team bakes one hardened image on a schedule. It must reach three regions and every workload account in the organisation, and each workload's scaling fleet must pick it up without a human editing anything. The security team also wants the hardened metadata service enforced.

Write the object chain from base image to running fleet, name what happens at each region and account boundary, and say where you would enforce the metadata setting and why not in the other place.

Hint

Three boundaries appear in this problem: region, account, and the fleet's own reference to an image. Ask what object crosses each one, and remember which enforcement point can never be undone.

Show the worked solution
  1. Base image into a pipeline. An Image Builder pipeline takes the base image plus your hardening components, builds it and runs the tests you defined. Nothing has crossed a boundary yet.
  2. Cross the region boundary by copying. The pipeline's distribution configuration copies the image into each of the three regions. Each copy is a distinct image with its own identifier, so the estate now holds three identifiers for one logical version.
  3. Cross the account boundary by sharing. The same distribution step shares the images across the organisation, so workload accounts can launch from an image they did not build and do not own.
  4. Cross into the fleet by updating the template. The distribution configuration updates the launch templates to the new image, which creates a new template version. The scaling group references the template rather than the image, so this is the step that makes the fleet aware of the new build without anyone editing the group.
  5. Enforce the metadata setting at the account level first. The account-level default applies to new instances and can be changed if something in the estate still uses the older protocol. The image attribute is the stronger guarantee because it travels with the image, and it is irreversible, so it belongs at the end of the rollout rather than the beginning.

Sanity check. Your chain should contain three image identifiers for one build and exactly one new template version per region, and your enforcement answer should start at the reversible control. If your answer baked the irreversible attribute into the first build, ask what you would do on the morning a tool turns out to need the old protocol.
