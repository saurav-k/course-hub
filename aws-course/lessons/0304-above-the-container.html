A managed runtime hides this whole module, and one of them is no longer on offer

working 6 min Capability keys paas-web-runtime, static-site-hosting and service-mesh. · Elastic Beanstalk platforms

The one-minute version

  • Above the orchestrator sits a layer that takes application code and runs it, hiding the instances, the images and the scaling this module spent four lessons on.
  • AWS has three answers here and they are in three different states: Elastic Beanstalk is the classic path, the dedicated managed web runtime is closed to new customers, and Amplify Hosting covers git-driven web hosting.
  • The named successor for the closed one is not a new product. It is ECS Express Mode, which builds a service, a load balancer and scaling from a single call.
  • Between services, AWS is mid-transition: its Envoy-based mesh is discontinued, and the two successors are different products for the two orchestrators.
  • What it costs: a managed runtime hides layers rather than removing them. Beanstalk platform branches retire, so the platform version is a thing you maintain even when the servers are not.

1. The mental model: the same stack, drawn from above

2. Three answers, three states

AnswerStateWhat it is for
Elastic Beanstalk Available, still shipping platform releases Language platforms on EC2-based environments, with the underlying resources still yours to control
App Runner Closed to new customers Code or a container straight to an autoscaled web service. Existing customers continue; new designs use the named successor
Amplify Hosting Available Git-driven hosting for static and server-rendered sites on a CDN-backed edge, with a preview per branch

The successor named for the closed runtime is worth noting because it is not a fourth product. ECS Express Mode provisions a service, a load balancer and scaling from one call naming an image, so the replacement for "hand it code, get a URL" is the orchestrator from lesson 0300 with a shortcut on the front. AWS also points at Amplify Hosting rather than raw bucket hosting as the recommended path for static sites (S3 website hosting).

Beanstalk hides servers, not maintenance. Its platform branches retire on their own schedule and an environment left on a retired branch stops receiving platform updates (retiring platform versions). "Managed" moved the work from patching an operating system to tracking a platform branch; it did not delete it.

3. Between services: a transition, not an absence

AWS's Envoy-based service mesh is discontinued, and this is a place where saying it precisely matters. The capability has not left the platform - it has split into two successors aimed at the two orchestrators. AWS's own migration guidance sends ECS users to Service Connect and EKS users to VPC Lattice (AWS migration guidance, a vendor blog rather than a documentation page).

The reframing This module is a ladder and every rung trades reach for effort. The honest way to choose is not "how managed do we want to be?" but "which layer will we need to reach into, and how soon?" A team that will need node-level control within a year should not start above the orchestrator, however attractive the shortcut looks in week one.

Check yourself

Retrieval practice

Answer from memory before revealing.

A new project wants to hand AWS a container image and get an autoscaled web service. What should it use?
The dedicated runtime is closed to new customers, and ECS Express Mode is the successor AWS names, building a service, a load balancer and scaling from one call. Amplify Hosting is for git-driven web sites rather than arbitrary containers, and Beanstalk is available but is not the only remaining option, which is what makes that wording wrong.
Which statement about the service mesh situation on AWS is accurate?
The capability is mid-transition rather than absent: AWS sends ECS users to Service Connect and EKS users to VPC Lattice, which are two different products. Claiming there is no capability at all is the false-negative this course guards against, and neither successor is a built-in cluster add-on.
What maintenance does Elastic Beanstalk still leave with you?
Platform branches retire on their own schedule, so keeping an environment on a supported branch is recurring work. Operating-system patching, load-balancer sizing and image building are exactly the jobs Beanstalk takes over, which is why they read as plausible answers.

Practice about 15 minutes, with paper

Practice 1working

A four-person startup is choosing where to run three things: a marketing site rebuilt from a git branch on every merge, a single containerised web API, and an internal tool that talks to that API. A compliance requirement says traffic between the two internal services must be mutually authenticated.

Place each piece, then find the requirement that no runtime on this page satisfies on its own and say what you would tell the compliance reviewer.

Hint

Two of the three placements are easy. The third requirement is not about where a service runs at all, and the honest answer names what is missing rather than pretending a service covers it.

Show the worked solution
  1. Marketing site: Amplify Hosting. Git-driven, rebuilt per merge, served from a CDN-backed edge, with a preview per branch. It is exactly the shape the product is for, and it is the path AWS recommends over hosting a site directly out of a bucket.
  2. Containerised web API: ECS Express Mode. A single call naming an image produces the service, the load balancer and the scaling. The dedicated managed web runtime that used to be the obvious answer is closed to new customers, so it is not available to a new project.
  3. Internal tool: the same orchestrator. Putting it beside the API keeps one vocabulary, one registry and one deployment mechanism for a four-person team, which matters more at this size than any per-service optimisation.
  4. Find the unmet requirement. Mutual authentication between the two internal services. ECS Service Connect gives discovery, routing and metrics but explicitly does not do mutual TLS, so the requirement is not satisfied by choosing it.
  5. Tell the reviewer precisely. Do not say AWS cannot do mutual TLS - say that the ECS-native connectivity layer does not provide it, and that meeting the requirement means naming another mechanism explicitly and budgeting for it, rather than assuming it arrives with the runtime.

Sanity check. Two placements should be quick, one requirement should end up unmet by the runtime layer, and your answer to the reviewer should describe a boundary rather than an absence. If you concluded that AWS has no answer for service-to-service identity, you have overstated a scope decision into a platform gap.
