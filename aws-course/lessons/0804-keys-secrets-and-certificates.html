What you store is decided by who has to rotate it

working 8 min Capability keys key-management, hsm, byok-hyok, secrets-store, certificate-manager and certificate-authority. · AWS KMS concepts

The one-minute version

  • KMS never encrypts your data directly. It protects a data key, the data key encrypts the data, and that indirection is what envelope encryption means.
  • Keys come in three classes: AWS owned (the default, invisible to you), AWS managed (visible, rotated for you) and customer managed (yours, with opt-in annual rotation and an optional multi-Region form).
  • Beyond those sit imported key material and an external key store, which keeps keys entirely outside AWS and double-encrypts - and whose availability risk AWS's own documentation says usually outweighs the benefit.
  • Secrets Manager rotates; Parameter Store does not. That single difference is the selection rule, and AWS names rotating database credentials as the case for Secrets Manager specifically.
  • What it costs: a public certificate auto-renews only while it is associated with an integrated service, and an imported certificate never auto-renews.

1. The mechanism: the envelope

2. The custody ladder

CloudHSM is the separate answer for exclusive custody: single-tenant hardware security module clusters, with the current instance type certified to FIPS 140-3 Level 3. KMS itself is also backed by FIPS 140-3 Level 3 hardware and is multi-tenant, so the honest distinction is tenancy rather than certification level (CloudHSM FIPS validation). Check the certification status of the specific instance type you plan to use - the legacy one is moving to historical status.

3. Two secret stores, one deciding question

Secrets Manager is purpose-built for secrets: native rotation by a Lambda function or a managed rotator, staging labels that version a secret through a rotation, and cross-Region replication. Parameter Store is a hierarchical configuration store whose standard tier is free up to ten thousand parameters and whose SecureString type adds KMS encryption - but it has no native rotation (Parameter Store).

So the rule is short. If the value must rotate - and AWS names rotating database credentials explicitly - it belongs in Secrets Manager. If it is static configuration, or not secret at all, Parameter Store is the cheaper home and the hierarchy is genuinely useful (Secrets Manager).

4. Certificates, and the renewal that quietly does not happen

Internal certificates are a different product. AWS Private CA runs managed certificate authority hierarchies that issue, renew and revoke internal X.509 certificates for mutual TLS between your own workloads, and its root and subordinate authorities are separately billed resources. A short-lived certificate mode lowers the per-certificate cost for workloads that rotate constantly (AWS Private CA).

The reframing Every service on this page answers the same question differently: when this material has to change, who does the work. AWS-managed keys, Secrets Manager rotation and certificate auto-renewal all say "the platform". Imported keys, an external key store, Parameter Store and imported certificates all say "you" - and each of those four is a calendar entry somebody has to actually keep.

Check yourself

Retrieval practice

Answer from memory before revealing.

A public certificate in Certificate Manager expires despite the service being described as automatic. Why?
An imported certificate is outside the managed-renewal path entirely, and an unassociated one is too. Validation records matter for issue and renewal of certificates the service issued, a request quota would block issuing rather than renewing, and a private authority issues internal certificates rather than public ones.
Which requirement points at Secrets Manager rather than Parameter Store?
Rotation is the capability Parameter Store lacks, and rotating database credentials is the case AWS names specifically. Path hierarchies and the free standard tier are Parameter Store strengths, and SecureString already offers KMS encryption at rest.
What does an external key store change about a read of encrypted data?
Keys stay outside AWS, so every decryption depends on your external manager being reachable - the availability risk AWS's own guidance highlights. KMS remains in the path and double-encrypts, nothing is cached to remove the dependency, and automatic annual rotation is a customer-managed-key feature rather than an external-store one.

Practice about 15 minutes, with paper

Practice 1working

A payments team holds four things today: a database password in a configuration file, an API token for a partner that the partner rotates every ninety days, a public TLS certificate bought from a commercial authority and uploaded, and an encryption key for cardholder data that a regulator requires the company to generate itself.

Place each one, say who performs the rotation afterwards, and name the item whose placement adds a new failure mode you must design around.

Hint

Ask two questions of each item: does it change on a schedule, and who is allowed to generate it. The item that adds a failure mode is the one where the answer to the second question is not "AWS".

Show the worked solution
  1. Database password - Secrets Manager with rotation. It changes on a schedule and the platform can perform the change, so rotation moves from a calendar entry to a configured rotator, and staging labels keep the application working across the change.
  2. Partner API token - Secrets Manager, without automatic rotation. The partner controls the value, so nothing here can rotate it for you. It still belongs in the secret store for versioning, access control and audit, and the ninety-day cycle stays a human process on the partner's calendar rather than yours.
  3. Public certificate - request one from Certificate Manager instead of importing. An imported certificate never auto-renews, so continuing to upload the commercial one keeps the annual expiry risk. Requesting one and associating it with the load balancer or distribution puts it inside the managed renewal path.
  4. Cardholder key - imported key material in KMS. The regulator requires the company to generate the material, which is exactly what import is for. Everything above imported material on the custody ladder should be justified by a stated requirement, and none is stated here.
  5. Name the new failure mode. The imported key. Its material originates outside KMS, so its lifecycle is yours: if it expires or is deleted without a copy, the data encrypted under it is unreadable. That risk needs a written procedure before the first byte is encrypted, not after.

Sanity check. Two items should end up in the same service with different rotation owners, one should change product rather than move, and exactly one should carry a new failure mode. If you put the partner token in Parameter Store because you cannot rotate it, re-read what the store is for - access control and audit apply regardless of who turns the handle.
