Three per-request decisions that neither identity nor a firewall makes

working 7 min Capability keys zero-trust-app-access, verified-permissions and ai-safety-guardrails. · AWS Verified Access

The one-minute version

  • Verified Access decides, per request, whether a person reaches an internal application - evaluating identity and device posture with no VPN client involved.
  • Verified Permissions decides, per request, whether an action on a resource is allowed inside your application. It is a decision point, not a proxy: your code asks it and enforces the answer.
  • Both are written in Cedar, the open-source policy language, in terms of principal, action, resource and context.
  • Bedrock Guardrails decides whether words may pass - filtering harmful content, denied topics and sensitive information, on both the prompt and the model's response.
  • What it costs: a decision point that your application forgets to call is a policy that does not exist, so enforcement discipline is the design work here.

1. The mental model: three gates, one per layer

2. The mechanism: a decision point is not a proxy

What this buys is that authorisation logic stops being scattered through the application. Rules live in Cedar policies against a schema, they can be changed without a deployment, and they can be read by someone who does not read your language - which is what makes an authorisation model reviewable.

3. The third gate: what a model is allowed to say

The reframing All three are the same shape: a policy, evaluated per request, at a layer the network cannot see. Identity policies of module 08 protect AWS's own APIs; these protect yours. An application that has adopted the first and not the second has a beautifully governed cloud account and an authorisation model living in scattered conditional statements.

Check yourself

Retrieval practice

Answer from memory before revealing.

What happens if an application code path forgets to call the authorisation decision point?
A decision point is asked rather than interposed, so an uncalled decision is simply an unenforced policy. There is no proxy in this design, nothing fails closed on the application's behalf, and no queueing is involved.
Which requirement points at Verified Access rather than at identity policies?
Verified Access is about people reaching an application, judged per request on identity and device posture, with no VPN client. The other three are all decisions about AWS resources, which belong to the trust policies, guardrails and identity policies of module 08.
What does a guardrail screen?
Guardrails screen in both directions, which is what allows a response to be blocked or redacted even when the prompt was acceptable. Screening one side only would leave the other unprotected, and this is enforcement rather than after-the-fact auditing.

Practice about 15 minutes, with paper

Practice 1working

A company builds an internal assistant. Employees reach it from laptops and personal devices. It answers questions about documents, and each employee may see only the documents their team owns. It calls a hosted model, and legal is worried both about employees pasting customer data into prompts and about the assistant repeating something it should not.

Place each requirement on one of the three gates, name the failure mode of the middle gate, and say which requirement is not solved by any of them.

Hint

Sort the requirements by the layer each one lives at: reaching the thing, acting inside it, and what may be said. One requirement about people and devices belongs to the first gate, and one requirement is not a policy question at all.

Show the worked solution
  1. Reaching the assistant - the first gate. Verified Access evaluates identity and device posture per request, so the personal-device concern is expressed as a trust requirement rather than as a network rule. No VPN client is involved, and an identity provider integration is a prerequisite rather than an optional extra.
  2. Document-level access - the second gate. Each employee seeing only their team's documents is principal, action, resource and context, which is exactly what Cedar expresses. Write it as policy against a schema rather than as conditionals scattered through the retrieval code.
  3. Name the middle gate's failure mode. A code path that fetches a document without calling the decision point. The service cannot intercept anything, so the discipline is architectural: one place in the application asks, and everything that reads documents goes through it.
  4. Both of legal's concerns - the third gate. Guardrails screen the prompt, so customer data pasted in can be blocked or redacted, and they screen the response, so the assistant repeating something unacceptable is caught on the way out. Sensitive-information redaction is the specific mechanism for the first, and the content filters and denied topics for the second.
  5. Name what is not solved here. Whether the underlying documents were correctly labelled by team in the first place. Every gate on this page evaluates policy against attributes that already exist, and no policy language can fix a document whose ownership metadata is wrong - that is a data problem, and it belongs upstream.

Sanity check. All three gates should be used, legal's two worries should land on the same gate, and your final answer should be about data quality rather than about a missing service. If the device-posture requirement ended up as a network rule, re-read what the first gate evaluates.
