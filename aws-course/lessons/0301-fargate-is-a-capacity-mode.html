Fargate is not somewhere you deploy - it is how the nodes stop existing

working 6 min Capability key serverless-containers. · AWS Fargate

The one-minute version

  • Fargate is a capacity mode shared by both orchestrators, not a third orchestrator. You still write an ECS service or a Kubernetes deployment; Fargate only changes where it runs.
  • Each task or pod gets its own kernel-isolated environment, which is the isolation property that makes it different from packing containers onto a shared node.
  • On ECS it appears as a capacity provider, and there is a reclaimable variant with a two-minute eviction.
  • On EKS it appears as a profile, and it withdraws a specific list of Kubernetes capabilities that a manifest may already depend on.
  • What it costs: the withdrawn list is the whole trade. No DaemonSets, no privileged containers, no host ports, no GPUs, no EBS volumes, and no reclaimable variant on EKS.

3. What Fargate withdraws on EKS

This list is the reason a working manifest can fail to move onto Fargate, and every item on it is a capability a real cluster commonly uses (Fargate on EKS).

Not available on Fargate with EKSWhat that breaks in practice
DaemonSetsThe usual way a log shipper or agent is placed on every node, since there is no node to place it on
Privileged containersAnything that expected elevated access to the host
Host portsManifests that bind a port on the node rather than on the pod
GPUsEvery accelerated workload, which stays on node-backed capacity
EBS volumesPods that expected a block volume attached to their node
Fargate SpotThe reclaimable rate, which exists on ECS only
The reframing Every item on that list is a thing that assumed a node. Read it that way and it stops being arbitrary: Fargate did not remove six unrelated features, it removed the one object those six features are addressed to. A manifest ports onto Fargate cleanly exactly when it never mentions the host.
There is one more node-shaped assumption, and it is in identity rather than in the manifest. Newer EKS designs default to the pod-identity mechanism that does not need a per-cluster identity provider, but Fargate still requires the older service-account approach. Module 08 works through both; what matters here is that "we use the new way everywhere" is not true of a cluster with a Fargate profile in it.

Check yourself

Retrieval practice

Answer from memory before revealing.

A team says they are "moving from ECS to Fargate". What is wrong with the sentence?
Fargate supplies capacity underneath both orchestrators, so a service keeps its task definitions and only changes where tasks run. It is not a third orchestrator, it is available to ECS as a capacity provider, and neither service is global in the sense the last option implies.
A Kubernetes manifest runs a logging agent as a DaemonSet. What happens when its pods move to Fargate?
A DaemonSet places one copy per node, and Fargate has no node to place it on, so the mechanism is unavailable and the logging path has to be built another way. Nothing converts a DaemonSet into a per-profile or sidecar deployment, and the control plane never runs your workloads.
Where can you run containers on reclaimable Fargate capacity?
The reclaimable Fargate capacity provider exists on ECS and is unsupported on EKS, which is a real asymmetry between the two doors into the same capacity layer. Reclaimable capacity is certainly not EC2-only, since the ECS provider is exactly that on Fargate.

Practice about 15 minutes, with paper

Practice 1working

An EKS cluster runs four workloads: a stateless web API, a log-shipping agent deployed as a DaemonSet, a nightly batch job that would happily be interrupted, and an inference service that needs a GPU.

Decide for each whether it can move to a Fargate profile. For the ones that cannot, name the exact capability that blocks them and say what the workload runs on instead.

Hint

Go through the withdrawn list once per workload and ask the single question this page reduced it to: does this workload mention the host?

Show the worked solution
  1. Web API: yes. A stateless HTTP service names no host port, needs no privileged access, attaches no block volume and wants no accelerator. It is the shape Fargate was built for.
  2. Log shipper: no, blocked by DaemonSets. The mechanism places one copy per node and there is no node. The workload does not simply move elsewhere - the logging design changes, because the pods on Fargate still need their output collected by some other path.
  3. Nightly batch: yes for the compute, no for the discount. The job itself is an ordinary container, but reclaimable Fargate capacity is unsupported on EKS, so it runs at the full Fargate rate. If the discount matters more than the isolation, it belongs on node-backed capacity with reclaimable instances underneath.
  4. Inference service: no, blocked by GPUs. Accelerators are not available on Fargate, so this workload stays on node-backed capacity - a node group or Auto Mode - inside the same cluster.
  5. State the resulting cluster. A mixed cluster: a Fargate profile selecting the API's pods, and node-backed capacity for the accelerated service, the batch job and whatever logging path replaces the DaemonSet. That mixture is normal and is exactly why a profile selects pods rather than applying to the cluster.

Sanity check. Two of the four should move cleanly and two should be blocked by named capabilities, and your answer should end with one cluster rather than two. If you concluded that the cluster has to choose Fargate or nodes for everything, re-read what a profile does: it selects pods.
