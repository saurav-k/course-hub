There is no AWS platform object - every service is its own product

foundation 7 min The shape of the catalogue, and the skill that shape demands. · AWS Documentation

The one-minute version

  • You never program against "AWS". You program against a service, and each service is a separate product with its own API, its own quota pool, its own identity integration and its own idea of what a log is.
  • The account and the region from the last two lessons are the axes that every one of those products is scoped along. Quotas in particular are per service, per account, per region.
  • Because the catalogue grew service by service, several services answer the same question. Choosing between overlapping services is the defining AWS skill, and it is what the certifications test.
  • AWS gives you one shared frame for making those choices: the Well-Architected Framework, six pillars a design is argued against.
  • What it costs: there is no central switch for anything. Turning on logging, raising a limit or applying a standard is a per-service job repeated across the estate.

1. The mental model: a federation, not a product

The useful picture is a federation of separately built services that agree on a few things and disagree about everything else. Three of those disagreements are visible on the first day and shape every operational habit afterwards.

The limit that catches every new estate is the quota that starts near zero. EC2 quotas are counted in vCPUs per instance family, and a fresh account often begins with a small standard allowance and nothing at all for accelerated families (EC2 instance quotas). Check the quota before you size the fleet, not after the launch fails, and remember that quotas for genuinely global services are requested in us-east-1 whatever region you work in.

2. The mechanism: overlapping services, one constraint

A federation that grew for two decades has several answers to most questions. That is not untidiness to be corrected; it is the shape of the platform, and reading a requirement well enough to pick one answer is the work.

Modules 02 to 14 walk these rows one at a time. What matters here is the habit: read the constraint first, then reach.

3. The frame AWS argues designs in

The Well-Architected Framework is the vocabulary AWS reviews a design in, and it is worth knowing because the platform's own guidance, its review tooling and its certifications are all shaped by it. Six pillars: operational excellence, security, reliability, performance efficiency, cost optimisation and sustainability. The free Well-Architected Tool runs a review against them and lens libraries tailor the questions to a workload type.

What this certification tests The AWS Solutions Architect Associate blueprint does not have a services domain at all. It splits its scored content by quality, and the official guide states the weights: Design Secure Architectures 30 per cent, Design Resilient Architectures 26 per cent, Design High-Performing Architectures 24 per cent, Design Cost-Optimized Architectures 20 per cent (SAA-C03 exam guide). At professional level a whole domain appears that has no associate equivalent: Design Solutions for Organizational Complexity, weighted 26 per cent, which is Lesson 0101's tree in exam form (SAP-C02 exam guide).

4. What the federation costs

Every convenience you might expect from a single platform has to be assembled. There is no one place that turns on audit logging, no single limit page that governs the estate, and no guarantee that two services express the same idea the same way. That is why later modules keep returning to a small number of assembling services - Organizations for policy, CloudWatch and CloudTrail for telemetry, CloudFormation for shape - rather than to a platform setting.

Check yourself

Retrieval practice

Answer from memory before revealing.

A launch of a GPU instance fails immediately in a brand-new account. What is the most likely cause?
EC2 quotas are counted in vCPUs per instance family, and a new account commonly starts with nothing at all for accelerated families, so the request is refused before any hardware is consulted. Regions do carry accelerated capacity. There is no enable step for a family. And a second account would start from the same defaults, so vending one changes nothing.
Which of these is genuinely shared by every AWS service rather than decided per service?
The account and region grid is common to everything, which is why the first two lessons come first. Resource-based policy support varies by service and is looked up in a table, log streams and their defaults are each service's own decision, and quota pools are held per service rather than centrally.
The associate blueprint has no domain called "services". How is its scored content split?
The guide splits by quality - secure, resilient, high-performing, cost-optimised - and security carries the largest weight. Splitting by layer, by lifecycle or by workload type are all plausible taxonomies that other vendors' blueprints use, which is exactly why the distractors are worth reading twice.

Practice about 15 minutes, with paper

Practice 1foundation

A requirement arrives: "several dozen render workers must all read and write the same working directory, the directory grows and shrinks unpredictably during a job, and finished renders are published to a public web page."

Split this into the selection questions it actually contains, name the discriminating constraint in each, and say which of the storage services each constraint selects. Then say what you would still need to look up before committing.

Hint

There are two different storage jobs hidden in one sentence. For each, ask how many hosts read it at once and whether the reader is inside the network or on the public internet.

Show the worked solution
  1. Separate the two jobs. The working directory is one storage problem and the published output is a different one. Answering both with a single service is the usual mistake here.
  2. Take the working directory. The discriminating constraint is "several dozen workers all read and write the same directory". Shared read-write across many hosts eliminates block storage, which attaches to one instance at a time, so this is a managed shared file system rather than a volume.
  3. Take the growth pattern. "Grows and shrinks unpredictably" eliminates any answer that requires you to declare a size up front, and points at an elastic file system rather than a provisioned one.
  4. Take the published output. The reader is the public web and each render is a whole finished file, so this is object storage, which is addressed by key over HTTP rather than mounted.
  5. Name what is still unknown. Two things: the quota position in the account and region you intend to use, since limits are per service, per account and per region, and the throughput the render fleet actually needs, because the file-system choice within the family is decided by that number rather than by the capacity.

Sanity check. A correct answer names two different services for two different jobs and justifies each by a phrase quoted from the requirement. If your answer uses one service for both, re-read the sentence: "all read and write the same directory" and "published to a public web page" cannot be satisfied by the same access model.
