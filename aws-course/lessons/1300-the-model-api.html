The model is an API, and how you buy the inference is the design decision

working 6 min Capability key managed-model-api. · Amazon Bedrock

The one-minute version

  • Foundation models from several providers - Anthropic, Meta, Mistral and Amazon's own among them - are reached through one managed API rather than one endpoint per vendor.
  • There are three ways to buy inference: on demand, batch at half the on-demand rate, and provisioned throughput for reserved capacity.
  • Beyond those, the service names four inference tiers - Standard, Flex, Priority and Reserved - which is where latency and capacity expectations are chosen.
  • Guardrails from lesson 1104 attach here, screening the prompt and the response, and the same policy can be applied to models hosted elsewhere.
  • What it costs: batch halves the rate by removing the promise of a prompt answer, so the saving is only real for work that genuinely has no deadline.

1. The mechanism: three ways to buy the same inference

2. When capacity has to be certain

The content controls of lesson 1104 attach here rather than being a separate product: guardrails screen both the prompt and the response, and a dedicated API applies the same policy to models hosted outside this service. That is what lets one organisation-wide content policy cover models in more than one place.
The reframing Treat model inference as a capacity resource with three purchase options, exactly like compute. The temptation is to spend the design effort on model selection and prompt wording, and the durable decisions are which workloads have a person waiting, which can be batched, and which cannot tolerate a throttle.

Check yourself

Retrieval practice

Answer from memory before revealing.

Overnight classification of a million stored documents is running on demand. What should change?
Nobody is waiting for an overnight job, so batch halves the rate for exactly this shape of work. Provisioned throughput buys certainty rather than a discount, model choice is a quality decision, and a guardrail is a content control rather than a cost control.
What does provisioned throughput buy?
It is a capacity commitment: the reserved rate is available when the workload needs it. It is not a discount mechanism, it does not unlock a different catalogue of models, and it reserves capacity rather than making a single call faster.
Which statement about the managed model API is accurate?
One managed API fronts models from several providers, including AWS's own. Per-provider endpoints are exactly what it removes, the catalogue is not limited to AWS models, and guardrails are part of the service rather than a proxy in front of it.

Practice about 15 minutes, with paper

Practice 1working

A company runs three model workloads. A support assistant answers customers live, with a hard requirement never to be throttled during business hours. A nightly job summarises the previous day's tickets. A quarterly evaluation re-runs ten thousand prompts against several models to compare them.

Choose a purchase mode for each, say what each choice costs, and name the control that belongs on the live workload for reasons that have nothing to do with capacity.

Hint

Ask of each workload whether a person is waiting, and whether being throttled is acceptable. Those two questions separate all three, and the last part of the question is about content rather than cost.

Show the worked solution
  1. Support assistant - provisioned throughput during business hours. A person is waiting and the requirement explicitly forbids throttling, which is a capacity guarantee rather than a discount. The cost is the commitment itself: reserved capacity is paid for whether or not the peak arrives.
  2. Nightly summaries - batch. Nobody is waiting, so half the rate is available for the same work. The cost is that results arrive when they arrive, so anything downstream must tolerate a variable completion time rather than assuming the job finishes by a fixed hour.
  3. Quarterly evaluation - batch as well. Ten thousand prompts with no user waiting is the same shape as the nightly job. Its cost is the same, and it is a good example of work that is often run on demand out of habit rather than requirement.
  4. Check the boundary between the first two. If the support assistant has an out-of-hours mode where a slower answer is acceptable, that traffic can move to on-demand or batch. Splitting one workload by time of day is often more valuable than choosing a cheaper model.
  5. Name the control. A guardrail on the live assistant. It screens the prompt, which is where a customer might paste something sensitive, and the response, which is where the model might say something the company would not. That is a content decision and it belongs on the live path whatever the purchase mode.

Sanity check. Two of the three should be batch, and only the live workload should carry a capacity commitment. If you put the quarterly evaluation on provisioned throughput, ask who is waiting for it.
