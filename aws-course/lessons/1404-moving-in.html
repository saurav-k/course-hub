What is moving decides the tool

working 7 min Capability keys migration-service, online-transfer and db-migration-service. · Application Migration Service

The one-minute version

  • Three tools, chosen by what is moving: a whole server, a file system's contents, or a database.
  • Server migration uses the same continuous block replication as the recovery service, with wave planning and launch and post-launch templates - and an agentless path for VMware sources.
  • File transfer covers NFS, SMB, HDFS and object sources into object, file and managed file-system targets, with encryption, integrity validation and scheduling, and AWS names it the successor as the offline appliances retire.
  • Database migration works between any source and target where one side is on AWS, with an ongoing change-capture mode that is what makes a low-downtime cutover possible.
  • What it costs: the programme-tracking and discovery services are closed to new customers, so a new migration starts on the successor rather than on the tooling most guides describe.

1. The mental model: sort by what is moving

2. The mechanism: a wave, from discovery to cutover

3. Databases, where the cutover is the hard part

Two lifecycle facts a migration plan has to start from. The programme-tracking and dependency-discovery services are closed to new customers, with a named successor, so guides describing them are describing an earlier state of the platform. And there is no first-party VMware stack on AWS in this snapshot following the transition of that product to another vendor - so a plan that assumed running VMware natively here needs to be re-checked against the current offer rather than assumed.
The reframing These tools solve the easy half. The hard half is everything the previous thirteen modules were about: which account each workload lands in, which network it joins, what identity it runs as, how it is watched, and how it is deployed afterwards. A migration that copies servers into an ungoverned account has moved the problem rather than solved it.

Check yourself

Retrieval practice

Answer from memory before revealing.

A migration must move fifty terabytes from an on-premises NFS share into object storage. Which tool fits?
The transfer service reads NFS, SMB, HDFS and object sources and validates integrity on the way, which is exactly this task. Replicating the whole file server moves more than was asked, the database tool is for databases, and the offline appliance family is closed to new customers with this service named as its successor.
What makes a low-downtime database cutover possible?
Continuous change capture keeps the target current while the source stays live, so the cutover window is short. A faster full load still requires the source to be quiescent, schema conversion is a separate step for heterogeneous migrations, and instance sizing affects throughput rather than the cutover model.
Which statement about migration tooling is currently accurate?
The programme-tracking and discovery services are closed to new customers with a named successor, so a new programme starts there. There is no first-party VMware stack in this snapshot, and the offline appliance family is retiring with the online transfer service named in its place.

Practice about 15 minutes, with paper

Practice 1working

A company must leave its data centre within a year. It has 300 virtual machines on VMware, 90 terabytes on a file server, an Oracle database that must become PostgreSQL, and a second Oracle database that will stay on Oracle. The business will accept two hours of downtime per application, on a weekend, once.

Plan the migration, naming the tool for each of the four items, and say what has to be decided before the first server moves.

Hint

Sort the four by what is moving before naming any tool, and notice that the two databases are not the same kind of migration. The last part of the question is not about tooling at all.

Show the worked solution
  1. The 300 virtual machines - server migration, in waves. The VMware source means the agentless path is available, which removes the need to touch 300 guests. Group them into waves that can be tested and cut over together, sized so that a weekend window is enough for one wave.
  2. The 90 terabytes of files - the online transfer service. It reads the file-server protocols directly, validates integrity, and can be scheduled to run repeatedly so that the final synchronisation before cutover is small. Note that the offline appliance family that older plans would have used is retiring.
  3. Oracle to PostgreSQL - a heterogeneous database migration. Two exercises rather than one: convert the schema, then move the rows with a full load followed by ongoing change capture. Budget for the conversion separately, because it is the part that finds application code depending on engine-specific behaviour.
  4. Oracle staying on Oracle - a homogeneous database migration. The same service, without the schema-conversion exercise, and the same full-load-then-change-capture pattern to keep the cutover inside two hours.
  5. Say what must be decided first. Not a tool. The account and organisational-unit layout, the network the workloads join, the identity each will run as, what will watch them, and how they will be deployed afterwards. Every one of those is a module of this course, and deciding them after 300 servers have landed is far more expensive than deciding them before.

Sanity check. Your four tool choices should be three distinct services, with the two databases differing by a conversion step rather than by product. If your answer to the last part named a migration tool, re-read what a migration actually decides.
