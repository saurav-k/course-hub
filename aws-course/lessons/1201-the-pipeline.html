A pipeline moves one artefact across accounts and no credentials at all

working 7 min Capability keys cicd-pipeline and artifact-registry. · AWS CodePipeline

The one-minute version

  • AWS's own reference sequence is short: version control, orchestration, build, deploy, monitor - four services and the telemetry of module 10.
  • CodeConnections attaches a pipeline to GitHub, GitLab or Bitbucket without storing a secret, which is what lets a third-party source host slot in cleanly.
  • CodeBuild runs a buildspec and produces artefacts; CodeDeploy rolls them out; the orchestrator's job is to sequence, gate and promote.
  • The production pattern is an account per environment, with the pipeline assuming a role into each - so promotion crosses an account line rather than a folder.
  • What it costs: a package registry caches upstream packages, and a build still depends on upstream availability unless versions are pinned - and its build tokens expire in twelve hours by default.

2. Promotion across an account line

Two mechanisms scale this pattern. StackSets from lesson 1200 deploy one template across many accounts at once, and CDK Pipelines arrange stages into waves that deploy in parallel where the dependency graph allows. The account factory of lesson 0902 is what supplies the accounts these pipelines deploy into.

3. The registry, and the dependency it does not remove

The native source-control service has a status history worth knowing: it was closed to new customers and later reopened. Any material that says it is unavailable, or that assumes it is the default, may be describing a different point in that history - check the service's own document history before designing around either claim.
The reframing A pipeline's real product is not automation, it is a single path to production that leaves a record and holds no secrets. Judge a delivery design by two questions: how many credentials exist anywhere in it, and how many ways there are to change production. The good answers are zero and one.

Check yourself

Retrieval practice

Answer from memory before revealing.

How does a pipeline read from a third-party source host without a stored token?
A connection is the mechanism, and it exists precisely so no secret is stored. Storing and rotating a token is what the connection replaces, no role is federated into the source host, and mirroring would be an additional moving part rather than the supported path.
Why build once and promote the same artefact rather than rebuilding per environment?
Rebuilding produces a different artefact, so the tests that passed were not run against what reaches production. Cost is a minor consideration, artefacts can be shared across accounts, and the deployment service does not impose this.
A build fails when a public repository is unavailable, despite a caching package registry. Why?
A cache holds what it has already fetched, so an unpinned build asking for a version the domain has never seen still reaches upstream. Tokens govern build authentication rather than cache lifetime, upstream caching is exactly what the registry does for public packages, and it does not revalidate every request.

Practice about 15 minutes, with paper

Practice 1working

A team deploys by running a script from a laptop, using a long-lived access key, against a single account that holds development and production side by side. Their source is on GitHub. Builds occasionally fail because a public package repository is unreachable, and twice a change intended for development reached production.

Design the delivery path, naming what fixes each of the four problems, and say which fix is the one that makes the others meaningful.

Hint

Four problems: a credential, a boundary, an unreliable dependency, and a lack of a single path. One of them has to be fixed first or the others cannot be expressed.

Show the worked solution
  1. The access key - remove it with a pipeline. The pipeline runs with a role rather than a key, and nobody needs deployment permissions on a laptop at all. Attach the GitHub source through a connection so the source side stores no secret either.
  2. Development beside production - separate accounts. This is the fix that makes the rest meaningful: while both environments share an account, no permission boundary can prevent a development change reaching production, and no approval gate is more than a convention.
  3. The accidental production deployments - one path with a gate. With separate accounts, promotion into production is a stage that assumes a role there, behind a manual approval. There is then exactly one way to change production, and it leaves a record.
  4. The flaky builds - a package domain and pinned versions. Route builds through a managed registry so upstream packages are cached, and pin versions so every build asks for something already seen. Caching alone would not have fixed it, because an unpinned version can always be one the domain has never fetched.
  5. Say which fix is foundational. The account split. Every other improvement - the role, the gate, the single path - is expressible only once development and production are different accounts, which is the module 09 argument arriving in a delivery context.

Sanity check. Your design should contain zero stored credentials and exactly one route to production. If the account split appeared last in your answer, reconsider what an approval gate means when both environments share one set of permissions.
