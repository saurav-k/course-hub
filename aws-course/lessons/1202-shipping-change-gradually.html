Traffic shifting differs by compute type, and the rollback is the point

working 7 min Capability key progressive-delivery. · AWS CodeDeploy

The one-minute version

  • Every compute type shifts traffic differently: instances by in-place or blue-green replacement, functions by alias weights, containers by a second task set behind the balancer, and the API layer by a canary percentage on a stage.
  • The named configurations describe the shape of the shift - a canary holds a small share for a fixed time, a linear shift steps up on a fixed interval, and all-at-once does neither.
  • Hook functions run before and after traffic moves, which is where a smoke test belongs.
  • Rollback is what you are buying: deployments roll back on failure or on an alarm threshold, and reverting a function alias is a single call.
  • What it costs: configuration is a separate axis. Feature flags deploy gradually with validators and alarm-triggered rollback, and can be reverted for 72 hours after completion.

3. The rollback, which is what you are actually buying

Configuration has its own undo and its own deadline: a feature-flag deployment can be reverted within 72 hours of completing, and validators run before it is applied at all (reverting a configuration). After that window, going back means deploying the previous value as a new change - which is fine, and is a different operation with a different audit trail.
The reframing Do not choose a configuration by how cautious it sounds. Work backwards: how long does your monitoring need to notice this class of problem, and what share of users is acceptable during that window. Those two numbers pick the shape, and the alarm you attach is what makes the choice mean anything.

Check yourself

Retrieval practice

Answer from memory before revealing.

How does a function shift traffic between two versions?
Alias weighting is the function mechanism, and reverting it is a single call. A replacement environment is the instance blue-green pattern, a second task set is the container one, and a stage percentage belongs to the API layer.
A canary holds ten percent of traffic for five minutes. What must be true for that to be useful?
The exposure window is only protective if something notices within it, so the alarm's evaluation has to be faster than the shift. Template management restricts which configurations are available rather than making the canary useful, the seventy-two hours belongs to configuration revert, and one artefact is deployed rather than two.
Where does a smoke test belong in a gradual deployment?
A pre-traffic hook runs before any user is affected, which makes it the cheapest gate available. Build-stage tests run against no deployed environment, a post-traffic hook runs after exposure, and an alarm observes rather than tests.

Practice about 15 minutes, with paper

Practice 1working

A payments API runs as containers behind a load balancer, with a function handling asynchronous settlement and a rate limit held as configuration. Errors of the kind that matter show up in the error-rate metric within about four minutes. The business will tolerate at most a small minority of requests being affected by a bad release, and a previous incident was caused by a rate-limit value changed by hand.

Choose a shift shape for the API and for the function, place the rate limit, and say what has to be attached for any of it to work.

Hint

Start from the four-minute detection time and compare it against each shape's exposure window. Then ask what kind of change the rate limit actually is.

Show the worked solution
  1. Do the timing arithmetic first. Detection takes about four minutes. A canary holding ten percent for five minutes leaves roughly a minute of margin, which is thin but workable; a canary holding for fifteen minutes is comfortable. Anything shorter than the detection time offers no protection at all.
  2. The API - a container blue-green deployment with a canary shift and a bake time. A second task set runs behind the same listener, a small share of traffic goes to it, and the bake time keeps the old task set available until the shift is confirmed. If the deployment is managed from a template, check the available configurations, because custom ones are not permitted there.
  3. The function - alias weighting, with the same reasoning. A canary weight for at least as long as detection takes, and a pre-traffic hook running a smoke test before any settlement traffic is affected. Reverting is one call, which is the cheapest rollback on the page.
  4. The rate limit - a feature flag, not a manual edit. It is configuration, so it gets validators before it is applied, a gradual strategy, an alarm-triggered rollback, and a revert window of seventy-two hours after completion. That directly addresses the previous incident, which was a hand-edited value with none of those four.
  5. Say what must be attached. An alarm on the error-rate metric, wired to each deployment as its rollback trigger. Without it, all three changes above are slower deployments rather than safer ones, and somebody has to be watching a dashboard at the right moment instead.

Sanity check. Both shift windows should be at least as long as the four-minute detection time, and the rate limit should end up as a deployed configuration rather than as a code change. If your answer contains no alarm, nothing in it can roll back on its own.
