A data lake is a bucket, a catalogue and a grant model

working 7 min Capability keys data-lake, data-catalog and clean-rooms. · AWS Lake Formation

The one-minute version

  • The bytes live in S3, and that is the least interesting layer. What makes a bucket a lake is a catalogue that says what the objects mean and a grant model over that catalogue.
  • The Glue Data Catalog is the Hive-compatible metadata layer every engine here reads: Athena, Redshift Spectrum, EMR and Glue ETL all resolve tables through it.
  • Lake Formation grants access in database terms - tables, columns, rows and tags - rather than in object terms, and it does it on catalogue objects rather than on the bucket.
  • DataZone sits above both as a business catalogue with publish and subscribe workflows, and it neither stores data nor runs queries.
  • What it costs: the catalogue is Region-scoped and does not replicate, and cross-account access runs through Lake Formation and resource sharing rather than through plain IAM.

1. The mental model: three layers, only one of them storage

2. The mechanism: what happens when a query arrives

Two limits shape lake designs and neither is obvious from a diagram. Glue Data Catalogs are Region-scoped and do not replicate across Regions, so a multi-Region lake has as many catalogues as Regions and something has to keep them in step. And cross-account access flows through Lake Formation permissions and Resource Access Manager sharing rather than through a plain IAM policy, so the bucket policy you were about to write is the wrong instrument (AWS Glue).

3. Sharing outside the organisation

The reframing "We put it in S3" describes a storage decision and no more. A lake exists when the meaning of the objects and the right to read them are both written down somewhere an engine can consult. Skip either layer and you have not built a lake, you have built a directory that several teams read by convention.

Check yourself

Retrieval practice

Answer from memory before revealing.

An analyst must see every row of a table but only four of its twelve columns. Where is that expressed?
Lake Formation grants are expressed on Glue Data Catalog objects in table and column terms, which is the only layer that knows a column exists. S3 sees whole objects, object metadata is not consulted for authorisation, and IAM has no column-shaped resource to name.
A lake is being extended into a second Region. What follows for the Glue Data Catalog?
Catalogues are Region-scoped and do not replicate, so the second Region gets its own and keeping the two consistent becomes your problem. Bucket replication moves objects and not metadata, and nothing about a second Region promotes or relocates a catalogue.
Two companies want a joint audience analysis without either seeing the other's rows. Which service is built for that?
Clean Rooms is the multi-party form: tables stay with their owners and only rule-constrained queries run. DataZone governs discovery and approval inside an organisation's own estate, and both Lake Formation grants and a shared catalogue end with one party's principals reading the other party's rows, which is exactly what the requirement forbids.

Practice about 15 minutes, with paper

Practice 1working

A company keeps six years of clickstream data in one S3 bucket. Every team has read access to the bucket through an identity policy. Three things are now being asked for at once: analysts in a different account need one table, the privacy team needs the email column hidden from everyone outside marketing, and a product manager wants to find out what tables exist without asking an engineer.

Say which layer answers each request, and name the single change to the current setup that has to happen before any of the three is possible.

Hint

Write down which layer knows about each object in the requests: a bucket, a table, a column, an asset description. The prerequisite is the layer that none of the three requests can be expressed in.

Show the worked solution
  1. Name the prerequisite first. Nothing here is expressible today, because there is no catalogue. A bucket with an identity policy has no tables, no columns and no assets - so the first change is registering the data in the Glue Data Catalog so the other layers have something to point at.
  2. Cross-account access - Lake Formation plus resource sharing. Not a bucket policy. Cross-account catalogue access flows through Lake Formation permissions and Resource Access Manager sharing, which is also what keeps the grant to one table rather than to the prefix.
  3. Hiding the email column - a Lake Formation column grant. The grant is made on the catalogue table and every engine that resolves the table through the catalogue inherits it. Tag-based access control is worth reaching for here if the same rule applies to many tables, so that new tables inherit the rule rather than needing a new grant each time.
  4. Discovery for the product manager - DataZone. A business catalogue with publish and subscribe workflows is what lets a non-engineer find an asset and request access through an approval rather than through a ticket. Remember that it stores nothing and runs nothing, so it is a layer over the catalogue rather than a replacement for it.
  5. Then remove what made the requests impossible. The blanket bucket read for every team. While it exists, a column grant is advisory: anyone can bypass the catalogue and read the underlying objects directly.

Sanity check. Your answer should name three different layers for the three requests, and the prerequisite should be the catalogue rather than any of the three. If your last step did not remove the direct bucket access, the column-level rule you just designed does not actually hide anything.
