What the platform emits is about the platform

working 8 min Capability keys telemetry-agent, profiler, managed-prometheus and network-diagnostics. · AWS Distro for OpenTelemetry

The one-minute version

  • Platform telemetry describes the platform. Your application's own behaviour is instrumented by you, and the producer side has converged on OpenTelemetry.
  • Two agents matter: the OpenTelemetry collector distribution, which is actively released, and the unified CloudWatch agent, which collects logs, metrics and traces plus StatsD, collectd and OTLP.
  • Application Signals is the application monitoring layer built on that foundation - zero-code auto-instrumentation, golden metrics, service level objectives and a service map - and only the OpenTelemetry route yields unsampled metrics.
  • For a Kubernetes-shaped estate, Managed Service for Prometheus stores metrics in a workspace queried with PromQL, usually paired with managed Grafana.
  • What it costs: several honest questions have no stream at all, and two of them - reachability and stated network intent - are answered by analysing configuration rather than by watching traffic.

1. The mechanism: one producer standard

Managed Service for Prometheus is the alternative metric store for estates that already think in PromQL. Its workspace is the unit of ingestion, query and access control at once; collection can be an AWS-managed scraper against a Kubernetes cluster or your own collectors remote-writing in; and its rules are Alertmanager-compatible (Managed Service for Prometheus). It is usually paired with managed Grafana for dashboards.

2. Some answers come from configuration, not traffic

3. The questions with no stream

The last of those three shapes real designs. There is no automatic exception-grouping service: log metric filters and application monitoring will surface an error rate, and neither deduplicates stack traces into tracked issues. A team that expects that capability from the platform will build it themselves or buy it, and it is better to decide that deliberately than to discover it during an incident.
The reframing Observability here is assembled from three sources with different owners: what AWS emits about itself, what you emit about your application, and what can only be derived by analysing configuration. Knowing which of the three a question belongs to is faster than searching for a service, and for a few questions the honest answer is that none of the three covers it.

Check yourself

Retrieval practice

Answer from memory before revealing.

Where do policy denials appear?
Denials are ordinary management events carrying an access-denied error code, so finding them means filtering the general audit stream. There is no separate denial stream, flow logs record network flows rather than authorisation outcomes, and guardrail policies keep no evaluation history of their own.
A team must confirm an instance can reach a database before the workload is deployed. What answers that?
Reachability Analyzer evaluates route tables, security groups, network ACLs and gateways without sending a packet, so it answers before anything is running. The other three all require live traffic or a running workload, which the requirement rules out.
Which capability does AWS not provide as a service in this inventory?
There is no automatic exception-grouping service - error rates are surfaced, and stack traces are not deduplicated into issues. Zero-code instrumentation, a managed Prometheus store and reachability analysis are all present.

Practice about 15 minutes, with paper

Practice 1working

A team is standardising observability for twelve services, half on Kubernetes and half on serverless functions. Four questions must be answerable: which release introduced a latency regression, which recurring exception is hurting most users, whether a new subnet can reach the shared database, and who approved a permission change last month.

Assign each question a source, name the instrumentation decision that covers the first two, and identify the question this platform does not answer as asked.

Hint

Sort the four into the three sources from the reframing before naming any service. One of the four falls outside all three, and one is answered without any telemetry at all.

Show the worked solution
  1. Latency regression by release - your own instrumentation. Instrument with OpenTelemetry and use the application monitoring layer's golden metrics and service level objectives. Note the useful detail: the OpenTelemetry route yields unsampled metrics, so a regression that affects a small share of requests is still visible even though traces are sampled.
  2. Name the instrumentation decision. One standard for all twelve services - OpenTelemetry, through the collector distribution - with the unified agent on the hosts that need host-level collection. The Kubernetes half can additionally scrape into a Prometheus workspace if the team already thinks in PromQL, which is a storage choice rather than a second instrumentation.
  3. Reachability of the new subnet - configuration analysis. Reachability Analyzer answers before anything runs and names the blocking component, so this needs no telemetry and no deployment.
  4. Who approved a permission change - the platform's own stream. A permission change is an API call, so it is in the audit stream, provided a trail was delivering it a month ago. This is where lesson 1001's default column decides whether the question is answerable at all.
  5. Name the question that is not answered as asked. The recurring exception. Error rates are available and stack traces are not grouped into tracked issues by any service here, so the team must either build that grouping on top of their logs or adopt a tool for it - and that decision belongs in the standardisation, not in the next incident.

Sanity check. Your four answers should use three different sources plus one gap. If you answered the exception question with a metric filter, re-read what was asked: a rate is not a grouping, and the question was which exception hurts most users.
