Glossary

92 terms Every term this course introduces, linked to the page that develops it. Print it and cover the right-hand column.

TermWhat it means here
Additive-only evolution Promising that the published surface only ever grows, so no caller ever migrates. A real versioning scheme with a real price, paid at design time: every field you regret stays.
Age The time since a response was generated by, or last validated with, the origin server. Not the time since this cache stored it, which is why a response can arrive already stale.
Allow field The response field listing the methods a target resource currently supports. RFC 9110 makes it a MUST on a 405, permits it anywhere else, allows an empty value, and forbids a proxy from modifying it.
Ambiguous failure A timeout that a client cannot resolve: the request may never have arrived, or the response may have been lost. The two histories need opposite actions and produce identical evidence.
Backtracking The walk undoing a step when the literal branch it took first turns out to be a dead end. The cost of trying the more specific pattern first, and bounded by the depth of the path.
Backward compatibility New code making sense of data written by the version already deployed, including everything already sitting in a queue, a log or a table. One of the two directions a rolling deploy exercises at once.
Boundary parsing A check at the edge that returns a value of a different type rather than a boolean, so the knowledge it earned travels with the value and cannot be lost by the next function.
Breaking change A change that makes a call correct yesterday fail today. Removing or renaming is the obvious form - narrowing what an existing field accepts is the form that looks like a bug fix.
Cache key The name an entry answers to, and a claim that everything under that name changes at the same moment. RFC 9111 builds the protocol's own from the method and target URI, with Vary adding a secondary key.
Cache stampede Every reader of a hot entry missing at once when it expires, and each one querying the store for the same answer. Also called a thundering herd. The recomputation window admits the herd and the herd lengthens the window.
Cache-aside The read pattern in which the application, not the cache, goes to the store on a miss and writes the answer back. Also called lazy loading, or a look-aside cache. It is what keeps the cache an optional dependency.
Cacheable method A method whose responses may be stored and reused for a later request. RFC 9110 defines caching semantics for GET, HEAD and POST, and notes that most implementations support only the first two.
Client error (4xx) The status class saying the client seems to have erred. Repeating the request unchanged gets the same answer, so a 4xx is not a retry signal and not an availability signal.
Cold start (cache) An empty cache after a restart, a scale-out or a failover, during which the store receives the full read rate it was not provisioned for. A scheduled, normal state, and the one the service least survives.
Conditional request A request carrying a precondition on a validator, so the server acts only if the representation still matches. If-None-Match gives a cheap re-check; If-Match gives optimistic concurrency control.
Content negotiation The client stating preferences in the Accept family and the server choosing. Advisory in one direction and authoritative in the other, with Vary naming the request fields the choice depended on.
Credentialed request A cross-origin request carrying cookies or an authorization field. The page opts in, the server must allow credentials explicitly, and a wildcard origin is refused rather than expanded.
Cursor pagination Continuing a collection from the sort key of the last row delivered, so the position is a value rather than a count. Concurrent writes elsewhere in the collection move nothing it depends on.
Custom method An action no standard method expresses, written after a colon on the resource name, as in orders/42:cancel. POST when it has side effects, and used only where a standard method will not do.
Delete-on-write Removing the cached entry after the store is updated, leaving the next reader to refill it. Preferred over replacement because deletes are idempotent, so a retried, delayed or reordered one is still harmless.
Derived key A key built from a question rather than from an identity - a list page, a search result, a rendered fragment. The writer cannot enumerate the derived names its change made wrong, which is where invalidation becomes a design.
Eviction An entry removed because the cache ran out of memory rather than because its lifetime elapsed. Governed by a policy: a volatile- policy considers only keys carrying an expiration and evicts nothing when none do.
Field number The integer that identifies a field in the protobuf wire format. It is what a reader matches on, so it can never change once a message type is in use and must never be reused.
Forward compatibility Old code making sense of data written by a newer version. Unavoidable during a rolling deploy, because instances of both builds are producing and consuming at the same time.
Freshness lifetime How long the origin believes a representation will not change in a way that matters. Set by s-maxage, then max-age, then Expires minus Date, and guessed heuristically when none is present.
Header field A name and value pair carrying what the method and target cannot say. A flat, extensible namespace of independent statements, readable by an intermediary that never parses the body.
Header versioning Carrying the version out of band, usually date-named and defaulted or pinned per account. The caller pays nothing until they opt in, and the provider keeps every old behaviour alive.
Hit rate The share of reads the cache answered by itself. Its complement is the quantity that sizes the store, which is why two hit rates that sound alike can differ by an order of magnitude in database load.
HTTP method The token saying what action is asked of the target. A request for a defined semantic rather than a hint, which is why moving the verb into the path loses every guarantee it carried.
Idempotency fingerprint A digest of the request payload stored beside an idempotency key, compared on every arrival. It is what separates a genuine retry from the same key sent with a different body.
Idempotency key A client-generated value that lets a server recognise a retry of a non-idempotent request. The server stores the first result beside it and replays that result rather than repeating the work.
Idempotent method A method whose intended effect from several identical requests equals the effect of one. PUT, DELETE and the safe methods. It compares server state, not the responses returned.
Immutable key A name that carries the content or a version, so a change produces a new name rather than a wrong entry. Invalidation becomes a rename: nothing is found, nothing is deleted, and the old entries expire unread.
Interim response (1xx) A response reporting connection status or progress before the final one. It carries no content, and a request may have several of them followed by exactly one final response.
JSON number A decimal literal with no declared precision. RFC 8259 names the interoperable integer range as -(253)+1 to 253-1; beyond it a binary64 parser rounds, with no error raised.
JSON value types The six kinds RFC 8259 allows: object, array, number, string, boolean and null. There is no seventh and no extension point, so every domain type is carried by one of them under a convention.
Layer A named unit of responsibility on the request→response spine. Transport, HTTP shape, routing, and your code; a framework hides a layer, never removes it.
Lease (cache) A token the cache issues on a miss and verifies on the matching set, refusing the store if a delete invalidated it meanwhile. It closes the stale-set race by making a fill conditional on nothing having happened to the key.
Media type The type and subtype token naming both a data format and how a recipient should process it. Carried as a fact in Content-Type and as a preference in Accept.
Message body The optional fourth part of a request. Its presence is a property of the method and the framing, so a request with no body is complete rather than truncated.
Method dispatch Selecting a handler by the request method as well as the path. An exact token comparison, placed in front of the path walk because it discards most of the route table for the price of one equality.
Method Not Allowed (405) The status saying the method is known to the origin server but not supported by this target resource. It asserts the resource exists, which is the fact a 404 withholds.
Middleware A component that wraps the thing after it, acting as an application to the server above and as a server to the application below. Wrapping is what gives it a pass on the way in and a pass on the way out.
Middleware chain Middleware composed by nesting rather than queueing. Registered first means outermost, so the registration order is the request order and the exact reverse of the response order.
Miss penalty The extra cost a read pays when the cache has nothing: the ask, the query and the write-back, three trips where no cache would have cost one. It is why a cache makes most reads faster and the rest slower.
Mount path The prefix an inner router was reached through, kept aside rather than discarded so the inner router can build correct URLs. WSGI's SCRIPT_NAME and Express's req.baseUrl.
Mounting Registering one router inside another under a path prefix. Possible with no new machinery, because a router is itself a handler and nothing above it can tell the difference.
Not Found (404) The status saying the origin server found no current representation for the target, or is not willing to disclose that one exists. It says nothing about whether the absence is permanent.
Offset pagination Continuing a collection by a count of rows to skip. One insert or delete before the reader's position shifts everything after it, so the next page repeats or skips items.
Page token The encoded cursor a caller sends back to continue a collection. Published guidance requires it to be opaque and unparseable, and requires the other request parameters to match the call that issued it.
Path parameter A named hole in a path pattern standing for one whole path segment. It ends at the next literal slash, so a value containing a slash needs a multi-segment hole or an explicit converter.
Path pattern The shape a route matches paths against: a sequence of segments, some literal and some named holes. A hole must be a full segment, so a hole glued inside a literal segment is not a pattern.
Path versioning Putting the version in the URI, so it is part of the resource identity, visible in every log and cached separately. The caller pays by rewriting URLs and the provider by running both surfaces.
Prefix stripping Removing the mount prefix from the path before the inner router matches, so its patterns are written without it. Go's StripPrefix copies the request and answers 404 when the prefix is absent.
Prefix tree The structure a router compiles its patterns into: host, then method, then consecutive path segments, one level each. Shared prefixes are shared nodes, so a match costs one lookup per segment.
Preflight request An OPTIONS request the browser sends unasked, naming the method and fields the real request will use, so permission is obtained before a request with effects is sent.
Proactive negotiation The client sending preferences in the Accept family and an algorithm on the server choosing from the representations it has. Advisory: a user agent cannot rely on a preference being honoured.
Problem details document An application/problem+json body carrying type, status, title, detail and instance, plus any members the problem type defines. The machine-readable half of a failure the status code can only classify.
Problem type The URI identifying a kind of failure, and the member a client branches on. An identifier rather than a location, and absent it defaults to about:blank, meaning the status code is the whole story.
Published surface Everything a caller can observe and rely on, whether or not you meant to offer it: field names, status codes, error wording, identifier shapes. A promise nobody wrote down is still a promise.
Quality value The q parameter on a media range, expressing relative preference. Where several ranges match one type the most specific wins, so a full type beats type/* and type/* beats */*.
Query string The non-hierarchical component of a URI, after the question mark. Part of the identifier and part of the cache key, and reachable by the handler but never by the router.
Read-through The read pattern in which the loader is registered with the cache, so every read goes through it and the application never learns whether it hit. A better abstraction and a worse dependency than cache-aside.
Representation One concrete rendering of a resource, in a particular media type, language and encoding. A single URI can have several, and the response has to say which one it sent.
Representation metadata The fields describing the representation carried in this message rather than the resource behind it: Content-Type, Content-Length, Content-Encoding, Content-Language.
Request target The components of the parsed target URI, sent so a recipient can identify the resource the client meant. The fragment is excluded, so a server never sees it.
Reserved field number A protobuf field number promised never to be used again, declared so the compiler refuses a reuse. The only part of the compatibility rule set a build can enforce.
Resource Whatever you are willing to give a stable name and a representation. Not a table and not a class: HTTP separates identifying a resource from the semantics of the request, which live in the method.
Route A registered pair of a method token and a path pattern, with the function to call. Compiled once at registration, so a malformed pattern fails at startup rather than on an unlucky request.
Route precedence The rule deciding between two patterns that both match. The more specific one wins, meaning the one matching a strict subset of the other's requests; when neither does, the two conflict.
Safe method A method whose semantics are essentially read-only: the client neither requests nor expects a state change. GET, HEAD, OPTIONS and TRACE. Every safe method is also idempotent.
Same-origin policy The browser rule that script on one origin may not read a response from another unless that origin permits it. Enforced in the browser, so a non-browser client is unaffected.
Schema-first Writing the message definition before the handler and generating both ends from it, so the shape, names and types are checked by a build rather than remembered by a reviewer.
Serialization The mapping between your program types and a format's small type system, in both directions. It is generated from a declaration on each side, and neither side can check the other.
Server error (5xx) The status class saying the server erred or could not perform the method. The request may be valid, so a retry with backoff is meaningful, and this is the class an availability alert fires on.
Short circuit A middleware answering the request itself instead of calling the next link, so nothing nested inside it runs. The mechanism behind every authentication gate and rate limiter.
Simple request A cross-origin request the browser sends without a preflight and judges afterwards: GET, HEAD or POST, only CORS-safelisted fields, and one of three permitted content types.
Stale set A reader storing a value it fetched before a write replaced it, so the entry is wrong after the write already removed it. Caused by the read path rather than the write path, so no ordering of the writer's steps prevents it.
Staleness window How long a reader may see a value that is out of date. Every caching design has one whether or not it states it, and a lifetime is what bounds it when the invalidation message is lost.
Stated non-promise Writing down what a caller may not rely on, so an accidental promise becomes a documented reservation. The cheapest design act available and the one most often skipped.
Status class The first digit of a status code, which every client must understand. An unrecognised code is treated as the x00 of its class, which is what keeps the status space extensible.
Sunset The response header naming the date a resource is expected to stop responding. It travels with Deprecation, which names the date deprecation takes effect, and it may never be the earlier of the two.
Surrogate key A tag attached to an entry when it is stored, so the cache can maintain a reverse index and one purge can remove every entry carrying it. The only mechanism that solves the derived-key problem outright.
Trusted type A type that cannot be constructed in an invalid state, produced by the boundary and accepted by everything downstream. A function taking one states its precondition in its signature.
Uniform interface REST's central distinguishing feature: identity, methods and their guarantees agreed once for the whole web, so caches, proxies and clients act correctly without reading your documentation.
Unknown field A field a parser meets and its schema does not define. Proto3 keeps it and writes it out again, which is what lets a middle hop lag the schema without losing data.
URI template A syntax describing a URI space with expressions expanded from variables. RFC 6570 gives the path and the query different operators, so the split between them is encoded in the grammar.
Validator A compact token for the state of a representation: an ETag the server alone interprets, or a Last-Modified date. Sent back in a precondition, it turns a refetch into a 304.
Wire format The grammar two programs both parse, and the only layer of a serialized message with a specification behind it. It decides valid or not, and never what the bytes mean.
Write-around Updating the store and leaving the cached entry untouched, so the caller waits for the store alone and the entry stays wrong until its lifetime runs out. What a service has when nobody changed the write path.
Write-back Acknowledging a write once the cache holds it and flushing to the store later, so between the two the authoritative copy lives in the cache. Also called write-behind. An eviction is enough to destroy an acknowledged write.
Write-through Updating the store and the cached entry in the same request, so the entry is never stale. It costs two trips on every write and fills memory with answers nobody reads.
