A container is an ordinary process the kernel tells a smaller story to

working 8 min How two instances of a service come to be genuinely identical. · namespaces(7)

The one-minute version

  • There is no guest kernel and no hypervisor. A container is a process on the host kernel with two features applied.
  • A namespace wraps a global resource so the process appears to have its own copy of it: its own process table, its own network stack, its own mounts.
  • A cgroup puts processes in a hierarchical group whose resource use is limited and accounted, which is where a CPU and memory limit come from.
  • The image is a content-addressed stack of filesystem changesets, so an instance is identical to another because it is the same digest, not because it was built the same way.
  • What it costs: the isolation boundary is the host kernel's system-call surface, and the process runs as PID 1, which changes what signals reach it.

1. The mental model: two kernel features, no second kernel

A namespace decides what the process can see

The kernel's own definition is the clearest one available: "a namespace wraps a global system resource in an abstraction that makes it appear to the processes within the namespace that they have their own isolated instance of the global resource". There is one process table on the machine, and a PID namespace makes a process see a table containing only itself and its children. There is one network stack, and a network namespace gives it its own devices, addresses and ports, which is why two containers can both listen on port 8080.

The man page lists eight kinds and each isolates one named thing: Cgroup isolates the cgroup root directory, IPC isolates System V IPC and POSIX message queues, Network isolates devices and ports, Mount isolates mount points, PID isolates process IDs, Time isolates the boot and monotonic clocks, User isolates user and group IDs, and UTS isolates the hostname. Nothing on that list is a machine. Every one of them is a view of something the host already had.

A cgroup decides what the process may use

Seeing less is not the same as being bounded. That is the other feature: control groups are a "Linux kernel feature which allow processes to be organized into hierarchical groups whose usage of various types of resources can then be limited and monitored", with per-resource controllers doing the work, including limiting the CPU time and memory available to a group and accounting for what it used. The hierarchy has one rule worth carrying: limits set higher up cannot be exceeded by descendants, so a nested group can only ever be more constrained than its parent.

2. The mechanism: the image, and why it is a stack

Layers, digests and interchangeability

The OCI image specification defines four things: an image manifest, which describes the components of an image, an optional image index, which is an annotated list of manifests, filesystem layers, each "a changeset that describes a container's filesystem", and an image configuration, "a document determining layer ordering and configuration of the image". The manifest names each layer by its content-addressable identity, which is the property lesson 1302 actually needed. Two instances are the same instance when they run the same digest, and that is checkable rather than believed.

The stack has a build-time consequence that decides how long your pipeline takes. Docker's documentation states it plainly: "if a layer changes, all other layers that come after it are also affected", and those downstream layers must be rebuilt "even if they wouldn't build anything differently". So a Dockerfile that copies the source before installing dependencies rebuilds the dependency install on every commit, and one that installs first reuses it until the manifest changes.

Building in one image and shipping another

The compiler, the package manager and the test dependencies are needed to produce the artefact and are liabilities in the thing you deploy: more bytes to move, and more installed software to keep patched. Multi-stage builds solve it structurally rather than by cleanup. Each FROM starts a new stage, COPY --from takes named files out of an earlier one, and only the final stage becomes the image, so "none of the build tools required to build the application are included in the resulting image".

Dockerfile · the toolchain builds the binary and is then left behind
FROM golang:1.24 AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download          # cached until the manifest changes
COPY . .
RUN go build -o /out/api ./cmd/api

FROM gcr.io/distroless/static
COPY --from=build /out/api /api
ENTRYPOINT ["/api"]

3. The trade-off: one kernel, and your process is PID 1

The shared kernel is the whole economy of containers and it is also the boundary. A container's isolation is enforced by kernel code that every container on the host shares, so the attack surface is the system-call interface rather than a hypervisor, and a kernel flaw is a flaw in the wall between tenants. That is a reason to run mutually distrusting workloads on separate kernels, and not a reason to avoid containers for your own fleet.

The second cost is smaller and bites sooner. Your process is the first in its PID namespace, which makes it that namespace's init, and init has special signal semantics: "only signals for which the 'init' process has established a signal handler can be sent to the 'init' process by other members of the PID namespace". A process with no SIGTERM handler therefore ignores the polite stop and is killed at the end of the grace period instead. The same page notes the other half: if init terminates, the kernel kills every remaining process in the namespace with SIGKILL. Lesson 1304 is where that grace period is spent, and module 11's graceful shutdown is what spends it.

An image is immutable and the environment it runs in is not, which is the separation the twelve-factor app calls build, release and run: the build turns a commit into a bundle, the release combines that bundle with this deploy's configuration, and the run stage executes it. Baking configuration into the image collapses those three, and the symptom is a rebuild required in order to change a hostname, with a new digest that nothing has tested.

Check yourself

Retrieval practice

Answer from memory before revealing.

Two containers on one host both listen on port 8080. Which feature makes that possible?
The network namespace isolates devices, stacks and ports, so each container has a port 8080 of its own. Cgroups limit and account for resource usage rather than isolating names, the manifest's exposed ports are documentation with no enforcement, and there is no guest kernel anywhere in a container.
A Dockerfile copies the whole source tree before installing dependencies. What is the cost?
A changed layer forces every downstream layer to be rebuilt even when nothing about them differs, so the dependency install runs on every commit. Carrying the source is a separate problem multi-stage builds solve, layer order is not reversed by anything, and a changed digest per build is true of any real change and is not the cost here.
