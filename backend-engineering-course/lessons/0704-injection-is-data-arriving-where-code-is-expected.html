An interpreter cannot see where your string stopped and the user's began

working 8 min The first of the three threats, and the one with a complete fix. · OWASP - SQL Injection Prevention Cheat Sheet

The one-minute version

  • The threat first. You build a command by joining your text to the user's text. The interpreter receives one string, parses all of it, and the user's half is now grammar rather than a value.
  • This is not a fact about SQL. It is a fact about every interpreter you hand a constructed string to - shells, LDAP filters, template engines, ORM fragments.
  • The fix is structural, not lexical: send the command and the values on separate channels, so the database always distinguishes between code and data, regardless of what user input is supplied.
  • Parameters bind values, never identifiers. A table name, a column name or a sort direction cannot be a placeholder, and those are the parts you must allow-list.
  • What it costs: the defence lives at the sink, so it protects the one call site that uses it and no other. Escaping is the last resort and OWASP says it cannot be guaranteed to work.

1. The threat: concatenation destroys the boundary

Two strings go in and one string comes out

Consider a lookup by email. Your code holds a template and a value, and it joins them; what reaches the database is a single sequence of characters with no record of which half came from where. The parser then does its job perfectly: it reads quotes as quotes, semicolons as statement separators and OR as a boolean operator, because that is what those characters mean in the language it was handed.

So an email of x' OR '1'='1 does not smuggle anything past a check. It closes your string literal, adds a disjunction that is always true, and reopens a literal so the trailing quote you wrote still balances. The result is valid SQL that means something you never wrote. There was no moment at which the database could have known better: by the time it saw the text, the boundary you were relying on no longer existed.

2. The defence: separate channels, at the sink

The same shape in both voices

OWASP puts prepared statements first among the primary defences and gives the reason in one sentence: with them the database will always distinguish between code and data, regardless of what user input is supplied. Note the scope of that promise - it holds whatever the input is, which is what makes it a defence rather than a filter you have to keep ahead of.

lookup.go · the placeholder is part of the statement, Go
// Wrong: one string reaches the parser, and the value is part of it.
q := "SELECT id, name FROM users WHERE email = '" + email + "'"
rows, err := db.Query(q)

// Right: the statement and the value travel separately.
rows, err := db.Query(
    "SELECT id, name FROM users WHERE email = $1",
    email,
)
lookup.py · the same boundary in Python, DB-API 2.0
# Wrong: an f-string is concatenation with better ergonomics.
cur.execute(f"SELECT id, name FROM users WHERE email = '{email}'")

# Right: the driver sends the statement, then the parameters.
cur.execute(
    "SELECT id, name FROM users WHERE email = %s",
    (email,),
)

The two languages disagree about the placeholder's spelling and agree about everything that matters. Nothing here is escaping the value, and nothing is inspecting it. The value is never part of the text the parser sees, so its contents cannot reach the grammar - which is why this works for an email containing a quote, a name containing a semicolon, and a deliberate attack, without treating them differently.

3. The trade-off: parameters bind values, and not everything is a value

Placeholders stand where a literal may stand, and nowhere else. A table name, a column name, and the ASC or DESC in an ORDER BY are parts of the statement's structure, so no driver will bind them. OWASP is direct about what to do instead: where a query cannot use bind variables, input validation or query redesign is the most appropriate defense. In practice that means mapping the caller's sort=created_at through a fixed dictionary of permitted columns and rejecting anything absent from it - an allow-list, never a pattern that tries to describe what a bad identifier looks like.

The other limit is reach. Lesson 0403 argued that validation belongs at the boundary, once, and this defence is the opposite kind: it belongs at the sink, every time. One call site left concatenated is one vulnerability, whatever the other four hundred do, which is why this is a defect that survives code review and gets found by a scanner. The two rules are complements - boundary parsing narrows what values exist, and parameterisation makes the surviving values harmless at the point of use.

Escaping is on OWASP's list and is last on it, with an unusually blunt warning: it is very database specific in its implementation, is fragile compared to the other defences, and cannot be guaranteed to prevent all SQL injection in all situations. Stored procedures carry a similar caveat - they are safe only when they do not themselves build a statement from their arguments, which is easy to do and invisible from the calling code.

Why does a parameterised query stop injection where careful escaping might not?
The property is about ordering: planning completes first, and the value then lands in a slot that holds data only. Nothing rejects quotes - a quote in a surname must work. The database does not treat prepared statements more strictly, and the third option describes client-side escaping, which is the fragile defence this one replaces.
A caller supplies the column to sort by. What is the correct defence?
An identifier is structure, so it is allow-listed rather than sanitised. Binding it is not possible - drivers bind values only, and the placeholder would be sent as a string literal. Identifier quoting helps but still admits any name the caller invents, and the last option is a deny-list, which fails on the input nobody thought of.
