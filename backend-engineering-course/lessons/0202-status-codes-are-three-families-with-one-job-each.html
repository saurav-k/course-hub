The first digit is the contract: 4xx blames the request and 5xx blames the server

foundation 7 min Why the class matters more than the code. · RFC 9110 §15 - Status Codes

The one-minute version

  • Five classes, and the first digit carries the meaning: 1xx interim, 2xx accepted, 3xx more to do, 4xx your fault, 5xx mine.
  • A client must understand the class of any status code and treat an unknown one as the x00 of that class. That is what makes the space extensible.
  • The 4xx / 5xx split is an assignment of blame, and it decides who is paged, what retries, and what an error budget counts.
  • A single request can have several interim responses and exactly one final one.
  • What it costs: the split is a judgement your handler makes, and a mis-classified error is a real outage measured as a client bug.

1. The mental model: the digit is the interface

The status space is extensible, and the way it stays extensible is a rule most engineers have never read. RFC 9110 requires a client to understand the class of any status code, given by the first digit, and to treat an unrecognised code as equivalent to the x00 of that class. A client receiving 471 knows from the leading 4 that something was wrong with its request and may treat it as 400. A response with a code outside 100 to 599 is invalid and should be processed as a 5xx.

That rule is the whole design. It means a server can invent a code without breaking clients, and it means your code that switches on 200 and 404 and falls through everything else is not merely lazy but wrong: the fallthrough is supposed to be per class, not per code.

2. The three that say where the request stands

1xx: not an answer yet

The 1xx class is an interim response that communicates connection status or request progress before the requested action is complete. A 1xx response is terminated by the end of the header section and can carry no content. A single request has zero or more interim responses followed by exactly one final response, which is the sentence to remember: a client that treats the first response line it sees as the answer will occasionally be wrong.

2xx and 3xx: accepted, or redirected

2xx means the request was successfully received, understood and accepted. 3xx means further action needs to be taken by the user agent to fulfil the request, which is not the same as failure and not the same as success: a redirect is a well-formed answer that happens to be an instruction. Both are ordinary outcomes, and treating a 3xx as an error is a common source of noisy dashboards.

3. The two that assign blame

4xx: the request is the problem

4xx says the client seems to have erred. The specification's own hedge is worth keeping: seems. The server is making a judgement, and the practical consequence is that repeating the same request unchanged will get the same answer. A well-built client does not retry a 4xx, a well-built dashboard does not alert on one, and an error budget that counts 4xx as failure will be dominated by scanners and stale bookmarks.

5xx: the server is the problem

5xx says the server is aware it has erred or is incapable of performing the method. Here the request may be perfectly valid, so a retry is meaningful and backoff is required to stop the retry becoming the outage. This is the class your alerts fire on. In both classes, except when answering a HEAD request, the server should send a representation explaining the situation and whether it is temporary or permanent.

The line between the two is a judgement, and it is genuinely hard in one place: a dependency you called has failed. The request was valid, your service could not perform it, and the class is 5xx even though the fault was somewhere else. That is worth stating explicitly in a service's error-handling code, because the tempting alternative is to pass the dependency's own 4xx straight through and blame a caller who did nothing wrong. This page owns the vocabulary and Module 11 owns the retry policy, but the classification itself is decided here, at the moment a handler picks a number.

The expensive mistake is returning 200 with an error inside the body. It is comfortable, it makes a client library simpler, and it makes the request invisible to every layer that reads the status: no proxy retries it, no dashboard counts it, no cache declines to store it. An outage served as 200 is an outage nobody is paged for.

Check yourself

Retrieval practice

Answer from memory before revealing.

A client receives status 471, which it has never seen. What should it do?
A client must understand the class, and an unrecognised code is equivalent to the x00 of that class, so 471 reads as 400. The first option reads the wrong class, the second discards a valid response, and the third is a retry the 4xx class specifically does not warrant.
Which response should an availability alert fire on?
Only the 5xx class says the server erred or could not perform the method. The 4xx class blames the request, so it tracks client behaviour rather than availability; 3xx is a normal outcome; and the last option collapses all three distinctions into one noisy signal.
