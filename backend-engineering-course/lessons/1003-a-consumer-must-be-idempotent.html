The duplicate is not a risk to guard against, it is a delivery you already scheduled

working 10 min What the previous two lessons oblige you to build. · Amazon SQS - exactly-once processing

The one-minute version

  • Two mechanisms you have already accepted produce duplicates on purpose: the expiring lease of lesson 1001 and the retry policy of lesson 1002. Nothing upstream will stop them.
  • Idempotence is a property of the effect, not of the code. Assignment repeats safely, accumulation does not, and the fastest fix is often to change the write rather than to add machinery.
  • When the effect cannot be made naturally repeatable, claim a key: a row inserted under a unique constraint, in the same transaction as the work. That is lesson 0605's mechanism moved to the consumer side.
  • Key on a value the producer chose, not on the broker's message id. A redelivery reuses the id, but a producer that retried its send created a genuinely new message for the same intent.
  • What it costs: the dedup store has a retention, so the guarantee expires - and it covers only the effects inside the transaction that claimed the key.

1. The mental model: the ambiguous acknowledgement, one layer down

The consumer and the broker cannot agree

Lesson 0605 named the knot on the HTTP side: a client that gets no response cannot tell a lost request from a lost response. The consumer side is the same knot with the parties swapped. The worker finishes the job, sends the acknowledgement, and the acknowledgement is lost, or the process dies in the microsecond between the commit and the delete. From the broker's position nothing distinguishes that from a worker that died before it started, and its only correct action - the action that stops work from being lost - is to hand the message to somebody else.

So the duplicate is not the symptom of a bug anywhere. It is the deliberate output of a system that has chosen not to lose work. Amazon writes it into the guarantee itself: even under a FIFO queue's ordering and deduplication, "due to the at-least-once delivery model of Amazon SQS, there's no absolute guarantee that a message won't be delivered more than once during the visibility timeout period".

What deduplication upstream does and does not buy

It is worth being precise about the one place a broker will deduplicate for you, because it is narrower than its name suggests. An SQS FIFO queue with a MessageDeduplicationId will, if you retry the SendMessage action within the 5-minute deduplication interval, not introduce any duplicates into the queue. Read the two boundaries in that sentence. It is send-side, so it collapses a producer's retries and touches nothing about delivery. And it is five minutes, so it is a window rather than a promise.

That distinction decides what you key on. A redelivery caused by an expired lease carries the same message id, so the broker's id would catch it. A duplicate caused by the producer retrying its send is a different message with a different id and identical intent, and the broker's id would not catch it at all. The value that identifies the intent has to come from the party that has the intent, which is the producer - the same argument, for the same reason, as the client-generated key in lesson 0605.

2. The mechanism: change the effect, or claim a key

Assignment repeats, accumulation does not

Before reaching for a dedup table, look at what the job actually writes. UPDATE orders SET status = 'shipped' WHERE id = 77 can run any number of times and leaves the same row. UPDATE accounts SET balance = balance + 10 WHERE id = 5 cannot run twice, ever. The first is an assignment and the second is an accumulation, and a surprising number of jobs can be rewritten from the second form into the first by computing the target value rather than the delta. Inserts have the same split: a plain INSERT duplicates and an upsert against a natural key does not.

Sidekiq's phrasing of the goal is the one to hold: "Idempotency means that your job can safely execute multiple times." When the effect can carry that property by itself, it should, because a naturally idempotent job needs no extra table, no retention policy and no second thing to keep correct during a schema change.

When it cannot, claim a key in the same transaction

Some effects have no assignment form. Appending an audit entry, incrementing a counter, allocating a sequence number and calling an external API all change something by an amount rather than to a value. For those, the mechanism is the one lesson 0605 already built: a table of processed keys with a unique constraint, and the insert into it committed together with the work.

consumer.go · the claim and the effect share one transaction
func Handle(ctx context.Context, db *sql.DB, job Job) error {
    tx, err := db.BeginTx(ctx, nil)
    if err != nil {
        return err
    }
    defer tx.Rollback() // a no-op once Commit has succeeded

    // The claim goes first, and it is what makes the effect single.
    _, err = tx.ExecContext(ctx,
        `INSERT INTO processed_jobs (idempotency_key) VALUES ($1)`, job.Key)
    if isUniqueViolation(err) {
        return nil // already done - acknowledge and move on
    }
    if err != nil {
        return err
    }

    if _, err = tx.ExecContext(ctx,
        `INSERT INTO ledger_entries (account_id, amount) VALUES ($1, $2)`,
        job.AccountID, job.Amount); err != nil {
        return err
    }
    return tx.Commit()
}

Two properties of that shape matter more than the spelling. The claim is attempted before the work, so two workers racing on the same key resolve against the unique constraint rather than against luck. And the claim and the effect commit together, so there is no window in which the key says "done" and the ledger says otherwise. Writing the key after the work is the common version of this code and it is broken in exactly the way the mechanism exists to prevent: a crash between the two leaves the effect applied and unclaimed, and the redelivery applies it again.

3. The trade-off: the key expires and the transaction bounds it

The dedup table grows by one row per job forever unless something prunes it, and pruning is what gives the guarantee an expiry date. A duplicate that arrives inside the retention window is absorbed; one that arrives after it is a new job that will do the work again. That is not a defect to be fixed, it is the same published limit that Stripe's 24-hour key pruning has, and it must be chosen deliberately: long enough to cover your longest retry schedule plus the dead-letter redrive you might perform days later.

The second bound is the one that catches teams after they believe they are finished. The claim protects exactly what commits with it. A job that writes a row, sends an email and publishes an event has one of those three inside the transaction, and a crash after the commit but before the email leaves a claimed key with no email sent - so the redelivery is absorbed and the email never goes. Put the unrollbackable effects after the commit and accept that they may repeat, or move them into their own job with their own key. What you cannot do is claim one key for three effects and call all three protected.

Standard queues make best-effort ordering only - Amazon's own wording is that "messages may occasionally arrive out of order" - so the figure above is not an exotic case brought on by a long lease. It is the ordinary behaviour of the queue type most systems default to, and a version column is the cheapest defence against it.

Check yourself

Retrieval practice

Answer from memory before revealing.

Why key deduplication on a producer-supplied value rather than the broker's message id?
A producer that retried its send created a second message with its own id and identical meaning, so an id-keyed check sees two different things and does the work twice. A redelivery keeps its id, which is the case the broker id does catch. Ids are indexable and are visible to consumers, so neither of those is the reason - the reason is that only the producer knows two sends were one intent.
A worker inserts the processed-key row after the effect commits. What breaks?
The window between the two writes is the whole hazard: a crash there leaves the effect applied and no key claiming it, so the redelivery applies it a second time - which is the failure the key existed to prevent. The constraint still functions, it is simply consulted too late to help. Growth is unchanged, since the same number of rows is written either way. And the ordering matters precisely because a crash can land between any two separate writes.

How this connects

  • Ahead, enqueue and commit are two writes builds a publisher that is itself at-least-once, so the consumer built here is what makes it usable.
  • Behind you, idempotency keys make retries safe is the same mechanism published as an HTTP interface, and it is what the rightmost leaf of the decision figure asks a remote service for.
  • Behind you, a failed job is a policy is where the attempt count that makes duplicates routine was set.
Your teacher. Take one consumer and list every effect it has: rows written, messages published, remote calls made. Mark which of them share a transaction with anything. Then ask the agent which effects would survive being run twice, and which of the survivors would still be correct if the two runs arrived out of order.
