Module 03 · Routing · Lesson 0305

Prefix mounting strips the prefix before the inner router matches, which is what makes routers composable

working 8 min One service, several independent routers. · PEP 3333 - SCRIPT_NAME and PATH_INFO

The one-minute version

  • A router is a handler like any other, so a router can be registered inside another router under a path prefix.
  • The outer router removes the prefix before handing the request on, so the inner one matches the remainder and nothing else.
  • That is what makes an inner router reusable: it is written against /orders, and where it is mounted is decided somewhere it never reads.
  • The prefix is not thrown away. WSGI keeps it in SCRIPT_NAME, Express keeps it in req.baseUrl, and both keep the whole original too.
  • What it costs: every URL the inner router generates must have the prefix put back, and its 404 is now the service's 404.

1. The mental model: a router is a handler

Everything in this module has treated the router as the thing that finds handlers. The useful inversion is that a router is one. It takes a request, it produces a response, and nothing above it can tell whether the thing it called dispatched further or answered directly. Once that is true, registering a router inside a router needs no new machinery at all.

PEP 3333 names this as one of the things middleware is for: routing a request to different application objects based on the target URL, after rewriting the environment accordingly. The clause that matters is the last one. Handing the request on unchanged would make the inner router match against a path it does not recognise, because it was written against /orders/{id} and the request says /api/v2/orders/8123. Rewriting is what makes the inner router's patterns true again.

2. The mechanism: strip, hand on, keep the original

Mounting: the outer router's registration

A mount is an ordinary registration whose target happens to be a router, on a pattern that matches a whole subtree rather than one path. In Go a trailing slash does it, since a trailing slash acts as an anonymous multi-segment wildcard; in Express app.use(path, router) does it; in Flask a blueprint registered with a url_prefix does it. The outer router matches the prefix, and everything after it is the inner router's problem.

Stripping: what the inner router is given

Go's StripPrefix is the whole mechanism written out with nothing hidden. It returns a handler that removes the prefix from the request URL's path and calls the wrapped handler. It copies the request rather than mutating the one it was given, and if the prefix is not actually there it answers 404 instead of guessing. Express states the same behaviour from the documentation side: the mounting feature of app.use() rewrites req.url to strip the mount point.

mount.go · Go, net/http, the prefix removed before the inner mux runs
api := http.NewServeMux()
api.HandleFunc("GET /orders/{id}", showOrder)   // no /api/v2 anywhere

root := http.NewServeMux()
root.Handle("/api/v2/", http.StripPrefix("/api/v2", api))
root.HandleFunc("GET /healthz", healthz)
mount.py · Python, WSGI, the prefix moved from PATH_INFO to SCRIPT_NAME
def mount(prefix, inner, fallback):
    def app(environ, start_response):
        path = environ["PATH_INFO"]
        if not path.startswith(prefix):
            return fallback(environ, start_response)
        environ["SCRIPT_NAME"] = environ.get("SCRIPT_NAME", "") + prefix
        environ["PATH_INFO"] = path[len(prefix):]   # the remainder
        return inner(environ, start_response)
    return app

The prefix is kept, not discarded

Stripping would be a lossy operation if the prefix vanished, so every implementation keeps it somewhere with a name. PEP 3333 splits the path into two variables for exactly this: SCRIPT_NAME is the initial portion corresponding to the application object, so that the application knows its virtual location, and PATH_INFO is the remainder. Express does the same with req.baseUrl, and keeps the untouched original in req.originalUrl: for a request to /admin/new?sort=desc mounted at /admin, those three read /admin, /new and /admin/new?sort=desc.

3. The trade-off: independence has to be paid for somewhere

The first cost is URL generation. A router that does not know its prefix cannot build a correct absolute link, so every framework that supports mounting also supplies the base back for that purpose - Flask's url_for and Express's req.baseUrl exist for this. Hand-building a Location field or a pagination link from a pattern string is where mounting bites, because it works perfectly until the day the mount moves.

The second is that verdicts compose too. A request that matches the prefix has been given away, so if the inner router finds nothing, its 404 is the service's answer, and the outer router's own routes are never consulted. That is correct - the subtree belongs to the mounted router - but it means the Allow field of Lesson 0304 is computed from the inner table only, and a resource whose verbs are split across two routers will list half of them.

The third is ordering. The outer chain of Lesson 0303 wraps the mount, so it runs for every request in that subtree, and the inner chain nests inside it. That is usually what you want, and it is worth stating once so nobody re-adds request logging inside every mounted router.

Two prefixes where one is a prefix of the other is the case to check by hand. Mounting /api and /api/v2 on the same outer router is legal, and which one wins is decided by the specificity rule of Lesson 0302 rather than by the order you wrote them in. Go will tell you at startup when two patterns genuinely conflict; a framework that resolves ambiguity by first-registered-wins will not tell you anything at all, and the symptom is a whole subtree quietly answered by the wrong router.

Check yourself

Retrieval practice

Answer from memory before revealing.

A router is mounted at /admin. What path does it match against?
The prefix is stripped before the inner router runs, which is what lets its patterns be written without it. Matching the full path would break every one of those patterns, no redirect is involved, and the query was never part of path matching at all.
Why does WSGI keep SCRIPT_NAME rather than dropping the prefix?
PEP 3333 gives that reason in the definition itself: an application needs its own base in order to build correct URLs. Matching it twice is exactly what stripping prevents, no proxy reads a WSGI variable, and the cache key is built by a cache from the target URI rather than from the environment.
