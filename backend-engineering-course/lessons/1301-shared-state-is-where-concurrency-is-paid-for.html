Anything two requests can reach at once must be serialized by something

working 9 min The bill for the overlap lesson 1300 bought. · The Go Memory Model

The one-minute version

  • A data race is a write concurrent with any other access to the same location, and its result is not a wrong value but an undefined one.
  • The fix is stated as a requirement rather than a suggestion: programs that share data across goroutines must serialize that access.
  • Two disciplines do it. A lock names the data it protects. A channel hands ownership across, so only one holder exists at a time.
  • Python's interpreter lock protects the object model, not your invariants: a dictionary will not corrupt, and read-then-write across two lines still races.
  • What it costs: a race is invisible to review and to any test that does not run the path, and the tool that finds it slows the program by 2 to 20 times.

1. The mental model: a race has no value, not a wrong one

The definition is mechanical

The Go memory model defines the term without reference to timing or luck: a data race is "a write to a memory location happening concurrently with another read or write to that same location", unless every access involved is an atomic operation from the sync/atomic package. Note what is absent. There is no threshold, no notion of how likely the overlap is, and no requirement that the two accesses be to different values. One concurrent write is the whole condition.

The consequence is stronger than most engineers assume. Go promises that a program with no races behaves as if every goroutine were multiplexed onto a single processor, which the document calls DRF-SC: data-race-free programs execute in a sequentially consistent manner. Outside that guarantee, the language offers much less. An implementation "may always react to a data race by reporting the race and terminating the program", and for anything wider than a machine word it explicitly declines to promise a coherent result: "races on multiword data structures can lead to inconsistent values not corresponding to a single write". A struct read during a concurrent write can therefore be half of one value and half of another, which is a state your code has no branch for.

2. The mechanism: two ways to make the access serial

A lock names the data, a channel moves it

The memory model states the remedy as a requirement: "Programs that modify data being simultaneously accessed by multiple goroutines must serialize such access. To serialize access, protect the data with channel operations or other synchronization primitives such as those in the sync and sync/atomic packages." Two families, and the difference is what they make explicit.

A mutex leaves the data where it is and adds a rule about who may touch it. Go's sync package gives it the smallest possible surface: the zero value is an unlocked mutex, and a mutex must not be copied after first use, which is the whole reason a struct carrying one is passed by pointer. The rule a mutex encodes is not in the type system, though. Nothing links the lock to the field it guards except a comment and the discipline of everyone who edits the file afterwards.

A channel takes the other route, and Go states it as a slogan: "Do not communicate by sharing memory; instead, share memory by communicating." The value is handed from one goroutine to the next, so at any instant exactly one of them can reach it, and the compiler's own type is what carries the handover. The same package that ships the mutex says which it prefers: "Higher-level synchronization is better done via channels and communication", with the primitives "intended for use by low-level library routines".

What the interpreter lock does and does not protect

CPython's global interpreter lock is often mistaken for a general answer. The glossary is precise about its scope: it assures that only one thread executes Python bytecode at a time, which "makes the object model (including critical built-in types such as dict) implicitly safe against concurrent access". That sentence protects the dictionary's own internal structure. It says nothing about the invariants of your program, and a read followed by a write is two bytecode sequences with a scheduling point available between them.

the same race, in both voices · neither is fixed by the runtime
// Go: the field is shared, so the lock is named beside it.
type Tally struct {
    mu    sync.Mutex // guards today
    today int
}
func (t *Tally) Add() { t.mu.Lock(); defer t.mu.Unlock(); t.today++ }

# Python: the dict is safe, the read-then-write across two lines is not.
with tally_lock:
    tally["today"] = tally["today"] + 1

The tool, and what it cannot see

Go ships a race detector, enabled with -race on build, run or test. Its stated limit is the one to hold onto: "the race detector only finds races that happen at runtime, so it can't find races in code paths that are not executed". It is a runtime observer, not an analysis, so a race in a branch your tests never take is a race it never reports. The cost is documented too: memory use may grow by 5 to 10 times and execution time by 2 to 20 times, which is why it runs in CI and under load tests rather than in production.

3. The trade-off: every lock is a queue you built on purpose

Serialization works by making concurrency stop, and the part of a request that runs under a lock is a part the whole fleet takes in turn. A handler that holds a mutex for two milliseconds out of a two-millisecond critical path has quietly capped the process at 500 of those operations a second, no matter how many cores or goroutines are available, and adding either makes the contention worse rather than better because more waiters arrive at the same door.

So the design question is not which primitive to use but how much of the request needs to be inside one. A lock held across a network call is the classic version of the mistake: the critical section is now as long as somebody else's latency, and lesson 1300's arithmetic applies to the lock exactly as it applied to the worker pool. Shrink what is shared before choosing what protects it.

A race that has never been observed is not a race that does not exist. The Go memory model permits an implementation to terminate the program on detecting one, and permits a multiword read to return a value that was never written, so the behaviour you have observed in production is one of several the language allows and not a guarantee you can rely on. A compiler upgrade, a different core count, or a change in scheduling is enough to move it.

Check yourself

Retrieval practice

Answer from memory before revealing.

By the Go memory model's definition, when does a data race occur?
One write concurrent with any read or write is the whole condition, unless every access is an atomic operation. Concurrent reads are not a race because nothing changes, no definition mentions a quantum or any window of time, and a goroutine blocked on a channel is not accessing the location at all.
What does CPython's interpreter lock guarantee about a shared dictionary?
The glossary claims implicit safety for the object model, which is the container's internal structure and nothing else. The read-then-write is two operations with a scheduling point between them, references are not restricted at all, and no ordering across threads is promised anywhere.

Practice about 10 minutes, with paper

Practice 1working

A handler updates an in-memory index under a mutex. The critical section is 0.4 milliseconds of pure computation. A later change moves a 12 millisecond call to Redis inside the same section, so that the index and the cache are updated together.

Find the process's ceiling for that operation before and after the change, and say what adding cores or goroutines does to each.

Hint

Only one worker is inside the section at a time, so the section is a pool of exactly one. Lesson 1300's arithmetic applies to it unchanged.

Show the worked solution
  1. Treat the lock as a pool of one. The ceiling is 1 divided by the time each holder occupies it.
  2. Before the change. 1 ÷ 0.0004 s = 2,500 of that operation a second, for the whole process.
  3. After the change. The section is now 0.4 + 12 = 12.4 ms, so 1 ÷ 0.0124 s = about 80 a second.
  4. Add hardware. Neither number moves. Cores and goroutines add waiters at the same door, so the queue in front of the lock grows and the ceiling does not.

Sanity check. The ceiling is one over the section length, so the ratio of the two answers must equal the ratio of the two section lengths: 12.4 ÷ 0.4 = 31, and 2,500 ÷ 80.6 = 31. A 31-fold longer section buys a 31-fold lower ceiling, and nothing else changed.
