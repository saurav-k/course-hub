The path names the resource and the query modifies the view of it

foundation 8 min Which half of a URL carries which fact. · RFC 3986 §3.3 - Path

The one-minute version

  • RFC 3986 gives the two components different characters: the path is hierarchical data and the query is non-hierarchical data.
  • Both are part of the identifier. The query is not an argument list bolted onto a URL - it helps identify the resource.
  • The router matches on the path only. The query reaches your code as parsed values and never chooses a handler.
  • A slash inside a value cannot travel in one path segment, and a repeated or reordered key cannot travel in a path at all.
  • What it costs: the query is part of the cache key, so every optional filter you add doubles the number of distinct entries a cache can hold for one resource.

1. The mental model: hierarchy against modifiers

RFC 3986 defines the two components in almost the same words and changes exactly one adjective. The path carries data "usually organized in hierarchical form"; the query carries "non-hierarchical data". Both, in the same sentence in both definitions, serve to identify a resource. That is the whole distinction, and it is sharper than the usual advice about nouns and verbs.

Hierarchical means the segments nest: /orders/8123/items/4 reads left to right as a containment chain, and a segment only means something inside the one before it. Non-hierarchical means the pairs do not nest and have no natural order: ?status=open&sort=date says two independent things about how you want the collection presented. So the test is not "is this a noun" but does it nest. An order id nests inside orders. A sort direction nests inside nothing.

2. The mechanism: what each half can carry

The path parameter: one segment, captured by name

A path parameter is a named hole standing for a whole segment. Go's ServeMux matches a wildcard only up to the next literal slash, and it unescapes the pattern and the request path segment by segment, so /a%2Fb/100%25 is two segments, a/b and 100%. Flask spells the same idea with converters, and <path:subpath> is the explicit opt-out that accepts slashes. The rule underneath both: a value with a slash in it does not fit in one segment, and pretending otherwise is where encoding bugs live.

The query string: repeatable, reorderable, optional

The query is a flat sequence of pairs and gets three abilities the path does not have. A key may repeat, which is how a list travels. Keys may arrive in any order, because nothing nests. And a key may simply be absent, which is how a default is expressed without inventing a URL for it. Frameworks hand it over already parsed - req.query in Express, request.args in Flask - and none of them consulted it when choosing your function.

The template language agrees with the split

RFC 6570 is the useful third opinion, because it had to describe both halves in one grammar and chose different operators for them. {/var} is path segment expansion, appending a slash and then the value. {?var,var} is form-style query expansion, appending a question mark and then name=value pairs joined by ampersands. A single template such as /orders/{id}{?fields,sort} therefore states the whole contract of an endpoint in one line, and the operator you reach for is a decision you have already made.

3. The trade-off: the query is in the cache key

RFC 9111 defines the cache key as being composed, at a minimum, of the request method and the target URI, and the target URI includes the query. Two requests differing only in one query key are two entries. That is correct behaviour and it is also the cost nobody prices in, because the entries multiply rather than add.

keys(n) = 2n Read as: the number of distinct URLs for one resource, where n is the number of independent optional filters and each one is either present with a fixed value or absent.
  1. Count the choices. Each filter is present or absent, independently, so there are two choices per filter.
  2. Multiply them. Independent choices multiply, so n filters give 2n distinct query strings.
  3. Drop the fixed order. If a client may also send the keys in any order, the k present keys can be arranged k! ways, and the total for five filters rises from 32 to 326.

Two rules follow, and both are cheap to hold. Put a filter in the query when it genuinely shapes a view of one resource, and keep the set small and its keys canonically ordered by the client. Put an identifier in the path when it names a thing that exists on its own - and note the consequence in the other direction: a value in the path is a value the router can match on, so /orders/{id} can carry different middleware from /orders, while ?id=8123 can carry none.

The failure this causes is a security one rather than an aesthetic one. Authorisation rules are usually written against route patterns, so a tenant identifier moved into the query - /reports?tenant=42 - is invisible to every rule the router can express, and the check falls to whichever handler remembers to make it. The path is where a value goes when something other than your handler has to reason about it.

Answer from memory before revealing.

By RFC 3986, what separates the path from the query?
The standard defines both as identifying the resource and separates them by hierarchy alone. The second option is the common misreading, since the query identifies too; the third is true of the syntax but is not the distinction; and the fourth is backwards, because the query is inside the cache key.
Which value genuinely cannot travel in one path segment?
A wildcard ends at the next literal slash, so a value containing one needs a multi-segment hole or a path converter. Hyphens and digits are ordinary segment characters, and an encoded percent sign survives because matching unescapes each segment before comparing it.
