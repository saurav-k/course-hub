Module 05 · The layered service · Lesson 0503

A repository names the loads and saves the domain needs, and the query language stops at its edge

working 8 min The lower door, built properly. · Spring Data - Repository core concepts

The one-minute version

  • A repository is a contract for the loads and saves the domain needs, written in the domain's vocabulary and nobody else's.
  • It is not a mirror of the schema. The number of methods follows the number of operations, never the number of tables.
  • Everything the store speaks - SQL, driver errors, row types, connection handles - lives on the far side of the contract and never crosses it.
  • Spring Data draws the same line by extending a store-agnostic interface into technology-specific ones, so the generic part is what a domain depends on.
  • What it costs: the contract hides the query language and therefore hides the query cost, which is the one thing a caller most needs to see.

1. The mental model: a collection whose contents outlive the process

The useful picture is not a data-access object with one method per table. It is a collection: something you can add to, take from, and look things up in, whose contents happen to survive a restart. A service asking for an order by its identifier is doing the same thing it would do with an in-memory map, and the fact that the answer travels over a socket and arrives as rows is an implementation detail it has no interest in.

Spring Data draws the line in its type hierarchy rather than in prose: the store-agnostic interfaces come first, and the technology-specific ones extend them to expose what a particular store can additionally do. A domain that depends on the generic part is portable. A domain that reaches for the specific part has chosen a store, which is sometimes right and is always a choice rather than an accident.

2. The mechanism

The contract the domain declares

The methods come from the operations, not from the schema. Ask what the service actually does with orders: it loads one by identifier, it saves one, and for the cancellation screen it lists the ones a customer placed. That is three methods. A schema with an orders table, an order_lines table and an order_events table still yields three methods, because the service never asked for a line or an event on its own. When it does ask, the interface grows by one method with a name from the domain.

The identifier type matters as much as the method list. A method taking OrderID rather than string cannot be handed a customer identifier by mistake, and a method returning Order rather than a row means the mapping from columns to fields happened on the far side, where the schema is known.

the contract and one implementation · the SQL exists only in the second block
// The contract: three operations, all in the domain's vocabulary.
type Orders interface {
    ByID(ctx context.Context, id OrderID) (Order, error)
    ForCustomer(ctx context.Context, id CustomerID) ([]Order, error)
    Save(ctx context.Context, o Order) error
}

// One implementation. Every store-specific word in the file is below this line.
func (r *PostgresOrders) ByID(ctx context.Context, id OrderID) (Order, error) {
    row := r.db.QueryRowContext(ctx,
        `SELECT id, customer_id, state, placed_at FROM orders WHERE id = $1`, id)
    var o Order
    switch err := row.Scan(&o.ID, &o.CustomerID, &o.State, &o.PlacedAt); {
    case errors.Is(err, sql.ErrNoRows):
        return Order{}, ErrNotFound      // the driver error is translated here
    case err != nil:
        return Order{}, fmt.Errorf("load order %s: %w", id, err)
    }
    return o, nil
}

Notice what the last block does with sql.ErrNoRows. The driver's way of saying nothing matched is turned into the domain's named outcome at the boundary, which is the second door of the previous page being locked from this side. Go's standard library is honest about how far its own abstraction goes: database/sql provides a generic interface around SQL databases, which makes it generic over drivers and not over stores. Being generic over stores is this contract's job, not the library's.

The persistence model against the domain model

The two shapes are allowed to differ, and pretending otherwise is what makes repositories degenerate. A domain object holds what the rules need. A schema holds what queries and constraints need, and those are shaped by indexes, joins and history. When they diverge, the mapping is work the implementation does, and doing it there is the point rather than an inconvenience. When a framework maps the two automatically, the domain object is being defined by the schema, and any rule that would want a different shape now costs a migration.

3. What the contract costs

It hides the cost. A caller reading ForCustomer(ctx, id) cannot see whether that is one query with a join or one query per order, and the interface is doing its job by not saying. That is the trade this boundary makes, and it is why a repository is not a licence to stop thinking about queries: the cost has to become visible some other way, through the timings the observability module adds and through a review that reads the implementation rather than the contract.

It also erodes under pressure from the user interface. A screen wants a page of results, sorted, with two fields from another entity, and the honest ways to serve that are a new domain-named method or a separate read path that queries the store directly. The dishonest way is a general filter object with sort keys and field lists, which is a query language again, expressed worse and now inside the domain's own package.

A repository whose method list grows one entry per screen has stopped being a domain contract. Twenty methods named after views is a query language with no optimiser, no documentation and no way to see which of them are slow. When that starts happening, the honest fix is usually to split reads from writes - let the write side keep the narrow domain contract and let the read side query the store directly for the shapes a screen needs - rather than to keep widening one interface. This course does not build that split, and Module 08 is where the query cost that forces it becomes measurable.

Check yourself

Retrieval practice

Answer from memory before revealing.

What decides which methods a repository interface carries?
The operations come first and the storage follows, which is why three tables can sit behind three methods or behind one. Deriving the interface from tables, from an ORM's base class or from the index list all let the store dictate the domain's vocabulary, which is the coupling the contract exists to remove.
Which signature leaks the store through the contract?
A query string means the caller has to know the store's language, so no other implementation can satisfy the interface and the substitution test fails immediately. The other three are the contract working as intended: domain types in, domain types out, and nothing that names a store.
