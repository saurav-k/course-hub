Module 04 · Serialization and contracts · Lesson 0405

Adding a field is safe and reusing a number is corruption, and JSON and protobuf disagree about renaming

working 9 min The rules follow from what the reader matches on. · Protocol Buffers - Updating a Message Type

The one-minute version

  • Two directions, and a rolling deploy exercises both at once: backward is new code reading old data, forward is old code reading new data.
  • In protobuf the wire identity is the number, so renaming is free and reusing a number is corruption. Deleting a field means reserving its number forever.
  • In JSON the wire identity is the name, so renaming is the breaking change that protobuf renaming is not. ProtoJSON keys on names too, which is why it accepts both spellings.
  • Some type changes are wire-compatible and lossy: an int64 read as an int32 truncates exactly as a cast would, with no error.
  • What it costs: a field you added and regret is a field you keep forever, marked reserved, because the alternative is a number that means two things.

1. The mental model: both directions, at the same time

Backward: new code reading old data

Backward compatibility is the direction people think of first, because it is the one a database migration has. Your new consumer must still make sense of every message written by the producer as it stands, and of everything already sitting in a queue, a log or a table.

Forward: old code reading new data

Forward compatibility is the harder one and the one a rolling deploy forces on you. While the deploy is in flight, some instances run the new build and some run the old, and the old ones are receiving messages from the new ones. That is old code reading new data, and it is not a theoretical case: it is every deploy, for as long as the deploy takes.

2. The mechanism: the protobuf rules, stated

Safe, unsafe, and safe but lossy

Because the reader matches on the number, the rules are unusually crisp and the language guide states them as a list. Adding a field is safe: old code parses the message and keeps the new field as an unknown one. Removing a field is safe provided the number is never used again. Adding a value to an enum is safe. Turning a single field with explicit presence into a member of a new oneof is safe; moving it into an existing one is not. Changing the number of an existing field is not safe, and neither is reusing a number that a deleted field once held.

A third category exists and is the one that bites: changes that parse and lose information. int32, uint32, int64, uint64 and bool are all mutually compatible on the wire, and a 64-bit value read as an int32 is truncated to 32 bits exactly as a C++ cast would truncate it. sint32 and sint64 are compatible with each other and with none of the others. string and bytes are compatible as long as the bytes are valid UTF-8. Each of those is a legal edit that produces wrong values rather than an error, which is lesson 0400's silence arriving on schedule.

3. The mechanism: JSON's rules are the other way round

The identity is the name, so the name is frozen

Run the same reasoning over JSON and the answers invert, because the reader is matching a string. Adding a member is safe, for the same reason and with the same caveat: most parsers ignore what they do not recognise, and Go's encoding/json ignores unmatched keys by default. Removing a member is safe only if no consumer required it, which is a fact about your consumers rather than about the format. And renaming a member is a hard break, in both directions at once: the old reader stops finding the value and the new reader finds nothing in old data.

The clearest evidence that this is a real difference rather than a stylistic one is that the Protocol Buffers project had to write it down. The ProtoJSON mapping keys on names, defaulting to lowerCamelCase, and it specifies that a parser must accept both that name and the original proto field name. It also states that a ProtoJSON parser should reject unknown fields by default, which is the opposite of the binary format's retention rule. The same schema, encoded two ways, gives you two different sets of legal edits.

4. The trade-off: wire-safe is not program-safe

The rules above are about parsing, and parsing is not the whole story. Adding an enum value is listed as safe, and it is: an older reader receives the unknown number, keeps it, and re-serialises it intact. What that reader then does with it is entirely your problem. Generated code will typically surface it as the zero value or as an unrecognised case, so a switch statement written before the value existed falls through to its default, and a status the business now treats as distinct is handled as if it were something else.

So the discipline is two-layered. Follow the encoding's rules so the bytes survive, and separately make every consumer handle a value it does not recognise in a way you chose deliberately: reject it, route it to a human, or pass it through untouched. The rule set keeps your data intact; only your own code keeps your behaviour correct.

A compatibility rule protects you only where it is checked, and none of these is checked by the compiler that builds each side. What checks them is a schema registry or a CI step that compares the proposed schema against the deployed one and fails the build on a forbidden edit. Without that, the rules on this page are a convention, and a convention is exactly what lesson 0400 called a contract nobody re-reads. If you take one operational action from this module, make it that comparison.

Check yourself

Retrieval practice

Answer from memory before revealing.

Why must a deleted protobuf field number be reserved rather than freed?
Messages written before the deletion are still in queues, logs and tables, and a new field on the same number would parse those old bytes as its own value. Field numbers are chosen by hand and never renumbered automatically, deleting the field is what removes it from generated code, and there is no version bump that retires a number.
Which edit is safe in binary protobuf and breaking in JSON?
The binary format matches on the number, so a rename never reaches the wire, while a JSON reader matches the name and simply stops finding the value. Deleting a field a consumer needs breaks both, narrowing an int64 truncates in both, and adding an enum value is wire-safe in both and is a program concern rather than an encoding one.
