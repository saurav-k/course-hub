A broker owns the message between sent and done, and the acknowledgement is where that ownership ends

working 9 min The asynchronous branch, and the guarantee it actually offers. · RabbitMQ - Consumer acknowledgements and publisher confirms

The one-minute version

  • The whole mechanism is one boundary: the broker keeps a message until a consumer acknowledges it, and only then is it gone.
  • Automatic acknowledgement moves that boundary to delivery - "a message is considered to be successfully delivered immediately after it is sent" - which the documentation calls unsafe.
  • An unacknowledged delivery is requeued when its channel or connection closes, which is what makes broker delivery at least once and duplicates ordinary.
  • Producers publish to an exchange, never to a queue. Bindings decide whether one message becomes one unit of work or ten copies for ten readers.
  • What it costs: your database and the broker are two systems with no shared transaction, so publishing after a commit is a dual write that can half-happen.

1. The mental model: who is holding the message right now

At every instant a message is in exactly one of three places: with the producer, with the broker, or being worked on by a consumer. The design question that decides everything else is when the broker is allowed to forget it, and the answer is: when a consumer says so. That single decision generates redelivery, duplicate handling, dead-lettering and the shape of a worker's error handling.

RabbitMQ offers the shortcut and warns about it in the same breath. In automatic acknowledgement mode "a message is considered to be successfully delivered immediately after it is sent", so the broker forgets it before anyone has done anything with it, and the documentation says outright that this "should be considered unsafe and not suitable for all workloads". If the consumer's connection drops mid-work, the message the server sent "will be lost". Manual acknowledgement moves the boundary to the end of the work, which is where it belongs.

2. The mechanism

Redelivery, and the duplicate that follows

Requeueing has a consequence the documentation states rather than implies: "consumers must be prepared to handle redeliveries and otherwise be implemented with idempotence in mind". A message that was fully processed by a worker that then crashed before acknowledging will be delivered again, and the work will be done twice. The broker marks the second copy - redeliveries carry a boolean redeliver property set to true, false on a first delivery - but that flag tells you a redelivery is possible, not that the first attempt succeeded.

So the guarantee a broker of this kind offers is at least once, and the design consequence is not optional: the handler must be safe to run twice on the same input. That is the same requirement lesson 0605 imposed on an HTTP endpoint, arrived at from the other direction, and the mechanism is the same - a stored key, claimed before the work, that lets the second run recognise itself.

Dead-lettering, for the message that will never succeed

Requeueing on failure is right for a transient error and catastrophic for a permanent one: a message that always throws is requeued, redelivered, throws again, and occupies a worker forever. Dead-lettering is the escape. A message is dead-lettered when a consumer rejects it with requeue set to false, when a per-message TTL expires, when the queue exceeds a length limit, or when it has been returned to a quorum queue more times than its delivery limit. The broker republishes it to a dead letter exchange, which is an ordinary exchange, and records the history in an x-death header that counts how many times and for what reason.

Routing decides work-sharing or fan-out

Producers do not publish to queues. They publish to an exchange, and bindings - rules with an optional routing key - decide which queues receive a copy. The exchange type is the routing algorithm: a direct exchange matches the routing key exactly, a topic exchange matches it as a pattern, a headers exchange ignores it in favour of header values, and a fanout exchange "routes messages to all of the queues that are bound to it and the routing key is ignored".

That indirection is what lets one publish mean two entirely different things. Many consumers on one queue share the work, because each message goes to one of them. One publish to a fanout exchange bound to several queues gives every reader its own copy. Getting this backwards is how a team ends up sending three confirmation emails, or how a job runs on one worker when it was meant to reach all of them.

3. The trade-off: the dual write

Here is the cost that no broker feature solves. Your service commits an order to its database and then publishes order.placed. Those are two systems with no transaction between them. Crash after the commit and before the publish, and the order exists with no event; publish first and crash before the commit, and the event describes an order that does not. Neither is recoverable by retrying, because the process that knew what to do is gone.

The standard answer is the transactional outbox: write the message into an outbox table in the same local transaction that writes the business data, so the two either both happen or neither does, and let a separate relay read that table and publish. The catalogued drawback is honest and worth quoting: "the message relay might publish a message more than once. It might, for example, crash after publishing a message but before recording the fact that it has done so." Which lands you exactly where the section above already left you - the consumer has to be idempotent - and that is the point. The outbox buys atomicity, not exactly-once.

A queue is a place where work goes to be forgotten. Nobody is waiting for it, so nothing complains when it stops moving: the symptom of a broken consumer is a number on a dashboard nobody opened. Alert on queue depth and on the age of the oldest unacknowledged message, and alert on the dead letter queue being non-empty, because the whole point of dead-lettering is that it fails quietly on purpose.

A worker finishes the work, then crashes before acknowledging. What happens?
Any delivery not acknowledged when the channel or connection closes is automatically requeued, so the message goes to another consumer and the work runs again. The first option describes automatic acknowledgement mode, the third needs an explicit reject with requeue false, and the fourth invents a per-consumer replay the protocol has no concept of.
Three services each need to react to one order.placed event. What routes it?
A fanout exchange copies the message into every bound queue and ignores the routing key, so each service gets its own copy and drains it at its own pace. One queue with three consumers shares the work instead - each message reaches exactly one. The second option describes a routing scheme, not a duplication one, and the fourth puts knowledge of every consumer into the producer.
