A cache hit is a freshness contract between the clock that set a lifetime and the clock that counts age

working 7 min Freshness, then validation. · RFC 9111 - HTTP Caching

The one-minute version

  • A response is fresh while its age has not exceeded its freshness lifetime, and stale once it has. That single comparison is the whole hit rule.
  • The origin sets the lifetime with max-age or Expires; the cache tracks the age from the moment the origin generated the response.
  • Stale is not unusable. It means the cache must ask again, and a validator makes that question cheap.
  • A successful validation freshens the stored response, so a 304 costs headers instead of a body and restarts the clock.
  • What it costs: you are choosing, in advance, how wrong a reader is allowed to be, and no cache can undo a lifetime you already published.

1. The mental model: two clocks, one comparison

Caching feels complicated because it is usually taught as a list of directives. It is not a list. There are two numbers and one comparison. The origin server declares a freshness lifetime, which is how long it believes the representation will not change in a way that matters. The cache tracks an age, the time since the origin generated or last validated the response. RFC 9111 writes the rule in one line: the response is fresh when the freshness lifetime is greater than the current age.

Everything else is detail hanging off that comparison. max-age sets the lifetime directly. Expires sets it as a date the cache subtracts Date from. s-maxage overrides both, for shared caches only, and is checked first. When none of them is present the cache may guess, using a heuristic, which is the situation you never want to be in because the guess is not yours.

2. The mechanism

Freshness lifetime: the origin's clock

The lifetime is a claim about the future made by the server that generated the representation. RFC 9111 evaluates the rules in order and uses the first match: s-maxage if the cache is shared, then max-age, then Expires minus Date, then a heuristic. Two things follow. The order is why a CDN and a browser can be given different lifetimes for one response. And using Expires minus Date rather than the cache's own wall clock is deliberate: it takes the calculation off the client's clock and onto the server's, which is the only clock both parties saw.

Age: the cache's clock

Age is the time that has passed since the response was generated by, or successfully validated with, the origin. It is not the time since this particular cache stored it. A shared cache reports the value it holds in the Age field, so a response with max-age=600 and Age: 550 arrives at a browser with fifty seconds of life left in it. A response can therefore be stale on arrival, which is correct behaviour and is regularly reported as a bug.

Validation: the cheap re-check

When a stored response cannot be served, the cache does not have to refetch it. It sends a conditional request carrying the validator from the stored copy - the ETag in If-None-Match, or the Last-Modified date in If-Modified-Since. If the representation is unchanged the origin answers 304 with no body, and the cache freshens the stored response and serves it. The saving is the body, which on most responses is nearly all of the bytes.

3. The trade-off: you are pricing staleness in advance

A lifetime is a promise you cannot withdraw. Once a response leaves with max-age=86400, every cache that stored it is entitled to serve it for a day, and there is no mechanism in HTTP for reaching out and taking it back. That is why the standard pattern for assets is a long lifetime plus a content hash in the URL: you never invalidate anything, you publish a new target and let the old one expire unread.

The other half of the trade-off is which directive means what, and two of them are routinely confused. no-store means the response must not be stored at all. no-cache means it may be stored and must be revalidated before every reuse. For a page whose content changes but whose bytes usually do not, no-cache with a strong ETag is almost always what was wanted, and no-store is what was typed.

The directive that decides the blast radius is a different one again. private and public do not describe the content, they name which caches may store the response, and there are two kinds on the path: the private cache belonging to one reader, and the shared cache in front of the origin serving everyone.

A private response in a shared cache is the failure worth being afraid of, because it is silent and it affects the wrong person. Any response that varies by user must carry private, or be excluded from storage, or key correctly through Vary. The symptom is one reader seeing another reader's page, and it is discovered by a user rather than by a monitor.

Check yourself

Retrieval practice

Answer from memory before revealing.

A response arrives with max-age=600 and Age: 620. What is it?
Age is measured from the origin generating the response, not from local storage, so 620 against 600 is already stale and must be revalidated. The first and fourth options both restart the clock at the wrong point, and the third invents a constraint the specification does not have.
You want a page stored but re-checked on every use. Which directive?
no-cache permits storage and forbids reuse without revalidation, which is exactly the ask. no-store forbids storage, so there is nothing to revalidate against; private is about which caches may store rather than when; and max-age=0 is close but leaves stale reuse open in cases no-cache closes.
