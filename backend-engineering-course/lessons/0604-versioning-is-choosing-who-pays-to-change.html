Every versioning scheme moves one cost, so pick the one you can afford to carry

working 9 min A version is an accounting decision, not a label. · GitHub - REST API versions and the support window

The one-minute version

  • A breaking change has a fixed cost - somebody rewrites something - and a versioning scheme only decides who pays it and when.
  • A version in the path is visible and cacheable and hands the caller a migration they must schedule.
  • A version pinned in a header costs the caller nothing until they opt in, and costs you every old behaviour, kept alive, forever.
  • No version at all is a real scheme with a real price: you may only ever add, and you pay it on every design decision from then on.
  • Retirement has standard machinery: RFC 9745's Deprecation and RFC 8594's Sunset, with the sunset never earlier than the deprecation.

1. The mental model: the cost does not disappear

It helps to state the accounting before the mechanisms, because the mechanisms are easy and the accounting is what people get wrong. A breaking change costs somebody a piece of work: reading a changelog, editing code, testing, deploying. That work exists no matter which scheme you choose. What a scheme decides is whose calendar it lands in, how much notice they get, and how long you carry the old behaviour while they get to it.

Once it is stated that way, the schemes stop looking like styles and start looking like positions on one axis. The provider can pay in duplicated surface area, or the caller can pay in scheduled migrations, or the provider can pay in permanently constrained design by never breaking at all. There is no fourth column where nobody pays.

2. The mechanism: three placements, three bills

A version in the path

Putting /v1/ and /v2/ in the URI makes the version part of the resource identity. It is visible in every log and every bug report, it caches independently because the URIs differ, and a caller can hold two versions open side by side while migrating one call at a time. The bill arrives twice: you run both surfaces until the old one is retired, and the caller must edit every URL to move, which is a project rather than a configuration change. It also sits awkwardly against lesson 0601, because the same underlying resource now answers to two names.

A version pinned in a header

The alternative sends the version out of band. GitHub uses X-GitHub-Api-Version with date-named versions, and a request that omits the header is served the 2022-11-28 version rather than the newest one, so an old integration keeps working untouched. Stripe goes one step further and pins the version to the account: your requests get your account's default version unless a Stripe-Version header overrides it, so a caller who never touches anything never sees a change at all.

That is a genuinely different bill. The caller pays nothing until they choose to, and their upgrade is a one-line change rather than a URL rewrite. You pay by keeping every pinned behaviour alive and correct, which means your service now carries a translation layer per version and your tests carry a matrix. The cost is invisible on the day you adopt the scheme and compounds quietly from then on.

No version, and why it counts as a scheme

The third option is to promise that the surface only ever grows, which is what lesson 0600's asymmetry buys if you are willing to be strict about it. Nobody migrates, nothing is duplicated, and the price is paid at design time: every field you regret stays, every default you chose badly stays, and each of those constrains the next design. It is the cheapest scheme to operate and the most expensive to have been wrong under, which makes it a good fit for a small, well-understood surface and a poor one for a product still finding its shape.

3. The mechanism: retiring a version out loud

Deprecation announces, sunset ends

Whichever scheme carries the version, retirement has standard machinery and it is worth using rather than inventing. RFC 9745 defines the Deprecation response header field, a structured-field date saying when the resource was or will be deprecated, and it is explicit that deprecating changes no behaviour: the resource keeps working, the header is a signal to whoever is reading. RFC 8594 defines Sunset, an HTTP-date saying when the resource is expected to stop responding, and the two are designed to travel together with one ordering rule: the sunset timestamp must not be earlier than the deprecation timestamp.

A version number in a URL is not a version unless something behind it is genuinely frozen. The common failure is one codebase serving both paths from the same handlers, with a branch or two where they differ: the old path then inherits every change made to the new one, and callers on /v1/ get breaking changes with a stable-looking URL over them. If you cannot say what code would have to change for a /v1/ response to change, you have a prefix rather than a version, and you are carrying the cost of the scheme without buying any of its protection.

Check yourself

Retrieval practice

Answer from memory before revealing.

What does a caller omitting X-GitHub-Api-Version receive?
GitHub serves a fixed default so an integration written before the header existed keeps working unchanged. Defaulting to the newest would break exactly the callers the scheme exists to protect, the header is optional by design, and per-account pinning is Stripe's variant rather than GitHub's.
What is the ordering rule between the Deprecation and Sunset headers?
RFC 9745 requires that the sunset timestamp not precede the deprecation timestamp, so a resource is always announced as deprecated before or when it is announced as ending. Equal dates are legal but give no notice, deprecation precedes rather than follows the sunset, and the two fields are complementary rather than alternatives.
