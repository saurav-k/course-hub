A WebSocket buys the server the right to speak first, and pays for it with statelessness

working 9 min The third branch, and the one that changes how the fleet is shaped. · RFC 6455 - The WebSocket Protocol

The one-minute version

  • A WebSocket connection begins as an HTTP request and stops being HTTP at the 101 Switching Protocols response.
  • After that it is a "two-way communication channel where each side can, independently from the other, send data at will" over one TCP connection.
  • The protocol exists because the alternative was "abusing HTTP through polling", with a connection per message and the overhead that implies.
  • The open connection lives in one process's memory, so a message for one reader has to reach the exact machine holding that reader's socket.
  • What it costs: statelessness, which is what made the fleet of module 13 possible - and the browser will not reconnect for you, while server-sent events will.

1. The mental model: a request that never ends

Everything in this course so far has assumed a request arrives, is answered, and is forgotten - which is what lets any machine in a fleet serve any request. A WebSocket breaks that assumption deliberately. RFC 6455 was written because bidirectional traffic on the web had been built by abusing HTTP: polling on a timer, or holding a request open and answering it late, both of which spend a connection per message and put a floor under latency that is the polling interval.

What replaces it is a single connection that both ends may write to whenever they like. The consequence for your service is not that messages are faster. It is that a reader is now represented by an object in the memory of one particular process, and that process is the only one that can reach them.

2. The mechanism

The handshake, and what the 101 changes

The client sends a normal GET carrying Upgrade: websocket, Connection: Upgrade and Sec-WebSocket-Key, a randomly chosen 16-byte nonce in base64. The server answers 101 Switching Protocols with Sec-WebSocket-Accept, the base64 SHA-1 of that key concatenated with the fixed string 258EAFA5-E914-47DA-95CA-C5AB0DC85B11. The value is not a secret and not authentication; it is proof that the peer read the WebSocket handshake rather than echoing a header it did not understand.

From the 101 onwards the connection carries frames, not messages with headers, and closing is symmetric: either peer sends a Close control frame, the other replies with one, and the TCP connection is then closed. A connection that vanishes without that exchange is an abnormal closure, and your application will see plenty of them - phones change network, laptops sleep, intermediaries time out idle connections.

The socket pins a reader to a process

Here is the part that reshapes the architecture. A price update is produced by some service that has no idea which of your twenty web processes is holding a given reader's socket. There is no route to a connection, because a connection is not addressable - it is a file descriptor in one process. So a fleet serving WebSockets always grows a second layer: every process subscribes to a broker, and delivering to a reader means publishing an event that reaches the process that happens to own them.

3. The trade-off: often you wanted server-sent events

Before paying for all of that, check the direction of the traffic. A dashboard, a notification feed, a progress bar and a live score are one-way: the server pushes and the client only reads. That is what server-sent events are for, and the properties are the ones you would otherwise write yourself. The connection is one-way, "so you can't send events from a client to a server". Reconnection is built in: "by default, if the connection between the client and server closes, the connection is restarted", the stream can set the retry delay with a retry field, and an id field lets the browser resume with the last event it saw.

The historical objection to server-sent events was the connection cap: over HTTP/1.1 the limit is six per browser and domain across all tabs, which a user with three tabs open exhausts. Over HTTP/2 that disappears - the maximum number of simultaneous streams is negotiated and defaults to 100 - so on a modern stack the objection is largely spent. Reach for a WebSocket when the client genuinely needs to send too: a chat, a collaborative editor, a game.

An open socket makes a deploy visible to users. A rolling restart of twenty processes disconnects every reader they hold, all of them reconnect at once, and the reconnect storm lands on a fleet that is one process short. This is where the graceful shutdown of module 11 stops being hygiene: drain by refusing new connections first, close existing ones with a Close frame and a reason, and give the client a randomised backoff so the herd arrives spread out rather than together.

Why does a WebSocket fleet almost always need a broker behind it?
A connection is a file descriptor in one process and cannot be addressed from outside it, so the producer has to broadcast and let the owning process deliver. The first two invent guarantees the protocol never offered, and the fourth misreads the handshake, which is complete before the connection is useful and is never shared.
A live dashboard needs updates pushed but sends nothing upward. What fits?
One-way traffic is exactly the case server-sent events were designed for, and they hand you reconnection and a resume point at no cost. A WebSocket also works but you write the reconnect yourself; long polling reintroduces the overhead RFC 6455 was written to remove; and a browser cannot make a native gRPC call at all.
