Every test buys one class of defect, and the price is feedback time

working 9 min The gate a change passes before the pipeline of lesson 1306 will move it. · Fowler - TestPyramid

The one-minute version

  • The pyramid makes two claims and no more: write tests at different granularities, and have fewer of them the higher you go.
  • The reason is cost, not purity. End-to-end tests are brittle, expensive and slow, and their non-determinism "can undermine trust".
  • A contract test is the cheap way to buy the expensive confidence: the consumer writes what it needs and the provider runs it.
  • That is the missing mechanism lesson 0600 named. Nothing in your build knows a caller broke, unless a caller's expectations are in your build.
  • What it costs: a flaky test is worse than no test, because it teaches the team that red does not mean broken.

1. The mental model: granularity is a budget

What the pyramid actually claims

The picture is older than most of the arguments about it, and its content is small. Fowler states two assertions: write tests with different granularity, and "the more high-level you get the fewer tests you should have". Mike Cohn's original three layers were a broad base of unit tests, a middle layer of tests through the service layer, and a narrow top driven through the user interface.

The reason for the shape is economic and it is stated as such. Tests that run end to end are "brittle, expensive to write, and time consuming to run", and they suffer from "non-determinism problems, which can undermine trust". The failure mode has a name: record a few user journeys, replay them, and you arrive at an ice-cream cone, an inverted distribution where the slowest and least reliable tests are the ones you own most of.

2. The mechanism: what each layer can see

Four purchases, four defects

The practical version names them. A unit test verifies one unit of your codebase with "the narrowest scope of all the tests", replacing its collaborators with doubles at the boundary. An integration test exercises the parts that live outside your application: a database, a filesystem, another service. An end-to-end test drives the whole integrated system and gives "the biggest confidence when you need to decide if your software is working", which is why the advice attached to it is to keep the number "to a bare minimum".

The fourth is the one that answers a question this course has already asked twice. In consumer-driven contract testing, "consumers of an interface write tests that check the interface for all data they need" and publish those tests so the providing team can fetch and run them. Read that beside the warning at the end of lesson 0600: a compiler will not tell you that removing a response field breaks a caller, because the caller is not in your build. A contract test is precisely the move that puts the caller in your build, without putting the caller's deployment in it.

Running them, and finding what only concurrency shows

The mechanics are ordinary. Go's testing package takes functions of the form TestXxx(*testing.T) in files ending _test.go, with t.Run for subtests and t.Parallel, which "signals that this test is to be run in parallel with (and only with) other parallel tests". That last one matters more here than it looks. Lesson 1301's race detector only finds races on paths that actually execute, so parallel tests run under -race are one of the few ways a race in a rarely taken branch is ever observed before a customer observes it.

3. The trade-off: an unreliable test costs more than a missing one

Every test is also a liability. It has to be maintained when the code moves, it lengthens the loop between writing a line and learning whether it works, and if it fails for reasons unrelated to the change it teaches the team a lesson you cannot unteach: that a red build is a thing you rerun. Fowler's word for it is trust, and once the suite has lost it, the expensive tests at the top are doing negative work, because they are consuming the minutes that made the fast ones useful and are no longer believed when they fail.

So the practical rule is not "write more tests" but "for each defect you are afraid of, buy it at the lowest layer that can see it". Most fears are cheaper than they look. A wrong calculation is a unit test, a wrong query is an integration test, and a broken promise to another team is a contract test. What is genuinely left for the top of the pyramid is small: that the pieces are wired together at all, and that the one journey you cannot afford to break still runs.

Coverage measures which lines were executed, not which behaviours were asserted, so a suite that runs every line and checks nothing reports the same number as one that checks everything. It is a useful floor and a dishonest target: the moment it becomes a threshold a build enforces, the cheapest way to meet it is a test that calls the code and asserts nothing at all.

Check yourself

Retrieval practice

Answer from memory before revealing.

A provider removes a response field its own tests never referenced. Which layer catches it first?
The contract is the only artefact that records what somebody else depends on, and it is evaluated on the provider's own build. Integration tests reach the database, which never knew about the response shape, unit tests were updated in the same commit as the removal, and the end-to-end suite finds it only if some journey happens to read that field.
Why does the pyramid put fewer tests at the top rather than more?
The argument is cost and reliability: expensive to write, slow to run, and non-deterministic in a way that undermines trust in the whole suite. Some duplication is real but is not the stated reason, broad tests reach more branches rather than fewer, and nothing in the pyramid depends on where the data comes from.
