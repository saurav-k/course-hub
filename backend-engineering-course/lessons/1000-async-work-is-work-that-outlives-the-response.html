When the work outlives the response, it has to leave the request path

foundation 9 min The first module where the caller stops waiting. · RFC 9110 §15.3.3 - 202 Accepted

The one-minute version

  • A response is a promise about a result. When the work takes longer than the caller will wait, that promise cannot be kept, so the honest move is to promise something smaller.
  • RFC 9110 defines 202 as "accepted for processing, but the processing has not been completed", and states the consequence plainly: "There is no facility in HTTP for re-sending a status code from an asynchronous operation."
  • The mechanism is a durable handoff: a producer writes a job, a broker stores it, a worker takes it later. All three can restart without losing the job, which is the whole difference from a background thread.
  • Put identifiers in the job, never the state. Sidekiq states it as a rule - save simple identifiers and look the objects up in the worker - because the job outlives the memory that created it.
  • What it costs: the caller no longer learns the outcome from the response, so you owe them a status resource, and every failure after the 202 is yours to detect.

1. The mental model: a deadline the work does not respect

The response is a promise you may not be able to keep

A synchronous handler makes a bet: that the work will finish before the caller, the load balancer, the proxy and the browser all stop caring. Encoding a video, rebuilding a report, sending ten thousand emails and reindexing a catalogue all lose that bet, and they lose it in a specific way - the connection is held open, a worker thread or goroutine is pinned to it, and the caller sees a timeout that tells them nothing about whether the work happened.

The important part is that this is not a performance problem with a performance fix. Making the encoder twice as fast moves the boundary and does not remove it. The mismatch is structural: the lifetime of the work and the lifetime of the connection are set by different things, and no amount of tuning makes one a function of the other.

What 202 promises, and what it refuses to

HTTP already has the smaller promise. RFC 9110 §15.3.3 defines 202 Accepted as meaning the request "has been accepted for processing, but the processing has not been completed", and adds that it "might or might not eventually be acted upon, as it might be disallowed when processing actually takes place". The specification calls the response "intentionally noncommittal" on purpose: its whole point is to let a server take a request for some other process without holding the user agent's connection open until that process is done.

Then comes the sentence worth memorising, because it is the entire design consequence in one line: "There is no facility in HTTP for re-sending a status code from an asynchronous operation." The protocol will not deliver the outcome later. That is why the same section says the 202 body ought to describe the request's current status and point to, or embed, a status monitor. A 202 with an empty body is not a smaller promise, it is no promise at all.

2. The mechanism: three parties and a record that survives all of them

A background thread is not a queue

The cheapest-looking version of this is to answer the request and finish the work on a spare thread, in a goroutine, or on an event loop. It is the wrong mechanism, and the reason is not style. That work exists only in the memory of one process. A deploy, a crash, an out-of-memory kill or a scale-in event destroys it with no record that it was ever owed, so the system cannot tell the difference between work that finished and work that evaporated. There is nothing to retry because there is nothing to retry from.

A queue replaces that with a durable record and three separable parties. The producer writes a job and gets an acknowledgement that it is stored. The broker holds it, on disk or replicated across failure domains - Amazon SQS, for instance, stores a message redundantly across multiple availability zones before it acknowledges the send. The consumer asks for work when it has capacity. Each can be restarted, redeployed and scaled without the other two knowing, because the only thing they share is a record neither of them holds in memory.

Put identifiers in the job, not state

A job is serialised at one moment and executed at another, and everything module 04 said about a wire contract applies to it unchanged: it is a message between two programs that do not deploy together. Sidekiq's guidance is the sharp version - "Don't save state to Sidekiq, save simple identifiers. Look up the objects once you actually need them in your perform method." A serialised order object in the payload is a snapshot that is already stale when the worker opens it, and it will be a different shape after your next deploy while the old jobs are still in the queue.

enqueue.py · the payload is identifiers and a version, not an object
def request_report(session, account_id: int, period: str) -> str:
    report = Report(account_id=account_id, period=period, state="pending")
    session.add(report)
    session.flush()          # the id exists, the transaction has not committed
    enqueue("build_report", {"report_id": report.id, "v": 1})
    session.commit()
    return report.public_id

That snippet is correct about the payload and wrong about the ordering, deliberately, because it is the mistake lesson 1004 is about: the enqueue and the commit are two separate writes and a crash between them loses one of the two. Hold the shape in mind and read the ordering as a defect to be paid for later.

3. The trade-off: you moved the failure, you did not remove it

The synchronous version had one virtue that is easy to undervalue: the caller learned the outcome. A 500 arrived at the person who could do something about it, and the work either happened inside the response or visibly did not. Once you return a 202, every failure after that point is invisible to the caller and invisible to you unless you built the machinery to see it. Module 11 is where that machinery is named, and it is not optional - it is the second half of the cost of this page.

The rest of the bill is a queue's own operational surface. A backlog is now a thing that can grow, so the depth of the queue and the age of the oldest message become numbers somebody has to watch. Workers are a fleet with their own deploys and their own memory limits. The job payload is a published contract with old versions still in flight during a rollout. And the ordering between the enqueue and the database write is a correctness question with a real answer, which is lesson 1004.

A 202 with no status resource is the most common way this design is shipped broken. The caller is told the request was accepted and given nothing to ask about it with, so their only recovery from a failed job is to send the request again - which is a duplicate, arriving through the front door, for a system that has not yet been made idempotent. The specification asks for a status monitor in the same paragraph that defines the status code, and it asks for a reason: 202 is the one success code that guarantees the caller will need to come back.

Why is finishing the work on a background thread not a substitute for a queue?
The queue's contribution is a durable record: after a crash, a deploy or a scale-in, the job is still there to be taken again. A thread can certainly outlive the response, and often does, which is what makes the pattern tempting. Speed is not the difference either - a thread on the same box may well be quicker. And a fleet of application processes does scale across machines; what it cannot do is remember what any dead member of it owed.
RFC 9110 says a 202 response ought to point to a status monitor. Why does it have to?
The specification states it directly - there is no facility in HTTP for re-sending a status code from an asynchronous operation - so the outcome can only reach the caller if the caller comes back and asks. There is no rule that a 202 body be a resource, cacheability is governed by the method and the freshness headers of module 02 rather than by a monitor link, and a retry made safe is lesson 0605's stored key, which is a different mechanism entirely.

How this connects

  • Ahead, a queue delivers at least once takes the durable handoff apart and shows what the broker actually promises, which is less than most designs assume.
  • Ahead, enqueue and commit are two writes is where the deliberately wrong ordering in the code above gets paid for.
  • Behind you, status codes are three families is where 2xx was defined as a claim about the request rather than about the work, which is what makes 202 legal.
Your teacher. Take the slowest endpoint you own and write down what its caller would have to poll if it returned a 202 tomorrow: the URL, the states it can report, and how a caller learns that the job died. Then ask the agent which of those three you already have.

Primary source to go deeper
