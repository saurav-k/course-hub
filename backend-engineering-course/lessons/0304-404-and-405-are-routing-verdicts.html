Module 03 · Routing · Lesson 0304

The router decides no such resource against wrong verb on a real one, and a 405 owes an Allow field

working 8 min The two answers no handler can give. · RFC 9110 §15.5.6 - 405 Method Not Allowed

The one-minute version

  • When nothing matches, no handler ran, so the answer has to come from the router. These two status codes are its verdicts.
  • 404 means the origin server found no current representation for the target, or is not willing to say one exists.
  • 405 means the method is known to the server but not supported by this resource, which the router can only say because it kept the method half of every route.
  • RFC 9110 makes the Allow field a MUST on a 405, listing the methods that resource does support. An empty value is legal and means none.
  • What it costs: telling 404 and 405 apart tells a stranger which of your URLs are real, and sometimes that is a leak rather than a courtesy.

1. The mental model: only the table knows

Ask why a handler cannot return 405 and the answer is immediate: the handler for that method does not exist, so there is nobody to ask. The router is the one component that holds the whole route table, which means it is the only one that can compare the request against every registration and say which half failed. Lesson 0300 said a route is a pair; this is what the pair pays for.

The two verdicts differ in exactly one fact. RFC 9110 defines 404 as the origin server not finding a current representation for the target resource, and 405 as the method being known by the origin server but not supported by the target resource. So 405 asserts that the resource is real. It is a stronger statement than 404, and a router that discarded the method half of its patterns cannot make it.

2. The mechanism: one extra lookup, and one required field

404: no current representation

The router walked the tree, ran out of children, and no leaf held a handler. The specification is careful about what this does and does not say: a 404 does not indicate whether the absence is temporary or permanent, and 410 Gone is preferred when the origin server knows the condition is likely to be permanent. It also stays honest about intent, since 404 covers a server that found a representation and is not willing to disclose that one exists.

405: the resource is real, the verb is not

Producing a 405 costs the router one more question. Go's ServeMux does it in the plainest possible way: when no node matched with the request's method, it asks the tree which methods would have matched this host and path. A non-empty answer is a 405 and an empty one is a 404. That second lookup is the entire implementation, and it is only possible because the method is a level of the tree rather than a field the handler reads.

The Allow field: not optional

RFC 9110 says an origin server MUST generate an Allow header field in a 405 response containing the target resource's currently supported methods, and may send it in any other response. Two details are worth carrying. An empty value is legal and means the resource allows no methods, which is what a temporarily disabled resource looks like. And a proxy MUST NOT modify the field, so what you send is what the client reads.

3. The trade-off: an honest verdict is also a disclosure

The distinction you have just been asked to make correctly is a distinction an attacker can use. A service that answers 405 for /admin/users/42 and 404 for /admin/users/43 has confirmed which user identifiers exist, without ever serving a byte of either. Enumeration of that kind needs no credentials and leaves ordinary-looking traffic in your logs.

This is why the specification's phrasing on 404 is written the way it is. A server that is not willing to disclose that a representation exists is entitled to answer 404, and that permission is the escape hatch for exactly this problem. The rule that follows is a boundary rule rather than a global one: be precise on the public surface where a client is trying to use your API correctly, and be uniform behind authentication, where a wrong answer is more likely to be probing than a mistake.

The second cost is smaller and more common. Allow is a claim about this resource at this moment, so it has to be produced from the route table rather than typed into a constant. A hand-written Allow: GET, POST beside a resource that has since gained PATCH is a specification-conformant lie, and it will be believed.

Watch what your monitoring does with these. A 404 is a client error, so it is not an availability signal, and a dashboard that alerts on it will page somebody every time a crawler guesses a URL. A sudden change in the rate of 404s is worth knowing about - it is what a broken deploy or a mistyped link looks like - but the absolute count is noise, and treating it as an error budget burns the budget on strangers.

Check yourself

Retrieval practice

Answer from memory before revealing.

What does a 405 assert that a 404 does not?
405 says the method is known to the server but not supported by this resource, which asserts the resource is there. A retry of the same request gets the same answer, a method unknown to the server everywhere is 501 rather than 405, and a missing credential is 401.
Your 405 response carries no Allow field. What is wrong?
The specification requires the field on every 405 and permits it on any other response, so OPTIONS is a use rather than the rule. A proxy must not modify the field, which is a reason to send it rather than a condition on sending it, and 501 is for a method the server does not implement at all.
