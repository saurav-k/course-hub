Module 06 · API design · Lesson 0601

The uniform interface is already defined, so a verb in the path gives away what the network knows

foundation 8 min Why the noun goes in the URI and the verb does not. · RFC 9110 §3.1 - Resources

The one-minute version

  • RFC 9110 states the split as a design goal: HTTP separates identifying the resource from the semantics of the request, and puts the semantics in the method.
  • So a URI names a thing and a method says what to do with it. POST /orders/42/cancel puts the verb in the noun's half.
  • The cost is not aesthetic. Caches, proxies and client libraries read the method and nothing else to decide whether a request is safe, retryable or storable.
  • Fielding names the uniform interface as REST's central distinguishing feature, and names its price in the same paragraph: standardised messages are less efficient than bespoke ones.
  • What it costs: some operations genuinely are not a create, read, update or delete, and forcing them into one is worse than an honest custom method.

1. The mental model: identity and intent are two questions

A resource is whatever you decided to name

RFC 9110 is unusually direct about this. Section 3.1 says the target of a request is a resource, that HTTP does not limit what a resource may be, and then states the goal plainly: one design goal of HTTP is to separate resource identification from request semantics, which is made possible by putting the semantics in the method. Two questions, two slots, and each slot answers exactly one.

That leaves the naming question genuinely open. A resource is not a database table and not a class. It is any concept you are willing to give a stable name and a representation, so a shopping basket, a search result set, a nightly report and an order's cancellation record can all be resources even though none of them is a row. The test is not "does this exist in my schema" but "will I still be willing to name this in a year", which is the promise from lesson 0600 applied to the URI itself.

2. The mechanism: what an intermediary does with the method

The guarantee is read by software that never saw your docs

Put the verb in the path and the request still works. What changes is what everything between the client and your handler is allowed to assume. A shared cache may store a GET response and serve it to the next client, because GET is defined as safe and cacheable. A client library may repeat an interrupted PUT, because RFC 9110 permits an automatic repeat only when the method is idempotent. None of that machinery reads your path, and none of it can be told what your path means.

When an action really is not a noun

Some operations resist the shape honestly. Cancelling an order, retrying a payment and rebuilding a search index are actions with side effects that no member URI plus a standard method expresses without contortion. The usual bad fix is a boolean in a PUT body, which makes the whole member's replacement semantics depend on one field, and quietly makes the update non-idempotent.

Google's published guidelines take the honest route and name it. AIP-136 defines a custom method, requires the URI to carry a colon followed by the verb, as in /v1/orders/42:cancel, requires POST when the call has side effects and GET when it only retrieves, and says custom methods should only be used for functionality that cannot easily be expressed by the standard ones. The colon matters: it keeps the path segment a noun and marks the verb as an exception rather than hiding it as another segment.

3. The trade-off: uniformity costs efficiency, and Fielding says so

The uniform interface is not free, and the argument for it is not that it is elegant. Fielding's dissertation names it as the central feature that distinguishes REST from other network-based styles, and in the same passage names the price: a uniform interface degrades efficiency, because information is transferred in a standardised form rather than one specific to an application's needs. You will sometimes make several round trips where one bespoke call would have done, and you will sometimes send fields a particular caller does not want.

That is a real cost and it is the reason bespoke shapes keep being invented. What you buy for it is the column of guarantees above: behaviour supplied by caches, proxies, client libraries and load balancers that you did not write, cannot break, and do not have to document. The trade is worth making by default and worth breaking deliberately, which is exactly what a named custom method is.

A tidy URI is not the same claim as REST, and it is worth being exact about which one this page defends. Fielding's uniform interface has four constraints, and the fourth is hypermedia as the engine of application state: the client discovers what it may do next from links in the responses. Almost no service in industry does that, this course does not teach you to, and calling a well-shaped URI space plus the standard methods "RESTful" is a widely accepted stretch. Take the first three constraints because they pay for themselves, and do not claim the fourth if you did not build it.

Answer from memory before revealing.

What is actually lost when a read is expressed as POST /getOrder?
Safe, idempotent and cacheable are properties of the method, and every intermediary reads them from there, so a POST-shaped read forfeits storage, reuse and automatic retry. Validators are independent of the method, a path may name any resource whatever the method is, and the extra body parse is real but trivial beside the lost network behaviour.
Under AIP-136, how is a genuine action written when no standard method fits?
The colon form, as in orders/42:cancel, keeps every path segment a noun and marks the verb as the exception it is. A query parameter hides the action inside the identity, an extra segment is exactly the shape the guideline exists to avoid, and inventing a method token means every intermediary treats it as unrecognised.
