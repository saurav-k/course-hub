A self-contained token buys you the lookup and sells you the revocation

working 9 min The second shape of the credential, and the bill it moves. · RFC 7519 - JSON Web Token

The one-minute version

  • A JWT carries its claims in the credential itself, signed, so a server can decide who is calling without reading any store.
  • The signature is the entire security of the scheme: RFC 7519 says the contents cannot be relied upon in a trust decision unless they have been cryptographically secured.
  • Two classic breaks are about the alg header, not the maths: setting it to none, and switching RS256 to HS256 so the public key becomes the shared secret.
  • Verification is a checklist, not a call: your allowed algorithms, the signature, exp and nbf, then iss and aud - and a token addressed to someone else must be rejected.
  • What it costs: you cannot take it back. A revoked permission keeps working until the token expires, so token lifetime is the length of that window and you choose it deliberately.

1. The mental model: the claims travel with the request

Three base64url parts, and only the third one matters

A JWT is a sequence of URL-safe parts separated by period characters: a header naming the algorithm, a payload of claims, and a signature over the first two. The first two parts are encoded, not encrypted. Anyone holding the token can read every claim in it, which is worth saying out loud because engineers put things in tokens that they would not print in a log.

The claims themselves are a small registered set (RFC 7519 §4.1): iss names who issued it, sub names who it is about, aud names who it is for, exp is the time on or after which it MUST NOT be accepted, nbf the time before which the same holds, iat when it was issued, and jti a unique id for it. Each is a normal JSON field with no protection of its own; the signature is what makes any of them believable, and §11.1 says so directly.

2. The mechanism: verification is an ordered checklist

The two famous breaks are both in the header

The classic JWT failures are not attacks on cryptography. RFC 8725, the JWT best-practices document, records them as deployment defects: the algorithm can be changed to "none" by an attacker, and some libraries would trust this value, and an RS256 token can be re-signed as HS256 so that a library validates it using the RSA public key as the HMAC shared secret. In the second case the attacker needs only a public key, which is public.

Both have the same root cause: the library asked the token which algorithm to use. The fix is stated as a requirement - libraries MUST enable the caller to specify a supported set of algorithms and MUST NOT use any other algorithms. You name the algorithms; the token does not get a vote. Two more from the same section are worth holding: the relying party MUST validate the audience value and reject a token not addressed to it, and different kinds of JWT in one system need mutually exclusive validation rules, so an identity token can never be spent as an access token.

You cannot un-issue what you did not keep

Now the bill. A password change, a sacking, a leaked device: with a session you delete a row and the next request arrives as a stranger. With a self-contained token there is no row. RFC 7009, which defines OAuth's revocation endpoint, sets out the same fork: an access token may be self-contained, so that a resource server needs no further interaction with an authorization server, or it may be a handle that requires a lookup on every use. In the first case the RFC notes that immediate revocation needs some non-standardised back-channel between the two servers.

The practical compromise is the third option the same section names: issue short-lived access tokens refreshable at any time, which allows the authorization server to impose a limit on the time revoked when access tokens are in use. Access tokens live minutes, refresh tokens live longer and are checked against real state each time they are spent. RFC 7009 states the general law plainly: the cost of revocation in terms of required state and communication overhead is ultimately the result of the desired security properties.

3. The trade-off, stated as a choice

Neither shape is the safe default. A session is right when revocation must be immediate and the traffic can afford a read: anything with money, admin powers, or a support team who need to lock an account while a customer is still on the phone. A token is right when verification has to work without a shared store: many services, no common database, or an edge that must not call home on every request.

What is never right is a long-lived self-contained token with no plan for withdrawal, because that is the session design with the one operation you will eventually need quietly missing. If you find yourself adding a deny-list of revoked token ids checked on every request, notice what you have built: a session store, reached by jti, with the signature now paying for nothing.

A token is a bearer credential, so possession is the whole of the proof and there is nothing in the token tying it to the client that was given it. RFC 9700 therefore recommends that authorization and resource servers use mechanisms for sender-constraining access tokens to prevent misuse of stolen and leaked ones. Until you have done that, every log line, error report and browser extension that touches the token is holding a working credential.

Check yourself

Retrieval practice

Answer from memory before revealing.

Why does accepting the token's own alg header break verification?
Letting the token choose the algorithm lets the attacker choose it: none removes verification, and HS256 turns the published RSA public key into the shared secret. The header is covered by the signature, which is why the substitution has to change the algorithm rather than merely the value; and encoding is not the issue, since base64url decodes deterministically.
A user is banned. A 60-minute self-contained access token was issued 5 minutes ago. What happens?
Self-contained means the resource server asks nobody, so the ban is invisible to it until exp passes. Cascading revocation is real but it reaches tokens the authorization server can still see; and the signature stays valid, because nothing about the ban changed the key it was signed with.

Primary source to go deeper

RFC 8725 is the one to read: it is short, it is written as threats paired with requirements, and every item in it is a defect somebody shipped. RFC 7519 is the reference for the claim names, and RFC 7009 §3 is two paragraphs that frame the revocation trade-off better than most articles about it.
