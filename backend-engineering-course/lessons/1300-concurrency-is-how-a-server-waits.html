Concurrency is a structure for waiting, and parallelism is the hardware

working 9 min The first of two pages on what happens inside one process before the fleet is drawn. · Effective Go - Concurrency

The one-minute version

  • A request handler is mostly not computing. It is blocked on a database, a downstream service, or the network.
  • Concurrency is a structure that overlaps those waits. Parallelism is a count of cores. A service can need one and not the other.
  • The unit of cost is the occupied worker, not the used CPU, so the ceiling is the pool size divided by how long each request holds one.
  • Three shapes: a thread per request, goroutines multiplexed onto threads, and one event loop running one task at a time.
  • What it costs: an event loop has no preemption, so one function that computes instead of awaiting stops every other request in the process.

1. The mental model: the worker is held, not busy

Waiting is the dominant term

Read a typical handler honestly. It parses a body, which is microseconds. It asks the database for a row and waits. It calls a downstream service and waits. It serialises a response, which is microseconds again. Between the first and last line, the process it runs in has almost nothing to do, and yet something has been reserved for the whole duration: a thread, a coroutine, a connection, a slot in a pool. That reservation is the resource that runs out.

This is why CPU utilisation is such a poor guide to a service's ceiling. A machine reporting 6% CPU can be entirely unable to accept another request, because every worker it has is parked inside a socket read. The measurement that matters is how many requests are in flight at once, and that is set by two numbers: how fast they arrive, and how long each one holds a worker.

in flight = arrival rate × hold time Read as: in a steady state, the number of requests being worked on at any instant equals how many arrive each second multiplied by how many seconds each one occupies a worker. At 500 requests a second and 200 milliseconds each, that is 500 × 0.2 = 100 requests in flight. If the pool has 32 workers, the pool is the binding constraint and the extra 68 are queued or refused.

2. The mechanism: three ways to overlap a wait

A thread per request, and why it stops

The oldest shape gives each connection an operating-system thread and lets it block. It is the easiest to reason about, because the code reads top to bottom and the kernel handles the interleaving. What limits it is that a thread is expensive in a way a request is not: it carries a stack sized in megabytes and a scheduler entry, so a few thousand of them is a real cost in memory and in context switching, long before the CPU is busy.

Goroutines, which are threads the runtime owns

Go keeps the blocking style and moves the cost. A goroutine is, in the language's own words, a function executing concurrently with other goroutines in the same address space, lightweight, "costing little more than the allocation of stack space", with stacks that start small and grow on demand. The scheduling claim is the one that matters here: goroutines "are multiplexed onto multiple OS threads so if one should block, such as while waiting for I/O, others continue to run". The blocking read is still written as a blocking read, and the runtime turns it into a wait that costs one small stack rather than one thread.

One event loop, one task at a time

Python's asyncio takes the other route: keep one thread and make the waiting explicit in the syntax. The documentation is unusually blunt about what that buys. Event loops use cooperative scheduling: "an event loop runs one Task at a time. While a Task awaits for the completion of a Future, the event loop runs other Tasks, callbacks, or perform IO operations." One task at a time is concurrency without parallelism, and for a handler that waits for all but a millisecond or two of its life that is the entire win.

two voices, same shape · the wait is what overlaps, not the work
// Go: the call blocks, the runtime does not.
for _, id := range ids {
    go func(id string) { results <- fetch(ctx, id) }(id)
}

# Python: the wait is spelled out, one thread throughout.
results = await asyncio.gather(*(fetch(session, i) for i in ids))

Threads in CPython, and the one thing the GIL does not block

CPython carries a global interpreter lock, which the language glossary defines as the mechanism that assures "that only one thread executes Python bytecode at a time". That sentence is usually quoted as a reason threads are useless in Python, and the next sentence in the same entry is the one that is usually dropped: "the GIL is always released when doing I/O". So a thread pool in CPython is a real answer for a service that waits, and no answer at all for one that computes. Python 3.13 added a build in which the lock can be disabled, specified in PEP 703, which changes the second half of that sentence and not the first.

3. The trade-off: cooperative scheduling has no interrupt

The event loop's guarantee is also its failure mode. Control returns to the loop only when a task awaits, so a task that computes for 300 milliseconds without awaiting holds the entire process for 300 milliseconds, and every other in-flight request pays it. The same applies to any library call that blocks the thread rather than yielding: one ordinary database driver used inside an async handler converts a concurrent server into a serial one, and nothing reports it except the latency of every other request rising together.

Go trades differently. Its runtime can move work between threads and preempt a long-running goroutine, so a single expensive function degrades the process rather than stopping it. In exchange, blocking code and concurrent code look identical on the page, which means a call that quietly holds a lock or a database connection is invisible in review, and lesson 1301 is about exactly what happens then.

Neither model raises the ceiling of whatever you are waiting on. A service that overlaps 500 waits on a database with 20 connections has not become concurrent, it has moved the queue from its own accept backlog into the connection pool, where it is harder to see and where the timeout that fires is somebody else's. Before adding concurrency, find the smallest pool on the path and ask what it is.

Check yourself

Retrieval practice

Answer from memory before revealing.

A service reports 6% CPU and refuses new connections. What is the most likely binding constraint?
Low CPU with no capacity is the signature of held workers rather than busy ones: the pool size divided by the hold time is the ceiling, and neither term is CPU. A collector pause raises CPU rather than lowering it, a full accept queue is a symptom of the same exhaustion rather than its cause, and a saturated link would show as bytes moved, which 6% CPU does not suggest.
Why does a thread pool still help an I/O-bound service written in CPython?
The glossary entry says both things: only one thread executes bytecode at a time, and the lock is always released during I/O, so waiting threads do not hold it. Simultaneous bytecode is precisely what the lock prevents outside a free-threaded build, a blocked thread needs no core, and no conversion of blocking calls happens anywhere.

Practice about 10 minutes, with paper

Practice 1working

A service takes 900 requests a second at peak. Each request holds a worker for 250 milliseconds: 10 of its own work, then a 60 millisecond database read, then a 180 millisecond call to a downstream service, the two calls made one after the other. The worker pool holds 200.

Find how many requests are in flight at peak, whether the pool covers it, and what the pool needs once the database read and the downstream call are made concurrently instead of sequentially.

Hint

In flight is arrival rate times hold time. When two waits overlap, the pair costs the longer of the two rather than their sum.

Show the worked solution
  1. Convert the hold time to seconds. 250 ms is 0.25 s.
  2. Multiply by the arrival rate. 900 × 0.25 = 225 requests in flight at peak.
  3. Compare against the pool. 200 workers against 225 in flight, so the pool is short by 25 and those requests queue or are refused. The service is capacity-bound while its CPU is nearly idle.
  4. Overlap the two waits. The new hold time is 10 + max(60, 180) = 190 ms, because the two calls now wait together rather than in turn.
  5. Recompute. 900 × 0.19 = 171 in flight, which the pool of 200 covers with 29 workers spare.

Sanity check. The relation is linear in hold time, so the two numbers must move by the same fraction: 250 to 190 is a cut of 24%, and 225 to 171 is a cut of 24%. If your two percentages differ, one of the multiplications is wrong.
