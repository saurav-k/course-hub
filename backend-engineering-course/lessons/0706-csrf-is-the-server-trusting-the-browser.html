Module 07 · Auth and security · Lesson 0706

The browser attaches the cookie whoever asked, so presence proves nothing

working 8 min The last threat, and the one that needs no injected code. · OWASP - CSRF Prevention Cheat Sheet

The one-minute version

  • The threat first. Another site causes your reader's browser to send a request to you. The browser attaches the session cookie, because browser requests automatically include all cookies.
  • Your server sees a well-formed, fully authenticated request. Nothing about it is abnormal, so authentication cannot distinguish it from one the user meant.
  • The attacker cannot read your response - the same-origin policy still holds - and does not need to, because the damage is the write.
  • The defence is a secret the attacker's page cannot obtain: a synchroniser token, or a custom header that a cross-site form cannot set.
  • What it costs: SameSite is a strong default and OWASP is explicit that it does not replace a proper CSRF defence, so it is the second layer rather than the first.

1. The threat: authentication answers the wrong question

The cookie says who, and nobody asked who sent it

A cross-site request forgery, in OWASP's words, occurs when a malicious web site, email, blog, instant message, or program tricks an authenticated user's web browser into performing an unwanted action on a trusted site. The mechanism is one sentence long: browser requests automatically include all cookies, including session cookies, and the browser does not care which page caused the request.

Set that beside lesson 0700 and the shape becomes clear. Your server asks two questions - who is this, and may they do it - and both get the right answer. The user is real, and they are allowed to transfer their own money. The question nobody asked is whether the user intended this request, and HTTP offers no field that answers it. That is the gap, and it exists for every application that authenticates with something the browser sends on its own.

2. The defence: require something the other site cannot know

A token that lives where a cross-site page cannot look

Since the credential arrives automatically, the fix is to demand a second thing that does not. The synchroniser token pattern issues an unpredictable value, unique per user session, and requires it back in the body or a header of every state-changing request. The attacker's page can cause a request but cannot read your pages, so it cannot learn the value. OWASP adds one constraint that is easy to miss: the token is generated using cryptographically secure methods rather than stored in cookies - a token delivered as a cookie is attached automatically too, which defeats the point.

That last sentence explains why the naive double-submit pattern is weak. It puts the same value in a cookie and in the form, and compares them; but OWASP records that this is bypassable by an attacker who can write cookies on the target domain, which a sibling subdomain can do - the integrity gap RFC 6265 admitted in lesson 0701. The signed variant, an HMAC bound to the session, closes it.

For APIs called by script there is a cheaper defence. A custom request header cannot be set by a cross-site form, and adding one puts the request outside the CORS-safelisted set, so the browser preflights it and your policy from lesson 0205 decides. OWASP's reasoning is that requests with custom headers are automatically subject to the same-origin policy.

SameSite is a good default and not a defence

The SameSite attribute lets the browser withhold the cookie on cross-site requests. Strict sends it only for requests originating from the same site that set the cookie; Lax adds an exception for top-level navigations using a safe method, so following a link into your site still works while a cross-site POST does not; None restores the old behaviour and must be paired with Secure. Most browsers now treat Lax as the default when the attribute is absent.

It is genuinely valuable, and OWASP still refuses to call it sufficient: it is useful as a defense-in-depth control but it does not replace a proper CSRF defense in most deployments. Two reasons carry the argument. Same-site is measured at the registrable domain, so a compromised or careless sibling host is not cross-site at all; and any endpoint that changes state on a GET is still reachable under Lax, which is the sharpest form of OWASP's rule: do not use GET requests for state changing operations.

3. The trade-off, and the pair that closes the module

Token plumbing is real cost. Every form and every scripted write has to carry the value, single-page applications have to fetch it and refresh it, and a session that expires mid-form produces a failure that looks like a bug to the user. The pattern is worth it because the alternative is trusting a signal that was never about intent - but it is worth choosing per endpoint, and the endpoints that need it are exactly the ones that change something.

It is worth ending the module on the symmetry. Cross-site scripting is your reader's browser trusting content because your site served it. Cross-site request forgery is your server trusting a request because the reader's browser sent it. Two directions of one misplaced trust, and neither is fixed by making authentication stronger - which is the sentence lesson 0700 was written to earn.

Every defence on this page is downstream of lesson 0705. Script running on your origin can read your synchroniser token out of the page, set any custom header it likes, and issue same-site requests that SameSite was never meant to stop. So an unfixed XSS is not one vulnerability beside this one; it is the thing that removes all three defences at once, and it is the first bug to fix when both are open.

Check yourself

Retrieval practice

Answer from memory before revealing.

Why can the attacking site cause the request but not read the response?
The same-origin policy governs reading, not sending, which is exactly why forgery targets writes. Responses do not carry cookies back in that sense, bodies are not stripped on navigation, and the server answers normally - it saw nothing unusual, which is the whole problem.
Your session cookie is SameSite=Lax. Which endpoint is still forgeable?
Lax withholds the cookie from cross-site unsafe methods but sends it on a top-level navigation with a safe method, so a plain link reaches a state-changing GET with full authority. The other three are all unsafe methods and all blocked - which is why the rule is to keep state changes off GET rather than to rely on the attribute.

How this connects

  • Behind you, authentication answers who, authorization answers what named the automatic re-presentation this exploits.

Your teacher. List every endpoint in your service that changes state, and check the method on each - any GET on that list is forgeable today. Then ask the agent where your CSRF token comes from, and whether it is delivered in a cookie.
