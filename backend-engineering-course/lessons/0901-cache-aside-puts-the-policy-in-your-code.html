Module 09 · Caching · Lesson 0901

Cache-aside puts the fill policy in your code, and that is what keeps the cache optional

working 9 min The read path, and who is responsible for a miss. · Azure Architecture Center - Cache-Aside pattern

The one-minute version

  • A read pattern answers exactly one question: who goes to the database when the cache has nothing.
  • Cache-aside answers "the application", so the cache is a thing your code consults and can skip. It is also called lazy loading or a look-aside cache.
  • Read-through answers "the cache", so the loader lives behind it and every read goes through it whether it hits or not.
  • The consequence is a dependency, not a style: cache-aside degrades to a slow service and read-through degrades to no service.
  • What it costs: cache-aside puts the same six lines at every call site, only fills on demand so a cold cache is a cold start, and leaves an entry stale until something removes it.

1. The mental model: the cache is a party, not a layer

Three parties and one open question

Draw a read and there are three participants: the application that wants an answer, the cache that might have one, and the store that certainly does. The application always talks to somebody. The store always ends up consulted when nothing is stored. The only genuinely open question is who makes that second call, and the two available answers give the two patterns their names.

Facebook's memcache is the reference implementation of the first answer, and the paper names the shape precisely: memcache is used as a demand-filled look-aside cache. Demand-filled means nothing is put in until somebody asks for it and finds it missing. Look-aside means the web server, not the cache, is the one that goes to the database and puts the answer back (Nishtala et al., NSDI 2013, §2). AWS documents the same pattern under a third name, lazy loading, and Microsoft under a fourth, cache-aside. Four names, one mechanism.

2. The mechanism: six lines, and where they go

Cache-aside, written out in both voices

The pattern is short enough to write in full, and worth writing in full once because the interesting part is the error handling rather than the happy path. Every call to the cache is wrapped so that a failure is treated as a miss, never as an error to return.

users.go · the read path, with the cache as an optional dependency
func (r *UserRepo) Get(ctx context.Context, id int64) (User, error) {
	key := fmt.Sprintf("user:v1:%d", id)

	if raw, err := r.cache.Get(ctx, key); err == nil {
		var cached User
		if json.Unmarshal(raw, &cached) == nil {
			return cached, nil // hit
		}
	} // any cache error, and any unreadable entry, is simply a miss

	user, err := r.db.LoadUser(ctx, id)
	if err != nil {
		return User{}, err // a store error IS an error
	}

	if raw, err := json.Marshal(user); err == nil {
		_ = r.cache.Set(ctx, key, raw, 5*time.Minute)
	}
	return user, nil
}
users.py · the same path, and the same rule about which errors count
async def get_user(user_id: int) -> User:
    key = f"user:v1:{user_id}"

    try:
        raw = await cache.get(key)
    except CacheError:
        raw = None                      # unreachable cache reads as a miss
    if raw is not None:
        return User.model_validate_json(raw)

    user = await db.load_user(user_id)  # a store error propagates

    try:
        await cache.set(key, user.model_dump_json(), ex=300)
    except CacheError:
        pass                            # a failed set is one future miss
    return user

Three things in those twenty lines are the pattern rather than the language. The key is built from a stated shape, user:v1:<id>, which lesson 0903 will show is the whole basis of invalidation. The entry carries a lifetime, because without one nothing ever removes a wrong answer. And no error from the cache reaches the caller, because the moment one does, the optional dependency has become a required one and the property the figure above just proved is gone.

Read-through, and what moves

Read-through changes one thing: the loader is registered with the cache, and the application only ever calls the cache. On a miss the cache itself invokes the loader, stores the result, and returns it, so the application never learns whether it hit. Microsoft's guidance is explicit that this is a capability of the caching product rather than of the pattern - "for caches that don't provide this functionality, the applications that use the cache must maintain the data", which is precisely why cache-aside exists as a named pattern at all.

3. The trade-off: what demand-filling costs

Filling only on demand has two costs and they arrive at different times. The everyday one is the miss penalty of lesson 0900: three trips instead of one, paid by whichever unlucky reader asked first. The occasional one is that a cache which has never been asked is empty, so a restart, a scale-out or a failover starts every entry at a miss. AWS names this cost on the other side of the ledger too: with lazy loading "only requested data is cached", so a demand-filled cache never wastes memory on the answers nobody wants.

The second cost is staleness, and it is the one this module spends three more pages on. A demand-filled entry is written once and then never touched again by the read path, so nothing about a later change to the underlying row reaches it. AWS states it plainly: with lazy loading alone, "data in the cache can become stale... because there are no updates to the cache when data is changed in the database." That is not a bug in the pattern. It is the pattern's boundary, and the two ways past it are a lifetime on every entry and a write path that removes entries, which are lessons 0902 and 0904.

The failure worth rehearsing is the one where a cache-aside cache stops being optional by accident. It happens when the cache client is given the same timeout and retry policy as the database client: a cache that is slow rather than dead now adds its full timeout to every read, and a read path that was meant to degrade to "slower" degrades to "timed out" instead. Give the cache a timeout far shorter than the store's, treat exceeding it as a miss, and measure how the service behaves with the cache stopped - once, deliberately, before it happens on its own.

What does a read-through cache change, compared with cache-aside?
Read-through relocates the loader behind the cache, which is why the cache becomes an unavoidable hop. The first option describes write-through, a write pattern and the subject of lesson 0902; the second is wrong because a managed fill says nothing about when the answer stops being true; and the third describes priming or refresh-ahead, which is a different mechanism again.
Under cache-aside, what should a service do when the cache returns an error?
A cache error and a cache miss have the same correct response, which is what makes the cache optional at all. Returning a 503 converts an optimisation into a required dependency; retrying spends the caller's deadline on the component that was supposed to be saving time; and serving a per-process last value is an unbounded in-memory cache nobody designed, with no lifetime and no invalidation.
