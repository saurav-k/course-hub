A log is not a queue: reading does not consume, and the reader holds the position

working 10 min The second asynchronous shape, and why it is a different tool. · Apache Kafka - Design

The one-minute version

  • A queue forgets a message when it is acknowledged. A log does not: events "are not deleted after consumption", and retention is a per-topic setting.
  • The broker therefore tracks no per-message state. Each consumer group holds an offset, which is a position it can move backwards as easily as forwards.
  • A topic is partitioned, and order is guaranteed only inside a partition: same key, same partition, same order as written.
  • Within a group, each partition is read by exactly one consumer, so the partition count is the ceiling on how far you can parallelise.
  • What it costs: with no per-message acknowledgement, a message that always fails blocks its partition, and there is no dead-letter queue unless you build one.

1. The mental model: the reader holds the bookmark

In lesson 1203 the broker knew, per message, whether it had been delivered and whether it had been acknowledged. That per-message state is what a queue is. Kafka has none of it. A topic is an append-only sequence of events, and the documentation is blunt about what reading does to them: "events are not deleted after consumption. Instead, you define for how long Kafka should retain your events through a per-topic configuration setting, after which old events will be discarded."

What a consumer holds instead is an offset: the position it has reached. Two consequences follow immediately and neither has an equivalent in a queue. Several unrelated consumer groups can read the same topic without knowing about each other, because each has its own offset and none of them removes anything - no fanout exchange, no extra queues, no producer change. And a consumer group can move its offset backwards and read history again, which turns a bug in a downstream service into a rerun rather than into lost data.

2. The mechanism

Partitions, and the only ordering you get

A topic is not one sequence. "Topics are partitioned, meaning a topic is spread over a number of buckets located on different Kafka brokers", and that spreading is what makes throughput scale past one machine. The price is that there is no total order across a topic, and the guarantee is stated at partition scope: "events with the same event key are written to the same partition, and Kafka guarantees that any consumer of a given topic-partition will always read that partition's events in exactly the same order as they were written."

So ordering is something you buy with the key. Key by customer identifier and every event for one customer is ordered relative to the others, while two different customers have no defined order at all - which is almost always exactly what a domain needs, and is far cheaper than a global sequence.

Consumer groups, and the parallelism ceiling

A consumer group is a set of processes that share the partitions of a topic between them. Each partition is consumed by "exactly one consumer within each subscribing consumer group at any given time", which is what preserves the per-partition order while several machines work. It also fixes your ceiling: a topic with six partitions supports at most six useful consumers in a group, and the seventh sits idle.

Where the offset is committed decides the guarantee

Kafka names three delivery semantics: at most once, where "messages may be lost but are never redelivered"; at least once, where "messages are never lost but may be redelivered"; and exactly once, where "each message is processed once and only once". Which of the first two you get is not a setting on the broker. It is decided by the order of two lines in your consumer.

Exactly-once is available but it is narrower than the name suggests. The idempotent producer assigns each producer an identity and a sequence number so a resend does not become a second log entry, and transactions let a producer write atomically across several partitions. Both keep the log itself clean. What they do not do is reach into your database: for a consumer writing to an external system, Kafka's own advice is to have "the consumer store its offset alongside its output in the same location", so the position and the effect commit together. Exactly-once is a property of a closed loop, not a checkbox on the transport.

3. The trade-off: no ack means no escape hatch

The absence of per-message state is the source of everything good on this page and of the one thing that hurts. A queue can reject a single message and move on, sending it to a dead letter exchange while the rest of the queue drains. A log cannot: the consumer's position is a single number, so the only way past record 42 is to commit past it, and committing past it means accepting whatever happened. A record that always throws will be retried forever, and while it is, every record behind it in that partition waits.

That is head-of-line blocking, and it is not a bug to be configured away - it is what a strictly ordered position implies. The working answer is to build the escape yourself: catch the failure, publish the record to a separate errors topic with the exception attached, commit past it, and treat that topic as the dead letter queue Kafka does not have. The ordering guarantee you bought is exactly what you are spending to do it, so do it deliberately, per topic, and never by default.

Retention is a promise about disk, not about correctness, and a replay is only possible inside it. A topic with seven days of retention cannot rebuild a downstream store from a bug introduced eight days ago, and nobody discovers that until the day they need it. If a topic is a source of truth that something is derived from, its retention is a data-loss boundary and should be chosen and reviewed as one - compaction, or a longer retention, or an archive to object storage.

Check yourself

Retrieval practice

Answer from memory before revealing.

A topic has six partitions. You add a tenth consumer to one group. What changes?
A partition is read by exactly one consumer in a group, so six partitions support six working consumers and the rest idle. The first and third assume a partition can be split, which is precisely what the ordering guarantee forbids, and the second describes the consequence that assumption would have if it were true.
Your consumer commits the offset before processing the record. What have you chosen?
Committing first moves the position past a record that has not been handled, so a crash in between loses it - messages may be lost but are never redelivered. The second describes the opposite ordering, the third requires the offset and the output to commit in one place, and the fourth describes a queue's acknowledgement model rather than a log's.
