Module 09 · Caching · Lesson 0903

You can only invalidate what you can name, so the key design is the invalidation design

working 10 min The first half of the hard problem. · RFC 9111 §4.1 - Calculating Cache Keys

The one-minute version

  • An invalidation is the instruction "make this name absent", so the question a write has to answer is which names it just made wrong.
  • That answer is fixed by how the keys were built, which happened before the write path existed. Key design is invalidation design done early.
  • Entity keys - one row, one name - make the answer trivial. Derived keys - a list, a page, a rendered fragment - make it unknowable from the write alone.
  • Two mechanisms buy back what derived keys lose: a version segment in the name, which retires a whole family at once, and a tag attached to the entry, which lets one purge reach many names.
  • What it costs: precise names need bookkeeping the write path has to maintain, and broad names throw away hit rate you paid for. There is no free naming scheme.

1. The mental model: a key is a claim about what changes together

The protocol already made this decision once

HTTP settles the question in one line, and it is worth borrowing the vocabulary. RFC 9111 defines the cache key as "the information a cache uses to choose a response", composed at minimum "from the request method and target URI". That is the primary key. When one URI can produce several representations, the origin names the request fields that distinguish them in Vary, and those fields become a secondary key alongside the first.

The interesting part is the cost the specification then has to warn about. Every distinct combination of the Vary fields is a separate stored entry, so a header with many possible values fragments the stored copies until each one is read once and never again. That is the whole trade-off of key design in miniature: a key that distinguishes more things is more correct and hits less often, and there is no setting at which both are maximised.

Your own keys are the same object without the specification. A key is a claim that everything answering to this name changes at the same moment. When the claim is true, invalidation is a delete. When it is false, some of what you removed did not need removing, or some of what needed removing was not named.

2. The mechanism: three ways to make a name reachable

Carry the names with the write

The most direct answer is to make the write state its own invalidations. Facebook's memcache does exactly this at the storage layer: "SQL statements that modify authoritative state are amended to include memcache keys that need to be invalidated once the transaction commits", and a daemon on each database reads the commit log, extracts those deletes, and broadcasts them. The keys travel with the transaction that made them wrong, which is the only place that knows both facts at once.

The technique is available at every scale. In a service it means the repository that writes a row also returns the list of keys that row appears in, rather than leaving each call site to remember. What it does not do is solve the derived-key problem: a list of names is only as complete as the developer who wrote it, and a cached search result nobody thought of is a name nobody added.

Put a version in the name

A version segment turns bulk invalidation into a rename. The v1 in user:v1:42 is not decoration: change the shape of the cached value and deploy v2, and every old entry is instantly unreachable, ages out on its own lifetime, and never has to be found or deleted. This is the same move lesson 0204 described for static assets, where a content hash in the URL means you "never invalidate anything, you publish a new target and let the old one expire unread".

Push the version down a level and it becomes a per-entity bulk invalidation. Keep a counter for a tenant or a user, include it in every derived key for that tenant, and one increment retires every derived entry they own without knowing a single one of their names. The cost is one extra read to learn the counter, which is usually cached itself, and a wave of misses immediately after each increment.

Attach a tag to the entry

The third mechanism inverts the lookup: instead of computing names from the write, the entry declares what it depends on when it is stored, and the cache maintains the reverse index. Fastly's CDN implements this as surrogate keys - the origin returns a Surrogate-Key header listing tags, Fastly builds "a mapping from each key to the cached content", and a purge of one tag removes every object carrying it. The relationship is many-to-many: an object may carry several tags and a tag may cover many objects. The limits are worth knowing because they bound how fine the scheme can get: an individual key may not exceed 1,024 bytes and the whole header may not exceed 16,384 bytes.

3. The trade-off: broad names lose hits, narrow names lose entries

Every scheme sits somewhere on one axis. At one end, a single name covers everything a tenant owns: invalidation is one delete and cannot miss, and every write costs that tenant their entire cache. At the other end, each entry is named by the exact question that produced it: nothing unnecessary is ever removed, and the writer cannot find most of what it broke. Real schemes sit in the middle and are made of the three mechanisms above.

One measurement is worth carrying from the memcache paper, because it shows how the middle behaves in production. Of every delete Facebook issued through its invalidation pipeline, "only 4% of all deletes issued result in the actual invalidation of cached data". The other 96% named entries that were not cached anywhere. That is not waste to be optimised away - it is the expected shape of broadcasting an invalidation to a cache you cannot query. It also means the volume of your invalidation traffic tells you nothing at all about how much staleness you prevented.

The failure this page exists to prevent is the derived entry nobody registered. A team caches individual entities correctly, wires up delete-on-write, and is genuinely careful. Then someone adds a cached listing endpoint keyed on its query parameters, and it is now the only entry in the system with no path from a write back to its name. It will be stale for its full lifetime after every relevant write, it will never appear in an invalidation log, and it will be discovered by a customer describing something they deleted still being visible. Before caching anything derived, write down which write invalidates it and how that write will find it. If you cannot answer, the answer is a short lifetime, chosen deliberately.

Retrieval practice

Answer from memory before revealing.

Why is a cached search result harder to invalidate than a cached row?
The name of a derived entry is built from a question, and no write can search the space of questions its change affected. Size is irrelevant to a delete; the lifetime is a consequence of the problem rather than its cause; and sharing is a different axis entirely, since a shared entity key is still trivially nameable.
What does adding a version segment to a key format actually buy?
A version bump is a rename, so the old entries are never read again and expire quietly - no scan, no delete, no list of names. The first option describes a shape marker inside the value rather than in the key; the second is what tags do; and the third is false, since the old entries live out their full lifetimes, they are simply unreachable while they do.
