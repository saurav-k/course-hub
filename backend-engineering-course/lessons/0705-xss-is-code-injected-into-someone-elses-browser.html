Module 07 · Auth and security · Lesson 0705

Injected script runs as your origin, so every defence your origin has now protects it

working 9 min The same defect as 0704, with the browser as the interpreter. · OWASP - Cross Site Scripting Prevention

The one-minute version

  • The threat first. A value you rendered becomes markup, the browser runs it, and it runs as your site - same origin, same cookies, same permissions the user granted you.
  • That is why it is worse than it sounds: the same-origin policy is not breached, it is recruited. The attacker's code is inside the boundary that policy protects.
  • The defence is output encoding chosen by context. HTML body, attribute, JavaScript, CSS and URL each need a different encoding, and using the wrong one is a defect.
  • Where user-authored HTML is genuinely required, encoding is not an option: sanitise the fragment with a maintained library instead of writing a filter.
  • What it costs: a strict Content Security Policy is the second layer for the site you missed, and it is real work - a fresh nonce per response and no inline handlers.

1. The threat: what the attacker gets, precisely

Execution inside the origin, not access to it

The interesting part of cross-site scripting is not that script runs; it is where it runs from. Script injected into your page has your origin. It can read the DOM, call your API with the user's ambient credentials, register listeners on the login form, and rewrite what the user sees before they act on it. Nothing has been bypassed: the browser is enforcing the same-origin policy exactly as designed, and the attacker's code is on the inside of it.

Three deliveries are worth naming because their defences differ in where they sit. Stored XSS is persisted by your service and served to everybody who views the record. Reflected XSS comes back in the response to a request the victim was induced to make, so it needs a lure but leaves nothing behind. DOM-based XSS never reaches your server at all: the page reads a value from the URL or storage and writes it into a dangerous sink in the browser, which is why a server-side template audit finds nothing.

2. The defence: encode for the context you are writing into

Five places, five encodings, not interchangeable

Escaping is the right answer here, and this is the difference from lesson 0704 worth sitting with: a database offers a separate channel for values and a browser does not, because HTML has no placeholders. What you can do is transform the value so that the browser's parser reads it as text in the exact place you are putting it - and where that is decides which transformation.

OWASP names five contexts and a different treatment for each: HTML body takes entity encoding, an HTML attribute takes attribute encoding with the value quoted, JavaScript takes hex escaping, CSS takes CSS hex encoding, and a URL takes percent encoding. The warning attached is the operative one - using the wrong encoding method may introduce weaknesses or harm the functionality of your application. HTML-encoding a value on its way into a <script> block is a real and common failure: the browser decodes the entities before the JavaScript parser ever sees the text.

Frameworks help, and their escape hatches are named

A modern template engine encodes interpolated values by default, which is why XSS is rarer than it was. What survives is the deliberate bypass: OWASP names React's dangerouslySetInnerHTML, Angular's bypassSecurityTrustAs* and Lit's unsafeHTML. Each is correctly named, each exists because somebody genuinely needed raw markup, and each is where to start reading in an unfamiliar codebase.

The second layer is a Content Security Policy, which MDN describes as instructions from a website to a browser to place restrictions on the things that the code comprising the site is allowed to do. A strict CSP puts a random nonce on the scripts you meant to run and refuses everything else - and MDN is emphatic that the nonce must be different for every HTTP response, and must not be predictable, because a static nonce is a permanent password to your script-src. Two shapes to avoid: 'unsafe-inline', which MDN warns defeats much of the purpose of having a CSP, and host allow-lists, which are hard to get right and often admit an unsafe domain.

A CSP is not a replacement for encoding, and MDN says so directly: setting one is not an alternative to sanitizing input - do both, for defence in depth. Treat the policy as insurance against the one template that was missed, and keep the transformation at the sink as the actual fix. A site that ships a strict CSP and interpolates raw values has one layer, and it is the outer one.

3. The trade-off: correctness per site, not per service

Injection at a database had one fix applied at one kind of call. XSS has a fix that changes with the surrounding syntax, applied at every place a value meets markup - which in a real application is thousands of places, most of them handled by a template engine you did not write. That is why the practical strategy is different in shape: rely on the framework's default, hunt the named escape hatches, and add a policy that limits the damage of the one you miss.

The policy costs something real. A nonce per response means the page cannot be a static file, inline handlers have to move into script files, and third-party widgets that inject their own scripts need 'strict-dynamic' - which MDN notes does make your CSP less secure, because a trusted script that builds elements from untrusted input is no longer covered. None of that is a reason to skip it; all of it is a reason to plan it rather than to add a header on a Friday.

Check yourself

Retrieval practice

Answer from memory before revealing.

Why is script injected into your page more dangerous than script on the attacker's page?
The policy is intact and that is the problem - the code is inside the boundary, so it reads your DOM and calls your API as you. TLS is unaffected by what the page contains, execution order depends on where the injection landed, and nothing is bypassed, which is what makes the last option the most tempting wrong answer here.
A value is HTML-entity encoded and then written inside a <script> block. What happens?
The HTML parser resolves entities first, so the JavaScript parser receives the original characters and the encoding has done nothing. This context needs JavaScript hex escaping instead. Quoting style does not change the decoding order, and encoded values in a script block are fine when the encoding is the right one.

How this connects

  • Behind you, a session is server state behind an opaque id is where HttpOnly was set, and this is the attack it exists for.
  • Behind you, CORS is the browser enforcing the server's own policy defined the origin boundary this page runs inside.
Your teacher. Grep your front end for innerHTML, dangerouslySetInnerHTML and their equivalents, and for each one decide whether the value can be reached by a user. Then ask the agent what a strict, nonce-based CSP would break on your busiest page, before you try shipping one.
