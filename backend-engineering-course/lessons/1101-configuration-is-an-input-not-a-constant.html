Configuration is untrusted input with a longer fuse, so parse it once at boot

foundation 9 min The same boundary rule as lesson 0403, applied to the deploy. · The Twelve-Factor App · III. Config

The one-minute version

  • Config is everything that varies between deploys of the same build, and that definition is what separates it from a constant you can simply write down.
  • It arrives as strings from outside the process, so it is untrusted input and takes exactly the boundary treatment lesson 0403 gave a request body.
  • The whole win is when the failure surfaces. A value parsed at boot fails a deploy; the same value parsed on first use fails a customer, days later.
  • The twelve-factor litmus test for whether the split is clean: the codebase could be made open source at any moment without compromising any credentials.
  • What it costs: a strict boot check turns a partially working deploy into no deploy at all, and that is the trade you are actually making.

1. The mental model: what makes a value config

The dividing line is not "is it in a file" or "is it a string". The twelve-factor definition is operational: config is everything likely to vary between deploys - staging, production, one developer's laptop - of the same code. A retry ceiling that is 3 everywhere is not config, it is a constant, and putting it in an environment variable buys an operator a knob nobody will ever be qualified to turn. A database URL is config even when there is only one of them today, because there will be two the first time somebody stands up a staging environment.

The second half of the definition is the credentials, and twelve-factor gives it a test you can actually run: could this codebase be made open source at any moment without compromising anything. That test is sharper than a rule about file names, because it catches the cases a rule misses - a default password in a fixture, a bucket name that identifies a customer, an internal hostname in a comment.

2. The mechanism: one parse, one typed value, at boot

The environment is a string map, and your program is not

Twelve-factor's recommendation is environment variables, and the reason given is worth separating from the habit: they are a language- and OS-agnostic standard, they can be changed between deploys without touching code, and they are granular rather than grouped. The last one is the argument against config environments. Named groups like development, test and production stop scaling the moment somebody needs joes-staging, and twelve-factor calls the result a combinatorial explosion of config that makes deploys brittle.

What arrives, though, is a flat map of strings. DB_MAX_CONNS is the text "25" and might be the text "twenty-five", and FEATURE_X being present but empty is a different thing from being absent. This is precisely the situation lesson 0403 described at the request boundary: untrusted text that must become a trusted value exactly once, so that no code deeper in the process ever re-checks it.

config.py · one parse, one typed value, one refusal
@dataclass(frozen=True)
class Config:
    database_url: str
    max_conns: int
    shutdown_grace: timedelta

def load(env: Mapping[str, str]) -> Config:
    problems: list[str] = []
    def need(key: str) -> str:
        value = env.get(key, "").strip()
        if not value:
            problems.append(f"{key} is required and was empty or unset")
        return value

    url, conns = need("DATABASE_URL"), need("DB_MAX_CONNS")
    ...
    if problems:                       # every problem, not the first
        raise ConfigError(problems)    # the process does not start
    return Config(url, int(conns), timedelta(seconds=int(grace)))

Two details in that shape do the work. The value is frozen, so nothing downstream can rewrite it and no test can leave it modified. And the errors accumulate rather than raising on the first one: an operator who has three variables wrong should learn all three from one failed deploy, not discover them over three attempts. That is the same argument lesson 0603 made about a problem document listing every invalid field.

Precedence, stated once and in one direction

Most services end up with more than one source: a built-in default, a file baked into the image, the environment, and sometimes a flag. That is fine as long as the order is stated in one place and runs one way. The failure is a service where a file overrides the environment in one subsystem and the environment overrides the file in another, because then the answer to "what is this setting actually" is a code-reading exercise during an incident. Print the resolved values at boot, with the secrets redacted, and the question never has to be asked.

3. The trade-off: strictness buys certainty and costs availability

Refusing to start is a real cost and it is worth naming rather than assuming away. A process that exits because an optional feature flag is misspelled has turned a cosmetic mistake into an outage, and a rollout that fails closed at 3am when nobody meant to touch config is not obviously better than one that limps. The discipline is to be strict about what the service cannot function without and permissive about the rest, and to write down which is which - a required value has no default, and an optional value has a default that is safe rather than convenient.

The second cost is that config parsed once cannot change while the process runs. That is usually the right trade, because a value that changes underneath running code has all the problems of shared mutable state plus a network. Where genuinely dynamic behaviour is needed, the honest answer is a separate mechanism with its own consistency story - a feature flag service, or a value re-read on an explicit signal - and not a config file the process happens to stat again.

Config is the most common way a secret reaches a log. A startup line that dumps the parsed configuration, a stack trace that includes a connection string, an error message that quotes the value it could not parse - all three are ordinary code and all three publish credentials to wherever lesson 1102 sends the stream. OWASP's logging guidance names database connection strings, access tokens, passwords and encryption keys as data that should not be recorded directly in logs. Redact at the type, so a secret value's own string representation is already the mask, rather than remembering at every call site.

Why does twelve-factor argue against grouping config into named environments?
The stated objection is a combinatorial explosion once somebody needs a group like joes-staging. The first option is not the argument, since a group can hold credentials as badly or as well as anything else; the second is a portability claim twelve-factor does not make; and the third confuses grouping with the separate question of when a value is parsed, which this page treats on its own.
