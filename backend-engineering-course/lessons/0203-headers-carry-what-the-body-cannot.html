Module 02 · HTTP is the language · Lesson 0203

Headers are the negotiation surface, and a body that has to describe itself has already failed

working 7 min Four families of field, one job each. · RFC 9110 §12 - Content Negotiation

The one-minute version

  • Fields are independent statements about the message, readable before a byte of body is parsed, which is what makes them a negotiation surface.
  • Four families do nearly all the work: representation metadata, content negotiation, conditionals, and credentials.
  • Content negotiation is the client stating preferences and the server choosing, then naming its choice back so caches can key on it.
  • A conditional request attaches a precondition to a validator, which is how you get a cheap re-check and a defined outcome under concurrency.
  • What it costs: every field is optional and unenforced, so a client that omits one gets a default somebody else chose.

1. The mental model: metadata that arrives first

A body is opaque. It is a sequence of bytes, and nothing inside it tells a recipient what it is, how it was encoded, how long it should be kept or who sent it. Every one of those questions has to be answered outside the body, before or around it, by something a recipient can read cheaply and act on without parsing. That is the header section, and it is why the design has held for three decades: the frame stayed fixed while the vocabulary of fields grew without limit.

The practical consequence is that a proxy, a cache or a load balancer can make a complete decision about a message it never reads. That is the whole basis of the machinery in the next two lessons, and it is also the reason a field is worth spending design attention on: it is the only part of your response that intermediaries act on.

2. The mechanism

Representation metadata: what this actually is

A resource can have several representations - the same order as JSON, as HTML, in English or in German, gzipped or not - and the representation metadata fields describe the one in this message rather than the resource behind it. That distinction is the reason the same URI can legitimately answer with different bytes to different callers, and the reason the fields have to travel with each message instead of being configuration.

Content negotiation: preferences in, a choice back

The client sends its preferences in the Accept family and the server picks. Nothing obliges the server to honour a preference, which is the part that surprises people: negotiation is advisory in one direction and authoritative in the other. The server then states what it chose, and where the choice depended on a request field it says so in Vary. That last part is not politeness. A shared cache uses Vary to know that one stored response cannot answer for a client that asked differently, and a missing Vary is how a German page gets served to an English reader.

Conditional requests: a precondition on a validator

A validator is a compact token for the state of a representation: an ETag, which the server generates and only the server interprets, or a Last-Modified timestamp. A conditional request carries that validator back in a precondition field and asks the server to act only if it still matches. Sent as If-None-Match, it is the cheap freshness re-check that lesson 0204 is built on. Sent as If-Match on a write, it is optimistic concurrency control: the update applies only if nobody else changed the resource since you read it, which is the missing piece the previous lesson's warning pointed at.

3. The trade-off: unenforced by design

Every field is optional, and a recipient may ignore any field it does not understand. That is what made thirty years of extension possible, and it is also the cost: nothing tells you that the field you relied on was dropped by a proxy, rewritten by a CDN, or never sent by a client library whose defaults you did not read. A design that depends on a field arriving needs to state what happens when it does not, and the honest answer is usually a default the server chooses and documents.

Header fields are the easiest place to leak information without noticing. A field naming your framework and version, an internal hostname in a debug field, or a stack trace in a custom error field all travel to every client and through every intermediary, and none of them are visible in the response body a developer looks at. Module 07 owns the threat model; the exposure starts here.

Retrieval practice

Answer from memory before revealing.

Why does a server send Vary on a negotiated response?
Vary names the request fields the selection depended on, so a shared cache does not answer a differently-phrased request from this stored copy. The first option describes an Allow-style field, the second is true of negotiation but is not what Vary says, and the fourth inverts it: Vary constrains reuse rather than enabling it.
Which field makes a PUT safe against a concurrent update?
If-Match applies the write only while the validator still matches, so a stale write gets 412 instead of overwriting. If-None-Match is the read-side precondition used for revalidation, Cache-Control governs storage rather than concurrency, and Content-Length is representation metadata.
