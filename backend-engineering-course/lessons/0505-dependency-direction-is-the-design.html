Module 05 · The layered service · Lesson 0505

Every dependency points inward toward the domain, and one file at the edge decides what is really there

working 8 min The module in one property. · Spring - Dependency injection

The one-minute version

  • The architecture is the import graph, not the folder tree. Draw the arrows and the design is either there or it is not.
  • The rule is one sentence: an inner layer never names an outer one, and where it needs something from outside it declares the contract itself.
  • Spring states the mechanism as an inversion: an object declares what it needs and the container supplies it, rather than the object going to find it.
  • All the concrete choices - which database, which cache, which clock - are made in one file at the edge, the composition root, which everything imports and nothing imports back.
  • What it costs: with a container the wiring is resolved at start-up rather than at compile time, so a missing binding is a runtime error at boot.

1. The mental model: read the imports, not the folders

A codebase's real structure is its import graph. Directories are labels a team applies to it, and a label can be wrong for years without anything failing. So the question to ask of any layered design is mechanical: for each edge in the graph, which way does it point? Draw it once for a service you already have and the answer is usually uncomfortable, because a domain package importing a driver is invisible in a folder tree and obvious in a graph.

The rule the rest of this page defends is a single sentence. An inner layer never names an outer one. The domain does not know about the store, the store does not know about HTTP, and where an inner layer needs something an outer one provides, the inner layer declares the contract and the outer one satisfies it. That is one sentence and it is the whole architecture, which is why folders are commentary on it rather than a substitute.

2. The mechanism

Declaring instead of fetching

Spring's reference describes injection as an object defining its dependencies through constructor arguments and the container supplying them when it creates the bean, and it names this the inverse of the object controlling the instantiation or location of its dependencies itself. That inversion is the mechanism, and the reason to prefer the constructor form is stated there too: it produces components that are handed back fully initialised, with required collaborators that cannot be null, and it lets the fields be final. NestJS reaches the same place by resolving a constructor parameter's type against its container, so a service arrives with what it asked for and never goes to find it.

The languages differ in where the contract lives, and the difference is worth holding. In Go the consumer declares the interface in its own package, and satisfaction is membership rather than a declaration, so nothing outward-facing has to be edited when a new implementation appears. In Java or TypeScript the interface is a named type someone must implement explicitly, so the same discipline is available and has to be chosen: put the interface in the inner package, not beside the implementation, or the arrow quietly points the wrong way while every class name stays right.

The composition root

Somewhere the abstractions have to stop. Something must open a real connection pool, construct a real repository, hand it to a real service, and give that to a handler. That place is the composition root: one file, at the outermost edge, that imports everything and that nothing imports back. Its job is to be the only file in the system where a concrete choice is written down.

the composition root in two voices · the only place any concrete type is named
// Go: main is the composition root, and it is boring on purpose.
func main() {
    db := mustOpen(os.Getenv("DATABASE_URL"))
    orders := postgres.NewOrders(db)               // the only mention of Postgres
    svc := order.NewService(orders, clock.System)   // the service sees interfaces
    handler := httpapi.NewOrderHandler(svc)
    http.ListenAndServe(":8080", handler)
}

# Python: the same wiring, done explicitly rather than by a container.
def build_app() -> App:
    pool = create_pool(os.environ["DATABASE_URL"])
    orders = PostgresOrders(pool)
    service = OrderService(orders=orders, clock=SystemClock())
    return App(routes=order_routes(service))

Two things follow from having one. A test builds its own root with doubles in it, which is the substitution test from lesson 0500 answered at the level of the whole application rather than one class. And the answer to "what is this service actually running against" is one file long, instead of a search for every place a connection is created.

3. What the direction costs

Wiring is verbose. The Go root above will be forty lines in a real service, and every new collaborator adds one. A container removes that typing by resolving constructor parameters against a registry, which is what Spring and NestJS do, and the trade is that the graph is now assembled at start-up from metadata rather than written down. A missing or ambiguous binding becomes an error at boot instead of an error at compile time, and the message names a type rather than a line you wrote.

That is a real trade rather than a wrong answer: at fifteen collaborators the manual root is honest and readable, and at a hundred and fifty it is a file nobody maintains. What does not change with the choice is the direction of the arrows. A container makes wiring cheaper and makes no dependency point inward on its own, and a service whose domain imports its driver is exactly as coupled with a container as without one.

The failure to watch for is an interface placed beside its implementation instead of beside its caller. Everything about it looks right - there is an interface, the service depends on it, the tests use a double - and the arrow still points outward, because the package holding the contract is the package holding the driver. The test is the same one this module opened with: delete the implementation package and see whether the domain still compiles. If it does not, the boundary was a naming convention.

What actually makes a dependency point inward?
Ownership of the contract is what sets the direction: if the inner package declares it, the inner package compiles without the outer one. Folder nesting says nothing about imports, a container changes how the graph is assembled rather than which way it points, and build order is a consequence of the graph rather than a cause.
What does a composition root do that no other file may?
The root is the single place a concrete choice is written down, which is what makes the rest of the system depend on contracts only. Rules belong to the service layer, a deadline belongs to the request rather than to start-up, and outcome-to-status mapping is the controller's table from lesson 0501.
