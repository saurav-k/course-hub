A failure has exactly one owner, and every other layer may only add context

foundation 9 min Error handling as routing rather than formatting. · The Go Blog - Working with Errors in Go 1.13

The one-minute version

  • An error is a value travelling towards the one layer that can act on it, and handling it means deciding whether this layer is that one.
  • Two questions classify every failure: can the caller do anything about it, and can this layer do anything about it. Nothing else about a failure matters at the moment it is raised.
  • A layer that is not the owner has exactly two honest moves: add context and pass it on, or translate it into a failure its own callers understand.
  • Wrapping is not free. Go's own guidance is that wrapping an error makes that error part of your API, so it commits you to it.
  • What it costs: the discipline buys nothing on the happy path and only pays back at 3am, which is why it is the first thing dropped under a deadline.

1. The mental model: an error is a value with a destination

The instinct most services are built on is that an error is an interruption: something went wrong, so stop what you were doing and report it. That framing produces the two failure modes every codebase has - the same failure reported five times as it climbs the stack, and the same failure reported nowhere because a middle layer decided it was not serious. Both come from treating error handling as a formatting question.

The more useful framing is that an error is an ordinary value moving towards a destination, exactly as a response is. Somewhere in the process there is one layer that can do something other than give up: retry the call, fall back to a default, ask the user for a different input, refuse the request with a status. That layer is the owner. Every layer between the failure and the owner is a courier, and a courier's only jobs are to keep the value intact and to write on the envelope where it has been.

2. The mechanism: wrap, translate, or hand it on unchanged

Wrapping keeps the identity and commits you to it

Both of this course's implementation languages have the same two operations, spelled differently. Go's fmt.Errorf gained the %w verb in 1.13: the returned error carries an Unwrap method returning the original, and errors.Is and errors.As walk that chain rather than comparing the outermost value. Where an error wraps several children the chain is a tree, and both functions do a depth-first traversal of it.

Python has carried the same idea since PEP 3134, which exists because of a specific loss: before it, an exception raised while handling another exception propagated outward and the original was simply gone. Implicit chaining now records the one being handled in __context__, and raise NewError(...) from original sets __cause__ when the translation is deliberate.

wrapping, in both voices · the identity of the failure survives the trip
// Go: %w keeps the sentinel reachable through errors.Is
if err := q.Row(ctx, id).Scan(&u); err != nil {
    return fmt.Errorf("load user %s: %w", id, err)   // sql.ErrNoRows still matches
}

# Python: "from" records the cause, so the traceback keeps both frames
try:
    row = cursor.fetchone()
except DatabaseError as exc:
    raise UserLookupFailed(user_id) from exc

The cost is stated plainly in Go's own release note and is easy to skip past: wrapping an error makes that error part of your API, and if you do not want to commit to supporting it as part of your API in future, you should not wrap it. A caller that writes errors.Is(err, sql.ErrNoRows) is now depending on your repository using that particular driver. This is lesson 0600's asymmetry arriving inside the process: the promise was cheap to make and is expensive to take back.

Swallowing is the only move that is always wrong

There is a third thing a layer can do, and it is the one that produces the incidents. Catching an error, logging it, and returning a zero value looks like handling: something was written down and the program kept going. What actually happened is that a failure was converted into a success with wrong data, and every layer above it now reasons about a value that does not correspond to anything. The log line is not a mitigation, because nobody reads a log line about a request that returned 200.

The same defect wears a second costume: catching a broad exception class at a layer that owns none of the failures inside it. except Exception around a block that does both a network call and an arithmetic step will absorb a typo in your own code and report it as a downstream outage, and you will spend the incident looking at the wrong service.

3. The boundary: one failure becomes one answer, once

The handler is the last layer that can still say something to the caller, so it is where the internal vocabulary of errors becomes the external vocabulary of status codes and problem documents that lesson 0603 defined. Doing that conversion in exactly one place is what keeps the two vocabularies from leaking into each other: a repository that returns an HTTP 404 has made itself unusable from a background job, and a handler that inspects a driver error has made itself dependent on the storage engine.

The conversion is a small total function over a closed set. Each domain failure maps to one status and one problem type; everything not in the set maps to 500 with a generated identifier, and that identifier is the only part of the internal failure the caller ever sees. RFC 9457's security considerations are explicit that a problem detail must not disclose implementation internals, so the mapping is a privacy boundary as much as a translation.

The unmapped case is the one that decides how your service behaves in an incident, and it is almost never designed. If the default arm of that mapping logs at error level and returns 500, then a single malformed input from one client becomes a page for your on-call engineer, because your alert counts 5xx. A failure the caller caused belongs in the 4xx family however surprising it was, and lesson 0202 is why: the first digit is what every layer outside your process reads.

4. The trade-off: every promise about a failure is a promise

Rich, precisely typed errors are pleasant to hold and expensive to keep. A caller that branches on six distinct failure types is a caller you can break in six ways, and each new type you expose is a decision you make once and live with, exactly as a response field is. The opposite extreme is just as costly in the other direction: a service that returns one opaque failure forces every caller to retry blindly or give up, and the retries land on you.

The workable position is to expose the failures a caller can act on differently and hide the rest behind one. A caller can act on this order already exists, this payment was declined and you are over your rate limit. It cannot act on connection pool exhausted, and telling it so buys nothing and commits you to a pool.
