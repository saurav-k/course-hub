Module 07 · Auth and security · Lesson 0700

Identity is established once and permission is decided again on every request

foundation 8 min The two questions the rest of this module answers separately. · RFC 9110 §11, HTTP Authentication

The one-minute version

  • Authentication answers who is calling. Authorization answers what this caller may do to this resource, and they are different decisions with different lifetimes.
  • Authentication is deliberately expensive and rare: a password check is designed to take about a second, so you run it once and hand back something cheap to re-present.
  • Authorization is cheap and constant: it is re-decided on every request, because nothing about the earlier login says anything about this URL.
  • HTTP frames only the first question. It gives you a challenge, a credential field and two refusals - 401 for "I do not know you", 403 for "I know you and the answer is no".
  • What it costs: the thing handed back after login is the identity from then on, so everything in the rest of this module is about who else can get hold of it or make your browser send it.

1. The mental model: two questions, two lifetimes

One is answered once and one is answered always

OWASP states the split plainly: authentication is verifying an entity's identity, and authorization is the process of verifying that a requested action or service is approved for a specific entity. Read as a pair of sentences they sound like two steps of one operation. They are not, and the difference that matters is how long each answer is good for.

Authentication is priced to be slow. The recommended password hash is Argon2id at m=19456 (19 MiB), t=2, p=1, chosen so that verifying one password costs real memory and real time; the whole point is that an attacker with a stolen table pays that cost per guess. You cannot pay it on every request, so you pay it once and hand the caller something cheap to show instead.

Authorization has the opposite shape. The earlier login said nothing about the resource in front of you now, so the answer has to be recomputed: OWASP's rule is that permission should be validated correctly on every request, regardless of whether the request was initiated by an AJAX script, server-side, or any other source, with a deny-by-default posture and the check on the server rather than in the client that drew the button.

2. The mechanism: what HTTP actually supplies

A challenge, a credential field, and no scheme

HTTP supplies a frame and almost nothing else. RFC 9110 describes a general framework for access control and authentication, via an extensible set of challenge-response authentication schemes, and then says outright that the document specifies no schemes of its own. A server challenges with a 401 carrying WWW-Authenticate; a client answers with an Authorization field. That is the whole protocol-level contract.

One piece of it is worth knowing because it explains browser behaviour that otherwise looks like magic. A protection space is the origin plus the realm, and it determines the domain over which credentials can be automatically applied: once a request in that space has been authorized, the user agent may reuse the same credentials for every other request in it, without being asked again. Automatic re-presentation is written into the specification, and lesson 0706 is about what an attacker does with exactly that.

The two refusals say different things

The status codes carry the distinction, and RFC 9110 is precise about it. A 401 (Unauthorized) says the request lacks valid authentication credentials for the target resource, and a server generating one MUST send a WWW-Authenticate challenge - a 401 with no challenge is a malformed response. A 403 (Forbidden) says the server understood and refuses, and if credentials were supplied it considers them insufficient to grant access; the client SHOULD NOT automatically repeat the request with the same credentials.

So the pair is a retry instruction as much as a diagnosis. A 401 tells a client to go and get credentials; a 403 tells it not to bother. The specification adds one escape hatch worth knowing: a server that wishes to hide the existence of a forbidden resource MAY answer 404 instead, which is how you avoid confirming that order 91 exists to somebody who is not allowed to read it.

3. The trade-off: the credential becomes the identity

Everything above buys one thing and sells another. It buys you a login that can afford to be slow and careful. It sells you a period - minutes, hours, sometimes weeks - during which a short string is treated as though it were the user. Nothing later in the request path re-examines the password; it examines the credential, and anyone presenting that credential is, to your service, that person.

That is why the second half of this module is threats rather than mechanisms. Lessons 0701 to 0703 are three shapes for the credential: an opaque handle to server state, a signed document the client carries, and a scoped grant issued by somebody else. Lessons 0704 to 0706 are three ways an attacker reaches it - by getting your database to run their string, by getting your page to run their script, or by getting the browser to attach the credential to a request they wrote.

An incidence rate here is the share of tested applications with at least one instance, so these bars count findings in a contributed dataset rather than exploited breaches. They say what testing tools find often, which is not the same claim as what attackers use most. Treat the ordering as evidence that these defects are common, and not as a ranking of risk to your particular service.

Check yourself

Retrieval practice

Answer from memory before revealing.

Why is the permission decision made again on every request rather than at login?
Login establishes identity, and identity does not imply permission on a resource nobody had mentioned yet. Credentials do expire, but that is a separate timer and not the reason. HTTP stores nothing either way and imposes no such rule, and the whole point of a credential is that the expensive hash is not recomputed per call.
A caller sends a valid session cookie and asks for another user's order. What is correct?
The credentials are valid and merely insufficient, which is exactly RFC 9110's definition of 403 - and the same section permits 404 to hide the resource. A 401 would tell the client to fetch credentials it already has, a 401 without WWW-Authenticate violates a MUST, and 400 claims the request was malformed when it was well-formed and refused.

Primary source to go deeper

RFC 9110 §11 is four pages and worth reading in full: it is the whole of what HTTP itself says about authentication, and its brevity is the point - every scheme you use is defined somewhere else. Read it beside OWASP's Authorization Cheat Sheet, which owns the half the RFC deliberately does not.
