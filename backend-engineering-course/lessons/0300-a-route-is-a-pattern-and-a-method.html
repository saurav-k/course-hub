Module 03 · Routing · Lesson 0300

A route is the pair of a method and a path pattern, and either half on its own is not a route

foundation 8 min The pair, before the matching. · RFC 9110 §9.1 - Method overview

The one-minute version

  • A route is a registered pair: one method token and one path pattern. The router matches both or it has not matched.
  • The two halves answer different questions. The pattern asks which resource, the method asks what is being asked of it.
  • A pattern is a shape, not a string: it holds literal segments and named holes that stand for one segment each.
  • Real routers key on the method before the path, because that is one exact comparison in front of a walk.
  • What it costs: one resource with four verbs is four registrations, and a router that drops the method half can no longer tell a missing resource from a wrong verb.

1. The mental model: two keys, not one string

Most people picture a router as a lookup on the URL. That picture is wrong in a way that costs you later, because it throws away half of what the client said. RFC 9110 is explicit that the method token is the primary source of request semantics: it says what the client wants done, and the target says what it wants done to. A router that reads only the target has read the object of the sentence and thrown away the verb.

So the unit a router registers is a pair. GET /orders/{id} and DELETE /orders/{id} name the same resource and are two different routes, dispatched to two different functions, because reading an order and destroying one are not the same request. The pair is also what lets a router answer honestly when nothing matches, which Lesson 0304 develops: a router holding both halves can say this resource exists but not for that verb, and a router holding only the path cannot.

2. The mechanism: registration, then lookup

A route: what registration actually stores

Registration puts an entry into a structure the router owns. The entry holds the method token, the compiled path pattern, and a reference to the function to call. Nothing about it is textual at match time; the pattern was parsed once, when the service started, and the string it came from is not consulted again. This is why a router can reject a malformed pattern at boot rather than on the unlucky request that first reaches it.

The path pattern: a shape with named holes

A pattern is a sequence of path segments in which some segments are literal and some are named holes. Go's ServeMux states the rule tightly: a wildcard must be a full path segment, so it has to be preceded by a slash and followed by a slash or the end of the pattern, and /b_{bucket} is not a valid pattern at all. A hole normally matches exactly one segment, ending at the next literal slash. The value it captured is then handed to your code by name.

Method dispatch: the second key, checked first

The method half is an exact token comparison and the path half is a walk over segments, so a router that keys on the method first throws away most of its table for the price of one string equality. Go's routing tree does exactly that: it branches on host, then on method, then on consecutive segments of the path. Two conventions ride on top of that comparison and both are worth knowing. Go treats a pattern registered for GET as matching HEAD as well; Flask adds HEAD whenever GET is present, and implements OPTIONS for you.

routes.go · Go, net/http ServeMux, the method is part of the pattern
mux := http.NewServeMux()
mux.HandleFunc("GET /orders/{id}", showOrder)
mux.HandleFunc("DELETE /orders/{id}", deleteOrder)
mux.HandleFunc("POST /orders", createOrder)

func showOrder(w http.ResponseWriter, r *http.Request) {
    id := r.PathValue("id") // the named hole, by name
}
routes.py · Python, Flask, the method is an argument to the same decorator
@app.get("/orders/<int:order_id>")
def show_order(order_id):
    ...

@app.delete("/orders/<int:order_id>")
def delete_order(order_id):
    ...

The two spellings are the same object. Go writes the method inside the pattern string and Flask writes it as a decorator or a methods argument, but both register a pair, and both hand the captured segment to the function by name rather than by position in the URL.

3. The trade-off: the pair is four registrations, and it is worth them

One resource with four verbs is four entries, four functions and four tests. The tempting economy is to register the path once and branch on request.method inside the handler, and every framework lets you. It reads as less code and it is, but it moves a routing decision into application code, and three things follow. The router can no longer report which methods a resource supports, so the Allow field that Lesson 0304 owes has nowhere to come from. The middleware chain of Lesson 0303 can no longer differ by verb, so a write path and a read path get the same treatment. And a verb the branch forgot falls through to whatever the last else does.

The other economy, more common and worse, is putting the verb into the path: POST /orders/8123/delete. That produces a route the pair can still match, so nothing breaks on the day it ships. What it loses is everything the method token bought in Lesson 0201: a cache, a proxy and a retrying client all read the method and none of them read your path segment, so a delete disguised as a POST is invisible to every intermediary on the wire.

A pattern registered with no method matches every method. Go's ServeMux documents it plainly, and the same is true of Django's path() and of Express's app.use. It is the shape that reaches production most quietly, because the handler under it was written for one verb and is now reachable by all of them - including the DELETE nobody sent while the feature was being reviewed.

Why does a router key on the method as well as the path?
The pattern names the resource and the method names the action asked of it, so both are needed to identify one route. Paths are perfectly capable of being unique, nothing in HTTP forbids reusing a path across verbs, and the cheap comparison is a consequence of the pair rather than the reason for it.
Which registration is not a valid Go ServeMux pattern?
A wildcard must be a full path segment, so a hole glued to a literal prefix inside one segment is rejected. A trailing multi-segment hole is allowed at the end of a pattern, a pattern with no method is allowed and matches every method, and a pattern with no hole is the ordinary literal case.

Primary source to go deeper

RFC 9110 §9.1 states that the method token is the primary source of request semantics and that the token is case-sensitive. Go's net/http.ServeMux documentation is the shortest complete statement of a pattern grammar in wide use: method, host and path in one string, with the wildcard rules written out.
