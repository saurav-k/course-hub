Module 05 · The layered service · Lesson 0504

Per-request facts belong to the request, so they are threaded through the layers rather than parked in a global

working 9 min The one argument every layer takes. · Go - the context package

The one-minute version

  • Four things belong to one request and not to the process: a deadline, a cancellation signal, the caller's identity, and a trace id.
  • A global has the lifetime of the process, so parking a per-request fact in one is a lifetime mismatch, and concurrency turns it into a wrong answer rather than a crash.
  • Go states the shape: a context carries deadlines, cancellation signals and request-scoped values across API boundaries, and it is the first parameter of every call that needs it.
  • A deadline is an instant, not a duration, so every hop inherits what is left rather than restarting the clock.
  • What it costs: a value in a context is invisible in the signature, so the mechanism that carries a trace id will happily carry a required argument nobody can see.

1. The mental model: match the lifetime to the fact

A process-level global lives as long as the process. A request lives for milliseconds, and a hundred of them are alive at once. Putting a per-request fact in a process-level place is a mismatch of lifetimes, and the symptom is not a crash: it is one request reading another request's user identity, on a busy afternoon, in a log line nobody thought to doubt.

So the fact travels with the work. Go's context package names the four things worth carrying and states the rule directly: a context carries deadlines, cancellation signals and other request-scoped values across API boundaries and between processes. Python's contextvars reaches the same destination from the other side, by giving each concurrent flow its own copy rather than one shared slot. Its documentation is explicit that stateful context managers should use context variables instead of threading.local(), so that state does not bleed into other code in concurrent use, and an asyncio task copies the current context and runs its coroutine in the copy.

2. The mechanism

What a context is

An immutable value with a cancellation signal attached. You never modify one. You derive a new one from it - with a deadline, with a cancel function, with a value - and pass the derived one down. Because it is immutable and derived rather than mutated, the same context can be handed to work running concurrently: Go's documentation states that contexts are safe for simultaneous use by multiple goroutines. That property is what lets a handler fan out to three calls and cancel all of them from one place.

Go also states the two conventions that make it readable: the context is the first parameter, named ctx, and it is not stored inside a struct type. Both are worth following outside Go. First-parameter means a reader can see at a glance which functions are request-scoped. Not-in-a-struct means the context cannot outlive the request that created it by being captured in something that lives longer.

A deadline is an instant

This is the detail that decides whether propagation works. A deadline is a point in time, not a number of seconds, so a call three layers down inherits what remains rather than starting a fresh two seconds of its own. Three hops each granting themselves the same duration is a budget silently multiplied by three, and it is why a client's timeout and a server's timeout so often disagree about who gave up first.

the deadline in two voices · both derive a bounded scope and both propagate downward
// Go: a deadline is a time, and the derived context carries what is left of it.
ctx, cancel := context.WithTimeout(r.Context(), 2*time.Second)
defer cancel()                       // release the timer whatever happens
err := h.orders.Cancel(ctx, id, reason)

# Python: the timeout cancels the running task and surfaces as TimeoutError.
async with asyncio.timeout(2.0):
    await orders.cancel(order_id=order_id, reason=reason)

The identity that survives the network

The trace id is the one per-request fact that has to mean the same thing in a service you did not write, which is why it is standardised rather than invented per team. The W3C Trace Context recommendation defines a traceparent field with four parts: a version, a 32-character trace id, a 16-character parent span id, and a two-character flags field whose only defined bit says whether the caller sampled the trace. All-zero values for the trace id and the parent id are invalid, and a vendor must ignore a traceparent whose trace id is invalid. A companion tracestate field carries vendor-specific name and value pairs alongside it.

3. What threading costs

Every function that needs the request now has an extra parameter, and so does every function between it and the edge, including ones that use nothing from it. That is real noise and it is the honest price: the alternative is ambient state, which removes the parameter by making the dependency invisible instead of absent.

The subtler cost is the value bag. A context can hold anything, and anything held there is missing from the signature, so a required argument can enter through the back door and no compiler will object. Go's documentation draws the line explicitly: use context values only for request-scoped data that transits processes and APIs, not for passing optional parameters to functions. A trace id qualifies. A page size does not.

Two failures ship together and both look tidy. Storing a context in a struct field lets it outlive the request, so a background worker built from that struct is holding a cancellation signal that fired minutes ago, or one that will never fire. Reaching for an ambient variable instead of a parameter - a context variable, a thread local, a framework's request-scoped singleton - passes review because the call sites get shorter, and it converts a compile error into a runtime one that only appears when the code is called from somewhere with no request in flight. The rule that avoids both is the boring one: pass it explicitly, to each function that needs it.

Why is a request deadline carried as an instant rather than a duration?
An instant is subtractive: three layers deep, what remains is what remains. A duration restarts at every hop, so a two-second budget becomes six seconds across three layers. Serialisation cost is irrelevant at this size, clients find durations easier if anything, and cancellation is a separate signal from either representation.
What does Go's documentation say a context's values are for?
The documentation says to use context values only for request-scoped data that transits processes and APIs, and names optional parameters as the thing not to use them for. Shared handler state and start-up configuration both have the process's lifetime rather than the request's, so neither belongs in a value that dies with the request.
