Module 06 · API design · Lesson 0600

A published shape cannot be recalled, so design is choosing what to promise

foundation 8 min The one constraint every later page in this module answers to. · Stripe - API upgrades and backward-compatible changes

The one-minute version

  • An API is a set of promises about observable behaviour, and the party who pays when one is withdrawn is the caller, not you.
  • You cannot recall a shape because you cannot enumerate the callers and cannot make them deploy on your schedule.
  • The asymmetry is the whole subject: adding is cheap and removing is not, so every published field is a decision you make once and live with.
  • Providers publish the asymmetry as two lists: what they may change freely, and what forces a new version. Stripe and GitHub both do.
  • What it costs: a promise small enough to keep forever is often too small to be useful, and the design work is choosing where between those to stand.

1. The mental model: a promise you cannot take back

The surface is whatever a caller can observe

Inside a process, an interface is a compile-time fiction: rename a method and the build tells every caller at once, because every caller is in the repository. Publish the same interface over HTTP and three of those properties vanish. You do not know who calls it. You cannot make them rebuild. And nothing tells you that a caller broke until the caller tells you, which is usually a customer telling you.

So the useful definition is behavioural rather than declarative: the promise is everything a caller can observe and rely on, whether or not you meant to offer it. That includes the field names in a response, the exact status code for a refusal, the wording of an error string a client is matching on, and the shape of an identifier a client is parsing. A promise nobody wrote down is still a promise once somebody depends on it.

2. The mechanism: which changes are free and which are not

The asymmetry, as two providers state it

The asymmetry is not folklore, and the clearest evidence is that large providers publish it as an explicit list. Stripe names the changes it considers backward-compatible and reserves the right to make them at any time: adding a resource, adding an optional request parameter, adding a response property, reordering response properties, changing the length or format of opaque strings such as object identifiers, and adding new event types. A client that breaks on any of those has broken on something it was told not to rely on.

GitHub publishes the mirror image: the changes it will only make in a new API version. Removing an operation, removing or renaming a parameter or a response field, adding a required parameter, making an optional parameter required, changing the type of a field, removing enum values, adding a validation rule to an existing parameter, and changing authentication requirements. Read the two lists together and a rule falls out that no specification states, because it is a property of the two ends rather than of the protocol.

Saying what you did not promise

The second half of the technique is stating the negative. Stripe does not merely say identifiers are opaque - it says the length and format may change, gives the concrete example of the ch_ prefix appearing or disappearing, and tells integrators to store up to 255 characters. That sentence exists because somebody parsed the prefix, and it is what lets Stripe keep changing identifier formats without a version bump.

Writing the negative down does real work: it converts an accidental promise into a documented non-promise, and it moves the cost of a later change from you to the caller who ignored it. It is the cheapest design act in this module and the one most often skipped, because it protects you against a problem you have not had yet.

3. The trade-off: a small promise is easy to keep and hard to use

The obvious response to all of this is to promise as little as possible: return identifiers only, document nothing, reserve everything. That does minimise your future cost, and it maximises everybody else's. A caller who cannot rely on a field has to fetch it again, defend against it, or ask you. An interface whose behaviour is entirely reserved is one nobody can build on without a support conversation, which is a cost you also pay, just in a different column.

So the design question on every field is not "is this correct" but "is this worth freezing". A field that is cheap to compute and expensive to promise - an internal state name, a count that will get slow at scale, a nested object you have not stabilised - is a field to leave out of the first release. You can add it later at no cost to anyone. That is the one direction the asymmetry runs in your favour, and it is worth spending deliberately.

Nothing in this page is enforced by a tool you already run. A compiler will not tell you that removing a response field breaks a caller, because the caller is not in your build, and your test suite passes because it was updated in the same commit. What catches it is a recorded description of the interface compared against the previous one in CI, which is the same mechanism lesson 0405 asked for on the wire schema, pointed at the HTTP surface instead. Without it, every rule here is a convention, and a convention is what people follow until a deadline.

Answer from memory before revealing.

Why can a published API shape not be withdrawn the way an internal interface can?
The constraint is organisational rather than technical: you cannot list the callers and cannot make them rebuild, so the change has no moment at which it is complete. HTTP does have retirement machinery, which lesson 0604 uses; caches expire on the rules of lesson 0204; and no wire format prevents a removal, which is exactly why lesson 0405 had to state the rule.
Which of these does Stripe publish as a change it may make without a new version?
Identifier length and format are declared non-promises, prefixes included, which is why integrators are told to store 255 characters. The other three appear on GitHub's list of changes that force a new API version, and each breaks a caller that was correct yesterday.

How this connects

  • Next, resources are nouns and the method is the verb spends this promise well, by borrowing a shape the whole network already understands.
  • Ahead, versioning is choosing who pays to change is what you reach for when the asymmetry runs out and a break is the honest answer.
  • Behind you, compatibility is a rule, not a hope made the same argument one layer down, about the bytes rather than the interface.
Your teacher. Take one endpoint your team owns and write the two lists for it: what a caller may rely on, and what you reserve the right to change. Ask the agent which items on your second list a caller could already be depending on today, and how you would find out.

Primary source to go deeper

Stripe's API upgrades page is a short, concrete statement of one provider's additive list, and reading it next to GitHub's API Versions page gives you the two halves of the asymmetry in about ten minutes. Both are worth reading as design documents rather than as reference: each list is a decision somebody had to defend.
