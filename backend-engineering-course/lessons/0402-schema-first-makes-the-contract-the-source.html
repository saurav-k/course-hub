Module 04 · Serialization and contracts · Lesson 0402

When the schema is compiled, the contract is checked by a build rather than by a reviewer

working 8 min The contract becomes a build artefact. · Protocol Buffers - Language Guide (proto3)

The one-minute version

  • A .proto file is not documentation. It is compiled into code both ends import, so the contract is something a build consumes rather than something a reviewer remembers.
  • The wire identity of a field is its number, not its name. Names never travel, which is what makes the encoding small and renaming cheap.
  • Field numbers run from 1 to 536,870,911, with 19,000 to 19,999 reserved for the implementation, and 1 to 15 costing the least space.
  • Proto3 preserves unknown fields through a parse and re-serialise, so an intermediary built against an older schema does not destroy a newer field.
  • What it costs: a build step, generated code in your tree, a payload no human can read in a log, and a new failure mode where the two ends compiled different revisions of the same file.

1. The mental model: the contract compiles

One declaration, two generated implementations

Schema-first inverts the usual order. Instead of writing a handler, deciding what JSON it emits, and describing that JSON afterwards, you write the message definition first and let a compiler produce the types on both sides. The producer's Order struct and the consumer's Order class are then not two independent guesses about the same shape. They are two outputs of one input, and if either end changes its idea of the shape the change has to be made in the shared file.

The property this buys is narrow and worth stating precisely: the shape, the names and the types of the fields become mechanically checked on each side, against a single declaration. That is a real reduction in the surface described in lesson 0400. It is not the whole surface, and section 4 says which part is left.

2. The mechanism: the number is the name on the wire

What a tag costs and why it is fixed

In JSON, the string "customer_email" is written into every message, every time. In protobuf the field carries only its number, and the number is what the parser matches on. The language guide is explicit that a number cannot be changed once the message type is in use, because it is the field's identity in the wire format, and that numbers should never be reused.

Two practical consequences follow directly. Numbers 1 to 15 encode their tag in a single byte, so the guide recommends them for the fields set most often, and the range 19,000 to 19,999 is reserved for the implementation and unavailable to you. Renaming a field, meanwhile, changes nothing on the wire at all: the name exists only in the schema and in the generated code, so it never crossed the gap in the first place.

3. The mechanism: unknown fields survive the trip

Why an old intermediary does not damage a new message

Number-keyed encoding creates a second useful property. When a parser meets a tag its schema does not define, it does not have to guess or discard: the tag is a well-formed number and the value is length-delimited or otherwise self-describing enough to skip. Proto3 keeps those unknown fields and includes them again when the message is serialised, which matches proto2's long-standing behaviour.

That matters most for anything in the middle. A gateway, an audit logger or a queue consumer built against last quarter's schema will parse a message containing a field it has never heard of, do its job, write the message back out, and pass the new field through intact.

4. The trade-off: a build, an opaque payload, and one new failure

The costs are real and worth naming rather than hand-waving. A build step and a generator now sit between the schema and the running code, which is a dependency in every CI pipeline that touches the service. The payload stops being readable, so a request you could once paste into a terminal now needs a tool to inspect, and the friction lands hardest during an incident. And the format is a poor fit for a public browser-facing API, which is why gRPC deployments so often terminate in a JSON gateway at the edge.

The failure that is genuinely new is subtler. A compiler checks each end against the schema revision that end was given. It has no way to check the two ends against each other, so two services compiled from different commits of the same .proto both build cleanly and can still disagree. That is why the schema wants a single distribution point, a registry or a versioned module, rather than being copied into each repository.

Generated code that is committed to a repository is a snapshot of a schema at one moment, and it is the moment nobody remembers to refresh. If you check generated files in, make regenerating them part of the build and fail the build when the output differs from what is committed, so a stale copy is a red pipeline rather than a live inconsistency. The alternative, generating at build time, trades that risk for a toolchain dependency on every developer machine.

Check yourself

Retrieval practice

Answer from memory before revealing.

Why can a protobuf field be renamed without breaking a consumer?
Encoded messages carry a tag number and a value, so the field's name exists only in the schema and the generated code and is not part of what the reader matches. No alias is generated, protobuf does no name matching of any kind on the binary wire, and reserving a name is a guard against future reuse rather than a grace period.
What does unknown-field retention in proto3 actually buy you?
Retention means a parser holds fields it does not recognise and writes them out again, so a service in the middle built on an older schema passes new fields through untouched. A malformed message still fails to parse, retention is the reason the ends do not need identical schemas, and uniqueness of numbers is enforced by the compiler in the file rather than by the wire format.
