Module 06 · API design · Lesson 0605

A retried POST is safe only when the server can recognise the repeat, and that is a stored key

working 9 min The promise the network cannot make for you. · RFC 9110 §9.2.2 - Idempotent Methods

The one-minute version

  • A client that gets no response cannot tell whether the request was lost or the response was, and those need opposite actions.
  • RFC 9110 lets a client automatically repeat a request only if the method is idempotent. POST is not, so a retried POST is a second order unless you make it otherwise.
  • An idempotency key is a value the client generates and the server stores with the first result beside it, so a repeat is answered rather than executed.
  • Stripe stores the status code and body of the first attempt whether it succeeded or failed, prunes keys after at least 24 hours, and errors when a key returns with different parameters.
  • What it costs: a key store with a retention policy, a fingerprint, and a hard truth - the key protects only what is inside your transaction.

1. The mental model: two failures that look identical

The client sees one thing and it means two

A client sends a request and the connection times out. Two histories produce that observation. In the first the request never arrived, nothing happened, and the correct action is to send it again. In the second the request arrived, the server did the work, and the response was lost coming back, so the correct action is to do nothing. The evidence is identical and the client still has to choose.

RFC 9110 addresses this directly and its answer is a permission with a condition: if a communication failure occurs before the response is fully received, a client may automatically repeat the request if and only if the method is idempotent. GET, HEAD, PUT and DELETE qualify. POST does not, which is not an oversight - POST is defined as asking the target to process an enclosed representation according to its own semantics, and two of those are two of whatever it does.

2. The mechanism: claim the key before doing the work

What the server stores

The server keeps a record per key holding the outcome of the first attempt. Stripe's implementation is worth copying in one respect that surprises people: it saves the status code and body of the first request for a given key regardless of whether it succeeded or failed, so a retry receives the same result including a 500. That is correct behaviour: retrying a key that failed lets the retry take a different path from the original, which puts you back where you started.

The rest of the contract is scope and lifetime. Keys are removed after they are at least 24 hours old, and a key reused after that pruning starts a fresh request. Sensitive data does not belong in a key, because the key is a lookup token and lives in your storage and your logs. And a key is only meaningful where it was needed: Stripe accepts keys on every POST and says not to send them on GET or DELETE, which are idempotent already.

The fingerprint, and the ordering that actually matters

A key on its own is not enough, because a client can send the same key with a different body, by accident or by attack. The answer is a fingerprint: a digest of the request payload stored beside the key, compared on every arrival. The IETF's Idempotency-Key draft names the three refusals that follow - 400 when a required key is missing, 422 when a key returns with a different payload, and 409 when the retry arrives while the original is still in flight.

That third one is where implementations go wrong, and it is an ordering problem rather than a storage one. If the key record is written after the work completes, two retries racing each other both find no record and both do the work, which is the exact failure the key exists to prevent. The claim has to come first and it has to be atomic: insert the key row under a unique constraint, in the same transaction as the effect, so that the second arrival either loses the insert and reads the winner's state, or finds a claimed-but-unfinished record and is refused with a 409.

3. The trade-off: the key protects your transaction, not the world

The guarantee is exactly as wide as the atomic write that claims the key. If the endpoint writes one row in one database, the key and the row commit together and the protection is total. If the endpoint charges a card, publishes an event and writes a row, the key covers only the part that shares a transaction with it, and a crash between the charge and the commit leaves an effect nobody's key knows about. Every module after this one that adds an integration point makes this cost larger, which is why the honest version of the promise names its boundary.

The rest of the bill is ordinary but real: a record per mutating request for at least a day, indexed by a client-supplied value, with a pruning job that actually runs. And you are now replaying stored responses, so a wrong stored result is served identically forever. The key store is a piece of the interface, not a cache in front of it.

The Idempotency-Key header is not a standard. The IETF draft that defines it is expired, so what you have is a widely copied convention with provider-specific semantics underneath: the retention window, what counts as a payload mismatch and which status a conflict returns are all decisions each provider made separately. Read the specific provider's documentation rather than assuming the draft, and when you publish an endpoint that accepts keys, document your own window and your own refusals. A caller cannot infer them, and a caller who guesses wrong retries outside your window and pays twice.

Check yourself

Retrieval practice

Answer from memory before revealing.

Why must the idempotency key be generated by the client rather than the server?
The server receives two identical requests and cannot tell a retry from a genuine second order, so the sameness has to be asserted by the party that has it: the caller. A server-issued value would need a round trip that the failure case has already lost, collisions are handled by scoping the key rather than by who made it, and indexing cost is identical either way.
A retry arrives while the first request is still executing. What should the server return?
The draft assigns 409 to a retry that overlaps an in-flight original, because the server has claimed the key but has no result to replay yet. It cannot return a result it does not have, 422 is reserved for a key reused with a different payload, and running the second request is the duplicate the key exists to prevent.

How this connects

  • Ahead, Module 10, async work takes the same problem to a queue, where delivery is at-least-once and a consumer needs this mechanism by default rather than on request.
  • Behind you, methods are verbs with guarantees is where idempotence was defined, and this page is what to do when the method does not have it.
  • Behind you, an error body is part of the contract is how a 409 or a 422 from this mechanism tells the caller which refusal it was.
Your teacher. Take one endpoint of yours that creates something and write out what happens if the same request arrives twice, one second apart. Then ask the agent where the key claim would have to sit relative to your transaction boundary, and which side effects would still escape it.
