An index is a second sorted copy, and every write pays to keep it true

working 10 min Why the depth of the tree barely grows and the write cost does. · PostgreSQL - Indexes

The one-minute version

  • With no index the engine scans the whole table row by row. With one it can walk a few levels down a search tree instead.
  • A B-tree is the default and it serves equality and range on sortable data: the five comparison operators, BETWEEN, IN, IS NULL, sorted retrieval, and a LIKE pattern anchored at the start.
  • Because the branching factor is large, depth grows logarithmically: a handful of levels reaches billions of rows, so a lookup on a big table is not much dearer than on a small one.
  • Once created, the index must be kept synchronised with the table, which adds overhead to every data manipulation. Reads got faster because writes got slower.
  • What it costs: an index that no query uses is pure write tax and storage, which is why the documentation says seldom-used indexes should be removed.

1. The mental model: a sorted copy of one column

The alternative is reading everything

PostgreSQL describes the unindexed case without euphemism: with no advance preparation the system would have to scan the entire table, row by row, to find all matching entries, and where there are many rows and only a few matches this is clearly an inefficient method. With an index maintained on the column, it might only have to walk a few levels deep into a search tree.

The mental model that survives contact with real systems is this: an index is a second structure, stored separately from the table, holding the indexed values in sorted order together with a pointer to where each row lives. It is a copy. It is derived from the table and it must be kept true, and both of those facts are where its costs come from. Lesson 0800 already created one of these without saying so, because a primary key is a uniqueness constraint that produces a unique B-tree index as its enforcement mechanism.

Why depth is not the problem

Engineers reason about tree lookups as if the cost grew with the table, and at the sizes a service actually reaches it barely does. Each node in a B-tree holds many keys, so the number of children per node, the fanout, is in the hundreds rather than the twos of a binary tree. That number is what decides everything.

  1. Assume a fanout. Take 200 children per node, which is the right order of magnitude for a page-sized node holding short keys. The exact figure depends on key width and page size and is worth measuring rather than assuming.
  2. Count what each level reaches. A tree of depth d addresses 200d entries: 200 at one level, 40,000 at two, 8,000,000 at three.
  3. Add one more level. Depth four reaches 1,600,000,000 entries. So the table grew two hundredfold and the lookup got one node read more expensive.

2. The mechanism: which questions a B-tree can answer

An index is only useful for questions its ordering can answer, and the documentation is specific. B-trees handle equality and range queries on data that can be sorted into some ordering, which means the five comparison operators, plus constructs equivalent to combinations of them such as BETWEEN and IN. An IS NULL or IS NOT NULL condition can use one. So can a pattern match, but only when the pattern is a constant anchored to the beginning of the string: col LIKE 'foo%' can use the index and col LIKE '%bar' cannot. And because the leaves are in key order, a B-tree can also be used to retrieve data in sorted order, which is how an ORDER BY avoids a sort.

That list explains most of the cases where an index exists and is not used. A leading wildcard has no prefix to descend on. A function applied to the column, such as WHERE lower(email) = ..., is a different value from the one the index stores. And a condition that matches most of the table is one the planner will refuse the index for on purpose, because reading most of the rows through an index means the two reads of the figure above, in random order, for nearly every row.

The other index types exist for the questions a sort order cannot answer. Hash serves simple equality comparisons only. GIN is an inverted index for values with several components, such as an array or a document, and is efficient at testing whether a component value is present. BRIN indexes block ranges and is most effective when a column's values are well correlated with the physical order of the rows, which is the shape a timestamp on an append-only table has. GiST and SP-GiST are infrastructure for geometric and nearest-neighbour searches. Reach for one of these when the question is not "where does this value sit in an order", and reach for the default when it is.

3. The trade-off: the write path pays

PostgreSQL states the bill in one sentence: after an index is created, the system has to keep it synchronised with the table, and this adds overhead to data manipulation operations. It draws the obvious conclusion in the next: therefore indexes that are seldom or never used in queries should be removed.

That is a maintenance instruction more than a tuning tip, and it is easy to act on because the engine records index usage. An index nobody reads is a pure loss with three parts: the write amplification above, the storage, and the time it adds to every restore and every rebuild. The habit worth forming is to audit index usage on a schedule rather than to argue about each one at review time, since the only evidence that settles the question is production traffic.

An index also slows down the thing it was added to speed up, if it is added to the wrong shape of table. Every insert into a B-tree on a monotonically increasing column, a timestamp or a sequence, lands on the same rightmost leaf, so a heavily written table contends on one page. It works and it is the standard shape, but it is the one case where the sequential access pattern that helps a range scan hurts the writer, and it is worth knowing before you conclude that the disk is the problem.

Answer from memory before revealing.

Which condition can a plain B-tree index on email help with?
A pattern anchored at the start gives the descent a prefix to follow, and the ordered leaves then serve the sort for free. A leading wildcard has no prefix, a function over the column stores a different value from the one indexed, and an inequality matches nearly the whole table so the planner will prefer to read it directly.
A table grows from 8 million rows to 1.6 billion. What happens to an indexed single-row lookup?
Depth grows with the logarithm of the row count at the fanout, so two hundred times the rows is one more level. A proportional cost is what a scan does rather than a tree, the depth does grow rather than being fixed, and an index larger than memory costs more page reads but does not stop being used.
