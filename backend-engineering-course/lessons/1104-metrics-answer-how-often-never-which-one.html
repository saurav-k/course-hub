Module 11 · Resilience and observability · Lesson 1104

A metric is an aggregate, so it can say a service is unwell and never which request was

working 10 min The third signal, and the only one you can afford to keep for every request forever. · Google SRE Book - Monitoring Distributed Systems

The one-minute version

  • A metric is a number per label set per interval, not a record per request, which is what makes it cheap enough to keep for years and useless for identifying anything.
  • Its cost is cardinality. Every unique combination of label values is a new time series, so a user id in a label is how a monitoring bill becomes an incident.
  • Latency is a distribution and a mean is a bad summary of it. The Google SRE book's own example: a 100 ms average at 1,000 requests a second can easily hide 1% of requests taking 5 seconds.
  • So durations are recorded as bucketed histograms, because buckets can be added across instances and precomputed quantiles cannot.
  • What it costs: an unread dashboard is the normal outcome. A number earns its place only once a target and a consequence are attached to it.

1. The mental model: a number per label set, not a record per request

The other two signals are records: one per execution, one per operation. A metric is not. It is a small set of numbers, updated in place, sampled at an interval, and identified by a name plus a set of label values. Ten thousand requests move a counter ten thousand times and store nothing extra, which is what makes it the only signal you can afford to keep at full resolution for a year.

Everything else about metrics follows from that. It can tell you a rate, a trend, a ratio and a shape. It cannot tell you which request, which customer or which value, because none of those were kept. Reaching for a metric to answer "which one" is the mistake that produces a label carrying a user identifier, and that is not a small mistake - Prometheus' naming guidance is explicit that every unique combination of key-value label pairs represents a new time series and that labels must not store high-cardinality dimensions such as user ids or email addresses.

2. The mechanism: the mean is where almost nothing happens

The four golden signals of the SRE book are latency, traffic, errors and saturation, and the book is careful about latency in a way most dashboards are not: it says to distinguish the latency of successful requests from that of failed ones, because a fast failure otherwise flatters your numbers. Then it makes the argument that decides how the number is stored at all. If you run a service with an average latency of 100 ms at 1,000 requests a second, 1% of requests might easily take 5 seconds.

Buckets add up and quantiles do not

The fix the SRE book recommends is to collect request counts bucketed by latency rather than actual latencies: how many requests took 0 to 10 ms, 10 to 30 ms, 30 to 100 ms, and so on. That is a histogram, and the reason it is a histogram rather than a precomputed 95th percentile is arithmetic. Prometheus' own guidance labels avg(http_request_duration_seconds{quantile="0.95"}) as bad and says averaging quantiles yields statistically nonsensical values: the 95th percentile of ten instances is not the 95th percentile of the fleet, and no operation on the ten recovers it.

Bucket counts do compose. Add the le="0.1" counters of ten instances and you have the fleet's count of requests under 100 ms, exactly, and the quantile is estimated from the summed buckets afterwards. The price is accuracy: the estimate is interpolated inside whichever bucket the quantile falls in, so a spike at 220 ms inside a 200-to-300 ms bucket comes back as roughly 295 ms rather than 220. That is not a rounding error, it is the difference between comfortably inside an objective and about to breach one, and it is decided by bucket boundaries you chose before you had the data.

3. Making the number answer something: a target and a consequence

A number with no target is a number nobody looks at, which is the ordinary fate of a dashboard. The SRE workbook's construction is three steps. An indicator is a ratio of good events to total events - not a raw gauge, a ratio, so it is comparable across load. An objective is a target for that ratio over a window. And the error budget is what is left: 100% minus the objective, so a 99.9% objective over three million requests in four weeks is a budget of 3,000 failures.

The budget is what converts observability into a decision, because it is spendable. Below budget, ship. Out of budget, the policy says what stops. The workbook is direct about why the target is never 100%: components fail, users cannot perceive the difference through their own network anyway, and a service that must never fail can never be changed - it calls 100% an operations team's objective rather than an engineering culture's.

Cardinality is the failure that arrives as a bill and stays as an outage. A label set of five labels with ten values each is a thousand series and is fine; adding a customer id to it multiplies by your customer count, and the series are created by your own running code faster than anyone can react. Two rules close most of it: no label may take a value from user input or from a request path segment, and a new label is a review question rather than a one-line change. The status code, the method, the route template and the outcome are labels. The order id, the tenant name and the user agent are not - those belong on the log line of lesson 1102, which was designed to carry them.

Why record latency as histogram buckets rather than as a precomputed 95th percentile?
Averaging per-instance quantiles is statistically meaningless, while adding bucket counters is exact and the quantile is estimated afterwards. The first is false - a set of buckets costs more series than one quantile; the second is the opposite of what a bucket does, since bucketing discards the value; and the fourth is wrong in the way that matters, because bucket boundaries are chosen in advance and a badly chosen one distorts the estimate.
Which of these is safe to use as a metric label?
A route template has as many values as you have routes, which is a number you control. The other three are unbounded sets driven by traffic - the path expands to one series per order, the customer id to one per customer, and the user agent to one per client build - and each new value is a series your own code creates at request rate. Anything unbounded belongs on a log line instead.
