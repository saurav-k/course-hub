JSON has six kinds of value, and a date, a decimal and a 64-bit integer are none of them

foundation 9 min The type system is smaller than you remember. · RFC 8259 §3 - Values

The one-minute version

  • RFC 8259 allows a value to be an object, an array, a number, a string, or one of the three literals true, false and null. That is the whole type system.
  • A number is a decimal literal with no declared precision. The RFC names the interoperable integer range as -(253)+1 to 253-1, and nothing outside it is safe.
  • A date, a money amount and a database id therefore arrive as a string or a number by convention, and the convention lives in your documentation or nowhere.
  • Member names should be unique and their order is not guaranteed to be visible, so neither is a place to put meaning.
  • What it costs: JSON's readability is paid for by making every domain type your problem, on both ends, forever.

1. The mental model: six values and a large hole

The six, in full

The specification is unusually blunt about it. A JSON value must be an object, an array, a number or a string, or one of the three literal names false, null and true, which must be lowercase, with no other literals allowed. Count the kinds and you get six: object, array, number, string, boolean, null. There is no seventh, no extension point and no way to tag a value with what it means.

Every backend type you actually work with therefore has to be carried by one of those six, with a rule attached that the format does not record. That rule is the contract from the previous lesson, and this is where most of it comes from.

2. The mechanism: the number is the sharpest edge

Where exactness stops

JSON's grammar for a number is an optional minus, an integer part with no leading zeros, an optional fraction and an optional exponent. Infinity and NaN are not permitted at all. What the grammar deliberately does not say is how large or how precise a number may be, and the RFC hands that back to the implementation.

It then does something more useful than a rule: it names the range that works everywhere. Because software implementing IEEE 754 binary64, the double, is what nearly every parser is built on, integers in the range -(253)+1 to 253-1 are interoperable in the sense that every implementation will agree exactly on their value. Above that, agreement stops being guaranteed, and the disagreement is a rounding rather than an error.

The arithmetic is worth doing once, because it makes the failure concrete. Take the id 9007199254740993, which is 253+1. A binary64 double has 53 bits of significand, so at this magnitude the representable values are spaced two apart: 9007199254740992 is representable and 9007199254740993 is not. A parser reading that number stores the nearest representable value, 9007199254740992, and re-serialising it writes that back. The document was valid, the parse succeeded, and the id now points at a different row.

This is exactly why the Protocol Buffers JSON mapping, which is a specification written by people who had to survive this, encodes int64, uint64 and fixed64 as decimal strings rather than as JSON numbers, while accepting either on the way in. It is the standard workaround, promoted to a rule.

3. The mechanism: the conventions that fill the hole

Three carriers you have to choose deliberately

Once you accept that JSON will not help, the work is to choose each carrier on purpose and record the choice. Timestamps go as RFC 3339 strings, in UTC, with an explicit offset, because a string carries the time zone and an epoch integer does not. Money goes as an integer of minor units or as a decimal string, never as a JSON number, because 19.99 is not exactly representable in binary floating point and a sum of a thousand such values will drift. Identifiers go as strings whenever they can exceed the safe integer range, which in practice means always, since an id that grows is an id that will cross it.

None of these is a rule the format enforces. Each is a line in your API documentation and a type at your boundary, and lesson 0403 is about making the second one carry the first.

4. The trade-off: three ways to say nothing

Missing, null, and zero

The last gap is the one that produces the most support tickets. A field can be absent from the document, present with the value null, or present with a zero-like value: 0, "", []. Those are three distinct states in the document and they usually mean three different things: not sent, explicitly cleared, and genuinely zero. Most deserialisers flatten them. Go's encoding/json matches incoming keys to struct fields, so a key that never arrives matches nothing and leaves the field at the zero value it started with, which is the same value an explicit 0 would produce.

The cost of the flattening only appears on a partial update: a client that omits a field to mean "leave it alone" and a server that reads absence as zero will together clear the field. Carrying the distinction means a pointer, an Optional, or a sentinel type at the boundary, which is more code for a case most requests never hit. That is a real trade-off and it should be made per endpoint rather than per service.

JSON's tolerance goes further than most people expect, and two of its allowances are places where the specification itself declines to promise anything. Member names within an object should be unique; when they are not, RFC 8259 says the behaviour of receiving software is unpredictable, with implementations variously keeping the last pair, erroring, or keeping all of them. Member order is likewise not guaranteed to be visible to the calling program. Never encode meaning in either, and never assume a document that round-trips through your service preserves the order it arrived in.

Why does the Protocol Buffers JSON mapping send an int64 as a string?
Most parsers hold every JSON number as a double, so an integer beyond the interoperable range is silently rounded to the nearest representable value. JSON's grammar sets no size limit at all, so nothing is forbidden; compression is unrelated and would favour the shorter form; and the rule about names being strings is true but concerns keys rather than values.
A client omits nickname from a PATCH body. What has it said?
RFC 8259 defines the grammar and says nothing about what an absent member means, so the meaning is yours to state and yours to implement. The second and third options are both defensible designs, which is exactly the problem: they cannot both be the default. The fourth describes what many deserialisers do by accident rather than what the client meant.
