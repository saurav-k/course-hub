Module 06 · API design · Lesson 0603

The status code says which family the failure is in and the body says which failure it is

working 8 min Two readers, two granularities, one response. · RFC 9457 - Problem Details for HTTP APIs

The one-minute version

  • RFC 9457 opens by naming the gap: HTTP status codes cannot always convey enough information about errors to be helpful.
  • The status class is the coarse signal every intermediary reads. The body is the fine one, and only the caller reads it.
  • A problem document is application/problem+json with five optional members: type, status, title, detail, instance.
  • type is the identifier a client branches on, not title. Absent, it defaults to about:blank, meaning the status code is the whole story.
  • What it costs: a stable problem type is a promise, so your error vocabulary now has the same change rules as the rest of the API.

1. The mental model: two readers with different needs

The status line is shared and therefore coarse

A status code is read by software that knows nothing about your domain: proxies, load balancers, retry libraries, dashboards. That audience is why the code is deliberately coarse. It has to mean the same thing for every service on the web, so it can distinguish "your request was wrong" from "my server broke", and it cannot possibly distinguish "this card was declined" from "this currency is unsupported". Both of those are 4xx and both are correctly 4xx.

The caller's code needs the second distinction, and it needs it in a form it can switch on. Left without one, every client team invents the same workaround: match on the human-readable message. That converts your prose into an interface, and from then on rewording a sentence breaks a caller, which is the accidental promise from lesson 0600 in its purest form.

2. The mechanism: the five members, and the one that matters

A problem document, stated

The media type is application/problem+json, and the object carries five members, all optional. type is a URI reference identifying the problem type. status is the status code the origin generated, repeated in the body so the document survives being copied out of the response. title is a short human-readable summary of the type. detail is a human-readable explanation of this specific occurrence. instance is a URI reference identifying that occurrence.

a 422 response body · application/problem+json, with one extension member
{
  "type": "https://api.example.com/problems/unsupported-currency",
  "title": "Unsupported currency",
  "status": 422,
  "detail": "Orders in ZWL cannot be created from a GB merchant account.",
  "instance": "/orders/attempt-9f2c",
  "supported_currencies": ["GBP", "EUR", "USD"]
}

The last member is the part people miss. Section 3.2 allows a problem type to extend the object with members specific to that type, and that is where the machine-actionable detail belongs: the field that failed, the values that are allowed, the time to wait. A client that does not recognise an extension member ignores it, which is the same forward-compatibility rule module 04 established for every other body.

The type URI identifies, and does not have to resolve

Two rules about type are worth stating precisely because both are commonly misread. First, when type is absent it defaults to about:blank, which means the problem has no semantics beyond the status code itself - a legitimate document rather than an incomplete one. Second, the URI is an identifier and not necessarily a location: the specification says consumers should not automatically dereference it, except when showing information to a developer. Using a URI buys you a namespace nobody else can collide with, and it buys that whether or not anything is served there.

3. The trade-off: an error vocabulary is a published surface

Adopting problem documents does not reduce your obligations, it names them. The moment a caller branches on type, that URI is under the rules of lesson 0600: you cannot rename it, cannot repurpose it, and cannot split one type into two without breaking whoever matched the old one. Adding a new type is safe, in the same way adding a field is safe, and only if callers were told to treat an unrecognised type as a generic failure of its status class.

There is also a limit on how much to say. Section 5 of the specification is about exactly this: a problem document can leak information that helps an attacker, and generators are encouraged to keep implementation details such as a stack dump out of the HTTP interface. The rule that follows is a useful one to hold: detail is for a person who is allowed to know, and anything an unauthenticated caller should not learn goes into your logs behind an instance identifier instead of into the body.

A convincing error format is not the same as a correct status code, and the second mistake is worse. A service that returns 200 with a problem document in the body has broken every retry library, cache and dashboard between it and the caller, all of which read the status line and stop. If you take one thing from this page it is that the body extends the status code and never substitutes for it: choose the code first, by the rules of lesson 0202, and let the document say which member of that family this is.

Check yourself

Retrieval practice

Answer from memory before revealing.

Which member of a problem document should a client branch on?
RFC 9457 names the type URI as the primary identifier for a client. Detail is prose about one occurrence and changes freely, instance points at this single event rather than at a kind of event, and title is a human summary that the specification treats as advisory precisely so you can reword it.
What does an absent type member mean?
All five members are optional, and an absent type defaults to about:blank, meaning there are no semantics beyond the status code. The document stays valid, instance identifies an occurrence rather than a kind, and there is no registration requirement that an absent member could signal.
