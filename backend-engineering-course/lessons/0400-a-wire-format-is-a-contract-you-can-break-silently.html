Module 04 · Serialization and contracts · Lesson 0400

Serialization is where two independently deployed programs agree, and the failure mode is silence

foundation 8 min The one boundary no compiler crosses. · RFC 8259 §6 - Numbers, and what "interoperable" means

The one-minute version

  • Serialization is two functions in two programs that must agree: one turns values into bytes, the other turns bytes back into values.
  • The two programs are deployed on different days by different people, so nothing compiles them together and nothing type-checks across the gap.
  • A format checks its grammar, never your contract. {"amount": 19.99} parses everywhere and still means two different things.
  • So the break arrives as a wrong value that flows onward, not as an exception at the point of the mistake.
  • What it costs: writing the contract down is work nobody asks for until the day the silence gets expensive.

1. The mental model: one agreement, two deploy schedules

Inside one program, passing a value is free of doubt. The compiler or the interpreter knows the type, the field names are checked when you build, and renaming something breaks the build in the place that needs fixing. None of that survives the socket. The moment a value leaves your process it becomes a run of bytes, and the program that reads it back has its own idea of what those bytes mean, written by someone else, released last Tuesday.

So a wire format is not a serialisation detail. It is the interface between two teams, expressed in the one medium both can read. When people say an API has a contract, this is the layer they are pointing at, and it is worth being exact about what lives in it.

2. The mechanism: three layers, and only two are checked

The wire format: the grammar both ends parse

The format is the outermost layer, and the one with a specification. JSON's grammar is a few pages of ABNF in RFC 8259: what a value may be, where a comma goes, which escapes are legal. A parser either accepts the bytes or reports an error, and that decision is deterministic and shared. This layer is genuinely checked, and it is the only one that fails loudly.

Serialization: the mapping from your types to that grammar

The second layer is the mapping between the format's small type system and the far richer one your program uses. A Go struct field with a tag, a Python dataclass field, a generated protobuf accessor: each is a rule saying that this application-level concept is carried by that place in the document. Libraries do this well and it rarely goes wrong within one language, because the mapping is generated from a declaration that is compiled.

The contract: everything the grammar cannot say

The third layer is the one with no enforcement anywhere. It is the set of statements that make the bytes mean something: that amount is minor units and not major, that created is UTC and not local, that status is one of five strings, that an absent discount means no discount rather than an unknown discount. Not one of those is expressible in JSON's grammar, and none of them fails when broken. The document still parses.

3. The mechanism: what a silent break actually looks like

The word "silent" is doing real work here, so it is worth four concrete shapes rather than an adjective. Each of these produces a valid document, a successful parse and a wrong outcome.

4. The trade-off: tolerance is what buys the silence

It is tempting to conclude that parsers should be stricter, and to stop there. But the tolerance is deliberate, and it is what makes independent deployment possible at all. Go's encoding/json states the rule plainly: object keys with no corresponding struct field are ignored by default. That is exactly what lets a producer add a field on Tuesday without coordinating a release with six consumers, and it is exactly what makes a typo in a field name invisible.

You cannot have both properties from one default. What you can do is choose per boundary: tolerant where a third party you do not control is the producer, strict where you own both ends and would rather find the typo now. Go exposes the strict half as Decoder.DisallowUnknownFields. Lesson 0403 makes that choice a design position rather than a flag.

A contract that lives only in a wiki page, a Slack thread or the reviewer's memory is not a contract, because nothing re-reads it. The rest of this module is about moving each part of it somewhere that gets re-read on every build: a schema a compiler consumes, a validator at the boundary, a compatibility rule with a name. Where you genuinely cannot do that, write the assumption in the field's own documentation and say who breaks if it changes.

Why is a serialization break usually silent rather than loud?
A renamed field or a changed unit leaves a document that is still valid under the format's grammar, so every mechanical check passes and the wrong value flows onward. Parsers do report grammar errors, HTTP does have 400 and 422 for a request it cannot use, and log sampling is unrelated: the point is that nothing detected an error to log.
Which of these is part of the contract rather than the format?
What absence means is a decision your two programs make and no specification states, which is why it has to be written down. The other three are all settled by RFC 8259 itself: trailing commas are ungrammatical, interchanged JSON text must be UTF-8, and an object member name is always a string.

Primary source to go deeper

RFC 8259 §6 is the shortest demonstration of this whole page. It defines the grammar of a number precisely, then spends the rest of the section on what the grammar does not settle: precision, range, and the fact that a document one implementation writes may not be a document another can read back exactly. §4 does the same for duplicate member names, where the specification says only that behaviour is unpredictable.
