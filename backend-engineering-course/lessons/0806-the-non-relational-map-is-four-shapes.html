Non-relational is four shapes, and each buys speed by refusing a question

frontier 11 min Choosing a store is choosing which queries you promise never to invent. · AWS - NoSQL design for DynamoDB

The one-minute version

  • "NoSQL" names no shape. There are at least four, and they differ from each other more than any of them differs from SQL.
  • The shared move is the same in all four: the access pattern is designed in, so the store never has to work out how to answer a question at read time.
  • AWS says it directly for DynamoDB: do not start designing the schema until you know the questions it must answer, and keep as few tables as possible.
  • The corresponding refusal: data can be queried efficiently in a limited number of ways, outside of which queries can be expensive and slow.
  • What it costs: the invariants of lesson 0800 and the boundary of lesson 0801 usually do not span entities here, so they move back into every writer.

1. The mental model: four shapes, not one category

Key-value and wide-column: the pattern is the schema

AWS states the design method for DynamoDB as an inversion of the relational one. In a relational system you design for flexibility without worrying about implementation details, and normalisation matters. In DynamoDB you design the schema specifically to make the most common and important queries as fast and inexpensive as possible, and you should not start designing it until you know the questions it will need to answer. The advice that follows sounds wrong to a relational ear and is consistent with that premise: maintain as few tables as possible, keep related data together, and design keys so related items sort together and traffic spreads across partitions rather than concentrating on one.

The refusal is stated just as plainly. Data can be queried efficiently in a limited number of ways, outside of which queries can be expensive and slow. A question you did not design for is not merely slower here, it is a scan.

Document: the record is the unit

A document store keeps a whole nested record as one value. MongoDB's stated core principle is that data that is accessed together should be stored together, and its schema is flexible in a specific sense: documents in one collection are not required to have the same fields, and a field's type may differ between documents. Modelling a relationship is then a choice between embedding and referencing, and embedding is what avoids joins across collections.

The limit is where the shape shows through. A document has a maximum size, 16 mebibytes, and a nesting depth cap of 100 levels. An entity that grows without bound, an order with unbounded line items or a post with unbounded comments, cannot be embedded, so the access pattern that made embedding attractive is exactly the one that eventually breaks it.

In-memory structures, and graphs

Redis describes itself as a data structure server, and that is the accurate description rather than "a cache". It provides strings, hashes as field-value records, lists sorted by insertion order, sets of unique strings with membership testing in constant time regardless of size, sorted sets ordered by a score, and streams that act as an append-only log. You do not query it. You pick the structure whose operations are the thing you need, and the choice of structure is the design.

A graph store makes the connection the unit. Neo4j's property graph model has nodes, which describe entities and carry zero or more labels, and relationships, which connect a source node to a target node and always have a direction. Both may carry properties. The reason to reach for it is a question whose answer is a path of unknown length, which in SQL is a join whose depth you must write out in advance.

2. The mechanism: what you are handed instead of a guarantee

That figure is the shape of every trade on this page. The property you lost is one you never had to name while it was there, so the cost lands in application code written by someone who assumed it. The list is short and worth holding: a store that does not enforce a foreign key has moved referential integrity into every writer, a store whose transaction cannot span two entities has moved atomicity into a retry design, and a store with no planner has moved query planning into your schema, permanently, at design time.

None of this makes a relational engine the safe default in the way its defenders usually mean. It refuses to scale writes past one node without work you also have to design, its planner can change a plan under you between two Tuesdays for the reasons lesson 0805 gave, and a schema change on a large table is an operation with a lock in it. The honest position is that both sides of this page cost design work, and the difference is when you pay: the non-relational shapes charge you up front, at schema design, and the relational one charges you later, at scale.

3. The trade-off: choosing, and the polyglot temptation

Which is the honest end of this page. Running two stores is a real answer and it has a real cost, and the cost is not operational: it is that a fact now lives in two places and nothing in either engine will keep them agreeing. The invariant that lesson 0800 could state in one line of schema becomes a synchronisation problem the moment the order lives in the relational store and its search document lives elsewhere. Module 10 is where that problem gets a mechanism, and until then the useful discipline is to name which store is authoritative for each fact and to treat every other copy as a derived view that is allowed to be behind.

So the decision procedure is short. Write down the questions the system must answer, and be honest that the list will grow. If you cannot enumerate them, you are buying flexibility and should start relational. If you can, and the volume genuinely exceeds one node, the up-front design is a fair price. And if the answer is "we need both", pick which store owns the truth before you pick the second one, because that choice is much harder to change later than either engine is.

What does AWS say you must do before designing a DynamoDB schema?
The stated method is to identify the query patterns first, because the schema is built to serve them. Normalisation is the relational habit this inverts, size matters for partitioning but comes after the patterns, and secondary indexes are chosen to serve patterns rather than before them.
A read straight after a successful write returns the old value. What happened?
Eventually consistent is the default, so a read may be served by a replica that has not caught up, and repeating it shortly after returns the newer value. The write was durably persisted before the 200 came back, no refusal occurred, and a different key would return nothing at all rather than a stale value.

  • Behind you, a constraint is the only rule every writer obeys is the guarantee most of these stores decline, and the reason declining it costs something.
  • Behind you, a composite index has one useful order is the same access-pattern-first argument, made inside a store that will also answer the questions you did not plan.
Your teacher. Write down every question your service asks of its store, then ask the agent which of them a key-value shape could serve with one key and which would become a scan. The ones that become scans are the argument for the store you already have.
