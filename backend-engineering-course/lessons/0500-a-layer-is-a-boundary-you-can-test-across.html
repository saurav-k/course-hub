A layer earns its name when you can replace what is below it in a test

working 9 min The test that separates a layer from a folder. · The Go specification - Implementing an interface

The one-minute version

  • A directory named services is a claim about intent. A layer is a contract, and the difference is testable.
  • The test: take everything below the boundary away, put something else there that satisfies the same contract, and run the code above it.
  • The thing that makes the swap possible is a seam: a name the caller depends on and any number of things may satisfy.
  • Cases multiply along a request path and add across a boundary, which is the whole economic argument for layering.
  • What it costs: indirection every reader pays for, and a double that can drift from the real thing while every test stays green.

1. A folder is a claim, a layer is a contract

Most codebases have a directory called services and another called repositories, and most of them do not have layers. The directories are a claim about intent, and intent is not enforceable. A layer is something stronger: a named boundary where the code above depends on a contract rather than on any particular thing that satisfies it. The test for that is blunt, and it is the whole of this page. Take everything below the boundary away, put something else there that answers to the same contract, and run the code above it. If that is possible, the boundary is real. If it is not, you have a folder with an aspirational name.

The reason to use that test rather than a prettier one is that it is the only property that cannot degrade quietly. A naming convention erodes one merge at a time and nothing reports it. A boundary you can substitute across stops working the moment somebody reaches through it, because the substitute no longer satisfies what the caller reached for.

2. The mechanism: a seam, and something to put in it

The seam

A seam is a place where behaviour can be changed without editing the code whose behaviour changes. It is not a design pattern and it needs no framework. In a statically typed language it is usually an interface, and Go states the property that makes this work: a type implements an interface if it is an element of that interface's type set, and no declaration anywhere says so. Nothing has to announce that it implements anything. The consequence is the one that matters here. The interface can be declared by the code that consumes it, in the consumer's own package, listing only the operations the consumer actually calls, and any type that happens to have those methods satisfies it - including one that exists only in a test file.

Python has no compiler enforcing the match, so its seam is the constructor argument. A service handed its store as a parameter has a seam whether or not anybody writes a Protocol for it. A service that imports a module-level connection has none, and no directory structure will give it one, because the dependency was resolved at import time and there is no argument to pass anything else in.

the seam in two voices · the interface names what the caller needs, not what the store offers
// Go: the consumer declares the contract, in its own package.
type Orders interface {
    ByID(ctx context.Context, id OrderID) (Order, error)
    Save(ctx context.Context, o Order) error
}

type OrderService struct{ orders Orders }   // no database type named here

# Python: the seam is the constructor argument, and the type is documentation.
class OrderService:
    def __init__(self, orders: Orders) -> None:
        self._orders = orders               # never a module-level handle

The test double

A test double is whatever you put on the far side of the seam while the test runs: a map in memory, a recorder that remembers what it was asked for, a stub that fails on every call. Its job is not to be realistic. Its job is to make the behaviour under test the only thing in the run that can vary, so that a failure names one cause instead of a region.

3. Why the indirection pays for itself

Cases multiply along a request path and add across a boundary. Suppose the path holds k decision points and each one has m outcomes. A test that starts at the HTTP edge and ends at the database has to reach every combination, because it cannot stop halfway. A test that can stop at a boundary covers each decision point separately.

end-to-end cases = mk     layered cases = k × m Read as: k is how many places on the path make a decision, and m is how many outcomes each of those places has. Crossing the whole path in one test costs m multiplied by itself k times. Stopping at each boundary costs m cases per decision point, added up.

4. What the boundary costs

Every boundary is an indirection, and a reader tracing a call pays for it at each crossing: one more name to resolve, one more file to open, one more place where the thing actually running is decided somewhere the code does not say. That cost is real and it is charged on every future reading, not once at authoring time.

So a boundary earns its place when something is genuinely substituted across it - a test double, a second implementation, a store you have concrete plans to replace. A boundary with exactly one implementation and no test that swaps it is ceremony, and the honest move is to delete the interface and keep the folder. The rest of this module argues for three specific boundaries, and each of them has to make that case rather than inherit it.

The arithmetic above assumes the decision points are independent, which is exactly what layering is supposed to make true and frequently is not. It also buys nothing about whether the double behaves like the real store: a fake repository that never raises a unique-constraint violation supports a green suite that has never seen the failure production shows you first. The layered count covers the decisions and not the integration, and the tests that cover the integration are a separate cost this course meets again in Module 13.

What makes a boundary a layer rather than a folder?
Substitution is the only one of the four that fails loudly when somebody reaches through the boundary. Grouping by role and agreeing a naming rule are both claims about intent that erode one merge at a time, and a linted import list catches the imports somebody wrote down rather than the coupling they actually created.
Why can a Go test double satisfy a service's interface?
Go's specification defines implementation as membership of the interface's type set, with no declaration involved, which is what lets the consumer own the interface. Declaring implementation is what Java requires and Go does not, a container is a wiring mechanism rather than a satisfaction rule, and nothing is rewritten at link time.
