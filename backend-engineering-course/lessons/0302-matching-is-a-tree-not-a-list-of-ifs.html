Module 03 · Routing · Lesson 0302

A router compiles its patterns into a tree, so match cost tracks path depth rather than route count

working 9 min The structure behind the match. · Go - net/http routing_tree.go

The one-minute version

  • Patterns are compiled once, at registration, into a tree whose levels are host, then method, then consecutive path segments.
  • Matching walks the tree one segment at a time, so the work is set by how deep the path is, not by how many routes exist.
  • Shared prefixes are shared nodes. A hundred routes under /v1/orders pay for those two segments once.
  • Precedence is decided by specificity: a pattern matching a strict subset of another's requests wins, and Go panics at registration when neither is more specific.
  • What it costs: a literal that loses to a wildcard forces the walk to back up and try again, and the tree cannot express a pattern the segment grammar has no shape for.

1. The mental model: the list of ifs, and where it breaks

The obvious router is a list. Keep every registered pattern in the order it was added, and for each request compare the incoming path against each one until something matches. It is correct, it is about fifteen lines, and it is what a first router always is. Its cost is the problem: the work per request is proportional to the number of routes, and it is worst for the routes registered last, which in a growing service is the newest feature.

The tree replaces one long list of whole-path comparisons with a short chain of single-segment lookups. Nothing about the answer changes. What changes is that the request stops paying for routes it was never going to match, because the first segment it consumed already eliminated every subtree that did not begin that way.

2. The mechanism: build once, walk per request

The tree: host, then method, then segments

Go's implementation states the shape in four lines of comment and it is the shape most routers share. The root branches on the host of the request. The next level branches on the method. The remaining levels branch on consecutive segments of the path. Interior nodes hold a map from a segment to a child, plus two special children: one for a single-segment wildcard and one for a trailing multi-segment wildcard. A leaf holds the pattern and the handler registered with it.

A lookup is then a loop. Take the next segment of the request path, try the literal child first, and fall back to the wildcard child when there is no literal. Reach the end of the path at a node holding a handler and you have matched; the values consumed by wildcard children are the path parameters, handed to your code by name.

Precedence: the more specific pattern wins

Two patterns can both match one request, and something has to decide. Go's rule is stated as a property rather than as a heuristic: a pattern P1 is more specific than P2 if P1 matches a strict subset of P2's requests, meaning P2 matches everything P1 does and more. So /images/thumbnails/ beats /images/ because every request the first matches the second matches too. When neither is a strict subset of the other, the patterns conflict, and registering the second one panics at startup rather than resolving the ambiguity silently.

Backtracking: the cost of that rule

Specificity is a property of the pattern set, not of the walk, so the walk sometimes has to undo a step. Go's own comment gives the case: with /a/b/z and /a/{x}/c registered, the path /a/b/c takes the literal b first, finds no c under it, backs up, and tries the wildcard branch instead. The literal-first order is what makes the match correct; the backtrack is what it costs.

3. The trade-off: what the tree buys and what it forbids

The arithmetic is worth doing once. A linear scan over R routes whose paths are D segments deep costs up to R times D segment comparisons per request. The tree costs one lookup per segment, plus one for the host and one for the method: D plus two, whatever R is. At four segments deep those are 4R against 6.

What the tree forbids is the other half of the deal. A pattern has to decompose into segments, so an arbitrary regular expression over the whole path has no node to live in; routers that offer one keep it as a separate, slower list checked after the tree. Conflicts have to be decidable at registration, which is why Go panics rather than picking. And the structure is fixed once the service is running, so a route added at runtime means rebuilding, not appending. Every one of those is a restriction, and every one of them is what makes the walk cheap.

Route count is rarely the thing that is actually slow. A tree walk is a handful of map lookups next to a database round trip, and a profile will say so. The reason to know the structure is not micro-optimisation: it is that the tree explains the behaviour you will otherwise find baffling - why a route conflict is a startup panic, why /images redirects to /images/, and why the more specific of two patterns wins without either being registered first.

In a tree router, what sets the cost of one match?
The walk consumes one segment per level, so depth is the cost. Route count is the linear scan's cost and the whole reason for the tree; the longest pattern bounds the tree's height but not this request's walk; and registration order decides nothing, since precedence is decided by specificity.
Two patterns overlap and neither is more specific. What happens?
Specificity is defined as a strict subset relation, so patterns that overlap without one containing the other cannot be ordered, and Go panics when the second is registered. First-wins and longest-wins are both real rules in other routers, but they resolve the ambiguity instead of reporting it, and a 404 would be wrong because a handler does match.
