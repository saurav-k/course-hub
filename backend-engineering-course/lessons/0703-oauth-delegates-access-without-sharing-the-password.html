Module 07 · Auth and security · Lesson 0703

The password is the one credential you cannot scope, so OAuth stops sending it

working 9 min The third shape of the credential: one somebody else issued. · RFC 6749 - The OAuth 2.0 Authorization Framework

The one-minute version

  • The problem is delegation: an app needs to act on your data at another service, and handing it your password gives it everything, forever, unrevokably.
  • OAuth splits that into four roles so the credential the app ends up holding is scoped, time-limited, and withdrawable on its own.
  • The authorization code grant never lets the app see the password: the user authenticates at the authorization server, and the app receives a code it redeems.
  • PKCE is not optional any more. It closes an interception attack on that code, and RFC 9700 requires public clients to use it and every authorization server to support it.
  • What it costs: OAuth answers what may this app do, not who is this person. Using an access token as proof of identity is the standard mistake, and OpenID Connect is the layer that answers the other question.

1. The mental model: five things wrong with sharing a password

The specification opens with the failure it exists to fix

RFC 6749's first page is a list of what goes wrong when a third-party app authenticates with your credentials directly. The app has to store the password in cleartext to keep using it; the service has to keep supporting password authentication at all; the app gets unrestricted access to everything you own rather than a slice; you cannot revoke that one app without changing the password and breaking all the others; and a compromise of any one app exposes all of your data at that service.

Every item is a property of the password rather than of the app. A password has no scope, no expiry short of a rotation, and no identity of its own, so it cannot be issued once per relying party. The whole of OAuth follows from wanting a credential that has those three things.

2. The mechanism: the code, and why it needs a verifier

The redirect carries a code, and the code is redeemed out of band

In the authorization code grant the client sends the user to the authorization server, which authenticates them and asks whether this app may have this scope. On approval the browser is redirected back to the client with a short-lived authorization code, which the client then exchanges at the token endpoint for an access token - a string representing an authorization, which replaces the various credential shapes with one the resource server understands. A refresh token may come with it, used to obtain a new access token when the current one expires.

The two-step shape exists so the token never travels through the browser's address bar. But the code does, and RFC 7636 documents what happens next on a mobile device: a malicious app can register itself as a handler for the custom scheme in addition to the legitimate OAuth 2.0 app and intercept the redirect. It now holds a valid code, over a path the RFC notes is not protected by Transport Layer Security.

What the security document now requires

RFC 7636 defines two transforms and is explicit about which to use: if the client can use S256 it MUST use "S256", as "S256" is Mandatory To Implement (MTI) on the server. The plain method sends the verifier as the challenge and protects nothing against an attacker who saw the authorization request.

RFC 9700, the current OAuth security best current practice, tightens the surrounding rules. Public clients MUST use PKCE, it is RECOMMENDED for confidential clients, and authorization servers MUST support it. Redirect URIs are matched by exact string matching, with an exception only for the port of a localhost redirect. Clients SHOULD NOT use the implicit grant or anything else that returns an access token in the authorization response. And the grant where the app collects the user's password and posts it - the one that looks like the simplest option - MUST NOT be used.

3. The trade-off: you have delegated authorization, not identity

An access token says a resource server should serve some data. It does not say who is sitting at the browser, and it is not addressed to your application. A client that treats "the token endpoint gave me a token" as "this person is logged in" has built a login on a signal that was never about the person - the classic failure is accepting a token minted for a different application entirely, which is exactly why lesson 0702 insisted on checking aud.

The layer that answers the identity question is OpenID Connect, a simple identity layer on top of the OAuth 2.0 protocol. It adds an ID token: a JWT containing claims about the authentication of the end user, with iss, sub, aud, exp and iat required, where aud MUST contain the client's own id. The ID token is for the client and is validated by the client; the access token is for the resource server and is opaque to the client. Two tokens, two audiences, two questions.

Adopting OAuth adds a dependency with your service's own availability and blast radius. If the authorization server is unreachable nobody logs in, and if its signing keys leak every client that trusts them is compromised at once. That is often still the right trade - it concentrates the hardest security work in one place run by people who specialise in it - but it is a trade, and a service that adopts OAuth to avoid storing passwords has moved the risk rather than removed it.

What does PKCE add that the plain authorization code grant lacked?
PKCE binds the code to the client that began the exchange, so an intercepted code cannot be redeemed by anyone else. It encrypts nothing - the code still crosses the redirect in the clear, which is precisely the assumption it is built on. Scope approval is the authorization server's own step, and the access token's format is not PKCE's concern.
Your app receives an access token from a provider. Why is that not proof of who the user is?
The token's audience is the resource server, so one minted for another application can be replayed at yours if you treat possession as identity. Access tokens do expire; they may be opaque or structured, and that is a deployment choice rather than the reason; and they are issued only after the owner has authenticated and approved.

Primary source to go deeper
