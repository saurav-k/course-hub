A constraint in the schema is the only rule every writer has to obey

foundation 8 min Why the relational model is a place to put invariants, not a table format. · PostgreSQL - Constraints

The one-minute version

  • A relation is a named collection of rows with the same named columns, and SQL guarantees no order among them, so a query that does not sort is asking for whatever arrives.
  • A validation rule in service code binds only the callers that run that code. The migration, the second service and the console session do not.
  • A constraint is declared once in the schema and checked on every write, because every writer passes through the same engine.
  • Check-then-write is a race, and no amount of application care fixes it. A unique constraint is not a check, it is the arbitration.
  • What it costs: constraints refuse writes at the worst moment, foreign keys couple the order of your deletes, and every one of them is a rule your schema change now has to satisfy.

1. The mental model: the store is where the writers meet

A relation is a set of rows, not a spreadsheet

PostgreSQL states the model in one sentence: it manages data stored in relations, and relation is essentially a mathematical term for table. Each table is a named collection of rows, each row of a table has the same set of named columns, and each column has a type. The part engineers forget is the next sentence: columns have a fixed order in each row, but SQL does not guarantee the order of the rows in any way.

That is not a limitation to work around, it is the model doing its job. A relation is a set of facts, and a set has no first element. Order is something you ask for at read time with ORDER BY, which is why lesson 0602 could build a cursor on a sort key at all: the sort was always the caller's request rather than a property of storage. A list endpoint with no ORDER BY is not returning the oldest rows first, it is returning whatever the plan happened to produce, and it will change the day an index changes.

2. The mechanism: what the engine will refuse

Five kinds, and each forbids one thing

The constraint catalogue is short, which is what makes it learnable. A check constraint holds a Boolean expression over the row. A not-null constraint forbids the absent value in a column. A unique constraint forbids two rows agreeing on a column or a group of them. A primary key is unique and not-null together, at most one per table, and it creates a unique B-tree index as a side effect, which is the first hint that lesson 0804 was always part of this subject. A foreign key says the values in a column must match the values appearing in some row of another table, and PostgreSQL names the property that maintains: referential integrity between two related tables.

schema.sql · the invariants, declared once
CREATE TABLE accounts (
  id        bigint  PRIMARY KEY,
  owner_id  bigint  NOT NULL REFERENCES owners (id),
  currency  text    NOT NULL,
  balance   numeric NOT NULL CHECK (balance >= 0),
  UNIQUE (owner_id, currency)
);

Read that as five sentences a caller cannot argue with. There is one row per identifier. Every account belongs to an owner that exists. A currency is always present. A balance is never negative. One owner holds at most one account per currency. Nothing in any service needs to be trusted for those five to be true of every row, today and after the next three teams have written against this table.

A check constraint is satisfied if the expression evaluates to true or to null. Most expressions evaluate to null when any operand is null, so CHECK (balance >= 0) does not prevent a null balance and never did. The documentation says exactly this, and it is the single most common way a constraint quietly means less than its author read it as. The fix is not a cleverer expression, it is the NOT NULL beside it, which is why the column above carries both.

Check-then-write is a race, and a constraint is not

The argument for putting rules in the schema is usually made as tidiness, and that undersells it. There is a class of rule that application code cannot enforce correctly at all, no matter how carefully written, because the check and the write are two separate trips and something else can happen in between.

So the service still runs its own check, and it runs it for a different reason: to produce the readable refusal that lesson 0603 asked for, before the work starts. The constraint is what makes the answer true. Handle the constraint violation as a normal outcome rather than a 500, because under concurrency it is one.

3. The trade-off: what declaring the rule costs you

Every constraint is checked on every write that touches it, and a foreign key check is a lookup in another table. That is real work on the write path, and it is work you cannot switch off for one endpoint that is in a hurry. A unique constraint needs its index maintained, which is lesson 0804's bill arriving early. None of this is large at ordinary sizes and all of it is real at large ones.

The heavier cost is coupling. A foreign key gives the child table a say in what the parent may do: a delete has to be ordered, cascaded, or refused, and the choice now lives in the schema rather than in whichever service happened to run the delete. Schema changes inherit the same property, and the shape of that is worth drawing once.

The alternative is not free either, and it is worth naming plainly because the next module of this course spends a page on it. AWS states the contrast for DynamoDB: in a relational system you design for flexibility without worrying about the query plan, and normalisation matters, while in DynamoDB you design the schema specifically for the queries you already know you will run. A store that will not enforce a cross-entity rule has not removed the rule. It has moved it into every writer, which is where this page started.

Check yourself

Retrieval practice

Answer from memory before revealing.

Why does a uniqueness check in service code fail to guarantee uniqueness?
The gap between reading and writing is the whole defect, and it exists on a single healthy primary with one service deployed. Replica lag makes it worse but is not required, cross-service visibility is not the issue since both writers see the same table, and parse order is unrelated.
A column carries only CHECK (balance >= 0). Which value does the constraint accept?
A check passes when the expression is true or null, and comparing null to zero yields null, so the row is admitted. Type mismatches are rejected by the column type rather than the check, checks are evaluated as the row is written rather than at commit, and they apply to updates as well as inserts.
