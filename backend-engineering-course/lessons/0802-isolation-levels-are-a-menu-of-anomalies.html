An isolation level names the anomalies you have agreed to live with

working 11 min The default is not the safe one, and nothing tells you when it bites. · PostgreSQL - Transaction Isolation

The one-minute version

  • The standard defines four levels by which of four phenomena each one permits: dirty read, nonrepeatable read, phantom read, serialization anomaly.
  • PostgreSQL's default is Read Committed, which permits three of the four. It is the default because it is cheap, not because it is correct for your code.
  • Under Read Committed each statement gets a fresh snapshot. Under Repeatable Read the whole transaction gets one.
  • Serializable emulates running the transactions one at a time, and pays for it by refusing to commit some of them. Your application must retry.
  • What it costs: the stronger levels turn a silent wrong answer into a visible error you have to handle, which is a better failure and still a failure you now own.

1. The mental model: four phenomena, and a level is a subset

The four things that can go wrong

The standard does not describe levels by how they work. It describes them by which of four named phenomena they allow, and PostgreSQL restates all four precisely. A dirty read is reading data written by a concurrent uncommitted transaction. A nonrepeatable read is re-reading a row you already read and finding it modified by a transaction that has since committed. A phantom read is re-running a query and finding the set of rows matching your condition has changed. A serialization anomaly is the general one: the result of committing a group of transactions is inconsistent with every possible order of running them one at a time.

The fourth is the one worth holding on to, because the first three are special cases of it that were easy to name in the 1990s. A serialization anomaly is not a corrupted row or a failed write. Every transaction did exactly what its code says, every write committed, and the state they left behind is one that no serial order could have produced.

2. The mechanism: whose snapshot, and when it was taken

Reading never blocks writing

All of this rests on multiversion concurrency control. Each statement sees a snapshot of the data as it was some time ago, regardless of what the underlying rows currently hold, and the stated advantage over locking is blunt: reading never blocks writing and writing never blocks reading. A reader is never waiting for a writer, so the question is never whether you get an answer. It is always which version of the world your answer came from.

Under Read Committed, a query sees only data committed before that query began, and each command begins with a new snapshot. Under Repeatable Read, the transaction sees only data committed before the transaction began, so successive queries within one transaction see the same data. One word moved, and that word is the whole difference between the two levels.

The surprise inside Read Committed

Writes behave differently from reads, and the rule is stated in the documentation rather than folklore. An UPDATE, DELETE or SELECT FOR UPDATE finds target rows committed as of the command's start. If a concurrent transaction has already updated one of those rows, the second writer waits for the first to finish. If the first committed, the second applies its operation to the updated version of the row, and the search condition of the command is re-evaluated to see whether that updated version still matches.

PostgreSQL's own example of what that produces is the one to memorise. A two-row website table holds hits of 9 and 10. One session runs UPDATE website SET hits = hits + 1 inside a transaction; another runs DELETE FROM website WHERE hits = 10. The delete has no effect, even though a row with 10 hits exists both before and after the update. The row that held 9 was skipped because it did not match at command start, and by the time the delete gets its lock the other row holds 11 rather than 10.

The documentation names the consequence directly: an updating command can see an inconsistent snapshot, because it sees the effects of concurrent updates on the rows it is updating but not their effects on other rows. That makes Read Committed unsuitable for commands with complex search conditions, and just right for simpler cases. The trap is that "complex search condition" is not a warning your code prints. If your UPDATE ... WHERE depends on a column another transaction is also writing, you are in the unsuitable case, on the default level, with nothing telling you.

3. The mechanism: paying for correctness with retries

Repeatable Read and Serializable do not make conflicts disappear. They make them loud. A Repeatable Read transaction cannot modify or lock rows changed by other transactions after it began, so the attempt fails with could not serialize access due to concurrent update. Serializable goes further: it monitors read-write dependencies among concurrent transactions and refuses those whose combination could not have arisen from any serial order, with could not serialize access due to read/write dependencies among transactions.

Both are the same instruction to you, stated twice in the documentation: applications using these levels must be prepared to retry transactions due to serialization failures. That sentence is the actual cost of the strong levels, and a service that does not implement it has not chosen Serializable, it has chosen an outage under load.

retry.py · the obligation the level creates, in the smallest honest form
import psycopg
from psycopg import errors

def transfer(conn, src, dst, amount, attempts=5):
    for attempt in range(attempts):
        try:
            with conn.transaction():
                conn.execute("SET TRANSACTION ISOLATION LEVEL SERIALIZABLE")
                conn.execute("UPDATE accounts SET balance = balance - %s WHERE id = %s",
                             (amount, src))
                conn.execute("UPDATE accounts SET balance = balance + %s WHERE id = %s",
                             (amount, dst))
            return
        except errors.SerializationFailure:
            if attempt == attempts - 1:
                raise
            # back off, then run the whole transaction again from the start

Three properties of that loop are not optional. The retry re-runs the whole transaction, including the reads, because the failure means the reads were based on a world that did not survive. It backs off, because retrying a contended transaction immediately is how a conflict becomes a storm. And it gives up, because a transaction that cannot commit in five attempts is telling you something about your write pattern that a sixth attempt will not fix.

Check yourself

Retrieval practice

Answer from memory before revealing.

Two SELECTs in one Read Committed transaction return different data. Why?
Read Committed takes a fresh snapshot per command, so anything committed between the two statements is visible to the second. Replica routing is a separate concern that would show the same symptom for a different reason, the snapshot is taken at the statement rather than before BEGIN, and no engine restarts your transaction without telling you.
What obligation does choosing Serializable place on the application?
The level converts anomalies into refusals to commit, and the documentation says applications must be prepared to retry. Explicit locking is what Serializable saves you from doing by hand, statement order does not decide serializability, and holding a transaction open is the opposite of the fix since it widens the conflict window.
