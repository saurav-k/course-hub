Module 02 · HTTP is the language · Lesson 0200

An HTTP request is a method, a target and a set of headers, and only the body is optional

foundation 8 min The frame every framework fills in. · RFC 9110 §7.1 - Determining the Target Resource

The one-minute version

  • A request carries three things that are always present: a method, a target, and a set of header fields.
  • The body is the fourth part and the only optional one. A GET with no body is a complete request, not a truncated one.
  • The target is not a file path. It is a URI the recipient resolves to a resource, and the server decides what that resource is.
  • Header fields are not decoration: they carry the routing, the content type, the caching rules and the credentials.
  • What it costs: this page teaches no framework API, and it buys the vocabulary the rest of Module 02 uses without redefining it.

1. The frame is what a framework fills in

Ask a framework what a request is and you get an object with fifty attributes. Ask the protocol and you get four things, three of which are always there. A recipient needs to know what action is being asked for, what it is being asked of, and under what conditions. Those are the method, the target and the header fields. Anything else the request wants to say goes in the body, and a great many useful requests never need one.

This is worth holding as a frame rather than a list, because it tells you where to look. When a request behaves unexpectedly, exactly one of four things is wrong: the wrong action was asked for, it was asked of the wrong thing, a condition was set or missing, or the payload was not what the server expected. Every framework request object is those four parts plus conveniences it computed from them.

2. The three parts that are always there

The method: what action is being asked for

The method is a token that says what the client wants done to the target. RFC 9110 defines eight of them and the registry holds more, but the number matters less than the fact that the method is a request for a defined semantic and not a hint. A server that treats POST /users/42/delete and DELETE /users/42 as interchangeable has moved the action out of the method and into the path, and lost every guarantee the method carried. Lesson 0201 is about exactly those guarantees.

The target: a resource, not a file

The target is where the intuition of most engineers is quietly wrong. RFC 9110 defines it as the components of a parsed target URI, sent so that recipients can identify the same resource the client meant, and it explicitly excludes the fragment because a fragment is for the client alone. The server never sees anything after the #. What the target names is a resource, an abstraction the server defines: it may be a row, a computed report, a redirect, or nothing that exists until the request arrives.

Header fields: the conditions the request travels under

Header fields are name and value pairs carrying everything the method and target cannot say. Which host the request is for, what representations the client will accept, what the body's media type is, which credentials are offered, whether the client already holds a copy it would rather keep. They are a flat namespace of independent statements, which is why a request can be extended for thirty years without the frame changing. Lesson 0203 works through the families that matter.

3. The optional part

The message body: content, never a requirement

A body is content the request carries, and its presence is a property of the method and the framing, never a requirement of HTTP itself. GET, HEAD, DELETE and OPTIONS requests routinely carry none. This is not an omission to work around: a request whose whole meaning is "give me this" has nothing to put in a body, and the metadata it does need already fits in the header fields. When you find yourself wanting a body on a GET, what you actually want is either a different method or the query component of the target.

The failure this frame prevents is subtle and expensive: putting the action in the target. A path like /api/v1/orders/1234/cancel reads well and quietly moves the verb out of the method, so no cache, no proxy and no retry policy can tell that request from any other POST. The protocol's guarantees are attached to the method, and a verb in the path is invisible to every layer that would have used them.

4. The frame outlives the wire format

HTTP/2 changes how these parts are written on the wire and changes none of what they are. RFC 9113 carries the method, the scheme, the authority and the path as the pseudo-header fields :method, :scheme, :authority and :path, compresses the whole field section with HPACK, and requires every field name to be lowercase. The request line as text is gone. The method, the target and the fields are not, because they are the semantics and the framing is only how the semantics are spelled.

That is what makes this frame worth learning once. A page that taught the HTTP/1.1 request line as the definition of a request would have been out of date the moment a connection negotiated HTTP/2, and everything above still holds on both.

Which part of an HTTP request is the optional one?
Only the body is optional. The first option confuses the Host field with the target, which the target still needs; the third describes the anti-pattern this page warns about rather than a rule; and the fourth is wrong because fields carry far more than the body's media type.
A client requests /report#summary. What reaches the server?
A fragment is reserved for client-side processing and is excluded from the target URI, so the server sees the path alone. The first and third options assume the fragment is transmitted somewhere, and the second inverts the rule entirely.
