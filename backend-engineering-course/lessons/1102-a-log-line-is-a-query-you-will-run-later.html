Module 11 · Resilience and observability · Lesson 1102

A log line is written once and read under pressure, so write the fields you will filter on

working 10 min The first of three signals, and the one that answers about a single request. · OpenTelemetry - Logs Data Model

The one-minute version

  • Instrumentation earns its place by answering a question you will actually ask. Three signals answer three different questions, and picking the wrong one is why dashboards go unread.
  • A log answers what happened inside this one execution. It is the only signal that can carry a value specific to a single request.
  • So a log line is a query written in advance: an event with named fields, not a sentence with values glued into it.
  • The severity is a routing decision, not an adjective. It says who is woken and what is retained, which is why the scales are short and numeric.
  • What it costs: fields are storage and storage is money, and the fields you regret are the ones that were free to add and are now in every line.

1. The mental model: three questions, three signals

The failure mode of observability work is installing the whole kit and then, during an incident, having no idea which pane to look at. That happens because the signals were adopted as products rather than as answers. Put the questions first and the division is obvious: how often is this happening and how bad is it is a question about a population, where did the time go for this request is a question about a path, and what did the code actually do on this attempt is a question about one execution.

A metric is an aggregate, so it can tell you that 2% of requests are failing and can never tell you which ones. A trace is a path, so it can tell you that the payment call took four seconds and cannot tell you what the payment client had decided beforehand. A log is a record of one execution, so it can carry the customer identifier, the branch that was taken, and the exact value that failed to parse - and it is hopeless at counting, because counting log lines means storing all of them.

2. The mechanism: an event with fields, not a sentence

The line is written for a filter, not for a reader

A log line reaches a human roughly once. Every other time it is reached it is by a query: give me the lines for this request identifier, or every line where the tenant is this one and the outcome was a refusal. A sentence cannot be queried, because the values are embedded in prose and the only tool left is a substring match that breaks the first time somebody rewords the message.

So the record is an event with named fields. OpenTelemetry's logs data model states the shape: a timestamp taken from the origin clock, a severity as both a number and its original text, a body, a set of attributes carrying what is specific to this occurrence, a resource describing the emitting entity, and - the field that makes the whole module hang together - a TraceId and SpanId for correlation with the trace of lesson 1103.

the same event, twice · only one of these can be filtered
ERROR failed to charge card for order 8f2c after 3 attempts (gateway timeout)

{"time":"2026-08-31T09:14:22.418Z","level":"ERROR","msg":"charge failed",
 "order_id":"8f2c","attempts":3,"reason":"gateway_timeout","tenant":"acme",
 "trace_id":"4bf92f3577b34da6a3ce929d0e0e4736"}

The two lines carry the same facts and are not equivalent. Only the second answers "how many orders failed with a gateway timeout for this tenant in the last hour" without a regular expression, and only the second joins to a trace. Note also what the second does not do: it does not put the order identifier into the message text. A message that varies per event is a message you cannot group by, and grouping by message is how you find out that one error is now 90% of the volume.

Both of this course's languages ship this natively. Go's log/slog defines a record as a time, a level, a message and key-value attributes, with a JSONHandler that emits line-delimited JSON, and Logger.With returns a logger that includes given attributes on every output operation - which is how a request-scoped logger carries the trace identifier without every call site repeating it. Python's standard logging reaches the same shape through the extra mapping and a JSON formatter.

Severity is a routing decision

Levels look like adjectives and are not. RFC 5424 defines eight numeric severities from Emergency, "system is unusable", down to Debug, and the numbers exist because a relay has to decide what to forward without reading English. log/slog keeps four - Debug at -4, Info at 0, Warn at 4 and Error at 8 - with gaps between them precisely so intermediate levels can be defined later. OpenTelemetry normalises everything onto a 1 to 24 scale and keeps the original text beside it.

The practical consequence is that the level answers two operational questions and nothing else: does this wake somebody, and how long is it kept. If nothing is routed differently for Warn than for Info in your pipeline, then Warn is decoration, and the honest fix is to route it or to stop emitting it. The level that causes the most damage is Error used for a failure the caller caused: it is the one that makes a 400 look like an outage on a dashboard, and lesson 1100 is where that mapping is decided.

3. The trade-off: every field is kept for every line, forever

Logs are the most expensive signal per unit of insight, because their cost scales with request volume rather than with the number of distinct things you measure. A field added to a request-scoped logger appears on every line of every request, and the decision to add it is made in a second by one engineer while the decision to remove it needs somebody to prove nothing queries it. That asymmetry is lesson 0600's again, one layer down.

The judgement is to log events rather than progress. A line per state change that somebody could ask about - accepted, refused with a reason, retried, completed - is worth its storage. A line saying a function was entered is not, and the volume it generates is what pushes teams into sampling, at which point the one execution you needed is the one that was dropped. Where the code path is genuinely worth tracing step by step, that is the signal on the next page, which was designed for it.

A log is the easiest place in a system to publish a credential, because the code that does it looks like diligence. OWASP's logging guidance names access tokens, passwords, session identifiers, database connection strings, encryption keys and payment card data among the things that should not be recorded directly, and adds that personal data may not be lawful to retain at all. Two habits close most of it: redact at the type, so a secret's own string form is already a mask, and never log a whole request or config object - log the named fields you decided on.

Check yourself

Retrieval practice

Answer from memory before revealing.

Which question is a log the right signal for, and the other two signals wrong for?
Only a log can carry a value specific to a single execution, because the other two must stay small enough to retain for every request. The first and fourth are population questions a metric answers, and the second is a path question a trace answers - putting any of the three into logs means counting or timing by scanning stored lines.
Why does putting the order identifier inside the log message text cost you something?
A message that varies per event gives every occurrence a distinct value, so "which error is now most of my volume" has no answer. There is no such universal length limit; severity is set explicitly rather than derived; and the trace identifier is an independent field that is unaffected by what the message says.
