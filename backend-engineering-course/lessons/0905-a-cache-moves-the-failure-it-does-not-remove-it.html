Module 09 · Caching · Lesson 0905

A cache moves the failure rather than removing it, and every move lands on the store

working 11 min Where the capacity bet of lesson 0900 comes due. · Redis - Key eviction

The one-minute version

  • Once the store is provisioned for the miss rate, every cache failure mode is the same event: the miss rate jumps and the store is asked for work it was not sized for.
  • Four ways it jumps: a hot entry expires and every reader misses at once, the cache evicts under memory pressure, the cache is empty after a restart, or the cache is gone.
  • The stampede is the one with a measured fix. Leases at Facebook took the peak database rate on herd-prone keys from 17,000 to 1,300 queries a second.
  • Eviction is not expiry, and confusing them is a live trap: a Redis instance set to a volatile- policy with no lifetimes on its keys returns errors instead of evicting anything.
  • What it costs: every mitigation is another mechanism that can fail, and none of them gives you back a store that could survive a cold cache.

1. The mental model: one event with four causes

Every failure in this module reduces to a miss rate that rises faster than the store can absorb. That framing is worth holding because it collapses four scary-sounding phenomena into one measurable quantity, and because it says where the mitigation has to act: either fewer misses reach the store, or the store refuses work politely. Nothing else is available.

2. The mechanism: the four, and what each one needs

The stampede, and why it is not solved in your process

A popular entry expires. Between that moment and the moment somebody stores a fresh one, every reader misses, and every one of them queries the store. The load is not the store's usual miss traffic - it is the full read rate of the hottest key in the system, arriving at once, and it lasts as long as one recomputation takes. Worse, the recomputation is now slower because the store is busy serving its duplicates, which extends the window that is generating them.

Two mitigations exist and they act in different places. Collapsing duplicates lets one caller do the work while the others wait on its result. Go ships this as singleflight, whose whole documented job is that "only one execution is in-flight for a given key at a time", with a shared return value telling a caller its result came from somebody else's call. Python builds the same thing out of a task registry.

fill.go · one fill per key, per process
var group singleflight.Group

func (r *UserRepo) Feed(ctx context.Context, id string) (Feed, error) {
	if f, ok := r.fromCache(ctx, id); ok {
		return f, nil
	}
	v, err, _ := group.Do(id, func() (any, error) {
		return r.loadAndStore(ctx, id) // exactly one of these runs
	})
	if err != nil {
		return Feed{}, err
	}
	return v.(Feed), nil
}
fill.py · the same collapse, built from one task per key
_inflight: dict[str, asyncio.Task[Feed]] = {}

async def feed(key: str) -> Feed:
    cached = await read_cache(key)
    if cached is not None:
        return cached

    task = _inflight.get(key)
    if task is None:                        # the first caller does the work
        task = asyncio.create_task(load_and_store(key))
        _inflight[key] = task
        task.add_done_callback(lambda _: _inflight.pop(key, None))
    return await task                       # everyone else awaits it

Both of those collapse a herd inside one process, which is the limit worth stating plainly: with two hundred service instances you have turned 500 duplicate queries into 200, not into one. Collapsing across the fleet needs the cache itself to arbitrate, which is what a lease does - and it is why Facebook implemented leases in memcached rather than in the web servers. Their measurement is the one number to remember from this page: on a set of keys prone to thundering herds, peak database query rate without leases was 17,000 a second, and with leases 1,300.

The second mitigation attacks the synchronisation instead of the duplication. If a herd forms because every reader learns at the same instant that the entry is gone, then have readers refresh slightly early, independently and at random. Vattani, Chierichetti and Lowenstein prove the optimal distribution for that decision is exponential, and their algorithm is one line inside the ordinary fetch.

refresh early when   now − (Δ × β × ln U) ≥ expiry Read as: each reader pretends to be a little way in the future and refreshes if the entry would be expired by then. Δ is how long the last recomputation of this entry took, β is a tuning factor that defaults to 1, and U is a uniform random number between 0 and 1 - so ln U is negative and the whole bracket is a positive random leap forward.

Two properties make it worth the strangeness. The leap scales with how expensive the entry was to build, so slow entries are refreshed earlier and cheap ones almost never are, with nothing to configure. And because each reader draws its own U, the readers spread themselves out instead of arriving together. The same reasoning applies one level up: entries written together, by a deploy or a bulk import, will expire together unless their lifetimes are jittered, and a herd on a thousand keys at once is the same event with a wider blast radius.

Eviction is a different removal from expiry

An entry can also vanish because the cache ran out of room, and this is a separate mechanism with separate settings. Redis compares memory use against maxmemory on every write and evicts according to maxmemory-policy until it is back under. The policy names matter more than they look: an allkeys- policy may evict any key at all, while a volatile- policy only considers keys that have a lifetime - and, in the documentation's own words, the volatile policies "behave like noeviction if no keys have an associated expiration". A cache configured with volatile-lru whose keys are all written without a TTL does not evict. It fills up and starts returning errors on every write.

Two more details are worth knowing before you read an eviction graph. Redis does not compute a true LRU: it samples a small number of keys at random and evicts the least recently used among them, tunable with maxmemory-samples, because a true LRU "costs more memory". And allkeys-lfu tracks frequency with a probabilistic counter that decays over time, so a key that was hot last week does not hold memory forever. Neither approximation is a problem, but both mean the entry that disappeared may not be the one your reasoning nominated.

The empty cache, and the missing one

The remaining two causes are the crude ones. A restarted or newly scaled cache is empty, and under cache-aside every read is a miss until it refills - which is the full unmitigated read rate arriving at a store sized for a fraction of it. Facebook treats this as a first-class operational problem rather than an accident: their Cold Cluster Warmup lets an empty cluster fill itself from a warm one instead of from the databases, bringing it "back to full capacity in a few hours instead of a few days", at the price of a documented consistency race that they close with a two-second hold-off on deletes.

A cache node that is gone is different again, because the tempting fix makes it worse. Rehashing its keys onto the surviving nodes spreads a hot key onto a machine that already has its own load, and the paper notes that "a single key can account for 20% of a server's requests" - enough to take the next server down and start a cascade. Their answer is to spill misses into a small dedicated pool, about 1% of the servers, rather than redistributing: it reduces client-visible failures by 99% and converts 10% to 25% of failures into hits each day.

3. The trade-off: none of this gives the store its slack back

Every mitigation on this page is another moving part with its own failure mode. Leases add state to the busiest path in the system. Probabilistic refresh spends origin work you did not have to spend, on entries that had not expired yet. A spare pool is capacity you bought and do not use. Warming from a peer creates a consistency race that has to be closed by hand. These are all correct engineering, and each one is a thing that can be misconfigured at three in the morning.

What none of them changes is the underlying position. The store is provisioned for the load it usually sees, the cache is what makes "usually" true, and there is no arrangement of mitigations under which a store sized for 1% of the read rate survives 100% of it. So the design question this module ends on is not how to stop the cache failing. It is which of two prices you would rather pay: a store with enough headroom to survive a cold cache, which is expensive every day, or a service that sheds load and degrades visibly when the miss rate jumps, which is cheap every day and unpleasant on the day. Module 11 is where the second one is built.

The measurement that tells you which position you are in is not the hit rate. It is the answer to "what is our read rate, and what is the store's safe query rate", and the gap between them is your actual exposure. Most teams have never taken it, because the experiment - stop the cache during business hours - is exactly the one nobody wants to run. Take it on a load-tested copy instead, and write the number down beside the cache's configuration, because it is the number that decides whether an incident is a slow afternoon or an outage.

Why does in-process duplicate suppression only partly fix a stampede?
A group registry lives in one process's memory, so two hundred instances produce two hundred queries rather than one - which is why arbitration has to move into the cache for a fleet. The first option describes the intended behaviour rather than a limit; the second is false, since the whole point is that the first fill serves everyone waiting; and the third confuses it with serving stale data during a refresh, which is a different technique.
A Redis cache set to volatile-lru holds keys written with no TTL. What happens at maxmemory?
A volatile policy only considers keys carrying an expiration, and the documentation states that with none it behaves like noeviction - so writes fail while memory is full of keys the policy will not touch. The first option is what allkeys-lru would do, the third is allkeys-random, and no Redis policy has ever selected by value size.
