Module 13 · Scale, fleet and shipping · Lesson 1304

You write down the state you want and a loop keeps closing the gap

working 9 min The orchestration model, stated as the one idea the rest of it is built from. · Kubernetes - Controllers

The one-minute version

  • A control loop is non-terminating. It compares desired state against current state and acts on the difference, forever, exactly like a thermostat.
  • Applying a manifest deploys nothing. It writes down a wish, and separate loops notice the gap and close it.
  • Controllers mostly do not act directly: they send messages to the API server, and another controller acts on those, which is how a rollout is composed.
  • A rolling update is arithmetic on two defaults: surge 25% up and unavailable 25% down, which is the whole envelope the fleet moves inside.
  • What it costs: a loop has no idea what a failed deploy is. It keeps retrying, so a broken release is a stable state rather than an error.

1. The mental model: a thermostat, not a deploy tool

The loop is the whole idea

The Kubernetes documentation borrows its definition from control engineering: "in robotics and automation, a control loop is a non-terminating loop that regulates the state of a system", and the analogy it offers is a thermostat. The temperature you set is the desired state, the room's temperature is the current state, and the thermostat acts to bring one closer to the other. A controller in Kubernetes tracks at least one resource type whose spec field is the desired state, and is "responsible for making the current state come closer to that desired state".

The word missing from that description is deploy. There is no moment at which a release happens and no component whose job is to perform one. Writing a manifest changes the desired state and then stops; every visible effect afterwards is a loop noticing that current and desired differ. That is why a pod deleted by hand comes back, why a rollout continues after your terminal is closed, and why there is nothing to roll back if the loop never converged in the first place.

2. The mechanism: loops composed, and the arithmetic they obey

Controllers talk to the API server, not to machines

A single loop would be a small idea. What makes it a system is stated in one sentence of the same page: a controller "might carry the action out itself; more commonly, in Kubernetes, a controller will send messages to the API server that have useful side effects". So a controller's action is usually another write to desired state, which some other controller is watching. The chain from your manifest to a running process is several loops long, and no link in it knows about the whole.

A rollout is two percentages

A Deployment describes a desired state and "the Deployment Controller changes the actual state to the desired state at a controlled rate". Updating the pod template creates a new ReplicaSet, which is scaled up while the old one is scaled down, and each revision is kept so a rollback is a move to an earlier one rather than a rebuild. The rate is governed by two fields whose defaults are both 25%: maxSurge, the pods allowed above the desired count, rounded up, and maxUnavailable, the pods allowed to be missing, rounded down.

Readiness and liveness answer different questions

The loop cannot know when a container is usable, so the container tells it. The three probes differ in consequence rather than in shape. A readiness probe determines when a container is ready to accept traffic, and on failure "the EndpointSlice controller removes the Pod's IP address from the EndpointSlices of all Services that match the Pod": no traffic, no restart. A liveness probe determines when to restart a container, catching a deadlock where the process runs but cannot progress, and on repeated failure "the kubelet restarts that container". A startup probe gates both, so that a slow initialisation is not mistaken for a hang.

The two consequences are what make the choice load-bearing. A liveness probe that checks a downstream dependency turns that dependency's outage into a fleet-wide restart, because every pod fails the check at once and restarting none of them helps. A readiness probe that checks the same dependency is the correct expression of the same worry: the pod stays alive, takes no traffic, and returns on its own.

Stopping is a sequence with a clock

Scaling down and rolling out both end at the same place, and the Pod lifecycle spells it out. On deletion the Pod is removed from Service endpoints at the same time as SIGTERM is sent, a preStop hook runs if one is defined, and the process then has terminationGracePeriodSeconds, 30 by default, before SIGKILL. That is the budget module 11's graceful shutdown spends, and lesson 1303 is why it can be lost: a process that installs no SIGTERM handler is PID 1 in its namespace and ignores the signal entirely, so it is killed at the end of the window with its in-flight requests still open.

Scaling is one more loop

The HorizontalPodAutoscaler is the same pattern with a metric in it. Its algorithm is a single ratio: desiredReplicas = ceil(currentReplicas × (currentMetricValue / desiredMetricValue)). It runs on a sync period that defaults to 15 seconds, and skips any action when the ratio is within a tolerance that defaults to 0.1, which is what stops the fleet oscillating on noise.

3. The trade-off: a loop cannot tell a bad release from a slow one

Because reconciliation never terminates, there is no built-in idea of failure. A Deployment whose new pods crash on start is not an error condition, it is a difference the controller keeps trying to close, and it will keep trying at whatever the restart backoff allows for as long as the manifest says so. Nothing raises its hand. What tells you is watching the rollout status or the readiness of the new ReplicaSet, and that watching is a thing your pipeline has to do deliberately, which is lesson 1306's subject.

The second cost is that the declarative model is only as good as the declaration. Anything not in the spec is not reconciled: a manually scaled Deployment stays where the autoscaler last put it, a Secret changed outside the manifest is not noticed by the pods already holding it, and a resource created by hand is orphaned rather than owned. The system is exactly as reproducible as the set of files you actually apply.

Horizontal autoscaling does not apply to objects that cannot be scaled, a DaemonSet being the stated example, and it scales replicas rather than capacity. If each pod's ceiling is a database connection pool rather than CPU, adding replicas multiplies the connections and moves the failure into the database. Lesson 1300's question applies unchanged here: find the smallest pool on the path before you multiply anything.

Check yourself

Retrieval practice

Answer from memory before revealing.

A liveness probe checks that the database is reachable. What happens when the database fails?
A failed liveness probe restarts the container, so a shared dependency failing means the whole fleet restarts on a problem no restart addresses. Holding back from traffic is what a readiness probe does and is the right expression of this worry, connection state is irrelevant to the probe, and nothing rolls a Deployment back on its own.
With both rolling-update defaults, how many pods may exist during an update of 8 replicas?
maxSurge defaults to 25% and rounds up, so 8 becomes at most 10, and maxUnavailable governs the floor of 6 rather than adding to the ceiling. A full second copy is a different strategy entirely, removing before starting would breach the floor of 6, and the two defaults govern opposite ends of the band rather than summing.
