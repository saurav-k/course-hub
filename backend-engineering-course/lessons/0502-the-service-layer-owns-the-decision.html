Module 05 · The layered service · Lesson 0502

A rule that neither the transport nor the store can reach is a rule you can move and a rule you can test

working 8 min Where the decision goes, and why there. · NestJS - Providers

The one-minute version

  • The service layer is where the decision lives: the rule that says whether the thing being asked for is allowed and what it means.
  • It is defined by what it cannot reach. No request type above it, no driver type below it, and no global anything.
  • That placement buys two properties at once: the rule is portable across transports and reachable by a test that starts nowhere near a socket.
  • A service names every outcome it can produce, which is what gives the controller a table to map and the caller something to decide on.
  • What it costs: a decision spanning two writes needs a transaction, and a transaction is a store concept the layer has just refused to import.

1. The mental model: a rule needs a room with two locked doors

Take one rule: an order that has shipped cannot be cancelled. It is a statement about orders. It is true when the request arrived over HTTP, true when it arrived from a queue consumer replaying a message, and true in a batch job with no network at all. Nothing about it refers to a status code or to a table.

So the rule has a natural home, and the home is a room with two locked doors: nothing above it may pass a transport type in, and nothing below it may pass a storage type up. Both locks matter, and the second one is the one people forget. A service that receives a database row and reads its columns has a rule that cannot run without a database, which means it cannot run in a test without one either. NestJS treats a service as a provider, an ordinary class the container hands its collaborators to, and that framing is the whole point: the class is ordinary, and everything it needs arrives as an argument rather than being fetched.

2. The mechanism

What the service layer is

A service is a plain object holding the collaborators it was given, exposing one method per operation the application supports. Each method takes the values the intent carried, loads what it needs through a contract it declared, applies the rule, and reports a named outcome. Spring's dependency injection reference states the shape from the container's side: an object defines its dependencies through constructor arguments and the container supplies them, which is the inverse of the object going and finding them itself. That inversion is exactly the second lock. A collaborator that arrives as an argument can be replaced. One that is imported cannot.

The practical test is an import list. A service that imports its own domain types, the interfaces it declared, and a clock is inside the room. A service that imports a driver's result type, a framework's request type, or a module-level connection has already lost the property, whatever the directory says.

the decision in two voices · both take collaborators as arguments and name the outcome
// Go: the rule is four lines, and none of them is about HTTP or SQL.
func (s *OrderService) Cancel(ctx context.Context, id OrderID, reason string) error {
    order, err := s.orders.ByID(ctx, id)      // s.orders is an interface
    if err != nil {
        return err
    }
    if order.State == Shipped {
        return ErrAlreadyShipped              // a named outcome, not a status
    }
    order.State, order.CancelledAt = Cancelled, s.clock.Now()
    return s.orders.Save(ctx, order)
}

# Python: the same rule, with the collaborators arriving in __init__.
class OrderService:
    def __init__(self, orders: Orders, clock: Clock) -> None:
        self._orders, self._clock = orders, clock

    async def cancel(self, order_id: OrderID, reason: str) -> None:
        order = await self._orders.by_id(order_id)
        if order.state is State.SHIPPED:
            raise AlreadyShipped(order_id)
        await self._orders.save(replace(order, state=State.CANCELLED))

Naming every outcome

The method above returns ErrAlreadyShipped rather than a 409 or a boolean. That is a deliberate third thing, and it is what makes the two locked doors useful rather than merely tidy. A named outcome is a value in the service's own vocabulary, so the controller can map it to a status, a queue consumer can map it to a dead-letter decision, and a test can assert on it without parsing a message. A boolean loses the reason. A status code puts HTTP back in the room. A raw string forces every caller to match on prose that somebody will reword.

The set of named outcomes is part of the contract, and it should be enumerable: a reader should be able to open the package and see every way the operation can end. That is what lets the mapping table on the previous page be complete rather than a default with exceptions.

3. What the placement costs

Two costs, and the second is genuinely unresolved at this layer. The first is dilution: once a service layer exists, methods that do nothing but forward a call to the repository accumulate in it, and a file of thirty pass-through methods is indirection with no decision in it. The cure is to notice that a pass-through has no rule and let the controller call the repository contract directly, rather than to keep the method for symmetry.

The second is the transaction. A decision that reads, decides and writes is fine. A decision that must write to two places atomically needs a transaction, and a transaction is a concept the service layer has just refused to import. Every solution to this is a compromise: a unit-of-work object passed in as another collaborator, a transaction started by the controller and threaded down, or a repository method coarse enough to contain both writes. Module 08 owns the mechanism and this course states the trade-off rather than pretending the boundary is free.

The tempting shortcut is to let the service catch the store's own errors and reinterpret them - matching on a unique-constraint violation to mean "this order already exists". It works, and it quietly moves a rule into the store's vocabulary, where it is expressed as a constraint name that a migration can rename with nothing failing until production. If a condition is a rule, check it as a rule. If you rely on the constraint for correctness under concurrency, which is often right, then the translation belongs in the repository implementation, on the other side of the door, and the service sees a named outcome like every other.

Which import inside a service is the strongest sign the boundary failed?
A driver type means the rule cannot run without that driver, so it is neither portable nor testable without a database. The other three are exactly what the room is meant to contain: its own vocabulary, the contracts it declared, and a collaborator handed to it rather than fetched.
Why should a service name every outcome it can produce?
Named outcomes are what let an HTTP controller, a queue consumer and a test each interpret the same result in their own terms. The first option puts HTTP back below the boundary, the third confuses outcomes with the store contract, and the fourth removes the layer that does the mapping rather than serving it.
