Retrying is a policy you choose before the failure, not a reaction to it

working 10 min Four decisions, all of which have a default you did not pick. · AWS - Exponential Backoff And Jitter

The one-minute version

  • A retry policy answers four questions: which errors, how far apart, how many, and where the job goes when they run out. Every queue has an answer to all four whether you wrote one or not.
  • Classify the error first. A timeout is worth repeating and a malformed payload never will be, so retrying it burns capacity to reach the same failure at a later hour.
  • Capped exponential backoff spreads attempts out in time but leaves them clustered, because every client waits the same amount. Jitter is what removes the cluster, and AWS measured the call count falling by more than half with 100 contending clients.
  • A bound is what a dead-letter queue is for. SQS moves a message there once its receive count passes maxReceiveCount, and for a standard queue the retention clock keeps running from the original enqueue - so a short DLQ retention deletes the evidence.
  • What it costs: retries add load exactly when the system is failing, and stacked layers multiply, so the honest policy caps attempts and retries at one layer.

1. The mental model: classify the failure before you repeat it

Retriable means the input was fine and the world was not

Two failures wear the same exception type in most codebases and deserve opposite treatment. A connection reset, a lock timeout, a 503 from a dependency and a throttled write are all statements about the world at that instant: the same job, run again in ten seconds, has a genuine chance of succeeding. A missing required field, a foreign key that does not exist, a payload the deserialiser cannot read and a permission the caller does not have are statements about the job itself. Repeating those thirty times reaches the same failure thirty times and costs a worker slot each time.

Module 06 already drew this line for you in a different vocabulary. The 4xx and 5xx families exist precisely to say whether the request or the server was at fault, and a consumer can lean on the same split: treat a terminal classification as an immediate move to the dead letter, and a retriable one as a wait and another attempt. What you must not do is default everything to retriable because the classification is work. That default is how a queue fills with jobs that cannot succeed, all of them being retried at the same interval, in front of the jobs that could.

2. The mechanism: backoff, jitter, and a receive count

Backoff spreads attempts out, jitter spreads clients apart

Capped exponential backoff means each attempt waits twice as long as the last, up to a ceiling. It helps, and on its own it does not solve the problem it appears to solve. AWS's analysis puts the failure precisely: with backoff alone "there are still clusters of calls. Instead of reducing the number of clients competing in every round, we've just introduced times when no client is competing." Every client computes the same delay from the same attempt number, so they all sleep together and all wake together. The retry storm is not slowed down, it is scheduled.

Jitter is the correction, and it is a small one. The published simulator gives four strategies, and reading them beside each other is the fastest way to understand what each buys.

backoff.py · the four strategies, as published in the AWS backoff simulator
def expo(base, cap, n):
    return min(cap, base * 2 ** n)              # capped exponential

def no_jitter(base, cap, n):
    return expo(base, cap, n)                   # every client waits the same

def full_jitter(base, cap, n):
    return random.uniform(0, expo(base, cap, n))

def equal_jitter(base, cap, n):
    v = expo(base, cap, n)
    return v / 2 + random.uniform(0, v / 2)     # keeps a floor under the wait

def decorrelated(base, cap, prev):
    return min(cap, random.uniform(base, prev * 3))   # grows from the last wait

AWS ran these against a contended optimistic-concurrency workload with a base of 5ms and a cap of 2,000ms. Their reported result for full jitter, with 100 contending clients, is that it "reduced our call count by more than half" and significantly improved time to completion against un-jittered backoff. Of the four, no-jitter is described as the clear loser on both work and time, equal jitter does slightly more work than full jitter and takes much longer, and the choice between full and decorrelated is close. Full jitter is the sensible default: it is one line, and the line is random.uniform(0, delay).

The count, and where the job goes when it is spent

The bound on attempts is usually a property of the queue rather than of your code. In SQS it is the redrive policy's maxReceiveCount, described as "the number of times a consumer can receive a message from a source queue before it is moved to a dead-letter queue". Note what is being counted: receives, not application-level failures. A worker that dies before it can fail properly still burns one, which is correct - it is a message that has now been attempted.

Two details of the dead letter are worth holding, because both bite after the incident rather than during it. First, for standard queues the expiry of a message is always based on its original enqueue timestamp, and moving it to the DLQ does not reset that clock - so a message that spent a day in the source queue and lands in a DLQ with a four-day retention is deleted three days later. Amazon's stated best practice follows directly: always set the DLQ's retention period longer than the source queue's. Second, a DLQ is a diagnostic surface. The whole point is that you can read the messages, find why processing failed, and redrive them once the cause is fixed.

3. The trade-off: a retry is load, arriving at the worst moment

Every retry is an extra unit of work sent to a system that has just demonstrated it cannot keep up. Google's SRE chapter on cascading failures draws the arithmetic: a backend rejecting requests at 100 QPS sees those retried, so "the volume of retries grows: 100 QPS of retries in the first second leads to 200 QPS, then to 300 QPS, and so on". The failure feeds itself.

The multiplication across layers is worse and easier to miss, because each layer's policy looks reasonable in isolation. The same chapter states it as a rule: "avoid amplifying retries by issuing retries at multiple levels: a single request at the highest layer may produce a number of attempts as large as the product of the number of attempts at each layer to the lowest layer."

A retry policy is a promise that the work is safe to repeat, and nothing in the queue verifies it. If the consumer is not idempotent, then increasing maxReceiveCount from 3 to 10 does not improve reliability - it raises the number of duplicate charges, duplicate emails and duplicate rows a single bad afternoon can produce. Retries and idempotence ship together or neither ships. That is lesson 1003, and it is not optional reading after this one.

Retrieval practice

Answer from memory before revealing.

Capped exponential backoff without jitter still causes a retry storm. Why?
The delay is a pure function of the attempt number, so a hundred clients that failed together sleep for the same interval and arrive together - AWS's own description is that backoff introduces times when nobody is competing rather than reducing how many compete. The cap does bound the wait, but the clustering is present from the first retry. Doubling is aggressive, not slow. And resetting a counter would change the schedule, not the synchronisation.
A message reaches an SQS dead-letter queue. When is it deleted from there?
For standard queues the expiration is always based on the original enqueue timestamp, and the move does not reset it, which is why Amazon advises a longer retention on the dead letter than on the source. Arrival-based expiry is what people assume and is the FIFO behaviour, not the standard one. Dead letters are ordinary queues and do expire. And changing a redrive policy governs future moves rather than messages already sitting there.
