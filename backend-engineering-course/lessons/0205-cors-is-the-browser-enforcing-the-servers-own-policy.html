CORS is enforced by the browser, and the server only ever states a policy

working 7 min Who enforces what, and when. · MDN - Cross-Origin Resource Sharing

The one-minute version

  • The browser enforces CORS. The server states a policy in response fields and enforces nothing, which is why curl never sees a CORS error.
  • A simple request is sent first and judged afterwards: the server has already acted before the browser decides whether the page may read the answer.
  • A request outside the simple set gets a preflight: an OPTIONS asking permission for the method and the fields, before the real request is sent.
  • Credentials change the rules: a wildcard origin is refused outright and the server must name the origin and allow credentials explicitly.
  • What it costs: CORS protects the reader, not the resource. Anything reachable without a browser still needs real authorisation.

1. The mental model: the browser is the enforcer

The same-origin policy, and who obeys it

The same-origin policy is a rule inside the browser. Script running on one origin - a scheme, host and port taken together - may not read a response from another origin unless that other origin says it may. Cross-Origin Resource Sharing is the mechanism by which the other origin says so: a set of response fields the server sends, which the browser reads and acts on.

Two consequences follow immediately and both are the point of this page. First, the server does not block anything. It answers the request and states its policy in fields, and a client that is not a browser ignores those fields entirely. Second, a "CORS error" in a console is not a failed request. It is usually a successful request whose response the browser refused to hand to the script, which is why the network tab shows a 200 that your code never received.

2. The mechanism: two shapes, one policy

The simple request, judged after the fact

Some requests are sent straight out, and the browser applies the policy only to the response. MDN's conditions are narrow: the method is GET, HEAD or POST, the only request fields set by the page are the CORS-safelisted ones - Accept, Accept-Language, Content-Language, Range, and Content-Type limited to application/x-www-form-urlencoded, multipart/form-data or text/plain - with no upload progress listener and no stream body. A JSON POST is outside that set, purely because application/json is not one of the three content types, and that single fact accounts for most preflights an API ever sees.

The preflight, which asks first

Anything outside the simple set gets an OPTIONS request the page never wrote. It carries Access-Control-Request-Method and, when custom fields are involved, Access-Control-Request-Headers. The server answers with Access-Control-Allow-Origin, Access-Control-Allow-Methods, Access-Control-Allow-Headers and optionally Access-Control-Max-Age, which is how long the browser may reuse this permission - the same freshness idea as the previous lesson, applied to a policy instead of a representation. Only if the answer permits it does the real request go out.

3. Credentials, and the trade-off

A credentialed request

A credentialed request carries cookies or an authorization header across origins, and the rules tighten because the stakes change. The page must opt in. The server must answer Access-Control-Allow-Credentials: true, and it may not answer * for the origin, the methods, the headers or the exposed headers: a wildcard is refused rather than expanded. The preflight itself never carries credentials. On top of all of that, the browser's own third-party cookie policy still applies, so a correct CORS configuration is necessary and not sufficient.

Response fields have a matching restriction. By default a script may read only Cache-Control, Content-Language, Content-Length, Content-Type, Expires, Last-Modified and Pragma from a cross-origin response. Anything else - a pagination header, a request identifier, a rate-limit counter - has to be listed in Access-Control-Expose-Headers, and its absence is the second most common CORS puzzle after the preflight.

The trade-off is easy to state and easy to forget under a deadline. CORS buys one thing: it stops a page the reader did not trust from reading an answer meant for a page they did. It buys nothing against a script, a scraper or an attacker who is not driving a browser, because none of them is bound by a policy they can simply not read. So a resource that must not be public needs authentication and authorisation on the server, and the CORS configuration beside it is a separate decision about which front ends may talk to it.

Reflecting the Origin field back as Access-Control-Allow-Origin makes every CORS error disappear, and that is exactly the problem: combined with Allow-Credentials: true it permits any site on the internet to make authenticated requests as your signed-in user and read the answers. It passes every test you will write. Name the origins you mean.

Retrieval practice

Answer from memory before revealing.

A fetch fails with a CORS error but the same URL works in curl. Why?
The server states a policy and never enforces it, so a non-browser client is unaffected. The second option is nearly true and still not the reason; the third has the server doing enforcement it does not do; and the fourth describes a preflight failure, which would not produce a working curl either.
Which request triggers a preflight?
Only three content types are safelisted and JSON is not among them, so a JSON POST is preflighted. The other three sit inside the simple set: Accept-Language and Range are CORS-safelisted fields, and multipart form data is one of the three permitted content types.
