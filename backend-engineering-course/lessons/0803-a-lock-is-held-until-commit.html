Module 08 · Data · Lesson 0803

A row lock is held until commit, so the length of a transaction is its blast radius

working 10 min Why a correct transaction can still take a service down. · PostgreSQL - Explicit Locking

The one-minute version

  • Writing a row takes a lock on it, and row-level locks are released at transaction end, not at the end of the statement that took them.
  • So the cost of a write is not how long the UPDATE ran. It is how long the transaction stayed open afterwards.
  • Two transactions taking the same two rows in opposite orders deadlock. PostgreSQL detects it and resolves it by aborting one of them.
  • The stated best defence is not cleverness, it is acquiring locks on multiple objects in a consistent order everywhere in the application.
  • What it costs: shrinking a transaction usually means giving up a guarantee it was providing, so you have to know which guarantee you are selling.

1. The mental model: the statement ends, the lock does not

Hold time is transaction time

When a transaction updates a row it takes an exclusive lock on that row, and it keeps it. PostgreSQL states the lifetime plainly: row-level locks are released at transaction end or during savepoint rollback, just like table-level locks. Nothing releases a row lock early, there is no way to ask for one, and there should not be, because releasing it early is precisely the atomicity of lesson 0801 being withdrawn.

That single sentence is what makes transaction length a design property rather than a style preference. A one-millisecond UPDATE at the top of a handler that then spends 300 milliseconds calling a pricing service holds that row for 301 milliseconds. Every other request for the same row waits the whole time. The slow thing and the blocking thing are not the same statement, which is why the slow-query log has nothing to say about it.

Reads are the exception that makes this bearable. Under the multiversion model of the last lesson a plain SELECT takes no row lock and waits for nobody. The moment you write SELECT ... FOR UPDATE you have opted back in: the rows are locked as though for update, which prevents them from being locked, modified or deleted by other transactions until the current transaction ends. The weaker modes exist for the same reason a read is different from a write. FOR SHARE takes a shared lock, so several transactions may hold it at once but none may update the rows, and FOR KEY SHARE is weaker still: it blocks deletes and updates that change the key, which is what a foreign key check needs and nothing more.

2. The mechanism: how two correct transactions stop each other

A cycle in the waiting

A deadlock is not a bug in the engine and not a failure of either transaction. It is a cycle: A holds row 1 and wants row 2, B holds row 2 and wants row 1, and no amount of further waiting resolves it. PostgreSQL detects the situation automatically and resolves it by aborting one of the transactions involved, allowing the others to complete.

The fix is an order, agreed everywhere

The documentation's advice is a design rule rather than a tuning knob: the best defence against deadlocks is generally to avoid them by being certain that all applications using a database acquire locks on multiple objects in a consistent order. Read the scope in that sentence. All applications, not this handler, because a deadlock needs only two participants and either of them can be the one that has not read the rule.

In practice the order has to be something both sides can compute without talking to each other, which in a relational store means the primary key.

transfer.go · the same two rows, always in the same order
func transfer(ctx context.Context, tx pgx.Tx, from, to int64, amount int64) error {
    // Lock in primary-key order, whichever direction the money moves.
    first, second := from, to
    if second < first {
        first, second = second, first
    }
    for _, id := range []int64{first, second} {
        if _, err := tx.Exec(ctx,
            `SELECT id FROM accounts WHERE id = $1 FOR UPDATE`, id); err != nil {
            return err
        }
    }
    // Both rows are now held. The debit and credit can run in business order.
    return applyTransfer(ctx, tx, from, to, amount)
}

The lock acquisition and the business logic have been separated on purpose. The order money moves in is a domain fact and the order rows are locked in is a concurrency fact, and letting the first decide the second is exactly the defect. Retrying on deadlock is still worth having, for the same reason the retry loop in lesson 0802 is: the rule protects the code that follows it, and there is always some code that does not.

3. The trade-off: what a shorter transaction gives up

Every technique for reducing hold time is a technique for holding less inside the boundary, and the boundary was there for a reason. Moving the remote call out of the transaction means the call can now succeed while the commit fails, which is a state the transaction was preventing. Splitting one transaction into two means there is now an instant where half the work is visible, which is atomicity being sold back. Taking a weaker lock mode means admitting a class of concurrent write you were previously excluding.

None of those is wrong, and all of them are decisions rather than optimisations. The question to ask each time is which guarantee is being given up and what pays for it instead, and the answers this course has already given are the ones to reach for: an idempotency key so the repeated attempt is safe, a constraint so the invariant survives the split, an outbox row so the message and the write share one boundary.

A connection pool turns a local wait into a global outage. Requests blocked on a row are not idle, they are each holding a pooled connection, so a contended row with a long hold time exhausts the pool and then every unrelated endpoint fails too, including the health check. That is the mechanism behind the incident shape where one slow write path takes down a service that mostly does reads. The lock is the cause and the pool is the amplifier, and only the second one appears in the dashboard.

Row locks are released at transaction end, so the hold covers the statement and everything after it inside the boundary. The first option is the assumption that causes the incident, the third drops the statement itself, and no engine hands a lock over on request because doing so would break atomicity.
What does PostgreSQL name as the best defence against deadlocks?
Consistent ordering removes the cycle, which is the only structure a deadlock can have. A lower timeout finds the cycle sooner and pays for it in needless checks, a stronger isolation level changes which conflicts are reported rather than preventing cycles, and single-statement transactions are impossible for work that spans two rows.
