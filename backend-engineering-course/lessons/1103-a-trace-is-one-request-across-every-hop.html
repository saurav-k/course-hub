A trace answers where the time went, and it only exists if every hop passes the context on

working 9 min The second signal, and the one that crosses a process boundary. · W3C - Trace Context

The one-minute version

  • A trace answers one question: where did the elapsed time of this request go, across every process it touched.
  • It is built from spans. A span is a named unit of work with a start, an end and a parent, and the parent link is what makes a set of spans a tree rather than a pile.
  • The link travels in a header. W3C's traceparent carries a version, a 32-hex trace id, a 16-hex parent id and flags, and standardising it is what lets two vendors correlate one request.
  • Propagation is the whole mechanism and it is all-or-nothing per hop: a service that does not copy the header forward does not blur the trace, it ends it.
  • What it costs: a span per operation is data per request, so tracing is sampled, and the request you most want is the one sampling is most likely to have dropped.

1. The mental model: a tree of intervals, not a list of events

Take a request that took 4.0 seconds and think about what you actually need to know. Not what happened - a log gives you that - but how the 4.0 seconds was spent, and specifically whether it was one slow thing or forty ordinary things. Those two have completely different fixes, and no amount of reading log lines distinguishes them reliably, because a log line is a point in time and duration is the difference between two of them.

A span is that difference, made into a first-class value. OpenTelemetry defines it as a unit of work carrying a name, a parent span id, start and end timestamps, a span context, attributes, events, links and a status. The parent id is the load-bearing field: a span with a trace id and no parent is a root span, and every other span names the span that caused it. What you get is a tree of intervals, and a tree of intervals can be drawn as a waterfall that answers the question by eye.

2. The mechanism: one header, copied at every hop

What travels between processes

A span tree can only be assembled if every process agrees on an identifier, and before 2019 they did not: the W3C Trace Context specification exists because traces collected by different vendors could not be correlated, there being no shared unique identifier. The fix is one header with a fixed grammar.

the traceparent field · four dash-separated fields, all lowercase hex
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             ^^ ^------------------------------^ ^--------------^ ^^
          version          trace-id                  parent-id   flags
           1 byte          16 bytes                    8 bytes    1 byte

The trace id identifies the whole distributed trace and is 32 hex characters; the parent id, called a span id in most systems, identifies the caller's own span and is 16. All-zero values are invalid in both fields, which matters because it makes an uninitialised identifier a detectable error rather than a plausible-looking trace everything joins to. The flags byte currently carries one meaningful bit, sampled, which says whether this trace was recorded. A companion tracestate header carries vendor-specific key-value pairs and is deliberately opaque, so a vendor can extend the context without breaking anyone else's parsing.

Propagation is what breaks, and it breaks silently

OpenTelemetry names context propagation as the core concept that enables distributed tracing, and in practice it is also the entire failure surface. A trace is not degraded by one uninstrumented service - it is severed there. Every span below the break becomes a second, unrelated trace with no parent, and the waterfall you go looking for shows a request that mysteriously ends.

Three places lose it reliably. A hop through a queue, because the header is an HTTP concept and a message is not, so the context has to be copied into the message envelope by hand - which lesson 0605's asynchronous work makes routine. A thread or goroutine started without passing the request context down, which is why Go's convention of taking ctx context.Context as the first parameter exists. And any hop through a component you do not instrument, including a proxy that strips unknown headers.

3. The trade-off: you cannot keep them all

A span is a record per operation per request, so a service doing a thousand requests a second with eight spans each produces eight thousand records a second, and that is one service. Everybody samples, and the sampled bit in the flags byte is where the decision travels. The decision is genuinely hard: sample at the head, before you know the outcome, and the failing request is dropped with the same probability as any other; sample at the tail, after the trace completes, and you must buffer every span of every request somewhere until you decide.

The consequence for you as an author of a service is that a trace is not a guarantee. It is a good chance of an answer, and the way to keep it useful is to make the sampling decision at the point where the most is known - which usually means keeping every trace that contains an error or exceeds a latency threshold, and sampling the ordinary ones hard. That is a policy decision, and like every other one in this module it belongs somewhere you can change it without a deploy.

A trace identifier is not an authentication token and must not be treated as one, but it is still an identifier from an untrusted party. A public endpoint that accepts an incoming traceparent unchecked lets a caller choose which trace their request joins, which is at best a way to poison your own data and at worst a way to inflate storage on purpose. Validate the grammar, reject the all-zero identifiers the specification already calls invalid, and consider starting a fresh trace at the public edge while recording the caller's id as an attribute.

Check yourself

Retrieval practice

Answer from memory before revealing.

A middle service in a chain of five does not forward traceparent. What do you see?
Propagation is all-or-nothing per hop: downstream services see no incoming context, so each starts a root span and a whole new trace id. The first three options all describe partial degradation, and there is no mechanism for any of them - a span is either linked to a parent or it is a root.
What does the parent id inside traceparent identify?
It is the immediate caller's span id, rewritten on every outbound call, which is what makes the spans a tree. The first describes the root span, which the parent id does not name; the third describes the trace id, which is the other field and is 16 bytes to the parent id's 8; and the fourth is the flags byte.
