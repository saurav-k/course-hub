A transaction is a boundary you draw, and the log is what makes it survive a crash

working 9 min Atomicity and durability, and the one ordering rule that buys both. · PostgreSQL - Transactions

The one-minute version

  • A transaction is atomic: from the point of view of other transactions it either happens completely or not at all.
  • Its writes are invisible until commit, and then all of them become visible at the same instant. There is no moment where half of it is readable.
  • Durability is not the data pages reaching disk. It is the write-ahead log reaching disk first, which is one sequential flush instead of many scattered ones.
  • A crash is recovered by replaying the log forward over whatever the data files happen to hold, so an unflushed page costs nothing.
  • What it costs: a commit is a real disk flush, so transaction count is a hard cost the batch size divides, and every open transaction holds resources the next lesson makes you pay for.

1. The mental model: all of it, or none of it, and never half

Atomicity is a claim about observers

PostgreSQL introduces transactions with a bank transfer, and the example is worth keeping because the failure it names is so concrete: it would certainly not do for a system failure to result in Bob receiving a hundred dollars that was not debited from Alice. The definition follows from that. A transaction is said to be atomic: from the point of view of other transactions, it either happens completely or not at all.

Read the qualifier carefully, because it is where the idea actually lives. Atomicity is not a claim that the engine writes four rows in one instruction. It plainly does not. It is a claim about what any other transaction is able to observe: the updates made so far by an open transaction are invisible to other transactions until it completes, whereupon all the updates become visible simultaneously. The half-finished state exists. It is simply not addressable from outside.

2. The mechanism: durability is an ordering rule

Log first, data pages later

The obvious way to make a commit durable is to write the changed pages to disk before answering. It is also the slow way: the pages a transaction touches are scattered across the files, so a commit becomes several random writes and a wait for each. Write-ahead logging replaces that with an ordering rule and one sequential write.

WAL's central concept is that changes to data files must be written only after those changes have been logged, that is, after log records describing the changes have been flushed to permanent storage. Everything else follows from that single ordering. If the rule holds, the data pages do not have to be flushed on every commit, because a crash can be recovered by replaying the log forward over whatever the files contain. PostgreSQL names that roll-forward recovery, or REDO.

The commit is the cost, so count commits

That flush is a genuine wait on the storage device, and it is per commit rather than per row. So the arithmetic that decides throughput on a bulk write path is not how many rows you have but how many times you said COMMIT.

  1. Take a commit flush as one storage round trip. Call it f seconds - on durable network-attached storage it is often a fraction of a millisecond, and it is measured rather than assumed.
  2. Write 10,000 rows one transaction at a time. That is 10,000 flushes, so the floor is 10,000 × f, no matter how fast the rows themselves are.
  3. Write the same rows 1,000 at a time. That is 10 flushes, so the same floor is 10 × f, a thousandfold reduction in the part that waits on the device.

This is derived arithmetic from the ordering rule rather than a benchmark, and the real system beats the pessimistic version of it: PostgreSQL notes that when the server is processing many small concurrent transactions, one flush of the log may suffice to commit many of them. That is a gift from concurrency, not a reason to leave the batch size at one, and it does nothing for a single client writing in a loop.

3. The trade-off: where you draw the edges

Because a transaction is a boundary you draw, the interesting failure is drawing it in the wrong place, and there are two wrong places. Too small, and a group of writes that are only correct together can be interrupted between them, which is the bank transfer with the constraint removed. Too large, and you are holding a boundary open across work that has nothing to do with the store.

The second is the common one in service code, and it has a specific shape: a transaction opened at the top of a request handler, an HTTP call to a payment provider in the middle of it, and a commit at the bottom. That transaction is now as long as somebody else's network, holding everything the next lesson describes for the duration. The rule that falls out is worth stating as a rule: never wait on a remote system inside a transaction. Do the remote call before or after, and make the whole handler safe to repeat using the idempotency key of lesson 0605, which exists precisely because the alternative is a boundary you cannot honour.

A transaction is a boundary inside one database. It is not a boundary across two, and it is not a boundary across a database and a queue. Writing a row and publishing a message are two systems, so a crash between them leaves exactly the half-state this page told you does not happen, because it does not happen only within the one engine's boundary. The mechanisms that repair this - the transactional outbox, and consuming your own committed rows - belong to Module 10, and until then the honest position is to know which of your writes are inside one boundary and which merely look like it.

Why does write-ahead logging make a commit cheaper than flushing the changed pages?
A transaction's pages sit in different places in the files, so flushing them is several random writes, while the log is appended in one place. Compression is not the mechanism, the log must reach disk rather than stay in memory or the promise is void, and the scattered writes still happen later regardless of their granularity.
A crash happens after COMMIT returned but before the data pages were written. What is lost?
The log records were flushed before the commit was acknowledged, so recovery redoes them over whatever the files hold. The first option describes a crash before the flush, the third describes a system with no log at all, and indexes are logged like everything else rather than rebuilt.
