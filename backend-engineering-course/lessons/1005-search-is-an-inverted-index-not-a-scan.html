Module 10 · Async work and search · Lesson 1005

Search answers the question in advance, which is why it does not read your documents

working 9 min The second half of the module, fed by the first. · PostgreSQL - Introduction to full text search

The one-minute version

  • LIKE '%satisfy%' asks every document the same question. PostgreSQL names the three consequences: no linguistic support, no ranking, and "slow because there is no index support, so they must process all documents for every search".
  • An inverted index stores the answer to the opposite question: for each word, which documents contain it. The lookup then costs the length of one list rather than the size of the corpus.
  • Getting there means normalising text into lexemes - parse into tokens, fold case, strip suffixes, drop stop words - so that satisfies and satisfy become the same entry.
  • The query must go through the same normalisation as the document, which is why tsquery is a separate type from a string and not a convenience.
  • What it costs: a derived structure you cannot read the original out of, an analyser fixed at index time so a change means a reindex, and - in a separate engine - a copy that lags.

1. The mental model: which way the map points

A scan asks the documents, an index has already been told

A pattern match walks the table. For each row it takes the text and asks whether the pattern occurs in it, and because the pattern can start anywhere, no ordinary B-tree can help - the index is sorted by the whole value and the query does not know the beginning of it. So the cost is the corpus, on every query, and it grows with your success.

An inverted index reverses the direction of the map. Instead of document to text, it stores word to documents: for each distinct word, the list of documents that contain it. PostgreSQL's description of a GIN index is exactly this - "As inverted indexes, they contain an index entry for each word (lexeme), with a compressed list of matching locations." A query for one word is then a lookup of one key and a read of its list; a query for two words is two lookups and an intersection. Nothing touches a document that does not match.

That is the entire performance story, and it explains a property that otherwise looks strange: search gets cheaper, relative to scanning, the more documents you have and the rarer the term. A word that appears in twelve documents costs twelve entries whether the corpus holds a thousand rows or a billion.

2. The mechanism: text becomes lexemes before it becomes an index

Tokens, lexemes, and the words thrown away

Raw text cannot be an index key, because the reader who searches for satisfy expects to find a document containing satisfies. PostgreSQL names that as the first failing of pattern matching directly: "Regular expressions are not sufficient because they cannot easily handle derived words, e.g., satisfies and satisfy. You might miss documents that contain satisfies, although you probably would like to find them when searching for satisfy."

The preprocessing that fixes this has three steps and the vocabulary is worth learning exactly. Documents are parsed into tokens - raw fragments of the text, classified by a parser. Tokens are converted into lexemes, which are normalised so that different forms of the same word are made alike, typically by folding upper case to lower and removing suffixes such as s or es. Finally stop words are eliminated: words so common that they are useless for searching. The documentation's own summary of the difference is the sentence to keep: "tokens are raw fragments of the document text, while lexemes are words that are believed useful for indexing and searching".

The result is stored as a tsvector, the type for preprocessed documents, and a query is a tsquery, the type for processed queries. Two types rather than one, because a query string must be put through the same normalisation as the document was, or a search for Satisfying will look for a key that no document ever produced. This is the single most common way a first full-text implementation appears to work and quietly does not: the documents were indexed with one configuration and the queries built with another, and the only symptom is that some searches return nothing.

GIN, and what the index chooses not to store

PostgreSQL offers two index types over a tsvector and states a preference: "GIN indexes are the preferred text search index type." GIN stores the lexemes with their compressed location lists, so a multi-word search can find the first match and then use the index to remove rows lacking the additional words. GiST is lossy - the index may produce false matches, so the actual table row has to be checked to eliminate them, and that lossiness costs fetches of records that turn out not to match.

GIN drops something too, and it is worth knowing which: it stores only the lexemes of tsvector values and not their weight labels, so a query that involves weights needs a table row recheck. Weights are the mechanism lesson 1006 uses to say that a title match counts for more than a body match, so this is not an obscure corner - it is the cost of the ranking feature you are most likely to want.

3. The trade-off: a second store, derived and behind

Once search moves out of the database into an engine of its own, the index becomes a separate system holding a copy of your data, and every property of a copy applies. It has to be populated, which is a background job; it has to be kept in step, which is what lesson 1004's outbox exists for; and it is behind. Elasticsearch is explicit that search is near real-time rather than real-time: "When a document is stored in Elasticsearch, it is indexed and fully searchable in near real-time--within 1 second", because new documents sit in a buffer until a refresh writes and opens a new segment, and by default that happens about once a second.

That second is a product decision more often than a technical one. A user who saves a record and immediately searches for it may not find it, so a screen that lists results straight after a write either reads from the database instead or is designed to tolerate the lag. The other standing cost is the analyser: it is applied at index time, so changing the language, the stemmer or the stop-word list changes what is stored, and every document already indexed has to be rebuilt to agree with the new queries. Plan a reindex path before you need one, because you will.

A search index is not a source of truth and must not become one. It is lossy by construction - the stored form is stemmed, stop words are gone, and the field that was analysed cannot be recovered from its lexemes - so a document that exists only in the index is a document you have partially lost. Store the record in the database, derive the index from it, and make the derivation repeatable from scratch. The test is simple: if you deleted the whole index this afternoon, could a job rebuild it by evening from data you still hold?

Why can a B-tree index not accelerate LIKE '%satisfy%'?
A B-tree orders entries by the whole value, so it can seek to a known prefix and cannot help when the pattern may begin anywhere inside the text - which is why the documentation says such queries must process all documents. B-trees index text perfectly well when the query is anchored. The planner is fully involved and simply has nothing useful to choose. And case folding is part of full-text normalisation, not something the operator does on the way to an index.
A search for "Satisfying" returns nothing, though matching documents exist. What is the likeliest cause?
Matching happens on lexemes, so a query normalised differently from the documents looks up a key nothing produced, and the failure is silent - an empty result rather than an error. An unbuilt index would make the query slow rather than wrong. Stop words are common function words, not content terms like this one. And GiST is the lossy index, whose lossiness produces false matches to be rechecked, never missing ones.
