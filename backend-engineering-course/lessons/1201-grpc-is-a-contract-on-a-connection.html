gRPC is not a message format - it is a generated stub and one mapping onto HTTP/2

working 9 min What the schema of lesson 0402 becomes once it is put on a wire. · gRPC over HTTP/2 - the protocol mapping

The one-minute version

  • Protobuf gave you the types. A service block in the same file gives you the methods, and the compiler emits a stub whose body is a network call.
  • One RPC is one HTTP/2 stream. That is the whole mapping, and everything else about gRPC follows from it.
  • Messages inside the stream are length-prefixed: one flag byte, four length bytes, then the payload. That framing is what makes streaming a call shape rather than a workaround.
  • The outcome arrives in trailers, as grpc-status. The HTTP status is 200 even when the call failed.
  • What it costs: every hop must speak HTTP/2 and pass trailers through, so an intermediary that does neither breaks the call in a way the HTTP status will not show.

1. The mental model: the stub is the product

A .proto file that declares service Payments { rpc Charge(ChargeRequest) returns (ChargeReply); } compiles into two artefacts. On the server it is an interface with one method left for you to implement. On the client it is a concrete class with that method already written, whose body opens a stream, writes a serialised ChargeRequest, waits, and returns a ChargeReply. Neither side ever writes a URL, a status code or a JSON key.

That is the whole appeal and it is worth being precise about what it does and does not remove. It removes the hand-written client, which is where drift between two services usually starts, and it removes the question of what a field is called on the wire, which lesson 0405 showed is a question JSON answers badly. It does not remove the network, and the largest mistake teams make with gRPC is treating a stub that looks like a local function as if it were one. Lesson 1202 is entirely about that mistake.

2. The mechanism: one call, one stream

The mapping onto HTTP/2

gRPC maps one RPC onto one HTTP/2 stream, and uses the stream identifier as the identity of the call. The request opens with a HEADERS frame carrying :method POST, a path of the form /Service-Name/method-name, content-type: application/grpc, an optional grpc-timeout, and te: trailers. That last one is not decoration: the specification says it is there so that incompatible proxies can be detected.

Because HTTP/2 multiplexes many streams over one TCP connection, a client that makes a thousand concurrent calls opens one connection rather than a thousand, and none of the calls blocks another. This is the property that makes the streaming shapes practical, and it is inherited from the transport rather than invented by gRPC.

The outcome is in the trailers

The part that surprises people reading a packet capture for the first time: the HTTP response status is 200 on a failed call. The gRPC outcome lives in HTTP trailers, as grpc-status with a decimal code and grpc-message with a percent-encoded description, and the specification requires that status be sent in trailers even when it is OK.

Trailers are the right place because a server streaming a thousand rows does not know at header time whether the thousandth will fail. Header fields have to be sent before the body, and the outcome is not known until after it, so any protocol that streams has to carry the outcome behind the data or lie about it early.

3. The trade-off: the mapping is also the constraint

Everything gRPC gives you comes from that mapping, and so does everything it demands. The path must carry HTTP/2 end to end, and every hop must forward trailers unchanged. Terminate the connection at a proxy that speaks HTTP/1.1 to the backend and the call cannot complete, because there is nowhere to put the status. This is the single most common gRPC deployment failure, and its symptom is a request that looks fine in the load balancer's access log.

The second constraint is the connection itself. A gRPC channel is long-lived by design, and gRPC's default load-balancing policy, pick_first, "does no load balancing but just tries each address it gets from the name resolver and uses the first one it can connect to". A client left on that default sends every call to one backend for the life of the process, which is invisible while traffic is low and becomes an unbalanced fleet exactly when it is not. Choosing round_robin or a look-aside balancer is a decision the client has to make, not something the network arranges for it.

A browser cannot make a gRPC call. The mapping needs control over HTTP/2 framing and access to trailers, and the browser fetch API gives a page neither, which is why the browser story is gRPC-Web: a second, different mapping with a proxy that translates. If the caller you are designing for is a web front end, the schema still helps, but the transport on that hop is not the one this page describes.

Retrieval practice

Answer from memory before revealing.

A gRPC call fails with RESOURCE_EXHAUSTED. What HTTP status does a proxy see?
The mapping sends 200 in the response headers and puts the outcome in grpc-status, which the specification requires even when the outcome is OK. The other three are what a reader expects an HTTP-shaped protocol to do, and expecting them is exactly how a failing call gets logged as a success.
Why does each gRPC message carry a four-byte length before its payload?
A serialised protobuf message is not self-delimiting, so a stream of them is unreadable without a framing marker - which is what makes the streaming call shapes possible at all. The first is a real side benefit rather than the reason; HTTP/2 frames carry their own lengths and do not align with message boundaries; and no proxy reads gRPC payloads.
