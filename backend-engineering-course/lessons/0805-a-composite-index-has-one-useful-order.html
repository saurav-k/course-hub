A composite index has one useful order, and the planner picks from an estimate

working 11 min Column order is a design decision, and the plan is a guess made from a sample. · PostgreSQL - Multicolumn Indexes

The one-minute version

  • An index on (a, b, c) is sorted by a, then b within equal a, then c. There is one order, and it is not symmetric.
  • The documented rule: equality on leading columns, plus one inequality on the first column that has no equality, is what limits the part of the index scanned.
  • Everything after that first inequality is a filter rather than a limit, which is why the ranged column goes last.
  • An index-only scan answers from the index alone, but only when every referenced column is in it and the visibility map says the page is all-visible.
  • What it costs: the planner works from a sample, so a wrong estimate produces a wrong plan, and the only honest way to know which plan you got is EXPLAIN.

1. The mental model: sorted by the first column, then the second

One order, and it decides everything

An index on several columns holds its entries sorted by the first column, then by the second among entries that agree on the first, and so on. That is the whole structure, and every rule about composite indexes is a consequence of it. PostgreSQL states the consequence exactly: equality constraints on leading columns, plus any inequality constraints on the first column that does not have an equality constraint, will always be used to limit the portion of the index that is scanned. It also states the softer version that follows: such an index can be used with any subset of its columns, but it is most efficient when there are constraints on the leading ones.

Work that rule against one index and it stops being abstract. Take (tenant_id, status, created_at), which is the shape most multi-tenant list endpoints want.

Two design rules fall out. Put the columns you always match exactly first, and put the one you range over last, because a range can only be the last useful thing. And keep the index short: the documentation says multicolumn indexes should be used sparingly, that in most situations an index on a single column is sufficient and saves space and time, and that indexes with more than three columns are unlikely to be helpful unless the table's usage is extremely stylised. The hard ceiling is 32 columns including INCLUDE columns, and it exists to be far away rather than to be approached.

2. The mechanism: answering without touching the table

Lesson 0804 ended each lookup with a second read, from the index entry to the row itself. An index-only scan is how that second read is avoided: values are returned directly out of each index entry instead of consulting the associated heap entry. Two conditions, and the second is the one people miss.

The first is simple. The query must reference only columns stored in the index, so SELECT x, y FROM tab WHERE x = 'key' can be answered by an index on (x, y) and SELECT x, z cannot. A covering index is one built for this on purpose, with CREATE INDEX tab_x_y ON tab (x) INCLUDE (y): the included column is not part of the search key, so it need not even be a type the index can order, it is merely stored.

Which is exactly the stated caveat. There is little point in including payload columns unless the table changes slowly enough that the scan is likely not to need the heap, because if the row must be visited anyway it costs nothing more to read the column from there. The other cost is size: non-key columns duplicate table data and bloat the index, potentially slowing searches, and an index tuple that exceeds the maximum size for its type makes the insertion fail outright. Be conservative with wide columns.

3. The mechanism: the plan is an estimate

Having the right index does not mean it is used, because the planner chooses between access paths by cost, and cost is computed from an estimate of how many rows each condition will match. That estimate comes from statistics collected by ANALYZE and stored in pg_statistic, readable through the pg_stats view: a list of most common values, a histogram of the rest, the count of distinct values, the fraction that are null. The documentation notes these are always approximate even when freshly collected, and by default each column keeps up to 100 entries in its lists.

That is the whole failure mode of query planning, and knowing it makes the diagnosis routine. When a plan is wrong, ask whether the estimate is wrong first. Stale statistics after a bulk load, a correlation between two columns that single-column statistics cannot see, a value distribution that is not close to uniform inside its bucket: each produces a bad estimate, and the bad plan is the correct decision given it. The documentation calls out the correlated case specifically, saying estimates over more than one column are frequently wrong when the planner has only single-column data, and that this causes it to select bad plans.

EXPLAIN shows you the plan the planner chose from estimates. EXPLAIN ANALYZE runs the query and shows the estimate beside the real row count, which is the only form that can tell you the estimate was wrong. Read them as a pair rather than as a number: the interesting quantity is the ratio between the estimated and actual rows at each node, and a factor of a hundred at the bottom of the tree is what turns into a wrong join strategy at the top. It also genuinely executes the statement, so do not reach for it on a write.

Check yourself

Retrieval practice

Answer from memory before revealing.

Given an index on (tenant_id, status, created_at), which query limits the scan by all three columns?
Two equalities on the leading columns then one inequality on the third is exactly the documented rule. The first has no constraint on the leading column at all, the third ends the useful part at the range over status, and the fourth ranges on the first column so nothing after it can limit anything.
Why can an index-only scan still have to read the table?
Visibility lives with the row, so when the visibility map says a page is not all-visible the row must be read to find out whether you may see it. B-tree entries hold the real value rather than a hash, no verification sampling exists, and INCLUDE columns are stored in the index, which is the entire point of them.

Your teacher. Take your busiest list query and run EXPLAIN ANALYZE on it. Compare the estimated and actual row counts at every node, then ask the agent which node's ratio is worst and whether the composite index it uses has its ranged column last.
