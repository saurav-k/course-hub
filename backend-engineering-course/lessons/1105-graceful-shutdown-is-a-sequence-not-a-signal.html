SIGTERM is the first step of a shutdown, and the rest is an ordered sequence against a deadline

working 10 min The failure you schedule yourself, several times a day. · Kubernetes - Termination of Pods

The one-minute version

  • Every deploy stops a running process, so shutdown is the failure mode you trigger most often and the only one you fully control.
  • A signal is not a shutdown. It is the start of a sequence: stop being advertised, stop accepting, finish what is in flight, release, exit.
  • The step everyone misses is the first one. Kubernetes removes the pod from its EndpointSlices at the same time as the kubelet starts the shutdown, so requests can still arrive after SIGTERM.
  • The sequence runs against a clock. The default grace period is 30 seconds, after which SIGKILL is sent to anything still running, and SIGKILL cannot be handled.
  • What it costs: every second you spend draining is a second the deploy is slower, and holding a connection open forever is not draining, it is refusing to leave.

1. The mental model: shutting down is a handover, not a stop

The instinct is that shutdown means stop. Run the deferred cleanup, close the database pool, exit zero. That produces a service which drops in-flight requests on every deploy, and because a deploy replaces instances one at a time, the damage is spread thinly enough to look like background noise rather than a bug you introduced.

The better model is a handover. Somewhere there are replicas that are staying, or that have just started. Your job on the way out is to make sure that everything currently in your hands either finishes or is given back cleanly, and that nothing new is put into your hands after you have started. Those are two different obligations and they run in opposite directions - one is about the future and one is about the past - which is why the order of the steps is the whole subject.

2. The mechanism: what the orchestrator actually does

The signal and the withdrawal happen at the same time

Kubernetes documents the termination flow step by step, and one step in it is the reason naive shutdown handlers fail. When the pod is marked terminating, the kubelet begins the local shutdown; if a preStop hook is defined it runs first, and only then does the kubelet ask the container runtime to send TERM to process 1 in each container. Meanwhile - and the documentation says at the same time - the control plane evaluates whether to remove the shutting-down pod from the EndpointSlice objects that back its Services.

Two things are racing, and neither waits for the other. Endpoint removal has to propagate to every kube-proxy, every ingress controller and every client-side load balancer in the cluster, and each of those learns about it by watching and reacting. Your process, meanwhile, got its signal immediately. So there is a window, typically a second or two and occasionally much longer, in which a component still holds your address and will send you a request that you have already decided not to serve.

The budget, and what the runtime gives you

The clock is terminationGracePeriodSeconds and it defaults to 30. When it expires the container runtime sends SIGKILL to anything still running. There is one small piece of slack documented: if a preStop hook is still running when the grace period expires, the kubelet grants a one-off extension of 2 seconds - and no more, so a hook that sleeps longer than the grace period allows needs the grace period changed rather than the hook trusted.

Inside the process, the language runtime gives you the middle of the sequence. Go's http.Server.Shutdown is a precise description of the contract: it closes all open listeners, then closes idle connections, then waits for active connections to return to idle, and if the provided context expires first it returns the context's error. It also states what it does not do - it does not close or wait for hijacked connections such as WebSockets, and the caller must notify those separately. That exclusion is the second-most-common shutdown bug after the endpoint race.

shutdown.go · the sequence, in the order the sequence has to run
<-ctx.Done()                                  // SIGTERM arrived

readiness.Store(false)                        // 1. stop being advertised
time.Sleep(cfg.DrainDelay)                    // 2. let the withdrawal propagate

deadline, cancel := context.WithTimeout(context.Background(), cfg.ShutdownGrace)
defer cancel()
if err := srv.Shutdown(deadline); err != nil { // 3. finish in-flight work
    slog.Error("drain incomplete", "err", err) // the deadline beat us
}

wsHub.CloseAll()                              // 4. hijacked conns, by hand
consumers.StopAndWait(deadline)               // 5. in-flight jobs, not requests
db.Close()                                    // 6. release, last of all

Step 6 is last for a reason worth stating: closing the database pool before the in-flight requests have finished converts a graceful shutdown into a burst of 500s, and it is an easy mistake because the cleanup reads naturally at the top of the function. Resources are released in the reverse order of the dependency, which means after everything that uses them has stopped.

3. The trade-off: draining costs deploy time, and the budget is fixed

Every second of drain delay is a second added to every instance replacement, and a rolling deploy of forty pods pays it forty times. Worse, the delay and the drain share one budget: a 30-second grace period spent as 5 seconds of propagation wait leaves 25 for in-flight work, and if your slowest request is a 60-second report then no arrangement of those numbers is honest. The fix is not a longer grace period, it is a request that does not take 60 seconds - or a job queue, which is what lesson 0605's asynchronous work exists for.

The same budget question decides what to do with work that is not a request. A background consumer holding a message must decide, at the signal, whether to finish the message or return it to the queue for another instance. Finishing is right when the work is short and the redelivery is expensive; returning it is right when the work is long, and it is only safe because the consumer was made idempotent - which is the argument lesson 0605 already made about retries.

A process that ignores SIGTERM is not merely impolite - it makes every deploy take the full grace period and then lose data. Two ordinary situations produce it without anybody deciding to. A container whose entrypoint is a shell script gets the signal delivered to the shell as process 1, which does not forward it to the application unless the script uses exec. And a runtime that installs no handler for the signal takes the default disposition, which is to terminate immediately with nothing flushed. Both look completely healthy until the day you need the last few seconds.

Why can a request arrive after your process has received SIGTERM?
The control plane starts removing the pod from EndpointSlices at the same moment the kubelet begins shutdown, and that removal has to reach every proxy. The first option is not how signal delivery works; the third describes a different mechanism that does not explain the first arrival; and the fourth is a real effect of keep-alive but does not account for a fresh connection reaching a terminating pod.
Go's Server.Shutdown documents one class of connection it will not wait for. Which?
Shutdown neither closes nor waits for hijacked connections, and says the caller must notify them separately. Idle connections are closed by Shutdown, which is one of the steps it documents; a request past its read timeout is handled by the server's ordinary timeout machinery; and a connection mid-handshake has not been hijacked, so it is inside the set Shutdown manages.
