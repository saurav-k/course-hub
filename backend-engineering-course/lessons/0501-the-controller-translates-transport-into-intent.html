Module 05 · The layered service · Lesson 0501

A controller turns a request into a call with no HTTP in it, and a result back into a status

working 8 min Two translations, and nothing else. · RFC 9110 §15 - Status Codes

The one-minute version

  • A controller performs two translations and no third thing: transport into intent on the way in, result into status on the way out.
  • The call it makes carries no transport type - no request object, no header map, no framework context - which is what makes the layer below portable.
  • The outward translation is a mapping table: each named outcome the layer below can produce gets one status, decided once.
  • RFC 9110 already separates the cases you need: 400 for malformed, 422 for well-formed but unprocessable, 409 for a state conflict.
  • What it costs: the table is duplication of a kind, and a second transport means a second one that has to agree with the first.

1. The mental model: a translator faces two ways

A controller sits between a protocol and a program. On one side there is a method, a target, a header section and possibly a body, all of which are facts about HTTP. On the other side there is a function that wants an order identifier and a reason. Nothing in the second description mentions the first, and the controller's whole job is to get from one to the other and back.

NestJS states the outward-facing half plainly: controllers are responsible for handling incoming requests and sending responses back to the client. The part worth adding is that the two halves are separate translations with separate failure modes. Inbound, the controller is turning bytes and strings that arrived from a stranger into values a program can act on. Outbound, it is turning an outcome the program produced into a status a stranger will interpret. A controller that does anything between those two is doing another layer's work at the one place in the system where the framework is hardest to test around.

2. The mechanism

What the controller owns

Four things, and they are all translation. It reads the request parts that address the work: the path parameters, the query string, the relevant header fields. It decodes and validates the body into the values Module 04 taught it to trust. It calls exactly one operation on the layer below, passing values that carry no transport type. Then it writes a status, any response fields the answer needs, and a body.

The thing it must not own is the decision. Whether an order may be cancelled is a rule about orders, not about requests, and a rule written inside a handler can only ever be exercised by constructing a request. That is the substitution test from the previous page, failing: there is no seam between the rule and the transport, so the rule cannot be run without one.

the shape in two voices · both handlers are translation and dispatch, with no rule inside
// Go: net/http. The handler reads, calls once, and maps.
func (h *OrderHandler) Cancel(w http.ResponseWriter, r *http.Request) {
    id := OrderID(r.PathValue("id"))
    var body cancelRequest
    if err := json.NewDecoder(r.Body).Decode(&body); err != nil {
        writeProblem(w, http.StatusBadRequest, "body is not valid JSON")
        return
    }
    err := h.orders.Cancel(r.Context(), id, body.Reason)
    writeProblem(w, statusFor(err), err)   // one table, one place
}

# Python: the same three moves, with the framework doing more of the reading.
async def cancel(order_id: str, body: CancelRequest) -> Response:
    try:
        await orders.cancel(order_id=OrderID(order_id), reason=body.reason)
    except DomainError as err:
        raise HTTPException(status_code=STATUS_FOR[type(err)], detail=str(err))
    return Response(status_code=204)

Mapping a result onto a status

The outward translation is a table from named outcomes to status codes, and RFC 9110 has already done most of the work of separating the cases. A body that is not valid JSON is a 400, which the specification defines as the server not processing the request because of something perceived to be a client error, malformed syntax included. A body that parsed cleanly but asks for something incoherent is a 422: the specification reserves it for content whose syntax is correct but whose instructions the server was unable to process. An order that exists but is in the wrong state is a 409, defined as a conflict with the current state of the target resource. A resource that is not there is a 404. An outcome nobody anticipated is a 500, which the specification defines as an unexpected condition, and that word is the test: if you predicted it, it is not a 500.

3. What the table costs

The mapping is duplication of a sort: the service already knows that shipping an order makes cancellation impossible, and now the controller knows it too, in a second vocabulary. That is the price of the boundary and it is worth paying, because the alternative is a service that returns status codes, which is a service that has HTTP in it and cannot be called from a queue consumer.

The price is charged again for each additional transport. A gRPC front end for the same service needs its own table onto gRPC's status codes, and the two tables have to agree about which outcomes exist even though they disagree about what to call them. The way to keep them agreeing is to make the outcomes an explicit, enumerated part of the service's contract rather than a set of exception types that grew, which is what the next page is about.

The failure that is easy to ship: passing the underlying error's text through to the client as the body. A driver's message names the table, the column, sometimes the query, and it reaches every client and every intermediary that logs a response. The status is the part the client acts on and the message is the part your on-call engineer needs, so map the first and log the second. Module 07 owns the threat model, and this is where the exposure starts.

Retrieval practice

Answer from memory before revealing.

The service reports that an order has already shipped. Which status?
RFC 9110 defines 409 as a conflict with the current state of the target resource, which is exactly this. 422 is for content that parsed but could not be processed, 400 is for a request perceived as malformed, and 500 is reserved for an unexpected condition - and an outcome the service named is by definition not unexpected.
What does a controller owe the layer directly below it?
Anything the layer below can only obtain from a request has put HTTP inside it, which is the coupling the boundary exists to prevent. The first two options hand a transport type across under different names, and the fourth inverts the direction: the status is produced from the outcome, never supplied to the code that produces the outcome.

Your teacher. Take the longest handler in your own service and cross out every line that is reading a request or writing a response. Ask the agent whether what is left is one call or a decision, and if it is a decision, where it would have to move for a test to reach it without a request.
