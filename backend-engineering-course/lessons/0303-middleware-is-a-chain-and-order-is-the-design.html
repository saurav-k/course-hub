Middleware wraps the handler in both directions, so registration order is request order and reverse response order

working 8 min The chain around the handler. · PEP 3333 - Middleware components

The one-minute version

  • A middleware is not a step in a queue. It wraps the thing after it: PEP 3333 describes it as an application to the server above and a server to the application below.
  • Wrapping gives every link two passes: code before it calls the next link runs on the way in, code after it runs on the way out.
  • So one registration order gives you two orders. First registered is first in and last out.
  • A link that never calls the next one ends the request there. That is not an error, it is how authentication and rate limits work.
  • What it costs: the outward pass is only real until the first byte is written, and after that the status and fields cannot be changed.

1. The mental model: an onion, not a queue

The word "chain" invites the wrong picture: a row of steps, each finishing before the next begins, with your handler at the end. That picture cannot explain how a timing middleware measures a request, because a step that has already finished has nothing left to measure with.

PEP 3333 gives the right picture in one sentence: a middleware component acts as an application to its containing server, and as a server to a contained application. It is both halves of the interface at once, which means it holds the call to the next link inside itself. Control goes in through every layer and comes back out through every layer, in reverse. The layers are an onion, and your handler is at the centre.

2. The mechanism: a function that returns a handler

The shape, in both voices

Go states it in the type system. A handler is anything with a ServeHTTP method, so a middleware is a function taking a handler and returning a handler. The returned handler closes over the one it was given and decides when to call it. Python's WSGI states the same thing with a callable that holds another callable. Neither framework invented the pattern; it falls out of the interface being the same on both sides.

middleware.go · Go, net/http, a handler wrapped in a handler
func withTiming(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        started := time.Now()          // the inward pass
        next.ServeHTTP(w, r)           // everything inside runs here
        log.Printf("%s %s took %s",    // the outward pass
            r.Method, r.URL.Path, time.Since(started))
    })
}

srv := withTiming(withAuth(mux))       // outermost written first
middleware.py · Python, WSGI, a callable that holds a callable
class Timing:
    def __init__(self, app):
        self.app = app

    def __call__(self, environ, start_response):
        started = time.perf_counter()              # the inward pass
        body = self.app(environ, start_response)   # everything inside
        log(environ["PATH_INFO"], time.perf_counter() - started)
        return body                                # the outward pass

app = Timing(Auth(router))

The chain: one order, two directions

Composition is what builds the chain, and the nesting is visible in the source. Express reaches the same arrangement from the other end, by registration: its documentation states that the order of middleware loading is important and that functions loaded first are also executed first. Both statements describe one structure. Registered first means outermost means first in and last out.

The short circuit: not calling the next link

A link is under no obligation to continue. Express says a middleware that does not end the request-response cycle must call next() or the request hangs, and the contrapositive is the useful half: a link that writes a response and returns without calling next() has ended the request, and nothing inside it ever runs. That is not a failure mode. It is the mechanism behind every authentication gate, rate limiter and maintenance switch you have written.

3. The trade-off: the order is now yours to get right

The chain buys you one place to put every cross-cutting concern, and charges you for a decision you now have to make deliberately. Three ordering rules cover most of it, and each one follows from the onion rather than from taste.

Anything that must observe everything goes outermost: request logging, tracing, panic recovery. A recovery link inside the handler cannot catch a panic raised by a link outside it. Anything that rejects goes next, cheapest first, because a short circuit only saves the work still inside it. Anything that prepares state for the handler goes innermost: body parsing, session loading, the request context of Module 05, since only the handler needs it and doing it for a request that will be refused is pure waste.

The rule that catches people is the outward pass. A link that wants to add a response field - a cache directive, a correlation identifier, a compression encoding - has to be outside anything that might write the response, because the outward pass is where it will do its work and by then it may be too late.

The outward pass is not symmetric with the inward one, and the asymmetry is in the protocol rather than in any framework. A response's status line and fields go on the wire before its body, so once the first byte is written they are gone. Go's ResponseWriter documents it exactly: changing the header map after a call to WriteHeader or Write has no effect. A middleware that sets a header on the way out is correct only while nothing inside it has started writing, which is why response-shaping links buffer or wrap the writer rather than trusting their position alone.

Answer from memory before revealing.

A link is registered first. Where does it sit in the two passes?
Registered first means outermost, and an onion is entered from the outside and left from the inside, so first in is last out. The first and second options describe a queue rather than a wrapping, and the fourth reverses the nesting entirely.
Where does a rate limiter belong relative to token verification?
A short circuit only saves the work nested inside it, so the cheaper rejection belongs further out. Counting only verified users is a real requirement but it pays a signature check per flood request; middleware nests rather than sitting side by side; and position matters precisely because rejecting is what they do.
