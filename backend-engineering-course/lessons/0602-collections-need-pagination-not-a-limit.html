Module 06 · API design · Lesson 0602

A cursor is stable under concurrent writes and an offset is not, so the choice is correctness

working 9 min Why the page number is the bug, not the page size. · PostgreSQL - LIMIT and OFFSET

The one-minute version

  • An unbounded collection endpoint is an outage you wrote yourself, but a bare limit is truncation, not pagination: it gives the caller no way to continue.
  • Offset counts rows, so one insert or delete before the reader's position shifts every later row and the next page repeats or skips items.
  • A cursor anchors on values in the last row seen, so a write elsewhere in the collection moves nothing the cursor depends on.
  • Offset also gets slower with depth: PostgreSQL states that rows skipped by OFFSET are still computed inside the server.
  • What it costs: a cursor cannot jump to page 57, usually cannot give a total count, and must be treated by the caller as opaque.

1. The mental model: two ways to say where you got to

Offset remembers a count

Offset pagination says "skip the first 100 and give me 50". The position is a number of rows, and a number of rows only means something if the rows have not moved. Between the first request and the second the collection is live: other users create orders, cancel them, and change the field you sorted on. Nothing in the request told the database which items you already saw, so the second page is computed against a collection that is no longer the one the first page came from.

A cursor remembers a place

Cursor pagination, also called keyset pagination, says "give me the 50 that come after this row". The position is the sort key of the last item the caller actually received, so the query is a comparison rather than a count: everything ordered after that value, limited to 50. An insert somewhere else in the collection changes no value the comparison reads, and the caller's place is exactly as valid as it was.

2. The mechanism: the comparison, and what it needs

A cursor is a value, not a page number

The query behind a cursor is a comparison on the sort key, and the sort key has to be unique or the comparison has a tie it cannot break. In practice that means a compound key: the column you actually sort by, plus the primary key as a tiebreaker. Ask for everything whose sort pair is ordered after the last pair delivered, ordered the same way, limited to the page size. The cursor the caller sends back is that pair, encoded.

Two rules keep it honest, and both come straight from published guidance. Google's AIP-158 requires page tokens to be opaque and explicitly not user-parseable, and requires that every other parameter of the request match the call that produced the token, with an error rather than a silent reinterpretation when it does not. Both exist for the same reason: the token encodes an internal position, and a caller who parses or edits it has started depending on something you never promised, which is lesson 0600 arriving on schedule.

The second cost: depth

Correctness is the main argument, and there is a second one worth stating with numbers because it is often the one that gets noticed first. PostgreSQL documents that the rows skipped by an OFFSET clause still have to be computed inside the server, so a deep page is not cheaper than a shallow one - it is the shallow one plus everything before it.

  1. Fix the page size. 50 items per page, so page k asks for LIMIT 50 OFFSET 50(k-1).
  2. Count what the server produces. It must generate the skipped rows and then 50 more, which is 50k rows for page k.
  3. Put page 100 beside page 1. 50 × 100 = 5,000 rows produced to return 50, against 50 for the first page - a hundredfold difference for the same response.

3. The mechanism: telling the caller how to continue

Whichever scheme you pick, the next page has to be reachable without the caller reconstructing a URL. Two published conventions do this and they compose. The first is the Link header from RFC 8288, which carries a typed connection between resources: a target URI plus a relation type such as next or prev, registered with IANA rather than invented per API. GitHub returns exactly that, with next, prev, first and last, and its documentation tells callers to follow those URLs rather than build their own, precisely because the query parameters differ between endpoints.

The second is a token in the body, which is what AIP-158 specifies: a next_page_token the caller passes back as page_token, absent when the collection is exhausted. Note the termination rule in both: the caller stops when there is no next link or no token, never by comparing the number of items returned against the page size. A page can legitimately come back short, and a caller that stops on a short page stops early.

A cursor removes the duplicate and the skip - it does not give you a snapshot. Items already delivered can still be edited or deleted after the caller read them, and a caller walking a large collection over several minutes is assembling a picture that was never true at any single instant. If the caller genuinely needs a consistent view, that is a different mechanism entirely: a repeatable-read transaction, an export job, or a change feed they replay. Say which one you are offering, because a cursor quietly reads like a snapshot and is not one.

Check yourself

Retrieval practice

Answer from memory before revealing.

A row is deleted from the head of a collection between page 1 and page 2. Under offset, what happens?
A delete shifts every later row up by one, so the row that would have been at position 51 moves to 50, which the caller already passed. A repeat is what an insert causes, the page still fills because rows further down slide up, and an offset past the end returns an empty page rather than an error.
Why does AIP-158 require page tokens to be opaque and not user-parseable?
The token encodes an internal position, so the moment a caller reads or edits it, your encoding is frozen by dependence rather than by decision. Size is irrelevant at these lengths, authorization is checked on the request regardless of the token, and the matching-parameters rule, not opacity, is what handles a changed sort order.
