Module 04 · Serialization and contracts · Lesson 0404

One resource has many representations, and a mismatch is 406 or 415 rather than 400

working 8 min A wish in one direction, a label in the other. · RFC 9110 §12.1 - Proactive Negotiation

The one-minute version

  • A resource is not its bytes. One URI can answer as JSON, as CSV, in English or in German, and each of those is a representation.
  • Accept is a preference about the response; Content-Type is a statement of fact about the body in this message. One is a wish, the other is a label.
  • The server chooses, which RFC 9110 calls proactive negotiation, and then names the request fields it used in Vary so a shared cache can replay the choice.
  • No acceptable response representation is 406. A request body in a format the resource does not support is 415. Neither is a 400 - the syntax was fine.
  • What it costs: every dimension you negotiate on multiplies the cache key, and RFC 9110 lists reduced cache reuse among proactive negotiation's serious disadvantages.

1. The mental model: the resource and its representations

Why the same URI may return different bytes

Lesson 0200 said the target names a resource rather than a file. This is where that distinction pays. A resource is the concept the URI identifies: this order, the report for March. A representation is one concrete rendering of it, in a particular media type, language and encoding. The order can be rendered as JSON for a mobile client, as CSV for a finance export and as HTML for a browser, and all three are the same resource answering honestly.

Once you accept that, the question of which one to send becomes a real decision rather than a configuration accident, and HTTP gives it a name and a mechanism.

2. The mechanism: preferences in, a labelled choice back

What the server is actually given

In proactive negotiation the client sends its preferences and an algorithm on the server picks from the representations available. RFC 9110 defines Accept, Accept-Charset, Accept-Encoding and Accept-Language for this, and a server may also use implicit signals such as the network address, which is generally a bad idea for the reasons the specification lists.

Weights, and the rule that resolves a tie

Each media range in Accept may carry a q weight expressing relative preference, and ranges may be wildcards: */*, type/*, or a full type. The specification's own example, Accept: audio/*; q=0.2, audio/basic, reads as a preference for audio/basic with any audio type acceptable at a substantial discount. Where more than one range matches a candidate type, the most specific reference takes precedence, so text/html beats text/*, which beats */*.

Two things about this surprise people. First, the preference is advisory: a user agent cannot rely on it being honoured, and the specification says outright that a server might decide a non-conforming response is better than a 406. Second, the server's answer is a fact and not a negotiation. Content-Type states the media type of the representation actually enclosed, and a recipient that finds it absent may assume application/octet-stream or sniff the bytes, which is a security risk the specification warns about directly.

Which refusal, and why not 400

RFC 9110 defines 406 as the target resource having no current representation acceptable under the request's negotiation fields, with the server unwilling to supply a default, and recommends the response list the available alternatives. It defines 415 as the origin server refusing because the content is in a format not supported by this method on this resource, and adds that the cause may be the Content-Type, the Content-Encoding, or something found by inspecting the data. A 400 says the request was malformed, and in both of these cases it was not: it parsed, it was well formed, and the disagreement is about format rather than syntax.

3. The trade-off: every dimension multiplies the cache

Negotiation is not free, and RFC 9110 lists its disadvantages without softening them: a server cannot really know what is best for a user, describing capabilities on every request is inefficient and a privacy risk, it complicates the server, and it limits the reusability of responses for shared caching. That last one is the operational cost you will actually feel.

The mechanism is the one lesson 0203 introduced. A cache that stores a negotiated response has to know which request fields decided it, and Vary is where the server says so. Each field named in Vary becomes part of the cache key, so a response varying on Accept, Accept-Language and Accept-Encoding is stored once per distinct combination the clients happen to send. Since client libraries send long and idiosyncratic Accept strings, the number of distinct keys is set by the clients rather than by you.

Vary is the field people forget, and forgetting it is worse than not negotiating at all. A response selected by language and stored by a shared cache with no Vary will be served to the next reader whatever they asked for, and the bug appears only under cache pressure, only for some users, and never on a developer machine. If a request field influenced the response, name it, and if you cannot name it, do not negotiate on it.

Check yourself

Retrieval practice

Answer from memory before revealing.

A client POSTs an XML body to a JSON-only endpoint. What is the status?
415 is defined for exactly this: the origin server refuses because the content is in a format this method does not support on this resource. 406 concerns the response the server would send rather than the body it received, 400 claims a malformed request when the XML may be perfectly well formed, and 422 requires the server to have understood the content type first.
Why does a negotiated response need a Vary field?
A shared cache has to reproduce the server's selection, and it can only do that if it knows which request fields fed into it, so those fields become part of the stored key. The first two describe things a client might like but not what Vary is for, and the third inverts it: naming a field constrains reuse rather than permitting it.
