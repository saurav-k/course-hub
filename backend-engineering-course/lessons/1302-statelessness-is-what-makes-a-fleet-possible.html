Module 13 · Scale, fleet and shipping · Lesson 1302

A process that remembers nothing can be replaced by any other

working 9 min The constraint that turns one server into a fleet, and the one this course promised to explain. · Fielding, chapter 5 - the stateless constraint

The one-minute version

  • Vertical scale buys a bigger machine and ends. Horizontal scale buys more machines and needs one property: any request can be served by any instance.
  • The stateless constraint is the price of that property: each request carries everything needed to understand it, and the server keeps nothing between them.
  • It buys three things by name - visibility, reliability and scalability - and each of them falls out of the same fact.
  • Sticky sessions look like a way around it and are not: pinning holds until the instance is unavailable, which is the moment you needed it.
  • What it costs: repeated data on every request, and state that did not vanish but moved into a shared store that must now scale in its place.

1. The mental model: interchangeable, therefore countable

What the constraint actually says

Fielding states it as a requirement about the request rather than about the server: each request from client to server must contain all of the information necessary to understand the request, so it cannot take advantage of any stored context on the server. Session state lives entirely on the client. Three named benefits follow, and the useful exercise is to derive each from that one sentence rather than to memorise the list.

Visibility comes first: a monitor does not have to look beyond a single request to know what the request means, which is why a log line, a trace and a cache all become possible. Reliability follows, because recovering from a partial failure is easier when nothing was in the middle of being remembered. Scalability is the one this page is named for, and its mechanism is that the server can free every resource associated with a request as soon as it answers, so instance count and capacity move together.

The operational restatement is the sixth factor of the twelve-factor app: "twelve-factor processes are stateless and share-nothing", and "any data that needs to persist must be stored in a stateful backing service, typically a database". Same constraint, said from the deploy side rather than the protocol side.

2. The mechanism: a balancer in front, a store behind

What the balancer is choosing between

In front of the fleet sits something that picks an instance per request. nginx documents three methods and they differ in what they assume. Round-robin distributes in turn and assumes every request costs about the same. Least-connected sends the next request to the server with the fewest active connections, which is the better default whenever hold times vary, because it is measuring the very quantity lesson 1300 made the unit of cost. Weights bias the split for machines of different sizes.

The same page documents in-band health checking: if a response from a server fails with an error, nginx marks that server as failed and avoids it for a while, governed by max_fails and fail_timeout. That behaviour is only safe because the instances are interchangeable. A balancer that skips an unhealthy instance is silently asserting that the one it picks instead can do the same job, which is the property this page is about.

Why sticky sessions are not the way out

The third method, ip-hash, hashes the client address so that "the requests from the same client will always be directed to the same server". Read the clause that follows it in the same document: "except when this server is unavailable". That exception is not a footnote, it is the failure mode. Pinning works while nothing is wrong, and stops working during a deploy, a scale-down, a crash or a node drain, which are the four moments a user is most likely to be in the middle of something. The twelve-factor position is blunter: "sticky sessions are a violation of twelve-factor and should never be used or relied upon", with a time-expiring store such as Memcached or Redis named as the replacement.

An instance has a lifecycle, and it is short

Once instances are interchangeable, they also become disposable, and the fleet gains the right to create and destroy them at any time: to scale with load, to replace a failed node, or to roll out a new version. That is what lesson 1304 automates. What it demands from the process is that it be able to say when it is ready to take traffic and to finish what it is holding when told to stop, which is the same graceful-shutdown discipline module 11 owns.

3. The trade-off: the state moved, it did not disappear

Fielding names two costs and both are real. The first is network performance: the same data is sent on every request because the server may not keep it, so an auth token, a tenant identifier and a cursor ride along each time and are re-parsed and re-validated each time. The second is subtler: putting application state on the client "diminishes server authority over consistent behavior", because the client may hold an old shape and the server cannot correct it, which is the same asymmetry lesson 0600 named for the interface.

The larger cost is architectural. Every session you take out of process memory arrives somewhere else, and that somewhere is now shared by the whole fleet. A hundred stateless instances in front of one session store have not removed the single point of failure, they have moved it and made it busier. That is why module 09 exists, and why the honest version of this page's claim is that statelessness converts a scaling problem you cannot solve into one you can buy a known answer for.

An in-process cache is not automatically a violation, and the test is whether correctness depends on a hit. A cache that is consulted and falls through to the shared store is fine and every instance may hold a different one. A cache that is the only copy of something is state wearing the word cache, and it fails the moment the instance is replaced. Ask what happens on a cold start, because that is the state every new instance in a fleet begins in.

Check yourself

Retrieval practice

Answer from memory before revealing.

Why is ip-hash routing not a substitute for storing session state elsewhere?
The documented guarantee carries its own exception: the same client goes to the same server except when that server is unavailable, which is every deploy, scale-down and crash. Uneven spread is a real but separate cost, a changing client address breaks the pin without being the reason it is unsafe, and weights are supported alongside it.
Which benefit of the stateless constraint follows most directly from a request being self-contained?
Visibility is the benefit stated in exactly those terms: a monitoring system does not have to look beyond a single request datum. Requests get larger rather than responses getting smaller, handler simplicity is a pleasant side effect rather than a claim the constraint makes, and deploy speed has nothing to do with it.

Practice about 15 minutes, with paper

Practice 1working

A service keeps five things in the process. A JWT verification key fetched at start-up and held for 24 hours. Each signed-in user's shopping basket, in a module-level dictionary. Uploaded avatar images, written under /var/app/uploads. A counter of requests this instance has served, exported to the metrics system. A ledger of seen idempotency keys, in a local LRU cache.

Decide which of the five survive an instance being replaced mid-session, and for each that does not, name where it belongs instead.

Hint

The test is not whether the value is lost. It is whether anything is wrong once it is lost. A cold start that is merely slower is not a violation.

Show the worked solution
  1. The verification key survives. It is a cache with a cold-start refetch, and correctness never depends on a hit. A new instance is slower on its first request and right on all of them.
  2. The basket does not. It is session state and the only copy is in one process, which is the sticky-session failure of this page. It belongs in a time-expiring shared store.
  3. The avatars do not. The file exists on one node, so a later read served by any other instance is a 404. They belong in object storage, with the URL in the database.
  4. The per-instance counter survives. It is meant to be per instance, and the aggregate is the metrics system's job, so a replaced instance starting at zero is the design rather than a loss.
  5. The idempotency ledger does not, and it is the worst of the five. A retry landing on another instance finds no key and re-executes the work, which is exactly the guarantee lesson 0605 sold. It belongs in the shared store that lesson already required.

Sanity check. Exactly the items whose only copy is in the process fail, and two of the five are legitimately per-instance. If you marked all five as violations, the test you applied was "is it lost" rather than "is anything then wrong".

Your teacher. Restart one instance of a service you own while a user session is active, and write down everything that broke. Ask the agent to help you list every place the process writes to local disk or to a module-level variable after start-up, because that list is the same list.
