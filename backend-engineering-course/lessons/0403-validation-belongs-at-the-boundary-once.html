Module 04 · Serialization and contracts · Lesson 0403

Parse untrusted input into a trusted type at the edge, and the checks deeper in stop being needed

working 8 min One check, one place, one resulting type. · OWASP - Input Validation Cheat Sheet

The one-minute version

  • Deserialization gives you a value of the right shape. It never gives you a value of the right meaning, and the difference is this whole page.
  • Do the check once, at the boundary, and have it produce a type the rest of the program cannot construct wrongly. That is parsing rather than validating.
  • A re-check in the middle of a service is a symptom: it says the value that arrived there carried no guarantee, so someone had to re-earn it.
  • The boundary asks three questions in order: does it parse, is the value meaningful, is this caller allowed. Only the first two belong to this module.
  • What it costs: a second set of types at the edge, and the discipline never to pass the raw decoded map inward.

1. The mental model: parse, do not validate

A check that returns a type instead of a boolean

The common shape is a function that takes the decoded request and returns true or false, after which the request is passed onward unchanged. That function has thrown away everything it learned. The value that continues into the service has exactly the type it had before the check, so nothing downstream can tell a checked value from an unchecked one, and the only defence available to a careful author further in is to check again.

The alternative is to make the check constructive. The boundary takes the untrusted input and either fails or returns a value of a different type: not a map with a quantity key that might be anything, but an OrderRequest whose quantity is a positive integer because there is no way to build one where it is not. Now the knowledge is in the type, it travels with the value, and a function that accepts an OrderRequest is stating its precondition in its signature rather than in a comment.

2. The mechanism: three questions, in order

A boundary that is doing its job asks three things, and mixing them up is what produces the wrong status code and the unhelpful error message.

The middle rejection has a status code of its own. RFC 9110 §15.5.21 defines 422 as the server understanding the content type and finding the syntax correct, while being unable to process what the content asked for, and it says in the same paragraph that this is the case where 415 is inappropriate. A well-formed body carrying a negative quantity is exactly that.

Doing it in two languages

The mechanism is the same in a typed and an untyped language, and only the spelling differs. In Go the decoded target is a struct, the field names are bound by tags, and the strictness is a decoder option: DisallowUnknownFields makes an unrecognised key an error instead of a silent skip. The constructive step is a function that takes that struct and returns a domain type or an error, and it is the only exported way to build the domain type.

boundary.go · the constructive step, Go
type orderWire struct {
    Quantity *int   `json:"quantity"`
    Currency string `json:"currency"`
}

// OrderRequest cannot be built except through ParseOrder.
type OrderRequest struct {
    quantity int
    currency string
}

func ParseOrder(r io.Reader) (OrderRequest, error) {
    d := json.NewDecoder(r)
    d.DisallowUnknownFields()
    var w orderWire
    if err := d.Decode(&w); err != nil {
        return OrderRequest{}, fmt.Errorf("malformed body: %w", err)
    }
    if w.Quantity == nil {
        return OrderRequest{}, errors.New("quantity: required")
    }
    if *w.Quantity <= 0 {
        return OrderRequest{}, errors.New("quantity: must be positive")
    }
    return OrderRequest{quantity: *w.Quantity, currency: w.Currency}, nil
}

Note the pointer on Quantity. It is there for the reason lesson 0401 gave: without it an absent key and an explicit zero are the same value, and the required check silently passes for a request that never sent the field. In Python the same design is a frozen dataclass or a pydantic model whose constructor raises, and the rule that makes it work is identical: nothing in the service constructs the domain type by hand.

3. The trade-off: two type sets, and the temptation to skip one

The honest cost is duplication. You now have a wire type that mirrors the document and a domain type that mirrors your model, plus the function between them, for every endpoint. On a small service that feels like ceremony, and the tempting shortcut is to decode straight into the domain type and check afterwards.

The shortcut works until the two shapes diverge, which they always do: the wire keeps a field you renamed internally, the domain gains a field no client should ever set, an endpoint accepts a partial update. At that point a single shared type has to satisfy two contracts with different requirements, and the usual resolution is to loosen the domain type until it can hold anything the wire might send. That is the failure this separation exists to prevent, and it is worth paying the duplication before you feel the need rather than after.

Rejecting input is not the same as sanitising it. Stripping suspicious characters and continuing produces a value nobody specified, from a request nobody made, and it hides the attempt from your logs. OWASP is explicit that input validation should not be the primary defence against XSS or SQL injection, though it contributes to reducing their impact, and points instead at the mechanism that sits at the sink: a parameterised query for a database, contextual encoding for a page. It also says to build the boundary as an allow-list, defining exactly what is permitted, rather than a list of characters to strip. Reject at the boundary, encode at the sink, and never trade one for the other.

Retrieval practice

Answer from memory before revealing.

Why is a quantity re-check inside the repository a design smell?
The re-check exists because the type reaching that function cannot express whether it was checked, so the author had no way to rely on the earlier check. The cost in time is negligible, a database constraint is a good idea for a different reason, and the re-check reports its error perfectly well - the problem is that it was needed at all.
A body parses cleanly but carries a negative quantity. What should it get?
The grammar held and the shape was right, so the failure is semantic and the client should be pointed at the value rather than at the syntax. A 400 is defensible and widely used but tells the client less; 415 is about the media type of the body, which the next lesson covers; and a 500 blames the server for a request that was the client's to fix.
