Module 07 · Auth and security · Lesson 0701

The cookie carries a name, and the server keeps everything the name refers to

foundation 8 min The first of three shapes the credential can take. · OWASP - Session Management Cheat Sheet

The one-minute version

  • A session id is a pointer, not a fact. It should say nothing, mean nothing, and be guessable by nobody; the server holds everything it refers to.
  • Because the fact lives on the server, logout is a real operation: delete the entry and the next request arrives as a stranger, whatever the browser still has.
  • The id needs at least 64 bits of entropy, and it must be replaced at login, or an attacker who plants an id in your browser is logged in as you afterwards.
  • Four cookie attributes carry the whole client-side defence: Secure, HttpOnly, SameSite, and a narrow Domain and Path.
  • What it costs: a lookup on every request, and a store every instance of your service has to reach - which is the first thing in this course to genuinely break statelessness.

1. The mental model: the id means nothing on its own

A handle you could print in a log and lose nothing but the account

A session identifier is deliberately empty of content. It is not the user id, not a signed blob, not an encoded role - it is a random string that the server uses as a key into a table it owns. Everything real about the session, including who the caller is and when they logged in, sits in that table's row, where the client can neither read it nor change it.

That emptiness is a security property with numbers behind it. OWASP requires that session identifiers have at least 64 bits of entropy to prevent brute-force session guessing attacks, which at hexadecimal encoding means at least 16 characters, and it asks you to rename the framework default because PHPSESSID in a cookie jar announces your stack to anyone who looks. Neither rule makes sense for a value carrying meaning; both make sense for a value whose only job is to be unguessable.

2. The mechanism: the cookie, its attributes, and the store

Four attributes, and what each one actually stops

The transport is Set-Cookie going out and Cookie coming back, with the attributes defined in RFC 6265 §4.1.2. Four of them do the work. Secure means the cookie is only sent over HTTPS. HttpOnly forbids JavaScript from accessing the cookie through document.cookie, while still attaching it to fetch() calls the page makes - so injected script can act as you but cannot walk away with the credential. SameSite governs whether the browser attaches it to requests started by other sites, which is lesson 0706's subject. Domain and Path decide how widely it travels, and OWASP asks for a narrow or restricted scope for these two attributes.

Two limits are stated in the specification itself and are easy to forget. Cookies do not provide isolation by port and do not provide isolation by scheme, so another service on the same host is inside your boundary; and cookies do not provide integrity guarantees for sibling domains, so a subdomain you do not control can set a cookie your origin will read. A staging host on the same registrable domain is a real path into production sessions.

Renewing the id is what stops fixation

Session fixation is the attack that makes the lifecycle worth drawing. The attacker does not steal your id - they give you theirs. They obtain a valid session id from the site, get the victim's browser to adopt it, and wait for the victim to log in. If the server keeps the same id across the login and simply attaches the account to it, the attacker's copy of that id is now an authenticated session.

The defence is one line in the login handler and OWASP states it as a requirement: the session id must be renewed or regenerated by the web application after any privilege level change, authentication included. The old id is invalidated and a new one issued, so whatever the attacker planted refers to a row that no longer exists. OWASP's list of authentication failures names the same defect from the other end - reuse session identifier after successful login - and it is CWE-384.

3. The trade-off: the store is shared state

The lookup is the price. Every authenticated request now reads a row before it can do anything, which is a network hop if the store is Redis and a query if it is your database. That is usually affordable. The real cost is architectural: the store is state that every instance of your service must reach and agree on, and lesson 0000 called statelessness the thing that makes horizontal scale cheap. Sessions are the first mechanism in this course that genuinely takes some of it back.

Two escapes are common and both are worse than they look. Sticky sessions, pinning a user to one instance so the session can live in that process's memory, trade the shared store for a load balancer that cannot freely rebalance and a deploy that logs people out. Signing the session contents into the cookie itself removes the store, and removes revocation with it - which is exactly the bargain lesson 0702 is about, so it is worth understanding as a deliberate choice rather than as a way to avoid running Redis.

Invalidation has to happen on both sides. OWASP is explicit that when a session ends the application must take active actions to invalidate the session on both sides, client and server. A logout handler that only clears the cookie is not a logout: anyone who copied the id - from a shared machine, a proxy log, or a browser extension - still holds a working credential, and your server will keep honouring it until the timeout it never knew to shorten.

Check yourself

Retrieval practice

Answer from memory before revealing.

Why must the session id be replaced at the moment of a successful login?
That is session fixation: the attacker supplies the id rather than stealing it, so promoting the same value to authenticated hands them the account. Entropy is a separate requirement that applies to both ids, Secure can be set on any response, and a browser overwrites a cookie of the same name without complaint.
What does HttpOnly stop, precisely?
It closes the read, not the use: a cookie set HttpOnly is still attached to fetch() and XMLHttpRequest calls the page makes, so injected script can still act as you. The third option is what SameSite governs and the fourth is what Secure governs.
