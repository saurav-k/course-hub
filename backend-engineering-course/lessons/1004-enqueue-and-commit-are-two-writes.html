A handler that writes a row and sends a message is writing to two systems that cannot agree

working 9 min The defect deliberately left in lesson 1000's code. · microservices.io - Transactional outbox

The one-minute version

  • A command that must update the database and publish a message is two writes to two systems, and there is no transaction spanning them. Every ordering of the two loses something.
  • Publish first and the message may describe a transaction that rolled back. Commit first and, as the pattern's own statement of the problem puts it, there is no guarantee the process will not crash before sending the message.
  • The fix is to make it one write: insert the message into an OUTBOX table in the same local transaction as the business data, and let a separate relay publish from that table.
  • The relay is at-least-once by construction - it can crash after publishing and before recording that it did - so the outbox does not remove lesson 1003's obligation, it depends on it.
  • What it costs: a table that grows, a relay you now operate, publish latency measured in polling intervals, and ordering that has to be arranged rather than assumed.

1. The mental model: two stores, no shared transaction

Both orderings are wrong, differently

The requirement is ordinary. A service command "typically needs to create/update/delete aggregates in the database and send messages/events to a message broker", and it needs those two facts to be true together. A database transaction cannot cover a broker, and a distributed transaction across the two - two-phase commit - is generally not available and would couple the service's availability to the broker's, so it is not the answer either.

That leaves a choice of orderings, and both leak. Publish before the commit and a rollback - a constraint violation, a deadlock, a validation failure late in the handler - leaves a message describing an order that does not exist, which a consumer will faithfully act on. Commit before the publish and the pattern's own statement of the problem applies exactly: "if a service sends a message after committing the transaction there's no guarantee that it won't crash before sending the message". The row exists and nobody will ever be told.

Of the two, the second is the one shipped by default, because it looks careful. It also fails silently in the direction that is hardest to notice: there is no error, no exception and no failed job. There is simply an order in the database that no consumer has heard of, discovered days later by a customer asking where their confirmation went.

2. The mechanism: the outbox table and its relay

One transaction, two tables

The solution is stated in one sentence by the pattern: the service that sends the message first stores the message in the database as part of the transaction that updates the business entities, and a separate process then sends the messages to the message broker. The outbox row is ordinary data in the same database as the order, so the database's own atomicity covers both - either the order and its pending message both exist, or neither does. No new guarantee is invented; an existing one is stretched to cover the second write by turning it into a row.

place_order.py · the corrected version of the snippet in lesson 1000
def place_order(session, account_id: int, items: list[Item]) -> str:
    order = Order(account_id=account_id, state="placed")
    session.add(order)
    session.flush()

    session.add(Outbox(                       # same session, same transaction
        aggregate_type="order",
        aggregate_id=order.id,
        event_type="OrderPlaced",
        payload={"order_id": order.id, "v": 1},
    ))
    session.commit()                          # both rows, or neither
    return order.public_id

Compare it with lesson 1000's version and the difference is that enqueue has become an INSERT. That is the whole idea, and it is worth noticing what it buys structurally: the handler no longer talks to the broker at all, so a broker outage now delays publication instead of failing the request. The command path's availability has stopped depending on the messaging system's.

The relay, and the two ways it reads

Something has to move rows out of that table. There are two families. A polling publisher selects unpublished rows on an interval, publishes them, and marks them sent - simple, needs no privileges beyond the ones your service already has, and its cost is a query against the table on every tick plus a publish latency of up to one interval. Transaction-log tailing instead reads the database's own replication log and publishes what it sees, which is how change-data-capture tools do it; it adds no query load and no latency of its own, and it costs a second piece of infrastructure with database-level privileges.

Whichever you pick, the relay's guarantee is fixed and it is the one this module has been circling. The pattern states it without hedging: "The Message relay might publish a message more than once. It might, for example, crash after publishing a message but before recording the fact that it has done so." The publish and the mark-as-sent are, once again, two writes to two systems. The outbox does not escape that; it relocates it to a component where a duplicate is harmless because lesson 1003's consumer absorbs it.

3. The trade-off: a table, a component, and an ordering question

The obvious costs are the table and the relay. The table takes a write on every command that publishes anything, and it needs an index that makes "unpublished rows, oldest first" cheap, plus a pruning job so that index stays small. The relay is a process with its own deploy, its own failure modes and its own alerting, and if it stops, nothing breaks loudly - the database keeps accepting commands and the queue simply goes quiet, which is another silent failure to put a monitor on.

The subtler cost is ordering. Messages leave the outbox in whatever order the relay reads them, and two commands that committed in one order can be published in another if the relay parallelises or if identifiers are not monotonic. Where order matters, it has to be arranged deliberately - a single reader per aggregate, or a key that puts related messages on the same partition - and it must not be assumed because the rows looked sequential in the table. Lesson 1003's version check is the defence that does not depend on getting this right.

An outbox is not a licence to publish the whole entity. The row is written inside the transaction, so its payload is a snapshot taken before commit, and a consumer receiving a fat event is reading a copy of your schema that will drift from it. Publish the identifiers and the fact that happened - the shape lesson 1000 asked for - and let the consumer read the current state if it needs more. Every argument module 04 made about a wire contract applies here, with the extra difficulty that these messages can sit in the table across a deploy.

Why is committing the row and then publishing the message the more dangerous ordering?
A crash after the commit leaves committed data that no consumer ever hears about, and there is no exception, no failed job and no signal to alarm on - which is worse than publishing early, where the surplus message can at least be rejected or reconciled. Brokers do not care when a message was sent relative to your transaction. Publishing after the commit shortens the transaction rather than lengthening it. And the publish is as retryable as any other call - the problem is the process that would have retried it is gone.
The outbox makes the write atomic. What guarantee does the relay still fail to give?
The relay can crash after the broker acknowledges and before it marks the row sent, so it republishes - at-least-once, exactly as the pattern documents. Durability is precisely what the outbox row buys, since the message is committed before anything tries to send it. Atomicity across the business tables is the local transaction's job and is unaffected. And delivery does happen, possibly more than once, which is the whole point of the residual weakness.

How this connects

  • Ahead, search is an inverted index introduces a second store that has to be kept in step with the database, and this is the machinery that does it.
  • Behind you, a consumer must be idempotent is what makes the relay's at-least-once publishing an acceptable price rather than a new bug.
  • Behind you, compatibility is a rule, not a hope governs the payload of every outbox row, which outlives the deploy that wrote it.

Then ask the agent what would have to change for the second write to become a row in the first transaction.
