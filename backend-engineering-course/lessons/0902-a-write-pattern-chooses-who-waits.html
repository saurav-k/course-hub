Module 09 · Caching · Lesson 0902

A write pattern chooses who waits for the write and what is lost if it stops half way

working 10 min Four things a write can do to the second copy. · AWS - Caching strategies for ElastiCache

The one-minute version

  • A write now touches two copies, and no transaction spans a database and a cache. Every pattern below is a two-step with a gap in the middle.
  • Four answers: update the entry, remove the entry, ignore the entry, or let the entry be the record. Those are write-through, delete-on-write, write-around and write-back.
  • Facebook's memcache removes rather than updates, and states the reason in four words: "deletes are idempotent", so a lost or reordered removal is harmless.
  • Order is load-bearing: write the store first and touch the cache second, or a concurrent reader refills the entry with the value you just replaced.
  • What it costs: write-through pays two trips on every write and fills the cache with answers nobody reads; write-back is faster and hands your durability to a process that is allowed to evict things.

1. The mental model: two copies, no transaction

The constraint that generates all four patterns

When a request changes something, there is a row to update and an entry that may already hold the old value. Your database can make the row change atomic with other row changes. It cannot make the row change atomic with a network call to Redis, because the cache is not a participant in that transaction and has no mechanism to become one. So every write is at least two operations with a gap between them, and every write pattern is an answer to the question of what should be in that gap.

Four answers exist, and they are exhaustive because there are only four things you can do to an entry that might be stale: make it right, make it absent, leave it alone, or make it the thing that is right. Naming them that way is more useful than the industry vocabulary, because the vocabulary hides which of them changes who owns the truth.

2. The mechanism: what each one actually does

Write-through, and the cost AWS lists next to it

Write-through updates the store and then writes the new value into the cache, in the same request. Its advantage is exactly stated: "data in the cache is never stale", because there is no path by which the store changes without the cache changing. Its price is two trips on every write - and AWS makes the honest observation that this is usually the right way round, since "end users are generally more tolerant of latency when updating data than when retrieving data".

The two disadvantages are less obvious and both are about what ends up in memory. A new cache node is empty, and write-through only fills entries that are written, so data that is read but never updated stays missing until somebody writes it - which AWS's guidance fixes by running lazy loading alongside. And most rows are never read at all, so a pure write-through cache spends memory on answers nobody wants, which AWS calls cache churn and fixes with a lifetime on every entry.

Delete-on-write, and why removal beats replacement

The variant most large systems actually run is not to update the entry but to remove it, leaving the next reader to refill it through the ordinary cache-aside path. Facebook's memcache paper gives the reason in one sentence: "We choose to delete cached data instead of updating it because deletes are idempotent." That is a distributed-systems argument rather than a style preference. A delete can be sent twice, arrive late, arrive out of order with another delete, or be retried after a timeout, and every one of those still leaves the entry absent - which is a state the read path already handles perfectly. An update has none of those properties: two updates that arrive in the wrong order leave the older value in place, permanently.

Write-back, and the durability it quietly borrows

Write-back - write-behind in Microsoft's vocabulary, where the caching system "automatically writes any changes made to cached data back to the data store" - acknowledges the write as soon as the cache holds it, and flushes to the store later. It is the fastest write available and the only one of the four that moves the authoritative copy, because between the acknowledgement and the flush the true value of that row exists in exactly one place: the cache.

The reason that is worse than it sounds is that a cache is usually configured to throw things away. Redis under a maxmemory limit with allkeys-lru will "evict any key" when the limit is reached, and it has no way to know that one of them is a write nobody has flushed. So the loss does not require a crash; it requires memory pressure, which is a condition you deliberately arranged. Write-back is a real pattern with real uses - metrics counters, view tallies, anything where losing a few seconds of increments is genuinely acceptable - and it is a pattern to reach for by name, having said out loud what you are willing to lose.

3. The trade-off: pick the pattern per key family, not per service

None of the four is a default, and choosing one for a whole service is how a system ends up with the wrong one everywhere. The choice is per key family and it follows from two facts about that family: how bad a stale read is, and how expensive a refill is. A rarely-written, expensively-computed aggregate wants write-through, because the refill is the thing you were avoiding. A frequently-written row read by one user wants delete-on-write, because the refill is one indexed query and the removal is the cheapest correct thing you can do. A write-heavy counter that nobody bills from wants write-back, having stated the loss budget.

The pattern that should never be chosen by default is write-around with no lifetime, which is what a service has when somebody added a cache and nobody added anything to the write path. It is the one combination with an unbounded staleness window, and it is common because it is what you get by writing no code at all.

Every pattern on this page has a gap between the two steps, and the correct ordering narrows that gap without closing it. A reader that misses, queries the store, and is then descheduled before writing its result back can put a value into the cache after a later write has already removed it - and no ordering of the writer's two steps prevents that, because the offending write came from a read. Lesson 0904 is that race in full, and the reason a lifetime on every entry is not a lazy substitute for invalidation but the backstop that makes invalidation survivable.

Check yourself

Retrieval practice

Answer from memory before revealing.

Why does a write path delete the cached entry rather than overwrite it?
Idempotence is the property being bought: repeated, delayed and reordered deletes all end in the same state, and the read path already handles absence. The first option is a real but tiny effect and not the reason; the second is false, since a delete is as losable as any other message, which is why lifetimes exist; and the fourth is wrong because a delete only guarantees the next reader refills, not that every reader has stopped holding an old copy.
Under write-back, what destroys an acknowledged write besides a crash?
A policy such as allkeys-lru is documented to evict any key at the memory limit, and it cannot tell an unflushed write from a cached read. Expiry is a near miss and worth separating: an entry written by write-back is normally given no lifetime for exactly this reason. A refill would overwrite the pending value with the stale stored one, which is a different bug, and a rejected flush at least produces an error somewhere.
