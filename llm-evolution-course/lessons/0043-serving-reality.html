Serving reality: the cache, and what it costs

Generating a token requires re-reading everything the model has already seen, so serving is a memory problem before it is an arithmetic problem, and most of the engineering since 2022 is about that memory.

Settled Accurate as of 21 August 2026. Interpretation is stable. Corrected by appending, never rewritten to fit a new event.
Where this lesson starts

Most of this course is about training a model. This one is about the other half of the bill, which is paid every time anyone uses it. It assumes you know what attention computes.

1. Where this lesson sits

What you need first

  • The Transformer: what dropping recurrence unlocked Delete the recurrence and keep only attention, and every position in a sentence can be computed at the same time with a constant number of operations between any two words.

The one tight idea

Generating a token requires re-reading everything the model has already seen, so serving is a memory problem before it is an arithmetic problem, and most of the engineering since 2022 is about that memory.

2. Training reads. Serving writes.

A language model is trained on text that already exists. Every position of a training example is known before the run starts, so the whole example can be pushed through the network at once and every position scored in the same pass. That is exactly what the 2017 architecture bought: The Transformer: what dropping recurrence unlocked describes deleting the recurrence so that positions no longer have to be visited one after another.

Serving is the opposite situation, and the difference is not a detail. The model is asked for text that does not exist yet. The token in position 51 cannot be computed until the token in position 50 has been chosen, because that token is part of the input that decides what comes next. Generation is therefore strictly one step at a time, however many chips you own. Buying more hardware makes each step faster and does not make the steps fewer.

So one set of weights is really being used by two different machines. The first, usually called prefill, reads the prompt. Every position of the prompt is already known, so it goes through in one pass, and it is a lot of arithmetic done all at once. The second, usually called decode, writes the answer. It runs once per token produced, and each run touches the whole model to produce a single number's worth of decision. Almost everything surprising about what serving costs follows from the fact that these two phases have opposite shapes.

3. What the cache holds, and how fast it grows

Consider the naive way to generate the fifty-first token: take the prompt plus the fifty tokens already written, and run the whole thing through the model again. It works, and it repeats almost all of the previous step's arithmetic. Over a long answer the waste grows with the square of the length.

The escape is a property of attention itself. In an attention step every position produces three things: a query saying what it is looking for, a key advertising what it holds, and a value it hands over when chosen (query, key and value in the glossary). When a new token arrives, the keys and values of all the earlier tokens do not change. They were computed from text that is already fixed. So compute them once and keep them.

That store is the key-value cache, and it holds one key vector and one value vector for every token the model has seen, at every layer of the stack. Nothing about it is clever. It is a straightforward trade of memory for arithmetic, and it is the single most consequential engineering decision in how these models are served.

The size is worth doing in full, because a cache figure quoted without its configuration means nothing. The PagedAttention paper works the arithmetic for the 13-billion-parameter OPT model, which has 40 layers and a hidden size of 5,120, stored at two bytes per number: two vectors, times 5,120 numbers, times 40 layers, times 2 bytes, is 800 kilobytes for a single token. That model generates sequences of up to 2,048 tokens, so one request can hold 1.6 gigabytes of cache.

Run the same arithmetic on GPT-3, whose configuration is published in its own paper: 96 layers, a hidden size of 12,288, and the same 2,048-token window. Two vectors, times 12,288, times 96, times 2 bytes, is about 4.7 megabytes per token, and a full window is about 9.7 gigabytes. That number is arithmetic done here from the paper's stated configuration rather than a figure the paper quotes, and it assumes the plain multi-head arrangement that model used.

The important part is not the size but the ownership. The weights are shared: every user of a server reads the same parameters. The cache is not shared. Each conversation in flight owns its own, and it grows for as long as that conversation continues. A server's capacity is therefore not "how big is the model" but "how many caches fit beside the model", which is why a machine that comfortably holds a model can still only serve a handful of long conversations at once.

4. The bill is bytes moved, not sums performed

The intuition most readers arrive with is that a large model is expensive because it does an enormous amount of arithmetic. During prefill that is true. During decode it is misleading, and the reason is a fact about hardware rather than about models.

To produce one token, the accelerator must read every parameter it will use out of its main memory, and read the whole cache as well, in order to perform roughly two arithmetic operations per parameter. That is a very small amount of work per byte fetched. The FlashAttention paper states the hardware situation plainly for the A100 generation: 40 to 80 gigabytes of high-bandwidth memory running at 1.5 to 2.0 terabytes per second, against a small on-chip scratchpad estimated at around 19 terabytes per second, and it observes that as compute has grown faster relative to memory, most operations in these models are bottlenecked by memory accesses rather than by arithmetic.

The multi-query attention paper had made the same diagnosis three years earlier and named the culprit directly: incremental inference is slow because of the memory-bandwidth cost of repeatedly loading the large key and value tensors. Once you accept that, the shape of every fix that follows becomes predictable. If the limit is bytes moved, then the useful moves are to store fewer bytes, to waste fewer of the bytes you store, to avoid writing intermediate bytes at all, or to get more than one token out of a single sweep through memory.

5. Four families of fix

Each family attacks a different term, which is why real systems use all four at once rather than choosing between them.

Store fewer bytes per token

Noam Shazeer's 2019 multi-query attention proposed sharing a single key and value across all of the attention heads instead of giving each head its own, which shrinks the stored tensors by the number of heads and, the paper reports, costs only minor quality degradation. Grouped-query attention in 2023 took the middle position: more than one key-value head, fewer than the number of query heads, and, importantly for adoption, a recipe for converting an existing trained model rather than training a new one, using about five per cent of the original pre-training compute. DeepSeek-V2 in 2024 went further and compressed the keys and values into a smaller learned latent vector, reporting a 93.3 per cent reduction in cache size against its own previous model. The papers course covers multi-query attention and the grouped compromise in full.

Waste fewer of the bytes you store

Until 2023 serving systems reserved one contiguous block of memory per request, sized for the longest answer that request might produce. Most answers are shorter than that, so most of the block sat empty, and the leftovers between blocks were too small to be usable. The PagedAttention authors measured the result: only 20.4 to 38.2 per cent of the cache memory in the systems they profiled was holding actual token states. Their fix borrows virtual memory from operating systems, storing the cache in fixed-size pages that need not be adjacent, so a request grows a page at a time and two requests that share a prompt can share its pages. Their system, vLLM, reported two to four times the throughput of the systems it was compared against at the same latency.

Never write the intermediate bytes

A plain attention implementation builds the full square of scores in memory before turning it into weights. FlashAttention, in 2022, reorganised the computation so that the square is processed in tiles inside the chip's small fast scratchpad and never written out to main memory at all. It is worth being precise about what this is and is not: it computes exactly the same answer as before, so it is not an approximation, and its gain is entirely in memory traffic.

Get more than one token per sweep

Speculative decoding, published in November 2022, uses a small cheap model to guess the next several tokens, then runs the large model once over all of the guesses in parallel to check them. Every guess the large model would have made anyway is kept, and the first disagreement is corrected. A careful sampling rule makes the output distribution provably identical to what the large model alone would have produced, and the authors measured two to three times the speed on T5-XXL with unchanged outputs. This is the family that exploits the bandwidth diagnosis most directly: one sweep through the weights was going to happen regardless, so it may as well settle several tokens. The papers course treats it in full.

6. What this does to the price of a product

Two consequences follow directly, and both shape what gets built.

The first is that the cost of a request is not a property of the request. It is a property of the request plus everything already in the conversation. Prefill grows with how much text you send, and each decoded token has to re-read a cache that is larger than it was for the previous token. A long chat therefore gets more expensive per token as it goes on, and the pricing of these products is arranged around that fact. Reading a prefix whose cache entries already exist is dramatically cheaper than computing them: Anthropic's developer documentation, read on 22 August 2026, prices a cache read at a tenth of the ordinary input-token price, and a cache write at 1.25 times it for a five-minute entry or twice it for a one-hour one. Those three multipliers are this whole lesson expressed as a price list. Prompt caching is a billed product feature rather than an internal optimisation, because what it saves is exactly the prefill work described above.

The second is that the shape of a product decides its bill. A single question and a short answer is cheap. A system that loops, re-reading a growing transcript on every iteration, is the most expensive shape there is, and Why agents are a systems problem is where this course takes up what that does to building one.

This is also why the industry did not simply keep making context windows longer and stop there. A longer window is a larger cache, a larger cache is more bytes per token, and more bytes per token is a slower and dearer answer. The work that followed went in two directions: make attention itself selective, which Sparsity moves to attention covers, and manage what goes into the window rather than only enlarging it, which Long context: capacity is not competence covers. Both of them are debts opened by this lesson.

Retrieval practice

Why is generating an answer sequential when training on text is not?
A training example is text that already exists, so every position is known in advance; a generated answer is not, so position 51 has to wait for position 50.
What does the key-value cache actually store?
Earlier tokens are fixed text, so their keys and values never change, and storing them is what stops each new token re-running the whole sequence.
During decode, what usually limits how fast a token can be produced?
Each generated token does about two operations per parameter fetched, which is very little work per byte moved, so memory bandwidth binds before arithmetic does.
Why does a long conversation get more expensive per token as it continues?
The cache is per conversation and only grows, so the bytes moved for each successive token grow with it, which is exactly what shapes the pricing of these products.
