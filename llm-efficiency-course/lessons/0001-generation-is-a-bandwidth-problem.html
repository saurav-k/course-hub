Generating a token is a memory-bandwidth problem, not a compute problem

foundation 9 min The physics every later page prices its trade-offs in. · Serve LLMs with vLLM (Spark playbook)

The one-minute version

  • Generation has two phases: prefill reads your whole prompt once (compute-heavy) and decode emits tokens one at a time (memory-bound).
  • Each decoded token requires reading essentially every active weight from memory - the whole network takes one walk per token.
  • So the ceiling token rate is bandwidth ÷ bytes per token, and FLOPs sit mostly idle behind it.
  • Batching shares one weight-walk across many requests, which is why aggregate throughput rises with concurrency while every individual stream slows.

1. Two phases, two bottlenecks

When you press enter on a prompt, the server does two different jobs. Prefill reads your entire prompt through the network at once - every token in parallel - to fill the KV cache. That is matrix-multiply territory: compute-bound, and on any modern accelerator it finishes fast. Decode then emits your answer one token at a time, and each token must pass through every active layer of the network before the next one can start.

Here is the part that surprises people. To produce decode step t+1, the hardware must read essentially every active weight again. The previous step's weights are already in registers and caches, but they produced a different token; the matrix multiplications for this step need the numbers again, from memory. Compute is cheap relative to that walk: one token costs roughly two FLOPs per active parameter - for an 18B-active model, about 36 GFLOPs - which even a modest GPU finishes in microseconds. Reading the weights it multiplies costs milliseconds on desk bandwidth.

2. The ceiling, and what shares it

Divide bandwidth by bytes per token and you get the ceiling rate. At 8-bit storage, an 18B-active model must read about 18 GB per token: 273 ÷ 18 ≈ 15 tokens per second ideal, realistically nearer 10 once attention, the router, and cache traffic take their share. That single division is the most important line in this course.

Concurrency behaves the way it does because of this walk. Serve six requests at once and the server still reads the weights once per step - the walk is shared - so aggregate throughput rises even as each individual stream waits its turn. But the KV caches grow with every concurrent session, eating the capacity that was going to hold experts, and each stream's latency climbs. On desk hardware the useful concurrency is small, and Lesson 09 budgets it explicitly.

The key insight Every optimisation in this course is a sentence about that division: make bytes per token smaller (quantization), make some steps read nothing new (speculative decoding), or accept slower streams for more aggregate work (batching). Nothing else moves the number.

Check yourself

Retrieval practice

Answer from memory before revealing.

Your model streams at 8 tokens per second solo. Six colleagues each start their own session on the same server. What happens?
The weight walk is shared, so aggregate rises with concurrency - but the walk plus six KV caches must all fit in the same bandwidth, so each stream gets less. Rejection and aggregate collapse do not happen until memory runs out.
Doubling the prompt from 2,000 to 4,000 tokens most affects which phase?
Prefill scales with prompt length; the decode loop's per-step cost does not care how long the prompt was. Prompts are not free - they are just paid in a compute-bound phase, and only once.

Practice about 10 minutes, with paper

Practice 1foundation

GLM-5.3-Flash has 18 billion active parameters. At 4-bit storage with overhead, budget half a byte per parameter.

Find the ideal ceiling rate on a 273 GB/s Spark, and compare it with the 8-bit ceiling of about 15 tokens per second from the lesson.

Hint

Bytes per token: 18 billion × 0.5 bytes. Then divide 273 by that.

Show the worked solution
  1. Bytes per token. 18 × 109 × 0.5 = 9 GB per token.
  2. Ceiling. 273 ÷ 9 ≈ 30 tokens per second ideal - double the 8-bit ceiling.
  3. Reading it. Halving the bytes per weight doubles the speed ceiling. This is why quantization, next module, is a throughput lever and not only a storage lever.

Sanity check. Halving bytes per token must double the rate; 30 is twice 15.
