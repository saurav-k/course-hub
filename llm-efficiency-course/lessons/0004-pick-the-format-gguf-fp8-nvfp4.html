The quantization format you pick decides which machines can run the model

working 10 min GGUF, FP8, and NVFP4 as shipping formats with hardware opinions. · GLM-5.3-Flash vLLM recipe

The one-minute version

  • A format is Lesson 03's arithmetic made into a product: bit layout, grouping, and the hardware it expects.
  • GGUF runs anywhere llama.cpp runs - CPU included - at the cost of hand-tuned integer kernels rather than native low-precision matrix units.
  • FP8 is the vendor-native 8-bit floating format on Hopper-class and newer NVIDIA silicon; NVFP4 is Blackwell's native 4-bit floating format.
  • The rule: the format must be native to your silicon, and its file must leave room for KV cache on top of the weights.

1. The three formats as products

GGUF is the llama.cpp ecosystem's container: a single file holding weights in a choice of quantization schemes, plus the tokenizer and metadata (llama.cpp). Its superpower is reach - the same file runs on a laptop CPU, a Mac, or a CUDA GPU - because its integer kernels are hand-tuned per architecture. Its compromise is speed at the frontier: integer simulation of 4-bit multiply is slower than hardware that multiplies 4-bit natively.

FP8 is an 8-bit floating format with real exponent bits, so it keeps dynamic range in a way 8-bit integers cannot. NVIDIA Hopper-class GPUs and newer execute FP8 matrix multiplies natively; the official GLM-5.3-Flash checkpoint ships in FP8, about 306 GiB (vLLM recipe). That is the canonical quality reference the other formats are traded against.

NVFP4 is Blackwell's 4-bit floating format: a floating layout per Lesson 03, fine grouping, and hardware units that multiply it directly. It roughly halves the FP8 file - about 160 GiB derived for this model - and doubles the bandwidth ceiling from Lesson 01. It exists on exactly the chips this course cares about: the GB10 in a DGX Spark. Community NVFP4 checkpoints of the model appeared within a day of release, which tells you the ecosystem treats Blackwell as the desk platform of record.

2. The decision rule

Ask two questions in order. Does your silicon multiply it natively? NVFP4 without Blackwell means emulation, which surrenders the speed advantage and sometimes correctness support; FP8 without Hopper-class hardware likewise. Does the file leave KV room? A 256 GB pool holding a 160 GiB file has roughly 90 GB left for the KV cache, runtime buffers, and the operating system's share of unified memory - Lesson 09 budgets that remainder precisely. If either answer is no, step down or across the format ladder: a GGUF that runs beats a native format that does not fit, and an FP8 file that pages from disk loses to everything.

3. What it costs

Format choices price three things at once: quality relative to FP8, speed on your silicon, and reach across your machines. GGUF maximises reach and sacrifices frontier speed; NVFP4 maximises speed and fit on Blackwell and sacrifices reach entirely; FP8 is the quality anchor that most desk memory cannot hold for this model. Release velocity is also real: the model shipped FP8 first, and lower-bit formats followed within hours from community quantizers - so for a brand-new model, the newest format is also the least battle-tested. Budget a validation pass on your own workload before committing a fleet to it.

Check yourself

Retrieval practice

Answer from memory before revealing.

You own a last-generation GPU without FP8 or FP4 units, 24 GB of memory, and you want the biggest model that will actually answer. Which way do you step?
Without native low-precision units the exotic formats lose their speed edge and gain risk; a paged or memory-mapped 306 GiB file is slower than any local model. The honest answer is a model that fits whole.
Why does this course call FP8 the quality reference rather than the target?
FP8 still quantizes - it is 8 bits, not 16 - but it is the format the publisher ships, so the community measures every alternative's quality delta relative to it.

Practice about 10 minutes, with paper

Practice 1working

Your machine has 64 GB of unified memory, of which the OS and runtime realistically claim 8 GB. The model you want has 90 billion total parameters.

Find the minimum bits per weight at which the file fits, ignoring KV cache, then re-answer budgeting 12 GB for KV.

Hint

Usable memory: 56 GB, then 44 GB. Bits per weight ≈ usable bytes ÷ 90 billion, times 8.

Show the worked solution
  1. No KV. 56 GB ÷ 90 billion ≈ 0.62 bytes per weight ≈ 5 bits. A 5-bit or 4-bit quant fits; 8-bit does not.
  2. With 12 GB KV. 44 GB ÷ 90 billion ≈ 0.49 bytes ≈ 4 bits. Now only 4-bit fits, and it is tight.
  3. Reading it. The KV budget is not an afterthought; it can decide the format. Lesson 09 makes this ledger explicit.

Sanity check. Adding a KV budget must push the minimum bits per weight down, and it does: 5 to 4.
