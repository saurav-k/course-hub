Module 03 · Steering a Frozen Model · Lesson 07

LoRA is one point in a family of cheap adapters - pick by where you inject

frontier 11 min The parameter-efficient family, ranked by what each one trains and where. · LoRA (Hu et al., 2021)

The one-minute version

  • Every parameter-efficient method answers the same question differently: what is the smallest thing I can train that still changes the output?
  • Prompt and prefix tuning train virtual tokens; IA3 trains per-channel scales; LoRA and DoRA train low-rank matrix updates.
  • DoRA keeps LoRA's shape but decomposes the update into direction and magnitude, closing part of the quality gap to full fine-tuning.
  • When training ends you choose: keep the adapter hot-swappable, or merge it into the weights and pay nothing at inference.

1. The family, by what it trains

Prompt tuning prepends a handful of trainable virtual tokens and trains nothing else. The adapter is kilobytes, serving cost is a slightly longer sequence, and capacity is the lowest in the family - it nudges an already-capable model, it does not teach skills. Prefix tuning generalises it: trainable key-value prefixes inside every attention layer, so the injection point moves from the input to every depth. More capacity, more memory per layer, still no weight-matrix change.

IA3 trains one learned rescaling vector per channel inside attention and feed-forward blocks - reweighting existing computations rather than adding new ones. It is smaller than LoRA and sometimes sharper for narrow tasks, at the cost of expressive range. DoRA stays inside LoRA's shape but decomposes the weight update into a direction component and a magnitude component, training them separately; its published results sit measurably closer to full fine-tuning than plain LoRA at the same rank, for a little more training complexity (LoRA lineage). For a desk practitioner the practical reading is: LoRA remains the default; DoRA is the upgrade when quality on held-out examples stalls.

2. Merging: paying nothing at inference

A trained LoRA adapter can ride along at inference - the BA product added to each forward pass - costing a small latency and one more file to manage. Or it can be merged: the product added once into the base weights, after which the model is a single file with the behaviour baked in and zero adapter overhead. The choice is an operational one, and it has a lifecycle:

Merging has one honest caveat from Lesson 03: an adapter trained on a 16-bit view of a 4-bit QLoRA base merges cleanly back into that 4-bit base only approximately, and re-quantization after merging adds a second rounding pass. Merge into the highest-precision copy of the base you keep, then quantize once, deliberately.

3. The selection rule

Start at LoRA rank 16 over query and value projections - the family's proven default - and hold out examples before you train. If quality stalls, climb the ladder in both directions that matter: more rank or wider coverage inside LoRA, or DoRA for a better-shaped update. Step down to IA3 or prompt tuning only when you need many tiny behaviours over one shared base and can tolerate their ceilings. Never choose by parameter count alone: the family differs by capacity, and capacity is decided by your measurement, not by megabytes.

Check yourself

Retrieval practice

Answer from memory before revealing.

You want many task behaviours, each switchable per request, over one deployed base model. Merge or stay hot?
Merging bakes one behaviour per file; many behaviours want the hot path, paying its small latency tax per request. This is exactly the lifecycle fork from the page.
What is DoRA's change to LoRA, in one sentence?
DoRA keeps LoRA's two-thin-matrices shape and factors the update into orientation and scale, which is why its quality sits closer to full fine-tuning at equal rank.

Practice about 10 minutes, with paper

Practice 1frontier

You serve one 70B base to four teams. Each team's adapter is LoRA rank 16 over Q and V: 80 layers, two matrix pairs per layer, matrices 8192 by 8192, 16-bit halves. Merging would need a full extra copy of the base per team: 70B at 4-bit ≈ 38.5 GB each.

Find the memory cost of four hot adapters versus four merged copies, and the decision.

Hint

Adapter per team: 80 × 2 pairs × 2 × 8192 × 16 parameters, times 2 bytes.

Show the worked solution
  1. One adapter. 80 × 2 × 2 × 8192 × 16 × 2 bytes ≈ 168 MB.
  2. Hot path. Four adapters ≈ 0.7 GB over one base.
  3. Merged path. Four base copies ≈ 154 GB - five times the memory for the same four behaviours.

Sanity check. Shared-base serving must win when behaviours outnumber bases, and 0.7 against 154 GB is the whole argument.
