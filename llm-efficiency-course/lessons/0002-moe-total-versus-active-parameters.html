Module 01 · The Wall · Lesson 02

A 320B MoE reads like an 18B model but loads like a 320B one

working 10 min Total versus active parameters, and why mixture-of-experts changes both sides of the ledger. · GLM-5.3-Flash model card

The one-minute version

  • A mixture-of-experts model holds many expert networks but routes each token through only a few of them.
  • Total parameters decide what must be stored in memory; active parameters decide what must be read per token.
  • GLM-5.3-Flash: 320B total, 18B active - 8 of 288 experts per token - so it speeds like a small dense model but loads like a giant.
  • The catch is capacity: all 288 experts must be resident, even though each token visits eight. Desk deployment is a capacity fight, and Lessons 03 and 04 are the weapons.

1. Two ledgers, one model

Keep Lesson 01's division in hand: rate equals bandwidth divided by bytes per token. For a dense model, total and active parameters are the same number, so the model that knows the most is also the model that reads the most - capability and speed are welded together. Mixture-of-experts cuts the weld.

A MoE layer holds a set of expert feed-forward networks and a small router. For each token, the router scores all experts and sends the token down the top few - for GLM-5.3-Flash, 8 of 288 experts, across 45 layers, with the attention layers shared by every token (model card). The two ledgers diverge:

bytes stored = total params × bytes per weight   ·   bytes read per token ≈ active params × bytes per weight Read as: storage is decided by every parameter in the file - all experts, whether or not this token visits them. per-token reading is decided only by the parameters this token actually touches - its 8 experts per layer plus the shared attention.

GLM-5.3-Flash: 320 billion total, 18 billion active. At 8-bit storage the file is about 306 GiB - derived, matching the vLLM recipe's figure (vLLM recipe) - but each token reads roughly 18 GB. The model is a giant on disk and a mid-sized network in motion.

2. What the router costs and saves

The router itself is tiny, but routing is not free in a subtler way: which experts a token visits depends on the token, so batching six requests together reads different experts for each - the walk is less shareable than a dense model's. MoE models still batch well because expert choices cluster, but the clean Lesson 01 picture of "one walk, shared six ways" gets fuzzier.

What MoE buys is the capability-speed weld cut. A dense 320B at 8-bit would read 320 GB per token: about one token per second even ideally on a Spark. The MoE reads 18 GB: fifteen. Same file, same knowledge, twenty times faster - bought entirely with storage you must be able to afford.

The capacity trap: every desk-fit failure for this model is a storage failure, not a speed failure. Two Sparks pool 256 GB; at 8-bit the file alone is ~306 GiB, so it does not fit - no serving-time cleverness fixes that. Shrinking storage is the next module's subject, and it is mandatory, not optional.

Check yourself

Retrieval practice

Answer from memory before revealing.

A dense 320B model at 8-bit and GLM-5.3-Flash at 8-bit have nearly identical file sizes. Why do their speeds differ by roughly twenty times?
Same file, different walk: 320 GB per token versus about 18 GB. No extra compression and no caching are involved - the routing itself decides what gets read.
Your Spark cluster reports the model loaded fine but produces barely one token per second. Which ledger did you get wrong?
One-token-per-second symptoms mean the per-token walk is reading from storage, not memory: a capacity failure. The router reads only 8 experts by construction.

Practice about 10 minutes, with paper

Practice 1working

A MoE has 120 billion total parameters, 12 layers, and routes each token through 4 of 64 experts per layer. Attention parameters total 3 billion and are active for every token; the other 117 billion are expert parameters spread evenly.

Find the active parameters per token.

Hint

Experts per layer: 117 ÷ 12 ≈ 9.75 billion. The token visits 4 of 64 of them per layer.

Show the worked solution
  1. Experts per layer. 117 billion ÷ 12 layers ≈ 9.75 billion per layer.
  2. Active expert parameters. 9.75 × (4 ÷ 64) ≈ 0.61 billion per layer; × 12 ≈ 7.3 billion.
  3. Total active. 7.3 + 3 = about 10.3 billion active per token.

Sanity check. Active must sit far below total (10 of 120) and above the attention floor (3 billion), as it does.
