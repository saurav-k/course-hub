Module 01 · The Wall · Lesson 00

Three levers decide whether a frontier model fits on your desk

foundation 8 min The on-ramp: the hardware, the model, and the three ideas the other ten pages develop. · GLM-5.3-Flash model card

The one-minute version

  • Running a big open model locally used to mean a server rack, because weights are huge and generation is slow for a reason most people misdiagnose.
  • The reason is memory bandwidth, not compute - and bandwidth, not FLOPs, is what desk hardware lacks.
  • Three levers answer it: shrink the weights (quantization), steer behaviour without unfreezing (LoRA/QLoRA), and speculate several tokens per step (speculative decoding).
  • Each lever has a bill: quality, a training-run cost, or wasted compute. This course teaches you to price all three.

1. The machine on your desk, stated honestly

The course follows two concrete machines. The first is a pair of NVIDIA DGX Spark units: each carries a GB10 Grace Blackwell chip, 128 GB of unified memory shared between CPU and GPU, and a memory bandwidth of 273 GB/s (NVIDIA DGX Spark). A two-hundred-gigabit ConnectX-7 port lets one cable join the pair into a single 256 GB pool (Connect Two Sparks). The second is a Mac Studio with 256 GB of unified memory, in the roughly 800 GB/s bandwidth class of the Apple-silicon Ultra chips (Apple M2 Ultra, 800 GB/s).

The model they run is GLM-5.3-Flash, released in August 2026 under the MIT licence: 320 billion total parameters, 18 billion active per token, 45 layers that route each token through 8 of 288 experts, a one-million-token context window, and a built-in multi-token prediction draft layer (model card). It approaches Claude Opus 4.8 on coding and agentic benchmarks, which is why it is the right running example: it is the kind of model you would actually want on a desk.

2. The three levers, named once

Shrink. Quantization stores each weight in fewer bits: from two bytes down to one, or half a byte, or a quarter. Lesson 03 works the arithmetic of what that costs in rounding error, and Lesson 04 turns it into a format decision - GGUF, FP8, or NVFP4 - that decides where a model can physically load.

Steer. Post-training a 320B model the naive way means holding optimizer states for every parameter. LoRA instead freezes the model and learns two small matrices per touched layer; QLoRA keeps the frozen base in 4-bit so the whole undertaking fits in the memory you have. Lessons 05, 06, and 07 cover LoRA, QLoRA, and the wider adapter family including DoRA, IA3, and merging.

Speculate. Decode is bandwidth-bound and your silicon sits mostly idle behind it. Speculative decoding drafts several tokens cheaply and checks them all in one weight-reading pass. On desk hardware, where the gap between bandwidth and compute is widest, this is the lever that multiplies. Lesson 08 derives its formula, including the multi-token prediction layer GLM-5.3-Flash ships with.

3. How the course teaches

Every page earns its idea with arithmetic you can redo on paper: a model's footprint from parameter count and bytes per weight, a token rate from bandwidth divided by bytes per token, an adapter's size from two matrix ranks. Numbers derived in this course are labelled as derivations, because no published benchmark of this exact model on this exact hardware existed when the course was written - the resources file lists exactly what would settle each open number.

The order is load-bearing. The wall comes first because every later trade-off is priced in bandwidth. Quantization precedes QLoRA because QLoRA is quantization plus adapters. Speculation comes last because its payoff is largest exactly when the wall from Lesson 01 is strictest. The two case studies reuse every page before them; nothing in a case study is new machinery.

Check yourself

Retrieval practice

Answer from memory before revealing.

A DGX Spark has 128 GB of memory but only 273 GB/s of bandwidth. Which limit does that bandwidth number actually gate?
Bandwidth gates the reading rate, which is what decode does constantly. Loading a model is gated by capacity (128 GB); the context window is a software configuration; the CPU clock is a different subsystem entirely.
Why does this course treat the two case-study machines as a pair rather than picking a winner?
Two Sparks buy 256 GB of pooled capacity over a 200 GbE link at 273 GB/s per node; the Mac keeps all 256 GB local at a higher bandwidth. The final lesson prices both and lets your workload decide.

Practice about 10 minutes, with paper

Practice 1foundation

A hypothetical model has 10 billion active parameters per token, and at 8-bit storage each parameter occupies one byte. Generating one token requires reading every active parameter once.

rate ≈ bandwidth ÷ bytes per token Read as: the ceiling token rate equals the memory bandwidth divided by the bytes that must be read to produce one token. bandwidth: 273 GB/s on a Spark. bytes per token: active parameters times bytes per parameter, here 10 billion × 1.

Find the ideal ceiling rate on a Spark, then judge how a realistic rate of about a third of that ceiling would feel for interactive coding.

Hint

Divide 273 by 10. Keep the units honest: gigabytes per second divided by gigabytes per token gives tokens per second.

Show the worked solution
  1. Bytes per token. 10 × 109 parameters × 1 byte = 10 GB per token.
  2. Ceiling rate. 273 GB/s ÷ 10 GB/token = 27.3 tokens per second, ideal.
  3. Realistic. About a third of the ceiling - say 9-10 tokens per second - after overheads later lessons itemise. Comfortable to watch, sluggish for a chatty agent.

Sanity check. The ceiling must exceed the realistic figure, and both must fall as bytes per token rise - which is exactly the lever Lesson 03 pulls.
