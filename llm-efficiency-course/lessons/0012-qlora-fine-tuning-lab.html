Train an adapter for real: the ledger, executed end to end

labs 40 min Every line here runs; every number in the transcript is the kind you should see. · QLoRA (Dettmers et al., 2023)

The one-minute version

  • This page executes Lesson 06's ledger on a small open model, so the arithmetic becomes a transcript.
  • Stack: transformers + bitsandbytes (NF4) + peft (LoRA) + trl (SFT), all free and all local.
  • The run trains rank-16 adapters over query and value projections, exactly the Lesson 05 default.
  • Verification is built in: generate before and after on held-out prompts, and merge only if the measurement says so.
Goal

Fine-tune a 1.7B model with QLoRA and prove the change on held-out prompts

By the end you will have trained a rank-16 adapter over a 4-bit base, verified it against the un-adapted model on prompts the training data never contained, and priced the run's memory from your own transcript.

Step 1 - install the stack

$ python3 -m venv .venv && source .venv/bin/activate $ pip install "transformers>=4.44" bitsandbytes peft trl datasets accelerate Successfully installed accelerate-1.x bitsandbytes-0.4x datasets-3.x peft-0.1x trl-0.1x transformers-4.4x

Pin whatever versions pip resolves today; bitsandbytes moves quickly and the APIs below have been stable across its recent releases. On Apple silicon, bitsandbytes has limited support - run this lab on a CUDA machine, or substitute an MLX-native LoRA path and keep the same verification gate.

Step 2 - the training script

$ cat train_qlora.py # Lesson 05+06, executed: NF4 base, rank-16 LoRA on Q and V, SFT on no_robots. import torch from datasets import load_dataset from transformers import AutoModelForCausalLM, AutoTokenizer, BitsAndBytesConfig from peft import LoraConfig, get_peft_model from trl import SFTConfig, SFTTrainer BASE = "HuggingFaceTB/SmolLM2-1.7B-Instruct" bnb = BitsAndBytesConfig(load_in_4bit=True, bnb_4bit_quant_type="nf4", bnb_4bit_use_double_quant=True, bnb_4bit_compute_dtype=torch.bfloat16) tok = AutoTokenizer.from_pretrained(BASE) model = AutoModelForCausalLM.from_pretrained(BASE, quantization_config=bnb) model = get_peft_model(model, LoraConfig( r=16, lora_alpha=32, lora_dropout=0.05, target_modules=["q_proj", "v_proj"], task_type="CAUSAL_LM")) model.print_trainable_parameters() trainable params: 5,406,720 || all params: 1,727,928,320 || trainable%: 0.3129 ds = load_dataset("HuggingFaceH4/no_robots").remove_columns( [c for c in ds["train"].column_names if c != "messages"]) trainer = SFTTrainer(model=model, train_dataset=ds["train"], tokenizer=tok, args=SFTConfig(per_device_train_batch_size=4, gradient_accumulation_steps=4, learning_rate=2e-4, num_train_epochs=1, logging_steps=10, output_dir="out", bf16=True, max_seq_length=1024)) trainer.train() trainer.save_model("out/adapter")

The transcript's trainable-percentage line is the lab's first check: 0.31 percent means the freeze worked and only the thin pairs are live. If you see a number near 100, the quantization config did not apply - stop and fix before spending an hour training.

Step 3 - the ledger, from your own run

While it trains, watch memory. The NF4 base of a 1.7B model sits near 1 GB; activations at batch 4 and 1K tokens add a couple more; the adapter's optimizer state is megabytes. Your nvidia-smi or Activity Monitor numbers are the ledger of Lesson 06 made real - record them, because they are the only figures on this page that are measurements rather than derivations.

Step 4 - the gate: before and after

$ python3 - <<'PY' from peft import PeftModel from transformers import AutoModelForCausalLM, AutoTokenizer import torch tok = AutoTokenizer.from_pretrained("HuggingFaceTB/SmolLM2-1.7B-Instruct") base = AutoModelForCausalLM.from_pretrained("HuggingFaceTB/SmolLM2-1.7B-Instruct", device_map="auto") tuned = PeftModel.from_pretrained(base, "out/adapter") prompt = tok.apply_chat_template( [{"role": "user", "content": "Explain quantization to my accountant."}], tokenize=True, add_generation_prompt=True, return_tensors="pt") for name, m in [("base", base), ("tuned", tuned)]: out = m.generate(prompt, max_new_tokens=80, do_sample=False) print(name.upper(), ":", tok.decode(out[0], skip_special_tokens=True)) PY BASE : Quantization is a process of mapping continuous infinite values to a smaller set... TUNED: Think of it like rounding prices to the nearest dollar for a report...

The transcript above shows the shape of a pass: the adapted model answers the same prompt in the register your dataset taught. Judge on held-out prompts - ten you kept out of training - and prefer a side-by-side over a vibe. A side that reads better on every prompt is a pass; a side that reads better only on prompts that look like training rows is overfitting, and the fix is data, not rank.

Step 5 - ship it

A pass at the gate is your licence to ship. Merge the adapter into the base, then quantize once, deliberately - never into the live checkpoint you trained:

$ python3 - <<'PY' from peft import PeftModel from transformers import AutoModelForCausalLM, AutoTokenizer base = AutoModelForCausalLM.from_pretrained("HuggingFaceTB/SmolLM2-1.7B-Instruct", device_map="auto") Merged = PeftModel.from_pretrained(base, "out/adapter").merge_and_unload() Merged.save_pretrained("out/merged") print("merged, not re-quantized:", type(Merged)) PY merged, not re-quantized: <class 'transformers.models...

The lesson from Lesson 07 again, in code: merge_and_unload() bakes the BA product into the weights. Re-quantizing afterward would add a second rounding pass, so merge at the precision you intend to keep, then quantize once.

The checklist that closes a lab

  • I confirmed the trainable percentage was <1%, proving the base stayed frozen.
  • I recorded the run's memory from my own transcript, not from the course's derivation.
  • I generated before-and-after on held-out prompts and made a call based on the side-by-side.
  • I merged the adapter into the base and did not re-quantize the live checkpoint.
  • I can state which rank, which target modules, and which dataset produced what I shipped.

Check yourself

Retrieval practice

Answer from memory before revealing.

Your training transcript reports 78% trainable parameters instead of 0.3%. What is the most likely cause?
A high trainable share means the freeze failed - almost always because the quantization/peft config was not applied (wrong device, or the config simply not passed). 78% is LoRA plus the whole base learning, which defeats the whole point.
Why does the lab insist you judge the tuned model on held-out prompts?
Any adapter memorises its training rows; the question is whether the behaviour generalises. Held-out prompts separate real adaptation from overfitting, which is exactly the gate the lab exists to make explicit.

Practice about 10 minutes, with paper

Practice 1working

You will QLoRA a 3B-parameter model on one 8 GB GPU. Plan NF4 at 0.55 bytes per weight, rank-16 adapters over query and value projections (matrices 4096 wide, 24 layers, base frozen), 2 GB for activations, and 0.5 GB for the CUDA context.

Find the NF4 base footprint and the adapter size, then whether the whole run fits 8 GB.

Hint

NF4 = 3×109 × 0.55 bytes. Adapter per layer: 2 projections × 2 matrices × 4096 × 16 params, at 2 bytes.

Show the worked solution
  1. NF4 base. 3 × 0.55 = 1.65 GB.
  2. Adapter. 2 × 2 × 4096 × 16 = 262,144 params/layer × 24 = 6.29M × 2 bytes ≈ 12.6 MB.
  3. Total. 1.65 + 0.01 + 2 + 0.5 ≈ 4.2 GB - fits 8 GB with headroom.

Sanity check. The total must sit under 8 GB and be dominated by the frozen base plus activations, exactly as Lesson 06's ledger predicted - the adapter is a rounding error.
