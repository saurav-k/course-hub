PRODUCTION SYSTEMS Syllabus Glossary
Reference · Print-friendly

Glossary

111 terms One definition each. Every term links to the section that develops it, with its real-world example and its behaviour at 100, 1,000 and 10,000 requests per second.

How to use this

  • Cover the definition column and recall it from the term. Retrieval beats re-reading.
  • Any term you cannot define in one sentence is a term you cannot defend at a whiteboard.
  • Definitions here are deliberately single-meaning. The chapters carry the nuance and the arithmetic.

Chapter 1 · Edge and Traffic Management

10 terms · developed in Chapter 1.

TermDefinition
Rate limitingEnforcing a capacity contract by refusing requests above a sustained refill rate and a burst capacity, usually with a token bucket.
CachingServing a stored answer instead of recomputing it, so that origin load falls to requests multiplied by the miss ratio.
Load balancingChoosing which healthy backend serves each request, trading affinity, work-awareness, and stability under fleet churn against each other.
Reverse proxiesAn intermediary that acts as the origin to the client, buffering and terminating connections so a slow client cannot occupy an application worker.
API gatewaysA reverse proxy given policy duties, centralising authentication, quota metering, routing, and attribution for every client of an API.
CDNA geographically distributed cache fleet plus the request routing that decides which point of presence serves each user.
Edge cachingCaching at the point of presence nearest the user, which buys latency at the cost of a smaller working set and a lower hit ratio per node.
Cache invalidationMaking a cache stop serving a wrong answer, through expiry, conditional validation, or an explicit purge whose throughput you must budget for.
WAFRequest inspection that scores attack patterns cumulatively and blocks above a threshold, trading false positives for coverage of unpatched vulnerabilities.
DDoS protectionDefending bandwidth, CPU, and connection state against exhaustion, starting from the rule that unverified hosts must never cause state to be allocated.

Chapter 2 · Resilience Patterns

10 terms · developed in Chapter 2.

TermDefinition
Circuit breakerA three-state proxy that stops calling a failing dependency once recent failures cross a threshold, so callers fail fast instead of paying the timeout.
TimeoutThe maximum time a caller will wait before abandoning a request, which is a budget allocated down a call chain rather than a number chosen per client.
RetryRe-sending a failed request on the assumption the fault was transient, which multiplies load at every hop that applies its own policy independently.
Exponential backoffDoubling the wait before each successive retry, which only prevents a thundering herd when it is combined with random jitter.
IdempotencyThe property that repeating an operation has the same effect on the server as performing it once, which is the precondition that makes any retry safe.
BackpressureA receiver telling a sender how much work it can accept, so a fast producer cannot force a slow consumer into unbounded buffering.
Health checkAn endpoint an external system polls to decide whether to send traffic to an instance, whose depth determines how many instances fail together.
Liveness and readiness probesTwo separate questions in Kubernetes: liveness decides whether to restart a container, readiness decides whether to send it traffic.
FailoverMoving traffic from a failed resource to a working one, which is a capacity event rather than a routing event once the surviving side inherits the load.
Chaos engineeringDeliberately injecting failure into production within a bounded blast radius to test whether the resilience you designed actually works.

Chapter 3 · Asynchronous and Event-Driven Systems

10 terms · developed in Chapter 3.

TermDefinition
Message queueA durable point-to-point buffer whose lease timer, not the consumer, owns a message until it is explicitly deleted.
Publish and subscribeOne-to-many delivery where each subscription holds its own independent cursor and backlog over the same topic.
Event-driven architectureDesigning services to publish facts about what happened rather than commands about what should happen next.
Distributed transactionAtomic commit across separate data stores, bought with two-phase commit and paid for in blocked participants.
Saga patternA sequence of locally committed steps with a compensating undo for every step before the pivot transaction.
Dead letter queueThe sideline a message is moved to once its receive count exceeds a threshold, isolating poison from traffic.
Cron jobSchedule-triggered work whose specification defines the time fields and deliberately says nothing about reliability.
WebhookA signed HTTP callback from a provider, delivered at least once, retried for days, and never guaranteed in order.
Service discoveryResolving a stable service name to the endpoint set that is reachable right now, trading freshness against query load.
Leader electionA consensus-granted, time-bounded lease making exactly one process responsible for work that must not run twice.

Chapter 4 · Protocols and Real-Time Transport

9 terms · developed in Chapter 4.

TermDefinition
WebSocketsA full-duplex message channel that begins as an HTTP Upgrade handshake and then costs you a held socket, sticky routing, and a reconnect storm on every deploy.
Long PollingA client request the server deliberately holds open until it has news or the timeout expires, which converts request rate into concurrent open requests rather than removing either.
Server-Sent EventsA one-directional UTF-8 text stream from server to client over a never-closed HTTP response, with automatic reconnection and event-id resumption defined by the standard itself.
DNSA hierarchical name-to-address lookup cached everywhere by TTL, which means your failover time is detection time plus TTL and the TTL is only ever a maximum.
TCP vs UDPThe choice between a reliable ordered byte stream that costs per-connection state and head-of-line blocking, and a bare 8-byte datagram header on which you build your own reliability.
HTTP/2 and HTTP/3Multiplexed streams over one connection, where HTTP/2 still inherits TCP's single ordered byte stream and HTTP/3 moves to QUIC so a lost packet stalls only its own stream.
gRPCA calling convention layered on HTTP/2 with schema-defined payloads, deadlines, cancellation, and four streaming shapes, bought at the price of long-lived connections that defeat naive load balancing.
API VersioningThe mechanism that lets you change a published interface while existing callers keep working, whose real cost is operating every version you have ever shipped.
Semantic VersioningA numbering claim about backward compatibility relative to your declared public API, which nothing enforces and which is worthless the first time you break it in a patch.

Chapter 5 · Database Performance

8 terms · developed in Chapter 5.

TermDefinition
Database indexA separate ordered structure, almost always a B-tree, that turns a lookup whose cost grows linearly with table size into one whose cost grows logarithmically.
Query optimizationThe work of getting the planner's cost model to choose the plan you intended, which at scale means valuing plan stability over plan quality.
N+1 queriesAn application pattern that issues one query for a collection and one more per member, converting a single round trip into N+1 serial ones.
Connection poolingLending a bounded set of database connections to requests, sized against concurrency rather than request rate, so an autoscaling fleet cannot multiply its way past the server's connection limit.
Read replicaAn asynchronously updated read-only copy that buys read capacity by spending consistency, which obliges you to decide explicitly which reads may be stale.
Database migrationA versioned change to the shape of the database, judged in production not by correctness but by which lock it takes and for how long it blocks the queue behind it.
Schema versioningTreating the schema as an artifact that must stay compatible with two application versions at once, which makes expand-contract the only safe shape under rolling deploys.
BackupA copy of the data whose only meaningful property is a restore you have actually timed, because an untested backup is a hypothesis rather than a backup.

Chapter 6 · Distributing Data

9 terms · developed in Chapter 6.

TermDefinition
ShardingSplitting one dataset across independent machines by a shard key, which buys write throughput and costs you joins, cross-shard transactions, and the freedom to change the key later.
PartitioningDividing one logical table or topic into disjoint parts by key so the engine can skip the parts that cannot match, whether or not those parts live on different machines.
ReplicationKeeping more than one copy of the same data so a machine loss is not a data loss, priced as a choice between commit latency and the size of the window you can lose.
CAP TheoremThe proof that during a network partition a system cannot be both linearizable and available, and nothing at all about how it behaves when the network is healthy.
Eventual ConsistencyA guarantee that replicas converge once updates stop, which is only useful in production when paired with a session guarantee such as read-your-writes.
Network PartitionsAny condition where one group of nodes cannot exchange messages with another, including packet loss and long pauses, because a node cannot tell a lost message from a slow one.
Clock SkewThe unavoidable disagreement between machine clocks, which makes wall-clock timestamps an unsafe way to order concurrent writes unless the uncertainty is bounded and waited out.
Multi-Region DeploymentsPlacing replicas in separate geographic regions to survive losing one, paid for on every quorum write at a latency floor set by the speed of light in fibre.
Disaster RecoveryThe plan for losing an entire location, measured only by how much data you lose and how long you are down, and worthless until the restore has been rehearsed.

Chapter 7 · Concurrency and Runtime

9 terms · developed in Chapter 7.

TermDefinition
Optimistic lockingDo the work unlocked and let the write fail if the version moved, which is cheapest exactly while conflicts stay below the lock-overhead crossover.
Pessimistic lockingTake exclusive ownership before doing any work, buying certainty at the price of a throughput ceiling of one over the lock hold time.
Distributed locksMutual exclusion across processes that share no clock, which is safe for efficiency but never for correctness unless a fencing token is checked at the resource.
Race conditionsA result that depends on timing the system never ordered, whose probability rises with the per-key write rate until a rare mystery becomes a daily incident.
DeadlocksA circular wait between lock holders that the database breaks by killing one transaction, so handling it is always the application's job to retry.
Memory leaksMemory still reachable but never used again, visible only in the live set measured after collection and hidden entirely by a frequent deploy cadence.
Garbage collectionAutomatic reclamation that trades throughput, latency, and footprint against each other, where at production rates pause magnitude matters far more than pause frequency.
Thread safetyCorrect behaviour under concurrent calls with no caller coordination, achieved by not sharing, not mutating, serialising, or making operations atomic.
Cold startsThe cost of building an execution environment before your code runs, whose share of traffic depends on the gap between requests rather than their volume.

Chapter 8 · Scale, Latency and Cost

9 terms · developed in Chapter 8.

TermDefinition
AutoscalingA control loop that adds and removes capacity against a utilisation target, which optimises cost but arrives minutes late and so never absorbs a spike.
Horizontal ScalingAdding more units of the same size, which is the only scaling that also buys redundancy and the only one bounded by contention rather than by a vendor's largest machine.
Vertical ScalingMaking one unit bigger, which costs nothing in engineering time and buys sub-linear throughput at linear price until you hit the largest instance and have to re-architect.
Serverless LimitsThe account and function quotas that replace capacity planning on a function platform, where the requests-per-second ceiling usually binds long before the concurrency ceiling does.
Cost OptimizationMoving spend toward delivered work, whose central decision is the computable utilisation crossover between per-hour provisioned capacity and per-request consumption pricing.
LatencyThe time to service one request, which is a distribution rather than a number and which grows as service time divided by the idle fraction of the server.
ThroughputThe rate of completed work measured at the exit rather than the entrance, equal to bounded concurrency divided by residence time, so a latency regression is a throughput regression.
P99 LatencyThe value below which ninety-nine percent of requests fall, which is the honest headline number because a mean can sit flat while the tail doubles.
Tail LatencyThe slow end of the distribution, whose defining property is that it amplifies with fan-out, so a one-percent leaf tail becomes a sixty-three percent service tail across a hundred leaves.

Chapter 9 · Delivery and Deployment

13 terms · developed in Chapter 9.

TermDefinition
CI/CDA pipeline that builds one immutable artifact from trunk and promotes that same artifact through every later stage, so pipeline duration directly sets how many changes are batched into each deploy.
DockerContent-addressed container images made of stacked filesystem layers, whose real delivery value is that a digest proves the artifact in production is byte-identical to the one that passed testing.
KubernetesA reconciliation loop that turns deploying into declaring desired state, which is only as safe as the readiness probe that decides a new pod may take traffic.
Infrastructure as CodeDescribing the target environment in version-controlled text so it can be reviewed, diffed, and rebuilt, which makes console fixes a source of drift rather than a shortcut.
TerraformAn infrastructure tool whose defining artifact is the state file binding configuration to real resources, making state partitioning and lock contention the scaling problems rather than syntax.
Helm ChartsVersioned, templated bundles of Kubernetes manifests that make the deployable unit a triple of chart version, values, and image digest rather than an image alone.
Build CachingReusing prior outputs keyed by a hash of declared inputs, which buys large wall-clock savings with sharply diminishing returns and one serious risk: a fast, wrong cache hit.
Dependency HellThe state where pinning too tightly blocks upgrades and pinning too loosely breaks builds, so deferred upgrade debt eventually comes due during a security incident.
Feature FlagsRuntime controls that decouple deploying code from releasing behaviour, giving you a kill switch far faster than any rollback at the cost of combinatorial configuration debt.
Blue-Green DeploymentsTwo identical environments with traffic switched between them, buying the fastest possible rollback with double capacity while protecting the stateless tier only.
Canary ReleasesExposing a small traffic fraction to the new version and comparing it against a concurrent control, which is a statistical test that lacks the power to find small regressions at low traffic.
Rolling DeploymentsReplacing instances in batches with no extra standing capacity, paid for with an availability floor during the rollout and a long window where both versions serve traffic.
RollbacksReturning to the last known-good artifact, which restores code but never restores state, so a migration that already ran turns a successful rollback into a second outage.

Chapter 10 · Observability and Operations

12 terms · developed in Chapter 10.

TermDefinition
MonitoringContinuously collecting and aggregating a pre-chosen set of signals so you can answer, cheaply and instantly, the questions you decided to ask before the incident started.
LoggingEmitting one structured, timestamped record per event, which costs linearly with traffic and is the only signal that can carry unbounded-cardinality detail about a single request.
Distributed TracingPropagating one trace identifier across every service hop so a request's total latency can be attributed to the specific span that actually caused it.
MetricsNumbers aggregated in the client into time series whose cost scales with distinct label combinations rather than with traffic, which is why cardinality, not volume, is what kills them.
AlertingConverting a continuous signal into a discrete interruption of a human being, which should fire on user-visible symptoms and never on internal causes.
SLOsA service level indicator plus a target threshold plus a measurement window, deliberately set below 100 percent so that routine change remains possible.
SLIsA ratio of good events to valid events, measured as close to the user as you can afford, where the definition of good is a product decision rather than a measurement detail.
Error BudgetsThe permitted unreliability implied by an SLO, expressed as a spendable quantity so that shipping-versus-stability becomes arithmetic instead of an argument.
ObservabilityWhether you can answer a question you did not anticipate, without shipping new instrumentation first, which in practice is decided by how much cardinality you retained at collection time.
Production IncidentsA coordination problem wrapped around a technical fault, handled by separating command, operations and communication so that nobody debugging is also holding the overall state.
On-callThe rotation that guarantees a human with authority to act is reachable within a bounded time, whose real capacity limit is set by alert precision rather than by headcount.
PostmortemsThe written record that converts an outage into a permanent system change, blameless because truthful timelines require it, and worthless unless its action items are scheduled and closed.

Chapter 11 · Security

12 terms · developed in Chapter 11.

TermDefinition
Secrets managementStoring credentials outside source code in a central vault that issues, scopes, audits, and rotates them, so a leaked value is short-lived rather than permanent.
IAMThe policy engine that decides whether a named principal may perform a named action on a named resource, evaluated as deny by default with an explicit deny overriding every allow.
OAuthThe RFC 6749 delegation framework that lets a user grant an application scoped access to their data without ever handing that application their password.
JWT rotationReplacing short-lived signed tokens on a schedule because a self-contained token cannot be revoked, so lifetime is the only control over how long a compromised session survives.
TLSThe RFC 8446 protocol that gives a single network connection confidentiality, integrity, and server authentication, with forward secrecy on every key exchange.
Encryption at restEncrypting stored data so that possession of the media discloses nothing, typically through envelope encryption with a per-object data key wrapped by a protected key.
Encryption in transitEncrypting every hop a request takes rather than only the public one, so that an internal network is never trusted merely because it is internal.
CORSA browser mechanism that relaxes the same-origin policy so a page may read a cross-origin response; it is not a server-side access control and never restricts a non-browser client.
CSRFAn attack that abuses a browser's automatic attachment of cookies to make an authenticated but unintended state change, defeated by a token the attacker's page cannot obtain.
SQL injectionUser input altering the structure of a query rather than only its values, fixed by parameterised queries that send data in a separate channel from statement text, never by escaping.
XSSAttacker-controlled text reaching a page where the browser interprets it as markup or script, fixed by output encoding chosen for the exact rendering context.
SSRFCoercing a server into fetching an attacker-chosen URL, dangerous because of what the server can reach from inside the trust boundary, above all the cloud metadata endpoint.
Your teacher. Work down one chapter with the definitions covered and say each aloud. The terms you stumble on are your revision list. Then pick any three and ask me what changes about each one between 100 and 10,000 requests per second - that is the question this course exists to answer, and it is the one an interviewer will keep pulling on.
