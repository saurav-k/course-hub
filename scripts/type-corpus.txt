Every chapter before this one assumed a single authoritative copy of the data. Once you delete that assumption, three new questions appear and they never go away. Where does a given row live? How many copies of it exist? And what does a reader see while those copies disagree? Almost every distributed data design is an answer to those three questions, and almost every distributed data outage is one of those answers being wrong under load. The vocabulary is worth pinning down before we start, because it is used loosely in practice. Partitioning is splitting one logical dataset into disjoint parts. Sharding is partitioning across independent machines so that each machine owns a subset. Replication is keeping more than one copy of the same part. The two axes are independent: you can partition without replicating, replicate without partitioning, or do both, which is what any system above a few thousand requests per second ends up doing. The three scale tiers. At 100 requests per second, do not shard. One primary with a standby handles this comfortably, and every cross-shard problem you would import is pure cost with no benefit. At 1,000 requests per second, sharding is still usually the wrong answer, but this is the tier where you must choose the key you would shard on and stop writing queries that would be impossible under it. Concretely: stop relying on cross-entity joins and multi-row transactions that span customers. At 10,000 requests per second with a write-heavy mix, sharding is mandatory, because sustained write throughput is the one thing a read replica cannot help with. The decision that actually matters was made two tiers earlier. Resharding cost is the other number nobody computes until they need it. Assume 16 shards holding 4 TB each, doubling to 32, so half of every shard moves: 2 TB per shard, 32 TB in total. Assume a migration budget of 200 MB per second, deliberately throttled so the copy does not starve live traffic. Then 2 TB / 200 MB per second = 10,000 seconds, about 2.8 hours per shard, and 16 shards run sequentially in roughly 44 hours. With four migrations in flight, about 11 hours. Those are stated assumptions, not measurements, but the shape holds: resharding is measured in hours or days at best, and the F1 experience shows what it looks like when the key was wrong and the migration is manual. Replication keeps more than one copy of the same data so that a machine loss is not a data loss. Three mechanisms dominate. Leader-based replication streams a change log from one writable node to followers. Consensus replication commits a write once a majority of nodes have durably accepted it. Leaderless quorum replication writes to several nodes at once and reads from several, sizing the two sets so they must overlap. The three scale tiers. At 100 requests per second, one asynchronous standby is the whole design, and it exists for durability rather than throughput. At 1,000 requests per second read replicas start carrying real traffic, and the instant they do, replication lag stops being an operational metric and becomes a correctness property of your application. At 10,000 requests per second you have a replica set per shard, and you are choosing synchronous commit per transaction class rather than per cluster, because paying a network round trip on all 10,000 writes per second is a different business than paying it on the 300 that move money. The trade-off and the failure mode. Synchronous replication trades latency and lock contention for a bounded recovery point; asynchronous trades a bounded recovery point for latency. The failure mode people forget is that a replica faithfully replicates a mistake. A dropped table, a bad migration, or a malicious delete arrives at every replica in milliseconds. Replication protects against machine loss, never against data loss caused by the writer. The three scale tiers. At 100 requests per second, all reads go to the primary and eventual consistency is a non-issue you should not import. At 1,000 requests per second, you start serving reads from replicas, and this is the tier where read-your-writes breaks in production for the first time: a user saves a profile, is routed to a lagging replica, sees the old value, and files a bug that the team cannot reproduce. The fix is a session guarantee, usually sticky routing or a write token carried by the client. At 10,000 requests per second across regions, you additionally need a written conflict-resolution policy, because concurrent writes to the same key from two regions are no longer hypothetical. Timeout selection is the concrete design decision and it has arithmetic. A failure detector declares a peer dead after a silence longer than its timeout, so the timeout trades detection speed against false positives. One heartbeat per second is 86,400 per day. If one heartbeat in ten thousand exceeds a tight 100 ms timeout, that is 8.64 false failovers per day, each one a leader election and a write stall. Widen the timeout so that only one in ten million exceeds it and you get 0.0086 per day, roughly one every four months, at the cost of detecting a genuine failure more slowly. There is no setting that is fast and quiet; there is only the pair of numbers, and you should be able to state both. The three scale tiers. At 100 requests per second, last-write-wins on wall-clock timestamps is usually harmless, because two writes to the same key inside a few milliseconds are rare. At 1,000 requests per second, hot keys begin producing timestamp ties and the resolution starts silently discarding real updates. At 10,000 requests per second with any hot key at all, it is continuous, and you need either a logical ordering, an explicit merge function, or bounded-uncertainty timestamps. Convert those SLA figures into the unit humans argue about. A year is 525,600 minutes, so 99.99 percent allows 52.56 minutes of unavailability per year and 99.999 percent allows 5.26 minutes. The multi-region configuration buys back about 47 minutes a year. Whether 47 minutes is worth a permanent write-latency penalty is a business question, and the point of doing the arithmetic is that it becomes a business question rather than an architectural preference. The write-latency penalty is not a tuning problem, it is physics. Assume signal propagation in single-mode fibre at a group index of about 1.47, giving roughly 204,000 km per second, and assume a straight great-circle path, which no real fibre route follows. Then: The three scale tiers. At 100 requests per second, run in one region and keep backups in another; a multi-region write path at this volume is cost and complexity with no measurable benefit. At 1,000 requests per second with a geographically spread user base, put read replicas near users and keep a single write region, which captures most of the latency win for a fraction of the complexity. At 10,000 requests per second, you must choose consciously between write-partitioned, which preserves correctness by giving each key exactly one home region, and write-local, which preserves latency and hands you a conflict-resolution problem. Choosing write-local by accident, because it was the default, is how this goes wrong. The three scale tiers. At 100 requests per second, backup and restore is correct and everything above it is waste. At 1,000 requests per second, pilot light with continuous replication is the usual landing point, because the restore time in the backup-and-restore approach now exceeds what the business will tolerate. At 10,000 requests per second, warm standby or active/active, because at this volume both the restore duration and the lost-write count from a backup-shaped RPO become unacceptable in the same conversation. A failure at 20:00 means 18 hours of writes since the 02:00 backup, so the achievable RPO is 18 hours regardless of what the policy document claims. The restore is 4 TB / 500 MB per second = 8,000 seconds, which is 2.2 hours.
