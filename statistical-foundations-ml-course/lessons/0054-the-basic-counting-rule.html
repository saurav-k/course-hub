Lecture 4 · Part 9 of 12 · the basic counting rule

Stages that do not constrain each other multiply, and that is the only counting rule there is

9 min foundation Every formula in the rest of this lecture is this one rule applied carefully. The lecture states it in one line and gives two examples.

The one-minute version

  • Build a configuration by making a sequence of choices: (C1, C2, ..., Cn). If choice i can be made in mi ways, whatever the earlier choices were, the total number of configurations is m1 × m2 × ... × mn.
  • The lecture's first example: three slots with 4, 5 and 3 options, giving 4 × 5 × 3 = 60.
  • The second is a machine-learning hyperparameter grid: batch size from (16, 32, 64), learning rate from (0.001, 0.01), optimiser from (Adam, SGD), giving 3 × 2 × 2 = 12 combinations.
  • The condition to watch is whatever the earlier choices were. When the count at one stage depends on what happened at an earlier one, the rule still works as long as the count is the same number every time - which is exactly the distinction the next page turns into two separate formulas.

1. The rule, in words before symbols

A configuration is something assembled out of parts, where a decision is taken for each part. A meal is a starter, a main and a dessert. A password is a first character, a second character, and so on. A training run is a batch size, a learning rate and an optimiser.

Counting configurations works because the decisions stack. Fix the first decision, and the number of ways to finish is however many ways there are to make the rest. There are m1 ways to fix the first decision, and each of them opens the same number of continuations, so the totals multiply rather than add.

total = m1 × m2 × m3 × ... × mn n is how many decisions are taken, one per slot in the configuration. mi is the number of options available at slot i. The subscript is a label for the slot, not a power. The rule requires that mi be the same count no matter which options were chosen earlier; it does not require that the same options be available, only the same number of them.

2. The lecture's first example, worked

The notes take a configuration written (S, P, T) with three slots, offering 4, 5 and 3 options respectively.

  1. Fix the first slot. There are 4 ways to choose S.
  2. For each of those, fix the second. There are 5 ways to choose P, and this is true whichever S was chosen, so the running total is 4 × 5 = 20 pairs.
  3. For each of those pairs, fix the third. There are 3 ways to choose T, so the total is 20 × 3 = 60.

Note what step 2 says and does not say. It does not claim the same five options are offered for every S. It claims there are five of them each time. That is a weaker condition and it is the one the rule actually needs.

The notes' second example is a machine-learning training sweep, which is worth working slowly because it is the shape this material takes at work.

  1. Multiply the three counts. 3 × 2 × 2 = 12. A full sweep of this grid is twelve training runs.
  2. Check by a different route. Batch size and learning rate together give 3 × 2 = 6 pairs; each pair runs under two optimisers; 6 × 2 = 12. Grouping the slots differently changes nothing, because multiplication does not care about order.
  3. See what one more slot costs. Adding a fourth axis with three options, say a weight decay from three values, multiplies the whole thing again: 12 × 3 = 36 runs.

4. When the rule does not apply

The rule needs the count at each stage to be a fixed number. It says nothing when the number of options genuinely changes depending on earlier choices.

Suppose a meal is a starter and a main, three starters and four mains, but one particular starter rules out two of the mains. Then the second stage offers four options after two of the starters and two options after the third, and 3 × 4 = 12 is simply wrong: the true count is 4 + 4 + 2 = 10, obtained by splitting into cases and adding.

That is the general repair, and it is worth naming: when stages interact, partition into cases where they do not, count each case with the multiplication rule, and add the cases. Adding disjoint cases is the third axiom doing its job, exactly as in the law of total probability, and it is the same move that made the medical test tractable on Part 2.

5. Check yourself

A sweep has 3 batch sizes, 2 learning rates and 2 optimisers. How many runs does adding a third learning rate cost?
The new total is 3 times 3 times 2 = 18, so the third learning rate costs six runs, one for every combination of the other two axes. One extra run would be adding a configuration rather than an axis value. Three would be counting only the batch sizes it pairs with, forgetting the optimiser. And twelve would be right for a whole new binary axis, which doubles the grid, rather than for one extra value on an axis that already exists.
Three starters and four mains, but one starter rules out two mains. What is the correct count?
Split by starter: two of them offer four mains each and one offers two, so 4 + 4 + 2 = 10. Twelve is the multiplication applied where its condition fails. Six would be three starters times two mains, which wrongly imposes the tightest constraint everywhere. And two counts a single starter's options rather than the configurations.
Your teacher. The next time you queue a parameter sweep, compute the product before you press the button, then multiply by the wall-clock of one run. The number that comes out is usually the argument for a smaller grid, or for a search that is not a grid at all. This is one of the few pieces of probability that pays for itself on the day you learn it.
