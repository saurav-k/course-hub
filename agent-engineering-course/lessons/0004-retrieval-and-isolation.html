Retrieval and Isolation

3 topics Getting the right evidence into the window, from documents that are not plain text, without letting one tenant or one agent reach another.

The one-minute version

  • Most enterprise documents are not text. Multi-modal retrieval indexes tables, charts, and page layout instead of throwing them away in a text-extraction step you never inspected.
  • A multi-tenant vector store filters on a tenant field inside the search, not after it. Post-filtering does not leak data, but it silently destroys recall, which is the harder bug to find.
  • Anything an agent reads is untrusted input, including another agent's output and a tool description. Agent A can inject Agent B through content it merely summarised.
  • The defence is bounded authority rather than better wording. Constrain what the receiving agent is permitted to do, since no filter reliably removes an instruction from prose.

1. The mental model: retrieval is an authority boundary

You are used to treating a database read as a data operation and an authorisation check as a separate concern layered around it. In an agent system those merge, and the merge is the whole chapter. Every document retrieved becomes text the model treats as knowledge, and that text can contain instructions. Retrieval is therefore the point where both a permission decision and a trust decision are made, and both are made per request, inside the query, on live state.

Two independent failures follow from getting this wrong, and they are easy to confuse in an incident review. A permission failure means a tenant received evidence it was not entitled to, which is a disclosure. A trust failure means the evidence contained instructions that changed what the agent did, which is an integrity failure and does not require any data to have leaked. A design that only defends the first is the common case, and it fails the second in a way that is invisible in access logs.

2. Retrieving what the document actually contains

Multi-modal RAG

A conventional retrieval pipeline runs a document through text extraction, discards whatever the extractor could not represent, and embeds what is left. For a plain prose document that is nearly lossless. For a quarterly report, an engineering drawing, a scanned invoice, or a slide deck it is destructive in a way nobody measures, because the extractor's failures are silent and the resulting index simply lacks the answer. Users then report that the assistant "cannot find" a figure that is plainly on page four.

The research direction that made this tractable is to stop extracting. ColPali embeds page images directly with a vision language model and retrieves using a late-interaction mechanism, which means the layout, the table structure, and the chart are part of what is indexed rather than casualties of a preprocessing step. The paper's own claim, and the ceiling on what you should assert, is that this approach outperforms modern document retrieval pipelines on their visual document retrieval benchmark while remaining end-to-end trainable. Source: "ColPali: Efficient Document Retrieval with Vision Language Models" (Faysse et al., 2024).

The engineering trade is storage and compute against recall on visually structured content. Late interaction keeps multiple vectors per page rather than one, so the index is substantially larger and scoring is more expensive than a single-vector dot product. That cost is worth paying where the corpus is genuinely visual and wasteful where it is prose. The pragmatic production shape is a hybrid: keep the cheap text path for documents the extractor handles well, add the page-image path for the document classes it does not, and route by document type at ingestion. Whichever path you choose, the chunk that reaches the window should carry its page reference so the answer can cite a location a human can open, which is the grounding requirement the interview track develops under citation grounding.

3. Keeping tenants and agents apart

Multi-tenant vector databases

The instinct to give each tenant its own collection is usually wrong at scale. Qdrant's guidance is direct: creating a separate collection for each tenant is rarely the most efficient approach, because each collection carries its own resource overhead and many collections become expensive quickly. The recommended default is a single collection with a keyword index on a tenant field, marked as a tenant key, and every query filtered on it, which the documentation describes as efficient for a large number of small, similarly sized tenants. Dedicated sharding per tenant and a tiered combination of the two remain available for the minority of tenants large enough to justify them. Source: Qdrant multitenancy guide.

The correctness question underneath the efficiency question is when the filter is applied. Approximate nearest neighbour search walks a graph and returns a candidate set; if the tenant filter is applied to that candidate set afterwards, the search wasted its budget on other tenants' vectors and your tenant is left with whatever survives. For a small tenant in a large index that can be very little, and occasionally nothing at all. This is why the filter must participate in the search rather than follow it, which is exactly what a tenant-key index exists to enable.

The failure mode is worth stating precisely because it is counterintuitive. Post-filtering is not a disclosure bug: the other tenants' documents are removed before anything is returned. It is a recall bug, and it presents as an assistant that cannot answer questions about documents the tenant certainly owns, on some queries but not others, more often for smaller tenants. Nobody files that as a security ticket, which is why it survives for months. Test it directly: seed a tiny tenant inside a large index and assert that its own documents are retrievable at your production top-k.

Your vector store applies the tenant filter after the approximate nearest neighbour search returns its candidates. What is the actual failure?
The search spends its candidate budget across the whole index, so a small tenant's own documents may never enter the candidate set and the filter then removes almost everything that did. Cross-tenant disclosure is what post-filtering does prevent, which is why the bug hides: it is a recall failure wearing the costume of a correct security control. Ranking order and duplication are separate concerns that pre-filtering neither causes nor fixes.

Inter-agent security

Once agents hand work to each other, one agent's output is another agent's untrusted input. The attack is direct: a web page instructs the agent reading it, the summarising agent carries those words forward faithfully because carrying words forward is its job, and the receiving agent acts on them with whatever authority it holds. No boundary was crossed that a permission system would notice, because the injected content travelled the same path the legitimate content did.

Google's published framework for agent security is built on three principles worth memorising, because they are the vocabulary a reviewer will expect: agents must have well-defined human controllers, their powers must be carefully limited, and their actions and planning must be observable. The approach combines traditional deterministic security controls with dynamic reasoning-based defences, and the framing is important because it concedes that a reasoning-based defence alone is not a control. Source: "Google's Approach for Secure AI Agents" (Diaz, Kern, and Olive, 2025).

The design pattern that gives this teeth is separating planning from data. The CaMeL work proposes defeating prompt injections by design rather than by detection, keeping control flow under a trusted component that never sees untrusted content, so retrieved text can supply values but cannot alter the plan. Applied to a multi-agent system this becomes a concrete rule: an agent that touches untrusted content proposes data, never actions, and any capability it might trigger is granted by a component that has not read the untrusted text. Source: "Defeating Prompt Injections by Design" (Debenedetti et al., 2025).

Four controls follow, and none of them is a wording change. Give each agent its own least-privilege credential rather than a shared service identity, so a compromised summariser cannot reach the mail API at all. Type every handoff, as Chapter 1 argued, since a schema-constrained payload has far less room to carry prose than a paragraph does. Put a human in the loop for consequential, irreversible actions, which is what "carefully limited powers" means operationally. And make the trajectory observable and retained, because the only way you will ever detect this class of attack is by looking at what the agent did rather than at what it said. The threat itself is catalogued as the first entry in the OWASP list for these applications. Source: OWASP Top 10 for LLM Applications.

Agent A summarises an untrusted web page and hands the summary to Agent B, which can send email. What is the strongest available control?
Limiting what the agent may do holds regardless of what it was persuaded to want, which is why bounded authority is a control and the others are mitigations. An instruction to ignore instructions is more text in the same window the attacker is already influencing. A classifier raises the cost of an attack without bounding its success, so it belongs in a layered defence rather than at the load-bearing position. Sharing a system prompt spreads policy without removing any capability, and capability is what the attacker is after.

4. Field drill

Questions a Staff+ reviewer will put to this design, and the trap inside each one.

  • "A user says the answer is on page four and the assistant cannot find it. Where do you look?" The trap is tuning retrieval parameters. Look at ingestion first, because the likeliest explanation is that page four was a table and the extractor dropped it before any embedding was computed.
  • "Is your tenant filter applied before or after the search?" The trap is answering "we filter by tenant", which is true of both and distinguishes nothing. Say which, and say how you tested that a small tenant's documents are still retrievable inside a large index.
  • "Agent A was compromised. What can the attacker reach?" The trap is describing the prompt defences. Answer with the credential each agent holds, since the blast radius is the union of those capabilities and nothing about the wording changes it.
  • "Why not filter injection attempts out of retrieved text?" The trap is agreeing that filtering solves it. There is no reliable way to separate an instruction from prose, so filtering raises attacker cost and cannot be the load-bearing control.
  • "Multi-modal indexing tripled our storage. Justify it." The trap is defending it everywhere. Justify it per document class, with recall measured on the visual corpus specifically, and keep the cheap text path for everything the extractor already handles well.
Your teacher. Run the two experiments that expose this chapter's failures, because neither shows up in normal use. First, seed a tenant with three documents inside your largest index and check that all three are retrievable at your production top-k; if they are not, your filter is running in the wrong place. Second, put a plain instruction inside a document your agent will summarise and watch what the downstream agent does with it. Bring me both results and we will decide which control you are actually missing.

Primary source to go deeper

Read "Defeating Prompt Injections by Design", because it is the clearest published argument that this is a control-flow problem rather than a filtering problem, and that reframing is what changes your architecture. Pair it with "Google's Approach for Secure AI Agents" for the three principles a reviewer will expect you to name.
