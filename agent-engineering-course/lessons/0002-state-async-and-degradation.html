State, Async and Degradation

3 topics What happens to a half-finished agent when the process dies, the tool takes four minutes, or the provider stops answering.

The one-minute version

  • An agent loop holding state in process memory is an unreplicated database with no write-ahead log. Durable execution moves that state to a recorded history you can replay.
  • A tool call that outlives a request timeout must become a long-running operation: return a handle immediately, deliver the result by webhook, and let the agent resume on arrival.
  • A degradation chain trades quality for availability in a defined order, and each tier needs its own trigger, timeout, and quality expectation. An untested tier is not a tier.
  • Every degraded response must declare which tier produced it, or your evaluation data silently mixes tiers and your quality metrics become uninterpretable.

1. The mental model: an agent step is a distributed transaction

Here is the framing that makes this chapter easy for someone with your background. A single agent turn reads state, calls a remote service that charges money, mutates the world through a tool, and writes state back. That is a distributed transaction with no coordinator, and most agent frameworks default to keeping the coordinator's state in a Python variable inside one process. Every reliability property you would demand of a payment flow is absent by default, and nothing complains until a deploy restarts the pod at step seven of twelve.

The three topics in this chapter are the three consequences. Persistence answers what survives a crash. Asynchrony answers what happens when a step outlives the request. Degradation answers what the system serves when a dependency will not answer at all. They are the same question asked at three timescales, and a design that answers only the first is the one that pages you.

2. Surviving the crash

Stateful persistence and checkpoints

Durable execution is the property that an application runs to completion despite adverse conditions, and Temporal implements it by recording a complete and durable log of everything that has happened in the lifecycle of a workflow execution. If a worker crashes, the replacement worker uses that event history to replay the code and recreate the workflow state as it stood immediately before the crash. The responsibility for failure management moves from your application to the platform, which is precisely the trade you want when the application logic is already hard enough. Source: Temporal, "Understanding Temporal".

LangGraph reaches a similar place from the agent-framework direction. A checkpointer persists a thread's graph state as checkpoints, which is what enables conversation continuity, human-in-the-loop pauses, time travel, and fault tolerance. The vocabulary differs and the shape does not: the loop's state becomes an inspectable, restorable, external artifact rather than a stack frame. Source: LangGraph persistence documentation.

Choosing between them is a scope decision rather than a quality one. Take the workflow engine when the agent coordinates work across services, holds money or inventory, spans hours or days, or needs a human approval step in the middle; you get timers, retries, versioning, and visibility that a framework checkpointer does not attempt. Take the framework checkpointer when the durable unit is a conversation and the operational win you want is resuming a thread and inspecting how it got where it is. The expensive mistake is running an engine's determinism model without understanding it, because replay requires that your workflow code produce the same decisions given the same history, and a bare model call is not deterministic. The model call belongs on the other side of the boundary, in an activity or a node whose result is recorded, so replay reads the recorded answer rather than paying for a new one.

Your agent crashes at step seven of twelve, after two paid model calls and one external charge. What does durable execution give you that a retry queue does not?
The recorded history is what makes resumption possible, so the completed steps are not re-executed and the external charge is not repeated. A retry queue gives you the second option, a clean restart from the beginning, which is exactly the behaviour that double-charges the customer. Backoff is a policy for a single failed call and says nothing about the eleven other steps. Returning a typed error is honest but abandons work that is recoverable.

3. Surviving the long tool call

Async tool execution with webhooks

When a tool takes longer than a request timeout, holding the connection open is not an option, and neither is polling from inside the agent loop. The established API pattern is the long-running operation: a method that takes a substantial amount of time should return an operation object instead of the ultimate response message, which Google's API guidance compares to a promise or a future in other languages. The operation carries its own identity, status, metadata, and eventual result or error, and clients interact with a standard operations service rather than a bespoke interface per endpoint. Source: Google AIP-151, Long-running operations.

Delivery of the completion is where webhooks come in, and the reason to follow a specification rather than invent one is that the failure modes are all security failures. Standard Webhooks exists because webhook implementations fragmented across providers, and it addresses server-side request forgery, spoofing, and replay explicitly, alongside the reliability concerns of retry and ordering. A signed, timestamped, idempotency-keyed callback is the difference between an agent that resumes correctly and an agent that can be resumed by anyone who guesses a URL. Source: Standard Webhooks specification.

Two design consequences follow that are easy to miss. The first is that the agent's context must be reconstructable at resume time rather than held in memory, which is why this topic sits next to persistence rather than in its own chapter. The second is that the user-facing contract changes: something must tell the user the work is in flight, and something must handle the case where the callback never arrives. Give every operation a deadline and a reconciliation sweep that polls for the operations whose webhooks were lost, because a webhook-only design has no answer for a receiver that was down for ten minutes. The interview track frames the same boundary as async processing.

4. Surviving the dependency

Graceful degradation chains

A degradation chain is an ordered ladder of progressively cheaper and weaker ways to answer, walked when the tier above it will not serve. A frontier model first, then a mid-tier model, then a locally hosted open-weight model, then a cached or retrieval-only answer, then an honest refusal. The SRE literature separates the two mechanisms cleanly: load shedding drops a proportion of requests as a server approaches overload, while graceful degradation reduces the amount of work done per request instead of rejecting it, serving results without images or using a faster and less accurate ranking algorithm. Agent systems are unusually well suited to the second, because quality is a continuous dial rather than a binary. Source: "Addressing Cascading Failures", Google SRE Book.

The same source carries the warning that matters most here, and it is the one teams skip. Degradation paths should trigger infrequently, stay simple and testable, and be monitored, because rarely exercised code carries higher risk, and complex implementations can trigger inappropriately or create feedback loops. A four-tier chain written once and never exercised is four untested code paths that will run for the first time during your worst incident. Exercise them deliberately: force each tier in a scheduled test, and score each tier against the golden dataset separately so you know what quality you are actually promising when it fires.

Three properties turn a diagram into a working chain. The trigger must include latency, not only errors, because providers commonly fail slowly rather than cleanly, which is the standard argument for tripping a circuit breaker on latency. The budget must be end-to-end, since a chain that gives every tier a full timeout turns a fast failure into a four-times-slower one and the user leaves before tier three answers. And the cheaper tiers usually have smaller context windows and weaker instruction following, so the request must be re-packed for the tier that will serve it rather than replayed verbatim.

Your degradation chain works correctly in an incident, but the following week your quality dashboard is unreadable. What was most likely missing?
Unlabelled responses mix four systems into one average, so an outage reads as a model regression. Retrying the primary on every request defeats the circuit breaker that opened for a reason and prolongs the incident. Returning an error at the first failure is the absence of a chain rather than a fix for it. Running every tier multiplies cost by four on every request and still would not tell you which answer was served.

5. Field drill

Questions a Staff+ reviewer will put to this design, and the trap inside each one.

  • "A deploy restarts every pod mid-conversation. What does the user see?" The trap is answering "we retry". Retry from the top re-executes side effects. Answer with where the loop's state lives, what is recorded before each effect, and where the resume point is.
  • "Why not just poll the slow tool from inside the agent?" The trap is calling it simpler. Polling holds a worker, burns context on every wake, and turns one long operation into many short billable ones. The operation handle plus a signed callback costs nothing while parked.
  • "Your webhook receiver was down for ten minutes. Now what?" The trap is describing sender retries, which you do not control. Answer with a reconciliation sweep over operations past their deadline, plus idempotency so a late callback and a reconciled result cannot both take effect.
  • "How good is tier three?" The trap is not knowing. Every tier needs its own score against the golden dataset, because the chain is a promise about degraded quality and an unmeasured promise is a guess.
  • "When did your fallback chain last run?" The trap is answering "during the incident in March". Untested degradation paths fail when they fire. Answer with the scheduled exercise that forces each tier on a cadence.
Your teacher. Try this on a system you own: pick the agent step that spends real money, and trace what is durably recorded immediately before and immediately after the side effect. Most implementations record after, which means a crash in the window repeats the charge on resume. Bring me the sequence and we will work out where the record has to move to, and what idempotency key makes the repeat harmless when it moves.

Primary source to go deeper

Read "Addressing Cascading Failures" in full, particularly its insistence that degradation modes be exercised regularly, because that is the discipline this chapter most often loses. Pair it with AIP-151, which is short and gives you a defensible shape for every slow tool you will ever integrate.
