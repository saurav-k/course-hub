Context and Protocol

4 topics The substrate every other chapter stands on: what goes into the window, how tools arrive, and how agents hand work to each other.

The one-minute version

  • Prompt engineering optimised one string. Context engineering curates the whole token budget across a long-running loop, which is a state management problem rather than a writing problem.
  • The Model Context Protocol turns the N times M integration problem into an N plus M one. Writing a server is easy; deciding what a server must never expose is the engineering.
  • Agent-to-agent handoffs travel as validated typed objects, never as free text. A schema converts a silent downstream misinterpretation into a loud upstream failure.
  • Guardrails belong in version control next to the code they protect, with a diff, a review, a test, and a rollback. A safety rule you cannot bisect is not a control.

1. The mental model: the window is a working set

You already know how to reason about a cache under pressure. The context window is that cache, the eviction policy is yours to write, and the cost of a miss is not a slow request but a wrong answer delivered confidently. That is the single transfer of intuition this chapter is built on, and it is why the discipline moved from writing better prompts to managing better state.

A single-turn assistant made the window a formatting question, because you controlled everything that went into it. An agent running for forty turns does not work that way. Every tool result, every retrieved document, every intermediate plan, and every error message accumulates in the same finite space, and nothing evicts itself. By turn thirty the model is reasoning over a working set assembled by chance rather than by design. Production agent engineering is mostly the work of taking that assembly back under explicit control.

2. Curating what the model sees

Context engineering

Context engineering is the set of strategies for curating and maintaining the optimal set of tokens available to the model during inference, covering system instructions, tool definitions, protocol-supplied data, external documents, and message history. It displaced prompt engineering for a structural reason rather than a fashionable one: prompt engineering assumes a single authored input, and an agent in a loop generates its own inputs. Once the model is writing most of what it will later read, the interesting decisions move from wording to admission, compaction, and eviction.

The practical shape is a budget with named slots and an owner for each one. System policy is stable and belongs at the front of the request so a provider prefix cache can serve it, which links this directly to prompt caching in the interview track. Turn history needs a compaction rule, usually summarise-and-drop with the last few turns kept verbatim. Retrieved evidence needs a hard cap and a relevance floor, because adding a marginal document costs tokens on every subsequent turn of the loop, not just this one. The answer reserve is protected first and shrunk last. Source: "Effective context engineering for AI agents" (Anthropic).

The failure you will actually hit. Tool definitions are the slot engineers forget to budget, because they are invisible in the application code and paid for on every single model call. An agent with sixty tools spends a large and permanent fraction of its window describing capabilities it will not use in this task. The fix is retrieval, not a bigger window: expose a small stable core, and put the long tail behind a search-and-fetch interface that loads a definition only when the task needs it.

Building a custom MCP server

The Model Context Protocol is an open protocol that standardises how applications supply context and capability to language models. It carries JSON-RPC 2.0 messages between three roles: hosts, which are the applications that initiate connections, clients, which are the connectors inside a host, and servers, which are the services that provide context and capability. A server can offer three things. Resources are context and data for the user or the model to read. Prompts are templated workflows a user invokes deliberately. Tools are functions the model may execute. Clients can offer sampling, roots, and elicitation back to the server. Source: Model Context Protocol specification, revision 2025-06-18.

The value is the same value a language server protocol delivered to editors. Without it, every host integrates every data source separately and the work multiplies. With it, you write one server for your internal system and every conforming host can use it. That is why the build decision is rarely whether to write a server and almost always what the server is allowed to do.

Three design choices decide whether your server survives contact with production. The first is granularity: a tool that returns an entire record dumps hundreds of unbudgeted tokens into the window on every call, so return the projection the task needs and offer a detail tool for the rest. The second is the resource-versus-tool split, which is a trust split rather than a stylistic one, because resources are read into context while tools execute code. The third is that tool descriptions are themselves untrusted input. The specification is explicit that descriptions of tool behaviour, including annotations, should be considered untrusted unless they come from a trusted server, which means a server you did not write can attempt to influence your agent through nothing more than the text of a tool description.

Your agent grew from six tools to sixty and its accuracy on the original six tasks fell. Which change addresses the cause most directly?
Fifty-four irrelevant definitions are permanent noise on every call, and selection accuracy falls as the candidate set grows. A larger window keeps the noise and adds cost. Temperature changes sampling variance, not the size of the candidate set the model is choosing from. A reviewer model catches a bad choice after it is made and doubles your per-turn cost to do it, which treats the symptom.

3. Making handoffs legible

Typed state handoffs

When one agent hands work to another, the payload must be a validated typed object, not a paragraph. Pydantic is the usual carrier in Python, and its guarantee is worth stating precisely: if validation completes without raising, the fields of the resulting model instance conform to the field types declared on the model. That is a narrow promise and exactly the right one, because it converts an entire class of downstream failure into a single loud exception at a known boundary. Source: Pydantic models documentation.

The argument against free text is a distributed-systems argument you have made before. Text between services is an untyped, unversioned, unvalidated wire format, and every consumer reimplements a parser that disagrees slightly with every other consumer. When the researcher agent writes "the customer is probably on the enterprise tier" and the billing agent reads a tier, the ambiguity does not surface as an error. It surfaces as a wrong invoice, three hops later, with no stack trace pointing home. A schema makes the researcher fail at the moment it cannot produce a valid tier, which is the moment when the context to fix it still exists.

Two properties matter beyond the type check. Schemas need versioning, because an agent pipeline is a distributed system with independently deployed components and you will eventually run two versions at once. And validation is necessary rather than sufficient: a schema-valid object can still be semantically wrong, so a confidence field or an explicit unknown variant is usually better than a required field the upstream agent is forced to guess at.

Guardrails as code

A guardrail is a check around the model: input screening, output validation, schema conformance, policy classification, and refusal handling. Guardrails-as-code means those rules live in files in your repository, review through a pull request, run in continuous integration, deploy with a version, and roll back like anything else you ship. NVIDIA's NeMo Guardrails is a useful reference implementation of the shape, because it makes the rules declarative artifacts: a YAML configuration plus Colang flows, with rails placed at five distinct points in the request lifecycle. Input rails screen the user's submission, retrieval rails control fetched content, dialog rails manage conversational flow, execution rails oversee tool invocation, and output rails validate what the model produced. Source: NVIDIA NeMo Guardrails documentation.

The reason to insist on this is operational rather than aesthetic. A guardrail edited through an admin console has no diff, no author, no test, and no bisect. When a safety incident happens at 02:00 the only question worth asking is which change caused it, and a console-edited rule cannot answer. Treat the rule set as source: every rule carries a test case that would fail without it, the whole set runs against a fixture corpus in continuous integration, and a rule change ships behind the same release process as a code change.

Two subtleties separate a real control from a checkbox. Guardrails must have a defined failure direction, decided per rail: a policy classifier that is unavailable should block, while a formatting validator that is unavailable can usually let the request through. And a guardrail is a control only if it runs somewhere the model cannot influence, which means an independent, separately monitored component rather than another instruction inside the same prompt. The interview track develops the threat side of this under prompt injection.

Your team moves an unchanged safety rule from an admin console into the repository. What is the primary engineering benefit of that move?
Version control buys attribution and reversibility, which is exactly what an incident review needs at 02:00 and exactly what a console cannot supply. Where a rule is stored does not change how fast it executes. Coverage is a property of the rule's own logic, so an unchanged rule blocks precisely the inputs it blocked before the move. Tenant scoping is an independent design decision that a console can express just as well.

4. Field drill

Questions a Staff+ reviewer will put to this design, and the trap inside each one.

  • "Why not just use a bigger context window?" The trap is treating the window as capacity. It is a working set with an eviction policy you either write or inherit by accident. Cost, latency, and the accuracy cost of irrelevant tokens all move against you, and none of them is fixed by a larger allocation.
  • "What does your MCP server refuse to do?" The trap is answering with the feature list. Answer with the boundary: what it never returns, what scope its credential holds, why a tool is a tool rather than a resource, and how it behaves when the caller is an agent acting on a low-trust user's behalf.
  • "Two agents disagree about the customer's tier. Where does that surface?" The trap is proposing a reconciliation step. With free-text handoffs it surfaces as a wrong action with no error, so the answer is that the schema makes it surface at the producer, before the ambiguity travels.
  • "How do you roll back a guardrail?" The trap is describing a toggle. A toggle disables a rule; it does not tell you which rule change broke production last night. Answer with the release process: versioned rules, a test per rule, continuous integration on a fixture corpus, and a revert.
  • "Your agent behaved differently for the same input yesterday. Why?" The trap is blaming sampling. Sampling is one candidate among several, and in a long-running agent the more likely cause is that the assembled context differed, through compaction, a changed tool set, or a retrieval result that moved.
Your teacher. The exercise that pays for this chapter is an audit. Take an agent you already run, dump the exact bytes sent on its tenth turn, and account for every token by slot: policy, tools, history, evidence, reserve. Almost everyone discovers that tool definitions and stale history own more of the window than the evidence does. Bring me your breakdown and I will push on which slot you would evict from first and what breaks when you do.

Primary source to go deeper

Read the Model Context Protocol specification end to end once, paying particular attention to its security and trust section rather than its message formats. Pair it with "Effective context engineering for AI agents", which supplies the vocabulary the rest of this course uses for the window.
