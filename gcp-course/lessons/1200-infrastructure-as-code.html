The native infrastructure-as-code path is Terraform, run for you

working 8 min Capabilities native-iac-template, terraform-provider, iac-in-code-sdk and kubernetes-config-management. Sourced from Infrastructure Manager and the Deployment Manager deprecations page.

The one-minute version

  • Cloud Deployment Manager, the original YAML and Python template engine, is deprecated: out of support, closed to new users, and scheduled to turn down. Existing deployments need a migration plan.
  • Infrastructure Manager is the successor, and it is not a new template language - it runs Terraform, with the state hosted by Google and a service agent doing the work.
  • The google and google-beta providers are the de-facto standard for the platform's surface, with the beta provider tracking pre-general-availability resources. They are maintained by HashiCorp, not by Google.
  • There is no first-party imperative in-code infrastructure SDK. The nearest paths are third-party tools that generate provider calls, and client libraries or command-line scripting.
  • Config Connector is the other shape: Google Cloud resources modelled as Kubernetes custom resources, so a cluster's own tooling manages cloud objects.

The reframing Three questions and the answers are short. What language - Terraform, because the alternative is retiring. Who runs it - your pipeline or Infrastructure Manager, and that is a state-and-operations decision rather than a code one. Where does intent live - a repository for most estates, and a Kubernetes cluster for the ones where that is already true.

Retrieval practice

Answer from memory before revealing.

What is Infrastructure Manager, relative to the product it succeeds?
The successor story is Terraform run by a Google-managed service with the state hosted for you. The second assumes a like-for-like replacement, which is exactly the assumption this page corrects. The third and fourth describe tools that are not what this is.
Who maintains the Terraform provider that covers the Google Cloud surface?
The provider is HashiCorp-maintained, which is why this course labels its documentation as third-party at the point of use. The first conflates the execution service with the provider. The second and fourth misstate how the provider is published.
A team wants to define infrastructure in a general-purpose programming language. What does the inventory record?
The absence is real and the substitutes are third-party tools whose output the platform's own service can still run. The first invents the SDK. The second describes declarative custom resources, not code. The third is the over-reading that turns a support-relationship gap into a capability gap.

Practice about 12 minutes, with paper

Practice 1working

An estate has forty Deployment Manager templates, a small platform team, and a policy that every supported component must have a vendor support relationship. A developer proposes rewriting the templates in a third-party code-first tool, because the team prefers a programming language to a configuration one.

Say what must happen to the forty templates and why it has a deadline, assess the proposal against the support policy, and describe the option that satisfies both the policy and the team's preference least badly.

Hint

The deadline is not a preference. The support question has two layers, and one of them is already third-party whichever option is chosen.

Show the worked solution
  1. The forty templates. They must be migrated. Deployment Manager is out of support, closed to new users and scheduled to turn down, so this is dated work rather than a preference, and the dates are on the vendor's deprecations page.
  2. Assess the proposal against the policy. A code-first tool that generates provider calls is third-party, so it fails a strict reading of the policy. But note the layer below it: the google provider is HashiCorp-maintained too, so even plain Terraform has a third-party component. The policy as written would refuse the supported native path as well.
  3. Sharpen the policy question. The thing Google supports is the execution service and the platform APIs. What no vendor supports for you is the provider and any tool above it. That is the honest description, and the policy should be rewritten against it rather than applied to a product name.
  4. Describe the option. Terraform configuration, run by Infrastructure Manager: the state is hosted and the runs are performed by a Google-managed service, which is the largest supported surface available. The team's language preference is not met, and the alternative that meets it adds a second unsupported layer on top of the one they already have.

Sanity check. Your answer should have found that the support policy fails against the supported path too. If the proposal was refused purely as third-party, the same argument refuses Terraform, and the estate is left with a retiring product.

Your teacher. Ask an agent to list every Deployment Manager deployment still live in the estate. The count is the size of a piece of work with a date attached, and it is the kind of thing that stays invisible until the service stops accepting the calls.
