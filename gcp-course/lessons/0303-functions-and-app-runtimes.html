Functions are events on the Cloud Run substrate, and App Engine is still its own runtime

working 7 min Capabilities functions-faas, paas-web-runtime and static-site-hosting. Sourced from Google's functions documentation.

The one-minute version

  • Cloud Run functions is the current name of what was Cloud Functions, and the second generation runs on Cloud Run infrastructure. The first generation remains as legacy.
  • Events reach a function through Eventarc, and a function instance has a concurrency setting, so a function here is not automatically one request per container.
  • App Engine is the classic platform runtime and remains generally available, in a Standard environment with scale-to-zero runtimes and a Flexible environment, with versions and traffic splitting of its own.
  • Firebase Hosting covers static and web-framework sites on a content delivery network, with preview channels and custom domains. A Cloud Storage bucket serving a static website is the alternative without Firebase.
  • These three are not tiers of one product. They differ in what you hand over: a handler, an application, or a set of files.

1. Three runtimes, three units of handover

2. Functions, and the substrate under them

Cloud Run functions is the current form and it is built on Cloud Run infrastructure, which is why the previous page called Cloud Run the middle of this module rather than its end. The practical consequence is that the properties you learned there - revisions, scaling behaviour, the shape of the billing - are the properties underneath a function too.

The first generation, under the older Cloud Functions name, remains as legacy. A tutorial or a repository written against it still describes something real, and it does not describe the current product. Check which generation a piece of guidance targets before following it, because the substrate underneath changed and much of the surrounding advice changed with it.

3. App Engine, stated carefully

App Engine ships two environments. Standard runs second-generation language runtimes and scales to zero. Flexible is the other environment of the pair. Both are generally available, and both carry the versions and traffic splitting drawn above.

The research this course is written from records that Google steers new applications towards Cloud Run while App Engine remains generally available - and it explicitly flags that positioning statement as one it did not finish verifying. This course therefore states the part that is verified, that App Engine is generally available with both environments, and names the steering as guidance to check on the environments page rather than asserting it. An existing App Engine application is not on a deprecation path on the evidence behind this page.

4. Static hosting is a third answer, not a smaller one

Firebase Hosting serves static and web-framework sites from a content delivery network, with preview channels for branch-style review and custom domains. Google also documents a plainer path: a Cloud Storage bucket configured for static website hosting, which is the answer when Firebase is not wanted in the picture. Firebase App Hosting adds framework-aware continuous integration and delivery on top.

The reframing The temptation is to rank these four runtimes from most to least serverless and pick a rung. Resist it. A function, an application, a container and a folder of files are different artefacts, and the runtime that accepts your artefact is usually already decided by the repository you have. The genuine choice appears only when you are willing to change the artefact, and that is a refactoring decision with its own cost.

Retrieval practice

Answer from memory before revealing.

What runs underneath the current generation of Cloud Run functions?
The second generation is built on Cloud Run infrastructure, which is why the name changed. The first option describes the older shape. The third and fourth each name a real Google Cloud runtime, and both are wrong here in a way that would mislead a capacity or networking design.
Why must a function's handler be safe to run concurrently?
Concurrency is a per-instance setting, so several events can be in flight inside a single process and shared state inside that process is shared. The first option is true and is not the reason - separate instances do not share memory. The other two describe real distributed-systems concerns that are not this one.
A team runs an existing App Engine application. What does the evidence behind this course support?
General availability of both environments is what the sources support, and the steering of new applications elsewhere was flagged as unverified rather than asserted. The second and third options each turn that unverified steering into a hard status. The fourth confuses App Engine with the functions product, which is the one built on the Cloud Run substrate.

Practice about 15 minutes, with paper

Practice 1working

Three teams arrive on the same day. Team one has a build directory of compiled assets. Team two has a repository containing an application and a language runtime declaration. Team three has a single handler that should run whenever an object is written to a bucket.

Place each team on a runtime from this page, then say which of the three has a real second option and what changing to it would cost.

Hint

Place them by artefact rather than by preference. Then ask which artefact is closest to being a different artefact.

Show the worked solution
  1. Place team one. Built files go to Firebase Hosting, or to a Cloud Storage bucket configured for static website hosting if Firebase is not wanted. Nothing has to change about the artefact.
  2. Place team two. An application plus a runtime declaration is the App Engine shape, and Standard is the environment that scales to zero.
  3. Place team three. A handler with a trigger is a function, delivered by Eventarc, running on the Cloud Run substrate.
  4. Find the real second option. Team two's application can be containerised and moved to Cloud Run, because an application with a runtime declaration is a short step from a container image. The cost is a build to write and maintain, plus the operational surface of an image rather than a declared runtime. Team one's files and team three's handler have no comparable second home without becoming different artefacts entirely.

Sanity check. Exactly one team should have a real choice, and its cost should be a build rather than a rewrite. If every team came out with several options, the placement was done by preference rather than by artefact - which is how these decisions become arguments.

Your teacher. If the functions concurrency setting still feels like a detail, ask an agent what happens to a module-level variable in a handler when concurrency is raised above one. The answer is the reason this setting is worth knowing before it is worth tuning.
