Module 01 · The lay of the land · Lesson 0100

Every resource declares a scope, and that scope is the failure domain you chose

foundation 9 min Capability region-az-model. Sourced from Google's regions and zones reference.

The one-minute version

  • Google Cloud places every resource at one of three scopes: zonal, regional, or global. The scope is a property of the resource type, not a setting you add later.
  • A zone is a separate failure domain. A region is a deployment geography that holds several of them.
  • Choosing a zonal resource is choosing to lose it when that zone is lost. Nothing warns you, because the choice was made when you picked the resource type.
  • Some zones are designated AI zones, which is where accelerator hardware lives, so accelerator availability is a zone question rather than a region question.
  • The platform's own inversion arrives on the first page of networking: a VPC network is global while its subnets are regional, which is the opposite of the arrangement most engineers expect.

1. Three scopes, and the resource picks one for you

Google's own reference states the relationship plainly: regions contain zones, zones are separate failure domains inside a region, and a region is a deployment geography. Every resource then declares which of the three scopes it belongs to.

That declaration is the whole lesson. A virtual machine is zonal, so it has one zone and no other. A subnet is regional, so it is reachable from every zone of its region. A VPC network is global, so it has no region at all. None of these are configured into their scope - they arrive with it.

The reframing A cloud design is usually described as a list of services. Read it instead as a list of scopes: for every box on the diagram, say zonal, regional or global. The boxes you cannot label are the ones you have not finished designing, and the zonal boxes are the ones a single zone can take away.

2. What a zone is for

The corpus this course is written from records the design rule in one line: zone-independent designs are the reliability default on this platform. That is a statement about the shape of a design, not about a feature. The regional forms exist across the whole catalogue - regional managed instance groups spread members across zones, a regional Persistent Disk replicates synchronously to a second zone - and each of them is the same decision taken at a different layer.

One zone property is easy to miss because it has nothing to do with reliability. Some zones are designated AI zones, which is where accelerator hardware is offered. So can I get this accelerator is a question about a zone, not about a region, and a region that lists an accelerator does not offer it everywhere inside itself.

The count of regions and zones changes, so this course does not print one. Google's regions and zones page is the live list, and it is the only honest place to read the current geography from. A design that names a specific zone should be checked against that page rather than against any course, this one included.

3. What each scope costs

The trade is real in both directions. A zonal virtual machine has one copy of its state in one place, which is the easiest thing in the world to reason about and the easiest thing in the world to lose. A regional resource has removed that single point and added a second one to keep in step. A global resource has no region to fail, and in exchange it is the resource whose behaviour you understand least well when something goes wrong in one part of the world.

4. The inversion you will meet on every networking page

One consequence of the scope model is sharp enough that the research this course rests on calls it the single most important architectural fact about Google Cloud. A VPC network is a global object and its subnets are regional objects inside it. One network routes across every region, and no subnet spans two.

Module 07 works the network properly. It appears here because the scope model is what makes it possible, and because an engineer arriving from another platform will otherwise spend a week looking for the object that joins two regions.

What this certification tests Geography and scope are not a domain of their own on either Google Cloud certification - they are the vocabulary the other domains are written in. The Associate Cloud Engineer guide puts Planning and implementing a cloud solution at about 30 per cent of the exam, and placement questions live there. The Professional Cloud Architect guide opens with Designing and planning a cloud solution architecture at about 25 per cent, where the same facts are asked as a trade-off rather than as a task.

Check yourself

Retrieval practice

Answer from memory before revealing.

A team wants a virtual machine that survives the loss of a zone. What does the scope model say about that wish?
Scope arrives with the resource type, and an instance is zonal, so zone survival is a question of how many instances there are and where they sit. The first option invents a setting. The second confuses the disk's scope with the instance's - a regional disk survives, the instance still does not. The fourth confuses the network's global scope with the workload's.
Two subnets sit in two different regions of one VPC network. What has to be built to route between them?
The VPC is a global object, so two of its subnets are already in one routed network. The three wrong options each name a real mechanism from a platform where the network itself is regional, and each would be the right answer there. Reaching for one of them here is the classic first-week mistake on Google Cloud.
A workload needs a particular accelerator. At which level of the geography is that question actually answered?
Accelerator hardware lives in designated AI zones, so a region can list an accelerator without offering it in every zone inside itself. The third option is the near miss that costs a deployment: it is the level people check, and it is one level too coarse. The first and second confuse an availability question with a catalogue or an API question.

Practice about 15 minutes, with paper

Practice 1foundation

A small service is sketched as five boxes: one VPC network, one subnet, two virtual machines, and one disk attached to each machine.

Label every box with its scope, then write down the smallest single failure that takes the service offline, and the smallest change that removes it.

Hint

Do the labelling first and resist deciding anything until it is finished. The failure you are looking for is whichever failure domain appears under more than one box.

Show the worked solution
  1. Label the network and subnet. The VPC network is global. The subnet is regional, so it is reachable from every zone in its region and from nothing outside it.
  2. Label the machines and disks. Both instances are zonal. Each attached disk is zonal too unless it was created as a regional disk, in which case it replicates synchronously into a second zone.
  3. Find the shared domain. If both instances were placed in one zone, that zone sits under both of them and under both disks. Losing it takes four of the five boxes, and the subnet that survives has nothing left to serve.
  4. Make the smallest change. Put the second instance in a second zone of the same region. The subnet does not change, because it was already regional and reachable from the new zone - which is the point of the scope model.

Sanity check. The fix should have touched exactly one box. If your answer added a second subnet, a second network or any connecting object, you have solved the problem a regionally scoped network would have - and the scope of a Google Cloud VPC is what makes that work unnecessary.

Your teacher. If the scope habit has not stuck, ask an agent to list the resource types in any small design you already have and to mark each one zonal, regional or global. The argument you have about the two or three it gets wrong is where the model actually lands.
