Build, admit, deploy - and only the middle step can refuse

working 8 min Capabilities cicd-pipeline and progressive-delivery. Sourced from Cloud Build, Cloud Deploy and Binary Authorization.

The one-minute version

  • Cloud Build is serverless continuous integration: builds made of container steps, triggered from a repository or a pull request, on shared or private worker pools, and it emits software bills of materials and provenance.
  • Cloud Deploy is the delivery half: pipelines with targets, canary and blue-green strategies, approvals and rollback, into GKE and Cloud Run.
  • Binary Authorization sits between them and is the only step here that refuses: it admits only images that satisfy a policy, and it can consume the vulnerability severities from lesson 1103.
  • A build that reports a problem and a gate that blocks a deployment are different things. Reporting is advice; admission control is a rule.
  • First-party private Git has moved: Cloud Source Repositories is retiring, and the successor named on its own page is Secure Source Manager, regionally deployed and single-tenant.

Cloud Source Repositories, the original first-party private Git hosting, is retiring - closed to new customers and heading for shutdown. Its own documentation names the successor: Secure Source Manager, which is regionally deployed and single-tenant. Anything still hosted in the old service needs a destination chosen, and an external Git host is the other supported answer. Check the current status on the product page.
The reframing Three verbs, and only one of them is a control. Build produces an artefact and evidence about it. Admit is the policy decision, and it is the only step that can refuse. Deploy moves an admitted artefact through targets with a strategy and an approval. A team that says "the pipeline enforces our policy" is usually describing a build step, and a build step is advice.

Somebody deploys an image that was pushed by hand and never went through the pipeline. What can still stop it?
Admission control acts when something is deployed, so it covers artefacts that never met the pipeline. The first attributes an admission role to a build service. The third invents a refusal Cloud Deploy does not perform. The fourth is the scanner, which produces evidence rather than a decision.

Private pools exist for exactly this. The first names a trigger mechanism, which decides when a build starts rather than where it runs. The second names an output. The third belongs to the delivery product, not the build one.

The retiring product's own page names Secure Source Manager as the successor. The first names the service that is going away. The second names an artefact store. The fourth is the over-reading - an external host is one supported answer and not the only one.

Practice about 15 minutes, with paper

Practice 1working

A team is asked to guarantee that nothing reaches production unless it was built from a reviewed commit and has no critical vulnerabilities. Their current design adds a scanning step to the build that fails when a critical vulnerability is found. A reviewer asks what happens if an engineer with deploy permission pushes an image directly.

Explain what the current design guarantees and what it does not, add the missing control, and describe how the release then reaches production safely.

Hint

The reviewer's question is the whole point. Only one step on this page can refuse, and it is not in the build.

Show the worked solution
  1. What it guarantees. That builds passing through this pipeline do not carry a critical vulnerability at build time. Within the pipeline, it is a real control.
  2. What it does not. Anything about images that arrive another way. A failing build step stops a build; it does not stop a deployment, so an image pushed directly by somebody with the permission is unaffected by it.
  3. Add the control. Binary Authorization, with a policy that admits only images carrying the required attestations. Artifact Analysis supplies the vulnerability metadata and the build supplies the provenance, and the policy is evaluated at deployment - which covers the direct push.
  4. Describe the release path. Cloud Deploy pipeline with targets, promoting the same admitted image through them rather than rebuilding. An approval before the production target, a canary or blue-green strategy on it, and rollback available if the release misbehaves.
  5. Name what remains a people problem. "Built from a reviewed commit" is enforced by the repository's review settings, not by anything on this page. The pipeline can attest that a build came from a commit; whether that commit was reviewed is decided where the code is hosted.

Sanity check. Your added control should act at deployment, and your last point should have identified a requirement no product on this page satisfies. If the answer solved the direct push by removing deploy permissions, that is a real mitigation and it is IAM rather than delivery.

Your teacher. Ask an agent one question about any pipeline: what stops an artefact that never went through it. If the answer names a build step, the pipeline documents a policy rather than enforcing one.
