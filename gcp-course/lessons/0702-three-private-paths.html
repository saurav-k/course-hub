Module 07 · Networking and delivery · Lesson 0702

Three mechanisms are called private, and they are not variations of one thing

working 7 min Capabilities private-google-access, private-services-access and private-endpoint. Sourced from Private Service Connect and Private Services Access.

The one-minute version

  • Private Google Access is a subnet flag. It lets machines with no external address reach Google's own APIs over internal paths.
  • Private Services Access is a peering-based connection into a producer VPC. It is how a managed service such as Cloud SQL gets a private address in your network.
  • Private Service Connect is a consumer-controlled endpoint, built on global forwarding rules and addresses, and it also lets you publish your own service for others to reach the same way.
  • The verified inventory is directional: new designs should prefer Private Service Connect over the peering-based mechanism.
  • The three names differ by two words, and the distinction between the last two is one of this platform's most reliable traps.

1. The three, told apart by what is on the other end

Private Google Access is the one that surprises people by being a checkbox. It lives on the subnet, alongside the other subnet-level toggles from lesson 0700, and it pairs naturally with an organisation policy that forbids external addresses - the guardrail removes the public path and the flag supplies the private one.

2. Peering into a producer, and owning an endpoint instead

The Private Services Access and Private Service Connect names differ by one word and describe different mechanisms with different address consumption, different ownership and different lifecycles. When reading a design document, an incident write-up or an examination question, the safe move is to check which object exists - a peering with an allocated range, or an endpoint address - rather than to trust the phrase.
The reframing Three sentences, worth memorising in this shape. Private Google Access is a property of a subnet. Private Services Access is a peering that costs you a range. Private Service Connect is an endpoint you own, and it also publishes. Everything else about the three follows from which of those objects exists.

Check yourself

Retrieval practice

Answer from memory before revealing.

Machines with no external address must call Google's own APIs. What is needed?
This case is a subnet flag rather than a connection. The first two create objects the case does not need. The third would work by sending the traffic out to the internet, which is the thing being avoided and would also consume the port budget from lesson 0701.
What does the peering-based mechanism cost that the endpoint mechanism does not?
Peering consumes a range while an endpoint consumes an address, which is the difference that compounds across an estate. The first invents a regional limit. The third invents a billing distinction. The fourth claims filtering is bypassed, which would contradict the distributed enforcement of the previous lesson.
Which capability does only Private Service Connect provide?
Publishing is the half that has no counterpart in the peering mechanism. The second and third are true of more than one of the three, so neither separates them. The fourth describes a naming concern rather than a capability unique to one mechanism.

Practice about 12 minutes, with paper

Practice 1working

A platform team runs an internal risk-scoring service and wants twelve other teams, in twelve separate VPCs, to call it privately. Those same teams also run workloads with no external addresses that read from Cloud Storage, and several use Cloud SQL with private addressing set up two years ago.

Pick a mechanism for each of the three needs, say which of the three is a subnet setting rather than a connection, and state what you would change about the two-year-old arrangement and what you would not.

Hint

Three needs, three mechanisms, one each. The last part is about the difference between a documented preference and a reason to rebuild something that works.

Show the worked solution
  1. The internal risk service. Publish it with Private Service Connect. Each of the twelve teams creates its own endpoint in its own network, so twelve endpoints exist and no network is peered to another. Nothing else on this page can publish.
  2. Reading Cloud Storage without external addresses. Private Google Access. It is a flag on each subnet holding those machines, and it needs no object at all.
  3. Name the subnet setting. That second one. The other two create objects with lifecycles - an endpoint, or a peering with an allocated range.
  4. Decide about the existing Cloud SQL arrangement. It uses Private Services Access, and the recorded guidance prefers Private Service Connect for new designs. "New" is doing the work in that sentence: a working private path is not a defect. Record it as the older shape, hold the range it consumed in the address plan from lesson 0700, and move it when the service is next rebuilt rather than as a project of its own.

Sanity check. Your answer should use all three mechanisms exactly once, and only one of them should have created twelve objects. If you migrated the Cloud SQL arrangement immediately, ask what the migration buys today - the answer is an address range and consistency, which is a reason to schedule it and not a reason to hurry.

Your teacher. When a document says "private access", ask an agent which object exists: a subnet flag, a peering with an allocated range, or an endpoint address. The answer names the mechanism unambiguously, and the phrase never does.
