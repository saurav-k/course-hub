The project is the atom, and almost everything else attaches to it

foundation 8 min Capability org-hierarchy. Sourced from Google's resource hierarchy documentation.

The one-minute version

  • The tree is organization, then folders, then projects, then resources. Folders nest up to ten levels deep.
  • Every resource belongs to exactly one project. There is no resource outside a project and none in two.
  • The project is where the platform attaches: APIs are enabled per project, and quotas, service accounts, networks and the billing link all sit at that level.
  • The billing account is not part of the tree. A project links to one, one billing account can serve many projects, and moving a project in the tree does not move its billing.
  • Because the project holds all of that, creating one is the cheap isolation move on this platform - which is why estates here have far more projects than an outsider expects.

1. The tree, and the column beside it

The resource hierarchy is four levels. The organization is the company root, one per Google Workspace or Cloud Identity domain. Folders group projects the way teams and environments group work, and they nest up to ten levels deep. Projects hold resources. Every resource belongs to exactly one.

The billing account is the exception that catches everyone. It is not a level of the tree. A project links to a billing account, and a single billing account can serve many projects, including projects in different organizations. Reorganising the folder tree therefore changes what a project inherits and leaves the bill exactly where it was.

The reframing Ask of any Google Cloud fact: does this attach to the project, or does it flow down the tree? API enablement, quotas, service accounts and networks attach to the project. Permissions and organization policy flow down the tree. Billing does neither - it hangs off the side. Almost every confusion about this platform's tenancy is one of those three being mistaken for another.

2. What the project actually holds

API enablement is the branch that surprises people most. A Google Cloud service is off in a new project until it is enabled there, so a script that works in one project can fail in an identical one for no reason visible in the code. Quotas behave the same way: they are per-project service limits, both rate limits and allocation limits, and raising one is a per-project request. Some increases need billing history, which is a real constraint on a project created this morning.

Because all of that is per-project, a project is the cheapest isolation boundary the platform sells. Separating two workloads into two projects separates their API surface, their quota pools, their default network and their service accounts in one move. That is why a real Google Cloud estate has many more projects than an engineer coming from an account-per-environment model expects, and why Shared VPC exists at all: it is the deliberate exception that lets one host project own the networks that many service projects build in.

3. Where the tree earns its keep

Module 08 works permissions properly. What belongs here is the shape: a grant made anywhere on the ancestor chain applies to everything below it, so height in the tree is reach. That is also why the tree is worth designing rather than growing - folders that mirror how you want permission and policy to spread will keep giving you the right blast radius, and folders that mirror last year's org chart will not.

One part of this area is recorded in the research behind this course as verified in outline but not in detail: Google Cloud also supports creating a standalone organization without a Google Workspace super-admin. The hierarchy documentation confirms the flow exists, and the exact mechanics were left unverified rather than guessed, so this course names it and stops there. Check the hierarchy documentation before designing around it.
What this certification tests The hierarchy is examined as a setup task rather than as theory. The Associate Cloud Engineer guide puts Setting up a cloud solution environment at about 20 per cent of the exam, and its first section covers exactly this material: creating projects, assigning them to a billing account, and assessing quotas. The billing link being separate from the tree is the detail those questions turn on most often.

Check yourself

Retrieval practice

Answer from memory before revealing.

A project is moved from one folder to another folder in the same organization. What changes?
Inheritance follows the ancestor chain, so moving the project changes what flows down to it. Billing is off-tree and does not move, which makes the first option the trap. APIs are enabled on the project itself and are unaffected, and folders have no region at all, so the fourth option is a category error.
A script works in the development project and fails in an identical production project with a service-not-available error. What is the likeliest cause?
APIs are enabled per project, so an untouched project has the service switched off however identical the code is. The first two describe real differences that would produce permission or billing errors rather than this one. The third is a category error - a project has no region, only its resources do.
An operator needs one grant to reach every project a team will ever create. Where should it be attached?
A folder-level grant reaches every project beneath it, including ones created later, which is exactly the requirement. The second option works and does not survive the next project. The third grants nothing on resources, because billing is not part of the tree. The fourth would work and is far too wide, and the claim inside it is false - folders inherit too.

Practice about 15 minutes, with paper

Practice 1foundation

A company has two business units, each with development, staging and production environments, and one finance team that must see a single bill for everything.

Draw the hierarchy you would build, then write down which of the two requirements the tree satisfies and which one it does not touch at all.

Hint

Count the projects first. Then ask which of the two requirements is about inheritance and which is about a link that hangs off the side of the tree.

Show the worked solution
  1. Count the projects. Two business units times three environments is six projects, because environment separation on this platform is project separation - separate APIs, quotas, service accounts and default networks.
  2. Shape the folders. A folder per business unit, and a folder per environment inside it, gives every future grant two useful heights: everything for one unit, or everything of one environment inside one unit. Ten levels of nesting are available and two are enough.
  3. Satisfy the first requirement. The unit boundary is now an inheritance boundary, so a permission or a policy attached to a unit folder reaches that unit's six-project future and nothing else.
  4. Notice what the tree did not do. The single bill is not a tree property. All six projects link to one billing account, and they would do so whatever the folder shape was - so the finance requirement is satisfied by the off-tree link and is entirely independent of the drawing.

Sanity check. Exactly one of the two requirements should have been solved by the folder shape. If your answer put finance somewhere in the tree, or created a folder whose only job is billing, the off-tree position of the billing account has not landed yet.

Your teacher. If the project boundary still feels arbitrary, ask an agent to name every platform setting that is per-project and every one that is inherited, then check its list against this page. The three or four it misfiles are the ones worth arguing about.
