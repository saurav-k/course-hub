A recurring Spark job is two decisions, and they are independent

working 7 min Capabilities managed-spark and workflow-orchestration. Sourced from Dataproc, Managed Service for Apache Spark and Cloud Composer.

The one-minute version

  • Decision one is how much of the Spark cluster you run. Two products sit under that capability, and they are two rungs of the same ladder.
  • Dataproc gives you fast ephemeral Hadoop and Spark clusters on Compute Engine, with Spot workers and autoscaling. Choose it when you need cluster control or Hadoop ecosystem pieces.
  • Managed Service for Apache Spark is zero-ops serverless Spark, in batches and sessions. The inventory says to prefer it for new Spark jobs that have no cluster needs.
  • It used to be called Dataproc Serverless, and the rename is one of this platform's live naming traps.
  • Decision two is what submits the job. Cloud Composer is managed Apache Airflow for data pipeline DAGs, and it is a separate product from the runtime.

1. The Spark ladder, and where it points

The rename matters more than a rename usually does. Managed Service for Apache Spark was Dataproc Serverless, so older material, internal runbooks and muscle memory all point at a name the console no longer uses, while the product itself is the recommended one. This module's other rename in the same family is Managed Service for Apache Kafka from the previous lesson, and Cloud Composer is the managed Airflow - three separate products whose names share a pattern.

2. What "ephemeral cluster" means as a lifecycle

On the serverless rung none of this is visible: batches and sessions are submitted and the platform decides what runs them. That is the whole trade. You give up the ability to place a Hadoop component beside your Spark job, and you stop owning a lifecycle.

3. The second decision, which is a different product

Two products share the orchestration capability on this platform and they are not interchangeable. Cloud Composer is managed Airflow for data pipeline DAGs. Workflows, which module 12 covers, is the lighter API-and-service orchestrator. Reaching for Composer to sequence two API calls buys an Airflow environment nobody needed, and reaching for the lighter tool to run a data DAG loses the ecosystem that made Airflow the answer.
The reframing Write the two decisions down separately. Runtime: do we need cluster control or a Hadoop component - if not, the serverless rung. Schedule: what owns the order and the retries - and the answer is a product, not a cron line inside the job. A design that answers only the first has a job that runs when somebody remembers.

Check yourself

Retrieval practice

Answer from memory before revealing.

A new Spark job needs no Hadoop components and no control over the cluster. What does the inventory record as the preference?
The documented preference for new jobs with no cluster needs is the serverless rung. The second reverses the guidance. The third swaps engines and rewrites the job. The fourth confuses the orchestrator with a runtime - Composer submits work, it does not execute Spark.
What is the practical risk of the Dataproc Serverless rename?
It is the same product under a new name, so the cost is in searching, documentation and habit. The first invents a retirement. The third claims a different product, which would be a much larger problem. The fourth confuses two services that merely share a naming pattern.
Which orchestration product suits sequencing a Spark job and the SQL that depends on it?
A data pipeline DAG is exactly what Composer is for. The first names the lighter orchestrator that module 12 covers, which is the right answer to a different question. The second replaces a dependency with a guess about timing. The fourth puts SQL on a Spark cluster to avoid naming an orchestrator.

Practice about 12 minutes, with paper

Practice 1working

A team is moving an on-premises nightly chain into Google Cloud. It has one Spark job that reads yesterday's files, one step that uses an ecosystem component from the Hadoop distribution, and one SQL report that must run only after both succeed. Cost pressure is high and the chain is not urgent - a rerun the next morning is acceptable.

Choose a runtime for the Spark work, justify the choice against the documented guidance, name what owns the order, and state the cost lever the tolerance for reruns unlocks.

Hint

One sentence in the requirements rules out the preferred rung. A different sentence unlocks a lever that only the other rung offers.

Show the worked solution
  1. Test the preferred rung. The guidance prefers the serverless service for new jobs without cluster needs. This chain has a Hadoop ecosystem component, which is a cluster need, so the condition fails.
  2. Choose the runtime. Dataproc, on an ephemeral cluster created for the chain and deleted after it. The Hadoop component sits beside the Spark job, which is the documented reason to be on this rung.
  3. Name what owns the order. Cloud Composer. The dependency - report after both jobs - is a DAG edge, and it belongs in the orchestrator rather than inside either job.
  4. Take the cost lever. Spot workers. They are reclaimable, so they suit work that can be rerun, and the stated tolerance for a next-morning rerun is exactly the condition that makes them safe here. Autoscaling shrinks the cluster when the chain does not need it.

Sanity check. Your runtime answer should have been forced by one requirement rather than chosen by preference, and the cost lever should have been unlocked by another. If Spot workers felt risky, note that the requirement explicitly permits a rerun - that permission is the whole justification.

Your teacher. If a chain is being lifted from an existing cluster, ask an agent to list every component the jobs touch that is not Spark itself. An empty list points at the serverless rung, and a single entry on it is usually what keeps a team on Dataproc for another year.
