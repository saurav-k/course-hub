One file-storage row holds four engines, and the protocol picks first

working 9 min Capability file-storage. Sourced from Google's Filestore overview.

The one-minute version

  • Four managed engines answer one capability: Filestore, NetApp Volumes, Managed Lustre and Parallelstore.
  • Protocol decides first. Filestore is managed NFS. NetApp Volumes serves NFS and SMB, so a Windows-facing share has one obvious home.
  • Filestore spans tiers from Basic through Enterprise and High Scale, and multishares split one instance into many exports.
  • NetApp Volumes brings the ONTAP feature set, including cross-region replication and snapshot-style replication between volumes.
  • The two parallel filesystems split on access pattern: Lustre for throughput-heavy data loading, Parallelstore for latency-sensitive, metadata-heavy work.

1. Protocol first, then pattern

Filestore is the managed NFS service and the default answer for shared file storage: volumes for GKE workloads, and lift-and-shift applications that expect a mount point. Its tiers run from Basic up through Enterprise and High Scale, and multishares let one instance be divided into many exports rather than requiring an instance per share.

Google Cloud NetApp Volumes is the enterprise NAS answer, running ONTAP, serving NFS and SMB, and bringing the replication features that come with that lineage, including cross-region replication between volumes. It is named explicitly in the Associate Cloud Engineer exam guide, which is a fair signal of how often it is the right answer in practice.

2. The two parallel filesystems, and the line between them

Managed Lustre is the fully managed Lustre filesystem, optimised for the read-heavy data loading that machine-learning training does. Parallelstore is built on DAOS and targets very low latency. The research behind this course states the split in one line, and it is the line worth carrying: choose Lustre for throughput-heavy data loading, and Parallelstore for latency-sensitive, metadata-heavy input and output.

The reframing Four products under one capability key is not indecision on the vendor's part. Two of them differ by protocol and feature set, and the other two differ by what the input and output actually looks like. Ask the two questions in that order - what does it speak, and what does its traffic look like - and the four collapse to one every time.

3. The bucket that pretends to be a filesystem

One more option belongs in a file-storage conversation without being a file service. Cloud Storage FUSE mounts a bucket so that code expecting a filesystem can read and write objects. It is the right tool when the requirement is really "this program wants a path", and it is not a shared filesystem with file semantics underneath. The next page returns to it, because it is also the answer the platform gives to a question it has no product for.

Check yourself

Retrieval practice

Answer from memory before revealing.

A Windows application needs a shared file volume. Which engine is the obvious candidate?
The protocol question resolves it: NetApp Volumes serves SMB. The first option reaches for a tier of a managed NFS service. The second and third pick parallel or specialised systems for a general workload, and the third also misdescribes Lustre as the general answer.
A training cluster is idle waiting for data while reading one large dataset from many nodes. What is the useful move?
Concurrent readers are what parallel filesystems are for, and that is the property a bigger share does not add. The first option is the intuitive answer and buys capacity rather than concurrency. The third loses the shared view the nodes need. The fourth names a preview class and a mount layer rather than solving the concurrency problem.
What separates Managed Lustre from Parallelstore?
They sit at opposite ends of the access-pattern axis, which is why both exist. The first is false about both, since both are managed. The second invents a protocol split. The fourth invents a succession that would make the choice trivial, which is exactly why it is tempting.

Practice about 15 minutes, with paper

Practice 1working

A migration brings three workloads onto Google Cloud: a legacy reporting application whose Windows servers share a volume, a Linux content management system that mounts an NFS export, and a machine-learning team whose training jobs read one dataset from thirty-two nodes at once.

Assign an engine to each, state the question that decided each assignment, and note the one assignment you cannot finish from the information given.

Hint

Two of the three are decided by the first question alone. The third needs the second question, and the stem does not answer it.

Show the worked solution
  1. The Windows share. Decided by protocol: SMB points at NetApp Volumes. No performance discussion is needed to reach it.
  2. The Linux content system. Decided by protocol and by not being parallel work: managed NFS, so Filestore, with the tier chosen from its capacity and performance needs and multishares available if several exports are wanted from one instance.
  3. The training workload. Thirty-two concurrent readers is the parallel branch, so it is Lustre or Parallelstore and not a general file service.
  4. Name the missing information. The stem does not say whether the job is throughput-bound on large sequential reads or latency-bound with heavy metadata activity, and that is exactly the question that separates the two. The honest answer is to measure the access pattern rather than to pick the more familiar name.

Sanity check. Two assignments should be firm and one should end in a question. If all three came out firm, check what evidence chose between Lustre and Parallelstore - if it was familiarity rather than the access pattern, the decision was made without its input.

Your teacher. If a file requirement is vague, ask an agent to state it as a protocol and an access pattern before naming any product. Most file-storage arguments end the moment those two are written down.
