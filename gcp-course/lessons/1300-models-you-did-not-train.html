A prompt, or an API that already knows the task

working 7 min Capabilities managed-model-api and speech-vision-document-ai. Sourced from Vertex AI generative models and Document AI.

The one-minute version

  • Vertex AI serves the Gemini family and a Model Garden of more than two hundred models behind one managed surface, including tuned endpoints.
  • Two features change the shape of an application rather than a setting: grounding, which ties a response to sources, and context caching, which reuses a large repeated context.
  • The other shape is a task API. Speech-to-Text, Translation, Vision and Document AI already know their task, so there is no prompt to design and no output format to negotiate.
  • Those task services each have their own console and pricing, so they are separate products under one shared capability row rather than one service with four modes.
  • The decision is not about model quality. It is about how much of the problem you want to own - a prompt, an evaluation and an output contract, or none of the three.

The reframing Two questions, in order, and the second is only reached if the first fails. Is this a task somebody already built an API for? If yes, the work is integration. If not, what is the smallest model that answers it? - asked as a configuration value, with grounding designed in from the start if the answer must rest on your own material.

Check yourself

Retrieval practice

Answer from memory before revealing.

A workload must transcribe recorded calls. Why start with the task API rather than a general model?
The task API removes the prompt, the output contract and the evaluation, which is where the real cost of the general path sits. The first invents a limitation. The second and fourth assert commercial claims the inventory does not record.
What does grounding change about a model response?
Grounding is the correctness feature and attaches an answer to sources. The second describes context caching, which is the other feature on the same page. The third describes output formatting. The fourth invents routing.
What follows from the four pretrained task services sharing one capability row?
The row is a taxonomy convenience and the four are separate products with separate consoles and pricing. The first two draw operational conclusions from a classification. The third is close to right and stops before the useful half of the answer.

Practice about 12 minutes, with paper

Practice 1working

An insurer wants to process claim submissions. Each submission has a scanned form, a photograph of the damage, and a voice message from the customer. The team also wants a short natural-language summary of the whole claim, resting only on the documents supplied. A proposal suggests sending all three files to a general model with one long prompt.

Assign each of the three inputs, place the summary, name the feature that makes the summary trustworthy, and say what the proposal would have made the team own.

Hint

Three of the four requirements are tasks that already have APIs. The fourth is the one that genuinely needs a general model, and it has a named feature attached to the words "resting only on".

Show the worked solution
  1. The scanned form. Document AI, whose processors extract structured fields from a document kind rather than describing an image. The output is a defined shape.
  2. The photograph. Vision, which is the task API for image analysis.
  3. The voice message. Speech-to-Text. If the customer's language varies, Translation is the fourth task API in the same row.
  4. The summary. A general model from the Gemini family - this is the one requirement no task API covers, because summarising a whole claim is not a defined task with a defined output.
  5. Name the feature. Grounding. "Resting only on the documents supplied" is a correctness requirement about sources, and grounding is what ties the response to them rather than to the model's own recollection.
  6. Say what the proposal would have cost. Ownership of everything the task APIs already solve: a prompt that reliably extracts the form's fields, an output contract for them, and an evaluation proving it works across the range of forms and photographs the insurer receives. That is three engineering programmes traded for one prompt.

Sanity check. Three of your four assignments should be task APIs, and the general model should appear exactly once. If the whole claim went to one prompt, ask how you would prove the extracted policy number is right - the task API answers that with a defined output, and the prompt answers it with an evaluation you have to build.

Your teacher. Before writing a prompt, ask an agent whether a pretrained API already performs the task. Where one does, the remaining work is integration, and where none does, you have just learned that the prompt, the output contract and the evaluation are all yours.
