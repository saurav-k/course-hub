Module 04 · Storage · Lesson 0400

A bucket names itself out of one namespace shared by every customer

working 10 min Capabilities object-storage and object-storage-highperf. Sourced from Google's Cloud Storage introduction.

The one-minute version

  • Bucket names are globally unique across all of Google Cloud, so the name you want is competing with every other customer's, not only with your own organisation's.
  • The object model is buckets, objects, folders and managed folders, with a hierarchical namespace mode for workloads that behave like a filesystem.
  • Uniform bucket-level access is how access is expressed at the bucket rather than object by object, and the bucket also speaks an S3-compatible interface.
  • Soft delete is on by default with a seven-day window, which is a real safety net and also a real cost you did not ask for.
  • A single object tops out at 5 TiB, and a Rapid zonal class exists for high-performance co-located workloads - in preview, so check its stage before designing on it.

1. One namespace for everybody

Bucket names live in a single namespace spanning all of Google Cloud. That has two consequences worth internalising before the first bucket is created. Obvious names are gone, so a naming convention that includes something specific to your organisation is not a nicety. And a bucket name is a public fact: choosing one that encodes a customer name or an unreleased project publishes that word into a namespace anybody can probe.

2. What is inside a bucket

The 5 TiB ceiling on a single object is worth holding as a design fact rather than a trivia item. Any pipeline that produces one growing artefact - a database dump, a media master, a model checkpoint set written as one file - eventually meets it, and the fix is a chunking decision that is much cheaper to make before the data exists.

3. The default that quietly protects you

That is the honest shape of the feature: a strong default for the common case and a surprise on the bill for the uncommon one. A short-lived scratch bucket used by a pipeline that churns objects is exactly the case where the default deserves a second look.

4. Where a bucket sits, and what a second copy costs

The location and the default storage class are both fixed at bucket creation, which makes bucket creation a design decision rather than a setup step. Google's availability and durability page is the reference for what each location shape promises, and it is the page to read when a requirement is stated as a number.

A newer zonal class exists: Rapid storage, a high-performance object class with hierarchical namespace and streaming appends, meant for analytics and machine-learning work co-located with the data. The research behind this course recorded it as preview and explicitly flagged that its stage should be re-checked before it is taught as settled. Read it as a direction the product is moving in rather than as something to design a production system around today.
The reframing Five properties of a bucket are chosen at creation and are awkward or impossible to change afterwards: the name, the location, the default storage class, whether the namespace is hierarchical, and whether access is uniform at the bucket level. That is why bucket creation deserves a review and a two-minute conversation, and why a bucket created by a script during a demonstration tends to become a permanent fixture with the wrong properties.

Practice about 15 minutes, with paper

Practice 1working

A team is about to create the bucket that will hold a product's uploaded media for the next several years. Someone runs a command with a short obvious name, in the default location, and moves on.

List the properties that decision just fixed, and say for each one what going back would actually involve.

Hint

There are five, and every one of them is set at creation. For each, ask whether the fix is a setting, a copy, or a new name that other systems already reference.

Show the worked solution
  1. The name. Fixed, and taken from a namespace everyone shares. Changing it means a new bucket and updating every reference anything has stored - including references in other people's systems if the bucket was ever shared.
  2. The location. Fixed at creation, so moving means copying the data to a new bucket in the right place and cutting over. For years of media that is a transfer project rather than a setting.
  3. The default storage class. Fixed at creation. Existing objects can be managed by lifecycle rules, but the bucket's default follows the bucket.
  4. The namespace mode and the access mode. Whether the namespace is hierarchical and whether access is uniform at the bucket level are both creation-time choices, and both change how every consumer addresses and is authorised against the data. Retrofitting either is a migration with an audit attached.

Sanity check. Every item on your list should have a remedy that is a copy or a migration, and none of them should be a checkbox. If any came out as a simple setting change, check it against the creation-time list - the reason bucket creation deserves a review is that none of the five is cheap afterwards.

Your teacher. If the creation-time properties are hard to remember, ask an agent to produce the command that creates a bucket with all five stated explicitly. Writing them down once, even at defaults, is what turns them from invisible into decisions.
