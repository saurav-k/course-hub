Bigtable trades transaction scope for scale, and Firestore does the reverse

working 7 min Capabilities nosql-keyvalue, nosql-document and timeseries-database. Sourced from Bigtable and Firestore.

The one-minute version

  • Bigtable is a wide-column store at petabyte scale. Its three shaping constraints: single-row transactions only, eventually consistent replication, and an HBase-compatible interface.
  • Firestore is a serverless document store with two modes - Native mode with live sync and offline support, and Datastore mode.
  • Firestore carries multi-region strong consistency options, point-in-time recovery and TTL policies, which are the properties an application database usually asks for.
  • Firestore's MongoDB compatibility is an interface layer, not a MongoDB engine. Read it as an interface promise and check the surface you actually use.
  • There is no dedicated managed time-series database. Google's documented pattern is Bigtable for time series.

1. Two stores, two centres of gravity

Bigtable earns its scale by keeping the write path narrow, and the narrowness is visible in its contract. Firestore spends its effort on what an application needs from a database that is not a spreadsheet of rows - recovery to a point in time, expiry of documents, and a client that keeps working while the network does not.

2. The constraint that decides most Bigtable designs

Eventually consistent replication is the second half of the same bargain. A Bigtable design that spans clusters accepts that a read served by one cluster may not yet reflect a write accepted by another, and it either tolerates that or it routes reads and writes to the same place. The HBase-compatible interface is the third property, and it is the one that makes an existing HBase workload a lift rather than a rewrite.

Firestore's MongoDB compatibility is an interface layer on Firestore, not a MongoDB engine. The distinction is the difference between "your driver connects" and "your database behaves the same", and only the first is what is offered. Check the specific surface a workload depends on against the Firestore documentation before treating a MongoDB migration as a configuration change.

3. The time-series row, and why it is a gap rather than a Bigtable row

Cloud Monitoring does hold a time-series store, and module 10 covers it, but it is internal to the observability service rather than a database an application writes into. The one product that looked like a counter-example, the Timeseries Insights API, is retired.

The reframing Choose between these two by asking what the application does with a key. If it reads and writes one entity at a time at enormous rate, and the invariant fits inside that entity, it is a Bigtable shape. If it wants documents, recovery, expiry and a client that survives a lost network, it is a Firestore shape. If the answer is "both", the requirement has not been split yet.

Retrieval practice

Answer from memory before revealing.

An application must update two related records as one atomic unit at very high write rates. What does Bigtable's contract say?
Transactions are single-row, so the invariant is moved into one row at design time. The first two invent a cross-row guarantee that is not offered. The third describes an error path, but there is no failure to retry - the operation is simply not part of the contract.
What is the accurate reading of Firestore's MongoDB compatibility?
It is an interface layer on Firestore, which makes a driver connect without making the database behave identically. The first is the over-reading that turns a migration estimate wrong. The third and fourth describe a migration tool and a client library, neither of which is what compatibility means here.

Practice about 15 minutes, with paper

Practice 1working

A fleet-telemetry platform ingests one reading per vehicle per second from a large fleet, and keeps a year of it for range queries over a vehicle and a time window. A separate mobile application shows drivers their own trip history, works on a train with no signal, and must let a support agent restore a driver's records to how they looked before a bad bulk edit.

Place each of the two workloads, justify each placement with one property, and name the part of the first workload that is design work rather than a product feature.

Hint

The first workload names a shape the inventory records as a gap. The second names three properties that appear in exactly one product's list on this page.

Show the worked solution
  1. Place the telemetry. High-rate ordered writes with range reads over a window is a time-series shape, and the documented pattern for it is Bigtable. Its scale is the property that justifies it, and the single-row transaction limit costs nothing here because each reading is independent.
  2. Place the mobile application. Offline operation on a train is Native-mode live sync and offline support. Restoring records to a previous state is point-in-time recovery. Both properties are Firestore's, so the placement is settled by two independent requirements rather than by preference.
  3. Name the design work. Because there is no dedicated time-series product, the row key that puts a vehicle and a time in an order that makes range reads cheap is yours to design, and so is the expiry of data past a year. In a time-series product those would be a schema setting and a retention policy.
  4. Check what neither placement needs. Nothing here asks for a transaction spanning two entities, which is why no part of this reaches back to the relational pages.

Sanity check. Each placement should rest on a property named on this page rather than on "NoSQL is fast". If your telemetry answer treated Bigtable as a time-series product, re-read the third figure - the missing piece is exactly the row-key and retention work you have to do yourself.

Your teacher. If a workload seems to want both stores, ask an agent to list the operations that must be atomic and the largest object each one touches. When the atomic operations all fit inside one entity you are in Bigtable territory, and when they do not, you are being told which product to use.
