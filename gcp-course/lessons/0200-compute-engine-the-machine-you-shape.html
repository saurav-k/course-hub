Module 02 · Compute · Lesson 0200

A Compute Engine machine is shaped by dial, and its host moves under it

working 10 min Capability vm-instances. Sourced from Google's machine families reference.

The one-minute version

  • You pick a machine family first - general-purpose, memory-optimized, compute-optimized, storage-optimized, network-optimized or accelerator-optimized - and the family decides the hardware profile.
  • Inside a family you can go beyond the catalogue: custom machine types let you choose CPU and memory independently, so the shape of the machine follows the workload rather than the price list.
  • Live migration is the default. Host maintenance moves a running instance rather than rebooting it, so most maintenance is invisible from inside the guest.
  • The platform watches every instance without an agent, at about one-minute granularity, and an agent is only needed for what the hypervisor cannot see.
  • There is no bundled fixed-price virtual private server here. Everything is billed per component, and the discount mechanisms are commitments rather than a flat monthly price.

1. Family first, size second

The machine families reference is the catalogue, and the general-purpose family carries the widest set of series - E2, N2, N2D, C3, C4, C4A and C4D - because it is where most workloads start. The other five families exist because a workload that is short of memory, of per-core speed, of local input and output, of bandwidth, or of accelerator time is not helped by more of everything.

2. The dial the catalogue does not have

The cost of the dial is the loss of a shorthand. A predefined type is a name two engineers can say to each other, and a custom shape is a pair of numbers that has to be written down somewhere. That matters more than it sounds, because the commitment discounts described in module 09 are bought against a machine family in a region, so a fleet of individually tuned shapes is harder to cover with one commitment than a fleet of identical ones.

3. Maintenance that does not reboot the guest

Live migration is the platform behaviour that most changes how a Compute Engine design reads compared with the same design elsewhere. It does not remove the need for more than one instance - a zone can still be lost, and the previous module was about exactly that - but it does remove the need to plan around a maintenance reboot on a schedule you do not control.

Live migration is the default and not a universal guarantee. Some instance configurations, including the discounted reclaimable form on the next page but one, do not behave this way, and an instance can still be terminated for reasons other than routine maintenance. Read the behaviour on the machine documentation for the exact configuration you are about to build, rather than carrying the default forward as a promise.

4. What the platform sees without being asked

An instance emits hypervisor-visible processor, disk and network metrics into Cloud Monitoring automatically, at roughly one-minute granularity, with no agent installed. What the hypervisor cannot see - memory pressure inside the guest, application logs, per-process detail - needs the Ops Agent, which carries logs and metrics in one installation. Module 10 works the telemetry properly; the fact worth carrying into a compute design is that the free tier of visibility stops at the guest boundary.

5. The shape this platform does not sell

One compute packaging is genuinely absent here, and the research behind this course records it as an absence rather than as a naming difference: there is no bundled fixed-price virtual private server, the kind sold as one predictable monthly figure with compute, storage and transfer included. Compute Engine bills per component. The nearest arrangement is an E2 machine type with a committed use discount, which lowers the rate and still bills each component separately.

The reframing Read that absence precisely. It does not say small cheap machines are unavailable - it says the bundle is. A workload that wanted a predictable monthly number gets it here by choosing a shape and committing to it, which is a budgeting exercise rather than a product. Committed use discounts come in a resource-based form, tied to a machine family in a region, and a spend-based form, tied to an hourly amount that flexes across services.

Check yourself

Retrieval practice

Answer from memory before revealing.

A workload needs many virtual CPUs and unusually little memory. What does Compute Engine offer that a fixed catalogue does not?
Custom machine types break the fixed ratio between processor and memory, which is exactly this workload's problem. The first option moves in the wrong direction along the ratio. The second invents a discount that does not exist. The third solves nothing and doubles the instances to manage.
Google needs to perform maintenance on the physical host running your instance. What is the default behaviour?
Live migration is the default, so the guest keeps running through host maintenance. The first and fourth describe what happens on platforms without it, and both are what a design assumes if the default is not known. The third would mean hosts are never maintained, which is not a promise any provider makes.
A team wants one predictable monthly price covering compute, storage and transfer for a small instance. What does Google Cloud offer?
The bundled virtual private server shape is genuinely absent here, and the honest answer is to size a machine and cover it with a commitment. The other three each invent a product with a plausible-sounding qualifier attached, which is how an absence usually gets papered over in a design review.

Practice about 15 minutes, with paper

Practice 1working

A batch encoder is profiled and found to saturate its processors while using a small and stable amount of memory. It currently runs on a predefined general-purpose shape, and the team wants both a better fit and a lower rate.

Work out the two independent decisions available here, and say which one has to be made first and why the order matters.

Hint

One decision changes what the machine is. The other changes what it costs. Ask which of the two you can undo cheaply.

Show the worked solution
  1. Separate the two decisions. The first is the shape - which family, and whether to leave the catalogue for a custom machine type. The second is the rate - whether to cover the running machine with a committed use discount.
  2. Fix the shape. The profile says processors are the bottleneck and memory is not, so a compute-optimized family, or a custom shape with high processor count and low memory, both stop paying for memory the workload does not touch.
  3. Then fix the rate. A resource-based commitment is bought against a machine family in a region, so buying it before the family is settled commits to the family you were about to leave.
  4. State why the order matters. The shape is a redeploy and the commitment is a term. Doing them in the wrong order locks the cheaper rate onto the wrong machine for the length of the commitment, which is worse than not discounting at all.

Sanity check. Your answer should have shape before rate, and the reason should be about reversibility rather than about size. If you concluded that the discount should be bought first to save money while testing, notice that a resource-based commitment names a family - so it is not a saving during an experiment, it is a bet on the experiment's outcome.

Your teacher. If family choice still feels arbitrary, ask an agent to take a workload you know and name which resource it is short of before naming any machine type. The families exist to answer that question, and a machine chosen without it is a guess with a price attached.

Primary source to go deeper

The machine families and resources reference is the catalogue itself: the families, the series inside each one, and the rules that govern custom shapes. It is the page to read before committing to any machine type, because the series available in a family change more often than the families do.
