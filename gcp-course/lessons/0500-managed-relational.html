Cloud SQL runs the engine you already know, AlloyDB changes it

working 7 min Capabilities relational-managed and relational-serverless. Sourced from Cloud SQL and AlloyDB.

The one-minute version

  • Two products share the managed relational row. Cloud SQL runs MySQL, PostgreSQL and SQL Server as they are. AlloyDB runs one engine only, and that engine is not stock.
  • Cloud SQL's shape is a high-availability pair plus read replicas, and its Enterprise Plus tier adds near-zero-downtime maintenance, a caching layer and read-pool autoscaling.
  • AlloyDB is PostgreSQL-compatible with a columnar engine built in, so one database answers transactional and analytical queries. It also takes cross-region replicas.
  • Choose by engine first. Only Cloud SQL offers MySQL and SQL Server, so those two workloads never reach the AlloyDB question at all.
  • There is no serverless relational database on this platform. Three services come close and none of them scales to zero.

1. One row, two products, and the question that separates them

Cloud SQL is the ordinary answer and it is deliberately unremarkable: the engine behaves as the engine does, and Google operates the machine under it. Its Enterprise Plus tier is worth naming because it changes an operational property rather than a functional one - maintenance that would otherwise interrupt connections becomes near-zero-downtime, and read pools autoscale. Customer-managed encryption keys are supported, which is the hook module 08 picks up.

2. What "columnar acceleration built in" actually buys

Hybrid transactional and analytical processing - HTAP - is the name for the shaded band, and the ordinary answer to it is two systems with a pipeline between them. AlloyDB puts the second layout inside the first database instead. The cost is the one the diagram does not show: an engine that is PostgreSQL-compatible is not the same object as PostgreSQL, so compatibility becomes a thing to check rather than a thing to assume, and there is only ever one engine to choose from.

The verified inventory behind this course records AlloyDB's Autopilot-style Slices for elastic scaling with an explicit instruction to confirm the stage before teaching it, and records AlloyDB read-pool autoscaling as preview. Neither is stated here as a settled capability. Check the product documentation for the current stage before a design depends on either.

3. The row with nothing in it

This is an absence the verified inventory records deliberately, with its reasoning, so it can be stated plainly rather than hedged. It matters most for the shape of a bill: a fleet of small, mostly idle databases costs the floor times the count, and the platform's answer is to put more schemas into fewer instances rather than to expect the instances to disappear.

The reframing Read the relational row as engine first, then engine behaviour, then cost floor. Engine narrows the choice to one product in two of the three cases. Engine behaviour is the only thing AlloyDB really sells. And the cost floor is a platform property that no product on this row escapes.

Practice about 15 minutes, with paper

Practice 1working

A company is moving forty small PostgreSQL databases into Google Cloud. Each one is idle most of the day. Two of the forty also carry an hourly reporting query that scans a whole table, and the reporting query is currently served by a nightly copy into a separate system.

Decide what the forty land on, say what changes for the two, and state the cost property that no choice on this row removes.

Hint

Three separate questions. One is settled by the engine, one by the query shape, and one is a property of the platform rather than of any product.

Show the worked solution
  1. Settle the engine. PostgreSQL is available on both products, so the engine does not decide this one. That is unusual: for MySQL or SQL Server the question would already be over.
  2. Place the thirty-eight. They are ordinary transactional databases with no analytical shape, so Cloud SQL for PostgreSQL is the plain answer. Nothing about them asks for a reworked engine.
  3. Place the two. A whole-table scan every hour beside ordinary transactions is exactly the mixed band. AlloyDB's columnar acceleration serves both from one copy, which removes the nightly copy and the staleness that comes with it.
  4. Name the cost property. Idle is not free. There is no serverless relational SKU, and the near answers floor above zero, so forty mostly-idle instances bill forty floors. The lever is consolidation - fewer instances carrying more schemas - not an expectation that idle instances stop costing.

Sanity check. Your answer should use both products rather than one, and the reason for the split should be the query shape and not the size of the database. If your third answer was "run them serverless", re-read the state diagram - the zero state is the one nothing on this row reaches.

Your teacher. If you are unsure whether a workload really needs AlloyDB, ask an agent to describe the reporting query you run today and where its data comes from. If the answer names a copy, a nightly job or a second system, you are in the mixed band. If it names the same tables the application writes to, you were already served.
