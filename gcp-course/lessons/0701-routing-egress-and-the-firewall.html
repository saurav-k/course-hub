Nothing sits in the path - routing and filtering are properties of the fabric

working 9 min Capabilities route-table, bgp-dynamic-routing, nat-gateway and stateful-packet-filter. Sourced from Routes, VPC firewall rules and Cloud NAT.

The one-minute version

  • There is no route table object. Routing is VPC-wide, made of system routes, custom static routes with priorities, and dynamic routes learned by Cloud Router over BGP.
  • A custom route is aimed at particular machines with network tags rather than by attaching a table to a subnet.
  • The firewall is enforced at every instance interface, so there is no appliance in the path and no choke point. Rules target network tags, secure tags or service accounts, not only addresses.
  • The implied rules are allow all egress and deny all ingress until something overrides them, and priority decides between a matching allow and a matching deny.
  • Cloud NAT gives private machines outbound internet with no inbound exposure, and its port reservation arithmetic is where designs fail.

1. Three sources of routes, and no table

2. A firewall with no place to stand

Targeting is the part that changes designs. A rule can name a service account or a secure tag rather than an address range, so a policy can say "the payments service may reach the payments database" and stay true when either side is rebuilt with new addresses. Hierarchical firewall policies push rules down from the organisation and folder, which is how a guardrail written once applies below it. Google sells this as the standard tier of Cloud NGFW.

Secure tags are the nearest thing here to routing by intent, and the verified inventory records the difference carefully: they let a rule reference resource tags instead of addresses, and they do not constrain the path independently of the underlying network the way an intent-based policy would. Read them as identity-shaped filtering, not as a separate control plane over the path.

3. Getting out, and the arithmetic that bites

Cloud NAT is regional and managed, and it gives private machines and serverless workloads outbound internet with no inbound exposure. Two levers matter: the reservation arithmetic above, and manual endpoints, which pin the addresses traffic leaves from - the thing a partner's allow-list needs.

The other egress decision is the network service tier. Premium rides Google's own backbone and is the default; Standard uses ordinary internet transit. The tiers documentation is the reference, and the choice is a latency-against-cost decision rather than a functional one.

The reframing Stop looking for the box. Routing is a property of the network plus the tags on a machine. Filtering is a property of every interface. Egress is a regional service with an arithmetic budget. Designs that go wrong here usually do so by trying to recreate a choke point - and a choke point you build yourself is a bottleneck the platform was not going to give you.

Retrieval practice

Answer from memory before revealing.

How is a custom static route aimed at only some machines in a VPC?
Routing is VPC-wide and per-machine targeting comes from network tags. The second imports a route-table model this platform does not have. The third is real targeting for firewall rules but not for routes. The fourth invents a scope that routing does not carry.
What follows from the firewall being enforced at every instance interface?
Distributed enforcement removes both the bypass and the bottleneck. The first misstates where evaluation happens. The second describes the appliance model this design replaces. The fourth reverses the implied rules - ingress is denied and egress allowed.
A growing fleet of private machines starts failing to open outbound connections. What is the likely cause?
Ports are reserved per machine against a supply fixed by the gateway's addresses, so growth crosses a line. The first and second are real failures that would not correlate with fleet size in this way. The third would stop machines being created rather than stop existing ones connecting.

Practice about 15 minutes, with paper

Practice 1working

A regional service runs on private machines with no external addresses. It calls one partner API on the public internet, and the partner requires the calls to arrive from a fixed, small set of source addresses. The team plans to grow the fleet from 200 machines to 900 over a year.

Design the egress, show the arithmetic that decides whether it survives the growth, and state the two facts you would have to look up rather than assume.

Hint

Two separate requirements: getting out at all, and being recognised on arrival. The arithmetic is a product against a supply, and you are being asked to write it as an inequality rather than to know the numbers.

Show the worked solution
  1. Give the fleet a way out. Cloud NAT, regional, in front of the private machines. No machine gains an external address, so no inbound exposure is created by solving the outbound problem.
  2. Satisfy the partner. Manual endpoints on the gateway pin the addresses traffic leaves from, which is what makes an allow-list on the partner's side stable. Letting the platform choose addresses would break the allow-list the first time they changed.
  3. Write the arithmetic. Let p be the ports reserved per machine and n the number of machines. Demand is n × p. Supply is the number of addresses assigned to the gateway multiplied by the usable ports each provides. The design survives while supply is at least demand, so at 900 machines the requirement is supply ≥ 900p - four and a half times the 200-machine requirement of 200p.
  4. Name what to look up. The ports reserved per machine as currently configured, and the usable ports each address provides, both on the Cloud NAT documentation. Neither is assumed here, because a printed number would be the part of this answer that rots.

Sanity check. Your inequality should scale linearly in the machine count, so a fleet growing four and a half times needs its supply to grow by the same factor unless the per-machine reservation is reduced. If your answer gave the machines external addresses to reach the partner, note that it also gave the internet a way to reach them.

Your teacher. If an outbound failure is intermittent and correlates with load, ask an agent for the machine count behind the gateway and the ports reserved per machine, and multiply. A product that has crept past the supply is the answer, and no amount of firewall reading will find it.
