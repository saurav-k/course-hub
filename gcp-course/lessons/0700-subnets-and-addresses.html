Module 07 · Networking and delivery · Lesson 0700

A subnet's primary range grows in one direction only

working 8 min Capabilities virtual-network, subnet, network-interface and ip-address-management. Sourced from VPC networks and Subnets.

The one-minute version

  • A VPC network is created in auto mode or custom mode. Auto mode creates ranges for you; custom mode is the production choice.
  • The subnet is where the addressing actually lives. Its primary range can be expanded without downtime and can never be shrunk.
  • Secondary ranges sit beside the primary one. They can be removed and replaced while unused, which makes them the flexible half of the plan.
  • A NIC belongs to exactly one subnet of one VPC. A machine may have several NICs, and alias IP ranges on a NIC are how GKE pods get real VPC addresses.
  • There is no organisation-wide address plan here. The internal ranges API reserves and tracks space; pools, scopes and utilisation reporting are not offered.

4. The row with nothing in it: an address plan

The reframing Treat the address plan as a schema, not a configuration. It is written before the first subnet, it is enforced by people rather than by the platform, and the parts of it that turn out wrong divide cleanly into two kinds: too small, which expansion fixes, and too large, which nothing does.

Retrieval practice

Answer from memory before revealing.

A subnet was given a far larger primary range than it will ever use. What can be done about it?
Expansion is offered without downtime and shrinking is not offered at all, which is why the oversized allocation is the expensive mistake. The first reverses the rule. The third invents a conversion. The fourth would replace one set of unplanned ranges with another.
Where do GKE pod addresses come from in a VPC-native cluster?
Secondary ranges feed alias IP ranges on the NIC, so a pod holds a real VPC address. The first describes an overlay, which is what this design avoids. The second would exhaust the node range. The third names a reservation API that does not allocate pod addresses.
What does the inventory record about organisation-wide IP address management here?
The internal ranges API reserves and tracks, and pools, scopes and utilisation reporting are what is missing. The first names centralised ownership, which is not an address plan. The second overstates the API. The fourth is the over-reading of a partial absence into a total one.

Practice about 15 minutes, with paper

Practice 1working

A platform team is creating the first VPC for an organisation that expects around forty teams, several GKE clusters, and eventual connectivity to an on-premises estate whose ranges are already fixed.

Choose the network mode, say which two allocation mistakes are recoverable and which is not, name the artefact the platform will not maintain, and state what the on-premises estate adds to the problem.

Hint

Two of the three range decisions on this page behave differently under change. The fourth part of the question is about a constraint that arrives from outside the platform entirely.

Show the worked solution
  1. Choose the mode. Custom mode. Auto mode would create a subnet in every region with ranges nobody planned, and those ranges immediately become facts that later expansion and later peering have to work around.
  2. Sort the recoverable mistakes. A primary range that is too small is recoverable - it expands without downtime. A secondary range that is wrong is recoverable while it is unused, because it can be removed and replaced.
  3. Name the unrecoverable one. A primary range that is too large. It never shrinks, so the space it claims stays claimed, and with forty teams to place that space is the scarce resource.
  4. Name the missing artefact. The organisation-wide address plan. Reservation and tracking exist through the internal ranges API, and pools, scopes and utilisation reporting do not, so the plan is a document the team owns.
  5. Add the on-premises constraint. Those ranges are already fixed and cannot be renumbered, so every range chosen here has to avoid overlapping them. Overlap is not a warning at creation time - it is a routing failure discovered when the two estates are joined, which lesson 0703 covers.

Sanity check. Exactly one of your three allocation mistakes should be unrecoverable, and it should be the generous one rather than the tight one. If that felt backwards, look at the chart again - the arrow that is crossed out points left.

Your teacher. Before creating a first subnet, ask an agent to list every address range your organisation already uses anywhere, including on-premises and any other cloud. The list is the constraint, the platform will not hold it for you, and every range you allocate afterwards has to live around it.
