One API, three levels of custody, and one of them Google never holds

working 8 min Capabilities key-management, hsm, byok-hyok, secrets-store, certificate-manager and certificate-authority. Sourced from Cloud KMS and Secret Manager.

The one-minute version

  • Cloud KMS manages symmetric and asymmetric keys in key rings, with rotation and with customer-managed encryption keys across Google Cloud services.
  • Cloud HSM is not a separate product to integrate - it is a protection level on the same API, backed by FIPS 140-2 Level 3 validated hardware.
  • Cloud External Key Manager is the third level: the key is held outside Google, in your own or a partner's system, and it still controls Google Cloud data.
  • Secret Manager holds versioned secrets governed by IAM, with a replication policy, rotation notifications and customer-managed keys, and it can be mounted as a volume in Cloud Run and GKE.
  • Certificates split in two: Certificate Manager deploys TLS certificates to load balancers through maps, and Certificate Authority Service is a private certificate authority you operate.

1. The custody ladder

Cloud External Key Manager is the hold-your-own-key pattern, and the inventory records that EKM over a VPC keeps the requests private. Cloud HSM is reached by setting the protection level on the key, so an application never learns which rung it is on.

2. Customer-managed keys, and the two features that stop accidents

The other feature worth naming is Autokey, which simplifies the wiring of customer-managed keys to services. The wiring is where CMEK adoption usually stalls, because every service that stores data needs to be pointed at the right key ring.

4. Two certificate products, for two different jobs

The reframing Four questions, and each selects one product. Who must hold the key material picks the KMS rung. What must be readable only at run time and auditable when it is read is Secret Manager. What must a browser trust is Certificate Manager. What must your own workloads trust about each other is Certificate Authority Service. None of the four is answered by the others, and all four are enforced by the identity model of the previous three pages.

Retrieval practice

Answer from memory before revealing.

How is Cloud HSM reached from an application's point of view?
It is a protection level on the same API, which is what makes moving a key to hardware a configuration change. The first invents a separate integration. The second describes the external key manager, which is the next rung up. The fourth invents a ring type.
What does Secret Manager give a workload that a deploy-time environment variable does not?
The auditable read and IAM-governed versions are what the inventory records as the difference. The first overstates the contrast. The third invents a failure mode. The fourth is close - rotation notifications exist - but a value can be changed by redeploying too, so it is not the distinguishing property.
Workloads must present certificates to each other for mutual TLS inside the estate. Which product issues them?
Internal public key infrastructure is exactly what the private certificate authority is for. The second names the product that deploys public certificates to load balancers. The third supplies keys but issues no certificates. The fourth stores material without issuing or validating anything.

Practice about 15 minutes, with paper

Practice 1working

A regulated customer requires that its data in Google Cloud be encrypted with keys the cloud provider cannot access, that access to the application's database password be individually auditable, and that internal service-to-service traffic use mutual TLS. The public site also needs certificates on several load balancers across two regions.

Choose a product for each requirement, name the operational risk the first one introduces, and say what protects against the worst accident in this area.

Hint

Four requirements, four products, one each. Two of the requirements say something about who may hold or read something, and the difference between them is whether Google is in the answer.

Show the worked solution
  1. Keys the provider cannot access. Cloud External Key Manager. Software keys and Cloud HSM both leave Google holding the material, so neither satisfies the wording; only the external rung does, with the key in your own or a partner's system.
  2. The individually auditable password. Secret Manager, read by the workload's attached service account. The read is an event, which is the property the requirement is actually asking for, and an environment variable set at deploy time produces no such event.
  3. Mutual TLS internally. Certificate Authority Service, issuing from a private hierarchy with issuance policies. Nothing outside the estate needs to trust these certificates.
  4. Public certificates across regions. Certificate Manager, with certificate maps deploying to the load balancers and DNS proving domain control. This is the product that stops the estate attaching certificates one balancer at a time.
  5. Name the operational risk. The external key manager puts an external system in the path of reading your data. Access to the data now depends on that system as well as on Google Cloud, which is the cost of the custody the requirement bought.
  6. Name the protection against the worst accident. The destroy schedule on a key version. Destroying a key that encrypts live data makes it unrecoverable, and the scheduled delay between the request and the act is the only chance to undo it.

Sanity check. Each requirement should map to a different product and the first should be the external rung rather than the hardware one. If you chose Cloud HSM for the first, re-read the requirement - hardware changes how the key is protected, not who holds it.

Your teacher. When a requirement says keys must be "under our control", ask an agent to make the customer's wording precise: managed by us, held in hardware, or never held by the provider. Those are three different rungs, and only the third one requires an external system you then have to keep available.
