Module 04 · Storage · Lesson 0404

Two storage rows are genuinely empty, and each one has a documented substitute

frontier 7 min Capabilities hybrid-storage-gateway, object-storage-tables, bulk-transfer-appliance and online-transfer.

The one-minute version

  • Two capabilities in the storage area have no Google Cloud product: a hybrid storage gateway, and object storage that understands table formats natively.
  • Neither absence means the problem is unsolvable here. Each has a substitute the vendor documents, and the substitute has a different shape from the missing product.
  • There is no first-party storage gateway appliance. The nearest things are Cloud Storage FUSE and Storage Transfer Service agents, and partner gateways cover the rest.
  • There is no table-aware bucket type. BigLake managed Iceberg tables give managed Iceberg storage, and they are created and maintained by BigQuery over ordinary buckets.
  • Two transfer products do exist and are often confused with a gateway: Storage Transfer Service for scheduled online transfers, and Transfer Appliance for shipping data physically.

1. The two empty rows, with what stands in for each

The table row is the subtler of the two and its wording repays care. BigLake managed Iceberg tables genuinely give managed Iceberg storage with automatic optimisation. What makes the row an absence rather than a packaging difference is where the table lives: the tables are created and maintained by BigQuery, and Cloud Storage itself still holds their files as opaque objects. So the capability is delivered by the lakehouse, and the storage service has not gained a table type. Module 06 covers the lakehouse side of that sentence.

2. What a gateway would have done, and what you do instead

The substitutes divide the job differently. Cloud Storage FUSE mounts a bucket so that code expecting a path can read and write objects, which covers the case where the requirement was really that a program wants a filesystem. Storage Transfer Service agents move on-premises data into Cloud Storage on a schedule, which covers the case where the requirement was really that the data has to arrive. Between them they cover a great deal of what a gateway is usually bought for, and neither is a caching protocol translator, so a requirement that genuinely needs one goes to a partner product.

3. The two products that do exist for getting data in

Storage Transfer Service is the online counterpart: scheduled and incremental transfers into Cloud Storage from another cloud's object storage, from on-premises sources, or from another bucket, driven by a manifest and filters, with an agent-based path for on-premises data. It repeats on a schedule, which is what makes it a useful component in an ongoing pipeline as well as in a migration.

Transfer Appliance capacities vary by hardware generation, and the research behind this course flagged the current models as something to re-check rather than something to quote. Read the capacity and the logistics from the appliance documentation at the time you plan the transfer, because a sizing decision made against a superseded model is the kind of error that only shows up when the hardware arrives.
The reframing Three questions separate everything on this page, and they are worth asking in this order. Does the data need to arrive once, or keep arriving? Once is the appliance or a transfer job; keep arriving is Storage Transfer Service on a schedule. Does an application need to keep speaking a file protocol? If yes, that is the gateway shape, and the first-party answer is FUSE if a path is enough and a partner product if the protocol is not negotiable. Does something need to understand the table format? If yes, that belongs to the lakehouse rather than to the bucket.

Check yourself

Retrieval practice

Answer from memory before revealing.

Google Cloud ships no first-party storage gateway appliance. What is the correct conclusion?
The absent thing is the caching protocol translator on your premises, and the substitutes cover much of what it is bought for. The first is contradicted by two transfer products. The third is contradicted by Cloud Storage FUSE. The fourth is the over-reading this course exists to prevent, stated at full strength.
Why is table-aware object storage recorded as an absence when BigLake managed Iceberg tables exist?
The row is about the storage service understanding tables, and here the lakehouse owns and maintains them over ordinary buckets. The first two make factual claims the sources do not support. The third invents a format distinction, which is the kind of detail that sounds authoritative and is not.
An on-premises system must keep writing to an NFS share while the data ends up in Cloud Storage. What fits?
A continuous on-premises protocol translation is exactly the gateway case, and it is the case with no first-party product. Transfer Appliance terminates. Storage Transfer Service repeats but does not serve the protocol. FUSE gives a path to code you control, not an NFS export to systems you do not - which makes it the strongest distractor here.

Practice about 20 minutes, with paper

Practice 1frontier

A media company is moving to Google Cloud. It has four petabytes of archived footage on premises, an editing suite whose software mounts an SMB share and cannot be changed, a nightly export from a partner's object storage on another cloud, and an analytics team that wants to query the whole archive as tables.

Assign a mechanism to each requirement, and mark which of the four is answered by a product that does not exist on this platform.

Hint

Ask the three questions from the reframing above in order. One requirement is answered by a partner rather than by Google, and one is answered by a different module's product entirely.

Show the worked solution
  1. Four petabytes of archive. Arrives once, at a scale that argues against the network: Transfer Appliance, with the current model's capacity read from the documentation rather than assumed. Its destination class is the archive decision from earlier in this module.
  2. The nightly partner export. Keeps arriving, from another cloud's object storage: Storage Transfer Service, scheduled and incremental, with a manifest and filters to select what is wanted.
  3. The editing suite. An unchangeable application speaking SMB is the gateway shape. Two honest answers exist and neither is a Google product: a partner gateway, or NetApp Volumes as a cloud-side SMB share if the editing suite can be moved to the cloud with the data. Mark this one as the row with no first-party product.
  4. The analytics requirement. Querying the archive as tables is not a bucket feature. It belongs to the lakehouse - BigQuery over the bucket, with managed Iceberg tables if a managed table format is wanted - which is module 06's material and not a storage product.

Sanity check. Exactly one requirement should have landed on a partner or a redesign, and exactly one should have left the storage module entirely. If the archive and the nightly export were given the same mechanism, re-read the first question - once against continually is what separates the appliance from the transfer service.

Your teacher. When any source tells you a cloud "cannot" do something, ask an agent for the sentence the vendor actually writes and for what it names instead. On this platform the answer is usually a different shape rather than a missing capability, and the difference between those two findings is worth an architecture review.
