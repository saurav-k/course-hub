The GKE mode you pick decides whether you operate nodes at all

working 10 min Capability managed-kubernetes. Sourced from Google's cluster mode documentation.

The one-minute version

  • Google Kubernetes Engine runs the control plane in both of its modes. The mode decides who runs the nodes.
  • Standard keeps node pools visible and yours to size. Autopilot removes node management entirely and bills per pod resources rather than per node.
  • That billing difference is the mode difference made visible: in Standard you pay for capacity, in Autopilot you pay for requests.
  • Google Cloud sells no separate node autoscaler product, and that is a packaging fact rather than a gap - node auto-provisioning and the cluster autoscaler are built into GKE.
  • A cluster can have a regional control plane, and release channels automate the upgrade cadence rather than leaving it to a person to remember.

1. One control plane, two answers about nodes

The cluster mode documentation is the page that settles this, and it is worth reading before a first cluster rather than after one. Standard mode is the familiar Kubernetes shape: node pools that you size, upgrade and pay for whether or not the pods on them are using the capacity. Autopilot removes node management from the picture and bills per pod resources.

2. What the billing difference actually looks like

That reframing is what makes the mode decision tractable. A cluster whose node pools run near their requests is already efficient, and Autopilot's benefit there is operational rather than financial. A cluster with a lot of slack - a small workload on a machine shape chosen for a bigger one - is paying for that slack every hour.

3. The autoscaler that has no product page

This row is worth pausing on, because it is exactly the kind of fact that gets read backwards. On some platforms the just-in-time node provisioner is a separate project you install. Here node auto-provisioning and the cluster autoscaler are part of the cluster, and Autopilot goes further by removing node management altogether. A comparison that lists a missing product name and stops there produces the wrong conclusion; module 01 named this pattern and this is the first place it bites.

4. Two settings that decide the cluster's operational character

Regional control planes. A cluster's control plane can be regional, which places it across the zones of a region rather than in one. The same reasoning as the regional instance group applies: it converts a total loss into a partial one rather than removing the loss.

Release channels. Upgrades are automated by channel rather than performed on a schedule someone has to remember. The choice of channel is a choice about how quickly the cluster follows Kubernetes releases, so it is a risk decision rather than a convenience one - and it is made once, at cluster creation, for a cluster that may live for years.

The reframing Two facts about GKE that come free and are easy to miss. Telemetry is on by default: Kubernetes API server audit records flow into Cloud Audit Logs, and container output reaches Logging when the cluster has the Logging API enabled, with the system and workload categories configurable per cluster. And pods hold real VPC addresses, through the alias IP ranges of the subnet the cluster sits in, which is why GKE networking is a subnet design question rather than an overlay question.
What this certification tests Cluster operation is examined as a task. The Associate Cloud Engineer guide puts Planning and implementing a cloud solution at about 30 per cent and deploying an Autopilot cluster sits inside it, while the day-two work of scaling and troubleshooting a cluster falls under Ensuring the successful operation of a cloud solution, also about 30 per cent.

Check yourself

Retrieval practice

Answer from memory before revealing.

What is the difference between the two GKE modes, stated precisely?
Google runs the control plane in both, so the mode is a statement about nodes and about the billing unit that follows from them. The first option invents a different API. The second confuses mode with control-plane placement, which is a separate setting. The fourth contradicts the whole point of Autopilot.
A cluster's node pools already run close to their pod requests. What does moving it to Autopilot mainly buy?
Autopilot moves the cost of unused headroom, so a tightly packed cluster has little headroom to move and the gain is in the work you stop doing. The first option is the right mechanism applied to the wrong cluster. The third invents cross-region behaviour. The fourth is false - the autoscaler is in the service, not in one mode.
Google Cloud publishes no standalone Kubernetes node autoscaler product. What follows?
The capability is delivered inside the managed service, so the missing product name says nothing about the missing capability. The first two describe what a genuine absence would force. The third is the subtler error, attaching a service-wide capability to one mode.

Practice about 15 minutes, with paper

Practice 1working

A team runs two GKE Standard clusters. Cluster A hosts many small services whose pod requests total roughly a third of the node capacity it runs. Cluster B hosts one large service that fills its nodes.

Decide which cluster gains most from Autopilot and say why, then name the gain the other cluster still receives.

Hint

Ask what is billed in each mode, then ask how big the difference between those two amounts is for each cluster.

Show the worked solution
  1. State what each mode bills. Standard bills node capacity. Autopilot bills pod resources. The financial gain from switching is whatever sits between the two.
  2. Measure the gap on cluster A. Requests are about a third of capacity, so roughly two thirds of what cluster A pays for is headroom nobody asked for. That is the gap Autopilot removes.
  3. Measure it on cluster B. The nodes are full, so requests and capacity are close and there is almost nothing between them. Switching cluster B changes the bill very little.
  4. Name cluster B's gain anyway. It stops sizing, patching and upgrading node pools, and the node-shape decision disappears from its future. That is an operational gain that exists whatever the packing efficiency is - which is why the mode choice is not only a cost calculation.

Sanity check. Cluster A should be the clear financial win and cluster B should still have a reason to move. If your answer concluded that Autopilot is simply cheaper, notice that a perfectly packed node pool has no headroom to give back - the mechanism has to have something to work on.

Your teacher. If the two modes still feel like a preference, ask an agent to list every operational task that exists in Standard and not in Autopilot. The length of that list is the decision, and the cost difference is a second one that happens to point the same way most of the time.
