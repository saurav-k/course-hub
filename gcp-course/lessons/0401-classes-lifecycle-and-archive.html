Module 04 · Storage · Lesson 0401

A storage class is a price shape with a minimum duration attached

working 7 min Capability archive-storage. Sourced from Google's storage classes documentation.

The one-minute version

  • Four classes - Standard, Nearline, Coldline and Archive - live inside one bucket API, so moving between them changes the bill and not the code.
  • Each class trades a lower storage rate for a higher access cost, and each carries a minimum storage duration. That duration is what turns the trade into a bet.
  • Archive is the coldest, meant for data kept for a year or more, and the minimum duration is what makes it the wrong home for anything that might be deleted early.
  • Lifecycle rules move objects on rules you write. Autoclass moves them on observed access instead, which is the answer when you do not know the access pattern.
  • Bucket Lock and object retention put immutability in the platform rather than in the application, which is what a compliance requirement actually asks for.

1. The trade, in one picture

The minimum storage duration is the part that turns this from a rate comparison into a commitment. Data placed in a colder class and deleted before its duration elapses is charged as though it had stayed, so an aggressive lifecycle policy over data that turns out to be short-lived costs more than leaving it alone. The storage classes page carries the durations and the access-cost trade for each class, and it is the page a policy should be written against.

Archive is the extreme end of both curves: the lowest storage rate, and a class intended for data retained for a year or more. Nothing about it changes the interface - it is a class inside the same bucket and the same API - which is exactly what makes it easy to apply carelessly.

2. Two ways to move an object between classes

The failure this framing prevents is the confident lifecycle rule. A rule that moves everything to a colder class after thirty days is easy to write and is a bet that nothing will be read afterwards. When it is wrong the cost appears twice - once in retrieval charges, and once in the early-deletion charge if anything is removed before its minimum duration is up.

3. Retention that the platform enforces

Cloud Storage provides object retention and Bucket Lock as its immutability mechanisms, and they are the platform's answer for a write-once requirement. That matters as a piece of estate-level vocabulary too: Google Cloud has no managed ledger product of the append-only, cryptographically verifiable kind, and this immutability pair is the nearest thing the research behind this course records, together with a transactional database for history that must be queried rather than merely kept.

The reframing Three different requirements get called "keep this data" and they want three different mechanisms. Do not lose it by accident is soft delete and versioning. Keep it cheaply because we might need it is a colder class with a lifecycle or Autoclass policy. Prove that nobody could have removed it is retention with a lock. Reaching for the second when the requirement was the third produces a design that is cheap and fails the audit.

Check yourself

Retrieval practice

Answer from memory before revealing.

A lifecycle rule moves objects to a colder class after a month, and many are deleted soon afterwards. What happens?
Colder classes carry a minimum storage duration, and deleting inside it is charged as though the data had stayed. The first option describes what a rate-only comparison would predict. The third invents an automatic reversal. The fourth turns a billing rule into an access control, which retention locking does and storage classes do not.
A team cannot predict how their data will be read, and access varies object by object. What fits?
Autoclass exists exactly for the case where the access pattern is unknown or varies. The first option builds a rule on an average that hides the variance. The second is the expensive mistake, since unpredictable is not the same as unread. The third is defensible and gives up the saving entirely.
A regulator asks for evidence that records could not have been deleted early. What satisfies that?
Locking moves retention from a setting into a platform guarantee, which is what "could not have been deleted" means. The first two are recovery mechanisms and both leave the retention itself changeable. The fourth confuses a class policy with a deletion control entirely.

Practice about 15 minutes, with paper

Practice 1working

A finance system writes two kinds of object into one bucket: daily transaction records that regulation says must be kept for seven years and must be provably unalterable, and interim working files that are read heavily for a week and then never again, though sometimes they are deleted after a fortnight.

Design the class and retention policy for each kind, and name the mistake that a single policy across the bucket would produce.

Hint

Handle the two kinds separately from the start. For each one, ask which of the three "keep this data" requirements it actually is.

Show the worked solution
  1. Classify the transaction records. Seven years and provably unalterable is the retention-with-lock requirement, not a cost requirement. Apply retention and lock it, so nobody with any permission can shorten the period.
  2. Choose their class. Seven years of untouched data is squarely inside Archive's intended use, and its minimum storage duration is irrelevant because the data is not going anywhere.
  3. Classify the working files. Heavy reads for a week means Standard while they are hot. The complication is the fortnight deletions: moving them to a colder class after a week can trigger the early-deletion charge on whatever is removed at day fourteen.
  4. Name the single-policy mistake. One rule across the bucket either archives the working files, which pays early-deletion charges on the ones deleted at a fortnight and retrieval charges on any that are read again, or it leaves the transaction records in Standard, which pays years of hot storage and, worse, leaves them without a lock. Both halves of the bucket lose.

Sanity check. Your answer should have used a different mechanism for each kind, and only one of them should involve a lock. If a single lifecycle rule covered both, check the deletion pattern of the working files against the minimum storage duration - that mismatch is the whole trap.

Your teacher. If a class decision is in dispute, ask an agent for the current minimum storage duration and access cost of each class and then do the arithmetic on your own volume. The classes page carries both numbers, and a policy argued without them is an argument about intuitions.
