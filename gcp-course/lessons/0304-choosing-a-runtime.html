Pick the runtime by the layer you want to stop operating

working 9 min The placement decision for managed-kubernetes, serverless-containers, functions-faas, paas-web-runtime and static-site-hosting.

The one-minute version

  • The five runtimes in this module form one ladder, and each rung removes a layer you would otherwise operate.
  • Two questions settle almost every case: what artefact do you have, and which layer do you want to stop touching.
  • Kubernetes is the answer when you need the Kubernetes ecosystem - operators, custom resources, a mesh, multi-cluster policy - not merely when you have containers.
  • Cloud Run is the answer when you have a container and want no cluster. Functions and App Engine are the answers when you have less than a container.
  • All the container rungs pull from Artifact Registry. The old Container Registry name is not a synonym: it is shut down and it refuses writes.

1. The ladder, drawn as what you still operate

2. The two questions

RuntimeChoose it whenWhat you give up
GKE Standard node shape, local storage or accelerator placement is part of the design nothing, which is the problem - every layer stays yours
GKE Autopilot you want the Kubernetes ecosystem without operating nodes node-level control, and the billing unit becomes pod requests
Cloud Run you have a container and no Kubernetes-shaped requirement the Kubernetes ecosystem, including meshes and custom resources
Cloud Run functions the unit of work is a handler responding to an event control of the image, and a process shape you own end to end
App Engine the artefact is an application and a declared runtime the container boundary, and with it portability of the image

3. Where the image comes from, for every container rung

The predecessor name is a trap rather than a synonym. Container Registry is shut down: reads redirect into Artifact Registry and writes are unavailable. A pipeline that still pushes to the old host fails at the push, which is late, and the error will not say that a product was retired. Module 12 owns the registry properly, including the scanning and admission controls around it.
What this certification tests Runtime placement is one of the most reliably examined decisions in this area. The Professional Cloud Architect guide puts Designing and planning a cloud solution architecture at about 25 per cent, where the placement question is asked as a trade-off against stated constraints. The Associate guide asks the same material as a task under Planning and implementing a cloud solution, about 30 per cent. In both, the constraint in the question stem is what decides - simplest, cheapest, or least operational overhead each point at a different rung of this ladder.

Check yourself

Retrieval practice

Answer from memory before revealing.

A team has a container image and no requirement that mentions Kubernetes. What does the ladder suggest?
Having a container is not a Kubernetes requirement - Cloud Run runs containers without a cluster. The first two assume the container implies the cluster, which is the reasoning this page exists to interrupt. The third proposes rewriting the artefact when nothing asked for that.
Which requirement genuinely points at GKE Standard rather than Autopilot?
Node-level control is the layer Autopilot removes, so it is the requirement that keeps Standard. The second names the ecosystem, which both modes have. The third and fourth are properties of the service rather than of a mode, and choosing Standard for either buys operational work for nothing.
A pipeline that has not run for a long time now fails when pushing its image. What is worth checking first?
Container Registry is shut down for writes, so an old pipeline fails at exactly this step. The other three are all real causes of a failed push, which is what makes them good distractors - and none of them explains why the pipeline worked before and stopped without being changed.

Practice about 20 minutes, with paper

Practice 1working

A GKE Standard cluster runs four workloads: a public web API in containers, a nightly report generator, an image-thumbnail step triggered whenever an object lands in a bucket, and a training job that needs particular accelerator hardware and local disks.

Place each workload on the ladder, and say what remains in the cluster afterwards and whether the cluster is still worth keeping.

Hint

Do the placements first without thinking about the cluster. Then look at what is left and ask whether that residue justifies the operational surface underneath it.

Show the worked solution
  1. Place the web API. A container with no Kubernetes-shaped requirement is the Cloud Run case, and it gains revision-based traffic splitting for its releases.
  2. Place the nightly report. Work that runs and finishes is a job. Cloud Run jobs fit, and Batch fits if the work needs Compute Engine resources rather than a container runtime.
  3. Place the thumbnail step. A handler triggered by an object write is a function, delivered by Eventarc.
  4. Place the training job and judge the residue. Particular accelerator hardware and local disks are node-level concerns, which is the layer Autopilot removes - so this workload is the one that keeps GKE Standard. Everything else has left, and the honest question is whether one workload justifies a cluster: the answer depends on whether the node control is genuinely required, and if it is, the cluster is now doing exactly the job that only it can do.

Sanity check. Exactly one workload should have needed the cluster, and it should be the one naming hardware. If two or more stayed, check whether their reasons were requirements or habits - "it is already containerised" is not a Kubernetes requirement, because Cloud Run takes the same image.

Your teacher. If a placement argument on your own team keeps going in circles, ask an agent to restate each position as a layer from the chart above: nodes, cluster configuration, image, code. Most runtime disagreements turn out to be two people defending different layers.
