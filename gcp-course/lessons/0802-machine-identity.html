Module 08 · Identity and access · Lesson 0802

A workload's identity is attached to it, and no key is issued

working 9 min Capabilities workload-identity, workload-identity-federation, cross-account-assumption, short-lived-credentials and agent-identity. Sourced from service accounts and Workload Identity Federation.

The one-minute version

  • A virtual machine, a Cloud Run revision or a GKE workload runs as a service account. Client libraries collect short-lived tokens from the metadata server, so there is no key material on the machine.
  • Impersonation is the cross-boundary equivalent of assuming a role: roles/iam.serviceAccountTokenCreator lets one principal mint short-lived credentials for a service account.
  • The grant is the trust. There is no separate trust document per resource - an IAM binding on the target naming the foreign identity is the whole arrangement.
  • Workload Identity Federation trusts an external system - AWS, any OIDC issuer, SAML or X.509 - through a pool and a provider with attribute mapping and an attribute condition. No long-lived secret crosses the boundary.
  • Service account keys exist and Google's guidance is to avoid them entirely. There is also no distinct agent identity object - agents run as ordinary service accounts.

1. Attached, so nothing has to be distributed

On GKE the mapping is explicit: a Kubernetes service account is mapped to a Google service account, so a pod inherits an identity the same way. Two hardening notes come with this. The default compute service account should be disabled in hardened designs, and service account keys exist but the vendor's guidance is to avoid them entirely.

3. Trusting a workload that is not here

Terraform · the provider shape, from the research behind this course
resource "google_iam_workload_identity_pool_provider" "github" {
  workload_identity_pool_id          = google_iam_workload_identity_pool.pool.workload_identity_pool_id
  workload_identity_pool_provider_id = "github"
  attribute_mapping = {
    "google.subject"       = "assertion.sub"
    "attribute.repository" = "assertion.repository"
  }
  attribute_condition = "assertion.repository == \"org/repo\""
  oidc { issuer_uri = "https://token.actions.githubusercontent.com" }
}

Read the last two settings together. The mapping makes the external repository name available as an attribute; the condition refuses everything that is not that repository. Supported provider kinds are AWS, any OIDC issuer, SAML and X.509.

4. Short-lived credentials, and the row with no object

The verified inventory records downscoped access tokens, narrowed with a credential access boundary, and flags the current API surface as needing confirmation. Nothing about their shape is stated here. Check the short-lived credentials documentation before a design depends on them.
The reframing Three questions cover every machine-to-machine case here. Does the code run on Google Cloud? Attach a service account and stop. Does it run somewhere else? Federate, and put the security in the attribute condition. Does one identity need to act as another? Grant token-creator on the target, because the binding on the target is the trust. A service account key is not the answer to any of the three.

Retrieval practice

Answer from memory before revealing.

Where does a Cloud Run revision get credentials for a Google Cloud API?
The revision runs as a service account and the libraries collect short-lived tokens from the metadata server. The first and third describe the secret distribution this design removes. The fourth denies attached identity for a runtime that has it - federation is for workloads outside the platform.
Where is the trust recorded when a principal in one project acts as a service account in another?
There is no separate trust document - the token-creator binding on the target service account is the trust. The first imports a two-document model from elsewhere. The second names federation, which is for external workloads. The fourth confuses the guardrail axis with the identity axis.
In a federation provider, which setting actually stops an unintended external workload?
The condition is the gate; without it, every workload the issuer vouches for is trusted. The first narrows the issuer but not which of its workloads. The second makes claims available and decides nothing. The third names the container rather than the control.

Practice about 15 minutes, with paper

Practice 1working

A build pipeline runs outside Google Cloud and must deploy into two projects. The current arrangement stores a downloaded service account key in the pipeline's secret store, and the same key is used for both projects. A reviewer asks for a design with no long-lived secret and with each project's access separately revocable.

Replace the key, say what the security of the new design rests on, design the two-project access, and state what the platform will not track for you.

Hint

The first move is named in the one-minute version. The second project is not a second pool - look at what the trust document actually is.

Show the worked solution
  1. Replace the key. Workload Identity Federation. A pool and a provider trust the pipeline's OIDC issuer, its token is exchanged, and the exchanged token is used to impersonate a service account. No long-lived secret is stored anywhere.
  2. Name what the security rests on. The attribute condition. The issuer will vouch for many workloads, so the condition that pins the repository, the branch or the equivalent claim is what separates your pipeline from everybody else's on the same issuer. A provider without one trusts far more than it looks like it does.
  3. Design the two projects. One service account per project, and the pipeline's federated principal granted token-creator on each. Each project's access is then a binding on its own service account, so revoking one is a single binding removal and does not touch the other.
  4. Reject the shortcut. One shared service account with roles in both projects would work and would make the two revocations one, which is exactly what the reviewer asked to avoid.
  5. State what is not tracked. If any of this runs an agent, note that there is no distinct agent identity object - it is an ordinary service account - so the record of which human sponsors it lives in your own documentation.

Sanity check. Your design should contain zero stored credentials and two independently removable bindings. If revoking one project's access would also have removed the other's, the two projects are sharing a service account.

Your teacher. If a repository contains a service account key, ask an agent which of the three cases the workload is in - on the platform, outside it, or acting as another identity. All three have a keyless answer, so the key is evidence of a design that predates one of them.
