Memorystore is one row with four engines under it

working 6 min Capability in-memory-cache. Sourced from Memorystore for Redis and Memorystore for Valkey.

The one-minute version

  • Memorystore is the in-memory row, and it is four engines: Redis, Redis Cluster, Valkey and Memcached.
  • The four have different feature envelopes, so choosing Memorystore is not one decision - it is a decision followed by an engine decision.
  • The documented threshold: pick Redis Cluster when the workload needs horizontal scale or more than 5 TB.
  • Valkey has its own documentation set rather than being a footnote under Redis, which is a hint about how separately the engines are tracked.
  • Everything on this row holds a copy. The record of truth stays in one of the stores from the previous three pages.

1. The tier that holds no truth

2. Four engines, and where the choice stops being about features

The Memorystore for Redis overview is the reference for the Redis side, and Valkey has a documentation set of its own rather than a section inside the Redis one. That separation is a useful signal: the engines move at their own pace, so a feature confirmed for one is not thereby confirmed for another.

The reframing Two questions, in order. Does the workload need a cache at all - which is answered by what the store of record costs per read, not by how fast memory is. Then which engine - answered by the feature envelope, and overridden by the scale threshold when the dataset or the scale-out requirement crosses it.

Check yourself

Retrieval practice

Answer from memory before revealing.

What is the documented reason to choose Redis Cluster over the other Memorystore engines?
Scale is the documented threshold and it is the only one of the four that the inventory records. The second claims a durability property this row does not sell. The third confuses capacity with latency. The fourth invents a protocol bridge that no engine offers.
Why is "we run Memorystore" an incomplete statement of a design?
The engine carries the feature set, so naming the row names almost nothing. The first is wrong about the product's stage. The second inverts the tier - the record of truth is in the stores of the earlier pages. The fourth names a real design question, but it is not what makes the sentence incomplete here.
A team sizes its database for the read rate that reaches it once the cache is warm. What has been missed?
A cache can be empty at any time, and the miss path sends the whole read rate to the database, so that is the rate to size for. The first invents traffic the cache does not generate. The third denies the defining property of the tier. The fourth reverses the reason a cache exists at all.

Practice about 10 minutes, with paper

Practice 1working

A product catalogue is served from Firestore. Reads are heavy and repetitive, and the team wants a cache in front of it. The catalogue in memory would be about eight terabytes, and the team also wants a data structure the application already uses in its own Redis deployment.

Choose the engine, say which of the two requirements decided it, and state what the team must still confirm and what the database must still be able to do.

Hint

One of the two requirements has a documented threshold attached to it, and thresholds beat preferences. The thing still to confirm is a property of the engine family rather than of Memorystore.

Show the worked solution
  1. Apply the threshold. Eight terabytes is above the five-terabyte mark, and the documentation names Redis Cluster for exactly that case. The size requirement decides the engine on its own.
  2. Check the other requirement against the choice. The data-structure requirement is a feature question, and the engines have different feature envelopes, so it does not automatically survive the move to Cluster. It has to be confirmed against the engine's own documentation rather than assumed from the Redis name.
  3. Size the store of record. The cache can be empty at any moment, so Firestore has to be able to serve the full read rate on a cold cache. If it cannot, the cache is hiding a capacity problem rather than solving one.
  4. Say what the cache is allowed to lose. Everything. Nothing in the catalogue exists only in Memorystore, which is what makes it safe to empty it deliberately during an incident.

Sanity check. The size requirement should have decided the engine and the feature requirement should have become a check rather than a second vote. If your answer sized the database for the warm read rate, the design fails on its first cold start.

Your teacher. If you are unsure whether a cache is warranted, ask an agent for the read rate and the cost per read at the store of record, then compute what the cache saves against what the cache costs. A cache added because memory is fast, rather than because a read is expensive, is a second thing to operate for no return.
