The fleet, not the cluster, is the thing you govern

working 6 min Capabilities kubernetes-fleet-management, service-mesh and kubernetes-backup. Sourced from Google's fleets overview.

The one-minute version

  • One cluster is one failure domain and one place to be inconsistent, so a real estate has several - and then needs somewhere to make decisions once.
  • A fleet groups clusters across projects, regions and on-premises sites so that policy, configuration and multi-cluster services are managed at that level.
  • Config Sync is the reconciliation loop of the fleet: configuration lives in Git and drift is corrected back towards it rather than reported.
  • Cloud Service Mesh is the managed Istio-derived mesh for clusters and fleets, and it carries traffic management including fault injection as a first-party feature.
  • Backup for GKE is workload-aware: it backs up cluster objects and their volumes together, which the general backup service does not do.

1. Why the second cluster changes the problem

Fleet management arrives under the GKE Enterprise name, which is where the Anthos brand went: the products are the same lineage and the word has changed, which module 01 warned about as a general hazard and this is one of its instances.

2. Configuration as a loop, not as a deployment

3. The mesh, and the feature that surprises people

Cloud Service Mesh is the managed Istio-derived mesh for GKE clusters and fleets, with a managed control plane, and its telemetry lands in Cloud Observability alongside everything else. The capability it names is service-to-service identity, mutual transport security, traffic splitting and layer-seven telemetry between workloads.

The reframing Google Cloud ships no standalone chaos-engineering platform, and that absence is real and recorded. It is also narrower than it sounds: Cloud Service Mesh includes managed fault injection, which can add delay or abort faults to a percentage of requests. So "no first-party fault injection" would be false. What is missing is the standalone experiment platform around it, not the ability to inject a fault - and the two claims sound identical until you need one of them.

4. Backup that understands what a workload is

Backup for GKE is deliberately separate from the platform's central Backup and DR Service, which module 14 covers. The distinction is scope: the central service protects a wide range of resources from one plane, and this one understands Kubernetes objects. A design that assumed the central service covered clusters has a gap it will discover during a restore.

Retrieval practice

Answer from memory before revealing.

What problem does a fleet solve that a cluster cannot?
A fleet is a unit of decision for clusters spread across projects, regions and on-premises sites. The first two attribute compute or control-plane behaviour to what is a management grouping. The fourth inverts the point, since spanning regions is one of the reasons fleets exist.
Someone changes a cluster by hand and the change contradicts what is in Git. What does Config Sync do?
Reconciliation means the live state is corrected towards the declared state, continuously. The second option describes drift detection, which reports rather than corrects. The third inverts the direction of truth. The fourth describes an admission control the product does not claim.
A team wants to inject latency into a percentage of requests between two services. What is available?
Managed fault injection is part of the mesh's traffic management, so the capability exists even though a standalone chaos platform does not. The first option is exactly the over-reading this course warns about - the missing product is the experiment platform, not the fault. The other two attach the capability to unrelated services.

Practice about 15 minutes, with paper

Practice 1working

An estate has grown to six GKE clusters in three regions, owned by two teams in different projects. Each cluster has drifted: namespaces, quotas and network policies differ in ways nobody planned.

Say which construct on this page addresses the drift, name what has to exist before it can be turned on, and state what it will not fix.

Hint

The mechanism is a loop, and a loop needs something to compare against. Ask what that something is and who has to write it.

Show the worked solution
  1. Pick the construct. Drift across clusters is what Config Sync exists for, applied at the fleet level so that six clusters are reconciled from one declaration rather than six.
  2. Name the prerequisite. The clusters must be joined into a fleet, and there must be a Git repository holding the intended configuration. The loop compares live state against that declaration, so somebody has to decide what the correct state actually is - which is the real work.
  3. Notice what the tool cannot decide. The six clusters currently disagree. Reconciliation makes them agree with Git, so if Git is written from one cluster's current state, the other five change to match a configuration nobody chose deliberately.
  4. State the limit. Config Sync fixes divergence and does not fix a bad declaration. It converts an unmanaged difference into a managed one, and the quality of the result is the quality of what was written down.

Sanity check. Your answer should name a prerequisite that is a decision rather than a product. If the answer was purely a list of services to enable, the hard half of the problem - agreeing what the six clusters should look like - has been assumed away.

Your teacher. If fleets feel like an enterprise abstraction you do not need yet, ask an agent how a policy change reaches six clusters without one. The answer is a script, and the fleet is what that script grows into.
