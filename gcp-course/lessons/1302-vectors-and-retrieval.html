Vectors live in five places, and the rest of the query decides which

working 7 min Capabilities vector-store, managed-rag-pipeline and managed-search. Sourced from Vertex AI Vector Search and the RAG Engine overview.

The one-minute version

  • Vertex AI Vector Search is the dedicated store: high-scale approximate nearest neighbour retrieval over embeddings.
  • The inventory records four alternatives as well: vector search in AlloyDB and Spanner, vectors in Memorystore, and vector indexes in BigQuery.
  • The choice is rarely about the vectors. It is about what else the query needs - a transactional join, a warehouse scan, a cache lookup, or nothing at all.
  • Above the store sit three levels of assembly: build the pipeline yourself, use the managed retrieval pipeline, or use the enterprise search product.
  • Two warnings. The managed pipeline is recorded as preview, and the search product's name has changed more than once, with old documentation URLs gone.

1. Five homes for the same embedding

Where the vectors liveChoose it when the query also needs
Vertex AI Vector Searchnothing else - retrieval at scale, on its own
AlloyDBa transactional join against operational rows
Spannerthe same, across regions, with global consistency
Memorystorethe lowest latency, on data that may be lost
BigQuerya warehouse scan over data already in the warehouse

2. Three levels of assembly

Two cautions from the verified inventory. The managed retrieval pipeline is recorded as preview, so confirm its stage before a design depends on it. And the enterprise search product has been renamed more than once - it appears in different material under at least three names, and the inventory notes that an older product page and its first replacement URL are both gone. Navigate from the current documentation rather than from a remembered name.

3. What retrieval actually has to get right

The reframing Two questions, in this order. How much of the pipeline do you want to own - because the managed levels decide part of the rest for you. Then, if you own it, what else does the query need - a join, a scan, a cache, or nothing - because that, and not the vectors, selects the store you already operate.

Check yourself

Retrieval practice

Answer from memory before revealing.

A retrieval query must also join against live customer rows in a transactional database. Where should the vectors live?
What else the query needs is the deciding factor, and a transactional join points at the operational store. The second is workable and adds a round trip and a system. The third moves live rows into a warehouse. The fourth adds a cache that still has to be filled from somewhere.
What does the inventory record about the managed retrieval pipeline?
Preview, with an explicit instruction to confirm the stage. The first overstates it. The second invents a retirement. The fourth collapses two products the inventory records separately.
An answer is wrong because the material handed to the model did not contain the fact. What should be examined?
Retrieval decides what the model sees, and nothing downstream recovers a document that was not returned. The first is exactly the reflex this page argues against. The third confuses a feature that ties an answer to sources with the step that finds them. The fourth invents a truncation behaviour.

Practice about 12 minutes, with paper

Practice 1working

A support team wants an assistant that answers from the company's own help articles. A second team wants product recommendations that combine a semantic match with the customer's live order history. A third wants an analyst-facing similarity search over five years of transcripts already in the warehouse.

Place the vectors for each, choose an assembly level for the first, and say what you would confirm before committing to it.

Hint

Three requirements, and each names something the query needs besides nearest neighbours - except one, which names nothing at all.

Show the worked solution
  1. The help articles. Retrieval stands alone here - no join, no warehouse scan. The dedicated vector service fits, and so does the enterprise search product if the team would rather not assemble anything.
  2. The recommendations. The query combines a semantic match with live order history, so the vectors belong in the operational database that holds those orders, using its own vector search. Keeping them apart would mean a second system and a copy of the catalogue kept current.
  3. The transcripts. Five years of data already in the warehouse, queried by analysts. BigQuery vector indexes keep the search where the data is, and no export or second store is created.
  4. Choose the assembly level for the first. The enterprise search product is the least work and gives the least control; the managed retrieval pipeline sits between; building it yourself gives control over chunking and ranking, which is where answer quality is usually won. For a first version over a defined article set, the packaged product is a reasonable starting point.
  5. Say what to confirm. Two things. The current name and documentation location of the search product, because it has been renamed more than once and old URLs are gone. And, if the managed pipeline is chosen instead, its stage - the inventory records it as preview.

Sanity check. Each of your three placements should be justified by something other than the vectors. If all three landed in the dedicated service, ask what second system and what copy each of the other two would then need.

Your teacher. When a team asks which vector database to use, ask an agent to write out the full query the application will run. If it contains a join, a filter on live data or a scan over a warehouse table, the store has already been chosen by the rest of that query.
