The layer above the data decides who can actually use it

working 7 min Capabilities data-catalog, clean-rooms and bi-dashboards. Sourced from Knowledge Catalog, BigQuery data clean rooms and Looker.

The one-minute version

  • Knowledge Catalog is the governance layer: zones and assets, a business glossary, lineage, and policy tags that drive column-level security in BigQuery.
  • Its name has changed twice - Data Catalog, then Dataplex Universal Catalog, then Knowledge Catalog - so older material and search results point at all three.
  • BigQuery data clean rooms let several parties query joined data without any party reading the other's rows. They are built on Analytics Hub sharing rather than sold as a separate service.
  • The publisher shares views and sets analysis rules such as aggregation thresholds and join restrictions, and subscribers query in place - no copy leaves the publisher's project.
  • Two products share the dashboard row: Looker, governed by a LookML modelling layer, and Looker Studio, free and self-serve across many sources.

1. The catalogue, and the one part of it that enforces

The rename chain is worth stating plainly because it reaches every search you will do: this product was Data Catalog, then Dataplex Universal Catalog, and is now Knowledge Catalog. Its documentation is still served under the Dataplex path, which is the usual half-finished state of a platform rename.

2. A clean room is a query somebody else's data never leaves

The verified inventory records this as built on Analytics Hub sharing rather than as a service of its own, which is worth knowing when you go looking for it in the console. The documentation is where the analysis rules are described, and the rules are the design surface - the join and the aggregate you allow are the whole agreement.

3. Two products on the dashboard row

Looker Studio was Data Studio, which is the third rename in this module. Its Pro tier adds team governance, and it connects to a great many sources beyond BigQuery, which is exactly why it spreads faster than a modelling layer does.

The reframing These three products answer three questions that get confused with one another. What does this column mean and where did it come from is the catalogue. May this party see that party's rows is the clean room. Is everyone computing the metric the same way is the modelling layer. Buying a dashboard tool answers only the third, and only if it has one.

Check yourself

Retrieval practice

Answer from memory before revealing.

Which part of Knowledge Catalog actually prevents somebody reading a column?
Policy tags are the enforcing mechanism and the rest of the catalogue is descriptive. The first describes lineage as an access log, which it is not. The second and fourth are organising features - useful, and neither of them blocks a read.
Two companies want to measure the overlap between their customer bases without sharing customer lists. What fits?
Querying in place under analysis rules is exactly the clean-room shape, and no copy leaves either project. The first still exposes whatever the view returns without aggregation rules. The second puts both datasets somewhere both can read. The third requires the data to be modelled together, which is the thing being avoided.
What does LookML give a business intelligence estate that a self-serve tool alone does not?
A modelling layer defines a measure once so every report reuses it. The first is the self-serve tool's advantage rather than Looker's. The third describes Looker Studio's pricing. The fourth is a catalogue and warehouse function, not a property of either dashboard product.

Practice about 15 minutes, with paper

Practice 1working

An analytics platform is live. Three complaints arrive in the same week. Finance and marketing report different revenue numbers for the same month. A privacy review finds an email column readable by every analyst. And a retail partner asks to measure campaign overlap, offering to send a customer file by secure transfer.

Assign each complaint to the product that answers it, and say for the third why the partner's own proposal is the wrong shape.

Hint

Three complaints, three different products, and none of them is fixed by the tool that drew the chart. The third one is answered by refusing the transfer rather than by securing it.

Show the worked solution
  1. Two numbers for one month. The metric is defined twice, once in each report. That is what a modelling layer prevents: LookML defines the measure once and every report reuses it, so the two teams cannot diverge by construction.
  2. The readable email column. This is enforcement, so it is policy tags in Knowledge Catalog driving column-level security in BigQuery. Documenting the column as sensitive in a glossary would describe the problem without changing who can read it.
  3. The partner's overlap question. A clean room. Both parties share views into it, analysis rules set the aggregation threshold and the permitted joins, and each side queries in place.
  4. Say why the transfer is the wrong shape. A secure transfer still produces a copy, and the copy outlives the campaign, the contract and the relationship. The clean room's defining property is that no copy is made, so the risk it removes is not interception - it is possession.

Sanity check. Each complaint should map to a different product, and none of them to a dashboard tool by itself. If the email column was answered with a glossary entry, ask what it stops - the answer is nothing.

Your teacher. If two teams disagree about a number, ask an agent to find every place that metric is defined. A count above one is the finding, and it is an argument for a modelling layer rather than for a meeting.

Primary source to go deeper

The data clean rooms documentation is where the analysis rules and the query-in-place model are described, and it is the page a data-sharing agreement should be designed against. Knowledge Catalog covers the governance layer, and Looker the modelling one.
