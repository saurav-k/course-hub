Module 03 · Containers and serverless · Lesson 0302

Cloud Run gives a container a URL, no cluster, and a floor of zero

working 10 min Capability serverless-containers. Sourced from Google's Cloud Run overview.

The one-minute version

  • Cloud Run takes a container and runs it with no cluster and no nodes, fronting HTTP directly and scaling to zero when nothing is arriving.
  • It has four shapes, not one: services for HTTP, jobs for work that finishes, worker pools, and single instances.
  • A deploy creates a revision, and traffic is split across revisions - so a canary release is a property of the platform rather than something you assemble.
  • Billing has two modes: request-based and instance-based, and the choice follows from whether the container does anything between requests.
  • Google Cloud ships no proprietary non-Kubernetes orchestrator. That absence is real, and Cloud Run is not it - Cloud Run is a serverless runtime, not a general orchestrator.

1. Four shapes, one platform

2. Revisions, and why canary is free here

This is the same idea the compute module met in the instance template: a new version is a new immutable object, so the old one still exists and going back is a pointer move. Cloud Run applies it to running traffic rather than to a fleet's blueprint, which is why progressive delivery on this platform starts working before anybody has built a pipeline for it.

3. The floor of zero, and what it is billed against

The billing model comes in two forms and they are not interchangeable. Request-based billing charges for the time a container is handling requests, which suits a service that does nothing between them. Instance-based billing charges for the time the instance exists, which is what a container doing background work between requests actually needs - under request-based billing that work is happening outside the window being paid for, and the platform is under no obligation to let it run.

4. Where a Cloud Run service sits on the network

Direct VPC egress puts a Cloud Run workload's outbound traffic onto your VPC network, which is what lets a serverless container reach private resources without a public path. There is a pleasing consequence in the telemetry: VPC Flow Logs cover Cloud Run resources using Direct VPC egress as well as virtual machines, so a serverless workload's connections are visible in the same flow records as everything else.

Observability arrives without configuration in the other direction too. Request records and container output both land in Cloud Logging, and Error Reporting groups exceptions out of those logs on its own. Module 10 works both properly.

The reframing One absence on this row is genuine and worth stating exactly. Google Cloud has no proprietary non-Kubernetes container orchestrator - the kind of scheduler some platforms sell beside their Kubernetes service. The nearest managed alternative is Cloud Run, and the research behind this course is careful about the wording: Cloud Run is a serverless runtime rather than a general orchestrator. So the choice here is genuinely two-way - Kubernetes, or serverless containers - where on another platform it might be three.

Retrieval practice

Answer from memory before revealing.

A container does background processing between requests. Which Cloud Run billing mode fits, and why?
Request-based billing pays for the time spent handling requests, so work outside that window is not what is being paid for. The first option misdescribes the work. The second is a price claim that ignores what the container needs. The third names the right mode for the wrong reason, which is the distractor worth catching.
A new Cloud Run deploy is misbehaving under real traffic. What is the fastest way back?
Both revisions exist, so rollback is a change to the split and nothing has to be rebuilt. The second option works and is slower for no reason. The third confuses scaling with routing - the split, not the instance count, is what sends traffic. The fourth is destructive when a dial would do.
Google Cloud has no proprietary non-Kubernetes container orchestrator. What does that mean for a design?
The absence is a real one and it narrows the menu to two managed answers rather than removing container hosting. The second option is the near miss - Cloud Run is a serverless runtime, not a general orchestrator. The first and fourth both turn a narrower menu into a missing capability.

Practice about 15 minutes, with paper

Practice 1working

An internal reporting tool receives a handful of requests during working hours and none overnight. Users complain that the first request each morning is noticeably slow. The team proposes setting a minimum instance floor.

Explain what the floor fixes and what it costs, then name the question that decides whether it is worth it.

Hint

Look at the schematic again. The floor is a horizontal line, so ask over what fraction of the day it sits above the actual instance count.

Show the worked solution
  1. Name the symptom's cause. Between bursts the service scales to zero, so the first request of the morning arrives with nothing running and pays for a container to start.
  2. State what the floor does. A minimum instance floor keeps at least one container alive, so the first request finds something already running and the slow morning disappears.
  3. State what it costs. The floor is held all the time, including the overnight hours when the service receives nothing. The bill goes from roughly the working-hours traffic to a whole day of at least one instance.
  4. Name the deciding question. How much is one slow request per morning worth, against paying for an idle container through every night and weekend. It is a business question and not a technical one, and the technical answer is only the price tag on each side.

Sanity check. The cost should be described as continuous and the benefit as occasional. If they came out symmetrical, the shape of the schematic has not been used - the floor is a flat line across the whole day and the problem it solves happens a handful of times.

Your teacher. If the four Cloud Run shapes still blur, ask an agent to describe how each one is triggered. Services wait for a request, jobs are started, worker pools process, single instances just are - and the trigger is what tells you which one your workload is.
