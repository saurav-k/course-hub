Module 11 · Security services · Lesson 1101

Three places can stop a request, and each sees something the others cannot

working 8 min Capabilities waf, recaptcha-enterprise, cloud-firewall and packet-mirroring. Sourced from Cloud Armor and Cloud NGFW.

The one-minute version

  • Cloud Armor attaches security policies to the load balancer from lesson 0705. It carries managed rule sets for the common injection and scanning attacks, plus custom rules written in CEL.
  • Two Armor features change designs rather than settings: preview mode, which evaluates a rule without enforcing it, and rate limiting through throttle and ban rules.
  • reCAPTCHA Enterprise is a different kind of judgement: it scores a sign-in or checkout for fraud and abuse rather than matching a request against a rule, and it integrates with the edge policy.
  • Cloud NGFW is the firewall family from lesson 0701. The standard tier is the classic rules and policies; NGFW Enterprise adds threat inspection, including of TLS traffic.
  • Packet Mirroring is not an enforcement point at all. It clones traffic to an out-of-band collector, and it is a capture tap rather than a log stream.

1. Three depths, three kinds of knowledge

Cloud Armor's managed rule sets cover the common families - injection, cross-site scripting, file inclusion, remote code execution and scanners - and custom rules are written in the same expression language used elsewhere on the platform. Its always-on protection at layers three and four was introduced in lesson 0705; this page is the configurable half.

2. Preview mode, and why every rule should start there

Rate limiting is the other lever, expressed as throttle and ban rules on the same policies. It is worth naming separately because it addresses a different attack: not a malformed request but too many well-formed ones.

4. Inspecting deeper, and looking without stopping

The reframing Place a control by asking what it can see. The shape and rate of a request is the edge. Behaviour across sessions is the abuse score. Who is talking to whom is the firewall. What is inside the payload is threat inspection, and a copy for something else to analyse is the mirror. A requirement that names an attack rather than a product usually answers itself once you ask which of the five could have seen it.

Check yourself

Retrieval practice

Answer from memory before revealing.

Why should a managed Cloud Armor rule set be added in preview mode first?
Rules written for the whole internet always catch something particular to your application, and preview is where you find it without an outage. The first invents a requirement. The second and third invent a dependency and a billing rule that the inventory does not record.
What does reCAPTCHA Enterprise return, and what follows from that?
It scores rather than decides, so the design is incomplete until a threshold and an action are chosen. The second and third describe what a rule does. The fourth turns a control into telemetry.
A team wants a copy of traffic for a third-party detection appliance. What provides it?
Packet Mirroring is the capture tap and it is not a log stream. The first offers sampled, interpolated records with no payload. The second inspects in the path rather than cloning out of it. The fourth confuses preview mode with mirroring.

Practice about 15 minutes, with paper

Practice 1working

A retail site reports three problems in one week. Automated scripts are creating thousands of fake accounts. A scanner is probing the application for injection flaws. And an internal service is being reached by a workload that should have no business calling it.

Place each problem at the control that can actually see it, say what the first control returns and what the team must add, and state how you would deploy the second one safely.

Hint

Three problems, three depths. One control returns something that is not a decision, and one should never be switched straight to enforcing.

Show the worked solution
  1. The fake accounts. reCAPTCHA Enterprise on the sign-up flow. This is behaviour across sessions rather than a malformed request, so no rule at the edge would match it and no firewall would see anything unusual.
  2. Say what it returns. A score. The team must choose a threshold and a consequence - challenge, refuse, or flag for review - because the product describes and does not decide. Collecting scores and acting on none of them changes nothing.
  3. The scanner. Cloud Armor managed rules at the edge, which cover the injection and scanner families, backed by rate limiting through throttle or ban rules so that the probing itself is expensive.
  4. Deploy it safely. In preview mode. Observe what the rules match on real traffic, narrow the ones that catch legitimate requests, then switch to enforcing - the same habit as the perimeter dry run on the previous page.
  5. The unexpected internal caller. The firewall, and the useful part is the targeting from lesson 0701: write the rule against the calling service account or a secure tag rather than an address, so it stays true when either side is rebuilt.

Sanity check. Your three answers should sit at three different depths, and the account-creation one should not be a rule. If the internal-caller problem was solved at the edge, note that the traffic never passes the edge at all.

Your teacher. Given an attack description, ask an agent which of the five controls on this page could have observed it. Usually only one could, and that answer selects the product before any feature comparison starts.
