Module 01 · The lay of the land · Lesson 0103

The platform is eight layers on one network, and several of its names have moved

foundation 9 min The orientation page for the other thirteen modules. Sourced from Google's product catalogue.

The one-minute version

  • Google Cloud is one global production network with compute, storage and managed data services attached to it. Everything in this course hangs off that sentence.
  • Above the network sit eight layers: geography, hierarchy, compute, storage, data, networking, operations and identity - which is the shape of the remaining thirteen modules.
  • Several products were renamed or retired under engineers who already knew them. A stale name is not a cosmetic problem: some of the old services no longer accept writes.
  • A second family of traps is worse, because nothing fails: things that sound equivalent to another platform's feature and are not.
  • When a capability has no product, there are two very different reasons - the platform ships nothing, or the capability lives inside another service - and this course always says which.

1. The map

Two branches deserve a sentence now because the rest of the course leans on them. Identity is one system for people and for machines: a workload runs as a service account and fetches short-lived tokens, so a design that copies a key file around is not a Google Cloud design. Data is where the platform's own centre of gravity sits, with a warehouse that separates storage from compute inside itself rather than beside itself.

The churn reaches into the certification material itself: the current Associate Cloud Engineer guide names an AI runtime by a name the product documentation has since changed again. Treat any product name in a course, a blog post or an exam guide as a pointer that may have moved, and resolve it against the product catalogue before building. This page will age the same way, which is why every row above carries the vendor link rather than only the claim.

3. The traps where nothing fails

Renames announce themselves eventually. The following do not, because each one is a thing that resembles a feature you already know and behaves differently.

The private-connectivity one is the most expensive. Google Cloud has three distinct mechanisms for reaching managed services privately - Private Google Access, Private Services Access and Private Service Connect - and they are not tiers of one thing. Module 07 separates them properly.

4. How to read a capability with no product

Sometimes a capability you expect has no service name here. There are two very different reasons, and this course states which one applies every time.

The reframing The four-cloud view of these gaps is a different course's job. Comparing the Four Clouds opens with a capability matrix that separates the two branches above as distinct cell states, cloud by cloud. This course stays inside Google Cloud and names the branch in prose instead.

Check yourself

Retrieval practice

Answer from memory before revealing.

A build pipeline written some time ago pushes images to Container Registry. What happens when it runs today?
Container Registry is shut down rather than renamed: reads redirect into Artifact Registry and writes are unavailable, so the push is the step that breaks. The first and fourth options describe the gentler outcomes of a rename, which is exactly the assumption that gets a pipeline stuck. The third invents a behaviour nobody documents.
Google Cloud has no separate Kubernetes node autoscaler product. What does that tell you?
Node auto-provisioning and the cluster autoscaler are part of the managed Kubernetes service, so this is a packaging difference rather than an absence. The second option is the false negative this course is built to prevent. The first and fourth each describe a real situation on some platform, and neither is this one.
Which statement about the private paths into managed services is correct?
Private Google Access, Private Services Access and Private Service Connect are three separate mechanisms with different shapes and different use cases. The other three options each fold them into one thing, which is exactly the mistake that produces a design reaching a service by a path it does not support.

Practice about 15 minutes, with paper

Practice 1foundation

An architecture document written a few years ago names these five things: Cloud Functions, Container Registry, Deployment Manager, Anthos Service Mesh, and Cloud Source Repositories.

For each one, write down the current name and the state it is in, then rank the five by how urgently the document must be changed, and say what the ranking is based on.

Hint

Two of the five are only words. The ranking is not about how old the name is - it is about what happens the next time someone runs the thing.

Show the worked solution
  1. Resolve the names. Cloud Functions is now Cloud Run functions, with the first generation legacy. Container Registry is shut down and reads redirect into Artifact Registry. Deployment Manager is deprecated and turning down, replaced by Infrastructure Manager. Anthos Service Mesh is now Cloud Service Mesh. Cloud Source Repositories is closed to new customers, with Secure Source Manager as the current first-party managed Git.
  2. Separate words from behaviour. Cloud Functions and Anthos Service Mesh are renames - the document is confusing rather than broken, and nothing stops working.
  3. Rank by what breaks next. Container Registry first, because writes are refused today. Deployment Manager second, because it is on an announced path to turndown. Cloud Source Repositories third, because a new project cannot adopt it at all. The two renames last.
  4. Name the criterion. The ranking is by whether the next attempt to use it succeeds, not by how unfamiliar the name looks - which is why the two most alarming-sounding entries rank lowest.

Sanity check. Exactly two of the five should be pure renames and exactly one should be an immediate failure. If everything landed in one bucket, the four-state picture at the top of this section has not been applied - the states are genuinely different and the document only needs urgent work for some of them.

Your teacher. If a name in your own notes feels uncertain, ask an agent to resolve it against the product catalogue and to say which of the four states it is in - current, renamed, deprecated, or shut down. The state is the part that decides what you have to do, and it is the part most answers leave out.

Primary source to go deeper

The Google Cloud product catalogue is the only list that is current by construction. Read a name off it rather than out of a tutorial, and follow the product's own documentation link from there - it is where a rename or a turndown notice appears first.
