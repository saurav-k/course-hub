Module 06 · Identity and access · Lesson 0603

Encryption is table stakes - custody of the key is the decision

working 8 min Capability area secrets-keys, six rows of the matrix: key-management, hsm, byok-hyok, secrets-store, certificate-manager, certificate-authority.

The one-minute version

  • All four clouds run envelope encryption against a managed key. The question a design has to answer is how far that key may get from the cloud.
  • Only AWS and Google Cloud hold the key entirely outside their own boundary. OCI gives exclusive custody of a hardware partition that still sits inside OCI.
  • Azure is the only cloud where every service encrypts by default with a platform key and a customer key is layered on top rather than chosen per service.
  • AWS is the only cloud that splits the secret store in two - a rotating store and a cheap parameter store with no rotation.
  • Azure ships no managed private certificate authority. OCI has one and sells no separate product for it, which is a different claim and a different cell.

1. The custody ladder

The rung a cloud reaches is a fact worth stating precisely, because the two middle ones are easy to confuse with the top one. Azure customer-managed keys wire a Key Vault key as the root of each service's envelope encryption, which is rung three. OCI reaches rung three twice over - it imports your key material, wrapped with the vault's public wrapping key before upload, and it gives you a single-tenant hardware partition - but the research records the distinction explicitly: the hardware still sits inside OCI, so this is not the hold-your-own-key pattern of the other two.

4. Where a secret lives

Three clouds ship one secret store. AWS ships two, and the split is the design decision. Secrets Manager carries native rotation, staging-label versioning and cross-region replication and charges roughly forty cents per secret each month; Parameter Store is free in its standard tier up to ten thousand parameters, encrypts with a key when you ask it to, and has no rotation at all. AWS's own guidance is to use the first specifically where a database credential has to rotate.

5. Certificates, and the one genuine absence

Two rows sit under one word here and they answer different questions. A certificate manager issues, renews and deploys TLS certificates onto load balancers and edge services. A certificate authority is a private hierarchy you operate, for mutual TLS between your own workloads.

The public side diverges too, in the opposite direction. AWS Certificate Manager issues free public certificates that renew themselves, provided the certificate is associated with an integrated service - an imported certificate never auto-renews. Google Cloud Certificate Manager deploys managed and self-managed certificates onto load balancers through certificate maps. OCI's service is an internal authority plus imports rather than a public issuer, so a public certificate there comes from your own authority or is imported.

6. What this certification tests

Key custody is examined heavily on three of the four tracks and the verified inventories mark key management as high exam weight on AWS, Azure, Google Cloud and OCI alike. On OCI it is named inside the heaviest domain of the blueprint: Architect Security Solutions at 25 percent lists application and data security with WAF, Certificates and Key Management by name. On Azure the same ground sits in the 25 to 30 percent identity, governance and monitoring domain, whose objectives include managing secrets, certificates and keys explicitly.

Check yourself

Retrieval practice

Answer from memory before revealing.

A regulator requires that the cloud provider be unable to decrypt the data. Which clouds can meet it?
Only the AWS external key store and Google Cloud External Key Manager keep the key material outside the provider entirely. The first option is the common mistake: imported material still lives in the provider's hardware afterwards. The second and third both name real single-tenant offerings, and exclusive custody of a partition inside the cloud is not the same claim as the key never entering it.
A team needs a private certificate authority for mutual TLS between their own services. Which cloud has none?
Azure records a genuine absence: Key Vault issues certificates through integrated public authorities, and a private hierarchy runs on your own AD Certificate Services. OCI has the capability inside its Certificates service, which is a packaging difference and not an absence. Google Cloud and AWS both sell a separate private authority product, so the second and fourth options describe a real thing and answer a different question.
Why does a design on Azure rarely start by asking whether to encrypt a data store at rest?
Azure encrypts at rest by default with a platform key and accepts a customer key on top, so the real question is whether to override rather than whether to encrypt. The second inverts the default and would make the platform key pointless. The third invents an inheritance Azure does not have, since a resource group is a lifecycle container. The fourth confuses the rotation policy on a vault key with the service itself.

Practice about 15 minutes, with paper

Practice 1working

A workload must run on all four clouds under one policy: the customer can revoke access to their own data at any moment by destroying a key, and the cloud provider cannot undo that.

Say what you would build on each cloud, and name for each one the cost the design pays for that promise.

Hint

Start at the top rung of the ladder and walk down only when a cloud cannot reach it. Then ask what a read looks like on the rung you landed on - the cost of the promise is always in that path.

Show the worked solution
  1. AWS - the top rung. An external key store keeps the key in your own manager behind a proxy, so destroying it there ends every read. The cost is availability: your key manager is now in the path of the data, and AWS's own documentation notes the double encryption and that the availability risk usually outweighs the benefit.
  2. Google Cloud - the top rung. External Key Manager holds the key outside Google, optionally reached over a private path. The cost is the same shape - an external dependency on every operation that touches the key.
  3. Azure - rung three. A customer-managed key in Key Vault becomes the root of each service's envelope encryption, and destroying it stops the service serving data. The cost is that revocation semantics differ per service, so the kill switch has to be verified service by service rather than assumed.
  4. OCI - rung three. Import your own material into a vault key, or hold a dedicated partition. The cost is that the hardware is still inside OCI, so the promise is about your key rather than about the provider's reach, and the policy has to say so honestly.
  5. State what changed between the two halves. On two clouds the promise is enforced by physics; on two it is enforced by the provider honouring a key state. Both are defensible and only one of them survives a regulator asking who could technically decrypt.

Sanity check. Exactly two clouds should reach the top rung. If your answer puts OCI there because of its single-tenant partitions, re-read the difference between exclusive custody inside a cloud and material that never enters it - the research corpus flags that exact confusion.

Your teacher. If the ladder blurred, ask an agent to write the read path for one encrypted object at each of the four rungs and to mark the point at which a network failure makes the data unreadable. The reason the top rung is rare stops being abstract as soon as the failure point is drawn.
