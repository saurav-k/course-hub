Module 06 · Identity and access · Lesson 0601

A machine proves who it is with something the platform mints

working 9 min Capability area identity-workload, five rows of the matrix: workload-identity, workload-identity-federation, cross-account-assumption, short-lived-credentials, agent-identity.

The one-minute version

  • All four clouds remove the stored key the same way: the workload asks a local endpoint and gets a short-lived token bound to the compute it runs on.
  • They differ in what the identity is bound to - a role wrapped in a profile, a directory object, an attached account, or a rule that matches the instance.
  • OCI is the only one where authorisation runs through a dynamic group match first, and it carries two caveats the vendor prints on the same page.
  • Crossing a boundary is a token mint on AWS and Google Cloud, and a pair of aligned policy statements on OCI, where nothing is assumed at all.
  • The worst-case life of one credential runs from about one hour to twenty-eight, and the longest one buys near-real-time revocation in exchange.

1. The shared move: ask locally, receive briefly

2. What the identity is bound to

Oracle prints two consequences of instance principals on the page that introduces them, and both are first-order for least privilege. Any user who can reach the instance over SSH automatically inherits the privileges granted to the instance. And every compute instance principal holds an irrevocable compartment_inspect permission - the page states plainly that you cannot revoke it - so a compromised instance can enumerate compartment names, descriptions and free-form tags across the whole tenancy (calling services from instances).

Kubernetes is where the bindings diverge most. AWS offers two generations at once: EKS Pod Identity, which needs no OIDC provider and trusts a single pods.eks.amazonaws.com principal, and the older IRSA, which registers a per-cluster OIDC provider and has pods exchange a projected service-account token. OCI reaches pod-level identity only on enhanced clusters through OKE Workload Identity; a basic cluster falls back to node-level instance principals, which over-grant every pod on the node.

3. Trusting a workload that is not yours

A build running on someone else's infrastructure has no metadata endpoint of yours to ask. Every cloud solves this by trusting an external issuer and exchanging its token.

OCI's coverage here is narrower and the research says so plainly rather than calling it an absence: the supported paths are OKE Workload Identity for Kubernetes-native claims and identity-domain OAuth applications for software clients, so the generic token-exchange federation AWS and Google Cloud offer for arbitrary external issuers has no direct counterpart (identity domain federation).

4. Crossing a boundary

The trap worth carrying In an AWS trust policy, arn:aws:iam::111122223333:root does not mean the root user. It delegates to the entire account, so any principal there whose own identity policy allows the action can use it. AWS states this on the Principal element page, and the bare account identifier behaves the same way.

5. How long the credential lives

6. Identity for an agent

The newest row in this area is the one where the four clouds are furthest apart, and it is a clean example of why the matrix separates two kinds of empty cell. Azure ships Entra Agent ID, a directory object with a human sponsor and governance controls, currently in preview. AWS has the capability and no directory object for it: agent credentials are issued and scoped inside Bedrock AgentCore Identity, which the matrix records as delivered elsewhere and links to the agent platform row. Google Cloud and OCI are recorded as genuine absences with the same reason on both - agents run as ordinary service or resource principals, so agent lifecycle and human sponsorship are not modelled separately.

7. What this certification tests

Machine identity is examined as design rather than as configuration. The AWS Solutions Architect Professional guide reserves 26 percent for Design Solutions for Organizational Complexity, where cross-account roles and federation chains live, and adds an unscored emerging-topics block that names AgentCore Identity access controls explicitly. On Google Cloud, workload identity federation and impersonation sit inside the designing for security and compliance domain at about 17.5 percent.

Answer from memory before revealing.

A GitHub Actions job needs to deploy to a cloud with no stored key. What actually gates the trust?
A federation that names an issuer without pinning the subject trusts every repository on that issuer, so the attribute condition is the boundary. The first option matters after the fact and limits damage rather than preventing entry. The second is not part of the exchange at all. The fourth decides what the credential can do once trust has already been granted, which is a different question.
Two OCI tenancies must share data. What has to exist for the call to succeed?
OCI has no AssumeRole primitive: the source writes Endorse, the target writes Admit and the Define lines that resolve the foreign group, and both must exist. The third option is the AWS shape and the fourth is the Google Cloud shape, which is why both feel plausible. The first is close to the AWS resource-policy idea, and OCI has no resource-level policy layer at all.
Why does a long Azure token lifetime not automatically mean weaker offboarding?
The extension to 24 to 28 hours is granted precisely because revocation stops depending on expiry: critical events such as an account disablement propagate in near real time. The first two are true statements about other mechanisms and do not explain the extension. The third is false and is the misconception this page's previous lesson exists to remove - Conditional Access runs at authentication, not per request.

Practice about 15 minutes, with paper

Practice 1working

An auditor asks a single question of a four-cloud estate: if one virtual machine is compromised at 09:00 and you revoke its access at 09:05, when does the attacker actually lose it on each cloud?

Answer for AWS, Azure, Google Cloud and OCI, using only what the vendor pages state, and say which cloud you cannot answer for and why.

Hint

Separate two clocks that are easy to merge: how long an already-issued credential stays valid, and how quickly a revocation signal reaches the place that checks it. Only one cloud documents the second clock.

Show the worked solution
  1. AWS. The session already minted runs to its own expiry, up to the role maximum of twelve hours, or one hour if it arrived by role chaining. Removing the permission stops the next call once the policy change takes effect, so the honest answer is bounded by the session, not by the revocation.
  2. Azure. About 75 minutes by default. On a surface that supports continuous access evaluation the token may live 24 to 28 hours, and that is the case where revocation arrives on a signal rather than on expiry - so the answer is minutes if the resource speaks continuous access evaluation, and up to 28 hours if the token is long-lived and it does not.
  3. Google Cloud. Credentials from the metadata server are temporary, and the pages read for this course state no maximum. This is the cloud you cannot answer for from the verified corpus, and saying so is the correct answer rather than guessing an hour.
  4. OCI. Instance principal session tokens are documented at about one hour and refreshable, so the window closes within roughly an hour of the dynamic group or policy being changed.
  5. State the design consequence. Three of the four answers are governed by expiry, which means the revocation you perform is really a promise about the next hour rather than about this minute.

Sanity check. Every number in your answer should be traceable to a vendor page, and exactly one cloud should have no number at all. If you wrote an hour for Google Cloud, check where that hour came from - it is a reasonable guess and it is not on the page.

Your teacher. If the federation section stayed abstract, ask an agent to write the trust configuration for the same CI job on all four clouds side by side, then to delete the subject condition from each one and say what an attacker could now do.
