Module 04 · Analytics · Lesson 0401

Every cloud runs the same analytics pipeline and cuts it into products differently

working 8 min Capability keys compared here: stream-ingest, stream-analytics, data-lake, etl-service, managed-spark, data-warehouse, serverless-query-engine, managed-search, bi-dashboards, data-catalog, clean-rooms.

The one-minute version

  • The pipeline is identical everywhere: ingest, land, transform, query, present, with a catalogue across the whole of it.
  • The clouds differ in where the product boundaries fall. The same capability is a separate product on one cloud and an attribute of a bigger one on the next.
  • Two rows here have no separate product on two clouds and are delivered inside another one, which is a packaging finding rather than a gap.
  • Exactly one genuine absence sits in this whole area, and one row's design constraint is a scope rule rather than a feature.

1. One skeleton, four fillings

Read the eleven rows of this area as one pipeline and the comparison becomes tractable. Each stage has an answer on every cloud, and the only question is whether that answer is its own product or a mode of a larger one.

2. The boundary moves: querying files without a cluster

Running SQL straight over files in the lake with nothing to provision is one capability with four packagings, and this row is the clearest example on the page of why a name-matching table misleads.

AWS sells it as its own product: Athena, billed per terabyte scanned, which is why a columnar format such as Parquet cuts the bill sharply and why workgroups can cap the scan a single query is allowed. Azure sells it as a mode of a workspace, the Synapse serverless SQL pool, reading Parquet, CSV, JSON and Delta from the lake and billed per terabyte processed. Google delivers it inside BigQuery, which is itself serverless and bills per byte scanned over managed storage and external lake tables alike. Oracle delivers it through Autonomous external tables and Data Flow SQL over Object Storage.

The reframing The same capability is a product on AWS, a pool on Azure, an attribute of the warehouse on Google Cloud, and a feature of the database on OCI. All four can query files in place. A comparison table that only counts product names reports that two clouds are missing something, and it is wrong on both.

3. Ingest is where the numbers live

The ingest row is the one stage of the pipeline whose sizing is arithmetic rather than judgement, and it is also where the four clouds sell the most different-looking things for the same job.

Kinesis Data Streams publishes that arithmetic plainly, and it is worth carrying because it is the shape every partitioned stream has. One shard takes 1 MB per second in and gives 2 MB per second out, a single record may be up to 10 MiB, and retention runs from 24 hours to 365 days.

The other three package the same idea differently. Azure Event Hubs buys capacity in throughput or processing units, speaks the Kafka protocol at its own endpoint, and can capture raw events into storage without a consumer. Google's answer on this row is Managed Service for Apache Kafka, with Pub/Sub holding its own row in the messaging area rather than this one. OCI ships two products in one cell and the choice between them is real: the classic serverless Streaming service with a seven-day replay, and managed Kafka clusters for change-data pipelines and stream analytics at scale.

4. One dedicated streaming engine, three other homes

Continuous queries over an unbounded stream, with windows, joins and late arrivals, is sold as a dedicated product by exactly one cloud. Azure Stream Analytics is a streaming SQL processor with windowing, reference joins and anomaly detection built in. AWS answers with Managed Service for Apache Flink, whose own legacy SQL application type has been retired, so new work there is Flink SQL, Java, Python or Scala rather than the SQL product the old name implied. Google delivers the capability inside Dataflow, whose Apache Beam pipelines carry windowing, triggers and exactly-once semantics. Oracle delivers it through Data Flow Spark Streaming and GoldenGate Stream Analytics.

5. The catalogue split, and the one genuine absence

The catalogue row is the second place a boundary moves. AWS splits it in two: the Glue Data Catalog is the technical metadata every query engine reads, and DataZone is the business portal where people find and request assets. The other three combine both jobs in one product. Carry one constraint off this row: a Glue catalog is region-scoped and does not replicate across regions, so a multi-region lake has multiple catalogues by construction rather than by choice.

The last row is the only genuine absence in the whole analytics area. Multi-party collaboration, where each party queries joined data without seeing the other party's rows, is a separate service on AWS, a confidential-computing product in preview on Azure, and a feature of BigQuery sharing on Google Cloud. OCI ships no multi-party clean room service. That is a real gap, recorded as one, and it is worth contrasting with the two rows above where a missing product name meant nothing at all.

Check yourself

Retrieval practice

Answer from memory before revealing.

One Kinesis shard feeds three consumers reading in the standard way. What does each consumer get?
Standard reads share the shard's 2 MB per second, so three consumers divide it. Per-consumer bandwidth is what enhanced fan-out buys, which is the first option and is exactly the upgrade this question is testing you have not assumed. The second option quotes the write side, and the third adds capacity that no configuration on this row creates by itself.
Google Cloud has no separate product on the serverless query engine row. What follows?
The cell says delivered elsewhere and names BigQuery, which queries external lake tables without a cluster. The second option is the opposite of what external tables are for. The third invents a provisioning step the row explicitly does not require. And nothing in the data records a roadmap, which is a state this taxonomy does not have.

Practice about 15 minutes, with paper

Practice 1working

A telemetry stream carries 1,200 records per second at roughly 2 KB each. Four independent teams each want to read the whole stream: a real-time alerting service, a warehouse loader, a fraud model and an archive writer. A replay of the last three days must be possible after a consumer outage.

Compute how many Kinesis shards the write side needs, compute what the read side needs under standard reads and under enhanced fan-out, and state the retention setting the replay requirement forces.

Hint

Do the write side and the read side as two separate divisions, then take the larger answer. The read side is the one that surprises people, because the shard's read budget is shared by every standard consumer rather than granted to each of them.

Show the worked solution
  1. Size the write. 1,200 records per second at 2 KB each is 2,400 KB per second, about 2.4 MB per second. At 1 MB per second per shard that needs 3 shards.
  2. Size the standard read. Four consumers each reading the whole stream want 4 × 2.4 = 9.6 MB per second. Standard reads share 2 MB per second per shard, so the read side needs 9.6 ÷ 2 = 5 shards, not 3.
  3. Take the larger. The write side asked for 3 and the read side for 5, so the stream is provisioned at 5 shards and the read side is what set the number.
  4. Re-size with enhanced fan-out. Each consumer gets its own 2 MB per second per shard, so 2.4 MB per second across 3 shards is 0.8 MB per second per consumer per shard, well inside the dedicated budget. The stream goes back to 3 shards, and the cost moves from shard hours into fan-out charges.
  5. Set retention. Three days is 72 hours, above the 24-hour default, so extended retention must be turned on explicitly. It is inside the 365-day maximum, so no second mechanism is needed.

Sanity check. The read answer must be larger than the write answer whenever more than two consumers read the whole stream, because each one wants the full 2.4 MB per second out of a 2 MB per second shared budget. If your read figure came out at or below 3 shards, check step two: you have probably given each consumer its own budget without buying enhanced fan-out.

Your teacher. When a comparison shows a blank in an analytics row, ask which product on that cloud absorbed the capability before you conclude anything. Three of the four rows on this page that look thin are packaging, and only the clean-room row is a real absence. Asking "what absorbed it" is the habit that keeps a four-way comparison honest.
