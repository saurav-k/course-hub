A scaling fleet is a template plus a controller, and only one cloud fuses the two

working 9 min Capability area compute-scaling, two rows of the matrix: instance-template and autoscaling-group.

The one-minute version

  • Every cloud builds a scaling fleet out of the same two parts: a template that says what one member looks like, and a controller that holds the count and replaces the dead.
  • AWS, Google Cloud and OCI ship those as two separate resources. Azure fuses them into the scale set, which is why the matrix row for a standalone template records an absence on Azure alone.
  • That absence is about a resource, not a capability. Azure stamps identical machines from the scale set model, and puts scheduled scaling in the autoscale profile instead of in a template.
  • Three scaling triggers exist across the four clouds - reactive, scheduled and predictive. OCI instance pools carry the first two and not the third.
  • The sharpest trap is a fleet that looks like a controller and is not one: an EC2 Fleet does not health-check and replace the way an Auto Scaling group does.

Two objects, one job

AWS EC2 Launch Template, versioned Auto Scaling group
Azure no standalone resource - the scale set model plays the part Virtual Machine Scale Set
Google Cloud Instance Template, immutable once created Managed Instance Group
OCI Instance Configuration Instance Pool with autoscaling
The reframing Read Azure's row as a missing resource, never a missing capability. Azure stamps identical machines from the scale set model exactly as the other three stamp them from a template, and its scheduled scaling lives in the Azure Monitor autoscale profile rather than in a template object. Reading that row as "Azure cannot do this" is the single most common way a four-way comparison misleads.

What the controller does without being asked

All four run that loop. Health signals differ: an Auto Scaling group and a managed instance group read the health of the instance and of any attached load balancer, Azure gets health from the Application Health extension, and an OCI instance pool can attach a load balancer of its own.

On AWS there is a second family of constructs that looks like a controller and is not. EC2 Fleet and Spot Fleet launch across many types, zones and purchase options in one request and will replace an interrupted Spot instance, but they do not health-check and replace a failed instance the way an Auto Scaling group does. Steady-state replacement needs an Auto Scaling group beside them.

Three triggers, and the one that is not everywhere

Auto Scaling groups carry dynamic, predictive and scheduled policies, and AWS recommends target tracking as the dynamic form. A detail worth holding: cooldown applies only to simple scaling, so a target-tracking policy is not governed by it. Scale sets in Uniform orchestration mode take Azure Monitor autoscale, which includes scheduled and predictive scaling. Managed instance groups include predictive autoscaling. OCI instance pools scale on metric thresholds or on a schedule, with up to fifty policies on one instance configuration, and Oracle documents no predictive form.

Where the fleets stop being peers

Two further divergences shape real designs. First, stateful members: Auto Scaling groups and managed instance groups support them, and a stateful managed instance group preserves disks and addresses across a replacement, while scale sets and instance pools are simpler homogeneous fleets. Second, reclaimable capacity inside a fleet: an AWS launch template is the only launch specification that allows mixed purchase options, and on OCI a preemptible instance cannot be used in an instance configuration at all, so a discounted instance pool is not available the way a Spot-backed Auto Scaling group is.

One AWS shape is closing quietly. Launch configurations, the predecessor of launch templates, are shut by account age rather than by announcement: a sufficiently new AWS account cannot create one by any method, and the newer instance types are unsupported in the ones that already exist. Warm pools and mixed purchase options were never available in them. A design that still names a launch configuration is not deprecated so much as unbuildable.

What this certification tests Fleet scaling sits inside the compute domain on both Azure blueprints - AZ-104 names scale set deployment among the skills measured under Deploy and manage Azure compute resources, 20 to 25 per cent, and AZ-305 folds it into Design infrastructure solutions, 30 to 35 per cent. On SAA-C03 the same material is split across Design Resilient Architectures, 26 per cent and Design High-Performing Architectures, 24 per cent, because a fleet is both a resilience mechanism and a performance mechanism. That split is the tell: an AWS question about an Auto Scaling group is usually really a question about which of the two properties the scenario is buying.

Check yourself

Retrieval practice

Answer from memory before revealing.

The matrix records an absence on Azure for the standalone instance-template row. What does that absence actually mean?
The scale set fuses the specification and the controller, so the resource is missing and the capability is not. The first option is the false negative this course exists to prevent. The third invents a limit nobody documents, and the fourth is wrong because scale sets are a first-party service.
A fleet must start growing before a daily traffic peak arrives, using its own history. Which controller has no documented form of that?
Oracle documents metric-based and schedule-based autoscaling for instance pools and no predictive form, so the ramp has to be scheduled by hand. The other three all name a predictive policy in their own documentation, which is what makes them wrong answers here rather than merely different ones.
An architect replaces an Auto Scaling group with an EC2 Fleet to get many instance types in one request. What breaks?
A fleet diversifies launch pools and replaces interrupted Spot capacity, but it does not health-check and replace a failed instance. Option one has the relationship backwards. Options two and four each name a real-sounding consequence of the wrong mechanism, and the point is that only the health loop is actually lost.

Practice about 15 minutes, with paper

Practice 1working

A team runs a stateless web tier on Google Cloud: a managed instance group of ten members, a stateless instance template, predictive autoscaling switched on, and a rolling update whenever the template version changes.

Write down what each of the four parts becomes on Azure and on OCI, and name the one part that has no direct translation on each of them.

Hint

Go part by part rather than service by service. For each part ask: is there a resource for this, is it a mode of another resource, or is there nothing at all?

Show the worked solution
  1. Map the controller. The managed instance group becomes an Azure Virtual Machine Scale Set and an OCI instance pool. Both hold a target size and replace unhealthy members, so this part translates cleanly on both.
  2. Map the template. On OCI it becomes an instance configuration, a separate resource like the Google Cloud one. On Azure there is no separate resource - the specification lives inside the scale set model, so the part exists but the object does not.
  3. Map predictive autoscaling. On Azure a Uniform-mode scale set takes Azure Monitor autoscale, which includes predictive scaling. On OCI there is no predictive form, so this is the part with no OCI translation and the ramp must be rewritten as a schedule.
  4. Map the rolling update. Both clouds roll a fleet through a new specification. The difference is where the version lives: on Azure the change is an edit to the scale set model rather than a pointer at a new immutable template, so the rollback story is the part with no clean Azure translation.

Sanity check. Exactly one part should be missing on each target and they should be different parts. If you concluded that Azure cannot roll a fleet forward at all, or that OCI cannot autoscale at all, you have turned a packaging difference into a capability gap - which is the failure this whole comparison is built to avoid.

Your teacher. If the template-and-controller split has not landed, ask an agent to build the same three-member fleet twice on one cloud - once by hand and once through the controller - and to kill a member in each. The difference in what happens next is the whole lesson.

Primary source to go deeper

The Amazon EC2 Auto Scaling user guide is the fullest written account of the controller loop in this area, and the vocabulary it uses - target tracking, cooldown, warm pools, instance refresh - is the vocabulary the other three clouds' documentation is most usefully read against.
