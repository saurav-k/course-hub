Module 05 · Networking, delivery and edge · Lesson 40

The four clouds build one private network and pin its edges to different things

working 13 min The thirteen networking-core rows of the capability matrix, compared across all four clouds.

The one-minute version

  • All four clouds give you the same five parts: a private address space, ranges carved out of it, interfaces that attach to a range, a routing decision, and a stateful filter on every packet.
  • What differs first is scope. A Google Cloud network spans every region at once and the other three are one region each. An AWS subnet is pinned to one zone and the other three are not.
  • Peering is non-transitive on all four, which is the single reason all four also sell a transit hub.
  • Reaching a managed service privately is four mechanisms at four granularities, and it is where a habit carried between clouds does the most damage.

1. One mechanism, four vocabularies

Before any brand name, the mechanism. You declare a block of private addresses that is yours alone and carve it into ranges. A workload gets a virtual adapter, which attaches to exactly one range and takes an address from it. Anything leaving the range consults a routing decision that names a next hop, and every packet is tested against a stateful filter. Five parts, and all four clouds have all five.

The vocabularies then diverge completely. The address space is a VPC, a virtual network, a VPC network and a virtual cloud network. Four names for one object is the normal condition in this course, and it is the least interesting difference on the page.

2. Scope is the first real difference

Google Cloud states the inversion plainly: the network is global and its subnets are regional, so a cross-region design needs no peering and no hub. On AWS, Azure and OCI the network is a regional object, so reaching a second region is an explicit act with its own object and its own bill.

One level down, AWS is the outlier. An AWS subnet sits inside exactly one Availability Zone, so choosing a subnet there is choosing a failure domain and "make this highly available" begins with a subnet per zone. Elsewhere the subnet carries no such meaning. OCI keeps a trap: a subnet may be regional, which a new design wants and which a regional endpoint such as the API gateway requires, or it may take the older form tied to one availability domain, which is what copied configuration still creates.

AWS reserves five addresses in every subnet, the first four and the last, and Azure reserves five on the same pattern. A /28 therefore holds eleven usable addresses on both, not sixteen.

3. Where the filter hangs, and what a rule may name

All four evaluate a stateful filter on every packet with no appliance in the path, and all four let a rule name something other than an address as its source. That second point is what stops a tiered design from hard-coding ranges.

Where the rule hangs differs, and so does how many layers a packet must clear. AWS runs two: security groups at the interface, stateful and with no deny rule at all, and network access control lists at the subnet edge, stateless, evaluated in number order and so needing an explicit rule for return traffic on ephemeral ports. Both apply. OCI also runs two, security lists at the subnet and network security groups at the interface, with the twist that each individual rule is declared stateful or stateless, so a stateless rule needs its own matching rule in the other direction.

Azure allows one kind of group at two places, subnet and interface, and both may be attached at once - inbound traffic then clears the subnet group first and must be allowed by both, which is why Microsoft's guidance is to pick one layer. Priorities run from 100 to 4096, the lowest number wins, and evaluation stops at the first match. Google Cloud runs a single layer in the fabric, with implied rules that allow all egress and deny all ingress until overridden, and hierarchical policies pushed down from the organisation and folder above.

4. Peering is non-transitive on all four, and the arithmetic is why hubs exist

All four sell a direct private connection between two networks, and on all four it is strictly non-transitive: if A peers with B and B peers with C, A cannot reach C. So it is documented on AWS, Azure, Google Cloud and OCI, none of which permits overlapping ranges between peers. The consequence is arithmetic.

  1. Count the mesh at thirty networks. 30 × 29 = 870, halved is 435 peerings, each an object somebody creates and routes.
  2. Count the hub at thirty. One attachment per network, so 30.

The hub is a product on every cloud and the shapes differ. AWS splits the regional hub, Transit Gateway, from the global policy-managed Cloud WAN. Azure's Virtual WAN hub and Google Cloud's Network Connectivity Center each combine the two, and OCI does it all in the Dynamic Routing Gateway. The cost is stated in AWS's own pricing: a peering carries no per-gigabyte processing charge and the transit gateway does, so a small estate that peers is cheaper and a large one that peers is unmanageable.

5. Four mechanisms for one problem: reaching a managed service privately

Every cloud lets a workload with no public address reach a managed service without touching the internet, and every cloud does it differently enough that the habit you carry in will be wrong.

The granularity is where they part company.

The figure names the four shapes, so here is only what it cannot carry: which document each rests on, and the one detail per cloud that bites. AWS splits gateway endpoints from interface endpoints, and exams punish conflating them. An Azure private endpoint targets a sub-resource, so blob and file storage on one account need one endpoint each. Of Google Cloud's three - Private Google Access, Private Services Access and Private Service Connect - the last is the one a new design should prefer. The OCI service gateway is one per network and same-region only, and its label for object storage alone and its label for the whole Oracle Services Network are mutually exclusive.

6. The central plane, and where an absence is real

Four rows in this area answer differently, and the difference between "sold as a product" and "there is nothing there" is the one the matrix is most careful about. Reading it wrongly is how an architect designs around a gap that is not one.

The reframing Only Google Cloud sells the BGP speaker as its own object, Cloud Router. The other three all speak BGP to your routers - AWS inside the virtual private gateway, the Direct Connect gateway and the transit gateway, Azure inside the VPN and ExpressRoute gateways, OCI inside the Dynamic Routing Gateway. "No product for it" and "cannot do it" are different sentences, and confusing them is the most common serious error in cross-cloud comparison.

Two absences here are genuine. Only Azure ships a plane that manages many networks at once: Virtual Network Manager deploys topologies across hundreds of networks and adds security admin rules that evaluate before the ordinary filter and can deny across it. The other three have no equivalent object and each substitutes something narrower. Address planning splits the same way: AWS IPAM and Azure's pools are products, while Google Cloud and OCI have none and the plan lives in a spreadsheet.

One row is neither. Google Cloud sells Shared VPC, where a host project owns the subnets and other projects attach workloads to them. AWS delivers that same pattern with no product of its own, by sharing subnets across accounts through its resource-sharing service, so the matrix marks the cell delivered elsewhere and links the row it lives on. Azure has no sharing construct and peers spokes into a hub instead, and OCI does not need one because a network already sits in a compartment inside a single tenancy.

Outbound-only internet access is the one row here where the four look identical and behave differently at the edges. The AWS gateway and the Azure gateway are scoped to one zone, so redundancy is something you build per zone, while Cloud NAT and the OCI gateway are regional. Two of the four publish a connection ceiling and it is not the same ceiling: AWS documents 55,000 simultaneous connections to a single destination per address, expandable across up to eight addresses, and OCI documents 20,000 concurrent connections per destination address and port. OCI adds a restriction the others do not: a peered or on-premises network cannot use another network's gateway.

7. What this certification tests

Only one of the four architect tracks gives networking a domain of its own. Azure's AZ-104 lists "Implement and manage virtual networking" at 15 to 20 per cent, and AZ-305 folds it into "Design infrastructure solutions" at 30 to 35 per cent, whose objectives name connectivity to the internet and on-premises, network optimisation, and load-balancing recommendations.

The other three examine networking everywhere rather than anywhere. AWS SAP-C02 has four domains, none of them networking: organisational complexity at 26 per cent, new solutions at 29, continuous improvement at 25 and migration at 20. Google's Professional Cloud Architect guide is the same shape. Oracle's Architect Professional blueprint puts network content inside Architect Security Solutions, its heaviest domain at 25 per cent.

Check yourself

Retrieval practice

Answer from memory before revealing.

A design must place workloads in three regions on one private network with no connection built between them. Which cloud does that on its own?
A Google Cloud VPC network is a global resource holding regional subnets, so three regions are already one network. The AWS and OCI options state their scope correctly and therefore rule those clouds out rather than in - both need an explicit peering or hub. The Azure option states the scope wrongly: an Azure virtual network is regional too.
Twelve networks must all reach each other. How many peerings does a full mesh need, and why is a hub sold?
12 times 11 halved is 66, and the reason a mesh is needed at all is that peering is non-transitive on all four clouds. The second option is the hub count, not the mesh count, and its reason is the opposite of the truth. The third double-counts: one peering serves both directions. The fourth is a chain, which fails for exactly the same non-transitive reason.
The matrix says a cloud delivers BGP dynamic routing elsewhere rather than as a service. What does that entitle you to conclude?
Delivered elsewhere means the capability is present inside a service listed on another row - here the VPN, circuit or transit gateway. The first option is the error this course exists to prevent, and the other two invent restrictions the cell never claims: the speaker serves tunnels as well as circuits, and it is BGP.

Practice about 15 minutes, with paper

Practice 1working

An estate runs eight private networks in one region. Every network must reach every other, and every network must reach the platform's object store with no path over the internet.

(a) How many peerings would a full mesh cost, and how many attachments would a hub cost?
(b) On AWS, which of the two endpoint kinds serves the object store, and what does it place in the network?
(c) On OCI, how many service gateways does the estate need, and why is that number not one?

Hint

For (b), the split is not by which service you like but by which two services are named in the free tier of the mechanism. For (c), re-read the scope sentence about the service gateway rather than counting workloads.

Show the worked solution
  1. Count the mesh. 8 × 7 = 56, halved is 28 peerings.
  2. Count the hub. One attachment per network, so 8. The hub saves twenty objects and buys a per-gigabyte processing charge in return.
  3. Pick the AWS endpoint. A gateway endpoint covers S3 and DynamoDB only, and it places no interface at all - it adds a prefix-list route to the route table, and carries no extra charge. An interface endpoint would also work and would bill hourly per zone plus per gigabyte for no benefit here.
  4. Count the OCI gateways. A service gateway is limited to one per virtual cloud network and to the same region, so eight networks need 8 service gateways. The estate cannot borrow one network's gateway from another, in the same way that it cannot borrow another network's NAT gateway.

Sanity check. The mesh count must exceed the hub count for any estate above three networks, and 28 against 8 is the right side of that. If your OCI answer was 1, check the scope rule rather than the arithmetic: the per-network limit is what makes the two clouds differ here, and it is also why the OCI answer is the same number as the network count every time.
