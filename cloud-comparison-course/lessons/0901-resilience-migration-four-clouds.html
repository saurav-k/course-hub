Module 09 · Resilience and migration · Lesson 0901

A resilience promise is only as good as the failure-domain map it is stated against

working 10 min Capability keys compared here: region-az-model, backup-service, cross-region-replication, dr-orchestration, migration-service, online-transfer, resilience-assessment, well-architected-framework.

The one-minute version

  • Every cloud states availability against its own failure-domain geography, and the four geographies are not the same shape, so "multi-zone" does not mean one thing.
  • OCI is the structural outlier: many regions hold a single availability domain, and the anti-affinity unit inside one is the fault domain, of which every domain has exactly three.
  • Azure numbers its zones per subscription, so your zone 1 and another subscription's zone 1 can be different physical places.
  • Cross-region replication is a set of per-service primitives everywhere, not one product, which is why it is the row most likely to be half-configured.

1. Four maps, four different shapes

Read this row first on any cloud you do not know, because every other promise on the page is stated against it. All four use a region as the outer blast-radius unit and split it into something smaller. The something smaller is where they part.

AWS Global Infrastructure records 124 availability zones across 39 regions, with a minimum of three zones in a region, plus 46 Local Zones and 33 Wavelength Zones as separate edge tiers. OCI records 41 commercial regions, of which many hold a single availability domain, and every domain contains exactly 3 fault domains for anti-affinity. That contrast is the whole point of the next figure.

Azure adds a trap that no diagram shows. Zone numbering is per subscription and deliberately unmapped: your zone 1 and another subscription's zone 1 can be different physical zones, including two subscriptions inside one tenant. Aligning zonal placement across subscriptions means reading the zone mappings from the platform rather than trusting the number (Azure availability zones overview). OCI does the same thing one level up: availability domain names are randomised per tenancy, so they are not stable data-centre identifiers either.

2. The ladder every design climbs

Once the map is understood, the design choice is a ladder rather than a switch. AWS names the four rungs in its own disaster-recovery guidance, and the names travel to the other three clouds unchanged because the trade behind them is physics rather than branding.

The replication row is where the ladder meets reality, and it is the same shape on all four clouds: a set of per-service primitives rather than one product. On AWS that is bucket replication, Aurora Global Database, DynamoDB Global Tables and ElastiCache Global Datastore (disaster recovery options). On Azure it is the storage redundancy ladder from in-region through geo-redundant, with a readable-secondary variant and a customer-triggered account failover (storage redundancy). Google composes dual-region buckets, multi-region Spanner and disk replication (availability and durability), and OCI composes bucket replication policies, block volume replicas, file system replication and NoSQL global tables (replication).

The reframing Because replication is assembled from primitives everywhere, this is the row a design is most likely to have half-configured: the object store replicated and the database not, or both replicated and the load balancer never built in the second region. Read one Azure detail as the general warning: ordinary geo-redundant storage carries no published recovery-point figure on its own page. A number a vendor has not published is not a number you can design to.

3. Orchestration: replicate the blocks, or replicate the plan

Replication moves the bytes. Orchestration decides the order in which things come back, and this is where the four clouds genuinely differ rather than differing in name.

AWS Elastic Disaster Recovery replicates blocks continuously from an agent into a low-cost staging subnet, giving a crash-consistent recovery point measured in seconds and a recovery time in minutes, with non-disruptive drills and failback. Azure Site Recovery adds recovery plans that sequence a multi-machine boot with scripts. Google delivers orchestration from the same product as its backup vaults (Backup and DR Service). OCI Full Stack Disaster Recovery takes the widest scope of the four: a protection group spanning compute, volume groups, databases, file systems and load balancers, with generated switchover, failover and drill plans across all of them at once.

Backup follows the same split. AWS, Azure and Google each run one policy plane over many resource types, with immutable or locked vaults as the ransomware answer: AWS Backup covers more than twenty service families and its compliance-mode lock cannot be undone even by the account root after a grace period, and Azure Backup splits vault types by workload. OCI is the outlier here too: backup is still largely per-service policies, with volume groups giving the crash-consistent multi-volume snapshot that a single plane would otherwise provide.

4. Testing the promise, and the absence to read carefully

AWS is the only cloud of the four that ships both halves of resilience testing as first-party products: Fault Injection Service runs chaos experiments built from actions, targets and alarm stop conditions, and Resilience Hub scores an application against a stated recovery objective and can launch those experiments. Azure splits the two between Chaos Studio and its Business Continuity Center. OCI covers the rehearsal half through Full Stack DR drills and leaves true fault injection to third-party tooling.

Google Cloud carries an absence on this row and it is the most easily misread cell in this whole section. Cloud Service Mesh does ship managed fault injection, delaying or aborting a percentage of requests, so "Google Cloud has no first-party fault injection" is false. What is absent is a standalone chaos platform, and separately a policy-based resilience score against a stated recovery objective. Write the narrow claim, never the wide one.

Two other rows close the area. Online transfer is a managed, scheduled, incremental bulk copy into cloud storage, and three clouds sell one: AWS DataSync, Azure Storage Mover and Storage Transfer Service. OCI has no managed online path: its data transfer service is the offline appliance and disk route, and online copies are left to command-line and third-party tools. Well-Architected is published by all four, six pillars on AWS and Google Cloud, five on Azure and five on OCI, and AWS is the only one whose review tool records your answers rather than reading as guidance.

5. What this certification tests

This is the most heavily weighted area of the four in this section, on three of the four exams. The AWS associate guide lists Design Resilient Architectures at 26 per cent of scored content, and the professional guide gives migration a domain of its own, Accelerate Workload Migration and Modernization, at 20 per cent (SAA-C03, SAP-C02). Azure lists Design business continuity solutions at 15 to 20 per cent, with recovery objectives named in its sub-objectives (AZ-305). Oracle lists Architect High Availability and Disaster Recovery Solutions at 15 per cent and names Full Stack Disaster Recovery inside it (1Z0-997-26). Google's architect guide instead weaves the Well-Architected pillars through its domains and calls familiarity with them a requirement (PCA exam guide).

Check yourself

Retrieval practice

Answer from memory before revealing.

A design places two instances in different availability domains in an OCI region. What should you check first?
Many OCI regions hold a single availability domain, so the placement can be impossible before any other question matters, and the anti-affinity unit there is the fault domain instead. Power independence is a property Oracle states for domains rather than something you verify per region. A second subscribed region is a different design and a different row. And shape availability is a real concern, but it is the second question, not the first.
Why is "Google Cloud has no fault injection" a wrong reading of the resilience assessment row?
The mesh ships managed fault injection, so the narrow absence is a standalone chaos platform and a policy-based resilience score, not the ability to inject a fault. Backup and DR runs recovery workflows and does not inject faults of its own. The third option is wrong about the row, which covers chaos and scoring together, and that width is exactly why the wide claim is tempting. And nothing in the sources puts fault injection inside the monitoring product.

Practice about 15 minutes, with paper

Practice 1working

A payments service must survive the loss of one building with no data loss, and the loss of one region with at most fifteen minutes of data loss and a two-hour return to service. The team has budget for a small permanently running copy in the second region but not a full second production estate.

Name the rung of the ladder each of the two requirements sits on, say what the building-level requirement demands of the failure-domain map on each of the four clouds, and list the parts of the estate that the replication row makes it your job to configure separately.

Hint

Treat "one building" and "one region" as two different rungs, because they are. Then ask, for the building requirement, what the smallest independent failure unit is on each cloud, and remember that one of the four does not always give you the unit the other three do.

Show the worked solution
  1. Place the building requirement. No data loss at all means synchronous within one region, so this is not a disaster-recovery rung: it is ordinary multi-zone deployment inside the region.
  2. Place the region requirement. Fifteen minutes of data loss with a two-hour return, plus a small live copy, is warm standby. It is not pilot light, because pilot light keeps compute off, and not active-active, which the budget rules out.
  3. Read the map, cloud by cloud. On AWS a region has at least three availability zones, so the placement always exists. On Azure it exists in regions that have zones, and the zone numbers must be read from the platform rather than assumed to line up across subscriptions. On Google Cloud a region holds independent zones and the resource declares its own scope. On OCI it exists only in a multi-domain region, and in a single-domain region the anti-affinity unit is the fault domain, of which every domain has exactly three.
  4. List what replication leaves to you. Because no cloud sells one replication product, each of these is configured on its own: the object store, the database, any cache with a cross-region mode, and the block volumes. The load balancer and the network in the second region are built rather than replicated.
  5. Check the recovery point you can actually claim. Fifteen minutes has to come from a figure the vendor publishes for the mechanism you chose. Where a redundancy option publishes no recovery-point figure, it cannot be the evidence for a fifteen-minute objective.

Sanity check. The two requirements must land on different mechanisms, because zero data loss and fifteen minutes of data loss cannot be bought by the same replication. If both came out as cross-region replication, re-read step one: no data loss over a distance is a synchronous promise, and no cloud on this page offers that between regions.

Your teacher. Before comparing any two clouds' resilience products, ask for their failure-domain maps and put them side by side. Nearly every wrong cross-cloud assumption in this area comes from carrying one map into another cloud, and the two questions that expose it are how many independent domains a region is guaranteed to have and who numbers them.

It is written about one cloud and the reasoning is portable, which is exactly why the other three clouds' documentation uses the same four names.
