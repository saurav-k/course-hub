Module 03 · Storage and data · Lesson 0301

The storage menu is the same on all four clouds, and the failure domain under it is not

working 11 min Capability keys compared here: object-storage, object-storage-highperf, object-storage-tables, block-storage, file-storage, archive-storage, hybrid-storage-gateway, bulk-transfer-appliance.

The one-minute version

  • All four clouds answer the same eight storage capabilities, and on six of them all four ship a product. The taxonomy is not where they diverge.
  • They diverge on packaging. An archive tier is a storage class inside the object store on two clouds, an access tier on the third, and a separate tier with its own restore call on the fourth.
  • A single-zone object class is a deliberate trade: cross-zone redundancy sold back for latency. Two clouds sell one, and two say plainly that they do not.
  • Three rows carry a genuine absence. The reason is worth more than the gap, because two of the three have a documented pattern that does the same job.

1. One taxonomy, eight rows

The shared vocabulary splits storage by what the reader addresses, not by who sells it. An object store is addressed by key, a block volume by offset, a file system by path. Archive is the coldest tier of the first of those and is a separate row because it behaves differently: the data cannot be read until it is restored. The last two rows are not stores at all, they are the two ways bulk data arrives, over a wire or in a shipped box.

Six of these rows are filled by all four clouds: Amazon S3, Azure Blob Storage, Google Cloud Storage and OCI Object Storage are four answers to one question, and each of them documents versioning, lifecycle-managed tiers and replication. Google states a hard ceiling worth carrying: a single object tops out at 5 TiB (Cloud Storage quotas). Both Google and OCI expose an S3-compatible API alongside their own, which is why a tool written against S3 often moves without a rewrite.

2. Archive is one idea packaged four ways

Every cloud sells storage priced near tape whose data must be restored before it can be read. The mechanism is identical and the packaging is not, and packaging is what decides whether a design has one bucket or two.

AWS keeps archive as storage classes inside S3: Glacier Flexible Retrieval restores in 1 to 5 minutes expedited through to 12 hours bulk, and Deep Archive in 12 to 48 hours with no expedited tier at all. Google does the same thing with its Archive class, aimed at data kept a year or more. Azure makes it a per-blob access tier rather than a class, and rehydration to hot or cool takes up to 15 hours unless you pay for high priority. OCI ships Archive Storage as its own tier with an explicit restore, first byte in about an hour, and a bucket's default tier fixed at creation.

The reframing Three of the four charge a minimum storage duration, so archive is cheap only for data you will not delete soon: AWS 90 days on Glacier Flexible Retrieval and 180 on Deep Archive, OCI 90 days, and OCI's Infrequent Access tier 31 days. Deleting early does not save the money, it bills the remainder.

3. Block storage, where the numbers size the design

A block volume is the one storage shape whose ceiling a design runs into directly, because a database sitting on it inherits that ceiling. Two clouds publish a per-volume input/output ceiling on the pages this course rests on, and the two numbers are close enough that the interesting difference is not the ceiling but how you buy it.

How the ask is made is the real divergence. On AWS gp3 a baseline of 3,000 operations per second and 125 MiB per second is included and scales to 80,000 and 2,000 independently of volume size, and io2 Block Express reaches 256,000 operations and 64 TiB. On OCI Block Volume performance is bought as volume performance units per gigabyte, from 0 for lower cost through 10 balanced to 30 and above for ultra high performance, and an auto-tune setting raises the level quickly and lowers it slowly. Azure Managed Disks reach the same independence at the Premium SSD v2 and Ultra tiers, and Elastic SAN pools one performance budget across volumes instead. Google is mid-generation: Persistent Disk scales performance with size, while Hyperdisk provisions it separately and is the one a new design should choose.

All four also sell ephemeral locally attached NVMe on the same row, because it is the same capability with the durability removed: AWS instance store, Google Local SSD, Azure local NVMe and OCI dense-IO shapes. Google's own page is blunt about the trade, calling it scratch storage with no durability.

4. File storage: one row, four to seven engines

The file row is where the count of products stops meaning anything. AWS answers with two entries, EFS for elastic NFS and the FSx family, which is four managed third-party engines in one wrapper: Lustre for high-performance computing, NetApp ONTAP, OpenZFS and Windows File Server. Azure splits the same ground between Azure Files and Azure NetApp Files. Google sells four separate products: Filestore, NetApp Volumes, Managed Lustre and Parallelstore. OCI answers with one, File Storage Service, covering NFSv3 and NFSv4 with snapshots, clones and cross-region replication.

One product against four is not a capability gap, it is a packaging choice, and reading it as a gap is the single most common mistake in a four-way comparison. The question that separates them is which engine you need, not how many are on the menu.

5. Where a row is genuinely empty

Three rows carry an absence, and each one has to be read exactly.

The gateway row is a first-party appliance that presents cloud storage as a local protocol, which AWS Storage Gateway and Azure File Sync both do and the other two do not sell at all. The high-performance row is a trade rather than a product: S3 Express One Zone and Google's Rapid class give up cross-zone redundancy to buy consistent single-digit millisecond latency, and Azure premium block blob reaches that latency while staying regionally redundant, which is why it is not the same answer. The table row is S3 Tables alone, a bucket type that stores Apache Iceberg tables natively and compacts them for you.

Read those three absences as capability gaps and you will be wrong twice. Google does maintain Iceberg tables automatically, through BigQuery over ordinary buckets, and Microsoft holds Delta tables with managed maintenance in OneLake. What is absent in both cases is a storage service that understands tables, not the managed table. The comparison lessons return to this on the analytics page, where those same products hold their own row.

6. What this certification tests

Storage is not a topic the professional exams treat as its own domain, so it appears inside larger ones. The Azure architect exam guide lists Design data storage solutions at 20 to 25 per cent of scored content, and the administrator guide lists Implement and manage storage at 15 to 20 per cent (AZ-305 study guide, AZ-104 study guide). On AWS the storage decisions sit inside Design High-Performing Architectures at 24 per cent and Design Cost-Optimized Architectures at 20 per cent of the associate exam (SAA-C03 exam guide). Storage-class selection, restore latency and the zonal trade above are exactly the shape of decision both guides describe.

Check yourself

Retrieval practice

Answer from memory before revealing.

A comparison table shows a single product in the file row for OCI and four for Google Cloud. What does that difference actually tell you?
Product count is packaging, not capability, and the row is filled on both clouds. Nothing on the row states throughput, so the first option invents a number. The second turns a packaging difference into a capability claim, which is the exact error this course exists to prevent. The fourth reads a history into a table that records no history at all.
Why do Azure and OCI carry no equivalent on the single-zone high-performance object row?
The row is about a trade, giving up cross-zone redundancy to buy latency, and neither cloud offers a class that makes it. Hardware is not the reason: Azure premium block blob is solid-state backed and already delivers single-digit millisecond first-byte latency. Nothing in the sources says anything about pricing, and nothing restricts a class by account size.

Practice about 15 minutes, with paper

Practice 1working

A media archive holds 400 TB of finished footage. It is read back roughly twice a year, and when it is read the editors want the first file open the same working day. The team also keeps 20 TB of working footage that an editing suite reads at random all day, and it wants that on a single volume rather than a striped set.

Choose a storage class or tier for each of the two datasets on any one cloud, state the restore behaviour the archive choice commits the team to, and say which published per-volume figure decides whether one volume can carry the working set.

Hint

Take the two datasets separately. For the archive, the deciding number is not price, it is how long a restore takes and whether a minimum storage duration applies. For the working set, the deciding number is what a single volume is allowed to deliver, and whether that ceiling depends on the size of the volume.

Show the worked solution
  1. Place the archive. Twice-yearly reads with a same-day open rules out the deepest tier everywhere. On AWS that is Glacier Flexible Retrieval, restoring in 1 to 5 minutes expedited through to 12 hours bulk, rather than Deep Archive at 12 to 48 hours. On Azure it is the archive access tier accepting rehydration of up to 15 hours, or high priority if same-day is firm.
  2. Name the commitment. The data is unreadable until a restore completes, so a request must be issued first and the application must handle a refused read rather than a slow one. A minimum storage duration also applies: 90 days on Glacier Flexible Retrieval, 180 on Deep Archive, 90 on OCI Archive.
  3. Size the working set. 20 TB is well inside the io2 Block Express ceiling of 64 TiB, so capacity is not the constraint and the deciding figure is operations per second.
  4. Pick the volume type by how performance is bought. A gp3 volume includes 3,000 operations per second and scales to 80,000 independently of size, so a 20 TB gp3 volume can be asked for far more than its baseline. Below 80,000 that is the cheaper answer, above it the volume has to be io2 Block Express at up to 256,000.

Sanity check. Both answers should name a number the vendor published, not a preference. If the archive choice came out as the deepest tier while the requirement says same-day, re-read step one: the deepest tier is measured in tens of hours everywhere. And if the volume answer depended on 20 TB, check step four, because on gp3 and on Hyperdisk the size of the volume no longer sets its performance.

Your teacher. Ask for a row rather than a product: "archive storage, four clouds, restore times" gets you the comparison, while "what is Glacier" gets you one vendor's page. When an answer says a cloud has no equivalent for something, ask what the nearest documented pattern is before believing it, because that is where this comparison went wrong most often before it was verified.
