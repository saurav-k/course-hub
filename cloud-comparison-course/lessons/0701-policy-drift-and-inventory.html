A governance control is defined by the moment it fires

working 8 min Capability area governance-policy, 4 rows of the capability matrix: policy-as-code, config-drift-assessment, resource-graph-query and compliance-pack.

The one-minute version

  • A rule about your estate can fire at three moments: before a resource is requested, at the instant it is created, or continuously afterwards.
  • The four clouds sit at different moments, and only one of them covers all three with a single engine.
  • "Drift" is not one measurement. Two clouds compare a resource against its own recorded history, one compares it against the template you last applied, and one raises it as a security finding.
  • The estate can only answer questions in the language its inventory speaks, and the four languages are not equally expressive.

1. The three moments

Strip the product names away and every governance engine in this comparison does one of three things. It refuses a request before any resource exists. It refuses at creation, so the resource never appears. Or it lets the resource appear and then reports, or repairs, what is wrong with it.

AWS evaluates continuously and adds a proactive lane. Config rules judge resources after they exist, in managed or custom form, and conformance packs bundle rules with their remediations for a whole organisation. Control Tower then names the three lanes explicitly: preventive controls are the organisation guardrails of the previous page, detective controls are Config rules, and proactive controls are template hooks that block a bad resource before provisioning (how controls work).

Azure runs one engine at two moments. Azure Policy as code is the same definitions and assignments authored in a repository, validated in a pipeline and rolled out safely; the effects decide the moment, with deny acting at creation and the modify and deploy effects acting afterwards on what is already there.

Google Cloud enforces at creation and reports afterwards, with two different products. Custom organisation constraints are written as expressions and enforced when a resource is created (custom constraints). Anything already running is judged instead by the security posture service, which raises a finding rather than blocking an action.

OCI blocks at creation and detects continuously. Security Zone recipes refuse a non-compliant creation in a compartment, and Cloud Guard detector and responder recipes evaluate what exists and can act on it.

2. What "drift" measures, which is not the same question

That reference is the difference nobody writes down. AWS and Azure both compare a resource against its own recorded past: the Config recorder stores point-in-time configuration items and relationships that make a per-resource timeline, and Azure reads property-level change history out of Resource Graph, with in-guest change tracking for what happens inside a virtual machine. OCI compares against something else entirely: Resource Manager drift detection reports, per resource, how live infrastructure differs from the Terraform state last applied by a stack. Google Cloud does not frame it as drift at all - a resource that moves outside its posture becomes a finding.

Those are three different questions wearing one word. "Has this changed since yesterday" and "does this still match the template we deployed" have different answers for any resource that was never deployed from a template, and the second question cannot even be asked about one. Carry the reference, not the feature name, when you compare a drift report across clouds.

3. Asking the estate what exists

Every control above assumes you can find the resources it applies to. That is a query problem, and it is the capability in this area where the four clouds are least alike.

4. Evidence, and the one service to stop reaching for

The last row of this area is the compliance pack: prebuilt mappings from your configuration to a published benchmark, plus the attestation documents an auditor asks for. Azure ships built-in initiative packs mapped to the common benchmarks and scores them (policy samples), Google Cloud reports compliance inside Security Command Center, and OCI ships a CIS Foundation detector recipe in Cloud Guard beside downloadable attestation artifacts.

AWS is the one to be careful with. Audit Manager, the service that automated evidence collection, is entering maintenance. The capability has not gone: AWS Artifact still self-serves the attestation documents and Security Hub still carries the control findings. But a new design should not be built on Audit Manager, and a course that teaches it as the AWS answer teaches a narrowing path.

What this certification tests

Governance sits inside a heavily weighted domain on three of the four professional exams. AWS gives Continuous Improvement for Existing Solutions twenty-five percent of scored content (exam guide), Azure gives Design identity, governance, and monitoring solutions twenty-five to thirty percent (skills measured), and Google Cloud gives Designing for security and compliance about seventeen and a half percent of the professional architect exam (certification page).

Check yourself

Retrieval practice

Answer from memory before revealing.

An OCI drift report says a load balancer has drifted. What has it actually compared the live resource against?
Resource Manager reports how live infrastructure differs from the last-applied stack state, so a resource nobody deployed from a stack has no drift to report. The second option is the AWS and Azure model of a per-resource change history. The third is how Google Cloud frames the same concern. The fourth is a compliance mapping, which judges against a standard rather than against your own last deployment.
You need one query language that spans every subscription and returns resource properties with their change history. Which cloud answers with a single surface?
Resource Graph is the one general-purpose query language here with history attached to it. AWS splits the job in two, keyword search in one service and a SQL subset over configuration items in another. Cloud Asset Inventory answers well but leans on export for analysis. OCI Search has its own syntax and no change-history surface of the kind the question asks for.

Practice about 15 minutes, with paper

Practice 1working

A rule arrives: no storage bucket in the estate may be publicly readable. You are asked to implement it on all four clouds, and to say for each one whether a bucket that is already public will be caught.

Choose the object and the moment for each cloud, then state what happens to the buckets that already exist and whether anything puts them right without a human.

Hint

Split the requirement in two before you start. "No new public bucket" is a question about the moment of creation. "No public bucket at all" is a question about what judges resources that already exist, and those are different objects on three of the four clouds.

Show the worked solution
  1. New buckets, AWS. A preventive organisation guardrail caps the action, and a proactive control can reject the template before provisioning. Existing buckets are untouched by either.
  2. Existing buckets, AWS. A Config rule judges them after the fact, and a conformance pack can carry the remediation with it, so the repair is available but is a separate piece from the rule.
  3. Azure, both halves in one engine. A policy assignment with a deny effect stops new ones; the same definition set with an audit or a remediating effect reports and can repair the ones already there.
  4. Google Cloud, two products. A custom organisation constraint refuses the creation. Everything already running is judged by the posture service, which raises a finding - a finding is a report, not a repair.
  5. OCI, two products. A Security Zone recipe blocks the creation in that compartment. Cloud Guard detectors find the existing ones, and a responder recipe is what acts on them.
  6. Answer the second half plainly. Only Azure closes the loop inside one object. On the other three, blocking the new and fixing the old are two different things you have to configure, and on Google Cloud the second one reports rather than repairs.

Sanity check. Your answer should name two objects for three of the clouds and one for Azure. If you named a single object everywhere, you answered the creation half and left every bucket that already exists public.

Your teacher. When you meet a governance feature in any vendor's documentation, ask two questions before you read the rest: when does it evaluate, and what does it compare against. Almost every cross-cloud mistake in this area is one of those two answers carried over from the cloud you already know. Ask an agent to describe a control and to withhold the moment, then work it out from what the control can and cannot prevent.

Primary source to go deeper

How controls work in AWS Control Tower is the clearest vendor statement of the three moments, because it is the only one that names all three lanes in a single page. Read it as a frame, then place the other three clouds' objects into it.
