One DNS product name hides three separate jobs, and only two of them are the same everywhere

working 9 min The four dns-domains rows of the capability matrix, compared across all four clouds.

The one-minute version

  • Three jobs travel under one name: buying a domain, answering for it publicly, and answering for it privately inside your own networks.
  • Public answering is the part all four do the same way. Two of them publish a 100 per cent availability commitment for it.
  • Buying is where the row breaks up: three clouds are registrars, one is not and says so plainly, and one is retiring its registrar.
  • Answering privately is what makes a private endpoint work, and Azure is the only cloud that sells the hybrid resolver as a separate product.
  • Steering policies are one vocabulary per cloud, and the overlaps are wider than the counts suggest.

1. Three jobs, one name

Public authoritative answering is the least interesting of the four, in the good sense: Amazon Route 53, Azure DNS, Cloud DNS and OCI DNS all serve public zones from anycast and all support DNSSEC. Two of them go further and publish a 100 per cent monthly availability commitment for answering queries in a zone - AWS and Google Cloud - and the AWS wording is worth reading closely, because that commitment covers the queries and not the registration beside them.

2. Buying the name is where the row breaks up

Registration is the one job in this area that a cloud can simply decline, and one of the four does. Oracle states it plainly: OCI is not a registrar, so a domain is bought at a third-party registrar and the zone is delegated in. This is a real absence with a real reason, and it changes nothing about the other three rows - OCI answers authoritatively for any zone delegated to it.

Of the three that do register, AWS is an accredited registrar in its own right, with hosted DNS and privacy included and the standard sixty-day transfer lock after a registration or a transfer. Azure sells registration through App Service Domains, a partner registry surfaced inside the portal with billing on the subscription.

Google Cloud's registrar is the one cell in this area that a new design should not lean on. Cloud Domains carries a retiring status in the matrix, because Google has announced a transition away from the domain-registration business. The verified research that this course is built from stops there deliberately: it records the status and flags that the exact migration path was not confirmed. So treat the row as "do not start here" rather than as a migration you can plan from this page.

3. Answering privately, and the endpoint that depends on it

Every cloud lets you hold a zone that only your own networks can see, and give a name a different answer inside them than outside. That is the mechanism that makes a private endpoint reachable: the public name of a managed service resolves, inside your network, to the private address the endpoint holds.

The shapes underneath differ in ways that bite. A Route 53 private hosted zone is associated with a VPC and needs that VPC's DNS hostnames and DNS support both switched on, with an explicit authorization step when the association crosses accounts. Azure private zones are linked to virtual networks and can register machine records automatically, and the forwarding work lives next door in Azure DNS Private Resolver, whose rule sets replace the forwarder virtual machines people used to build by hand. Cloud DNS private zones add forwarding zones and DNS peering, with the platform's own internal machine names sitting in a separate automatic set beside them. OCI private DNS gives each network a resolver you can extend with listeners and forwarders.

The trap worth carrying On OCI, steering policies apply to public zones only - they do not act on private zones at all. A design that expects weighted or failover answers on an internal name will get a plain answer and no error. Where a cloud splits public and private answering into two services, check every feature you assumed was shared.

4. Steering: four vocabularies over one idea

  1. Count the AWS list. Simple, weighted, latency, failover, geolocation, geoproximity, multivalue answer and IP-based is 8, and multivalue answer returns up to eight healthy records at once.
  2. Count the others. Azure Traffic Manager names priority, weighted, performance, geographic and subnet, which is 5. Cloud DNS names weighted round robin, geolocation, geofenced and failover, which is 4. OCI steering names failover, load balance, geolocation, autonomous-system number, address prefix and a custom composition, which is 6.
  3. Find the real differences. Only AWS names geoproximity, which biases an answer away from the nearest region by an amount you set. Only OCI steers on the caller's autonomous-system number. Azure's subnet method and the AWS IP-based policy are the same idea under two names.

One structural difference sits behind the counts. Azure sells steering as a separate product from its DNS zones, so a Traffic Manager profile steers to any publicly reachable endpoint, including one that is not on Azure at all - and OCI's steering runs a fixed pipeline of filter, then health, then priority or load balance, then a limit on how many answers come back.

5. What this certification tests

None of the four architect blueprints gives DNS a heading of its own, and it is examined inside the networking material either way. On Azure that means the AZ-104 networking domain at 15 to 20 per cent, whose objectives name private endpoints and service endpoints directly - which is the section 3 material, because on Azure the endpoint and the private zone are one design. Elsewhere it arrives inside scenario questions about failover and about reaching a managed service privately.

Check yourself

Retrieval practice

Answer from memory before revealing.

An internal name on OCI needs weighted answers between two regions. What happens if you attach a steering policy to the private zone?
Oracle documents steering as a public-zone feature, so a private zone keeps answering plainly. The first option adds a condition the documentation does not: health checks drive the policy, they do not enable it on private zones. The second is the failure people expect and is why the trap is quiet. The fourth invents a scope no cloud offers.
Which cloud sells the inbound and outbound hybrid resolver as a product separate from its private zones?
Azure DNS Private Resolver is a separate product carrying the inbound endpoint, the outbound endpoint and the rule sets. On the other three the same two directions are features of the private zone service: AWS resolver endpoints, OCI resolver listeners and forwarders, and Cloud DNS forwarding and peering zones.
A team must register a new domain and serve it from OCI. What does the platform oblige them to do?
Oracle states plainly that it is not a registrar, so the name is bought at a third-party registrar and delegated in - which OCI then answers authoritatively. The two options that register in OCI describe a service that does not exist. The third gives up the part OCI does well for no reason.

Practice about 12 minutes, with paper

Practice 1working

An application in your own data centre must call a managed database that has a private endpoint inside a cloud network. The application uses the database's ordinary public host name, and it must keep using it.

(a) Which direction of hybrid resolution does this need, and what does it mean the on-premises resolver must be able to reach?
(b) On Azure, name the two objects involved and say which of them is a separate product.
(c) Why does this design fail silently rather than loudly when the resolution half is missing?

Hint

For (a), work out who is asking and who holds the answer, then read the sequence figure in that direction. For (c), think about what a public name resolves to when nothing has overridden it.

Show the worked solution
  1. Pick the direction. Inbound: the asker is on-premises and the answer is held in the cloud's private zone. So the on-premises resolver must be able to reach an inbound endpoint inside the cloud network, over whatever private path already joins the two.
  2. Name the Azure objects. A private DNS zone for the service's private-link suffix, linked to the virtual network, and an Azure DNS Private Resolver inbound endpoint. The resolver is the separate product - the zone is part of Azure DNS.
  3. Explain the silence. The public host name always resolves to something. With the private answer missing, the on-premises resolver gets the service's public address instead, and the application then connects over the internet or is refused at a firewall - either way the failure looks like a connectivity problem rather than a naming one.

Sanity check. Your answer to (a) should be the direction whose arrow starts outside the cloud. If you chose outbound, re-read who is asking: outbound is for cloud workloads resolving names your own resolvers hold. And the object count in (b) should be two, not one - a design with only the zone has nowhere for the on-premises query to arrive.

How this connects

  • Hybrid connectivity builds the private path this page's resolvers assumed was already there.
  • The private network is where the private zone's answers point.
Your teacher. Section 4's bar chart is a count of words, not of power. Ask an agent to "take AWS geoproximity and OCI autonomous-system steering, and say for each whether the other three clouds can reach the same effect another way". Where the answer is yes, the bar chart overstates the gap, and knowing which two of the eight are genuinely unmatched is the useful part.
