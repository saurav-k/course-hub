Module 02 · Compute: placement, scaling, containers · Lesson 0202

All four clouds run Kubernetes, so the question is how much of the cluster they run

working 10 min Capability area containers, eight rows of the matrix: managed-kubernetes, serverless-containers, container-orchestrator-nonk8s, container-registry, kubernetes-node-autoscaler, kubernetes-fleet-management, kubernetes-backup and service-mesh.

The one-minute version

  • Managed Kubernetes is the one row where all four clouds answer with the same idea. The difference is how far up the stack the provider takes over, and three of the four will run the nodes too.
  • Only AWS ships a proprietary orchestrator that is not Kubernetes. On the other three that row is a genuine absence, and each names its nearest alternative.
  • Serverless containers split into two shapes: platforms that scale to zero and front HTTP themselves, and compute modes that run under an orchestrator you still configure.
  • The node-autoscaler row is where this course's three cell states are all visible at once - a product on AWS, the same engine as a cluster mode on Azure and Google Cloud, and a real absence on OCI.
  • Two rows are mid-transition on somebody: the legacy Google registry is shut, and the AWS mesh is discontinued while the OCI managed mesh has reached end of life.

Eight rows, four questions

The ladder of handover

EKS Auto Mode runs locked-down nodes with a bounded lifetime and takes over autoscaling, load balancing, domain name resolution, storage and network policy, while the customer keeps the network, the cluster configuration and the application containers. GKE Autopilot bills for the resources a pod requests rather than for nodes. OKE reaches the same rung through virtual nodes, which are a feature of its enhanced clusters. AKS keeps node pools visible.

OKE carries an exam trap worth knowing before you meet it in production: an enhanced cluster is the default in the console and a basic cluster is the default from the command line and the API. Only the enhanced cluster carries virtual nodes, self-managed nodes, node cycling and a financially backed service level agreement. A basic cluster can be upgraded to enhanced only if it is already virtual-network-native, and there is no downgrade.

The first row of that table is the one to read carefully. Amazon ECS is a proprietary orchestrator with its own task, service and capacity-provider model, and the verified inventories record a real absence on the other three - Azure's Container Apps runs on Kubernetes and KEDA underneath, Google's Cloud Run is a serverless runtime rather than a general orchestrator, and on OCI anything larger than a single container group goes to OKE. Each is a genuine absence with a stated nearest alternative, which is a very different claim from "no way to run containers".

The second and third rows are the same word meaning two things. Cloud Run and Container Apps scale to zero, split traffic between revisions and answer HTTP directly. Fargate and OCI Container Instances are a way to run a container without owning a node, but the routing, the scaling policy and the service model come from the orchestrator above them. On Azure the inventory is explicit that a new design should prefer Container Apps to Container Instances, and Container Instances is kept for the single fast-starting container and the run-once job.

The row where all three cell states are visible at once

The rows only two clouds sell, and the two in transition

Workload-aware Kubernetes backup and multi-cluster fleet management are the pair where two clouds ship a product and two do not. Azure Backup for AKS and Backup for GKE capture cluster objects together with their persistent volumes. AWS records an absence because AWS Backup does not cover EKS objects, so teams run their own tool, and OCI records one because Block Volume backup policies cover the volumes and not the cluster objects. For fleets, Azure Kubernetes Fleet Manager and GKE Enterprise fleets group clusters so upgrades and placement are managed once, while AWS and OCI manage clusters one at a time.

Two more rows carry a service that a new design should not choose. On Google Cloud the container-registry row is the legacy Container Registry, which is deprecated with reads redirecting into Artifact Registry - the matrix holds that successor on its own artifact-registry row, because on Google Cloud one service holds images and language packages together. On AWS, App Mesh is discontinued and closed to new customers, and ECS Service Connect is its replacement for ECS - a narrower one, with no mutual TLS and no advanced traffic splitting. On OCI the managed mesh has reached end of life, so a mesh on OKE is self-run Istio. Only the AKS Istio add-on and Cloud Service Mesh are managed meshes a new design should reach for.

What this certification tests This is the area with the clearest exam signal of the four in this module. The OCI Architect Professional blueprint gives Architect Cloud-Native Solutions 20 per cent and names OKE, Container Instances and the registry inside it, so containers are an explicitly weighted domain rather than a topic scattered across others. On AZ-305 the same material sits inside Design infrastructure solutions, 30 to 35 per cent, whose own objective list names container compute as one of the choices being tested, and AZ-104 names Container Instances and Container Apps provisioning under its compute domain.

Check yourself

Retrieval practice

Answer from memory before revealing.

The node-autoscaler row shows AKS as delivered elsewhere rather than as an absence. Why is that the correct cell?
Node autoprovisioning in AKS is Karpenter-based and built into the cluster, so the capability is present and the product is not - which is exactly what delivered elsewhere means. Option two is the false negative to avoid. Options three and four each invent a mechanism the inventory does not record, and neither would justify a cell that points at another row.
A design needs a container platform that scales to zero and answers HTTP without an orchestrator in front of it. Which pair fits?
Cloud Run and Container Apps front HTTP themselves and scale to zero. Fargate and OCI Container Instances run containers without a node but do not provide the routing, so option one misses the requirement. Options two and four are orchestrators, which is precisely what the question rules out.
Which statement about the container registry row is the one the verified inventories actually support?
Reads from the old Container Registry redirect into Artifact Registry and writes are gone, which is a succession rather than an absence. Option one is the false negative. Option three is wrong because the Google row is explicitly deprecated, and option four is wrong because OCIR also scans on push through the vulnerability scanning service.

Practice about 20 minutes, with paper

Practice 1working

A platform team runs forty Kubernetes clusters. They want three things: one place to drive version upgrades across the whole estate, a backup that captures cluster objects and their volumes, and nodes provisioned just in time at the size the pending pods actually need.

Score each of the four clouds against those three requirements using the matrix rows on this page, and for every requirement a cloud does not meet with a product, say what the reader would have to build instead.

Hint

Three rows carry the answers: kubernetes-fleet-management, kubernetes-backup and kubernetes-node-autoscaler. For each cell, decide first which of the three kinds of answer it is, because the gap-filling work is different for each.

Show the worked solution
  1. Take fleet management first. Azure Kubernetes Fleet Manager and GKE Enterprise fleets both meet it. AWS and OCI record a genuine absence, so on both the estate is driven cluster by cluster and the upgrade order becomes your own automation.
  2. Then backup. Azure Backup for AKS and Backup for GKE meet it. AWS records an absence because AWS Backup does not cover EKS objects, and OCI records one because volume backups miss the cluster objects, so on both the team runs its own object-aware backup tool and keeps the volume snapshots separate.
  3. Then the node autoscaler. AWS meets it with Karpenter as a named product. Azure and Google Cloud meet it as a cluster mode rather than a product, so nothing has to be built - only switched on. OCI is the one genuine absence, and there the team sizes node groups in advance and lets the cluster autoscaler move within them.
  4. Read the score. Azure and Google Cloud meet all three, two of them with products and one with a mode. AWS meets one with a product and needs building work for two. OCI needs building work for all three.

Sanity check. Exactly one of the twelve cells you scored should be delivered-elsewhere on Azure and one on Google Cloud, and both should be the node autoscaler. If you scored either of those as an absence, you have told the team to build something the cluster already does.

Your teacher. If the ladder of handover is still abstract, ask an agent to list, for one cloud, every operational task that moves from you to the provider between the middle rung and the top rung. The length of that list is the real argument for the top rung, and its cost is the freedom you give up on the nodes.

Primary source to go deeper

Google's own comparison of GKE Autopilot and Standard is the clearest vendor statement of what the top rung of the ladder costs and buys, and it is written as a choice rather than as a sales page, which makes it a good lens for reading the equivalent AWS, Azure and OCI documents.
