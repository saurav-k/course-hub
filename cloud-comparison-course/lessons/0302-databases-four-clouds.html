Module 03 · Storage and data · Lesson 0302

Pick a managed database by its packaging, not by its engine

working 10 min Capability keys compared here: relational-managed, relational-serverless, globally-distributed-sql, nosql-keyvalue, nosql-document, graph-database, timeseries-database, in-memory-cache, ledger, db-migration-service, change-data-capture, database-fleet-management.

The one-minute version

  • All four clouds run the same open-source engines. PostgreSQL is PostgreSQL everywhere, so the engine name settles almost nothing.
  • What differs is the capacity model bolted to the engine: which one scales without a restart, and which one pauses to zero when nobody is using it.
  • One strongly consistent SQL image across regions is sold by three clouds and each buys it differently, so the design question changes with the cloud.
  • Two rows on this page are delivered inside another product rather than absent, and reading them as gaps is the classic four-way comparison error.

1. Twelve rows doing three different jobs

The database area is not one list. Eight rows are engines, chosen by data model. One row is a capacity model rather than an engine at all. Two rows move data rather than hold it, and one watches the whole estate.

The engine row is where the four clouds look most alike. Amazon RDS runs MySQL, PostgreSQL, MariaDB, Oracle, SQL Server and Db2, and each of the other three runs the community engines its customers ask for: Azure Database for PostgreSQL Flexible Server, Cloud SQL and OCI Database with PostgreSQL. Each also sells an enhanced version of its own: Aurora, Azure SQL Managed Instance, AlloyDB and MySQL HeatWave. They share a row because an architect reaches for either one to solve the same problem.

2. "Serverless" is a capacity model, and one cloud has no relational one

A serverless relational tier is not a different engine. It is the same engine with the capacity dial moved by the provider, and the property that matters is whether the dial reaches zero.

Aurora Serverless v2 scales in 0.5 capacity-unit increments between a floor and a ceiling, and the floor can be 0, at which point it pauses and resumes in roughly 15 seconds. The Azure SQL Database serverless tier does the same between minimum and maximum virtual cores, with the documented caveat that auto-pause needs a database using no long-running feature. Autonomous Transaction Processing scales instantly on Oracle's own billing unit, with compute autoscaling on by default up to three times the provisioned figure and storage autoscaling off by default, which is a billing surprise worth knowing before it arrives.

Google Cloud has no true serverless relational tier, and the reason is specific rather than a shrug. Spanner bills in provisioned processing units, AlloyDB autoscales read pools with a floor of one node, and Cloud SQL Enterprise Plus autoscales read pools too. All three are elastic. None of them scales to zero, which is the property this row is about. Reading that as "Google Cloud cannot run a relational database elastically" would be wrong in a way that changes a design.

3. One global SQL image, three different bargains

Three clouds sell a relational database that spans regions. They are not the same product with different logos, because each buys global consistency with a different currency, and the currency is what your application feels.

Spanner orders transactions with TrueTime and presents one globally consistent relational database. Aurora DSQL reaches the same promise with an active-active design and optimistic concurrency, so a write conflict surfaces at commit rather than as a row lock, and its published availability is 99.99 per cent in one region and 99.999 per cent across regions. Globally Distributed Autonomous Database takes the other road: shared-nothing shards that each hold a subset, one logical database to the application, with data residency per region as the headline use case. Azure has no equivalent on this row. Cosmos DB is globally distributed, but it offers tunable consistency over a NoSQL model rather than one strongly consistent SQL image, which is a different product answering a different question.

4. Two rows that live inside another product

Continuous replication of database changes into another store is sold as its own product by two clouds and delivered inside another product by two. Google sells Datastream and Oracle sells OCI GoldenGate. On AWS the same capability is the ongoing-replication mode of Database Migration Service, and on Azure it is the online mode of its own migration service plus change data capture in Data Factory and Fabric.

The reframing A cell that says delivered elsewhere and a cell that says no equivalent look adjacent in a table and mean opposite things. The first says the cloud has the capability and names where it lives. The second says the cloud ships nothing. Change data capture on AWS and Azure is the first kind, and a design that avoided those two clouds because the row looked thin would be avoiding a capability they both have.

The migration row itself carries a real difference worth knowing. AWS and OCI both cover heterogeneous migrations, where the source engine and the target engine differ, and AWS pairs its service with a separate schema-conversion tool for that case. Google's Database Migration Service is homogeneous only, moving MySQL, PostgreSQL and SQL Server into their managed counterparts.

5. Where a row is genuinely empty

Three rows carry an absence recorded by the audit rather than assumed by a table.

Time-series. AWS sells Timestream and Azure answers with Azure Data Explorer. Google Cloud has no dedicated managed time-series product and documents Bigtable as the pattern instead. OCI has none either, and points at its monitoring metric store, which is platform telemetry rather than a database you put your own measurements in.

Ledger. Azure sells confidential ledger, a tamper-evident append-only store inside hardware enclaves. Oracle sells a multi-party blockchain platform, and notes that its closer single-party analogue is blockchain tables inside an ordinary Autonomous Database. Google Cloud has no managed ledger product. On AWS this row is a warning rather than an answer: QLDB is shut down, and Managed Blockchain is not its replacement, because a multi-party permissioned network solves a different problem from a single-owner verifiable journal.

Fleet management. Neither AWS nor Azure ships one console covering the health of every database engine in an estate. On AWS the per-engine view is the RDS console with CloudWatch and Performance Insights beside it. Google's Database Center is in preview, and OCI Database Management reaches across Autonomous, Base, Exadata and on-premises databases through an agent.

One more label is worth reading as carefully as an absence. Where two services sit in one cell, the badge on the name says which one a new design should pick: Azure Managed Redis is current and Azure Cache for Redis is retiring. AWS splits the same row differently, between ElastiCache as a cache and MemoryDB as a durable primary database, which sounds like two cache tiers and is not.

6. What this certification tests

Databases are a named domain on the Oracle architect professional blueprint, which lists Architecting, Implementing, and Operating Databases in OCI at 20 per cent of the exam and names Autonomous Database, the globally distributed form and OCI Cache inside it (1Z0-997-26 exam page). On Azure the same ground sits inside Design data storage solutions at 20 to 25 per cent, whose sub-objectives name relational tier selection and the balance between semi-structured and unstructured data (AZ-305 study guide). Both descriptions are decision-shaped rather than product-shaped, which is exactly what section 2 and section 3 above are about.

Check yourself

Retrieval practice

Answer from memory before revealing.

A workload runs a small PostgreSQL database that is idle every night and busy for four hours a day. Which property decides the cloud?
Idle for twenty hours a day is exactly the case auto-pause exists for, and it is the one property this row is not uniform on. Engine version is not the discriminator, because all four run community PostgreSQL. Cross-region replicas answer a durability question this workload did not ask. And an availability figure does not change the bill for twenty idle hours.
The change data capture row says "delivered elsewhere" for AWS and Azure. What should a reader conclude?
Delivered elsewhere means the capability exists and lives inside a product with its own row, which here is the database migration service on both clouds. The first option is the error the state exists to prevent, and it is the opposite of the truth. Nothing in the state says anything about a release schedule. And the engine restriction in the third option is invented: it is not what the cell records.

Practice about 15 minutes, with paper

Practice 1working

A retailer must keep each country's customer rows inside that country, and wants one application talking to one logical relational database rather than four connection strings. A second team on the same platform wants a globally consistent order ledger where a write in one region is immediately visible in every other.

Decide which of the three globally distributed offerings fits each of the two requirements, name the design decision each choice forces on the team, and say which of the four clouds cannot answer either requirement on this row and why.

Hint

The two requirements pull in opposite directions. Data residency wants the data pinned by key, and immediate global visibility wants agreement before the commit returns. Ask which of the two bargains in the sequence diagram each requirement is really asking for, then read what that bargain costs.

Show the worked solution
  1. Match the residency requirement. Rows pinned by country is a sharding problem, so the fit is a shared-nothing sharded database presenting one logical image, which is the Globally Distributed Autonomous Database shape on OCI.
  2. Name what that forces. The sharding key. It has to be the attribute that decides the country, it is transparent to the application only while queries stay inside a shard, and changing it later is a data migration rather than a setting.
  3. Match the ledger requirement. Immediate visibility everywhere is one strongly consistent image, so the fit is Spanner or Aurora DSQL.
  4. Name what that forces. Latency, and on Aurora DSQL a concurrency model too: optimistic concurrency means a conflicting write is rejected at commit time, so the application needs a retry path rather than a lock wait.
  5. Name the cloud that cannot. Azure, which carries no equivalent on this row. Cosmos DB is globally distributed but offers tunable consistency over a NoSQL model, so it is not one strongly consistent SQL image.

Sanity check. The two answers must be different products, because the two requirements ask for opposite things. If one product came out as the answer to both, re-read step one: a database that agrees every write across regions is not pinning any row to a country, and a database that pins rows by key is not making a write in one shard immediately visible in another.

Your teacher. When you are handed a database comparison, ask two questions before the engine names: does the capacity model reach zero, and is the consistency promise made across regions or inside one. Those two answers rule out more options than any feature list, and they are the two an engine name never tells you.
