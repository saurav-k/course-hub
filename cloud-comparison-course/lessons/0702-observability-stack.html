The observability stacks differ in their defaults, not in their shape

working 9 min Capability area observability, 12 rows of the capability matrix: telemetry-agent, metrics-store, log-store, managed-prometheus, distributed-tracing, dashboards, alerting, synthetic-monitoring, error-reporting, profiler, network-diagnostics and service-health-dashboard.

The one-minute version

  • Twelve capabilities, one shape: feeds carry telemetry in, stores hold it, surfaces let a human act on it.
  • All four clouds fill nine of those twelve boxes with a product. Read the shape first and the brand names second.
  • What actually separates them is how long a data point survives at the resolution you collected it at, and that is a design constraint rather than a preference.
  • Three of the twelve are not four-way. In one of them a cloud has the capability inside another product, and that is a different finding from not having it.

1. Twelve capabilities, three jobs

The agent is the least interesting box on that map and the most quietly different. AWS ships two collectors, its OpenTelemetry distribution beside the unified CloudWatch agent (ADOT). Google Cloud folds logs and metrics into one Ops Agent. Azure's Monitor Agent is one binary whose behaviour is set centrally by data collection rules, so what a machine sends is a property of a rule rather than of the machine. OCI's Management Agent covers cloud and on-premises hosts and also scrapes Prometheus endpoints.

2. The number that shapes the design

The stores are where a comparison stops being a name-matching exercise. Every cloud will hold a metric for a long time. The question that decides whether you can debug last month's incident is how long it holds that metric at the resolution you collected it at.

CloudWatch metrics take one-minute points as standard, or one-second at high resolution, and roll them up: one-minute points are kept fifteen days and hourly points four hundred and fifty-five. Azure Monitor keeps free platform metrics at one-minute cadence for ninety-three days. Cloud Monitoring keeps its named service families for twenty-four months but only about six weeks of that at the original sampling frequency, after which the series becomes ten-minute points. OCI's Monitoring service holds service, custom and connector-derived metrics and is queried in Oracle's own metric query language; the retention figure was not recorded in the research this course rests on, so it is not printed here.

The log stores diverge in the same way and more sharply, because a log store's default is what a team inherits when nobody chose. CloudWatch Logs never expires a log group by default, which is a bill rather than a gap. Log Analytics gives every table one of three plans, and the plan decides not only the ingest price but whether querying is charged by the volume it scans. Cloud Logging splits the difference structurally: the required bucket holds four hundred days and cannot be changed, while the default bucket holds thirty. OCI Logging puts audit, service and custom logs into one store organised as log groups, with retention set on the log.

The reframing Nobody chooses a cloud for its retention default, and everybody inherits one. Write down the two numbers you need - how far back at full resolution, and how far back at any resolution - before you read a single vendor page. They turn a feature comparison into a two-column check.

3. Three capabilities that are not four-way

Error reporting. Only Google Cloud sells it separately: Error Reporting groups exceptions out of ingested logs into counts with first-seen and last-seen tracking. Azure has the capability and delivers it inside Application Insights, whose failures view groups exceptions by problem identifier. AWS and OCI are the genuine absences, and the research records why in the same words for both: error rates and raw stack traces are visible, but nothing deduplicates them into tracked issues.

Profiler. Cloud Profiler covers Java, Go, Node, Python, .NET and Ruby continuously in production; AWS answers with Application Signals alongside CodeGuru Profiler for JVM flame graphs; Azure's profiler is a real product with a narrow surface, .NET only. OCI has no cross-language continuous profiler, and the nearest capabilities recorded are Java-only.

Managed Prometheus. AWS, Azure and Google Cloud each sell a Prometheus-compatible store queried with PromQL. OCI does not. It is precise to say that Prometheus metrics still arrive on OCI - the management agent scrapes those endpoints into the Monitoring service - and that what is absent is the PromQL-queryable store, because the metrics land in a service read with Oracle's own query language.

4. Same box, different filling

CapabilityThe difference worth carrying
AlertingAWS composite alarms combine alarms with boolean expressions to cut storms; Google Cloud can alert on a service-level-objective burn rather than a threshold; OCI alarms are written in its metric query language; Azure adds dynamic thresholds.
DashboardsAzure ships three layers - portal dashboards, workbooks and managed Grafana - plus curated packs per workload. The other three ship one dashboard object each.
Distributed tracingAzure, Google Cloud and OCI are OpenTelemetry-native. AWS X-Ray keeps its own segment model, where annotations are indexed and metadata is not - a difference you meet the first time a trace search returns nothing.
Synthetic monitoringAWS canaries run scripted browsers as often as once a minute; Azure standard availability tests are URL probes; Google Cloud probes from several geographies; OCI splits scripted monitors from lightweight health checks.
Network diagnosticsNetwork Intelligence Center gathers connectivity tests, firewall insights and flow analysis in one console. AWS, Azure and OCI ship the same functions as separate analyzers.

What this certification tests

Observability is one of five equally sized domains on the Oracle architect professional blueprint: Implementing Observability Solutions carries twenty percent, and its objectives name Monitoring, Alarms, Notifications, metric queries, Logging and Connector Hub explicitly (exam topics). On Azure it is folded into the twenty-five to thirty percent Design identity, governance, and monitoring solutions domain, whose objectives include recommending a logging and monitoring solution (skills measured). Google Cloud names Ensuring solution and operations excellence at about twelve and a half percent (certification page).

Check yourself

Retrieval practice

Answer from memory before revealing.

The matrix marks Azure's error-reporting cell DELIVERED ELSEWHERE. What does that entitle you to conclude?
Delivered elsewhere means the capability is present inside a service that holds its own row, which here is Application Insights and its failures view. The second option is the reading reserved for NO EQUIVALENT, and applying it here would be exactly the error this matrix is built to prevent. The first invents a third-party dependency. The fourth would make it a service cell rather than a cross-reference.
You must answer one-minute-resolution questions about traffic from ten weeks ago, using platform metrics only. Which cloud still has them?
Ten weeks is seventy days, and only Azure is still at one-minute resolution there. The second and third options quote the real long numbers and hide the rollup: AWS keeps one-minute points fifteen days before the hourly series takes over, and Google Cloud keeps about six weeks at original sampling before ten-minute points do. The fourth repeats that mistake for all three at once.

Practice about 15 minutes, with paper

Practice 1working

A team runs one service on each of the four clouds. They want three things: exceptions rolled up into tracked issues, continuous CPU profiling of a Go binary, and PromQL over their own application metrics.

Work out, cloud by cloud, which of the three they get from a first-party product, which they get from inside another product, and which they must build or buy. State your answers as sentences a reader could not misread as an absence.

Hint

Two of the three requirements are answered by a product on three clouds and not on one - but it is not the same cloud both times. Work the profiler row by language rather than by product name.

Show the worked solution
  1. Exceptions, Google Cloud. A first-party product, Error Reporting, which groups them out of ingested logs.
  2. Exceptions, Azure. Present, inside Application Insights, whose failures view groups by problem identifier. Say "inside Application Insights", never "Azure has no error grouping".
  3. Exceptions, AWS and OCI. No product groups stack traces into tracked issues. Error rates and raw records are available, so the team builds the grouping or buys it.
  4. Go profiling. Google Cloud covers Go in Cloud Profiler, and AWS covers continuous profiling through Application Signals with CodeGuru Profiler for the JVM. Azure has a profiler but it is .NET only, so this Go binary is not covered. OCI has no cross-language continuous profiler and its nearest paths are Java only.
  5. PromQL. AWS, Azure and Google Cloud each sell a managed Prometheus store. On OCI the metrics still arrive, scraped by the management agent into Monitoring, but they are read in Oracle's metric query language, so a PromQL dashboard is the piece that does not exist.
  6. Count the gaps honestly. Three genuine absences - grouping on AWS and OCI, a PromQL store on OCI - and two facts that look like absences and are not: Azure's grouping lives in another product, and OCI does ingest Prometheus metrics.

Sanity check. OCI should come out shortest on all three rows and Google Cloud longest, and your Azure sentences should contain the words "inside" and "only .NET" rather than the word "no". If any sentence reads "cloud X cannot", check it against the two findings in the last step.

Your teacher. The habit worth building here is reading a retention figure as two numbers rather than one. Every vendor quotes the long number, because it is the flattering one. Ask an agent for the resolution schedule behind any retention claim it makes, and treat a single number with no schedule as an unanswered question.

Primary source to go deeper

The Cloud Monitoring quotas page is the most explicit retention schedule any of the four vendors publishes, because it states the downsampling steps rather than only the outer bound. Read it once and you will never again accept a bare retention number from any cloud.
